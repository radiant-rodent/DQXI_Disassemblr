# A_map_ui — readable native-code coverage map

## What I did

The old `progress/progress.svg` was 836 px wide with 4 px cells and put 18,518 of 18,787
functions into one grey `General_Procedures` block. Opened directly it left most of the browser
window white and the population was impossible to navigate.

### New interactive page: `progress/map.html`

Self-contained HTML/CSS/JS, no external libraries, no network requests, dark page (`#0b0f16`) with
no max-width container:

- **Responsive canvas**: the map is drawn with `<canvas>` and fills the window from 375 px to 4K.
  Cell size scales with width (4 px below 480, 5/6/7/9/11 px through the breakpoints, 13 px above
  3200). Canvas backing store respects `devicePixelRatio` (capped at 2) so cells stay crisp.
- **Layout**: the 11 known subsystem blocks stay at the top (Audio, Battle, Camera,
  Actors_and_Entities, UI_and_Message, Memory_and_Heaps, Save_and_Persistence, Field_and_World,
  Input, Kernel_and_System, IO_and_Files). The functions with no subsystem match
  (`General_Procedures`, 18,518 of 18,787 when the task started and 18,404 at the final run as
  naming proposals reclassified some) are split into **99 labelled 64 KiB address rows**
  (`0x0010xxxx` … `0x0072xxxx`), with each row's first/last address, function count and named
  count. Cells wrap inside each row, so narrow screens get more visual lines rather than 1 px
  cells.
- **Embedded JSON**: all 18,787 functions are in one compact positional array
  (`[address, name, size, status, domain, summary, readablePath]`) and ~1.4 MB of `map.html` is
  the JSON. Section metadata is embedded too. No fetch, no external data file.
- **Hover tooltip**: address, effective name, size in bytes/KiB, state, subsystem, and the
  summary when one exists. A white hover ring shows the exact cell. Hidden states are not
  hoverable.
- **Click**: opens `../decomp/readable/<path>` in a new tab (18,748 cells have a readable C twin;
  the 39 covered/unresolved entries do not). Works on `file://` and through the board server.
- **Filters**: the legend is also the state filter — five checkboxes (unnamed / proposed / named /
  documented / matching C) each with the real count. Unchecking hides that state.
- **Search**: by function name, address (`0x00123456`), address range (`0x0012xxxx`) or subsystem
  name. Non-matches are dimmed to 12% opacity and matches get a white outline; the match count is
  shown and Enter scrolls to the first hit.
- **Optional size weighting**: "weight cells by function size" grows the filled square inside each
  fixed grid cell using a log scale, so large functions stand out without breaking hit testing.
- **Legend/nav**: all generated HTML pages share the same nav; "Coverage map" now points at
  `map.html` and the static SVG is linked as "Coverage SVG". The overview's map image also links
  to `map.html`, and the generated footer explains the canvas page (no external scripts/network).

### Board server: read-only readable C

`orchestration/live.py` gained one route:

- `GET /decomp/readable/<relative path>` → the file as `text/plain; charset=utf-8`, restricted to
  `decomp/readable` after `resolve()` (encoded `../` traversal is rejected with 404; missing files
  are 404 rather than falling back to the worker-board HTML).
- The worker board header also links `/progress/map.html`.

### Static SVG kept for badges/README

`progress/progress.svg` is still generated with the same subsystem blocks, but now:

- `width="100%"` with `height:auto`/dark `background` and a full-size `<rect fill="#0d1117">`, so
  opening it directly no longer shows a white page around an 836 px map;
- numeric entities only (`&#183;`, `&#8211;`), no named entities;
- a small "hover/search: progress/map.html" hint.

## Open problems / not verified

- **Mouse-only hover**: the tooltip is driven by `mousemove`; there is no keyboard cell navigation
  or focusable list equivalent. Clicking still works with a tap only where the browser synthesises
  a click; I did not test a real 3DS-era browser or a touch device.
- **File size**: `map.html` is ~1.4 MB because the whole function table is inline as required.
  Browsers handle it fine locally, but it is not a lightweight README asset — that is what
  `progress.svg` remains for.
- **Static SVG still shows one `General_Procedures` block.** I intentionally kept its compact
  shape for badges/README. Only the interactive page got the 99 address rows.
- **README is now slightly stale**: it still links "Coverage map" to `progress/progress.svg` and
  says the pages have no JavaScript. I did not edit it because it is outside this task's owned
  files; the generated pages themselves are consistent.
- Counts in the snapshot (622 named, 1.1% documented) are a point in time; concurrent `N_*`
  workers were adding proposals between runs. Rerun `python tools/progress.py` for current data.
- The 39 covered/unresolved entry points have no readable C twin, so their cells have no click
  target (the tooltip still shows their address/name/state). This is honest rather than linking to
  a wrong file.
- The board route has no caching or range support; fine for a local read-only viewer, not a CDN.
