## What I did

1. Read `README.md`, `orchestration/WORKER_RULES.md`, `orchestration/PLAN.md`,
   `orchestration/tasks/G_002.md`, `tools/typedb/common.py`, `tools/typedb/apply.py` and the
   readable C for every function named in the batch.
2. For every one of the 90 addresses I:
   * dumped the 64 bytes at the address and classified every word (text pointer, rodata/data/bss
     pointer, float, zero);
   * matched the address against `orchestration/types/structs.json` (1,930 recovered classes and
     2,103 recovered vtables) to identify vtables and class types;
   * resolved every literal slot in `literals[]` through the retail image (`tools.typedb.common`)
     and read its use sites in `decomp/readable/functions/*.c`;
   * did a reverse lookup (all image words holding the address) to find writers as well as readers —
     this is how the BSS "class type tokens" and the lazy-init records were identified.
3. Wrote `orchestration/types/out/G_002.json` as one JSON object per global with
   `address/name/type/comment/confidence/evidence`.

Key findings that shaped the names:

* The batch mixes **five different kinds of objects**:
  * real scalar/string globals (`g_actorDefaultAnimName`, the UTF-16 debug format strings, the
    `.data` float constants, the BSS tables);
  * **C++-style vtables** and **`{create function, vtable}` class descriptors** in `.rodata`
    (items around 0x007259xx..0x0077D198) — these are the bulk of the batch (44 entries);
  * **class-type tokens** in BSS: addresses that are compared against the first vtable slot as a
    class id (`g_actorRttiTokenB/C`, `g_fieldTwoPartObjClassToken`, `g_gfxModelPartClassToken`,
    the jump target tokens, …);
  * **lazy-init records** `{flag, pointer}` for the motion and handle tables;
  * **one false object** (0x0074756E): the "literals" that resolve there are the addresses of the
    inline ASCII string `"nut\0"` (0x00177D20 / 0x0018024C / 0x001816FC). Reading those four bytes
    as a little-endian word gives exactly 0x0074756E. This entry is named
    `maybe_g_rodata_74756e` with confidence 0.10 and a comment that says not to use it. It is
    reported as noise rather than invented as a global.
* The `structs.json` vtable start is often 4 or 8 bytes after the batch address because the first
  word is a factory/code pointer or the Itanium-style offset-to-top word. Names were derived from
  the **constructor that installs the pointer** plus the slot names in `structs.json`, not from
  the address alone.
* Items 11–13 are the small `std_StateSequence` vtables (leading 0 + 6 slots), which is why their
  types are `void*[7]`, not the usual 11-word actor-action vtable.

## Confidence / honesty notes (what is NOT verified)

* **Vtable ownership**: the class names come from `structs.json` (heuristic vtable slot runs) and
  the ctor that stores the pointer. For a few vtables (items 39, 52, 53) two candidate classes share
  the slot names, so the names are hedged (`maybe_...` or `*B` suffixes). The slot counts are
  derived from the contiguous text-pointer run and are not from RTTI metadata.
* **`{create function, vtable}` descriptors** (items 2/14/15/17/20/28/29): the first word is a code
  pointer that Ghidra has not named; I call it a factory because the surrounding ctors use it that
  way, but its exact role is not proven. Array lengths for those descriptors are the vtable length
  plus the two header words; the inventory's `array_bytes` (0x9C/0xA0/0xD8) sometimes includes the
  start of the next object, so I did not blindly copy it.
* **`.data` floats 0x007A3ED0/0x007A3F44/0x007A3F4C** are zero in the retail image and multiplied
  into speeds/rotations at runtime; the writers are class-registration code that writes through a
  parameter-block pointer, so the initial values are not visible in the image. The purpose names are
  therefore `maybe_` at 0.40.
* **BSS class tokens 75/77/78/84/85/86/87**: the reader and the compared field are certain (e.g.
  `+0x297`, `f_B2`, jump map/locator fields); the concrete class name is not, so they are
  `maybe_g_actorBookIdClassToken*` / `g_actorJumpInfoClassToken` / `g_*JumpTargetClassToken`.
* 0x007C4244 is typed `u32[18]` because `Actor_GetDefaultMotionId` selects a second 0x24-byte record
  at +0x24; the inventory only reported 0x28 bytes of read evidence.
* 0x007CCAA0 is used both as an action-sequence request buffer (0x11C bytes) and passed with size
  0x400 to a text/icon routine; it is named as a **shared scratch buffer**, not as a game state.
* Nothing here was checked against the emulator or hardware. No claim is made that renaming these
  globals changes any behaviour; `apply.py` only emits declarations/comments.
