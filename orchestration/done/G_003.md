## Method

1. Read `README.md`-level rules, `orchestration/WORKER_RULES.md`, `PLAN.md`, and the task brief.
2. For every global: resolved the batch `literals` back through the retail image
   (`original/exefs/code.decompressed.bin`, VA = file offset + 0x00100000) and dumped the real
   object bytes, not just the batch summary.
3. Interpreted each word of every table as a code/data pointer, mapped the code pointers to the
   merged function names (`decomp/readable/**`) and to their owning classes from
   `orchestration/types/structs.json` (`vtables`, `functions`). This is what decided most names:
   e.g. `0x007629E4`'s word 1 is `maybe_Field_Action_Nut_DeletingDtor`, so it is the
   `Field_Action_Nut` table, not the generated `maybe_Anim_CreateVariantA`.
4. Read the full readable C of the user functions (`maybe_Anim_Instance_ApplyTemplate`,
   `Anim_FormatMotionPackPath`, `Anim_Sequence_CtorBase`, `Anim_Instance_CtorSprite`,
   `Anim_ModelLoad_ByName`, `maybe_Anim_Instance_Ctor`, `Anim_UpdateAttachTrack`,
   `Anim_UpdateModelInstance`, `Anim_SetupNamedTrackList`, `Anim_Clip_Start`, ...) and the three
   functions that contain the otherwise-orphaned literals `0x00124F5C`, `0x00160DB0`,
   `0x001BBBFC` (`Fs_ResourceFindByName`, `maybe_Math_BuildTransform44`,
   `maybe_Ui_AddResourceEntry`).
5. Cross-checked `structs.json` vtable lists (`Ui_ListWindow`, `Anim_AnimClip`, `Anim_ClipSlot`,
   `Field_Action`, `Ui_Anim`, `std_StateSequence39/40/64/65`) and computed every table length by
   scanning words from the install address to the last code pointer (same convention as G_001).

Key engine facts that shaped the answers:

* Most of this batch is **method tables (vtables)**, not scalar globals. The install address is
  word 0 of the table and slot *i* is dispatched through `*(vptr + 4 + 4*i)` (G_001 documented
  the same convention). Several tables therefore start with a 0 word
  (`0x0075AB34`, `0x0075D3E8`, `0x007615A4`, `0x0076160C`, all `Field_Action` tables) while others
  start with the complete destructor (`0x0075D434`, `0x0075E360`, `0x00760568`, `0x007815D8`).
  `structs.json`'s `slot_count` only sees the consecutive code-pointer run, which is why it is 2
  for `0x0075E360` / `0x007815D8`; I counted through the last code pointer as G_001 did and said
  so in the comments.
* `0x0072D754` is a real integer table: `Anim_FormatMotionPackPath` indexes it by the animation
  kind (switch cases 0..5) and returns early if `table[kind] <= motionId`; the six values are
  2,1,4,1,1,1.
* `0x007A6888` is a **null function-pointer hook** in `.data` (called as
  `(*(code *)*g_0029eaf4)(&out, f24, f24[1])`), followed by the nine 9-slice anchor name strings
  (LeftTop/Left/LeftBottom/Top/Center/Bottom/RightTop/Right/RightBottom) and `0x4EE`; no writer in
  the readable tree, so it is registered at runtime outside these functions or stays unused.
* `0x007B6D70` / `0x007B6D74` are the two rotating counters of `Anim_ModelLoad_ByName`: a
  0..0x1FF free-slot cursor into a 0x200-entry table at `g_004d2a8c`, and a 22-bit id counter
  (mod 0x3FFFFF via a magic multiply) packed into the object as `id << 10`.

## Type decisions

* Method tables are `void*[N]`, with `N` counted from the install address through the last code
  pointer (`void*[2]` for a pure destructor pair). This matches the dominant convention in the
  other G outputs (132 `void*[N]` entries) and makes `include/dqxi/globals.h` emit
  `extern void* g_x[N];`.
* `g_animClipSpriteBuilder` is `void*`, **not** `void (*)(void)`, even though the task allows the
  latter: `tools/typedb/apply.py:write_headers` emits `extern <type> <name>;`, which would produce
  the invalid C `extern void (*)(void) g_x;`. `apply.py` also has a `FNPTR_RE` used only by the
  validator, so the pipeline is inconsistent here. The comment keeps the exact call signature.
* `0x00782564` is `char[16]` (a 16-byte all-zero block immediately before `0x00782574`, of which
  only the first word is copied into the `%03d` suffix buffer) and `0x0072D754` is `u32[6]`.
