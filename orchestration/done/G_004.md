## Method

1. Read `README.md`, `orchestration/WORKER_RULES.md`, the task file and the batch. The previous output file
   was absent, so all 300 globals are new work.
2. Read the retail bytes at every batch address (`original/exefs/code.decompressed.bin`, VA − `0x00100000`,
   via `tools.typedb.common`), decoded as words / floats / ASCII, and walked the 12 following words to
   recognise vtables (`slot 0` header or destructor, later slots `.text` pointers).
3. For every `.text` literal slot in `literals[]`, searched all readable `.c` files for the `g_XXXXXXXX`
   token and read the surrounding statements (the batch `samples[]` show only 1–4 of them).
4. Resolved vtable slots through `symbols.json` (function address → name, including `+0xNN` offsets) and
   cross-checked `orchestration/types/structs.json` (class → vtable, size, slot list). Eight classes were
   confirmed that way: Battle_PopupEntry, Battle_TextWindow (two tables), Battle_AnimWindow,
   Battle_HpGaugeWindow, Battle_Actor, Battle_Action_SpecialMove, Battle_Ui, Gfx_Scene/Battle_PopupPool.
5. For the 93 globals used by `Battle_ActionAnimWindow_Init`, parsed that 1,492-line readable function and
   matched each literal to the **state-name string** that `Battle_ActionAnimWindow_Init` registers just
   before it (`s_avoid`, `s_escape`, `s_vanish`, `s_sleepStart/Loop/End`, `s_guard_s/w`,
   `s_pre_move_1..4`, `s_move_back_1..4`, `s_post_move_1..4`, `s_approach_1..4`,
   `s_sp1Start..s_sp25End`). That gives an exact `start`/`loop`/`end` name for 75 Sp* tables plus the four
   movement families, instead of guessing from slot names. (Two literals register the base name
   `s_battleact`; they are the action-table slots 3/4 and are named by slot index instead.)
6. Only then wrote names. Confidence is the naming confidence, not the type confidence; below 0.50 the
   name is prefixed `maybe_` as the task requires.

## Findings worth knowing

* **225 of the 300 objects are vtables.** The block layout is `slot 0` (0 or the class destructor), `slot 1`
  the deleting destructor, then the virtual methods; later slots belong to base classes. The `u32`/`void*`
  declarations are the measured extent up to the first non-pointer word (two objects are interior aliases of
  one 0x30-byte block and are declared with their full extent: 0x0076C4DC/0x0076C4EC and
  0x007728A8/0x007728C4).
* **`0x0072AD60` is a 37-pointer table of BCH model names** `n4101a.bch … n4103o.bch`; the `size_hint 0x94`
  comes from `std_memcpy(local_120, g_004c4780, 0x94)` in `Battle_TextWindow_LoadTextureSet`.
* **`0x007A7800` is a 3-entry pane-name table** (`icon_target_3d`, `icon_target_2d`, `gau_hp_bar2`), not a
  single string. **`0x007AE19C` is a 78-entry table of `gim_*` icon/model names** indexed by a unit's status
  byte (guard `unit[3] < 0x4E` in `maybe_Battle_Action_CheckStatusCondition`).
* **The target-marker/UI geometry lives in overlapping float tables**: `0x00726EA4` is a 26-float table
  (`1.0, 2.5, 330, -310, 130, 210, …`) and the batch addresses 0x00726EA8/0x00726EAC are entries inside it;
  `0x007A60D0` (5 factors) and `0x007A60E4` (5 group factors) are the two halves of the target-panel block.
  They are declared as separate objects so no declaration covers the next batch global.
* **String lengths matter:** `'_2way.pack'` is 10 chars + NUL (`char[11]`), `sp10_end…sp16_end` are 8 chars
  + NUL (`char[9]`), `0x007BFC18` is the NUL padding byte *before* `pre_move_1` (declared `u8[2]`, low
  confidence).
* **`0x00796873` is not code and not text**: unaligned, non-pointer bytes passed by address as the parameter
  block for action-table slot 0x9F, so it is named `maybe_g_rodata_00796873` on purpose.
* **`0x007B6D78`** is the header of an open-addressed 8-byte-entry handle table (`(id & mask>>12)*8 + 4`),
  used by `Anim_ModelLoad_ByName` and UI message code; the entries follow the header at runtime.

## Open problems

1. **Duplicate writer for one lane.** A second session wrote `G_004.json` while this lane ran; the last
   writer wins silently. The dispatcher should refuse a second worker for a lane whose output file exists and
   is newer than its batch, or take a lock.
2. **`maybe_g_*` vs `apply.py`.** `merge_globals` historically called `check_identifier(name, prefix="g_")`,
   which rejects `maybe_g_...`. The task prescribes that spelling below 0.50; G_002 used `g_maybe_`. The
   current `apply.py` was since relaxed, but M3 should normalise one form.
3. **Vtable lengths** are exact where the next non-pointer word or `structs.json` proves them; for the
   `battleact` action table the length is the measured leading pointer run. A refine pass could compare with
   `structs.json:classes[*].vtables[*].slot_count` once more classes are named.
4. **Low-confidence names (37).** Mostly the UiFlow window tables of generic Ui classes (named after the
   opener + slot 1/2 function), the four `Field_*`-named action-anim elements, the float-literal pool, and
   the two zero target-slot descriptors. They are deliberately vague rather than precise-but-wrong.
5. **Not verified in game.** Every name is static evidence only; no emulator/3DS run was made (not needed for
   a naming batch), and no merge has been executed.
