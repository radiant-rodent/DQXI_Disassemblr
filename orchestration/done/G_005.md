### Load-bearing findings

* **The engine's C++ RTTI nodes are 20-byte static blocks in `.bss`.** The helper the
  earlier passes named `maybe_Ui_TextWidget_Ctor` (0x002A55EC) is really the
  **class-registration** routine: it self-links the node (intrusive list at +0/+4/+8),
  stores the **parent class** at **+0xC** and the **class-name string** at **+0x10**.
  Verified against the already-named `Field_RegisterActorClass_EnemyActor` (0x0067C498:
  node 0x7C3684, name "EnemyActor", parent 0x7C4324). This turned five anonymous BSS words
  into certain identities:
  - `0x007C428C` = **"EnemyBattleActor"** (parent `0x007C33D4`)
  - `0x007C42A0` = **"EnemyBattleActor_Nizuzerufa"** (parent 0x7C428C)
  - `0x007C4E14` = **"AttachVehicleActor3D"** (parent `0x007C33D4`)
  - `0x007C5014` = **"PlayerBattleActor"** (parent `0x007C33D4`)
  - `0x007C33D4` = the **parent of all of them** → the base actor class, read by 134
    functions as an "is this an actor?" test, after which they touch the transform at
    +0x9C..+0xA4 (`obj->f_9C` in the readable C).
* **`0x007C5120..0x007C5174` is one table of 12-byte (3-float) vectors.** The layout
  initialiser fills entries 0..6 with `(0,0,0)`, `(0,0,0)`, `(-5.4,0,-2.33)`,
  `(5.48,0,-2.32)`, `(-3.51,0,4.66)`, `(3.52,0,4.62)`, `(0,0,7.24)`; entry 7 belongs to
  G_017. `BattleScene_ApplyUnitSlotTransform` picks slot *N* by `index == N`
  (index 0 → 0x7C5150, 1 → 0x7C5144, 2 → 0x7C5138, 3 → 0x7C515C, 4 → 0x7C5168), the
  slide-in routine uses 0x7C512C as the fixed first-unit position, and
  `maybe_BattleScene_LayoutUnitModel_2` reads the **y** of 0x7C5120 as the unit height
  (`piVar1[0x28] = *(int *)(0x7C5120 + 4)`). Hence `g_battleLayoutOrigin`,
  `g_battleEntryPosition`, `g_battleUnitSlotPos0..4`.
* **The 59 `sp*_start/_loop/_end` strings are model clip names.** Each is the sole
  argument to `(**(code **)(*self->f_28 + 0x84))(self->f_28, <string>)` in exactly one
  `Battle_Action_SpecialMove_Sp*_Play` thunk, so the names follow the function
  (`g_battleClipSp17End`, …) and the type is `char[len+1]`.
* **The 8 `%`-strings are two duplicated format sets** used by
  `BattleScene_BindUnitModelResources`: `"sp%s"` + `"%s.ani"`/`"%s.bxon"`/`"%s.bch"`
  build the per-part resource paths of the 47×6 loop; the second identical set
  (`…B` names) is the unit-400 ("m210b") extra pass.
* `0x007C4304` = 3-float placement offset seeded to `(0, 0, -6.5)` by the
  EnemyDesertWhale class registration and consumed by
  `maybe_Battle_CameraRangeBlend_Update`; `0x007C5180` = 8 float *pairs* indexed
  `+i*8` by `maybe_Battle_Ui_UpdateScrollAnimation`; `0x007C8578` = last node of the
  static 0x58-byte actor-list pool built by `Field_InitActorListNodePool`.

  `0x7E7000..0x7E703C` are the "default basis/default orientation" block that constructors
  copy into new transforms (several pre-existing notes in `symbols.json` call 0x7E7000 the
  identity orientation and 0x7E7030 a negated axis), but **I did not find the startup code
  that writes them** and I cannot prove which axis this particular one is. It is used
  negated in `Math_ClampPointToBox` and in effect-spawn code.
* `0x007E2164` (`maybe_g_modelClass`): proven to be a type-info node checked after
  model/animation loads (and the target of `maybe_Class_IsInstanceOf`), with parent
  0x7E2000 and code pointers 0x576E90/0x576CBC at +0x10/+0x14 — but the class *name* string
  is set at runtime, so "model (animation) instance" is the meaning, not a factory name.

  battle/gfx functions that look generic (aura/composite/LOD updates, effect forwarding)
  test against it. Either those are per-boss duplicates with misleading recovered names,
  or the string belongs to a sibling node — flagged in the record's evidence.

  described here for entries 0..6.
* Descriptor layout knowledge (20 bytes, +0xC parent, +0x10 name) was **not** applied to
