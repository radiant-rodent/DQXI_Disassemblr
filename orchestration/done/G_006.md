## Result

| address | name | type | conf |

| `0x007275DC` | `g_bg2dLayerPageSearchOrder` | `u8[8]` | 0.70 |

Retail bytes (rodata, verified in `asm/rodata/rodata_00725000.s`):

```
0x007275DC: 01 02 03 00      -> row A: 1,2,3,0   (successor ring)
0x007275E0: 03 00 01 02      -> row B: 3,0,1,2   (per-layer first choice)
```

### How it is used (from the real ARM code, not the pseudocode)

`Bg2D_ResolveLayerTextures` (0x0061CDC8) loads both words through literal slot `0x0061CF50`
(`ldr r0,=0x007275DC`, `ldr r1,[r0]`, `ldr r0,[r0,#4]`) and spills them to `sp+4` / `sp+8`.
Its outer loop walks four 6-byte layer entries at `self + i*6` (page index at `+0x60`,
two u16 texture ids at `+0x62`/`+0x64`):

* the page id tried first for layer `i` is `row B[i]` — 3, 0, 1, 2;
* on failure (`0x61CEB8`: `ldrb r0,[fp,r0]` with `fp = sp+4`) the next candidate is
  `row A[current]`, i.e. the ring `0 -> 1 -> 2 -> 3 -> 0`, retried up to 4 times;
* a page id indexes the page table at `[self->f_4c->f_8 + 0x34 + id*4]` / `+0x44`
  (two name offsets, `-1` = page absent), resolved with `maybe_Gfx_ResourceTrie_Lookup`
  (0x00659668) after `strlen` (0x0011CCA0), and the resulting handles are stored at `+0x62`/`+0x64`.

The readable counterpart `decomp/readable/functions/Bg2D_ResolveLayerTextures_0061cdc8.c`
agrees word for word: `local_2c = *g_0061cf50` is the fallback row, `local_28 = g_0061cf50[1]`
the first-choice row, and its header already calls these "4 candidate page bytes each".
Project vocabulary ("layer page", "page id", `Bg2D_SetTexturePages`,
`maybe_Bg2D_FindTexturePageByName`, `Bg2D_ResetLayerPages` writing 0xFFFF page ids) makes
"page" the right word, so the name does not invent a new concept.

Type `u8[8]` is deliberate: the object is two adjacent `u8[4]` rows and the code addresses them
as two words, so a flat 8-byte byte array is the only declaration that is true for both accesses.
`apply.py`'s `normalise_type` accepts it and emits `extern u8 g_bg2dLayerPageSearchOrder[8];`.

## Decisions recorded

* **No `maybe_` prefix.** Confidence is 0.70. The mechanism (8 bytes, two 4-entry rows,
  first-choice row, successor ring, 4 layers) is proven by the asm; only the human wording of the
  concept is a judgement call. The name is deliberately vague-but-correct ("search order") rather
  than claiming a precise meaning for the rotated ordering (why layer 0 prefers page 3 is not
  explained anywhere in the code).

  prefix the name with `maybe_`", but `tools/typedb/apply.py:check_identifier(name, prefix="g_")`
  rejects any global name that does not start with `g_` and drops the whole entry at merge time
  (the G_001 worker hit exactly this). This entry is ≥ 0.5 so the conflict does not bite here; I
  mention it because a future < 0.5 global in another batch will.
