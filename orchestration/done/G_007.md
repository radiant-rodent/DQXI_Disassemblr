## How the evidence was gathered

1. `tools/typedb/globals.json` (the full inventory record) was used instead of the trimmed batch
   copy — it lists **all** literals per address (the batch shows only three; `0x007A6428` has 11).
2. Every literal slot was re-read from `original/exefs/code.decompressed.bin`
   (address − `0x00100000`) to confirm which real object it points at, and the object's own words
   were dumped (this is how `0x7A6050 = 0x42C80000 = 100.0f` and the 0.0 values of the whole
   `0x7A6058..0x007A6078` block were established).
3. The readable C of every user function was read (not just the one-line samples): `Camera_Update`,
   `Camera_ResolveCollision`, `Camera_SetTransitionTarget`, `Camera_UpdateTransition`,
   `Camera_SetupFromActor`, `Camera_UpdateManualYaw`, `Camera_IsCandidateVisible`,
   `Camera_BuildVisibleTargetLists`, `Camera_CalcStereoEyePositions`, `Camera_Field_Update`,
   `Camera_RegularShake_Ctor`, `maybe_Camera_UpdateWorkPathEx`, `maybe_Camera_ComputeDistanceScale`,
   `maybe_Camera_ComputeAnchorPoint`, `maybe_Camera_InitOrbitParams`,
   `maybe_Ui_ModelView_SetCharacterText`, `maybe_Gfx_ComputeViewTransform`, … plus the raw Ghidra
   pseudocode where the M1 rewrite hides the pointer arithmetic.
4. Vtable boundaries were found by scanning forward in `.rodata` for the next table header
   (null word + first pointer) and each slot was mapped to a function name via
   `decomp/ghidra/functions_merged.jsonl`.
5. `func_0010009C` (0x0010009C, called from `maybe_Camera_UpdateWorkPathEx`) was disassembled from
   `asm/text/text_00100048.s`: `ldr r1,[r0]; cmp r1,#0; beq -> str #1,[r0]; return 1` — i.e. it is
   `__cxa_guard_acquire`, not a noreturn helper as the readable-C "WARNING" comment claims.

## Key findings a modder should know

- **Literal-pool semantics**: in this readable C, `g_00XXXXXX` denotes *the 32-bit value stored in
  the literal slot*, i.e. the address of the real object. So `*g_0044223c` = `*(float*)0x007A6050`
  = 100.0f, and `pfVar = g_004417e0` = `pfVar = 0x007A6060`. Several `width: 1` records are really
  4-byte floats (the inventory's byte guess came from a `*g` deref, not from a `(float*)` cast).
- **`0x007A6428` and `0x007A64B0` are null objects**, not lists: every use is
  `ptr = ...; if (ptr == 0) ptr = g_00XXXXXX;` followed by field reads. `0x7A6428` is exactly
  0x88 bytes (highest field `+0x84`, next object at `0x7A64B0`) and is shared by camera, UI
  row-layout, field-NPC, battle and screen-view code.
- **`0x007A63E4` is a `__cxa_guard` word** (`0x7A63D8 + 0xC`), used for a lazily initialised
  static block in the camera work-path update.
- **`0x007A8B80` is the base of a 0x28-byte distance-scale config struct**; the batch's
  `0x7A8B81/8C/90/9C/A0` are its `+1`, `+0xC`, `+0x10`, `+0x1C`, `+0x20` fields, not independent
  scalars. All zero in the retail image → the overlay scale-by-distance feature is off.
- **The whole `0x7A6058..0x007A6078` block is zero** and no readable function writes it
  (`globals.json` `stores` is empty for all of them). These are the camera collision/transition
  smoothing factors; in this build the smoothing is consequently a no-op. The only non-zero word in
  that block is `0x7A6050 = 100.0f`, the pad-yaw speed multiplier in `Camera_UpdateManualYaw`.
- `0x7A6070` / `0x7A6074` / `0x7C51C0` are the *published camera pose* of the last
  `Camera_SetTransitionTarget` (eye scale, eye distance, look-at target), read back by
  `Camera_UpdateTransition` when no transition is running.

## Not verified / open problems

- **No runtime evidence**: nothing here was checked in Azahar or on hardware. Confidence reflects
  static evidence only.
- **Vtable lengths** (`void*[24]`, `void*[24]`, `void*[4]`) come from the zero-header boundary in
  `.rodata`, not from a proven install list; an off-by-one to two words is possible for the two
  24-word tables. Their *start* addresses are certain (installed by the constructors).
- **The two battle-camera range tables** are confidently vtables installed by the 0x0046E8B8 /
  0x004E5B3C constructors (called from `maybe_Field_SetEncounterParams` near the
  `shortRange`/`battle` strings), but which of the four range variants each one is has not been
  proven; the B suffix is deliberate.
- **`0x007A6078`** (`self->f_114 * 57.29578`) has no recovered reader; the "angle in degrees"
  reading is a hypothesis (conf 0.35).
- **`0x7A6148`** and **`0x7A6184`** sit in a Ui-camera shared-defaults area and are reused for
  several fields; the names say "default/roll" but the exact engine meaning is unknown.
- **No writer was found** for the zero `0x7A6058..0x7A6078` block or the BSS vectors. If a startup
  routine outside the 18,737 readable functions fills them (e.g. a debug parameter loader), the
  comments ("retail value 0, feature off") stay true for the retail image but the *intended* values
  are then unknown.
- The overlapping field declarations (`g_distanceScaleConfig` as `u8[0x28]` plus its `+1/+0xC/...`
  aliases) are legal `extern` declarations but describe the same bytes; `apply.py` will emit both.
  If the merge ever defines (not declares) them, they must be folded into a real struct.
