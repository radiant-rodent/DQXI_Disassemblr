# G_008 — Casino globals (33)

Resumed lane. At start `orchestration/types/out/G_008.json` and
`orchestration/done/G_008.md` did not exist (the old log only had two aborted

UTF-8).

## What the batch actually is

All 33 addresses are *literal-pool targets*, i.e. the real data objects. 27 of
them are **method tables** (3 class vtables + 24 action-node tables; the other
six are two small tables, one PMF constant, two name arrays, one guard byte and
one BSS state object). Their exact shape turned out to be:

* class vtables (`0x00766DC4`, `0x00776084`, `0x0077A2B8`): 10 words,
  `+0` = destructor (or 0 for `Casino_Slot`), `+4` = deleting destructor, then
  the virtual methods;
* "action node" tables (`void*[5]`): `+0` = out-of-line unlink thunk (arm:
  `add r1,r0,#8; ldm r1,{r1,r2}; str r1,[r2,#4]; str r2,[r1,#8]; bx lr`),
  `+4` = 0, **`+8` = the actual `exec(node, ctx)` method** (`Ui_SlotWindow_ProcessPatterns`
  calls `(**(code**)(*node + 8))(node, ...)`), `+0xC/+0x10` = 0.

This is *not* the Itanium class-vtable layout of the PokerWindow/SlotDisplay
classes. Naming the slot at `+8` from the decompiled function at that address is
what makes every node name defensible; each entry's `evidence` lists it.

## Method

1. Resolved each literal slot through `tools/typedb/common.py` (`word_at`,
   `section_of`) and re-read the retail bytes, so the record is the *object*
   and not the `.text` slot.
2. For every user function in the batch I read the readable C under
   `decomp/readable/functions/` (Casino_Slot_BuildPayoutSequence,
   Casino_Slot_CalcPatternPayout, Casino_Slot_Ctor, Casino_Slot_InitPanes,
   Casino_Slot_PickStopBySymbol, maybe_Ui_SlotWindow_{Payout,ReelStop}Sequence,
   maybe_Ui_SlotMachine_ExecState, Ui_SlotMachine_UpdateInput,
   Ui_MessageVoice_UpdateLine0..3/FinishLine4, maybe_Ui_UpdateTextIdProgression,
   maybe_Ui_DigitRoll_Update, maybe_Ui_TextBuild_Start, the four
   Casino_Slot_UpdateWinLine* functions, Casino_Slot_Display/ PokerWindow dtors,
   maybe_Casino_Slot_StepDigitAnim, ...).
3. Mapped every `+8` slot to its function with `decomp/functions_index.json`
   (exact file, or `file+offset` when Ghidra merged a 20-byte thunk into the
   previous function) and disassembled the ambiguous ones with Capstone 5.0.7
   from the retail image (`0x003B6D84`, `0x003EB614`, `0x003EB648`,
   `0x0064BFC8`).
4. Cross-checked `orchestration/types/structs.json` for the three class
   vtables: `Casino_Slot` (9 slots at `0x00766DC8`), `Casino_PokerWindow`
   (10 slots at `0x0077A2B8`); `Casino_SlotDisplay` has no vtable recorded but
   its ctor/dtor both load `0x00776084`.
5. Used N_088 (Casino_Slot_Ctor: vtable slots InitPanes/ReleaseEffects/
   RenderReels), N_065 (SlotDisplay/DigitPanel ctor), N_067 (PokerWindow dtor),
   N_056/N_027 (slot command vtables) and N_049/N_052/N_076 only as
   cross-checks - every claim in the JSON is re-derived from the retail image
   or the function body, not copied.

## Load-bearing findings

* **`0x0072AB4C`** is not zero: it is `s32[5] = {0,1,2,3,4}`, the per-reel column
  offset into the interleaved symbol rows (`Casino_Slot_PickStopBySymbol`:
  `strip[row*5 + table[reel]]`). The inventory's "zero-initialised" hint only
  looked at word 0.
* **`0x0072AC78`** is a two-word C++ pointer-to-member-function
  `{0x003805E4 Ui_Delegate_BindActionB, 0}` copied into the jackpot node whose
  exec is `Ui_Delegate_Invoke`.
* **`0x0075E0AC/D4/FC/124/14C`** are the five win-message text lines
  (`UpdateLine0..3`, `FinishLine4`), not five reels: `Casino_Slot_BuildPayoutSequence`
  registers a 0x2F-byte `MessageVoice` node per animation slot
  `+0x47C/+0x494/+0x4AC/+0x4C4/+0x4DC`, and `maybe_Ui_SlotWindow_ReelStopSequence`
  uses the same slots for the same five lines.
* **`0x007AA048` / `0x007AA158`** are 3-entry `char*` tables, not single
  pointers: `{"win_talk","win_yesno","coinget"}` (looked up and detached in
  `Casino_Slot_InitPanes`) and `{"light_l","light_c","light_r"}` (digit step
  animation names).
* **`0x00839800`** is a 228-byte `.bss` **object**, not a pointer: the ARM
  loads its address into `r0` and writes the seed to `[r0,#0xD8]`; the shuffle
  loop uses `+0xDC/+0xE0` as its two LCG state words. `0x007C22FC` is the
  once-only guard byte for that function-local static (it is the argument of
  the `0x0010009C` guard helper).
* `Casino_Slot_Ctor` stores `0x00766DC4` at object **+0x11C** (the raw C says
  `*(u32*)((u8*)result + 0x11c)`), so this is the method table of the embedded
  5880-byte Casino_Slot part, not of the whole casino window. Word 0 is 0 and
  the first real slot is at +4, which is why `structs.json` lists the vtable as
  `0x00766DC8`.

## Open problems / honest gaps

1. **Two node names are field-descriptive, not semantic**:
   `g_slotDisplayByte173NodeVtable` (`Casino_Slot+0x173`) and
   `g_slotDisplayByte171NodeVtable` (`Casino_Slot+0x171`). Their exec writes the
   node byte and finishes - certain. Which of `self+0x40`/`self+0x3C` is "bet"
   and which is "credit" is *not* proven, so I did not put bet/credit in the
   names. A Casino/UI worker should settle that from `Ui_SlotWindow_Ctor` and
   the medal counter.
2. `g_slotWinSequenceNodeVtable` (`0x00771B24`) has slot +8 = `Ui_SlotMachine_UpdateInput`,
   an obvious misnomer: the body is a 0x65-frame spin-result timeline (stops
   reels at 0x14, sets reel states at 0x19/1E/23/28/2D, starts win state at
   0x64). It is a candidate for a function rename in a future N batch.
3. The "win text" family (`g_slotWinTextLine*Vtable`,
   `g_slotWinTextCycle/Layout`, `g_slotWinMessageRows`) is named from the
   casino *use site*; the exec bodies (`Ui_MessageVoice_*`,
   `maybe_Ui_MessageWindow_UpdateRows`) are generic UI text machinery that other
   windows may share. If a later batch names the same machinery for the message
   window, the vocabulary should be unified (M1 pass).
4. The `0x766008` node (`g_slotDisplayScaleNodeVtable`) applies a
   1/10/100 scale from `Casino_Slot_GetPayoutRank`; *why* that is needed on the
   no-bet path is not explained by any constant/string I found.
5. Not verified by running the game: no emulator/3DS confirmation that these
   tables are reached in the order the readers imply; no merge run
   (`tools/typedb/apply.py --merge` writes shared `orchestration/types/merged/*`,
   outside this lane).
