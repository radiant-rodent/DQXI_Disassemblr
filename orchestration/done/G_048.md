## Open problems / not verified

- **`asm/text/text_00140048.s` is wrong for this function.** The slice disassembles
  `0x001577FC..0x001578EC` as Thumb (e.g. `0x00157804: 4cd0 beq #0x1578a0` for the ARM word
  `e24dd04c`) and only emits `.arm` at `0x001578EC`. The function is ARM from its prologue; the
  literal pool at `0x00157954..0x00157964` is loaded by `ldr rX,[pc,#...]` from inside it. Any worker
  reading that slice will mis-read the first ~0xF0 bytes.
- **`decomp/functions/Str_HashName.c` is damaged** (Ghidra): `flags` is undeclared, `*(u8*)((u8*)result
  + ctx) = index` and `*(u8*)((u8*)result + 1]!` are nonsense, and the CRC loop is reduced to
  `ip = *(u16*)(ip)`. The name/type above come from the hand-decoded ARM, not from that C.
- **`symbols.json` says `Str_HashName` "splits at ':'"** - the separator is `'@'` (string at
  `0x0015795C`). The same entry also calls `0x0011CCA0` `strlen` correctly but the function index
  attributes that address to `Os_ThreadEntry`; `0x00123660` is `strncmp` (index says `0x00123664`).
  These are outside this task's ownership and should be fixed by a naming/refine batch.
- **`Str_HashName` has no callers in this build**: no `bl`/`blx` targets `0x001577FC` and no word in
  `.text`/`.rodata`/`.data` equals `0x001577FC` or `0x001577FD`. The function (and therefore the
  table) is unreachable in the retail image as shipped - it may be dead code kept by the linker or
  reached through a computed address. The table's identity does not depend on this, but the "who
  uses it" answer is "only dead code".
- **The `CATEGORY@name` format is inferred from the code, not from a sample string.** No
  `ENEMY@...`-style literal exists in `.rodata` (the only real printable strings containing `@` are
  the hex-format helpers `0123456789ABCDEF@0X` / `0123456789abcdef@0x`; everything else the scan
  found is binary noise), so the names are built at runtime. The `'@'` separator, the 58-entry
  category table and the CRC-over-suffix behaviour are all directly visible in the disassembly.
- Bits 16..23 of the returned handle are always 0 in the code path (`mov r1, r6, lsl #16` with
  `r6 = 0`), so the comment describes the high half as "category index in bits 24..30 plus a flag
  bit" rather than claiming a full byte layout.
