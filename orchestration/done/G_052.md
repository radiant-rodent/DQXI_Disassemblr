# G_052 — UI globals (300 vtables)

## Status

Completed. `orchestration/types/out/G_052.json` contains 300 entries, one for every global in
`orchestration/types/batches/G_052.json`.

The task said "RESUMED", but I checked first: `orchestration/types/out/G_052.json`,
`orchestration/done/G_052.md` and any previous scratch output did not exist, so there was nothing
to continue. I produced the batch from scratch. The answer file is generated deterministically by
`out/scratch/G_052/gen.py` from the batch + `structs.json` + the retail image; because the whole
batch completed in one pass, no intermediate partial saves were needed (re-running the generator
rewrites the same 300 entries).

## What the batch actually is

All 300 addresses are C++ virtual method tables in `.rodata` (0x00759FBC..0x00768510), not plain
data objects. Each entry is installed with `*object = &g_...` by the constructor/destructor named
in `functions[]`, and the word at the address is either the first virtual function (no RTTI) or 0
(offset-to-top / no RTTI header), followed by code pointers and occasional 0 pure-virtual slots.

Two independent evidence sources were used for the exact table layout:

* `structs.json` -> `classes[].vtables[]` (address, `slot_count`, per-slot function names). This
  covers 158 of the 300 addresses and also proves that entries 16..43 are the `std_StateSequenceNN`
  state machines embedded in UI windows (e.g. batch base 0x0075A7B0 + leading null word =
  `std_StateSequence39` vtable at 0x0075A7B4, 6 slots -> `void*[7]`).
* `structs.json` -> `pointer_tables[]` (`slot_count`, `slot_names`) supplied most of the remaining
  counted tables.

Naming rules applied:

* class recovered in `structs.json` + matching ctor/dtor -> `g_<className>Vtable` (0.85 for an exact
  class + ctor/dtor pair, 0.70-0.80 for a class plus ctor or slot evidence);
* generic class (`Ui_Widget`, `Ui_Window`, `Ui_Object`) -> name from the concrete
  `*_InitPanes` / `*_BindPanes` / `*_Setup*` slot (`g_uiItemInfoWindowPaneVtable`,
  `g_uiTwoLineGuideWindowVtable`, ...);
* class unknown but installer meaningful -> `maybe_g_...Vtable` at 0.35-0.50;
* nothing defensible -> honest placeholder `maybe_g_rodata_<hex>` at 0.30.

15 candidate names collided with primary vtables already named by other G batches. Rather than
overwrite those names, I renamed mine as secondary/body tables and recorded the primary address in
the log: `g_uiPokerWindowBaseVtable` (primary 0x00762BB8), `g_uiShopWindowWidgetVtable`
(0x00759704), `g_battleTextWindowWidgetVtable` (0x00761474), `g_uiCompositeWindowObjectVtable`
(0x00759388), `g_uiComplexWindowWidgetVtable` (0x00759724), `g_uiItemMenuRootPartVtable`
(0x00758D78), `g_uiFadeWindowWidgetVtable` (0x0075869C), `g_uiItemInfoWindowPaneVtable`
(0x00761E68), `g_uiBigScreenWidgetVtable` (0x00759CD0), `g_uiObjectBaseAltVtable` (0x0076334C),
`g_battlePopup3DResultListVtable` (0x00769A40), `g_uiLoadingScreenWidgetVtable` (0x007587A8),
`g_uiGuideWindowBodyVtable` (0x007654C4), `g_uiPresentMessageManagerVtable` (0x0076741C),
`g_battleActorActionBaseVtable` (0x0076F260).

## Types

* 227 entries: `void*[N]` with N = class `slot_count` (+1 when the batch address points at the
  leading null word). This N is taken from `structs.json`, not guessed.
* 73 entries: `void*`. For these no authoritative slot count exists; a naive run of code/zero words
  over-reads because neighbouring vtables are contiguous in `.rodata`. `void*` is an allowed real C
  type and avoids stating a length I cannot defend. The comment says what the table is; follow-up
  work can add the length once the neighbouring tables are mapped.

## Confidence distribution

* 0.80-0.85: 84 entries, class + exact ctor/dtor/slot evidence.
* 0.50-0.75: 158 entries, class or a concrete pane/setup slot, lower for shared/base tables.
* < 0.50: 58 entries, all `maybe_`-prefixed (including the four `maybe_g_rodata_*` placeholders at
  0.30).

## What is NOT verified / open problems

* The 73 `void*` lengths are deliberately unverified; exact N needs a full vtable map of the
  0x00759xxx-0x00768xxx rodata band (several tables are not in any batch).
* Names for shared/base tables (`g_uiWidgetVtable`, `g_uiWidgetBaseVtable`, `g_uiObjectVtable`,
  `maybe_g_uiSystemVtableA/B`, `maybe_g_actorBaseVtable`, `maybe_g_objectHandlerVtable`) describe
  the family, not a single concrete class; a follow-up should assign the concrete subclass by
  checking the overwrite store order in the constructors.
* `g_uiPartyHpGaugeWindowVtable` (0x0075A07C) and `g_uiAdventureLogWindowVtable` (0x0075C87C)
  are derived from one pane/setup slot each and could be a shared sub-widget table instead.
* `g_uiMessageVoiceLine0..3Vtable` (0x0075E0C0..0x0075E138) is inferred from the four
  `Ui_MessageVoice_(Finish|Update)LineN` slot groups; the class name itself is not in
  `structs.json`.
* No emulator or runtime test was done; this batch only changes names/types/comments for the
  readable C pass.
