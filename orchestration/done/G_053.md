## What the batch actually is

All 300 addresses are tables of code pointers / vtable-like data in `.rodata`
(`0x00768574..0x0077C75C`), immediately after the G_052 band. 145 of them are listed in
`structs.json` as a class vtable (`classes[].vtables[]`), 204 are also in `pointer_tables[]`,
and the rest are vtable-like tables whose class was recovered from their own slots or from the
installer function named in the batch.

The decisive evidence was, in this order:

1. `structs.json` class vtables at the batch address or at `address+4` (a 0 offset-to-top word in
   front of the function slots). This gives both the class and `slot_count` (used for the C type).
2. The vtable words themselves, resolved through `out/scratch/G_052/symmap.json`. Slot 0/1 is
   usually the destructor, slot 4..8 the class `*_InitPanes` / `*_BindPanes` / `*_Ctor`.
3. The doc comments of the readable functions. 115 of the 300 addresses are explicitly mentioned
   in a function doc ("installs vtable 0x76xxxx"), which settled the class for tables that
   `structs.json` does not list.

Scratch files are in `out/scratch/G_053/` (`gen4.py` is the deterministic generator, `check.py`
the schema/UTF-8 self-check, `verify_merge.py` the in-process merge check, plus the evidence
dumps `analysis.txt`, `words.txt`, `docs.txt`, `review3.txt`).

## Naming / typing rules applied

* `g_<lowerCamelClassName>Vtable` when `structs.json` recovers the class (0.76–0.88).
* Concrete class from a destructor / `*_InitPanes` slot when no class is recovered (0.50–0.70).
* `maybe_g_*` for anything below 0.50 (51 entries, 42 of them below 0.50 confidence; the other 9
  are deliberately hesitant names at 0.50).
* `maybe_g_rodata_<hex>` for the 10 objects that are not dense vtables or whose class is genuinely
  unknown (0.30). Their comments say exactly what is known.
* Table lengths: 255 entries get a concrete `void*[N]` (203 of them `void*[10]`, the usual 9
  virtual slots plus the leading offset/null word); 45 have no authoritative slot count and stay
  `void*` rather than stating a length I cannot defend.
* Confidence: 102 entries at 0.80–0.88 (structs.json class + matching slot), 156 at 0.50–0.79
  (class from one strong slot or from the installer), 42 below 0.50 (all `maybe_`).

### Non-vtable findings worth keeping

* `0x00773DE0..0x00773E10` + `0x0076E29C` are **five static message-voice typing-blip pattern
  descriptors**, selected by `Ui_MessageVoice_SelectBlipPattern` (0x002CFCC0) with weights
  50/30/20 for long runs and 70/30 for lineIndex>=2. They are not class vtables; named
  `g_messageVoiceBlipPatternLongA/B/C`, `g_messageVoiceBlipPatternDefault`,
  `g_messageVoiceBlipPatternLongLine`.
* `0x00773728`, `0x0077559C`, `0x007755B4`, `0x0077C3B8` are four generic popup-entry tables used
  by `Ui_PopupEntry_SpawnFromDescriptor`; named `maybe_g_uiPopupDescriptorVtableA..D`.
* The other popup-entry tables are attached to their spawn function
  (`g_uiPopupSpeakerBalloonVtable`, `g_uiPopupMonsterPairVtable`, `g_uiPopupEquipCompareVtable`,
  `g_uiPopupLogEntryVtable`, `g_uiPopupMultiActorVtable`, `g_uiPopupModelDebugTextVtable`).
* `0x0076BD1C` is a descriptor stored at `textPart+0x10` by `maybe_Ui_TextPart_Create`; the
  following 0x20 bytes are the separate `Gfx_WindowNode` vtable, so it is not a normal vtable
  (placeholder, 0.30).
* `0x007792D0`, `0x0077A51C`, `0x0077A630`, `0x0077BA38`, `0x0077C648`, `0x0077C75C` are
  anonymous screen/3D-text classes whose constructors are still called `maybe_Ui_ScreenCtor_*`.
  Where a slot names the class (`Battle_Ui_SkillPopup`, `Battle_Ui_PartyPanel`,
  `Battle_Ui_MemberPanel`, `Text_MessageWindow`, `Text3D`) the slot name was used; otherwise the
  entry is `maybe_g_*`.

## Open problems / not verified

* 45 entries have no authoritative length and are typed `void*`; a full rodata table map is
  needed before their `void*[N]` lengths can be stated.
* The 10 `maybe_g_rodata_*` entries are honest placeholders: 5 are non-vtable descriptor/helper
  tables and 5 have no recoverable class.
* Class ownership for 155 entries has no `structs.json` class entry; their owner comes from one
  slot name, the installer function name, or a function doc comment, so identical folded functions
  can still be misleading.
* The five blip descriptors and the four popup descriptor tables are named from the selecting
  function/weights; their internal field layout is still unknown (typed `void*` / `void*[4]`).
* No emulator or runtime test was done; this batch only changes names/types/comments for the
  readable-C pass and does not touch code or data.
