## What the batch actually is

This band is the tail of the UI `.rodata` globals, immediately after the G_053 vtable band. It is
**not** all vtables; three source classes were used:

* **Vtables** (176 entries named `…Vtable`): class vtables recorded in `structs.json` (at the address or at
  `address+4` when a leading null/offset word precedes the slots), `pointer_tables[]` lengths, or a
  readable-function doc that says "installs vtable 0x…". Slot 0 is very often the deleting
  destructor (`*_Dtor`, `*_Delete*`), which identifies the class where `structs.json` is silent.
  For the 0x00782C18..0x00783438 band the addresses are **secondary/sub-object vtables** written
  into a member field of a larger object (panel-message, skill panel, scroll-list, dive-manager,
  sequence, title screen, …); they are named after the owning constructor plus `SubVtableA..K`.
* **Tables** (view lookup / dispatch / colour tables): e.g. `g_uiSmithPageSuffixes` is the
  `{"_start","_loop","_end"}` string table used by the smith page label; 0x0078430C is a 6-entry
  best-item scoring dispatch table; 0x00784324..0x007843BC are the eight 4/6/8-word vertex-attribute
  tables of the layout-text quad builders; 0x007A4268 is the field-object factory kind→constructor
  table.
* **Runtime state / static singletons** in `.data`: lazy-singleton vtable slots (movie frame,
  anim sequence, layout block, state request, game-data manager, text layout, pack manager), the
  12-entry UI colour palettes, three-flag list-row override bytes, party-panel text colours, and
  eleven module-static UI object state blocks registered at startup.

Every one of the 300 addresses is a real object referenced by the retail image; no numeric
literal was named.

## Naming rules applied

* `structs.json` class + matching ctor/dtor slot → `g_<lowerCamelClass>Vtable`, confidence 0.80-0.85.
* Class/owner named explicitly in the readable-C doc → class name, 0.55-0.75.
* Owner inferred from the *function that writes the table* (always certain) but the table role
  inferred → `maybe_` at 0.40-0.45; the evidence names the installer, so a later pass can upgrade it.
* Exact table length only when `structs.json`/`pointer_tables` gives one or when the
  code-pointer run has a clear non-code terminator. Otherwise `void*`, never a guessed `void*[N]`
  (several UI vtables have null/pure-virtual holes in the middle, so counting a code run undercounts;
  those are left `void*` on purpose).
* Two class vtables per class exist in this region (this band plus the G_053 band). To avoid
  duplicate symbols, my secondary tables use the `…Vtable2` suffix; the primary name is in G_053.
  Collisions with G_015/G_036/G_047/G_051/G_052 were resolved the same way (see **Names that had
  to differ** below).

## What is NOT verified / open problems

* **Table lengths.** 191 entries use plain `void*` because no authoritative slot count exists
  (71 entries have a concrete `T[N]`/`void*[N]`, 38 are scalar `u8`/`u32`/`f32`). Several
  UI vtables contain null slots in the middle; a raw code-pointer scan therefore undercounts
  (e.g. 0x0077C8B0 reads as 4 words but has far more slots). Only `structs.json`/`pointer_tables`
  counts were trusted.
* **Secondary vtables in 0x00782C18..0x00783438** are named by owning constructor + letter. The
  owning *object* is certain (the ctor/dtor writes the field), but which sub-widget each table
  belongs to is not recovered; several `Ui_PanelMessageWindow` tables could not be told apart.
* **Kind tables** 0x007A4268 / 0x007A4338 are a single contiguous code-pointer block longer than
  400 words, so their true lengths and the boundary between the main and monster sub-table are
  unknown; both are typed `void*`.
* **`.data` state objects** (0x0079D000, 0x0079F000, 0x007A6F98, 0x007A7714, 0x007A7795,
  0x007A6088/0x007A6140/0x007A6200) are zero in the retail image and are filled at runtime; their
  sizes are inferred from the *next* referenced block or from the largest indexed offset, not from
  a constructor that memsets them.
* **0x007A71A4** is a mixed record: word 0 is patched at runtime with a self-relative pointer and
  the rest is the UTF-16 text `"[Debug] "`; the type `u32[6]` is a storage size, not a decoded
  struct.
* **0x00786574** is the pane-name string `"_c1"` (a pointer into the packed pane-name block); it is
  typed `char[4]`, but why the gauge window looks up a pane named `_c1` was not verified in the
  layout resource.
* **Static UI objects** `maybe_g_uiStaticObjectA..K` are module-static state blocks registered at
  startup; their widget classes are not identified. `structs.json` has no entry for them.
* No emulator or runtime test was done; this batch only changes names/types/comments for the
  readable-C/header pass.

## Suggested follow-ups

1. A vtable-boundary pass over 0x0077C8B0..0x00783438 (including the G_053 band) that records
   `slot_count` for every table, so the 191 `void*` entries can become `void*[N]`. The reliable
   signal is the vtable's use in a constructor plus the next table's head, not a code run.
2. An S/R pass over `Ui_PanelMessageWindow`, `Ui_PanelMessage`, `Ui_ScrollListWindow`,
   `Ui_DiveManager`, `Ui_Sequence` and `Ui_MessageSelectWindow` to map their member offsets to
   sub-object classes; that would replace the `SubVtableA..K` letters with real class names.
3. Investigate 0x007A4268/0x007A4338 as one factory table: find the highest kind byte actually
   passed and split it into the main/monster ranges.
4. Read the static-object register functions (0x00695480, 0x0069A5DC, 0x006A14C0, …) to give
   `maybe_g_uiStaticObjectA..K` their real widget types.
5. Confirm the 0x7A7814..0x7A7830 2x4 colour block's selected/unselected row order together with
   the G_055 owner of 0x7A7828..0x7A7830.
