## What was done

`tools/typedb/inventory.py` had already resolved every `g_XXXXXXXX` literal to the real data address, so the work
was reading the evidence per address. I used `tools/fn.py` on the functions that reference each global (never a
tree walk), plus the retail words read through `tools.typedb.common.word_at` / `bytes_at`. Scratch stayed in
`out/scratch/G_055/` (`dump.py`, `summary.txt`, `words.txt`, `gen.py`, `validate.txt`).

The batch is not 300 unrelated objects — it is a handful of structures plus a large string table:

| Range | What it really is | Entries |

### Findings worth keeping

1. **The singleton table `0x007BE2DC..0x007BE388` is a run of `{u8 flag; void* instance}` pairs.** Every accessor in
   the cluster `0x006F1D50..0x006F250C` uses the same template: test the flag byte, clear it, allocate, store into the
   adjacent pointer word. I matched each pair to its accessor, which gives the object identity and size:
   `Ui_GetSceneTransitionManager` 0x28, `Sound_GetPlayer` 0x1EB0, `Os_GetGameWork` 0x1C, `Ui_GetRootSingleton` 0x80,
   `Fs_CacheSet_Initialize` 0x21C, `Ui_GetCore` 0x98, `Input_Initialize` 0x1D4, `Gfx_GetContext` 0x1348.
2. **`0x007BE308` is the party/save work, not the UI manager.** The accessor `0x006F1F88` is currently named
   `Ui_UiManager_GetInstance`, but its constructor is `SaveWork_Container_BaseCtor` (0x00103594) and the object is the
   0xE3C8-byte party/save container that `FACTS.md` already records. I named the global `g_partySaveWork` and said so
   in the comment; the *function* name is outside my ownership, so it is unchanged.
3. **`0x007BE388` is the graphics context** (`Gfx_GetContext`, 0x1348 bytes: camera matrices, material layers, UI draw
   lists, font pages, fade state, model/anim registries). The project notes call the same object the "FX manager"; the
   comment mentions both so neither reading is lost.
4. **`0x007BE330` is the Fs cache-set *pointer*, not the cache set.** The object itself is `0x007CF324` (already named
   `g_fsCacheSet` by G_013), so this one is `g_fsCacheSetSingleton` — the first validator run failed on exactly that
   duplicate, which is how the distinction surfaced.
5. **`0x007AC834`** is a `void*` to the message format-argument slot array (stride 0x108, formatted string at slot+8),
   NULL-checked before use. 230 references from 83 functions.
6. **`0x007AB814`** is a `void*` to the external list-data object; `Ui_ListItemRef_ResolveRow` NULL-checks it and then
   indexes `*g + 0x6B8 + i*0x98`. The inventory's `u32[0x6BC]` guess was the *pointee*, not the global.
7. **Five C++ function-local static guards** (`0x007A9238`, `0x007AECCC`, `0x007AECE4`, `0x007AECEC`, `0x007AED04`,
   `0x007AED08`): `if ((*g & 1) == 0) { func_0010009C(g); }`, i.e. `__cxa_guard_acquire`. Typed `u8`.
8. **The `.bxon` block is a resource-name table**, not data-table descriptors: `Ui_Layout_LoadAndBind_Type1/Type6` pass
   each name to `func_00124B24(manager, screenType, name)`. Named `g_resName<CamelCase>` with the exact byte length.
   `skill_param.bxon` appears twice (once per loader), hence `g_resNameSkillParam` / `g_resNameSkillParam2`.
9. **The wide-string block**: `0x007BE72C` and `0x007BE736` are empty wide strings (the first is the `std_wcsncpy`
   source used to blank 7-character name fields, the second the fallback format for `wcslen`); `0x007BE774` and
   `0x007BE8AA` are `L"%ls"`; `0x007BE77C` / `0x007BE780` are single-character placeholders (code points 0xFF1F /
   0xFF01) passed as the `%ls` argument when a text widget has no text.

## Open problems / not verified

- **102 entries are `maybe_` at 0.3–0.45.** They are static state blocks where the only visible evidence is "a word at
  +0xC / +0x14 is read by these one or two UI functions". The names describe the owning window, not the field's
  meaning. This is deliberate: a vague correct name beats a precise wrong one.
- **The palette colour order at `0x007AB514` is not verified.** `Ui_InitColorPalette_7AB514` decompiles with damaged
  control flow (`halt_baddata`), and the alpha-byte positions it writes are not a clean 4-byte stride, so I did not
  claim which colour is which. The 40 byte entries are named by offset (`g_uiColorPaletteByteNN`) with the colour index
  and channel derived from the offset only.
- **`0x007BE2F0` (`g_memoryManager`) and `0x007BE2F8` (`g_uiCommonResources`)** rest on the project notes and on the
  function names that use them; I did not locate their accessor functions, so their sizes are unknown.
- **`0x007BE358` (`maybe_g_engineStateFlag`)** is unresolved: a `u8` cleared by `Engine_Initialize` and read by the
  overlay draw and main-menu text code, with no further structure visible.
- **`0x007BA2D0` (`maybe_g_handleTable`)** is inferred from the index/generation validation pattern
  (`(base + (handle & mask) * 2)[0..1]` compared against `handle >> 0xC`), not from a located allocator.
- **`0x007A7874`, `0x007A7934`, `0x007A7AC0`, `0x007A7B40`, `0x007A7BC4`, `0x007A7FCC`-family** are static objects
  accessed at fixed offsets; the array lengths I gave (`u32[4]`, `u32[6]`, ...) are the smallest size that covers the
  highest offset actually observed, not a proven object size.
- No emulator run was made, so none of the runtime behaviour (which colour is actually used, when a singleton is
  created) is confirmed by execution.
