### Key finding that unlocked the batch
All 8 addresses are **static BSS instance buffers of lazily created singletons**, not plain scalars.
Every reference is the same inlined allocator template:

```
p = ALIGN_UP(LITERAL, 16);          // __aeabi_uidivmod round-up: 0x0011CFAC
memset(p, 0, SIZE);                 // 0x00116AE0 is memset (stmhs zero stores)
p = CTOR(p);                        // 0x1051F0 / 0x1064D4 / 0x11CFDC / 0x122120 ...
*p = VTABLE;  *FLAG = 0;  *HOLDER = p;
```

I confirmed this by hand-reading the ARM at `0x006F245C` (`Input_GetPadState`), where the true arguments
are visible: `mov r1,#0x1d4` is the memset count and `r0` is the aligned literal address. The decompiler
renders the pair as a meaningless `func_0011CFAC(0x00836F24 + 0xf, 0x10) * 0x10` product, which is why
these records looked like 8.6 MB "sizes".

## Decisions on ambiguous items
- `0x007F52E4`: named for the party/save work container, following the established FACT
  "*0x007BE308 = 0xE3C8-byte party/save container (0x00103594)". The current tree name of the accessor
  (`Ui_UiManager_GetInstance`) is misleading; its callers are `Save_LoadTask_Update`,
  `Save_SlotUi_BuildThree`, `Ui_Menu_UpdateModeTransition`, and its ctor runs `Save_InitPartySnapshot`.
- `0x00833C98`: kept a deliberately vague `g_uiSubsystemWork` (0.55) because the 0x80-byte object is
  handed to `Ui_LoadIconTextures` (which calls it `UiIconCache*`) while `Ui_System_Update` calls it the UI
  subsystem singleton and `maybe_Text_MeasureOverflow` uses flags at +0x68/+0x6C. I did not pick one of
  the two specific identities because neither is proven; the name stays vague rather than wrong.
- `0x00837148`: named `g_gfxContextStorage` per `Gfx_GetContext` (123 named callers, 3 sub-objects), and
  the comment also records that effect code (`Effect_Instance_ReleaseResources`, 0x0030B5F4) returns
  render nodes to *0x007BE388, consistent with the established "FX manager" fact.
