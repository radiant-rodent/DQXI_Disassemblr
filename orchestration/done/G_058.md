## What the 24 globals are

### 1. `0x0072EB3C` → `g_crc32Table`, `u32[256]`, confidence 0.95

The batch flagged this as "zero-initialised (no data bytes in the retail image)" — that is a
false alarm caused by the **first** table entry being `0x00000000`. All 256 words match the
standard reflected IEEE 802.3 CRC-32 table (`0x00000000, 0x77073096, 0xEE0E612C, 0x990951BA,
0x076DC419, ...`), verified entry by entry against a locally computed table.

`std_Crc32_InitTable` (0x005F08DC) is `std_memcpy(stack, 0x0072EB3C, 0x400)` followed by
`std_memcpy(dst, stack, 0x400)`; its callers are `SaveCode_GenerateCheckDigits` (0x005F0408) and
`SaveCode_DecodeAndVerify` (0x005EFE3C), so the table is the save-file checksum table.

### 2. `0x00735154` → `g_moLiveAllocatorOutOfMemoryMessage`, `char[63]`, confidence 0.85

Exact text: `"MoLive::Allocator: not enough memory to allocate %d bytes !!!\n"` (62 chars + NUL).

It is not a log string. `std_SlotVector_Reallocate` (0x00710170) and `std_RbTree_AcquireNode`
(0x0070C414) both do

```c
p = (*alloc->vt[0])(alloc, size);          /* Alloc */
if (p == NULL) (*alloc->vt[2])(alloc, 0x00735154, size);   /* report OOM */
```

so the string is the message handed to the allocator's report/assert slot together with the
failed byte count. Literal slots `0x005EE394`, `0x0070C524`, `0x0071016C`, `0x007102F8` all hold
this address.

### 3. `0x00781FA0 … 0x00782130` (22 globals) → `g_formatStringTag<N>` / `g_wideFormatStringTag<N>`, `void*`, confidence 0.50

These are **not** 22 independent objects. Each is the class word written at offset 0 of one
fixed-capacity format-string temporary. The real function entry is the wrapper **8 bytes before**
the Ghidra symbol:

```
wrapper:  push {r0-r3}          ; save out, fmt, first vararg
          mov  r1, #cap         ; buffer capacity (omitted when the body sets it)
body:     push {r4,lr}
          mov  r4, r0
          mov  r0, #0
          strb r0, [r4,#4]      ; strh for the wide variants
          ldr  r0, =<tag>
          str  r0, [r4]         ; obj->tag = <tag>
          ldr  r2, [sp,#0xc]    ; fmt
          add  r3, sp, #0x10    ; &first vararg
          add  r0, r4, #4       ; buffer
          mov  r1, #cap         ; (only in the three bodies that set it themselves)
          blx  vsnprintf / vswprintf
```

So the object is `{tag; char buf[cap]}` or `{tag; wchar_t buf[cap]}`, and every caller only ever
uses `out + 4` as a `const char*` / `const wchar_t*` (e.g. `Ui_GridTextWindow_InitPanes` passes it
as a pane name, `Ui_CharaStatusWindow_FillPartyMember` as a text-layer string).

I decoded the `mov r1,#imm` of every wrapper and every body, so each tag is named by its buffer
capacity. The capacities are all distinct inside each family, which makes the names unambiguous:

### 4. `0x007C6E7C` → `g_itemBagCategoryOrder`, `s32[31]`, confidence 0.80

BSS, so zero in the image and filled at runtime. `0x0017B994` loops `i` in `0..0x1E`, calls
`0x0066B0E4(work + 0x24A98, i)` and stores `*(int *)(0x007C6E7C + category*4) = i` whenever the
returned category is `< 0x1F` — i.e. `table[category] = slotIndex`, 31 entries.

`std_less_itemId8` (0x0071428C) reads it as the bag sort order:

```c
if (*(int *)(0x007C6E7C + classB*4) <= *(int *)(0x007C6E7C + classA*4)) return 0;
```

after bounding both item-record class bytes (`ItemRecord + 4`) to `< 0x1F`. The same table is used
by `std_less_itemName8`, `std_insertion_sort_itemId8/Name8` and `std_push_heap_itemId8/Name8`.
The earlier name for this table was the literal slot `g_007143A0`; the real object is `0x007C6E7C`.

## Open problems / not verified

1. **What the 16-byte tag slot really is.** Each tag address is a 16-byte block that is *all zero*
   in `original/exefs/code.decompressed.bin`, yet it sits in the `.rodata` vtable area
   (neighbours `0x007815D8`, `0x00781D94`, `0x007822A0` hold real code pointers) and is stored
   exactly like a vtable pointer. No code compares it or calls through it. I therefore did **not**
   name them `*Vtable`; `Tag` is true under either reading and the comment states the zeros
   explicitly. The most plausible explanation is a vtable whose virtuals were never linked — the
   temporaries are stack objects that are never deleted or virtually called, so zero entries are
   harmless — but I could not prove it.
2. **`0x007820E0` is missing from every G batch.** `G_058` jumps `0x007820D0 → 0x007820F0`, and a
   search of all `orchestration/types/batches/G_*.json` finds no batch containing it. It is the
   wide format-string tag with capacity 32 (body `0x006F0DE4`, wrapper `0x006F0DDC`, used by
   `Ui_MessageWindow_SetCounterDisplay`, `Save_SlotUi_BuildEntry`, `Ui_PageList_ShowPage`, …).
   I left it out rather than answer an address I do not own.
3. **`0x00782080` / `0x00782090` (other batches) overlap my range.** `G_0xx` already named
   `0x00782080` `g_initListObjectDescriptor` (`void*`) and `0x00782090`
   `maybe_g_battleTargetSlotPatternA` (`u32[12]`). The `u32[12]` declaration spans
   `0x00782090..0x007820C0`, which overlaps my `0x007820A0` and `0x007820B0`. That earlier answer
   looks wrong (the region is a run of 16-byte slots, not a 48-byte array); worth a re-check.
4. **`std_ThrowNarrowRangeEx` (0x001001C4) and `std_ThrowWideRange` (0x001001FC) are misnamed.**
   Their bodies are `vsnprintf` / `vswprintf` into a `[msg, msg+len)` range, not exception throws.
   Renaming them would make the 22 format-string constructors read correctly.
5. The `maybe_std_String_FormatCtor*` / `maybe_std_WString_FormatCtor*` function names themselves
   are misleading (they are not constructors of a `std::string`); a refine batch should rename
   them to `Str_FormatNarrow<N>` / `Str_FormatWide<N>`.
