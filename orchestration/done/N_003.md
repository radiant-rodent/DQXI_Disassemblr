# N_003 — native naming batch (lane tag `Field_and_World`)

## Summary

Named and documented all **150** functions in `orchestration/naming/batches/N_003.txt`
(`0x0028A0E0`–`0x003251FC`) in `orchestration/naming/out/N_003.json`.

The batch's lane tag says `Field_and_World`, but the address range is almost entirely
**UI/menu window pane wiring**, trail-mesh and effect creation, animation-resource plumbing, and
**battle popup management**. Names therefore follow the code, not the tag:

| Subsystem | Entries |
|---|---|
| `Ui_` | 58 |
| `Gfx_` | 33 |
| `Battle_` | 29 |
| `Anim_` | 20 |
| `Field_` | 6 |
| `Effect_` | 4 |

Nothing was invented: every name is grounded in at least one of (a) a vtable slot whose siblings
and layout identify the class, (b) literal pane/shader/resource strings, or (c) the callee set
shared with an already-identified sibling. Where that evidence ran out, the name is a coarse but
correct placeholder and carries the required `maybe_` prefix.

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `TEMPLATE.md`, the batch file, and other
   `orchestration/naming/out/` proposals for consistency.
2. Read all 150 readable C files (`decomp/readable/functions/`, **0 missing**) and dumped the
   full bodies of the non-trivial ones; skimmed the trivial "call base ctor + write vtable"
   constructors.
3. Worked **bottom-up on helpers first**: allocator `0x00109DC8`, layout pane find/add
   `0x003E00CC`, pane visibility `0x003E043C`, pane enable `0x003E021C`, show pane `0x003DFF34`,
   child-layout anim `0x001A6230`, named mesh `0x005F541C`, scene object by class name
   `0x00225D90`, mesh factory `0x002D1F28`, transform apply `0x002D1304`, object-list construct
   helper `0x00100050`, sprite/tex setup `0x002D0B4C`/`0x002D0C98`, frame/timer accessors
   `0x0063C7xx`, UI cursor init `drN` (`0x001A6520`).
4. **Vtable analysis as primary structural evidence**: scanned the `0x0075–0x0077` data region
   for pointers into the batch range. 50 of 150 addresses are confirmed vtable slots; slots
   7/8 are usually the `Update`/`Draw` pair, and shared base slots group the layout windows.
   77 entries cite vtable evidence directly or through their family.
5. Resolved literals against `original/exefs/code.decompressed.bin`
   (`file offset = address − 0x100000`). Pane names (`gauge`, `flash`, `ring1..3`,
   `gauge2_base`, `gauge2_flash`, `null_txt_l1..l5`, `txt_l1..l5`, `select4/5`, …) and resource
   names (`ChipShader.shbin`, `syscmn.bch`, `cha_shadow01`) were the main semantic evidence.
6. Cross-checked callers/callees through a generated call graph; most batch functions have **no
   direct callers** in the decompiled tree because they are invoked through vtables/function
   pointers, which is why vtable slots, strings and family membership carry the weight.
7. Grouped recurring families and named them as families:
   - `0x0028BCB0`–`0x0028CF34` — trail/ribbon mesh builders + dispatch
   - `0x0028E2A0`–`0x0028EAF4` — `fCol` / `exFCol` / `mesh` / `equip` object creation
   - `0x002AC4A0`–`0x002B7440` — list/select window pane init
   - `0x002D0B4C`–`0x002D274C` — sprite/anim list + resource lifecycle
   - `0x002D4F28`–`0x002D55B8` — character-shadow render pass and render-pass task
   - `0x002E18F0`–`0x002E3CA4` — battle popup manager (`Battle_Popup_Ensure*`)
   - `0x002EC50C` — battle action-animation window
   - `0x0030A0E0`–`0x0030AD54` — field "runway" environment

## Verification performed

## Open problems / not verified

- **Names are proposals only.** They are not merged into `decomp/native_names.json` or the readable
  C; no runtime or emulator check was performed. A `maybe_` name must not be treated as final.
- **Three bodies are Ghidra `halt_baddata`**: `0x2C4948` (`maybe_Ui_UnknownPaneSetupC`, 0.20),
  `0x2FB668` (`maybe_Ui_PaneSetupD`, 0.20) and `0x323F20`
  (`maybe_Ui_TwoTextWindow_InitPanesB`, 0.50 — the high byte is unrecovered but the pane calls are
  readable). Their exact roles are not established.
- **`0x2904A0` lost argument registers** in the Ghidra output, so only its shape (creates eight
  emitters) is known; name is `maybe_Effect_CreateEightEmitters` at 0.30.
- **62 functions have only `self` recovered**; any argument-level signature detail is inferred from
  callee usage, not from a debug ABI.
- **Most batch functions have no direct callers** in the decompiled tree (vtable/function-pointer
  dispatch), so call-graph evidence is sparse; class identity for the `maybe_*` constructors rests
  on base constructor + vtable slot only.
- **Lane tag mismatch**: `Field_and_World` does not describe this range. If the dispatcher uses the
  tag to route review, that label is misleading.
- **Ghidra string mis-decodes** (e.g. `4%x`, `4"x` instead of `1%x`): only plausible, confirmed
  literals were used as evidence; a few pane names may differ in one character from the source.
- Several entries share a generic "InitPanes" suffix because the exact widget class is not
  recoverable; they are correct about the step (pane wiring) but vague about the widget.

## Suggested follow-ups

1. Run the merge step (`M1_merge_names`) and regenerate readable C so the 67 entries at
   `confidence >= 0.50` become usable names; keep `maybe_` entries provisional in the progress
   tracker.
2. Re-disassemble the three `halt_baddata` functions from the raw ARM bytes (and check whether
   `0x323F20` is a duplicate/alias of `0x002E8608`, the other two-text window init).
3. Recover `0x2904A0` arguments by tracing its two call sites' register setup, then re-check the
   eight-emitter claim.
4. For the `maybe_*` constructors, scan the vtable → RTTI/class-name tables (or the
   `syscmn.bch` layout names) to promote them; that is the cheapest path to raising the 83
   low-confidence entries.
5. Sanity-check UI names by opening the corresponding layout assets and matching the pane strings
   (`gauge`, `ring*`, `select*`, `txt_l*`) against the live editor.
6. Consider relabelling the `N_003` lane (or documenting the mismatch in `PLAN.md`) so reviewers
   are not sent to field/world code that is not in this range.
