# N_004 — native naming batch (lane tag `Field_and_World`)

## Summary

Named and documented all **150** functions in `orchestration/naming/batches/N_004.txt`
(`0x003267D8`–`0x003EA420`) in `orchestration/naming/out/N_004.json`.

This was a resumed task, but **no prior output existed**: `orchestration/naming/out/N_004.json`
was absent, and `orchestration/logs/N_004.log` contained only a previous attempt reading
`orchestration/done/N_003.md` (its text is a copy of N_003's report) with no naming work. All 150
entries were therefore produced from scratch.

The lane tag says `Field_and_World`, which is only partly true: the first third of the range
(`0x003267D8`–`0x0036BAF8`) and several later blocks are **UI window pane wiring** built on the
shared cursor widget `drN` (`0x001A6520`). The rest is model/animation part construction, field
scene/actor code, monster behaviour subclasses, script int-table lookups, the battle action
animation table and a large UI/effect configuration block. Names follow the code, not the tag.

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `naming/TEMPLATE.md`, the batch file, and the
   N_001–N_003 outputs for naming consistency.
2. Built a per-function digest over all 150 readable C files (`decomp/readable/functions/`, and
   `recovered/` for `0x0035A1D0` / `0x003BB9F8`):
   signature, numeric calls resolved to names, named calls, callers (from a full call graph parsed
   out of all 18k readable files), `s_*` string tokens, resolved `g_*` literals (raw image word
   reads), and interesting constants.
3. Resolved every function's **vtable context**: scanned
   `original/exefs/code.decompressed.bin` for 4-byte pointers to each batch address
   (`file offset = address - 0x100000`) and dumped the surrounding slot table with all slot
   targets resolved through the merged name map. This identified ~60 functions as vtable slots
   (mostly slot 7/8 of the `0x00763xxx`–`0x0076Bxxx` UI/actor ladders, plus
   `0x007597AC`/`0x0075DED0`/`0x00782244` style tables).
4. Read the actual bodies of every non-trivial function (the large ones truncated to the first
   70 lines + targeted re-reads) rather than trusting the digest alone.
5. Resolved literal pointer tables in `.text` to recover the UI layout names, which are the main
   semantic evidence in this range:
   - `0x007AA5B8` → `txt_title`, `txt_l1..l8` + `_num1/_num2`, `txt_r1..r8` + `_num1/_num2`,
     `pager_num_l/r` (function `0x0032B948`);
   - `0x003749xx`/`0x00376Fxx` → `battleact`, `revival`, `avoid`, `escape`, `atkspell`,
     `revspell`, `escapeunsurround`, `skill_01..08`, `stskill_*`, `acskill_*`, `fjump`, `bjump`,
     `guard_st/lp/ed`, `atk1_start`, `use_item`, `poison_damage`, `move_landing`,
     `bat_tumble_end`, `combination*`, `weapon_guard`, `shield_guard`, `resurrectionspell`,
     `supportspell`, `cutin`, `cskill_01..16`, `cstskill_*`, `cacskill_*` (function `0x003744C8`);
   - `action`/`nut`/`run`/`atk`/`dmg`/`protect`/`break`/`dead`/`end` (`0x0032CD24`),
     `action`/`nut`/`move`/`dash`/`jump`/`auto` (`0x003E6618`/`0x003E6634`),
     `open1..3`, `open_in1..3`, `skill_1..3` (`0x003994F8`),
     `ten_in`/`ten_loop`/`ten_out` (`0x003A5294`),
     `icon_box48.bin`/`icon_msg40.bin` (`0x00383764`),
     `equip` (`0x003D4834`), `Dragon_Jump` (`0x003E5008`), `meshHorse` (`0x0036671C`),
     `meshWeapon`+`R_Weapon`+`meshAcc`+`Head` (`0x003823EC`), `collision` (`0x003663E0`,
     `0x003E8E1C`), `effect0..6` (`0x003D4600`), `icon_d1..3`/`win_d1..3` (`0x003D2194`).
6. Used named vtable slot siblings from N_002/N_003 to pin subsystem and role
   (`maybe_Actor_UpdateTurnAnimation`, `maybe_Actor_UpdateAimPoseIK`,
   `maybe_Ui_ObjectBase_Ctor`, `maybe_Anim_ObjectBaseCtor`, `maybe_Anim_Clip_Update`,
   `Battle_ActionAnimWindow_Init`).
7. Worked bottom-up: identified the helpers `drN` (`0x001A6520`), `ToD` (`0x001D863C`), the pane
   attach helper `0x003E00CC`, pane show/hide `0x003DFF34`, flag registration `0x003DF9AC` /
   `0x003DFA44`, resource bind helpers `func_0057B988`/`0x0055E2A8` etc., then named the callers.
8. Grouped recurring families and used suffixed family names rather than inventing distinct
   classes: `..._InitPanes`/`..._InitPanesB/C`, `Gfx_ModelPart_Init*`, `Gfx_SpriteActor_AddChild*`,
   `Model_Bind*Resource`, `Field_CollisionObject_Init/B`, `Field_HitBox_Setup/SetupFloat`,
   `maybe_Monster_ActionBehaviorCtorA..D`, `Battle_ActionAnimObject_CtorA..D`.

## Verification performed

- All 150 batch addresses are present in the JSON **in exact batch order**, no duplicates.
- Every object has `address`, `name`, `signature`, `params`, `summary`, `confidence`, `evidence`.
- `params` is normalised to `param_1..param_N` for all 150 (keys match the argument positions).
- The function identifier in every `signature` equals the entry's final `name`.
- Addresses are `0x%08X`; names match `Subsystem_VerbNoun` / `maybe_` + name; no duplicate names.
- **Zero** confidence/prefix violations (checked mechanically).
- No name collides with a name already present in `symbols.json`, `symbols_recovered.json`,
  `decomp/native_names.json` or the N_001/N_002/N_003 proposals (checked mechanically).
- All 150 readable-C paths from the batch file exist (checked mechanically).
- Spot re-reads of the produced JSON against the source bodies for
  `0x0032B948`, `0x0032CD24`, `0x003744C8`, `0x003823EC`, `0x003A5294`, `0x003B5914`,
  `0x003E5008`, `0x003E6634`; pane-name tables were re-resolved from the raw binary rather than
  taken from the digest.

## Open problems / not verified

- **Names are proposals only.** They are not merged into `decomp/native_names.json`,
  `symbols.json` or the readable C, and no emulator/runtime check was done.
- **`0x0034354C` and `0x00384C80` are effectively unknown bodies** (`halt_baddata` / lost Thumb
  registers). Both names are placeholders at 0.20 and 0.15.
- **`0x0035A1D0`** is a recovered entry point with most argument registers lost; its name only
  records that it belongs to the three-function scene-spawner block.
- **`0x00352DBC`, `0x00353074`, `0x0035A1D0`**: the factory call set (field actors, map objects,
  effect emitters, model parts) is certain, but "SpawnByType" is an interpretation of the type-id
  switches (`0x1044`…`0x1281`); the exact descriptor format of `func_0066AA7C` was not decoded.
- **`0x003C2120`** is a very large object (`+0x2200` fields) that I could only characterise as a
  screen/manager; "maybe_Ui_ScreenManager_Ctor" is a guess at 0.30.
- **Sprite/template factories `0x00335A6C` / `0x00335F04` / `0x00336054` / `0x003361D8`**: the
  object layout and frame-rect copy are clear, but the exact class ("sprite actor child") is
  inferred from the `trap` literal and the 2D-sprite ctor; `0x00336054` additionally lost
  registers (halt_baddata), so its 38-argument signature is not real.
- **UI class identity** for the generic `..._InitPanes` entries is limited to what the pane names
  imply; e.g. `Ui_EquipmentListWindow_InitPanes` (`0x003653C0`) is named from the `txt_e` column,
  which could stand for something other than equipment.
- **`0x003820A0`** attaches `meshAcc` but the target node is only proven by the sibling
  `0x003823EC` (`Head`); its own body does not name the node.
- **Lane tag mismatch**: `Field_and_World` does not describe a range that is ~43% UI.
- A number of names end in `_InitPanes` because the exact widget class is not recoverable; they
  are correct about the step (pane wiring) but vague about the screen.
