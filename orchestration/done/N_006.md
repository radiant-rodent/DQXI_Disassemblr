## Method

1. **Corpus index** over all readable C (`functions/` + `recovered/`): address → file, address →
   callees, inverted caller map, plus a name map merged from `symbols.json`,
   `symbols_recovered.json`, `decomp/native_names.json` and **all** existing
   `orchestration/naming/out/*.json` (N_001–N_004), so established vocabulary
   (`Mem_AllocAligned`, `Gfx_CreateMeshObjectByParams`, `Ui_ApplyTextColor`,
   `Battle_ActionAnimWindow_Init`, `maybe_Ui_CursorWindow_Init`, …) is reused rather than renamed.
2. **Literals.** Every `s_xxx_00xxxxxx` / `g_00xxxxxx` in a function was resolved against
   `original/exefs/code.decompressed.bin` (offset = address − `0x100000`), recovering the real
   pane names, error strings and float/int constants. (Caveat found and applied: a `g_` in a
   literal pool is sometimes a *number* that happens to look like a short string, e.g.
   `0x00593058`/`0x003D2528`; those are described as numeric ids, not pane names.)
3. **Vtable membership.** Every batch address was searched for in the binary's 4-byte word stream;
   when it appears inside a vtable the slot index and the neighbouring slots were resolved to
   names. This is what separated "Init" (`slot 7/8` of a window vtable) from "CreateChild"
   (`slot 1` of an effect-node vtable) from "constructor not in any vtable".
4. **Registration sites (the key trick for this batch).** Grepping the corpus for a batch
   address and printing the *calling line together with its string arguments* recovered the action
   names: e.g. `func_00484D3C(..., s_guard_st_00375354,1)` in `0x003744C8`, or
   `func_006D5DE8(piVar7,self,0x95,s_counter_act01,1)` which identifies `0x00484C70`. 21 battle
   action classes and 4 monster action classes were named exactly this way.
5. **Layout cross-check.** For every Ui init, the pane names from step 2 were looked up in
   `game_assets/layouts/**/*.bflyt.json` (pane list per layout). A pane set that occurs in exactly
   one layout names the window (table above); common pane sets (`txt_lN`, `pager_num_l/r`) were
   deliberately left generic.
6. **Bottom-up.** `drN` (`0x001A6520`, shared Ui window base ctor — matches the N_004/N_005 usage),
   `0x003E00CC` (bind pane by layout name), `0x003E043C` (show/reset pane), `0x003DFF34`
   (enable pane), `0x0053D4C4`/`0x0053D604` (child lookup/creation), `0x005F6C4C` (transform),
   `0x004AE7FC` (colour block), `0x0028E754`/`0x0028E940` (mesh / fCol animator),
   `0x00336054` (sprite child), `0x0020002C`/`0x001FF200` (screen object alloc/init),
   `0x00322CC8`/`0x0038ACEC`/`0x002B09BC` (three shared battle-action base ctors).

Progress was not checkpointed every 25 entries because the whole batch was completed in one pass;
the file was written once at the end after a coverage check (`missing []`, `extra []`, `dups []`).

   each wraps one ctor from this batch. Mapping factory → owning screen would turn the 16
   `maybe_Ui_ScreenCtor_vt…` entries into real screen names. The 3DS scene enum is probably in a
   BXON table or in `game_assets/scripts/`.
3. **Effect/sprite class table** (`0x75B0B0`–`0x75B240`): 7 child classes and 10 sprite-desc
   initialisers all await the same identification; look at the 3D effect `.pack` names
   (`2d/battle2/parts_effect/%s.pack` was found in this range) for a name→class mapping.
4. **Battle action registry**: `0x003744C8` and `0x002EC50C` register ~120 action classes with
   `(id, name, flag)`. Only the classes that fell in this batch were named. A dedicated pass over
   both registries would name the remaining ~90 action classes in other batches consistently.
5. **Layout-name recovery for dynamic panes**: many pane names are generated at runtime
   (`select%d`, `pop_damage%d`, `%s_sl`). A small index of "pane name patterns" per layout would
   let future batches resolve them automatically.
