## Method

1. **Index.** Parsed all 18,159 readable C files (`decomp/readable/functions` +
   `decomp/readable/recovered`) into address → file, address → callee set and the inverted
   caller map. Every batch entry had a readable C file, so the `decomp/ghidra/` fallback was
   never needed. (Some entry points are merged into a neighbour in Ghidra, e.g. `0x005F50DC`
   lives inside `0x005F5078`; that was checked explicitly when a callee had no file.)
2. **Name map.** Merged `symbols.json` (which is `{project, version, symbols:[…]}`),
   `symbols_recovered.json`, `decomp/native_names.json`, `decomp/functions_index.json` and
   **all** existing `orchestration/naming/out/*.json` (N_001–N_005), so the batch reuses the
   established vocabulary (`Mem_AllocAligned`, `Ui_LoadIconTextures`,
   `Battle_ActionAnimTable_Build`, `Battle_ActionAnimWindow_Init`, `maybe_Ui_ScreenController_InitChildren`,
   `maybe_Ui_ListSubObject_BaseCtor`, `Gfx_CharShadowPass_Init`, `maybe_Sound_InitPlayers`, …).
3. **Literals.** The readable view already names string labels (`s_txt_l1_004f8e1c`); the
   suffix is the **address of the bytes themselves** (they sit inline in `.text` after the
   function), so every literal was resolved by reading a NUL-terminated ASCII run at that
   address in `original/exefs/code.decompressed.bin` (file offset = address − `0x100000`).
   Nine functions had usable literals; those are the highest-confidence names in the batch.
4. **Vtables / class tables.** For the C++-style objects the decisive evidence is the first
   store (`*self = g_XXXX`, a `.data` pointer). Grouping by that vtable gave the class families
   and let me name sibling constructors consistently, following the precedent already in the
   naming outputs (`Ui_ScreenCtor_77C648`, `maybe_Ui_SceneObject_Ctor_77AE08`). There is **no
   RTTI** in this binary (vtable[-1]/vtable[-2] are zero), so a class name can only come from
   behaviour, literals or the script-side factory.
5. **Script-side factories.** A very useful find: `0x006C2070`–`0x006C2xxx` is a table of
   *script native-class factories*. Each one does `Mem_Alloc(size)` and then calls one batch
   constructor, e.g. `0x006C21B8` allocates `0x193C` bytes and calls `0x004F697C` or
   `0x004E1D84`, and `0x006C23DC`/`0x006C243C` call `0x00590CF4`/`0x00591010`. That both proves
   these are script-visible classes and gives a size class per constructor. It also explains
   the many "only caller is 0x6C2xxx" entries and why so many functions in this range have no
   ordinary callers at all.
6. **Bottom-up helpers** identified once and reused in evidence:
   | helper | role |
   |---|---|
   | `0x001A6520` (`drN`) | shared UI base-window initialiser (used by every `…_InitPanes`) |
   | `0x003E00CC` | bind a named pane to a window |
   | `0x0020002C` | shared C++ base constructor (two vtables at +0 and +0xB0) |
   | `0x003CAE00` | 0xDE18-byte object base with a 96×0x1B0 pool |
   | `0x00597C90` | 0x1800-byte object base (UI-list flavour) |
   | `0x001FF200` | trailing object initialiser (`+0x50` + handle = −1) |
   | `0x0038ACEC` | UI list sub-object base → battle action-anim element ctors |

   | `0x00109DC8` | `Mem_AllocAligned(size, heap, align)` |
   | `0x0011B57C`/`0x0011B89C` | allocate + enqueue a thread-queue node (tag byte at +4) |
   | `0x00111CD8`/`0x00111E28`/`0x00111D50` | mutex / condition / lock helpers |
