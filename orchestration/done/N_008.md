# N_008 — naming batch 008 (`0x005D19B8`–`0x006D5E84`, 150 functions)

**Status: completed.** Output: `orchestration/naming/out/N_008.json` (150 entries, batch order).
No previous worker output existed (`orchestration/naming/out/N_008.json` and this report were both
absent), so all 150 addresses were named from scratch.

## What I did

**Method.** I built a per-address dossier from the readable C (`decomp/readable/functions` +
`recovered`), an inverted caller map over all 18,159 readable files, a callee name map merged from
`symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and every existing
`orchestration/naming/out/N_*.json`, and resolved every `g_`/`DAT_` reference against
`original/exefs/code.decompressed.bin` (`offset = address - 0x100000`). Because most of these
functions are dominated by literal-pool loads, resolving the literals was what actually made them
readable: it turned `g_005d1db4` into `1.0`, `g_006c04e0` into `0x1388` (a class size), `g_006c04e4`
into `0x760C08` (a vtable) and `g_0072d564` into the string `"<ix"`.
I also disassembled the call sites with capstone (`asm/` text is misaligned around literal pools,
which is what produced the batch's off-by-4 addresses — see below).

**Two findings that carry most of the batch**

1. `0x006C0460`–`0x006C2D4C` (80 of the 150) are **object factories behind two dispatch tables**.
   `0x7A4338` holds 1,375 function pointers indexed by a `u16` type id, `0x7A4268` holds 52 pointers
   indexed by a `u8` kind id. The spawn loop at `0x169A4C`/`0x169B48` does
   `ldr ip,[table, id, lsl#2]; blx ip` with `r0 = map+0xB4` (allocator context), `r1` = owning map,
   `r2` = id, `r3` = *(system+0x4244) == 1*, then stores the id at `object+0x1230` and links the
   object into the map list at `+0x10C`. Every factory has the same shape: `Mem_AllocAligned(<class
   size>)`, constructor, vtable store, two state words, and finally `owner` at `object+0x122C`.
   The `r3` flag is the game's **2D/3D mode** switch (`*(system+0x4244)`: `0x0027D6E4` branches on
   the same byte with `func_003D2084` vs `func_003D22A8`), so each type has a 3D class and a 2D
   class. Three factories are the defaults for most ids and are named by what they construct
   (`Field_ObjectFactory_MonsterModel` = 668 ids, `Field_ObjectFactory_GameObject` = 149,
   `Field_ObjectFactory_Actor` = 524); the rest are `Field_ObjectFactory_Type####` /
   `Field_ObjectFactory_Kind##`, the id being the value the game actually stores.
   *Conflict recorded:* N_007 called this block "a table of script native-class factories". I
   disagree and say why in each entry's evidence: the table is indexed by a runtime id taken from a
   record and the result is linked into the caller's scene list, not registered with Squirrel.
2. `0x0061BEBC`–`0x006201C0` are the **font layer**: `%s.binst` binary font resources,
   `%s_loop` companion textures, 0x40-byte per-glyph metric records, metric reads through the BXON
   int tables (`Script_GetIntTable1/2/3`), and three font slots (`+0x174`, stride 8).

**Distribution:** Field 92, Sound 16, Ui 13, Gfx 13, Font 6, Model 3, Battle 3, Effect 1, Script 1,
Monster 1, Anim 1. Mean confidence 0.512; 34 entries below 0.5, all `maybe_`-prefixed; only one
entry reaches 0.7 (`0x00617844`, three literal pane names).

**Notable individual results**

* `0x00617844` `Ui_CheckListWindow_InitCheckIcons` — creates `icon_check_mark`, `icon_check_base`,
  `icon_rarity_gold`; called by three different check-list windows' `InitPanes`.
* `0x00658D18` `Field_Clock_ConvertTimestamp` — ticks → packed date/time (86,400,000 ticks/day,
  weekday via mod 7, epoch `0x7CFC8400`).
* `0x0063AD40` `Anim_Clip_IsFinished` — recursive child-list walk plus a duration compare.
* `0x0062A860`/`0x0062A90C` — the position/direction queries used by all four
  `Gfx_TrailMesh_Build*` variants.
* `0x005EA734`/`0x005EA950`/`0x005EAA8C` — the streaming sound player setup/release pair, sized by
  `Sound_ArchiveStream_Calc*` (`0x65E660`, `0x65E7C4`), which is where the 0x5C/0x40/0x138/0x2D8
  memory layout comes from.
* `0x006B87F0`, `0x006B8BB0`, `0x006B8F8C`, `0x006B9B88`, `0x006B90A8` — five two-store
  "register allocator callback pair" functions filled by `Gfx_InitVramBanks`, consumed by
  `Gfx_Vram_AllocEntry`/`Gfx_Vram_FreeEntry`.
* `0x005D19B8`/`0x005D22E4` — I first took these for glyph-quad builders (the batch's neighbouring
  `0x5D0714` is named `Font_GlyphQuad_CreateFromDescriptor` by an earlier batch). Reading the code
  refuted it: the loop steps over 2-byte entries with a 12-case *kind* switch (`0..0x0B`, not a
  character set) and positions them at `(0,0,125-5*i)`. They are now
  `maybe_Ui_ObjectList_BuildEntries`/`Clear` (0.4/0.45), and I wrote the refutation into the
  evidence so `M1_merge_names` does not have to redo it.

**Address quirk worth knowing:** ~30 of the 0x6C factories are listed in the batch (and in Ghidra) at
`entry+4`. The real entry point is the table value, e.g. table `0x6C23D8` vs. batch `0x6C23DC`: the
compiler hoisted `cmp r3,#0` in front of `push {r4,lr}`, so the prologue scan started 4 bytes late and
the decompiled body lost the `arg4` test (`if (in_ZR)` in the C). I mapped table values with `a` and
`a-4` to compensate, and every factory entry names the table slot so the true entry is recoverable.

## Open problems / not verified

* Names are not merged into `symbols.json` or the readable C — that is `M1_merge_names`.
* No emulator or hardware check, so no name is confirmed by observed behaviour.
* The meaning of the id space behind the two factory tables is inferred, not proven: 0..1374 looks
  like map placements / actor records (5 records per row, `0x8C` bytes per record, owner back-pointer
  at `+0x122C`, layer index at `+0x124`), but it could equally be party/monster actor records. The
  factory mechanism itself (table → class, 2D/3D variants) is proven.
* `maybe_Ui_ObjectList_BuildEntries` (`0x5D19B8`) and its siblings at `0x5D23D0`/`0x5D2AA0`/
  `0x5D32A4` build three parallel sub-lists of one window (`+0x1570`, `+0x1D7C`, `+0x1FDC`, validated
  together by `0x668BBC`) whose owner screen is unknown. That is the biggest single gap in the batch.
* `0x60260C` and `0x6042F0` are vtable-only (slots 0xE8 and 0x28) and their naming rests on the
  shared 0x43C864 track-node helper, so they are 0.35.
* `0x6232D8` copies a 32-word block to fixed offsets `0x20..0xA0` — I read that as a PICA200
  TEV/texture register upload, but Ghidra's `_DAT_` output for it is too distorted to be sure.
* 5 of the 6 `Gfx_Vram_SetAllocator*` names are positional (A–D); only the globals and callers, not
  the bank roles, are proven.
