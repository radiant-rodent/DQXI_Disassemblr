## Method (repeatable)

1. **Callers**: for each batch address, grep all 18,748 `decomp/readable` files for the
   `func_XXXXXXXX` token, then read the caller's readable C.
2. **Class identity**: for the functions that are never called directly, locate the address in the
   `.word` stream — all 8 of the `0x6E65F4`-family / `0x6E7220`-family slots live in descriptor
   tables in `asm/rodata/rodata_00765000.s`. To identify what those classes are, dump the *other*
   slots of the same descriptor (e.g. the one-instruction "name accessor" at slot +0x74 /
   the `.bflyt`-name accessors around `0x64D5xx`).
3. **Inline literals**: Ghidra loses `add rX, pc, #imm` strings, so the literals were decoded from
   `original/exefs/code.decompressed.bin` at the address the `add`/`ldr` targets
   (`0x65424C/5C/70` → `queen` / `freespin` / `metalchange`; `0x7C2ACE..` → `g3101_1_out` …).
4. **Asset cross-check**: every recovered string was matched against `game_assets/layouts`,
   `game_assets/models`, `game_data/packs`; the BCH of `g3101a` literally contains
   `g3101_1_in/1_out/2_in/3_in/4_in/5_in`, which is what makes the five panel panes identifiable.
5. **Bottom-up naming**: `Container_StringHashMapInsert` (already named in N_002) → its tree
   primitives `0x6F322C/333C/359C`; `maybe_Container_LookupType4Value` (N_006) → the typed handle
   resolver `0x71342C`; the shared string helpers (`0x11CCA0` strlen, `0x100990` strncat,
   `0x10540C` strcmp) were verified in asm rather than assumed from Ghidra names.

## Open problems / not verified

1. **The five panel panes (`0x006E65F4..0x006E68EC`) are byte-identical.** Only the animation name
   their descriptor returns distinguishes the classes, and the owning screen is unknown (the model
   `g3101a` is a 1×1 UI quad with no layout referencing it; it is loaded by code). Their names are
   therefore positional (`1Out`, `1In`, `2In`, `3In`, `5In`) — a `g3101_4_in` sibling exists at
   accessor `0x64D558` but is outside this batch. If a later batch identifies the screen, these five
   names should be renamed as a family together.
2. **Casino initialisers**: `self->f_4` is used as the resource manager passed to `0x53D604`; its
   type is not established, and I did not prove whether `queen`/`freespin`/`metalchange` resolve to a
   BFLYT layout, a BFLAN animation set, or a combined resource. The names are solid; the exact
   resource kind is a hypothesis (animation player, because `0x536424` binds element 0 of a
   0x24-byte entry table).
3. **`0x006F333C`**: the `node+0x10` adjustment is Ghidra modelling a second map instantiation whose
   payload embeds a base; the owner of that map is not known.
4. **`0x00707A7C`**: semantically a "insert text at offset" on the small-string layout, but the
   public API it belongs to (a `std::string`-like helper vs. a local path/format builder) and the
   exact meaning of `arg4` (length cap vs. flag; callers pass 1) are unproven.
5. **`0x0071342C` / `0x0071371C`**: the registry is understood mechanically (page table at
   `0x007BA2D0`, type id in BSS at `0x007C8584` / `0x007C5214`), but *which* class the type id
   represents is only inferred from its consumers (pack-info objects with `f_90->f_60/f_6c/f_78`
   name arrays). The `f_78 == 4` object kind is the same one N_006 documented as "type 4".
6. **Broken sibling output (needs fixing before M1):** `orchestration/naming/out/N_012.json` is
   **invalid JSON** — an unescaped newline inside the `summary` string at line 624/625 and trailing
   extra data at line 1384 (`Extra data` on parse). It will abort `M1_merge_names` unless repaired.
   I did not touch it (not my file).
