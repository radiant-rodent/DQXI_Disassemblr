# N_010 — native function naming (150 functions, 0x0010F6BC … 0x001BB13C)

Lane label from the batch file: `UI_and_Message`. Range: `0x0010F6BC`–`0x001BB13C`, 150 entries.

## What already existed

Nothing. There was no `orchestration/naming/out/N_010.json` and no `orchestration/done/N_010.md`,
so the previously stopped worker left no output. All **150 of 150** addresses were named from
scratch in this session.

## Method

1. **Corpus index.** Indexed all 18,367 readable C files (`decomp/readable/functions` +
   `decomp/readable/recovered`) by address, extracted each body's calls, and inverted it into a
   caller map. `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and every
   existing `orchestration/naming/out/N_*.json` were merged into one address → name map.
2. **Callers from the assembly.** Many entries here have *zero* decompiled callers, so I also
   parsed every `asm/text/*.s` line into an address → `bl`-target map and attributed each call
   site to its containing function via `functions_index.json`. This recovered real callers for
   `0x1160AC`, `0x11CFE0 → 0x120464`, `0x15698C` (every `*MessageSetup` native), `0x15BCAC`,
   `0x1772C4`, `0x179xxx`, `0x17DAD8`, `0x184EF8`, `0x1856EC`, `0x18F374`, `0x19xxx` and others.
3. **Script-native registration table (new, reusable finding).** `.text` embeds the Squirrel
   native table at `0x0024A304`–`0x002531CC`. Each entry is
   `{ u32 wrapper_thunk, u32 implementation, char name[] (4-byte padded) }`, e.g.
   `0x24A304: 0x00706EAC 0x0015154C "IEMessageSetupEx"`, and
   `0x24CFF4: 0x006FA610 0x0015D074 "GetActorIDFromUniqueID"`. This is what makes the
   `0x0014xxxx`–`0x0016xxxx` range legible: the *registered* address is a tiny stub that either
   validates arguments and **falls through** into the implementation, or tail-branches to it.
   Verified examples:
   `0x14868C StartFadeIn` → `0x148698`, `0x14A9AC StartFadeOut` → `0x14A9B8`,
   `0x152E04 StartDelayFadeIn` → `0x152E14`, `0x155564 StartDelayFadeOut` → `0x155574`,
   `0x147D68 ChangeUIMap` → `0x147D70`, `0x158E84 StartShiftFadeColor` → `0x158E90`,
   `0x158994 IsEndShiftFadeColor` → `0x158998`, `0x14C2B4 GetMovieFrame` → `0x14C2B8`.
   Seven entries in this batch are the implementations of those natives and are named after them
   (confidence 0.6–0.8). **This table is the best handle for future naming batches**: search the
   whole `.text` for `name\0` runs preceded by two plausible code pointers.
4. **String / constant resolution.** Every `s_*` literal was taken from the readable C; the few
   unnamed ASCII literals (`"fast"`, `"disabled"`, `"normal"`, `"opened_in"`, `"opened_in2"`,
   `"opened"`, `"seal"`) were read straight out of `original/exefs/code.decompressed.bin`
   (file offset = address − `0x100000`). The leading byte of those UI-animation strings is a
   length/format byte, hence the `+1` in the assembly.
5. **Bottom-up families first**, then callers:
   * `Pack_ReleaseHandle` (`0x12416C`) / `Pack_FreeHandleEntry` (`0x1241D0`) — generation-tagged
     `index<<12 | gen` handle table with refcount + free list; used by every resource consumer.
     This fixed the reading of the four release-chain helpers (`0x120408`, `0x120454`) and of
     `0x124904`/`0x1249E0` (table loaders feeding `0x120464`).
   * Shared UI helpers reused from other batches (`0x1A6680` layout-animation start,
     `0x1A6768` animation finish, `0x1D85EC` pane creation, `0x1235A4` list link,
     `0x29126C`/`0x291220` window create/destroy, `0x10F69C`/`0x10F6CC` engine delete,
     `0x21F738`/`0x21F8B8` object registration/release, `0x6F229C` UI-context accessor).
   * Field/map grid cluster (`0x179084`, `0x179144`, `0x179154`, `0x1798D0`, `0x17C8D8`,
     `0x17CBAC`, `0x17CC38`) named from the shared 0x98-byte `MapGrid` singleton, level-revision
     check and wrapping instance counter.
   * `Ui_WorldMap_*` (`0x17CF50`–`0x17FE68`, 10 entries) from the `ui_map_*.bxon` and
     `world_map/%c%s.arc` literals.
   * Text engine (`0x1901F4`–`0x198314`): line-glyph buffer (24 glyphs), font-record apply,
     four-line layout, cursor blink, control-tag dispatch (`0x1F076C` word-dictionary slot 5).
   * Item/equipment window (`0x198774`–`0x19C164`): all thirteen `win_dougu_*` pane literals.
   * Message-window close family (`0x19E2D4`–`0x1A00D4`): fifteen variants, each releasing one
     sub-system and then calling the text manager (`0x625E00` / `0x625FD8`).
   * Layout-animation part helpers (`0x1B8410`–`0x1BA12C`) from the `"fast"/"disabled"/"normal"/
     "opened_in"/"opened_in2"/"opened"/"seal"` literals; `Ui_AttachLayoutAnimation` is the
     shared slot allocator, `Ui_AttachLayoutAnimationEx` its second slot bank.
6. **Save cadence.** The JSON was rebuilt from a scripted source; it was written in full after
   each cluster (not only every 25), so a resumed worker always finds a valid file.

## Not verified / open problems

* Names are **not merged** into `symbols.json`, `decomp/native_names.json` or the readable C;
  that is the `M1_merge_names` step. Nothing was rebuilt, booted or emulated.
* **`0x0010F6BC`–`0x00120464`** (allocator/SDK): the block layout (`begin/+4`, `size/+8`,
  flags/`+C`, refcount at `-8`) is clear from the code, but the allocator's owner (which heap)
  and the SVC used by `0x1193AC`/`0x11F65C` (SVC #0x32) are not identified. 8 entries stay
  `maybe_` at ≤0.45.
* **`0x00153328`** (0x85C) is a big transition state machine with no caller and no string; named
  `maybe_Ui_FadeController_Update` at 0.30 — the weakest entry in the batch.
* **`0x0014DBAC`** is a genuine 2-instruction thunk (`bl 0x63B368; pop {r3,pc}`); its script
  name is not recoverable from any table, so it is documented as a thunk instead of invented.
* **Character-look cluster** (`0x18DC74`/`0x18DC98`): the `0x1F076C(id, value)` global string/
  value registry and the +1/+4/+0x17/+0x67/−0x69/+0x61 part-id mappings are proven, but whether
  the ids are character-creation parts, button bindings or word-table slots is inference (0.35).
* **`0x1832D4`, `0x19536C`, `0x1A1AA4`, `0x1A27B0`/`0x1A2D94`, `0x1B65EC`, `0x1BABC4`/`0x1BB13C`**
  are multi-stage controllers whose *mechanism* is documented (flags, callees, state counters)
  but whose owning screen/script name is inferred; all are `maybe_` at 0.30–0.45.
* The 15 `Ui_MessageWindow_Close*` entries are distinguished by *which sub-system they release*
  (emote, balloon, pager, gauge, choice, name-tag, …), not by which script call site uses them;
  the per-variant script names are not in the registration table.
* `orchestration/naming/out/N_014.json` is not valid UTF-8 (byte `0x97` at offset 20828) and will
  break a naive `M1_merge_names` reader. `N_012.json`, which N_009 reported as broken, now parses
  fine. (Neither file is mine to edit.)

   byte currently makes it undecodable).
2. **Document the native registration table** (`0x0024A304`–`0x002531CC`, 8-byte header +
   inline name, 4-byte padded) as a tool: `tools/native_table.py` could dump
   `name → wrapper → implementation`, which would immediately give exact names for the
   `0x0014xxxx`–`0x0016xxxx` impl functions across all batches. Many of the `maybe_` entries in
   this batch sit next to an unnamed-but-registered neighbour.
3. A **`Ui_MessageWindow_*` family pass** that reads the 15 close variants together with the
   `*MessageSetup` natives' state field (`f_1D`) would turn the variant names from "what it
   releases" into "which message mode it ends".
4. Identify the **`0x1F076C` value registry** (ids 0..0x20; slot 5 is the word dictionary,
   slots 7–12 take character-part ids, slot 0xD an extra id). Once its consumer (`0x61xxxx`?)
   is found, the character-look cluster can go above 0.5.
5. Optional: name the **allocator pair** (`0x110A28`/`0x6BA234` and helpers) as one family in a
   dedicated SDK batch; it is the last large unnamed block below `0x00120000`.
