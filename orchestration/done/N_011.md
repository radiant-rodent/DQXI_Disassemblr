## Method

1. **Corpus index**: one pass over all 18,748 `decomp/readable` files building
   address → callers / address → callees, plus a merged name map from `symbols.json`,
   `symbols_recovered.json`, `decomp/native_names.json`, `decomp/functions_index.json` and the
   other batches' `orchestration/naming/out/N_*.json`.
2. **Bottom-up**: named the well-known leaves first (`Mem_AllocAligned`, `Message_SetArg`,
   `Container_StringHashMapInsert`, `Gfx_Resources_Release`, `EndUI`, `InnMessage`,
   `TalkStart`/`MessageEnd`), then read their callers with those names in hand.
3. **Strings are the strongest signal here** — the readable C keeps the Ghidra string labels
   (`s_shop_type_bxon_001c1798`, …). Every named window is anchored on at least one `.bxon`/`.bch`
   literal, and each literal was cross-checked against `game_assets/tables/packs/ui/**` and
   `game_assets/layouts/arcs/ui/**` to confirm the subsystem (e.g. `senreki` = 戦歴, the
   records/history menu: 216 layout files named `menu_senreki_*`).
4. **Squirrel cross-check**: `game_assets/scripts/**/script.nut` (316 scripts mention
   `MessageEnd`/`TalkStart`) confirmed the message natives and the open/close pair.
5. **Shared idioms identified once and reused**:
   `0x0011FE8C`/`0x0011CFAC`/`0x00116AE0`/`0x00627308` = sized allocation (lazy singleton `new`),
   `0x0012416C`/`0x001241D0`/`0x00124DD0`/`0x00124D48` = release/retain a refcounted handle,
   `0x0021F8B8`/`0x0021F738` = release/retain a heap object,
   `0x0036B45C` = UI update-node init (type byte + u16 layout id + sorted global list),
   `0x003E04BC`/`0x001A6768` = embedded-member destructor (`this-0xNN` chains),
   `0x0010F6CC` = operator delete, `0x006F229C`/`0x006F20C0` = game-work singleton, and
   `0x001C0F28(state, n, 0)` + `0x00311524`/`0x00311530` = UI state-machine step pick/commit.
6. **Families named as families**, not guessed individually: the six
   `Ui_MessageWindow_ReleaseChild*` vtable callbacks (`+0x18/+0x20/+0x24×2/+0x28/+0x30`), the
   `Ui_HandleSet_*` 9+3 resource-set functions, and the five `_Delete`/`_Dtor` pairs.

## Decisions taken (no orchestrator available)

- Batch order is preserved in the JSON (same order as `N_011.txt`) so a reviewer can diff it
  against the batch file directly.
- When a function's *class* could not be proven, the name states the observed *behaviour*
  (`Ui_RowList_ReleaseItems`, `Ui_HandleSet_IsReady`) instead of inventing a screen name. That is
  the "correct vague name beats a precise wrong one" rule.
- Two bodies are byte-level duplicates of another function in the batch (`0x001C44D0` duplicates
  `0x001C44A4`; `0x001E5DFC` duplicates the second half of `0x001E53F8`). They are kept as separate
  entries with a distinguishing suffix rather than renamed away, because both are real entry points.
- `0x001D03D0` and `0x001F2438` are recovered fragments whose prologues were merged into another
  function. Their bodies are one expression with `in_r3`/`unaff_r4`/`unaff_r5` register arguments;
  named `maybe_*` at 0.30 with that stated in the evidence rather than pretending to know the
  signature.

## Open problems / not verified

- Names are **not merged** into `symbols.json` or the readable C; that is `M1_merge_names`.
- No emulator or hardware check was done, and none is meaningful for a names-only output.
- The 0x00206BBC–0x00209DF0 group (`maybe_Gfx_Scene_*`) is the weakest part: the field layout
  (`f_423c`…`f_4d74`, list at `f_4260`) and the neighbouring `Gfx_BuildDisplayList` suggest a
  render-scene object, but nothing in its own body proves UI vs. general renderer. A future pass
  with the vtable resolved (as `N_006` did for Ui screen objects) should settle it.
- `Ui_HandleSet_*` (0x001BB368–0x001BC67C) is described as a generic "handle set" because the four
  probed handles and two child lists are never given semantic names by any caller; the class that
  owns them is unknown.
- `0x001DC080` is not UI: it is a system object teardown using `software_interrupt(0x23/0x24)`
  (CTR critical sections) and mutex/thread helpers. Named `maybe_Svc_Object_Shutdown` at 0.40; it
  probably belongs to the Kernel/threading subsystem and should be re-batched.
- `0x001D03D0` (`maybe_Svc_IsFeatureAvailable`) calls two merged entry points with no C body
  (`0x00503F58`, `0x00503F8C`), so what it queries is genuinely unknown.
