# N_012 — UI and message batch (150 functions, `0x00209F30`–`0x0025B9A4`)

## What the state was on arrival

## What I did

1. **Read the docs** (`README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`,
   `docs/CODE.md`, `src/README.md`) — they define the naming schema, the `maybe_` rule and the
   "readable C is a reading tree, not a build target" caveat.
2. **Literal-pool decoding.** Ghidra's C hides every string, float and hard constant. I wrote a
   small ARM scanner over `original/exefs/code.decompressed.bin` (image base `0x00100000`) that
   walks each function's `ldr rX,[pc,#imm]` / `vldr` instructions, resolves the pool word and prints
   it as a pointer, a float or a word. This is where most of the concrete evidence in the JSON comes
   from (`'win_camp_select%d'`, `'card0'`, `0.1f`, `0x0F0F0F0F`, …).
3. **Vtable reconstruction.** I built a map of every maximal run of code pointers in
   `.rodata`/`.data` (2 998 candidate vtables) and looked each batch address up. 26 of the 150 sit
   in an exact `vtable + slot`, which identifies their class, their dtor pair (slot 0 = complete
   destructor, slot 4 = deleting destructor — the ARMCC D1/D0 layout) and their siblings.
4. **Callers.** I ignored the readable C for caller analysis (it turned out to be misleading) and
   scanned the whole `.text` for `BL` to each address instead, then mapped each hit back to the
   containing Ghidra function. That gave real caller sets, e.g. `IsMenuActive` → `0x00217374`,
   `GrayOutLower` → the four dim/undim helpers, `SQCommand`/`ChangeEquipedItem` → `0x00254C20`.
5. **Bottom-up naming.** Leaf primitives first (`0x0025B658` = one layer-hide call,
   `0x00257FB0` = ring-buffer advance, `0x00217290`–`0x00217340` = the four dim/undim variants),
   then their callers, then the constructors/destructors of the classes they belong to.
6. Cross-checked against `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`, every
   other `orchestration/naming/out/*.json`, and the asset tree for the layout names.

### Framework knowledge recovered along the way (useful for later batches)

- `func_006F229C(buf)` is the **per-thread UI context accessor**: `ctx->[0x14]` is the renderer,
  `->[0x10]` / `->[0x1C]` are its two layers (vtable `+0xC/+0x1C/+0x28` = set-flag / set-state /
  set-state-pair, with the float pair 0.0/0.3 as the fade values), `->[0xC]` is the UI heap, and
  `->[0x94]` is a short "busy" latch.
- **`0x001A6460` is `SetOpen(bool)`, not a destructor.** It stores the bool at `self+0x12` and
  shows/hides the two layout parts at `+0x14` / `+0x64`. I initially mis-read it as a release; the
  C was checked and four entries were corrected before finishing.
- `drN` (`0x001A6520`) is the shared **window base init**; it also creates the selection cursor from
  `icon_cursor` / `cursor_select` / `cursor_disabled`.
- `func_001A5F9C(self, self == elem)` (`0x00259928`) is the **element selector**; passing 0 deselects.
- Object handles are `(generation << 12) | index` validated against an 8-byte slot table; the empty
  sentinel is `0xFFFFF000`.
- `0x0010F6CC` is the free/operator-delete behind every deleting destructor.
- The 8-byte-stride `{fn, 0}` table at `0x00726D08` is the **per-screen handler table**
  (`0x00209EF4`, `0x00209F20`, `0x00209F30`, `0x0020D458`, `0x0020D970`, `0x0020EF04`,
  `0x0020B798`, `0x0020B8C8`, `0x0020E27C`, …). Its second word is always zero; purpose unknown.

## Honest gaps / what is NOT verified

- **Two of the 150 addresses are not functions.** `0x00210880` is the loop tail of `0x002107B4`
  (verified in `asm/text/text_00200048.s`: `add r4,#1 / cmp r4,#0x120 / ble back`), and
  `0x0024039C` is literal-pool data holding `0x0076B520`/`0x0076B1D8`, not code. They are documented
  as such instead of being given invented semantics.
- **~15 class-neutral names are mechanism-level, not screen-level** (`maybe_Ui_DetachChildren`,
  `maybe_Ui_ReleaseSlotEntry`, `maybe_Ui_SingleLayoutObject_Dtor`, …). They have no layout string
  and no vtable slot, so the owning screen is genuinely unknown; the names describe exactly what the
  code does and nothing more.
- **Ghidra decode failures**: `0x002107B4`, `0x00244768`, `0x00241D0C` and `0x0025B9A4` contain
  bad-instruction data. I read `0x002107B4` and `0x00244768` from the assembly; for `0x00241D0C`
  and `0x0025B9A4` one branch each is still unread (the ctx payload handling and the flag-4 path).
- **Unrecovered jump tables** at `0x002A4A64` (`0x0025A3C0`) and `0x001DAB4C` (several `0x0025A7xx`
  message helpers) mean the page contents there are inferred from the call shape only.
- **Signatures are normalised.** Ghidra shows four arguments on many of these functions because it
  tracks `r3` into the `func_006F229C` stack scratch; where only `self` is actually read I wrote the
  single-argument signature and said so in the evidence. Struct types (`UiWindow*`, `BattleTextWindow*`)
  are descriptive placeholders, not declared types.
- The meaning of the second word in the `{fn,0}` handler table at `0x00726D08` is unknown (always 0).
- `maybe_Ui_UpdateAllSlots` (`0x002107B4`) iterates "up to `arg2` slots, max 0x120", but what the slot
  objects are is only partly established (they expose `vtbl+0xE8` accessor and a `+0x38` flag).
