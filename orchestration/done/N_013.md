## Method

1. **Index.** Parsed all 18,367 readable C files (`decomp/readable/functions` +
   `decomp/readable/recovered`) into address → body, address → callee set, address → referenced
   `g_`/`s_` literals, and the inverted caller map. All 150 had readable C **except**
   `0x00289B8C` and `0x002A48D8`, whose entry points Ghidra merged into `FUN_002134DC` and
   `FUN_0025A3C0` (exactly the two the batch file warned about); both were read from
   `asm/text/text_00240048.s`.
2. **Name map.** Merged `symbols.json` (a `{project, version, symbols:[…]}` document, not a flat
   map), `symbols_recovered.json`, `decomp/native_names.json` and **all** existing
   `orchestration/naming/out/*.json` (N_001–N_007, N_011, N_012). This reuses established
   vocabulary — `Mem_AllocAligned`, `Ui_CursorIcon_Show/Hide`, `Ui_MessageWindow_Open`,
   `Ui_MessagePage_Dtor`, `Ui_MessagePair_SetPanels`, `Message_SetArg`,
   `Ui_Setup*Window`, `Ui_*Window_InitPanes`, `Ui_StpassCallVipMsg_Create`.
3. **Literals.** The readable view already carries `s_<text>_<address>` labels; the suffix is the
   address of the bytes themselves, so every string was re-read from
   `original/exefs/code.decompressed.bin` (file offset = address − `0x100000`). This produced the
   highest-confidence names in the batch: the layout ids passed to the window manager.
4. **Call sites from the assembly.** 118 of the 150 have **no** decompiled caller — they are
   virtual slots. So I additionally scanned every `asm/text/*.s` for `bl #0xADDR` and for the
   address appearing as a data word. That found the handful of real callers (e.g.
   `0x002175BC` is a factory that calls `0x002849F0`, `0x00295AAC`'s class, `0x002B088C`;
   `0x00212298`/`0x00212508` call the two credit-model loaders; `0x00242564`/`0x002427D0`
   call the battle-history constructors) and confirmed that the `0x25Bxxx` cluster has *no*
   call site at all.
5. **Bottom-up helpers**, identified once and reused as evidence:

   | helper | role | how it was proven |
   |---|---|---|
   | `0x001D85EC(self, widget, "layout", id)` | register a child pane under a layout name | every `Ui_Setup*Window` (already named) uses it with `win_message`, `win_yesno`, `win_talk`, … |
   | `0x0029126C(pane, flag)` | pane show/hide | writes `pane+0x14` and the child's visible bit `+0x44` bit 0 |
   | `0x00123594(head, node)` | intrusive doubly-linked list append | pure pointer splicing on `head+0x110` |
   | `0x0062F070(self)` / `0x0010EBD8(self)` | child count / unlink first child | walk of the same `+0x110` list |
   | `0x00259928(self, node)` | reset child-list flag (`0x001A5F9C(list, a+0x838==node)`) | thin wrapper, 38 callers |
   | `0x001A5F9C(list, bool)` | notify every child (vtable `+0x1c`) | list walk |
   | `0x001A6768` / `0x003E04BC` / `0x001A6764` | the three embedded-widget destructors | set a vtable then free the `+0x38` child |
   | `0x001F0BE4(idx)` | **get message text argument** | getter into the `0x7ABEEC` singleton's 8-byte argument vector (count `+0x60`, base `+0x58`→`+0x24`); its sibling `0x001F076C` was already named `Message_SetArg` |
   | `0x001DAB30(widget, argRecord)` | bind an argument record to a pane | stores the record at `widget+0x28` then calls slot `+0x14` |
   | `0x0045D9F8(self)` | current record of an 816-byte-stride table | `self+0x50 + index*0x330`, index from slot `+0x44` |
   | `0x00109DC8(size, heap, 4)` | `Mem_AllocAligned` | already named |
   | `0x0010F6CC` | free | tail of every deleting destructor |
   | `0x006F229C` / `0x001D8B6C` | the two singleton/pool allocators used by all UI code | 0x98-byte aligned objects with a per-module vtable |
   | `0x0063AF08` | `table_0x72C778[index]` (colour/variant remap, `0xFF` = none) | `ldrd` of `{0,1,2,3,4,6,7,0xff}` then a byte index |
   | `0x001A6460` | widget flag setter (`strb r1,[r0,#0x48]` + anim bookkeeping) | disassembly |
   | `0x00100B74` | UTF-16 `strlen` | 2-byte stride until a zero halfword |
   | `0x003E04BC` chain idiom | "construct embedded sub-object at `prev − N`" | every composite ctor in this binary |

6. **Layout-name matching.** The strongest single lever: `0x001D85EC` is the pane registrar, so
   any function that calls it with literal layout ids is an `InitPanes`. Nine names come straight
   from this (`win_tsuyosa*`, `win_sakusen_*`, `menu_dive_*`, `menu_senreki_*`,
   `menu_training_select`, `win_boushi_shop`, `icon_top`/`icon_bottom`+`txt_1..4`+`txt_r`,
   `icon_rank_*`).

## NOT verified / open problems

1. **The `0x0072C788`–`0x0072CB3C` descriptor table.** The 22 entries in `0x0025BCA4`–`0x0025E65C`
   have **no direct call site anywhere** in the binary — no `bl`, no literal. The only reference
   is an 8-byte-stride `{function, 0}` array starting at `0x0072C788`, which the 7,748-byte
   constructor `FUN_0025EB88` copies into `obj+0x11c+0x374`, `+0x37c`, … when a per-object flag
   (`[obj+0x13c]`) is set. I could not prove what that table *is*. Best hypothesis: a per-instance
   method/constructor table for an inline "pane list" sub-object at `self+0x11c`. It refuses to
   look like a normal 4-byte vtable because *every other slot is 0*, which is why `Ui_*_Ctor`
   here is deliberately vague rather than claiming a class.
2. **The twelve `Ui_CompositeWindow_InitParts*` entries** (`0x002609E0`, `0x00264CF4`,
   `0x00293660`, `0x00299A28`, `0x0029A4D0`, `0x0029C42C`, `0x002A4838`, …) are 0x1B8–0x4B0-byte
   chained sub-object constructors. Their owning screen is unknown; only the *shape* is proven.
3. `0x0028DDB0` is now `Ui_SpriteSpan_Select` (not "NumberSprite") because the three pointers it
   rebases could be a number glyph **or** a generic rich-text span; callers include the damage
   popup but also several menu windows.
4. `0x002A48D8` (`maybe_Ui_Color_SetChannelOrder`) is the least certain call in the batch: the
   code builds a 4-byte colour plus a 0..6 channel-order byte list, but the semantics of
   `0x005AF920(i)` are unproven.
5. `0x00288AE0` and `0x00288990` are credited as credit-window frame selectors on the strength of
   the shared handle array at `+0x5a0`; that is inference, not proof.
6. Names are **not** merged into `symbols.json` or the readable C — that is `M1_merge_names`.
7. Nothing was built, booted or emulated. No test suite was run (naming batches are exempt per the
   task), so rule 5 does not apply here.
