# N_014 — name and document 150 native functions (UI/message region 0x002B0968–0x00316344)

## What I did

Resumed the lane from scratch: `orchestration/naming/out/N_014.json` did not exist and neither did a
partial notes file, so all 150 addresses were named in this session. Every address in
`orchestration/naming/batches/N_014.txt` is covered (150/150, batch order preserved).

Method (all read-only, no other files touched):

1. **Literal-pool resolution.** The readable C only shows `g_00XXXXXX` pool labels. I mapped every
   `g_`/`p_` reference of the batch through `original/exefs/code.decompressed.bin` (base 0x00100000,
   same address space as the symbols) and decoded each word as float / integer / string pointer /
   function pointer / vtable pointer. This is what exposed, for example, the resource names in
   `0x002BC32C` (`mainmenu_text.bxon`), `0x002EAC64` (`dive_*.bxon`), `0x0030E1AC`
   (`win_kyoukai_party` …), the animation clip names in the poker window ("flash1/3/4", "open",
   "open2/3", "poker_up_card_red/silver/gold"), and the 1/30 s frame step (0x3D088889).
2. **Caller index.** Every one of the 18,159 readable functions was scanned for `func_XXXXXXXX`
   references, inverted into an address→callers map, so the (many) functions that are only reachable
   through vtables still have documented callers.
3. **Vtable / descriptor-table membership.** For every batch address I searched `.data`/`.rodata` for
   the 32-bit function pointer, walked the surrounding run of function pointers and reported the
   table start, the slot index and the neighbouring slots (with their names from
   `symbols.json` / `symbols_recovered.json` / `decomp/native_names.json` / all `orchestration/naming/out/*.json`).
   This is where most of the class identity comes from: e.g. `0x002D8A9C` is slot 0 of the table whose
   slot 1 is the already-named `Ui_ItemListWindow_InitRows`, `0x002FC44C` sits next to
   `Ui_ItemMenuWindow_InitPanes`, `0x0030412C` next to `Ui_PokerWindow_InitPanes`, `0x002D2850`
   next to `Gfx_CharShadowPass_Init`.
4. **Named helpers read first (bottom-up).** I read the shared engine helpers before naming their
   callers, which is why several names are confident: `0x0010F6CC` (reference-counted free),
   `0x0021F8B8` (delete owned object), `0x00116AE0` (zero-fill), `0x00124E5C` (open resource by
   name), `0x0012416C` (drop reference), `0x0036B45C` (register in the priority update list),
   `0x001A6680` (set sprite frame), `0x003A7D78` (bind up to 32 textures), `0x003E04BC` /
   `0x001A6768` (container / intrusive-list destructors).
5. Every ~8/16 functions the JSON was rebuilt from the notes files and re-validated (resumability).

## Engine facts confirmed here (useful for the next batches)

* The 0x98-byte lazily created global at `0x007BE340` (guard `0x007BE33C`, count `0x00833F78`,
  vtable `0x00782A08`) is the shared **UI/engine manager**; ~40 functions in the binary bootstrap it
  with the identical inline sequence. `0x0031101C` is the "create and clear busy bit" variant.
* Vtable convention: the stored vptr points at the *offset-to-top* word, i.e. the first virtual
  function lives at `vptr+4`; destructor = slot +4, deleting destructor = slot +8, and
  `0x001D863C` ("ToD") is the draw/transfer-to-display virtual of the 2D widget base.
* `func_00124E5C(ctx, prio, name)` = open a named resource (returns the resource node); the entry id
  is at node[0x16]->f_20 and the resource type at `0x007E7250`.
* Timer pumps appear three times with identical code but different slot counts:
  12 slots at `self+0x35C` (0x002C1D60), 8 slots at `0x11C` (0x0030E810), 24 slots at `0x11C`
  (0x00316250), 5 slots at `0x120` (0x002E9614). The 1/30 s constant is the frame clock.
* The `win_kyoukai_*` layout family (0x002CE7C8, 0x0030E1AC) plus `win_gold`, `win_bind_select`,
  `win_kyoukai_2d3d` identifies the world-map / 2D-3D toggle screen; `flash*`/`open*` clips belong to
  the poker minigame window (0x00304084–0x003045FC).

## Open problems / not verified

* **No neighbouring names from N_013.** `orchestration/naming/out/N_013.json` is still missing, and
  N_013 covers 0x25BCA4–0x2B088C, i.e. exactly the constructors that immediately precede this batch
  (the constructor of the class whose deleting destructor is 0x002B0968 is at 0x002B088C). Several
  "class identity" gaps in 0x002B0xxx–0x002B8xxx would be resolved by that batch.
* **Class names are inferred, not proven.** Most entries are named from behaviour + vtable
  neighbourhood. Names like `maybe_Ui_Gauge_SetValue`, `maybe_Ui_GridCursor_CalcNextIndex`,
  `maybe_Anim2D_BindChannelSet`, `maybe_Ui_TreeWidget_Ctor` describe what the code does; the owning
  game screen is only a hypothesis. 107/150 are below 0.5 for this reason.
* **Three decompiler-corrupted entries** deliverately got behaviour-only names:
  0x002CF8C0, 0x002CF950 and 0x002CF9BE contain "control flow encountered bad instruction data" and
  fall into an inlined copy of the 0x002CF644 drawable destructor; 0x002CF9BE is most likely a
  mis-detected function start, not a real separate routine. They should be re-decompiled (fixed
  function boundary) before their names are trusted.
* **0x00304534** uses a name operand the decompiler could not recover (pool label 0x00304594), so its
  animation-clip name is unknown; the other four poker clips are proven.
* Two pairs are intentionally numbered instead of class-named because I could not distinguish their
  owners: `maybe_Ui_CreateChildWidget_11D8*` (three identical factories differing only in the
  post-init call) and the `maybe_Ui_PaneSet_Dtor_*` family (same generated destructor for different
  vtables); likewise `maybe_Ui_ApplyDisplayModeRect_*`.
* Not verified against a running game: no emulator/console check of any of these roles (nothing was
  changed in the binary, so no risk, but the names are static-analysis only).
