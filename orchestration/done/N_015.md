## Method (reproducible)

Built a throw-away analysis harness in `%LOCALAPPDATA%\Temp` (not added to the repo):

1. **Instruction index** — regex over all 25 `asm/text/*.s` files (1,689,993 decoded lines) into
   `{address: (mnemonic, operands)}`.
2. **Call graph** — every `bl #0x…` / `blx #0x…` gives a callee; inverted into a caller map. This
   matters because 90+ of the 150 functions have no direct `bl` caller (they are vtable slots), so
   "callers: (none in asm)" was treated as evidence itself.
3. **Literal/string resolution** — every `ldr rX,[pc,#imm]` *and* `add rX,pc,#imm` inside a
   function was resolved against `build/code.bin` (image base `0x00100000`; the file also carries
   `.rodata` + `.data`, so `addr-0x100000` works for all three). Printable NUL-terminated runs were
   decoded. This uncovered the short strings that Ghidra *and* my first pass missed because they sit
   in code tails as immediates, e.g. `"in"`/`"out"`/`"num1"` at `0x3190e8`/`0x3190ec`/`0x3190e0`,
   which is what identified the tween animation binding in 0x318F60.
4. **Name merge** — `symbols.json` (3 top-level keys → `symbols[]`), `symbols_recovered.json`,
   `decomp/native_names.json` and every existing `orchestration/naming/out/N_*.json`, so names from
   the other lanes (e.g. `Ui_MessagePair_Bind`, `Ui_MessagePage_Dtor`, `Ui_ListWidget_Ctor`,
   `Container_RingBuffer_Next`, `Message_SetArg`, `Ui_PaneCrossFade_Update`) are used consistently.
5. **Asset round-trip** — for every literal layout name, checked that a matching asset exists:
   `game_assets/layouts/arcs/ui/**` and `game_assets/tables/packs/ui/**`. This is what turned
   guesses into evidence (see below).

## Open problems / NOT verified

- **No emulator, no Ghidra re-import.** Nothing was booted; all semantics are static. In particular
  no name here is runtime-confirmed by watching a value change in Azahar.
- 0x316994 / 0x32BD88 (`maybe_Ui_MessageWindow_SetRecordHandle` / dive twin): the tail call to
  `0x00100B74` is Thumb code that Ghidra decoded as ARM, so whether it copies a UTF-16 name into
  `self->f_4a4` or does something else is inferred from the xref chain, not read directly.
- 0x36422C–0x365388 (shop/dialog open-hide, `%d_%ls` 12-row list) and 0x37C8E0–0x37D4C0 (record
  detail sub-page handlers) are named structurally. The decompiled virtual calls (`+0x24`, `+0x3C`,
  `func_004E7108`, `func_00654D30`) hide which sub-window they operate on, and I did not trace those
  vtables to a class, so the `maybe_Ui_ShopWindow_*` / `Ui_RecordDetailWindow_HandleInput*` names
  are placeholders that a reviewer should tighten.
- 0x380F3C–0x381C14 and 0x35F950/0x361890/0x3618A0 are model/effect code that merely falls inside
  this address range; their per-function confidence is 0.35–0.55.
- The 0x318EB4 "0xFF = no pane" interpretation matches the cross-fade fields used by the already
  named neighbours but was not proven against a call site (the callers are vtable-only).
- Several "Dtor"/"DtorBase" pairs are inferred from the `free` / no-`free` difference only; that is
  a very reliable pattern in this binary (20+ instances) but is still an inference.
