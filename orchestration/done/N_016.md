## What I did

1. **Read the docs** (`README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`)
   and the earlier reports (`done/N_011.md`, `done/N_012.md`, `done/N_014.md`, `done/N_015.md`,
   `done/N_017.md`) for the conventions and for helper semantics already established by other
   lanes.
2. **Built an evidence index over the whole readable tree** (18,748 `.c` files):
   callees per file, inverted caller map, plus a real ARM `BL` scan over
   `original/exefs/code.decompressed.bin` (image base `0x00100000`) so that vtable-only and
   Ghidra-merged entry points still get caller evidence.
3. **Literal-pool decoding — including the rotated immediate.** This was the decisive tool.
   Ghidra's C in this range never shows a string, and the compiler emits them almost
   exclusively as `add rX, pc, #imm` where `imm` is a **rotated 8-bit** ARM immediate
   (`ror(imm8, 2*rot)`). A naive `ldr [pc,#x]` scan finds zero strings here; the corrected
   scanner recovered `equip_text.bxon`, `ui/location/%s`, `atari_txt7`,
   `panel_reset_msg.bxon` + `menu_skill_party/point/reset/list2`, `win_gold`, `win_talk`,
   `win_yesno`, `quest_stamp_s`/`null_stamp_l`, `2d/model/%s.pack`, `%s.bspa`,
   `%s_cs.bspa`, `icon_up`/`icon_down`/`txt_num_l`/`txt_gold`, `null_btn`, and the
   `menu_slot_display`/`plate1..6` neighbours. It also decodes `vldr` floats and
   `ldr`-pool code/data pointers.
4. **Vtable reconstruction.** For every batch address I mapped its data references to a
   maximal run of code pointers, i.e. an exact `vtable base + slot`. 28 of the 150 sit in a
   vtable, which is what identifies the owning class of otherwise nameless destructors and
   shows shared base methods (e.g. `0x003BD778` occupies slot 4 of four different window
   vtables and slot 5 of a fifth).
5. **Allocation-size → constructor matching** through the two UI factories:
   * `func_00217DAC` (the "UI part rebuild" switch) allocates the object and calls the
     ctor: case 0 → 0xB4 → `0x0039E698`, cases 5..9 → `g_002181F4 = 0x12F0` →
     `0x00387378` with style 0..3, case 7 → 0x1F8 → `0x0039AC04`.
   * `func_001DE2B8` (`Ui_PanelMessageWindow_LoadPanels`) calls `0x003ACA54`,
     `0x003ACDA4`, `0x003ACE88`.
6. **Bottom-up naming**: leaves and shared helpers first (`0x003E04BC` element destructor,
   `0x003E0454` element constructor, `0x0012416C` handle release, `0x001A6680` set text,
   `0x00633560` UI string lookup), then their callers, then the window classes and their
   handler-table entries.
7. **Input-handler tables.** Two `{fn, 0}` tables in `.data` are indexed by the same
   script/UI command dispatcher that N_012 described at `0x00726D08`:
   `0x0072A158..0x0072A1A0` (skill panel) and `0x0072C4C8..0x0072C560` (profile form).
   Their members are the `Ui_SkillPanel_On*` / `Ui_DiveForm_On*` entries. The second word
   is zero in every entry (still unexplained).

### Framework knowledge recovered along the way (useful for later batches)

- **`0x003E0454` / `0x003E04BC` are the paired constructor/destructor of the embedded UI
  element** (the "tween/layout-ref" object): ctor installs vtable `g_003E0498`, embeds a
  `0x005402F0` object and returns `base-8`; dtor releases the handle at `+8` and returns
  `base-8`. 25 of the 150 batch functions call the dtor, and every window destructor is
  just a chain of those calls plus `0x0010F6CC` (free).
- **`0x003E0088` = element visible**, **`0x003E021C` = element metrics/position (float
  compare, early-out)**, **`0x003E043C` = element animation/snap**.
- **`0x001D8B6C` is the singleton-ctor allocator**: it returns the object pointer for the
  class whose vtable the caller stamps next. Most UI ctors in this range start with it.
- **`0x001A6460` = SetVisibleWithAnim(bool)** (N_012), used as the whole body of two
  InitPanes overrides in this batch.
- **`0x00100B74` is a tail-call trampoline into Thumb code** that Ghidra decodes as ARM and
  marks "does not return"; N_015 hit the same artefact.
- **`0x0029126C` is a noreturn UI helper** (assert/abort-style or a control transfer): two
  handlers here end in it on every path, so they never return normally.
- The UI layer id table (`0x00633560(layer,index)`) is indexed by small constants
  (0x15, 0x21, 0x40, 0x4D, 0x4E, 0xD8..0xDA, 0x62..0x69), which is how the menu category
  switch at `0x003D6138` could be described without guessing the glyph ids.

## Honest gaps / what is NOT verified

- **120 of 150 names are mechanism-level (`maybe_`).** The reason is structural: this
  address range is a dense run of vtable slots, deleting destructors and `{fn,0}` handler
  entries. Many functions have no string of their own and no direct caller (83 had no
  caller at all before the `BL` scan, and 55 still have none), so their owning class is
  inferred from the vtable they sit in or from the neighbour that allocates them.
- **Corrupt decompilations.** `0x003B27BC` (`halt_baddata` + a misdecoded literal block),
  `0x003D82E0` (overlapping instructions at `0x003D8312`) and `0x003D7634`
  (register-relative accesses, `unaff_*`) are named from their one surviving call plus
  neighbours, not from a readable body. `0x003B8AD0` and `0x003B8B88` contain partial bad
  data too.
- **`0x0039ED7C` is not a real function start** — it is a 4-byte entry-point split of the
  deleting destructor `0x0039ED80`; it is documented as a thunk rather than given semantics.
- **`0x003D2E2C` / `0x003D2EE4`** are static/global initialisers of a 12-byte descriptor
  whose tail call `0x00100B74` is Thumb code Ghidra decoded as ARM. They are named
  `maybe_Os_StaticCtorA/B` (0.25) because their owning module is genuinely unknown.
- **The list builder cluster `0x003A8D80`/`0x003A9398`/`0x003A953C`/`0x003A9640`** is only
  known as "the location/quest list": the row layout strings live in the callers
  (`0x0036AD6E`, `0x00369458`), not in the functions themselves, so the names stay
  descriptive.
- **Both handler tables' second word is always zero** and still unexplained; the exact
  command index of each handler is not recoverable from the `{fn,0}` table alone.
- **`0x003BD778` / `0x003BE00C`** are shared base-class methods (slot 4/5 and slot 9 of four
  different vtables). Their class is known only as "the common window base"; whether the
  four vtables belong to one inheritance tree or to four unrelated windows that share a
  template is not proven.
- **Signatures are normalised.** Ghidra loses the 2nd/3rd argument of several ctors and
  handler entries (register-only use, stack scratch); where the caller passes an argument
  the readable C drops, I documented it and said so in the evidence field.
- **Names are not merged** into `symbols.json` or the readable C (that is
  `M1_merge_names`). No emulator or hardware check was performed.
