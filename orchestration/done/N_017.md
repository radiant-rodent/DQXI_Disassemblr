## Method (reproducible)

Throw-away harness in `%LOCALAPPDATA%\Temp\opencode` (nothing added to the repo):

1. **Caller index** — regex over all 18,748 `decomp/readable/{functions,recovered}/*.c`
   files, inverted into `{callee address -> caller addresses}`. Important here: 90+ of the
   150 functions have no `bl` caller at all because they are vtable slots; "no caller" is
   itself evidence of a destructor/callback.
2. **Name merge** — `symbols.json` (`symbols[]`), `symbols_recovered.json`,
   `decomp/native_names.json` and every existing `orchestration/naming/out/N_*.json`, so
   neighbours from N_004/N_005/N_012/N_015 (e.g. `Ui_MessagePage_Dtor`,
   `Battle_TextWindow_Ctor`, `Ui_ListWidget_Ctor`, `Ui_Pane_SetVisibleWithAnim`,
   `Message_SetArg`, `Battle_Popup_InitMissPopup`) are used consistently.
3. **Literal / vtable resolution** — every `g_`/`s_`/`PTR_` token was resolved against
   `original/exefs/code.decompressed.bin` (image base `0x00100000`; the file also carries
   `.rodata`+`.data`, so `addr-0x100000` works for all sections). For constructors and
   destructors the first stored vtable was dumped and every entry resolved to a name; the
   functions that reference the same `g_` token were listed as class siblings. This is how
   `0x003DA0C8 -> vtable 0x76A57C -> Gfx_SceneNode_LoadMeshByName` and
   `0x003F05DC -> vtable 0x76B8F8 -> 0x003EE058` were proven.
4. **Asset round-trip** — every literal layout/table name was checked against
   `game_assets/layouts/arcs/ui/**` and `game_assets/tables/packs/ui/**`. This is what turns
   the clusters from guesses into evidence (see table below).
5. **Bottom-up order** — leaf dtor/ctor/helper functions first, then the page handlers that
   call them.

## Open problems / NOT verified

- **Everything is static.** Nothing was booted, no emulator was run, no Ghidra project was
  re-imported. No name is runtime-confirmed. Vtable dumps come from the clean retail
  `code.decompressed.bin`, so the addresses are trustworthy, but behaviour is inferred.
- 114 entries are below 0.5. Their *role* is usually certain (dtor/ctor/page update), their
  *owning class* is not; I deliberately left them as `maybe_Ui_*_Dtor`/`_DtorB` rather than
  inventing class names. Two examples:
  - `0x0041C48C`/`0x0041C4B8`, `0x00412B0C`/`0x00412B40`, `0x003E071C`/`0x003E0750`,
    `0x003E07EC`/`0x003E087C`, `0x003F28B8`/`0x003F2904`, `0x00419EC8`/`0x00419F44` are
    certainly dtor/deleting-dtor pairs; only the class is vague.
- `0x003F2DB0` is a **damaged decompilation** (base pointer reconstructed as `arg3>>9>>8`);
  the class is proven (same vtable 0x76BB28 and same teardown as `0x003F2904`) but the
  parameter list is unusable — don't port it blindly.
- `0x003E3628` is named from a name-probe loop only: the base string at `g_003E36EC`
  (`efctf0`/`else…`) looks like a fragment of an effect/else label, so
  `maybe_Ui_Text_ScanNumberedPanes` is deliberately vague.
- `0x003EB694`/`0x003EB994`/`0x003EBA30` are grouped as a two-option choice widget
  (shared vtable 0x728550, command ids 0xEE5/0xEE6). They could be a different two-state
  prompt; the sequence role is the honest part.
- `0x003EE5C4` is Thumb code that Ghidra decompiled with register-relative garbage; only the
  call chain (`0x003D6138`/`0x0041CA58`/`0x0064D6E0`) places it in the smith item-selection
  path.
- The smith-menu *controller* at `0x00625308` / `0x0062564C` / `0x006258B0` is still unnamed
  and drives many pages; until it is named, “page state” names here remain descriptive.
- No semantic-collision review: only exact textual uniqueness was checked.
