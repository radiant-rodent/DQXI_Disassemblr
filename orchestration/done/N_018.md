# N_018 — UI and Message naming batch (resumed)

**Outcome:** `orchestration/naming/out/N_018.json` now contains **150 / 150** entries, one per
address in `orchestration/naming/batches/N_018.txt`, in batch order. The previous worker produced
no output (its log shows only `README.md`, `PLAN.md` and the batch file were read), so everything
was named from scratch in this session.

## What I did

1. **Built the call graph once.** Scanned all 18,748 `decomp/readable/{functions,recovered}` C files
   in a single Python pass and indexed `func_XXXX`/`FUN_XXXX` callers and callees for every batch
   address. This is what turns "150 isolated functions" into ~25 coherent UI class families.
2. **Merged every known name.** `symbols.json` (`symbols[]`), `symbols_recovered.json`,
   `decomp/native_names.json` and all existing `orchestration/naming/out/N_*.json` → 2,488 known
   addresses, so callees are shown with their names where they exist.
3. **Resolved literal-pool references.** Every `g_XXXXXXXX` / `s_XXX` / `PTR_DAT` used by a batch
   function was decoded against `original/exefs/code.decompressed.bin` (same address space, base
   `0x00100000`, covers `.data` + `.rodata`). Pane names, resource names and format strings were
   the strongest class evidence in this batch.
4. **Read the disassembly where Ghidra gave up.** `asm/text/text_00440048.s` (and
   `text_00480048.s`) for the bodies Ghidra truncated with *bad instruction data* or replaced by a
   tail call: `0x45C598`, `0x45CEA0`, `0x477618/84/F0`, `0x479260`, `0x444B48`, `0x45C004`.
5. **Worked bottom-up.** Leaf helpers first (`0x4445A4`, `0x443EEC`, the `0x4478AC/0x4478F8` dtor
   pair), then the callers that use them (message window open/step, list-widget mode switch, grid
   refresh).
6. Saved the JSON after every 25 functions and re-assembled it from parts, so a resumed worker could
   always pick up a complete, valid file.

## Open problems (honest)

- **Class identity is the weak point.** Most of these 150 are vtable slots with no direct caller.
  For those I named the *behaviour* (`Ui_Window_DtorDelete`, `Ui_GridWindow_MoveCursor`, …) rather
  than guessing a game-facing class name. Merging should treat the `Ui_`/`Battle_`/`Casino_` prefix
  as a subsystem hint, not as a proven class.
- **Truncated decompiles.** `0x460888`, `0x46DF7C`, `0x4A6840`, `0x4A5E38`, `0x4A6EDC` end in
  `func_00100B74` (noreturn assert) or in *bad instruction data*; their last operations (free,
  final unlink, or a table write) are missing from the C. Names are based on the recovered prefix.
- **`0x479260` is 4 bytes in Ghidra** because the literal pool after it was decoded as code. The
  real body is `bl 0x1A66A0; ldr r1,=0x00773E20; str r1,[r0]` (verified in
  `asm/text/text_00440048.s`), which is why its name is a factory description.
- **Library calls not in the decompilation.** `0x0060F06C` (input sampler), `0x00624D78`,
  `0x00627230`, `0x00625FC0`, `0x0065D3B8` live in the statically linked library part of the image
  and have no `decomp/readable` file. Where I relied on them (`0x451F2C`, `0x4A66D0`, `0x4A6720`,
  `0x4AD9C8`) the evidence text says "inferred", and those entries sit at 0.3–0.55.
- **`0x4546A8` register arguments were not recovered** (`unaff_r4…r11` in the C). The `%s.pack`
  literal and the tail handle swap are certain; which register is the pack name is not, so
  `param_2` is marked unused and the signature is a best guess.
- Nothing here was executed, emulated or booted, and no name has been merged into `symbols.json`
  or the readable C — that is `M1_merge_names`' job.

## Suggested follow-up tasks

1. **`M1_merge_names`**: merge the 0.55+ proposals first (they are mostly leaf helpers and animation
   setters with concrete literal evidence); hold the `<0.5` ones until their class is known.
2. **`Ui_class_ids`** (new, small): for the UI widget family, dump each constructor's stored vtable
   (e.g. `g_00445cf4`, `g_0046c3b8`, `g_00475070`) and group functions by *shared vtable* rather than
   by address neighbourhood. That would let `Ui_Window_DtorDelete` style names be replaced with real
   class names in one pass — the same trick that made the `0x443AC8` dive-capture cluster readable
   in N_017.
3. **`N_0xx` neighbour note**: `0x4698C8`/`0x469B84`/`0x469D84` (damage-number popup) belong with the
   already-named `Battle_Popup_InitDamagePopup` (0x46A9DC) and `Battle_Popup_PrepareDamageNumberPanes`
   (0x46AB14). Whichever batch owns 0x46A9xx should reuse the names proposed here
   (`Battle_Popup_InitNumberWidget`, `Battle_Popup_UpdateNumberAnim`,
   `Battle_Popup_PlayQueuedNumber`) so the popup family ends up consistent.
4. **`casino_names`** (new): the slot machine block `0x4ACDD0-0x4AD9C8` is proven by its pane names;
   the remaining slot/roulette/poker windows (`Ui_PokerWindow_Ctor` 0x1E3E78,
   `Ui_RouletteSelectGrid_Init` 0x4B49B8, `Ui_CasinoJackpotWindow_Init` 0x46C0B0) deserve one
   dedicated naming pass with the board/table tables open.
5. **Tooling**: add a `--fallback-ghidra` flag to the batch generator so functions whose readable file
   is missing (`0x1DAB30`, `0x1A61FC`, `0x3DFEC4`, …) can be inspected without manual lookup; that
   cost the most time in this batch.
