# N_019 — UI and Message naming batch (resumed)

**Outcome:** `orchestration/naming/out/N_019.json` now contains **150 / 150** entries, one per
address in `orchestration/naming/batches/N_019.txt`, in batch order. The previous worker produced no
output (no `out/N_019.json`, no done report), so everything was named from scratch in this session.

- Mean confidence **0.458**; 13 entries ≥ 0.6, 41 at 0.5–0.59, 96 below 0.5 (all `maybe_`-prefixed).
- Subsystem split: Ui 96, Gfx 22, Os 8, Svc 5, Battle 4, Model 4, Str 4, Event 3, Field 2, Actor 1,
  Text 1.
- Mechanical validation: JSON parses, 150/150 addresses in batch order, 150 unique names, no name
  collision with `symbols.json` / `symbols_recovered.json` / `decomp/native_names.json` / any other
  `out/N_*.json`, all seven keys present, every signature contains its own name, every `params` key is
  `param_N`, and `confidence < 0.5` exactly for the `maybe_` names.

## What I did

1. **Built the call graph once.** One Python pass over all 18,159 `decomp/readable/{functions,recovered}`
   C files indexed callers and callees for every batch address. That turned 150 isolated functions into
   coherent class families (many of these are vtable slots with no direct caller, so the reverse index
   was essential for the ~100 that *do* have callers).
2. **Merged every known name.** `symbols.json` (`symbols[]`), `symbols_recovered.json`,
   `decomp/native_names.json` and all 15 existing `out/N_*.json` outputs, so callees are shown with
   their names where they exist and reused names could be avoided.
3. **Resolved literal pools against the real image.** Every `g_XXXXXXXX` / `s_XXX` reference was decoded
   from `original/exefs/code.decompressed.bin` (base `0x00100000`, covers `.text`+`.rodata`+`.data`).
   Inline strings were the strongest evidence in this batch: `ui/dive/%s`, `slot_rot_loop`,
   `slot_stop`, `side_in`/`side_out`, `num_normal`/`num_yellow`/`num_red`, `hit_num_in`/`hit_num_out`,
   `lamp_in`/`lamp_out`, `uma_course1_mask`/`uma_course2_mask`, `menu_uma_main/prize/select`,
   `win_gold`, `select_in`/`select_out`, `pop_damage_num1..3`, `null_txt_l0`, `%s_%s.bflan`,
   `Rura_Up`, wide `%d`/`%02d` format strings.
4. **Recovered the vtable of every batch address.** For each address I searched the whole image for the
   32-bit pointer, walked backwards to the start of the pointer run and printed the slot index plus the
   named neighbours. That is what gives the otherwise nameless destructors a class
   (`Ui_Widget_Dtor_776E68`, `Ui_Widget_Dtor_773740`, `Ui_Widget_Dtor_77C56C`,
   `Ui_LayoutElement_Dtor`, `Ui_LoopPane_DeleteDtor`, `Ui_LoopPane3_DeleteDtor`, the
   `Ui_UmaWindow_Dtor`/`DeleteDtor` pair, `Ui_SakusenWindow_DtorBase`, …).
5. **Disassembled the merged/undocumented helpers.** `0x001A6680`, `0x001A629C`, `0x001A66A0`,
   `0x001A60A0` are not in the Ghidra export (Ghidra merged them or missed them). Capstone on the
   retail bytes confirmed they are the pane set-text / set-text-colour / 0x48-byte widget base ctor /
   text-forward helpers, which changed several "icon" descriptions into "text id".
6. **Worked bottom-up.** Leaf setters and dtors first (digit setters, animation-by-name helpers,
   handle release), then the callers that use them (slot-plate window states, horse-race panels, list
   fillers, model-instance draw paths).

## Open problems / what is NOT verified

- **56 of the 150 have no direct caller in the readable tree** (vtable or callback-table slots), and 96
  names stay below 0.5. Their owning class is inferred from the vtable they sit in (or from the sibling
  init function); the *verb* is usually solid, the class noun is often a best guess
  (`maybe_Ui_Widget_*`, `maybe_Ui_ListWindow_*`).
- `0x4D4D90` is decompiler-mangled (`unaff_r4` / `ZR` condition): only the two tail animations
  (`side_in` / `side_out`) are certain.
- `0x4C7430`, `0x4C74AC`, `0x4C7508` sit in a `{function, 0}` callback table at `0x727300` and are named
  by behaviour (`maybe_Event_*`), not by a proven owner.
- `0x4DB5AC` / `0x4DB5DA` are 3-instruction tail wrappers; Ghidra mixed the owner and record fields, so
  the parameter list is a hypothesis.
- `0x5AF920`'s body is mostly `halt_baddata`; only "clears the global sub-dialog flag" is visible.
- `0x5B1164` has no caller and only a lazy-singleton + string-id `0xF4` pattern to go on.
- `0x4C2B1C` is identified only through its single caller `Ui_PokerWindow_Ctor` and the 0x274-byte
  `0x4A46D8` tween panel it builds.
- The fade/screen-state helpers (`0x4C7430/0x4C74AC/0x4C7508`, `0x4D9760/0x4D97F8`, `0x59F928`)
  are named from the global UI core layout that N_021 proved from `ui_text.bxon`
  (`Ui_GetCore` +0x10 = screen/2D manager, +0x14 = fade/transition manager); the exact fade operation
  each one performs is inferred from its vtable slot, not traced end-to-end.
- The OS/SVC wrappers (`0x5018E8-0x501CFC`, `0x51A6C4/0x51A6FC`, `0x509C6C`) are named by their
  command words and `software_interrupt` numbers; which NN service they belong to was not verified.
- The `0x588DD8`/`0x58935C` pair is called "render pass 1/2" from the `0x4000000` vs `0x8000000` flag
  and the two visibility windows; the actual GPU state they set lives in unnamed 0x2Dxxxx code.
- Names are **not** merged into `symbols.json` or the readable C — that is the `M1_merge_names` task.
- Nothing was booted, emulated or exported.
