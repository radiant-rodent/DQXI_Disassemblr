# N_020 — native function naming (UI_and_Message, 0x005D5A24–0x0063B5A0)

## Status
Completed: `orchestration/naming/out/N_020.json` contains 150 entries, one per address in
`orchestration/naming/batches/N_020.txt`, in batch order. No prior `N_020.json` or done report
existed (the lane was resumed from nothing), so all 150 were named in this session.

## Result
- 150/150 addresses covered, 150 unique names, no collision with `symbols.json`,
  `symbols_recovered.json`, `decomp/native_names.json` or any other `out/N_*.json`.
- Mean confidence 0.462; 79 entries ≥ 0.5, 71 below 0.5 (all `maybe_`-prefixed).
- Subsystem split (after removing `maybe_`): Ui 52, Field 44, Gfx 18, Script 9, Data/literal 5,
  Fs 4, Container 3, Anim 3, Text 2, Font 2, ItemBag 2, plus Sound/Pack/MonsterBook/Model(2)/
  Message 1 each.

## What the range actually is
The batch tag `UI_and_Message` is only partly right. The range is a contiguous slice of the
game-logic band:

- **0x005D5A24–0x005E2594 (34) — field object ("gimmick") action handlers.** These are
  callbacks on the field objects the player interacts with. Evidence: `self->f_14`/`f_18` are
  128-slot generation-tagged object handles resolved by `0x004A1E00`/`0x0032D27C`; actors have a
  part array at `+0x1420` (`0x00650D34`, count `+0x1460`) and an animation controller at `+0x60`
  (`0x005E7848` tail-calls `0x002A891C`); `self->f_38` is the action step, `f_34`/`f_2c`/`f_48`/
  `f_90` are embedded 0x18-byte state machines driven by the `0x006D3024`/`0x006D334C`/
  `0x006D39B4`/`0x006D3CE8` transition helpers (each with a different state count 4/5/5/7).
  Events are 0x28-byte records built by `0x005E5410` and queued through `0x003D5648`/`0x003D5610`/
  `0x003D562C` with type bytes 1–7, 0xD and 0xE; item/object ids (0x413, 0xA82–0xB3B) select the
  event kind. The constructors `0x005D8B98` (64-slot handle table `0x7ba0c0`, state table
  `0x783DD4`) and `0x005E4D04` (vtable `0x784174`, field-scene root with sub-object vtables
  `0x784018`/`0x784040`/`0x7840B8`) tie this class to the field scene.
- **0x005EB31C–0x00605B1C (17) — field/map scenegraph nodes, the sound stream player destructor,
  the Squirrel UI-system wrappers, and two large UI destructors** (`0x6034BC`, `0x605B1C`).
  `0x005F2E24`–`0x005F710C` use `Map_FindRecordById`/`Map_AddInstance` (named elsewhere) to keep
  scene nodes in sync with map placement records.
- **0x0060C06C–0x0060EEDC (20) — graphics screen/draw-list layer.** Badly decompiled because most
  of it is Thumb; capstone shows Thumb prologues and the ARM decompiler emits `halt_baddata`.
  The readable parts are two hard-coded per-screen colours, a 7-entry colour switch with byte-swap
  (RGBA), and per-index (0/1) virtual calls, i.e. the 3DS top/bottom screen state.
- **0x0061054C–0x006190AC (22) — level pack names, level-data destructor, message window and
  equipment window.** `0x61054C`/`0x610580` format `level2d/%s.pack` / `level3d/%s.pack`.
  `0x61542C`–`0x6170E4` are the two-page message window (`0x614CF0 MessageWindow_Builder`,
  layout `scroll_txt1`/`scroll_txt2`, `Message_SetArg`, `Ui_PaneCrossFade_Refresh`).
  `0x617E20`/`0x617FB0`/`0x618824` are the equipment window.
- **0x0061B724–0x0063B5A0 (57) — status text, date substitution, level background, font cache,
  hit effects, pose blending, the smith/forge menu, and list/message text providers.**
  Decisive anchors: `level_3dBGTime.bxon`/`level_3dBGFog.bxon` (`0x61DD8C`), the four
  `%s_chit.rcb`/`vhit`/`yhit`/`ehit` hit effects (`0x61ED9C`), `3d/motion/%s_%s.pack`
  (`0x63675C`), and the `Ui_SmithMenu_*` cluster (`0x624B68`–`0x627288`) whose callees were
  already named in other batches (`Ui_SmithMenu_DetailOpen`, `Ui_PageStack_Push`, etc.).
- The four `0x604EA6/0x604EBA/0x604F16/0x60E5A8/0x60E7B0` entries are **not real functions** —
  VFP literal-pool words that the function splitter promoted; they are documented as data with
  confidence 0.2 rather than given invented behaviour.

## Method
1. Indexed all 18,159 `decomp/readable/functions/*.c` files to get per-function callees and an
   inverted caller map; merged every name source (`symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json`, every `orchestration/naming/out/N_*.json`; `N_014.json` is not
   valid UTF-8 and was read with `errors="replace"`).
2. Resolved every `g_XXXXXXXX` literal against `build/code.bin` (base 0x100000, `.text`+`.rodata`+
   `.data`) and turned the results into strings/floats/pointers. This is what exposed
   `level2d/%s.pack`, `level3d/%s.pack`, `3d/motion/%s_%s.pack`, `scroll_txt1/2`,
   `level_3dBGTime.bxon`, `level_3dBGFog.bxon`, the four `%s_*hit.rcb` paths, `$%x`, `_day` and
   `Nut`.
3. Followed function pointers into `.data`/`.rodata`: the state/descriptor tables at `0x783DD4`
   and `0x784018`–`0x7840B8`, the field-scene vtable `0x784174`, the 0x18-byte scheduler vtable
   `0x75B2F0`, and the 128-slot handle table around `0x7ba0c8`. This identified otherwise
   caller-less callbacks (they are table slots).
4. Disassembled entry points that Ghidra merged into neighbours (`0x633070` inside `0x632FC4`,
   `0x5E7848`, `0x5E5410`, `0x6D3024` inside `0x6D2EB4`, `0x3D55F4`/`0x5598`/`0x5610`) with the
   project's `asm/text/*.s` and capstone; found the recurring "entry is 4 bytes late" pattern
   (`cmp` hoisted before `push`) in `0x613350`, `0x60E800`, etc.
5. Worked bottom-up: leaf predicates/event senders first, then the state handlers and the window
   classes that call them.

## Mechanical validation
- JSON parses; 150 objects; addresses exactly match the batch order (no missing/extra/duplicate).
- All seven required keys present; `params` is an object everywhere; every `param_N` key maps to a
  human-readable name; every signature contains its own name.
- No `FUN_`/`func_`/`param_N` left in any signature or summary; evidence references were
  normalised to raw addresses.
- Every `confidence < 0.5` name is `maybe_`-prefixed; no `maybe_` at ≥ 0.5.
- No name clashes with `symbols.json` or any other batch output (4 initial clashes were renamed).
- No test suite was run — the task explicitly exempts naming lanes from rule 5.

## Honest gaps / unverified
- **Class ownership is inferred, not proven.** The 0x5D band is called `Field_Gimmick_*` from
  structure (object handles, model parts, actor animation, map records) and the project's existing
  "gimmick" terminology (e.g. `0x4FA030` field lamp gimmick in N_019). No class-name string exists
  in the binary, and the field-scene root at `0x5E4D04` is itself only identified structurally.
- 71/150 are below 0.5. The weakest groups: the Thumb screen/draw-list band
  (`0x60C310`, `0x60E6BC/73C/79C`, `0x60EEDC`), the five literal-data entries, and the bad-control-
  flow gimmick entries `0x5DF4B8`/`0x5DFB14`.
- `0x604EA6`–`0x604F16` and `0x60E5A8`/`0x60E7B0` are almost certainly not functions; the batch
  contains them because the splitter emitted them. They are marked as data, not silently dropped.
- `0x613350`/`0x6135F8`/`0x613638` are level-map code named by structure only (the +0x5000 cell
  table and 8-byte descriptors); the owning class and the tile format are not decoded.
- The `0x62A738`/`0x630898`/`0x636CC4`/`0x63AB90`/`0x63AF40` predicates all share a virtual
  `slot 0x18` call on the script/global object. They are named "condition check" because the
  object and flag slots differ but the mechanism is identical; their exact game meaning (quest
  flag, event flag, message condition) is not proven.
- The `Ui_ListText_*` family (`0x63A838`–`0x63B5A0`) is proven to be a list row text/icon
  provider (string ids 0xC/0xD/0xE/0xF/0xBD, icon base 0xCA, 0x5A-row bag loops next door), but
  which menu owns it (bag, monster book, quest list) is not proven.
- Names are proposals only: they are not merged into `symbols.json` or the readable C. That is
  `M1_merge_names`. Nothing was built, booted, emulated or exported.

## Suggested follow-up
1. Dump the `.data` tables `0x783DD4`/`0x784018`–`0x7840B8` and `0x75B2F0` into a small tool and
   use them to name the whole field-object/state-machine family across batches (they are reused
   far outside N_020).
2. Decompile Thumb functions with capstone/IDA-style mode switching before the next naming batch:
   the whole 0x60C–0x60E band and the 0x5DF/0x613 entries are readable as Thumb, not ARM.
3. Add an automatic "is this a literal pool / VFP data" detector to the batch generator so
   `0x604EA6`-style non-functions stop consuming naming slots.
4. Cross-check the "gimmick" reading against the map placement records once `Map_FindRecordById`/
   `Map_AddInstance` are fully documented.
