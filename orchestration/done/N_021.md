## Key findings worth recording for the merge step

- **`0x006F229C` = `Ui_GetCore`** (666 callers). Lazy 0x98-byte singleton:
  `+0x10` = 2D/screen manager (passed to `0x216608` by `Ui_ChangeUIMap`, resolves UI text through
  `0x633560`), `+0x14` = fade/transition manager (`+0x10`/`+0x1c` = the two fade objects whose
  vtable `+0x34` is queried by `Ui_IsEndFade`), `u16@0x94` = the UI mode word cleared by the pane
  push functions. Naming this one function unlocks a large part of the UI tree.
- **`0x00633560` = UI text id lookup** (`0x633560(uiCore->f_10, id)` returns a string). Verified with
  `ui_text.bxon`: `0xd`=どうぐぶくろ, `0xe`=そうびぶくろ, `0xbd`=だいじなもの, `0x24..0x26`=㍉/㌔/㌢.
- The ten `0x6E33xx` clones are the status screen rows; each pushes a row (label from the table at
  `0x729A7C+0x28`), sets message argument 6 to the label string, adds the measured value width to a
  per-column accumulator (`f_1c8`/`f_1ca`/`f_1cc`/`f_1ce`) for the two-column layout and registers
  the entry in the compendium (`0x618394`). The literal pool also carries the **999** threshold used
  to switch max HP/MP to the four-digit layout.
- The pane push family is one algorithm with a per-class capacity word; the capacities are
  `self[9]`=1, `self[0xc]`=2, `self[0xf]`=3, `self[0x12]`=4, `self[0x15]`=5, `self[0x21]`=9.

## Open problems / what is NOT verified

- The four layout loaders `0x6D9730` (type 6), `0x6D9DC4` (type 1), `0x6DDFA4` (type 4),
  `0x6E0B28` (type 5) are named by **mechanism only**. The pack-entry name hashes passed to
  `0x124B24` were not reversed, so *which* screen each one belongs to is unknown. Cracking that
  hash would let a follow-up name all four precisely (and the ~250 part names at `0x6DD7xx`).
- `0x6E51E4`, `0x6E53A4`, `0x6E5C68`, `0x6E6180` are scroll/cursor movers whose **upper clamp is
  invisible**: Ghidra truncates the bodies with *bad instruction data* and my reading of the
  surviving part gives only the negative-wrap branch.
- `0x66D680` / `0x66D928` are **byte-identical** 0xE0F8-byte node constructors; I could not tell the
  two classes apart, so they are named A/B. Same for `0x6E661C/66B4/674C/67E4/6914`, which are
  five identical `Gfx_SceneNode_Dtor` + `operator delete` stubs: numbered 1–5, not named.
- `0x641DAC` (icon id) and `0x6484EC` (list value under the global cursor) rest on inferred field
  offsets; the 8-byte icon-bank records and the `>>16` payload in `0x6484EC` are not proven.
- `0x6F2394` is called a "command list singleton" from its intrusive list shape (`+0x14..+0x20`
  self-referencing) and its overlay-draw callers; the type of the 0x34-byte object is not confirmed.
- `0x64609C`, `0x64715C`, `0x63A794` and the other leaf helpers referenced heavily by this batch
  have **no decompiled body** (container/merged entry points), so their contracts are inferred from
  call sites. Naming them in a future batch would firm up the sprite-frame and list-cursor names.
- Names are **not** merged into `symbols.json` or the readable C — that is `M1_merge_names`.
  Nothing was booted, emulated or exported to hardware.
