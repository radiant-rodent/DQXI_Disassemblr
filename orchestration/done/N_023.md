## What I did

1. **Indexed everything once.** A Python pass over all 18,748 `decomp/readable/**/*.c` records, for
   every function, its callers, callees, `g_` literal-pool references and inline string literals.
   Because ~60% of this batch are vtable slots with no `bl` caller, I also built a second index from
   `asm/text/*.s` (165,855 `b`/`bl` sites) and a *reverse literal* index: every occurrence of each
   batch address as a 32-bit word in `original/exefs/code.decompressed.bin`, plus the surrounding
   run of function pointers. That table context is what gives a slot its class
   (`0x759734: 0x1c1c1c Ui_JumonWindow_Init, 0x1c1fd0, *me*, ...` → "Jumon window virtual").
2. **Merged every known name** from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 18 existing `out/N_*.json`, so callees are shown with names
   and new names could not collide (the build script fails loudly on a collision — it did once,
   `maybe_Field_CreateActorObject` was already taken by N_002, and was renamed).
3. **Resolved literal pools against the retail image** (base `0x00100000`, `.text`+`.rodata`+`.data`):
   every `g_XXXXXXXX` was decoded as string / int / float / pointer / code-pointer run. Strings were
   the strongest single source of names in the UI-part cluster: `normal_in_1..6`, `fast`, `base`,
   `normal`, `disabled`, `hibi`, `hibi_loop`, `_hibi_in`, `opened`, `seal`, `null_shadow_l/s`,
   `null_panel_l/s`, `null_panel_l_lw`, `atari_txt`, `reset_flash`, `disabled_line`,
   `normal_line`, `opend_line`, `select`, `dummy`, `win_jumon_party1`, `%0F0s0`.
4. **Disassembled the helpers Ghidra did not decompile** (`0x003A0790`, `0x003A083C`,
   `0x00672318`, `0x00614024`, `0x001F3CF4`, `0x001F3DE8`) straight from `asm/text/*.s`. They turned
   out to be *struct init* + *struct copy* (0x30-byte sprite/draw record), a 9-byte sound-parameter
   copy, a one-field u16 store, and two message-variant setters — which is what identified the
   0x19EE60/0x19FAB8/0x19FF68 trio as battle-actor effect/popup builders rather than "stats refresh".
5. **Corrected an earlier misname for the record.** `0x0062AB4C` is named
   `maybe_Battle_RefreshUnitStats` in another batch, but its body is plainly
   "copy the actor's world transform (`func_006344A0/451C/4418` position/rotation, `006343FC/35E88/
   35EBC/35EA0` scale/alpha) into a 0x40-byte billboard-sprite record". The three actors above it
   pass `&self->f_b0->f_48` as that record. I did **not** edit the other batch's file (ownership
   rule) — this is a suggestion for `M1_merge_names`.
6. **Worked bottom-up.** Leaf getters/setters and the handler tables first, then the state machines
   that call them.

## Honest gaps / what is NOT verified

- **Confidence is low by design.** 131/150 names are `maybe_`. Most of these functions are vtable
  slots of UI classes whose constructor is in a different (still unnamed) batch; the *role* is
  proven by the vtable neighbours and the strings, the *owning class* often is not. Example:
  `0x1BF838-0x1C0EBC` is provably one screen's handler chain (`{fn,arg}` pairs, one table, item ids,
  price, stack limit) but I could not prove whether that screen is the bag, the shop or the
  "present" list — the item-id ranges and the price/99-stack logic point at the shop, so the family
  is named `Ui_ItemScreen_*`/`Ui_ShopItemList_*` rather than a single confident class name.
- **The batch tag `Actors_and_Entities` is only right for about a third of the range.** 92 of 150
  are UI code, because the dispatcher's address windows do not follow subsystem boundaries.
- **Decompiler-damaged entries** (name is structural only, parameters are guesses):
  `0x001C1F24`, `0x001C6788`, `0x001F1F78`, `0x001F2958`, `0x001E5DA8`, `0x0021066C` (Thumb code
  with lost registers), `0x001BF838`, `0x001F2D10` (`halt_baddata` in the middle), `0x001E4CF4`
  (Ghidra removed 20+ unreachable blocks).
- **`0x001D5440`** (party snapshot) is only half-read: its allocator constants (`0x2fb28`,
  `0x804160`) look like a heap-size/stride pair but I could not prove which array grows.
- **`0x00207A8C`** (`maybe_Party_InitBattleSlots`) writes ids 0xbb..0xc0 = 0x9c. The ids are in the
  same range as the battle-command table but I did not verify which table, only that it runs for
  party member 0 from the battle state update `0x0020AB04`.
- **`0x0019EE60`/`0x0019FAB8`/`0x0019FF68`**: the *mechanism* (transform → sprite record → sound →
  message) is solid; which game event each one represents (damage number vs status popup) is not.
- No emulator, no hardware, nothing booted. No test suite run (naming batches are exempt from rule 5).
  Nothing outside `orchestration/naming/out/N_023.json`, `AGENT_LOG.md` and this report was written.
  Names are not merged into `symbols.json`/readable C — that is `M1_merge_names`.
