## What the batch actually is

The batch is titled `Actors_and_Entities`, but the range is mostly **UI and 2-D sprite-actor**
code. Resulting split by name prefix: 99 `Ui_*`, 24 `Actor2D_*`, 8 `Party_*`, 7 `Field_*`,
3 `Gfx_*`, 2 each `Actor_*`, `Anim_*`, `ModelPreview_*`, `Text_*`, 1 `Container_*`. This matches the
already-named neighbours in the same addresses (`Ui_TalkWindow_*`, `Ui_PokerTable_*`,
`Ui_CreditWindow_*`, `Ui_SenrekiWindow_*`, `Ui_TsuyosaWindow_*`, `Field_*_SpawnByType`), and the
batch labels in `PLAN.md` are by subsystem *count*, so overlapping ranges are mixed. I named what
the code does, not what the header says.

None of the 150 addresses has a name in `symbols.json`, `symbols_recovered.json`,
`decomp/native_names.json`, `decomp/ghidra/by_subsystem/*` (the batch files all live in
`by_subsystem/General_Procedures` with `FUN_xxxxxxxx` names) or any other batch output, so every
name here is reverse-engineered rather than looked up.

## Method

1. **Reusable index** (outside the repo, in `%TEMP%\opencode\n24\`): `ctx.py` caches the body and
   caller/callee edges of all 18,748 `decomp/readable/{functions,recovered}/*.c` files and merges
   every known name from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and
   all other `orchestration/naming/out/N_*.json`. That is what turns `func_0021AF9C` into
   `Actor2D_UpdateFacingToTarget` when it shows up as a callee.
2. **Literal resolver** `str.py`: maps any `g_XXXXXXXX` token to `build/code.bin` (image base
   `0x00100000`), prints it as a string, a float, or a pointer that can be dereferenced again.
   This was the single highest-value tool: it produced `Open_Front` / `Open_Back`, the `u"%d"` /
   `u"%02d"` play-time formats, the `AI: …` Japanese wide-string table, `$%x` child-name formats and
   all the "magic" scale constants (0.01, 1/65536, 0.5, 3600/60 divisors).
3. **Merged-function check** via `decomp/functions_index.json`: several important callees
   (`0x00629A24`, `0x0063F530`, `0x005F5818`, `0x00665564`, `0x004AE7FC`, `0x004FA8A4`,
   `0x003A994C`) have **no standalone readable file** because Ghidra merged them, so their role was
   inferred from all their call sites instead.
4. **Bottom-up naming**, then the callers were named from the newly named callees. Every function's
   field offsets were cross-checked against the class it appears in (`self+0x298+i*0x48` spans,
   `core+0x24a98`/`core+0x27508` tables, `heap+0x24ACC` party bag).
5. **Parallelisation and merge.** The 132 functions outside my own first chunk were split into five
   independent sub-tasks (18-47, 48-79, 80-91, 92-121, 122-149) run against the same tooling, each
   writing a part file; `merge.py` re-emits batch order, normalises the `params` keys, and
   `validate.py`/`collide2.py`/`final_check.py` check the result mechanically. I inspected the
   first 18 bodies myself line by line and re-read 8 further entries (including the biggest,
   `0x0026E56C`) against their sources before accepting them.

## Key findings worth recording for the merge step

- **The `0x219D5C-0x21BA10` cluster is the 2-D sprite actor.** Four near-identical constructors
  take different placement-record layouts; all of them build `f_326/f_327` state, a per-state
  pattern table (`f_274`), two `func_00336054` transform children and the 8-span chain at
  `self+0x298+i*0x48`. `0x0021AF9C` + `0x0021B22C` implement the classic DQ 3DS front/back flip by
  dot-producting the direction to the target with the actor's forward axis.
- **`0x0029059C` is a byte-for-byte duplicate of `0x0021B52C`** (own literal pool, same `$%x`
  name format, same `0x0FFE` constant). The retail binary ships duplicate translation units, so a
  future dedup pass should not treat them as different behaviour.
- **Debug output is centralised**: `0x006D3EA0` / `0x006D3EDC` are a printf pair writing into
  0x108-byte on-screen label slots (`g_006d3ed8` / `g_006d3f14`); `0x005E5C40` formats a sprite-span
  name into one of them. Three functions in this batch are pure diagnostics.
- **`0x00643324`/`0x00629A24` are the character/actor manager queries** reached through
  `heap+0x24a98`; `0x006F20C0`/`0x0011CB38` are the thread-local static-base accessors used to
  reach every global. Naming those four would upgrade dozens of `maybe_` names across
  N_010-N_031.
- **The `0x26E56C-0x281150` layout engine is the battle tactics (sakusen) window**, proven by the
  Japanese `AI: …` strategy strings it resolves plus state ids `0x0b/0x0c/0x11` that match
  `Ui_SetupSakusenWindow`/`Ui_SetupMessageWindow`.
- **`0x006D4588(self, 0xFF, name, payload)` is the script trigger dispatcher** (other callers pass
  `OnFieldEnd`, `OnCutSceneEnd`, `TrgEvent`, `TrgCommand`), so `0x00256678` firing `"TrgRCommand"`
  after registering a gadget is script-visible behaviour.

## Decisions taken (no orchestrator available)

- **Subsystem prefix for the sprite-actor family = `Actor2D_`.** The real symbol table contains
  `Actor2DChangeAnim`, `Actor2DWalk`, `Actor2DRun`, `Actor2DSetCollide`, so `Actor2D` is the game's
  own term; `Gfx_SpriteActor_*` is reserved for the lower-level span/transform helpers other
  batches already named that way.
- **`maybe_` is used for every confidence < 0.5**, including names I believe are right but could
  not prove; 86 of 150 entries are `maybe_`.
- **Void functions keep `"params": {}`** (two entries: `0x0023A410`, `0x0024272C`). Fabricating a
  parameter would be worse than an empty map.
- **One rename to avoid a symbol clash**: my `0x0029479C` was `Ui_PartySelectWindow_Init`, which
  N_006 already uses for `0x0047AA0C`; renamed to `Ui_PartySelectWindow_InitLayout` (it builds the
  panes and binds the data source, while the other one is the real ctor).

## Open problems / what is NOT verified

- **Coverage vs depth.** 132 of the 150 entries were produced by five parallel helper agents from
  the same tooling; I re-read 26 bodies (the whole first chunk plus 8 spot checks) against the
  source. Their evidence strings are specific and internally consistent (`0x…` callees, string
  literals, field offsets all check out in the samples I verified), but I did **not** re-derive all
  150 by hand. Treat the 0.40-0.49 band as proposals, not conclusions.
- **`0x002A5B4C-0x002A6464`** (4 `maybe_Ui_Window_InitAndActivateA-D` + 3 input handlers) differ
  only in sub-widget offset and trailing constants; the owning window class is not pinned down, so
  they are named by variant letter.
- **`0x0027168C`** is an instruction-identical clone of `0x00271658` with a different ABI and **no
  caller anywhere** (not even in `asm/`), so its parameters had to be described, not typed.
- **`0x0029E41C`** (Thumb fragment, control flow ends in unreachable code) and **`0x0028F92C`**
  (1920 bytes, every parameter is `unaff_rX` in the decompiler output) are the two weakest names in
  the file (0.30 / 0.35).
- **`0x00263B04` / `0x00263BEC`** have Ghidra bodies containing bad instructions and overlap the
  following function; the declared sizes (0xC / 0xEC) contradict the decompiled text.
- **`Party_Status_*`** (8 entries) rests on the `core->f_48` record layout: 12 member pages with a
  3-D model at `+0x244[i]` and an effect at `+0x420[i]`, per-page 3-bit masks at `+0x274fc/0x27500`.
  The values written are clamped to a vtable maximum, which looks exactly like HP/MP, but I did not
  confirm which stat each page is.
- **`0x00240A7C` = play time** assumes the global `heap->f_24abc` is the 60 Hz frame counter; the
  divisors prove "hours/minutes/seconds" arithmetic, not which unit the source counter has.
- **Nothing was booted, emulated or exported**; no name was merged into `symbols.json` or the
  readable C — that is the `M1_merge_names` step.
