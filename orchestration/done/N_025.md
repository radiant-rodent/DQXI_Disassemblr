## What I did

1. **Built the call graph once** (cached outside the repo): one Python pass over all 18,748
   `decomp/readable/{functions,recovered}` C files mapping caller ⇄ callee for every batch address.
   First version of the regex only matched `func_002A66EC` and missed the `func_0x002d8838` spelling
   used by the `recovered/` files; after fixing it several "no caller" functions gained callers.
2. **Merged every known name** — `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json`, `decomp/ghidra/functions_merged.jsonl` and all 18 existing
   `out/N_*.json`, so callees are printed with their known names and no proposed name duplicates
   another batch.
3. **Read every function's readable C** and worked bottom-up: the small helpers first
   (`Ui_DrawList_Append`, `Container_GlyphSet_Insert`, `Container_RingBuffer_Pop`,
   `Anim_ClipSet_PlayById`, the `Text_CharSet_Build*` family, the `Ui_Message_Set*Arg*` family), then
   the state machines and destructors that call them.
4. **Recovered one vtable and one dispatch table.** The batch addresses 0x002A5xxx–0x002A79xx are
   slots of the pointer table at `0x0072BDEC..0x0072BF3C` (alternating pointer/zero), which contains
   0x002A66EC, 0x002A69A0 and 0x002A76A8 — that is why almost none of the 0x2A6xxx functions has a
   direct caller. The shared object model (state flags `f_3534` with the 0x142/4/8/0x10 bits,
   sequence data `f_3570` with 0x10-byte nodes at `f_34`..`f_38`, owning actor at `f_3574` whose
   vtable +0x14 requests an action id and +0x10 commits, `f_356c` = finished) identifies the family
   as an **actor action-sequence runner**.
5. **Decoded the literal pool words Ghidra hides.** `g_0030F538` is the constant `0x1930`, so
   `*(int *)(g_0030F538 + self)` is the message **tag table at self+0x1930** (0x43 tags, 0x28-byte
   rows, 8 parameter slots selected by `self->f_1942`); the pool words at 0x0030F540 / 0x0030F548
   are the wide strings `L"%u"` and `L"%l"` handed to `func_00707C1C(..., +0x848)`. That pins
   0x0030F258 as the message control-code interpreter and makes the whole 0x002A99C8–0x002B0A08
   group readable as message-window line/tag/step code.
6. **Cross-checked caller names from other batches** (`Battle_ActionAnimTable_Build`,
   `Ui_EquipmentWindow_Release`, `Ui_DiveManager_Ctor`, `Actor2DChangeAnim`,
   `Ui_CasinoWin_UpdateFukuroWindow`, `Ui_ShopWindow_CreateSubObjects`,
   `Ui_PokerWindow_InitPanes`-adjacent code) to anchor classes that have no strings of their own.

## Honest gaps / what is NOT verified

- The batch tag says **Actors_and_Entities**, but only ~30 of the 150 functions are actor/sequence
  code. The rest is message-window, text-layout, character-set and UI-root code, so names follow the
  observed behaviour, not the tag.
- **`maybe_Ui_DataPanel_*` (0x002CCC00–0x002CE694) is the weakest cluster in the file.** It is a
  state machine (states 3/5/6/9/10, 31 × 0x200-byte strings at +0x1830) whose block-size check
  (`0xc8b0` bytes) and 64-bit time-based hash (0x002CDC44) look like stored-data validation. I did
  **not** prove that it is save data, only that it validates a fixed-size block against a
  clock-derived hash.
- `maybe_Save_VerifyBlock` (0x002CE5B4) is named from that same evidence; it might be a suspend/
  street-pass/profile block instead of a save slot.
- **Decompiler-corrupted bodies** (0.12–0.15 confidence, placeholders): 0x002A76A8 (bad instruction
  data after its first virtual call), 0x002CB154 and 0x002CC714 (Thumb code mis-decoded — refcount
  masks and register-relative stores). Partial `halt_baddata`/tail-call truncation also affects
  0x002C21AC, 0x002FD45C, 0x002FE9B0, 0x00307DA8, 0x00307F88, 0x00308264, so their last operations
  are known to be missing.
- **The 113-entry icon grid (0x002C7584–0x002C89DC)** is named by mechanism only (28 icon slots,
  4 visible states, threshold digit count 1/10/100, 4-bit priority per entry). Which menu owns it is
  not proven; `Ui_IconList_*` is a descriptive, not a confirmed, class name.
- **The four `maybe_Actor_SubObject_Release*` destructors** only differ by which list they release
  (+0x3468 / +0x344c / +0x34d8 / +0xd36) and by the free offset; their concrete classes cannot be
  mapped because the neighbouring lane N_024 (0x248xxx–0x2A6xxx) has no output yet.
- **Twin pairs were numbered, not distinguished**: 0x002A66EC/0x002FDA70 and
  0x002A69A0/0x00308970 are near byte-identical; 0x002D88EC/0x002E3B98 differ only by one visibility
  store. Their names say which variant is which, but which game screen uses which variant is open.
- All names are **proposals**. Nothing was merged into `symbols.json` or the readable C (that is
  `M1_merge_names`), nothing was booted or emulated, and no bit-matching rebuild was attempted.
