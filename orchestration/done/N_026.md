# N_026 — naming batch for `0x00311704-0x0039D664` (resumed)

**Outcome:** `orchestration/naming/out/N_026.json` now holds **150 / 150** entries, one per
address in `orchestration/naming/batches/N_026.txt`, in exact batch order. The previous worker
left nothing behind — no output file, no done report, no log entry; the only trace is
`===== attempt 0 ... Error: Free usage limit reached` at the top of `orchestration/logs/N_026.log`,
so the whole batch was named in this session.

## What the batch actually is

The batch is titled `Actors_and_Entities`, but the address range is **UI and text code**, not
actor code. The resulting names split as: 106 `maybe_Ui_*`, 29 `Ui_*`, 4 `Gfx_*`, 3 `Casino_*`,
2 `Text_*`, 2 `Anim_*`, 1 each `Actor_*`, `Battle_*`, `Field_*`, `Model_*`. This matches the
already-named neighbours in the same range (`Ui_EquipWindow_*`, `Ui_GuideWindow_*`,
`Ui_RecordDetailWindow_*`, `Ui_CompareRow_*`, `Text_Line*`, `Casino_Slot_*`). The batch labels in
`orchestration/PLAN.md` are by subsystem *count*, so overlapping ranges end up with mixed content;
I named what the code does, not what the header says.

## Method

1. **Reusable index.** Built (outside the repo, in
   `%LOCALAPPDATA%\Temp\opencode\n026\`) a caller/callee/body cache over **both**
   `decomp/readable/functions/` and `decomp/readable/recovered/` — 18,367 bodies, 11,700 distinct
   callees. The previous batch's cache only covered `functions/`, which would have missed the 11
   `recovered/` entries in this batch.
2. **Merged every known name** from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 22 other `orchestration/naming/out/N_*.json`, so callees and
   callers show real names (`Ui_EquipWindow_PushPane`, `Text_ApplyFontRecord`, `Mem_AllocAligned`,
   `Casino_Slot_StepDigitAnim`, …). This is what made the equip-window, guide-window, record-window
   and casino families identifiable instead of guessed.
3. **Read every one of the 150 bodies**, with declarations stripped, grouped into 10 chunks. For
   the two big duplicated families I diffed the bodies against each other and against the already
   named reference implementation `Ui_MessageWindow_BuildLines` (0x2A99C8).
4. **Worked bottom-up.** Font/glyph helpers (`0x61BD4C` char→font record, `0x63E960/0x63E998`
   font tables, `0x1901F4/0x1902B4/0x19201C` text-object edits) first, then the message-line
   builders, then the windows that use them.
5. Wrote to the JSON after every ~30 entries (`merge.py` re-emits in batch order), so a resumed
   worker can always continue from the file.

## Key findings worth recording for the merge step

- **The four line-append variants** `0x31D6DC / 0x31DC48 / 0x31E1CC / 0x31E838` are the same
  algorithm as the named `Ui_MessageWindow_BuildLines` (0x2A99C8): the same `0x60`-byte line
  record at `self + line*0x60 + 0x5d0`, the same line counter `self[0xc90]` capped at `0x47`,
  the same `0x1FC4FC` commit, and the same `0x486208` message-record allocator. The only
  difference between the first two is the wrap flag (`1` vs `0`) in `0x486208`; the other two
  append many lines from the current candidate list.
- **`0x31D178` is a text-style classifier**, not a character comparison: it resolves both
  characters to font records and returns 1..15 from the first character's style byte `+0x29`,
  using the second character only to choose the odd/even variant. `0x40A680` compares its result
  with a pane byte `+0x149`, which is the strongest proof that the return value is a *style id*.
- **`0x31D4E0` computes the message column count** stored in `self[0xc92]`; three other windows
  (0x4BFA20, 0x4F5138, 0x59D638) read that field as a loop bound with `< 2` / `< 3` tests.
- **The guide/book reader** is the `0x369xxx` cluster: it sits directly next to the already named
  `maybe_Ui_GuideWindow_NextPage` (0x369458) and `maybe_Ui_GuideWindow_HandlePageInput` (0x36949C),
  and `0x36980C` attaches the sprite named `s_medalstamp_00369ac8`, i.e. the medal page of the
  in-game guide.
- **`0x319848` is a 65-caller shared sprite-actor factory** — scene check `0x66A7B8`, model-table
  lookup `0x62C388`, instantiation `0x62C3B0(model, entry, variant)`. Naming it as
  `Gfx_SpriteActor_CreateFromTable` is safe for the whole field/effect sprite tree.
- **The casino slot machine has six reel plates** at `+0xec0 / +0x1064 / +0x1208 / +0x13ac /
  +0x1550 / +0x16f4`, and five payout rows at `+0x5c0 + i*0x238`. Both facts recur in six
  independent functions, so they are reliable.
- **`0x35EB98` is the party/character record resolver** used by most of this batch (`arg < 0x1f`,
  returns a record whose `+0x675/+0x676`, `+0xda`, `+0xe4`, `+0xe8` fields are read everywhere).
  It still has **no decompiled body** and no name; naming it would remove a lot of "weird
  indirect" guesses across N_010-N_031.

## Open problems / what is NOT verified

- The 12 `maybe_Ui_Window_GotoState*` handlers at `0x316140-0x3177C8` are named **only by the
  state id they request** (`0x316140(self, N)`). The owning window class could not be pinned down:
  their helpers `0x383A58 / 0x383A80 / 0x383B34` have no decompiled body, and the only named
  caller in the cluster is `maybe_Ui_SmithMenu_Cancel`. The names are honest but not pretty.
- `0x35F110 / 0x35F38C / 0x35F4B4` (replace/measure glyphs in stored 24-slot names) rest on the
  record layout and the `0x190xxx` text-object calls; I could not connect them to a concrete menu.
- `0x33DC94`, `0x33ED70` and `0x35F110` contain `halt_baddata` / overlapping-instruction artefacts
  in the Ghidra output; their control flow is partly invented by the decompiler.
- `0x33376C` and `0x3337B6` are also truncated (`halt_baddata`) — the first half is readable, the
  second half is not.
- `0x32B7D0`'s "text span" naming depends on `0x5E5320/0x5E5380/0x622038` being span clear/add/set;
  those three still have no body in `decomp/readable`.
- The shop-window cluster `0x37F3FC / 0x37F7A8 / 0x37FB18` is placed in the shop window because
  0x37F384 (its neighbour) is called from `Ui_ShopWindow_Ctor`, but the three functions themselves
  have **no direct caller**, so their exact pane slot is unproven.
- The equipment-window names assume the 0x17c input-flag bit meanings (1=confirm, 8=page,
  0x40/0x80=direction); those bits are consistent across four functions but are not documented
  anywhere in the repo.
- Names are **not merged** into `symbols.json` or the readable C — that is `M1_merge_names`.
  Nothing was booted, emulated or exported to hardware.
