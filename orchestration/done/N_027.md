## Method (what the names are based on)

1. **Call graph.** Parsed all 18,748 files under `decomp/readable/{functions,recovered}` into an
   `address → body` map plus a reverse index over `func_XXXXXXXX` call tokens. The readable pass
   substitutes real names for functions other batches already named, so ~3,800 existing names
   (`symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`, other `out/N_*.json`)
   propagated into callee lists automatically.
2. **Literal-pool resolution.** Decoded every `g_XXXXXXXX` the batch functions touch against
   `original/exefs/code.decompressed.bin` (image base `0x00100000`) as C string / vtable / code
   pointer / float / integer. This is what identified vtables (e.g. `g_0039eb50 → 0x00767354`,
   whose slots are `Ui_EquipTextWindow_Dtor/Delete`), the `wbhm_*` weapon-node names and the
   pane-name string tables.
3. **Vtable ownership.** Scanned the image for each batch address, grouped hits into vtables, then
   searched for the vtable word in literal pools and mapped the pool address back to its containing
   function via `decomp/ghidra/functions_merged.jsonl` ranges. That gives both "this is vtable slot
   N of class X" and "constructor C installs it".
4. **Callers.** Reverse `func_` index (19 callers for `0x003BD148`, 19 for `0x0040A8C4`, …) plus
   the summaries other batches wrote for named neighbours (N_004/N_016/N_017/N_023/N_025 were the
   most useful).
5. **Assembly fallback.** `0x003BDAD8` has no readable body (the batch file points at
   `FUN_002A76A8`, a container Ghidra merged it into). It was decoded from
   `asm/text/text_00380048.s`.

Nothing was written outside `orchestration/naming/out/N_027.json`, `AGENT_LOG.md` and this report.
Analysis scratch scripts live in `%TEMP%\opencode\n027\` (not in the repository).

## Clusters that were actually proven

* `0x39D7C8` / `0x39DA6C` / `0x39DF08` — the equipment-text window's compare cache and character
  bind. They share `0x0031D178`, which returns the 1..15 equipment-compare code, and the
  `actor+0xCA` name field; `0x39E698` (N_016, `Ui_EquipTextWindow_Ctor`) calls `0x39DF08` directly.
* `0x3E1850` / `0x3E1A28` / `0x3E1B58` / `0x3E24A6` — builders of N_017's message-part table
  (0x18-byte parts: kind at +0x178, page pointer at +0x180, style key at +0x184/+0x188).
* `0x3E45BC` / `0x3E4830` — the `Ascent` / `Decent` action starts (string literals in the image; the
  misspelling is in the shipped data).
* `0x3F3B08` + `0x40A680`..`0x40B748` — the character-model equipment rig: attach/detach of
  `wbhm_r_base` / `wbhm_r_arm_off` / `wbhm_l_base` / `wbhm_l_arm_off` / `wbhm_grip_on` /
  `wbhm_grip_off`, with `actor+0x12E4` (pool word 4836) as the per-character visibility mask.
* `0x3FBA74` / `0x3FBC78` — the nine-stat comparison panel (it saves and restores the record's
  bit 8, so that bit is the "incapacitated" flag).
* `0x4026A0` / `0x402D0C` / `0x40400C` / `0x404204` / `0x404880` — 4-slot active-party validation:
  0x1F id bound, `0x66B0E4` (per-character state byte) + `0x63F8F0` (record), membership test
  `(~record[4] & 3) == 0`, `-1` slot sentinels.
* `0x3C2240` / `0x3C225C` / `0x3C2334` / `0x3C2358` — the filtered item-list iterator used by
  `Ui_ItemListCore_Ctor` (N_019) and `Ui_SmithMenu_SubObject_Ctor` (N_017).

## What is NOT verified (honest gaps)

* `0x003AF808` / `0x003AFAC4` / `0x003AFD88` iterate a 0x14-byte-record table gated by a
  story-flag bitset (`ctx+0x2A444`), the visited-map byte array (`ctx+0x27508`), a chapter field and
  a per-character condition-byte program (opcodes 0x19..0x22 read `actor+0x664..0x66C`). The gating
  is proven; **which** content table it is (quests vs. party-talk topics vs. actor appearance) is
  not. Named `maybe_Actor_FindNextEntryForCharacter*`, deliberately vague.
* Decompiler-damaged bodies where only structure and callees are trustworthy:
  `0x003A6958`, `0x003D75EC`, `0x003E24A6`, `0x003EC0DC`, `0x003EE568`, `0x0040400C`,
  `0x00404880` (all `halt_baddata` / lost frame pointer / `coprocessor_load` noise).
* `0x003D6480` / `0x003D6750` scroll a measured name width into a member-record u16 (`+0x14` /
  `+0x16`, clamped by `+0x12`) inside the equipment-detail class; the scroll behaviour is certain,
  the exact widget is inferred from the vtable neighbours (`Ui_EquipmentWindow_HandleInput` is slot
  +5 of both).
* `0x003CAD78`, `0x003EC0DC`, `0x0040563C` are named from callee mechanics only (16-child scale
  copy, command-stack unwind, child-class dispatch).
* `0x003F2230` builds kind-0xE1/0xE5 list entries — the same kinds N_005 named for its entry sets —
  but the panel itself is only identified as a character/quest detail panel.
* No emulator, no real hardware, nothing executed: these are static-analysis names only.
