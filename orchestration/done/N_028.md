## Method (what the names are based on)

1. **Call graph.** Parsed all 18,159 files under `decomp/readable/functions` into an
   `address → body` map plus a reverse index over `func_XXXXXXXX` call tokens. Names already
   assigned by other batches (`out/N_*.json`), `symbols.json`, `symbols_recovered.json` and
   `decomp/native_names.json` were substituted into the call/caller lists, so ~3,800 known names
   were visible while reading each function.
2. **Vtable check.** For every batch address I searched `asm/rodata/*.s` for a `.word` equal to the
   address. 62 of the 150 are virtual methods; the vtable neighbourhood (e.g. `0x0076DB54`, whose
   other slots include `Field_SceneNode_UpdateMapRecord` and `Ui_Widget_ReleaseSub`) decided
   whether a function is a field scene-node method or a UI widget method.
3. **Layout pane names (new, and the most decisive evidence in this batch).** Several functions bind
   panes by literal name (`icon_quest1_achievement`, `pager_num_r`, `txt_name`, `txt_lv`,
   `txt_sort`, `Slide_Out`, `stamp_%02d`, `icon_next_1`, `txt_in`, …). I searched
   `game_assets/layouts/**/*.bflyt.json` for those combinations to identify the owning window; e.g.
   `icon_quest1_achievement` + `icon_quest1_clear` + `icon_quest1_order` + `pager_num_*` occur
   together only in `menu_senreki_quest_3d.bflyt.json`, which pins `0x41A6C4` to the battle-records
   (戦歴) quest list window.
4. **Literal-pool sanity.** Where a constant decided the meaning (`0x3C` = 60-frame timer,
   `0x2A4E6`/`0x27C88`/`0x2D545` context offsets, `0x3B4D`/`0xED3D` battle-manager fields) it is
   quoted in the evidence.
5. **Assembly fallback.** `0x40D368`, `0x41200C`, `0x446C6C`, `0x45220C` and `0x4A3DA0` are
   truncated in the readable view because Ghidra treats `0x100B74` (strlen) as non-returning. I
   decoded `asm/text/text_00400048.s` for `0x40D368`/`0x41200C` and confirmed the missing body
   (string copy → text-id lookup → `func_006D3EA0` channel write).

Nothing was written outside `orchestration/naming/out/N_028.json`, `AGENT_LOG.md` and this report.
Scratch scripts live in `%TEMP%\opencode\n028\` and are not in the repository.

## Clusters that are actually proven

* **Records/quest list window** — `0x41A6C4` (`Ui_RecordQuestWindow_InitPanes`) binds
  `icon_quest1_achievement/clear/order`, `null_txt_l0`, `pager_num_l/r`; those names co-occur only
  in `menu_senreki_quest_3d.bflyt.json`. `0x41C88C/0x41C9A8/0x41CA14/0x41CE10` are the item-list
  widget row mapping (category list via `func_0035EB98`, `func_00629150` = count,
  `func_00629890` = at, `func_006292A4` = find).
* **Eight/ten-row window family** — `0x41D174`, `0x45407C`, `0x45F6A0`, `0x45F970` all iterate
  exactly 8 or 10 rows at `self + i*0x3C`, fill name/icon/flag through the row vtable `+0xC/+0x10/
  +0x14`, blank with `0xFF`/`-1`, and update the pager via `func_001D809C`.
* **Stamp book** — `0x452988` calls `Ui_StampWindow_ShowStamp` (already named in N_025), formats
  `stamp_%02d` with `func_006F0A50` and shows the `stamp_complete` pane; `0x4528DC` selects the
  stamp at `ctx->0x27C88 - page - 1`.
* **Slide windows** — `0x471494`/`0x471648` pass the literal animation names `Slide_Out` /
  `Slide_In` to vtable `+0x84`; `0x471820` is the event hook that forwards the flag to the child.
* **Battle monster stat getters** — `0x48FCA4/0x48FEFC/0x495A24/0x496650/0x496758/0x496B50/
  0x4972EC/0x4973E8` all follow the same recipe: `func_0035EB98(ctx, work[0x1DA])` → three u16
  fields (`0x738/0x73C/0x73E/0x740/0x744/0x746` with the `0xEB8`/`0xAF8` variants) → scale by
  `func_0048B278(...)` and recompute via `func_00487FC0` when the cached product differs. They are
  the per-stat display values of the enemy info panel.
* **Casino slot digits** — `0x4ACF0C` is called by `maybe_Casino_Slot_UpdateSpinState` (N_018) and
  switches the reel sprite frames for values < 10 and two-digit values; naming it
  `Casino_Slot_UpdateDigitSprites` is safe.
* **Text layout** — `0x459FE0` clears the `0xF00` work area and resets the 6/0x3C/4 u16 tables to
  the empty marker `g_0045A1DC`; `0x4573CC` and `0x459A70` are the two measuring passes over the
  same tables (`f_830/f_840/f_842`, `f_BEC/f_BEE/f_BF0`). Called from
  `Battle_ComposeMessageText` (N_025), which corroborates the "text layout" reading.

## Open problems / NOT verified

* **`func_006D3EA0` / `func_006D3F54`**: I read them as 16-slot wide-text channels
  (`0x108`-byte slots, formats are UTF-16 `%ls`/`%d` found in `asm/data/data_007BB000.s` at
  `0x7BE738`). If those slots were *message arguments* instead of a debug console, the eight
  `*_Log*` names in this batch would read better as `*_SetMessageArg*`. I lowered the three
  affected confidences to 0.45 and added the caveat to their evidence. `0x467730` dumping seven
  internal monster fields into channels 8..14 is the main argument for "log".
* **`0x46C56C` / `0x4A04D8`** — the two "battle manager update" twins use the same layout
  (`self[0x3B4D]` action, `0xED3D`, `0xED3E`, `0x3B50` state, `func_004D5228/004D5608` command
  selection) but I could not prove which battle mode (normal vs. auto/command) each serves, so both
  are vague `maybe_...UpdateState` names.
* **`0x4ABC48`–`0x4AC46C`** — I grouped these as casino/party-status code because they sit next to
  the `Casino_Slot_*` block and use the same `0x80`-byte table allocator, but only `0x4ACF0C` is
  definitely casino. Confidences 0.30–0.35.
* **`0x41D8F8`** (`maybe_Ui_RankWindow_UpdateRows`) — it binds `Ui_RankIcon_Bind` and formats
  numbers, but I could not identify the screen; "rank window" is a placeholder.
* **`0x418384`** — no caller anywhere in `decomp/readable`, so its role (sprite orientation from a
  layout record) is inferred from the field usage only.
* Ghidra damage: `0x41D8F8` (`halt_baddata` in case 2), `0x41A6C4` (`drN(self)` opaque call),
  `0x4A3DA0` (0x558 bytes, all but the first call unreachable). Names for these stay generic.
