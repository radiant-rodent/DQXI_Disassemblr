# N_029 — naming batch report (resumed)

**Task:** name and document the 150 native functions listed in `orchestration/naming/batches/N_029.txt`
(`0x004B0098`–`0x00611538`, lane label `Actors_and_Entities`).
**Output:** `orchestration/naming/out/N_029.json` — 150 entries, one per batch address, sorted by address.

## State when I started

Nothing had been produced for N_029: no `orchestration/naming/out/N_029.json`, no
`orchestration/done/N_029.md`, no `N_029` entry in `AGENT_LOG.md`, no log in `orchestration/logs/`.
All 150 were therefore named from scratch (the "resumed" note in the task was optimistic).

## Method

1. **Name map.** Merged `symbols.json` (function symbols), `symbols_recovered.json`,
   `decomp/native_names.json` and all 23 existing `orchestration/naming/out/N_*.json` into one
   `address -> name` dict and re-annotated every readable-C body with it, so callees show their
   real names instead of `func_XXXXXXXX`.
2. **Caller index.** Scanned all 18,219 `decomp/readable/{functions,recovered}/*.c` files for
   `func_XXXXXXXX` tokens (11,924 distinct callees, ~9 s) to get callers for every address. 66 of the
   150 have **no** direct caller; those had to be placed by vtable slot or by caller-of-caller.
3. **Literal-pool resolution.** Every `g_`/`s_` token was read out of
   `original/exefs/code.decompressed.bin` (image base `0x00100000`) and dereferenced
   string→pointer chains. This produced the strongest evidence in the batch:
   `poker_card_num_b_0` / `poker_card_slime` / `poker_card_box0` (0x4B4364),
   `txt_l1`/`txt_r1`/`txt_clear1`/`txt_difficulty2` (0x4CC670), `null_txt_l0`/`icon_ex0` (0x4D0380),
   `g3107_mat_all_off` + `Nut`/`Flashing`/`Act_02` (0x4B00xx cluster), `txt_title` (0x593250),
   and the time constants 60 000 / 3 600 000 / 86 400 000 that prove the `Svc_Time_*` group.
4. **Vtable recovery.** Searched the image for each batch address as a 32-bit word, then walked the
   surrounding pointer run and printed it with named neighbours. This identifies whole classes whose
   members have no direct callers: `0x776488` (field scene-object family, slot 4 = 0x4B0098),
   `0x776C20` (poker window), `0x776D70`, `0x777820` (33-slot field/actor class, slot 28 = 0x4BFA20),
   `0x778700` (Uma/odds window), `0x778D08` (scroll bar), `0x77A128` (Uma window page handlers),
   `0x77DE98` (base object ctor). The five `maybe_Ui_Screen_ResetActorFlagsA-E` came from finding the
   same reset body in five different screen vtables.
5. **Bound-native cross-check.** `decomp/native_names.json` lists four entry points a few bytes
   before batch addresses; the bytes there are `mov r0,#0; nop`, i.e. wrappers that fall into the body
   Ghidra exported as a separate function. That pins
   `0x6011BC = Casino_GetJackpotCoinStage`, `0x60169C = Casino_GetJackpotBunnyCoin`,
   `0x601C48 = Casino_GetJackpotCoinNum`, `0x601C88 = Casino_GetJackpotState` (confidence 0.7) —
   these four names should be treated as authoritative, not as proposals.
6. **Bottom-up order.** Leaf helpers first, then their callers: `std_FastSinCos` (0x51B158, a 16-byte
   entry sin/cos table at `0x72FC50` with linear interpolation) unlocked the emitter-transform and
   rotation-matrix builders; the `Svc_Time_*` group (0x50ECE4–0x50F004) explained the timestamp
   arithmetic; the shared helpers (`Ui_Widget_ReleaseChildEntries`, the `Work` flag-bitmap getters,
   the item comparators) were named before the windows that use them.

The lane label is misleading: the batch is **71 `Ui_*`, 19 `Field_*`, 9 `Casino_*`, 8 `Gfx_*`,
8 `Font_*`, 6 `Svc_*`, 5 `Work_*`, 5 `Actor_*`, 4 `Item_*`, 3 `Battle_*`, 4 `BattleUnitDisplay/BattleActor_*`,
2 `Math_*`, and 1 each of `std_/Fx/Script/Text/Party/Anim/Model`**. The area `0x4B0–0x5F5` is almost
entirely UI/layout code; the dispatcher's subsystem label just propagated from distant named
neighbours.

Identified clusters (all in the JSON with per-function evidence):

- **Casino jackpot (0x6011BC–0x601C88)** — four bound natives plus their helpers; the four missing
  natives' bodies are exactly these functions.
- **Smith menu item lists (0x4F27A8–0x4F2F30)** — four near-identical scanners over item ids
  `0x69..0xA81`, filtered by equipment slot / accessory category / armour predicates / weapon
  predicates; caller names (HandleArmorList/HandleWeaponList/HandleAccessoryList) confirm them.
- **Poker window (0x4B4364)** — resolves 4×13 card sprites by incrementing `poker_card_num_*_0`
  names, plus `poker_card_slime` / `poker_card_box0`.
- **Uma (race/betting) window (0x4CC670–0x4D9D54)** — page state machine (`ResetToPageN` helpers all
  funnel through 0x4D9228), entry flags, "apply purchase" (subtracts gold via func_00613FC0, which
  N_022 identified as the clamped gold decrement).
- **Font/glyph quads (0x5C8500–0x5D0640)** — constructors, UV→atlas-cell mapping, attach/rebuild pairs.
- **Slot-machine / counter text windows (0x4C4868, 0x4D64F8)** — clamp-value + random-delta + layout
  animation, almost certainly the HP/MP or coin counter with its "increase" animation set.
- **Gimmick `g3107` object (0x4B0098–0x4B0BE4)** — five methods of one scene-object subclass whose
  material is `g3107_mat_all_off` and whose action names are `Nut` / `Act_02` / `Flashing`.

## Not verified / open problems

- **Nothing was executed or emulated.** These are static-analysis names; no dynamic trace, no
  hardware check. None of it changes the binary, but correctness of the *semantics* is inference.
- **0x4BFA20 and 0x4F5138** (`maybe_Field_ActorFocusSequence_Update*`) are decompiler-damaged
  (`halt_baddata` inside the state dispatch). The state enum (`g_004bfd6c/70/74/78/7c`,
  `g_004f56f8…5718`), the actor flag bits (`f_72c` bits 1/2 via vtable +0x134/+0x128), the 0..1
  progress maths and the box computation are certain; whether the class is an event-camera focus
  controller or a staged actor initialiser is **not**. 0.30/0.32 confidence.
- **0x4B00xx `Field_Gimmick3107_*`**: only the model/material id `g3107` is hard evidence; the
  gameplay meaning of the gimmick is unknown. Other workers' note (N_022: `Nut`/`Ecstacy` are
  animation names used by `maybe_Anim_PlayByName`) supports reading `Nut`/`Act_02` as animation
  names, which is what the summaries assume.
- **The "Uma" and "Tsuyosa" window names are inherited from other batches** (`Ui_UmaWindow_*`,
  `Ui_TsuyosaWindow_*`). I kept them for cross-batch consistency, but the same window also contains
  `txt_difficulty2` and a difficulty byte at `Work+0x2A2C0`, so the real screen may be a
  difficulty/odds selector rather than a horse-race window. All entries in those families are
  `maybe_` and ≤0.48.
- **61 functions have no direct caller and no vtable slot I could anchor**; they are named from body
  shape only (`maybe_Field_GetTableByteByIndex`, `maybe_Text_ApplyToSpanArray`,
  `maybe_Model_InitWithFourAttachedParts`, `maybe_Script_JumpTableDispatch` …). The last one
  (0x5AF9F8) is an unrecovered jump table; only the dispatch mechanism is documented.
- **`func_0035EB98` wording.** N_022 established it as the world actor/character record getter
  (stride 0x12EC). My summaries call its result the "member record" because every caller in this
  batch passes a party-member index and reads `+0xCA` as the name id. `M1_merge_names` should prefer
  N_022's wording if it rewrites summaries.
- **Five identical resets** (`maybe_Ui_Screen_ResetActorFlagsA-E`) are compiler copies of one method
  in five screen classes; the letter suffix is a disambiguator, not a semantic distinction.
