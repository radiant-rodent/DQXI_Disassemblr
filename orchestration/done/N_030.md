## 2. Method

1. **Batch digest.** Scripted over `N_030.txt`: address, size, Ghidra signature, resolved callees
   (address → name through every known naming source), and any string literals. Saved as a 750-line
   digest so the whole batch could be triaged before reading bodies.
2. **Caller index.** Scanned all 18,748 `decomp/readable/**/*.c` files for `func_XXXXXXXX` tokens and
   inverted the relation, i.e. "who calls each batch address". Doing this *before* reading the bodies
   was what made the batch tractable: it showed immediately that the range is not one subsystem but
   the shared item/party/row-model layer used by the equipment, bag, shop, poker, smith, skill-panel,
   message and status screens (callers like `Ui_EquipmentWindow_Update`, `Ui_ShopItemList_*`,
   `Ui_PokerWindow_*`, `Ui_Part_*`, `maybe_Save_*`).
3. **Name resolution.** `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and the
   existing `out/N_*.json` files were merged into one address→name map; nothing in the batch had a
   name, but ~40 callees did (`Ui_Window_PushPane`, `Text_FormatMessageArg`, `Message_SetArg`,
   `Item_CountEquipped`, `Field_GetActorModelSetIndex`, `Ui_ListText_*`, `Ui_ListCursor_*`, …), and
   those names propagate through the readable C.
4. **Assembly for the damaged functions.** Where Ghidra emitted `halt_baddata`, `in_r3`, or
   "subroutine does not return", I read `asm/text/text_00600048.s` (and `text_00100048.s` for the
   helpers). This was decisive; see §3.
5. **Bottom-up ordering.** Leaf getters/string helpers first (`strlen16`, entity-id accessors,
   flag-bit tests), then their callers (row label builders, list cursors), then the top-level
   copy/load routines.
6. Wrote the JSON in one pass but kept a generation script in
   `%TEMP%\opencode\n030\emit.py` that asserts address order/count, uniqueness, prefix/confidence
   consistency and `params ⊆ signature`, so the file can be regenerated or patched safely.

## 3. Cross-cutting discoveries (the useful part for other lanes)

These three facts were re-derived and are worth reusing; they changed the reading of most of the batch.

* **`0x00100B74` is a UTF-16 `strlen`, not a noreturn function.** Its assembly
  (`asm/text/text_00100048.s` @0x00100B74) is `movs r1,#0; loop: ldrh r2,[r0]; adds r0,#2;
  adds r1,#1; cmp r2,#0; bne loop; movs r0,r1; bx lr`. Ghidra had it marked noreturn, which turned
  a dozen simple getters/setters in this batch into bodies that end in `halt_baddata`
  (`0x006121B4`, `0x006290A8`, `0x0062A320`, `0x0062A3CC`, `0x0062A64C`, `0x00613324`,
  `0x006135E4`). **Recommendation: fix the prototype in the Ghidra project and re-export** — several
  hundreds of functions across the image almost certainly suffer from the same mislabel.
* **`0x006F20C0` returns the global game context, and `ctx + 0x24a98` is the live work object.** Its
  layout, as established from this batch: bag rows = 50 × 0x8c at +0x5fe4; second row table =
  20 × 0x8c at +0x7b3c; per-member equipment = 0x18 u16 at member+0xf0; item/flag bitmaps at
  +0x295c8, +0x2a2c8, +0x2a444, +0x4b30; "seen" byte arrays at +0x27508/+0x27509; name blocks at
  +0x8630 and +0x86b4 (0x84 bytes each). A row is `{u16 name[66]; u8 f84; u8 f85; u16 pad;
  u32 key}` = 0x8c bytes, key = 0xffffffff means empty — that is why "insert / remove / reset row"
  functions all look alike.
* **`0x0061BD4C` is the item lookup pair** `{u16 id; ItemRecord* rec}` (rec = 0x8c, `+0xc` category
  byte, `+0x10` flag, `+0x11` view-model type, `+0x12..+0x18` four u16 material ids, `+0x20` flag
  word, `+0x29` sub-category, `+0x88` slot key), and **`0x00643504` / `0x0063A8A0` count *active*
  party members** (flag record +4, bit 0). Together with `0x0035F6C0` (entity by index) and
  `0x0035EB98` (entity by id) this pins the whole 0x63A7xx–0x643Cxx list-row/cursor family, which
  is otherwise easy to mistake for screen-local code.

Bonus: the executable contains a **native-registration blob** at image offsets 0x251ca0–0x252520 in
`original/exefs/code.decompressed.bin` (image base 0x00100000) holding inline
`{name, payload ptr, impl ptr}` triples for ~200 Squirrel natives (`SetLevelWorkEnable` → 0x00156D34,
`GetDisplayMode` → 0x0014DB64, `RegistThread`, `CSMessageSetup`, `GetQuestFlag`, …). **None of this
batch's 150 addresses appear in it**, so these are internal game functions, not bound natives. The
blob is still worth parsing properly — it is an almost free, 200-entry ground-truth name table for
0x0014xxxx–0x0016xxxx.

## 5. Confidence and honesty

* Mean confidence **0.452**; 5 entries ≥ 0.6, 1 at 0.5–0.59, 144 at < 0.5 (`maybe_` prefix).
  Distribution by leading subsystem token: 144 `maybe_`, 2 `std_`, 2 `Item_`, 2 `Party_`.
* What is actually proven (≥ 0.6) and can be cited by others:
  `std_Str_Length16` / `std_Str_Length16B` (assembly is a strlen), `Item_LookupRecord` (30+ call sites
  all treat the out-struct as {id, record*}), `Party_GetActiveMemberCount` (assembly is a direct
  delegation to 0x00643504), `Party_GetMemberIdAtIndex`, `Item_GetStoragePointer`,
  `maybe_Ui_DataPanel_CopyFromWork` and `maybe_Save_*` (0.45–0.5, behavioural, but the call chain
  work+0x24a98 → screen copy → restore is solid).
* What is *not* verified: the class identity of the 35 KB object (I call it `Ui_DataPanel_*`; it may
  simply be a per-screen mirror of the whole work object), the exact meaning of
  `0x006301A4`/`0x006302EC` (material storage tests — weakest names at 0.35), the numeric limits in
  `0x0064274C` (a 33-id range below `g_006427a4`), and most magic ids (0x9e0, 0x1f, 0x21, 0x99/0x9a,
  0x9bf/0xa19/0xa82/0xaa3) are recorded as constants, not interpreted.
* Decompiler-damaged bodies (structure only, named from callees/asm): `0x00613324`,
  `0x006135E4`, `0x00622038`, `0x00617B80`, `0x00617C80`, `0x0062A110`, `0x0062B2A4` (partly),
  `0x0063A820`, `0x0063A8A0`, `0x0064CB24` (partly). For `0x00617B80`/`0x00617C80` the element-copy
  loop was replaced by `func_00111378` "abort" calls, so only the empty/small path is trustworthy;
  `0x006135E4`'s real body is 0x11C bytes although the batch lists 0x14.
* No Squirrel script was needed in the end: the scripts confirmed that `SetLevelWorkEnable`,
  `GetDisplayMode`, `RegistThread` etc. are bound natives, which is how I proved this batch is *not*
  that table.
