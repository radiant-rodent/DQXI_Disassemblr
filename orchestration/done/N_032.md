# N_032 — native naming batch `0x00100080`–`0x00316B4C` (150 functions) — RESUMED

**Status: completed.** All 150 addresses in `orchestration/naming/batches/N_032.txt` have an entry in
`orchestration/naming/out/N_032.json` (150 objects, same order as the batch, 150 unique names).
Nothing was booted and no test suite was run (naming batches are exempt per the task, rule 5). The only
files written are the JSON, `AGENT_LOG.md` (Entry 75) and this report.

## 1. What already existed when I started

Nothing. There was no `orchestration/naming/out/N_032.json`, no `orchestration/done/N_032.md`, no
`N_032` string in `AGENT_LOG.md`, and when I started `out/` held only N_001–N_029 (N_030/N_031/N_033/

scratch; there was no partial file to merge.

## 2. Method

1. **Batch digest.** Scripted over `N_032.txt`: address, size, readable-C path, Ghidra signature,
   resolved callees (address → name through *all* naming sources) and resolved callers. Saved as a
   ~5,900-line digest in `%TEMP%\opencode\n032\digest.txt`.
2. **Caller index.** Scanned every `decomp/readable/**/*.c` for `func_XXXXXXXX` tokens and inverted the
   relation (excluding batch members, so "CALLEDBY" means a real outside caller). This was the single
   most useful step: it split the batch into "runtime with known-game callers" and "orphan stubs".
3. **Name resolution.** `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and the 29
   existing `out/N_*.json` files were merged into one address→name map (~4,100 names). Only a handful
   of addresses near my batch had names (`InitHeaps`, `PadReader_Read`, `PrepareBGM`, `PlayBGM`,
   `Ui_LoadIconTextures`, `SetBGMVolume`, `RequestChangeFieldBGMEx`), but those callers are what fixed
   the whole 0x1Exxxx cluster.
4. **Literal-pool resolution.** The readable C shows `g_00XXXXXX` for every PC-relative literal, and for
   this region the literal is *not* a global but a small struct offset or a heap pointer. I resolved
   every relevant literal against `build/code.bin` (image base 0x00100000, i.e. file offset = vaddr −
   0x100000; verified against `asm/text/text_00140048.s`). This changed the reading of three clusters
   (see §3).
5. **Assembly for damaged functions.** For the ~10 entries where Ghidra emitted `halt_baddata`,
   `unaff_rN`, `in_sN` or "bad instruction" (`0x1000BA`, `0x10C642`, `0x11223E`, `0x1148F0`,
   `0x11B048`, `0x152EA8`, `0x163858`, `0x1DBD58`, `0x316B4C`), I read the real disassembly in
   `asm/text/text_00100048.s` / `text_00140048.s` rather than guessing from the C.
6. **Bottom-up order.** Leaf helpers first (64-bit division, semaphore/ring primitives, heap alloc,
   field writers), then their users (channel-state init/restore, stream context, BGM player, allocator
   trampolines).
7. **Generation script** in `%TEMP%\opencode\n032\build.py` asserts: exact address-set equality with
   the batch, no duplicates, 7 keys per entry, `confidence` in range, `name` present in `signature`,
   `maybe_` exactly on `confidence < 0.5`, and no name collision with any other naming source. The JSON
   is generated, not hand-edited, so it can be regenerated after review.

## 3. Cross-cutting discoveries (reusable by other lanes)

* **`svc 0x32` is `svcSendSyncRequest`, and the `thread->f_80 = g_00xxxxxx; svc 0x32` idiom is an IPC
  client stub, not `svcGetSystemInfo`.** The literal values are CTR IPC headers:
  `0x00060040` (cmd 6, 1 normal param), `0x00150082`, `0x00160042`, `0x00130042`, `0x0018000182`,
  `0x08620040`, `0x000200040`, `0x000B0040`. Each wrapper stores the header/params at TLS+0x80.. and
  reads results back from +0x84.. — the standard CTR ABI. **I initially read these as GetSystemInfo
  wrappers (N_022 did too); the header values disprove that.** Names were corrected to
  `Os_SendIpcParam` / `Os_SendIpcQuery6` / `maybe_Snd_SendIpc*`.
* **`0x002FF628` is the game's global `malloc`** (`heap = *0x7B0078; lock(heap+0x58);
  Heap_Alloc(heap,size,4); unlock`), and **`0x0011EDA8` is the heap allocator** used by the whole
  binary (`0x122CF0` rounds to 4 bytes, walks the free lists and splits via `0x123E6C`). `0x122ABC` is
  a separate *linear address-range* allocator (base/end pair) used by `0x11E720` before a page map.
  Four **unreferenced** trampolines (`0x14BB08`, `0x14FB34`, `0x156114`, `0x156FE4`) are per-subsystem
  allocator stubs for the .bss heaps at 0x7C840C / 0x7C83B4 / 0x7C8464 / 0x7C835C; a byte search for
  their entry pointers finds no reference anywhere in the image.
* **`0x125E58` / `0x126198` are `__aeabi_uldivmod` / `__aeabi_ldivmod`** (reciprocal table at
  0x126108, three Newton steps). Any 64-bit division in the game goes through them.
* **The 0x112xxx–0x124xxx cluster is a double-buffered, 24-channel command state.** The readable C's
  `g_0011913c`/`g_00122ef4`/`g_00118ba8` literals hold the offsets **0x10A4 / 0x131E / 0x1322**, i.e.
  the base of two 0x60-byte banks of 24 channel pointers and the two bank-selector fields. Every
  "setter" in that range writes one field of one channel block, then ORs one bit into the block's
  dirty mask. Twenty-four channels + a 16 KB shared buffer + an IPC service session is the 3DS **DSP**
  profile (ndsp:), so I grouped it as `Snd_`, but see the honesty note in §6 — the evidence is
  structural, not protocol-level.
* **The real BGM player is at 0x1EC000–0x1F3D60** and is now mapped end-to-end:
  `Snd_PrepareBgmStream` (0x1EC088) → `Snd_RequestBgmPlay` (0x1EC1D0) → `Snd_StopPendingBgm`
  (0x1EC55C) / `Snd_RequestBgmStop` (0x1EE4F8) / `Snd_SetBgmVolume` (0x1ED8A4), plus
  `Snd_ResolveSceneBgmId` (0x1F3AC4) and `Snd_PlayBgmById` (0x1F3D38). The channel-level primitive they
  all use is `0x114CFC` (`Snd_FadeChannelToGain`), and the four `Gfx_SetLayerStateA..D` functions
  (0x1F336C/0x1F33E0/0x1F3454/0x1F34C8) are byte-identical four-slot state trackers called together by
  the renderer and `Ui_LoadIconTextures`.
* **`0x00100B74` is the UTF-16 `strlen`** (also found by N_030 and N_033). It appears as a "noreturn"
  call in `0x1DBD58`'s decompilation, which is why that function ends in an apparent abort; I named the
  function from its stream-callback role instead of trusting the call.

## 6. Honest gaps / what is NOT verified

* **111 of 150 are below 0.5 confidence.** This window is statically linked runtime code with no
  symbols, no strings and (for ~40 of them) no callers inside the game code, so behavioural naming is
  the best available. The names say what the code does, not what Nintendo called it.
* **The DSP-vs-GPU attribution of 0x112xxx–0x124xxx is inferred, not proven.** Evidence: 24 channels,
  double-buffered banks, a 16 KB shared buffer, an IPC service session, dirty-mask setters. That fits
  the 3DS DSP service best (and matches the batch label "Audio"), but I did not verify the service name
  or the protocol. If a follow-up finds the session open string (the `0x119498`/`0x11F6C0` IPC path),
  this whole cluster can be confirmed or renamed in one edit.
* **Signatures are reconstructions.** Where Ghidra lost arguments (`unaff_r6`, `in_s0`, `in_r3`,
  `register0x00000054`), the parameter lists in `0x10C642`, `0x11223E`, `0x1148F0`, `0x11B048`,
  `0x163858`, `0x1DBD58`, `0x316B4C` are my best reading of the surrounding callee usage, not a
  verified prototype.
* **`0x00152EA8` is not code that Ghidra could decode** (single `halt_baddata`). It is named
  `maybe_Game_UndecodedCallback` only so the batch is covered; a human must disassemble the bytes
  around it (it is called from `0x006B95E4` as a callback).
* **The subsystems behind `0x1B7340`, `0x1CFFCC`, `0x1D6CEC`, `0x1DBD58` and `0x316B4C` are guesses**
  from their callees (`0x4FFxxx`, `0x501xxx`, `0x514xxx`), which are themselves unnamed. Battle vs.
  field vs. save was not distinguishable from the code alone.
* **`0x10B524`, `0x163858` and `0x1148F0` remain fuzzy** even after reading the assembly: the first is a
  block/stream decoder object whose codec I could not identify, the second is a refcount-to-zero
  callback with an unrecovered register, the third is a ring-space search with bad instruction data.
* No decompiler/symbol change was made (owned files only), so the readable C still shows `FUN_`/`func_`
  for these addresses until the merge lane applies `M1_merge_names`.
