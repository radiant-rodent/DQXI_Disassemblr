## The lane title is wrong — the range is not audio

The dispatcher labels the window "Audio", but the addresses are a mixed bag of 3DS SDK modules and
one middleware block:

| prefix | count | what it really is |
|---|---:|---|
| `Svc_` | 77 | `y2r:u`/`ac:u`/`cecd:u` service clients, raw IPC senders, sync-object and refcount helpers |
| `Gfx_` | 35 | movie/video playback: track table, 4-slot surface ring, Y2R conversion, decoder state machines |
| `Ui_` | 25 | icon/atlas cache that sits on top of the CECD content service |
| `Text_` | 7 | UTF-16 text layout + the text parser of the message system |
| `Regex_` | 6 | a genuine regex engine (see below) |

## Method (all scratch tooling in `%TEMP%\opencode\n033\`, nothing written into the repo)

1. **Digest** (`analyze.py`): parsed all 18,748 `decomp/readable/**/*.c` bodies, built an
   `address → body` map, a reverse `func_XXXXXXXX` caller index, and merged every known name from
   `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all existing
   `orchestration/naming/out/N_*.json` (4,693 names) so callees/callers show real names where a
   previous batch already named them.
2. **Literal resolution**: every `g_XXXXXXXX` in a body was resolved against
   `original/exefs/code.decompressed.bin` (image base `0x00100000`) with the section map from
   `sections.ld` (text `0x100000-0x72403C`, rodata `0x725000-0x79AA18`, data `0x79B000-0x7C2D24`,
   bss `0x7C3000-0x8398E4`). Results were classified as code pointer / vtable (first words point
   into text) / string / struct / float / integer.
3. **Vtable recovery**: scanned rodata for runs of ≥2 code pointers (3,809 runs) and reported, for
   each batch function, its vtable base and slot plus the full slot list. That is how
   `0x004FC794` (slot 2 of `0x00780C14`), `0x004FD794` (slot 0 of `0x00780C3C`), `0x004FDEE8`
   (slot 0 of `0x00780C5C`), `0x00505448`/`0x00505510` (class `0x00780EAC`),
   `0x0050BED4/0x0050BF64/0x0050BFE8` (class `0x00780FE4`) and
   `0x0050C208/0x0050C1E0` (class `0x00780FC4`) were placed.
4. **Decisive string evidence**: the only trustworthy service strings in the image were located by
   scanning for `name:letter` patterns and then proving the address appears as a literal in the
   code:
   * `0x005012F4 → 0x0072D6F4 "y2r:u"` → Y2R colour conversion (`0x005012BC`/`0x00501300`/`0x00501470`);
   * `0x00501660 → 0x0072FB84 "ac:u"` → the `ac:u` client cluster (`0x00501554`..`0x00501D14`);
   * `0x0050C554 → 0x007418AC "cecd:u"` → the CECD content service client (`0x0050C328`..`0x0050D08C`).
5. **Bottom-up**: IPC command senders were identified first (they are unambiguous: header word +
   `software_interrupt(0x32)` = `svcSendSyncRequest`), then the session/pool layers, then the
   cache/atlas layer that calls them.

## Clusters that were actually proven

* **`0x004FC230`–`0x00501470` = movie playback.** `0x005012BC` opens `y2r:u`, `0x00501300` is a
  13-argument Y2R program (luma plane `w*h`, chroma planes `(w/2)*(h/2)`, input format, output
  RGBA, stride) and `0x00501470` inverts the unit's busy flag. The caller of both is
  `0x004FD4F4`, which pulls a decoded frame out of a 4-slot ring (`&3`, 0x14-byte stride) and hands
  the three planes to Y2R — that is a YUV420 video frame, not audio. The rest of the block is the
  track table (`0x007AE154`: array `+0x0C`, count `+0x14`, 0x70-byte slots, 0x18-byte frame
  descriptors), a 64-entry completion ring (`0x007C805C`, drained by `0x004FC8A8`), the demuxer
  client (`0x006B98B4`/`0x006B9920`/`0x006B9948`/`0x006B99B8`/`0x006B9BB4`/`0x006B9BF4`), the
  worker-thread state machine (states 0..8, mutex at `+0x20`, 500,000/16,000,000-tick polls) and
  the per-frame update `0x00500134`.
* **`0x00504050`–`0x00505E00` = a pool-based IPC service client** (77 `Svc_` entries overlap the
  neighbouring cluster). Each sender is a literal header + `svcSendSyncRequest`: `0x08040142`,
  `0x080C00C2`, `0x080E0080`, `0x08120080`, `0x080201C2`, `0x080A0040`, `0x080C0000`,
  `0x080200C2`, `0x08080000`, `0x08030102`, `0x08040000`. Objects come from two free-list pools
  (0x209 and 0x207 slots) and carry vtables `0x00780EAC`/`0x00780EF0`/`0x00780EC0`/`0x00780EDC`/
  `0x00780F1C`/`0x00780F60`.
* **`0x509A20`–`0x50D08C` = content (CECD) service + icon cache.** `0x0050C520` literally opens
  `cecd:u`; the wrappers around `0x0050C63C`/`0x0050C6F8`/`0x0050C7B0`/`0x0050C808`/`0x0050C9C0`/
  `0x0050CA64` are its commands 0x03/0x12/0x11/0x07/0x08/0x0A (each has an `A`/`B` duplicate for
  the second session slot `0x007B005C`). The higher layer stores 0x70-byte entries with the
  `0x6060`/`0x6868`/`0x6767` magic words, 0x18C-byte page headers, a 1 MB / 98-entry / 0x19000
  limit triple, and is called from `Ui_LoadIconTextures` (`0x00383764`) — hence the `Ui_IconCache_*`
  names, which are honest about the UI role while the `Svc_Cecd_*` names cover the proven protocol.
* **`0x0050F9A8`–`0x0051150C` = a regex engine.** `0x0050F9A8` implements `\Q…\E` quoting
  (`0x5C`,`0x51`,`0x45`), a 0x60-entry per-character dispatch table and `0x00510208` for non-ASCII;
  `0x0050FDC4`/`0x00510050` parse `{…}` quantifiers into node kinds 8 and 7; `0x00510EB8` walks
  node kinds 0/2/3/4/5/6/7/8/0x12 (alternation, concatenation, groups, any-char, repeats) with
  charclass builders `0x0051384C`/`0x00513F78` and state stacks `0x00513A38`/`0x005139F0`.
  `0x0050F3B4`/`0x0050F6C8` are the *other* parser in the same region: UTF-16 text layout with
  `0x85`, `0x2028`, `0x2029` and glyph lookup `0x00712028`.
* **`0x0050D864` / `0x00383B6C` / `0x00383C18`**: the icon load stages — poll a content version
  (`0x001184F0` with size 4 and id `0xD0000`), then read the atlas entry table
  (`Ui_IconAtlas_Init` → `0x0050B824` → `Ui_IconAtlas_Release`).

## Honest traps and corrections

* **String inference from rodata can fool you.** `g_00504514 = 0x00780EAC` reads as `"HTP\0"`
  because the vtable's first slot is `0x00505448` (`48 54 50 00`). "HTP" is not a module tag —
  it is a vtable pointer. Same for `0x00501CF0 = 0x002D0082` (an IPC header, not a pointer).
  Every string claim in the JSON was re-checked against an address that is *actually* referenced
  as a pointer to a NUL-terminated ASCII run.
* **`0x005019F4` is not a text function** even though Ghidra renders its literal as `'t_seikou'`;
  it is an IPC request (header `0x003E0042`).
* The batch file's `0x0050A714` and `0x0050B3CC` live in `decomp/readable/recovered/`; all other
  addresses resolved in `decomp/readable/functions/`. No address needed the assembly fallback.

## What is NOT verified (read this before trusting the names)

* **The movie block's "video" reading is inferred, not proven.** The Y2R + plane-size evidence is
  strong for `0x004FD4F4`/`0x00501300`, but I did not prove that the 0x70-byte track slots are
  video+audio tracks rather than, say, texture-stream requests. The names `Gfx_Movie*` follow the
  neighbouring `Gfx_StreamSlot_*` names from an earlier batch (which I did not verify either).
* **The `0x504000`-`0x505E00` service is unidentified.** I could not find its name string; its
  commands are small integers (2,3,4,7,8,10,12,14,18) and its objects carry a 0x30-byte record with
  64-bit timestamps and a UTF-16 checksum. The `Svc_Ipc_*` names state exactly what is true
  (header + `svcSendSyncRequest`) and deliberately say nothing about the service's purpose. A
  follow-up should look at `0x00711AD0`/`0x007118CC`/`0x007116A0` (the UTF-16 helpers this client
  calls) and at `0x00504554`'s callers to pin it down.
* **The `cecd:u` command numbers are read from the IPC headers** (bits 16–31); I did not verify them
  against a CECD protocol description, and the *semantic* names `Cmd0003` etc. are therefore safer
  than `OpenRawFile`/`WriteRawFile` on `0x0050C328`/`0x0050C3CC`/`0x0050C474`/`0x0050C55C` (0.45,
  `maybe_`).
* **`Ui_IconCache_*` is a UI-role name**, not a proven class name: the only hard anchors are the
  0x70-byte entry magic words, the caller `Ui_LoadIconTextures`, and `0x0050C520`'s `cecd:u`.
* The `ac:u` client is proven to open the session (`0x0072FB84`), but **what the commands mean is
  not** — `Cmd003E0042`/`Cmd0004`/`Cmd0024`/`Cmd0005`/`Cmd0027`/`Cmd0040`/`Cmd002D` are named after
  their header values on purpose. The `ac:u` service is the 3DS "AC" module; I did not confirm which
  account/parental-control feature each command implements.
* `0x0050E5B8` (font refcount) and `0x004662D4` (panel icon hook) are single-caller wrappers at
  0.40 — plausible, not proven.
* No emulator or hardware was used; nothing was executed. No test suite was run (naming batches are
  exempt per the task), but the JSON was validated mechanically (below).
