## 1. The batch label is wrong — this is not audio

`orchestration/naming/batches/N_036.txt` says "Audio – 9 unnamed functions". Nothing in the window is audio.
The nine addresses are three unrelated pieces of the image that happen to fall in one address window:

| Group | Addresses | What it actually is |
|---|---|---|
| Variant-tree container | `0x006E7910`, `0x006E796C` | child-list destructor + "new child node" of a 32-byte typed value/`variant` node tree, allocated from the 16-byte-granule pool allocator |
| Library text | `0x00708BE4` | the integer-only `vsnprintf` core of the C runtime; only caller is the variadic `snprintf` thunk `0x0051BAA0` |
| Hashed archive reader | `0x007116A0`, `0x0071180C`, `0x007118CC`, `0x00711A44`, `0x00711AD0`, `0x00711E90` | ROMFS-style hashed metadata lookup: name hash → bucket → 0x18-byte dir / 0x20-byte file entries, UTF-16 names, 3DS `FS` error codes |

Most of the batch (`6/9`) is one coherent subsystem, so it was named bottom-up: entry reader → find
directory / find file → hash+fallback lookup → resolve one child → resolve a whole path.

## 2. What was done per function

Order of work (bottom-up, exactly as the task asks):

1. `0x0071180C` — reads one 0x18-byte directory entry at a known metadata offset (and optionally its name).
2. `0x007116A0` / `0x007118CC` — hash-bucket search over the directory / file entry chains.
3. `0x00711E90` — the hash itself plus the directory→file fallback and the error codes.
4. `0x00711A44` — seed a query from a known directory entry, then one hash lookup.
5. `0x00711AD0` — the whole UTF-16 path walk (`.`/`..`, `//`, absolute paths).
6. `0x00708BE4` — read the whole 9148-byte body (printf state machine) and its only caller.
7. `0x006E7910` / `0x006E796C` — the node constructor/free pairs (`0x006E78EC`, `0x006E7744`, `0x00514390`,
   `0x0051435C`) and the ~10 inlined copies of the same link sequence that prove what the helpers are.

Key evidence (all of it is inside the JSON `evidence` fields, repeated here only in summary form):

* **Path hash = RomFS path hash.** Seed literal `0x075BCD15` (123456789) at `0x0071201C`; the instruction
  stream is `eor ip, r3, sb` (parent id ^ seed) followed by `eor r3, r0, ip, ror #5` per UTF-16 unit —
  exactly the documented CTR RomFS metadata hash, including the per-directory chaining through the parent id.
* **Hash tables.** `bucket = hash % count` is `0x0011CFAC` (unsigned divide whose remainder comes back in `r1`,
  which is why Ghidra shows `extraout_r1` in every readable-C file); entries are read with `0x005047E0` at
  a 64-bit offset.
* **Entry layout.** Directory record 0x18 bytes = `{parentId, payload[3], nextSibling, nameLen}` + UTF-16 name at
  +0x18; file record 0x20 bytes = `{parentId, payload[5], nextSibling, nameLen}` + name at +0x20.
  Name comparison is `0x00100AD6`, a UTF-16 `strncmp`.
* **Errors are 3DS `FS` results** (module 17): `0xE0C04702` and `0xC8804471` are the literals at
  `0x00712020`/`0x00712024`, and the fallback triggers on module 0x11 + description 0x6F ("not found").
* **Paths are UTF-16 with `/`.** `0x0050DA68` rejects anything not starting with `0x2f`, collapses `//`,
  `0x0050DAD4` yields one component per call and sets an end flag at +0xC; `'.'` = `0x2e`, `'..'` = `0x2e2e`.
* **The variant nodes** carry a type byte (1 = null, 2 = u16, 3 = list of values, 4 = byte — decoded from
  the value copy routine `0x006E7744`), a 32-byte allocation from a 16-byte-granule bitmap pool, and their
  own child ring at +0x10; `0x006E78EC` is the constructor that establishes exactly that layout.

Deliberate naming decision: I used `Fs_Archive_*` and **not** `Fs_Romfs_*`. The hash algorithm, table shape
and error codes are RomFS-compatible, but the names are UTF-16 (CTR RomFS uses UTF-8) and every record is
4 bytes longer than the CTR layout, so the archive is at best a RomFS *variant* / game-specific clone.
"A correct vague name beats a precise wrong one" — `Archive` says what is provable.

## 5. Open problems / what is NOT verified

1. **`0x00711A44` argument layout is partly inferred.** Ghidra declares 8 parameters, the readable C shows a
   call with 6, and two arguments arrive on the stack (`&arg6` is taken as a pointer into the argument block).
   The mapping `name` / `nameChars` follows what the callee `0x0050DBA4` actually consumes, but I did not prove
   which register holds which — the *name* of the function is solid, its parameter list is the weakest part.
2. **Pool unit asymmetry in the container pair.** `0x006E796C` allocates 32-byte nodes with 2 pool units;
   `0x006E7910` releases the children it frees with 1 unit. The instruction stream is unambiguous
   (`mov r1,#2` vs `mov r2,#1`, `0x006E797C` / `0x006E7940`), so either the pool accounting is not
   size-based in the way I read it, or the original leaks 16 bytes per freed child. I did **not** resolve
   this; it does not affect the names, but someone touching this code should know.
3. **Who owns the variant tree.** All callers of `0x006E7910`/`0x006E796C` live in `0x00511xxx`–`0x00513xxx`
   (a `{u16 count@+0xa, u16 count@+0xc, heap@+0x10, child ring@+8}` structure). That region looks like a
   parsed parameter/tree structure (candidate: the UI/layout or command-list interpreter), but I could not
   anchor it on a literal or an exported name, which is why the names say `Container_` and not `Ui_`/`Script_`.
4. **Read vs write on `0x005047E0`.** N_033 named it `maybe_Svc_Object_Write`; the memory-backed branch is
   `0x00116A14(arg5, *arg1 + arg3)` and `0x00116A14` is `memcpy(dst=r0, src=r1, size=r2)` (verified at
   `asm/text/text_00100048.s:0x00116A14`), and every caller of my six archive functions passes a *local*
   buffer as `arg5`. So I treat it as a read in my evidence text. Either N_033's `maybe_` label should be
   corrected, or the object protocol really does use the same entry point for both directions with a
   swapped argument order — I did not chase it further because it is outside this batch.
5. **The service behind `0x00504xxx` is still unidentified** in the project (N_033 reached the same
   conclusion). Because of that I avoided `Svc_` names even though the archive mount object is opened
   through those wrappers.
6. `0x006F0C10` and `0x00707CAC` were called "snprintf" by N_003 / N_021. They cannot be aliases of
   `0x00708BE4` (the only `bl` to it is at `0x0051BAAC`), so they are probably UTF-16 or width-limited
   wrappers around a different core. Not verified — flagged for the merge task.
