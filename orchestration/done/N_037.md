## What the batch actually contains (the "Camera" label is wrong)

`tools/make_naming_batches.py` propagates a subsystem label through the call graph and then chunks
by address, so the header label is only a hint. The 150 addresses are four unrelated things:

| Range | Count | What it is |
|---|---:|---|
| `0x00100150`–`0x00101A82` | 22 | C/C++ runtime (`ctype`, `strto*`, `qsort`, `strstr`, array delete, printf-style char sink) |
| `0x0010DF00`, `0x0010EFC4`, `0x0010F0C8`, `0x0011FF8C` | 4 | async-I/O submit + critical-section queue probes + a frame colour setter |
| `0x00126EF4`–`0x00132D80` | 24 | one block-conversion class, emitted **three times** (8 functions each) |
| `0x001336E4`–`0x0013F130` | 100 | a prediction / VLC / filter block, emitted **twice** (51 + 49 addresses; one of the 51 is a data table, see below). The third copy starts at `0x0013F27C`, i.e. in N_038 |

## Method

1. Built a caller index over all 18,159 files in `decomp/readable/functions` (4.5 s) so every
   address got caller evidence, not just callee evidence.
2. Per function: readable C, callee list annotated with every name already known
   (`symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`, the other 30
   `orchestration/naming/out/N_*.json`), literal-pool globals, and the calling context of each
   caller (I read the callers, not just their names, whenever the callee was opaque).
3. Read the assembly (`asm/text/text_00100048.s`) and the raw bytes in
   `original/exefs/code.decompressed.bin` wherever Ghidra's readable C was ambiguous or
   truncated. That is how the two structural findings below were made.
4. Byte-compared the two big copies with the binary to prove they are the same code.

## Two findings worth propagating to the merger

1. **`0x001336E4` is not a function.** It is the 32-bit PC-relative filter-offset table that the
   motion-compensation routines dispatch through (`&LAB_00133810 + *(int*)(&LAB_00133810 + i*4)`);
   it sits immediately after the `5 "  VXS2"` marker that also precedes the copies of the block at
   `0x0013380C` / `0x00139E0C` / `0x0014040C`. Ghidra emits only `halt_baddata()`. It is named
   `maybe_Video_McFilterOffsetTable` and described as data so the merge/editor can stop offering
   it as a callable routine.
2. **`0x00139E90`–`0x0013F130` is a literal second emission of `0x00133890`–`0x00138B30`.**
   Verified byte-wise: identical sizes for all 49 pairs, 0–56 differing bytes out of up to `0xD70`,
   all inside the relocated literal pools. Every copy-2 name is the copy-1 name + `_B`, so these
   49 entries can be folded mechanically. The third copy starts at `0x0013F27C`, which is the
   first line of `N_038` — that lane should be told.

## Confidence and honesty

* Mean confidence **0.458**; 136 of 150 names carry `maybe_` (rule: `< 0.5` ⇒ `maybe_`).
  `maybe_` is present **exactly** for `confidence < 0.5`.
* **Certain (0.8–0.9), 10 entries:** `std_tolower`, `std_toupper`, `std_isspace`, `std_strtol`,
  `std_strtoul`, `std_strtod`, `std_strstr`, `std_qsort`, `std_qsort_internal_quicksort`,
  `std_destroy_range`; plus 4 more at 0.5–0.75 (`std_operator_delete_array`,
  `std_vec_delete_from_cookie`, `std_strtod_core`, `std_uninitialized_copy`). Evidence is
  behavioural, not name-based: ctype mask bits 4/3/0, the `ERANGE` errno store, the `LONG_MIN`
  clamp, the 8-byte ARMCC array cookie (`return first-8`), and 239 call sites for the array
  destructor loop.
* Exact distribution: 10 × ≥0.8, 2 × 0.6–0.8, 2 × 0.5–0.6, 114 × 0.4–0.5, 22 × <0.4.
* **0.3–0.35, 6 entries:** the throw helpers `0x0010018A`–`0x001002AE`. They demonstrably build a
  `[msg, msg+len)` range and call `0x002FF6AA`/`0x002FF6E6` with a fixed literal, but the
  exception *types* live in stripped typeinfo, so they are only named as a family.
* **0.4–0.48, 124 entries:** the image/video module. What is proven: YUV/RGBA block conversion
  with saturating 8-bit arithmetic over four lanes `0x400` bytes apart, quarter-pel motion
  compensation with 16-phase luma and 8/4-phase chroma filter banks, a coefficient decoder with
  two interleaved VLC bodies (`switchD_00133b00` case bodies, escape code 9, reservoir refill at
  `0x00135868`), and 1:2:1 packed-RGBA filters. What is *inferred*: that this is the
  MOFLEX/Mobiclip movie decoder — the RomFS has exactly 10 `.moflex` files and no other video
  payload, and `0x006B8C38` drives the converter with 16 bpp rows. That inference is why every
  one of those names is `maybe_`.

## Not verified / open problems

* **No test suite was run** — the task exempts naming batches. Nothing was executed or emulated.
  The bit-matching rebuild is untouched: no file outside the three named above was written.
* **The three block-conversion classes (A/B/C)** differ only in their constant pools
  (`g_00126EEC`, `g_0012AC64`, `g_0012E9DC`). I named them by the *observable* block size
  (8/16/32 bytes) instead of by output pixel format; which format each emits is unproven.
* **`0x00132D80`** (the only member of that class with a real caller) is named
  `maybe_Video_ConvertStripTo16bpp`; "16 bpp" comes from the caller's 2-byte column step, not from
  the callee.
* **`0x00138964` / `0x00138B30` / `0x00138C7C`** are only partly visible in the readable C (many
  `unaff_r*` registers), so their summaries stop at "multi-pointer packed-RGBA filtering over the
  four `0x400`-spaced lanes".
* **`0x001352A0` / `0x00135534` / `0x00135740` / `0x00134EE4`** are case bodies of the switch at
  `0x00133B00` (Ghidra literally names them `switchD_00133b00::func_…`) and use the caller's
  `r6`/`r11`/`r12`; they are real functions in the entry-point table but not independently
  callable, which is why their names are `Vlc*`/`Coefficient*` rather than a full description.
* The `Fs`/`Os`/`Gfx` names at `0x0010DF00`/`0x0010EFC4`/`0x0010F0C8`/`0x0011FF8C` are
  behavioural only (vtable submit + handle release, `svc 0x24`/`0x14` critical-section probes,
  device vtable `+0x14` then a 5-byte colour record).
