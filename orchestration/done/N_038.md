# N_038 — Camera-labelled naming batch (resumed)

**Lane:** `N_038` · **Batch:** 150 unnamed functions, `0x0013F27C-0x0016B8F4` (non-contiguous)
**Output:** `orchestration/naming/out/N_038.json` (150 entries, batch order)
**Status:** complete for all 150 addresses; several identifications are inherited rather than re-proved (see *Not verified*).

## What already existed when I resumed

Nothing. There was no `orchestration/naming/out/N_038.json`, no done report and no
`AGENT_LOG.md` entry for this lane, so all 150 functions were named from scratch.

## Method

1. Merged every known name (`decomp/ghidra/functions_merged.jsonl`, `symbols.json`,
   `symbols_recovered.json`, `decomp/native_names.json`, all `orchestration/naming/out/*.json`)
   and built an address-indexed caller/callee graph over `decomp/readable` (`analyze.py`).
2. Read each function's readable C, then re-checked the interesting ones against the
   **disassembly** (`asm/text/text_00140048.s`). That was essential: the seed's Thumb-prologue
   heuristic produces false entry points inside ARM code, and Ghidra's Thumb decompilation of
   those addresses is nonsense. I wrote `enclosing.py` to walk the listing backwards to the last
   real `push {..,lr}` and name the fragments as fragments.
3. Scanned `original/exefs/code.decompressed.bin` for `[function pointer][name]` binding-table
   entries and for inline string literals (`scan2.py`, `scan3.py`). The literals are the strongest
   evidence in this batch (array errors, thread-state strings, format specifiers).
4. Compared with the neighbouring lanes. **N_037 covers `0x00100150-0x0013F130` and had already
   analysed the first copy of the same video-decoder module**, which made the first 51 functions of
   this batch a deterministic mapping rather than a guess (see below).

## Key findings

### 1. `0x0013F27C-0x00145ABC` is the `_B`/`_C` copy of N_037's `Video_*` decoder

N_037 named `0x00133890-0x00138C7C` (`McPredict*`, `DecodeCoefficient*`, `InterpolateBlock*`,
`BlendPlanes*`, `FilterRgba*`). Our range contains two more copies of exactly the same code:

* the `_B` copy at `0x139E90+` (its tail, `FilterRgbaFrame_B`, is our `0x0013F27C`);
* the `_C` copy at `0x140490+`, i.e. every address shifted by **0xCC00** (`_B` by 0x6600).

51 of our 150 functions match an N_037 address **one-to-one by size, in the same order**, and the
jump-table bases move by the same 0xCC00; e.g.

| ours | size | N_037 sibling | name |
|---|---:|---|---|
| `0x00140608` | 316 | `0x00133A08` | `McPredict1ApplyMv_C` |
| `0x001424BC` | 1296 | `0x001358BC` | `InterpolateBlock4x4_C` |
| `0x001441B4` | 3440 | `0x001375B4` | `FilterRgbaRow_C` |
| `0x0014587C` | 4672 | `0x00138C7C` | `FilterRgbaFrame_C` |

I copied N_037's summaries/evidence for these and marked each entry as inherited. I did
independently confirm the motion-compensation mechanics in the disassembly: origin pairs at
`+0x3BC/+0x3C0`, the 8×2 phase index `(x&7)+((y&1)<<3)`, the 4-phase (`and r7,#3`) and 2-phase
chroma banks, and the `lsr #1`/`lsr #2` plane addressing.

### 2. Twelve batch entries are not real functions

The prologue scanner fired on ARM `bl` encodings whose low halfword looks like a Thumb `push`
(e.g. `bl 0x634418` = `0xEB13B571`):

| entry | really |
|---|---|
| `0x00146E4C`, `0x00146E8C` | case 0 / case 1 branches inside `IECameraEx` (`0x00146DF4`) |
| `0x00148780`, `0x001487C4` | inlined `sq_getinteger` for argument 1 / 2 inside `0x0014872C` |
| `0x00152254` | tail of `SQCommand` (`0x0015179C`) |
| `0x00159C48` | continuation of `MessageRegistActor` (`0x00159B7C`) |
| `0x0015FA00` | inside `GetMiniGameIDFromGimmick` (`0x0015F988`) |
| `0x001637F4`, `0x001638BC` | inside the Thumb sound routine at `0x00163650` |
| `0x00169076`, `0x0016907A` | inside the window update routine `0x00168C64` |

These are named after the parent routine with the false-prologue fact in the evidence, so the merge
step (M1) can drop them instead of creating 12 bogus symbols.

### 3. Squirrel standard library, proven by literals

* `0x0014ABCC` `Script_ArrayRemove` — "index out of range", 8-byte elements, size/capacity at
  +0x1C/+0x20.
* `0x0014B0D8` `Script_ArrayResize` — "size must be a number", "wrong type", "idx out of range".
* `0x0014B36C` `Script_ArrayCopyRange` — "wrong indexes", "slice out of range".
* `0x0014F008` / `0x0014F10C` `std_string_tolower` / `std_string_toupper` — per-byte mapping
  through `0x00100150` / `0x0010016A`.
* `0x00148BA8` `std_string_findchar` — `strchr(string+start, byte)`, pushes the index.
* `0x0014F93C` `std_Format_ParseSpec` — printf/scanf conversion-character parser.
* `0x001590E0` `Script_ThreadGetStatus` — literals "running"/"suspended"/"dead" + state byte +0x74
  (0.85, the strongest name in the lane).

### 4. `0x0016815C-0x0016B8F4` is a UI window/command-queue class

Not camera, not gameplay: a global window list at `*(ctx+0x5C)+0x4260`, four instruction lists of
26 slots at +0x428C, and a per-frame queue at `self+0xE8` with 0x2C8-byte frames / 0x8C-byte slots
(event id at +0x88). `0x0016B810` is the enqueue primitive, `0x0016A78C`/`0x0016932C` drain it, and
`0x0016A080`/`0x0016A2C8`/`0x0016B8F4` poll the widgets' SE objects. Named `maybe_Ui_CmdQueue_*`
/ `maybe_Ui_Widget_*` at 0.4-0.6.

### 5. Smaller groups

* `0x00146B10` `Gfx_DrawLine2D16` — Bresenham rasteriser, 8-direction table at `0x00146C54`, two
  pixels per iteration, clamps to ±0x7FFF.
* `0x00148F08` `Battle_SetActorEffectId` — kind 0-2 action effect slots, 3 state effect, 4 extra.
* Seven `Sound_*` wrappers around `0x005F5818` (SE object) + `0x005F7F78`/`0x005F747C`.
* `0x00163254`-`0x001638BC` BGM-channel create/command/restore/load; `0x00165004`
  `Script_ParseNumberString`; `0x00166268` `Script_ToString`.
* `0x0016A3F8`, `0x0015BA5C`, `0x0015ACB0` (`Math_ClampPointToBox`) etc. are documented in place.

mechanical checks were run:

* All seven keys present on every entry; no empty `summary`/`evidence`; no `param_*` names.

  134 `maybe_` names.

## Open problems / not verified

* **The 51 `maybe_Video_*_B/_C` names are inherited from N_037, not independently proven.** The
  size/order/table-shift match is exact, so a wrong slot assignment is unlikely, but if N_037's
  reading of the module as a software video decoder is wrong, all 51 names are wrong with it.
* `0x00148CA4` `maybe_Script_StringFormat` is the weakest "confident" name; the body also looks like
  a generic "call this string/object with the remaining arguments" helper.
* The UI command ids (0x14, 0x15) and event meanings are inferred from usage, not from a name table.
* The `Sound_BgmChannel_*` names are structural (allocator + stream open + message-window calls); the
  exact channel semantics are not proven.
* Nothing was executed or emulated. The only ground truth used is the retail binary/disassembly and
  the inline literals.
