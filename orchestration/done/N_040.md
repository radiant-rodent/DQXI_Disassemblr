# N_040 — naming batch 0x001874EC–0x001BB260

Status: **completed** (150/150 addresses named; `maybe_` prefix exactly where confidence < 0.5).

## What was done

The lane was resumed from nothing: `orchestration/naming/out/N_040.json` did not exist, there was no
done report and no `AGENT_LOG.md` entry. All 150 addresses in
`orchestration/naming/batches/N_040.txt` were analysed and named.

Working method (bottom-up):

1. Built a caller/callee/string/data-reference index over the batch from
   `asm/text/*.s` (1.69 M instructions), `decomp/readable/functions`, `decomp/ghidra/functions_index.json`,
   `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all existing
   `orchestration/naming/out/N_*.json`
   (scratch: `%TEMP%/opencode/n040/report2.json`, `chunk2.py`, `body.py`).
2. Read the readable C for every address (the first batch item through `body.py`; large bodies by
   full file) and re-read the hot callees that had no name yet: `0x005FC86C` (lexer), `0x001BD318`,
   `0x001BDD50` (AddInstruction), `0x001BE454` (PopTarget), `0x001BCE5C` (PushTarget),
   `0x001BF7D8`/`0x001BF798` (SQObjectPtr assign/destroy), `0x00100BE0` (per-element destructor loop),
   `0x006F1EEC`/`0x006F20C0`/`0x006F1DF8`/`0x006F229C` (game-work accessors), `0x0051B1FC`+`0x0011CD80`
   (text width), `0x0061BD4C` (per-character record lookup), `0x0036175C`/`0x00360254` (scene slot
   ready/commit), `0x006D7454`/`0x006D7508`/`0x006D76A0` (pane stack), `0x0031A394`/`0x0031A48C`
   (sprite mesh), `0x002D1304` (Anim_Instance_ApplyTemplate).
3. Checked the literal pools directly in `original/exefs/code.decompressed.bin` to resolve every pooled
   string/vtable pointer (e.g. the compiler token-name table at 0x18775C, the level table at 0x7354BC,
   the tagged null constants 0x01000001 / 0x05000002 / 0x05000004).
4. Because the on-disk Squirrel reference source (`3DS_Translate/_emutest/tools/squirrel_src`) is 3.3
   while the game binary is 2.2.5, the compiler identification was cross-checked against this project's
   own 2.2 opcode table in `tools/sqbin.py` and the in-binary version string.
5. Saved results in seven chunks (`part1..7.json`) and merged them in batch order, then validated
   mechanically.

## What the range actually is

The batch header says **Camera**, but the label is wrong — there is no camera code in the range.

| `0x0018BBB0-0x0018BF48` | Squirrel-value array holder (C++) | 8-byte SQObjectPtr array, refcounted bit 0x08000000, tagged null 0x01000001, destructor that walks the array with `0x001BF798` |

## Not verified / open problems

- The `maybe_Text_*` group (0x00190xxx) is named from the observed 24-cell glyph grid, width
  accounting and font-record refreshes. I could not prove whether the same object is used by the
  message window, the equipment-row editor, or both (they share the +0xEC/+0x11C layout through
  `Text_InsertLineChar` 0x001901F4).
- The `Cut`/`Dig`/`Nut` action naming in 0x001BA2D8–0x001BAB48 rests on a name table reached through
  literal-pool reads and on the twin structure of the two action classes. The start/end direction is
  inferred from which half calls the state setter (0x0023B61C vs 0x00239A1C, 0x002219C8 vs
  0x0022225C), not from a symbol.
- 0x001A48D8 is Thumb and Ghidra's recovered body is only `0x0062AE90(); return 0;`. Its name is a
  neighbour-based guess (confidence 0.30).
- 0x0018BBB0 / 0x0018BF48 are named from the SQObjectPtr layout, not from a class symbol; the owning
  class is not identified.
- The four resource getters (0x001941D4/0x001943B8/0x00194620/0x0019466C) are confirmed to be
  string-keyed hash lookups, but which table feeds which renderer feature is not established.
- 0x0061BD4C is called `Item_LookupRecord` by an earlier lane; here it clearly returns a per-character
  record. The old name should be revisited in the merge step.
