# N_041 — Camera-labelled naming batch (resumed)

**Lane:** `N_041` · **Batch:** 150 unnamed functions, `0x001BB300-0x001D66F0` (non-contiguous)
**Output:** `orchestration/naming/out/N_041.json` (150 entries, one per batch address)
**Status:** complete for all 150 addresses, but the middle of the batch is identified by structure
only — read *Not verified* before trusting any single name below 0.5.

## What already existed when I resumed

Nothing. No `orchestration/naming/out/N_041.json`, no done report, no `AGENT_LOG.md` entry for
this lane, so all 150 functions were named from scratch. (Batch file is unchanged: 150 lines.)

## Method

1. Built a name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and
   every `orchestration/naming/out/N_*.json` (5,115 names), then indexed **every** occurrence of
   `func_XXXXXXXX` across all 18,748 files in `decomp/readable` into a caller index
   (`%TEMP%/opencode/callers.py`, cached in `calls_index.json`). Every entry's evidence line names
   its callers/callees as a result.
2. Dumped each function's body with the readable-C header stripped (`show.py`, `multi.py`,
   `peek.py`) and worked bottom-up: leaves (`Script_ObjectPtr_Assign`, `Math_QuatMultiply`,
   `Math_RandomChanceBelow`) first, then the containers that use them.
3. Read raw `.rodata` out of `original/exefs/code.decompressed.bin` at every literal the batch
   references. This is what actually identified the second block (Squirrel VM strings) and the
   camera block (`win_movie`, `win_dungeon_place`, `chara_skeletal_param.bxon`, `emotion_sleep`).
4. Cross-checked the Squirrel hypothesis from both sides: the object tags (`0x08000000`
   refcounted / `0x02000000` delegable / `0x0A000020` delegable table in the `.data` words at
   0x1BE7A4/0x1BE7A8) and the compiler callers at `0x00185720-0x001892A4`, whose token codes are
   plain ASCII (`0x5B` = `[`, `0x5D` = `]`, `0x2C` = `,`).

## What the batch actually is

The "Camera" label is a propagation artifact of `tools/make_naming_batches.py` (same finding as
N_038), not a module. In link order the 150 functions are five unrelated layers:

| Range | What it is | Confidence |
|---|---|---|
| `0x001BB300-0x001BC750` | UI object helpers: intrusive-list init/teardown, `2d/battle2/{common,bg,enemy,parts/effect}` pack open (0x1BC2A8), refcounted-handle release/re-parent | medium |
| `0x001BCE5C-0x001BF7D8` | **Squirrel script VM / compiler support**: `SQGenerator::Yield/Create/Resume/Release`, `PushLocalVariable`, `SQObjectPtr::operator=` | high |
| `0x001C33FC-0x001C9CD8` | field scene/render-activation: 10-slot object table, two attached objects with generation-checked handles, six broadcast families, `chara_skeletal_param.bxon` | medium |
| `0x001CA304-0x001CE8AC` | one large actor/character instance (32 components at +0xE9C, flags +0x39D, `emotion_sleep`, `win_movie`), incl. `Math_QuatMultiply` | low-medium |
| `0x001CF72C-0x001D66F0` | **camera**: two per-screen blocks 0xABC apart (+0x54 upper / +0xB10 lower), selector `f_15CC`, 0x1C-byte work entries, projection at +0x15F4, `Camera_Reset`, `Camera_SetupFromRecord` | medium-high |

Highlights worth keeping:

* `0x001BF7D8 Script_ObjectPtr_Assign` — 88 callers, tag bit `0x08000000`, refcount at `+4`,
  release through vtable `+8`. This is the single most reused helper in the batch.
* `0x001BDBC4 pushLocalVariable` — the only reference to
  `"internal compiler error: too many locals"`, with the literal `0xff` guard (Squirrel's
  `MAX_FUNC_STACKSIZE`). `0x001BDE42` is a duplicate entry point for its epilogue.
* `0x001BED00` / `0x001BF108` — `Yield` / `Resume`, each quoting its own engine error string and
  saving/restoring the VM's 0x30-byte call frame. Together with `0x001BF004`/`0x001BF614`
  (create/release) this is a self-contained, provable sub-module.
* `0x001CEC28 Math_QuatMultiply` — plain Hamilton product, seven callers in transform code.
* `0x001D2ADC Gfx_SetActiveScreen` and `0x001D18E0 Gfx_InitScreenViews` finally explain `f_15CC`:
  it selects the 0x54/B10 screen block, and it is set from `0x002F265C() == 2`.
* `0x001D52B0 Camera_SetupFromRecord` resolves its target with the already-named
  `Field_CreateActorFromId` (0x1C7370), which is the strongest single hint that the 0x1D4-D5 block
  is the camera-work system.

## Tests

No test suite was run — naming lanes are exempt per the task statement (rule 5), and nothing in
this lane touches code. Mechanical validation only (`validate.py`, `check2.py`):

* `orchestration/naming/out/N_041.json` parses as a JSON array of 150 objects;
* every object has exactly the seven required keys;
* `address` matches `0x[0-9A-F]{8}` and the set equals the batch address set (no extras, no dupes);
* every `signature` contains its own name, and every key in `params` appears as an argument in
  that signature (or is `returns`);
* `confidence < 0.5` is exactly the `maybe_`-prefixed set; no name repeats inside the batch, and
  no name collides with `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` or
  any other `orchestration/naming/out/N_*.json` (two names were renamed for this:
  0x1C7C6C -> `maybe_Effect_CreateFromVariantTable` because N_002 owns `maybe_Effect_CreateVariant`,
  and 0x1C8D28 -> `maybe_Field_CreateActorObjectModel` because N_002/N_023 own the
  `...CreateActorObject` / `...CreateActorRenderObject` names for the sibling creators).

## Not verified / open problems

1. **Battle vs. field.** The 0x1CA-0x1CE block is definitely one large character/actor class, but
   I could not decide whether it is the battle or the field variant (the 32-component table at
   +0xE9C, flags at +0x39D and the 45 KB instance appear in both kinds of caller). Names
   therefore say `Actor_`/`Model_`; do **not** merge them into a `Battle_*` namespace without
   checking a caller such as 0x001CCE7C against the battle scene code.
2. **Decompiler damage.** `0x001BDD50`, `0x001CA7A0`, `0x001C7C6C`, `0x001C1F0C` and the
   0x1D1FC4/0x1D2222 pair contain `halt_baddata`/overlapping-instruction warnings. Their names
   describe the readable part only.
3. **The 12 KB view-transform pair** (`0x001D1FC4`, `0x001D2222`) is read at the entry only; I did
   not prove the matrix layout. Same for the 3.5 KB `0x001D15AC`/`0x001D15F4` layout appliers,
   which I named `maybe_Ui_ApplyRowLayout*` because their caller mix is UI, not camera.
4. **Squirrel class mapping.** I am confident about `ObjectPtr`, `Generator` and
   `PushLocalVariable`; I am *not* sure whether the 0xF4-byte object created by `0x001BE0B4`
   (`maybe_Script_Compiler_CreateFunction`) is `SQFunctionProto` or `SQClass` — the initialiser
   (`maybe_Script_Function_Init`) creates two tables and nulls metamethod slots, which fits
   `SQClass` better than the proto. Rename both together if you resolve it.
5. **Not checked against the disassembly.** Unlike N_038 I did not walk `asm/` for false prologues.
   `0x001BDE42` is clearly a duplicate entry point (it sits inside 0x001BDD50) and is named as
   such, but other sub-0x20-byte stubs (0x1BC734, 0x1D0980, 0x1D47F0) were read from the C only.
6. **Unnamed helpers that would lift many names.** `0x00710938` (generator stack copy),
   `0x003B1698`/`0x003B17C0` (projection setup/release), `0x0063E5C8` (character parameter record),
   `0x0058FC38` (character parameter block), `0x00639954` (entity type query) and
   `0x00622458/0x00622480/0x006226D8/0x00622C30` (per-screen view block ops) all appear over and
   over; naming them once would raise dozens of these entries above 0.6.
