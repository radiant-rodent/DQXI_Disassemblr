# N_042 — naming batch 0x001D6DF0–0x001FA8C8

Status: **completed** (150/150 addresses named, `maybe_` where confidence < 0.5).

## What was done

The lane was resumed from nothing: `orchestration/naming/out/N_042.json` did not exist, there was no
done report and no `AGENT_LOG.md` entry. All 150 addresses in
`orchestration/naming/batches/N_042.txt` were analysed from scratch and named.

Working method (bottom-up, as the task requests):

1. Built a one-pass caller/callee index over all 18,159 files in `decomp/readable/functions`
   (regex over `func_XXXXXXXX`, plus the Ghidra signature header, referenced `s_*` strings and
   `g_*` globals) — scratch script `%TEMP%/opencode/n042_index.py`, results cached as JSON.
2. Merged every previously proposed name (`orchestration/naming/out/N_00*.json`,
   `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`,
   `decomp/ghidra/functions_merged.jsonl`) into one lookup so callees could be printed with their
   known names (`n042_names.py`). 5,957 named addresses were available; the names that mattered here
   were `Battle_HpGaugeWindow_Update` 0x003CEEB0, `Battle_InsertActionSlot` 0x0016F28C,
   `Gfx_CreateSpriteMesh` 0x0031A394,
   `Snd_RequestBgmPlay` 0x001EC1D0, `Snd_FadeChannelToGain` 0x00114CFC and
   `Ui_ShopWindow_*`/`Ui_PanelMessageWindow_*`.
3. Read each function's readable C with a dossier printer that substitutes the known names inline
   (`n042_dump.py`), then read the hot callees that had no file or no name
   (0x00423648, 0x005E754C, 0x005E7598, 0x005F2B54, 0x006F1EEC, 0x006F1DF8, 0x006F229C,
   0x003E00CC, 0x00639954, 0x002340B0, 0x001EC744, 0x001F4478 …).
4. Cross-checked 0x305-caller functions and the biggest bodies (0x001D8E2C, 0x001F512C,
   0x001F4478) by reading their full decompiled bodies, not just the first screen.
5. Saved the JSON in four chunks (39 / 36 / 31 / 44 entries) so a resumed worker would never lose
   more than ~40 entries; merged and validated mechanically after each chunk.

## What the range actually is

The batch header says **Camera**, but the label is wrong — there is no camera code in the range.
The 150 functions are three adjacent engine modules:

| Range | Module | Highlights |
|---|---|---|
| `0x001D6DF0-0x001DB924` | UI widgets / windows | sprite-mesh creation (`Gfx_CreateSpriteMesh`, literal `"sprite"`), cursor-icon animations (`icon_cursor_default/word2/word3`), cursor entry list + select-by-id, party HP gauge window (4 × 0x260 slots → `Battle_HpGaugeWindow_Update`), character status window (18 slot flags, 3D actor registration), `movie/%s` player, actor animation timer pair |
| `0x001E0990-0x001E4BC0` | field actor locomotion + panel sequences | analogue-stick sampling, map-cell walkability (`0x0062CB64`/`0x0062C23C`), velocity integration into `actor->f_100/f_104/f_108`, and a state-handler framework (`+0x30` code pointer, `+0x34` bit0 + jump-table index) |
| `0x001E6C20-0x001FA8C8` | sound system + HUD/battle balloons | **`Sound_PlaySeById` 0x001EBC68 (305 callers)**, voice gain/pan/stop by encoded handle (`0xE0000000\|counter<<12\|slot`), `movie/%s`, the 0x13c-byte stream-file cache, `hud_balloon` layout binding and balloon spawning (`0x003246F0`), battle action queuing (`Battle_InsertActionSlot`) |

## Open problems / not verified

- **Batch label is wrong** (Camera). Do not use the batch header as evidence for these names.
- The `Battle_Ui_*` vs `Ui_Balloon_*` split in `0x001F3EA8-0x001FA8C8` is a hypothesis based on the
  `hud_balloon` layout string, the 16-slot member arrays and the `Battle_InsertActionSlot` call —
  there is no symbol for the class. Every entry there is `maybe_` at ≤ 0.45.
- `0x001D8E2C` (2.4 KB), `0x001F512C` (2.9 KB) and `0x001F4478` (2 KB) are described only at the
  level their callee sets prove; their internals were not fully traced.
- `0x001D782A` / `0x001D784E` are Thumb fragments that use the caller's `r6` as `this`; Ghidra lost
  the argument registers, so their parameter lists were reconstructed from the sibling
  `0x001D77C8` (`Ui_CursorIcon_SetWordType`). Their names are plausible but not proven.
- `0x001E7660` and `0x001E7FB8` are generic container/table helpers; the "event"/"ui" grouping in
  their names is a guess.
- Sound "category"/volume-group ids (`g_001ec078`, `g_001ec98c`, `g_001f5f58`, `g_001f7d80`,
  `0x158`, `0x1e`) are used correctly as constants but their semantic meaning (which SE family) is
  not decoded.
- Callee names such as `0x006F1EEC`, `0x0062AB3C`, `0x002D0E84`, `0x0062EF8C`, `0x001E3BEC`,
  `0x0011CB38` are **not** named anywhere yet, so evidence strings refer to them by address.
