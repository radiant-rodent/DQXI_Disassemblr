### What this batch actually is
The batch header says **Camera**, but (as N_038/N_041 also found) the label is a BFS-propagated
label from `tools/make_naming_batches.py`, not a module. The 150 functions are the
**field-party / camp-menu layer**, in link order:

| Address range | Layer |
|---|---|
| `0x001FA974–0x001FF63C` | on-map party/follower group: camera-target position & bbox, formation slots, 32-entry attachment table, effect spawn (`func_003FBE4C`), voice/SE selection (`func_001EBC68`), 15-entry method tables repeated in rodata |
| `0x001FFF9C–0x00209FCC` | menu/entry action engine on the ~0x4E80-byte game-work state (`+0x4200…+0x56FF`), four actor-list groups at `+0x428C`, two 64-entry lists, 28-slot condition evaluators, 16-slot target-set builder |
| `0x0020A208–0x0020FD80` | camp/item menu window state machine: five 0x40-byte slot records, `func_003D13C4` command-handler factory, layout objects at `+0x4330` (field) / `+0x47A0` (camp), message work at `work+0x24A98`, `it_0001` / `sk_0155` / `sk_0034` / `sk_0104` icon sheets |
| `0x002109FC–0x00215A68` | camp-menu layout/animation: `null_txt_l0`, `win_camp_select%d`, descriptor callbacks (code pointer + halfword `this` adjustment), five entrance animations, `win_dougu_do_select2/4/5` item window, `Gesture2`/`H3Gesture` |
| `0x00215AE4–0x00218B00` | party-talk window: 24 sub-panels, `param/talk_party/talk_party_%s.pack`, `talk_content.bxon`, message-parameter application |

Naming therefore uses `FieldParty_*` for the first block and `Menu_*` for the rest, instead of a
camera prefix.

### Confidence profile and honest gaps
- **24 entries at 0.50–0.55** — only functions whose whole body is mechanically readable
  (list-walk broadcasts, two-instruction flag resets, list counters, `talk_party` pack loader
  with its literal).
- **126 entries at 0.20–0.45**, all prefixed `maybe_`. These are structural readings
  (call shape, vtable slot, constants, literals) rather than proven semantics.
- The `FieldParty_` vs `Menu_` split is inferred from the field/camp layout-object pair and the
  actor-position code; no symbol proves it.
- Ghidra artifacts: `0x00200A5C` (8.7 KB state machine), `0x00203BF4`, `0x002040D0`,
  `0x00204980` and `0x00204D88` contain `halt_baddata` / overlapping-instruction sections.
  `0x002040D0` and `0x00204980` are named only from their surviving neighbour calls and say so
  in their `evidence`.
- The meaning of the 28 entry-condition ids (`0x002049FC`, `0x002053CC`) is inferred from the
  checks performed (actor categories 6/8/10/0x9C/0xB9/0xDC–0xDE, party counts, HP/MP ratio,
  level), not from a schema.
- Byte offsets quoted in summaries are Ghidra field offsets (`f_9C` = +0x9C). They are
  hypotheses and should be re-checked against call sites before being promoted to structs.
- Nothing here is verified against a running game. No exported data was produced, so the
  bit-matching build is unaffected.
