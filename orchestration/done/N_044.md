## The batch is not "Camera"

The batch header says `N_044 - Camera`, but the 150 addresses contain **no camera code at all**.
`make_naming_batches.py` propagates a subsystem label through the call graph and chunks by address,
so the label is inherited from a neighbour. What the range actually contains (verified per function):

| Address range | What it is |
|---|---|
| `0x00218EA8`–`0x00219ACC` | 2D sprite-actor creation/state helpers (base class of the `Actor2D` family named by N_024; same fields shifted by 0x38) |
| `0x0021B090`–`0x0021BC88` | `Actor2D` derived class: facing/`Open_Front`/`Open_Back` state, span array destruction, follow mode; plus one `std::string::push_back` at `0x0021BC88` |
| `0x0021C334`–`0x0021E1F8` | ui2d layout parts: 4 child slots at `+0xC0` bound to layout panes, child-part factories (200x120 descriptors), name-entry kana keyboard, five-row list cell release |
| `0x0021F450`–`0x0021FD68` | core UI part factory (`0x0021F738`, called by ~110 window constructors) and list cursor move |
| `0x00220984`–`0x002258A8` | character-model attachment slots (`Model_AttachSlot`/`Model_Attach`): setup, show/hide chains, world matrix, spin animation, effect spawn, animation playback |
| `0x00225BF4`–`0x00229ACC` | field-actor state controllers (scripted approach/talk) and UI sprite parts |
| `0x0022A948`–`0x0022AEC8` | skill-panel / list-owner UI objects |
| `0x0022AF9C`–`0x0022E0B8` | actor action table, per-player-state model variants, `Actor_TryPlayActionSeqXX` family, actor destructor |
| `0x0022E0F8`–`0x00234BBC` | per-player-state model/attachment sync, character model with equipment, behaviour-task chains, model preview, attract/idle animation selection |

I kept the subsystem prefixes honest (`Actor2D_`, `Actor_`, `Model_Attach_`, `Ui_`, `std_`) instead
of forcing everything into `Camera_`.

## Method

1. **Readable C** for every address from the batch file (all 150 files exist; no fallback needed).
2. **Caller index** over all 18,748 `decomp/readable/**/*.c` files (callee address → caller files),
   plus name resolution from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`
   and every `orchestration/naming/out/N_*.json` (so N_024's `Actor2D_*`, N_012/N_02x's `Ui_*`,
   N_002's `Model_*`, N_042's `Field_Actor*` names are reused consistently).
3. **Literal-pool scanner** over `original/exefs/code.decompressed.bin` (base `0x00100000`): every
   word inside a function's own range that looks like a pointer/floating constant is decoded. Ghidra
   drops strings from this range, so this was the only way to get: `sprite` (`0x007BE7B5`),
   `Open_Front`/`Open_Back` (`0x0021B360`/`0x0021B36C`), `Shake` (`0x0022AF2C`), `effect0`,
   `txt_skill`/`txt_pane`/`txt_title`/`txt_panel_r`/`txt_panel2_r`, `null_txt_0`,
   `keyboard_hiragana`/`keyboard_katakana`, `N_ALL`, `H,W`, `Walk`/`Run`, and the float constants
   (0.0174533 deg→rad, 2π/π, 0.0333333 frame step, 0.3/0.33/0.5/0.8/1.25/1.41421, 200/120 …).
4. **ARM disassembly** of individual ranges (`asm/text/*.s`) where the readable C was ambiguous —
   e.g. `0x0064C740` is literally `return *(u8*)self == 5` (used to prove `0x0021B510`), and
   `0x001C7560`/`0x001C7AD0` are `manager + id*12 + 0x24/0x28` list-slot accessors (used to prove
   the intrusive-list code in `0x0021C404` and the id unregistration in `0x0021C334`).
5. **Function-pointer table scan** of the image (search for each address as a little-endian word):
   found the `Actor2D` type table around `0x0075BD50`/`0x0075BE10`, which corroborated several
   names (`0x002199E4`, `0x0021B090`, `0x0021B6F0`, `0x0021B52C` are vtable/type slots). Most
   entries in the `0x00218xxx` block have **no absolute reference in the image**; they are reached
   through runtime-built tables, which is recorded in their evidence.

## Honest gaps / what is NOT verified

- `0x0021C404 maybe_Field_ResolveActorOverlap`: a self-contained algorithm over two intrusive
  object lists (manager slot 8), with a class filter (`0x007C4CFC`), distance/axis tests and a
  push-apart that sets per-side bits at `+0x28C`. No caller and no data reference exists in the
  image. "Resolve overlap" is a shape argument, not a proven semantic.
- `Ui_Part_*` family (`0x0021C8B0`–`0x0021DB80`): the mechanics are proven (four child slots at
  `+0xC0`, ui2d pane binding, 200x120/0xFF descriptors, id-registry unregistration), but *which*
  game object owns the slots (portrait? window frame? character part?) is not. Names are
  deliberately structural.
- `maybe_Actor_*BoundsCheck` (`0x002267EC`/`0x00226880`/`0x0022742C`): the code keeps the owning
  actor inside a rectangle derived from the level cell size; I used the neutral "BoundsCheck"
  wording rather than claiming "shadow" or "camera".
- `0x0022F620`/`0x0022F638` are a tail-duplicated pair (pattern transform); the second adds a
  second rotation. Which one the engine actually calls per frame is not established.
- `0x00233BC8` (0x24-byte entry point, 153-line readable file) and `0x00233BEC` contain Ghidra
  `halt_baddata()` artifacts / merged neighbours — the tail of both is unreliable.
- The `Actor_TryPlayActionSeq07/08/0A/0B/0C/0D/0E/0F/10/11/16` names encode the **literal action
  id** passed to `func_005E74A0` (a fact); what each action looks like in game is not claimed.
- `0x0022AF9C` (`Actor_CreateActionTable`, 45 callees, 0x11B0 bytes) is summarised at the level of
  "builds the action/command table"; individual action entries were not decoded one by one.
- Nothing was executed: no test suite (naming batches are exempt), no emulator, no binary change.
  All conclusions come from readable C + disassembly + literal pools + the call graph.
