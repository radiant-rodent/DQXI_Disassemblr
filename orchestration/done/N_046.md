## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md` and the batch.
2. Built a scratch index in `%TEMP%/opencode/`: for every batch address its readable C
   (condensed to drop the boilerplate headers), its callers and callees (cross-indexed over
   `decomp/readable/functions` + `recovered`, not just per-file greps), all `s_*_<addr>` string
   literals **resolved against `original/exefs/code.decompressed.bin` at base 0x00100000**, and
   all `g_*` globals with their u32 contents.
3. Scanned the whole executable for little-endian dwords equal to each batch address, which
   recovers vtable / handler-table membership and sibling functions — this is how the 44-record
   table at `0x0072B56C` and the training-window vtables (`0x0075CBAC`, `0x0075CC00`) were found.
4. Read the helper functions the batch depends on (`0x001A5F9C`, `0x001C6914`, `0x001C6A9C`,
   `0x001DAD58`, `0x003A7A2C`, `0x0062B2A4`, `0x004D2538`, …) and the outputs of the sibling
   naming batches (notably N_002, N_013, N_023, N_024, N_038, N_041) so the names agree with
   already-proposed neighbours instead of inventing a parallel vocabulary.
5. Worked bottom-up: leaf helpers (record getters, handle decode, queue drain) were named first,
   then the layout modes, then their callers.

## Open problems / not verified

1. **The 44-record table is orphaned.** `0x0072B56C` is referenced by no code (only by other
   rodata pointers), so the owning class of each record could not be established. The `A..L`
   suffixes are disambiguators, not facts. The recipe-book attribution of that family rests on
   N_041's caller analysis, not on the records themselves.
2. **Damaged decompilation.** `0x00263B10`, `0x00263CD8`, `0x00269200`, `0x0027E1E4`,
   `0x0027E794`, `0x0027FC60` contain `bad instruction data` / lost-register artefacts. Their
   summaries describe only the readable part and their names are intentionally generic.
3. **`0x00269354` has no readable body** — as the batch header warns, Ghidra merged it into
   `0x00269200`. It is documented as a second entry point of that initialiser, not as an
   independent function.
4. **Recipe/item ambiguity.** `0x00265924`'s 30 clause blocks are decoded structurally (offset,
   enabled byte, compare mode), not as a schema; the “recipe/alchemy list” reading comes from
   `0x0026732C`'s {item,min,max} ingredient check plus the `recipe.bxon` / `recipebook.bxon` /
   `item_details_3d.bflyt` strings. It could still be the item-bag filter.
5. **“Training”** is the name used by the asset files and by N_013, not a confirmed menu title.
6. Everything here is static analysis; nothing was run on hardware or an emulator, and no claim
   about runtime behaviour (beyond what the code reads/writes) is verified.
