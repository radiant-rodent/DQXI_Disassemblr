## Method

1. Built one address→name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all other existing `orchestration/naming/out/N_*.json`.
2. Built a caller index over all 18,748 `decomp/readable/**/*.c` files. Fixed a real bug in the
   reusable index: `decomp/readable/recovered/*.c` uses a `/* Recovered entry point XXXXXXXX (arm) */`
   header instead of the `Address:` line, so the earlier N_035-style loader silently skipped every
   recovered body (the first digest had 12 "SIG ? / 0 callees" functions; after the fix, all 150 have
   a body).
3. Wrote a literal-pool resolver: most `g_00XXXXXX` references in this batch are *not* globals but
   literal-pool words inside a function, so `g_`/`s_` is resolved to the word, and the word to a
   string / float / function / `image+offset`. This is what produced every pane/format name above.
4. Read every readable C body, plus the callee bodies that decide meaning (`0x27C2F0`,
   `0x27CF54`, `0x6F1EEC`, `0x6F1DF8`, `0x6F20C0`, `0x6F229C`, `0x2AB62C`, `0x62F680/94`,
   `0x3DFEC4`, `0x3E0454`, `0x335C24`), and the two functions that reference the batch's handler
   tables (`Ui_InitWindowManager` 0x27A9C8, `maybe_Ui_SubWidgetConfig_Init` 0x38BF68).
5. Cross-checked the sibling names already produced by earlier batches (N_003/N_011/N_021/N_030/
   N_038/N_041/N_042) so the new names do not silently contradict them; where an earlier name
   already existed for a neighbouring function (e.g. `Ui_CompositeWindow_Dtor`, `Ui_DiveWindow_*`,
   `Ui_SenrekiWindow_*`, `Actor2D_*`) the new name uses a distinguishing suffix and the summary
   says which family it belongs to.

### Structural finding worth keeping for the merger

A full third of this batch has **no direct caller**. Their entry points are installed in 8-byte
`{fn, 0}` handler tables at `0x728C80`–`0x72A8xx`, and those tables are referenced per entry, not as
a vtable: `Ui_InitWindowManager` (0x27A9C8) stores `0x728D74`, `maybe_Ui_SubWidgetConfig_Init`
(0x38BF68) stores `0x728DC4`/`0x728EC4`. This is why grep over `decomp/readable` finds nothing for
e.g. `0x280498`. Anyone re-running this analysis should scan `original/exefs/code.decompressed.bin`
for 4-byte references to the function address before concluding "uncalled".

## Honest gaps / what is NOT verified

* The seven window teardowns (`0x283374`, `0x28340C`, `0x283784`, `0x2839E4`, `0x283B94`,
  `0x283C18`, `0x283D88`) and the four identical "request state 2" updates (`0x283A6C`, `0x283AD0`,
  `0x283B34`, `0x283C94`) are lettered **A..G** / **A..E** instead of being assigned to individual
  window classes. Each has a byte-identical body but lives at a different
  address, i.e. it belongs to a different class; the class tables were not recovered, so any
  per-class name would be invented.
* The five cue methods (`0x284AE4`, `0x284B6C`, `0x284BDC`, `0x284C40`, `0x284CA0`) are certain about
  *which* fields they touch (16-bit id at +0, two callback words at +4/+8, 1/30 s float timer at
  +0x14, duration at +0xC, class descriptor tagged `HYD\0` at `0x72A79C` with the five methods at
  `0x72A7FC`–`0x72A820`) but not about the game's own vocabulary for the object; "cue" is my word,
  and "id vs duration" is inferred from the timer arithmetic.
* `0x28F5A0` (0x38C bytes), `0x292FBC` (0x32C) and `0x281C18` (0x4E8) are decompiler-damaged
  (`halt_baddata` / "could not recover jumptable"). Their names are structural and their summaries
  stop at what the readable portion proves.
* `0x290580` is a two-call predicate whose callee 0x64C740 was not analysed; it is left at 0.30.
* The party-panel reading (`0x280498`–`0x282100`) is high-level solid (party helpers, four 0x470-byte
  status panels, four member slots) but the *window's own* name is my wording (`Ui_PartyPanel_*`);
  the game may call it the status/command window.
* Nothing was executed or emulated. No Squirrel script was needed: the batch contains no bound
  native, and `decomp/native_names.json` has no address in this range.
