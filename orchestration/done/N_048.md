# N_048 — native naming batch, 150 functions (`0x0029D5BC`–`0x002BB77C`)

## What existed before this worker

Nothing. There was no `orchestration/naming/out/N_048.json`, no done report, no
`orchestration/logs/N_048.log` and no `AGENT_LOG.md` entry for N_048. The task file
(`orchestration/tasks/N_048.md`) was the only trace. So all 150 addresses were analysed from
scratch in this session.

## Method

1. Built an address -> name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 42 other `out/N_*.json` files. That map is dense in this
   window: 0x29xxxx-0x2Bxxxx is the UI/menu link-order band and nearly every neighbour is already
   named (`Ui_ListWindow_*`, `Ui_SakusenWindow_*`, `Ui_TsuyosaWindow_*`, `Ui_MessageWindow_*`,
   `Field_Npc*`, `Gfx_SpriteActor_*`). Those neighbours are the anchors for this batch.
2. Read every one of the 150 readable C bodies (no missing files), plus the immediately
   surrounding named functions that define the classes (`Ui_Object_CtorBase` 0x1A66A0,
   `Ui_Object_DtorBase` 0x1A6768, the engine delete thunk 0x10F6CC, the 0x2D0xxx 2D draw-record
   class, the 0x2D09xx/0x2D0Cxx setters, `Game_GetWork` 0x6F20C0, `Ui_GetCore` 0x6F229C).
3. Built a caller index over `decomp/readable/**` (18,748 files) and a literal-pool scanner that
   resolves every word inside a function body against `original/exefs/code.decompressed.bin`
   (base 0x100000) as C string / UTF-16 string / pointer. This is what produced the hard evidence:
   `win_tsuyosa1`/`win_tsuyosa4`, `.bffnt`, `null_q`/`emotion_chara_q`, `sprite`, `Nut`, `Walk`,
   `Bt_Dead`, `Run`, `D`.
4. Built a vtable scanner (maximal runs of text pointers) and a "which table references this
   address" lookup. This is the single most useful tool in this batch: every UI class here is a
   vtable with a fixed shape (slot 0 dtor, 1 ReleaseSub, 6 Pane_SetVisibleWithAnim, **slot 7 =
   the class's InitPanes**, 14 = class override), so a destructor can be attributed to a class by
   reading slot 7 of the table that holds it.
5. Read the vtable/handler tables themselves: `0x72A5E0..0x72A6D8` is the **SakusenWindow**
   handler table, `0x72BE30..0x72BEE0` a second window-handler table, `0x7261B4..0x726214` the
   method table of the cutscene/script object. Table membership is quoted in the evidence fields.

## What this slice actually is

The batch header says "Camera". That is only true for ~4 of the 150 functions. The rest is the
UI/menu link-order band, and it splits into these groups:

1. **PagerWindow / list-window base classes** (`0x29D5BC`, `0x29DDAC`, `0x2A4F80`, `0x2A520C`,
   `0x2A5224`, `0x2AC854`, `0x2B1E30`, `0x2B2070`, `0x2B2098`, `0x2B2118`). Destructors and base
   constructors; class identity read from vtable slot 7 (`Ui_PagerWindow_InitPageNumbers`,
   `Ui_LoadWindow_InitPanes`, `Ui_ThreeRowWindow_InitPanes`, `Ui_NumberWindow_InitPane`,
   `Ui_PartySelectWindow_InitLayout`).
2. **2D sprite draw records** (`0x29E520`, `0x29EF64`, `0x29F3E0`). A tree of sprite nodes whose
   leaves are 0x14-byte records consumed by `0x2D0CCC`; `0x29F3E0` converts an animation frame +
   a 10-halfword placement block into the concrete quad (uv rect with 4 flip modes, position,
   size, rotation, alpha, palette row). This is the clearest low-level find of the batch.
3. **TsuyosaWindow** (party "strength" window): `0x29FFE4` binds `win_tsuyosa1/4`,
   `0x2A007C` mode flag, `0x2A00FC` creates the 0x234-byte composite, `0x2A01EC` destroys it.
4. **SakusenWindow** (battle-tactics window, 17 functions). `0x2A16E8` maps the cursor row to a
   command id 0x48-0x61 and pushes it; the `0x2A1FE4`/`0x2A3B68` pair are the two "confirm"
   pages (both write member value 3 and push 0x57); `0x2A2098` rebuilds the member order from the
   game work + four pending ids; `0x2A32FC`/`0x2A34D0`/`0x2A3D74` handle the detail pane.
5. **Generic `Ui_Window` base constructors** (`0x2A4774`, `0x2A47AC`) and **per-class
   destructors** (`0x2A45D8`, `0x2B3050`, `0x2B30BC`, `0x2BB660/0x2BB758/0x2BB77C`).
   `0x2A4774` is the common base of every window ctor in the game (poker, equip, skill panel,
   smith, shop...) - the highest-leverage name in the batch.
6. **18 window-action handlers** (`0x2A5DD8`..`0x2A79B0`). One shape: tick the widget at
   `self+0x34D8` with the frame context at `arg2+0x520`, gate on `0x62F680`/`0x62F694`, then call
   virtual slot 0x14 of `self+0x3574` with a **state/action id** (0, 1, 2, 4, 8, 0xB, 0xC, 0x12,
   0x17, 0x18) and slot 0x10 to commit. The action id and the side effects (list confirm, cursor
   hide, field-state write) are in the names; the game's word for each action is not recoverable
   from this code, so they are named by the state they start.
7. **Intrusive-container helpers** (`0x2A8698`..`0x2A8874`, `0x2AB6FC`..`0x2ABB8C`,
   `0x2AC978`..`0x2AEB74`). Two families: a "keyed list" with a select/commit protocol
   (vtable slots 8/0xC/4) and a plain intrusive list with a sentinel at +0xC. The
   `0x2AC978`/`0x2ACAA4`/`0x2ADFA4`/`0x2AE1B4`/`0x2AE944` group is a **name-keyed map with a
   hand-written FNV-1a hash** (`0x811C9DC5` offset basis, `0x01000193` prime), looked up through
   `0x6F2EE4`/`0x6F3088` - a new, reusable engine fact.
8. **Animation action-sequence timing** (`0x2A90B0`, `0x2A9330`): five independent event-cursor
   arrays inside a clip (strides 0x14/8/0x18/0x3C/8) advanced against the sequence clock.
9. **Talk/message-window state machine** (`0x2A9790`, `0x2A9924`, `0x2A9F4C`, `0x2AFD2C`,
   `0x2AFC80`). `0x2A9F4C` is the 4.8 KB machine: state id at +0x3260 (0x9C0/0x9C8/0x9EB/0x9F1),
   0x18-byte line records at +0x400, text id at +0x3292; it calls the already-named
   `Ui_MessageWindow_BuildLines/CanShowMessage/GetTalkId` and `Sound_PlaySeById`. `0x2AFD2C`
   pushes a control byte into the +0x1948 queue and executes it through
   `Ui_MessageWindow_ExecControlCode`.
10. **Camera** (finally): `0x2AEC9C` is the per-frame view+projection builder. It selects one of
    15 camera-work slots at +0xC, copies position/target/up, builds the orthonormal basis with two
    cross products and 1/sqrt normalisation, writes translations `-dot(p,axis)`, builds the
    perspective matrix (1.0/0.5/-1.0 constants, near/far, FOV) and stores both matrices into the
    render context at `+0x7C*slot+0x754` (view) and `+0x784` (projection). `0x2AEB74` is the same
    projection block standalone. These two are the highest-confidence entries (0.75 / 0.70) and
    the reason the "Camera" label is not entirely wrong.
11. **Cutscene/script object method table** (`0x7261B4`): `0x2B558C` and `0x2B5994` set a camera
    position + quaternion->direction, `0x2B5B80` moves a point toward a target, `0x2B5900`/
    `0x2B5D44` select a party-status page, `0x2B5950`/`0x2B5DB0` wait for the camera animation,
    `0x2B5834`/`0x2B6754` play `Nut`/walk motions. This is the closest thing in the batch to the
    script-side "IECamera"-style API.
12. **Field scene objects / sprite actors / NPC actions** (`0x2B28A4`..`0x2B6FC8`): constructors,
    destructors, sprite creation (`0x2B4938`/`0x2B6BCC`, `sprite` literal, 0x178-byte model,
    `Gfx_SpriteActor_CreateFromTable`), a drag controller state machine (`0x2B432C`/`0x2B4750`/
    `0x2B4854`), gadget trigger helpers and a collision-proxy ray sampler
    (`0x2B64C4`, 10 random rays + 0x574548 transform + nearest-hit fallback).
13. **Three false entry points** worth recording for the merge step:
    - `0x29D5BC` is 4 bytes into the real deleting destructor at `0x29D5B8` (vtable 0x75E274
      stores 0x29D5B8; the batch address has no reference anywhere in the image).
    - `0x2A2C0C` is not a function at all: it is the second `bl 0x1902A4` inside `0x2A29A8`
      (proven from `asm/text/text_00280048.s`).
    - `0x2B1A84` is 4 bytes into `0x2B1A80` (vtable 0x75EB10 stores 0x2B1A80).
    Seven of the action handlers are also 4 bytes after the pointer stored in the 0x72BE5C table
    (`0x2A5DD8`, `0x2A6BA0`, `0x2A6F64`, `0x2A701C`, `0x2A71DC`, `0x2A73C8` is exact, `0x2A77AC`);
    each such entry says so explicitly.

## Honest gaps / not verified

- **Not verified by running anything.** No emulator, no ROM boot, no test suite. Names are static
  analysis only.
- The **semantic name of the 18 window actions** is not known. The code proves the action id each
  handler starts (0, 1, 2, 4, 8, 0xB, 0xC, 0x12, 0x17, 0x18) and the immediate side effect, but
  not the game's word for it; hence `maybe_Ui_Window_StartAction12` rather than a menu verb.
- **Class attribution of the destructors** is vtable-based, not constructor-based. Slot 7 of the
  vtable is a reliable class fingerprint in this codebase, but for the D0 destructors that are not
  stored in any vtable (`0x29D5BC`, `0x29DDAC`, `0x2A45D8`, `0x2AC854`, `0x2B1A84`, `0x2BB758`,
  `0x2BB77C`) the class comes from the vtable the code stores or from the sibling function's class.
  These are deliberately at 0.35-0.45.
- `0x2A9F4C` is 4.8 KB with Ghidra artifacts (`unaff_r*`, truncated jump tables). The state ids and
  the line/text fields are proven; the *purpose* of each state is inferred (0x9C0 = collect lines,
  0x9C8/0x9EB/0x9F1 = paging/party-list paths). Named `Ui_TalkWindow_RunMessageState` at 0.60.
- The `0x2B0Bxx`/`0x2B13E0`/`0x2B18xx` group is attributed to **field/battle actor motion** because
  the vtable slot 0x84 is called with the strings `Nut`, `Walk` and (from the caller)
  `Bt_Dead`. Whether the owning object is the field actor or the battle actor is not proven; the
  `Field_` prefix is the safer of the two allowed subsystems.
- `maybe_Game_IsNotBattleState` (0x2B3F78) and `maybe_Game_SetTwoFlags` (0x2B3B80) are content
  guesses: the callees (0x64DB08, 0x70BBE4) are not named in this workspace yet.
- `maybe_Ui_PaneGroup_*` (0x2B2148/0x2B238C/0x2B28A4) rest on the pane-name lookups
  (`null_q`, `emotion_chara_q`) and on the four 7-entry method tables at 0x758DD0/0x759DE4/
  0x75ED2C/0x761558; the "PaneGroup" class name is my label, not the game's.
- `0x2AC978`-family is labelled **Container_NamedMap** by behaviour (FNV-1a key + sorted tree).
  The maps are probably resource caches but the stored object type was not resolved.
- No Squirrel script was needed: none of these addresses is a registered native (no address in the
  batch appears in `decomp/native_names.json`), so the scripts only expose the higher-level
  natives, not this layer.

## Suggested follow-ups

1. **Name the 15 camera-work slots and `0x2AEC9C`'s context**: `0x6F250C` (render context getter),
   `0x6F1EEC`/`0x6F20C0`/`0x6F229C`/`0x6F2224`/`0x6F1DF8` are used by every subsystem and are
   still only described by shape. Naming them properly would unlock the 0x2A9xxx/0x2AExxx band.
2. **`0x2D09E4`/`0x2D0B08`/`0x2D0A18`/`0x2D0C98`/`0x2D0CCC`/`0x2D0A4C`** (the 2D draw-record
   setters) are unnamed and are the key to the whole sprite path; `0x2D1258`/`0x2D19C8` likewise.
3. **`0x62F680`, `0x62F694`, `0x6D7F34`, `0x6D7FE8`, `0x6D8110`, `0x1DAB30`, `0x2BBAD0`** are the
   window-command/anim primitives used by dozens of functions in this batch and remain unnamed
   (partially named in earlier lanes: `Ui_SakusenWindow_PushPane` for 0x6D7FE8). Naming them would
   remove most of the `maybe_` prefix in the Sakusen and action-handler groups.
4. **`0x3BDxxx` family** (`0x3BD200`, `0x3BD228`, `0x3BD908`, `0x3BD9C4`, `0x3BDDD4`, `0x3BDE6C`)
   is called by the action handlers and was named `FieldMapState_*`/`ActorActionSeq_*` by earlier
   lanes; re-check that attribution, because the callers here are window actions, not field NPCs.
5. Re-label the batch generator: N_037/N_038/N_039/N_041/N_043/N_049/N_051 all report the same
   "Camera" mislabel. The BFS label propagation in `tools/make_naming_batches.py` is producing
   misleading headers; at minimum the header should list the dominant real subsystem after the
   batch is named.
6. Scratch tooling worth promoting into `tools/`: the vtable scanner + "which table references
   this address" lookup (`vt.py`/`vtmap.py`) and the literal-pool resolver (`an.py`). The
   false-entry detector (search for address-4 in tables) caught three of them here.
