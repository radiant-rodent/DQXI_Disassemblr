## What is actually in this batch (the label is wrong)

The batch is headed **"Camera"**, but the batch generator only propagates a subsystem label from
already-named neighbours through the call graph, and this range contains no camera code. In link
order the slice is:

Two structural findings worth keeping:

* Many entries have **no direct caller** because they are vtable/table slots. I resolved them with
  `PTR` scans over `.rodata`/`.data` (e.g. `0x2BF14C` in vtable `0x75FC60`, `0x2BF760`/`0x2BF9F4`/
  `0x2BF884`/`0x2BFCD4` in `0x75FCC8`, `0x2BBA60` in slot 0 of `0x75F928`, `0x2BDB4C` in
  `0x75FB14`). The surrounding slots (`Field_SceneNode_UpdateMapRecord`, `Ui_Object_DtorBase`, …)
  are what established the class family.
* `0x2C1F04`, `0x2C1F80`, `0x2C1F98`, `0x2C2094`, `0x2C20AC`, `0x2C211C`, `0x2C2134` are **not
  functions**. They are false-positive Thumb prologues (`push {…,lr}` byte patterns) inside the ARM
  date-label code. I verified this in the disassembly (`0x2C1F04` is the middle of a `bl` in the
  function that starts at `0x2C1EEC`). They are named `maybe_FalseEntry_*` with confidence
  0.15-0.2 and an explanation, so the merge step can either drop them or fix the seed scanner.

## Verification

Rule 5's full test run is explicitly waived for this lane, so nothing under `tests/` was executed.
What I did verify mechanically on the output:

* JSON parses; 150 entries; batch-order; 150 unique addresses; no missing and no extra address.
* Every entry has exactly the seven required keys; `summary` non-trivial; `evidence` non-empty.
* `confidence < 0.5` ⇔ name starts with `maybe_` (0 violations); no `maybe_` at ≥ 0.5.
* Parameter count matches the signature's argument list for all 150 entries.
* Mean confidence 0.40; 15 names at ≥ 0.5. That is deliberately conservative: the class *identity*
  for most of these is inferred from vtables and neighbouring names, not proven.
* Checks against other batches: the only address overlap with the other 43 outputs is none; the
  names I reuse as anchors (`Ui_MainMenu_LoadTextResources`, `Ui_CasinoJackpotWindow_Init`,
  `maybe_Casino_AddJackpotPayoutEx`, `Field_SceneNode_UpdateMapRecord`, `Ui_Object_DtorBase`) come
  from those files and are used with their original spellings where the prefix is shared.

## Open problems / not verified

1. **Jackpot attribution.** `0x2C6604` is certain to load `"jackpot"`/`"jackpot_jp"` models, and
   `0x2C6FE4` certainly calls the jackpot payout helper, so the `casino`/`jackpot` prefix is
   evidence-based. But the whole `0x2C6xxx-0x2C8xxx` state-machine block (`f_44` screen object,
   `f_50/f_54` next-callback pair, `f_D4/f_D8` row slots) could be a *shared* UI screen framework
   that the jackpot screen only fills in; I kept `maybe_Ui_JackpotScreen_*` (≤0.48) instead of
   claiming a class name.
2. **Unknown class names.** The vtable owners are only known by address (0x75F928, 0x75FAA0 block,
   0x75FC60/94/C8, 0x75FE04/6C, 0x771428). Their `this` layouts are described in the summaries via
   field offsets, but the game's own class names (from RTTI or the SDK headers) are not recovered.
3. **Decompiler damage.** `0x2BF9F4`, `0x2C49AC`, `0x2C9CD4` (0x1480 bytes, only the entry block
   recovered) and `0x2D9E00` contain `halt_baddata`/lost jump tables. The names there describe the
   part that is readable; the rest is unverified. `0x2C9CD4` is additionally suspicious: its
   callees are Squirrel-VM helpers, so it is probably in the script subsystem rather than UI.
4. **Seven false entries** (listed above) are documented, not fixed; the seed scanner
   (`tools/decompile_native.find_function_prologues`) should reject Thumb prologues that do not
   start a new function (e.g. require the previous instruction not to fall through).
5. **Camera label** in `orchestration/naming/batches/N_049.txt` should be regenerated; whoever
   merges names should not use that header as a subsystem hint.
