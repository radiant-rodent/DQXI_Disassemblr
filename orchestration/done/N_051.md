# N_051 — naming batch `0x002F3140-0x0030C4A4` (150 functions)

**Status: completed.** Resumed lane: nothing had been produced before (no `out/N_051.json`, no done
report, no `AGENT_LOG.md` entry), so all 150 functions were analysed from scratch.

## What was done

`orchestration/naming/out/N_051.json` now holds one object per batch address (150/150, in batch
order): `address, name, signature, params, summary, confidence, evidence`.

Method (bottom-up, leaves first):

1. Rebuilt an address→name map from `decomp/ghidra/functions_index.json`, `symbols.json`,
   `symbols_recovered.json` and every other `orchestration/naming/out/N_*.json`, then re-resolved
   every `func_XXXXXXXX` / `FUN_XXXXXXXX` / `g_XXXXXXXX` reference in the readable C so callees show
   their current names.
2. Built a caller census per batch address over all 18,748 readable files.
3. **Decoded the `.text` literal pools directly from `original/exefs/code.decompressed.bin`**
   (base `0x00100000`). The readable C drops strings, so this was the decisive step: almost every
   function in this slice is identified by an inline animation/effect/resource name or a float
   constant. Examples that were read out of the binary and are quoted in the evidence fields:
   `"Open"` / `"Off"` (0x002F3244/0x002F3248), `">OpenAnim"` (0x002F457F), `"CheckAny"` (0x00300A38),
   `"OpenDoor"` (0x00302178), `"Horse_Jump"` (0x00302F5C), `"Horse_Land"` (0x00302FF0),
   `"Horse_Run"` (`g_00302E7C`), `"Walk"` (`g_00300D20`), `"React"` (0x002F8964),
   `"outBalloon"` (0x002F8DCC), `"defaultTalk"` (`g_002F8DD8`), `win_hope_select`,
   `npc_jockey_visual_param.bxon`, and the 3-character animation-code table at `0x007A3EE8`
   (`DGx`, `8Gx`, `LGx`, `XGx`).
4. Read the shared helpers the slice leans on, so the names are grounded in real semantics:
   `0x005E754C` (base-node broadcast over the +0x54/+0x58 child list), `0x005E78E4`/`0x005E7A34`
   (base pause/resume), `0x0035FC84`/`0x0035FE7C` (effect-handle manager create/release, mask
   `0x3FFFFF`), `0x001DAD58` (UI widget input dispatcher), `0x00109DC8` (operator new with heap
   alignment), `0x0071342C` etc.

## The batch label is wrong — this is not camera code

Same link-order noise as the neighbouring N_049. The slice is four unrelated modules:

| range | what it is |
|---|---|
| `0x002F3140-0x002F4F88` | field map-marker object: vtable node + effect handle + 2D `sprite` child, animation names `Open`/`Off`/`OpenAnim` |
| `0x002F5048-0x002F66E8` | UI: the `win_hope_select` BFLYT window and a jockey panel that reads `npc_jockey_visual_param.bxon` |
| `0x002F6B14-0x002F7B08`, `0x002FC360-0x00309390` | UI pager/tab widgets + the big-window input handlers (18 near-identical `UpdateInput → set state N`) |
| `0x002FF68C-0x003005A8` | a statically linked C library: `strtoul` + the engine's own printf/vsnprintf |
| `0x00300958-0x00303DEC` | the field action state machine, incl. the horse-riding module (`Horse_Run`/`Horse_Jump`/`Horse_Land`) |
| `0x003047C0-0x0030C4A4` | menu item-box helpers, more window input handlers, container key search, handle validity/task step |

Because the label was wrong, subsystem prefixes were chosen per cluster (`Field_`, `Ui_`, `Menu_`,
`Container_`, `std_`) rather than from the batch header.

## Naming conventions used

* `Subsystem_VerbNoun`, PascalCase; `std_` for the C-runtime routines.
* Everything below 0.5 confidence is prefixed `maybe_` (109 of 150). 41 entries are >= 0.50, mean
  0.41 — deliberately conservative.
* The 18 window input handlers are named `Ui_Window_InputToState<N>` (plus `...IfFast`,
  `...Confirm`, `...Cancel`) because they are **mechanically identical except for the state id**;
  inventing menu verbs for them would have been precise-but-wrong.
* Duplicated secondary copies (two `strtoul`, two `vsnprintf` in the ROM) got `_B` suffixes, which
  matches the `_B`/`_C` convention already used by other batches; this also removes the only name
  collisions with `N_036`/`N_037`.

## What is NOT verified / open problems

* **The identity of the `0x2F3xxx` class is inferred, not proven.** It has an effect handle, a 2D
  `sprite` child, an id looked up in the world object table (arena `+0x24A98`) and the animation pair
  `Open`/`Off`, so it is a field marker/door/chest-like prop. `Field_Marker_*` is a deliberately
  vague label; a later pass with the class vtable owners recovered should refine it.
* **The 12 `Ui_Window_Input*` handlers** (`0x2FD8A8`–`0x2FED34`) and the 6 remaining ones
  (`0x304D70`–`0x309390`) are named by mechanism. Their real menu meaning needs the caller table
  (the function-pointer array that registers them) which was not located.
* **`0x30BF0C` is decompiler-damaged** — control flow starts at a label with `unaff_*` registers and
  only 0x84 of the declared bytes carry code. Named `maybe_Container_LinkByName` at 0.25.
* `0x2FA5BC` (2D glyph/icon draw) and `0x2FC360` (UTF-16 fit-to-width) are the least certain of the
  >=0.5 entries; the 2D submit call `0x0017CB7C` was not itself decompiled-inspected in depth.
* Effect ids `0x496` (marker) and `0x104` (walk/landing sound) were not resolved to names; no
  effect-name table for them was found.
* Several tiny accessors (`0x2F6B14`, `0x2F6C90`, `0x2F72D0`, `0x2FB460`, `0x300A70`, `0x301DD0`,
  `0x3021B0`) are C++ component-cast thunks returning `base - constant`; they are documented as
  finders but their owner class is unknown (0.25–0.30).
