## What the batch actually is

The header says **Camera**, but the slice contains no camera code. It is three UI/menu modules plus
two engine helpers, in link order:

1. `0x30C550–0x30CD90` — the **3D menu-icon model records**. `Menu_IconModel_LoadBch` formats
   `%s.bch` from the record's name buffer and attaches the resolved model; three sibling setters load
   the packs `3d/cs/combination/%s.pack`, `3d/cs/item/%s.pack`, `3d/cs/skill/%s.pack`; one release
   and one deleting destructor. Callers in the already-named N_014 output
   (`Menu_UpdateItemIcon`, `Menu_UpdateSkillIcon`, `Menu_ResetSlotRecord(s)`) pin the module.
2. `0x30D004–0x30E108` — the casino **roulette and coin-get/jackpot windows**: the roulette pane
   builder (eight numbered panes + `slime0_0/1` + `txt_in/out` + `roulette_lw_txt_00`), the coin-get
   window (creates the poker/win sub-window at `0x00406460` and binds `select`, `cursor`,
   `cursor_front`, `display`, `menu_txt`, `menu_casino_jackpot`), the win-rate tip animation
   (`@roulette_tip_win_rate_anim.bflyt`), the 113-pane reel builder/teardown, the red/green/blue
   frame selector, and the window ctor/dtor.
3. `0x30E948–0x30F100` — six recovered thunks whose whole body is
   `Ui_Object_BroadcastToChildren(self+0xD1C, flag)` (five with 1, one with 0). They are distinct
   vtable slots of sibling screen classes; they are lettered A..E rather than guessed into
   show/hide verbs.
4. `0x3103A8–0x314620` — the message **text builder / renderer**: an icon-request state machine that
   writes GameWork through `0x00613354` (base `+0x24A98`), a multi-part text build (3 parts, SE
   `0xE70`, 50-frame timeout), the proportional-font run/kern emitter (`0x0044641C`, 0x18 stride),
   style-resource binding (`0x003810D4`, special id `0x697`), the 4-part layout driver, the
   0x3B8-byte glyph object creation, and the message-window 3D transform/move finishers.
5. `0x315BB8–0x3179D0` — a large-window resource teardown plus **18 near-identical window state
   handlers**. Every one ticks the layout tween at `+0x4A4`, gates on `0x0062F680/0x0062F694`, asks
   the controller at `self+0x11C` (vtable `+0x14`) for a state id and commits with `+0x10`. Only the
   state id differs (0x17, 3, 2, 7, 0xE, 0xF, 5, 0x10, 0xD, 0xB, 0xC, 0x13, 0x16, 8), so they are
   named `maybe_Ui_WindowState_Goto<ID>` with A..E suffixes for the five copies.
6. `0x3190F4–0x31C3F4` — small UI pane pairs and ctor/dtor pairs (`win_sakusen_tutorial2/3`,
   `win_past_scenario`), a record-pointer resolver, actor 2D/3D transform setters, the 0xA8C-byte
   multi-pool actor hit test, and the sprite-actor appearance/motion layer (model size, appearance
   variants, motion modes 0..3 with quaternion, finish). These sit exactly between N_014's
   `Gfx_SpriteActor_*` names and use the same family vocabulary.
7. `0x31F3BC–0x322DE0` — the **battle action-sequence object** (> 0xDE50 bytes). Per-frame state
   machine with a `+0xD2` done flag and `+0x3786/+0x4E0` state words; participant list at `+0x3780`
   (0x1A*4 entries), per-unit action records with 0x68 stride, target-list builders
   `0x00398B28/0x003989FC`, battle context `0x001FD96C` with
   `0x003FC60C/0x003FDCC0/0x003FC220/0x003FC9F0`. The command interpreter at `0x3219E4` switches on
   the ASCII command characters `'7','8','9',':',';','=','>','C','D'` — the strongest identification
   in the batch.
8. `0x323AC8–0x326564` — battle popup, message/choice window and battle-window interfaces: the
   balloon pool (32 slots at `+0x11C`, called from `Battle_Start`/`Battle_Initialize`), the choice-row
   layouts (`txt_l3`, `null_txt_l1..l5`, cursor entries with style ids 2/0xB/0x13/0x18/3/0x10), the
   list scroll helpers (item height `+0x66`, visible rows `+0x68`, split via `0x0011CD80`),
   `Ui_SetNextBattleIcon` (`icon_next_battle_2d/3d`), the shared window base ctor/dtor, a tween step,
   and the 0x240-byte layout-table copy.
9. `0x326838–0x328E58` — the **casino slot machine**: win-line detection over the 5x3 reel table
   (runs >= 3, symbol 6 is wild), the pattern payout calculator (bet level, multipliers, 99-credit
   cap, jackpot helpers `0x00601320/0x00601B44`), the animation callbacks, the "play SE only when it
   changes" cache (ids 0xE00..0xE62 are skipped), and the 18-node payout/win sequence builder.
10. `0x329A8C–0x32CB3C` — effects and the dive mini-game: camera-relative effect placement, effect
    resource replacement, two tween helpers, the `diveDrop` impact effect (item lookup `0x0061BD4C`,
    effect `0x003D9A00`, SE `0x1F`), the screen-shake spawner (`0x0035FF3C`, camera basis at
    `0x0032B3C0..D4`), the two-column list window dtor pair and the dive sub-object ctor.
    `0x32B110` is a **merged alternate entry** inside Ghidra's `FUN_0032ABE0` file; it is recorded as
    such so M1 does not create a bogus body.

## Method

- Name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all 46
  sibling `out/N_*.json`; the already-named N_014/N_015 neighbours were the main class anchors
  (`Ui_SlotWindow_*`, `Ui_MessageWindow_*`, `Gfx_SpriteActor_*`, `Ui_DiveStartWindow_InitPanes`).
- Read all 150 readable C files (filtered to statements, 6.1k lines) and all six recovered entries.
- Caller index over all 18,748 readable files (18,159 in `functions/`, 589 recovered).
- Resolved every `s_..._XXXXXXXX` literal straight out of
  `original/exefs/code.decompressed.bin` (base 0x100000). Nearly all hard facts in this batch are
  such literals: `%s.bch`, the `3d/cs/...` pack paths, roulette/coinget/menu pane names,
  `frame_red/green/blue`, `win_sakusen_tutorial2/3`, `win_past_scenario`, `icon_next_battle_2d/3d`,
  `txt_l3`, `null_txt_l1..l5`, `diveDrop`.

## Results

- 150/150 batch addresses covered, exactly once, in batch order.
- Confidence: mean 0.414, min 0.20, max 0.65. 37 entries at >= 0.50, 113 prefixed `maybe_`
  (the confidence < 0.5 rule is applied mechanically).
- Validation run (`%TEMP%/opencode/n052_merge.py`, pure JSON assertions): parses, all seven keys,
  signatures contain their own name, params documented, `maybe_` set matches confidence < 0.5,
  150 unique names, no collision with the three symbol tables or the 46 other batch outputs.
- **No test suite / build run.** Naming lanes are explicitly exempt from rule 5 in the task, and
  nothing binary-producing was changed.

## Honest gaps (NOT verified)

- The 18 `maybe_Ui_WindowState_Goto*` handlers share a window base but I could not prove which
  concrete window class owns each vtable slot. Only the state ids are facts.
- The battle sequence's *game meaning* (which step is attack/skill/item) is not proven. The command
  characters are proven; the mapping from those characters to menu actions is not. The family is
  therefore left at 0.33–0.45.
- `0x315EC0` is only `return strstr(...) != 0` with the strstr operands lost by the decompiler;
  confidence 0.20.
- `0x3103A8/0x310680` (face/icon request) rest on GameWork writes at `+0x24A98` and the
  `0x0063DF14/0x0063FDEC` record lookups; which exact record field becomes the icon is unverified.
- `0x32ABE0` vs `0x32B110` are two entry points into one Ghidra function; which one the game calls
  is unproven.
- No Squirrel script could confirm any of these 150 as a registered native (`decomp/native_names.json`
  has no match), so no game-logic-side confirmation was available.
