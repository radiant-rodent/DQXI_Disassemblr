## Method

1. Rebuilt an address→name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and every sibling `orchestration/naming/out/N_*.json`.
2. Read all 150 readable C bodies (every path in the batch file exists; none needed a fallback).
3. Built a caller/callee index over all 18,367 readable functions.
4. For every function, scanned each 4-byte literal in its address range in
   `original/exefs/code.decompressed.bin` (base `0x00100000`) and decoded data pointers to strings.
   This produced the decisive evidence: `Mimic`, `LinkEnd`, `Break`, `N_ALL`, `sprite`,
   `win_loading`, `win_guide`, `stamp_msg_bxon` / `stamp_page_bxon` / `stamp_reward_bxon`,
   `NPC_Collision`, plus the SE/effect id tables (`0x007255D8`, `0x007255E6`, …).
5. Worked bottom-up within each cluster: leaf helpers first (e.g. `Effect_ReleaseHandle`,
   `Pack_HandleTable_Add`, `Sound_Emitter_*`), then their callers.
6. Cross-checked neighbours so the new names do not contradict already-named functions:
   N_015/N_026 own `0x333xxx` as `Ui_EquipWindow_*`; N_015 owns `0x368AE0
   maybe_Ui_GuideWindow_Ctor`; N_015 owns the guide-window page helpers. This forced two
   renames from my first draft (see below).
7. Wrote the JSON in 25-entry chunks (the final file is written whole after each chunk, matching
   the "save every ~25" instruction).

## Naming decisions worth recording

- The range is **not** camera code; I named by observed behaviour/callers, not by the batch label.
- `0x00335348` was first `Ui_Window_PopPane`, which collided with N_021's name for `0x006D7454`;
  renamed to `Ui_EquipWindow_PopCurrentPane` after confirming the `+0x128` pane stack.
- `0x0032DD74` was first `maybe_Field_Actor_UpdateEffectState`, colliding with N_049's name for
  `0x2C14B8`; renamed `maybe_Field_Actor_TickEffectState`.
- `0x00369060` was first `maybe_Ui_GuideWindow_Ctor`, colliding with N_015's `0x368AE0`; the body
  calls `std_destroy_range` on a `0x260`-element array, the UI-object base destructor and
  `operator delete`, so it is a destructor: `maybe_Ui_GuideWindowChild_Dtor`.
- `0x00336BE4` and `0x00337030` are the same routine in ARM and Thumb form (Ghidra marks the second
  "thumb"); the name only differs by the `Thumb` suffix. This is a genuine duplicate in the image.
- `Effect_ReleaseHandle` (`0x0035FC84`) is the highest-confidence name (0.75): ~80 callers, a packed
  20-bit handle, and it pairs with the already-named `maybe_Effect_FindOrCreateInstance`.

## Open problems / not verified

- **Struct types are invented presentation types.** `FieldActor*`, `UiWindow*`, `SoundEmitter*` etc.
  are readable placeholders; the real struct layouts are only partially recovered. Signatures are
  argument-count/role sketches, not verified prototypes.
- `0x00336BE4`, `0x00337030`, `0x00337CB4`, `0x0033AD44`, `0x0033EB5C`, `0x003400B4` are huge
  (0x44C–0x230C bytes) and Ghidra reports bad instruction data / merged neighbours; their tails are
  unreliable. They are named only at the "scene table spawn/update pass" level (0.32–0.40). A later
  pass with the ARM disassembly should split them.
- `0x00369060`-adjacent guide-window class split is inferred from position and callee set; the exact
  class boundary between `maybe_Ui_GuideWindow_Ctor` (N_015, `0x368AE0`) and
  `maybe_Ui_GuideWindowChild_Dtor` (this batch, `0x369060`) is not proven.
- The horse-action quartet `0x36C258-0x36C4FC` has no direct callers; the horse attribution comes
  from the next functions (`0x36C7A4/0x36C884`) calling the horse SE updates and from the
  `f_2d4`/`f_276` mount flags. Could be a more general "rideable actor action".
- `0x00337030` is flagged Thumb while every neighbouring function is ARM; I trusted Ghidra's mode
  flag but did not disassemble the bytes to confirm.
- `0x0032DBEC`, `0x0032DE54`, `0x0033DEC4`, `0x0034A03C` contain `halt_baddata()` tails; their
  summaries describe only the recoverable prefix.
