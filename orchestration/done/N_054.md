## What is actually in the range

The batch header says "Camera", but there is no camera code in `0x0036C54C-0x0038AA18`
(this is the same propagated-label noise as N_045..N_052). In link order it is:

1. `0x36C54C-0x36D364` — the **field horse-riding action** family and the shared actor-action
   base. `0x36C7A4`/`0x36C828` set state 1/2 and play the literal animations `Horse_Jump` /
   `Horse_Land`; `0x36C884` is the per-frame gravity / ground-normal / land transition update;
   `0x36D364` is the base ctor (vtable `0x76572c`, actor pointer at `+0x28`) used by three
   derived ctors.
2. `0x36D5AC-0x3708D0` — a large composite UI window ctor (five repeated child widget blocks),
   its child update/result handlers, and UI object ctor/dtor helpers.
3. `0x370F80-0x37446C` — field-actor list helpers (type-filtered begin/end walks), cell-transition
   / overlay-tag code, and the push / turn / jump action implementations (`Grab_Push`,
   `zDGrab_Push`, `TurnL`, wall-normal test, sweep test, effect and SE handles).
4. `0x37706C-0x382A44` — actor equipment/attachment model code (`Model_Actor_UpdateAttachment`,
   attach-slot show/hide, `Menu_Nut` + `wbhm_grip_on` grip animation, scale updates) mixed with
   message-slot open/close helpers.
5. `0x38363C-0x386DE8` — UI row/talk-window code (`icon_cursor`, `win_talk_lw`), the file-system
   named-object loaders, party-id list building, and two decompiler-damaged functions.
6. `0x3886C0-0x38AA18` — battle party UI state machines (row refresh, slot init, the big phase
   switch on `self+g_00389470`, command states) and battle-actor movement interpolators.

## Method (reproducible)

Scratch files are in `%TEMP%/opencode/` (`n054_digest.txt`, `n054_c2.txt`, `n054_names.json`,
`n054_callers.json`, `insp.py`, `vt.py`, `w1.py`, `w2.py`); nothing was added to the repo.

1. **Name map** — merged `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and
   all 50 readable sibling `out/N_*.json` (7,515 names) and inlined those names into the readable C.
2. **Callers** — scanned all 18,748 files under `decomp/readable` for `FUN_/func_<addr>` tokens.
   56 of the 150 have a direct caller; the others are vtable slots, which is itself evidence.
3. **Vtable dump (the key step)** — resolved `g_XXXXXXX` literal-pool words directly in
   `original/exefs/code.decompressed.bin` (base `0x00100000`) and read the table they point at.
   This proved the class families and the virtual slots: e.g. `g_0036c57c` → vtable `0x765674`,
   whose `+0x84` slot is the play-animation virtual behind `s_Horse_Jump_0036c814`; `0x36D364`
   installs `0x76572c`; the UI ctors install `0x7657e0`/`0x7658f8`/`0x76592c`/`0x7659a8`.
4. **Strings/constants** — every `s_*` literal was read from the bodies: `Horse_Jump`, `Horse_Land`,
   `Grab_Push`, `zDGrab_Push`, `TurnL`, `Menu_Nut`, `wbhm_grip_on`, `icon_cursor`, `win_talk_lw`.
5. **Scripts** — no Squirrel script in `game_assets/scripts/` binds any of these addresses as a
   native (all 150 are internal vtable entries), so the scripts gave no confirmation.

## Confidence and honesty

| bucket | count |
|---|---:|
| >= 0.70 | 2 (both horse animations at 0.75) |
| 0.60 – 0.69 | 6 |
| 0.50 – 0.59 | 25 |
| 0.40 – 0.49 | 81 |
| < 0.40 | 36 |
| **total** | **150** |

Mean confidence 0.428; 27 names unprefixed, 123 prefixed `maybe_`. The `maybe_` prefix almost
always marks uncertainty about the *owning class*, not the *role*: the ~20 destructors are
certainly destructors (vtable install + `Ui_Object_DtorBase` + `func_0010F6CC`), but several
cannot be tied to a provable screen/class name from their own body.

What is **NOT verified**:

- The game's own names for the UI screens are unknown. `maybe_Ui_CompositeWindow_CtorLarge`
  (0x36D5AC) is named by shape (five repeated child blocks, big offset spread), not by a recovered
  screen identity.
- `0x384B6C` (0.25) and `0x384C44` (0.35) are decompiler-damaged (`halt_baddata`, split control
  flow) and are described only at the visible-call level.
- The `Battle_*` attribution of `0x3886C0-0x38AA18` rests on the `func_00630DC8` party loop,
  `func_003FBE4C` message pushes and `Ui_GetCore` state checks; no recovered screen name proves it.
- `0x38A4F8`/`0x38A7CC`/`0x38AA18` are placed under `Battle_` because of their vtable band; the
  movement code itself is generic (could be field or battle).
- The exact meaning of several numeric action/state ids (0x30, 0x2e, 0x47, 0x13, 0x26 …) is not
  decoded; the names say "state machine" and the evidence records the ids as facts.
- Nothing here was merged into `symbols.json` or the readable C; that is `M1_merge_names`. No
  emulator/3DS run and no build was performed (naming lanes are exempt from rule 5).
