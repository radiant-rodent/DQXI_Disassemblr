# N_056 — UI / field-object / actor-action naming batch (`0x003A2658`–`0x003C1B00`)

## State on arrival

The task was marked RESUMED, but **nothing of the previous attempt existed**: no
`orchestration/naming/out/N_056.json`, no `orchestration/done/N_056.md`, and no N_056
entry in `AGENT_LOG.md`. All 150 addresses were therefore named from scratch.

The batch header calls the range "Camera", but only two of the 150 functions

## Honest gaps / what is NOT verified

- **107 of 150 names are mechanism-level.** The range is a dense run of vtable slots,
  delete-only destructors and paired window classes; 36 functions have no caller, no
  vtable reference and no string of their own.
- **The five field-object class names are placeholders**, not recovered class names:
  `Field_SceneObj` (0x7678E0), `Actor2D` (0x767A94, following the name an earlier lane
  used for `maybe_Actor2D_NotifySpanSlot`), `Field_ModelObj` (0x767C48),
  `Field_TwoPartObj` (0x767D40) and `Field_ApproachObj` (0x767EF4). They were chosen from
  the members each class touches (one model vs. two sprite children vs. side anchors),
  not from any symbol.
- **The "door/side" reading of the 0x0D handlers** (`0x003A42B8`, `0x003A4674`) is a
  hypothesis: the code definitely compares a packed 11-bit pair against two anchor words
  and stores 0/1/0xFF, then sends command 0x0D, but whether the object is a door, a
  stairs trigger or a warp gate is not proven.
- **`0x003A2658`, `0x003A3840`, `0x003A47F8`, `0x003A6B38`, `0x003BC820`, `0x003BC954`
  are delete-only destructors.** Their owner is inferred from the member offset they tear
  down (+0x298 / +0x278 / +0x2C8 / +0x24C), because no vtable or call site references
  them.
- **Decompiler-damaged functions**: `0x003A6B38` and `0x003BA310` contain `halt_baddata`
  / `unaff_*` register accesses. They are named from their strings and vtable slot only.
  `0x003AE480` (0x5E8 bytes of float math) is only summarised, not verified term by term.
- **`0x003BF564` / `0x003C022C`** are large state machines with no reference anywhere in
  the image (the entry point is reached from a computed jump). The name
  `Field_ActorActionSeq_*` describes the mechanism (12 × 100-byte action entries, actor
  index, event-command submission, SE/anim per actor), not a proven system name. The
  same caveat applies to the helper chain `0x003C0BCC`–`0x003C1B00`.
- **"Camera" names** (`0x003B1698`, `0x003B17C0`) rest on the fact that
  `Camera_SetupProjection` / `Camera_ReleaseProjection` are their only callers; the
  functions themselves are priority-ordered layer hit-tests, which is a plausible but
  unproven role for the camera module.
- **Signatures are normalised.** Ghidra drops register-only arguments in several
  functions (the `NotifyCommand*` handlers take an unused 2nd/3rd argument from the
  vtable call convention). Where that happened it is stated in the `evidence` field.
- **Names are not merged** into `symbols.json` or the readable C (that is
  `M1_merge_names`). No emulator or hardware check was performed.
