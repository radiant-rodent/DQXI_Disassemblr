## Summary

Named and documented all **150** functions in `orchestration/naming/batches/N_057.txt`
(`0x003C1C9C`–`0x003D7B6C`) in `orchestration/naming/out/N_057.json`.

This was a resumed task, but **no prior output existed**: `orchestration/naming/out/N_057.json`
was absent, there was no `orchestration/done/N_057.md`, no `orchestration/logs/N_057.log`, and
no `AGENT_LOG.md` entry mentioning N_057. All 150 entries were produced from scratch.

windows, the equipment list row, the message window binder, field-gimmick component initialisers
and a group of UI window constructors/destructors. There is no camera code.

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `naming/TEMPLATE.md`, the batch file, the `N_004`
   and `N_052` reports (same/adjacent address ranges and same conventions).
2. Built one address→name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and every `orchestration/naming/out/N_*.json`.
3. Built a per-function digest over all 150 readable C files: signature, calls resolved through
   the name map, callers (from a call-graph scan over all 18,159 `decomp/readable/functions`
   files), `s_*` string tokens, `g_*` literals and `f_*` field offsets.
4. **Vtable scan:** scanned every 4-byte word of `original/exefs/code.decompressed.bin`
   (base `0x00100000`) for pointers to the batch addresses, walked backwards to the table base and
   dumped the whole table with every slot resolved through the name map. This was the decisive
   step and identified, among others:
   - `0x00763444` / `0x00769480` / `0x00769C40` / … (15 tables): the battle **member-widget**
     class; slots 9, 11, 12, 14, 15, 16, 19 are batch functions;
   - `0x0075CD88` (18 slots) and `0x0075CDD4` (6 slots): the second member-widget / member-animation
     table family; slots 0,1,2,4,5,9,11,12,13,14,15,16,17 are batch functions;
   - `0x00769098`, `0x00769250`, `0x00769088`, `0x0076939C`: FieldParty UI classes;
   - `0x007697B8`: `Battle_HpGaugeWindow` (slot 8 = `0x003CF6A4`, slot 9 = the already-named
     `Battle_HpGaugeWindow_Update` at `0x003CEEB0`);
   - `0x00769E38`, `0x00769CE0`: battle target-marker manager;
   - `0x0076A02C`, `0x0076A07C`, `0x0076A0CC`: dungeon HUD windows;
   - `0x0076A298`: the equipment-list row (siblings `Ui_EquipRow_Update*` from N_004);
   - `0x0076A458`: the message window (slot 9 = `maybe_Ui_MessageWindow_ResetState`);
   - `0x00769850`: the event-packet class (`ccg392_v0xx`, `cbhm_tcs_mant` literal pool);
   - `0x007698A8`/`0x00769944`/`0x00769AF8`/`0x0076A230`/`0x0076A394`/`0x0076A3F8`: UI window
     classes whose slot 7 is an already-named `..._InitPanes`, which mechanically fixes the
     destructors (slot 0) named here.
5. Resolved every `s_*`/`g_*` literal through the raw image. Hard strings recovered:
   `_hpcolor` (HP gauge colour set), `gau_hp`, `gau_mp`, `zone_in`, `zone_loop`, `zone_loop2`,
   `zone_out`, `txt_name`, `txt_num1..3`, `txt_title3`, `txt_status` (HP gauge panes),
   `txt_meesage1`, `txt_meesage2`, `win_dungeon_hp_left`, `win_dungeon_operation`, and the message
   window layout set `bg_normal`, `title`, `menu_dive_main/title/sex/age/dragonquest/region1..3/
   list3/title2`, `win_load_keyboard`, `win_load_message`, `win_talk`, `win_yesno`
   (note the ROM's own typo `meesage`).
6. Read the bodies of every non-trivial function (large ones truncated with targeted re-reads of
   the switch heads and tails), then worked bottom-up: leaf helpers (`0x003C7EDC`,
   `0x003CB530`, `0x003D10B0`, `0x003D55BC`…) first, then the dispatchers
   (`0x003C583C`, `0x003C7478`, `0x003C52E0`), then the vtable slots.
7. Cross-checked the action-sequence naming against N_052, which named the preceding part of the
   same engine (`maybe_Battle_ActionSequence_*`, command characters `'7','8','9',':',';','=','>',
   'C','D'`) and explicitly listed `0x003C35D0`/`0x003C38EC` as "the battle sequence's participant
   helpers"; this batch uses the same family prefix.

## Key findings

- **The action-sequence object is split across link-order blocks.** The participant list is at
  `+0x3780` (0x1A-word entries), per-unit action records have 0x68 stride, and the state byte is
  `record+0x293` with command characters at `record+i*0x2C+0x59`. `0x003C583C` is the state
  dispatcher (states 1 / 0-6 / 3-4-7 / 5 → `0x003C52E0` / `0x003C819C` / inline / `0x003CA5E0`).
- **The 15 member-widget vtables share four implementations** (`0x003C332C` slot 9,
  `0x003C32A4` slot 11, `0x003C45AC` slot 12, `0x003C43CC` slot 19), which is why those four are
  named as base-class methods rather than per-character variants.
- **The four "balloon" spawners** (`0x003C5B58`, `0x003C5D8C`, `0x003C5FAC`, `0x003C62DC`) are
  byte-for-byte the same code with the record id field shifted by one (`+0x2CC`, `+0x2BC`,
  `+0x2BE`, `+0x2C0`) and different done flags; named A..D instead of inventing four meanings.
- **Seven destructors are mechanically fixed by vtable slot 7**: `Ui_IconRowWindow_Dtor`,
  `Ui_IconRowWindow_DtorB`, `Ui_GoldCounterWindow_Dtor`, `Ui_SinglePaneWindow_Dtor`,
  `Ui_TwelveRowNumberedTextWindow_Dtor`, `Ui_ThreeRowNumberedTextWindow_Dtor`,
  `Ui_EffectIconsWindow_Dtor`. `Battle_HpGaugeWindow_InitPanes` (0.65) is fixed by both slot 8
  and its twelve resolved pane names.
- `0x003C35D0`, `0x003C3560`, `0x003C3594`, `0x003C36AC`, `0x003C36C4`, `0x003C45AC`,
  `0x003C4A20`, `0x003C4ADC`, `0x003C4B9C`, `0x003D7B6C` have **damaged Ghidra bodies**
  (`unaff_r*`, `halt_baddata`, lost argument registers). They are named only at the level their
  surviving calls prove and are held at 0.25–0.35.
- `0x003D6D10` is the shared message-window pane binder; it binds the dive/debug menu, the load
  keyboard/message windows and `win_talk`/`win_yesno` in one function (0.55).

## Open problems / not verified

- **Names are proposals only.** They are not merged into `decomp/native_names.json`,
  `symbols.json` or the readable C; no runtime/emulator check was done.
- **The exact screen identity of several windows is not proven.** `Ui_DungeonMessageWindow` and
  `Ui_DungeonOperationWindow` are named from their pane strings
  (`txt_meesage1/2`, `win_dungeon_operation`) and their vtable position next to the already-named
  `Ui_DungeonHpWindow_Dtor`; the game's own class names are unknown.
- **`0x003CFE5C` (`maybe_Ui_Billboard_UpdateFromActor`)** — its vtable `0x00769820` is otherwise
  unnamed (0x003D033C/0x003D0284/0x003CFFA8) and N_004 called a sibling `maybe_Ui_ListSubObject_*`;
  the sprite/billboard placement is clear, the class is not. Lowest-value name in the batch.
- **The event-packet family** (`maybe_Event_Packet_*`, 5 entries) is named from the packet lookup
  helpers (`func_00194300`/`0x0019434C`/`0x001943B8` fallbacks), the model attachment call and the
  `ccg392_v0xx` animation names. "Event packet" is the best structural match, not a recovered
  name.
- **Damaged bodies** listed above: `0x003C3560`, `0x003C3594`, `0x003C36AC`, `0x003C36C4`,
  `0x003C45AC`, `0x003C4A20`, `0x003C4ADC`, `0x003C4B9C`, `0x003D7814`, `0x003D7B6C`. Their
  names describe the family and the surviving calls only; the original argument lists are lost.
- **`0x003C2F80` / `0x003CB3D0`** message-id choices (0x1F..0x22, 0x23..0x25) are proven as
  numbers, but which game event each id represents was not decoded.
- **No Squirrel script** binds any of these addresses as a native (`decomp/native_names.json`
  contains no address in the range), so the scripts gave no confirmation.
- Two other lanes (`N_056` = the immediately preceding 0x0038AB68–0x003C1B00 block, and `N_058`)
  had no output while this batch ran; their constructors would confirm several class names here.
  N_052's report already flags this gap.
