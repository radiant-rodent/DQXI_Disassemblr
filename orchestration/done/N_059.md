## What is actually in the range

The batch header says "Camera"; that is wrong (same propagated label as N_045..N_060).
`0x003ED950-0x00409FC8` is lazy link-order output of the **UI / battle-action** modules:

1. `0x3ED950-0x3EEA3C` — the **camera-animation window** (`Ui_CameraAnimWindow_*`:
   8 row-delegate binding, layout init loading `s_...loop_cmtsa`, ctor) plus the
   **Smith menu** page push and entry-delegate invoker.
2. `0x3F0CB4-0x3F1D48` — small child-widget ctor/dtor pairs, identified through their
   vtable groups: `TxtLowerWindow`, `SevenSlotWindow`, `TsuyosaWindow` child,
   `FourRowIconWindow`, plus the status window's alternating member-row tick.
3. `0x3F2E44-0x3F3650` — intrusive-list/notify-list helpers and the generic
   `MenuWindow` ctor/update.
4. `0x3F3AB4-0x3F3E74` — `TwoAxisSelectWindow` and `DigitTextWindow` child ctors/dtors.
   `0x3F3E90` is pure vector math (node basis → position + orthonormal basis).
5. `0x3F4564-0x3F8C48` — a large **action/party display UI** family: two near-identical
   state machines (`0x3F463C`, `0x3F5528`, probably 2D/3D variants), their decompiler-split
   continuation blocks (`0x3F6208`, `0x3F643C`), row-transform init, entry setup
   (100-byte entries at `self+0x70C`), member visibility/reset and the main driver
   `0x3F8C48` (0x2014 bytes, 59 callees).
6. `0x3FB7DC-0x4006A0` — virtual methods of the **battle action-animation elements**
   (vtables `0x76C4xx-0x76C5xx`), including the `UseItem` element that plays the
   `"UseItem"` action key; plus the popup entry dispatch primitives.
7. `0x3FBEC8-0x3FFECC` — the **popup / display-entry spawners**. Every one builds a
   `0x20C..0x220`-byte entry (fields `+0x208..+0x221`), optionally fills it from an
   actor/monster record (`+0x768` model id, `+0x1C` variant, `+0x10` flags) and posts
   it through `0x20A9B8` → `0x2DFDE8` (named `Battle_PopupEntry_Create` in N_003).
   `0x3FC60C` is the shared "clear all popups" (id `0xFFFF`), `0x3FDCC0` the
   "play id without new entry". The families differ only in which message-argument
   helper table they install (`Ui_Message_SetNameArg`, `...NameAndNumberArgs`,
   `...NameAndCodeArgs`, `...NameAndCountArg`, `...SpeakerArgs`, log-format helpers)
   and in the animation id they post.
8. `0x4006FC-0x40165C` — **battle effect / actor attachment**: `FocusPoint` effect,
   left/right hand effects (`"L_Hand"`/`"R_Hand"`), aura effect, and the `cbhm_arm_*`
   / `cbhm_mask_*` attachment animations.
9. `0x402180-0x405260` — the **battle party panel** in its several layouts: row text and
   colour refresh, member availability/order, HP-gauge show/hide and selection. These
   functions are entries of the two battle command tables `0x728CCC` and `0x728CE4`.
10. `0x405FFC-0x4062D8` — **casino slot-machine payout gauge**, proven by the shared
   7-segment `0x50`-stride array, the 9 999 999 clamp / divide-by-10 magic and the call
    to `Ui_SlotWindow_ResetPayoutAnim` (0x328E58); `0x40673C` initialises the two
    7×`0x50` template arrays.
11. `0x406CBC-0x4077B4` — message-window factories and the **effect-attachment
    descriptor** spawner family (`0x6A`-byte descriptor, `Effect_FindOrCreateInstance`).
12. `0x407BD0-0x409FC8` — menu windows: `ThreeLineTwoSelectWindow`, `SevenLineSelectWindow`,
    `PlaceNameWindow`, `DungeonSkillWindow` (loads `"win_dungeon_skill"`),

## Method (reproducible)

Scratch files are in `%TEMP%/opencode/`: `n059_prep.py`, `n059_vt.py`, `gen_n059.py`,
`n059_callers.json`, `n059_dossier.txt`, `n059_bodies.txt`, `n059_refs.txt`,
`n059_vtables.txt`, `n059_vptr.txt`, `n059_table.txt`, `n059_summary.txt`.

1. Parsed the batch (150 entries, every listed readable file exists; 3 are in
   `decomp/readable/recovered`).
2. Built a name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 55 existing sibling `out/N_*.json` (8 415 names).
3. Built a reverse-caller index over all 18 748 files in `decomp/readable`
   (`FUN_`/`func_` token scan), so every function has a caller list.
4. Resolved every literal-pool dword from `original/exefs/code.decompressed.bin`
   (base `0x00100000`) into code pointers, rodata tables, floats, ids and strings.
   This is what made the popup spawners readable: their literal tables are the
   `Ui_Message_Set*Arg` helper pairs.
5. Walked the vtable region: for every in-batch dtor, the word at `slot+0x1C` is the
   class's `InitPanes` virtual, so the class name can be recovered from the already
   named `Ui_*Window_InitPanes` function of that group. This named 17 dtor/ctor pairs
   without guessing.
6. Read all 150 bodies; where the body was decompiler-broken (see below) only the call
   sequence, state constants and structure were used.
7. Wrote the JSON in one deterministic generation script (so it can be regenerated and
   audited), with assertions: 150 objects, exact batch address set, no duplicate names,
   no name collisions with any symbol file or sibling batch, and every `<0.5` entry
   `maybe_`-prefixed.

## Honest gaps / what is NOT verified

- **`0x3F463C` vs `0x3F5528` identity.** They are unreferenced, near-identical state
  machines with the same state constants and the same party-table access. The 2D/3D
  split is the best explanation (DQXI 3DS has both modes, and the code checks the
  world mode byte `+0x4244`), but whether the object is the battle party display or
  the camp/field party display is **not proven**. Names use the deliberately vague
  `Battle_ActionUi_*` with 0.35 confidence.
- `0x3F6208`, `0x3F643C` and `0x404824` are Ghidra fragments (unaff_* registers,
  BADSPACEBASE, `halt_baddata`). They are named only as continuation blocks / from the
  surviving arithmetic; do not treat them as independent functions.
- `0x3F3E90` (basis→transform math) has **no callers and no vtable slot**; "camera"
  in its name comes from the shape of the output (position + orthonormal basis), not
  from a proven use.
- The popup-entry prefix follows `Battle_PopupEntry_Create` (N_003), but the callers
  include field/event code (`FieldParty_UpdateStateMachine`,
  `Field_ActorActionSeq_*`), so a more neutral `Ui_*` prefix may age better. The
  entry sizes/fields and dispatch ids are verified; the business meaning of most
  individual animation ids (0x18, 0x23, 0x25/0x26/0x28/0x29, 0x4C, 0x84, 0xD9..0xDB,
  0x8BE, 0xC53, 0xC76, 0xEBD...) is not.
- `0x3FF200` and `0x3FF6FC` are debug/label entries; their ids are read but their
  screens are unknown (0.35-0.40).
- Several class names used for the ctor/dtor pairs (`TxtLowerWindow`,
  `SevenSlotWindow`, `TsuyosaWindow`, `FourRowIconWindow`, `TwoLineTextWindow`,
  `PlaceNameWindow`, ...) come from sibling batches' `maybe_Ui_*Window_InitPanes`
  names. The **pairing** is structurally proven by the vtable; the class names
  themselves inherit the siblings' (sometimes `maybe_`) confidence.
- The real `Ui_TsuyosaWindow_Ctor` already exists at `0x002A0E14` (N_013); the one in
  this batch is the child widget, hence `Ui_TsuyosaWindow_ChildCtor/Dtor`.
- No Squirrel script in `game_assets/scripts/` binds any of these addresses; this is
  internal UI/engine code, not native script API.
