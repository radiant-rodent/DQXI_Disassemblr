Status: **completed**. Output: `orchestration/naming/out/N_060.json` — 150 entries, one per address
in `orchestration/naming/batches/N_060.txt`, no missing or extra addresses, no duplicate names, no

## Method

1. **Index, not grep-per-address.** Wrote a one-shot script that parsed every file in
   `decomp/readable/{functions,recovered}` once, built `address → callees` and `address → callers`
   maps, and resolved every callee through `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and every `orchestration/naming/out/*.json` (55 sibling batches).
   This is what made the range readable: dozens of callees are already named
   (`Gfx_Scene_SetEntryFlag`, `Ui_Object_CtorBase/DtorBase`, `Gfx_SpriteActor_CreateFromTable`, …).
2. **Literal-pool decoding.** `g_00xxxxxx` symbols in the readable C are literal-pool words. Read
   them (and their float reinterpretation) straight out of `original/exefs/code.decompressed.bin`
   at `addr − 0x100000`. That is where the constants that identify the code came from:
   0.5/0.1/0.9/0.3333/1.867/100/1000, effect ids 0x4af/0x4b0/0x4b5, message ids 0xe59/0xe5b/0xe5d,
   vtable addresses (0x76d83c, 0x76e760, …), and handle-table masks (0x1fffff/0x3fffff).
3. **String symbols.** Every `s_…_00xxxxxx` symbol in a function body was extracted; strings carry
   most of the semantic weight here (`racing`, `uma_course2_mask`, `win_talk`, `Narrow_Run`,
   `_effect`, `null_icon_next`, `pop`/`pop2`).
4. **Cross-check with the poker family.** `0x416D10` counts ranks 1..13, tests straights/flushes,
   handles wildcards and returns a category 2..9/0xff; its callers `0x294C8C`/`0x29520C` are
   script-bound natives that push the five dealt cards into the UI. The game data contains
   `poker_hand.bxon`, `poker_msg.bxon`, `poker_double_up.bxon`, `null_card_joker`, `poker_card_num1`.
   That is why the 0x4146–0x416D block is filed as `Casino_Poker_*` rather than the "MonsterRow"
   names an earlier batch guessed for the callers.
5. Bottom-up: leaf helpers first (scene-entry accessors, shuffle helpers, id tables), then the class
   methods that use them, then the UI/battle orchestration.

## Decisions taken alone (orchestrator unavailable)

- **Class naming.** The object family at 0x40B–0x40F has no proven class name in the project, so it
  is consistently called `Field_Object2D_*` (2D sprite field object), and the sprite-carrying
  extension at 0x41E–0x41F reuses the already-proposed `Field_Object2D_*` vocabulary with
  `DtorBase`/`InitSpriteActor`. This avoids inventing a new "Camera"/"Gadget" class name that later
  batches would have to reconcile.
- **Two show/hide vtable pairs** (0x40C200/0x40C2C0 and 0x40C920/0x40CB78) are named `…A`/`…B`
  instead of guessing which one is the body and which the shadow sprite.
- **Poker deal variants.** They are near-identical and differ only in the RNG moduli and the
  `func_0064D3D0(self,N)` mode switch. They are named `DealHandA…H` with the distinguishing mechanic
  written into `summary`/`evidence` rather than pretending to know which table/rule each one is for.
- **No file outside my ownership was touched** except `AGENT_LOG.md` and this report.

## Numbers

- 150/150 addresses covered.
- Confidence distribution (machine-checked): 0.60 ×4, 0.55 ×12, 0.50 ×48, 0.45 ×50, 0.40 ×28,
  0.35 ×6, 0.30 ×2. `maybe_` prefix appears exactly where confidence < 0.5 (0.45 and below); names at
  0.50+ are asserted without the prefix, which is why the dtor/ctor patterns sit at 0.50 rather
  than 0.45.
- Ghidra-broken bodies (only the call sequence trusted, confidence ≤ 0.40): `0x417EE0`,
  `0x41EF50`, `0x41EFBC`, `0x426784`, `0x417BC4` (recovered pass).

## Not verified / open problems

- The meaning of the shared gate **`func_00636AFC(work->f_6c)`** is inferred from usage ("is the
  field action still running"); it appears in ~12 of these functions. A single focused batch on the
  0x00636xxx / 0x0025xxxx work object would let several of my `maybe_` names become definite.
- **`func_00416638(self, CONCAT11(page,index))`** is clearly a 2-byte card-slot accessor, but the
  exact table layout (5 hands × 13 ranks?) is not proven; the poker deal helpers are therefore named
  by mechanics, not by game rule.
- **`func_00415AE8`** (shared hand-rotation helper) is named from behaviour only.
- Three field-object entries (0x41E5CC vs 0x41EFBC, 0x41EB50 vs 0x41EF50) are the same logic in a
  readable and a mangled form; I kept them as separate `…B` names instead of merging.
- No decompilation was regenerated, so none of the 150 addresses gets the *new* name inside
  `decomp/readable` yet — that happens in `M1_merge_names`.
- No emulator/hardware check applies (naming only).
