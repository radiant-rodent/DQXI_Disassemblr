## Method

1. Read all 150 readable-C bodies (plus callers/callees from `decomp/readable` and strings/constants).
2. Built the address→name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and **all** sibling `orchestration/naming/out/*.json` (N_014.json is
   not valid UTF-8; it was read with replacement).
3. Resolved every literal pool word against `build/code.bin` (base `0x100000`): floats, SE/effect
   ids, and — decisive — **vtable pointers**.
4. Scanned the whole image for 4-byte occurrences of each batch address, which found the owning
   vtable for ~90 of the 150 functions and let ctor/dtor/update slots be named by role instead of
   guesswork. Examples:
   - camera vtable `0x76FE90`: `+0x08` dtor `0x443A90`, `+0x0C` `0x4435B4`, `+0x14` update
     `0x442D5C`; sibling camera vtable `0x76FE60` has `0x4406A8` in `+0x14`.
   - action-element vtables `0x76FBB4` (AtkSpell), `0x76FC50` (GuardEnd), `0x76FC84` (RevSpell):
     slot `+0x10` is **exactly** `0x43FA8C`, `0x43FBB4`, `0x43FC34`, so those three are the
     element destructors (0.80 confidence).
   - `0x76F630/0x76F634` are the two battle-actor destructors `0x43BEBC`/`0x43BE48`, and
     `0x76F64C` is `0x4394D4` (the class update).
5. Worked bottom-up: list/camera/animation helpers first, then their callers.

  eye vectors), `Camera_UpdateGyroYaw`, `Camera_ResolveCollision` (uses

  / `Camera_SetupDualPath` (curve objects at `+0x1A0/+0x1C0`), `Camera_Update`, `Camera_Dtor`.
- **Anim timeline**: the 11 `Anim_TimeTrack_*` helpers are structurally proven — they all walk the
  same intrusive list, test `owner->vtable+0x18`, use a `1/65536` epsilon on the key time at `+0x1C`
  and renumber `+0x18`. `0x43D270`/`0x43D288` merge duplicate-time keys; `0x43DD80/0x43DDB4` are
  ctor/dtor; `0x43D9D0` is the reset.
- **UI strings** anchor several names: `txt_command` + `txt_target` (`0x43EDC0`),
  `txt_Br_%d` / `txt_Bl_%d` / `icon_state_up2o_l_%d` (`0x43F784`), `icon_hit` (`0x445EF4/0x445F44`),
  `icon_change` (`0x44645C`), `NONAME` + `%ls` (`0x43EF84`).
- `0x4394D4` is the 10 268-byte `Battle_Actor_Update` (vtable `0x76F64C`); its dtor pair is
  `0x43BE48/0x43BEBC` and its dispatch guard is `0x43BF48`.

## Honest gaps / what is NOT verified

- No dynamic verification: no emulator, no debugger, no runtime check. Names come from static
  structure only.
- The first band (`0x426794-0x4297E4`) is the weakest. `0x426794` is a Ghidra container whose
  real entry was merged at `LAB_004262D8` (Thumb), `0x429260` is truncated by `halt_baddata`, and
  the "which command/selection step is this" reading is inferred from neighbouring `Battle_Ui_*`
  names (0.30-0.50).
- The 37 `Battle_ActorAction_*` entries are named by their plumbing (popup, effect, SE,
  animation, state at `+0x497/+0x498/+0x623`, done flag `+0xD2/+0xD3`), **not** by a recovered
  action name. I deliberately used `Actor` rather than `Enemy` because the same records are used
  by both sides (the monster-pair popup at `0x428738` is the only clear enemy-specific one).
  Mapping each element to its action name would need the element registry (the action names
  `atkspell`, `revspell`, `bjump`, `guard_ed`, `sleepEnd`, ... exist in `.rodata` around
  `0x374E18-0x3757BC` but are **not** referenced by absolute pointers, so they are hashed at
  registration time — that is why they cannot be tied to a vtable statically without reading the
  registry/hash function).
- `0x430C86` is a Thumb fragment/duplicate of part of `0x4309A8` (register arguments lost).
- `0x4441B8-0x445008` message-window handlers: the state values 0/1/2 written to `+0x11C` are
  observed; their names ("closed/opened/advance") are inferred from the order of the vtable.
- `0x448938`/`0x448C94`: named `Script_IsSystemReady` from `func_00636AFC(engine+0x6C)`; the
  function behind that check is itself unnamed, so this is inference.
- `0x446978` is placed in the hit-icon class because its vtable neighbours are
  `Ui_HitIcon_Update`/`Ui_RotatePaneWindow_Init`; the class name is not proven.
- Class names everywhere are roles, not RTTI (the executable has no usable RTTI strings).
