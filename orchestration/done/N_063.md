# N_063 - native naming batch (lane tag `Camera`)

## Summary

Named and documented all **150** functions in `orchestration/naming/batches/N_063.txt`
(`0x0046443C` - `0x0047CEC0`, non-contiguous) in `orchestration/naming/out/N_063.json`.

This was a resumed task, but **no prior output existed**: `out/N_063.json` was absent, there was no
`orchestration/done/N_063.md`, no log entry mentioned N_063, and no scratch files were left behind.
All 150 entries were produced from scratch.

The lane label `Camera` is **wrong**. The band is the UI widget framework plus the party / message /
tactics screens, with a small side order of 2D sprite-offset nodes, field NPC markers and a battle
action-animation family. The only thing that could have suggested "camera" is the node name
`"Shake"` used by three sprite-offset factories, which turned out to be a 2D offset/damping node,
not a camera shake.

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`, the batch file and
   the reports of the neighbouring lanes (`N_060`, `N_058`, `N_059`, `N_057`, `N_056`) for the house
   conventions.
2. Built one address->name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and every `orchestration/naming/out/N_*.json` (3,381 known names).
3. Generated a per-function digest over the batch: signature, callees resolved through the name map,
   callers from a call-graph scan over all 18,159 `decomp/readable/functions/*.c`, `s_*` string
   literals and float globals. Then read all 150 bodies in four passes (the dump is kept in
   `%TEMP%/opencode/n063_bodies.txt`).
4. Worked bottom-up: first pinned down the recurring helpers, then used them to read the callers.
   The anchors that made the band legible:
   - `Ui_Object_CtorBase` 0x001A66A0 / `Ui_Object_DtorBase` 0x001A6768, and the `FUN_0010F6CC`
     operator delete that follows almost every destructor.
   - `Ui_AnimRef_ResetPanes` 0x003DFF34 (show/reset a pane) vs. the hide path 0x003E043C.
   - `Ui_TextLayer_SetText` 0x001A629C, `Ui_TextElement_SetString` 0x003A7A2C,
     `Ui_PlayAnimByName` 0x0053D604, `Ui_Window_PushPane` 0x006D7508.
   - **0x001D85EC** = "bind the named layout block and its panes" - proven by the literal string
     arguments (`win_talk`, `win_yesno`, `win_gold`, `win_casino_coin`, `win_operation`...).
   - **0x001DACFC** = `Ui_MessagePair_Bind` (already named) and **0x001DAD58** = the message-pair
     input pump, both applied to the talk window's +0x1fa8 member.
   - **0x006F229C** = `Ui_GetCore`, while **0x006F1EEC** (used in this band on nearly every function)
     is a different app/work singleton - the JSON evidence says so explicitly so the two do not get
     conflated later.
   - `Container_NameHash_Ctor` 0x002E4324 / `Container_NamedMap_Insert` 0x002ACAA4 (and the
     `0x002E4A70` / `0x002AE1B4` / `0x002ADFA4` second-map variants) - the named node factories.
   - `std_destroy_range` 0x00100BE0 calls reveal every inline array: `(offset, element_size, count)`
     is what pinned the row-widget sizes (5 x 0x50, 4 x 0x50, 16 x 0x58, 12 x 0x50, 5 x 0xf0 ...).
5. Cross-checked the sibling lanes so names stay consistent: N_062 owns the 0x0046xxx battle
   `Battle_ActionAnim_*ElementCtor` family (hence `Astron`/`GoldAstron` completion callbacks keep
   that prefix), N_048/N_015 already own `maybe_Ui_SakusenWindow_*` / `maybe_Ui_EquipWindow_DtorBase`
   / `maybe_Ui_PartySelectWindow_Dtor` (two of my drafts were renamed to avoid the collision).

  covered, no extras.
- All seven keys present on every object; `signature` contains the object's own `name` for all 150.

## What is NOT verified / open problems

- **`0x468320` and `0x4683F0`**: Ghidra lost registers (`unaff_r*`) and inserted `halt_baddata` in
  the middle of the state machine, so the entry arguments and the exact branch that selects state
  0x5a0/0x5b7/0x5c4 are reconstructed, not proven. Both are at confidence 0.30.
- **`0x47285C` / `0x472A0C`**: same problem (argument registers lost). The direction math and the
  `func_0035FF3C(..., 0x00472FCC, ...)` sprite spawn are clear; the trigger condition
  (event 1 vs. the 4/5 special cases) is a reconstruction.
- **~40 virtual constructor/destructor pairs** are identified by mechanism only. They are reachable
  exclusively through a vtable and nothing in the image (no RTTI, no string) names the class, so
  they carry hex suffixes (`maybe_Ui_Object_DtorVirtual_443C`, ...) to stay unique instead of
  inventing a class name.
- **Tactics-window slot semantics**: the type bytes 0x01/0x02 and 0x02/0x03 are proven as
  dispatched values (`func_0063FD24` -> `f_5e`/`f_5f`), but reading them as "row vs. column" and
  "all vs. one member" is an inference.
- **`0x46E50C`** is placed on the battle display path from its four battle-setup callers
  (`0x002BDAC8`, `0x002BE754`, `0x0040F940`, `0x004E55AC`) and the `Battle_SetupUnitFromMonsterData`
  call; the class it builds is not otherwise named.
- **Font helpers** `0x46C438` / `0x47B844` are named from the `0x0062Cxxx` / `0x0064ACEC` font API
  and from how the results are used (run length, glyph index at a point); the engine's own names for
  those API calls are unknown.
- `0x46CF94` is a one-liner over 0x001009B4, which Ghidra labels `std_strstr` but which is used here
  as a boolean busy flag - the callee's real identity is unresolved (0.35).
- No Squirrel script binds any of these addresses (they are internal UI/engine methods), so the
  game-logic side could not confirm any name.
