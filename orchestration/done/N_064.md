## What the range actually is (the "Camera" label is wrong)
The batch generator propagates subsystem labels through the call graph; "Camera" is this project's
largest label (6,151 functions) and covers most unnamed code. The real content:

1. **0x47D47C–0x483308 — battle command / party panel.**
   Two identical 23-slot vtables at `0x774680` and `0x77E924` contain 22 of this batch's methods. The
   object has two party display blocks of `0x16F3` words at `+0x18B4`, a state word at `+0xD058`, an
   actor id at `+0x497` and the message-row state counters `+0x5E0/+0x5E5/+0x5E7`. Methods cover child
   iteration (`func_00630DC8`/`0x630D64`), item-window opening (`Menu_FindSlotForEntry`,
   `Menu_OpenItemEntryWindow`), target markers (`0x4BEE8C`), party status, and battle-queue calls
   (`Battle_QueueActionEx`). Named `Battle_Ui_*`.
2. **0x47EBC8 / 0x483870 / 0x483E30 / 0x484030 — party-member display objects.**
   15-slot vtables of the `0x774468` family (slot 0 is `FieldParty_ResetMemberSlot`). They drive
   equipment/model nodes (`Model_AttachSlot_Release`, `Model_Equip_CommitNodeChanges`), the "Fear"
   (cursed equipment) animation and per-member SE/message states. Named `Battle_PartyMember_*`.
3. **0x484C10 / 0x484CB8 / 0x484D8C / 0x484E08 — battle-action element executes.**
   Proven by finding the literal-pool dword `vtable-4` inside the class constructors:
   `0x484C8C -> 0x774ABC` = `Battle_Action_CounterAct_Ctor`, `0x484D00 -> 0x774AF0` =
   `CounterEnd_Ctor`, `0x484DD4 -> 0x774B58` = `SpecialLanding1_Ctor`, `0x484E50 -> 0x774B8C` =
   `SpecialLanding2_Ctor`. Each is vtable slot 3 of its class.
4. **0x485C9C / 0x485CF0 — damage-popup and cursor widgets.**
   `0x485CE4` holds `0x774F04` (vtable `0x774F08`, slot 7 = `Ui_DamagePopupWindow_Init`), so 0x485C9C
   is the popup widget destructor. `0x485D8C` holds `0x774F68`; 0x485CF0 builds the cursor-select
   widget and is the only function in the batch that references a real string,
   `s_cursor_select_00485D58`.
5. **0x484EBC–0x485824 — model-actor node/visibility virtuals** of the 31-slot actor-model vtables
   `0x774C04` / `0x774D8C` (`+0xF22` visibility mode, `+0x39D` node reset, attachment handles).
6. **0x485D90–0x497520 — battle/message text layout + monster battle rows.**
   Rows are 0x2C-byte records reached through `func_0018C184(id)` (marker byte at `+0x58/+0x59`);
   actor/battle work is `0x35EB98` / `0x63FD24`; the shared layout engine is `0x4882F4`/`0x49ACF8`/
   `0x49AA0C`; `0x487FC0` is a one-call invalidation hook with 23 callers. The monster HP/MP bar
   helpers are `0x492520`/`0x4900A8`. Named `Text_*` for the generic measurement/layout half and
   `Battle_Message_*` / `Battle_Monster_*` where the evidence is battle-specific.

## Method (reproducible)
1. Parsed the batch file; built a name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all `orchestration/naming/out/N_*.json`.
2. Rebuilt a caller index over all 18,159 files of `decomp/readable` (18,748 entry points).
3. Per function: caller list, callee list with resolved names, virtual-slot calls, integer/float
   constants compared, and `g_XXXX` globals dereferenced from `original/exefs/code.decompressed.bin`
   (base `0x00100000`) so message ids, SE ids and float scales are real values, not `g_` names.
4. Vtable grouping: for each entry point scanned the image for its pointer, then for the *pool
   constant* equal to `vtable_start - 4` (the C++ object vptr), which gives the constructor and hence
   the class name from the already-named sibling constructors. This is how items 3 and 4 above were
   proven rather than guessed.
5. Read the full bodies of the very large outliers (0x47D47C, 0x47EFE8, 0x493980, 0x494F84,
   0x489A8C, 0x48B558) and the compacted bodies of all others, plus the 0xD6C/0xBB0 functions.

## Honest gaps / not verified
- The 23-slot panel is **named `Battle_Ui_*`, but whether it is the player command panel or the
  enemy/target panel is not proven**; the evidence is its callers (`Menu_*`, `Battle_Ui_IsIdle`) and
  its vtable neighbours, which earlier batches had also called `Battle_Ui_*`.
- The nine `Text_UpdateBlinkStateA..H` functions are distinguished only by the **flag-id sets they test**
  (0x2C..0x2F, 0x34..0x37, 0x83/0xBA/0x9E, 0x30..0x33, 0x47..0x4B, 0x3D..0x3F, 0x2B/0xC6); the ids are
  read from the code, their game meaning is not known.
- `0x47F9AA`, `0x481C4C`, `0x48356C` are Thumb fragments that Ghidra split out of the middle of ARM
  functions (their byte ranges are inside the parent function). They are named only from that
  structural relationship, with confidence 0.25.
- `0x484A1C` and `0x48C490` have broken Ghidra bodies (`bad instruction data` / `halt_baddata`); they
  are named from neighbours/callers only (0.30 / 0.20).
- The `Text_*` vs `Battle_Message_*` split is a judgement on which callers dominate (generic message
  window vs battle rows), not a proven module boundary.
- Shared helpers repeatedly used here are still unnamed and their exact semantics are inferred:
  `0x1CA474`/`0x1CA3E4` (row template lookup / message post), `0x3FBE4C`/`0x3FF9AC` (message or
  balloon spawn), `0x63FD24`/`0x63E5C8`/`0x63D018`/`0x63DCA4` (object-by-id resolvers),
  `0x630DC8`/`0x630D64`/`0x630BB8` (child iteration), `0x18C184`/`0x18C1B8` (layout row tables),
  `0x1FD96C`/`0x1F5C90` (battle-UI busy query), `0x6731EC` (layout invalidation),
  `0x640348` (fast/auto-battle gate, inferred from `gamework+0x4320`).
- No Squirrel script in `game_assets/scripts/` binds any of these addresses, so the game-logic side
  could not confirm the roles; these are internal engine/UI functions.
