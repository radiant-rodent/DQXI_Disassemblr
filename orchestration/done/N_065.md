## Important decision: the batch label is wrong

The batch header (and all 129 batch files) says **"Camera"**. The range is **not** camera code.
Everything in 0x00497690–0x004AF5E4 is 3DS **UI / menu / battle-HUD / field-object** code:

- the battle status/text row layout engine that continues N_064's range (`0x00485D90–0x00497520`),
- the UI list/marker window class whose vtables are at rodata `0x00772C70` and `0x00774FD0`,
- a spline/rotation motion path player (vtable `0x00775184`),
- concrete windows (dungeon battle window, casino slot screen, item+text window, battle command
  list, equipment list, mp-damage popup, party list),
- battle action classes (ShieldGuard / WeaponGuard / guard_s / guard_w / combination),
- field actor-group, field battle-trigger and 2D map-object classes.

Naming was therefore done with `Ui_`, `Menu_`, `Battle_`, `Field_`, `Actor_`, `Effect_`,
`Anim_`, `Casino_`, `Text_` prefixes, not `Camera_`.

## Method

1. Read the readable C for **all 150** bodies (`decomp/readable/functions/FUN_*.c`), falling back
   to `decomp/ghidra/functions/`.
2. Used the exact disassembly in `asm/text/text_00480048.s` for every function, and dereferenced
   every literal-pool word against `original/exefs/code.decompressed.bin` (image base
   `0x00100000`). This recovered **inline ASCII pane/clip names** that the pseudo-C hides, e.g.
   `win_dungeon_battle`, `win_dungeon_enemy`, `win_target`, `txt_in`, `item_in`, `fade`,
   `ShieldGuardKeep`, `WeaponGuardKeep`, `fukuro`, `soubi-chuu`, `mochimono`, `pop_mpdamage_d`,
   `menu_slot_belt_*.bflyt`.
3. Built a caller/callee index over all 18,159 decompiled readable files, and merged the name maps
   from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and every sibling
   `orchestration/naming/out/N_*.json`.
4. Scanned rodata/`.data` for pointers to batch addresses, which identified vtables
   (`0x772C70`/`0x774FD0` = the arc/list window class, `0x775184` = motion path,
   `0x775DA8`/`0x775DDC` = ShieldGuard/WeaponGuard actions, `0x775F48` = mp-damage popup,
   `0x7762E4` = 2D map object, …) and let constructors/destructors/virtual slots be named by role.
5. Worked bottom-up on the shared helpers first (`0x0048DF98` state→index mapper,
   `0x0048CA0C`, `0x00490D28`, `0x0048C120`, `0x0049ACAC`, `0x0049BD54`, `0x0049C93C`,
   `0x002AB62C`/`0x002AB698` handle getters, `0x00574548`/`0x005753BC` basis/matrix helpers),
   then named their callers.
6. Squirrel scripts were checked: **none** of the 150 addresses is a script native
   (natives live at 0x0015xxxx–0x0016xxxx), so there is no game-logic cross-check available.

## Honest gaps — what is NOT verified

1. **The 4×26 arc/handle class (0x0049B8B0–0x0049ECA8) is structurally proven but its owning screen
   is not.** 20 methods share the `0x772C70`/`0x774FD0` vtables, the `+0x220` handle grid and the
   `+0x428C` work table; what the window is (item wheel, battle target list, menu page grid) is
   unresolved. `Ui_ArcListWindow_*` is a deliberately neutral invention.
2. **The 0x00497690–0x0049B8B0 "battle status/text row" reading is corroborated, not proven.** It
   agrees with N_064's independently written lane report (same 0x2C row stride, same
   `0x0048DF98`/`0x00487FC0` helpers), but the meaning of the 8 row-type bytes (0x27/0x31 markers)
   and of the vtable+0xE8 type ids (0x62–0x67, 0x6C–0x70, 0x86, 0xB7, 0xE0/0xE1) is inferred.
3. **~25 constructor/destructor entries** are named from their vtable group or nearest sibling, not
   from a recovered class name (e.g. `Ui_NumberTextWidget_Dtor`, `Ui_EightLineTextWindow_Dtor`,
   `maybe_Ui_Widget_Ctor_7760E8`, `maybe_Ui_CharacterEntry_*`).
4. **Ghidra-damaged / semantic-only bodies** at low confidence: 0x004A70F8 (0x55C), 0x004A56D0
   (0x690, Thumb), 0x004A37F8/0x004A3A18, 0x004A9E58, 0x004A96B8, 0x004ACD30, 0x004AE12C,
   0x004A2124, 0x004A2B70. For these only the call sequence and field offsets are trusted.
5. **No in-game confirmation**: none of the 150 addresses is a Squirrel-bound native, so no script
   or gameplay behaviour could be used to confirm names; no emulator/hardware run was made.
6. Function signatures are reconstructed from the ARM calling convention and the pseudo-C. Where
   Ghidra lost argument registers, parameter counts/types are approximate; `params` only lists the
   parameters that are actually understood.
