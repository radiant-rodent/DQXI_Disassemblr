## Method

1. **One-pass index** over all 18,367 readable C files: `address → callees`, `address → callers`,
   plus name resolution through `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and every other `orchestration/naming/out/N_*.json`. That is what made
   the range readable: dozens of callees were already named by N_001–N_067
   (`Field_SceneObject_ReleaseEffectSlots`, `Effect_ReleaseHandle`, `Ui_Object_CtorBase`,
   `Monster_Model_Create`, `Battle_QueueActionEx`, `Gfx_Scene_SetNodeParams`, …).
2. **Literal-pool decoding** from `original/exefs/code.decompressed.bin` (base `0x100000`): resolved
   every `g_XXXXXXXX` in a body to its value/pointer/float. This gave the decisive constants:
   effect id `0x496`, `0xFFFF` sentinels, handle masks `0x1FFFFF`/`0x3FFFFF`, `0xFFFFFFF` slot
   sentinel, screen rect 400×240, colours 195/180, `0.01745` deg→rad, `6.283`, `1/15`,
   `-440.3f`, the state ids `0x1F18/0x1F2C/0x2C6D…0x2D29/0x309…0x458`, message ids
   `0x42/0x43/0x5D/0x803/0xE5F/0xE60`.
3. **Strings**: `g3107_mat_all_off`, `Flashing`, `TurnL`, `React`, `poor`, `Whale_Start`,
   `win_00`, `txt_l1`, `txt_l2`, `fChit_%d` — these carry most of the semantics.
4. **Vtable / class-table walk**: scanned the image for every 4-byte occurrence of each batch
   address. This exposed the class vtables at `0x776xxx` and the 8-byte-strided process tables at
   `0x726xxx`, which fixed the class membership of the smithy dtor (0x4B0190 in the table at
   `0x776488`, whose other slots are 0x4B0098 / 0x4B01F0 / 0x4B062C / 0x4B06CC), the show/hide
   pairs, and that `0x4B28BC/0x4B29FC/0x4B2A5C` are update stages of one process
   (`0x72616C/0x72618C/0x726194`). Note: these tables store `function_start-4` in several places
   (Ghidra split the leading `ldr` off the prologue), which is why a batch address such as
   `0x4B0194` is really the function at `0x4B0190`.
5. Bottom-up: leaf getters/setters and dtors first, then the classes that call them, then the
   battle/cutscene orchestration. 0x4BC6D0 (9,944 bytes of C) was summarised from its state ids,
   message flags and the complete call list rather than read line by line.

## Decisions taken alone (orchestrator unavailable)

- **Class vocabulary.** Nothing in the project proves names for most of these classes, so I kept
  one consistent role name per family instead of inventing plausible-sounding game terms:
  `Field_Prop_*` (the 0x2AC field objects), `Field_Actor_*` (the 0x2B8 actor objects),
  `Gfx_SpriteObject_*` (the scene-node + sprite wrapper at 0x4C62xx–0x4C6Exx),
  `Event_ActorModels_*` (the cutscene model set), `Field_Marker_*` (the world→screen marker
  objects), `maybe_Field_ModelSlotEmitter_*` (the 10-slot clone emitter).
- **Smithy.** `g3107` is proven to be the smithy: the model's material library is
  `smithy_tex`/`hammer_tex` and the function literals are `g3107_mat_all_off` and `Flashing`.
  I therefore named the dtor/effect functions in that vtable `Field_Smithy_*` rather than keeping
  generic `Field_SceneObject_*` names.
- **`Camera_FindOccludingSegment` (0x4B5DA4).** Its caller set (model/camera objects 0x386034,
  0x441B24, 0x49FD4C, 0x599E74) and its geometry (0x38-byte segments, cubic evaluation, camera
  position argument, first-hit index return) justify a camera/line-of-sight name; the exact use
  (camera collision vs. screen-pick) is not proven, hence 0.50 and a neutral verb.
- **`func_00636AFC`.** N_060 read it as "field action still running", N_067 as a handle-validity
  test. I mention both readings in 0x4B0BC4's evidence instead of asserting one.
- **No file outside my ownership was touched** except `AGENT_LOG.md` and this report. Scratch
  tooling lives in `%TEMP%/opencode/n066/`.

## Not verified / open problems

- **This is naming only.** Nothing was compiled, run, patched or emulated; no test suite applies
  (the task exempts rule 5). Validation was mechanical: JSON parses, 150/150 exactly once,
  schema keys exact, unique names, prefix/confidence rule, cross-batch collision scan.
- **Class names are roles, not recovered names.** No RTTI/class strings exist for these objects;
  `Field_Prop`, `Gfx_SpriteObject`, `Field_Marker`, `Event_ActorModels` and
  `Field_ModelSlotEmitter` are descriptive groupings, not proven original names.
- **`maybe_Field_ModelSlotEmitter_*` (0x4B2134–0x4B2FEC) is the weakest block.** The code
  demonstrably writes 0xB8-byte render-slot records in the shared `work+0x24A98` array and copies
  a 0x84-byte appearance record, but *what game feature* uses 10 timed clones is unresolved
  (party display? after-image? 2D camera actors?). All ten names are 0.40 and prefixed.
- **`maybe_Battle_AutoAction_*` (0x4B78C8/0x4B8258)** are named from `Battle_QueueActionEx`, the
  per-unit table and the state ids only; the UI that owns them is the tactics-window vtable
  (`0x776ED4`), but whether this is auto-battle, tactics preview or a cutscene action queue is
  not proven.
- **`maybe_Ui_Overlay_*` (0x4C24C8–0x4C2AD8)** are named from the 400×240 screen rect, the
  0x224-byte drawable and the frame-driven sounds; "fade/curtain" is an inference from the size
  and the poker-window caller.
- **`maybe_Text_BuildMessageGlyphRun` (0x4C3F50)** — the power-of-two allocation and the text calls
  are proven; whether the 0xA24 bytes are a glyph cache or a line buffer is not.
- `0x4C3C3C`, `0x4C39B4`, `0x4C73C0`, `0x4C756C`, `0x4C7D00` share the same world-position fields
  (`f_d4..f_e8`) and are all called "marker"; the visual role (actor plate vs. talk marker vs.
  damage popup anchor) is not separated.
- Ghidra split several prologues: batch addresses 0x4B0194/0x4B0B8C/0x4B1404/0x4B28BC/0x4B2A5C/
  0x4B78C8 really start 4 bytes earlier. The names apply to the real functions; the JSON keeps the
  batch address, as required.
- No decompilation was regenerated, so none of these names is inside `decomp/readable` yet — that
  happens in `M1_merge_names`.
