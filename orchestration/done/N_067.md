# N_067 — native naming batch (lane tag `Camera`)

## Summary

Named and documented all **150** functions of `orchestration/naming/batches/N_067.txt`
(`0x004C86D0` – `0x004DD0F4`, non-contiguous) in `orchestration/naming/out/N_067.json`.

This was a resumed task, but **no prior output existed**: `out/N_067.json` was absent, there was no
`done/N_067.md`, no `AGENT_LOG.md` entry mentioned N_067, no other lane's `out/N_*.json` named one of
the 150 addresses, and no scratch files were left behind. All 150 entries were produced from scratch.

**The lane label `Camera` is wrong.** Not one function in this band is camera code. The first half is
field scene objects / gimmick gadgets / actor-behaviour ("action") classes; the second half is battle
UI state machines, battle target markers, field object sprites and the casino poker/racing UI. The
label is probably a residue of the old `asm/text` chunk map — the only `"Shake"`-style nodes that
neighbour this band live in N_063, not here.

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`, the batch file and
   the neighbouring done reports (`N_062`, `N_063`) for house conventions.
2. Built one address→name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and every `orchestration/naming/out/N_*.json` (63 sibling files) — proposals
   from other lanes were used as callee names, and their names were never overwritten.
3. Built a caller index over all 18,159 `decomp/readable/functions/*.c` files (token scan for
   `func_XXXXXXXX` plus known names), so every batch function has its caller list.
4. Generated a stripped-body digest for all 150 functions: declarations and comments removed,
   `g_XXXXXXXX` annotated with the actual value/pointer/float read from
   `original/exefs/code.decompressed.bin` (base `0x00100000`), `s_XXXXXXXX` resolved to text, and
   `func_XXXXXXXX` replaced by the best known name. Read all 19 chunks.
5. Scanned the binary image for every 4-byte occurrence of each batch address and walked back to the
   vtable start: **92 of 150** functions sit in a vtable or pointer table. That turned anonymous
   blobs into readable slots (`[10]` = apply-model-record, `[12]` = on-event, `[29]` = trigger
   command, `[30]` = "field alive" predicate, `[0]/[1]` = deleting/base destructor, …).
6. Named bottom-up: first the shared engine helpers, then the leaf builders/dtors, then the
   state machines that call them. JSON was written after each ~25 functions (24 → 72 → 150), so a
   resumed worker can continue.

### Engine facts recovered on the way (useful for the merge, treat as hypotheses)

- `FUN_006F1EEC` = app-context singleton accessor. Observed sub-objects: `+0x48` scene/2D-effect
  layer (render-state bytes at `+0x27C`, `+0x281`), `+0x50` render layer (visibility index at
  `+0x71`), `+0x54` actor manager (`func_001C7570` = unregister handle), `+0x58` object-definition
  manager (`func_00642A28` = find by name), `+0x5C` battle context (`+0x4218`, `+0x4244`, `+0x4260`,
  `+0x4298`, `+0x4320`, `+0x4324`), `+0x60` effect manager, `+0x6C` field manager, `+0x74` UI widget,
  `+0x78` trail/2D capture (`func_002ACF58`, `func_00239A1C`, flag byte `+0x7D`), `+0x94` sound
  (`Snd_*`), `+0x98` RNG (`func_0051B1FC(max)`), `+0xB4` model/sprite resource table
  (`func_0066A7B8`).
- `func_00636AFC(obj)` = handle validity test: virtual call on `obj+0x3DC` yields a handle which is
  compared against the invalid sentinel `0xFF000000`.
- `func_002D1258(model, name, 0)` = play animation by name; `FUN_005E754C(node, event, arg)` = fan an
  event out to all children.
- `FUN_00294BD4` / `Field_ActorAction_Ctor` (`0x3E4A10`) / `maybe_Action_CtorBase` (`0x294C34`) are
  the three actor-action base constructors used by the action classes in this band.

## Results / validation

- `orchestration/naming/out/N_067.json`: 150 objects, 98 KB (97,958 bytes), UTF-8, keys exactly
  `address, name, signature, params, summary, confidence, evidence`.
- 150/150 batch addresses present **exactly once** (checked mechanically against the batch file);
  no extras.
- 150 unique names; no name or address collision with any other `out/N_*.json` (five names were
  changed because other lanes had already used them for *different* addresses:
  `Field_Gadget_TriggerStoredCommand`, `maybe_Battle_Ui_UpdateStateMachineTwin`,
  `maybe_Ui_SevenRowList_Ctor/Dtor/DtorBase`).
- Every `signature` starts with its `name`; every `params` key is `param_N` (project convention);
  every name with confidence < 0.5 is `maybe_`-prefixed, and no ≥0.5 name is.
- No code, data or shared file was touched. No test suite / build / emulator run — the task exempts
  naming lanes from rule 5, and nothing executable changed. `AGENT_LOG.md` and this report are the
  only other files written.

## Honest gaps

- The field-gadget class names are **by role**: this engine has no RTTI names, and the only string the
  builder passes is the model name `sprite`. `Field_Gadget_InitKind1B/1C/1D` are three variants that
  differ only in the command id (0x1B/0x1C/0x1D) and the animation/sound they later select.
- `0x4CB510` is the weakest name in the batch (0.35): it draws a chain of sprites along a curved path
  with per-segment RNG offsets and, for variant 1, allocates a 0x380-byte physics object plus a
  `Gfx_CollisionProxy`. Rope/vine vs. after-image chain is unresolved; behaviour is described
  precisely, the gimmick's identity is not.
- `0x4D2FE4` / `0x4D3344` are named from their popup calls, state ids and animation ids
  (0xB3/0xB4/0xBB/0x78/0x7A/0x10E, 0x121 loop) rather than from a recovered class; "level-up" and
  "skill learned" are the most plausible readings, not proven.
- ~30 member-less `Ui_Object` ctor/dtor thunks carry a hex suffix (`maybe_Ui_Object_DtorVirtual_CE978`)
  because their owning window is only reachable through a vtable and no string identifies it.
- `0x4D0E54` and `0x4D1CDE` are compiler-duplicated copies of the same state machine; Ghidra's
  4-parameter signature on the twin is register noise, not a real prototype.
- `0x4D0E54`'s state constants are state ids, not pointers; the decompiler shows them as addresses
  (`g_004D127C = 0x1645`). Do not read the `0x16xx` values as code.
- Japanese message strings at `0x4C9FC0/8/D0` are UTF-16LE; the ASCII-oriented readable C makes them
  look like garbage (`'\\x010…'`). They are furniture names.
