## What was checked and corrected

I audited the low-confidence and high-consequence entries in detail against
`decomp/readable/functions/FUN_*.c` and against the raw image
`original/exefs/code.decompressed.bin` (virtual address − `0x100000` = file offset), including
literal-pool dumps for every table/vtable claim below.

Corrections written to the JSON (19 entries):

* **0x004E5064 / 0x004E53B8 / 0x004E559C / 0x004E5B74** — were named `maybe_Ui3D_StaticFini_*`
  ("static destructor stub"). They are the deleting-destructor entries of four small UI-3D
  sub-objects: each is the `+4` word of a type table (`0x77B0F0`, `0x77B140`, `0x77B168`,
  `0x77B190`) and each body is exactly `0x0017C334` (embedded-list destructor) + `0x0010F6CC`.

  `maybe_Ui3D_EntryTable_DtorDeleting`, `maybe_Ui3D_AttackSequence_DtorDeleting`; the owning
  method of each table is now cited (0x4E5038 / 0x4E530C / 0x4E53D8 / 0x4E55AC+0x4E5AA4).
* **0x004E51A8 / 0x004E51EC** — evidence claimed `0x0017C02C` / `0x0017C040` were container
  constructors/destructors. They are 4-instruction helpers that set/clear the byte at
  `subobject+0x2C`. Text corrected to "enables / disables the two embedded sub-panels".
* **0x004E52AC** — corrected "two containers built in 0x004E51A8" to the three embedded list
  objects at `+0x98`, `+0x50`, `+0x48` destroyed by `0x0017C334`.
* **0x004E45D0** — was `maybe_Ui3D_StaticInit_4E45D0`, which contradicts its body (it destroys
  0x121 effect handles via `0x002F19AC` and then releases the block). Renamed
  `maybe_Ui3D_Panel_DtorDeleting`, confidence lowered to 0.30; the exact screen owner is not
  recovered, so this stays `maybe_`.
* **0x004E6548** — was `maybe_Ui_Message_IsGlobalHandleValid`. The body is a generic
  "is `app+0x6C` manager handle alive" predicate, identical to the inlined gate in
  0x004E6A70 / 0x004EFD04 and wrapped by 0x004EFF2C. Renamed `maybe_Ui_IsFieldManagerReady`.
* **0x004E6604** — was called a Ghidra fragment (`maybe_Ui_Message_ShowChildAux`, 0.30). The
  full body *is* recovered: it shows/hides **both** `f_168` and `f_16c` (slot `0x38` when the

* **0x004F0D98 / 0x004F0EA0** — were `Ui_PanePopAnim_*`. The vtable `0x77C404` is the base
  table of the **event gimmick** family, installed by 0x004F0ED4, whose concrete user is action
  index 8 of the event-action factory 0x0022AF9C with the literal `"landing_get_off_vehicle"`

  update 0x4F0D98]` and the `landing_get_off_vehicle` factory use, which pins the family.
* **0x004E2C48** — literal is `"$offset"` (0x004E2CE0), not `".offset"`.
* **0x004E3700 / 0x004E6F10 / 0x004E7E28 / 0x004F24D8 / 0x004F3220** — text said

  no omissions.

  (`N_014.json` is not valid UTF-8, so it could not be compared — same caveat as N_069).

  0.50 does.

## What is NOT verified

* I did **not** re-derive all 150 functions from scratch. The previous worker's analysis was
  preserved where my spot checks agreed; ~40 entries were read in detail, the other ~110 are
  accepted at their recorded confidence. Treat entries at 0.20–0.35 as leads, not facts.
* 0x004E45D0 has no caller in the readable tree and no reference in the scanned tables; its
  "panel deleting destructor" role is inferred from the 0x121-handle release loop and the
  `+0x220` secondary type-table store, not from a recovered class.
* 0x004DD4A8 / 0x004DD53C are only known to be two variant pane builders with different
  sprite factories (0x006D4B34 vs 0x006D4D08); which message-window style each serves is not
  proven. The `Ui_Message_*` role names for the 0x4DDxxx block are plausible but unconfirmed.
* The class split between 0x004DDA70 (`Text_MessageWindow_Update`), 0x004DF680
  (`Text_TalkWindow_Update`) and 0x004E95E0 (`Ui_Message_Update`) is inferred from their
  vtables/fields; the three windows are close relatives and the exact in-game window
  (message/party-talk/name-plate) each drives is not proven.
* 0x004E7500 / 0x004E7A50 remain the weakest UI entries (0.30/0.50): the style table at
  0x007285B4 and the 0x30-stride sub-entries are read from code, but the attribute names and
  the "8 sub-entries" count are interpretation.
* 0x004EFD04 / 0x004EFD80 / 0x004F04E8 are event-trigger wrappers named from their literal
  trigger strings (`TrgFloorMapJumpEvent`, `TrgRCommand`) and command ids; the UI class that
  owns them is not recovered.
* `0x0010F6CC` is described as a header-based (refcounted) object release based on its
  disassembly; the actual allocator API name and whether the header is a refcount or an
  allocator record were not resolved.
* No emulator run and no merge into `decomp/native_names.json` / `symbols.json`; the names are
  only in this batch output and await the project-wide merge.
