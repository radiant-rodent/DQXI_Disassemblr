## Correction: the batch is NOT "Camera"
The batch header says *Camera* — that is wrong for this whole range. Evidence accumulated while
working (details per entry in the JSON `evidence` field):

1. **0x0059FD24–0x005A6064** — 2D battle **unit display** objects and the **battle action
   sequence manager**. The objects hang off six vtables in `.rodata`
   (`0x77EAC0`, `0x77EC6C`, `0x77ED80`, `0x77F02C`, `0x77F1DC`, `0x77F34C`) which are created in
   `func_005A1654` / `func_005A1F08` / `func_005A4D9C` / `func_005A5F90` / `func_005AE770`.
   Their bases are `func_00438660` (monster-model instance) and `func_003CAE00` (the battle action
   slot container that `func_003CAB4C` = *ClearActionSlots* walks). Members use the battle-unit
   field layout already seen in the 0x59xxxx range (`self[0x497]` = character id,
   `self[0x498]` = model record, `self[0x14]` = model handle). The sequence manager calls
   `func_003C7478` (*ProcessActorCommand*), `func_003C8F74` (*SpawnSlotEffect*),
   `func_003C61CC` (*SpawnAllMemberBalloons*) and `func_003CAB4C` (*ClearActionSlots*).
2. **0x005A79A4–0x005AA2A4** — a render-object / material-animation class implemented at
   0x5A73DC–0x5AB0CC. Its full method table is the `.rodata` array at **0x7A2DD8**; slots 38–40
   (`0x5A9278`, `0x5A9DE8`, `0x5A8BF4`) were already named `Gfx_RenderObject_*` by N_007, which
   fixes the vocabulary for the neighbouring slots in this batch.
3. **0x005B22D8–0x005BB544** — the **Squirrel virtual machine**, statically linked into `code.bin`.
   Proof: this code range contains Squirrel's own error literals as inline data
   (`0x5B2AE4` "Native stack overflow", `0x5B34D0` "cannot iterate %s",
   `0x5B4CA4` "indexing %s with %s", `0x5B8FE8` "trying to resume a '%s' …",
   `0x5BA018` "cannot suspend an already suspended vm", `0x5BA3C0` "division by zero",
   `0x5BB2A0` "wrong number of parameters"). The 0x36C4-byte function at **0x5B64CC** references
   almost all of them and calls every other function of the cluster → it is the interpreter loop
   (`SQVM::Execute`).
4. **0x005BBBC0–0x005CD25C** — the **2D mode field**: map-chip queries (`func_0066735C`
   maps 8-pixel text cells to chip records, used by the "field_collision" loader at 0x5B0284),
   chip-walk / path helpers, and sprite actors positioned through
   `func_0031979C` (*Gfx_Actor_SetPositionXY*) and inserted into the spatial hash at
   `func_005C1B40`. Supporting assets in `game_data`/`game_assets` (`level2d.bxon`,
   `2d/battle2/enemy/%s.bch`, `2d/battle2/background/%s.bch`) match this reading.

So this lane spans **Battle 2D + Gfx render object + Squirrel VM + Field 2D**, not the camera.

## Method (bottom-up, as required)
1. Indexed all 17,779 readable C functions (caller/callee graph), the function index
   (`decomp/functions_index.json`) and all 64 sibling `out/N_*.json` files for known names.
2. Scanned every literal-pool word inside each batch function *and* all strings in `.text`,
   `.rodata` and `.data`, so strings embedded between functions (the Squirrel literals) and
   strings referenced from `.data` (asset paths, `field_collision`) were both found. Each string
   was attributed to its enclosing function.
3. Enumerated the 85 real vtables in `.rodata` (signature `{0, dtor, 0x001FEFC0, 0x001F96D4}`)
   and mapped every batch address to its vtable(s) and slot. This is what exposed the six-class
   hierarchy and the `0x7A2DD8` render-object method table (an unusual table whose entries are all
   in 0x5A73DC–0x5AB0CC).
4. Followed constructors back to their factories (`0x6C0990`/`0x6C0F44`/`0x6C10F0`/`0x6C19CC`/
   `0x6C2818`, `func_0033AD44`) to see which object kinds are instantiated where.
5. Read the agent's own logs from previous lanes (`N_065`/`N_066`) to reuse the vocabulary they
   established for the shared helpers (`func_006F1EEC`, `func_003FBE4C`, `func_0063FD24`, …).

## Honest gaps
- Class names are roles, not recovered names. No RTTI strings exist in this binary for these
  classes, so `Battle2DUnit_*`, `Battle_Sequence_*`, `BattleUi_*` are descriptive.
- The 0x77F1DC / 0x77F34C windows: 0x5A58F4 animates four party-member layout parts, while
  0x5ADC54 scrolls text lines. I name them party-panel / message-window respectively, but the
  exact screen (battle HUD vs. battle message window) is not proven (0.40–0.45).
- The 2D-vs-3D distinction in the display helpers is inferred from `2d/battle2/*` asset paths and
  the mode byte at `(engine+0x48)+0x281 == 8`, not from a switch statement.
- `0x5BFB2E`/`0x5BFB32`/`0x5BFB36` are 4-byte Thumb entry points whose shared body Ghidra
  decompiled three times; the direction encoded by each entry was not extracted from the omitted
  switch table (0.30).
- `0x5C6E12`/`0x5C6E92` are Thumb functions with a lost prologue (`unaff_*` registers); their
  classification as the two draw passes of the 2D field scene is a best guess (0.35).
- Signatures are pseudo-C from the readable tree; parameter *counts* follow the observed register
  use, and `arg2`/`arg3` are kept where a parameter's meaning is unknown rather than invented.
