## Correction: the batch label "Camera" is wrong
Neither half of the range is a camera.
- **0x005CD44C–0x005D9C84** (previous worker): text span/glyph cursor helpers, the Ui object-list
  class, and the field-gimmick family. Kept as-is (see the cross-lane warning below).
- **0x005DA76C–0x005E4D04** — one large **UI-driven field gimmick** class: it owns a scene actor
  (`f_154C`, created with a 0x1468-byte actor descriptor), a selection range (`f_1550`/`f_1554`/
  `f_1558`, stepped by **2**, so it is a multi-column list), two Ui objects (`+0x1D7C` row list,
  `+0x1FDC` window), two effect handles (`f_1FE0`/`f_1FE4`), a 32-slot handle table and a
  per-part colour block (`f_AD1..f_AD6`). It arranges the members of an actor group
  (`Field_ActorGroup_PlaceMember`) in a **circle** around itself, spawns the `Bt_Nut` effect,
  plays `Run`, and lets the player step a selection list and talk to the selected member.
  The most likely identity is the **camp / "talk to a party member" gimmick** (camp layout names,
  `DirectTalkParty`), but the class name itself is not proven, so all names use the neutral
  `Field_Gimmick_*` vocabulary that the neighbouring lanes already established.
- **0x005E5190–0x005E8xxx** — scene-node / scene-object base class: show/hide, child-list fan-out
  (28 callers on `0x5E7598`), renderer release, world-position getters, `Model_GetNodeWorldPosition`.
- **0x005E94F0–0x005EAE28** — the **BGM sequence player**: seek, event pump, voice masks, stream
  slot allocation (proven by `Sound_SetVoiceGainByHandle`, `Sound_PlaySeById`, `Snd_RequestBgmStop`
  callers and the 0x18-byte event stride).
- **0x005F24A4–0x005F3AF0** — sprite pool/instance creation and the **trail/ribbon path follower**
  (recursive map-cell walk through `Map_FindCellInDirection*`).

## Honest gaps (not verified)
- **The owning class of the 0x5DA76C–0x5E4D04 gimmick is not proven.** Everything is described from
  behaviour (fields touched, callees, effect names, table slots). The "camp talk-select" reading is
  the best fit for the circle of party members + `win_camp_select%d` + `DirectTalkParty`, but no
  level-data or script reference ties the class to the camp map, so no name says "Camp".
- The 0x5DDA54 / 0x5DDD50 / 0x5DDF48 / 0x5E13D8 / 0x5E15D0 entries keep the previous worker's
  `UpdatePartsVariantA..E` labels. They are honest "one of several sibling per-part update
  variants" names, but a modder will not learn much from them; they are the weakest names in the
  file (0.40–0.42).
- `0x5E64E0` (`maybe_Field_GetLevelViewObject`, 0.35) — the getter is mechanically clear (level
  object at core+0x48 → handle → interface chain filtered by class tag 0x7C33D4), but the class
  tag lives in `.bss` and cannot be read, and the callers only call generic
  `slot(0x38/0x3C/0x40, smallId)` commands. "Level view" is deliberately vague.
- `0x5E812C`, `0x5E812C`'s return codes 6/7, `0x5E6590`'s two anchor triples, and `0x5E6D8C`'s item
  brackets are read from code, not from a table dump; the item-id interpretation of
  199–201/834–837 is inferred.
- **Cross-lane risk flagged by N_071**: N_071's report says the names given to 0x005C82E8–0x005D0800
  as `Font_GlyphSprite_*`/`Font_GlyphQuad_*` are contradicted by its call graph (2D field sprite
  actors). The first 66 entries here (written by the previous N_072 worker) name
  0x005CD44C–0x005CE5B0 as `Text_*`/`SpanCursor` from the vtable at 0x783B80 and the 6-byte
  (payload, type, count) span records. I re-read 0x5CE294 and 0x5CDF3C and the span-record reading
  is correct for those two, but **the 2D-field-vs-text ownership of 0x5CECBC–0x5D0800 is still
  disputed between lanes** and must be settled in M1 before merging names into symbols.
- 0x5F3AF0 and 0x5DB8A4 are Ghidra-damaged (bad-instruction data, unreachable blocks removed);
  their names come from the readable parts plus the map-trail call sequence.
- No Squirrel native binds any of these addresses (they are all internal), so script-level
  cross-checking was only possible indirectly via the camp script and layout names.
