# N_074 — native naming batch (150 functions)

**Status:** complete
**Output:** `orchestration/naming/out/N_074.json` (150 entries, batch order)
**Range:** `0x0060DC10`–`0x0062F5C8` (non-contiguous, 150 addresses)

## What the batch actually is

The batch header says **"Camera"**, but that is wrong for almost the whole range (the same
mislabel appears in every N_0xx header). What the 150 functions really are, in address order:

| Range | Content |
|---|---|
| `0x60DC10`–`0x60E2B4` | 2D sprite sets in a scene: scale/facing applied from an anim object, animation-slot assignment, per-level anim-track init, menu window-layout teardown |
| `0x60EA18`–`0x60EE9C` | 2D sprite object helpers: default 200×120 `"sprite"` mesh creation, scene-BGM trigger update, touch-event start, dtor |
| `0x60F0DC`–`0x610768` | **field level** runtime (`level3d.bxon` / `level2d.bxon`, NPC tables, pack/resource handles) plus the two embedded scene sprite groups and their preset (0xd4-stride) records |
| `0x610A94`–`0x6111A4` | a reference-counted **script-value hash map** (find/insert, resize, remove) and small UI-object ctor/dtor + Squirrel iterator/registry hooks |
| `0x612B90` | message-builder control-tag writer (tags 0x20f/0x210/0x211/0x213) |
| `0x617674`–`0x61BC4C` | field scene-object record copy, NPC action state machine / sight reaction, and the **UI overlay slot** family (sprite creation, ctor/dtor pairs, 12-state update machine, interact), plus the inn/time window pane binding |
| `0x61E7C4`–`0x6217E8` | sky/weather presets (cloud effect + packed RGBA), scene sprite-group release/update/remove (`%s_C/_V/_Y/_E`), the **map window** (`map`, `monster`, `nameplate`, `scroll1/2`, `null_icon_aplayer*`, `arrow_*`) |
| `0x6223D0`–`0x627480` | screen-view collections, scene-entry lists, shader pack load (`syscmn.pack`, `ChipShader.shbin`), UI scene-flow slot binding, list-window input/selection, smith-menu transition |
| `0x627610`–`0x629C78` | battle targeting (target search/validation, unit state 0x1c/0x29, status-mask counters) and actor command/model-part accessors |
| `0x62A7B8`–`0x62B69C` | balloon anchor positioning, model-handle lookup, named model parts (`_swingOff`, `_cape`, `_faceOff`) |
| `0x62B99C`–`0x62C988` | battle pose-group selection, visibility/confuse predicates, and the row/cell **hit-test** engine |
| `0x62CC78`–`0x62D930` | model-attachment world matrix, camera candidate visibility/bucketing |
| `0x62DF4C`–`0x62F5C8` | text layout, the scene's oriented-box / screen-rect point containment tests (five box sets + three rect sets), and the 2D-mode view-flag accessors |

**Why this matters for the merge:** the neighbouring lanes named `0x0061BEBC` `Font_SetGlyphTable`
and `0x0061CF58` `Font_ApplyGlyphMetrics`, but those functions actually set **sprite-slot distance
fade / render-slot parameters** (`Gfx_Sprite_SetDistanceFade`, slot table at `render+slot*0x40`,
fields `f_7c..f_b7`). Likewise `0x0061CA38` (`Font_Init`) and `0x0061FA60` (`Font_LoadFontSlots`)
are the sky/preset and sprite-slot initialisers used by this cluster. These older names should be
re-checked before M1 because they will mislead anyone reading the 0x61C000–0x61FC00 band as font
code; the strings around them are `sky_cloud`, `sky_ruin`, `sky_ruin_cloud`, `sky_zorude`, `sky_red`,
`sky_dark` (0x61DCF4–0x61DD30).

## Method

1. Read `README.md`, `orchestration/PLAN.md`; confirmed the lane had no prior output
   (`out/N_074.json` and `done/N_074.md` were both absent, no N_074 log entry).
2. Built a context harness in `%TEMP%/opencode/`:
   * name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all 70
     sibling `orchestration/naming/out/*.json`;
   * caller index over all 18,159 `decomp/readable/functions/*.c` files;
   * per-function digest (address, size, callers, callees with known names, body) for all 150;
   * raw-byte / string dumper over `original/exefs/code.decompressed.bin` (base `0x100000`) used to
     resolve every `g_0XXXXXXX` / `s_0XXXXXXX` literal pool and inline string.
3. Read the full body of all 150 functions, plus the decisive shared callees to avoid guessing:
   `0x006F1EEC` (app-context singleton), `0x0066A7D8` (view-mode/actor record lookup),
   `0x0066AA9C`/`0x0062AFBC`, `0x005736A0` (disassembled at `0x5736A0`: Vec3 normalise with
   fallback), `0x005F5818`/`0x005F5F54` (node colour/direction), `0x0062AB3C`
   (`Field_IsMap2D`: byte `+0x3d == 0xff`), `0x0061BEBC`/`0x0061CF58`/`0x0061CA38`/`0x0061FA60`
   (sprite-slot fade/preset init), `0x0062C260`/`0x0062C464`/`0x0062C988` (hit test), and the eight
   near-identical box/rect containment routines.
4. Worked bottom-up: pure getters/dtors/thunks first (7–20 bytes), then their callers, then the
   state machines and the 1–2 KB layout functions.
5. Naming: `Subsystem_VerbNoun` with the approved subsystem vocabulary
   (`Gfx_`, `Ui_`, `Field_`, `Field2D_`, `Camera_`, `Battle_`, `Actor_`, `Model_`, `Text_`,
   `Event_`, `Sound_`, `Menu_`, `Script_`, `Container_`, `Math_`). Where the sentence was "what it
   does" but not "which game feature owns it", the name is deliberately generic plus `maybe_`.
6. Validation (mechanical): JSON parses; 150/150 addresses, exactly once, in batch order; seven
   keys per object; every `signature` contains its own final name; 150 unique names; **zero name
   collisions** with the 10,979 existing project names (one draft `Field_SceneObject_Dtor` clashed
   with `0x00336B3C` and was renamed); every entry with `confidence < 0.5` is `maybe_`-prefixed.

## Open problems / not verified

* **Ownership of the `0x60F768`–`0x610768` cluster is not proven.** It clearly operates on two
  embedded sprite groups (`f_98`, `f_114`), a 4-slot child list at `+0x428c`, anim tracks at
  `+0x308+i*0x3c` and 0xd4-stride preset records; I named it `Gfx_SceneSpriteSet_*`. It may be the
  2D-mode character sprite set rather than a generic scene effect set. Confidences 0.40–0.60.
* **`0x60E2B4` (0.35)** is a teardown helper whose owning window is only reachable through
  `maybe_Menu_TeardownWindow`; `maybe_Menu_WindowLayout_Teardown` is a role name.
* **`0x62DA68` (0.45)** and `0x62D930` have Ghidra `halt_baddata` tails from unrecovered jump
  tables; the camera-candidate reading is supported by the callers
  (`maybe_Gfx_ComputeViewTransform`, `Camera_UpdateTargetList`) but the exact returned candidate is
  not verifiable from the C alone.
* **`0x62DF80`–`0x62EE68` (eight near-identical routines, 0.45–0.55)** — the oriented-box and
  screen-rect point tests are structurally certain (same quaternion transform + extent comparison),
  but *which* game feature each set belongs to (trigger areas vs. collision vs. occlusion) is
  inferred from the differing object-table offsets (`f_38c/f_3cc/f_42c/f_54c/f_5ac/f_60c/f_960`)
  and from their callers only.
* **`0x62F0CC / 0x62F17C / 0x62F5B4` (0.40)** are one-byte view-mode getters
  (`f_22`, `f_1b`, `f_21` of the record returned by `0x0066A7D8`). I could prove the field offsets
  and that callers treat them as booleans, not what each mode bit means, hence `maybe_Field2D_GetViewFlagNN`.
* **`0x62F5C8` (0.35)** decompiles to a bare `Field_IsMap2D` call with no visible write; it is
  named as a placeholder for the 2D-mode visual branch and should be revisited with assembly.
* **`0x6110DC`** is named `Script_Iterator_NextIndex` from the Squirrel delegate convention
  (`Sq_VmResumeCallable` caller, integer tag `0x5000002`); the exact delegate (`nexti` vs. custom
  iterator) is inferred.
* **`0x629AE4`** has inverted control flow in the decompile (four `!= -1` checks followed by an
  assert call); named `maybe_Ui_AssertHandleRecordValid` at 0.40.
* `0x60E2B4`, `0x61A450`, `0x61BA6C`, `0x623DF0`, `0x623FF8` have **no callers** (vtable/tail
  slots), so their names come from body shape and neighbouring siblings only.
* No emulator run, no build and no test suite (naming lane is exempt; no code or data was changed).
  Verification is therefore static + mechanical, not behavioural.
