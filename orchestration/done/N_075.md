## 2. Method

1. **Batch fill / metadata.** Parsed `N_075.txt` (address, size, readable-C path — all 150 files
   exist), plus `decomp/ghidra/functions_merged.jsonl` for the Ghidra signature.
2. **Name map.** Merged `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all
   57 sibling `out/N_*.json` into address → name (10,431 known names). Nothing in this batch was
   already named, but most callees above/below the range are, and those names propagate into the
   readable C.
3. **Caller index.** Scanned all 18,159 files under `decomp/readable/functions/` for
   `func_XXXXXXXX` tokens and inverted the relation, giving "who calls this address" for every entry.
   This is what made the band readable: 125 of the 150 have at least one external caller
   (659 caller edges in total), the rest are vtable-only or unused in this build.
4. **Vtable / pointer-table scan.** Read `original/exefs/code.decompressed.bin` (base `0x00100000`),
   searched every aligned word for each batch address, walked outward while entries stayed code
   pointers, and reported `(table, slot)`. Ten addresses are confirmed virtual methods
   (`0x62F7E4`, `0x630BD0`, `0x634028`, `0x634244`, `0x634264`, `0x64362C`, `0x64C6C0`, `0x64C754`,
   `0x64D2DC`, `0x64DCE0`); `0x630BD0` is the same inherited slot in ~90 UI class tables.
5. **Parallel deep reading.** The 150 bodies (195 KB of pseudo-C) were split into five 30-function
   slices; five analysis workers each did caller/callee/asm-level reading and wrote a draft JSON.
   I then merged, cross-checked and normalised (see §4) and spot-checked bodies myself.
6. **Bottom-up.** Leaf accessors/predicates first (`Party_*` list scans, `Ui_Part_*` visibility,
   `Casino_Slot_*` maths), then their users (`Menu_*` selection, `Ui_Overlay_*` placement,
   `Ui_TextLayout_*` row pickers).

## 3. Cross-cutting discoveries (worth reusing in other lanes)

* **The batch label "Camera" is wrong for the whole range.** The band is the shared party/actor-work
  layer, UI list/overlay/text-layout helpers, model/animation glue, field NPC balloon records and
  the casino slot/poker maths. Only three entries are genuinely camera-related
  (`Camera_GetHeadingAngle`, `Camera_FindMotionByName`, `maybe_Camera_IsModeSlotBusy`).
* **`0x006F1EEC` is the app-context singleton accessor** and `0x006F20C0` is `Game_GetWork()`.
  `ctx+0x5c` is the party/battle work: **4 slots, stride `0x1c`**, each with intrusive lists at
  `+0x4218` (generic), `+0x4254`, `+0x4260/+0x4264`, `+0x4270`, `+0x4280/+0x427c`, `+0x428c`,
  `+0x4298/+0x429c`. Nodes are actor/work objects with a vtable at `+0` and the **actor id at
  `+0x768`** (Ghidra prints `[0x1da]`). Vtable slots `+0x10`, `+0x18`, `+0x1c`, `+0x24`, `+0x34`,
  `+0x90` are the predicates used everywhere in this band. This pinned the ten `Party_*` entries.
* **`ctx+0x74` is the camera/view object**: quaternion at `+0x140..+0x14c`, mode byte `+0x6c`,
  mode→slot table at `+0x14..+0x24`. Proven twice independently (0x00641150 rotates stick input with
  it, 0x0063B368 reads its heading). Consequence: `0x0062F840` is an *actor* rotation accessor with a
  camera fallback, not a plain getter — renamed accordingly.
* **`0x0062AB3C` is the display-mode byte** (`*(u8*)(ctx+8)+0x3d`, `0xFF → 1`); it gates nearly every
  2D/3D branch in this band (asm `0x0062AB3C`).
* **`0x00630BD0` is an inherited `Ui_Window` virtual**, not a party helper: it is the same slot in
  ~90 UI class tables (`0x75B480` slot 2/11; `0x75CCB4`…`0x77F360` slot 5/14). Named
  `maybe_Ui_Window_IsMenuActorVisible` to reflect the class rather than the callee set.
* **Ghidra missed several function entries in this range.** `0x0063D178`, `0x0063DCA4`, `0x0063E5C8`,
  `0x0063D6B8` are real small routines (`bx lr`-terminated) that start right after a
  literal pool but were never split, so the readable calls to them are dead ends.
  **Recommendation: add these as functions in the Ghidra project and re-export** — they are table /
  record accessors used by dozens of UI functions.

## 5. Honest gaps (what is *not* verified)

* Class/feature names are **roles**, not recovered symbols — the game ships no RTTI strings. 104 of
  150 are therefore `maybe_`.
* **Weakest entries (< 0.40):** `0x0063207C` (party-portrait/sector picker inside the UI object
  factory — behaviour described, concept invented, 0.30), `0x00632AF0`/`0x00632BC4` (near-duplicate
  "warm-up" calls whose result is discarded, 0.30), `0x00648D9C` (row-marker overlay test, 0.32),
  `0x0064362C`/`0x0064C6C0`/`0x0064C754` (three `IsHandleStale` twins: polarity is certain from
  `0x000FFFFF` mask + `0x7BA2D0` table + `+0x78 < 4`, but what vtable slot 11 *means* is not, 0.30),
  `0x00635E1C` (Ghidra-split tail, no static callers, 0.32).
* The **nine `Field_Object_GetKindNRecord`** entries (`0x642984`–`0x642E9C`) prove the per-kind master
  tables but not the kind enum, so the numeric tag is kept instead of an invented name.
* `0x006337CC` resolves a handle to an object with quaternion/position/scale/index; I call it
  "Menu_Cursor" because its callers are cursor/panel handlers, but it may be a generic locator.
* The casino entries are named from the 24-stop × 5-reel table at `0x72AB4C`, wildcard symbol `6`,
  and the payout mapping 0/1/2 → ×1/×10/×100 reproduced at four call sites; the *intent* ("make the
  player lose/lose not") is inferred from the callers, not from strings.
* `0x0063D178`/`0x0063DCA4`/`0x0063E5C8`/`0x0063D6B8` have **no decompiled body** (Ghidra never
  split them); callees of that shape were read from `asm/text/text_00600048.s` only.
* Nothing was run: no emulator, no build, no `tests/run_all.py` (naming-lane exemption; no executable
  or asset was modified). Validation was mechanical — see
  `%TEMP%\opencode\n075\final_check.py` (JSON parses as strict ASCII, 150/150 in batch order, exact
  seven-key schema, name⊂signature, prefix/confidence rule, name charset, uniqueness, cross-batch and
  symbol collision scan) — **0 errors**.
