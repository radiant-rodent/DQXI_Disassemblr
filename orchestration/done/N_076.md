## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md` and the existing
   done/log entries for the neighbouring lanes (N_070, N_073, N_075, N_078) to match conventions.
2. Built a name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`,
   the readable file names and all sibling `out/N_*.json` (11,385 distinct names).
3. Built a caller/callee index over all 18,159 `decomp/readable/functions/*.c` files after
   stripping the generated comment header (otherwise every function "calls" itself).
4. Produced a per-function digest (signature, size, callers and callees annotated with the names
   other lanes proposed, string literals, whole body) and read all 9,363 lines of C in nine
   chunks, in batch/address order.
5. For the functions whose C is wrong or truncated, read `asm/text/text_00640048.s` and
   `text_0060048.s` (notably `0x0064E9CC`, whose float return Ghidra dropped, and the five
   `x6_()`-guarded handle checks).
6. Pulled the shared helpers the whole band depends on (`0x006F1EEC` context singleton,
   `0x006F1DF8` sound singleton, `0x0062AB3C` mode byte, `0x00669250` sub-state id,
   `0x006281C8` player/context gate, `0x00634418`/`0x0063451C` actor rotation/position,
   `0x001D4828`/`0x001D47F0` camera projection, `0x0063DCA4`-family record accessors) so the
   evidence strings name real mechanisms instead of `param_1`/`FUN_xxxx` where possible.

## Open problems / not verified

- **Fully static.** No emulator, no debugger, no playtest. The mechanical descriptions are solid
  (they follow the C and asm); the *purpose labels* are the uncertain part, which is why 57
  entries are `maybe_`.
- The "Camera" batch label is wrong; the names use the subsystem the code actually touches
  (`Ui_`, `Field_`, `Battle_`, `Script_`, `Font_`, `Input_`, …), not the header.
- Weakest entries (0.30–0.40), all `maybe_`:
  `0x0066B11C` (tail call into a non-returning guard/atexit routine),
  `0x0066FBA0` and `0x0066FC40` (Ghidra control flow broken / uninitialised registers),
  `0x00667EA4`, `0x006684FC`, `0x006685EC` (field-2D path / text-span cursor code with damaged
  bodies), `0x00666700` (8-code vtable probe with no semantic anchor),
  `0x0064E9CC` (float return recovered from asm; purpose of the two constants unknown),
  `0x0064FE10` / `0x0065225C` (placement searches; the consumer of the output record is unknown),
  and the five `x6_()`-guarded `maybe_Ui_CheckActorRefIdle*` twins.
- Four near-identical orientation helpers (`0x651590`, `0x654F54`, `0x65506C`, `0x6661BC`) are
  named `maybe_Camera_SetTargetOrientation*`; the mechanism (quaternion from two vectors into
  +0x48) is certain, that the owner is a camera is inferred from
  `0x001D4828`/`0x001D47F0`/`Camera_CalcStereoEyePositions` in the same band.
- Whether `0x0064F9B4`/`0x006515C4` are "sleep" masks for the monster-list UI or for battle
  targeting is not proven; the flag name `sleep_enemy_check` is the hard fact.
- `0x00659668` is a genuine bit-string decision tree; I called it a "resource trie" because
  ~35 resource/model descriptor call sites use it, but the payload type is not proven.
- `0x006D4EDC`–`0x006D5AF4` are grouped as message-voice line 0–4 handlers by line index and
  by the `Text_MeasureGlyphRun` use; whether they are spoken dialogue voices or the text
  "typing" stream is an inference.
