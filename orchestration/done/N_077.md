## What the batch actually is

The header label is **"Camera"**, which is wrong. There is no camera code in the range. It is a
link-order slice through five nearby modules plus a large slab of generic library code:

| Range | Content |
|---|---|

| `0x6E4618`–`0x6E4C68` | one small byte-string `push_back` and the three cell-box *placement area tests* (`Map`/`Field` placement search: descriptor predicate, placement-overlap test, grid hit test) |

## Method

1. Read `README.md` and `orchestration/PLAN.md`; confirmed the lane was empty
   (`out/N_077.json`, `done/N_077.md`, log entry and scratch were all absent).
2. Built a harness in `%TEMP%/opencode/n077/`:
   * name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all 69
     sibling `orchestration/naming/out/*.json`;
   * caller index over all 18,159 `decomp/readable/functions/*.c` files;
   * per-function digest (address, size, callers, named callees, resolved `g_`/`s_` literals, body);
   * a whole-image pointer scan that finds every reference to each batch address (both ARM and
     Thumb encodings) and prints ±4 words of context, which is what proved the method-table slots;
   * a raw ARM word dumper over `original/exefs/code.decompressed.bin` (base `0x100000`) used to
     settle every damaged/merged body and every literal constant.
3. Worked bottom-up: leaf getters/dtors/shuffles first, then tables, then the state machines.
4. Verified the decisive shared helpers instead of guessing, in particular:
   * `0x001001C4` / `0x001001FC` are the **vsnprintf / vswprintf front-ends** (they build the
     `[dst, dst+len)` range and call `std_vprintf_flags0` 0x002FF6AA / `std_vprintf_flags1`
     0x002FF6E6), which is what turned the 34 unknown `0x6F09xx`/`0x6F0Cxx`/`0x707Axx` functions into
     one string-format-constructor family. N_037's earlier name `maybe_std_ThrowNarrowRangeEx` for
     0x001001C4 is misleading and should be re-checked in M1;
   * `0x00387CA4` disassembles to a pure slot getter (`i == 0xFF ? self->[0xC4] : ((void**)self)[9+i]`),
     which explains the 25 generated menu stubs;
   * `0x006F245C` is the pad state (callers only read button bits at `+0xC` and stick floats at
     `+0x1C/+0x20`), so it is `Input_GetPadState`;
   * `svc #0x23` is `CloseHandle` (cross-checked with N_080's independent reading of the same
     immediate at `0x00106A4C`), fixing `0x6E75A0`;
   * the five 0x60-byte copies at `0x6E662C..0x6E688C` are slot 5 of five distinct class tables at
     `0x0076E3EC/…/0x0076E6CC` whose neighbours are `Field_SceneObject_Hide`,
     `Gfx_Node_ApplyTransformMatrix` and `0x005F7874`.

## Honest gaps / what is NOT verified

* Nothing was executed: no test suite, build, emulator or ROM run (naming-lane exemption; no code or
  data changed). Validation was mechanical (JSON/schema/order/uniqueness/prefix/ASCII/collision) plus
  static reading.
* The **win-line semantics of the casino slot block** are inferred: the row bases `+0x4D/+0x4E/+0x4F`
  and the reel start indices 1/2/3/4 are facts, but whether A/B/C are "top/middle/bottom" payline and
  D is a diagonal/V line is not proven, so the names use neutral A–D suffixes.
* The 25 `maybe_Ui_CheckMenuSlotNN` stubs are proven one-liners (fetch `gameWork->ctx->+0x7C`, read
  pointer-array slot N, discard the result); their *purpose* is not proven — they look like generated
  assert/probe stubs, and the manager at `+0x7C` is only identified as "the menu/screen manager".
* The 34 string-format constructors: the class word written at `+0` points into `.bss` (zero in the
  image), so the class identity could not be recovered; "format constructor with inline capacity"
  is what the code proves, nothing more. All are `maybe_`.
* `0x6E524A`, `0x6E540A`, `0x6E568E`, `0x6E5CCA`, `0x6E5F4E`, `0x6E61DE`, `0x6E6404`, `0x6E6466`
  are Ghidra-damaged (Thumb with lost argument registers, or two neighbours merged); each is named
  from the surviving call pattern only.
* `0x6E4900/0x6E4ACC/0x6E4C68` are "test a w×h cell box" beyond doubt, but which UI/game feature
  owns each variant comes from the (themselves `maybe_`) caller names of other lanes.
* `0x6F1D50` is named `maybe_Ui_GetSceneTransitionManager` because the scene-flow state machine
  blocks on its `+0xC..` counter and message-window closes call it; the class name is a role, not a
  recovered symbol.
* `0x6E6C10` is confirmed only as far as "effect path twin of `0x6E6924`" (it calls
  `Gfx_EffectObject_Replace` instead of `Ui_ItemModel_Load`); the 200x120 billboard descriptor
  fields (`f_38/f_3a/f_3c/f_40`) are read from the code but their meaning is inferred from the
  values (200 × 0x78).
* Two ordering-guess names (`Casino_Slot_EvaluateWinLineC/D` at 0.5) sit exactly at the threshold;
  they are structural twins of the 0.5 entry A, so they inherit its confidence rather than a new
  measurement.
