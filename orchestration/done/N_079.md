# N_079 — Kernel_and_System naming batch (83 functions) — DONE

Task: name and document the 83 native functions listed in `orchestration/naming/batches/N_079.txt`
(labelled "Kernel_and_System").

## What existed before

Nothing. The lane was marked `RUNNING` in `orchestration/state.json`, but
`orchestration/naming/out/N_079.json`, `orchestration/done/N_079.md`, an N_079 entry in
`AGENT_LOG.md` and any scratch files were all absent, and no sibling `out/N_*.json` named any of
the 83 addresses (checked with a full cross-batch scan). So all 83 entries were produced from
scratch, bottom-up, in batch order.

## What I did

Method (all read-only, no code or data changed):

1. **Name map** from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all
   78 sibling `orchestration/naming/out/N_*.json` (~11k names). `N_014.json` is still not valid
   UTF-8 and was read with `errors='replace'`.
2. **Caller index** over all 18,159 `decomp/readable/functions/*.c` in one pass (the generated
   header comment is what makes a file "call itself", so the owning file is excluded).
3. **Literal-pool dereference** straight out of `original/exefs/code.decompressed.bin`
   (base 0x00100000) for every `g_XXXX` a body touches: that is how the service-name strings
   (`srv:`, `dsp::DSP`, `ir:USER`), the vtable pointers and the IPC header words were recovered.
   Note the binary is 0x6C3000 bytes, so any `g_` address >= 0x007C3000 is `.bss` and reads as
   empty - several Ghidra `g_` symbols are simply unreadable.
4. **Whole-image pointer scan** for the addresses with no callers, which proved that
   `0x00249E14 / 0x0024CBFC / 0x0024F1D0 / 0x0024FBE8 / 0x00251604 / 0x002518E8 / 0x002537C0`
   are slots of the class-registration table at 0x00253EF8 / 0x002555E0 and that
   `0x0011CC30` is a thread entry point.
5. **Raw assembly** (`asm/text/text_00100048.s`, `text_00240048.s`) wherever Ghidra's C was wrong.
   This mattered a lot:
   - `0x00106F70` is 0x24 bytes with a *tail branch* to 0x0010BDB0(0x03000000); the readable C
     inlines the callee and is misleading.
   - `0x0024C6B8` falls through into `0x0024CBFC` in the C; the disassembly shows it is a
     complete, byte-identical twin of `0x00250A38`.
   - `0x0011CC30` spans four *different* small library routines (thread trampoline tail,
     svcGetThreadId, svcSleepThread, strlen); only the first belongs to the batch address.
   - `svc` immediates: 0x09 ExitThread, 0x23 CloseHandle, 0x24 WaitSynchronization1, 0x32
     SendSyncRequest, 0x35 GetThreadId.
6. **Cross-check with the game scripts**, which is what fixed the two weakest game-side entries:
   `game_assets/scripts/packs/script/base/script.decompiled.nut` contains
   `for (frame = 0; EncountEventEx(battleID, false, frame) == false; ++frame)` - that loop is the
   definition of `Battle_UpdateEncounterTransition` (0x0015DCF0), and the same file names
   `RegistSubThread("g_sub_event", func)` for 0x00250A38.
7. **Cross-check with sibling batches** for shared helpers: `0x006F1DF8` = Sound_GetPlayer and
   `0x006F1EEC` = Os_GetGameWork (N_077), `0x006F229C` = Ui_GetCore (N_021),
   `0x0010EAB0` = Gfx_CommandBuffer_Submit (N_080), `0x005B9B90`/`0x005B3668` = Sq_VmNewSlot/
   Sq_VmGetSlot (N_071). Where my vocabulary touches theirs I used theirs (`Sq_Vm*`).

## What the range actually is

The batch header says "Kernel_and_System", which is only right for the first third.

| Range | What it is |
|---|---|
| 0x00100BA0 | CRT pre-initialiser array runner (ResetVector's 5th call) |
| 0x001027EC | second, absolute-pointer init array runner (empty in retail) |
| 0x00102874–0x00104400 | boot heap: create main heap, reset allocator state, grow/shrink the committed linear block through svcControlMemory, commit the free region |
| 0x00106EC8–0x00113420 | SDK memory-manager/session boot: cache the boot parameter, measure the free FCRAM window [0x0E000000,top), set the 48 MB (0x03000000) heap, open the `srv:` client with a retry loop, map the shared block through IPC |
| 0x0010C738–0x0011E0DC | the SDK audio layer: global sound state, DSP session open/close, the 0x00010040 / 0x00020080 / 0x00550040 IPC commands, mixing-unit and voice resets, fixed-block pools, archive loading through a reader, TLS |
| 0x00117E50 / 0x00118454 / 0x00118A88 / 0x0011CC30 | generic OS primitives used by the whole game: recursive critical section, one-shot init, block pool, thread entry |
| 0x0015DCF0 / 0x001F3604 / 0x001F39BC | the battle-encounter transition and its sound selection |
| 0x002496A0–0x002537C0 | the eight Squirrel native registration tables plus the two script-thread registrars |
| 0x004FC3E8–0x00549A70 | graphics command pool and the sound voice/stream/player objects |
| 0x00579D98–0x006BE448 | the Squirrel VM object/table layer and the class binder everything else calls |

The single most useful fact recovered: **0x006BC528 is the one native binder**
(`Sq_BindNativeMethod`), and the eight big functions in 0x0024xxxx–0x0025xxxx are its callers,
one per script class, with the script-visible method names present as string literals. That turns
~250 lines of opaque `func_006BC528(...)` into readable per-class API lists.

## Honest gaps — what is NOT verified

- **Fully static.** No emulator, debugger or playtest was run. Every *mechanism* claim (which
  function calls what, which `svc` reaches the kernel, which literal is loaded) is read from the
  bytes; every *purpose* label is inference.
- **The exact SDK library for 0x0010B000–0x0011FFFF is not proven.** The region contains both
  `dsp::DSP` client code (0x00107024 opens that service at 0x0072FBC0) and generic nn::os
  primitives that 100+ non-audio call sites use (0x00117E50 has 141 callers). I therefore used
  `Snd_` only where the call graph is audio and `Os_` for the primitives, and said so in each
  entry rather than pretending to know the link order.
- **11 entries are mechanism-only**: `Os_IpcCommand2`, `Os_IpcSend2Get2`,
  `Os_IpcSendGetHandle`, `maybe_Os_IpcSendByte`, `maybe_Os_SendServiceInitRequest`,
  `maybe_Os_IpcServiceInitWithHandle`, `Os_EnsureIpcSessionOpen`, `Os_CloseIpcSession`,
  `maybe_Os_WaitSharedBlock`, `maybe_Os_LookupParamEntry`, `maybe_Os_ScanParamBlocks`. The IPC
  header word, the svc and the data flow are certain in each; the service they talk to and the
  meaning of the records are not. `maybe_Os_LookupParamEntry` / `maybe_Os_ScanParamBlocks` describe a
  12-bit/12-bit centre pair with a 1.0f scale that *looks* like a calibration record, but the
  consumer is not visible anywhere in the batch.
- **`0x001114F4` / `0x00111C58` / `0x00111C72`** are one archive loader with a 0x28-byte header and
  0x20/0x18-byte record pools. Calling it "sound archive" is the weakest link in the whole batch
  (0.35/0.30/0.25). It is also the code Ghidra could only partially attribute (unaff registers),
  so two of the three names are deliberately "tail" names.
- **The six `maybe_Sys_RegisterGlobal_*` entries (0x00677E64 … 0x006959E0)** have no callers and
  no strings. They are provably "clear a global, initialise its critical section, publish a
  pointer", and they are provably a family, but I could not tell what each one serves, so the
  names carry the global address instead of an invented subsystem.
- **`0x0024C6B8`** is named from its caller (`RegistThread`) plus its twin (`0x00250A38`), because
  Ghidra's decompilation of it runs into the next function. Confidence 0.50 exactly.
- `0x0015DCF0`'s object layout (0x1348 bytes, fields at +0x119C/+0x11A0) is only partly understood:
  the frame timings are proven by the script loop, the *visual* effect is not.
