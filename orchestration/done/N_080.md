# N_080 — Memory_and_Heaps (0x001002F8–0x0010EC14), 150 functions

## What existed before this resume

Nothing. `orchestration/naming/out/N_080.json`, `orchestration/done/N_080.md`, an N_080
`AGENT_LOG.md` entry and any attributable scratch files were all absent, and no sibling
`out/N_*.json` named one of the 150 addresses. All 150 entries were produced from scratch.

## What the range really is

The batch label "Memory_and_Heaps" is only partly right. The range 0x1002F8–0x10EC14 is
the engine's **low-level runtime block**, in this order:

1. **0x1002F8–0x101AA0 — newlib/libc.**
   printf integer/hex/octal/special-float formatters and the narrow/wide/multibyte string
   emitters of the same printf core (`FormatStream` with putc callback at +4, width at +0x18,
   count at +0x20, precision at +0x1C), `mbrlen`/`mbrtowc`, `wcsncat`, and the `inf`/`nan`
   parser used by `strtod`. Cross-checked against the already-named siblings
   `std_PrintfFormatInt` (0x1003F8), `std_PrintfFormatFloat` (0x300090),
   `maybe_std_FormatSinkPutString` (0x100FB4), `std_mbrtowc`-adjacent helpers and
   `std_Utf16CompareN` (0x100AD6) in N_001/N_037.

2. **0x101B74–0x104520 — engine bring-up and the streaming-resource cache.**
   `0x101B74` is the one-shot initialiser (no callers; only caller of `InitHeaps`). It creates
   every global singleton with the repeated *flag + aligned size + allocate + construct*
   pattern. `0x103724` is the best-proven function of the batch: its inline literals are the
   cache category names `sound`, `cmn_cache`, `weapon`, `PL_256`, `PL_400`, `F_PLmotion`,
   `F_Cache`, `Cache1/2`, `B_PLsound`, `B_PLmotion`, `B_ENsound`, `B_ENmodel`, `B_ENmotion`,
   followed by the 16 registered table names `Common`, `ModeCmn`, `CacheCmn`, `Weapon`,
   `FldPlayer`, `BtlPlayer`, `BtlEnmMdl`, `BtlEnmMot`, `BtlPSound`, `BtlESound`, `Field`,
   `UICmn`, `UI`, `SoundCmn`, `TempSct`, `Fails`. Slot pools are the 0x58-byte and 0x54-byte
   record arrays built by 0x108574/0x108624/0x1086CC/0x108750/0x1087F4.

3. **0x104A38–0x10AE64 — Gfx display / framebuffer / GPU-context bring-up and present.**
   Screen geometry 400x240 and 320x240 (0x140), 0x400 line stride, 0xF0 rows,
   `svc 0x28` (ClearEvent) frame events, 0x1000-byte command buffers at base/base+0x2000,
   and the huge GPU-state initialiser 0x109FB0 with its register/value pairs (0x1C2/0xD1/
   0x1C1/0x92...). Verified `svc 0x23` = CloseHandle, `0x24` = WaitSynchronization1,
   `0x28` = ClearEvent, `0x32` = SendSyncRequest directly in `asm/text/text_00100048.s`
   (lines for 0x106A4C, 0x105704, 0x104CD4, 0x107820).

4. **0x10673C–0x109E88 — OS primitives, sync, mount table, input.**
   `SequenceTask` task ctor, 32-entry `name:` mount table (0x106BFC unmount / 0x10B6D4 mount),
   reentrant lock via TPIDRURO, svc-0x32 IPC stubs, and the pad/touch readers
   (`0x10C2D4` derives `(new^old)&~old` pressed and `old&~new` released masks — a hard fact).

5. **0x109E28–0x10EC14 — Gfx channel/transfer buffers, display-mode negotiation, IPC helpers,
   and the two container/allocator core routines** `Mem_Heap_FindFreeBlock` (0x10E78C,
   free-list first-fit with split) and `std_RbTree_EraseNode` (0x10EC14, transplant +
   rebalance callback, 92 callers from the project's maps/sets).

## Method

- Name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all
  70 other `orchestration/naming/out/N_*.json` (N_014.json is not valid UTF-8; decoded with
  `errors='replace'` when needed for collision checks).
- Caller index over all 18,748 `decomp/readable/{functions,recovered}/*.c`.
- Full read of all 150 bodies (39,802 bytes of ARM) plus the key callees
  (`0x2FF71C/0x2FF748/0x2FF7C4/0x2FF9D0`, `0x100050`, `0x10E540`, `0x10E78C`, `0x10EC14`,
  `0x56C5D4/0x56D028/0x56D8C4`, `0x6C2EE8/0x6C310C`).
- Literal-pool dereference from `original/exefs/code.decompressed.bin` (base 0x100000) to
  resolve every vtable claim used in the evidence, e.g. 0x10B504 -> 0x75A79C whose slots are
  the 0x6C2EE8 timeline object, and 0x108620/0x1086C8/0x10874C/0x1087F0 -> the 0x78230C/
  0x78236C/0x78239C slot-pool classes (0x56C5xx / 0x56D0xx / 0x56D8xx).
- `svc` immediates read from `asm/text/text_00100048.s`, not guessed.
- Batch order preserved; 150/150 addresses, exactly once.

## Result

- 150 entries, exactly the required seven keys, in batch order.
- Confidence 0.30–0.82, mean 0.492; exactly the 75 entries below 0.50 carry `maybe_`, and no
  entry at >= 0.50 carries it.
- 150 unique names; zero collisions with the other 70 `out/N_*.json`, `symbols.json`,
  `symbols_recovered.json` or `decomp/native_names.json` (readable set, N_014 excluded).
- ASCII-only text, no control characters, every signature contains its own name and every
  `params` value appears in its signature.
- Highest-confidence entries: `Fs_CacheSet_Initialize` 0.78, `std_mbrtowc` 0.75,
  `std_wcsncat` 0.82, `std_PrintfFormatHex64`/`Octal64` 0.72, `Mem_Heap_FindFreeBlock` 0.72,
  `Gfx_InitializeContext` 0.68, `Container_NameMap_Find` 0.68, `Fs_UnmountByName` 0.62.

## Honest gaps / open problems

- **No dynamic verification.** No emulator, debugger or ROM run was used; every claim is
  static (body shape, literals, call graph, vtable slots).
- The Fs-vs-Gfx boundary between 0x104A38 and 0x10AE64 is not fully proven: the same block
  contains framebuffer copies (0x400x0xF0), GPU command buffers (0x1000) and DSP-shaped
  96000/0x12C00 buffers. 0x104A38 is named `Gfx_Display_Initialize` (0.55) on the strength of
  the 0x200x0x200 / 0x100x0x200 target descriptors and the present routine; it could be a
  combined display+audio device init.
- `0x101B74` is named `Engine_Initialize` (0.50) because it spans Fs, Gfx, sound and tasks;
  the exact entry name from the original SDK (`nnMain`/framework init) is not recovered.
- The 0x1069xx–0x1076xx block is a **synchronisation/IPC** family whose *users* are not
  proven: `Os_InitSyncPrimitives`/`Os_WaitSyncObject`/`maybe_Snd_Initialize` are named from
  the svc calls, event handles and the 0x102904 call order, not from a service-name string.
- `0x108C5C` (input manager) and `0x108F64` (voice list) are the weakest mid-range entries;
  their bodies mix pad tables (0x10E8D0) with sound-queue helpers (0x1166B4).
- 23 entries are Ghidra-damaged (`unaff_r*`, `halt_baddata`, `_Reset/_IRQ` resolving to CPU
  vectors, "Could not recover jumptable"): 0x1053D0-adjacent 0x104430 body is fine, but
  0x108C5C/0x108F22/0x10C574/0x10CF50/0x10EAB0 have lost arguments or branches. They carry
  0.35–0.55 and `maybe_` where below 0.5.
- `0x102828`, `0x105238`, `0x105280` depend on data blobs inside `.text` (literal pool), so the
  actual strings could not be printed; they are described as "constant-string getters".
- The 0x10B2C4 class is proven structural (12-state 0x18-byte timeline with callbacks and a
  106-caller base ctor) but its *game-level* name (sprite anim? action sequence? effect)
  is a role name: `Anim_Sequence_CtorBase` at 0.50.

   structures at g_0010DCD0/g_0010DD14/g_0010DD50/g_0010DDC4 and matches the command ids
   (0x11, 0x62, 0x99, 0x200/0x400 capability queries) against 3dbrew service docs; that would
   promote ~25 `Svc_*`/`Gfx_*` entries here from 0.4 to 0.7.
2. Read the 0x78xxxx literal-pool tables for 0x108620/0x1086C8/0x10874C/0x1087F0 and the
   matching 0x56C5xx/0x56D0xx class methods, to settle whether the 0x58/0x54 record pools are
   file caches, texture caches or animation caches.
3. Recover the true entry point/name of 0x101B74 from `asm/start.s`/`asm/init.s` and the CRT
   init arrays, and confirm the `Engine_Initialize` ordering.

   entries: `0x2FF71C`, `0x2FF748`, `0x2FF7C4`, `0x2FF9D0`, `0x116AE0`, `0x11FE8C`,
   `0x11CFAC`, `0x1064D4`, `0x10F6CC`, `0x10F6EC`, `0x10E780`, `0x10E8D0`, `0x111F60`,
