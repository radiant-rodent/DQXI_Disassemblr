## What this batch actually is

The auto-generated label "Memory_and_Heaps" is misleading. The range is one contiguous
stretch of the game's linked-in low-level runtime, in this order:

1. `0x10EE9C`–`0x115290` — libstdc++ red-black tree (std::map/std::set) insertion, rebalance
   and erase-fixup, plus a few small container helpers and the game's own keyed lookup.
2. `0x10F6EC`–`0x117458` — the **GPU command-list driver** (custom XTV-style renderer on top
   of the 3DS PICA200/GSP): aligned heap allocator, pipeline-state block, command lists,
   ring buffer, VBlank handlers, GPU register writes and the GSP IPC client stubs.
3. `0x117B78`–`0x119E1C` — kernel synchronisation (semaphores/locks built on
   `ldrex/strex` + `svcArbitrateAddress` 0x11CC10), scheduler lock/unlock and the GSP
   session open/close helpers.
4. `0x1198DC`–`0x11B534` — GPU buffer read/write + event-wait loops and the **HID/circle-pad**
   helpers (dead-zone, axis normalisation, calibration, vibration) around the documented
   pad reader at `0x11AD3C`.
5. `0x11BC44`–`0x11FAA4` — default GPU register state, texture-binding updates, memmove
   backward path, and the remaining service IPC stubs (gsp::Gpu and one per-object service)
   plus texture-command builders and session finalisation.

## Method (and what was actually verified)

- Read all 150 readable-C files (plus the ARM disassembly for every ambiguous one, using
  capstone 5.0.7 against `original/exefs/code.decompressed.bin`, base `0x00100000`).
- Built a caller index over all 18,748 `decomp/readable/**/*.c` files, including the
  `func_0x...` spelling that the first pass missed; used caller clusters (e.g. the 28
  map/set insert sites of `0x10EE9C`, the 63 callers of the allocator `0x10F6EC`) to
  place functions in a subsystem before naming them.
- Resolved literal-pool constants for every IPC stub: command header (cmd id + normal /
  translate parameter counts) and the session handle it uses. All hard-wired stubs load
  the handle from `0x007AF0D8`; `0x00010082` (= GSPGPU WriteHWRegs) on that handle plus
  the framebuffer/VBlank/PICA200 context identifies it as the **gsp::Gpu** session.
  The `srv:` stub (`0x113554`) uses a different handle (`0x007AF900`) and the `srv:` name
  string at `0x00741AD8`.
- Used the cross-references in rodata (`gsp::Lcd`, `gsp::Gpu` at `0x0078C48C`/`0x0078C495`,
  `hid:NFC/QTM/USER/SPVR` at `0x00789E5D`–`0x00789E76`, `srv:`, `fs:LDR`, `fs:USER`) only as
  corroboration; the batch's own functions reference the service handles, not these strings.
- Worked bottom-up: leaf allocator/semaphore/memmove/RB-tree/strncpy helpers first, then
  the command-list, VBlank and IPC callers using those names.

## Open problems / honest gaps

1. **Bad Ghidra seeds (4 entries).** `0x1149AA`, `0x114B12`, `0x11AC6E`, `0x11B22A` are not
   real function starts (capstone decodes garbage from those addresses; `functions_index`
   disagrees with the bytes). They are documented placeholders at 0.25–0.30, not real names.
   `0x11B7EC` is a valid 0x54-byte routine that Ghidra marked `covered_by`.
2. **`0x114AB4`** is valid ARM that Ghidra failed to decompile ("bad instruction data");
   named `maybe_Gfx_CommandListWorker` (0.35) from the surviving instruction pattern only.
3. **Service identity of the per-object stubs.** The `0x11EA7C`–`0x11EC7C` family takes a
   session pointer from an object rather than the fixed `0x007AF0D8` handle. It sits next to
   the GPU interrupt-relay code and next to the HID calibration code, so I deliberately used
   the neutral `maybe_Svc_IpcCmd<header>` instead of inventing `Hid_`/`Gfx_`.
4. **Names with no callers.** ~30 entries have zero callers in `decomp/readable` (vtables,
   init tables, inline-only, or truly unused SDK code). Their roles come from structure and
   neighbours, hence 0.3–0.5.
5. **`0x11233C` "finalizers"** and **`0x119E1C` "scheduler unlock"**: the eight-callback
   table and the svc 0x14/0x23 pair are clear, but the owning module is not proven.
6. **N_080 is still missing.** The sibling batch for `0x001002F8`–`0x0010EE9C` (same
   "Memory_and_Heaps" label, the CRT/libc/input first half of this runtime) has no
   `out/N_080.json`. Several shared helpers used here (`0x116AE0` memset, `0x100050` memcpy,
   `0x11CCA0` strlen, `0x11CFAC` unsigned divide, `0x11CD80` signed divide, `0x11ED40`
   assert, `0x118100` panic) live in that gap and would be named there.
