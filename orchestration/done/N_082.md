## Method

1. Name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all
   77 sibling `out/N_*.json` (11,553 address->name pairs).
2. Caller index built over all 18,159 `decomp/readable/functions|recovered/*.c` files, so each
   function was read with its callers and callees annotated with other lanes' proposed names.
3. Literal-string dump from `original/exefs/code.decompressed.bin` (base `0x00100000`) for every
   inline-string claim. This is where `"opend_line"`/`"reset"` (0x1B9F94/0x1B9FA0),
   `"win_mode"` (0x2F76C8) and `"menu_present_list"`/`"win_talk"`/`"win_yesno"`/
   `"null_menu_present"` (0x3B02A4..0x3B02D0) came from.
4. `asm/text/text_00100048.s` (and the neighbouring listings) for the SDK stubs and for the
   bodies Ghidra damaged.
5. Bottom-up: the low-level helpers were pinned first and then used to read their callers:
   `0x116AE0` = bzero/memset, `0x11CD80`/`0x11CFAC` = unsigned division, `0x11FFC4` = word copy,
   `0x10EC00`/`0x10EC14` = std::string dispose, `0x10F6CC` = block free, `0x10EBE4` = list unlink,
   `0x115358`/`0x115390` = tree iterator, `0x1EBC68` = `Sound_PlaySeById` (N_042).

The single most useful fact for this batch: on the 3DS, **`svc #0x32` is
`svcSendSyncRequest`**, the request header lives at `TPIDRURO+0x80`
(`cmd<<16 | normal<<6 | translate`) and the service handle is in `r0`. That turns
`0x11FB18/0x11FB90/0x124C64/0x12412C/0x124CA0` from "unknown svc wrappers" into concrete IPC
commands 0x3D, 0x13, 0x06 and 0x0C, and it matches N_079's independently derived reading of the
same idiom in the `0x0010Dxxx` band (whose `Os_IpcSend*` vocabulary I adopted for consistency).

Two cross-checks with sibling lanes that raise confidence for the whole band:
`0x00116AE0`=memset / `0x0011CCA0`=strlen were also concluded by N_079, and `0x1EBC68` was named
`Sound_PlaySeById` by N_042.

## Highest-confidence findings (worth carrying into M1)

- `0x002CDB84`/`0x002CDE6C` are **Fs-result classifiers**: bit 31 set, module `0x4400`, code
  ranges 100..179 / 199..219 / `g_2CDC40`..399 map to status 1/2/3, everything else goes through
  the fatal reporter `0x11ED40`. Every save-file write validates through them.
- Save layout: four slots of 0xA8 bytes at game work `+0xE1C0`, slot states 1..4, global save
  state at `+0xE3C0`, load-active byte `+0xE3C5`, load mode `+0xE3C4` (0/3/4/6/7); the write path
  is `0x2CCC50`/`0x2CD02C`/`0x2CD948` + `0x2CDB84`, and the save-slot UI rows are built by
  `0x45D980`/`0x45DCF8` from `+0xE120/+0xE1C8/+0xE270`.
- `0x2D2xxx-0x2D57xx` is the **2D overlay/framebuffer layer** (400x240 top, 0x140x0xF0 bottom,
  two drawing passes, priority-sorted lists); N_014's `maybe_Gfx_Overlay_BeginDraw` (0x2D2D9C)
  is its entry point, and this batch supplies its draw/end/sort helpers.
- The printf engine at `0x2FF71C-0x2FF9D0` (Thumb) is the integer/pad/dispatch half of the
  `std_Printf*` family that N_001/N_037/N_051 called; names now share the `std_Format_` prefix.
- `0x00123360` is a proper lock-free queue push: 8-word messages, 15-slot ring (index in bits
  8..15 wrapping modulo 15), LDREX/STREX publish, wake through `0x11F730`+`0x12412C`.

## Honest gaps / what is NOT verified

- Fully static. No emulator, debugger or playtest; every description is read from bytes. The
  *mechanism* wording is factual, the *purpose* labels are inference.
- The SDK service behind the IPC commands 0x06/0x0C/0x13/0x3D is **not identified**; the entry
  names therefore keep the raw command id. Those five entries sit at 0.45.
- `maybe_Os_PerfSample_Loop` (0x122484), `maybe_Os_RecordReadWithRetry` (0x122650),
  `maybe_Os_Timer_ConvertTicks` (0x1237A0) and `maybe_Os_SyncObject_Init` (0x1D0134) are the
  weakest mechanism readings in the first cluster (0.30-0.40): the instruction-level facts are
  solid (TLS layout, svc numbers, 1e6 us constant, /1000 magic, 0x1000/0x10 init) but what the
  SDK uses them for is not proven.
- Save-task *state numbers* are mechanical: which of states 1..5 means "opened", "written" or
  "verified" is inferred from call order, not from a script or table dump.
- The UI classes have no RTTI; destructors are named by their field layout
  (`*_DtorStringAndLists`, `*_DtorPooledA/B`, `*_DtorStringListA/B/C`). These are honest but
  not pretty; M1 may prefer to unify them once the owning panels are named.
- Ghidra-damaged bodies: `0x2CC834` (lost prologue), `0x2D3C1C` and `0x2CF070` (bad instruction
  / truncated), `0x340C60` and `0x30B628`/`0x30B5F4` (read as Thumb; the 0x30B628 body is a
  duplicate of the ARM row builder), `0x411FC0` (only the string dispose survives). Their names
  stay at 0.30-0.40.
- `0x004217D0` (battle unit view update) has no callers in the readable tree, so its class is
  inferred from the `f_274` unit view and the `0x6400B4` expression table; 0.40.
- I did **not** run `tests/run_all.py`/`verify_project.py`: this lane changes no code or data
  (task's own exemption), and the only files touched are the out JSON, this report and
  `AGENT_LOG.md`.
