## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`, then built a
   name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all 77
   sibling `orchestration/naming/out/N_*.json`.
2. Built a caller index by scanning all 18,159 `decomp/readable/functions/*.c` for
   `func_xxxxxxxx` references, then dumped a per-function digest (address, size, annotated
   callers/callees, globals, body) to a text file and read it in chunks.
3. Worked bottom-up: first identified the shared low-level helpers, then used them to read the
   callers. The most valuable identifications were:
   - `0x0010EC00`/`0x0010EC14` = libstdc++ red-black-tree successor + erase-rebalance,
     `0x0010F6CC` = refcounted object release. That single pattern explains ~12 destructors here.
   - `0x00116AE0` = memset, `0x00116A14` = memcpy, `0x0011CFAC` = align-up, `0x0011FE8C` = align.
   - `0x006F202C`/`0x006F2394` = lazily created engine singletons; `0x00505A58` and
     `0x51C9EC`–`0x51CB94` = `svcSendSyncRequest` (svc 0x32) wrappers; `svc 0x23` = CloseHandle.
4. Resolved data pointers against `original/exefs/code.decompressed.bin` (base `0x00100000`).
   This proved the NG-word service name **`ngword:`** (`g_00514ab8`, `g_005150b0`) and the
   `%s:%s` stream path format, rather than guessing them.
5. Cross-checked every name against all existing names to avoid vocabulary collisions; one
   initial `Os_CloseHandleIfOpen` was renamed to `maybe_Svc_CloseHandleSlot` because
   `0x00106A38` already carries that name.
6. `params` is generated mechanically: for each entry the original Ghidra parameter names
   (`arg1`, `arg2`, `self`, …) are mapped positionally to the descriptive names used in the
   signature, so the mapping is trustworthy rather than hand-written.

## Honest gaps / what is NOT verified

- Completely static: no emulator run, no debugger, no playtest. The **mechanisms** (which
  vtable/handle/field is touched) are read from the decompiled bodies and are reliable; the
  **purpose labels** are the inference and that is where the `maybe_` entries sit.
- The big `0x56` cluster is one model renderer split into ~20 passes. The GPU state words were
  not resolved to PICA200 register names, so pass names like `DrawShadowPass`,
  `DrawEdgePass`, `DrawFogPass` are informed guesses (0.35–0.45). What is certain is which
  sibling pass each one calls and that each builds a GX state block + appends vertex data.
- `0x4FD264`, `0x4FED58`, `0x4FFB64`, `0x4FFDEC` are named from the movie state machine's call
  order (`self->f_c` states 1/3/7/8); the exact semantic of each state number is not proven.
- `0x5E7D84`/`0x5E7D74` (slot-handle destroy) and `0x5EB3D4`/`0x5EBA14`/`0x5EBBA8` (stream
  pools) are named from their allocator/list mechanism; whether the pools hold packets, voices
  or file chunks is not proven.
- `0x50DCB0` (icon-cache flush) and `0x504DB4`/`0x504F0C` (resource-name split) are 0.40: the
  call pattern is clear but the exact service contract is not.
- Ghidra damaged several bodies (`halt_baddata`, lost `unaff_*` registers, truncated jumps):
  `0x518154`, `0x51D25C`, `0x56149E`, `0x569D0C`, `0x5EA54C/0x5EAC38`. Their names are
  conservative and the summaries say so.
- No emulator/3DS verification of any behaviour, and no merge into `symbols.json` (M1 owns that).
