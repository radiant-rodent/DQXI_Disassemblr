# N_084 — Memory_and_Heaps (88 functions) — done report

**Status:** completed (naming lane; no code or data changed)
**Output:** `orchestration/naming/out/N_084.json` — 88 objects, batch order, exact 7-key schema
**Batch label:** "Memory_and_Heaps" is wrong for most of the range. The batch is really *four*
unrelated bands: the **MoLive audio reader/decoder** (0x005EB000–0x005EF000), scene-object/UI
destructors + UI style/render helpers (0x005F1A00–0x00627000), the **PICA200 GPU command/state
builders** (0x00655000–0x006F2000), and two container/library cores (0x0070C000–0x00716000).

## What I did

Resumed lane with nothing on disk: no `out/N_084.json`, no `done/N_084.md`, no N_084 log entry, and
no sibling batch named any of the 88 addresses. All 88 entries were produced from scratch.

Method:

1. **Index.** Parsed all 18,367 readable functions (`decomp/readable/functions/*.c` +
   `recovered/`) into a call graph: address → file, callees, callers, `g_XXXX` references. This is
   what made bottom-up naming possible (28 of the 88 have zero callers and are only reachable
   through vtables/tables, so their callers' callers had to be resolved first).
2. **Name map.** `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all 77
   sibling `out/N_*.json`, so cross-batch vocabulary is reused where it exists (N_083's
   `maybe_Sound_Stream_*`, N_021's `Gfx_GpuCmd_*`, N_040's `Ui_SceneFlow_*`, N_074's
   `Ui_SceneFlow_BindSlotObject`, N_042's `Sound_PlaySeById`, N_003's `Gfx_Resources_Release`).
3. **Strings.** `decomp/readable` contains no string literals, so I dumped every ASCII run from
   `original/exefs/code.decompressed.bin` (base `0x00100000`) and dereferenced each `g_XXXX` in the
   batch bodies. This is the single most valuable step: it *proves* the module identity
   (`MoLive::Allocator: not enough memory to allocate %d bytes !!!`, `ReadEp: cannot find stream %d`,
   `Ep goes beyond end of packet`, `ReadEp: stream %d already disabled`,
   `error: reader could not change its packet size`, `lyt_shader.shbin`) and all GPU command words
   (`0x0F0081/83/84/85/86/8E`, `0x0F0111/16/17/1C/1D/1E`, `0x0F006D`).
4. **Disassembly** (`capstone`, base `0x00100000`) for every body Ghidra damaged or for
   entry-point questions. Three findings that changed names:
   - `0x005EC19C` is a 4-byte ARM default-argument stub (`mov r2,#1`) that falls into `0x005EC1A0`,
     so `0x005EC1A0`'s third parameter defaults to 1.
   - `0x005EE430` is a 12-byte `if (arg2 == 0) return 0x40;` guard before the body at `0x005EE43C`,
     which is why `MoLive_Reader_SetSource` is called at `0x005EE430` and not at the batch address.
   - `0x005F1BFC` is a **separate** ARM function (a typed-handle validator, `handle >> 24 == 0x2D`)
     that Ghidra merged into `0x005F1AF8`'s range; it is what reclassified `0x005F1AF8` from a
     "battle popup release" into `maybe_Svc_HandlePool_Release`.
5. **Literal pools** dereferenced for every `g_` that looked like a pointer (e.g. `0x006126C4` =
   `0x31C1`, which turned "apply level A" from a guess into `self->f_31C1`).

## What the 88 functions actually are

## Open problems / what is NOT verified

- **Fully static.** No emulator, debugger or playtest. Mechanisms (which field, which call order,
  which GPU register) are read from bytes and are reliable; the *purpose labels* are inference.
- **MoLive vocabulary is inferred from the middleware's own strings, not from an SDK header.** The
  strings prove the module; the words "EP", "stream", "packet" are used the way the strings use
  them. `MoLive_StreamTable_BeginPackets`/`CommitPackets` rest on N_083's `maybe_Sound_Stream_*`
  reading of `0x005EBA14`/`0x005EBBA8` (allocate/append the pending segment) plus my own reading of
  the slot layout — if those two helpers turn out to mean something else, both names should follow.
- **`0x0070D126` / `0x0070D12A` / `0x0070D12E`** are three Thumb entry points that Ghidra records
  for one red-black erase-and-rebalance routine (4 + 4 + 0x216 bytes). They are *not* mid-function
  bytes as I first suspected: `0x0070D0F8` is an ARM function of exactly 46 bytes (0x2E) ending at
  `0x0070D126`, and Ghidra's decompilation of `0x0070D12E` is a coherent RB delete fix-up. Why the
  same body has three entries is still unknown (nothing in `asm/text/*.s` branches to the two
  4-byte ones), so all three stay `maybe_` at 0.30/0.30/0.45.
- **`0x00674E66`** (0x228C bytes) could not be decompiled: Ghidra reports bad instruction data and
  an instruction overlap at `0x006749AE`, and it is listed as Thumb while its neighbours are ARM.
  Only its two callees (float→fixed pack, normal transform) are evidence; confidence 0.30.
- **`0x006693B0`** is damaged in the middle (`halt_baddata`); the ring-buffer copy is certain from
  the intact parts and the caller, the exact "PCM" claim is not.
- **`0x00670DF0`, `0x0067254C`, `0x006740E8`** are GPU-state rebuilders with no callers other than
  the invalidator; which register group each one owns is inferred from the dirty bit and the
  float-packing idiom, not from register names.
- **`0x006F1F88`** is a 0xE3C8-byte singleton whose vtable (0x782964) points into the 0x66D9xx
  family, and whose callers read a mode byte at +0xE3C4 and walk a 0xA8-stride array at +0xE1C0.
  "UI manager" is a role name; the concrete class is not proven.
- **`0x00655F58`/`0x006579C8`/`0x006594D0`**: the command *words* are certain, the human names of
  the PICA200 registers behind them (size/param/LOD/border/addr/type) are the standard mapping and
  were not cross-checked against a register table.
- **`0x005F1AF8`/`0x005F26AC`**: the pool/handle mechanics (type tag 0x2D, bitmap, 0x70-byte
  instances, 0x88-byte work slots) are read from the code; the object type behind tag 0x2D is not.
  Note N_082 named the only caller (`0x002E6828`) `maybe_Sound_Channel_PauseIfPlaying`, which is
  probably wrong for the same reason — worth a second look.
