# N_085 — Save_and_Persistence (0x00100050–0x001A3EE0), 150 functions

## What existed before this resume

Nothing attributable to N_085. `orchestration/naming/out/N_085.json` did not exist, there was no
`orchestration/done/N_085.md`, no `N_085` line in `AGENT_LOG.md`, and no sibling
`out/N_*.json` named any of the 150 addresses (checked against all 77 sibling batches plus
`symbols.json`, `symbols_recovered.json` and `decomp/native_names.json`). No scratch files were
found either, so all 150 entries were produced from scratch.

## What the range really is

The batch header "Save_and_Persistence" is a guess by the batch generator and it is wrong for
almost the whole range. The 150 addresses are not contiguous; they are 12 clusters, in order:

1. **0x100050–0x100A74 — libc.** The array-of-objects construction helper (`std_ConstructArray`,
   593 callers), a `strtod` trampoline, `mbstowcs` and `wcsncpy`. These sit in the middle of
   N_001/N_037/N_080's printf/string block and were simply skipped by them.
2. **0x105584–0x105AFC — streamed-audio player.** Three functions of one class: the six banks of
   streamed-voice slots (0x24-byte slot records at +0x110, pack handle at +5), the voice state
   machine (a 64-entry command ring of 8-byte records at +0x1848, nine states at +0x1a50, fade
   timer +0x1a54), and one Ghidra mis-split of the second. `Snd_RequestBgmPlay@0x1ec1d0` /
   `Snd_RequestBgmStop@0x1ee4f8` enqueue into exactly that ring, which is what pins the identity.
3. **0x1064D8–0x109990 — constructors of large engine singletons.** Both are the
   "store vtable, clear a field range, `std_ConstructArray` N sub-records" shape; 0x109990 is the
   display-side one (neighbours are the Gfx framebuffer functions), 0x1064D8 the owner-table one.
4. **0x10AF94–0x10F790 — Gfx/sound resource tables.** The lazy pack-handle table, the two
   locked service-call wrappers (0x10CDE0/0x10D430, svc 0x32 with a three-code retry loop), a
   container walker, the sound command queue and channel release, a voice-loop programmer, the
   party-status data reset, and a GPU register/format table builder called from
   `Gfx_InitializeContext`.
5. **0x11108C–0x1114A4 — C++ container primitives.** Two byte-identical `std::vector<u32>::insert`
   instantiations, `memmove` (0x111378, proven by the backwards-copy body and by the overlap test
   that branches to the forward `memcpy` at 0x116a14), and a double-buffer reset.
6. **0x113814–0x11973C — session/IPC plumbing.** Five `svc 0x32` request builders (0x1144C0,
   0x114514, 0x1145C4, 0x11973C, 0x11ED70), two status queries, a callback invoker, a queue
   push/drain pair and an archive-header parser.
7. **0x11AE88–0x11FADC — sound mixer channel plumbing.** Channel release, priority-bucket
   reinsertion (8 buckets of 0xc bytes at g_0011b030, `usat(prio,7)`), a type-9 command queue,
   the lazily created game-data context (0x11CB38, 992 callers), a hash-map ctor, two more status
   queries and a priority-ordered list insert. These use the same vocabulary as N_032's
   `maybe_Snd_*` names for 0x11B048/0x11B57C/0x11FD1C, which I kept consistent with.
8. **0x122124–0x126250 — container ctor, address translation, pack handles.** VRAM/FCRAM
   virtual→physical translation (0x12345C, `0x1f000000 + 0xf9000000` = `0x08000000`), two range
   translators, `Pack_Handle_Dtor`, the pack-handle-entry ctor, handle-pair move-assign, and one
   more `memcpy` entry alias.
9. **0x147750–0x153280 — Squirrel standard library, first half.** `array.sort` (heapsort with a
   comparator closure), array clone, the "negative result → -1" shims, value comparison,
   coroutine wakeup, the compiler-expression helpers, `thread.wakeup` ("cannot wakeup a idle
   thread" / "cannot wakeup a running thread" strings), the two heap-sift bodies, and the
   system-globals registration (`_version_` = "Squirrel 2.2.5 stable").
10. **0x155608–0x166308 — Squirrel natives for the game API.** Frame/actor/message natives plus
    `Script_ToNumber` / `Script_ToInteger` (they parse strings with `Script_ParseNumberString` and
    raise "cannot convert the string"), `Script_ArrayTop` ("top() on a empty array"),
    `Script_CheckArgType` ("wrong argument type: expected %s"), `Script_ReportError`
    ("AN ERROR HAS OCCURED [%s]") and `Script_ClosureInfo`.
11. **0x167764–0x184E38 — battle action tables and UI/map plumbing.** Eleven functions share one
    data shape: two 80-record tables (0x2c8 bytes per record, five 0x8c-byte per-member
    sub-records) at `f_e8`/`f_ec`, with a snapshot/rebuild/compact family plus the battle ctor.
    Around them: a window base ctor, the map transform composer, a map-cursor ctor, a spawn-record
    applier and a dialog-root ctor.
12. **0x186CB4–0x1A3EE0 — Squirrel compiler, text engine, party-status and message windows.** The
    `function(...)` expression parser, two function-state ctors, the text glyph/metric cache
    (255 entries of 0x18 bytes with an LRU counter), the text-page reset/build pair, the text-style
    object and its 5-slot list, the party-status window reset and member-list inserts, two
    container helpers, the pager/root/sprite-widget ctors and the three message-window openers.

So the only functions here that genuinely touch persistence are the flag/condition evaluator
`Event_EvaluateConditionBlock` (0x1498FC), `maybe_Save_ResetGameFlagBlock` (0x15A690) and the
party-data reset 0x10F448 — everything else is audio, Gfx, C++ containers, Squirrel or UI.

## Method

- Name map (11,877 address→name pairs) built from `symbols.json`, `symbols_recovered.json`,
  `decomp/native_names.json` and all 77 `orchestration/naming/out/N_*.json`.
- One-pass caller/callee index over all 18,748 `decomp/readable/{functions,recovered}/*.c`, then a
  per-function digest (signature, size, mode, annotated callers/callees, neighbours, body) read in
  ten chunks of ~26 KB, leaf helpers first.
- Literal-pool scan of each body against `original/exefs/code.decompressed.bin` (base 0x100000) for
  inline strings. Only one string literal is embedded in this whole batch
  (`s_cursor_select_003afff4`), so almost all evidence is structural; the Squirrel/UI strings above
  are the exception and they are quoted from the readable C.
- Global dereference with a small script: every code-pointer argument passed to
  `std_ConstructArray` was resolved (`g_0010672c`→0x107f6c, `g_00109d94`→0x10f3b4,
  `g_0010e42c/30/34`→0x116798/0x1167b0/0x116780, `g_00110270`→0x11982c, `g_001144b0`→0x119838,
  `g_0011deac`→0x1235e0, `g_00124478`→0x1150a0, `g_001221bc`→0x106a10) and the first word of each
  constructed object is a vtable (e.g. `g_00106728`→0x7821c8). That is what turns the array
  helper from a guess into a certainty.
- Raw disassembly for every case where Ghidra was wrong or unhelpful: 0x11108C/0x11117C (vector
  insert), 0x1112EC/0x111378 (memmove), 0x116A14/0x116AE0/0x116C10 (memcpy/bzero/memcpy core),
  0x11AF14 (priority reinsert) and the 8-byte trampolines 0x1005EE / 0x126250.
- Cross-checks against neighbouring lanes' names were used where they were consistent with the
  bytes (N_032's sound lexicon, N_022's party-save snapshot, N_080's Fs caches) and explicitly
  overruled where they were not (see "Disagreements").

## Result

- 150 entries, exactly the required seven keys, in batch order, 150/150 addresses exactly once.
- Confidence 0.30–0.90, mean 0.457; 86 entries below 0.50, all `maybe_`-prefixed, and no entry at
  or above 0.50 carries the prefix.
- 150 unique names; zero collisions with the 77 sibling batches (five initial
  `maybe_Script_ApiResultOk*` shims were renamed `maybe_Script_ApiResultCheckA..E`) and zero
  collisions with the three project symbol files.
- ASCII only, no control characters, every signature contains its own name, every `params` value
  appears in its signature, `params` keys are `param_1..param_N` in declaration order.
- Highest confidence: `std_memcpy` 0.90, `std_memmove` 0.85, `std_wcsncpy` 0.80,
  `std_ConstructArray` 0.70, `std_mbstowcs` 0.70.
- Prefix distribution after stripping `maybe_`: Script 38, Ui 15, Battle 14, Snd 11, Text 11,
  Svc 10, std 9, Os 9, Pack 6, Container 6, Field 5, Gfx 4, others 12.

## Honest gaps / open problems

- **Nothing was verified dynamically.** No emulator run, no debugger, no playtest. Every mechanism
  claim comes from bytes; every *purpose* label is an inference. That is why 86 entries are below
  0.5 and prefixed `maybe_`.
- **0x105584 / 0x105AFC are called "Snd_*" from their data flow, not from a service string.**
  The evidence is strong (pack-handle validation identical to `Pack_FreeHandleEntry`, async reads
  through 0x10DF00, gain ramps through 0x114CFC, and the BGM request functions enqueueing into the
  same +0x1848 ring), but whether the class is "BGM stream voice" or a generic streamed-audio
  voice used for both BGM and voice/SE cannot be decided statically.
- **0x105ACE is very likely not a real function.** It starts exactly where 0x105584 ends, inside
  ARM code, and its body is a Thumb misdecode of 0x105AFC's state machine. It is named
  `maybe_Snd_StreamVoice_UpdateAlt` at 0.30 and should probably be deleted as a duplicate rather
  than merged.
- **The 12 script/UI "shims"** (0x14B31C, 0x14EF14/68/80, 0x155664/684/6CC, 0x157014, 0x1570AC,
  0x157268, 0x159088, 0x15AFB8, 0x15B030, 0x160EA4, 0x1661E8) are 0.30–0.45: each is 2–5
  instructions around one Squirrel API call, and without the native-binding table (which is built
  at runtime with string keys) there is no way to tell which script function they implement. They
  are named by mechanism only (`Script_ReturnArg`, `Script_ApiResultCheckA..E`, ...).
- **The battle action-table family** (0x16D8A8, 0x16F76C, 0x170CA4, 0x171DA4, 0x1748A0, 0x175840,
  0x175A78) is named from the data shape, not from class knowledge: 80 records × 0x2c8 bytes with
  five 0x8c sub-records, plus a live-index field at +0x124. Which record means "queued command",
  "target slot" or "reaction" is inferred from the copy/clear/compact pattern, and 0x175840's only
  caller is `maybe_Gfx_Scene_Init@0x206bbc`, so even the "battle" prefix is a role name.
- **0x10F448 + 0x19371C + 0x1939C0** are called "party status" because 0x19371C is reached from
  `Ui_Window_ResetState@0x35f814` and operates on five 0x44-byte style records and eight
  0x60-byte member records. The window class itself has no RTTI and no name string.
- **0x1498FC** (condition evaluator) is the one entry where I expect reviewers to want more: the
  record layout (0x28-byte rows, self-relative id lists, mode bytes) is described exactly, but the
  meaning of the two mode bytes (only 0/1 are handled) and of the id namespaces (0x66B17C / 0x66AF08
  / 0x66B380 are three different lookups) is inferred.
- 7 entries are Ghidra-damaged and are deliberately vague (`halt_baddata` in 0x19EB58, lost
  registers in 0x108F32, truncated bodies in 0x113F2C / 0x1143F4 / 0x173664 / 0x192F84 /
  0x1939C0). They are 0.30–0.40 and their summaries say what is actually visible.
- No build/test run: naming lane exemption (no code, data or asset was changed). Validation was
  mechanical (`%TEMP%/opencode/n085/build.py`): JSON parses as ASCII, 150/150 in batch order, exact
  key set, name-in-signature, params values in signature, `maybe_`/confidence rule both ways,
  uniqueness, cross-batch and symbol collision scan, character checks — 0 problems.

## Disagreements with sibling lanes (for M1)

- **0x00100050**: N_081's follow-up list guesses `memcpy` for this address. It is not: the
  disassembly is `blx r6` per element and the second argument dereferences to code. Use
  `std_ConstructArray`.
- **0x00116AE0**: N_081 calls it `memset`; the disassembly zeroes `r1` **bytes** with no fill
  argument (`mov r2,#0` inside). It is `bzero(dst, len)`.
- **0x0010F448 / 0x19371C**: N_022 treats 0x10F3E0..0x111D50 as the save system and 0x111B7C as
  "Save_CompleteAsyncRead". 0x10F448 is called *with the window pointer* from 0x19371C and writes
  only offsets inside that window, so it is UI party data, not the save object; M1 should not
  assume the 0x10Fxxx block is one subsystem.
- **0x0011AE88 / 0x11AF14 / 0x11FD44**: N_032's sound-channel reading is consistent with mine and
  the names are aligned, but both lanes are below 0.55 on this block.

## Suggested follow-up tasks

1. **Squirrel native binding table.** Dump the table the VM builds at runtime (or the static name
   array around 0x153ccc) and map name→function; that would lift ~20 `maybe_Script_*` entries in
   this batch from 0.3–0.45 to 0.8 in one pass, and it is also the missing link for N_081/N_082's
   script names.
2. **Name the shared helpers in the merge, once.** `std_ConstructArray` 0x100050, `std_memcpy`
   0x116C10, `std_memmove` 0x111378, `std_bzero` 0x116AE0, `std_memcpy` 0x116A14, and the
   allocator/align pair 0x11CFAC/0x11FE8C. Roughly 40 entries across N_081/N_082/N_085 would drop
   their `maybe_` prefix because their evidence could then cite a proven helper.
3. **The 0x105584 streamed-audio class**: read the vtable at the object built by
   `Snd_RequestBgmPlay` and the 0x78xxxx tables used by 0x114CFC/0x11B57C, and confirm whether the
   six banks are sound banks (Common/Field/Battle/...) — that would settle 3 entries here plus
   N_032's 0x114CFC/0x11B57C.
4. **Battle action tables**: one pass over `Battle_Update@0x16e3e0`'s use of `f_e8`/`f_ec`/`f_124`
   would turn the seven `Battle_*UnitAction*` names into exact ones (and fix 0x175840's caller
   attribution, which currently contradicts the "battle" prefix).
5. **Delete `0x00105ACE`** from the function list (Thumb misdecode of 0x105AFC, 46 bytes inside ARM
   code) instead of naming it; same class of artefact as N_082's 0x30B628 and N_083's duplicates.
