## Method

1. Name map (556 project names + 11,533 sibling batch names) from `symbols.json`,
   `symbols_recovered.json`, `decomp/native_names.json` and all 82 existing `out/N_*.json`
   (`N_014.json` is invalid UTF-8 and was skipped by the loader).
2. One-pass caller index over all 18,748 `decomp/readable/{functions,recovered}` files, after
   stripping the generated header comment (otherwise every function “calls” itself).
3. Per-function digest (signature, size, annotated callers/callees, `g_` globals, string labels,
   full body), read in six chunks of 25.
4. **Direct disassembly of helpers Ghidra never split** (`capstone`, from
   `original/exefs/code.decompressed.bin`, base `0x00100000`). This settled the load-bearing facts:
   * `0x00100050` = *construct-array* — `for (i < count) { ctor(dst); dst += stride; }`. About 25 of
     these functions are constructors that end in a construct-array call; their element sizes are
     how the class layouts were separated (e.g. 800-byte training rows of three 0x104 chara slots).
   * `0x0070F03C` = `std::vector<u8>::push_back` (begin/cur/cap at +0/+4/+8); `0x002CEAE4` is the
     same push_back for the message bytecode at +0xD6C.
   * `0x00100B74` = `wcslen` — a **Thumb interior entry** of the `wcsstr` function at `0x00100B32`.
     Ghidra marks it “does not return”, which turns `Save_LoadSlotName` and `0x002828BC` into
     apparent aborts. Two tails (`0x0025C480` → `0x001B7DDC`, `0x0027EB64`) were resolved from raw
     code instead.
   * `0x00267C0C`, `0x00263B60`, `0x00294F7E`, `0x0029E4C6`, `0x002D5EC0` and `0x002D6A34` are
     Thumb/recovered entries with destroyed registers; each is described as what the surviving code
     proves.
5. **Static handler tables read from the retail image.** `0x0072C5B8` holds the eight text-command
   handler pointers in dispatch order, and each handler's immediate control byte was read from the
   instruction stream; virtual-table pointers installed by constructors (`ldr rN,[pc,#…]` → literal →
   vtable) gave the class of ~30 UI functions. Named vtable slots (`Ui_TrainingWindow_LoadSlotLayouts`,
   `Ui_CreditWindow_CollectTextPanes`, `Ui_DiveForm_InitPanes`, …) made the class names defensible
   without guessing.
6. Data-manager table accessors were identified and reused: the singleton from `0x0011CB38` holds
   record tables at fixed offsets, and the inlined accessors are `+0x7CC` (`0x63E05C`, item/equipment),
   `+0x7C4` (`0x63FD24`), `+0x78C` (`0x63FE6C`), `+0x2BC` (`0x63D018`, 191 entries), `+0x2B4`
   (`0x63D384`), `+0x6..` etc. The item bag layout is: 289 counts at +0x124, 289 “new” flags at
   +0x5E0, four 7-entry equipment category arrays at +0x5A8/+0x5B6/+0x5C4/+0x5D2, and per-item
   10-byte sub-entries `{u16 id, u8 type, u16 value}`.

## Known gaps / honest caveats

* Fully static: no emulator, debugger or playtest. Mechanisms are read from bytes; **purpose labels**
  are the inferred part. The weakest entries (0.25–0.40) are documented as such.
* `0x00263B60` (0.25) is **not a real function**: 12 bytes starting mid-instruction inside the
  training-window code, a mis-detected recovered entry point. It is kept only so the address is
  accounted for.
* `0x0025EB88`, `0x0026423C`, `0x002A7A54`, `0x00298F54`, `0x002CF200`, `0x002BE…` are window/part
  constructors whose *class* is proven by the installed vtable but whose *screen role* sometimes
  rests on one caller (e.g. `Ui_ItemMenu_RootPart_Ctor` from `Ui_ItemMenu_CreateRoot`).
* `0x0025E920`, `0x00281618`, `0x0029FA00`, `0x002BEE1C` are four variants of the same
  “fill message struct, dispatch to children, call base layout” method; which slot each occupies is
  certain, the semantic difference is only partially recovered (2 × 2 message field values differ).
* `0x002ACF58` (“smoothed follow”) and `0x002B14A0` (“spin transform”) are integration maths whose
  per-frame effect is certain; whether the owner is the camera or an actor is inferred
  (`Ui_SceneFlow_Update` + trail actions call them).
* `0x002AFA88`/`0x002AFC5C` are a render-parameter init pair with partially bad control flow in the
  decompiler; the byte offsets and copied templates are exact, the parameter *meaning* is not.
* Item-bag function names describe the observable operation (acquire check, remove by group id,
  category value) rather than proven menu behaviour, because the item table has no strings.
* `0x002947E8` and `0x002CFACC`/`0x002B1E0C` are generic “widget with N entries” ctors used from many
  screens; their names therefore say what they build, not where they are used.
* Two callees were assumed equal to the training-window class even though the ctors are called from
  `Ui_TitleDemo_Init` / `Ui_RecipeBook_Ctor`: the installed vtable (`0x75CBA8`, with
  `Ui_TrainingWindow_LoadSlotLayouts`) is authoritative there, and the report keeps the class name
  while noting the callers.
* `0x002D4604` sorts and submits a render element; the sort keys are exact (depth shorts), the
  pass/batch semantics are inferred from the Gfx submission API it calls.
