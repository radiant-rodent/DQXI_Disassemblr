## 2. What this batch actually is

The batch header says `Save_and_Persistence`, but only a handful of the 150 addresses touch
save/party data (`0x0035F0CC`, `0x0035F640`, `0x0035F6C0`, `0x0035F774`). The 150 addresses are
one contiguous band of the retail executable and are overwhelmingly **UI, field-actor and menu
code**:

- **Ui window system** (`Ui_*`, 63 entries): BFLYT/BFLAN window constructors, `InitPanes`
  overrides, vtable slots, list/record/memories/quest/guide/status/skill-panel windows.
- **Field actors & NPCs** (`Field_*`, 33): actor/gimmick ctors, NPC action state machines
  (walk/run/fall/mimic/follow), attached effects, horse actions.
- **Battle HUD** (`Battle_*`, `BattleScene_*`, 19): damage/tension/popup widgets, battle party and
  enemy-list windows, model-slot release, target interpolation.
- **Gfx / Model / Anim / Sound / Fs / Craft leaves** (14): effect-pack loaders, sprite base ctors,
  clip-slot motion helpers, a sound emitter setter, a file-request updater, a crafting helper.

## 3. Method

1. **Digest per function.** For every address: readable C body (the path in the batch file,
   falling back to `decomp/ghidra/`), its direct callers, its direct callees, and the neighbouring
   named functions (within ±0x1800) to establish which class/region it belongs to. The caller/callee
   index was built by scanning all 18,748 files in `decomp/readable` for `func_XXXXXXXX` references.
2. **Name context.** Names were resolved against `symbols.json` (459 named function symbols),
   `symbols_recovered.json` (460), `decomp/native_names.json` (454) and **all 94 sibling
   `orchestration/naming/out/N_*.json` files**, so callees print as e.g. `Ui_WindowBase_Ctor`,
   `std_ConstructArray`, `Model_Equip_CommitNodeChanges` instead of `FUN_xxxxxxxx`.
3. **Literal-pool strings.** Ghidra's `s_` names are truncated, so each function's byte range in
   `original/exefs/code.decompressed.bin` (load base `0x00100000`) was scanned for words pointing
   into `.rodata` (`>= 0x725000`); the targets were decoded as Shift-JIS/ASCII. This recovered the
   load-bearing literals, e.g. `"Damage"` (0x2DBB28), `"Nut"/"Run"/"Walk"`, `"effect/%s.pack"`,
   `"effect/bitem/%s.pack"`, `"effect/spell/%s.pack"`, `"win_guide"`, `"win_dungeon_list2"`,
   `"background"`/`"side_lamp_bottom"`, `"ecoCoSub"`, `"mimic"`.
4. **Vtable identity.** For constructors the literal pool gives the vtable address; its slots were
   looked up in the already-named symbol set. That is how, for example, `0x00391070` became
   `Ui_BattlePartyWindow_Ctor` (vtable `0x766A3C`, slot +0x20 = `Ui_BattlePartyWindow_InitPanes`)
   and `0x0039439C` became `Casino_Slot_RenderReels` (vtable `0x766DC4`, slot +0x18).
5. **Bottom-up.** 150–250-byte leaf/ctor functions were named first (they carry the strongest
   evidence), then their names were used to interpret the large `InitPanes`/`Update`/`Render` bodies.
   Bodies Ghidra truncated (`Subroutine does not return`, lost arguments) were re-read in raw ARM
   from `asm/text/*.s` and from the binary.
6. **Validation.** The written JSON was re-read and checked independently: exact address set/order,
   unique names, exact seven-key schema, `maybe_` iff `confidence < 0.50`, name present in its own
   signature, ASCII-only, and **zero name collisions** against the project symbol tables and all 94
   sibling batches (six draft collisions were fixed, e.g. the two different two-column-list
   constructors now differ by a `B` suffix, and the second message-window ctor is
   `Ui_MessageWindow_CtorFieldPanes`).

### Load-bearing identifications (worth reviewing first)

- `0x0035F6C0` / `0x0035F774` — `Party_GetActiveMemberDataByIndex` / `...IdByIndex`: the first has
  46 C-level callers (shop, equip, party-select, status, battle); both walk `GameWork+0x24A98`
  (`f_27218` entries), resolve each slot with `0x0066B0E4`, and accept only slots whose master record
  has bit 0 of `+4` set (the "in party" flag). `0x0035F774` returns the id (or 0xFF) and is used by
  `Battle_DecideFirstStrike`.
- `0x0035F640` — `Party_ApplyFontRecordToActiveMembers` (0.70): the same active-member walk, calling
  `Text_ApplyFontRecord` (0x0019201C) on each member's name-text object; called once from the
  UI scene start-up path after fonts are loaded.
- `0x00391070` / `0x0038BE4C` — battle party and enemy-list window constructors, vtable-verified.
- `0x0030C094` / `0x0030C1B4` / `0x0030C2D4` — the three effect-pack loaders
  (`effect/`, `effect/bitem/`, `effect/spell/`) with the format string in the reader's own rodata.
- `0x003418CC` / `0x00341D24` — `Ui_StatusWindow_BuildIndexTablesA/B`: together they rebuild the same
  10 of the window's 11 key→index slots (index 8 unused) that `Ui_StatusWindow_ReleaseSlots`
  (0x0033D404) later frees (array `+0x60+i*4`, tree `+0x90+i*0x18`); A covers slots 7 and 10,
  B covers 0–6 and 9.
- `0x0036DE7C` / `0x0036F2E0` — skill-panel description/required-SP refresh; the description path
  writes the `win_talk` pane at `self+0x23A4` bound by `Ui_SkillPanel_InitPanes`.
- `0x003A08F8`…`0x003B2428` block — quest/record/guide/talk-menu code: `Ui_QuestWindow_CollectRewardItemIds`
  reads a master row and inserts its u16 ids into a sorted set; `Ui_QuestList_PopulateActiveQuests`
  is sized exactly 53×0x8C = 0x1CFC bytes of the quest table.

## 6. Not verified / open problems

- **Everything is static.** No emulator run, no debugger, no in-game confirmation. All summaries are
  derived from decompiled C, raw ARM and data references.
- 53 names are `maybe_`: the mechanism is evidenced but the *purpose/owner class* is inferred.
  Weakest are `0x003B1508` (0.30, a bare thunk into `std_ConstructArray`), `0x002FFAD8` (0.35,
  flag-bitmap + map-jump event), `0x003A7128`/`0x003A71D0` (0.35, twin opcode dispatchers whose
  subsystem — UI tween vs text-line layout — is ambiguous), `0x003096D4` (0.35, "DiveFormEx" only
  from an inherited label) and `0x0030B120` (0.35, 13 heterogeneous callers).
- Several bodies are Ghidra-damaged (`0x002FEDF4`, `0x00304DCC`, `0x003096D4`, `0x0035E4FC`,
  `0x003A08F8`, `0x003A816C`), so their signatures/arity are from the call sites, not the C.
- Names inherited from sibling batches (shown in brackets in the evidence) may themselves be
  `maybe_`; where a name was load-bearing for a decision, the address is quoted too, so a later
  correction does not silently invalidate the reasoning.
- The batch label `Save_and_Persistence` is a generator artefact; the band is UI/Field/Menu. Worth
  re-labelling in `orchestration/naming/batches/index.json`.
