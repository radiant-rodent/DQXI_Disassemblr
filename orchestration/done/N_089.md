## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`.
2. Built a name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and
   every sibling `orchestration/naming/out/*.json`.
3. Built a caller index over all 18,747 readable C files and a per-function digest (signature,
   size, annotated callers/callees, globals, body).
4. Read every one of the 150 bodies, leaf functions first, and used the named callers/callees
   from other lanes to anchor meaning.
5. **Vtable analysis against `original/exefs/code.decompressed.bin`** (base `0x00100000`): resolved
   the vtable pointed to by each constructor and listed its named methods. This is what identified
   `FieldParty_Ctor` (vtable `0x769398` → `FieldParty_InitFromParams`, `ResetMemberSlot`,
   `UpdateActorAttachments`), `Battle_HpGaugeWindow_Ctor` (`0x7697B8`), `Ui_StatusParamWindow_Ctor`
   (`0x76BB28`), `Ui_CameraAnimWindow_Ctor` (`0x76B840`), the seven text-window classes, etc.
6. Resolved strings/pointers in the retail binary, which gave the only hard anchors:
   `%s.bspa` / `%s_cs.bspa` (`0x003B37B4/BC`), `FrogJump` / `FrogJumpNoEffect`
   (`0x00409418/24`) and `shadow` (`0x003E1FCC`).
7. Naming follows the project convention `Subsystem_VerbNoun`; every entry below 0.50 confidence
   is `maybe_`-prefixed (checked both ways). No address was invented: all addresses come from the
   batch file and all 150 appear exactly once, in batch order.

## Confidence / honesty

- High confidence (0.65–0.80): constructors whose vtable methods are already named by other lanes
  (`FieldParty_Ctor`, `Battle_HpGaugeWindow_Ctor`, `Ui_StatusParamWindow_Ctor`,
  `Ui_CameraAnimWindow_Ctor`, `Ui_ColorSelectWindow_Ctor`, the text-window constructors), and the
  frog-jump pair (inline animation names).
- Medium (0.50–0.60): the message-command handlers, battle popup/anchor helpers, UI layout
  callbacks, battle unit-model update/state functions. The mechanism is certain; the exact
  purpose label is inferred.
- Low (`maybe_`, 0.33–0.45): constructors with no named vtable siblings or strings, Ghidra-damaged
  bodies (`0x003C470C`, `0x003C4AB4`, `0x0042963C`), register-passed Thumb code
  (`0x004040B6`), and pure helpers (`0x004066DC`, `0x00417F78` etc.). These names stay vague on
  purpose (e.g. `maybe_Ui_SevenSlotTextWindow_Update`) instead of inventing a precise class.
- The 0x3B3F8C–0x3B51C8 family is called `Ui_MessageCmd_*`: they emit command bytes (3/6/7/8/9/10/
  0x12/0x14) and render 8-byte text records through `Ui_Widget_ShowWithRecord`. That reading is
  consistent with the named sibling `Event_Handler_TriggerCommand7` and the `ExecuteCommand`
  caller of the message page, but the exact DQXI tag names (colour/ruby/icon/…) are not known, so
  I did not guess them.
- Everything is static analysis: no emulator, debugger or playtest. No claim here is verified
  against runtime behaviour.

## Verification / repair pass (second resume, 2026-10-26)

When this pass started, `orchestration/naming/out/N_089.json` was reported missing by the file
reader, so I began an independent build. While I was reading the batch the previous worker finished:
the file appeared complete (150 entries, 96,573 B, 20:00 local). I therefore **audited and repaired
the shipped file instead of overwriting it**, using an independent name map, a full caller/callee
index over all readable C, and a pointer scan of `original/exefs/code.decompressed.bin` that lists
every vtable-like table containing each of the 150 addresses with its neighbouring named methods.

Mechanical checks after repair: 150/150 batch addresses exactly once, exact seven-key schema, 150
unique names, `maybe_` iff confidence < 0.50, every name occurs in its own signature, every `params`
value occurs in its signature, ASCII only, valid UTF-8. Mean confidence 0.524, 36 entries below 0.50.

### Defects found and fixed

1. **Reversed array dimensions** in nine summaries/evidence entries:
   `0x003B460C` (8 entries x 0x18 B, not 0x18 x 8), `0x003B52A4` (9 x 0x18),
   `0x003B7640` (5 x 4), `0x003BBF70` (6 x 0x14), `0x003D5D0C` (3 x 0x18),
   `0x003DFB14` (0x20 x 8), `0x003E99E0` (2 x 4), `0x00411F78` (64 x 0x10),
   `0x0041B5D8` (8 x 0x4C). `std_ConstructArray` is `(dst, ctor, elemSize, count)`.
2. **Wrong vtable in a summary**: `0x003B460C` claimed vtable `0x72BC04`; the installed vtable is
   `0x768B40` (the literal `0x72BC04` is a dispatch-table word, not this object's vtable).
   Renamed `maybe_Ui_MessageCmd_CtorA/B` -> `Ui_MessageCommandWindow_Ctor8/9` (the class has 8
   versus 9 command slots at +0xD8C, walked by `0x003B3EB8`).
3. **Misidentified classes**, corrected from vtable membership:
   `0x003B7640` Event_Packet_Ctor -> `maybe_Ui_SoulWindow_Subwidget_Ctor` (vtable `0x768D7C`),
   `0x003B8A80` -> `Ui_PartySelectRowWidget_Ctor` (shared row widget, vtable `0x768EAC`, built
   inline by `Ui_TsuyosaWindow_Ctor`), `0x003BBF70` -> `Ui_PartySelectWindow_Ctor` (vtable
   `0x77404C`, six 0x14-byte member rows), `0x003C2638` -> `FieldParty_Dtor` (slot 0 of vtable
   `0x769240`; its entry is the continuation at `0x003C2634`), `0x003CFFA8` ->
   `Event_Packet_UpdateMotion` (slot 0 of `0x76982C`, next to the other Event_Packet methods),
   `0x003D5664` -> `maybe_Ui_DungeonOperationWindow_DrawChildren` (slot 0 of `0x76A090`),
   `0x003FADC8`/`0x003FAE4C` -> `BattleParty_Dtor`/`BattleParty_DtorNoFree` (slots 4/0 of
   `0x76C1A0`).
4. **Wrong subsystem for eleven battle functions**: `0x0042B560`, `0x0042C560`, `0x004302B0`,
   `0x00430584`, `0x0043074C`, `0x00437C48`, `0x00437E30`, `0x00430D24`, `0x0043111C`,
   `0x00434C24`, `0x00435458` were named `Battle_UnitModel_*`, but each is a slot of the battle
   actor-action vtables `0x76F3E0` / `0x76F380`, whose other slots are already
