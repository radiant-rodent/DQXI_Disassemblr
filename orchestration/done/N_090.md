# N_090 — native naming batch, resumed and completed

## What existed when I started

Nothing attributable to N_090: no `orchestration/naming/out/N_090.json`, no
`orchestration/done/N_090.md`, no N_090 entry in `AGENT_LOG.md`, and no scratch directory named
`n090`. No sibling `out/N_*.json` named any of the 150 batch addresses (the sibling collision scan
is part of the final validation), so all 150 entries are new and in batch order.

The batch file `orchestration/naming/batches/N_090.txt` lists 150 addresses from
`0x00442278` to `0x004C13B0`, all with readable C in `decomp/readable/functions/`.

## Method

1. **Name map**: `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all 86
   sibling `orchestration/naming/out/N_*.json` (≈13k address→name pairs), plus the symbols embedded
   in the readable-C file names.
2. **Call graph**: a fresh one-pass index over all 18,748 files in
   `decomp/readable/{functions,recovered}` (the stale `%TEMP%/opencode/n042_index.json` covered only
   14 of the 150 addresses). For each batch function I produced a digest with callers, callees
   (annotated with sibling names), inline strings, literal-pool values, the containing class and the
   full body, read in six 25-function chunks, leaves first.
3. **Literal-pool / vtable resolution** against `original/exefs/code.decompressed.bin`
   (base `0x00100000`). This was the decisive step: for every constructor-style function I
   dereferenced the vtable it installs and printed its slots with the names other lanes already gave
   them (e.g. `Ui_*_InitPanes`, `Ui_*_Dtor`), which yields the class name without guessing. I also
   used a whole-image pointer scan for the two unusual functions at the start of the batch.
4. **Capstone 5.0.7 disassembly** for the bodies Ghidra damaged (`0x442278`, `0x443B60`,
   `0x446D38`, `0x447864`, `0x11CFAC`, `0x11FE8C`, `0x100050`, …) and for every
   "the C stops at one call" case.
5. **Squirrel corpus** was checked for the bound natives that touch the same tables; it confirmed
   the save/work singleton and the party/record accessors but added nothing for the UI classes.

## What the range actually is

The batch label `Save_and_Persistence` is **wrong for 148 of the 150 functions**. In order:

- `0x442278` / `0x443B60` — two users of the game-wide work singleton (pointer at `0x007BE320`,
  0x2FB28-byte static buffer at `0x00804160`). The first publishes an effect-anchor transform at
  work+0x2A62C that the effect placement code (`0x1D8E2C`) reads; the second counts the valid
  records of the 50-entry, 0x8C-byte table at work+0x24A98+0x5FE4. Neighbours are Camera_* and
  Ui_DiveCapture_*, so they are named `maybe_Effect_StoreAnchorState` and
  `maybe_Ui_DiveCapture_HasFreeSlot` (both deliberately vague).
- `0x444610–0x448304` — the `Ui_DiveCapture` screen ctor and a run of UI-window ctors
  (PartyGauge, EquipmentRow, MessagePair, TenRowText…), identified via their vtables.
- `0x44AD1C–0x457000` — field scene-object callback reset, UI cursors/stamp/three-pair windows,
  the text-layout glyph collector and measurer (`Text_Layout_AddGlyph`,
  `Text_Layout_CollectGlyphs`) and the actor-action "egg jump" update.
- `0x47392C–0x476E10` — the **Dragon Jump** actor-action element updates, each proven by its own
  animation name string (`Dragon_JumpM_Down_Loop`, `Dragon_JumpS_Start`,
  `Dragon_JumpM_Up_StartSE`, `Dragon_JumpM_Down_End`, `Dragon_JumpM_Down_StartSE`) plus two
  monster-action constructors.
- `0x477BAC–0x47C140` — poker/paged-list/select-list/choice/party-select/two-position UI ctors and
  the generic grid/list helpers.
- `0x47D1A4–0x47EA10` — the **battle UI root** (`Battle_Ui_Ctor`), unit animation selection and
  the battle effect-parts pack loader (`2d/battle2/parts_effect/%s.pack`).
- `0x483FCC–0x48FDDC` — the battle effect spawn-transform computation
  (`Battle_Effect_ComputeSpawnTransform`, 10 callers, all `Effect_SpawnAttached*`), plus battle
  message row getters used by `Text_CalcRowRect`.
- `0x4993B8–0x4AA28C` — battle message/bar value getters, the arc-list window focus bounds,
  the battle target-panel look-at, the model-view path table, the battle command list window and
  the command-entry builder.
- `0x4B07C8–0x4B2A6C` — field prop/gimmick effect configuration and destructor helpers.
- `0x4B60F8–0x4B63D8` — a real **path builder** (`Path_BuildFromPoints`, six callers including
  both camera paths, the model-view path table and the field model-slot emitter) and its
  direction computation.
- `0x4B7304–0x4BC548` — grid cursor, strength-compare/sakusen windows, auto-battle action update,
  event actor-model manager (ctor, model slots, `%s.ani` animation switch, 47×6 part resource
  loading) and battle popup spawning.
- `0x4BF1A4–0x4C13B0` — battle UI model handle release/display id, field actor-focus movement,
  four-state widget ctor and the battle target-group marker rectangle.

## Load-bearing findings for later lanes

- **`0x00100050` is `std_ConstructArray(dst, ctor, stride, count)`**, not memcpy. Its body is a
  counted loop calling a function pointer with a stride; Ghidra marks it noreturn, which is why
  ~35 readable-C bodies in this batch appear to "end" at it. This independently confirms N_087's
  and N_091's reading. Almost every UI ctor here is just "install vtable + construct N sub-objects
  of stride S".
- **`0x0011FE8C` is popcount** (0x55555555/0x33333333/0x0F0F0F0F constants), and the "if
  (`*flag`) { alloc; align; construct; store }" prologue that appears in dozens of functions is the
  inlined lazy construction of the **game work singleton** (`pointer 0x007BE320`, storage
  `0x00804160`, size `0x2FB28`), built from 31 records of `0x12EC` bytes (`0x24A94` total) plus a
  sub-manager at `+0x24A98`. The same singleton carries the 50-record party/Dive table at
  `+0x5FE4` and the effect-anchor block at `+0x2A62C`.
- The vtable → class map is the cheapest way to name this band; the vtables I used are recorded in
  each entry's evidence, e.g. `0x774220` (Battle_Ui), `0x774FDC` (ArcListWindow), `0x7776F38`
  (Event_ActorModels), `0x772A98` (Battle_Popup), `0x773B40` (PokerDisplayWindow),
  `0x776C84` (RouletteSelectGrid), `0x777B9C` (FourStateWidget).

## Result and validation

- 150/150 addresses, exactly once, in batch order.
- Exact seven-key schema; 150 unique names; zero collisions with the 477 project symbols and all
  86 sibling batches (two initial clashes were renamed: `Ui_EquipmentRow_Ctor` →
  `Ui_EquipmentRow_CtorSmall`, `Ui_PartySelectWindow_Ctor` → `Ui_PartySelectWindow_CtorRows`).
- Every name appears in its own signature; every `params` value appears in the signature
  (`param_1`/`param_2` keys map to descriptive names as required); ASCII only.
- Confidence 0.30–0.70, mean 0.508; exactly the 78 entries below 0.50 are `maybe_`-prefixed and
  none at or above 0.50 is. Prefix histogram after stripping `maybe_`: Ui 56, Battle 41, Event 12,
  Field 9, Actor 9, Text 8, BattleScene 5, Monster 2, Path 2, and one each of Effect, Font, Game,
  Fs, Gfx, Condition.
- Mechanical validation via `%TEMP%/opencode/n090/merge.py`: JSON parse, 150/150 in batch order,
  exact key set, name regex, confidence/prefix rule both ways, name-in-signature,
  params-value-in-signature, ASCII, uniqueness, cross-batch + project-symbol collision scan →
  `ERRORS 0`.
- Per the task, I did **not** run `tests/run_all.py` or `tools/verify_project.py` (naming-lane
  exemption; no code, data or asset was changed, so the bit-matching build is untouched).

## Honest gaps

- Fully static: no emulator, debugger or playtest. Every mechanism claim is from bytes; purpose
  labels are inference. Nothing here is "verified in game".
- The weakest entries are the Ghidra-damaged bodies that the export reduced to a single
  `std_ConstructArray` call with lost arguments (`0x474084`, `0x4A4CBC`, `0x4A9FE4`, `0x4AA28C`,
  `0x4A25DC`, `0x4A25F0`). They are 0.30–0.35 placeholders named from their call sites only.
- `0x4A4BB4` (`maybe_Condition_ClearStruct`) is a 0x59-byte struct clear used by eight unrelated
  UI/battle callers; the struct's meaning is not recoverable from the binary.
- `0x442278`/`0x443B60`: the work singleton is provable, the "effect anchor" / "Dive capture"
  purposes are inferred from the single reader and the neighbouring screen code respectively.
- `0x4B8DEC`, `0x4B979C`, `0x4BA3F0`, `0x4BB154`: the resource-loading loops (47×6 entries,
  `.ani`/`.bxon`/`.bch`, `m210b`, unit id 400 special case) are exact, but which model class each
  row owns is not.
- Some sibling lane names I leaned on are themselves `maybe_` (`maybe_Party_FindEntryById`,
  `maybe_Actor_ReleaseTailMember`), so my entries inherit that uncertainty; the merge should
  re-check `0x66B11C` and `0x66AE3C` together.
- The batch header should be re-labelled: `Ui_and_BattleUi` + `Event_ActorModels` + `Actor_Action`,
  not `Save_and_Persistence`.
