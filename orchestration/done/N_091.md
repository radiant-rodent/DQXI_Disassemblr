## Method

Tooling in `%TEMP%/opencode/n091/`:

* `prep.py` — name map from `symbols.json` (477), `symbols_recovered.json` (460),
  `decomp/native_names.json` (454) and 85 sibling `out/N_*.json` (~12.6k address→name pairs);
  one-pass index over all 18,367 `decomp/readable/{functions,recovered}/*.c` (signature, callees,
  `g_` references, body); caller index; ASCII-run table of `original/exefs/code.decompressed.bin`
  (base 0x00100000).
* `dg.py` — per-function digest: signature, real callers (self-references removed), callee names and
  sibling summaries, **vtable-slot membership** (scans .data for the function's 4-byte value in runs of
  code pointers), literal pool classified as vtable / string / float, and the pseudo-C body.
* `vtdump.py` — dumps a data range as code pointers annotated with known names. This is what
  identified the class families: e.g. the vtable at 0x7799CC (Ui_MessageSelectWindow slots), the
  arc-list vtable at 0x77CE2C, the BCH/FLIM strings, the `Ui_Widget_DestroyChildren` slot of 0x781348.
* `armdis.py` — capstone disassembly with literal-pool resolution, used where Ghidra truncated a body
  at a tail call (0x4D4F5C is really 0x20C bytes, not the 4 lines Ghidra emitted).
* `peek.py` / `show.py` — read arbitrary functions (callers, callees, globals, body).

Work was bottom-up: the shared helpers were pinned first (`std_ConstructArray` 0x100050 takes
(dst, ctor, **stride**, **count**) — verified from its body, which matters because several
constructors are one line of pseudo-C), then `Ui_Object_CtorBase`, `Ui_Object_InitMemberPair`,
`Fs_FormatResultCode`, `Gfx_ResourceSet_Parse`, the vtable-slot map, and only then the callers.

## Honest gaps (not verified)

* **Fully static.** No emulator, debugger or playtest was run (naming lane: no code, data or asset
  changed). Mechanisms come from bytes; purpose labels are inference.
* 0x4C1680/0x4C1950/0x4C1E88/0x4C201C: the group walk (26 pointers per 0x68 block at +0x220, unit id
  at +0x768, monster-table lookups) is certain; that the widget is the **enemy target marker** rather
  than, say, a party/enemy list frame is my reading of the neighbouring `Battle_Ui_*TargetMarker*`
  names. 0.4–0.5.
* 0x4D3EC8/0x4D450C/0x4D49A4: the vtable (0x7799CC) contains `Ui_MessageSelectWindow_*` and
  `Ui_ListWindow_EnsureEntryVisible` slots, but the bodies walk the same 4×26 battle-unit blocks as
  the 0x4C1xxx cluster. I named them `Battle_Ui_TargetPanel_*`; they may belong to a window class
  shared by both systems.
* 0x4F91FC: sitting in the arc-list vtable family and using 1/(2π) is strong, but "ring layout" is
  inferred from the constants, not from a confirmed call site.
* The `Ui_*Ctor_vt<addr>` names (0x4C7F6C, 0x4CC93C, 0x4CE908, 0x4DC408, 0x4DC8E4, 0x4E7E68,
  0x4FA5EC, 0x4FBEC4, 0x4D6B34, 0x4CFF2C, 0x4D9EEC, 0x4EE7A8, 0x4F8E9C, 0x4EFAC8): the vtable address
  and the element counts/strides are facts, the class name is not recoverable from them.
* 0x509100, 0x5096C8: Ghidra lost the arguments of the `std_ConstructArray` tail calls; 0.30, only
  the family is certain.
* 0x505FD8: alignment/format-switch structure is clear, but the packed "status" constants and the
  format table were not resolved against a PICA200/ETC reference.
* 0x502F24/0x502E20/0x502CB4/0x5024A8: the 0x8C/0xD/0x10 code table is copied mechanically from the
  three copies of the same switch; what each code *means* (open/read/create) is not established.
* Two IPC stubs are named only by their fixed headers (`Svc_Ipc_Cmd1007`, `Svc_Ipc_Cmd001E`); the
  service behind them is unknown (cf. the N_079/N_082 note that the exheader service list was never
  dumped).
* 0x503298/0x503888/0x503A7C/0x503B78 are 0.45–0.55: they are the Fs request builder/read paths by
  caller and by the 0x7D0000 buffers, but the per-kind argument table is not decoded.
