## What the range actually is

The batch header says **"Save_and_Persistence"**, and that label is wrong for all 150 addresses.
There is no save/load, no file-format writer and no persistence code in the range. The label is a
propagated one (`tools/make_naming_batches.py` propagates the domain of the nearest named function),
and here it stuck to a block that is really the **message-window text renderer** followed by the
**NW4C-style sound library**.

## Method

1. Name map (project symbols + all sibling `out/N_*.json` names) from `symbols.json`,
   `symbols_recovered.json`, `decomp/native_names.json` and `orchestration/naming/out/*.json`.
   `N_014.json` is invalid UTF-8 and was skipped for the collision scan.
2. Caller index over all readable C files (`decomp/readable/functions`), after stripping the
   generated header comment (otherwise every function "calls" itself).
3. Per-function digest (size, annotated callers/callees, `g_` globals, full body), concatenated in
   batch order and read in full: all 150 bodies, ~235 KB of C. Leaf functions first, then their
   callers, as the task asks.
4. Sibling-batch names supplied the vocabulary for the two families: `Text_BuildGlyphQuads`
   (`0x0055B984`), `Font_*`, `TextBox_AllocBuffer` (`0x0053F344`) for the text side, and
   `Sound_WaveCache_*`, `Sound_SeqPlayer_*`, `Sound_Voice_*` for the sound side.
5. **Disassembly for the bodies Ghidra truncated.** ~14 of the 150 C exports stop at a call to
   `0x00100050`, because Ghidra decided that helper does not return. `0x00100050` is actually
   *construct-array* (`for (i<count) { ctor(dst); dst += stride; }`, it returns `arg1`), so those
   exports are only the constructor prefix. Every such body was cross-checked against
   `asm/text/text_00500048.s` / `text_00540048.s` and named from the visible prefix + the assembly
   shape (e.g. `0x0053B6DC` really does build four 2D vectors and then loop emitting quads).
6. No string evidence was available and none is claimed: every `g_` constant used by these functions
   is a 0x10/0x18/0x20-byte PICA command template or a float/scaling constant, not a string. The
   evidence in the JSON is therefore structural (vtables, command bytes, magic/version checks, callee
   families, field offsets).

## Naming decisions

* Prefix after stripping `maybe_`: **Sound 103, Text 34, Ui 11, TextBox 2**. This matches the two
  real families and the existing project vocabulary; the batch label was deliberately *not* honoured
  by inventing save-system names.
* `Text_*` is used for the message-window command builder (it builds glyph quads and window frame
  slices, next to the already-named `TextBox_*` and `Text_BuildGlyphQuads`), `Ui_*` for the widget
  draw helpers and class constructors that are not text-specific.
* Class constructors whose exact role is not recoverable but whose vtable and allocation size are
  facts are named by size (`Text_Node_Ctor_C0`, `Text_Node_Ctor_D8`, `Text_Node_Ctor_A4`,
  `Text_Node_Ctor_100`, `Sound_SeqPlayer_Ctor_3C8`), with the vtable address in the evidence. No
  invented class names.
* `0x00546D3A` is not a real entry point: Ghidra split it out of `0x00545520` and it reads its
  arguments from the caller's stack. It is kept as `maybe_Sound_StartSeqPlayer_Tail` at 0.30 rather
  than given a substantive name.

## NOT verified / open problems

* Everything is static. There was no emulator or debugger run, so the *mechanisms* are read from the
  bytes while the *purpose labels* are the inferred part.
* The text/glyph class hierarchy is not verified against RTTI. The vtables (`0x00538FE0`,
  `0x00540354`, `0x00540500`, `0x0053E8D4`, `0x0053ECE8`, `0x0053EE6C`, `0x0053FE6C`,
  `0x00541790`, `0x005419F0`) and the object sizes are facts, but which class is a character pane vs
  a paragraph pane vs a window frame is not. The `Text_Frame_*` vs `Text_Glyph_*` split is a reading
  of the data flow (part count 4/8 = border slices), not a confirmed class name.
* ~14 bodies are only partially decompiled (see method 5). Their tails are described from assembly
  shape only: `0x0053B6DC`, `0x00540BC4`, `0x00541798`, `0x005419FC`,
  `0x00541EC0`, `0x00545BDC`, `0x00554670`, `0x0054EF3C`, `0x0054FADC`, `0x00557410`,
  `0x005575D0`. Re-exporting them with `0x00100050` correctly typed as returning would
  let a follow-up give them full bodies.
* `0x00546D3A` (0.30) and the two `*_ConstructArray` thunks (`0x0054EF3C`, `0x00557410`, 0.35) are
  deliberately vague.
* The sound-side names follow the existing project vocabulary (`Sound_*`, module 0x54xxxx); the snd
  library is Nintendo's NW4C-style API, but no SDK header was available, so names describe observable
  behaviour (queue command id + payload, magic check, list operation) rather than official API names.
* The Squirrel script corpus was not used: these are internal engine routines, not Squirrel natives
  (the native binding table lives in the 0x15xxxx band, per `N_085`), so no script references them.
* `0x00558210` is shared by both families (text UV command writer and sound command-block writer); it
  is named after the text use (`Ui_CommandBlock_Write`) because that is where it is called most.
