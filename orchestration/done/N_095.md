## What the batch actually is (the header label is wrong)

The batch header says `Save_and_Persistence - 150 unnamed functions`. That label is a
propagation artefact: the address band `0x005D1858-0x00604B1C` is a cross-section of the module,
not a save subsystem. Measured against the names other lanes already gave the same pages, the
content is:

| group | addresses | entries |
|---|---|---:|
| **Field gimmick actor** (embedded sub-objects, state machines, message senders) | `0x5D1858-0x5E5024` | 74 |
| **Save data / Spell-of-Restoration code + Blowfish + CRCs** | `0x5EF028-0x5F1F08` | 19 |
| **Container / UI list / actor-data helpers** | `0x5E6784-0x5E945C` | 16 |
| **Sound engine** (command queue, mutexes, stream player) | `0x5EA564-0x5EB378` | 11 |
| **MoLive** decoder nodes | `0x5EBF8C-0x5EC4E8` | 4 |
| **Gfx / Field scene node / Ui balloon / Squirrel VM / hash table** | `0x5F36E0-0x60029C` | 12 |
| **Battle scene unit-model layout** | `0x602664-0x604B1C` | 11 |
| **Not code** (literal pools Ghidra promoted to entry points) | `0x5DB99E`, `0x5DBAEE`, `0x5DF5AE` | 3 |

(74 + 19 + 16 + 11 + 4 + 12 + 11 + 3 = 150.)

Only the `0x5EF028-0x5F1F08` block is genuinely persistence code — which is presumably why the
range got that label.

## Method

1. **Name map first.** Merged `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 93 sibling `orchestration/naming/out/N_*.json`
   (`N_014.json` is not valid UTF-8; it was read with `errors="replace"`). Those names anchored
   every cluster, e.g. `0x5D5D2C Field_Gimmick_LayoutPartsForAction`, `0x5E2594
   Field_Gimmick_SendEventType7`, `0x5EF33C SaveCode_Encode`, `0x5F87C4 Ui_Balloon_BindWinParts`,
   `0x600010 Sq_HashTable_FindKey`, `0x601CCC BattleScene_SyncUnitModels`.
2. **Fresh caller/callee index** over all 18,748 files in `decomp/readable` (calls only, header
   comments stripped, self-calls removed). This proved that most of the batch has **no C-level
   caller at all** — they are constructors referenced from vtables/literal pools, so neighbour
   context and construction order inside `0x5E4A78` were used instead.
3. **Literal-pool dereference** against `original/exefs/code.decompressed.bin` (base `0x00100000`):
   resolved every `g_005Dxxxx` / `g_005Exxxx` "global" from the readable C to its real value, which
   turned `*obj = g_005D6014` into "installs vtable `0x783D98`" and let me confirm which tiny
   objects are handle slots (sentinel `0xFFFFF800`), which are listener arrays (N x 0x18) and
   which are pointer lists.
4. **Read all 150 readable C bodies**, leaf-first in address order, then the raw ARM/Thumb listing
   in `asm/text/text_005C0048.s` for every body whose meaning depended on a lost register, a lost
   float argument or a Ghidra `halt_baddata`. That resolved 12 bodies the C alone cannot explain
   (see "recovered from disassembly" below).
5. **Saved progress in three passes** (50 / 43 / 57 entries) so a resumed worker could continue
   between them.

## Load-bearing findings

* **`0x5E4A78` is the master constructor of the field-gimmick object.** One body chains ~24 of
  this batch's constructors at fixed offsets (`+0x7C`, `+0xE4`, `+0x28`, `+0x14`, `+0x40`,
  `+0xDC`, `+0x18`, `+0x78`, `+0x158`, `+0x1D8`, …). This is what turns a pile of anonymous
  0x30-0x2B8-byte initialisers into a coherent class and is the basis for the
  `Field_Gimmick_Init*` names.
* **Two object-registry prologues** (`0x5D8B98`, `0x5DC838`, and `0x5E4A78` itself) publish an
  object as `id<<7 | generation` in a 0x40-entry table (`g_005D8E34`, `g_005DCDC8`), with
  `id = (counter+1) % 0x1FFFFFF`. Handle checks elsewhere in the batch (`>>0xB`, `&0x7FF`,
  `>>7`, `&0x7F`) use the same two encodings.
* **The 16 message senders** (`0x5E26C4..0x5E49F4`) are one family: fill a pending record, call
  the caller's virtual `+0x10`, then post through `0x5E5140(&self->f_C, cmd)` and store the
  result in `self->f_20`. N_073's `Field_Gimmick_SendEventType7` (0x5E2594) sits inside the same
  block and fixes their role.
* **`0x5EF028-0x5F1F08` is save data, and the cipher is Blowfish.**
  `0x5F0E14` zeroes an 0x48-byte P-array and a 0x1000-byte S-box block; `0x5F0E64` XORs the key
  into the 18-word P-array, runs 9 encrypt rounds to rewrite P and then 4 x 256 rounds to rewrite
  the S-boxes (the textbook `Blowfish_ExpandKey`); `0x5F14EC`/`0x5F19E8` walk 8-byte blocks
  through `0x5F1040`/`0x5F153C`; `0x5F1CC2` is the same cipher written with the four standard
  256-entry T-tables; and `0x5F0924` is *not* a CRC helper (my first guess) but
  `Save_Crypto_SetKeyFromString`, which feeds `strlen(key)` bytes into `0x5F0E64`.
  `0x5EF4F0`/`0x5EF914` extend the already-known `SaveCode_Encode`/`SaveCode_Decode`
  (0x5EF33C/0x5EF3CC) with the fixed-20 and variable-length code paths, and `0x5EFE3C` is their
  decode+verify counterpart.
* **`0x5E945C` is a pure arithmetic helper** (`Mem_CalcAlignedBufferRange`): align base, force
  element size >= 4, divide, write `{0, alignedBase, alignedBase+count*elemSize, elemSize}`.
  This one is mechanism-certain.
* **`0x5EB34C` / `0x5EB378` are the kernel mutex pair** — ARM11 `svc #0x14` (svcReleaseMutex) and
  `svc #0x24` (svcWaitSynchronization1), both followed by the OS error handler `0x118100`. They
  bracket the sound command-queue operations (`0x5EAEB4` commit, `0x5EAF40`/`0x5EB028` push into
  a 16-entry ring of 0x44-byte commands).

## Honest gaps (nothing was verified at runtime)

* **No emulator, no debugger, no playtest.** Everything here is static. No name was confirmed by
  watching behaviour; a wrong-but-plausible family label would not have been caught.
* **The gimmick family is named by construction site, not by class name.** I can prove each
  `Field_Gimmick_Init*`/`SendMessage*` belongs to the object built by `0x5E4A78`; I cannot prove
  which in-game feature ("wagon", "elevator", "save point", …) that object implements. Their
  vtables are all trivial (`{bx lr, bx lr, 0x101A9F}`), so the vtable adds no class name.
* **Sub-object suffixes `B`/`C`/`D` are disambiguators, not semantics** — several classes have
  2–4 identical members (`InitHandlePair`, `InitHandlePairB`, `InitHandlePairC`). They are
  distinguishable only by vtable address, which the evidence records.
* **`0x5E7F84`/`0x5E80A4`/`0x5E8218`/`0x5E82A0`** all resolve a u16 id through the game
  DataManager (`0x63E01C`/`0x63EEAC`, names unknown to every lane so far). I named them after
  the four-argument script ABI and the field each reads; the subsystem could be `Actor_`,
  `Data_` or `Script_`.
* **`0x5E8560` (`maybe_Field_Object_IsStatusFull`) and `0x5E82C4`
  (`maybe_Field_Object_GetModelScale`)** touch party/equipment state and the work record at
  `+0x24A98`; the arithmetic is exact, the purpose sentence is inference.
* **Battle-scene block (`0x602664-0x604B1C`)**: the mechanism (unit-model placement, ability
  checks against `0x1BBC0C`/`0x1BBF84`) is solid, the distinction between
  `LayoutUnitModel` / `AdjustUnitModelHeightA` / `B` is by call shape only.
* **`0x5F1C54`** is documented as the decrypt-side companion of `0x5F1CC2` purely by adjacency
  and one call site; Ghidra could not finish it, so its round order is unverified.
