Method, in the order I used it:

1. **Name map** from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all 93
   sibling `orchestration/naming/out/N_*.json`. This is what identified the region, because every
   neighbour was already named by somebody:
   - `0x006594D0 Gfx_GpuCmd_WriteTextureBind`, `0x006579C8 Gfx_GpuCmd_WriteTextureDescriptor`,
     `0x00655F58 Gfx_GpuCmd_WriteTextureUnits` (N_084) → the 0x00659xxx block is PICA command
     emission;
   - `0x0065EF6C maybe_Sound_WaveInfo_ParseFormat`, `0x0065E...` `Sound_WaveInfo_Read*` (N_035) →
     the 0x0065Fxxx/0x0066xxxx blocks are sound resource accessors;
   - `0x006639E4 Font_GetGlyphCell`, `0x0066503C Font_Atlas_LookupCell`,
     `0x0066509C Font_GetGlyphAdvance` (N_076) → the 0x00663xxx block is the font/glyph atlas;
   - `0x006647CC Container_HashMap_FindByKey` (N_021), `0x0063CDD8`/`0x0063D018`/`0x0063DED4`/
     `0x0063E998`/`0x0063F108`/`0x0063FFAC` (unnamed, sitting inside the N_021/N_031 data-table
     band) → the 0x00666xxx/0x0066Bxxx blocks are record lookups.
2. **Call graph** over all 18,748 files in `decomp/readable` (`%TEMP%/opencode/n097_graph.py`,
   cached to `n097_graph.json`), used to print, per batch address, the callees and callers with
   whatever names other batches had already given them.
3. **Read every body** (150 readable-C files, ~207 KB, dumped to `n097_c.txt` and read in four
   passes), leaves first, then their callers.
4. **Raw ARM listing** (`asm/text/text_00640048.s`, `text_00500048.s`) for every body whose meaning
   depended on a literal pool word or on float arguments that Ghidra dropped. That step produced
   the three findings that changed names:

   - `0x00508114` is **float → PICA FLOAT24** (`vmov r0,s0`, then pack sign at bit 23, 7-bit
     exponent, 16-bit mantissa). So `0x00659540` writes a quantised FLOAT24 constant plus register
     `0x000F004E`, using `128.0f` and `16777215.0f` from its own literal pool — not an address
     encoder.
   - `0x00672DB4` and `0x006731EC` are **saturating float→int** helpers (exponent decode with a
     ±0x17 clamp), *not* `sinf/cosf`. That turns `0x0065DCEC`/`0x0065DD98` into ratio/rotation
     maths rather than sine generation.
   - `0x005342D8` fills **128 floats (0x210 bytes)** by evaluating a linear ramp with a per-type
     switch. So `0x0065973C` builds a 0x218-byte ramp/state slot (8-byte header + 0x210 payload)
     keyed by a 16-bit id, and `0x00659B50` replays that slot into the command list only when the
     bound id changed (memcpy 0x210).

5. **Pattern extraction across families** (the time saver for 150 functions):
   - `0x0065F2F0..0x006630F8` is *one* family: field getters over a chunked record format, each
     parameterised by (sub-table offset, type code, default) and calling `0x00661534`. Types 0/1/2/4
     = byte / low byte / high byte / word; 8 and 9 chase relative pointers (9 adds a second
     dereference); 0x11 = flag bit; 0x1F = int. Defaults 0x3C (60), 0x40 (64), 0x60 (96), 0x7F
     (127), −1.
   - `0x0065DF90..0x0065E4A4` is *one* family too: ten vtable forwarders of the shape “call the base
     accessor, then let the attached extension object OR in its own value” (slots 0x0C, 0x18, 0x1C,
     0x24, 0x28, 0x2C, 0x38, 0x3C, 0x48, 0x50).
   - `0x006666xx..0x006668xx` is a set of small vtable implementations *of the same interface*
     (byte getters at style-record +0x12/+0x14/+0x15/+0x18, duplicated across classes), which is why
     three pairs are byte-identical bodies.
   - `0x00670A3C..0x00671E78` is the Field2D map/overlay object rebuild block: 0x40-stride object
     arrays compacted in place, objects rebuilt through `0x005BE5A8` / `0x005BE748` / `0x005C03C4` /
     `0x005CC878` / `0x005C95A4`, with 0x006719D4/0x00671A30 and 0x00671AA0/0x00671AFC being
     byte-identical twins (two virtual entries of the same interface).

## The region, in one paragraph

The batch label *“Save_and_Persistence”* is wrong for this range (it is a label propagated from the
address grouping, exactly as in N_088–N_093). What is actually here, in order: `0x0065854C` a hash
map slot lookup; `0x00659540–0x0065D1E0` PICA200 command emission for skinned model drawing
(texture/material constants, 0x218-byte ramp-state slots, part matrices, frustum-culled triangle
strips); `0x0065DCEC–0x0065DD98` matrix/ratio maths; `0x0065DF90–0x006617E8` sound sequence/voice
resource accessors plus the voice builder `0x006617E8` (`0x00555E38` + `0x005561BC`); the whole
`0x0065F...–0x006630F8` band of chunked-record field getters; `0x006633EC–0x006650F4` UI metric
getters, the font/glyph atlas page-and-cell sampler and the glyph-page selector; `0x00665A24`
combined bounds; `0x0066650C–0x006668B4` text-style predicates and style-record byte getters,
`0x006674A4` a pure-virtual trap, `0x00667xxx` text-window hit tests and list insert; `0x0066BE98–
0x0066D0D0` relative-offset chain resolvers in the data tables plus the U+000A→U+3000 text
normaliser `0x0066C834`; and `0x00670A3C–0x00671E78` the Field2D map/overlay object rebuilds.

## What is NOT verified

Be aware before consuming these names:

- **Nothing is runtime-verified.** No emulator run, no debugger, no playtest. Every entry is static.
  Mechanisms are bytes-backed; *purpose* labels are inference, which is why 108 entries stay
  `maybe_`.
- **Weakest groups** (0.30–0.40), in order of risk:
  - `0x0066650C` / `0x00666570` / `0x00666628` (`Text_Style_*`): the callers really are Text/UI code
    and the record really is reached through the style pointer at `self+0x175C`, but that record is
    not identified, so “style” is shorthand.
  - `0x00667A18` / `0x00667B40` / `0x00667E00` (`Text_Window_*`): the hit-test chain
    (`0x005C9F38` → `0x005BE14C`/`0x005C1098` → `0x005BDC98`) is clear; which window subclass each
    belongs to is not.
  - `0x0066BExxx..0x0066C34x` relative-offset resolvers: the link chasing is exact, the *table* they
    walk is not known.
  - `0x00670A3C..0x00671E78` (Field2D): every caller is a vtable, so there is no call-site evidence
    at all; only the shared builders and the 0x40-stride object arrays are certain.
  - `0x0066D0D0`, `0x0066D714`: lazily-created-singleton / thunk bodies with no callers.
- **The `Sound_` prefix** for `0x0065F87C–0x006630F8` and `0x00660A94–0x006612B4` rests on the
  neighbouring N_035 `Sound_WaveInfo*` names and on the 0x54xxxx/0x55xxxx callers — not on strings.
  If those N_035 names are re-labelled, these 44 entries should be revisited with them.
- **Two entries are byte-identical twins** by construction (`0x006719D4`/`0x00671A30`,
  `0x00671AA0`/`0x00671AFC`). I named them A/B rather than inventing a distinction; if the merge
  wants one canonical name, pick the first.
- `0x006633EC`/`0x00663418`/`0x00663444` are named by vtable slot (…C / …A / …B) because the slot
  order is all that distinguishes them; their semantic order (width vs height vs count) is unknown.
- No strings were available to disambiguate the 0x0066xxx tables; none of these functions reference
  rodata strings.
