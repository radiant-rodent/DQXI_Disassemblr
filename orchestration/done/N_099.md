## What the range actually is

The header label **"Save_and_Persistence"** is a batch-generator artefact - there is no save or
persistence code in this band (the real save/crypto code is at `0x5EF028-0x5F1F08`, see N_095). What
this band contains is **one contiguous block of the Squirrel script-native binding trampolines**:
the closure bodies that `Sq_BindNativeMethod` (0x006BC528) installs in the script root tables. It sits
between N_098's identical block (`0x6F5728-0x6F978C`, ends with `Script_Native_ActorGetCtrlOption`)
and N_100's (`0x705FF0-0x7077A4`, starts with `Script_Bind_CameraShakeEx`); the three batches are one
table split into three, so the whole run `0x6F5728..0x7077A4` is script bindings.

### The binding mechanism (established from the code, not guessed)

Every registration is a call `Sq_BindNativeMethod(table, "Name", &implPtr, 4, stubPtr, 0)` whose
literal pool holds `[impl ptr][name string][stub ptr]` in that order. `Sq_BindNativeMethod` pushes the
name, builds a one-element array from `&implPtr`, and creates the closure with `stubPtr` as its code
and that array as its single free variable. Consequently:

* the **stub** (= the function in this batch) is a *signature-specialised trampoline*, not the
  implementation. It reads the VM's stack depth (`0x006BBD6C`), raises
  `"wrong number of parameters"` if the arity does not match, converts each argument with the
  matching converter (`Script_GetIntArg` 0x00576478, `Script_GetIntegerArg` 0x007078E4,
  `Script_GetPlayerIdArg` 0x00576220, `Script_GetFloatArg` 0x0057629C, byte/`0x00576388`,
  bool/`0x006BDA0C`, string/`0x006BDA58`), fetches the real implementation out of the closure
  environment (`0x006BBDAC(...,-1,...)`), calls it, and pushes the result with `0x006BC6C8` (int,
  sometimes narrowed to u16), `0x006BC600` (bool) or nothing at all.
* because the behaviour depends only on the *signature shape*, **one stub serves many script names**.
  In this batch 26 of 150 stubs are shared; the largest serves **28** natives and one serves 25. In
  total the 150 stubs cover **280 distinct script natives**.
* each stub embeds the **type name(s)** it validates against (`"xp::ItemID"`, `"xp::PlayerID"`, ...)
  and the **table bound** it enforces (`0x2AD` global flags, `0x59` quests, `0x137` scenario battles,
  `0x15` revival points, ...). Those are the strongest semantic evidence in the band and are quoted
  per entry.

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`, all 150 readable C
   bodies from the batch list (no fall-backs needed) and the two neighbours' done reports.
2. Found that the stubs have **no static callers at all** (no BL, no pointer word anywhere in
   `code.decompressed.bin`), which is what led to the registration-table hunt.
3. Decoded the registration tables: scan `.text` for a word pointing at a script name string, take
   `[impl][name][stub]` and require the stub to have a `Sq_BindNativeMethod` call site. 276
   registrations recovered by that scan, 311 more via the decompiled C. Assigned each stub the set of
   names and implementations registered against it.
4. **Cross-validated the pairing**: for 148 of 150 stubs the recovered implementation name is
   *identical* to the registered script name (`SpiritMessage` for `SpiritMessage`,
   `SetRecordFlag` for `SetRecordFlag`, ...) using `decomp/functions_index.json` +
   `symbols.json` + `symbols_recovered.json`. The only two exceptions are `SetRevivalPointID`
   (impl 0x00155540) and `SetQuestFlag` (impl 0x0014A8A4), whose implementations are unnamed in
   every name source. A systematic off-by-one in the name↔stub pairing would have shown up as ~150
   mismatches, so this is strong evidence the table decode is correct.
5. Extracted per-argument types from the `Script_FormatTypeError` calls
   (`func_00576564(..., arg1, <index>, g_<typeName>)`) and per-argument range checks from the C, so
   argument order in the prototypes is data, not intuition.
6. Checked every "rejects ids above N" claim against the extracted constants mechanically (150/150
   consistent); fixed two summaries where the first draft attributed the `>>9` narrowing to the wrong
   argument.

## Naming decisions (for the merge step)

* Prefix `Script_Bind_` (e.g. `Script_Bind_SetRecordFlag`): the function is the *binding trampoline*
  for that script native, and the prefix avoids colliding with the implementation of the same name
  (`SetRecordFlag` at 0x0014C8A4), which the merge would otherwise duplicate.
  Sibling lanes used two other spellings for the same species: N_098 `Script_Native_*`,
  N_100 `Script_Bind_*`. **Recommendation: normalise all three runs to `Script_Bind_*`.**
* Primary name for a shared stub = the **first registration in table order** (lowest literal
  address); every alias is listed in `evidence`, and the summary says how many natives share the body
  and what the signature shape is. The alias list is the part a reader needs when debugging a
  *different* native that lands on the same stub.
* Prototypes name the script-level signature (`SetMessageArgItemName(xp::TextArgID slot, xp::ItemID
  item)`), while `signature`/`params` describe the real C signature of the stub
  (`u32 Script_Bind_X(ScriptVm* vm)` with `param_1 = vm`), consistent with the template.

## Honest gaps / not verified

* Everything is **static analysis**. No emulator run, no debugger, no playtest; nothing here has been
  observed executing.
* The *semantic* parameter names in the prototypes (e.g. "fadeMs", "gimmick") are read off the
  native's own name and the implementation; the argument **count, type and bound** are data, the
  English noun is interpretation. Where the implementation name did not make the meaning obvious I
  wrote `int param` instead of guessing.
* `0x00702098 PlayerSetFieldAction`: the name is certain (the string sits directly before the stub in
  the table) but its registration call was not recovered, so the implementation pointer is unknown
  and the entry is at confidence 0.70.
* `0x00155540` (`SetRevivalPointID`) and `0x0014A8A4` (`SetQuestFlag`) implementations are unnamed
  everywhere; they are cited by address.
* The two "second int" arguments of `StopSE`, `PlayBGM`, `StartFadeOut`-family calls are described
  generically (fade/duration/flag) because the stub only proves they are integers.
