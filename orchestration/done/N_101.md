# N_101 — native naming batch `0x0011EE0C-0x00721C34` (136 functions)

Status: **completed** (136/136 addresses), static analysis only.
Owned file: `orchestration/naming/out/N_101.json` (102,455 bytes, 136 entries).

## What I did

Resumed lane. There was nothing to resume: `orchestration/naming/out/N_101.json`,
`orchestration/done/N_101.md` and any `N_101` entry in `AGENT_LOG.md` did not exist, so all 136
entries are new work (no partial file, no scratch under `orchestration/`). All scratch stayed in
`%TEMP%/opencode/n101/`.

Method, in the order I used it:

1. **Name map** built from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and
   all 93 sibling `orchestration/naming/out/N_*.json`. This anchored most callees even though the
   batch itself contains almost no *named* function: `Gfx_CharModel_BindResources`,
   `Anim_ModelLoad_ByName`, `Anim_UpdateChannels`, `Model_Attach_ComputeWorldMatrix`,
   `maybe_Gfx_Movie_*`, `Font_Atlas_LookupCell`, `Script_ThreadWakeup`, `Sq_VmExecute`,
   `Pack_GetManager`, `Fs_NamedObject_LoadSimple`, etc.
2. **Full call graph** over all 18,748 files in `decomp/readable` (`analyze.py`): per batch address,
   callers and callees with any known names, plus the globals each body touches. 85 of 136 have at
   least one C-level caller; the rest are constructors/destructors reached through vtables.
3. **Read every body** (136 readable-C files, ~240 KB, dumped by `brief.py` with callers/callees
   inline and read leaves-first in ten passes).
4. **Raw ARM listing** (`asm/text/*.s`) for every body Ghidra damaged or truncated. That step is what
   turned three "placeholder" entries into real ones and corrected four names:
   - `0x00421628` is a normal list insert (`ctx+0x100C`, node `self+0x1C`), not a mystery thunk.
   - `0x0029E498` really *returns* a byte property (default `0x80`) read through the ±0x60-stride
     table at `ctx+0xF50` via `0x006651D4`; Ghidra lost both the return and the second lookup.
   - `0x00267BC4` is a normal "advance marker, then walk handle array" update; the `halt_baddata()`
     tail is Ghidra giving up, not bad code.
5. **Literal/constant work** for the ambiguous ones: 255.0f / 1.0f / 400x240 constants, the `0x7C`-stride
   per-screen matrices, the `0x60`-stride node arrays, the `0x40`-stride 2-D layer animators, the
   `0x74`-stride layout tweens, and the `0x5AC`-range keyframe tables.

## Main results

Load-bearing facts established or confirmed here (reusable by other lanes):

- **`0x006F250C` is `Gfx_GetContext`** — the lazily allocated process-wide graphics context (guard
  `g_006F29EC`, holder `g_006F29F0`, size `g_006F29F8`, vtable `g_006F29FC`, three 0xDC-byte
  sub-objects built with `std_ConstructArray` + ctor `g_006F2A00`). 131 callers in the tree reach it
  (camera, model attach, UI overlay/window/sprite, font, movie, sky). Its layout now has a map:
  `+0x2A4` attach-slot lists, `+0x304/+0x310/+0x31C` UI sprite layers, `+0x754+screen*0x7C` and
  `+0x84C` camera/projection matrices, `+0x8C8/+0x994/+0xA60` the three material layers,
  `+0xD90/+0xD98` sky texture, `+0xDD8` material colour, `+0xE6C` scene-sprite layer lists,
  `+0xF50` 2-D texture/glyph page, `+0xF68` BG-layer visibility mask, `+0xFE8` window draw list,
  `+0xFF4` unit-slot list, `+0x1000` anim list, `+0x100C` primary UI list, `+0x10B0` face controller,
  `+0x10C8..+0x10FD` 2-D colour presets, `+0x1200..+0x125C` screen fade/weather, `+0x12F0..+0x1300`
  overlay flash RGBA, `+0x1308..+0x1334` 2-D viewport/scroll, `+0x1340` draw-group counter,
  `+0x1346` UI-hide bits.
- **Model attach-slot family** (`0x00222148/0x002259CC/0x00225A9C/0x00225B78/0x00225BCC/0x002227B0/
  0x00222B54`): show/hide/ref-count visibility and resource release. `0x0010EBE4` is the
  intrusive-list insert/unlink and `0x001235A4` the list splice, which is what makes the
  "attach"/"detach" reading certain.
- **Two distinct camera writers**: `0x00297D04 Gfx_SetCameraMatrix` (full descriptor: pos, target, up,
  fov) and `0x00282CFC Gfx_SetCameraLookAt` (eye/target + fixed world-up). Both write the same
  `+0x84C..+0x8C0` matrix/projection block; `0x002435E0` is the senreki-monster-list variant of the
  same code, using layout panes and three monster models named in its strings.
- **Movie player** `0x004FE174` (`Gfx_Movie_Update`): buffer consume → thread start/stop/join →
  timeline advance → present, with state `+0x1038/+0x104C/+0x1050/+0x1052`; `0x004FF6E8`
  (`Gfx_Movie_HasFrameReady`) and `0x004FE0DC` (`Gfx_Movie_StartPlayback`) are its leaf helpers.
- **Animation pipeline** `0x005ACEC8 Anim_UpdateModelInstance`: material-layer refresh, end/blend
  handling, key search (`0x005AC3AC`), two event/attach tracks (`0x005AC4E8`, `0x005AC824`), then
  per-node transform evaluation (`0x005A7514`, with matrix composition in `0x00664130`). The release
  side is `0x005AD1CC` (+ `0x005B09F8` owner dtor) and the busy test is `0x00666BC8`.
- **2-D background/texture layer code** (`0x0061BFD8` level_2dtimeVisual, `0x0061C544`, `0x0061CDC8`,
  `0x0061CC6C`, `0x0061CA84`, `0x0056545C`): four 6-byte page entries at `+0x60`, three
  `0x40`-stride layer animators, and `0x0061CF58` configuring those animators from a preset. Colours
  are packed from 0..1 floats with a 255.0f multiplier into `+0x10C8..+0x10FD`.
  (This also corrected my first-draft names: this block is not font code — a sibling lane's
  `Font_ApplyGlyphMetrics` label on `0x0061CF58` does not fit the call site, and I used the address,
  not that label, in the evidence.)
- **`0x006BDBE4` is Squirrel `sq_resume`** — `Sq_VmExecute(..., 2|3)`, string
  `"cannot resume a vm that is not running"`, callers `Script_ThreadWakeup` and
  `Ui_SceneFlow_UpdateFadeAndJobs`.
- **`0x00721C34` is `std_Introsort`** (median-of-three quicksort + heapsort fallback, 16-element
  threshold); its only caller sorts the 18 UI layout-animation entries with comparator `0x0045503C`.
- **Sky/weather**: `0x0061DBCC` binds the sky model and picks `sky_cloud`/`sky_ruin`/`sky_ruin_cloud`/
  `sky_zorude`/`sky_red`/`sky_dark`; `0x00620804` is the `BG3DChangeFog`-facing "set sky texture by
  name" wrapper; `0x00194588`/`0x001945D4` are the model-resource name lookups (value vs texture id).
- **Level loaders**: `0x00610118` loads `level_mapType.bxon` / `level_weatherVisual.bxon` /
  `textures.bch` and stores the `encount2d` texture id at `ctx+0x1194`; `0x00610784` resets that
  whole level state; `0x0061BFD8` loads the 2-D time/weather set.

## Honest gaps

- **The batch label is wrong.** `N_101` is called `IO_and_Files`, but the address set contains no
  file/PACK function except two level-resource loaders; it is overwhelmingly **Gfx/Model/UI/Anim**
  code (spread over one function each in dozens of clusters). I named by behaviour, not by the label.
  Suggested: remove/re-label this batch in `batches/index.json`.
- **Everything is static.** No emulator, debugger, screenshot or playtest was used; no claim here is
  confirmed at runtime. "Purpose" words (fade, blink, popup, sky) are inferred from callers,
  strings and constants, while the *mechanism* is byte-backed.
- Weakest entries (all `maybe_`, confidence ≤ 0.35):
  - `0x002C6A0C` / `0x002C6A64` (`maybe_Ui_Screen_*SubObjects`): the vtable installs and the
    `+0x2EC` member block are certain, the class is not; the trailing `0x0010F6CC` in the first one
    looks like a delete but a constructor should not delete, so the direction of the function is open.
  - `0x004215F4` / `0x004222A4` / `0x0047E63C` (`maybe_Ui_DrawList_Merge*`): the list insert/splice
    call is certain, the lost third argument means "merge from" vs "merge to" is a guess.
  - `0x006E75FC` / `0x006E76B0` (`maybe_Script_*_DtorDelete`): they are clearly deleting destructors
    of two sibling vtable classes at `0x006E7620` / `0x006E76D4`; the second class's methods are the
    tagged value constructors (int/float/u16/list), the first class's methods manipulate a 0x58-stride
    element list. Neither class has a name anywhere in the project yet.
  - `0x001CA060`, `0x0022C390`, `0x0029E498`, `0x00454C34`: bodies Ghidra truncated or whose
    arguments are lost; mechanism described, purpose hedged.
- **`0x00220F78`** (largest, 0x478 bytes) is heavily damaged in the export (bad instruction data /
  `halt_baddata`). The cblm/cbhm strings, the resource lookups and the field writes justify
  `maybe_Model_ApplyResourceAppearance`, but roughly a third of the body is unreadable, so a future
  pass should decompile it from the raw ARM before anything relies on it.
- **Sibling names are not gospel.** Two labels I inherited from other batches did not survive my own
  reading: `Font_ApplyGlyphMetrics` on `0x0061CF58` (it is the 2-D background layer preset applier)
  and `Batch_*`-style names on the `0x0057CB78/0x0057CD58/0x0057E5F8/0x0057CE20` call cluster, which
  I cite by address only. If those batches are revised, re-check every entry here that cites them.
- The `Gfx_ModelResource_FindValueByName` / `..._FindTextureIdByName` pair is differentiated by field
  pair (`f_A8/f_AC` vs `f_54/f_58`) and call site, not by an authoritative struct definition; the
  "texture" half is solid (`sky_cloud` → `ctx+0xD90`), the "value" half is a little vaguer.
