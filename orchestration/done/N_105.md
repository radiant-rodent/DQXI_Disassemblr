## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`, and the
   two neighbouring done reports (N_101, N_103) for conventions.
2. Built a **name map** from `symbols.json` (477 symbols), `symbols_recovered.json` (460),
   `decomp/native_names.json` (454) and **all 104 sibling `orchestration/naming/out/N_*.json`**
   (14,951 address->name pairs). Every name I propose was checked for collision against all of
   them: **0 collisions**.
3. Built a **caller/callee index from the ARM itself** (`asm/text/*.s`, `bl`/`blx` immediate
   targets mapped to the enclosing function via `decomp/ghidra/functions_merged.jsonl`
   intervals). This was decisive: ~110 of the 150 have **no direct caller at all** - they are
   vtable slots, so the call-graph alone cannot identify them.
4. Because of that, built a **vtable membership index**: scanned every `.word` in
   `asm/data/*.s` + `asm/rodata/*.s` (161,231 words) for each batch address and printed +/-8
   words of context. That is where nearly all the class attributions come from - the
   neighbours are already-named functions from earlier lanes, e.g.
   `0x0072BB00` (Ui_ListWindow row states), `0x0072BExx` (Ui window actions),
   `0x007293D8` (Ui_DateDisplay), `0x007255xx` (Field actor motion), `0x0075Fxxxx`
   (Ui window / actor-action / Gfx node groups).
5. Read **all 150 bodies** in `decomp/readable/{functions,recovered}`. For the 21 bodies that
   Ghidra truncated (`halt_baddata`, `NO SOURCE`, or garbage `unaff_` pseudo-C) I read the raw
   ARM from `asm/text/text_00280048.s` / `text_002C0048.s` and hand-decoded the BL targets and
   literals; for the mid-function fragments I scanned backwards for the enclosing `push {...,lr}`
   prologue to find the real owner.
6. Read **strings and constants** straight out of `original/exefs/code.decompressed.bin`
   (base `0x00100000`): inline `.text` strings `"base"` (0x002BD6CC) and `"disabled"`
   (0x002BD6D4), the UTF-16 `"%d"` format literals (0x002B8F44/0x002B8F4C), the 1/30 s frame
   constant `0x3D088889` (g_00298670, g_002A5974), the 0.2 interpolation factor
   `0x3E4CCCCD` (g_002C05AC), the 0.5f sprite scale (g_002B3A58), and the class-type sentinels
   `0x007AE8A0` (g_002C31DC) / `0x007C33D4` (g_002B79C0).
7. Named bottom-up: leaves (deleting dtors, animator steps, formatters) first, then the
   state-machine drivers and event dispatchers that call them.

## Load-bearing identifications

- **`0x0010F6CC` is the object-free helper** every deleting destructor in this range ends in
  (`cmp r0,#0; r1=r0-8; ldrd; [vtable+4]; bx`). It is a *second entry inside* `0x0010F6BC`,
  which is why Ghidra shows those 8-16 byte bodies as "call X then call Y". That single fact
  identifies ~30 entries here as `*_DtorDelete`.
- **`0x00193E44` / `0x00193E40`** (inner entries of `0x00193D84`) are the shared Ui widget base
  destructors; **`0x00294C24` / `0x00294C88`** (of `0x00294C14` / `0x00294C74`) the shared
  actor-action ones. So "runs base dtor at 0x00193E44 then frees" = a widget deleting dtor.
- **`0x0029126C`** (inner entry of `0x00291220` `Ui_Widget_ReleaseSub`) is the "release this
  sub-widget" helper; it explains `0x002984A4`, `0x0029AEC4`, `0x00298BC4`.
- **`0x006F0F1C` is the wide `sprintf`** (its format arguments are UTF-16 `"%d"` literals
  inline in `.text`), and **`0x001A6680`** (inner entry of `0x001A664C`) is the
  "set text/label value" setter. Together they identify the whole `Ui_EquipmentWindow` and
  `Ui_MessageWindow` formatting block.
- **`0x00123594` / `0x001235A4`** are the intrusive-list attach/splice helpers; every
  `Ui_Window_StartActionNN` starts by attaching `child+0xD8` through them.
- **`0x00642710(self, id)`** starts a UI timer into `self+0x250`; the six
  `Ui_DateDisplay_EnterStateN` entries differ only in the id (6, 10, 7, 8, 4, 3).
- **`0x006C79A4`** is the inner "switch state" entry of the 4-state machine `0x006C7834`
  (`f_1c` pending count, `f_4` current state, 0x18-byte step records with enter/leave
  callbacks). It makes `Actor_Action_Move_AdvanceState` and
  `Actor_Action_Move_InterpolateToTarget` certain.
- The 9 `0x002B8Exx-0x002B90AC` entries are **not functions**: they are switch/loop blocks of
  the 0x1328-byte routine at `0x002B7DAC` (no prologue, use `r4..fp` from the caller, each
  block ends in `b 0x2B90B0`). They are named `maybe_Ui_MessageWindow_FormatNumberFragN` and
  documented as fragments. Same for `0x002A2C00` (inside `0x002A29A8`), `0x002B7700`/
  `0x002B7798`/`0x002B77FC` (inside `0x002B761C`), `0x002AFB04`/`0x002AFB24` (inside
  `0x002AFA88`) and the five `covered_by` entries.

## Result / validation

- **150/150** batch addresses, exactly once, in batch order; no extras, no duplicates.
- Exactly the seven required keys per object; every `name` appears in its own `signature`;
  `params` keys are `param_1..N` matching the signature order.
- **150 unique names**, **0 collisions** with the 477+460+454 project symbols and all 104
  sibling batches.
- `maybe_` prefix **iff** `confidence < 0.50` (117 entries). Confidence range 0.20-0.55,
  mean **0.431**. The distribution is honest: this batch is mostly vtable slots of classes
  whose *class* is certain (from the vtable neighbours) but whose *verb* is inferred from the
  body shape.
- Rule 5 exemption applied: this is a naming lane, `tests/run_all.py` / `tools/verify_project.py`
  were **not** run, and no code, data, asset or test file was touched.

## NOT verified

Everything here is **static**. No emulator run, no debugger, no playtest. In particular:

- The `Ui_ListWindow_ShowRowStateNN` family: the *state numbers* passed to the animator are
  literal and certain, but "row state" as the semantic is inherited from the earlier lanes
  (N_087 named 0x00298674 `ShowRowState10` the same way). If that reading is wrong, nine
  names here are wrong together.
- `Ui_TextWidget_Ctor` (0x002A55EC): the container/registry mechanics are certain, the
  "text widget" label rests on the 14 call sites all being in 0x0067xxxx-0x006Axxxx.
- `maybe_Actor_Action_CreateMoveSequence` (0x002BFA68): Ghidra emitted `halt_baddata`; the
  callee set (Anim_Sequence_CtorBase, Sound_PlaySeById, three 0x00423xxx helpers) is certain,
  the "move sequence" purpose is inferred from its neighbours in the move-action vtable group.
- `maybe_Ui_MessageWindow_CollectVisibleEntries` (0x002AFB24): the bitmask visibility test is
  read from the ARM (`tst mask, 1<<(v&0x1F)`), the caller-side meaning is inferred.
- The five `covered_by` / six false entries are documented as *not functions* rather than
  named - that is a deliberate, honest choice, not a gap in coverage.
- Class names (`Field_SceneObject`, `Actor2D`, `Gfx_SpriteNode`, `Ui_DateDisplay`, ...) are the
  names earlier lanes gave to the same vtables; if a later pass renames a class, the names
  here must be swept with it.
