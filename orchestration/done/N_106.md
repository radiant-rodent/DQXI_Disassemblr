## 2. Method (and how the addresses were actually identified)

Static only — no emulator run was needed for a naming task.

1. **Name map** built from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`
   and every sibling `orchestration/naming/out/N_*.json` (0 same-name collisions introduced).
   Important discovery: **lane N_051 overlaps this band** (`0x2F3140`–`0x30C4A4`) and had already
   named dozens of the *neighbours* of my 40 functions (`Field_Action_WalkUpdate`,
   `Field_Action_OpenDoor`, `maybe_Ui_SmallWindow_InputToState1`, …). Those names set the
   vocabulary I followed, so the merged symbol table will stay self-consistent.
2. **Caller/callee index** over `decomp/readable/{functions,recovered}`. Result: only 4 of my 40
   functions have a direct `bl` caller; the rest are virtual methods or table entries.
3. **Raw-binary work** against `build/code.bin` (base `0x00100000`, identical to
   `original/exefs/code.decompressed.bin`), with Capstone for ARM *and* Thumb:
   * literal-pool decoding (`ldr rX,[pc,#imm]`, `add rX,pc,#imm`) — this is what turned Ghidra's
     fake globals (`g_002fe874`, `uRam0030664c`, …) into real field offsets (`+0x3570`,
     `+0x0D5`-relative sentinels) and real format strings (the UTF-16 `L"%d"` at `0x002FE87C`);
   * **vtable recovery**: scanned `.rodata`/`.data` for runs of code pointers, then mapped each of
     my addresses to `vtable + slot`. 22 of the 40 are virtual methods or deleting destructors, and
     slot 0 of the recovered vtables is always the deleting destructor — this alone identified
     every `Field_Action_*` class;
   * vtable-install search (literal scan of `.text` for the vtable address) to find the
     constructor that owns a class where the direct-call path was empty;
   * an **ARM/Thumb `bl`/`blx` target scanner** to prove which batch addresses are real entry
     points and which are interior addresses (§5).
4. Cross-checked the Squirrel scripts (`game_assets/scripts/`) — the recovered natives in
   `symbols_recovered.json` (`XTV`, `Actor2DMove`, `CutSceneEnd`, …) do **not** touch this band, so
   they contributed nothing here; the UI/field action cluster is engine-internal.

## 3. What the remaining 40 functions are (the interesting results)

The band `0x002FE5BC`–`0x003083E4` is not "general procedures" — it is three contiguous
subsystems:

### 3.1 Ui window "action" starters (`0x002FE5BC`, `0x002FE7F4`, `0x002FECF0`, `0x003076C0`, `0x003083E4`)

All five are the **same function body** as the ten `Ui_Window_StartActionNN` entries that N_105
already named in `0x002A5Bxx`:

```
list_move(self+0x110, child+0xDC)        ; 0x00123594, an intrusive-list splice
self->vtbl[0x54](self, <actionId>, -1)   ; start window action <actionId>
```

Ids observed: `0x26`, `0x27`, `0x19` (this one passes the *count* of used text entries as the
third virtual argument instead of `-1`), `0x06`, `0x0D`. `0x002FE5BC`/`0x003083E4` additionally
pop pending entries first (`while (0x0062F070(self) > 1) 0x0010EBD8(self)`), and `0x002FE7F4`
formats `L"%d"` into a shared label at `(*0x007AC834)+0x848` from
`(allEntries - usedEntries - 50)`.

They are registered in the same **`{fn, 0}` step table** that runs from ~`0x0072B7FC` to
`0x0072C390` (8-byte entries: function pointer + zero word). This table is the backbone of the
whole band, and it is *not* referenced by any code pointer directly — it is indexed from a base
that the loader computes, which is why none of these functions has a caller in the readable C.

### 3.2 The `Field_Action` hierarchy (`0x0030069C` … `0x00304058`, 20 functions)

`0x00762854`–`0x00762BAC` is a **dense block of 15 contiguous vtables**, one per field-actor
"action" (what an NPC/player character is currently doing). Layout is uniform:

| slot | meaning | example |
|---|---|---|
| 0 | deleting destructor | `0x00300A9C Field_Action_CheckAny_DeletingDtor` |
| 1 | start | `0x00300AAC WalkStartToTarget` |
| 2 | update / cancel | `0x003013B8 MoveCollide` |
| 3 | end / finish | `0x00300A44 FinishIfDone` |
| 4..9 | shared base slots `0x00193C6C`, `0x00193CD8`, `0x00193CD4`, `0x0062A704`, `0x0062A714`, `0x0062A70C` | |

The object layout (recovered from the slot bodies): `+0x28` = owning actor; `+0x2C/+0x30/+0x34`
and `+0x38/+0x3C` = cached actor position/facing (written by
`0x0030069C Field_Action_SyncTransformFromActor`); `+0x40` = "movement blocked" latch; `+0x44` =
action-local flag. The action chain is: base (move-to-point) → CheckAny → Walk → Move(collide) →
Step → StepBehaviour → MoveDir → Nut → PlayStateAnim → AttachNamedEffect → OpenDoor → HorseInput →
Run → HorseStart → HorseMoveStep. Two classes expose the "may I continue?" predicate in slot 13
(`0x0030271C` for Run, `0x00303858` for both horse classes) returning `-1 / 2 / 3`.

### 3.3 Ui window state queue / text-line pool / DiveForm windows (`0x00304804` … `0x003083E4`, 15 functions)

* `0x00304840` / `0x00304804` are slot 6/7 of vtable `0x00762C4C`: a **two-slot state queue** at
  `self+0x35C` with a `0.5f` step timer, dispatching a member-function-pointer per entry.
  `0x0030746C` is the **20-slot** version of the same pattern for the DiveForm window
  (vtable `0x00762DF8`, whose neighbours are `Ui_BaseWindow_Close` and `Ui_DiveForm_LayoutPanes`).
* `0x00304900` (with its interior continuations `0x00304974`/`0x00304C14`) is entry 0 of the
  window step table at `0x00729398`. It builds the shared pool of `0x1C`-byte line records
  (aligned alloc `0x0011CFAC` + `0x00116AE0`, seven zeroed words each, record vtable
  `0x006293A00`) and pushes the next sub-state (`6` or `0x0B`) through
  `0x00295664 std_InlinedVector16_PushByte` into the state vector at `self+0x3B8`.
* `0x003064E8` is the constructor of the text-page container (called from
  `0x002FEE8C maybe_Ui_DiveForm_CtorB`); it sets up the record vector at `+0x344` with the
  inline/small-vector storage at `+0x6D4` and the sentinel at `+0x354`.
* `0x003058FC` builds one 7-word record from rows `0x28`/`0x29`/`0x2A` of the table at
  `self+0x6D4` and reconciles an ordered, key-recycled cache; `0x0030624C` drains the window's
  pending list into the `0x1C`-byte record vector (growth ≈1.5×, `0x380`-byte soft limit).
* `0x00304F34` is `Ui_DiveStartWindow_DeletingDtor` (base destructor `0x0032C1AC`, which another
  lane named `Ui_DiveStartWindow_Dtor`; the class has two vtables, at `+0` and `+0x3B8`).
* `0x003077BC` scans a compiled message stream as u16 opcode/operand pairs and extracts control
  code 4 with operands 2..0x0F (page/line control).
* `0x00307AC8` is a byte-identical copy of `0x002A6140 maybe_Ui_Window_CompareNameWithSlot`
  (compare `self+0x353C` against the string in the slot at `+0xDF8`).
* `0x0030535C` is a rolling odometer-style numeric display (four sub-slots, `'0'`/`'9'` carries,
  virtuals `+0x34`/`+0x38`, then two label rewrites and a buffer reallocation).

## 5. Index defects found (worth fixing in the tooling, not here)

* `0x00304C14` is listed as a **Thumb** function in the batch and in
  `decomp/ghidra/functions_index.json`. It is neither Thumb nor a function start: it is ARM
  interior code of the function at `0x00304900` (at `0x00304C14` the ARM stream reads
  `bl 0x006F20C0` and continues coherently, while Thumb decoding is nonsense). My `bl`-scanner
  finds no branch or literal anywhere in the image that targets it.
* `0x00304974` is likewise an interior address (it starts with `bl 0x006F20C0` and consumes
  registers set up by `0x00304900`).

  rather than as plausible-but-wrong functions.
* `decomp/native_names.json` / `symbols_recovered.json` contain two junk entries inside my band
  (`0x00303B24 "X80"`, `0x003058EC "lW0"`) that are literal-pool words misparsed as names by the
  recovery tool. They should be filtered by "is it a valid text pointer / identifier" in
  `tools/recover_native_names.py`.
