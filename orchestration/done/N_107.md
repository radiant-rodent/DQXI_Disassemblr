## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md` and the
   neighbouring done reports (N_088, N_102, N_103, N_105) for conventions.
2. Built a **name map** from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 104 sibling `out/N_*.json`; every proposal was
   collision-checked against them and all siblings (0 collisions).
3. Built a **caller index** over all 18,748 `decomp/readable` files and read **all 150
   bodies** (plus the raw C for the three `covered_by` entries).
4. The decisive step was **pointer/table membership**: scanned all little-endian words of
   `original/exefs/code.decompressed.bin` (base 0x00100000) for every batch address and
   for `address-4`, then printed the surrounding table/vtable with the names of its other
   entries. That is how the class attributions were established (see below). It also
   proved that 121 of the 150 are referenced as data (vtable slot or handler table), i.e.
   a call graph is not enough for this batch.
5. Used **raw ARM** from `asm/text/text_00300048.s` / `text_006C0048.s` and hand-decoded
   the Thumb/ARM boundaries whenever Ghidra's C was visibly wrong. Three such cases are
   documented in the entries.
6. Identified the shared helpers that recur in dozens of these bodies:
   `0x0010F6CC` = operator delete, `0x00123594` = intrusive-list splice into `self+0x110`,
   `0x001235A4` = list head init, `0x001DAD58` = generic UI window input handler,
   `0x001A60A0` = pane placement, `0x0029126C` = sub-widget show/hide,
   `0x00193E44`/`0x00193E40` = base-object/string destructor, `0x00200220` = party base
   destructor, `0x002A95B4`/`0x002A9748` = Gfx handle-table acquire/release,
   `0x00325BDC`/`0x00325C78` = curve sample / linear fallback, `0x0062B230`/`0x0062F680`
   = list-non-empty tests, `0x00669DD4` = actor-handle validity, `0x005E7848` = actor
   detach/finish. These are the reusable facts for the merge pass.

## Load-bearing findings

1. **Five 8-byte `{handler, 0}` tables anchor most of the batch** (all counted in words):
   - `0x72C248..0x72C388` - 40 entries, copied by the `Ui_DiveForm` ctor 0x3096D4
     (literal pool 0x309F94-0x309FA8; vptr 0x762DC8 whose InitPanes slot is 0x3BD260
     `Ui_DiveForm_InitPanes`). The five child-activation thunks are entries of this table and the pointer is stored at `0x72C320 -> 0x308940`, i.e. **four bytes
     before the batch address**. The real prologue is `add r1,r0,#0x3400; add r1,r1,#0xD8`,
     which is why the C looks like `arg2+0xD8` - there is no second argument.
   - `0x72BA3C..0x72BACC` - `Ui_MessageWindow` state handlers (neighbour 0x30E8E8 calls
     `Ui_MessageWindow_ExecControlCode` 0x30F258 with control codes 0x2C/0x0D).
   - `0x729840..0x7299xx` - `Ui_DiveForm` "menu_dive_dive" panel handlers.
   - `0x7285FC` - one entry used by the 0-110 rating helper.
   - `0x7286A0..0x7288E0` - interpolation/easing table: 59 code-pointer slots in
     0x7286A0-0x728878, then float/int defaults (1.0, 0.8, 0.5, 0.25, 0.1, 0..20);
     0x326564 copies the whole 0x240 bytes into each instance (literal 0x3267B4 -> 0x7286A0).
2. **Real vtables** confirmed by the surrounding named methods: `0x7631BC-0x7631E8`
   (`Gfx_Actor_*`), `0x76360C/0x763720` (`FieldParty`, also at 0x75E8A0 and four copies),
   `0x76397C-0x763A50` (`Battle_Action_*`), `0x763B08-0x763C50` (`Battle_Popup3D` /
   balloons), `0x764054/0x764060/0x764244/0x7642DC/0x76483C-0x7648B4` (tween sequence,
   Gfx sprite, damage popup, Field NPC actions), `0x762DC8` (`Ui_DiveForm`).
3. **`0x10F6CC` is operator delete** (`cmp r0,#0; sub r1,r0,#8; ldrd; ldr [vt+4]; bx`);
   `0x193E44`/`0x193E40` are the shared base/string destructors. Every
   `call X; call 0x10F6CC` body is therefore a scalar deleting destructor, which names
   ~25 entries here.
4. **Several batch addresses are four bytes into their function** (0x308944, 0x308B70,
   0x308E38, 0x3092C0, 0x3095A4, 0x309FB0). I named and documented the *real* entry
   (address-4) and said so in each entry; a later merge should not re-derive names from
   the truncated C.
5. **0x316398 is labelled Thumb but the bytes are ARM** (`efb501eb` = `bl 0x383B5C`), so
   the generated C for it is garbage; the real body returns a small state id (0x0A/0x0B/
   0x0D/0x13) from global queries. 0x327FB4's C is `halt_baddata` and 0x30D516's Thumb
   prologue was decoded as ARM - both are documented from the raw code instead of guessed
   from the C.
6. **`Ui_Tween` is inferred, not proven.** The 52 entries of 0x325882-0x3267C0 (50 table slots + 2 helpers) are mechanistically certain
   (same 0x325BDC/0x325C78 pair, mode-byte tests, float track fields), but whether the
   consumer is a tween player, an effect-parameter evaluator or a slot-reel animator is not
   established. It is flagged with confidence 0.35-0.45 and `maybe_`.

## What is NOT verified

- Everything is **static**: no emulator run, no debugger, no playtest. No name here was
  confirmed at runtime.
- The 130 `maybe_` names are mechanism-certain but purpose/owner-inferred. The class
  attributions depend on names produced by other lanes (notably N_015, N_026, N_052,
  N_053, N_088, N_101); if one of those anchors is later renamed, the names here must be
  swept with it.
- The weakest groups: the 52 `Ui_Tween_*` entries (purpose inferred), the 8
  `Battle_Action_*` destructor/detach slots (distinguishable only by vtable position),
  `0x313BCC` (0.30 - the 0-110 arithmetic is certain, the owner is not), `0x330026`
  (0.30 - hand-decoded Thumb with the base register uncertain), `0x30D516` (0.30 -
  decompiler output unreliable), `0x316398` (0.30 - the index has the wrong CPU mode).
- `Ui_DiveForm` is used as the class name for 0x308944-0x3095A4 because the handler table
  is copied by the DiveForm ctor and the handlers touch DiveForm's `+0x34D8` children; the
  table is shared/framework-level, so some of those five could belong to a base class.
- The `FieldParty` class attribution relies on N_043's 0.45-0.50 names in the same vtable
  (0x75E8A0), not on independent proof.
