## Method (what the evidence actually was)

The batch is almost entirely C++ vtable work: ~1/3 of it is scalar deleting destructors, and nearly
none of the functions has a *direct* caller, so a call graph alone is useless. I used, in this
order:

1. **Name map** — `symbols.json` (477 named), `symbols_recovered.json` (460),
   `decomp/native_names.json` (454) plus all 107 sibling `out/N_*.json` (≈15.9k entries) for
   callee resolution and collision checking.
2. **Vtable / data membership** — scanned every `.word` in `asm/rodata/*.s` + `asm/data/*.s` for
   each address, printed the ±18-word window with the resolved names of the other entries, and
   computed the vtable base by walking back over the preceding zero words. This (not the C) is
   what identified most classes: e.g. `0x0040EE10` sits in the Field::Object2D vtable that also
   holds `Field_Object2D_OnDeactivate`, `PlaceEffectInFrontOfCamera` and `PlayIdleEffect`.
3. **Literal-pool dereference** — read the raw image `original/exefs/code.decompressed.bin`
   (base 0x00100000, so file offset = vaddr − 0x100000, verified against a known string) to follow
   each constructor's `*obj = g_XXXX` literal to the real vtable address, then scan `.text` for
   that vtable value to find the constructing function. This is how `Ui_TimerDisplay_DeletingDtor`
   (0x004119CC) was pinned: the vtable 0x0076DD60 is written by `Ui_TimerDisplay_Ctor` at
   0x00411820.
4. **Neighbourhood clustering** — nearest already-named functions below/above each address. A
   class's methods are emitted contiguously, so this is stronger than 4-byte vtable adjacency for
   *which family* a function belongs to.
5. **Raw ARM/Thumb from `asm/text/text_00400048.s`** whenever Ghidra's C was obviously wrong or
   `halt_baddata()`. That fixed 7 entries: `0x0041F150` (a `b 0x0010F6CC` thunk), `0x0042164C`
   (3-instruction wrapper around an intrusive-list unlink), `0x00424030`/`0x00424088` (prologues
   only — wide-string formatting / entry-tag init), `0x00429434`, `0x00429680`, `0x004359B8`,
   `0x00438C72`.
6. **Constants** — dumped floats at every `g_XXXX` the C referenced. Two paid off:
   `0x004143FC` uses 1.0/−1.0 clamps plus `0.0174533` (deg→rad) and sets turn-left/turn-right
   bits → `Field_ActorAction_UpdateTurnDirection`; `0x0042222C` uses 0.05 / 0.0 / 255.0 →
   `Monster_Model_UpdateFadeAlpha`.
7. **Helper identification** — read the raw code of the shared helpers the batch leans on:
   `0x0010F6CC` = operator delete; `0x00100B74` = wcslen (16-bit loop) — **not** a noreturn call as
   Ghidra claimed, which changes the reading of `0x00412B6C`; `0x0010EBE4` = intrusive-list node
   unlink+re-init (defines `0x0042164C`); `0x00200220` = the shared base *deleting* destructor of
   the battle unit-list/party objects (its own vtable 0x0075B460 slot 0), used by 5 entries here.

## Load-bearing findings

- **`0x004143FC` is the turn-direction decision** for field actor actions: it is reached through
  slot 6 of the `Field_Action` vtables 0x0075FE3C and 0x00762ABC, and sets bit 0 / bit 2 of
  `actor+0x290` for "turn left" / "turn right" after clamping the planar dot product.
- **`0x004243A0` and `0x00429680` are the same 0x64-byte action-sequence entry**: 0x004243A0 clears
  one entry, 0x00429680 is the array allocator/initialiser (stride confirmed by decoding
  `r6*9 + r6*16` shifted left twice = `r6*0x64`), both using `MemZero(entry+0x1A, 0x38)`. These
  are the data structures fed by `Field_ActorActionSeq_AppendEntry` (0x00424BCC) and
  `BuildEntryFromUnits` (0x00424CA8).
- **`0x0042222C` … `0x004229E4` are one class**: fade alpha (0.05/255 constants), bounding box
  (two 3-vectors at +0x288/+0x294), embedded sub-object (+0x2D4 vtable) and a state-id dispatcher
  that switches on ids 0x1E9/0x1EB/0x21B/0x220/0x221/0x300+ and looks ids up in the model pattern
  table via 0x006400B4 walking 0x14-byte rows. This is the `Monster_Model` model-state block.
- **`0x004359B8` is a 0x610-byte battle action frame**: it calls `Battle_ActorAction_ShowDamage`,
  `maybe_Battle_ActorAction_Sequence`, `Battle_Ui_ForwardCommand` (×2), `Ui_GetCore` (×4),
  `Battle_Model_ApplyMonsterSize` and the aura-effect updater — i.e. the whole visual/audio side
  of one action step.
- **`0x00200220` is the base deleting destructor** shared by `0x00424318`, `0x004297CC`,
  `0x0042B148`, `0x0042B300`, `0x00438D38`, `0x00438FD4`; `0x004297CC` starts exactly at
  `Battle_UnitObject_Ctor + 0x190`, which is what makes it that ctor's destructor.

## Honest gaps — what is NOT verified

- **Nothing here was verified dynamically** (no emulator, no debugger, no playtest). All of it is
  static inference.
- ~25 of the 75 are **deleting destructors whose owner class cannot be named from the available
  data**. They are named at family level (`maybe_Ui_PanelPart_DeletingDtorA..D`,
  `maybe_Ui_TextWindow_DeletingDtor`, `maybe_Field_ActorMove_DeletingDtor(B)`, …) with confidence
  0.35–0.50. The *mechanism* is certain in every case (vtable slot 0 → base dtor → operator
  delete); the *class* is not. Four of them (`0x0040A374/0x0040BBA4/0x0040C3C8/0x0040CCC4`) are
  secondary (multiple-inheritance) sub-vtables of Ui window classes and I could not determine the
  owning class at all — do not trust those letters as stable identities.
- `0x00417EE8`, `0x0041DBEC`, `0x00424030`, `0x00424088`, `0x00429434`, `0x004359B8`,
  `0x00438C72` are **secondary entry points**: Ghidra gives them a function start and a size, but
  the surrounding code uses a large caller stack frame (e.g. `0x00424030` writes `[sp,#0x5E0]` in
  its first instruction) and `0x00438C72` ends with a branch back into 0x00438C10. Their names
  describe the fragment, not a self-contained function.
- `0x00412B6C` has `size 0` in `functions_index.json`; only its prologue was recovered.
- Several **inherited class names come from other lanes** (e.g. `Monster_Model_*`,
  `Field_ActorAction_*`, `Battle_ActorAction_*`, `FieldParty_*`). If a later types pass renames
  those anchors, my derived names must be swept.
- The `maybe_Ui_*` names near 0x0040A–0x0040C may in fact be Field model/equip classes: those
  addresses are interleaved with `Model_Equip_*` and `Field_Object2D_*` code, and I chose Ui
  because the shared base vtables are the 0x0026xxxx Ui window family. Confidence there is 0.40.
