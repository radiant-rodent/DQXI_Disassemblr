## What the batch actually is (the header label is wrong)

`N_111` is labelled `General_Procedures`, but the band is two interleaved game subsystems:

### A. Battle action-animation elements (`0x43C5E8`–`0x43FC80`, `0x468A64`–`0x469828`)

Small (0x2C-byte) polymorphic objects that drive one battle animation on an actor:

* `+0x28` = actor/motion handle (validated with `0x669DD4`);
* `+0x08` = inline motion-name buffer (some subclasses store their name there);
* vtable layout = `[0] deleting dtor, [1] play via actor vtable +0x84, [2] no-op,
  [3] update/finish`;
* animation names recovered: `pre_move_1..4`, `move_back_1..4`, `post_move_1..4`,
  `sleep_end`, `sleep_loop`, `AttackSpell`, `AttackStart`, `BackJump`, `Guard_End`,
  `RecoverySpell`, `Astron`/`GoldAstron`, `FrontJump`, `Guard_Loop`, `TumbleEnd`
  (string pool at `0x7BFB80`–`0x7BFD00`, `enemy_%s%d.ani` in the same page);
* the vtable is chosen by name inside the factory `FUN_002EC50C`, which allocates the
  0x2C-byte object (`Mem_AllocAligned`), runs base ctor `0x322CC8`, then stores a vptr from
  the literal pool at `0x2EE2EC`+ (`pre_move_1` → `0x76F9B4`, `pre_move_2` → `0x76F9E8`, …).
* Space for 12 virtual slots; slots 4–9 are shared base predicates (`0x193C6C`,
  `0x193CD8`, `0x193CD4`, `0x62A704`, `0x62A714`, `0x62A70C`).

### B. Ui screens, list windows and field scene objects (`0x43BCF0`, `0x43E0xx`,
`0x443CE8`–`0x468310`, `0x46B834`–`0x4712F8`)

* Ui screens derive from `Ui_Screen` (`0x20002C` ctor / `0x200220` dtor); three of them
  are created in the 0x6C0A00/0x6C1A00 ctor cluster. They own party slots
  (`FieldParty_ResetMemberSlot`), battle balloons and window sub-objects.
* The band contains several window families: party HP/MP gauge window
  (`0x447400`), item-info window (`0x45287C`), recipe info window
  (`0x44FF74`/`0x45073C`/`0x450788`), horse ("Uma") window (`0x4503A8`), party-select
  window (`0x46CC4C`), equipment window (`0x46CFB4`), talk/yes-no windows
  (`0x465C30`–`0x466460`), spirit-capture message window (`spirit_capture_msg.bxon`,
  `0x443CE8`–`0x445948`) and titled list rows (`title%d`, `0x464C2C`/`0x464DF0`).
* The Ui **serialized-reference resolver protocol** documented by N_109 is present here as
  three template instantiations (`0x446F74`, `0x4487BC`, `0x469FBC`, plus
  `0x46E320`): publish destination at `reader+0x60C`, resolve via `[[reader]]->+0x24`,
  store, clear the relocation slot.
* Field scene-object subclasses: 10 deleting destructors and 4 constructors, a generic
  handle→object resolver against the global actor table `0x7B80C0` with generation check
  `handle>>11` and RTTI tags `0x7C439C`/`0x7C4860`/`0x7C44F0`/`0x7C4B6C`
  (four instantiations `0x44C3D4`/`0x44C6E0`/`0x44CB48`/`0x44CEEC`), state-change handlers
  and a 4-list purge (`0x451B74`).
* `0x45D320` is not Ui at all: it validates a 6-character password, derives the save-crypto
  key (`Save_Crypto_SetKeyFromString`), opens a save block and calls `SaveCode_Encode`
  (`0x5EF33C`) to produce the 17-character Spell-of-Restoration code.
* `0x46B834`/`0x46B8BC` are the camera-shake object: destructor and per-frame update
  (180° / π/180 constants, calls into `0x6731EC`/`0x672E44`/`0x673BC8`, spawns nodes via
  `maybe_Gfx_SpawnShakeNode` `0x46BBA4`).

## Ghidra / index defects found

* **Seven entries are marked `thumb` but are ARM**: `0x43C678`, `0x43C6D4`, `0x43C730`,
  `0x43E040`, `0x43E0B8`, `0x4451AC`, `0x453C30`. Decoding them as Thumb produces the
  nonsense strings visible in `decomp/readable` (`add.w r0,r8,r0`, `pop.w {...}`).
* **Three batch addresses are interior addresses**, 0x0C bytes into the preceding ARM
  function: `0x43C678` = `0x43C66C+0xC`, `0x43C6D4` = `0x43C6C8+0xC`,
  `0x43C730` = `0x43C724+0xC` (Ghidra started a second function in the middle of the
  `PreMoveN_Update` bodies). These are named `…_UpdateBody` and documented as such.
* Ghidra sizes are too small for every function that contains an inline literal pool
  (it stops at the first data word); all evidence was therefore taken from raw bytes.
* Note for the merge: sibling lane N_104/N_107 named `0x66A2B4`
  `Battle_ActionAnim_AtkSpellElementDtor`, but in this binary `0x66A2B4` is the
  `…ElementDtor` of a different vtable and the `AtkSpellElement` *update* slot is
  `0x43FA8C`; the two names should be reconciled in `M1_merge_names`.

### Convention note for `M1_merge_names` (important)

Most classes in this band are constructed with a **vptr literal that points at a zero
word**; the first virtual function (the deleting destructor) is at **vptr+4** and call sites
use `(*(*obj + 4))(obj)`. So an evidence phrase `vtable 0x76F9B4 slot 0` means "vptr literal
`0x76F9B4`, first slot at `0x76F9B8`". `Battle_Actor` is the exception: `0x76F630` is a
normal vtable whose first function is at `+0`. The evidence for `0x43BCF0` was corrected to
say **entry 6 of `0x76F630`** (it previously said "slot 1"); nothing else in the JSON was
changed (no renames, no confidence changes) and the file was re-validated afterwards.
Current file size is 86,504 B (was 86,400 B); SHA-256
`09E4EF82CF111B699C1832E402D0E2982C247DC1EBC1BD8E3463D90F721BA3E1`.
