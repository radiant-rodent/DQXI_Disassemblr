## What the range actually is

The batch label `General_Procedures` is the default bucket, not a subsystem. The 150 addresses sit
inside a mostly contiguous C++ region that mixes five families, identified bottom-up from their
virtual tables, their string literals and their neighbours:

| Address span | What it is |
|---|---|
| `0x471D58`–`0x474884` | `Gfx`/`Ui` 2D sprite + layout-animation objects (sprite-node ctors/dtors, anim-channel setters, animation-ref callback binding) |
| `0x475078`–`0x476DE0` | **Actor action state machine** — specifically the Dragon Jump action family. Decoded the full `Actor_Action_DragonJump_*` set: vtable `0x773AB4` (`Begin`/`End`/`Update`/`OnEvent` + deleting dtor) and the nine per-segment update helpers registered in the action's element table |
| `0x477274`–`0x47E898` | Monster action ctor/dtor, UI window widgets (Sakusen, PartySelect, Choice, TwoPositionSelector) and the Battle UI unit-model widgets |
| `0x47EFD8`–`0x4A1564` | Battle party-member / action-model / action-element classes, message-row (`Text_Row`) and arc-list window code, casino slot-menu helpers |
| `0x4A1BF4`–`0x4B8794` | Field actor actions (Ivy, Whale, SklEd), field handle-refs, battle action classes (guard/counter/combination/shield/weapon), model-slot emitter, battle auto-action |

## Method

1. **Global name map** built from `symbols.json` (477), `symbols_recovered.json` (460),
   `decomp/native_names.json` (454) and every sibling `orchestration/naming/out/N_*.json`
   → 15,924 known addresses, used to resolve every callee and to avoid inventing duplicates.
   Final check: **0 name collisions** with those 15,924 names.
2. **Call-graph index** over all 18,159 readable-C files (79,082 call edges) to get callers/callees
   per function. 148 of the 150 have no *direct* caller — they are virtual methods, so the vtable is
   the real evidence.
3. **VTable / RTTI recovery**: scanned `.rodata`/`.data` of `original/exefs/code.decompressed.bin`
   for runs of code pointers (3,827 candidate tables), mapped each batch function to its table and
   slot, and found the constructor that installs each table by searching `.text` literal pools for
   the table address. That is how e.g. `0x471D58` was tied to vtable `0x773348` (whose slots 46–48
   are the named `Ui_SlideWindow_*` functions) and `0x4B3374` to `0x77696C`.
4. **String/constant evidence**: read the literal-pool targets behind each function (ASCII names such
   as `Nut`, `Run`, `sleep_bgn`, `Dragon_JumpM_Up_Loop`, `Dragon_JumpS_End`, `Ivy_Up_End`,
   `slot_display_font_spin0.bflim`, `enemy_%s%d.ani`, `txt_meesage1/2`), which gave the highest
   confidence names in the batch.
5. **Thumb/ARM decode fixes**: 13 addresses decompile to `halt_baddata` because Ghidra picked the
   wrong instruction set (the retail code has ARM functions listed as Thumb, plus jump-table interior
   entries). For those I disassembled the canonical `asm/text/*.s` listing (and Capstone with forced
   ARM mode) instead of trusting the readable C. They are marked `_Tail` / `_Body` with low
   confidence and the report says why.
6. **Bottom-up order**: leaf dtors and setters first, then their callers; the Dragon Jump action was
   reconstructed as a whole (vtable slots → per-segment helpers), which is the most solid result of
   the batch.

## Honest gaps (what is NOT verified)

- **Roughly 44 names carry `maybe_` (confidence 0.30–0.49).** Most are (a) deleting destructors whose
  only evidence is "base dtor + free" plus address adjacency, and (b) the 13 interior/jump-table
  entries that Ghidra split badly (`*_Tail`, `*_Body`). The destructor names are structurally safe
  but the *class* they belong to is inferred from the surrounding class block, not proven.
- **5 `Gfx_AnimSequence_ApplyFramesA..E` names are placeholders.** The functions are provably
  "apply animation variant to two channels + frame window", but which animation variant of which
  widget each one selects is not established; they should be revisited together with the
  `Ui_AnimRef` class (0x473A9C–0x4748xx).
- **`Menu_Slot_*` vs `Casino_Slot_*`** — the 0x4A0FC0/0x4A122C/0x4A1564 block was labelled `Menu_Slot`
  by earlier lanes and that name is kept for consistency; the helpers it calls (0x6406D0, 0x64C368,
  0x64EDF0) sit next to named `Casino_Slot_*` functions, so the class is probably the casino slot
  machine. Not resolved.
- **`Ui_SlideWindow_Ctor`** is identified from 3 named virtual slots; the object is large (0x2c9+
  bytes) and its non-window fields were not mapped.
- Names like `Battle_Ui_UnitModel_*` assume the reading "battle unit model widget"; the vtable
  (`0x7743BC`, `0x76EF98`, `0x774410`) is shared with `Ui_Widget` virtuals, so these are widget
  methods, not the 3D model itself.
