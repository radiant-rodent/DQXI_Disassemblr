## Method (what the evidence actually was)

The band is overwhelmingly C++ vtable work: ~2/3 of it is deleting destructors or one-line virtual
"play this animation" overrides, and almost none of it has a direct `bl` caller, so a call graph is
useless here. What worked, in order:

1. **Global name map** — `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and all
   110 sibling `orchestration/naming/out/N_*.json` (collision-checked: 0 same-address, 0 same-name).
2. **Dense vtable tables.** 87 of the 150 addresses are referenced from table slots. A local
   `vtable_base()` walk plus the names of the neighbouring slots identified the class family for
   every one of them (see the `Battle_Action_SpecialMove` result below).
3. **Registration-table decoding (the load-bearing trick).** The band's animation classes are
   registered by the huge initialiser at `0x002EC50C` as `(name string, vtable-4 pointer)` pairs laid
   out inline in `.text`. A scanner over `0x002EC000–0x002F2000` recovered 86 `(name → vtable)` pairs
   (`sp1Start`, `sp1Loop`, `sp1End`, … `sp25End`, `approach_1..4`, `pre_move_1..4`, `move_back_1..4`,
   `post_move_1..4`, `sleepStart/sleepLoop/sleepEnd`, `atk2`, `dmg`, `dead`, `avoid`, `escape`,
   `guard_w`, `guard_s`, `confuse`, `Entry`, `run`, `jump`, `shortRange`, …). This is what turns
   anonymous 0x10-byte destructors into named classes.
4. **Literal-pool decoding with Capstone.** Each 0x28-byte "play animation" wrapper loads its clip
   name from a pool word (`ldr r1,[pc,#imm]`); all 38 in this batch were decoded and **verified**
   against the name implied by the vtable registration (0 mismatches).
5. **Raw disassembly instead of the readable C** wherever the C was `halt_baddata`, `unaff_*`, or a
   merged container: `0x4BFF56`, `0x4C09A8`, `0x4C3ECC`, `0x4C4398`, `0x4C94EC`, `0x4C96E4`,
   `0x4D0CC8`, `0x4D2B0C`, `0x4DAE58`, `0x4DBCF0`. This corrected **real errors in the readable C**
   (see "Ghidra C defects" below).
6. **Neighbour clustering** for the few functions with no table slot: every unnamed function was
   compared with the nearest already-named functions below/above it, because a class's methods are
   emitted contiguously.

## Load-bearing findings (reusable for merge / types / follow-up lanes)

- **`Battle_Action_SpecialMove` phase classes.** All 34 sp "End"/"Loop" wrappers in this batch are
  the virtual **Start** slot of a per-phase vtable that the factory `0x002EC50C` builds by calling
  `Battle_Action_SpecialMove_Ctor` (0x004A8E5C, named by N_006) and then overwriting the vptr with a
  phase-specific table. Layout of every such vtable:
  `[0] deleting dtor → 0x00322D10 + operator delete`, `[1] play clip "spN_end"/"spN_loop" via
  model vtable +0x84`, `[2] 0x004A8E58 (bx lr, empty End)`, `[3] 0x004A8C7C
  maybe_Battle_Action_SpecialMove_Begin`, `[4..9] 0x00193C6C/0x00193CD8/0x00193CD4/0x0062A704/
  0x0062A714/0x0062A70C` (constant stubs), `[10..12] 0`. Vtable addresses (registered name in
  brackets): 0x007779CC [sp1End] (inferred, neighbours 0x00777A00 [sp2End] … 0x00777B6C [sp9End]),
  0x007794B8 [sp10End] … 0x007797F8 [sp25End], 0x007796C0 [sp1Loop] … 0x00779998 [sp9Loop],
  0x0077A8F8 [sp10Loop] … 0x0077A994 [sp13Loop]. Named
  `Battle_Action_SpecialMove_SpN<Phase>_Play` / `_DtorDelete`, aligned with N_111's
  `Battle_ActionAnim_<Name>_Play/_DtorDelete` scheme and with N_006's `Battle_Action_SpecialMove_Ctor`
  anchor.
- **`approach_1..4` classes** — vtables 0x007793E8/0x0077941C/0x00779450/0x00779484, layout
  `[0] dtor (0x00322D14 + delete)`, `[1] play "approach_N"`, `[2] bx lr`, `[3] update: if model ready
  (0x00669DD4) → 0x005E7848(model, 0)`; named `Battle_ActionAnim_ApproachN_Update/_DtorDelete`.
- **Shared helper identifications** (all previously unnamed, all verified from raw code):
  - `0x00406E04` = generational-handle release (mask 0x003FFFFF, table 0x007B4D68); three dtors in
    this batch call it on `self+0xC4` before `operator delete` (0x004C3ECC, 0x004DAE58, 0x004DBCF0).
  - `0x002B0A04` and `0x00294C24` are 1-instruction `b 0x00193E44` thunks; `0x003E4A4C` is a
    `b 0x00294C88` thunk. Several dtors call the thunk, not the target, so the readable C's "calls
    0x00193E44" was only indirectly right.
  - `0x00322D10` = the non-deleting destructor entry of the battle action-animation base (slot 0 of
    vtable 0x00775CBC); `0x00322D14` is its sibling used by the `approach` classes.
  - `0x0044C654` / `0x0044CAB4` = base-object factories used by the Field scene-object constructors
    (they install base vtables 0x007709E4 / 0x00770AA0 plus a secondary sub-vtable at +0x98/+0xD8).
  - `0x0017C1C8` = global object-pool allocator used by the small `Field_Marker` / `Field_ObjectSprite`
    factories.
  - `0x0019C878` = tiny "init object, vptr 0x00758E60" helper used by the Ui list child factory.
- **Two identical "clear one slot" bodies** (0x004C0058 and 0x004E15E4): call virtual `0x34(self,0)`,
  write `-1` into a per-unit word table at `self+0x3260` / `self+0x17FC`, then clear `+0x72C` of the
  record returned by virtual `0x3C`. Same code for two containers → one naming scheme with a suffix.

## Ghidra C defects found (worth fixing in the generator, not by weakening checks)

- `0x004C3ECC`, `0x004DAE58`, `0x004DBCF0`: readable C claims `func_002650C4`, the real first call is
  `0x00406E04` (handle release). Recorded in the entries.
- `0x004C4398`, `0x004CD584`: C claims `0x00193E44`; the code calls the `0x002B0A04`/`0x00294C24`
  thunks to it.
- `0x004C09A8`: C shows only base-dtor + delete; the real body is `bl 0x0038AD34` (Ui list sub-object
  destructor) + `b 0x0010F6CC`, and the entry is a merged 0x164-byte container.
- `0x004C9BCC`: no recoverable body at all (only an `unaff_r*` stack-fixup fragment).
- **Wrong CPU mode in `functions_index.json`**: `0x4BFF56`, `0x4C94EC`, `0x4C96E4`, `0x4C9754`,
  `0x4D0CC8`, `0x4D2B0C` are flagged `thumb` but are ARM (except the 2-byte Thumb `push` at
  0x4BFF56). Disassembling them as ARM gives coherent code.
- **Interior/secondary entry points**: `0x4BFF56` (2 bytes into a Thumb tail, then ARM that always
  branches back to 0x004BFD80 inside 0x004BFA20), `0x4C94EC`/`0x4C9754` (fall-through continuations
  of 0x004C9474/0x004C96E4 — no prologue), `0x4D0CC8` (starts mid-loop, branches back to
  0x004D0C88), `0x4D2B0C` (`bl 0x200220; pop {r4,lr}; b operator delete` with no prologue), and
  `0x4C09A8` (merged container). They are named as the fragments they are.

## Honest gaps — what is NOT verified

- **Everything is static.** No emulator, no debugger, no playtest. All class identities come from
  vtables/registration tables; no runtime confirmation exists.
- The 35 `maybe_` entries have certain *mechanics* but inferred *owners*. In particular:
  - the four `maybe_FieldParty_MemberModel_DtorA..D` (0x004BBC8C/0x004BF194/0x004BF420/0x004BF528)
    sit in four vtables that share `0x001FEFC0`/`0x001FF200` (FieldParty-ish, both names from other
    lanes at 0.45–0.50); the class name is a family guess. Same for `0x004D2B74`.
  - `0x004C3C28`/`0x004C3ECC` are called "Field_Marker3D" only because their vtables' slot 15
    neighbours are marker/raycast functions; they could be another 3D-widget class.
  - `0x004C09A8` is called `Battle_Action_SupportSpell_Dtor` from constructor adjacency
    (0x004C0988 installs vtable 0x00777C04) — the constructor's own name comes from another lane at
    0.65.
  - `0x004C0E38`/`0x004C0EA4` are described as "two timer slots of a Ui window"; the owning window
    (vtable 0x00777C64) is not identified.
  - `0x004D0CC8` and `0x004BFF56` are mid-function fragments; their names describe the fragment.
- The exact *slot semantics* of the `sp` classes are inferred from the N_006/N_111 convention
  (`[0] dtor, [1] start/play, [2] end, [3] update/finish`); the functional description (plays clip
  "spN_end"/"spN_loop" through model vtable +0x84) is certain, the words "Start"/"Update" are not.
- `0x004BA268` (rejects monster ids 0x18F/0x1A5/0x350 and faded units) is named
  `maybe_Battle_Action_ShouldUpdateUnitModel`; the three ids are *probably* special monsters, not
  verified against any monster table.
- `0x004D0180` resolves a row through a lazily built 0x0A24-byte table; the table's content
  (localised row labels vs. something else) is not proven, only its access shape.
- Struct offsets come from the decompiler and may be off where Ghidra merged entries.

### Three corrections applied to the JSON

1. `0x004C4398` `Ui_LoopPane_Dtor` -> **`Ui_LoopPane_DtorDelete`** (confidence 0.5 -> 0.6). The entry
   said "non-deleting destructor", but the body is `bl 0x002B0A04` (=`b 0x00193E44`) + `b 0x0010F6CC`,
   and `0x0010F6CC` is the free path of `func_0010F6BC` (it reads the 8-byte block header and calls
   `allocator->vtbl[1]`). The summary now also records why the class is what it is: vtable base
   `0x00777EC0` slot 1 (`0x004C4320`) plays the string **"dmg"** (`0x002E8EA4`) and slot 20
   (`0x004C43A8`) builds a child object with the string **"loop"** (`0x004C43EC`) via
   `0x003E00CC`/`0x003E021C`; `0x004C4400` releases that child.
2. `0x004BFF56` `maybe_Battle_Ui_FinishTargetSelection` -> **`maybe_Battle_Ui_SequenceStep_Tail`**.
   The entry itself documents that this is an overlapping entry, but the old name read like a real
   function. It has no prologue and ends in `b 0x004BFD80`, which is inside the function starting at
   `0x004BFA20`; the new name says "tail" and the summary states it is not standalone.
3. `0x004C869C` `maybe_Field_SceneNode_ApplyIdPair` -> **`Field_Marker_ApplyStoredOffset`**
   (confidence 0.38 -> 0.5). `0x0029E740` is exactly `strh r1,[r0,#0x4C]; strh r2,[r0,#0x4E]; bx lr`
   (disassembled), so the two signed-16 fields at `self+0x12`/`self+0x14` are the marker's stored
   screen offsets being written into the sprite's x/y halfwords - not "ids".
