## What this batch actually is

is **four contiguous C++ areas**, not general procedures:

   `Battle_Action_SpecialMove` per-phase animation class family: 76 of the 150

2. `0x004E2A40–0x004E4A18` — `Model_Actor` animation-state methods and their
   destructors, plus one actor-action flag/state transition (`0x004E4468`).
3. `0x004E6E04–0x004EC41C` — assorted Gfx scene-node / Ui window / Ui message

4. `0x004EFC44–0x00504FA4` — field event gimmicks (`Event_Gimmick`, `Event_BeeRise`,

## Method (and what was decisive)

1. Name map built from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and every sibling `orchestration/naming/out/N_*.json`
   (checked at the end: **0 same-address collisions, 0 same-name collisions**).
2. **Vtable-slot mapping against the raw image** (`original/exefs/code.decompressed.bin`,
   VA = file offset + 0x100000). Every batch address was searched as a 32-bit word in
   `.rodata`/`.data` and, where relevant, as a Thumb pointer (`addr|1`). ~110 of the
   150 are vtable slots and are never referenced from code, so this was the only way
   to learn their class. This also explained the "3 leading zero words" layout: the
   stored vptr sits 4 bytes before slot 0.
3. **Literal-pool decoding** of every ARM `ldr rN,[pc,#imm]`. This is what names the
   sp classes: each 0x28-byte body ends in
   `ldr r0,[r4,#0x28]; ldr r1,[r0]; ldr r2,[r1,#0x84]; ldr r1,="spN_phase"; bx r2`,
   and the pool words form the run `sp1..sp25` × `start/loop/end` embedded in the
   battle animation name table at `0x007BFExx` (next to `Act_Def`, `pre_move_1..4`,
   `approach_1..4`, `enemy_%s%d.ani`). The same pool decoded `"Bee_Rise"` + `1.2f` +
   `2.0f` for `Event_BeeRise_Start`, and `"txt"` for the Ui text-window helper.
4. Decoding the *instantiation* path: `0x002EC50C` (a single 17.5 KB Ghidra-merged
   function) loads the `battleact` resource and, for each entry index, calls
   `Battle_Action_SpecialMove_Ctor` (0x00322CC8) and then overwrites the vptr, which
   is how the 0x34-byte records at `0x77A960+` / `0x77BB50+` are produced. That
   confirmed "one class per clip name", not one class with a name parameter.
5. Raw ARM/Thumb disassembly (Capstone) wherever Ghidra's readable C was
   `halt_baddata`, `unaff_*`, `in_ZR`, or had lost the prologue. Several entries in
   this band are like that: `0x004F8F3C`, `0x004F8F50`, `0x004F8F80/84` (Ghidra split
   one function at a 4-byte boundary), `0x004E4468` (Thumb flag in the index is wrong,
   it decodes fine as ARM), `0x005022A6/0x005022E6` (one function split in two),
   `0x00501BC0+` (Thumb per the index, ARM in reality).
6. Consistency with the sibling lanes: **N_113 ends at `0x004E2570`
   `Battle_Action_SpecialMove_Sp13Loop_Play`**, i.e. immediately before this batch,
   so the 76 sp entries continue N_113's exact scheme
   (`Battle_Action_SpecialMove_SpN<Phase>_Play` / `_DtorDelete`, confidences 0.75 /
   0.72) instead of inventing a second vocabulary. Likewise the IPC wrappers reuse the
   already-established `Svc_Ipc_Send<header>` scheme (`0x005059EC`
   `Svc_Ipc_Send080D0144` from N_115), and the Fs helpers follow `Fs_FormatResultCode`
   (`0x00502164`).

## Load-bearing findings

* **The 76 sp functions are `Battle_Action_SpecialMove` phase classes**, not UI and not
  sound: their shared slots are the battle-action pair
  `0x004A8E58` (empty init) + `0x004A8C7C` (`maybe_Battle_Action_SpecialMove_Begin`
  from N_006), the base destructor is the battle-action dtor `0x00322D10 → 0x00193E44`,
  and the clip text lives in the battle animation name table.
  Pairing rule (mechanically verified for all 76): the destructor of phase *N* is the
  function **after** the play function of phase *N* in memory, and in the vtable the
  record is `[dtor, play, 0x004A8E58, 0x004A8C7C, 0x193C6C, 0x193CD8, 0x193CD4,
  0x62A704, 0x62A714, 0x62A70C, 0, 0, 0]`. 0 mismatch between clip literal and
  dtor↔play pairing.
* **`0x004EFC44` / `0x004EFCA8` are constructors**, not methods: they call
  `0x004D7124`, write `0xFF` to +0x48..+0x4A (three "invalid" ids) and 0 to +0x4C,
  then install a vtable. The first one installs `0x77C1C8`, the **third**
  `Field_BattleTrigger` sub-vtable (the others are `0x77627C`, used by N_112's
  `0x004AEBC0`, and `0x77E284`). Hence the `_Gated_` qualifier (its slot 3 is
  `maybe_Field_TryPlayerInteractGated`).
* **The `0x4FC7EC–0x50152C` block is the movie/video player**, established by its
  vtables `0x780C1x–0x780Dxx`, whose neighbours other lanes already named
  `maybe_Gfx_Movie_WaitForTracks`, `maybe_Gfx_MovieBuffer_*`,
  `maybe_Gfx_StreamSlot_*`, `maybe_Gfx_MovieSurface_Ctor`, and by the callee chain
  into `0x006B8xxx` (the codec layer). `0x004FD6E8` is reached from
  `0x001B6DE4 maybe_Gfx_Movie_IsPlayable`, which closes the loop.
* **`0x00501BC0–0x005022E6` are IPC request wrappers.** `mrc p15,0,rX,c13,c0,3` reads
  the thread pointer, the command header is stored at **TLS+0x80** (the per-thread IPC
  buffer), `svc #0x32` is `svcSendSyncRequest`, and the result code comes back at
  **TLS+0x84** with the first reply word at TLS+0x88. `0x00501E60` even writes a
  static-buffer descriptor (`count*0x180 | 0x0C`) at TLS+0x98, and `0x00501C3C`
  saves/restores TLS+0x180 as scratch. That is why these functions were named
  `Svc_Ipc_Send<header>` and not guessed at.
* **`0x005048B4` / `0x00504A2C`** are the Fs file layer: a priority in [-8..8] maps to
  one of five cached worker objects at `self+0xC` (`self+0x18` remembers the current
  one), and reads go through that worker with the file's 64-bit base offset
  (`+0x8/+0xC`) added and the length clamped to the remaining bytes.

## Honest gaps / what is NOT verified

* Everything is **static**. No emulator run, no playtest, no runtime confirmation of
  any name. In particular nobody has watched `sp14_loop` play.
* 29 entries are `maybe_` (0.35–0.49). Their *mechanics* are read off the code; the
  *owner* is a family guess:
  * `maybe_Ui_StatusPlate_*` / `maybe_Ui_AilmentPlate_*` rest on the neighbour names
    in the same vtables (`maybe_Ui_Status_RefreshMarker`,
    `maybe_Ui_Status_RefreshAilmentPlate`) which come from other lanes and are
    themselves `maybe_`.
  * `maybe_Ui_ItemInfoWindow_DtorDelete` rests on `maybe_Ui_ItemInfoWindow_Open`
    being in the same vtable.
  * `maybe_Battle_Ui_PartyPanel_/MemberPanel_DtorDelete` rest on a slot run of
    `0x001Fxxxx` helpers that different lanes named `maybe_FieldParty_*` *and*
    `maybe_Battle_Ui_*` — those two families are probably one class, and this batch
    could not settle which.
  * `maybe_Ui_ScreenSlideAnim_ApplyPart*` / `maybe_Ui_SceneWindow_*Part*` are
    "propagate one byte / one float to every part in a list" helpers; the byte target
    (`uiNode+0x128`) and the float target (`+0x9C`) are certain, their engine meaning
    (visible flag? X offset?) is not.
  * `maybe_Gfx_Movie_NotifyAndRelease*` (0.35) are 2-instruction virtual-call relays
    with no vtable slot and no callers; the "listener" reading is a guess from shape.
  * `maybe_Svc_Ipc_SendVarargsRequest*`, `maybe_Fs_CheckAndNormalizeResult`,
    `maybe_Fs_ReleaseObject`, `maybe_Fs_NotifyService`, `maybe_Fs_NoOp` — the IPC /
    Fs *block* is certain, the individual command ids are not.
* `0x004E7484` is **not code**: it is the 4-byte vtable pointer literal
  `0x0077B5E4` that the preceding Ui pane constructor loads (`functions_index.json`
  has a false positive there). It is named `Ui_Pane_VtablePtr` and documented as data.
* Two other batch entries are fragments of a bigger function, not standalone ones:
  `0x004F8F84` (tail of `0x004F8F80`) and `0x005022E6` (continuation of
  `0x005022A6`). Both are named as the fragments they are.
* `functions_index.json` marks `0x004E4468` and `0x00501BC0` as Thumb and several
  0x4F8Fxx/0x5015xx/0x5022xx addresses as `halt_baddata`; they are plain ARM and
  decode cleanly with Capstone. The index should be fixed (see follow-ups).
* `0x004FBD3C` (0.4) and `0x004FBDF4` (0.4) are the least certain entries in the
  whole file — both build/tear down a small heap object with a vtable from a literal
  pool and neither has a caller or a vtable slot, so their subsystem is inferred from
  the surrounding 0x4FBDxx Ui-scene-window block only.
