Method (all static; no emulator, no debugger, no game binary modified):

3. **Decoded every literal-pool constant the functions write into their IPC parameter
   block** (`ldr rX,[pc,#imm]` -> `code.decompressed.bin`, base `0x00100000`). For this
   batch that was decisive: ~50 entries are raw IPC wrappers whose only usable evidence
   is the 32-bit request header and the session-handle literal.
4. Read the sibling batches first (`N_033` in particular) to reuse their established
   `Svc_Cecd_*` / `Svc_Ipc_Send<header>` scheme instead of inventing a second one; then
   checked the raw ARM listings (`asm/text/text_00500048.s`, `text_00100048.s`) wherever
   the readable C was visibly wrong (`halt_baddata`, `in_ZR`, `unaff_r*`).

## What the batch actually is (the "General_Procedures" label is a generator artefact)

Five distinct bands, not one subsystem:

### A. fs:USER IPC senders + handle objects (`0x005055A0`-`0x00506xxx`)
`0x005055A0` closes a handle slot; `0x005059EC` is fs `Read` (header **0x080D0144**,
4 normal + 1 translate param, caller `0x00503E84` passes handle/buffer/size/offset);
`0x00505AB0`/`0x00505AE8` are parameterless **0x0817/0x0818** requests returning one
byte. `0x005064AC` invokes a single global callback slot at `0x007B2D1C`.

### B. Vertex colour/format helpers (`0x0050857C`, `0x00508740`, `0x005088DC`)
`0x00508740` builds 256 consecutive float deltas on the stack and `0x0050857C` quantises
them (saturating 1.0/255.0/2^7 constants) into two 0x82-word blocks at a selectable byte
lane. `0x005088DC` builds a 12-entry packed vertex-format descriptor (constants
`0x000F0201`, `0x00010062`).

### C. Icon cache / CECD (`0x00509A80`-`0x0050D...`)
* `0x0050B878` counts icon-cache entries whose flag byte matches a mask; `0x0050BAC4`
  stores a 0x60-byte cache record keyed by command 0x65..0xC7 (0x8C..0x8F write flag
  bytes at +0x1DD..+0x1DF); `0x0050A700` is a thunk to `Ui_IconCache_CommitEntry`.
* **Two CECD sessions are confirmed by the literal pools**: primary `0x007B0058` and
  secondary `0x007B005C`. This batch contains the previously unnamed command wrappers of
  both: request `0x000E`, `0x000D`, `0x000F`, `0x0010`, `0x0001`, `0x000C`, `0x000B`,
  `0x0009` on each session (N_033 already had 0x0003/0x0007/0x0008/0x000A/0x0011/0x0012
  and used the `...B` suffix for session B, which I kept). The two 0x000E/0x000F wrappers
  return event handles, i.e. `cecdGetCecInfoEventHandle` / `cecdGetChangeStateEventHandle`.
* After them: a cfg-style session at `0x007AF0F8` (command 0x0002 returns the 0..6 value
  that `0x0050D73C` switches over as the system language and uses to pick a font fallback
  glyph) and a third unidentified session at `0x007B00E8` (commands 0x0001/0x0002/0x0007).
* `0x0050E60C`-`0x0050E988` are a global address-range registry (`0x007F25C0`) with an
  interval tree: create block (16-byte header, tag 0x5048), find, unlink, insert.

### D. Sound (`snd:u`) (`0x005160E4`-`0x0051C8B8`)
`snd:u` session `0x007AEAB0`; wrappers for commands 0x0003, 0x0004 (buffer and
strlen-name forms), 0x001D, 0x001F, 0x002C. Then the software mixer (`0x00519544` mixes
two 0xA0-sample blocks, `0x0051978C` four), stream close, DSP coefficient write
(`0x005189A0`, square-root term + flag 8 in the DSP block), and two 400x240 three-plane
frame converters (`0x0051C5F0`/`0x0051C67C`) that look like **Y2R/YUV movie conversion**
rather than audio -- confidence is only 0.4 there.

### E. Fx particle system (`0x0051D5F0`-`0x005346B4`, 77 entries)
The whole tail of the batch is the particle effect runtime, matching the `Fx_*` names
already proposed in `N_001` (0x52AC80 emitter init, 0x52F4D4 destroy, 0x5342D8 table):

* `0x0051D5F0` = common render-quad builder (LCG at `+0x8C`, RNG table `0x0051D930`,
  local/world transform switch at `+0xCC`); `0x0051EBBC` is its sibling that also adds
  emitter drift and stores the source at `particle+0x150`.
* Ten emission variants (ring/disc `0x0052060C`, box `0x00520B18`, sphere `0x00520F1C`,
  oriented-quaternion `0x005212F0`, cone `0x00521BE8`, arc `0x00522300`, ...), each
  distinguished by its radius maths (`sqrt`, `(1-r)*r^2`), its RNG table and whether it
  does a matrix multiply (`0x0012551C`).
* `0x005209DC` unlinks a particle from the two doubly-linked lists via
  emitter`+0xE0/0xE4/0xE8/0xEC`; the `0x0052xxxx` family are the per-emitter-type list
  updates, the state appliers (`0x0052E08C`/`0x0052E4AC`), the batch begin/end
  (`0x0052E76C`/`0x0052E784`) and the node allocator (`0x00530338`).
* `0x005329E0`-`0x005346B4` are the billboard batch: `0x00532F44` is called from
  `Gfx_SceneObject_CullAndDrawParts` (0x0056572C) and walks the batch calling
  `0x00533DCC`, which normalises the source matrix with three square roots and emits
  point/vector/normal transforms.

## Known problems / not verified

* **Fx subtype letters are local identities, not stable names.** 20 of the 77 Fx entries
  are `maybe_Fx_EmitParticles<Shape>` / `maybe_Fx_UpdateParticleListA..U`. The *role* is
  certain (they are the per-emitter-type emission and update paths, all built on
  `0x0051D5F0` and the `0x521FFC`/`0x5221BC` keyframe appliers), but which emitter type
  owns which function is not recoverable from the emitter definition without a struct
  pass. Do not treat `A..U` as meaningful order.
* **CECD 0x000E vs 0x000F.** The wrappers certainly return the two event handles; which
  command id is CecInfo and which is ChangeState follows the libctru order and is not
  independently verified. Marked in the evidence of both entries.
* **The cfg-style session (0x007AF0F8) and the third session (0x007B00E8) are identified
  only by the shape of their commands**, not by the service name (no string reference to
  the opener survives in `.text`). Both are documented as `maybe_Svc_*`.
* **`0x0051C5F0`/`0x0051C67C`** are documented as Y2R/YUV frame conversion because of the
  400x240 loop and three destination planes; the alternative (a 3-plane audio/video
  surface blit) was not excluded.
* **Three batch entries are not real function starts** and are named as such:
  `0x0051045E` and `0x005104F2` are mid-instruction addresses inside the regex matcher;
  `0x00530054` starts in a Thumb/literal-pool region. `0x0050DEA6` and `0x00526814` are
  real code but split at a Thumb/ARM or MRC/VFP boundary, so their readable C is garbage
  (`halt_baddata`); the names describe only the surrounding, hand-decoded fragment.
* Everything is static. No emulator run, no playtest, no runtime confirmation of any
  parameter meaning. Struct offsets are read from the decompiler and may be off wherever
  Ghidra merged an entry point.
