## What I did

Named and documented all 150 functions. Method (entirely static: no emulator, no debugger,
nothing in `..\3DS_Translate` was written, no game binary modified):

1. Read the readable C for every entry from the path the batch names
   (`decomp/readable/{functions,recovered}`), with a generated per-function dump that also
   carried the size/seed metadata from `decomp/functions_index.json`.
2. Built a global name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all sibling `orchestration/naming/out/N_*.json` files, and a
   caller index over all 18,748 readable C files. **Only 15 of the 150 addresses have any direct
   `bl` caller**; the rest are C++ virtual methods or jump/step-table entries, so the call graph
   alone cannot name this band.
3. Read the neighbouring lanes first — `N_106` is the lane immediately before this one and had
   already named the four external callers of my first thirteen functions (`maybe_Ui_SpriteCache_LookupOrLoad`
   0x002F7814, `maybe_Ui_SpriteList_LoadSlotTextures` 0x002F787C, `maybe_Ui_SpriteList_AllocFreeSlot`
   0x002F79C0, `maybe_Ui_ResourceCache_GetOrCreate` 0x002F7A24). Those names fixed the vocabulary
   (`Ui_Sprite*`, `Ui_ResourceCache_*`) and are cited in the evidence, so the merged table stays
   consistent instead of inventing a second scheme.
4. **Decoded the literal pools of every `ldr rX,[pc,#imm]`** against
   `original/exefs/code.decompressed.bin` (VA = file offset + 0x00100000). This was decisive
   for the first group and for the text/glyph group (see findings below), and it caught three
   mistakes in my first pass (wrong byte order on the magic words, an unknown "format" that is
   really `"%s.bflyt"`).
5. Fell back to `asm/text/text_00XXXXXX.s` wherever the readable C was a stub
   (`halt_baddata`, `unaff_r*`, `in_ZR`, lost prologue). That exposed the seed-table defects
   listed under "Tool/index defects". `game_data/arcs/summary.json` (398 SARC archives, 10,718
   `bflyt`/`bflim`/`bflan` members) was used as corroboration for the archive reader names.

## What the batch actually is (the "General_Procedures" header is a generator artefact)

It is one continuous run of the game's **UI2D / text-rendering engine** (Ghidra's flat address
order split it into a batch), in five readable clusters:

### A. SARC archive reader + resource cache (`0x00535580`-`0x005367BC`)
The literal pool at `0x0072FAAC/0x0072FAB4/0x0072FABC` contains the ASCII magics **`SARC`**,
**`SFAT`**, **`SFNT`** and the code compares exactly those words, at exactly the standard SARC
offsets (header 0x14, BOM at +6, version 0x100 at +0x10, SFAT at header+0x14, node stride 0x10,
SFAT hashKey at +8, attribute `0x01000000` = file, start/4 in the low 24 bits). That makes
`0x00535E50` `Fs_Sarc_Open` (0.75) and `0x00535FA4` `Fs_Sarc_FindFile` (0.7 — hash, binary
search, then `strcmp`), with `0x00535E74/EDC/F50` as verified interior stages of the open path.
The 8-slot table the caller uses (`0x002F79C0`) is therefore "8 open archives", not sprites —
worth correcting in the N_106 write-up if M1 revisits it.
`0x00536150/0x005361E0/0x005362A0/0x00536728/0x005367BC` are the name-keyed cache around it
(0x80-char name at +8, payload at +0x88, kind at +0x8c, free-list via 0x0053CEF8), and
`0x00536104` is the tagged-block release hook they call for archive data.

### B. UI2D animator / animation binder (`0x0053682C`-`0x00537DF8`)
`0x0053682C` allocates one animatable object per layout-animation entry plus a fixed
`(object, tag)` array; `0x00536C48` appends compatible pairs into it; `0x00536E78` is the
per-tag sampler that evaluates keyframe tables (binary search over float pairs, `0x0053779C`
decodes the curve) and writes texture-pattern/texcoord/colour/rotate values into the pane's
packed material block; `0x005375DC` does the name-based binding. The packing bitfields are the
same ones `0x0054054C` builds. `0x00537D48/0x00537DA0/0x00537DF8` are three identical
channel-advance wrappers differing only in the layout vtbl slot (0x30/0x2C/0x28).
`0x00537AE8/0x00537B50/0x00537C4C/0x00537C5C` are **interior labels** of the SRT-to-matrix
builder around 0x005378xx (the seed table records them as Thumb, which is wrong — the code is
ARM and VFP), named as fragments at 0.30 confidence.

### C. Pane lookup + layout player (`0x005383F4`-`0x0053ADA0`, `0x0053D228`, `0x0053D57C`, `0x0053D718`)
`0x005383F4/0x00538494/0x005385CC/0x00538648/0x00538F2C` are one family of
"find pane by 0x18-char name" variants (own name at +0x80, children at +0x14 via vtbl[0x4c],
indexed children via vtbl[0x24]/[0x28], extended list via vtbl[0x50]); `0x0053E3BC` is the
variant with a cached child at +0xd4. `0x0053D228` really is a layout player factory: the
format string at **0x0072FB50 is `"%s.bflyt"`**, the loaded handle comes from the manager's
vtbl[0xc], the 0x3c-byte object gets vtable 0x0078144C and has the two intrusive lists that
0x0053D57C/0x0053D718 walk in the destructors.

### D. Text box / text layout (`0x0053CD74`-`0x005551B8`)
`0x0053E2B8`/`0x0053E344` are the copy/default ctors of a 0x14-byte text-run record; the
`0x0053EED4`/`0x0053F208`/`0x0053F7FC` triple measures, scales and draws one run
(vtbl 0x78 measure, 0x58 set width, 0x6c submit glyphs, 0x60 draw); `0x0053F940`/`0x0053F9EC`
append/write UTF-16 characters into the box's buffer (capacity +0xcc, length +0xce, dirty bit
+0xd0, `wcslen` = 0x00100B74 — confirmed in the N_111 audit); `0x0053F078` builds the per-run
draw parameter block and calls `0x0055730C` (`Ui_Text_CalcScreenScale`: 1/screen width/height);
`0x00541B38`/`0x00541BB8` grow and fill the 0x20-byte glyph quad array from the template table
g_00541CF8.

### E. Buffered stream, text styles, and the glyph atlas (`0x00549518`-`0x0056EEB8`)
`0x00549518`/`0x00549664`/`0x0054972C` are a buffered file reader (window +0x14/+0x18/+0x1c,
seek modes, vtbl 0x24 read / 0x40 seek / 0x54 refill) and `0x0056ED9C` is its "read from the
remaining buffer" sibling. The `0x0054EC70`/`0x0054FD50`/`0x00554910` triple are text-style
constructors. Two more of the game's own resource headers are hard-verified here:
**`CBNK`** (0x4B4E4243 at 0x00549354, version 0x01000000..0x01000100) and **`CWAR`/`CWAT`**
(0x52415743 / 0x54415743 at 0x0054BB78), both with a payload pointer at +8 of a resolved block.
`0x0056C4D8`-`0x0056C6C0` are six broadcast/query helpers over a glyph-handler table
(count +0x10, array +0x14), and **`0x0056CA44`/`0x0056CF18`/`0x0056D028`/`0x0056D138`/
`0x0056D1E4`/`0x0056D85C`/`0x0056D8C4`/`0x0056DA5C` are the glyph atlas** (0x58-byte page cells
or 0x54-byte cell tables, in-use/quality/owner/size fields, popcount-based granularity rounding,
split/coalesce, atlas texel fill and key-string lookup). `0x0056DD6C`/`0x0056EEB8` are the two
text-renderer destructors and are the only direct callers of `0x00535580`.

## Tool/index defects found (recorded, not fixed — not my files)

* **Wrong CPU mode**: 0x00537AE8, 0x00537B50, 0x00537C4C, 0x00537C5C, 0x00554D76, 0x00555BA0,
  0x00554Fxx-style entries and 0x0056ABC8 are seeded as `thumb` or as stub entries although the
  byte stream is coherent ARM/ARM+VFP. `functions_index.json`/`function_seed.tsv` should not
  trust the mode for this range.
* **Interior labels presented as functions**: 0x00535E74, 0x00535EDC, 0x00535F50 (inside
  `Fs_Sarc_Open`), 0x00537AE8/B50/C4C/C5C (inside the SRT matrix builder), 0x00546D4E and
  0x00546D62 (inside the 0x00546D28 cursor update), 0x00554D76 (inside the u16 width lookup),
  0x00556B3E (inside the sorted display-list insert), 0x0056ABC8 (inside the console draw
  routine). They are named as the fragments they are, with <= 0.35 confidence.
* `decomp/native_names.json` contains three-letter junk "names" inside this band
  (0x0053692C "xnS", 0x00552830 "lDU", 0x00555D50 "p2f", 0x00556C60 "hnU", 0x0056DB04 "XRf") —
  literal-pool words misparsed as symbols by `tools/recover_native_names.py`. None were used as
  evidence.

## Open problems / honest gaps

* Everything is static: **nothing here was verified in the emulator or on hardware**, and no
  visual behaviour (`sp`-style animation, text scroll, atlas upload) has been observed.
* 96 of 150 names carry `maybe_` because the *mechanics* are clear but the *owner class* is
  inferred from vtables/neighbouring lanes. The weakest groups are: the 0x53E-0x545 text-box
  helpers (owner "Ui_Text*" vs "Ui_Layout*"), the 0x54D-0x56E text engine (the game has its own
  text renderer separate from the NW4C layout text code named in N_092), and the glyph atlas
  (0.45-0.55) whose exact cell table variant (0x58 vs 0x54 stride) I report per function.
* `0x00547FB4`, `0x00555BA0`, `0x0054B6B4`, `0x0054EF94`, `0x00550B7C`, `0x005508A4` are
  singleton/instance accessors; four of them are only identifiable as such by shape, not by a
  named caller.
* `0x00535E50` carries the highest confidence in the batch (0.75) but the "8-slot" caller
  interpretation (`Ui_SpriteList` in N_106) will need one line of correction when the sprite
  cache and SARC reader are separated; the magic constants themselves are not in doubt.
* `0x0054BF38`, `0x00554D76`, `0x00556B3E`, `0x0056ABC8` are decompiler garbage and are named
  only as "fragment of X"; they should not be counted as named functions by the progress page.
