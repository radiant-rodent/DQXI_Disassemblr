## What the band is

The batch header calls it `General_Procedures`, which is a generator artefact. Address-ordered, the
band is a contiguous slice through several engine areas:

| range | area |
|---|---|
| `0x57010C-0x5729D0` | bitmap/pool allocator init + a 226-entry table of tiny object-type predicates |
| `0x573600-0x576900` | math/geometry: bounding sphere (Welzl), circumsphere, OBB/PCA, rotation matrices/quaternions; script VM helpers |
| `0x576A80-0x57EEA8` | container ctors, serialized var-int reader, scene-node/model-instance vtables |
| `0x585C18-0x58D5E8` | Gfx scene entries: mesh building, vertex dedup, bounds, name hashing, bit arrays |
| `0x5907C8-0x598898` | UI window / party-action / field-action / target-marker vtables (mostly deleting destructors) |
| `0x59AA20-0x5A62EC` | party row/talk panels, Battle2DUnit state blocks, render-object arena allocator, widget flag cascades |
| `0x5A6738-0x5B5684` | render-object/renderer helpers, save-record counters, Squirrel VM container/bitwise op |
| `0x5BD704-0x5CE1xx` | Field2D sequencer steps, sprite/effect bookkeeping, camera curve, sprite drawing |

The decisive evidence was **vtable reconstruction**, not the call graph. Only a handful of these
addresses have a direct `bl` caller; most are C++ virtual methods. For each batch address I scanned
the raw image for its 32-bit address, walked back to the preceding `{0,0}` pair (offset-to-top +
null RTTI), dumped the whole vtable and resolved every slot through `functions.jsonl` and the
sibling `out/N_*.json` names. That is how e.g. `0x5929DC` became `Field_BeeRiseAction_Delete`
(vtable slot 1 is the already-named `0x5926BC`, which plays the literal string **`Bee_Rise`**), and
how the six party-panel destructors were separated by their vtable slot 6 (`SpawnInfoPopup`,
`PlayEmote`, `WaitForActor`, `SpawnEventBalloon`, …).

Other load-bearing facts:

- **`0x574E48` / `0x57505C`** are the 3-point circumcircle and 4-point circumsphere; `0x5737A4` is
  the Welzl solver that uses them (switch on boundary-point count 0–4, move-to-front recursion),
  and `0x573600` is the array wrapper. This makes `0x58D5E8` (`Gfx_SceneEntry_BuildMesh`) and
  `0x575A40` (`Math_ComputeObbFromPoints`) consistent: the scene loader really does compute both a
  bounding sphere and an OBB per entry.
- **`0x5B5684` is the Squirrel bitwise-operator core** — its own literals are
  `"bitwise op between %s and %s"` and `"internal vm error bitwise op fai…"`, and the switch maps
  0/2/3/4/5/6 to and/or/xor/shl/sar/shr. Highest-confidence name in the batch (0.9).
- **`0x5C45CE` is a byte swap** (canonical bswap32 arithmetic), named `std_Bswap32`.
- **`0x5723C8`, `0x585C18`, `0x586E6C`, `0x586ED8`, `0x593668`, `0x59DC9A`, `0x5A1F54`,
  `0x5A1FA8`, `0x5A2210`, `0x5BD8A2/A6/AA`, `0x5CB3B8/BC`, `0x5CD9BE` are not normal
  functions.** `0x5723C8` is the first of 226 identical 44-byte type predicates Ghidra merged into
  one 0x608-byte "function"; the `0x5CB3B8/BC` pair are **jump-table slots** of the
  `ldr pc,[pc,r0,lsl #2]` switch at `0x5CB3A8`; several others are branch labels reachable only by
  fall-through. The `functions.jsonl` seed marks a number of ARM ranges as **Thumb**, which is why
  Ghidra emits `halt_baddata()` pseudo-C for them. Each such entry is named with `maybe_…` and a
  summary that says exactly what it is, so M1 and the progress page can exclude them rather than
  count them as named functions.
- **`0x10F6CC` is treated here as an intrusive-instance release** (it loads a control block at
  `[this-8]` and dispatches `vtable[1]`), which is consistent with other lanes' reading of it as
  operator delete over an 8-byte header. The "deleting destructor" pattern
  `class_dtor(); 0x10F6CC()` is used consistently in the evidence text.

   `asm/text/text_00XXXXXX.s` wherever Ghidra had produced `halt_baddata()` or an obviously
   corrupted body.

   (VA = file offset + 0x00100000): `2π`, `π`, `0.5`, `1.0`, the covariance/hash constants, the

5. Scanned the whole image for each batch address as a little-endian word (vtables, init tables,
   jump tables) and decoded the containing vtable with the names of the neighbouring slots.
6. Wrote the JSON incrementally by cluster and re-validated the schema/prefix/param rules after
   every write.

## Open problems / not verified

- **Everything is static.** No emulator run and no playtest; no behaviour (sphere fit, OBB, mesh
  build, sequencer step, UI panel reset) was observed executing. Names rest on code shape, string
  literals, constants and vtable neighbours.
- **`0x58D5E8` (`Gfx_SceneEntry_BuildMesh`) and the `Gfx_ModelInstance_*` names** are the most
  consequential guesses. The vtable 0x7828B4 mixes `Gfx_CharModel_*` methods with generic model
  instance ones (other batches' names), so the exact class boundary is still open.
- **`0x574B10`** is clearly "six covariance terms → orientation quaternion", but whether the
  scratch matrix helpers at `0x574CE8/0x574774/0x574A20` perform a Jacobi rotation or a simpler
  power iteration is not proven. Name is `Math_ComputePrincipalAxesQuaternion`, not
  "EigenDecomposition".
- **`0x5907C8`** is classed as a UI window deleting destructor because it calls `0x3BEE7C`
  (a composite-window destructor tail) and then releases the instance, but its vtable slot 1
  (`0x3A799C`) reads like a *setter* in the current Ghidra C, so the exact class is uncertain.
- **`0x5A62EC`, `0x5A61E8`, `0x5A6738`** (settings/parameter initialisers) and `0x5B14A4/0x5B1598`
  (124/25-bit counters) are mechanical descriptions; the *meaning* of the modes/records is unknown.
- **`0x5CD988` / `0x5CD9BE`**: Ghidra truncates in the middle; the draw/record interpretation is
  from the surviving stores and the vtable, not from a complete function.
- 83 entries deliberately keep `maybe_` because the mechanics are clear but the owner class is
  positional (the band is cut in address order, so a name like `Ui_*` vs `Field2D_*` is a family
  inference from the neighbouring vtables).
