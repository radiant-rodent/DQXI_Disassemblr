# N_118 — native naming batch — done report

Lane: `N_118` | Batch: `orchestration/naming/batches/N_118.txt` | 150 addresses
(`0x005CD9C2` .. `0x0064DDF8`), sizes 0x4 .. 0xC8C bytes.
Output: `orchestration/naming/out/N_118.json` — 150 objects, 97,658 bytes, exact batch
order (ascending address), exact 7-key schema.

## What existed before

Nothing. There was no `orchestration/naming/out/N_118.json`, no `orchestration/done/N_118.md`
and no `N_118` entry in `AGENT_LOG.md`. All 150 entries are new work.

## What I did

Entirely static analysis: no emulator, no debugger, nothing written to
`..\3DS_Translate`, no binary or asset modified.

1. Read the readable C for all 150 addresses from the paths in the batch file, then produced a
   compact per-function digest plus the seed metadata (mode, size) from
   `decomp/functions_index.json` / `decomp/function_seed.tsv`.
2. Built a name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 115 sibling `orchestration/naming/out/N_*.json` files, and
   a caller index over all 18,748 readable C files.
3. **Caller coverage is almost zero**: only 9 of the 150 addresses are called from another
   readable function. The rest are C++ virtual methods, tail fragments of larger functions or
   seed-table artefacts, so the call graph cannot carry this band. The few callers that exist
   were still decisive for the vocabulary:
   - `0x005F3484` / `0x005F362C` ← `Field_SceneObject_ReleaseEffect` / `Field_SceneObject_ShowEffect`
   - `0x005F9EF4` ← `Script_ArrayAppend`
   - `0x0061A1B4` ← `Ui_Layout_ResetAnimSlot`, `0x0061BBB4` ← `Ui_Layout_GetButtonState`
   - `0x006221D0` ← `Ui_ListWindow_ApplySelectedIndex` / `Ui_PageList_StepCounterUp/Down`
   - `0x00632C98` ← `maybe_Ui_CreditWindow_UpdateChildVisibility`,
     `0x0063A128` ← `maybe_FieldParty_UpdateMemberUiState`
4. Used the already-named neighbours on both sides of every address (the batch bands are cut in
   address order, so each cluster already has named anchors from N_072–N_101 and N_020/N_021/N_030/N_075/N_096).
   That is what fixes the class family for the many vtable methods: e.g. `0x005CD9C2`–`0x005CFCAC`
   sits inside the `Field2D_Sprite_*` run, `0x005D2xxx`–`0x005DAxxx` inside the
   `Field_Gimmick_*` run, `0x0060xxxx` inside `BattleScene_*`, `0x0062Bxxx`/`0x0064Dxxx`
   inside the Ui/Party/Battle helpers.
5. Fell back to the bit-matching disassembly (`asm/text/text_00XXXXXX.s`) wherever the readable C
   was a stub. This is what separates real functions from seed artefacts, and it recovered the
   prologues Ghidra lost.

## What the batch actually is (the "General_Procedures" header is a generator artefact)

(After stripping `maybe_`, the 150 names fall into: Ui 50, Field 23, Container 19, Data 15,
Field2D 12, Gfx 7, Actor 6, Sq 5, BattleScene 3, Battle 3, and 1 each for Anim/Save/Fs/Math/Party/Model.)

### A. Field2D sprite/glyph engine (`0x005CD9C2`–`0x005CFCAC`)
`Field2D_Sprite_UpdateGlyphAttachment` … `Field2D_Sprite_SetGlyphIcon` is a continuous named run
around this batch. The legible members are `0x005CF4B0` (positions the 12 quad cells of a
nine-slice 2D sprite through `0x001C3728`/`0x001C3774`) and `0x005CEEE8` (time based step
progress: `anim[0]`=start, `[1]`=length, `[2]`=remaining, rebuild or clear the 12 cells).
`0x005CFCAC` scales a record's alpha by `g_005cfd14` and submits it to the renderer's virtual
add slot. Everything else in the cluster is glyph-quad construction that calls the glyph lookup
`0x005BC04C` and the metric lookup `0x005C0A30`.

### B. Field gimmick state machines (`0x005D2860`–`0x005DAAB4`)
Three variants of one state-machine dispatcher are recognisable and documented as a family:
`0x005D5A84` (3 states, table at self+0x20, float time accumulated into f_28),
`0x005D8ADC` (4 states, table at self+0x34) and `0x005DA5D0` (5 states, table at self+0x2C,
disabled when `f_d4 < 0`). Each entry is a 0x18-byte record `{..., code* at +0x34, thumb bit at +0x38}`
resolved through a base pointer at self+0x40/0x4c/0x54. `0x005D6600`/`0x005D7BB8` clear all
children of the 0x1460-entry child manager (`0x004A1E00` + `0x00650D34`).
`0x005D3BE8` copies a whole variant config out of the global `g_005d3d70` and the byte table
`g_005d3d74`; `0x005DAAB4` instantiates up to 12 visual part records.

### C. Effect/trail/object part flags (`0x005F3484`–`0x005F6C14`)
Two verified pairs: `Field_SceneObject_ClearPartFlag` (`0x005F3484`, caller
`Field_SceneObject_ReleaseEffect`) and `Field_SceneObject_SetPartFlag` (`0x005F362C`, caller
`Field_SceneObject_ShowEffect`) both flip one bit of the `+0x52` part-flag byte and then notify
their child parts through vtable `+0x38` (hide) / `+0x3C` (show). `0x005F5B18`/`0x005F5D3C` are
the same idea for EffectPart with three children each.

### D. Squirrel engine (`0x005F9D1C`–`0x006009C0`)
Strongest names in the batch: `0x005FC6FC` `Sq_LexerSkipWhitespaceAndComments` (0.75, its own
error string `"missing ______ in comment"`) and `0x005FF9D8` `Sq_LexerAdvanceChar` (0.60, its own
string `"Invalid character"`, line counter at `+0xC`). `0x005F9EF4` is `Sq_Array_AppendRange`
(0.60) — bound native `Script_ArrayAppend` calls it, it grows the 8-byte element array with
`0x0014CE14` and handles the 0x08000000 refcount bit. The rest are the shared
container/value create-release helpers used by the compiler nodes (`0x00245C1C/40/80` list ops,
`0x00147AEC` pool free).

### E. Registry / container lookups (scattered)
Six addresses are the *same* function body with different globals — an open-addressed,
type-tagged object registry: `0x005D9214`, `0x005F2ECC`, `0x005F581C`, `0x00619C68`,
`0x00630C54`, `0x00630CDC`. They are named `Container_FindObjectByTypeIdE..J` to extend the
existing `Container_FindObjectByTypeId` (0x00619B20) instead of inventing a new scheme.
`0x00630414` is a red-black-tree name lookup (string hash from `g_0063055c/g_00630560` then
`strcmp` = `0x0010540C`), named `Container_FindEntryByNameHash` (0.55).

### F. UI / menu / data helpers (`0x00616900`–`0x0064DDF8`)
The bulk. Most are virtual methods of the Ui part/list/sprite classes already named around them,
e.g. three sprite vertex-colour writers (`0x00646400`, `0x0064663C`, `0x006470CC` — all write
the same colour into vertices 0..3 through vtable `+0x10`), three part-name comparators
(`0x0063B8EC`, `0x006435B8`, `0x00645D74`, each against its own literal pointer), and the
smith-menu row predicates (`0x0064D824`, `0x0064D9B8`, `0x0064DB1C`, all using the `0x306`
record sentinel and the vtable `+0x54`/`+0x7C` idle queries).
Two path builders are solid: `Anim_FormatMotionPackPath` (0.65, literal
`"3d_motion/%s/%s/%s.pack"` + `"%03d"`) and `maybe_Model_Build2DModelPackPath` (0.60, literal
`"2d_model/%s.pack"`). `Data_GetRecordEntry` (0.60) is a 0x24-byte record table with a call-once
guard (`0x0010009C`); `maybe_Fs_BuildBg2DResourceName` (0.60) formats `"2d_bg/%d"` clamped to 1..0x1F.

## Seed-table / decompiler defects found (not fixed, not my files)

`decomp/function_seed.tsv` and `decomp/functions_index.json` contain **15 addresses in this band
that are not function starts at all**; their readable C is decompiler noise. I named them
`maybe_Data_MisparsedSeed<address>` so the merge and the progress page can exclude them:

| address | why it is not a function |
|---|---|
| 0x005CD9C2, 0x005CD9C6 | Thumb seeds inside the ARM routine at 0x005CD988 (jump table at 0x005CDA0C) |
| 0x005CDBDA, 0x005CDBDE, 0x005CDBE2 | Thumb seeds inside the ARM routine at 0x005CDB8C |
| 0x0060404C / 0x00604054 | the ARM function is 0x0060404C..0x00604064; 0x00604054 is its `bl` instruction |
| 0x0060488C | `bl 0x006F1EEC` in the middle of the switch/VFP block 0x006048xx |
| 0x00622020 | `b 0x0010F6CC` tail thunk; the remaining 20 bytes are literal-pool words |
| 0x00625778 | real ARM prologue but Ghidra aborts; body recovered from asm only (kept as `maybe_`) |
| 0x0062DA24, 0x0062DBC0 | epilogues (`pop {..pc}`) of the preceding camera routines |
| 0x0063349E | 10-byte Thumb seed with no instruction at that address in the ARM stream |
| 0x005CDB8C, 0x005F5268, 0x0060404C | real entries Ghidra truncates with "bad instruction data" (kept, evidence from asm) |

Also worth recording for the merge: `0x00100B74` = `wcslen` (UTF-16), `0x00100B86` = `strcat`,
`0x00100B32` = `wcsstr`, `0x0010009C` = call-once/init guard, and `0x0010F6CC` = the engine's
**virtual delete** (loads the 8-byte header at `ptr-8` and calls vtable slot 1). Several prior
batches described `0x0010F6CC` as "abort/terminate"; it is not. That single fix would make ~30
existing summaries accurate.

## Honest gaps / what is NOT verified

- Everything is static. No emulator run, no playtest, no dynamic observation of any of these
  functions. Nothing here has been seen executing.
- 131 of 150 keep a `maybe_` prefix. For most of them the *mechanics* are read directly out of
  the C/asm (which offsets are touched, which vtable slots are called), but the *owner class*
  is inferred from the neighbouring named functions. That is still a guess.
- The first cluster (`0x005CE8F8`–`0x005CEA6C`, four glyph-quad variants) is the weakest: the
  seed marks them Thumb although the bytes look like ARM, so the function boundaries themselves
  are uncertain. Same for `0x005D2AE0`/`0x005D2B4C` (0x35) — the asm is readable only as VFP
  constant stores to unknown fields.
- `0x0063E064` (0.25) is an 0xC8C-byte function whose readable body collapsed to one call. Only
  the module (the data manager at 0x0071xxxx) is known; treat as unnamed in substance.
  `0x00649BD8` (0.30), `0x00616900` (0.30), `0x0064C82C` (0.30), `0x005F300E` (0.30) and the two
  `0x0063A0A4`/`0x0063A6D4` one-call wrappers (0.30) are in the same category.
- `maybe_Save_UpdateSlotEntry` / `maybe_Field_CollectIdsInRect` / `maybe_Field_SortPartLists`
  (`0x005F21CC`, `0x005F22E4`, `0x005F278C`) form a coherent little subsystem (0x88-byte records,
  rect queries, bitmask rows, merge sort), but I could not prove whether it is the save-slot
  table (as the N_095 anchor `Save_SlotTable_Init` suggests) or a field-scene grid. The three
  names hedge on purpose; the merge should pick one reading only after the struct owner is
  identified. This is the biggest open question of the batch.
- I did not verify the vtable slots claimed in the evidence against the raw vtables in
  `.rodata` (I only read slot *offsets* used in the code, not the table contents).
