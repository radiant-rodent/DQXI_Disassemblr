# N_119 — native naming batch (resumed)

**Task:** name and document the 150 functions in `orchestration/naming/batches/N_119.txt`
(`0x0064F8C0`–`0x0067C498`, header label `General_Procedures`).
**Status:** complete — `orchestration/naming/out/N_119.json` has all 150 addresses in batch order.

## What existed before

Nothing. There was no `orchestration/naming/out/N_119.json`, no `orchestration/done/N_119.md`
and no `N_119` entry in `AGENT_LOG.md`, so all 150 entries are new work. No scratch file from the

## Method

1. Built a name map from `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and
   every sibling `orchestration/naming/out/N_*.json` (16,894 names), then collision-checked the
   result.
2. Built a caller index over all ~18,700 readable-C files. Only seven of the 150 addresses have a
   direct caller in the decompiled C (`0x652160`, the four `0x65FDA0`–`0x65FE24` sound field
   getters, `0x660E20`, `0x6610EC`). The rest are virtual methods, static constructors, switch
   tails or seed artefacts, so a call graph is not enough for this band.
3. Scanned `original/exefs/code.decompressed.bin` (base `0x00100000`) for aligned runs of code
   pointers to recover vtables, mapped each address to `vtable + slot`, and printed all named
   sibling slots. This fixed the class family for ~35 functions.
4. Decoded every function's literal pools with Capstone (ARM and Thumb) and classified each literal
   as code / rodata / data / inline ASCII / float, then hand-decoded the ARM wherever Ghidra's
   readable C was `halt_baddata`, `unaff_*`, `in_Zr` or plainly split.
5. Cross-checked the adjacent completed lanes, especially `N_120` (the field-actor class library
   immediately after this band) and `N_117`/`N_096`/`N_097`/`N_101`, and reused their vocabulary
   instead of inventing a second one.
6. Checked the available native-binding scan (`%TEMP%bindings.txt`, 304 entries) for the 150
   addresses: none of them is a script-bound native, so the Squirrel scripts could not add
   game-logic evidence for this band.

## Load-bearing findings

- **`0x00672B4C` is `std_Atan2f`** (confidence 0.8). The body classifies both operands, divides
  `y/x`, evaluates the atan polynomial and adds `pi/2`/`pi`; `0xC0490FDB` is `-pi`. This was
  decisive for several camera/field functions that call it indirectly.
- **Four field-actor class registrations** were decoded from inline strings next to the functions:
  `Actor2D` (`0x678350`), `Actor3D` (`0x6786D0`), `GmShip2D` (`0x67A504`) and `EnemyActor`
  (`0x67C498`). Each allocates/links a registry node, writes the class name at `+0x10` and the
  factory/vtable word at `+0x0C`, and fills a 12/13-entry RGBA class colour table. `0x001787FC`
  (handle resolver) and `0x00291A5C` (`Ui_MapIcon_ProvideShipIconAlt`) identify the class by calling
  virtual slot 0 and comparing the returned descriptor with `0x007C3330` / `0x007C33D4` /
  `0x007C47AC` / `0x007C3684`. This agrees with N_120's `Field_RegisterActorClass_<Name>` scheme,
  so the names were aligned to it.
- **The `0x678D04`–`0x67C2C8` block is the actor class colour-table family**, not a second set of
  type init functions. Every one writes the same 12/13 RGBA entries
  (`A0A0A0`, `3A60`, `E735`, `50D2DC`, `B2F7`, `7D1E`, `181818`, `910B10`, `F62D`, …), with a
  per-class alpha/base colour; N_120 independently identified the same table and its reader-less
  static-initialiser shape. They are named `maybe_Field_InitActorColorTable_<data addr>`.
- **`0x006507E8` is slot 8 of the Dulneigh monster action vtable `0x00773AE8`** (slot 0 is N_111's
  `Monster_Action_Dulneigh_DtorDelete`). It reports ready when the actor motion is finished or the
  action id is `0x1b`.
- **`0x00663574`/`0x00663590`/`0x00663714` are the three virtual slots of two font-atlas
  implementations** (`0x00781DF0`, `0x00781F54`): glyph page, glyph-cell range search (3-byte cells,
  `0xffff` default) and glyph-quad builder. `0x006651D4` then maps character code → glyph id with
  the `0x80` fallback.
- **Fragments and seed defects were identified rather than invented as functions:**
  `0x65556A` (float/literal pool of the trail code), `0x658C40` (tail of N_035's
  `Svc_Blob_Serialize`), `0x661BEA` (tail of
  `Sound_Seq_ExecuteChannelCommand`), `0x6640FE` (tail of `Text_BuildCharTransform`), `0x667F8E`
  (tail of `Field2D_Sprite_ChoosePathStep`), `0x6695BC` (tail of `MoLive_Stream_ReadPcm`),
  `0x66F608` (tail of the `0x66F580` comparator), `0x673F48` (const pool after `std_Powf`),
  `0x6770F2` (tail of `Gfx_GpuState_PackTransformConstants`, not zero padding), and the six
  `0x668552`–`0x6685B2` interior addresses of the `0x6684F8`/`0x668598` ARM accessor stubs.
  All are named `*_Tail` / `*_Fragment` / `*_LiteralPool` / `*_ConstTable` with low confidence.
- **Static-init block `0x677B24`–`0x67A8F0`**: `0x677B24`/`0x677DC8` initialize global critical
  sections; `0x677B60`/`0x677CAC` initialize intrusive list sets; `0x678A88` wraps the already
  named `Mem_BitmapPool_Init` (`0x0057010C`); `0x678114` sets four `Gfx_Node` refcount globals and
  registers `Gfx_Node_RefPtr_Release` (`0x001BF798`). The eight guard-only bodies are
  `__cxa_guard_acquire`/release stubs (`0x0010009C` / `0x00101A94`), named
  `maybe_Field_InitActorGlobalState_GuardA..H`.
- `0x0066F0A0` is `std_wcslen` (tail-call to `0x00100B74`, identified as wcslen by N_111).
- `0x0066E370`/`0x0066E3AC` are the two virtual methods shared by dozens of field-object vtables
  (`SetMode` slot 1 and `OnEvent` slot 4); `0x0066D720`/`0x0066D7CC`/`0x0066D6B4`/`0x0066D984`
  are the Monster_Attach animation state machine (vtable `0x0078097C`, slot 3 = the named
  `Monster_AttachAnimation`).

## Open problems / honest gaps

- Everything is static; no emulator or playtest was used. Behaviour is inferred from code, callers,
  vtables and constants.
- 102 `maybe_` names. The weakest families are:
  - `maybe_Pack_ReadInline*` / `maybe_Pack_WriteWordQuadAt*` (0x6583E8–0x6584BC, 0x654DA4/0x654DF0):
    the mechanics are certain (fixed 3/6-byte and length-prefixed record readers, four-word
    writers) but the owning serialization system is not proven.
  - `maybe_Field_InitActorColorTable_*` (0x678D04–0x67C2C8): bytes/palette layout are certain,
    the consumer of each table is not; N_120 flagged the same gap.
  - `maybe_Field2D_Map_*LayerTask*` (0x67121C–0x6720F4): the task factories
    (`0x005BE370`/`0x005BF968`/`0x005C0378`/…) and callback pairs are certain; the exact layer
    each one builds is not.
  - `maybe_Field_Object_BindModelTransformB/C/D`: the body is identical to the first one but the
    owning window/class is positional.
  - `maybe_Field_Object2D_CalcScreenRect*`: the 0x0031A658 helper normalizes 2D coordinates, so
    these produce normalized screen-space quads; whether they are marker, sprite or gadget rects
    depends on the caller class.
- `0x00672B4C` is confidently `atan2f`; `0x00673288` was already named `std_Fmodf` by N_001 and
  was not touched. If both are really the same libm function, M1 should keep only one.
- Colour tables at `0x007A8E04` are written by both `0x0067A740` (this batch) and N_120's
  `0x0067FCBC`; that is recorded in the evidence and looks like a shared default table.
- Several addresses are fragments/tails rather than real entry points (see list above); M1 should
  exclude them from progress counts or collapse them into their parent.
