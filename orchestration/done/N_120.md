## 1. What this address band actually is

The batch header says "General_Procedures", which is a generator artefact. The band is
**one contiguous block of the 3DS field-actor ("Gm" = gimmick / NPC / spirit / vehicle) class
library**, and a second stub of the same library after a gap:

| range | content |
|---|---|
| `0x0067A000-0x0068A000` | field-actor class library: class registrations, per-class parameter/colour blocks, actor-list pools |
| `0x006A2000-0x006A6000` | the dive / EggRobo / pursuer-squad part of the same library |

### Evidence that this is the field-actor class library

string literals sit in `.text` next to the function that uses them). Every registration function

### Two registration shapes

* "big" (0x0067C498 / 0x0067D96C / 0x0067DBA0 / 0x0067DD9C / 0x00682038 / 0x00682208 /
  0x00680414 / 0x00683CB4 / 0x0068400C / 0x00686860 / 0x006869B8 / 0x006A38AC / 0x00689030):
  `func_0011CFAC`/`func_0011FE8C` allocate a 0x10-byte node, the node gets the class-name pointer
  at `+0x10` and the vtable/factory word at `+0x0C`, then `func_001235A4` links it into the global
  list head (`0x007BE378`, `0x007C4798`, `0x007C4BBC`, ...). The same function often also writes
  the class's 2-3 word defaults (`0xFF`, `-1`, ...) into `.data`.
* "small" (`func_002A55EC`, used by the NPC*/Gm* families): `(slot, base, name)` triples with a
  0x14-byte stride — no allocation, the registry storage is a static table (`0x007C4D4C`,
  `0x007C4D9C`, `0x007C47D4`, ...). Each call registers one derived class.

## 2. The static initialisers (the bulk of the batch)

~120 of the 150 addresses are **one-shot initialisers of global `.data` blocks**, not methods.
They all follow the C++ static-locals protocol:

```
push {r4,lr}
ldr  r0, =0x007BE2D0
blx  0x0010009C          ; __cxa_guard_acquire (single-threaded newlib: test-and-set)
cmp  r0, #0
beq  return              ; already done
... store the constant defaults ...
b    0x00101A94          ; add ip,pc,#1 ; bx ip  -> veneer to __cxa_guard_release
```

Two verified details:

* `0x0010009C` really is `__cxa_guard_acquire`: `ldr r1,[r0]; cmp r1,#0; beq take;
  movs r0,#0; bx lr; take: movs r1,#1; str r1,[r0]; movs r0,#1; bx lr`.
* `0x00101A94` is not a function body — it is the ARM→Thumb interworking thunk
  `add ip,pc,#1; bx ip`, i.e. the `__cxa_guard_release` tail call. (The disassembly dump shows
  garbage there because it is decoded in the wrong mode.)

**Open question worth flagging to the merge:** every function in the band tests the *same* guard
word `0x007BE2D0`. Either the compiler emitted one COMDAT guard for a shared inline helper, or the
block at `0x007BE2D0` is one module-level "initialised" flag (and then only the first initialiser
to run would execute). `0x00680C14` clears the word *after* the guard (`0x007BE2D4`), and the
`.data` at `0x007BE2D0` is a run of 12-byte records `{0, 0xFFFFFF01, 0}`, so the exact protocol is
not understood. All entries state the observed fact rather than guessing the consequence.

Because of the guard split, Ghidra produced many fragments:

* functions whose body decompiles to a single `func_0010009C(g_...)` call (the acquire path only),
* functions that start with `in_r3`/`arg4` (the destination pointer was loaded by an instruction
  that Ghidra attributed to the previous function),
* entries that are literal-pool words, not code.

Those are named for what they are and the summaries say so.

## 3. Naming scheme used

| kind | count | name | confidence |
|---|---|---|---|
| class registration (`func_002A55EC` / `func_001235A4` + name string) | 17 | `Field_RegisterActorClass_<ClassName>` | 0.6-0.75 |
| 12 × 4-byte constant table (A0 A0 A0 / 3A 60 / E7 35 / 50 D2 DC / B2 F7 / 7D 1E / 18 18 18 / 91 0B 10 / F6 2D, fourth byte = alpha argument) | 60 | `[maybe_]Field_InitActorColorTable_<data addr>` | 0.4-0.5 |
| small global state block (guard + zero/seed 8-12 bytes) | 40 | `[maybe_]Field_InitActorGlobalState_<data addr>` | 0.4-0.5 |
| parameter block written through a caller pointer | 20 | `maybe_Field_InitActorParamBlock_<code addr>` | 0.3-0.45 |
| literal-pool words / not code | 5 | `Field_DataWord_<addr>` | 0.6-0.7 |
| special (CRC-8 table, list pools, dive registration hook, packed-table reader) | 8 | `std_Crc8BuildTable`, `Field_InitActorListNodePool`, `maybe_Field_InitDiveActorRegistrations`, ... | 0.4-0.6 |

Rationale for the data-address suffix: every one of these blocks is unreferenced from the rest of
`code.bin`, so a name that points at *the data* (`..._7A7EE4`) is the only thing a modder can
verify. This follows the existing convention in `out/N_079.json`
(`maybe_Sys_RegisterGlobal_67D094`).

`maybe_` prefix is present exactly when confidence < 0.5 (79 entries; 71 without).

### Why "color table" and not something more precise

The byte groups are 4 bytes each and the last byte of each is the function argument (`alpha`,
`0xFF`, or `arg1 & 0xFF`), which is the shape of RGBA. The identical constant group is also
written inline, with alpha `0xFF`, by the `EnemyActor` registration at `0x0067C498`, so these are
per-class constant tables of the actor library. **What the engine draws with them is not
confirmed** (no reader exists in the image), so the summaries say so explicitly instead of
inventing e.g. "name plate colours".

## 4. Findings beyond the naming

1. **`0x0067E0D0` = CRC-8 table builder.** The inner loop is the CRC-8/ATM bit step
   (`if (x & 0x80) x = (x << 1) ^ 7; else x <<= 1;`, eight times per entry), 256 entries, stored at
   `0x007F2E45` inside the host object at `0x007F2E00` whose `+0x40` is set to `0xA5`. Named
   `std_Crc8BuildTable` (0.6).
2. **The 5 "small" registrations** show the 0x14-byte registry slot layout:
   `+0x00` base/self, `+0x04` type id, `+0x08` name pointer, ... (see 0x0067ECCC: `arg1[0..1] =
   arg2`, `arg1[2] = 0xFF`, then `func_002A55EC(slot, base, name)` for slots 0, 0x14, 0x28, 0x3C).
3. **`0x00680C54` + `0x00681A54` + `0x00687E38`** are the actor-list/node pool setup:
   0x58-byte nodes chained at `0x007C83B4..0x007C8578`, empty-list sentinel `0x00782234`, static
   descriptor `0x00781064`, and a vector built through `0x0010E8C0`.
4. **`0x006A3548`** is a second-level lazy initialiser: it guard-checks its own caller word, then
   calls `0x006F06AC` (guard `0x007B2D40`) and `0x006F0924` (guard `0x007B2D48`) — the dive/water
   actor helpers.
5. **Reachability:** a full branch-target scan of `asm/text/*.s` finds *no* `bl`/`b` from outside
   this band into any of the 150 addresses (the only 45 outside branches are tail-branches into
   the thunk table at `0x0068AB68`/`0x006A202A`). A 32-bit word scan for pointers into
   `0x0067C000-0x0068A000` finds only false positives (ASCII). So the band is linked but not
   reached from `code.bin`: the whole analysis is static, and the tables were never observed in
   use at runtime.

## 6. Honest gaps

* Everything is static. Nothing was run; no emulator, no screenshot, no runtime check that any of
  these initialisers executes or that the guard protocol above is what actually happens.
* The 60 colour tables: the *bytes* are certain, the *purpose* is not. "Behaviour like RGBA" is an
  inference from the 4-byte grouping and the alpha argument.
* Owner-class attribution in the summaries is positional (nearest registration) and is marked as
  such. Large gaps with no class string (e.g. `0x00680834-0x00683BA8`, 13 KB between
  `TimeSpirit3DActor` and `GmGondola2D`) could not be attributed at all.
* 5 entries are not functions (`0x0067F754`, `0x0067F758`, `0x006831A0`, `0x006831A4`,
  `0x00688268`) and 4 more have a wrong start or an undecodable body (`0x0068826C` is 4 bytes
  before the real prologue, `0x0068372C`/`0x00683910`/`0x00683610` are fragments). They are named
  for what they are, but they should not count as "named functions" on the progress page.
* `decomp/ghidra/functions_index.json` marks several of these entries `arm`/`bad instruction`
  although the bytes are valid ARM. The literal-pool entries are a systematic seed artefact of
  this band (Ghidra starts a function after `pop {r4,pc}`).

## 7. Suggested follow-ups (cheapest first)

1. **M1 merge**: treat `Field_RegisterActorClass_*` as high-value names; they are the only names in
   this band that a modder can act on. Consider dropping the five `Field_DataWord_*` entries.
2. **One struct pass** on the field-actor parameter record (`+0x00` float scale 0.6804f, `+0x04`
   float, `+0x0C` 0xFF, `+0x10..+0x3F` colour table, `+0x30` tail) would let all 60
   `InitActorColorTable` entries collapse into one documented type and lift them above 0.5.
3. **Find the reader of `0x007BE2D0`**: that single word decides whether this band is live code at
   all. If nothing reads it, the band is dead linked code and the progress page should say so; if
   it is a COMDAT guard, the initialisers are shared-inline-helper instances and the tables are
   per-class defaults.
4. **Name the shared helpers once** (they appear in dozens of summaries): `0x0010009C`
   `__cxa_guard_acquire`, `0x00101A94` `__cxa_guard_release` veneer, `0x0011CFAC` aligned pool
   alloc, `0x0011FE8C`/`0x001235A4` list allocate/insert, `0x002A55EC` small-registry insert,
   `0x0010E8C0` vector construction, `0x00116AE0`/`0x001114A4` object clear/construct.
5. **Fix the seed** for this band: 9 `functions_index.json` entries are literal pools, fragments or
   a too-early start. A simple rule (`ldr`/`pop {r4,pc}` + `ldr` pool detection) would remove them.
