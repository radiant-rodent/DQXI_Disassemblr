## Method

1. Read `README.md`, `orchestration/PLAN.md`, `docs/CODE.md`, and the previous batches
   `N_118`/`N_119`/`N_120` (the immediately adjacent address bands, same code family) to reuse
   their vocabulary. `N_120` in particular covers `0x0067C754-0x00689270`, the start of this same
   field-actor class library.
2. Read every readable C file from the batch (all 150 exist; none missing). Where Ghidra emitted
   `halt_baddata`, `unaff_*`, `in_r3` or truncated at the guard branch, I disassembled the raw
   function with Capstone (ARM/Thumb from `decomp/functions_index.json`) and read the bytes from
   `original/exefs/code.decompressed.bin` (VA = file offset + `0x00100000`).
3. Decoded every `ldr rX,[pc,#imm]` literal and every `add rX,pc,#imm`, then classified each
   target as `.text`, `.rodata`, `.data`, `.bss` or inline ASCII, following string pointers to the
   actual class names.
4. Scanned the whole 6.4 MB `.text` for ARM `b/bl/blx` and Thumb-2 `bl/blx` targets into the band,
   and scanned the whole image for 32-bit pointers into the band. This is how the reachability
   result below was established.
5. Reconstructed the shared helpers used by the whole band (see next section) and classified the
   150 functions by body shape rather than by name guesses.

## Load-bearing findings

### Shared helpers (reused from previous lanes, one correction)

- `0x0010009C` = `__cxa_guard_acquire` (single-threaded newlib test-and-set: read guard byte,
  set to 1 and return 1 on first call, return 0 afterwards). `N_118`/`N_120` already identified it.
- `0x00101A94` is **not a function**: it is the ARM→Thumb interworking veneer
  `add ip,pc,#1; bx ip` that lands on `bx lr` at `0x00101A9C` (the `__cxa_guard_release` path).
  Ghidra renders it as `stm r0!,{r0}` garbage.
- `0x00672404` is just `bx lr`; the many `b 0x00672404` tails are plain returns, not
  `__cxa_atexit` calls.
- `0x002A55EC` = small registry insert `(object, vtable/factory, class-name)`; sets `+0x00..+0x08`
  to a self-linked intrusive list, inserts into the global registry list and stores the name at
  `+0x10`. `0x002A56A4` = matching list unlink.
- `0x001235A4` = intrusive doubly-linked-list insert (link a node before the list head).
- `0x0011FE8C` = heap allocate entry (called with size `0x10` here).
- **Correction to N_120:** `0x0011CFAC` is *not* an "aligned pool alloc"; it is the libgcc
  unsigned-divide helper (`__aeabi_uidivmod` shape: compares the divisor against `dividend>>2/5/8/12/16`
  and returns quotient in r0, remainder in r1). The constructors call it as
  `(nodeSize + 0x0F) / 0x10 * 0x10`, i.e. a 16-byte size round-up before the `0x10`-byte node
  allocation. This matters if M1 wants to name these helpers globally.
- `0x00782AAC` is the shared typeinfo/vtable word copied into every newly built registry node;
  `0x007BE374` is its guard, `0x007BE378` the registry list head and `0x007BE2D0/0x007BE2D4` the
  shared one-shot/guard block.

### The band is the tail of the Dive field-actor class library

The 150 addresses are one contiguous run at the end of the same static-init block that N_120
started. Classification by body shape:

| shape | count | naming scheme |
|---|---|---|
| class registration / registry-node constructor | 19 | `Field_RegisterActorClass_<Name>` |
| 12-entry RGBA colour-table initialiser | 85 | `Field_InitActorColorTable_<data addr>` (plural/tables when several) |
| small global-state block initialiser | 28 | `Field_InitActorGlobalState_<data addr>` |
| parameter-block initialiser (`-1`/`0xFF`, sometimes in r3) | 16 | `maybe_Field_InitActorParamBlock_<addr>` |
| intrusive-list head initialiser | 1 | `maybe_Field_InitActorListHead_7C6E58` |
| literal-pool word, not a function | 1 | `Field_DataWord_6B24F8` |

Class names decoded from inline strings in `.text` (each is a real actor class of the 3DS game):

`Dive_ObjectActor3D`, `Dive_SpiritSquadActor3D` + `Dive_SpiritActor3D`, `EnemyDesertWhale`,
`SmithStandActor3D`, `SpiritMenuActor3D`, `GmHellkachaRock2D`,
`GmD011BookShelf3DActor` + `GmD011BookShelfSwitch3DActor`,
`Dive_GimmickActor3D` + `Dive_Gm_ItemBox3D` + `Dive_Gm_CheckPoint3D` + `Dive_Gm_ClearLayer3D`,
`QuickItemGet3DActor` + `PlayerJockeyActor3D`, `GmDullahanKnight2D`, `GmGetOffGondola2D`,
`SmithProductActor3D`, `GmSpiritGenerator2D` / `GmSpiritGenerator2DGlitter` /
`GmBlendSpiritGenerator2D`, `Bubble`, `AttachVehicleActor3D`.

The 85 colour tables all write the same 12 RGBA entries, with one alpha byte per entry:

```
00 00 00 / A0 A0 A0 / 3A 60 / E7 35 / 5F 3A / 50 D2 DC /
B2 F7 / 7D 1E / 18 18 18 / 91 0B 10 / F6 2D
```

This is the same default palette N_119/N_120 found in the adjacent band; the alpha is either a
constant `0xFF` or the low byte of the incoming first argument. No reader exists in the image, so
the draw use is stated as unconfirmed (confidence 0.45-0.5).

### Reachability (honest limitation)

- No `b/bl/blx` from outside the band targets any of the 150 addresses (full ARM and Thumb-2 scan
  of `.text`).
- No 32-bit word anywhere in the image points into `0x006A5AE4-0x006B5A30` (only ASCII false
  positives).
- The retail `.init_array` is empty: both `__init_array_start` and `__init_array_end` are
  `0x0079AA18` (read at `0x00102818/0x0010281C`). So this whole constructor block is linked but
  **not reachable from the retail static-init table**, exactly as N_120 reported for its half.
  The functions are real compiled C++ initialisers; they are not called by any code path in this
  image. I recorded this in every registration evidence and in the report rather than inventing a
  caller.
- There are a few Ghidra split points: the `GmSpiritGenerator2D` family constructor is split over
  `0x6AF790 / 0x6AF7FC / 0x6AF8A0 / 0x6AF948`; the `0x6B2350` colour table continues at
  `0x6B24FC` (and `0x6B24F8` is a literal-pool word, not code); the `0x6A6A88`/`0x6A6C50`/
  `0x6AD064` parameter writers take their destination in `r3` from the preceding split
  instruction. These are named and explained in the JSON.

## Open problems / not verified

- **Semantics of the colour tables are inferred, not observed.** The bytes, entry count and alpha
  handling are certain; "per-actor colour table" follows N_119/N_120's reading of the same
  palette. No emulator run, no playtest, no visual confirmation.
- **Reachability is unresolved.** Empty `.init_array` + zero xrefs means either the constructors
  are dead in this build or the game initialises them through a mechanism not present in
  `code.bin` (e.g. a table built outside the image). I did not find such a mechanism. This is the
  biggest open item, and it is the same one N_120 flagged.
- 19 registrations carry the class name in plain text and are high confidence (0.65-0.75);
  54 entries are `maybe_` because the owner class is positional or the block purpose is inferred.
- `0x6B3314` is a different descriptor shape (its `+0x10` slot holds a code pointer,
  `0x00162D9C`, not a name string); named `maybe_Field_RegisterActorClass_UnnamedDescriptor`
  at 0.3.
- The `0x6AF790/0x6AF7FC/0x6AF8A0/0x6AF948` split is named per part; M1 may prefer to collapse
  them into one `Field_RegisterActorClass_GmSpiritGenerator2D_Family`.
- Eight thin initialisers write only the shared block `0x007BE2D4`. I kept the N_120 convention but
  appended their own address (`..._7BE2D4_006A5AE4`) so the names are unique for the merge.
- `0x0011CFAC` is reclaimed as the unsigned-divide helper (see above); if M1 adopts N_120's
  "aligned pool alloc" label, that label should be corrected instead.
