# N_122 — naming batch report

**Task:** name and document the 150 native functions in `orchestration/naming/batches/N_122.txt`.
**Owns only:** `orchestration/naming/out/N_122.json` (+ `AGENT_LOG.md`, this report).
**Status:** completed — 150/150 addresses covered, 150 unique names, 0 collisions with 118 sibling
batches and the project symbol files.

## What the batch turned out to be

The header label `General_Procedures` is a generator artefact. The 150 addresses are two unrelated
bodies of code:

| part | addresses | what it is |
|---|---|---|
| A (34) | `0x006B5BF0–0x006BBD80` | tail of the 3DS **video/MoLive movie-codec helper layer** (`0x006B873C–0x006B9A98`), the **12-entry RGBA colour-table initialisers** of the field-actor/UI library (`0x006B5BF0–0x006B782C`), eleven `__cxa_guard`-style **one-shot static-init stubs**, one **named-object registry ctor** and a **GPU command-list quad emitter** |
| B (116) | `0x006C31C8–0x006C9708` | 33 of the 70 **dispatch tables of the game's generic C++ state-sequence / action-sequence framework** (vtable block `0x0075A7B0 … 0x0075B188`), 4 methods each |

The 32 dispatch tables `0x0075A7B0 … 0x0075AC0C` in this batch are exactly the ones that precede N_123's
38 tables (N_123 = `0x006C97C4–0x006D0E90`, vtable block starting `0x0075AC30`), so this batch is the
*first half* of the same framework. One object (`vtable 0x0075AC30`) is split across the two batches: its
`ChangeState`/`Tick` are here (`0x006C94E4`, `0x006C9708`), its `Delete`/`SetState` are N_123's
(`0x006C97FC`, `0x006C97C4`).

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md` and the sibling
   batch outputs (N_098, N_120, N_121, N_123 are the load-bearing ones).
2. For every address: readable C (`decomp/readable/functions/…`), then the raw ARM/Thumb listing
   (`asm/text/text_00680048.s`, VA = file offset + `0x00100000`) whenever Ghidra had truncated or
   mis-split the body.
3. Built a **vtable map**: scanned `.rodata` for every word equal to a batch address, then for each
   `ChangeState` walked back to the preceding zero word (offset-to-top) and dumped the six dispatch
   slots. This gave the class grouping, the slot roles and the table ordering for all 116 entries.
4. For every table base, scanned the image for the literal pointer store to find the **owner
   constructor** (the function that installs the vtable). All 33/33 owners were found and are cited
   in the entries (every one of them already carried a name from a sibling batch).
5. Decoded the object layout and the dispatch slots from the assembly (see below), and cross-checked
   every conclusion against N_123's independent analysis of the following 38 tables.
6. Verified the colour-table family by checking the substitution rule byte by byte (see below).

## Load-bearing findings

### The state-sequence object

```
+0x00  vptr (points at a zero word; slots below are vptr-relative)
+0x04  current state id
+0x08  float state timer
+0x0C  state frame counter
+0x10  float last delta
+0x14  pending-state queue, 2 slots (de-duplicated), count at +0x1C
+0x20  pointer-to-member-function 'this' adjustment
+0x24  state records (n × stride, stride 0x18/0x20/0x30/0x40)
+n*stride+0x24  owner's "state changed" pointer-to-member-function (code,+4 encoding)
dispatch: +0x04 Delete, +0x08 Tick, +0x0C event dispatch, +0x10 ChangeState,
          +0x14 QueueState, +0x18 SetState
```

* **ChangeState** (`0x224–0x254` body, slot 3): validates the queued id, calls the outgoing state's
  exit handler, the incoming state's enter handler (previous id as argument), then the owner's
  handler, zeroes the timer/frame counter and clears the queue; returns 1 on success.
* **Tick(dt)** (slot 1): calls ChangeState and, only if nothing changed, accumulates `dt` into
  +0x08 and bumps +0x0C.
* **QueueState** (slot 4): bounds + full-queue check, de-dupe, append at `+0x14+count*4`, `++[+0x1C]`.
  The batch contains one Thumb copy of it (`0x006C5398`), whose ARM twin `0x006C3384` is also here.
* **SetState** (slot 5): `if (QueueState(state)) ChangeState()` — the entry point the game code uses.
  N_123 named this trampoline `DeleteIfDone`; the disassembly shows the two slots are queue-state and
  ChangeState (the queue routine is byte-identical to `0x006C3384`/`0x006C5398`), so I named it
  `SetState` and flagged the difference in the evidence.
* **Delete** (slot 0): `b 0x0010F6CC` = allocator-aware release (`ldrd r0,r1,[p-8]`, call
  `(*(*r0))[1](r0,r1)`).

Per-class instantiations: 1 to 27 states per sequence (the common sizes are 2, 4 and 19), record
sizes `0x18 / 0x20 / 0x30 / 0x40` (`0x18` = three pointer-to-member-functions only; the larger records
carry per-state data in front of them). The count and record size of every entry is stated in its own
summary, so nothing relies on this list.

### Colour tables (`0x006B5BF0` family)

The 0x30-byte block is a **12 × 4-byte RGBA template** (`000000FF A0A0A0FF FF3A60FF FFE735FF
5FFF3AFF 50D2DCFF B2F7FFFF FF7D1EFF 181818FF 1800FFFF 910B10FF 00F62DFF`). I verified the actual
rule: the function writes every template byte **except** the ones that are `0xFF`, which receive the
argument instead (so an alpha of `0xFF` reproduces the opaque table N_119/N_120/N_121 also found).
The same bytes appear in the field-actor class registrations, so this is the library's per-class
colour set; no reader of any table exists in the image (N_120/N_121 report the same), which is why
these stay `maybe_` at 0.4.

### Reachability

None of the 34 addresses below the state-sequence block has a caller, a branch from outside the band
or a 32-bit pointer anywhere in the image — matching N_121's finding that the retail `.init_array` is
empty (`__init_array_start == __init_array_end == 0x0079AA18`). Exception: the movie-codec entries
*are* live — their free functions are called by the `Gfx_MovieStream_DtorDelete*` destructors at
`0x005014B8`, `0x005014DC`, `0x00501508`, `0x0050152C`.

## Naming scheme (important for M1)

`std_StateSequence<NN>_<ChangeState|Tick|SetState|Delete|QueueState>` — deliberately the same
vocabulary as N_123 so the merge step sees one scheme.

* N_123 numbered their tables `01–38` for vtables `0x0075AC30 … 0x0075B164`.
* The 32 tables `0x0075A7B0 … 0x0075AC0C` are numbered **39–70** (39 = `0x0075A7B0`, ascending) so
  nothing collides with N_123; the three further sequences that appear here only as a
  `SetState`/`Delete` pair are numbered by the same rule (49, 55, 60).
* The one object shared with N_123 (`vtable 0x0075AC30`) keeps **N_123's number 01** so that its
  four methods read as one object across the two batches.
* M1 can renumber the whole block `01–70` in address order at merge time; the mapping is
  `NN = 39 + (vtable - 0x0075A7B0)/0x24` for this batch (except `0x0075AC30`).

Everything below `0x006C0000` uses subsystem prefixes (`Gfx_`, `Svc_`, `Container_`, `Script_`) with
`maybe_` where confidence < 0.5 (24 entries).

## Honest gaps / not verified

* Everything here is **static**. No emulator run, no playtest: no state transition, no palette and no
  movie-frame conversion was observed happening.
* **What each state means is unknown** — I deliberately did not invent per-state names. The state
  records are plain `{exit, event, enter}` pointer-to-member-function triples in `.data`, and the
  handlers live outside this batch (`0x0019xxxx`, `0x0026xxxx`, `0x002Cxxxx`, …); naming states is a
  separate job.
* Owner attributions come from the literal vtable store, which is solid evidence for *which*
  constructor builds the object, but 14 of the 33 owner names are themselves `maybe_` in the sibling
  batches, so the domain label inherits that uncertainty.
* 34 entries (`0x006B5xxx`) are `maybe_`: the colour-table *bytes* are certain, their **meaning**
  (which UI/actor colours they are) is not, and the whole 0x006B6xxx–0x006B7D44 static-init run is
  unreachable in the retail image, so its purpose may be dead code.
* `maybe_Gfx_State_ApplyChangeFlags` (0x006BA360) and `maybe_Gfx_Codec_GetStreamInfo` (0x006B9A98)
  are the weakest names: mechanics read correctly, subsystem is a guess (0.30/0.35).
* The 6 dropped neighbours reported by the generator (`0x006C410C`, `0x006C4864`, `0x006C60F8`,
  `0x006C683C`, `0x006C6B68`, `0x006C7B4C`) are `Tick`/`Delete` slots of these same sequences that
  belong to other batches; I did not name them.
