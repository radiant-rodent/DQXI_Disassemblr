# N_123 — name & document 150 native functions (`0x006C97C4`–`0x006D0E90`)

Status: **done**, `orchestration/naming/out/N_123.json` has all 150 addresses (0 missing, 0 extra,
150 unique names).

## What the band actually is

The batch header says `General_Procedures`, which is a generator artefact (that label just means
"no keyword matched the name"). The band is **one contiguous slab of a C++ framework library**:
38 **"state sequence" classes** laid out back to back, each contributing a dispatch table of
exactly 0x24 bytes in `.data` at `0x0075AC30 … 0x0075B188`, and four functions in `.text`:

| dispatch slot | function | size | role |
|---|---|---|---|
| base+0x00 | – | – | 0 (offset-to-top-like hole) |
| base+0x04 | this batch (`0x10`) | 0x10 | `Delete` — tail-call to the shared deallocator `0x0010F6CC` |
| base+0x08 | this batch (`0xB8/0xBC`) | 0xB8/0xBC | `Tick(float dt)` — apply queued state change, else accumulate time |
| base+0x0C / +0x14 | in N_122's range (`0x006C9754` / `0x006C9654`) | 0x60 | invoke the current state handler / queue a state id |
| base+0x10 | this batch (`0x224`–`0x24C`) | 0x224–0x24C | `ChangeState()` — exit old state, enter new state |
| base+0x18 | this batch (`0x38`) | 0x38 | `DeleteIfDone` — virtual "finished?" test, then free |

37 of the 38 classes have all four of their slots inside this batch (class 01's `Tick` and
`ChangeState` sit just before the boundary at `0x006C97C4`), which is why the same four sizes repeat
over and over.

### The object model (recovered, not guessed)

```
+0x00  dispatch table pointer
+0x04  current state id
+0x08  float  elapsed time in the current state
+0x0C  u32    frames spent in the current state
+0x10  float  last dt handed to Tick
+0x14.. pending-state stack, 2 slots (deduplicated), count at +0x1C
+0x20  base added to a member-function pointer's this-adjustment (Itanium PMF {fn, adj},
       virtual PMFs encoded as vtable byte offset in bit 0)
+0x24.. array of state records, 0x18 or 0x40 bytes each
+0x??  the owner's transition callback (PMF pair right after the state array)
```

* state record (`0x18` variants): PMF exit, PMF enter, 2 words payload; only a **higher** id than
  the current one is accepted, i.e. a one-way step sequence.
* state record (`0x40` variants): bigger payload; the only transition applied here is **back to
  state 0**, i.e. "run this sub-action, then return to idle".
* `ChangeState` calls `exit(old)` (only when `old` is in range — in the 0x40 variants only state 0
  has an exit handler), `enter(new, old)`, then the owner callback `(old, new)`, resets
  `+0x08 = 0.0f` (every class has its own 0.0f literal in its pool — verified for all 37) and
  `+0x0C = 0`, and clears the pending stack.
* `Tick` first calls `ChangeState` (slot +0x10); if a transition was applied it does **not**
  advance the clock.

## Naming scheme

`std_StateSequence<NN>_<Role>` with `NN` = table order (`01`…`38`, `base 0x0075AC30 + 0x24*(NN-1)`),
`Role` ∈ `ChangeState`, `Tick`, `Delete`, `DeleteIfDone`. Unique, ordered, and every entry says in
plain words which object it belongs to, how many states it has and how big a state record is.
`DeleteIfDone` (confidence 0.45) carries the `maybe_` prefix; the other three are 0.62–0.72.

Confidence range 0.45–0.72 (mean ≈ 0.63). Structure (state array, exit/enter PMFs, pending stack,
timer, deallocator) is **certain**; what each *state* means (open/idle/close of a window, step of a
monster action, …) is not recovered, so no state-specific names were invented.

## Evidence chain (how the above was proven)

1. `vtable_of()` — scanned `original/exefs/code.decompressed.bin` (VA = file offset + 0x00100000)
   for each batch address: every one of the 150 appears **exactly once** in `.data`, at a regular
   0x24 stride, which produced the class grouping, the slot roles and the owner constructor.
2. Readable C for all 150 + Capstone ARM disassembly for the cases Ghidra mangled
   (`ChangeState` is mis-decompiled as returning `u32` and the `0x40` variants only partially).
3. `0x0010F6CC` (the `Delete` target) disassembled: `if (!p) return; ldrd r0,r1,[p-8]; ldr r2,[r0];
   ldr r2,[r2,#4]; bx r2` → hands the block back to the allocator recorded 8 bytes in front of the
   object. Its **117 direct callers are all teardown paths** (`Fs_CacheSet_Shutdown`,
   `Field_DestroyScene`, `Camera_Reset`, `Ui_TitleScreen_Dtor`, `Ui_Overlay_Shutdown`,
   `Menu_TalkParty_ReleaseAll`, …), which is what fixes the slot as *delete* rather than anything
   else. (N_117 independently called the same helper "instance release".)
4. `Tick`'s guarded virtual call was resolved to slot +0x10, i.e. each class's own `ChangeState` —
   that is why the tick skips the clock on the frame a transition happens.
5. `0x00100050` (Thumb, at the top of the image) is the out-of-line **array constructor**
   (`for i<n: ctor(p); p += stride`), which explained the `func_00100050(obj, ctor, 0x18, 8)` tails
   of the owner constructors: it builds the state array with the class's own state-record ctor.

## Open problems / honest gaps

* **What the states mean is unknown.** I recovered the machine, not the vocabulary. Any name like
  `Battle_Dulneigh_Open` would have been invention, so the roles are described structurally.
* `DeleteIfDone` (0x38, 38 entries, 0.45): the *shape* is certain (`if (vcall[+0x14](this, arg))
  vcall[+0x04](this)`), the intent is inferred. Slot +0x14 for the base class is the
  "queue next state" routine, which reads oddly for a "finished?" test; the most likely reading is
  that derived owners override that slot with their own done-test. Worth one more look in M1.
* The `0x40`-record variants only transition back to state 0; I documented that but did not find
  which code drives them into the non-zero states (probably the `+0x14` "queue" slot with a
  different override).
* Sixteen of the 38 owner constructor names are themselves `maybe_` in the sibling batches, so the
  owner attribution in those summaries inherits their uncertainty (the table address and slot are
  facts either way).
* `N_011` named a similar 4-function cluster at `0x001F2004/0C/1C` `maybe_Ui_Sequence_*`. That is
  the same framework seen from another angle (or a sibling family); M1 should decide one vocabulary
  (`std_StateSequence` here) rather than leave two.
* Ghidra merged several extra entry points into the neighbouring `ChangeState` bodies (e.g. the
  state-record constructor at `0x006C9628` sits inside `0x006C94E4`), so the function index counts
  slightly fewer functions than really exist. Not fixed — not my file.
