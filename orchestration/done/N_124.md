# N_124 — name & document 150 native functions (`0x006D0EA0`–`0x0070B820`)

Status: **done**. `orchestration/naming/out/N_124.json` contains all 150 batch addresses
(0 missing, 0 extra, 0 duplicates, 150 unique names).

## What the band actually is

The batch header says `General_Procedures`, which is a generator artefact. The band is seven
unrelated things glued together by address order:

| range | what it is | entries |
|---|---|---:|
| `0x006D0EA0`–`0x006D3E90` | **15 more "state sequence" classes** — the direct continuation of N_122/N_123. Tables 71–85 of the framework whose table block runs `0x0075AC30`–`0x0075B3A4` | 58 |
| `0x006D3F90`–`0x006D6060` | six byte-identical **UI child-widget-stack invokers** (one per UI class vtable) + a **numbered pack-name enumerator** | 7 |
| `0x006E2014` | a 4-byte **alignment filler** that the seed scan mistook for a Thumb function | 1 |
| `0x006E6854`–`0x006EF7D8` | the **animation keyframe-curve library**: damped-follow update, 20 verified cells of a 4×8 curve-evaluator table, 4 container/broadcast helpers, 16 bogus seeds | 42 |
| `0x006F465C`–`0x006F53E4` | the **easing kernels** used by the damped-follow update + one sample-buffer builder | 6 |
| `0x00707CD0` | UTF-16 **`WString::insert`** | 1 |
| `0x0070AFA0`–`0x0070B820` | **35 observer-notification handlers** registered in the 0x14-stride array at `0x007830F8` | 35 |

literal (verified: `0x00000000` in every pool) to `+0x08` and zeroes `+0x0C`.

### 2. `SetState`, not `DeleteIfDone`

The 0x38-byte dispatch slot (`vtable+0x18`) is:

```
if (vtable[+0x14](self, stateId)) vtable[+0x10](self);   // queue, then apply
```

`vtable+0x14` is the de-duplicating push into the pending stack (range check `id < N`, depth
check, duplicate scan, append). I reached this from the disassembly of S39's queue helper
(`0x006D1038`), then confirmed it on S37's (`0x006D099C`), and N_122 independently recorded the
same correction. **N_123's 38 entries still name this slot `maybe_std_StateSequenceNN_DeleteIfDone`**
— M1 should fix them.

### 3. The 16 "thumb" seeds in `0x006E972E`–`0x006EA68A` are not functions

All 16 addresses are `2 mod 4`. Each one is the second and third byte of an ARM instruction
(`0x6E972C: ldrblt r2,[r0,#8]` spans `0x6E972C..0x6E972F`). They are **switch-case labels** inside
eight real ARM evaluators found by sweeping for `push` prologues:

`0x006E96E4, 0x006E98F8, 0x006E9AD4, 0x006E9CF4, 0x006E9F18, 0x006EA104, 0x006EA324, 0x006EA538`

Starting the ARM decoder at `addr+2` yields coherent code (`beq / cmp / beq / cmp / beq / b` — the
mode switch that follows `ldrbgt r2,[r0,#9] / ldrblt r2,[r0,#8]`, the forward/reverse interpolation
mode bytes), which proves the 2-byte offset bug. Ghidra's readable C for these addresses
(`coprocessor_load`, `halt_baddata`) is an artefact of that misalignment. They are named
`maybe_Anim_CurveEvalCase_<addr>` and their summaries say "not a function entry", so M1 can drop
them from the progress count.

### 4. The animation curve library (20 verified cells + 12 interior siblings)

The dispatcher `0x0065B890` does

```
fn = ((void**)0x007AE7C8)[typeByte(self+0x0C) * 8 + modeByte(self+0x0D)];
```

i.e. a 4-format × 8-mode function table. I resolved all 32 cells; 20 are in this batch and named
`Anim_CurveEval_F<row>M<col>` (rows 0–1 return a float in `s0`) and
`Anim_CurveSample_F<row>M<col>` (rows 2–3 fill a caller output struct). Key strides (0x08 / 0x0C /
0x10) and 12-bit packed values were read from each body, which is why the rows are real formats
rather than a guess. The other 12 cells are interior entry points of the same functions.

The curve object carries the key count (u16 `+0x0E`), key pointer (`+0x20`), duration (`+0x18`),
scale/bias (`+0x10`/`+0x14`) and the two direction-mode bytes (`+0x08`/`+0x09`).

### 5. Damped follow + easing kernels

`0x006E7090` keeps `{value+0, prevTarget+4, holdTime+8, lastDt+0xC, kernel+0x10}`, snaps on
`dt <= 0`, otherwise advances the value with the previously selected kernel, records the new
target/dt and selects a new kernel from the 16-entry jump table at `0x006E7114`
(`ldrlo pc,[pc,r6,lsl#2]`). Three of the kernels are in this batch (`0x6F465C` mode 0,
`0x6F4898` mode 1, `0x6F4C60` mode 2); `0x6F4858`, `0x6F4BEC` are vector variants that are *not*
in that table, and `0x6F53E4` is a different, larger buffer builder.

### 6. `0x00707CD0` = `WString::insert`

UTF-16 string object: `+0x00` length, `+0x04` inline buffer with 0x3F-character capacity. The
function saves the tail after `pos` on a 0x9C-byte stack scratch (via `0x00100A74`), truncates,
appends `sub` (`0x00100A90`), re-appends the tail, and grows through the heap when the inline
buffer no longer fits. `0x00100B74` is the UTF-16 strlen. Highest-confidence name here (0.70).

### 7. The 35 observer handlers

Each one walks one intrusive doubly-linked listener list of its object (sentinel offsets 0x14,
0x18, 0x1C, 0x20, 0x24, 0x28, 0x2C, 0x30, 0x3C, 0x40, 0x54, 0x488, 0x6C, 0xA4, 0xE0) and calls
`listener->vtable[1](adjustedListener, self+0x14)` — i.e. "notify everybody interested in this
event". They are registered in the 0x14-byte records at `0x007830F8 + 0x14*i` (i = 0..34), so I
named them `maybe_Event_NotifyHandlers_00..34` and recorded the list offset in each summary rather
than inventing 35 class names (12 of them share the same offset, so the offset cannot identify the
class). `0x70B01C` additionally contains that class's constructor at `+0x3C` and destructor at
`+0x84`.

### 8. Six byte-identical UI functions

`0x6D3F90, 0x6D4008, 0x6D4080, 0x6D42C8, 0x6D4340, 0x6D4510` are the same 120-byte body (only
branch targets differ) in six different UI class vtables. They call the callback of the current
child-widget stack level and, when the stack unwinds to the base level, finish by calling their own
vtable slot `+0x14`. Same object offsets as N_021's `Ui_WidgetStack_Push*`
(`self+0x08` → manager, depth `manager+0x3C`, entry at `self + depth*8`, args at `+0x10/+0x14`).
They are disambiguated by their vtable slot address.

## Open problems / what is NOT verified

* Everything is **static**. No emulator, no playtest: no transition, easing curve, curve sample
  or listener notification was ever observed running.
* **What each of the 15 sequences actually does is unknown.** The owner constructors are only
  `maybe_` names in sibling batches (`maybe_Gfx_EffectNodeCreateChild_*`,
  `maybe_Gfx_SharedRenderState_Apply`, `maybe_Ui_Widget_Ctor_vt7781EC`,
  `maybe_Ui_UmaWindow_CtorSub11`, `Field_Gimmick_InitHandlerList3/4/3B/5/5B/9/7`,
  `Field_Gimmick_InitActorSlot`), and the state handlers live outside this band, so I recorded the
  owner in each summary but deliberately did not invent UI/field state names.
  `std_StateSequence71..85` is the honest level of knowledge.
* The curve-library cell names encode the **verified table coordinates**; what the 4 formats and
  8 modes mean semantically is inferred from key layout only (confidence 0.50).
* `maybe_Ui_WidgetStack_InvokeTop_*` describes the mechanics exactly, but the interpretation
  "close the group when the last child finishes" is a hypothesis (0.42).
* `maybe_Anim_BuildSampleBuffer` (`0x6F53E4`) and `maybe_Container_UnlinkNodeSubtree`
  (`0x6EF5AC`) are the weakest entries (0.35).
* `0x006E2014` and the 16 `0x6E9xxx` addresses are **not functions**; I kept them in the JSON
  (the batch requires every address) with summaries that say so, so the merge pass can drop them.
* The 35 observer handlers are named by table index, not by class — twelve share the same list
  offset, and I did not find the reader of the `0x007830F8` array that would identify the classes.
* `native_names.json` still contains the bogus `L3m`/`L4m` at `0x6D31DC`/`0x6D3400` (outside this
  batch); another lane should overwrite them.
