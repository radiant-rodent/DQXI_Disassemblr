# N_125 — name & document 36 native functions (`0x0070B85C`–`0x007115E8`)

Status: **done**. `orchestration/naming/out/N_125.json` contains all 36 batch addresses
(0 missing, 0 extra, 0 duplicates, 36 unique names, 0 collisions against `symbols.json`,
`symbols_recovered.json`, `decomp/native_names.json` and the 120 sibling `out/N_*.json`).

## What the band actually is

The header says `General_Procedures`, which is a generator artefact. The 36 addresses are five
unrelated things that happen to sit next to each other in the `0x0070B000`–`0x00712000` utility
band (the C++ support layer that the Field2D / UI / Squirrel code links against):

| range | what it is | entries |
|---|---|---:|
| `0x0070B85C`–`0x0070BA3C` | 9 **observer-notification handlers**, one per class, registered at record indices 35–43 of the 0x14-byte handler table at `0x007830F8` that N_124 named `maybe_Event_NotifyHandlers_00..34` | 9 |
| `0x0070BD14`–`0x0070BDD4` | 5 identical **float-pair → u16 getters** with a fixed table index 0–4 (real entry points are 4 bytes earlier) | 5 |
| `0x0070CD3C` | **node-chain release** helper of the container library (companion of the erase-range routine `0x0070CB90`) | 1 |
| `0x0070D344`–`0x0070D79C` | 8 **arity adaptors** of the closure/delegate library (5- and 6-argument invoke stubs) | 8 |
| `0x0070D8D4`–`0x0070DB7C` | 5 sprite/scene **element destructors** + 2 **element constructors** + 1 **buffer release**, i.e. the ctor/dtor/member-destroy set used by the Field2D scene builder and sprite release path | 8 |
| `0x0070E0B8`–`0x007115E8` | **node-pool recycle**, **single-node release**, **intrusive-list range copy**, **Squirrel value-stack destroy**, **2D tween evaluator** | 5 |

## Recovered mechanics (evidence, not guesses)

### 1. The nine notification handlers (`0x0070B85C`–`0x0070BA3C`)

All nine have the same body shape, differing only in *which* listener list of the host object they
walk and which context word they hand to each listener:

```
r4 = *(self + first)                 ; first node
while (*r4 != *(self + sentinel)) {  ; sentinel = end marker stored at the list anchor
    element = *r4; r4 = *(r4 + 4)    ; nodes are 8-byte {object, next}
    (*(*element + 8))(element, &self->field)   ; virtual slot at vtable+8
}
```

* `0x70B85C`, `0x70B898`, `0x70B988` → list at `self+0x20`/`0x24`, context `&self->f_14`
* `0x70B8D4` → list at `self+0x44`/`0x48`, context `&self->f_14` (the only 0x44 anchor in the family)
* `0x70B910`, `0x70BA00` → list at `self+0x14`/`0x18`, context `&self->f_11` (a flag **byte**, not a struct)
* `0x70B94C`, `0x70BA3C` → list at `self+0x18`/`0x1C`, context `&self->f_14`
* `0x70B9C4` → list at `self+0x24`/`0x28`, context `&self->f_14`

Each address is the first word of a 0x14-byte record in `rodata` (`0x007833B4 + 0x14*(i-35)`,
i = 35…42) and `0x70BA3C` sits at `0x00783454` (index 43). I first read these records as vtables
(`{slot0, 0, 0, 0, 0}`); the decisive counter-evidence is that none of the bodies sets a vptr, so
they cannot be destructors, and `0x70BA3C` is demonstrably the *user virtual* (+8) of the class
whose constructor is `0x0070BA78` (vptr `0x0078344C`, destructor `0x0070BAB4`). I therefore kept
N_124's "handler table" reading and continued its numbering instead of inventing a new scheme —
that way the merge task can see one table.

### 2. The five float-pair getters (`0x0070BD10`/`BD14` … `0x0070BDD0`/`BDD4`)

`asm 0x70BD14`: `bl 0x0066BA08` → `vcmpe.f32` against `0.0f` (literal pool at `0x0070BD3C`) →
`vcvths.u32.f32` → `uxth`, else `mvnlo r0,#0` (−1). `0x0066BA08` is
`base + index*16 + 0x57C8`, loads the two floats at `entry+4`/`entry+8` and returns the larger
positive one (0.0 if neither). The index is baked in by a 4-byte `mov r1,#N` that the seed scan
assigned to the *previous* function, so Ghidra's entry point is 4 bytes late (the real ones are
`0x70BD10 / 0x70BD40 / 0x70BD70 / 0x70BDA0 / 0x70BDD0`). No `bl` and no literal-pool word anywhere
in the image points at these five, so they are reached only through a table built at run time —
recorded honestly as `maybe_`.

### 3. Delegate / closure arity adaptors (`0x0070D344`–`0x0070D79C`)

Bodies are pure forwarders, e.g. `0x0070D344`: `ip=r0; r4=r3; r0=[sp,#0x1C]; [sp]=r0;
r3=[sp,#0x18]; blx ip` → calls `fn(a0,a1,a2,a3,a4)` (5 arguments, one taken from the caller's
stack); `0x0070D3F4`/`0x0070D59C` move **two** stack words (`ldrd`) → 6 arguments. Proof of use:
the Field2D 2D-scene task starters build 3-word records `{invoke stub, callee, context}` on the
stack and pass them on —

* `0x005C5A54` (`maybe_Field2D_Scene_StartObjectTask`): `{0x0070D344, 0x00670DF0, self}` → `func_005BD550`
* `0x005C5B08`: `{0x0070D378, handler, self}` → `func_005BD6C8`
* `0x005C72CC`: `{0x0070D518, handler, self}` → `func_005C0040`
* `0x005C3430` (`Field2D_Scene_AttachLayerObjects`): `{0x0070D5FC, handler, scene}` → `func_005C6F08`
* `0x005C7CFE`: `0x0070D3F4`

Three of the eight (the 5-arg `…D4C0`, the 6-arg `…D59C`, the 5-arg `…D79C`) have no observed
reference site, so they carry `maybe_` even though the forwarding behaviour itself is certain.

### 4. The scene-element ctor/dtor set (`0x0070D8D4`–`0x0070DB7C`)

The decisive find is `func_00100BCC(ptr, elementDtor)`: Thumb `push {r4,lr}; bl 0x00101A80;
blx 0x0010F69C`, where

* `0x00101A80` reads `{count, size}` from the block header at `ptr-8` and calls the Thumb loop
  `0x00100BE0` with the destructor → `for (i = count-1; i >= 0; --i) dtor(ptr + i*size)`
* `0x0010F69C` is the allocator-aware `Mem_Free` (`ldrd r0,r1,[p-8]; (*(*r0))[1](r0,r1)`)

so `0x00100BCC` is `Mem_DeleteArray(array, elementDtor)`, and the five functions passed to it from
`FUN_005C3FE4` (`maybe_Field2D_Sprite_ReleaseResources`) are **element destructors**:

| element dtor | destroys | array slot in the sprite |
|---|---|---|
| `0x0070D8D4` | owned object at `+0x30` | `+0x14a*4` |
| `0x0070DB7C` | owned object at `+0x30` (identical body) | `+0x146*4` |
| `0x0070D9AC` | owned object at `+0xE0` | `+0x143*4` |
| `0x0070D964` | owned object at `+0x30` (identical body) | `+0x140*4` |
| `0x0070DB14` | owned object at `+0x38` | `+0x13d*4` |

The constructors are anchored exactly: `0x00116AE0` is verified `memset(ptr, 0, size)`
(`mov r2,#0; subs r1,#0x20; stmhs r0!,{r2,r3,ip,lr}` twice per iteration), so

* `0x0070D98C` = `memset(this,0,0xE0); this->f_E0 = 0` → default ctor of the 0xE8-byte scene element,
  and it is passed as the constructor to `std_ConstructArray` (`0x00100050`) with element size `0xE8`
  at `0x005C2404` inside `Field2D_Scene_BuildFromMapData` (`0x005C1D64`). Its matching destroyer is
  `0x0070D9AC` (+0xE0). **This is the strongest pairing in the batch** (0.55).
* `0x0070DA50` = `memset(this,0,0xD8); this->f_D8 = 0` → ctor of the 0xDC-byte element, built at
  `0x005C2184` in the same function; its destructor `0x0070DA70` (outside this batch) unlinks an
  inline list at `+0xC4` and destroys a 9-entry array of 0x14-byte records at `obj+0x10`.
* `0x0070DA08` releases the three heap buffers (+0x04, +0x10, +0x1C) of the sub-object at `+0x28`.

### 5. Container helpers

* `0x0070CD3C` — `Container_Node_ReleaseChain`: recursively releases a node chain
  (`bl 0x0070CD34` on `node+0xC`), detaches or destroys the refcounted object the node owns
  (`node+0x18` via `(*(*node+0x14+4))(...)` and `(**(node+0x18))()`), then pushes the recycled node
  onto the pool free list at `pool+8`. The same instruction sequence appears inlined in
  `FUN_0070CB90` (tree erase-range), which is the only caller — so the "std container" reading is
  structural, not guesswork.
* `0x0070FB84` — `Container_Node_DestroyAndReturn`: same release sequence for one node, then a tail
  call through `owner->f_24`'s slot +4 to hand the node to its deleter.
* `0x007107FC` — `Container_List_AssignRangeNodes`: `count` × 0x10-byte nodes, forward when
  `dst <= src` and backward otherwise (memmove-style overlap handling); each destination node
  releases its previous object, copies the source node's object pointer and is spliced in right
  after its source node.
* `0x0070E0B8` — `Mem_NodePool_RecycleTree`: depth-first recycle of an 8-byte-node tree
  (`node+0` = child, `node+4` = sibling, `node+0xC` = free-list link at `pool+0x18`); called from
  `0x002FCDA8`, `0x002FE9E0`, `0x002FFA54`, `0x003065DC`.

### 6. `0x00710AA4` — `Sq_Stack_Destroy`

Destructor of the Squirrel value stack: for each 8-byte `SQObjectPtr` with the `0x08000000`
refcounted bit set it decrements `[object+4]` and calls `(*(*object+8))()` at zero, then frees the
buffer (`capacity << 3`). Callers `0x001BF704/10`, `0x002CC7A4`, `0x005FA088`,
`0x006231A8/B4` are Squirrel/VM teardown paths, and it is the exact companion of N_100's
`Sq_Stack_Resize` (`0x00710938`). **Highest confidence in the batch (0.80).**

### 7. `0x007115E8` — `Math_Lerp2D_Evaluate`

```
if (progress[0] >= progress[1])  out = {key[2], key[3]};      // finished -> end point
else if (key[6] == 0)            out = {key[0], key[1]};      // no easing -> start point
else  cb(&out, &start, &delta, key[4], key[5]);               // key[6] = easing callback
```
`delta = {key[2]-key[0], key[3]-key[1]}`; the two extra floats come from `key[4]`/`key[5]`.

## Honest gaps / what is NOT verified

* Everything is static analysis (readable C + `asm/text` + `asm/rodata`). No emulator run, no
  playtest, so no notification, tween or delegate invocation was ever observed at run time.
* The nine notification handlers: the *mechanism* is certain (list walk + virtual call + context),
  the *meaning* of each list and of the `+0x11`/`+0x12`/`+0x14` contexts is not. Names therefore
  continue N_124's positional `Event_NotifyHandlers_NN` scheme rather than inventing 9 class names.
* The five element destructors `0x70D8D4`/`0x70DB7C`/`0x70D964` are byte-identical (three distinct
  classes) — any name that claims to distinguish them semantically would be a lie; I only record the
  array slot each one is used for.
* The five `Math_GetPairMaxAsU16IndexN` getters are unreachable from any literal or branch in the
  image; their naming is descriptive of the code, not of a proven caller.
* `0x0070D344`…: three of the eight adaptors have no observed record site (marked `maybe_`), and the
  field order of the 3-word closure record (`{invoke, callee, context}` vs `{context, callee,
  handler}`) is inferred from one call site that mixes a code pointer with a data label.
* The 36 names are collision-checked but not yet merged into `symbols.json` — that is M1's job.
