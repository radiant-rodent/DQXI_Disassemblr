# N_126 — completed

**Task:** name and document the 150 native addresses in `orchestration/naming/batches/N_126.txt`.
**Owned output:** `orchestration/naming/out/N_126.json` (150 entries, 146,646 bytes).

## Headline: 75 of the 150 "functions" are not functions

The batch generator seeds entries from a prologue scan (`tools/decompile_native.py`):

* ARM: `(word & 0xFFFF4000) == 0xE92D4000` (`push {..., lr}`)
* Thumb: `(halfword & 0xFF00) == 0xB500` (`push {..., lr}`)

The Thumb rule is extremely noisy on 32-bit ARM data because many ordinary ARM
instructions contain a `0xB5xx` halfword:

* `bl <far>` → `0xEBxxxxxx`; when the encoded offset is around `0xB5xx` the low
  halfword is `0xB5xx` (e.g. `bl 0x29126C` from `0x263AE8` encodes `DF B5 00 EB`),
* `strh rX, [sp, #imm]` encodes as `E1CD B5xx`,
* `strb rX, [sp, #imm]` encodes as `E5CD 00xx`.

Ghidra then decompiles these interior addresses as **Thumb** and emits
`halt_baddata()` (or an endless coprocessor loop), which is why 70 of the 150
readable files are empty shells. Disassembling the same bytes as ARM from the
real container start gives perfectly coherent code, and every block sits at a
constant internal offset (see below), which proves the seeds are interior points.

I documented those addresses as interior labels/blocks instead of inventing
function names, and said so in every entry (`summary` starts with
"Interior block, not a function" / "Not a function"). 75 of the 150 names are of
that kind; they are all `maybe_` and confidence ≤ 0.5.

## What the batch actually contains

### A. `0x00123508 – 0x00126B0C` (21) — OS/IPC + CRT
* `0x123508`, `0x123C54`, `0x123D68` are hand-rolled IPC wrappers: they write a
  command header into the thread's IPC buffer at `TLS+0x80` and execute
  `svc #0x32` = **SendSyncRequest** (3dbrew SVC table). Headers are
  `0x00180000` (cmd 0x18, 8 response words, used by the date/time query
  `0x11F5C0`), `0x000E0042` and `0x000D0042` (2 normal + 1 translate buffer;
  `0x1228AC` chooses between the last two). Named by command id, not by service.
* `0x123664` is `std_Strncmp` (word loop + UQSUB8 NUL detection + bswap ordering).
* `0x125098` is the C++/EHABI **personality routine** whose `bl 0x1250BC` is
  followed by inline unwind bytecode (`0x806DB6DB`); `0x1250BC` is the opcode
  interpreter (`add pc,pc,ip,lsl #2`; `pop {r4,lr}; bx ip`).
* `0x125738 / 1257C4 / 125860 / 1258FC` are the four forward memcpy alignment
  variants (shift 0/8/16/24 bits); `0x125AD4 / 125B58 / 125BF4 / 125C90` are the
  four backward (overlap-safe) variants. All return `(src_end, dst_end)`.
* `0x126268` is the toolchain VFP `d8–d15` save/restore helper (not a real
  function: two entry labels merged by Ghidra), `0x1263E4` / `0x1268D4` are the
  soft-double divide/multiply cores, `0x126728` / `0x12677C` are `scalbn` plus
  its rounding tail.
* `0x126B0C` is the "planes identical" variant of the in-place 32-byte-block
  colour converter; dispatcher `0x12A84C` selects it over `0x129EF4`.

### B. `0x001F909C – 0x001FE184` (6) — UI screen base-class virtuals
The same six bodies appear in **93 vtables** in `.data` (`0x75B4xx – 0x75CExx`),
i.e. they are base methods inherited by every screen class (the vtable at
`0x75B460` is installed by `Ui_Screen_CtorBase` at `0x20002C`). They all go
through the pure-virtual row getter at `vtable+0x48` and touch row fields
`+0x10` (kind), `+0x108` (flag), `+0x110` (bound record/param id).

### C. `0x002500EC`, `0x0025063C` — Squirrel native-binding table slots
These are **not code at all**: they are two code-pointer fields of the
native-binding table that starts around `0x24FBE8`. The records are
`{name pointer, inline NUL-terminated name, code pointer}`, and the two slots
name the Squirrel natives **`GetPartyMemberMaxHP`** (→ `0x006FB5F0`) and
**`GetPlayableMemberNumber`** (→ `0x006FB540`). This table maps hundreds of
script names to their `0x006Fxxxx` stubs and is a cheap source of names for
other batches.

### D. `0x00256CC4 – 0x0025E7D4` (26) — load/save screen + window parts
Load-screen state machine at `self+0x918` (anim descriptor from `0x1F0BE4`, set
by `0x1DAB30`), input-mask gates (`0x142`/`4`/`1`/`8` bits), transition requests
through `self+0x11C`'s vtable (`+0x14` = request, `+0x10` = commit), plus two
deleting destructors and two text-setup helpers (`s_txt_title`, `st_txt_tr1/3/4`,
`s_txt_x`). Several handlers are byte-identical copies at different vtable slots
(0x25E694 / 0x25E7B0 / 0x25E7D4), so they got `…_B/_C` suffixes to keep names
unique.

### E. `0x002609CC – 0x002685E0` (14) — training window / recipe book
4 rows × 3 slots of stride `0x320` / `0x104` (training window), the
`0x263A70` close routine split by Ghidra into five fragments (`0x263AE8`,
`0x263AF4`, `0x263B24`, `0x263B34`, `0x263B6C`) that each stop one sub-state
machine (`0x29126C(part,0)`), the recipe-book input branch, an 8-byte alignment
gap (`0x264CD8`), a vtable block read by the part destructor (`0x264FC8`), and
`0x2685E0` = another `Container_FindObjectByTypeId` clone (same shape as the
already-named `…I`/`…J` at `0x630C54`/`0x630CDC`).

### F. `0x00336190 – 0x0033ED60` (4) — field/actor fragments
Interior tails of `Gfx_SpriteActor_AddChildC` (`0x336054`), the scene-object
deleting destructor (`0x336AB8`), `Field_SceneObject_ApplyRecordModel`
(`0x33DEC4`) and `Field_SceneObject_InitFromRecord` (`0x33EB5C`).

### G. `0x00341394 – 0x0035C758` (75) — the three field scene-object spawners
This is the big one. The addresses are interior points of three huge ARM
functions:

| container | range | what it is |
|---|---|---|
| `0x0034354C` | `0x0034354C – 0x0034A03C` (27 KB) | first field scene-object spawner |
| `0x0034A03C` | `0x0034A03C – 0x00353074` (37 KB) | second spawner |
| `0x0035A1D0` | `0x0035A1D0 – 0x0035E478` (17 KB) | third spawner (`maybe_Field_SceneObject_SpawnByTypeC`) |
| `0x003400B4` | `… – 0x003418CC` | `maybe_Field_SceneObject_InitFromRecordB` (one NPC-balloon block) |

Each address is the same internal point of one **per-category pass**: the pass
starts a loop over a list at `r1 + <offset>` (`0x4CB8`, `0x3EFC`, `0x2EF8`, …),
fills a stack record, calls `Mem_AllocAligned`, then a distinct factory
(`Field_SceneObject_InitModelFromLayout`, `Gfx_SpriteActor_InitFromRecord`,
`maybe_Effect_MeshEmitter_Setup`, `Actor2D_CreateFromParamA…D`,
`Ui_Message_ApplyRecord`, `Ui3D_InitElementFromDef`, …) and finally the list
insert `0x1235A4`. The factory call sits at a constant `+0x11C..0x120` from the
seed address in 60+ of the 66 spawner addresses — a very strong signature that
the seed addresses are the same point in every pass, not random interior words.

I therefore named each one `maybe_Field_SceneSpawnBlock_<Type>` where `<Type>` is
the object the pass builds, and put the factory address and container in the
evidence. That is the most useful honest name available without splitting the
containers (which a type/structure pass should do).

## Method
1. Read `README.md`, `orchestration/PLAN.md`, `orchestration/naming/TEMPLATE.md`,
   the sibling outputs and `docs/` where relevant.
2. Built a name map from `symbols.json`, `symbols_recovered.json`,
   `decomp/native_names.json` and all 125+ `orchestration/naming/out/N_*.json`
   (~18.1 k names) and used it for every callee resolution.
3. For every address: readable C, then Capstone 5.0.7 disassembly of
   `original/exefs/code.decompressed.bin` (VA = file offset + `0x00100000`) in
   both ARM and Thumb modes; chose the mode that decoded coherently. For the
   interior seeds this meant disassembling from the real prologue and finding
   the exact block/factory call.
4. Branch-target scan of all of `.text` (ARM `b/bl/blx`, Thumb `b/bcc/bl`) and a
   32-bit word scan of `.rodata`/`.data` for pointers into the batch, to
   separate real entries from interior seeds.
5. Prologue scan + per-address container mapping; verified factory-call offsets
   inside each container.
6. Literal decoding for command headers, vtable slots, string pointers and
   `.data` globals (e.g. `g_002001EC = 0x75B460` vtable, `s_txt_title`).

## Open problems / NOT verified
* Everything is static. No emulator run, no playtest: no IPC command, screen
  state or spawn path was observed at runtime.
* The three spawner containers are **not** fully understood: I know they iterate
  object lists and build one object category per pass, but the list offsets
  (`r1+0x3EFC` etc.) and the object type ids are not tied to real game type
  names. The `SceneSpawnBlock_*` names describe the factory each pass uses, not
  the object type id.
* `0x123508` / `0x123C54` / `0x123D68` are named by IPC command id because the
  owning service could not be proven. The shared handle at `0x007B2D2C` is used
  by several command families, so “which service” is deliberately left open.
* `0x1F909C..0x1FE184` are UI screen base methods; the meaning of row field
  `+0x110` (id? record handle?) is inferred, not proven.
* `0x256CC4`/`0x259918`/`0x2609CC`/`0x264CE0` are deleting destructors; the
  owning classes are positional (`Ui_Window`, `Ui_TrainingWindow`, …) based on
  neighbouring named functions.
* `0x00264FC8` is called a vtable block because `0x264CF4` loads pointer-sized
  values from `+0x168..+0x184`; the exact object layout is unverified.
* `0x0035EBB8` (`Item_AddToStorage`) is the strongest non-CRT guess (0.55); the
  0x61xxxx callees are not yet named, so “storage bucket” is inferred from the
  24-slot u16 array and the category switch.
