## What the batch actually is

The header label `Unknown` is a generator artefact. The batch is two unrelated bodies of code:

| range | what it is | entries |
|---|---|---:|
| `0x00361528`-`0x00372AF0` | **field-actor / actor-action / UI class methods**: 17 destructors (16 deleting + 1 destructor body), 3 constructors, 2 attachment virtuals of the player actor, 1 queue pop, 1 intrusive-list insert, 1 child-transform broadcast, and 10 Ghidra split artefacts (below) | 49 |
| `0x00689348`-`0x00694168` | one contiguous **C++ static-init / actor-class registration block** of the field subsystem: 51 RGBA colour-palette initialisers, 31 outlined guard stubs, 16 actor-class registration functions, 2 lazy singleton getters, 1 clip/param init | 101 |

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `naming/TEMPLATE.md` and the sibling batches (especially
   N_015, N_026, N_053, N_088, N_119-N_124, N_128) for vocabulary and known helper identities.
2. Built an 17.5k-name map from `symbols.json` + `symbols_recovered.json` + `decomp/native_names.json`
   + every sibling `out/N_*.json`, and resolved every callee/literal against it.
3. Read the readable C for every address, then **fell back to Capstone 5.0.7 disassembly** of
   `original/exefs/code.decompressed.bin` (VA = file offset + `0x00100000`) in both ARM and Thumb,
   resolving `ldr rX,[pc,#imm]` literals to strings/addresses and printing every `bl` target with its
   known name. This was required: 12 of the readable files are `halt_baddata()` and most of the 0x68
   band decompiles to `func_0010009C(g_007BE2D0)` only.
4. **Vtable reconstruction.** For every batch address I scanned the image for 32-bit words equal to
   it, delimited the table it sits in, and dumped every slot with the sibling names already attached.
   That gave a class and a slot role for 22 entries (e.g. `0x371D8C` = slot 12 of the table at
   `0x00765964` next to `Field_Actor_ResetStep`/`UpdateInputDirection`; `0x370384` = slot 5 of the
   `Ui_PastPlaceWindow` table between `InitPanes` and `LayoutRows`).
5. For the 0x68 band I decoded each function with its **first literal pointer in instruction order**,
   which identifies the `.data` table it fills, and extracted the **inline class-name strings** that
   sit inside the declared function body (a reliable signal: `GmSkyBase2D`, `PlayerActor2D/3D`, the
   20 2D gimmicks, the 33 3D gimmicks, `Barrier`, `EnemyMenuActor`, `Plain`).
6. Verified the RGBA template substitution byte by byte against the writers, and tested whether the
   palette bases are ever read (32-bit whole-image word scan).

## Key findings

1. **Deleting destructor idiom.** Slot 0 of the big class tables is a deleting destructor and has the
   uniform body `<dtor body>(); b 0x0010F6CC`. `0x0010F6CC` is the allocator-aware release
   (`p -= 8; ldrd r0,r1,[p]; (*(*r0+4))(r0,r1)`), not `free`. Shared dtor bodies used by this batch:
   `0x193E44` (actor/action/part family), `0x1E1B88` (field actor / component), `0x28E6C4`
   (sprite scene-node), `0x28EFB4` (2D node), `0x36FB10`/`0x366294` (UI panels), plus the two
   allocators `0x11CFAC` (libgcc round-up divide) and `0x11FE8C` (0x10-byte bucket round-up).
2. **Seed defects in the 0x36 band - 10 of 49 addresses are not function entries.**
   * Interior blocks of a larger function (real body starts earlier, they are cleanup loops / landing
     pads): `0x361528`, `0x361640`, `0x361724` (std::map teardown tails: `0x10EC14` =
     `std_RbTree_EraseNode`, `0x115358`/`0x115390` = rb-tree increment/decrement), `0x363E3C`,
     `0x363E68` (model/anim setup tails), `0x369300` (anim+SE loop tail).
   * Decoded **2 bytes late**: `0x36AD6E` (real entry `0x36AD70`), `0x36DCF6` (real body
     `0x36DCF4`), `0x36E566` (real body `0x36E568`). Each address is `mod 4 == 2`, so it cannot be an
     ARM entry, and starting 2 bytes later gives coherent code.
   * One 4-byte ARM->ARM veneer: `0x3620B4` = `b 0x0010F6CC`.
   * Three entries are declared **Thumb by Ghidra but are ARM**: `0x361528`, `0x361640`, `0x361724`
     (Thumb decodes 10-56 bad instructions, ARM 0-1). This is the same seed/mode bug N_126 and N_124
     reported for other bands.
   * `0x0036B238` is covered by `functions_index.json` but is a real 16-byte deleting-destructor
     wrapper calling `0x0036B248`.
3. **The 0x68 band registers named field-actor classes.** Inline names found inside declared bodies:
   `GmSkyBase2D`/`Body` (`0x689348`), `GmMiniGameBoot3DActor`+`GmBlacksmithStand3DActor`
   (`0x689544`), `CutSceneActor`/`CutScenePlayerActor`/`ScriptGadgetActor` (`0x68C2BC`),
   `PlayerActor2D` (`0x68C3BC`), `PlayerActor3D` (`0x68C520`), `GmDiveMonster2D` (`0x68DF10`),
   `GmBeeRider2D` (`0x68EA7C`), `GmHellkacha2D` (`0x68ECB4`), `GmWaterfall2D` (`0x68EEEC`), the seven
   `GmRace*3DActor` (`0x68F128`), `EnemyMenuActor` (`0x6926E4`), the twenty `*2DActor` gimmicks
   (`0x6928D0`), the thirty-three `*3DActor` gimmicks (`0x692E88`), `Barrier` (`0x693700`),
   `Plain` (`0x68A564`). Registration = `0x002A55EC(self, list, name)` (the named-record ctor that
   also appears as `maybe_Ui_TextWidget_Ctor` in a sibling batch) plus the intrusive-list splice
   `0x001235A4`.
4. **Palette writers use the template N_119-N_121/N_128 already found.** I verified the substitution
   rule on my writers: the template is
   `000000FF A0A0A0FF FF3A60FF FFE735FF 5FFF3AFF 50D2DCFF B2F7FFFF FF7D1EFF 181818FF 1800FFFF 910B10FF 00F62DFF`,
   and **every template byte equal to `0xFF` is replaced by the argument** (so `0xFF` reproduces the
   shipped table) while the other channels are literal. Two argument shapes exist here:
   `(tint, u8* dst)` (`strb r0,[r1]` x4) and `(unused, u32* dst, u32 color)` (`str r2,[r1]` x2 +
   `str 0xFF,[r1,#8]`).
5. **The palette bases are write-only.** Each palette base (e.g. `0x007A9590`, `0x007A3D74`,
    `0x007A8040`) has exactly **one** literal reference in the whole image - its own writer. The
    four-byte words *next to* the palettes are read (e.g. `0x007A9588` from four code sites), so the
    live data are the neighbouring parameter words, not the RGBA bytes. This block is therefore
    plausibly dead in the retail build (the same "no reader" result N_128 got for the UI palettes).
6. **The shared guard `0x7BE2D0`/`0x7BE2D4`.** 676 literal-pool slots in the image point at
    `0x007BE2D4`. It is read as an `{float, int}` pair and copied into object fields (e.g. `0x147230`
    `vldr s0,[r5]` + `ldr r5,[r5,#4]`; `0x181250` copies both words into object `+0x238/+0x23C`).
    The 31 guard-only entries are outlined cold paths of that one inline "ensure default value"
    helper; they all do `if (guard_acquire(0x7BE2D0)) { *(u64*)0x7BE2D4 = 0; guard_release(); }`
    (`0x0010009C` acquire, `0x00101A94` release veneer) and nothing else.
7. **Two lazy singleton getters**: `0x68B23C` (object `0x007C8608`) and `0x691C0C` (object
    `0x007E2164`) self-link a list head, round a node size with `0x11CFAC`, splice with `0x1235A4`,
    install two code pointers (`0x00576CBC`/`0x00576E90` for the second) and return via `0x00672404`
    (which is literally `bx lr`, as N_121/N_128 noted).
8. **`0x692C7C` is not a function**: it is the guard tail of `0x6928D0` (no prologue, reuses the
    caller frame) followed by the inline table of 2D-gimmick class names. Ghidra's declared Thumb mode
    is wrong; ARM decodes coherently.
9. **Player-actor attachment pair**: `0x371DDC`/`0x371E14` are slots 11/10 of the player-actor table
    `0x00765964` and pass `&self->f_30` / `&self->f_44` to the owner's "apply/attach part" slot
    (owner vtable `+0x84`, the same slot `0x364640` uses to detach a part). They are named
    `SetAttachmentA/B`, not "weapon shown", because the slot is shared with non-weapon parts.

## Naming convention used

* `Field_InitActorColorTable_<tableaddr>` / `...ColorTables_<first table>` for the RGBA writers
  (aligned with N_119-N_121; the UI band uses `Ui_InitColorPalette_*` - see follow-ups).
* `Field_InitActorParamBlock_<tableaddr>` for the small default-parameter writers.
* `Field_RegisterActorClass_<ClassName>` / `Field_Register<Group>Classes` for the registrations.
* `maybe_Os_EnsureDefaultValueInit_<addr>` for the 31 outlined guard stubs (the address suffix is the
  only honest discriminator - they are copies of one inline helper).
* `maybe_Os_Singleton_GetInstance_<objectaddr>` for the two getters.
* `*_DeletingDtor` / `*_Dtor` / `*_Ctor` / `*_Update` / `*_Check...` for the 0x36 methods, with the
  class taken from the vtable the function sits in.
* Everything below 0.5 confidence is `maybe_`-prefixed, per the template.

## What is NOT verified / open problems

* **Everything is static.** No emulator run, no playtest - no palette, registration or singleton was
  observed in use. The palette template and its substitution rule are byte-verified, but *what the
  colours are for*, and which actor class each table belongs to, is not proven.
* The palette bases look **write-only** (single reference each). They may be dead code or reached
  through a computed pointer I did not find; do not treat them as live UI colours without a reader.
* Class names identify the **registered class**, not the semantics of the neighbouring param block.
* The 31 guard stubs are semantically identical; their names differ only by address.
* Fragments (`*_Tail`, `*_EpilogueTail`, `*_DestroyLoopTail`) describe the local action only; the name
  of the function that contains them is a hypothesis.
* Weakest names: `maybe_Anim_Clip_Init` (0x68ADE8, 0.35), `maybe_Os_Singleton_GetInstance_*` (0.30),
  `maybe_Field_ActorPart_DtorBody` (0x364640, 0.45), `maybe_Ui_Window_ApplyActorProjection`
  (0x36898C, 0.45), `maybe_Field_RegisterGimmick2DClassesTail` (0x692C7C, 0.40).
* `0x68A798` mixes a per-instance palette (`self+0x50`) with shared template writes; the split between
  "instance" and "global" there is inferred from the register usage only.

## Suggested follow-ups

1. **Fix the seed generator** (validate a real Thumb prologue; reject `mod 4 == 2` ARM seeds). It
   would remove the 10 fake entries in this batch alone (and the same artefact is reported by
   N_124/N_126/N_128).
2. **Trace a reader of `0x7BE2D4`.** 676 sites reference it; one of them must reveal what the
   `{float,int}` default means (it is copied into actor/UI objects as a default pair). That would let
   the 31 `maybe_Os_EnsureDefaultValueInit_*` stubs get a real name.
3. **M1 vocabulary merge**: `Field_InitActorColorTable_*` (N_119-N_121, this batch) vs
   `Ui_InitColorPalette_*` (N_128) - one of the two should win, and the 12-colour template should be
   documented once in `docs/`.
4. Pair each palette/param table with the actor class registered nearest to it (the 16 registration
   functions in this batch supply names for a few tables).
5. A struct pass on the actor variant block: `+0x10` two floats, `+0x44/+0x48` id words, `+0x50`
   per-instance palette, `+0x74` state byte, `+0x30`/`+0x44` two attachment nodes.
6. Register the shared helpers once in `symbols.json`: `0x0010F6CC` (instance release),
   `0x0010009C` (`__cxa_guard_acquire`), `0x00101A94` (guard-release veneer), `0x001235A4` (list
   splice), `0x0011CFAC` (libgcc udiv), `0x0011FE8C` (0x10-byte size round-up), `0x002A55EC` (named
   record ctor), `0x0017D0DC` (default-block writer).
