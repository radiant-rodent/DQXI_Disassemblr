## What the band actually is

The header label `Unknown` is a generator artefact. The batch is two unrelated bodies of code:

| range | what it is | entries |
|---|---|---:|
| `0x00694300`-`0x006A2EBC` | the static-constructor / accessor block of a **C++ UI module**: per-widget 12-entry RGBA colour-palette initialisers, small guarded state-block resets, intrusive-list ("publish this static widget") constructors and two text-widget creators | 139 |
| `0x00717110`-`0x00723EF0` | the **generic algorithms / compiler-runtime tail** of `.text`: four `std::`-style insertion sorts and one introsort driver, plus three soft-float helpers (`u64->double`, `f32->u32`, `f64->u32`) | 9 |

Facts that decide the layout (all verified against `build/code.bin`, VA = file offset + `0x00100000`):

* **The 12-colour table.** 71 of the 139 UI addresses have a contiguous 12- or 13-slot palette run
  (80 contain the ARM `mov #0x91/#0x0b/#0x3a` constant triple), all writing the same 12 RGBA entries
  with one alpha byte per entry: `000000FF A0A0A0FF FF3A60FF FFE735FF 5FFF3AFF 50D2DCFF B2F7FFFF FF7D1EFF
  181818FF 1800FFFF 910B10FF 00F62DFF` (black, grey, red, yellow, green, cyan, pale cyan, orange,
  near-black, blue, dark red, bright green), followed by `0xFFFFFFFF` as "current colour". In the
  12-slot variant the current colour is written through the caller pointer (arg = 0xFF); in the
  13-slot variant it is the trailing slot of the block itself. N_119/N_120/N_121 found the identical
  template in the neighbouring field-actor constructor band and named it
  `Field_InitActorColorTable_*`; N_122 verified the substitution rule (every template byte `0xFF`
  receives the alpha argument). I kept my own `Ui_InitColorPalette_*` vocabulary because these
  functions are *not* in the actor band and the same block also constructs text widgets - see
  "Open problems" for the vocabulary conflict M1 has to settle.
* **Shared one-time-init guard.** Every UI entry ends in the same cold block:
  `if (!(*(u8*)0x7BE2D0 & 1)) { if (__cxa_guard_acquire(0x7BE2D0)) { *(u64*)0x7BE2D4 = 0;
  __cxa_guard_release(0x7BE2D0); } }` and returns through the ARM->Thumb veneer `0x00101A94` (which
  lands on `bx lr`). `0x0010009C` is the acquire helper - both identifications agree with N_121.
* **`0x00672404` is not a registration entry** - the word there is `1e ff 2f e1` (`bx lr`), as N_121
  recorded. Several of my first-draft summaries said "registers via 0x672404"; they were corrected
  before writing the JSON.
* **Reachability.** A full-image scan (every `bl`/`blx` immediate decoded in both ARM and Thumb mode
  for all 18,787 indexed functions, plus a 32-bit word scan of the whole image) finds **no caller and
  no address-taken pointer for any of the 148 functions**. Combined with N_121's finding that the
  retail `.init_array` is empty (`__init_array_start == __init_array_end == 0x0079AA18`), this
  constructor block is linked but never reached from the static-init table. This is recorded in the
  evidence of every entry instead of inventing a caller. (It is not unique to this batch: 4,811 of
  18,787 functions - 26 % - have no direct caller or pointer, which is what you expect in a binary
  whose objects are mostly reached through vtables built at run time.)
* **Ghidra split artefacts.** `0x694300`, `0x6944AC`, `0x69466C`, `0x694674` are not function starts:
  they are literal-pool words of the preceding palette initialiser (and `0x694674` is a 4-byte
  container entry). `0x694678` is a container entry whose listed address is `0x007AB514` inside the
  *previous* function's pool - the executable body starts at `0x694684`. `0x69DA98` and `0x6A0CD4`
  are guard-only stubs whose large sizes come from the literal pool that follows the return. All of
  this is stated in the individual entries.

## Method

1. Read `README.md`, `orchestration/PLAN.md`, `TEMPLATE.md` and the sibling batches (N_098, N_119,
   N_120, N_121, N_122, N_123) for vocabulary and already-established helper identities.
2. Read the readable C for every address, then fell back to Capstone 5.0.7 disassembly of
   `build/code.bin` (both modes, choosing the mode that decodes the most bytes) because Ghidra's
   pseudo-C is unusable for this band: dozens of bodies are `halt_baddata()`, `unaff_r4/r5/r6` or
   `*(u32*)arg1 = arg1`. My disassembly resolves `ldr rX,[pc,#imm]` literal pools and prints the
   target with its known name, which is what made the structures readable.
3. Built three reusable indexes in `%TEMP%/opencode/`: (a) per-function store maps - simulating
   `ldr =lit` / `add` / writeback so every `.data` store lands on its real address, which produced
   the 12/13-slot palette runs and the small state blocks; (b) a whole-image call graph from all
   `bl/blx` immediates; (c) a whole-image 32-bit word index for address-taken detection.
4. Grouped the 148 by body shape and named templates, never individual guesses:
   * 75 x `Ui_InitColorPalette_<block address>` (0.50-0.58)
   * 16 x `Ui_RegisterStaticObject_<block>` - builds a self-linked intrusive node and splices it into
     the module list head `0x7BE378` using `0x001235A4`, allocating through `0x0011FE8C` and rounding
     the node size with the libgcc unsigned-divide helper `0x0011CFAC` (0.50)
   * 2 x `Ui_CreateStaticTextWidgets_<addr>` - direct `bl 0x002A55EC` (`maybe_Ui_TextWidget_Ctor`)
     with a `.data` layout record and a per-widget callback (0.55) - a third palette initialiser
     (`0x69C68C`) additionally creates five of them
   * 41 x `maybe_Ui_EnsureSharedStatic_*` / `maybe_Ui_InitStateBlock*` guard stubs and small state
     resets (0.35-0.45)
   * 9 x `std_*` sort / soft-float helpers (0.25-0.55)
   * 5 x hand-written specials (`Font_InitGlyphBitmapPools`, `Ui_InitColorPalette_7A6944`,
     `maybe_Ui_InitColorPalettesAndMetrics_7ABEB4`, `maybe_Ui_InitTimestampObject_7AE174`,
     `maybe_Ui_InitAngleObject_7A3AF8`)

## Findings worth keeping

* **`Font_InitGlyphBitmapPools` (`0x69BD40`, 0.62)** is the strongest name in the batch: four calls
  to the already-known `Mem_BitmapPool_Init` (`0x0057010C`) with the pool objects `0x7C8584`,
  `0x7C85C0`, `0x7C85D8`, `0x7C85F0`, all sharing the parameter block `0x7E2000`, each with its own
  alloc/free callback pair (`0x161154/0x194398`, `0x162DDC/0x4B3600`, `0x16226C/0x2BD580`,
  `0x161DB8/0x1E6C1C`), then a self-linked pool list at `0x7C859C`. This is the glyph cache the text
  renderer draws from and it pins the module to UI/text.
* **`Ui_InitColorPalette_7A6944` (`0x69DB7C`)** proves the palettes are *object members*, not global
  tables: it takes the object in `r3` and writes `[r3+8]=0xFF`, `[r3+0xC]=0xFFFFFFFF` (current
  colour) and the 12 entries at `[r3+0x10]..[r3+0x40]`. That is why the Ghidra signature reads
  `(u32, int, u32)` and why the batch has ~90 near-identical bodies - one per widget class.
* **The module is text/UI, not field/actor.** `0x698444` and `0x69EF88` construct text widgets via
  `0x002A55EC`; `0x69C68C` constructs five of them; `.data` at `0x7BE390` holds the inline text-style
  names `"defaultTalk"` repeated in 16-byte records; and the code at `0x2A5404` next to the widget
  constructor is the already-named `Ui_Font_IsBffntName`.
* **Tail region.** `0x7210C8` is a self-recursive introsort loop over 2-byte records (median-of-three
  pivot by the bytes at +0/+1, depth limit), `0x723438` is its `std::sort` driver (introsort then
  insertion sort), `0x717110`/`0x717CB8`/`0x717E78` are three more insertion sorts with record-id and
  float-field comparators that continue the already-named `std_insertion_sort_*` family at
  `0x716858`-`0x717AB4`. `0x723D2C` is `u64 -> double` (exponent bias 1074, round-to-nearest-even),
  `0x723E7C` is `f32 -> u32` and `0x723EF0` is `f64 -> u32` (both use the 1.5f rounding bias
  `0x00C00000` at `0x723EA4`, float exponent bias 0xBE = 190).
* **`0x69FEEC`** writes 0.6806784 (39deg), 1.5, 7.0 and pi/4 into an object and calls the float helper
  entered at `0x00672E44` (the internal tail entry of `maybe_std_Ceilf` at `0x00672DA0`, per N_124)
  twice with pi/4, storing both results at +0xC/+0x10. I deliberately did **not** call it "random"
  (my first hypothesis) once I read the literals as floats.

## Open problems / honest gaps

1. **Vocabulary conflict for M1.** N_119/N_120/N_121 call the same 12-colour initialiser
   `Field_InitActorColorTable_*`; I call it `Ui_InitColorPalette_*` because this band is UI text code.
   Only one vocabulary should survive the merge; the palette bytes and the block addresses are
   identical either way, so the merge is cheap.
2. **No reader exists for any palette block.** Nothing in the image loads any of these `.data`
   addresses (full 32-bit word scan). Either the consumer builds its base pointer at run time from a
   pointer table I could not locate, or the whole constructor block is dead (consistent with the
   empty `.init_array`). I did not resolve this; it is the single biggest open question for this band
   and for N_119-N_121 as well.
3. **What the 12 colours mean is not proven.** The hues match the DQ colour-tag set and the
   surrounding code is text/UI, but no draw call was traced. Summaries say "colour palette" and mark
   the use unconfirmed rather than asserting "message text colours".
4. **The "register" family is structural, not semantic.** I can prove the list mechanics (self-linked
   8-byte node, `0x001235A4` splice, head `0x7BE378`) but not which widget each object *is*; the
   names use the object address as the discriminator, as the sibling batches do.
5. **Ghidra function splits are wrong across this band.** Four batch addresses are literal-pool data
   and at least four more (e.g. `0x695354`/`0x6953C0`) have their real body in the bytes after the
   literal pool, i.e. Ghidra cut one routine into "guard stub + init code". I described the whole
   byte range of each entry and flagged the artefacts; a seed-fix pass would remove 4 fake functions
   from the progress page.
6. **`maybe_std_SortHelper_71E66A` (0.25)** is the weakest name in the batch: the address is even but
   capstone cannot follow more than 26 bytes in Thumb mode and ARM is impossible at an unaligned
   address, so I could not recover its body. It sits between `std_insertion_sort_u16_item` and the ARM
   function at `0x71ECF8` in the sorting block; treat the name as "unverified sort/partition helper".
7. **`maybe_std_FloatToUnsigned` / `maybe_std_DoubleToUnsigned`** are identified by their instruction
   patterns (FPSCR read, bias 190/1074, 1.5f rounding trick, saturation paths), not by a symbol. They
   are almost certainly the libgcc `__aeabi_f2uiz`/`__aeabi_d2uiz` helpers.
