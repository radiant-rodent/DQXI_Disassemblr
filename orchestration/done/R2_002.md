# R2_002 — second naming pass (refine)

## What was done

Re-examined all **150** low-confidence `maybe_` functions in `orchestration/naming/refine/batches/R2_002.txt` (addresses `0x003F463C` down to `0x003B6DB8`) using the merged context from M1 (with ~8,500 confident function names available across `decomp/readable`) and the established domain facts in `orchestration/naming/FACTS.md`.

For each function:
1. Inspected its readable C file and documentation header (`previous_name`, `previous_confidence`, proposal batch, previous evidence).
2. Checked its newly confident callers, callees, and neighbourhood constants/vtables in `orchestration/naming/refine/scores.jsonl` and cross-referenced with `decomp/readable`.
3. Verified decompilation health (checked for `unaff_rN`, `coprocessor_`, `in_NG`/`in_ZR`/`in_OV`, and `halt_baddata`), predicate signatures, and poisoned address ranges.
4. Assigned honest verdicts (`confirmed`, `corrected`, `kept_maybe`) with new, concrete evidence.

**Result Breakdown:**
- **16 Confirmed** (confidence 0.55–0.65): context, vtables, and named callers/callees directly proved the original proposal.
- **1 Corrected** (confidence 0.55): context showed the previous name was misleading.
- **133 Kept Maybe** (confidence 0.30–0.45): retained `maybe_` prefix honestly because of damaged decompilation, unverified vtable variants, or ambiguous sub-object helpers.

Output written to `orchestration/naming/refine/out/R2_002.json`.
