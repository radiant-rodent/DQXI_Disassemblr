# R2_005 — second naming pass (refine)

## What was done

The previous worker left no draft and no output file, so all **150** low-confidence `maybe_`
functions in `orchestration/naming/refine/batches/R2_005.txt` were decided from scratch. For each
entry I read the readable C (header = previous name/confidence/evidence) and re-read it with the
post-`M1_merge_names` context:

- named callers and callees (verified that the call actually appears in the caller's C body, not
  only in its doc header);
- vtable siblings / neighbourhood shared with named functions;
- `neighbour_names` from `orchestration/naming/refine/scores.jsonl`;
- the batch grouping (the Fx particle/emitter family and the Ui scene-flow block at the end).

Decompilation health was checked (`unaff_`, `in_ZR`, `coprocessor_`, `halt_baddata`, damaged
signatures) and FACTS.md was applied (dropped return values, hard-float returns, poisoned ranges,
dropped register arguments).

Output: `orchestration/naming/refine/out/R2_005.json` — 150 entries, one per batch address.

## Deliberately kept honest

98 functions stay `maybe_` with < 0.5. Main groups:

- the whole `Fx_EmitParticles*` family (no direct callers; only the shared quad builder and
  arithmetic shapes are known — the shape words are descriptions, not proven emitter types);
- damaged bodies (`0x00627ADA`, `0x004B8DEC`, `0x001A1A00`, `0x0049ED7C`, `0x0045EB08`) kept at or
  below 0.40, and `0x00627ADA` at 0.30;
- vtable-only functions whose class is still inferred (`Ui_Billboard_UpdateFromActor`,
  `Field_ActorAction_CtorB`, `Ui_JackpotScreen_UpdateReelResult`);
- `maybe_Field_Npc_InitColorBalloonA/B`, where the body is certain but no caller/vtable names the
  "balloon" object.
