## Method

The batch is sorted by context score, so the top of the file was done first. For each function I
re-read the readable C with its now-named neighbours and, where the function had no static caller,
resolved **which vtable it is installed in** — that turned out to be the single most productive
signal in this batch:

- `findvt.py ADDR` locates every 4-byte word in `original/exefs/code.decompressed.bin` equal to the
  address (i.e. the vtable/native-table slots it occupies);
- `vt.py BASE` dumps that table with the current names, so a function can be attributed to a class
  by its **confident siblings** (`Actor2D_EffectNode_DtorDelete`, `Field_Marker_OnUpdate`,
  `Field_Actor_SetWalkState`, `Ui_PastScenarioWindow_InitPanes`, `Battle_Ui_PlayMemberSound`, …).

That is what produced most of the corrections below: the first pass had guessed the owner from the
module band, and the vtable said otherwise.

## Why 107 stayed `maybe_`

Structural, not caution. Most of these functions have **no static caller at all** — they are reached
only through vtable slots or function-pointer tables — so the only evidence is their own body plus
the class they belong to. Several are damaged: `0x002ACF58` is 3256 bytes with four "removing
unreachable block" warnings, `0x00517942` has `unaff_r4/r7`/`in_lr`, `0x00489788` has mis-resolved
callees. Promoting those to 0.5+ on their own body alone would be inflation, so they keep `maybe_`
with a sharper summary instead.

## Open problems / notes for the orchestrator

1. **Merge race (same as R2_018).** `decomp/readable/**` is regenerated by the merge; the 110 entries
   written by the previous worker may already be in the readable tree while the 39 written here are
   not. The JSON is complete either way — the readable headers will catch up on the next
   `tools/merge_names.py` run.
2. **`0x00228838` is a deleting destructor of a sub-object at `+0x2C`.** Its vtable is installed at
   the sub-object, but the free returns `this-0x2C`. If a later pass models multiple inheritance it
   should record that offset.
3. **`0x0044C454` / `0x0044C760` are twins on two different state blocks** (`+0x298` and `+0x2C8`).
   Which block belongs to the move-target logic and which to the effect state machine is still open;
   the callers suggest it but do not prove it.
4. **`0x00489788` needs a disassembly read.** The decompiled body calls `Text_MarkLayoutDirty` in the
   middle of battle-unit arithmetic, which cannot be right; the real output store was lost.
