## What I changed

**One real defect fixed — a name collision.** The previous pass named `0x0061B724` `Ui_SetNumberText`,
but that name is already taken by `0x003D2A8C` (the two-pane variant that reads the widget's own
`f_58`/`f_5C`). The merge silently disambiguated it to `Ui_SetNumberText_2`, which is meaningless to
a modder. Renamed to **`Ui_SetNumberTextValue`**: it takes the number as an argument, formats it
through the message-format singleton and writes the single font-`0x15` pane. `change` stays
`corrected`; the evidence now records why the first-pass name could not stand.

**Everything else was verified and left alone.** I checked, in depth, the four ≥ 0.50 entries, the
six highest-context entries (score 12), and a spread of the `corrected`/`kept_maybe` entries against
their bodies. The previous worker's reasoning held up in every case I opened:

- `Ui_DiveManager_Recreate` — the callee really is the confident `Ui_DiveManager_Ctor` (0.55) and the
  caller `Ui_Panel_PlayBgmAndShow` passes a three-float position struct. Sound.
- `Ui_UpdateCharaStatus` — the cited `Ui_CharaStatus_HideModelA/B` (0.55) are called on the
  sub-object this function creates; the `0x149`/`0x15C` state pair and the `0x007AE55C` entry table
  are literal in the body. Sound.
- `maybe_Ui_CreateMapCursor` — the "only caller is `maybe_Menu_TalkParty_WaitPanels`" claim is true
  (grep confirms one call site). Kept `maybe_` at 0.40: the summary already says the map-cursor role
  is unproven, so the name is honest as a `maybe_`.
- The `StoreRectPair*` / `StorePosPair*` family — the generic names are accurate (each copies one
  2-word pair out of a fixed global after a view query) and the old names encoded a source offset
  (`_0xA0`) or an unproven role (`CursorPos`), so the corrections were right.

## Not verified / open

- **The readable tree is stale for 72 of the 109 entries** (see above). They will land on the next
  merge; until then `decomp/readable/**` shows the old names for those addresses. This is expected,
  not a defect in the JSON.
- `maybe_Ui_CreateMapCursor` (0.40) still claims a "map cursor" that nothing in the body proves. The
  object is built with `maybe_Ui_MovieWindow_InitBase` and gated on 2D-field mode
  (`world+0x3C == 2`). If `maybe_Ui_MovieWindow_InitBase` is ever resolved, this name should be
  revisited — it may be a 2D-field window object rather than a cursor.
- `maybe_Field_GetSelectedId` (0.35) reads through `Ui_GetCore()->f_10->f_98->f_4C`, so a `Ui_`
  prefix would arguably fit better than `Field_`. Left as-is because the `0xFFFF` sentinel suggests a
  field/map selection id and neither reading is proven.
- `maybe_Battle_CommandSlots_UpdateContinuationA/B` (0x00169076 / 0x0016907A) are **not functions**:
  they are Ghidra split fragments of the routine at `0x00168C64` (no prologue, `r4`/`r6` live on
  entry, the routine returns at `0x001690EC`). They cannot get a standalone name; the honest outcome
  is to keep them as `maybe_` placeholders. A future task could suppress split symbols in the
  readable export instead.
