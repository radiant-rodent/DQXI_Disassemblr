## Method

1. Built a context digest per function (`out/scratch/R2_019/digest.py`, `compact.py`): the readable
   C header (previous name, confidence, evidence), the body, the `scores.jsonl` row
   (`callers_conf`/`callees_conf`/`vtable_siblings`/`strings`/`shared_constants`/`neighbour_names`),
   every caller found by scanning `decomp/readable`, and every callee resolved through
   `symbols.json` (so `func_XXXX` shows its current name and confidence).
2. Read the named neighbours that mattered, not just the batch function: `Ui_BaseWindow_UpdateStep`
   (0x002FCEAC) to identify the window core at `self+0x3574` and its 19-entry step table,
   `ActorActionSeq_RunNode` (0x003BD908) and `maybe_Actor_BindSubObjects` (0x002E3BF8) to identify
   `self+0x3570` as the owner pointer, `Ui_PromptRef_IsFirstChoiceConfirmed` (0x0062F694, 0.65),
   `Ui_CursorIcon_Hide` (0x001D7B1C, 0.55), `Event_OnTriggerCommand` (0x00253290, 0.60),
   `Ui_CommandQueue_*`, `Ui_List_ConfirmCurrent`, `Ui_Window_PopPaneRawB`, and the vtable at
   0x00762810 in `asm/rodata/rodata_00745000.s`.
3. Decided per function and wrote the JSON in five chunks (`out/scratch/R2_019/chunk_0*.json`),
   merging into the owned output file after each chunk so a resumed worker could continue.

### The three findings that drove most of the corrections

1. **The `self+0x34D8` widget / `self+0x3574` core template.** `Ui_BaseWindow_UpdateStep` shows that
   `self+0x3574` is the base-window *core* (step index at +0x04, 19-entry member-function step table
   at +0x34, `this` at +0x20) and that vtable slot +0x14 requests a step while +0x10 advances it.
   Every `..._StartActionN`, `..._InputToStateN`, `..._SetStateN`, `..._GotoStateN`,
   `..._UpdateChildrenToStateN` in this batch is that template, so the names could be confirmed
   mechanically (the id is a literal in the body) at 0.50 without claiming what the id means.
2. **`self+0x3570` is the owner pointer**, not a sequence object: `maybe_Actor_BindSubObjects` writes
   `self->f_3570 = owner`, and `ActorActionSeq_RunNode` reads the owner's 0x10-byte node array at
   +0x34/+0x38. That is why the `Actor_ActionSeq_Run*` and `Ui_Window_StartAction*` names in this
   batch describe the same body shape from two different angles; where the owner class could not be
   decided I kept `maybe_` instead of picking one.
3. **Suffixes that claimed a state id were wrong.** `UpdateChildrenToState2C/2D/2E/2A` all request
   state **2** (the letters only record the vtable slot) and `UpdateChildrenToState2B` also requests
   2 while setting a dirty byte. Renamed to `...State2CopyC/D/E/A` and `...State2SetDirty`. Likewise
   `SakusenWindow_UpdatePopCommand(B)` call `Ui_CommandQueue_AdvanceAlt` (advance, not pop) and
   `StartAction4_ShowCursor` calls `Ui_CursorIcon_Hide` (hide, not show).

### Other notable corrections

- `maybe_Party_CountMatchingMembers` → `maybe_Ui_Window_DispatchByRowCount`: the loop walks
  0x8C-byte per-actor records at `(work+0x24A98)+0x606C`, not the 0x12EC-byte `PartyMember` records,
  and the result selects one of five handlers from the table at 0x007291F0.
- `maybe_Ui_PlayWindowSe` → `maybe_Ui_Window_TriggerEventCommand`: the byte at `self+0x320` is passed
  to `Event_OnTriggerCommand` as a script command id; nothing touches a sound id.
- `maybe_Ui_Window_CommitRecordAndAdvance` → `maybe_Ui_Window_SyncRecordAndAdvance`: the copy runs
  work+0x2E2F8 → self+0x984, i.e. it loads the record into the window.
- `maybe_Ui_Object_NotifyEvent` → `maybe_Ui_Object_NotifyOverlayManager`: the argument is
  `(work+8)+0x48`, the UI overlay manager from FACTS.md.
- `maybe_Ui_TalkWindow_Update` → `maybe_Ui_Object_PopCallbackStack`: it is a one-shot pop of the
  3-word callback stack at +0x1C68, not a per-frame update.
- `maybe_Anim2D_SpriteNodeDtorC` → `maybe_Actor2D_SpriteNode_DtorC`: the installed vtable is
  `g_actor2DSpriteNodeClassDesc`, the class of the named `Actor2D_SpriteNode_Ctor` (0.55).
- `maybe_Ui_Widget_UpdateTimerChild` → `maybe_Ui_Widget_StepTo4Or0`: no timer anywhere in the body.
- `maybe_Ui_Window_InputCancel` → `maybe_Ui_Window_InputToState11Or6`: the scroll correction runs on
  the *confirm* branch, so "Cancel" was wrong.
- The six `Ui_Window_NotifyHandlerA..E` → `maybe_Ui_Window_NotifyResult*`: the bodies differ only in
  the result code they write (default / 9 / 0x10 / 1-or-2-with-effect), so the letters carried no
  information.
- The five `Ui_RacingWindow_UpdateStateA..E` → `HandleInput` / `FinishToState10(B/C)` /
  `StepToState9`, from the literals in the body.

## Not verified / open

- The owner class of the `self+0x34D8` / `self+0x3574` template is still open: `maybe_Actor_BindSubObjects`
  writes `f_3570 = owner` on an object that also owns a `Ui_ListView` and an effect set, so the
  object could be an actor with an embedded message window rather than a plain window. That is why
  the `Actor_ActionSeq_Run*` names in this batch were kept as `maybe_` instead of being renamed to
  `Ui_Window_*`.
- The vtable at `self+0x3574` was not identified. The vtable at 0x00762810 (which holds
  `Ui_BaseWindow_UpdateStep`) does **not** fit the +0x10/+0x14 slots used here, so the core is a
  different class; finding its constructor would settle the whole family.
- `func_0062F680` (the "widget finished" test used by ~90 of these functions) is still unnamed. It is
  the single biggest lever left in this address range.
