# R3_002 — second naming pass (refine)

**Status:** completed
**Output:** `orchestration/naming/refine/out/R3_002.json` (owned)

## What I did

Read the pre-baked dossier in chunks (roughly 10 functions at a time), decided every address, and
wrote the full JSON in one pass. Extra context came only from targeted `python tools/fn.py` calls
(callers/callees/siblings), the readable C of a named caller, and one `Select-String` on a single
readable file. No whole-tree walks of `asm/`, `decomp/` or `include/`.

Result: **5 confirmed, 20 corrected, 25 kept_maybe**; 20 entries at confidence >= 0.5, 30 below.

## Main findings (why names changed)

### Wrong class / wrong subsystem

- `0x002BBC3C`, `0x002BBD0C`, `0x002BBDDC` — `maybe_Ui_CreateChildWidget_11D8*` allocated 0x11D8
  bytes and called `Ui_SakusenWindow_Ctor` (0x2A3E78, the ctor also used by the confident
  `Ui_SakusenWindow_Create` at 0x6D7160). The three wrappers differ only in the post-construction
  step, so they are now `Ui_SakusenWindow_CreateWithIconState`,
  `Ui_SakusenWindow_CreateAndRefreshList`, `Ui_SakusenWindow_CreateWithMessageId`.
- `0x003DF9AC`, `0x003DFA44` — `maybe_Ui_SetNamedFlag*` are sprite-child render flags, not UI.
  `Gfx_SpriteActor_AddChild` (0x335A6C) passes `&spriteChild->f_3c`, the callees are
  `Gfx_GetSceneSpriteContext` / `Gfx_Scene_AddSpriteEntrySmall`, and the object appends up to 32
  `(nameHash, bits)` pairs. Renamed `Gfx_SpriteChild_AppendNamedFlags` /
  `Gfx_SpriteChild_AppendNamedFlagsFromTable`.
- `0x001078A8`, `0x001079C0` — `maybe_Snd_UpdateState*` are the GPU display/command pump: their
  callees are `Gfx_LockedIpcCmd3E0080`, `Svc_WaitReadyAndSendRequest`, `Gfx_WaitForIpcIdle` and
  `maybe_Gfx_NegotiateDisplayMode`, and the caller is `Engine_DispatchFrameCallbacks`. Renamed
  `Gfx_UpdateDisplayState` / `Gfx_UpdateDisplayStateB`.
- `0x00107AD4`, `0x00107AE8` — same neighbour set; renamed `maybe_Gfx_IsDisplayStateReady` /
  `maybe_Gfx_IsDisplayStateActive` (the two state getters 0x10CC10/0x10CC20/0x113A00 are unnamed,
  so confidence stays below 0.5).
- `0x002F5FB8` — the `JockeyPanel` owner had no support (no caller, no named vtable sibling); the
  named callees only show menu-cursor input handling. Renamed `maybe_Ui_Panel_HandleInput`.
- `0x002854E0` — the `Shop` owner was inherited and unverified; renamed
  `maybe_Ui_StopFadeAndSound`.

### Battle-math block (FACTS: 0x00485D90..0x00497900 is combat math, not text)

- `0x0048A63C` / `0x0048A720` — `maybe_Battle_CalcItemDamage[Ex]` resolves **SkillRecord** ids
  0x4E/0x4F/0x50 through 0x0018C1B8 (SkillRecord wrapper per FACTS) and switches on parameter type
  0x94/0x96/0x97, interpolating the skill record's min/max with RNG variance. The named caller
  `Ui_Status_CalcWeaponAttackValue` passes the record returned by `func_00639C98(member, 0x94/0x96)`.
  Renamed `Battle_CalcSkillParamValue` / `maybe_Battle_CalcSkillParamValueEx`.
- `0x00490164` — starts with the spell-record resolver 0x0018C184 and sums the eight 0x2C-byte
  effect rows (or lays out the default rows when the +0x296 flag is clear); renamed
  `Battle_CalcSpellEffectTotal`.
- `0x00492FC4` — single-row companion using the same resolver and the spell row-kind byte +0x2A;
  renamed `Battle_CalcSpellRowValue`.
- `0x00496650` — confirmed `Battle_Unit_RefreshDisplayValues` from the named caller
  `Battle_Monster_UpdateMpBar` and the display-slot/layout-dirty callees.

### Constructor vs destructor

`0x005D18E0`, `0x005D2880`, `0x005D3B9C` ended in `std_destroy_range` (0x00100BE0, verified to call
an element destructor backwards) after releasing handles; their only caller is
`Field_UiGimmick_Dtor`. They are now `Ui_ObjectList_DestroySlotsB/C/D` (3+2, 10 and 3 slots).

### Other corrections / confirmations

- `0x0059121C` — the real function behind the `ReguralyShake` key literal (0x591204 is a data blob);
  constructs with the named `Camera_RegularShake_Ctor` vtable 0x591360, so the `B` suffix was
  dropped: `Camera_CreateRegularShakeWork` (0.55).
- `0x00483E30` — the state handler calls the now-named `Ui_PopupEntry_SpawnRevive`, so it is
  `Battle_PartyMember_UpdateRevive`, not "UpdateEnter".
- Confirmed at 0.5-0.55: `Field_SpriteObject_InitFromShortRecord` (0x004CA28C),
  `Ui_BattleBindWindow_CtorA` (0x003D2260), `Gfx_SceneSpriteSet_UpdatePresets` (0x006105B4),
  `Svc_Cfg_EnsureService` (0x001121E4).
