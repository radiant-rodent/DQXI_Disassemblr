## What decided the batch: a vtable lookup straight from the ROM image

`original/exefs/code.decompressed.bin` is the decompressed `.code` with load base `0x00100000`
(verified: file offset `0x48` holds `01c08fe2 1cff2fe1`, the `add ip,pc,#1 / bx ip` at `0x00100048`).
Searching that image for a function's 4-byte little-endian address finds every vtable slot it
occupies, and the *neighbouring* slots name the class. This is the evidence the first pass did not
have, and it settled more than twenty entries. Scratch script: `out/scratch/R3_005/` (nothing
written outside it).

Two structural facts it produced:

* slot `+0x18` of a `Ui_Object` vtable is the visibility setter (`Ui_Pane_SetVisibleWithAnim`
  appears at `+0x18` in 262 vtables), slot `+0x1C` is the class's `InitPanes`.
* the `0x0072xxxx` tables with 8-byte `{handler, 0}` entries are command/handler tables, not
  vtables — five of this batch's functions are entries in them.

## Corrections worth reading

1. **The 13 "SetVisible" entries.** All are slot `+0x18` overrides. The class names in the batch
   were mostly wrong; the vtable's own `+0x1C` sibling gives the right one:
   `Ui_ShopWindow_` → `Ui_EquipmentListWindow_` (the pointer is shared by four vtables
   `0x00760820/0x00765274/0x0076B1DC/0x0077AECC`), `Ui_RecordListWindow_` →
   `Ui_TwoColumnListWindow_`, `Ui_ItemGrid_` → `Ui_PartyListWindow_`,
   `Ui_Widget_SetVisibleAndSetRowAlphas` → `Ui_SevenSlotWindow_…`,
   `Ui_Pane_SetVisibleGated` → `Ui_NumberedTextWindow_`,
   `Ui_Widget_SetVisibleAndLayout` → `Ui_PagedIconSelectWindow_`,
   `Ui_Widget_SetVisibleAndSetTextLayers` → `Ui_ListWindow_…`.
   `Ui_SkillPanel_`, `Ui_TextRowL1_Alt_`, `Ui_UmaWindow_` and `Ui_Pane_SetVisibleAndForward` were
   confirmed by their own vtables.
2. **`0x0066B11C` was not a tail helper.** Ghidra cut the body at `blx 0x00100B74` because that
   Thumb helper is mis-marked noreturn; `0x00100B74` is `wcslen` (loop counting `u16` until 0,
   `bx lr`). The real body loops over up to `0x32` records of `0x8C` bytes at `savework+0x5FE4`,
   `wcslen`s each name and tests the id at `+0x88` against `-1`. The real seed symbol
   `GetSpiritNum` (`0x00149854`) returns exactly this value and `Ui_ListData_BuildEntries` uses it
   as the row count for the same `0x8C`-stride records → `Spirit_CountRosterEntries`.
   The same trap turned `maybe_Ui_AssertHandleRecordValid` (`0x00629AE4`) into
   `maybe_HandleRecord_GetNameLength`: nothing aborts, the tail call returns the name length.
3. **Poisoned-range spill-over.** `0x00637EBC` and `0x006383F0` were named `Ui_TextLayout_*` but
   every caller is `BattleAi_*`, and the fifth caller of `0x00637EBC` (`0x00275E9C`
   "Ui_TextLayout_LayoutMode7") sits inside the poisoned `0x00269F64..0x00277700` range →
   `BattleAi_FindBestCandidate` / `BattleAi_HasCandidateCapacity`.
4. **`0x00595930`** resolves an *item* record (`Item_LookupRecord(&self->f_1754, id)` then
   `self->f_175C = 0x0063DF9C(dm, id)`); no model is involved, so `ResolveModel` was wrong.
5. **`0x00620A78`** restores vtable `0x0077F6C4`, which lives in the `Fs_Resource`/`FadeAnimator`
   block (`0x005F910C..0x005F9758`), and every callee is a resource-release helper — a scene-sprite
   pool destructor, not a font glyph cache.
6. **`0x0059A6D4`** installs vtable `0x0077E254`, whose `+0x04`/`+0x10` are `Camera_Field_Delete`
   / `Camera_Field_Update`.
7. **`0x003E3A90`** installs vtable `0x0076AE84`, which has *no* overrides (slots `+0x08/+0x0C/+0x10`
   are the base `Actor_Action` virtuals `0x00294BC8/0x00294BD0/0x00294BCC`) → `Actor_Action_BaseCtor`.
8. **`0x00365D9C`** ignores its argument, forces the `+0x1B8` sub-pane open and installs the
   `Ui_JewelShopWindow_UpdateSelect` callback at `+0x144` → an "open", not a "set visible".
9. **`0x005A55B8` / `0x005A57B8`** differ only in the show/hide flag passed to `0x00603B6C` and the
   animation id (`0x36` vs `0x34`) → show/hide, not fade in/out.

## Honest keeps (11)

* `0x005C6E12` / `0x005C6E92` — damaged Thumb, lost prologue (`unaff_r4`/`unaff_r11`); renamed to
  the neutral `maybe_Field2D_Scene_RenderObjectPassA/B` because the chip/sprite split is not
  demonstrable.
* `0x0015FA00` — mid-function split inside the ARM routine at `0x0015F988`.
* `0x00168200` — second half of the body is Ghidra absolute-address garbage (`_DAT_00000020`).
* `0x001BA29C`, `0x003E418C` — vtable-only factories; the override targets are unnamed.
* `0x001956A8` — verb clear, owning window class unproven, no callers.
* `0x0038335C` — both vtable siblings are themselves `maybe_`.
* `0x0059A6D4` — camera virtuals, but the class is unresolved.
* `0x002E999C`, `0x002E9C10`, `0x002E9DAC`, `0x0037B004`, `0x00283374` — five near-identical
  child-list reset copies; now known to be entries of the `{handler,0}` tables
  `0x0072ADF4` / `0x0072B784` / `0x00729140`, but nothing is freed, so the verb stays open.

   It took seconds per function here and would have saved the first pass most of its guesses. Also
   worth dumping the `{handler,0}` tables in `0x0072xxxx` with their entry indices.

   `0x00729288` and neighbours. Their entries are already half-named and the table identity would
   settle the five `ReleaseChildren`/`DestroyChildren` copies in one go.
