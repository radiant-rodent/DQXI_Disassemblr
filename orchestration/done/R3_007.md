## What I did

all 50 entries. Whenever the dossier body was not enough I checked the actual assembly of the

## Important problem found: decomp/xref.json is partly wrong
The pre-baked dossiers (and the refine context scores) are built from `decomp/xref.json`, which is
generated by `tools/xref.py` using function boundaries from `decomp/ghidra/functions.jsonl`. That
file is missing many real entry points and has over-long extents, so `owner()` attributes a branch
to whichever function start precedes it. Examples verified by hand:
- `0x0020D144 Text_GetRecordString` is listed as calling 0x0063D434/0x006038F4/0x006076F4, but its
  asm calls 0x0063F1E0 and 0x0063D790, which are not separate entries in `functions.jsonl`.
- 0x0063D434 shows **111 callers**, but many are calls to 0x0063D790/0x0063D85C inside its
  over-long 1708-byte extent. A checked "caller", `Ui_StoryListWindow_BindRowModels` (0x001C38C4),
  does not branch to 0x0063D434 at all.
- 0x0046D578's listed caller `Ui_GridWindow_RefreshRows` (0x0046D288, 752 bytes) has no `bl` to it.
- 0x00119498's listed callees `Gfx_WriteHwRegsMasked` / `Gfx_SetTextureSource` are not called there.

Caller lists are usually right when the target is an exact entry point (I re-verified many with
`bl` sites), but callee lists and "many callers" claims must be treated as hints only. Rebuilding
`decomp/xref.json` will not fix this by itself: `tools/xref.py` needs better function boundaries
(e.g. also using the readable-file/symbol list as starts, or bisecting with `decomp/ghidra`
function sizes fixed). This is a tooling follow-up, not something a refine worker may change.

I also observed the readable tree being rewritten concurrently during the run (files disappeared
and reappeared, e.g. `maybe_Ui_StoryTable_FindEntry_0063d434.c` -> renamed; the file count changed
between listings). Reads that failed transiently were retried by address suffix. This did not
affect the output, but the dispatcher should not run merges while refine workers are reading the
same tree.
