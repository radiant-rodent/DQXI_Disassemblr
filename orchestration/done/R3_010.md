# R3_010 — second naming pass (refine), 50 low-confidence `maybe_` functions

## What I did

- Read the batch `orchestration/naming/refine/batches/R3_010.txt`.
- The pre-baked dossier was **truncated to the first 10 functions** (`tools/fn.py` stopped
  mid-list at 0x003A06E8). I re-ran `python tools/make_dossiers.py R3_010`; the regenerated
  83 KB dossier covers all 50.
- Decided all 50 functions and wrote `orchestration/naming/refine/out/R3_010.json`
  (2 confirmed, 37 corrected, 11 kept_maybe; 15 at confidence >= 0.5).

### Key evidence used

1. **Type-table / vtable scan (the decisive new evidence).** Most of this batch are
   byte-identical deleting destructors (`Ui_Object_DtorBody(); operator delete();`), so the C
   body alone cannot name them. A scratch one-pass scan of the retail
   `original/exefs/code.decompressed.bin` data sections (scripts in `out/scratch/R3_010/`,
   no tree walks) found where each address is stored. The small engine type tables are
   0x28-byte records: slot 0 = non-deleting destructor, slot 1 = **this** deleting destructor,
   slots 2..6 = shared base methods, and **+0x1C = the class method**. That named:
   - 0x004D7350 `Field_ObjectSprite_DeletingDtor` (slot `Field_Object_DrawDescriptor`)
   - 0x004D79F8 `Field_AreaChange_DeletingDtor` (slot `Field_AreaChange_PlayTransitionAnim`)
   - 0x004A3B3C `Field_InteractJob_DeletingDtor` (slot `Field_InteractJob_Begin`)
   - 0x004AF40C `Field_MapObject2D_DeletingDtor` (slot `Field_MapObject2D_DispatchCommand`)
   - 0x0059B04C `Gfx_BgLayerMask_DeletingDtor` (slot `Gfx_ApplyBgLayerMask`)
   - 0x004E53B8 `Ui3D_SlotMaskPanel_DeletingDtor` (slot `Ui3D_ApplySlotMasks`)
   - 0x004FABB0 `Field_SceneObject_DeletingDtor` (slot `Field_SceneObject_UpdateComponents`)
   - 0x0017C320 `Ui_Object_DeletingDtor` (base vtable 0x7586EC, slot 0 = `Ui_Object_DtorBody`)
   and gave the correct subsystem/family for the rest.
2. **Split-symbol trap (confirmed on 6 functions).** Many "callers" in the dossiers are false:
   the call target is a local entry *inside* the symbol — 0x17C330 in 0x17C320, 0x18132C in
   0x18130C, 0x4D7150 in 0x4D713C, 0x28EFB4 in 0x28EFA4, 0x4AF56C in 0x4AF55C, 0x4C6E04 in
   0x4C6DF4. This explains why 0x17C320 appeared to have 51 callers (it is the base deleting
   destructor, not a per-class thunk).
3. **Named callers/callees** for the non-destructor half: `Ui_Panel_ResetTextState`,
   `Ui_Window_ReleaseChildLists`, `Ui_ListWindow_DispatchInput`, `Ui_MessageWindow_CloseAll`,
   `Ui_DiveForm_PollMessageEF`, `Ui_Window_PollPendingMessage(25)`, `Ui_Cursor_Ctor`,
   `Field_NpcObject_DeletingDtor`, `Battle_ActionModel_UpdateUnitVisibility`, etc.

### Main corrections

- `maybe_Ui_Object_DtorDeleteB` (0x0040E2CC) is an **Actor2D** deleting destructor with
  Actor_HandleRefEx + Pack_Handle sub-objects, not a UI object (disassembly calls 0x4AF56C,
  0x124154, 0x28EFB4 at computed offsets).
- `maybe_Actor_HandleRef_Dtor` → `Field_MapObject2D_DeletingDtor`.
- `maybe_Ui_SceneObject_Dtor*` → `Field_SceneObject_*` (wrong subsystem).
- `maybe_PartyPanel_InitFrame` / `FinishFrame` → `maybe_Ui_Panel_StartStep` / `FinishStep`:
  there is no party data; all work goes through the slot gauge.
- `maybe_Ui_TalkWindow_SelectRow` → `Ui_Panel_ShowOnlyRow`: shows exactly one of 8 row widgets,
  used by the attribute panel.
- `maybe_Field_Npc_FreeSubNode` / `DeleteShared` / `ApproachObj_Dtor` / `DeleteThunkSimple`
  were role words that hid the actual deleting-destructor shape; renamed accordingly.

## Open problems / not verified

- The remaining `maybe_..._DeletingDtor` entries (e.g. 0x4D7ABC, 0x4D7B3C, 0x4E5064,
  0x4E559C, 0x4E5B74, 0x4FAA14, 0x591AE0, 0x59F918, 0x5A60D0, 0x3A06E8, 0x3D9770) have a
  correct **family** from the +0x1C class method but no proven concrete class name; they
  intentionally keep `maybe_` at 0.45 or below.
- 0x004BF430: the data word before it (0x4BF4D4) is an internal label of the same function, so
  table 0x777778 is either a method vtable with this as slot 1 or a step table; kind 0x79 and
  the +0x125C countdown semantics are still unexplained.
- 0x001CAC74: battle state id 0x9A is opaque; only the player-actor-class branch is understood.
- 0x001CB3B0: the two model-parameter entries are timing/probability gated, but *what* the
  stored state selects (visual vs behaviour variant) is unknown.
- 0x004E7500: body is damaged decompilation (`extraout_r1`, `in_fpscr`); kept at 0.30.
- No emulator/runtime verification (name-only changes).
