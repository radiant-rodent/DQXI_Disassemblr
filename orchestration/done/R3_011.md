# R3_011 — second naming pass (refine)

**Status:** completed
**Owned output:** `orchestration/naming/refine/out/R3_011.json` (50 entries, every batch address covered exactly once)
**Also written:** `orchestration/done/R3_011.md`, append-only entry 303 in `AGENT_LOG.md`

## What I did

The previous worker on R3_011 had produced no output file and no report, so this was a fresh pass.
I read the pre-baked dossier `orchestration/naming/refine/dossiers/R3_011.md` in chunks, read the
full readable C for the entries whose dossier body was truncated, and checked the risky candidates
with `tools/fn.py` (`--asm`, `--max`), the surrounding `symbols.json` entries and the merged
naming outputs in `orchestration/naming/out/` + `refine/out/`. The 50-entry batch was not
regenerated. No `asm/`/`decomp/` tree walks were done: every disassembly check used the single
region file under `asm/text/` for that address range plus `tools/fn.py`.

**Verdicts:** 15 confirmed, 30 corrected, 5 kept_maybe; 22 entries at confidence >= 0.5.

## Main findings

The most important result: four entries are Ghidra mid-function splits, and their readable C is
either a recycled continuation or garbage. They are named as `...Tail` at confidence 0.25-0.30 so
they will not be merged as real routines:
