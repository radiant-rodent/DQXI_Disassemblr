# R3_013 — second naming pass (refine)

**Status:** completed
**Owned output:** `orchestration/naming/refine/out/R3_013.json` (50 entries, every batch address covered exactly once)
**Also written:** `orchestration/done/R3_013.md`, append-only entry 306 in `AGENT_LOG.md`

## What I did

Read the pre-baked dossier `orchestration/naming/refine/dossiers/R3_013.md` in chunks, then — because
the dossier alone could not name a single one of these functions — resolved the **class vtable** of
each entry from the disassembly. The batch was not regenerated. No `asm/`/`decomp/` tree walks were
done: the disassembly work was one pass over the `/* 0xADDR: HEX */` comments in `asm/text/text_*.s`
(~1.5 s, cached in `out/scratch/R3_013/`), the vtable dumps came from `asm/data` + `asm/rodata`, and
individual checks used `tools/fn.py` / `--asm`.

**Verdicts:** 2 confirmed, 46 corrected, 2 kept_maybe; 38 entries at confidence >= 0.5.

## The key method (worth reusing in later refine batches)

44 of the 50 entries are compiler-generated UI destructors whose class arrives in `r1`
(`*self = vtable`), so the body itself never names the class and the first pass could only guess from
the address region. Every one of them is entered through a 4-byte thunk:

```
0x003AA408:  ldr r1, [pc, #0x1c]     ; r1 = class vtable
0x003AA40C:  push {r4, lr}           ; <- the body in the batch
             str r1, [r0], #0x9c
             ...
```

Reading that literal gives the class vtable, and the vtable's **class-specific virtual** is already
named from string literals by earlier batches. Two vtable families appear here:

| family | layout | class-specific slot |
|---|---|---|
| `Ui_Widget` (26 slots) | `+0x00` D0, `+0x04` D1, `+0x08..+0x1C` base virtuals | **+0x20** |
| `Ui_Window` | `+0x00` 0, `+0x04` D0, `+0x08..+0x0C` base | **+0x10 / +0x14** |

So `0x003AA3E0` installs 0x00768510, whose `+0x20` is `Ui_NumberGridWindow_InitPanes` → the class is
`Ui_NumberGridWindow`. This resolved 45 of 50 addresses.

## Open problems / not verified

1. The class names behind the `Ui_Widget`-family slot `+0x20` are inherited from earlier batches
   (confidence 0.42–0.72) and were **not** re-derived here. If one of those is wrong, the destructor
   name that depends on it is wrong too. The weakest links used are
   `maybe_Ui_IconButton_InitPanes` (0.45) and `maybe_Ui_DigitDemo_Build` (0.42).
2. `func_0010F6CC` (the tail call that ends every "deleting" body) is inferred from six instructions:
   `if (p) { ctrl = p-8; obj = ctrl[0]; obj->vtable[1](obj, ctrl[1]); }`. I describe it as "releases the
   refcounted handle"; it may be a plain `operator delete` through a vtable. It has no readable file and
   no xref entry.
3. `Ui_LayoutRef_Release` returning its own argument is inferred from the destructor step pattern
   (`release(self+0x9C); release(x-0x50); base(x-0x4C)`), not from reading its tail.
4. `maybe_Ui_StatCompare_DeletingDtor` (0x0046E464) has a genuine naming conflict: the allocator
   `Ui_StatCompare_Create` (0x0046E438) loads vtable 0x00773178, but that vtable's class slots are
   `maybe_Ui_DigitDemo_Build` / `Ui_DigitDemo_ReadObjectRef`. One of the two families is misnamed.
5. `maybe_Sound_CloseObjectHandles` (0x00517E10) has no direct `bl` anywhere in `asm/text`, so the
   `Sound_Decoder_InitChannelTable` caller edge in `decomp/xref.json` is indirect or spurious.
6. No runtime/emulator test — this is a name-only change.
