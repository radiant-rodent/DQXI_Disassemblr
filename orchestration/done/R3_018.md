# R3_018 — refine pass on 50 low-confidence `maybe_` functions

## What I did
Second naming pass over `orchestration/naming/refine/batches/R3_018.txt` (50 addresses, context
scores 3–10). Read the readable C, the caller/callee dossiers and the disassembly where the C looked
suspicious, then wrote one decision per address to `orchestration/naming/refine/out/R3_018.json`.

Evidence highlights:
- **0x001A4D48** — the readable C is stale (one-line wrapper). The asm is a deleting destructor:
  unlink the nodes at +0x22C/+0x24C, `bl 0x0017C330`, `bl 0x00335DAC` (`Field_Object_DtorBase`),
  `b 0x0010F6CC` (the shared free thunk — not `operator delete`, see R3_022).
- **0x001CA378** — called once, as `Field_InitSceneObjects(... &battleWork->f_4218 ...)`, i.e. the battle
  RNG; the 6 words it copies contain 0x6C078965 and 0x5D588B65 (MT19937 init multipliers). It seeds an
  RNG state, it is not a colour.
- **0x002E5294** — the sibling `Gfx_EntryPool_Clear` (0x002E6428, caller `Field_DestroyScene`) frees the
  same 16 x 0x34 entries through the +0x18 occupancy bitmask; all three callers are field-scene code.
- **0x002BF52C** — installs `g_actorActionCurveMove2Vtable`, opcode 4; "Jump2" claimed a jump the code
  does not show.

## Problems found (worth fixing upstream)
1. **Empty pre-baked dossier**: `orchestration/naming/refine/dossiers/R3_018.md` contains
   "no readable file found" for all 50 functions (it was generated while `decomp/readable` was being
   regenerated). I rebuilt the same view into `out/scratch/R3_018/` with `tools/fn.py`. Regenerating
   the dossier would fix it (I did not overwrite the shared file).
2. **Wrong readable bodies**: at least two batch addresses have another function's C attached
   (0x001A4D48, 0x0024039C). `tools/fn.py`'s `CALLEES` list is correct for 0x001A4D48 while its body is
   not, so a worker that trusts the body alone will name these functions wrongly. A consistency check
   (first `bl` target in the C vs the asm) in `tools/fn.py` would catch it.
3. **`0x0039CBBC` is named `Text_LayoutSingleLine` (0.5+)** yet is called by four camera/vector helpers
   with `(record, float* from, mode)`. Either that name is wrong or the call graph attribution is; my
   batch entry 0x001D5098 documents the contradiction. Follow-up: re-examine 0x0039CBBC / 0x0039CD34.
4. **`0x001CFFCC`**: has ac:u session callees (`Svc_AcClient_CheckSession`,
   `maybe_Svc_AcClient_GetAccountState`) but only the two `Fs_FileJob_Update*` callers. One of the two
   side names is wrong; a job in the R2/R3 Fs lane should settle it.
