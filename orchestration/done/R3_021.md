# R3_021 - refine naming pass (50 low-confidence `maybe_` functions)

## What I did

Re-examined all 50 functions of `orchestration/naming/refine/batches/R3_021.txt`, starting from
the pre-baked dossier `orchestration/naming/refine/dossiers/R3_021.md` and the previous name /
confidence / evidence in each readable file. The whole batch turned out to be UI destructor
thunks, so the decisive question for every entry was *which class table owns the entry*.

To answer that I parsed the `.word` dumps in `asm/rodata/*.s` and `asm/data/*.s` into an
address -> word map (161,231 words) and looked up every slot that holds one of the batch
addresses, plus the slots in a +/-0x40 window (this also catches vtable entries that point at the
vtable-load instruction immediately before a recovered entry). That is targeted reading of seven
dumped files, not a walk of `asm/`, `decomp/` or `include/`. The class of each UI table is then
read off its `InitPanes`/`Init` slot (`+0x1C` in single-dtor tables, `+0x20` in two-dtor tables);
`tools/fn.py` was used to confirm the owning initialiser/constructor names and, for the unusual
bodies, `--asm 16`-`30`.

Every address got an entry, written in batch order:

- **11 confirmed** (name kept, `maybe_` dropped, confidence 0.50-0.55)
- **29 corrected** (the first guess named the wrong class/subsystem)
- **10 kept_maybe** (honest `maybe_`, confidence 0.30-0.48)
- **40 at confidence >= 0.5**

## Problems / notes

1. **The vtable evidence had to be reconstructed by hand** for this batch: `fn.py` reports
   `vtable=None` for all 50, and `scores.jsonl` has no vtable either, because the harness only
   attributes tables through Ghidra's vftable symbols. Parsing the seven `.s` dumps was enough and
   is fast, but a `tools/vtable.py` helper would make future destructor batches much cheaper.
2. **Many batch addresses are 4-8 bytes inside the real function**: the rodata slot points at the
   vtable-load instruction(s) that Ghidra left outside the recovered body (examples: 0x296E88 ->
   batch 0x296E8C; 0x29D5B8 -> 0x29D5BC; 0x2B1A80 -> 0x2B1A84; 0x39326C -> 0x393270;
   0x393340 -> 0x393344; 0x3E5FBC -> 0x3E5FC0; 0x403DD4 -> 0x403DD8; 0x446FFC -> 0x447000;
   0x4659DC -> 0x4659E0; 0x478364 -> 0x478368; 0x4CE974 -> 0x4CE978; 0x4CF3B8 -> 0x4CF3BC;
   0x4CF404 -> 0x4CF408; 0x4E3F98 -> 0x4E3FA0). The names describe the real function; the merge
   step should preferably fold these duplicates into their true entry points.
3. `0x001A6520` is still the garbage seed symbol `drN` (273 callers; it is the shared
   "bind parts" vtable slot). Several summaries call it "the shared Ui bind helper drN" because
   naming it was outside this batch.
4. The class stems for 0x003E9FE0 (`TxtLWindow`), 0x00479B94 (`CommandList`), 0x004AAD04 /
   0x004CF860 / 0x004DCF44 (`TextPaneWindow` variants), 0x004CEA98 (`RouletteWheel`) and
   0x004CEC4C (`ValuePanel`) come from *maybe_* initialiser names. The vtable link is solid, the
   wording of the class is not, hence 0.50 and an explicit note in each entry.
