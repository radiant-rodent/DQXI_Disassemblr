# R3_024 — refine naming batch (50 low-confidence `maybe_` functions)

Status: **completed**. Output: `orchestration/naming/refine/out/R3_024.json` (50 entries, one per
batch address).

## What I did

Decided every address in `orchestration/naming/refine/batches/R3_024.txt` from the pre-baked dossier
(`orchestration/naming/refine/dossiers/R3_024.md`), the readable C headers/bodies, and targeted
`tools/fn.py` / single-file `asm/text/text_*0048.s` reads where the dossier disagreed with itself.
No `asm/`, `decomp/` or `include/` tree walks; the batch was not regenerated.

Result: **13 confirmed, 16 corrected, 21 kept_maybe** (22 entries at confidence >= 0.5, all of them
without the `maybe_` prefix; 28 entries below 0.5 keep it).

Notable decisions:

* **0x00311450 `Shop_SellItem` (corrected, 0.65)** — the old `Shop_BuyItemToBag` had the transaction
  direction backwards. The named twin `Shop_BuyItemForMember` (0x0031120C) passes `-price*count` to
  the ItemBag gold helper 0x00613FC0; this function passes `+record[+0x1C]*count` (the sell-price
  field, not the buy price +0x18) and removes units via `Member_RemoveItemAtSlot` / 0x006115BC.
* **0x002C6A0C / 0x002C6A64 `Ui_TextListWidget_BaseDtorDelete` / `Ui_TextListWidget_BaseDtor`
  (corrected, 0.55)** — `Ui_TextListWidget_DtorDelete` (0x00478C34) begins with `bl 0x2C6A60`; the
  real entry is 0x2C6A60 (loads table 0x007601A8) and Ghidra split it at 0x2C6A64, the batch
  address. 0x2C6A0C is the same body ending in `b free`, i.e. the deleting variant. Old
  `Ui_Screen_SubObjectsDtor` / `Gfx_SceneObject_Dtor` were guesses.
* **0x00419EC8 / 0x00419F44 confirmed (0.55 / 0.50)** — the named `Ui_SenrekiWindow_DtorBody`
  (0x00296E8C) destroys them with `Ui_AdventureLogWindow_Dtor` and `Ui_QuestWindow_Dtor`, the tabs
  of the records/history window, which supports the monster-book entry class.
* **0x004E5394 `Ui3D_ConstructListElement` confirmed (0.50)** — installs type table 0x0077B140,
  the same table as the named `Ui3D_SlotMaskPanel_DeletingDtor`, and the named factory callers
  allocate 0x50 bytes and insert the object into the keyed tree.
* **Factory ctors renamed to `maybe_Field_Object_Ctor_vtXXXX` (0.40)** — 0x003A06A4 (0x007673DC),
  0x004AF5B0 (0x0077635C), 0x004D7A88 (0x00779F44), 0x004EFDC0 (0x0077C298) are all
  allocate + vtable + sentinel constructors called by `Field_Scene_UpdateObjectsFromTable`; their
  old class names were invented, so the vtable is the honest discriminator.
* **0x0036A494 `Ui_GuideWindow_CommitPendingPage` (corrected, 0.55)** — binds the stored page pane,
  marks the message window dirty and calls its layout vfunc; nothing is pushed onto a stack.
* **0x003205BC `Battle_ActionSequence_AnnounceAction` (corrected, 0.50)** and
  **0x002C8BEC `Ui_Screen_CommitPendingControl` (corrected, 0.50)** — the names now describe both
  branches/steps rather than one instruction.
* **0x0031AD20 `Field2D_TestAreaPassable` (corrected, 0.50)** — callers are the named `Actor2D*`
  movement functions and the callees are map/field predicates; it was not UI hit testing.

## Open problems / not verified

* Name-only change: no emulator or runtime test was performed.
* The class behind the `0x002BB758` / `0x002BB77C` handle-pair sub-object destructor trampolines is
  still unknown (kept `maybe_`).
* 0x0062923C returns bit 1 of a small character-table row; which game property that bit encodes is
  still unknown (the table is not the 0x434-stride `CharacterRecord`).
* 0x003AAB10 (`+0x2767D` flag) and 0x0063AF80 (row virtual +0x20/+0x24 protocol) stay unproven.
* The 0xF/0x10 attributes and the `cell+0x1C` short that choose the layer in 0x002D80F8 are still
  unexplained, so both direction helpers stay `maybe_`.
* Several callees referenced by these bodies (`0x0063F8F0`, `0x00613FC0`, `0x006115BC`,
  `0x00588D08`, `0x0029126C`) are mid-function split symbols, not real entries; `fn.py` reports
  them as if they were callees.
