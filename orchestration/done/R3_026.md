### Disassembly beat the readable C

- `0x00525494` is 0x44 bytes, not 632 (Ghidra merged the next routine at 0x005254D8). It is a pure
  boolean guard around 0x00505FD8 → `Gfx_TryConvertBuffer`.
- `0x0064E054` is 0x28 bytes, not 520, and is exactly `cursor == Party_GetActiveMemberCount` →
  confirmed as `Ui_List_IsCursorAtPartyEndRow`.
- `0x00634C3C` is 0x60 bytes and returns `[0x007A724C] * (mode ? record+8 : 7.0f)`; the sibling
  0x00634D74 uses `+4` and `1.75f`.
- `0x0051A6C4` is the 3DS IPC pattern (`mrc p15` TLS read, TLS+0x80 command buffer,
  `svc 0x32` = `svcSendSyncRequest`) → `Os_Ipc_SendRequestA0040`.

### Merged-symbol trap on 0x0063ECF0

The xref lists 155 callers, but the asm shows a **second entry point at 0x0063EEAC** (right after
the `bx lr` at 0x0063EEA8) that reads `[r3,#0x2EC]` and is the real `bl` target. Ghidra folded two
routines into one 1856-byte symbol, so the caller count neither supports nor contradicts the
recipe reading. The 0x0063ECF0 entry itself does walk a 0x10-byte row of u16 material ids through
`Item_GetStoragePointer`, so the name stays `maybe_Item_IsRecipeCraftable` at 0.45.

The same mid-function-label pattern was found for `0x0063F93C` (inside 0x0063F6D4),
`0x0066B534` (inside 0x0066B264), `0x0066AF08` (inside 0x0066AE3C) and `0x0063A794` (inside
0x0063A764). That is why the four `DataTable_*` accessors and the two `ItemBag_*` counters could
not be lifted above 0.4.

## Open problems

- **`decomp/readable/functions/` was being rewritten during this run.** The directory mtime moved
  and the file count went 17971 → 17994 while I worked, so `tools/fn.py` intermittently reported
  `no readable file found` for addresses that do exist. Retrying after ~45 s fixed it. Any worker
  that sees this should retry rather than conclude the file is missing.
- **Unresolved contradiction:** `0x0062D6D8` is named `Camera_FindEntryCoveringPosition` (0.50),
  yet two of its five callers are NPC-move routines (`Field_NpcUpdateMoveState`,
  `Field_NpcAction_Move`). Either that name or the two NPC names is wrong; both entries in this
  batch (`0x0062DDF0`, `0x0062DF2C`) stay `maybe_`.
- **Callee names from other subsystems** made several entries undecidable: `0x0062564C` calls
  `Craft_BuildIngredientOwnershipList` / `Ui_SmithMenu_OpenPage` / `Ui_SmithMenu_GetRecipeAttrBitmask`,
  `0x00646BB4` calls `SkillPanel_CanUnlockSkill`, `0x00634114` calls `Ui_Overlay_HasReachedTarget` /
  `Ui_HitTestRows` / `Ui_HitTest_FindCell`. Those callee names look wrong for their call sites and
  should be re-examined in a misname sweep.
- **No callers at all** for `0x0059F36C`, `0x0062564C`, `0x006713D4`, `0x0063AB0C`, `0x0063B590`,
  `0x00648BEC`, `0x0064DFF0`, `0x00647F90`, `0x00647FD0`, `0x00648008`, `0x00648048` — their class
  can only be inferred from siblings.
