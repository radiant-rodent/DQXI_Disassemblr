# R3_027 — refine naming batch R3_027

**Status:** completed. 50/50 addresses decided, `python tools/check_refine.py R3_027` → `R3_027: OK`.

## What I did

Read the pre-baked dossier `orchestration/naming/refine/dossiers/R3_027.md` in four chunks (12/12/13/13
functions), decided each function from its readable C plus named callees, string literals and vtable
slots, and appended the entries to `orchestration/naming/refine/out/R3_027.json` after every chunk.
Live `tools/fn.py` was used on ~20 addresses; no `asm/` or `decomp/` tree walk was done.

Two small scratch helpers (in `out/scratch/R3_027/`) read `build/code.bin` directly
(vaddr − 0x100000) to dump string literals and vtable slots, and to resolve vtable entries to current
symbol names. That is what produced the strongest evidence in this batch.

The 41 keeps are mostly the generic deleting-destructor family (vtable install + base dtor + free,

## Important finding for other workers: the dossier CALLERS lists are unreliable

Two independent checks by disassembly:

- `0x003CDEB4` is listed with 27 battle callers, but `Battle_Update` (0x0016E3E0) contains no `bl` to
  it; and `0x0020002C` (`Ui_Screen_CtorBase`) appears both as its caller and as its callee.
- `0x00592298` lists `0x001D718C` as a caller, but that function contains no `bl` to it either.

Every decision here was therefore based on the body, named callees, string literals and vtable slots,
never on the caller list alone. Other refine workers reading the same dossiers should do the same.

## A near-miss worth recording

I first confirmed `0x0029CFAC` as a DiveWindow virtual because vtable 0x0075E1B0 slot 0x50 holds
`0x0029CFA8`, four bytes before it. Decoding that word (`0xEAFC25EE`) shows `b 0x001D6768`, not a
fall-through into `0x0029CFAC`. The entry was downgraded to `kept_maybe` 0.45 with corrected evidence.
A vtable slot entry can be a thunk to a different address — check the branch, not the adjacency.
