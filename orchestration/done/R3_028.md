# R3_028 - refine naming batch R3_028

**Status:** completed. 50/50 addresses decided, `python tools/check_refine.py R3_028` -> `R3_028: OK`.

## What I did

Read the pre-baked dossier `orchestration/naming/refine/dossiers/R3_028.md` in four chunks, decided
each function from its readable C plus now-named callers/callees, vtable slots and (where the C was
ambiguous) the disassembly, and wrote all entries to `orchestration/naming/refine/out/R3_028.json`.

Live `tools/fn.py` was used on ~25 addresses. Two targeted asm reads (`--asm`) decided the two
"close window" functions. `decomp/functions_index.json` (18,787 rows) was used to list the named
functions within +/-0x500 of an address - the cheapest way to find a ctor/dtor partner or a class
family without walking `decomp/` or `asm/`. Eight addresses live only in
`decomp/readable/recovered/`, which `tools/fn.py` does not glob, so I read those files directly.

The batch was not regenerated and no whole-tree search was done. Full `tests/run_all.py` /
`tools/verify_project.py` were intentionally not run (naming batch: WORKER_RULES rule 5 does not
apply).

## Open problems

- `tools/fn.py` does not glob `decomp/readable/recovered/`, so 8 of 50 addresses showed "no readable
  file found" in the dossier and live. It also intermittently fails for `decomp/readable/functions/`
  while that tree is being regenerated (retry after a minute works). Suggested fix: glob both
  directories in `load_names()`.
- `*_vtXXXXXX` names can encode the literal-pool address rather than the vtable (0x0046CB9C).
  Worth a sweep for names whose hex equals the function's own address or its +0x1C.
