## Things worth knowing (for the dispatcher / next workers)

1. **The dossier's CALLERS/CALLEES lists are not reliable.** Twice the decisive address was absent
   from the real code: 0x003CE3D8's claimed callers (e.g. `Ui_PartyStatus_AdjustValue`) contain no
   reference to it in `asm/text/text_001C0048.s`, and 0x0064BFC8's eight "unrelated" callers
   (Text_DrawToken, Gfx_SpriteObject_*, Gfx_Scene_RaycastToWorldPoint...) do not call it either.
   The real callers (five `Casino_Slot_BuildSpinResult` calls, visible in that function's body)
   prove the casino reading. Treat >5 cross-subsystem callers as a red flag and check one `bl`
   in the caller's own `asm/text` region file before believing it.
2. **`tools/fn.py` cannot read `decomp/readable/recovered/`** (same as R3_026/R3_028/R3_032/R3_033/
   R3_034): 0x003F30EC prints "no readable file found" although
   `decomp/readable/recovered/maybe_Save_LoadTask_Finish_003f30ec.c` exists. `fn.py` should glob
   `readable/recovered` too.
3. **`Ui_Overlay_IsRectLargerThanScreen`'s old '~314' height threshold was a misread.** The C's
   integer form `0x43A00000 + -0x300000` is 0x43700000 = 240.0f, i.e. the 3DS screen height; the
   test is exactly "rect wider than 320 or taller than 240".
4. **The `Ui_Overlay_ReleaseHandle` callee is a handle-table release, not a UI call.**
   `0x001C7570` resolves a tagged handle through the 0x007B80C0 table, calls the object's virtual
   +0x10 and re-links its list node with the 0x001235A4 splice helper; the manager passed by the
   caller is `(work+8)->f_54` (Field_ObjectManager). So the object being released is a field object
   owned by the UI panel.

- **0x004D2AE0 / 0x004DEA54** share the field-party base-teardown prefix; the 0x58-byte x16 array at

  FieldParty layout would settle both destructors.
- **0x003F30EC** (recovered address, no readable C, no caller, four unnamed callees) cannot be
  named from the current evidence; it may be a vtable slot of a UI task object. Needs a vtable pass.
- **0x0051BDEC**: the err:f reading rests on FACTS.md's range; the exact two status bits and the
  two state hooks (0x00113A40(3), 0x001143C8(0)) are still unidentified. If another worker names
  0x0051C060 as an err:f query rather than `Sound_GetStatus`, the whole cluster should be renamed
  together.
