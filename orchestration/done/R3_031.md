## Open problems

1. **Dossier CALLERS are mostly mid-function split labels, not callers of the listed address.**
   Verified examples: `Ui_SceneEntry_Add` calls 0x002B7BE8 (range starts 0x002B7B58);
   `Battle_UiFlow_NotifyMenuUpdate` calls 0x0020C294 (not 0x0020C198); the jackpot handlers enter
   0x0030D66C; `Ui_LoadScreen_State39Or34` / `Cutscene_AdvanceTimeline` never reference 0x0018F6D4;
   0x004A1DEC is 0x14 before the real callee 0x004A1E00. A caller must be checked in the caller's
   own readable C before being used as evidence; `tools/xref.py` (or the function index behind it)
   should stop attributing a `bl` into the middle of a range to the range start.
2. **`tools/fn.py` cannot see `decomp/readable/recovered/`.** 0x001E9160, 0x003B1330 and 0x003B7640
   print "no readable file found" although their files exist (same complaint as R3_024..R3_038).
   Also, multi-address `--asm` runs intermittently reported "no readable file found" for files that
   a single-address run found immediately; re-running worked.
3. **Many bodies are truncated at `std_ConstructArray` because it is mis-marked `noreturn`.** The
   array-constructor call is the *first* statement in most of this batch; everything after it is
   dropped. Fixing the `noreturn` marking (or making the decompiler continue after it) would
   recover real bodies for ~20 functions here in one sweep.
4. **`Ui_MessageWindow_InitRenderParams` (0x002AFA88) is very likely misnamed.** It builds one
   0x8C-byte row record, and 0x003B1330 uses it to copy 0x35 rows from the save-work table; that is
   also why 0x002AFC5C was corrected to `maybe_Ui_RowRecord_Ctor`. Its owner batch should revisit it.
5. **0x00509100 and 0x005096C8 are reported to be 0x10 bytes inside their real entries**
   (0x005090F0 / 0x005096B8). The 0x005096C8 disassembly, however, starts with a clean
   `push {r4,lr}`; the boundary claim needs a re-check before those keys are used for patching.
