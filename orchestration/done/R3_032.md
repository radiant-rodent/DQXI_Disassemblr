## Findings that changed verdicts

### 1. The pre-baked dossier was empty

`dossiers/R3_032.md` was 7.6 KB and said *"no readable file found"* for all 50
addresses — it was generated at 17:20 while `decomp/readable/` was being rewritten.
`python tools/make_dossiers.py R3_032` produced the real 78 KB / 1354-line dossier.

The tree kept moving during the run: file count went 17977 -> 17994, the directory
mtime moved at 17:22 and 17:24, and 26 of my 50 batch paths briefly disappeared
before settling. Worth having the dispatcher wait for the readable tree to be stable
before baking dossiers.

`tools/fn.py` also cannot see `decomp/readable/recovered/`, so the seven
recovered-file addresses (0x0010D40C, 0x0016068C, 0x00160EB4, 0x00160F14,
0x00161918, 0x00162A98, 0x00166CA8) print "no readable file found" in both the
dossier and the live tool. I read those files directly.

### 2. `std_ConstructArray` truncated eleven bodies

`0x00100050` is mis-marked `noreturn` (already in FACTS.md), so the readable C of
0x005D6588, 0x00622C9C, 0x00652F48, 0x006539A8, 0x00678B54, 0x00680780, 0x00686C18,
0x0069A090, 0x006A1E50 and 0x006A5280 stops at that call. Reading the disassembly
changed four verdicts outright.

### 3. `0x006F56F4` is a bare `bx lr` stub, not a box test

The first pass recorded *"the real box test at 0x006F56F4 (which is the tail the
decompiler lost)"* for both 0x00652F48 and 0x006539A8. It is only the no-op element
constructor passed to `std_ConstructArray(sp+0x30, 0x006F56F4, 8, 4)`; the
four-corner box is built and tested inside the function itself. Both corrected to
`maybe_Field_TestAreaOverlapA/B` — the named caller `Field_Marker_TestOverlap`
(0.60) fixes the vocabulary, and the `Field_Gimmick_` prefix was unsupported (the
callers are Marker and Placement code).

### 4. The six `Container_*` static initialisers were not containers

- `0x00686C18` initialises the monitor at `0x007E793C` — exactly the one
  `maybe_Os_InsertListNodeByKey` (0x0010CCB0) locks before walking the ordered list
  at `0x007AE954` -> `maybe_Os_InitListRegistry`.
- `0x006A5280` ends in `b #0x54FADC` = the named `Sound_SeqPlayer_InitVoiceMap`
  -> `maybe_Sound_SeqPlayer_InitTables`.
- The other four (0x00678B54, 0x0069A090, 0x006A1E50, 0x00680780) have no caller and
  an unknown element type, so they became `maybe_StaticInit_*` with the global
  address in the name and stayed at 0.35. Their tail calls all land on `bx lr` stubs
  (0x00672404, 0x00509A18, 0x00509AE4, 0x00146AF4) — no-op static-destructor
  registrations, i.e. C++ global constructors.

## Suggested follow-up

1. **Fix `tools/fn.py`** to glob `decomp/readable/recovered/` as well, and have
   `make_dossiers.py` retry when a batch resolves to zero readable files. Two
   consecutive batches (R3_026, R3_032) shipped an empty dossier.
2. **Sweep for the `std_ConstructArray` truncation.** Any readable body whose last
   statement is `std_ConstructArray(...)` is cut short. A one-line check over
   `decomp/readable/functions/*.c` would list them all; several first-pass names
   were built on the missing tail.
3. **Re-examine the `bx lr` stub addresses** (0x00672404, 0x00509A18, 0x00509AE4,
   0x00146AF4, 0x006F56F4, 0x005052A4, 0x00509B1C). They are trivial constructors
   and destructors, and naming them `std_NoOpCtor` / `std_NoOpDtor` would stop the
   next worker from reading them as real callees.
4. **`0x00782234` is a 51-function base vtable** — worth one dedicated pass to name
   the base class, since it would fix the prefix of a large family at once.
5. **`maybe_Field_TestAreaOverlapA/B`** need a caller-side pass: the three
   `maybe_Field_Placement_TestAreaA/B/C` callers are still unnamed and would settle
   which is the box and which the zone test.
