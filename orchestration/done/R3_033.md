## What was done

Read the batch, then decided each function from its readable C plus its now-named neighbours
(`tools/fn.py` on ~30 addresses, ~8 single-address reads of `asm/text/*.s` where the decompiled body
was truncated or damaged). Decisions were written in five chunks of ten.

### Blocking issue found and worked around

The pre-baked dossier `orchestration/naming/refine/dossiers/R3_033.md` was **empty**: 7.7 KB for 50
functions, every block saying `no readable file found`. `tools/fn.py` works when run directly, so the
dossier was generated while `decomp/readable/functions/` was mid-rewrite -- I also caught the tree
transiently at 2,072 files instead of 17,994 while other R3 workers were running. I regenerated the
same content into `out/scratch/R3_033/dossier.md` (90 KB) instead of overwriting the shared dossier
file.

### Substantive findings

1. **0x001F0B80 is the formatted-message argument slot pool destructor**, not a "message window pane
   pool". FACTS.md fixes `*0x007AC834` as the argument buffer with 0x108-byte slots
   (`Message_FormatArgSlot_Reset`, 0.70); this destructor clears exactly that global and destroys 16
   elements of 0x108 bytes -> `Message_FormatArgSlotPool_DtorDelete` at 0.60. Its 16
   "Menu_OpenMessageDialog*" callers in the xref are callers of the mid-function split symbol
   0x001F0BE4, not of this function.
2. **The five "Container_Node_Dtor*" copies were not container nodes.** 0x0046B5C0, 0x0046BDEC,
   0x00591378 and 0x00591918 are byte-identical to the already-named 0x002E4488 / 0x002E4BD4
   (vtable install, unlink the intrusive list at +0x48/+0x4C, destroy the list at +4, pool free); the
   object only unlinks a list stored *inside* itself. They became
   `maybe_Ui_Object_DtorStringListD..G`. 0x004A37B8 lost its `Ui_ActorWidget` prefix the same way --
   its neighbour 0x004A37E8 is now the Field_HandleRef deleting destructor (vtable 0x00775534).
3. **Three "random" helpers had been read as deterministic.** 0x005F9650 is now the confident
   `Math_WeightedRandomIndexDefaultRng` (0.55), so 0x0018DE24 is not "hashes the first four u16" but a
   weighted pick (`maybe_Ui_PickWeightedKeyValue`); 0x004AE12C uses the *game* RNG at work+0x98, not
   the battle RNG (`maybe_Ui_PickWeightedEntryValue`, `Battle_` dropped); 0x0018E3D0's
   400/200/150/100/50/40/10 are weights for an index pick, not sizes
   (`maybe_Ui_PickWeightedStepIndex`).
4. **Two "register actors" functions had invented table kinds.** 0x00180B94 / 0x001835AC / 0x00184958
   all resolve relative name pointers through 0x0033D99C, which the disassembly shows is a
   red-black-tree map lookup (tree at obj+0x1E8, key at node+0x14), and register the result with
   `Ui_RegisterActor`. Nothing says "animation" or "rail" -> `maybe_Field_RegisterNamedActorsA/B/C`.
5. **Best confirmations.** `Member_SetItemAtSlot` (0x00191DE4) and `Member_SwapInventorySlots`
   (0x00191F70) at 0.65 -- FACTS.md fixes the 24 u16 inventory at member+0xEC and `func_006292A4` as
   the equipped test, and 13 named inventory callers agree. `Ui_Panel_SetState7` (0x00194F00) at 0.50 --
   its twin 0x001950B0 is already `Ui_Panel_SetState7B` at 0.50 with the same body and the same literal
   7, and `scores.jsonl` puts both in vtable 0x0062F680. That also fixed 0x002C2344, which is the same
   template with state 5 (`Ui_Panel_SetState5`, not "DateDisplay_OnReady").
6. **0x00174674 was the opposite of its name.** "ClearTargets" actually *fills* the caller's 8-slot
   selection array: the disassembly shows `strne r5, [r4, r8, lsl #2]` writing the collected units into
   slots 1..4, then `Battle_CalcTurnOrderPriority` per slot and `Battle_CommandQueue_PushEntry` with
   event ids 0x11/0x12/0x13/0x32 -> `maybe_Battle_CollectActionTargets`.

## Open problems / not verified

- No emulator or runtime test -- this is a name-only change.
- The classes behind the ten destructors in this batch are still unidentified, as are vtable
  0x00759FAC and the pool tables 0x007B4D68 / 0x007B5D70. The letter suffixes (A..G) are bookkeeping
  only; the summaries now state the exact field offsets so a later pass can match them to a class.
- 0x00193098: the 0x44-byte records at +0x92F4 are still unknown in content; the shift count is
  recovered as the nonsense literal 0x78787879 and `wcslen` (0x00100B74) is mis-marked noreturn.
- 0x0019EAA8: the "balloon" variant word is unproven -- nothing identifies the widget at +0x84.
- 0x00237034: what overlay entry states 2 and 3 mean is still an interpretation.
- 0x001A2FB4: the owner argument is recovered from `in_s0` (hard-float trap) and two of its three
  callers still carry garbage symbol names (`tEb`, `LFb`).

## Suggested follow-up tasks

   R3_034) print "no readable file found" for functions that do have readable C.
2. **Make the dispatcher sanity-check dossier size** before starting a refine worker: a dossier under

   `tools/make_dossiers.py` would have saved this worker a full regeneration step.
3. **Fix the xref attribution for short functions.** `decomp/xref.json` credits 0x0046B5C0 with callees
   of the next function at 0x0046B610, and 0x001F0B80 with callers of the mid-function split symbol
   0x001F0BE4. Both are cheap to detect (callee address outside the function's own byte range).
4. **A dedicated "pooled destructor class identification" batch**: the ten destructors here share a
   small number of templates. Matching each template's vtable constant and pool table against the
   constructors that install them would resolve all of them at once.
5. **Rename the garbage symbols `tEb` (0x00624688) and `LFb` (0x006247B0)** -- they are callers of
   0x001A2FB4 and currently unreadable.
