## Findings worth carrying forward

### The "ReleaseSpan"/"ReleasePart" bodies were the *next* function, not these functions

`0x002188E0` and `0x00219BB4` are 24 bytes each. The readable C printed for them continues into the
next symbol, so the previous summaries described the neighbour (`maybe_Actor2D_ResetIfRegistered`
at 0x002188F8 and `Actor2D_ResetPartsIfIdle` at 0x00219BCC). The real bodies are:

```
bl 0x005E78E4   ; Field_SceneObject_Show
mov r0,r4
pop {r4,lr}     ; return self
```

They are now `Field_SceneObject_ShowOverrideA/B` (0.5). Same trap as R3_047/R3_050 but here the
merged body looked entirely plausible, which is why the first pass believed it.

### `0x0020B504` computes the active party's average level

The disassembly is the ground truth: `s16=s17=0.0f`, for every active member `s17 += 1.0f` and
`s16 += (float)member+0xD8`, then `vdiv s0,s16,s17`. Ghidra dropped the `float` return (s0), so the
body looked like a no-op update. Renamed `Party_CalcAverageLevel` (0.65); its caller
`BattleScene_SpawnMonstersByProgress` uses the value to scale spawns.

### `0x0020B064` is a battle counter pass

The callee `0x00612A94` is `base + id*4 + 0x3AE4`, incremented only while below the literal
`0x0001869F` (99999). The caller walks the four battle unit rings at `battleWork+0x4298..+0x42EC`
(FACTS.md) and applies it to every live unit with none of the `0x46` flags set. Renamed
`maybe_Battle_IncrementUnitCounters` (0.42); the old `Field_RefreshActorSlots` name had the wrong
subsystem and described no effect.

### Battle action-list row constructors recovered from the inline labels

`Ui_ActionListWindow_Init` (0x0032CD24) builds eight rows and passes each row's 4-byte label as the
fourth argument. Reading `build/code.bin` at `vaddr-0x00100000` gives
`nut`, `run`, `atk`, `dmg`, `protect`, `break`, `dead`, `end` at 0x0032D130..0x0032D260.
Rows 4/5 already carry `Battle_Action_Protect_Ctor` / `Battle_Action_Break_Ctor`, so the four tiny
vtable wrappers are now `Battle_Action_TextRow_Ctor` (nut/end), `_RunRow_Ctor`, `_AttackRow_Ctor`
and `_DamageRow_Ctor` (0.50 each; the readable signature hides the five call arguments).

### Other corrections worth knowing

* `0x002BDE74` writes `0xFF` at `work+0x24A98+0x5A4E+id` — the shared pastword/quest id block — so
  `ClearFlagByte` became `maybe_Field_SceneObject_ClearQuestStateByte`. The lookup base in the
  literal pool is only `0x34A`, so that branch may be dead.
* `0x001EB368` releases the *message* window's variant widget (`self->f_84` from
  `maybe_Ui_MessageWindow_CloseWithBalloon`), not a shop-window object.
* `0x003B7B70` installs vtable `0x00768D7C`, the same one used by the named
  `maybe_Ui_SoulWindow_Subwidget_Ctor` (0x003B7640).
* `0x0047A510` is the slot immediately before the confident `Ui_ChoiceSelectWindow_LayoutRows`
  (0x0047A5B0) and only toggles five panes plus `Ui_List_SelectEntryById`.
* `0x006D8698` is a generic `Ui_PaneStack_Pop`; the named `Ui_TalkMenuWindow_RebuildContent` calls it
  as "pop the sliding pane at +0x124".
* `0x001F71A0` returns 0/1 without writing anything, so "Select" became `CanSelect`.
* `0x0022C344` really touches +0x2EC/+0x2F0 with the value of the zero-initialised global
  `0x007A3F6C` (the old summary's +0xBB0/+0xBC0 was wrong).
* `0x0022CAE8` builds a `Gfx_Trail_ResetSamples` sample, not a "move command".
