## Method notes worth passing on

1. **The dossier was empty.** `tools/make_dossiers.py` produced a 7.7 KB file with 50 ×
   "no readable file found" although every path in the batch exists. Re-running it produced the
   correct 87 KB file in 0.8 s. `make_dossiers.py` should check its output size and retry — this is
   the second dossier defect in a row (R3_036 was truncated at 31/50).
2. **`tools/fn.py` still cannot see `decomp/readable/recovered/`.** Four of my 50 (0x002C244C,
   0x00316B64, 0x00317088, 0x00316D00) print "no readable file found" although their files exist.
   I read them directly. This is the ninth batch reporting it.
3. **`scores.jsonl` reports `vtable=None` for all 50 addresses, but 30 of them are in a vtable.**
   Dumping the surrounding `.word` run from `asm/data`/`asm/rodata` settled the class of most of them
   in one pass and produced the best corrections in this batch. `make_refine_batches.py` should fill
   `vtable`/`vtable_siblings`, or `fn.py` should print the containing table — it is the cheapest
   context available for this lane.
4. **`Battle_CreateEnemyDisplay` (0x0046E50C, 0.50) is probably misnamed.** Its callers are three
   *field* functions plus `Ui3D_UpdateAttackSequence`, and its callees mix
   `Battle_SetupUnitFromMonsterData` with `Snd_RequestEncounterSound`, `Camera_SetTargetFromHandle`
   and `Gfx_SetBottomScreenRect`. It looks like a generic "build a 3D display object from a
   descriptor". That is why the three template copies above are named after the deferred start/poll
   rather than after the display.
5. **`Font_Atlas_GetGlyphCellByte` (0x00664A80) is certainly the wrong family.** `Map_IsCellPassable`
   calls it with a map cell and compares the result against terrain id 9, so it is a map/mode lookup.
   That poisons 0x005A3604 and 0x002D78C0 here; both were renamed to `maybe_GameMode_*` and kept
   below 0.5 because the accepted values (3/7/8/0xFF) are still unexplained.
