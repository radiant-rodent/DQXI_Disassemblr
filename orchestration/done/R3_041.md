# R3_041 - refine naming batch (50 low-confidence `maybe_` functions)

**Status:** completed. All 50 batch addresses decided and written to
`orchestration/naming/refine/out/R3_041.json`.

**Tally:** 4 `confirmed`, 23 `corrected`, 23 `kept_maybe`. 13 entries are at confidence >= 0.5;
37 keep the `maybe_` prefix.

## What I did

1. Read the batch file and the pre-baked dossier `orchestration/naming/refine/dossiers/R3_041.md`
   (complete, 50 blocks) in chunks and decided each function before moving on.
2. For every class-attribution question I read the literal word stream directly from
   `original/exefs/code.decompressed.bin` (mapping `file offset = vaddr - 0x00100000`) and resolved
   every function pointer to its current name. This was necessary because the `vtable` field in
   `scores.jsonl` is unreliable - for this batch it was usually a float constant (0x3D088889 =
   1/30, 0x00100000 = the reset vector) rather than a vtable base. The real vtables were found by
   searching the image for a little-endian occurrence of each function address and dumping ±0x40.
3. Where the readable C looked wrong (merged bodies, impossible literal addresses) I decoded the
   ARM words from the same image and trusted the disassembly; the two source trees disagree in a
   few places (see Findings 3-5).
4. Wrote the JSON in two chunks (29 + 21 entries) so a resumed worker could continue.

## Findings worth carrying forward

### 1. Three NPC action constructors identified from their literal tags

`Field_RegisterNpcActions` (0x0017FF58) allocates a different object size per action, loads an
inline action-name literal into `r8`, and calls one constructor per slot:

| Slot | Literal (address) | Constructor | Object size | Installed vtable |
|---|---|---|---|---|
| 0 | `nut` (0x0018024C) | 0x001DC214 | 0x2C | 0x0075A4EC (actor anim timers) |
| 1 | `move` (0x00180254) | 0x002273B0 | 0x54 | 0x0075C378 (`Actor_InitBoundsCheck`, `Actor_InitStateController`) |
| 2 | `flw` (0x00180250) | 0x002BDA98 | 0x2C | 0x0075FA64 (`maybe_Field_Gimmick_SnapToNearbyActor`) |
| 3 | `talk` (0x0018025C) | (not in this batch) | 0x28 | (not in this batch) |

They are now `Field_NpcNutAction_Ctor`, `Field_NpcMoveAction_Ctor` and `Field_NpcFlwAction_Ctor`
(0.60 each). The old names (`Gfx_CreateRenderNodeC`, `Gfx_CreateNodeA`,
`Field_CreateNpcActionC`) had the wrong subsystem and no action identity.

Ghidra had printed the *contents* of the literal words for `move`/`talk` as integers
(0x65766F6D, 0x6B6C6174) and resolved the `nut`/`flw` pointers to 0x0074756E/0x00776C66, which
are UTF-16 message strings - both are decompiler literal-pool traps, not real arguments.

### 3. 0x00119DF8 is a truncated function; the readable C merged its neighbour

The ARM bytes are `push {r4,lr}; bl 0x119BA8; bl 0x1198CC; bl 0x11A3B0; error check;
pop {r4,lr}` and the function returns at 0x00119E14. Ghidra printed a second function
(0x00119E1C, the `svcCloseHandle`/`svcWaitSynchronization` code) in the same body because of a
hidden mid-symbol boundary, so `maybe_Os_SignalEvent` described the neighbour. It is now
`maybe_Gfx_SubmitIpcCommand430040` (0.35).

### 4. `fn.py --asm` can decode the wrong instruction set

For `0x00107514` and `0x0011E374` the generated `asm/text/*.s` lists the region as Thumb and
prints nonsense (`ands`, `cdp`, `push.w`), while the actual bytes are clean ARM. Decoding the
words directly showed `0x00107514` = `mrc p15` (read TLS) / `str #0x210000` to TLS+0x80 /
`ldr r0,[0x007AEAB0]` / `svc 0x32` / `ldrge r0,[TLS+0x84]` - so the handle is a fixed global, not
a dropped argument, and the function is `Os_IpcSendSyncRequestCmd21`. The same method proved
0x00671AFC, 0x002B33B4 and the vtable words. If `fn.py --asm` is fixed, it should use the symbol
table's ARM/Thumb mode per address instead of carrying the mode of the preceding symbol.

### 5. `xref.json` maps call targets to the *containing* symbol start

`bl 0x001B7DB0` is reported as callee 0x001B7DA0, `bl 0x00294C24` as 0x00294C14, etc. That is
correct behaviour (the calls land on inner entries 0x10 past a thunk start), but it means the
"callee" in a dossier can be a wrapper whose real entry is +0x10. I used the raw ARM `bl` targets
when the distinction mattered (destructor base classes).

### 6. Ref-counted release, not operator delete

Per R3_045's finding, 0x0010F6CC is a virtual release through a reference-counted object header.
All destructor summaries in this batch therefore say "releases the storage through 0x0010F6CC";
0x006F5384 calls 0x0010F69C (the free helper) and is a triple-buffer release
(`Container_ReleaseTripleBuffers`).

## Open problems / suggested follow-ups

- The lettered destructor thunks (0x001DC418, 0x00213128, 0x002B13C0, 0x002BDAB8, 0x002C0A14,
  0x002FB480, 0x003ADF54) still have no concrete class. A `--vtable` mode in `tools/fn.py` that
  prints the owning table's named slots would settle these in one call each (R3_045/R3_046 made
  the same recommendation).
- `0x007B2D08` is a driver-session struct; its state bytes (+0xC -> object +8/+9) and the
  result codes 0xF9610C02/0xC8A10C01/0xC8A10C0D/0xC8810FEF are still unexplained. The function is
  now `maybe_Os_IpcSession_PollAsyncState`.
- 0x0010EBB0 / 0x0010E8C0 are not decompiled, so the 0x0069F284 initialiser stays
  `maybe_Sys_InitTimingSlot` even though its literals are known.
- The +0x11C / +0x586 state gate in `maybe_Ui_DiveWindow_Update` (0x0029AA14) needs the
  `Field_Object2D_RunStateSequence` contract.
- 0x002FB480's class may be a horse/scene node rather than a "gimmick" (the doc's old note);
  the table is distinct from `Field_CollisionObject` but its own `+0x04/+0x08` slots are not
  decompiled.
- 0x002EBDD8 / 0x002EBEFC are clip-slot objects; whether the final merged name should say
  "ClipSlot" rather than "Anim" is a style decision for the merge owner.
