### The method that mattered: reading the vtables

`scores.jsonl`'s `neighbour_names` is only an address-neighbourhood cluster, **not** the vtable, so it
cannot settle a class attribution. For every "which class is this destructor/constructor?" question I
dumped the vtable words out of `asm/rodata/*.s` + `asm/data/*.s` (a 40-line helper in
`out/scratch/R3_045/`) and resolved each slot to its current name. That is what turned 12 guesses into
facts, e.g.:

- `0x003047C0` installs vtable `0x00762BB8`, whose slots +0x20/+0x24 are `Ui_PokerWindow_InitPanes`
  and `Ui_PokerWindow_PlayStoredFollowUp` -> it is a **constructor**, not a "reset".
- `0x002D00EC` installs `0x00760480`, whose slot +4 is `Ui_DigitRoll_DeletingDtor`.
- `0x0040CF0C` installs `0x0076D7D4`, whose slot +4 is `Field_Object2D_Dtor`.
- `0x004CED44` / `0x004CF5E4` / `0x004CF5FC` / `0x004A3780` sit in the RouletteCursor / SmithGauge /
  SixRowTextWidget vtables, which is where their class names come from.

**Suggested follow-up:** add a `--vtable 0xADDR` mode to `tools/fn.py`. It is the single highest-value
missing lookup for this lane and every worker currently rebuilds it by hand.

### Two FACTS.md traps that were still live in the readable C

1. **`0x00100B74` is `wcslen`, not a noreturn abort.** Disassembly:
   `movs r1,#0; loop: ldrh r2,[r0]; cmp r2,#0; bne; movs r0,r1; bx lr`. The readable C still prints
   `/* WARNING: Subroutine does not return */ func_00100B74(...)`, which truncated three bodies:
   - `0x002A5458` `maybe_Task_ThreadEntry` -> `Save_SlotEntry_Reset` (clears +0x10/+8/+0xC and fills
     three 128-wchar name buffers at +0x18/+0x11C/+0x220 with empty strings; the caller
     `Save_SlotUi_BuildEntry` calls it as its first instruction).
   - `0x00308F1C` `maybe_Ui_AbortOnIndexError` -> `maybe_Text_MeasureLookString`.
   - `0x003D2EE4` `maybe_Os_StaticCtorB` -> `maybe_Text_LayoutState_Init` (its 976-byte body is real).
   `0x0029126C` is likewise **not** noreturn (`strb r1,[r0,#0x14]` + dirty-bit propagate + `bx lr`),
   which is why `0x003F34E4`'s body looked truncated.
2. **`func_0010F6CC` is a ref-counted release, not `operator delete`**:
   `cmp r0,#0; sub r1,r0,#8; ldrd r0,r1,[r1]; ldr r2,[r0]; ldr r2,[r2,#4]; bx r2`. Every
   `base_dtor(); func_0010F6CC();` body here is a deleting destructor over a ref-counted pool.
