## Findings worth carrying forward

### 1. Vtables are the only way to attribute these destructors

Nine of the fifty functions are deleting destructors whose body is just
`Ui_Object_DtorBase(); func_0010F6CC();`. Their class can only come from the vtable they sit in.
Dumping the vtable words turned eight guesses into facts:

| Address | vtable | class slot | verdict |
|---|---|---|---|
| 0x004D0934 | 0x00778CE8 | 0x004D0380 (ten-row paged list: `null_txt_l0..l9`, `icon_ex0..ex9`) | `Ui_TenRowWindow_Dtor` |
| 0x004D8300 | 0x0077A054 | `Ui_TextPairRow_Init` | `Ui_TextPairRow_Dtor` (old `Ui_RacingWindow_Dtor` was wrong) |
| 0x004DC9BC | 0x0077A394 | `Ui_TitleText_Init` | `Ui_TitleText_Dtor` |
| 0x004E3700 | 0x0077AE68 | `Ui_SelectCoreLoop_Init` | confirmed |
| 0x004E4158 | 0x0077AF4C | `Ui_TenRowTextWidget_Init` | confirmed |
| 0x004E6F10 | 0x0077B500 | `Ui_ThreeLineTextWindow2_Init` | confirmed |
| 0x004E7E28 | 0x0077B6B0 | `Ui_FourRowTextWidget_Init` | confirmed |
| 0x004FA224 | 0x0077CF14 | `Field_LampGimmick_InitModels` | `Field_LampGimmick_Dtor` (slot 0 is the base dtor) |
| 0x0061BA6C | 0x0078005C | `Ui_MessageWindow_InitStatusPane` | `Ui_MessageStatusPane_Dtor` |

`0x004FBEC4` installs vtable 0x0077D210, whose slots are `Ui_TitlePagerWindow_Dtor` /
`Ui_TitlePagerWindow_DtorBase`, and that destructor destroys exactly the 18 x 0xC-byte array this
constructor builds at +0x20 — so it is `Ui_TitlePagerWindow_Ctor`.

**Recommendation:** add a `--vtable 0xADDR` mode to `tools/fn.py`. Every worker in this lane
rebuilds that lookup by hand.

### 2. `fn.py`'s caller/callee lists are unreliable for folded bodies

`grep -c "#0xADDR" asm/text/*.s` shows that 0x004D0934, 0x004D8300, 0x004DC9BC, 0x004E3700,
0x004E4158, 0x004E6F10, 0x004E7E28, 0x004FA224 and 0x0061BA6C have **zero** `bl` sites — they are
referenced only from vtables — yet the dossier listed 3 callers for 0x004D0934 and 10 for
0x0061BA6C. The cause is address attribution: `Ui_ScrollBar_Dtor` really does `bl 0x4D0944` (the
non-deleting destructor) and `b 0x10F6CC`, and 0x004D0944 has no readable file, so it was
attributed to the adjacent 0x004D0934.

Same story for 0x0051CCFC: the dossier claimed 21 callers, the image has **2** — `0x001D035C`
inside `Fs_ReportFatalError` and `0x003359A8` — both fatal-error construction paths.

**Rule of thumb:** before trusting a caller count in this lane, grep the address in `asm/text`.

### 3. 0x0051CCFC is a mid-function split symbol

The real entry is `0x0051CCF8` (`ldr r0,[pc,#0x20]` loads the 0x406 argument); `0x0051CCFC` is the
`push {r4,lr}` that follows. That is why the decompiled body looks like a no-argument function that
"discards" the query result. With the head restored it is
`result = f(0x406); if (result < 0 && result != 0xC8A0CFFC) abort();` — the throw/abort step of
`nn::err`, confirmed by both call sites being the `FatalErrInfo` construction paths.

### 4. The static-initialiser family is truncated by a mis-marked `noreturn`

0x00680C14, 0x0069B5C0, 0x006B65A4, 0x006B68CC, 0x006B6CFC, 0x006B7038 and 0x006B7558 all decompile
to a single `func_0010009C(0x007BE2D0)` because Ghidra marks `__cxa_guard_acquire` noreturn. For
0x006B65A4 and 0x006B68CC I read the disassembly and confirmed the real shape
(`blx 0x10009c` -> `stm r0,{r1,r2}` zeroing 8 bytes -> `b 0x101a94` = guard release). The other five
are Thumb and the ARM-decoded listing is unreadable, so their summaries now say explicitly that the
initialised block is **not** visible in the C. I did not invent block addresses for them.

### 5. Other corrections

- 0x004E36E0 `maybe_Ui_StaticInit_GlobalObject` -> `Ui_SelectCoreLoop_Ctor`: it stamps vtable
  0x0077AE68, so it is a constructor, not a static initialiser.
- 0x005A5F90 `maybe_Ui_ScreenObject_Ctor_77F1DC` -> `Field_ObjectKind16_Ctor`: sole caller is
  `Field_ObjectFactory_Kind16`, same shape as the named `Field_ObjectKind15_Ctor`.
- 0x005A79D0 / 0x005A7DA4 `..._FindNodeByName*` -> `Gfx_RenderObject_CreateNamedNode*`: they
  allocate a node and resolve a name to an index; the sibling handler 0x005A8050 is the confident
  `Gfx_RenderObject_AllocFromArena`.
- 0x0068B23C / 0x00691C0C `maybe_Os_Singleton_GetInstance_*` -> `maybe_Ui_ListPanel_RegisterClass`
  / `maybe_Gfx_Model_RegisterClass`: class-registration shape (list head + 0x10-byte node + vtable
  0x00782AC0 + link via 0x001235A4), not a getter.
- 0x0069FEEC `maybe_Ui_InitAngleObject_7A3AF8` -> `maybe_Ui_StaticInit_7A3EC8`: the body writes
  0x007A3EC8, not 0x007A3AF8.
- 0x0068ADE8 `maybe_Anim_Clip_Init` -> `maybe_Field_InitDescriptorDefaults`: nothing
  animation-specific in the body.
- 0x004D4350 `maybe_Motion_UpdateBlendTimer` -> `Motion_UpdateBlendedTransform`: the output is the
  blended position at self+4/+8/+0xC, not a timer.
