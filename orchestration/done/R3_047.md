**Status:** completed. All 50 batch addresses decided and written to
`orchestration/naming/refine/out/R3_047.json`.

**Tally:** 3 `confirmed`, 11 `corrected`, 36 `kept_maybe`. 7 entries are at confidence >= 0.5;
43 keep the `maybe_` prefix.

## What I did

1. Read the batch file, then discovered the pre-baked dossier
   `orchestration/naming/refine/dossiers/R3_047.md` was **empty** — all 50 blocks say
   "no readable file found" although every column-4 path exists. I did not regenerate it; instead I
   read the 50 readable files directly (they are all small, 16–161 lines) and used
   `python3 tools/fn.py 0xADDR` for callers/callees.
2. Grouped the batch by neighbourhood before deciding anything. The batch is not one module: it
   spans the `Gfx_ColorTable_*`/`Gfx_Movie_*`/`MoLive_*` block (0x006B7xxx–0x006B9xxx), the
   `Field_InitActor*`/`Field_RegisterActorClass_*` block (0x00681xxx–0x006B3xxx), the
   `Ui_InitColorPalette_*` block (0x00694xxx), the `Script_Vm_*` block (0x006BBxxx) and the CTR SDK
   (0x0010xxxx–0x0012xxxx). Listing `decomp/readable/functions` filtered by address prefix was the
   cheapest way to get that context and it changed several verdicts.
3. Ran one single-pass Python scan over `decomp/readable/functions` for the 20 global addresses the
   batch touches (0x007AF058, 0x007AED34, 0x007BE2D4, 0x007BE380, 0x007C5214, …) instead of 20
   separate greps. That is what identified 0x007AF058 as the GPU pipeline-state record and
   0x007BE2D4 as the shared default/zero pair.
4. Read four targeted windows of `asm/text/text_00680048.s` and `asm/text/text_006C0048.s` to
   recover what the decompiled C hides behind a mis-marked `noreturn` call and behind split symbols.
5. Wrote the JSON in one pass after all 50 were decided (the file is small enough that a partial
   write would not have helped a resumed worker).

## Findings worth carrying forward

### The six `maybe_Field_StaticInit_006B7xxx` functions are one family, and their docs quoted the wrong address

All six decompile to a single `func_0010009C(0x007BE2D0)` because Ghidra marks
`__cxa_guard_acquire` noreturn. The disassembly of every one of them is:

```
push {r4,lr}
ldr  r0,=0x007BE2D0      ; guard
blx  0x0010009C          ; __cxa_guard_acquire
cmp  r0,#0 ; beq return
ldr  r0,=0x007BE2D4      ; data
mov  r1,#0 ; mov r2,r1
stm  r0,{r1,r2}          ; 8 bytes zeroed
ldr  r0,=0x007BE2D0
pop  {r4,lr}
b    0x00101A94          ; __cxa_guard_release
```

That is byte-for-byte the 30-member `Os_EnsureDefaultValueInit_*` family (0x00689770..0x0069268C),
so all six are now `Os_EnsureDefaultValueInit_<addr>`.

The addresses the old docs named as the guarded object — 0x007A6874, 0x007A6A80, 0x007A6614,
0x007A662C, 0x007A6620, 0x007A6638 — are literal-pool words of the **preceding** function and are
never loaded by these bodies. The cause is the ARM PC bias: `ldr rX,[pc,#imm]` uses
`PC = instruction address + 8`, so the literal at 0x006B75F0 (not 0x006B75EC) is the guard.

### 0x007BE2D4 is the shared 8-byte default/zero pair

81 readable functions reference it (`Actor_Action_*`, `Actor2D_*`, `Anim_*`, and the whole
`Os_EnsureDefaultValueInit_*` family) as the "no value" sentinel; `Field_InitActorGlobalState_7BE2D4`
(0x006AFDF4, 0.50) is the one that writes real defaults into it. The `Os_` prefix is arguably the
wrong subsystem for a compiler-generated guard helper, but the family name is established and
consistent, so I followed it rather than inventing a 37th spelling.

### Honest keeps (36)

Four are not code at all and are now described as such: 0x00694300 / 0x006944AC / 0x0069466C are
the guard-release tail (`b 0x00101A94`, `pop {r4,pc}`) plus literal pool of the preceding
`Ui_InitColorPalette_*`, and 0x00694674 is a 4-byte index entry with no body and no disassembly.
0x0068826C is a 12-byte literal-pool prefix in front of the real colour-table initialiser at
0x00688278. 0x00692C7C is a guard-block tail followed by the Gimmick2D class-name strings.
0x0069608C loads three constants and tail-branches to a bare `bx lr` stub, so it has no visible
effect.

The rest are damaged bodies (`unaff_r*`, `in_NG`/`in_OV`, `halt_baddata`) or field-offset names
where the mechanism is verified but the field meaning is not (the six `Snd_SetChannel*` setters,
`Os_GetLockDepth`, `Hid_GetEventObject`, `Gfx_SetTextureFill`, `Fs_SetTransferPriority`).

## Open problems / not verified

* No emulator or runtime test — this is a name-only change.
* The exact PICA200 register names for 0x0041..0x0044 and 0x0068 are not verifiable from this repo
  (no register table in `docs/` or `tools/`), which is why 0x006B8484 stays `maybe_`.
* What the two statics at 0x007B2D44 / 0x007B2D4C are (0x006A3548 only installs their vtables).
* What 0x007AE5C4 (`Gfx_ResetGlobalPair`) and 0x007AEA78 (0x0069608C) hold — neither is referenced
  by any other readable function.
* Which class 0x006B3314 registers (no name string in its literal pool).
* Whether 0x006B9A98's `self+4` really is a stream id; it is only "the key 0x00669A40 looks up".
* `tools/fn.py` prints "no readable file found" both for addresses with no readable file at all
  (0x0010009C, 0x00672404, 0x00688278) and, apparently, when the readable tree is being rewritten
  by a concurrent merge. A negative lookup is not evidence that a function is missing.

## Suggested follow-up tasks

1. **`R3_047a` — the 0x006B7xxx `Gfx_ColorTable_*` block.** `Gfx_ColorTable_FillOpaque_006b75fc`,
   `Gfx_ColorTable_InitOpaqueC_006b782c` and `Gfx_ColorTable_InitWithFillD_006b71ec` are named but
   the six `Os_EnsureDefaultValueInit_*` copies interleaved with them are not; a pass that reads the
   whole 0x006B71EC..0x006B7DE0 range as one unit would settle whether the colour tables are Gfx or
   Field (the neighbouring `Field_RegisterActorClass_Actor_006b7de0` suggests Field).
2. **`R3_047b` — the `Snd_SetChannel*` field meanings.** Six setters in this batch write +0x34,
   +0x39, +0x3A, +0x3E, +0x40..+0x46 and +0x56..+0x86 of a 0x34-byte channel record. Their single
   caller 0x0011EE78 computes every value, so reading that one function end to end would name all
   six fields at once.
3. **`R3_047c` — the `Os_EnsureDefaultValueInit_*` family (36 members).** They are all the same
   outlined cold path; a single batch could confirm the family and, more usefully, decide whether
   the `Os_` prefix should become `std_` (they are compiler-generated `__cxa_guard` helpers, not OS
   code).
4. **`R3_047d` — the 0x00694xxx `Ui_InitColorPalette_*` block.** Four addresses in this batch are
   literal-pool/tail artifacts of that block; a pass that re-derives the real function boundaries
   from `asm/text` would let the merge drop them instead of carrying `maybe_` data entries.
