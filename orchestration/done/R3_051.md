## Method (what actually produced the evidence)

1. **The pre-baked dossier was unusable, so I rebuilt the context.** `dossiers/R3_051.md` is 36
   lines: 22 of the 50 rows say "no readable file found". Two causes, both worth fixing upstream:
   - `tools/fn.py`'s `load_names()` globs only `decomp/readable/functions/` and never
     `decomp/readable/recovered/`, so every `recovered/` function is invisible to it (and to
     `make_dossiers.py`, which calls it).
   - The batch's column-4 paths are stale: readable files are named by the *current* name, not by
     the batch's `maybe_` name, so `maybe_Ui_DateDisplay_AdvanceByFlags_002c21ac.c` no longer
     exists under that name.

   I mapped address -> file by the `_XXXXXXXX.c` suffix across both directories and read the files
   directly.
2. **The readable tree was being regenerated while I worked.** `decomp/readable/functions/` went
   2279 -> 17994 files and `recovered/` repeatedly dropped to 0 mid-run (another worker re-running
   `tools/readable_c.py`). I snapshotted all 50 files into `out/scratch/R3_051/snap/` first, so
   every decision is against one consistent state.
3. **`decomp/xref.json` resolves a `bl` to the *containing* function, not the call target.** That is
   why many "callees" look absurd (a UI window holder "calling"
   `Field_Action_GetCameraRelativeDirection`, a deleting destructor "calling"
   `Snd_DetachChannel`). Reading the actual `bl` in `asm/text` showed the real targets are inner
   entries of those functions (0x0064150C inside 0x00641150, 0x001235A4 inside 0x00123564). I
   checked the disassembly whenever a callee looked out of place, and said so in the evidence.
4. **The decisive evidence was the rodata word stream.** Resolving each batch address to the rodata
   word that points at it and dumping the surrounding table turned class guesses into facts:
   - `0x00760004` = `Ui_WindowHolder` vtable: slot 1 `Ui_WindowHolder_DtorDelete`, slot 2 =
     0x002C1BC0, slot 3 = 0x0063BEF4 which the disassembly shows is `ldrsb r0,[r0,#4]; bx lr` — a
     getter of the very ready byte 0x002C1BC0 writes.
   - `0x007293F0` = `Ui_DateDisplay` step table (named `AdvanceByLoadState`, `FinishState1`,
     `FinishState2`, `FinishAndStep` siblings) -> confirms 0x002C23C4.
   - `0x0076089C` has six named `FieldParty_*` rows -> confirms 0x002D9D00.
   - `0x00760DD0` has `Battle_Unit_ApplyDefaultAnim` and `Battle_Unit_HandleCommand9` -> confirms
     0x002DB140.
   - `0x007614C8` has `Ui_EquipRow_Update` at +0x3C -> renamed 0x002EA468 from
     `Ui_Panel_DeletingDtor` to `Ui_EquipRow_DeletingDtor`.
   - `0x007615E0` / `0x007615DC` / `0x00761610` hold the confident
     `Anim_ClipSlot_UpdateLinearMotion` -> confirms the three `Anim_ClipSlot_*` entries.

## Stale readable C found

For 0x002DB98C / 0x002DBD88 / 0x002DBDD8 / 0x002DBE2C the C shows `func_00193E44()` but the
disassembly is `bl 0x38ad34` (inside `Battle_ActorAction_DeletingDtorAlt`). The four vtables
0x00760E38 -> 0x00760EA0 -> 0x00760ED4 -> 0x00760F08 are nested, each embedding the next at +0x34.

Also worth recording for other workers: 0x00193E40/0x00193E44 is not a destructor body at all but
`ldr r1,[pc,#4]; str r1,[r0]; bx lr`, i.e. "install base vtable 0x00758AE0"; and 0x0010F6CC is a
deallocation through the allocator vtable stored 8 bytes before the block, not a plain
`operator delete`.
