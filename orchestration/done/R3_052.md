## What the new context changed

1. **Five "ResetActorFlags" copies are one Ui-window template, not actor code.**
   0x004DE7D4 / 0x004F7F7C / 0x00595098 / 0x005A4D40 are byte-identical:
   `self[0x3784] = -1; Ui_ApplyScaleToChildren(self); if (actor0->f_10) actor->f_72C = 0`.
   0x00599974 is the same plus `Field_Actor_UpdateEquipDisplay`. Each sits at the same slot of a
   different screen table, so each was renamed after its own class:
   `maybe_Text_MessageWindow_ReapplyScaleAndClearActorFlag`,
   `Battle_ActionSequence_ReapplyScaleAndClearActorFlag`,
   `Battle_Ui_MemberScreen_ReapplyScaleAndClearActorFlag`,
   `Battle_Ui_MemberScreen_ReapplyScaleAndRefreshEquip`,
   `Battle_Sequence_ReapplyScaleAndClearActorFlag`.
   The two copies that save/restore the row through virtual +0x140/+0x144 are
   `Ui_Window_ReapplyScaleKeepingRow` (0x0031F4B4, confirmed) and
   `Ui_PartyStatusWindow_ReapplyScaleKeepingRow` (0x00468688).
2. **0x00322074 is the battle action-sequence controller, not a field world state.**
   Table 0x00763848 = `Battle_ActionSequence_Dtor` + `Battle_ActionSequence_UpdateTurn`;
   `maybe_Field_WorldState_Reset` → `maybe_Battle_ActionSequence_ReapplyLayout`.
3. **The "UpdateMarkerIfModel" family was wrong.** 0x002DB940 / 0x002DBB30 / 0x00400304 /
   0x004006A0 / 0x004ED338 all do `if (0x0066A2BC(self->f_28)) Battle_Action_RestoreActorIdleByHp(self)`.
   Disassembly: 0x0066A2BC = `if (model->f_160) return 0x00633F68(model)`, and 0x00633F68 compares
   the current animation entry's float at +8 with the end value at +0x10. So the gate is "the model's
   animation has reached its end" and the action is "restore idle posture by HP". Renamed
   `..._RestoreIdleByHpWhenAnimEnds` per class.
4. **Destructors re-attributed from vtable slot 0 / entry tables.**
   - 0x002F3B1C → `Field_Marker_DeletingDtor_2` (table 0x007618B0 = LoadMesh / OnDestroy / OnUpdate /
     OnNotify; the unsuffixed name is already the 0x002F3100 marker dtor, and the tree already names
     this file `Field_Marker_DeletingDtor_2_002f3b1c.c`).
   - 0x002FA43C → `Field_Npc_DeletingDtor` (table 0x00762410 also holds `Field_Npc_OnApproach`).
   - 0x002FB420 → `Field_NpcSprite_DeletingDtor` (table 0x00762500 also holds
     `Gfx_SpriteActor_ReleaseWithChildren`).
   - 0x002F2134 → `Field_NpcActionScript_DeletingDtor` (table 0x00761710 =
     `Field_SetupNpcActionScript` / `maybe_Field_NpcFinishAction` / `Field_NpcPlayGesture`; not the
     same class as 0x00332D90, whose base destructor is 0x00193E40).
   - 0x002F6B48 / 0x002F6B74 are the deleting / non-deleting destructors of the window **embedded at
     parent+0x138** (both callers are the item-info-window dtors), not of the item-info window.
5. **0x002DAA10 = `FieldParty_MemberActor_Ctor`.** It installs table 0x00760AC0, whose slots are
   `FieldParty_InitFromParams`, `FieldParty_ResetMemberSlot`, `maybe_FieldParty_CompactMemberList`,
   `maybe_FieldParty_IsMemberListed`; the only caller is the 2D/3D object factory kind 0x29.
   `Gfx_ObjectCtor` was too vague.
6. **Action-window names had to be qualified.** The plain `Ui_Window_StartAction1F` / `1E` names are
   already used by the 0x002A69xx family, so the text-window copies became
   `Ui_TextWindow_StartAction1F` (0x002FE024), `..._StartAction22` (0x002FE3FC),
   `..._StartAction1E` (0x002FE494), `..._StartAction19WithCount` (0x002FECF0); their bodies match the
   confident `Ui_Window_StartAction26` (vtable+0x54 = start-action). Similarly
   `Ui_TextWindow_DeletingDtor` is the 20-byte class at 0x0045C92C, so the big 0x404C+ window
   0x002FFA14 became `Ui_TextListWindow_DeletingDtor`.
7. **0x002C0E24 confirmed by a string literal.** `Ui_FieldActionListWindow_InitPanes` passes the
   4-byte label 0x0074756E (`"nut"`) when filling row 0; the sibling rows are
   `Field_CreateActionMoveStep/Run/HorseStart`. The same family explains `"Horse_Nut"` in the rodata
   next to 0x002FB444, corroborating the field action-list reading of 0x002FB710/0x002FB790.
8. **Two more inner-entry mis-seeds documented.** 0x002FB790 is a mid-function entry of 0x002FB710
   (it starts at the `bl Container_SlotReplace` inside the unrolled row loop); 0x002FB710 itself is
   ARM code exported as Thumb (hence Ghidra's `halt_baddata`). 0x002F234C is a Thumb case block, not a
   callable function.
9. **Honest keeps (10).** 0x002EC4B4 (slots +0x7C/+0x70 unverified, no caller), 0x002F2210 (only
   flag registers), 0x002F234C, 0x002F5038 (table mixes `maybe_Gfx_MeshNode_InitChildren` with
   `Event_Actor_PlayNutMotion`), 0x002FB710, 0x002FB790, 0x002FDCB4, 0x002FDE8C, 0x002FE24C,
   0x002C49AC (all carry `unaff_r4`/`unaff_r7` damage).
