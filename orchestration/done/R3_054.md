## Main findings (what changed the verdicts)

- **The dirty `maybe_` names in the `0x0048C490` area were split symbols.** 0x0048C490 is not a
  text-layout stub: it is the 24-byte ARM prologue of the function whose body starts at 0x0048C4A8
  (`maybe_Battle_CalcAttackMultiplier_Body`). The prologue sets `r1=8` and keeps `r0` in `r4` for
  that body's first call `0x00639954`. Renamed `maybe_Battle_CalcAttackMultiplier_Prologue`.
- **0x003E7394 is a template copy of the named `Field_Actor_Suspend` (0x003E7150).** Disassembly is
  instruction-identical after normalising branch targets, so it was confirmed as
  `Field_Actor_SuspendB` (0.55). The same "identical body, second address" rule confirmed the two
  hit-box constructors against the now-confident `Field_HitBox_Setup` / `Field_HitBox_SetupFloat`.
- **Two suspected UI icon-cache functions are actually the Cecd raw-file protocol.**
  0x0050B0E0 and 0x0050BED4 call the named `Svc_Cecd_OpenRawFile` (command 0x03) and
  `Svc_Cecd_ReadRawFile` (command 0x07). Renamed `Svc_Cecd_OpenRawWithRetry` and
  `Svc_Cecd_ReadRawWithRetry`; the latter needs the `Raw` qualifier because `Svc_Cecd_ReadWithRetry`
  is already 0x0050BF64 (dispatch path). 0x0050BFE8 goes through the command-0x09 dispatcher
  (0x0050D050 -> Cmd0009/Cmd0009B, header 0x000900C2), not a delete (delete is command 0x11), so it
  became `maybe_Svc_Cecd_Cmd0009WithRetry`.
- **0x003EC71C is not a marker-visibility setter.** Its 788-byte disassembly is a seven-iteration
  decimal-digit decomposition (repeated divide-by-10) writing digits into the three sub-nodes per
  smith-menu row, with the node visibility gated at the >=10 and >=100 thresholds. Renamed
  `maybe_Ui_SmithMenu_SetRowValueDigits`.
- **0x004C9BCC is a release path, not a mesh load.** The readable body is a bad-data fragment, but
  the disassembly is `Field_SceneObject_ReleaseEffectSlots` + manager notify + `Effect_ReleaseHandle`
  with the packed handle at f_2FC. Renamed `maybe_Field_SceneObject_ReleaseEffectBindings`.
- **Three more duplicate deleting destructors were identified by byte-identical bodies:**
  0x004DCE7C = `Ui_3DBackground_DeletingDtorB` (0x00463B24 twin), 0x005A1F9C =
  `Battle_AnimWindow_DeleteB` (0x0059F844 / 0x002F199C twins), and 0x004E45D0 =
  `maybe_Battle_AnimWindow_DtorWithVtable` (stores the vtable passed in r1 at +0 and its secondary
  at +0x220, then runs the same base dtor).
- **0x003D26CC has two writes, not one.** The asm sets sub-node +0x4C to the incoming flag and
  sub-node +0xE8 to its complement, so the old `SetSubPaneVisible` (singular) was incomplete.
- **0x0051BA38 is a wait loop, not a check.** It retries `Gfx_WaitForIpcIdle` while the result is a
  negative non-fatal code, sleeps 10 ms on 0xE0A0CC08 and stops on 0xC8A0CFFC (the err:f sentinel).
  Renamed `maybe_Err_WaitForIpcIdleOrFatal`; the old "1 ms" summary was wrong (0x00989680 ns = 10 ms).
- **0x005088DC is a genuine PICA200 vertex-attribute block.** The command words write registers
  0x0201/0x0203 and 0x0232 (FIXEDATTRIB_INDEX) and there are exactly twelve attribute entries, which
  matches the vertex-attribute facts in FACTS.md; confirmed at 0.50.

## Honest keeps and limits

- 17 entries stay `maybe_` because the body is damaged (`unaff_r*`, `in_ZR`, `halt_baddata`) or the
  owner class is only inferred: 0x003C36C4, 0x003D6008, 0x003D7634, 0x003E7728, 0x0040D8C0,
  0x0041E79C, 0x00454C34, 0x0046CBD0, 0x0046E8B8, 0x004D9E8C, 0x004ED870 and the three Svc_Ipc /
  Svc_Cfg wrappers, plus 0x003F0EC0, 0x003F44AC and 0x003F44E4.
- The `Svc_Ipc_Send0001/0002/0007` names stay vague on purpose: their bodies are clean IPC wrappers,
  but the session at 0x007B00E8 has no data symbol and the caller/callee lists in this region are
  literal-pool artefacts (no `bl` site exists in `asm/text` for any of the three). I checked the
  three `bl` claims and they are 2-byte Thumb branches decoded out of the literal pool.
- 0x0050D978 still cannot be pinned to "region": the query session is shared with the named
  system-language query, but no caller or data name constrains command 0x0003.
- **Not verified:** no emulator/runtime test (name-only change). The concrete classes behind the
  renamed destructors (only the base dtor is proven), the smith-menu sub-node semantics
  (+0x2EC/+0x33C/+0x38C), whether 0x00488638 is really a row-style applier or battle maths (its
  address lies in the combat-maths range from FACTS.md), and the exact CECD command-0x09 operation.
