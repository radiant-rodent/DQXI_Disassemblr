## What changed and why

The batch is one contiguous slice of the binary, `0x00502FF8..0x00537C5C`, and it turned out to be four
unrelated modules in a row:

| range | module |
|---|---|
| `0x00504050..0x0050F0F8` | CTR SDK object / sync / time layer |
| `0x0050F978..0x00510A28` | regex + text tokenizer |
| `0x00517478..0x0051D25C` | sound channel layer |
| `0x005225E8..0x0052F6D0` | Fx particle system |
| `0x00535EDC..0x00537C5C` | SARC / layout tail |

The first pass had guessed `Sound_*` for the whole `0x0051Bxxx..0x0051Dxxx` block and `Text_*` for
`0x0050F978`/`0x00510A28`; both were wrong for the same reason — the block boundaries were not known yet.

### Confirmed (13)
`Gfx_Y2r_ConvertPlane`, `Fx_UpdateParticlePosition`, `Fx_CopyEmitterBaseTransform`,
`Fx_CommitParticleStream`, `Fx_AppendNodeData`, `Gfx_ModelSlot_Release`, `Svc_ObjectPool_InitB`,
`Svc_AdvanceTimeMs`, `Ui_IconCache_StopService`, `Ui_IconCache_CountMatchingEntries`,
`Ui_IconCache_StoreRecordByCommand`, `Sound_GetSystemThunk`, `Sound_ForwardToVoicePlayback`.

The decisive new context in each case was a *named* neighbour that became confident after `M1_merge_names`:

- `Gfx_Y2r_ConvertPlane` (0.55) — the named caller `Gfx_Y2r_ConvertFrame` (0x0051C5F0) calls it three
  times with plane index 1, 0 and `(0, secondPlane=1)`. The disassembly at `0x0051C684` is
  `movne ip,#0x140 / moveq ip,#0x190` (320/400 rows), which is the conditional Ghidra lost as `in_ZR`.
- `Fx_UpdateParticlePosition` (0.55) — `particle->f_C += keyframe[4]*(keyframe[1]-particle->f_C)*dt`
  for all three components; the four per-particle updaters (0x5237C4/0x524390/0x5257E8/0x526F38) call it
  right after the scale step. `dt` arrives in `s0`, dropped by Ghidra as `in_s0` (VFP trap, not damage).
- `Fx_CommitParticleStream` (0.50) — four named list updaters end with `b`/`bl` to it, and the body is two
  `memcpy`s into `0x007AFF18[0]` plus "return advanced pointer".
- `Fx_AppendNodeData` (0.50) — three real callers pass one node and use the returned pointer as the next
  write position: `memcpy(stream, node[1], node[2]<<2); return stream + node[2]*4`.
- `Gfx_ModelSlot_Release` (0.55) — its only caller `maybe_Gfx_BindResourceSlot` (0x0055DBB8) calls it when
  the slot is occupied and then binds the replacement through the confident `Gfx_ModelSlot_Replace`.
- `Svc_ObjectPool_InitB` (0.50) — byte-identical to the confident `Svc_ObjectPool_InitA` (0x0050421C)
  apart from the pool address (0x007E7AA4 vs 0x007E7AB8) and the id (0x207 vs 0x209). Note 0x207 is the
  registered id, not an entry count as the old summary said.
- `Svc_AdvanceTimeMs` (0.50) — the only caller is `Svc_Time_GetCurrentTimestamp` (0x0050EFA4); the magic
  `0x431BDE82D7B634DB` is the 64-bit reciprocal of 1,000,000, so the unit conversion is certain.
- `Ui_IconCache_StopService` (0.55) — exact counterpart of `maybe_Ui_IconCache_StartService` (0x0050A010):
  same state block 0x007AE9E0, same lock, clears the +1/+2 bytes that StartService sets.
- `Sound_GetSystemThunk` (0.50) — `push/bl 0x5177DC/pop`; 0x005177DC is the real entry of
  `maybe_Sound_GetSystemIfInitialized` (Ghidra split that function at 0x005177E0).
- `Sound_ForwardToVoicePlayback` (0.50) — `bl 0x5177DC` then `bl 0x5179A8` (`Snd_StartVoicePlayback`);
  the decompiler's "does not return" claim was wrong.

## Open problems / things I could not verify
1. **`decomp/xref.json` is stale for this region.** It lists callers of 0x0051D040 and 0x00529A60 that
   contain no `bl`/`b` to them at all, and it resolves some `bl`s to the containing function instead of the
   target. I rebuilt the call graph for the 50 addresses with one regex pass over `asm/text/*.s`
   (`out/scratch/R3_056/real_callers.json` / `real_callees.json`) and took every caller/callee claim from
   the asm. **Suggested fix:** make the xref builder resolve to the nearest *symbol start* ≤ target and flag
   targets that fall inside another symbol.
2. **`asm/text/text_00500048.s` misdecodes some ARM as Thumb** (0x00502FF8, 0x00509B40, 0x00530054). Any
   caller/callee data in those spots is unreliable, which is why those entries stay at 0.15–0.45.
3. **`decomp/readable/functions/` is being modified concurrently by other workers** (file count went
   17972 → 17985 during the session). Names can shift between the dossier and the tree; every decision was
   re-checked against the file as read at decision time.
4. **Unresolved semantics** (all recorded in the JSON summaries): whether `0x001001C4` is a string-range
   constructor or a throw helper (affects 0x0051D040); the meaning of the Fx vertex-record fields
   +0x60/+0x64/+0x68/+0x6C; whether `f_78..f_84` is colour or UV; what the globals 0x007AFF18/0x007AFF3C
   hold; and what `0x0052E3C8` (the flush tail of `Fx_AdvanceEmitterFrame`) does exactly.
5. **No runtime verification.** This is a name-only change; nothing was exercised in the emulator.
