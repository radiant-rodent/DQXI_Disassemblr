## What changed and why

### Confirmed (19)
The six `Fx_UpdateParticleListL/M/N/O/Q/T` walkers, `Fx_AllocParticleNode`, `Gfx_LoadTextureByName`,
`Ui_AnimClip_InitRuntime`, the six `Sound_SeqPlayer_SetChannelFloat*` wrappers,
`Sound_SeqPlayer_SetAllChannelNotesFlag`, `Text_CharFilter_Match`,
`Gfx_ModelInstance_DrawOverridePass`, `Gfx_RenderObject_UpdateWithScaleOverride`.

The decisive new context in each case was a callee that became confident after `M1_merge_names`:
`Fx_UnlinkParticleFromLists` (0.50) sits on the dead branch of every list walker;
`Event_BroadcastSlotMask` (0.50) is documented as "loads the handler at self+0x90+i*4 for every set
mask bit and calls it with the value in s0", which is exactly the shape of the six channel setters;
`Gfx_Flim_Parse` (0.50) plus the literal `0x74696D67` (`"timg"`, the CTR texture magic) pins
`Gfx_LoadTextureByName`; `Ui_AnimClip_CtorEmpty` (0.50) calls `Ui_AnimClip_InitRuntime` as its base
initialiser.

## Open problems / things I could not verify
1. **The readable tree was rewritten mid-run.** `decomp/readable/functions/` went 17994 → 14962 files
   at 18:19 while I was reading; for a few minutes `ls <path>` and `find -name` reported "No such file"
   for files that `ls <dir> | grep` still listed. All decisions were re-checked against the post-rewrite
   files, but a worker that reads the dossier and the tree at different times can mix two naming states.
   **Suggested fix:** serialise `tools/readable_c.py` in the dispatcher.
2. **`decomp/xref.json` resolves a `bl` to the containing function, not the call target** (same defect
   R3_051 reported). This batch is full of it: 0x00564054 "calls" `SaveData_ResetAllSaveData` when the
   real targets are 0x0010F6CC/0x0010F69C (inner entries of that symbol); 0x00589D54 "calls"
   `Snd_DetachChannel` when the real target is 0x001235A4. Every suspicious callee was re-read in the
   disassembly. **Suggested fix:** make the xref builder resolve to the nearest *symbol start* ≤ target
   and flag targets that fall inside another symbol.
3. **`0x0010F69C` / `0x0010F6CC` are deleting-destructor thunks** (`sub r1,r0,#8; ldrd r0,r1,[r1];
   ldr r2,[r0]; ldr r2,[r2,#4]; bx r2`), not save code. They currently fall inside the
   `SaveData_ResetAllSaveData` (0x0010F448) symbol, which is why that symbol shows 77 callers including
   `std_operator_delete_array` and `Gfx_CommandBuffer_Release`. FACTS.md lists 0x0010F448 as
   `SaveData_ResetAllSaveData` at 0.70; I did not contradict it, but the caller list suggests the symbol
   range is wrong and should be split. **Suggested follow-up task:** re-split 0x0010F448 and re-check
   its name.
4. **Unresolved semantics** (all recorded in the JSON summaries): what the particle words
   +0x60/+0x64/+0x68 and the +0x6C marker mean; what the 0x5880-byte Fx pool block represents (one
   particle or a render bucket); which of the two glyph-cache tables (self+0x2C / self+4) is which page
   and what the 0x2000000/0x1000000 key bits select; the class behind vtable 0x00781498/0x007814F4;
   whether 0x005692CC really is a second textured-part draw variant (its symbol size of 132 bytes is
   wrong — the body runs past 0x569368).
5. **No runtime verification.** This is a name-only change; nothing was exercised in the emulator.
