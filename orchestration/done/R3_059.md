## Main findings (what changed the verdicts)

- **The dossier's caller/callee lists come from `decomp/xref.json`, which is wrong in places.**
  `xref.json` gives 0x00119254 thirteen callers (`Fs_OpenGlobalFile`, `Fs_Initialize`,
  `Svc_Ndm_AcquireService`, `Gfx_InitDrawState`, ...); the disassembly contains exactly one
  `bl #0x119254`, at 0x00112D60 inside `maybe_Snd_RestoreChannelState`, and `Fs_OpenGlobalFile`
  (0x00106A70) does not call it at all. I therefore re-derived every caller that mattered from the
  branch targets. Four functions in this batch turned out to be dead code with no branch target
  anywhere: 0x0010C642, 0x00118108, 0x00123BB0 and 0x001228FC.
- **0x007B2D2C is the `ir:USER` session handle.** Asm 0x00122260/0x00122264 load the name pointer
  0x00754FC0 (rodata bytes `69 72 3A 55 53 45 52 00` = "ir:USER") and the out-pointer 0x007B2D2C
  into r1/r0 before the `srvGetServiceHandle` wrapper 0x001192C0, and no other
  `srvGetServiceHandle` call in the image writes that global. This corrected three names:
  `maybe_Snd_IpcCmd18ChannelBuffer` -> `Svc_Ir_IpcCmd180182`,
  `maybe_Os_IpcCmd0BGetThreadValue` -> `Svc_Ir_IpcCmd0B0000`,
  `maybe_Os_IpcCmd0AGetProcessValue` -> `Svc_Ir_IpcCmd0A0000`.
- **The `Text_Style_*` accessor family is Field2D code.** 0x00668818 and 0x006688B4 read byte +0x15
  / +0x12 of `*(*(self+4)+0x298)`, exactly like the already re-attributed siblings 0x00667068
  `maybe_Field2D_Layer_GetField12`, 0x00667DE0 `maybe_Field2D_Scene_GetStyleByte18`, 0x0066882C
  `maybe_Field2D_Scene_GetStyleByte14` and the confident 0x00667108 `Field2D_Layer_GetKindGroup`;
  their callers are 2D map-chip functions. Renamed `maybe_Field2D_Scene_GetStyleByte15` /
  `maybe_Field2D_Layer_GetField12B`. Same story for 0x00667E00, whose neighbours are
  `Field_Object2D_CalcScreenRectB` and `Field2D_Sprite_ChoosePathStep`: it is a rectangle hit test,
  not a text-window scroll test.
- **0x0066DAD0 is an equipment-change method, settled by the method table.** Asm:
  `sub r4,r0,#0x220; ldr r0,[r0,#4]; blne 0x40A680` (`Model_Equip_ApplyCommand` with r1/r2 forwarded
  from the caller) then `b 0x377440` (the two-item equipment-label rebuild) on self-0x220. The table
  at 0x00765BF4 holds `{0x0066DAD0, -0x228}` directly after
  `{0x00377420 Field_Actor_SetEquippedPairText, -0x220}`, which fixes the owner class. Renamed
  `Field_Actor_ApplyEquipCommand` (0.50).
- **0x0066D928 is a destructor, not an initialiser.** Asm: `stm r0,{r1,r2}; add r0,r0,#0xE0F8;
  bl 0x5761D8` (`Os_ThreadObject_Dtor`, which returns its argument); `sub r0,r0,#0xE0F8;
  b 0x10F6CC` - and 0x0010F6CC is the tail of `Ui_DestroyRootSingleton`, i.e. "destroy the object in
  r0 through vtable slot +4". Renamed `maybe_Ui_Object_DestroyWithInlineThread` (0.30; the two
  leading stores are still unexplained).
- **0x006BB330 is Squirrel VM code, not graphics.** Its neighbours are `Script_Vm_IsInstance`
  (0x006BB248) and `Script_CreateNativeInstance` (0x006BB360). Also, 0x00147AEC is not
  `free(ptr, 0xB8)`: it is the tail of `maybe_Container_DestroyObject` and reads
  `g_objectDestroyTable->vt[0x10](manager, obj)`, a remove-from-table call. Renamed
  `maybe_Script_Object_Destroy`.
- **0x00663444 returns a height.** The caller `Math_Vector_FloatToFixed` (0.80) does
  `inFloat[1]=obj->f_14; h=GetMetricB(obj); inFloat[3]=h+obj->f_14`, i.e. y1 = y + result; the asm
  multiplies virtual slot +0x10 by the holder's scale at +0x0C (the twin 0x006633EC multiplies slot
  +0x0C by the horizontal scale at +0x08). Renamed `maybe_Ui_Element_GetScaledHeight`.
- **The 13 `Video_Convert*` entries stay `maybe_` on purpose.** None of them has a direct branch
  target (they are reached through the two dispatchers 0x0012A81C / 0x0012A84C or through their own
  computed jumps), so only the algorithm shape is provable. The A/B/C copies are not arbitrary: they
  differ only in the plane stride constants (A 0x400/0x3e0, B 0x100/0xe0, C 0x200/0x1e0), which is
  now recorded in each summary. The two dispatcher pairings are confirmed from the disassembly:
  0x0012A81C -> {0x0012762C | 0x001290A0} then 0x001281E0, and
  0x0012A84C -> {0x00126B0C | 0x00129EF4} then 0x00126EF4.

## Suggested follow-up tasks

   `Gfx_IpcCmd20000` (0x00117AE8), `Gfx_IpcCmd40000` (0x00117B18) and `Gfx_IpcCmd30000`
   (0x00117B48) are all `ir:USER` stubs (commands 0x09/0x02/0x04/0x03), not GPU stubs - the
   confident 0.60 names are wrong. `Gfx_IpcCmd50100Query` (0x001192F4) is the raw
   `srv:GetServiceHandle` command (header 0x00050100), and 0x001192C0 is its validating wrapper

   `ir:USER` Finalize path.
2. **Re-check `maybe_Os_GetCurrentProcessHandle` (0x00122440).** Its callee is now proven to send
   `ir:USER` command 0x0A, so the "process handle" reading is doubtful.
3. **Name the `ir:USER` command family properly.** 0x00123C54 (0x0E), 0x00123C9C (0x0A),
   0x00123CD8 (0x0B), 0x00123D10 (0x18), 0x00123D68 (0x0D), 0x00124C64 (0x06) and 0x00124CA0 (0x0C)
   all talk to the same session; the 3dbrew `ir:USER` command list would let them be named by
   operation instead of by header.
4. **Repair `decomp/xref.json`.** Its caller/callee edges are wrong for at least 0x00119254 and
   0x00106A70, which makes every dossier's CALLERS/CALLEES block unreliable. A rebuild from the

   dispatchers 0x0012A81C / 0x0012A84C (they are published together in the literal pool at
   0x0012A87C, so they are a vtable/table pair).
