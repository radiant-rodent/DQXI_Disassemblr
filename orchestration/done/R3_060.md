## Main findings (what changed the verdicts)

### 1. The dossier's caller lists are systematically inflated in this region

`decomp/xref.json` attributes a branch to the *containing* function, so a `bl` to a mid-function
address is reported as a call to the function start. 0x00106460 was given 35 callers
(`Engine_Initialize`, `Ui_UpdateWindowState`, `Camera_RebuildWorkList`, `Ui_MessagePage_ExecuteCommand`,
...) although **no `bl #0x106460` exists anywhere in `asm/text`** - the real target is 0x001064D4,
which lies inside the 120-byte range the index claims for 0x00106460. The same artefact produced
802 "callers" for 0x0011CF9C, 80 for 0x00125098, 41 for 0x0011ECC0 and 19 for 0x0011F6C0.

I rebuilt the lists with a one-pass exact-target scan (`out/scratch/R3_060/exact_callers.py`) and
used only those results. **30 of the 50 functions have no direct caller at all**, which is why so
many entries stay `maybe_`.

**Follow-up for the tooling:** `tools/xref.py` should map a branch target to a function start only
when the target *is* a start (or when the containing function's size is trustworthy); otherwise
every batch in this region gets misleading caller lists.

### 2. `asm/text` is Thumb-decoded over ARM code in places

0x00106460, 0x00105238, 0x0011CC28 and 0x003007B8 are decoded as 2-byte instructions although they
are ARM. Decoding 0x00106460 by hand (`e92d4010` / `eb0038a1` / `e3500000` / `03a00001` / `13a00002`
/ `e8bd8010`) gave the real 24-byte body and settled the name. Where the bytes were readable the
disassembly was decisive for six entries.

### 4. Confirmed (5)

- 0x0010F050 `Container_RemoveSmallSetEntry` - the release it calls is now the confident
  `Mem_PoolDestroy`, which pins "remove and give the slot back to the pool".
- 0x00112888 `Snd_ResetChannelUnitsInPlace` - callee is the confident `Snd_SetChannelMaskedFields`,
  driver context 0x007EF414.
- 0x0011EE0C `Container_ObjectDtor` - asm shows the vtable store, two `blne 0x11c814`, the
  `ldr r1,[r4,#0x10]!` list walk and `sub r0,r4,#0x10`.
- 0x0012A81C `Video_ConvertSelect_A` and 0x0012A84C `Video_ConvertSelectB_A` - their `_B`/`_C` twins
  (0x0012E594/0x0013230C and 0x0012E5C4/0x0013233C) are already confident names, and the literal
  pool at 0x0012A87C publishes both dispatchers together.

### 5. Honest keeps (33)

This batch is the CTR SDK / CRT region with no native symbols (`decomp/native_names.json` has none
of the 50) and almost no callers, so most names can only describe the body:

- 0x0010F31C and 0x0011B7EC are `missing_function` in `functions_index.json` with **no readable body
  at all** - kept at 0.25 with a summary that says so.
- 0x00114B12, 0x0011AC6E and 0x00123FAE are mis-seeded fragments (interior code, not function starts).
- 0x00117458, 0x0011B212, 0x00109F6C, 0x0010CB30, 0x001094C0, 0x001109A0/DC and 0x0013B704/B7C8
  carry `unaff_`/`in_ZR`/`in_r12`, so per FACTS.md they stay at 0.3 or below.
- 0x0011F6C0 keeps the `Snd_` prefix only as a guess: its exact callers are the `Gfx_*` command
  writers (0x1136D8, 0x113714, 0x11386C, 0x1198DC, 0x11A50C, 0x11F12C, 0x11F21C), which contradicts
  it. Flagged in the evidence rather than silently renamed.

## Suggested follow-up tasks

1. **Fix `tools/xref.py`** so a branch target is attributed to a function only when it is a function
   start. This batch alone had five functions with 19-802 phantom callers; every refine batch in the
   0x0010xxxx-0x0014xxxx region is affected.
2. **Re-check the `asm/text` ARM/Thumb mode boundaries** around 0x00105238, 0x00106460, 0x0011CC28
   and 0x003007B8 - the disassembly decodes ARM as Thumb there, which also corrupts the xref edges.
3. **Name the SDK globals** 0x007AE954 (28-word state block with two callbacks), 0x007AEA00 (sound
   driver context: session at +8, cached unit mask at +0xC, active byte at +0, pending byte at +2)
   and 0x007AE61C (VRAM region allocator table). Naming those three would unlock roughly a dozen
   `maybe_` entries in this region.
4. **Identify 0x00300308 and the record id 0x04000027** - that would settle 0x00102828 and the two
   string getters 0x00105238/0x00105280.
5. **0x0011F6C0** needs a decision from someone who can read the `Gfx_*` command writers: the exact
   callers say graphics, the name says sound. One of the two is wrong.
