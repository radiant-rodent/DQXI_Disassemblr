## Main findings (what changed the verdicts)

### 1. 40% of the batch is one family: the video decoder's second copy

20 of the 50 addresses (0x0013BD40..0x0013F27C) are the `_B` copies of the 0x00135xxx kernels.
The region is now confirmed video by confident names in the same block (`Video_IdctBlock4x4`,
`Video_IdctBlock4x4_B`, `Video_DecodeCoefficientBlock`, `Video_DecodeSubblockMask`,
`Video_McPredict*`), and 19 of the 20 bodies are complete, readable 1:2:1 / `(a+2b+c+2)>>2` kernels
with a byte-identical twin, so they were confirmed at 0.5.

Two things are worth recording:

- The kernels are entered with the **sample pointer in r11**, a hand-written ABI Ghidra cannot
  model. That is why every body shows `unaff_r11`; it is the only damage, the arithmetic is intact.
  The evidence field says so explicitly, because `tools/check_refine.py` flags confidence >= 0.5 on
  a damaged body.
- `Video_DecodeCoefficientBlock` (0x00134EE4) and 0x0013F27C have **no caller at all**, and no
  `bl` into the block exists from outside it: the family is reached through computed jumps, not
  direct branches. That is why so many of these have empty caller lists and why the first pass
  could not do better than 0.42-0.45.

The one exception is 0x0013BD40 (`maybe_Video_VlcDispatchEntry2_B`, kept 0.42): it is a jump-table
fragment with the code index in `in_r12`, so "Entry2" is a positional label, not a proven role.

### 2. Best correction: 0x001CA48C is a random roll, not a wrap

`maybe_Math_WrapIndexIntoRange` -> **`Math_RandomRange`** (0.60). The asm is

```
add r0,r0,#8 ; mvn r1,#0x80000000 ; bl 0x51B1FC ; add r1,r5,#1 ; bl 0x11CD80 ; add r0,r1,r4
```

i.e. `low + (random31(rng+8) % (high-low+1))`. That is exactly the `state+8` / `0x7FFFFFFF` roll
the confident `Math_RandomChanceBelow` (0x001CA3A0) and `Math_Random_InitState` (0x001CA378) use,
followed by a modulo and the low offset. 0x0051B1FC is the 64-bit LCG step
(`state = state*mult + inc`, then scaled by its second argument). Nothing wraps - the old name was
wrong about the operation.

### 3. 0x001C9F9C is a constructor, not a pool reset

`maybe_Ui_PooledRecord_ResetA` -> **`maybe_Ui_Record_Ctor`** (0.35). 0x001E4B98 is not a pool
allocator: its asm is `ldr r3,[pc]; str r3,[r0]; strb r1,[r0,#4]; strb r2,[r0,#5]; str r1,[r0,#8];
bx lr`, a base constructor. 0x001C9F9C calls it, overwrites the vtable with 0x007598C0 and clears
the fields, so it is a derived constructor.

### 4. 0x001E30D8 does more than timers

`maybe_Ui_PanelState_ResetTimers` -> **`maybe_Ui_PanelState_ResetSequence`** (0.45): it resets the
card slots (0x00379400), clears the running flag f_60 and installs the default duration pair.

### 5. Two confirms with asm proof

- 0x001C33EC `Ui_BaseObject_Delete`: `bl 0x1C33FC; pop {r4,lr}; b 0x10F6CC`, and 0x0010F6CC is the
  deleting-destructor thunk (`sub r1,r0,#8; ldrd r0,r1,[r1]; ldr r2,[r0]; ldr r2,[r2,#4]; bx r2`).
- 0x001C5390 `Ui_Window_ReleaseEmbeddedChild`: `add r0,r1,#0x1C34; mov r1,#0; bl 0x61B79C; ...;
  ldr r2,[r1,#0x18]; mov r1,#1; bx r2` - deactivate, then destroy through virtual +0x18.

### 6. Why 26 stayed `maybe_`

- The Actor model block (0x001CBB70, 0x001CBDE0, 0x001CAB74, 0x001CAFE4, 0x001CB070, 0x001CB304,
  0x001CC6B8, 0x001CA7E4) is a vtable-slot API whose slots (+0x3C/+0x40/+0x94/+0x9C/+0xE4/+0x120/
  +0x11C/+0xE8) are still unnamed, so the names can only describe the call sequence.
- The three message-window updaters (0x001C4E00 / 0x001C4E50 / 0x001C4EE8) are line-for-line the
  same shape on three different children, so their differing names (NamePlate / Paging /
  WindowStyle) stay guesses.
- 0x001F2DB6, 0x001C245C, 0x001C1F24, 0x001C7D78 and 0x001CB070 carry `unaff_` / `halt_baddata`
  and stay at 0.30-0.32 per FACTS.md.

## Tooling notes for the next worker

- `grep -rl` over `decomp/readable` (18k files) took **86 s** for one constant. Do not repeat it.
  `tools/fn.py --find` plus reading `asm/text/text_*.s` at an exact address is instant
  (`out/scratch/R3_062/asm.py` does the latter in ~0.2 s).
- `decomp/xref.json` caller lists are unreliable for mid-function addresses: 0x001CA48C is listed
  with two callers although no `bl #0x1ca48c` exists anywhere in `asm/text`.
- `tools/fn.py` only prints a dossier when a readable C file exists; for the many helpers that have
  none (0x0010F6CC, 0x0051B1FC, 0x001E4B98, ...) the asm window is the only source.
