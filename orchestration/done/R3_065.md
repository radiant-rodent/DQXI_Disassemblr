## Main findings (what changed the verdicts)

### 1. The evaluator table is real, but it has 60 entries, not 72

`0x007286A0` is an array of `{fnptr, this_adjust}` pairs. Entry 0 is `0x003267C0`, entry 24 is
`0x00325FEC`, entry 59 is `0x0032654C`; the table ends at `0x00728880` and the words after it are
small integers (`0x3C`, `0x3F`, `0x41`, ...), not code. The dispatcher `0x00326428` allows
`kind < 0x48` (72), so kinds 60..71 would jump into that data - either a latent bug or a table that
was truncated. The dossiers' "72-entry table" and their "Slot N" numbering are both wrong: "slot N"
was a batch position, not a table index (slot 14 in the dossier is table entry 24).

The dispatcher itself is now fully read:

```
kind = row[idx].f_28;                 // idx = track->f_8, row base = self->f_244 + 0x30 + idx*0x2C
if (kind >= 0x48) return track->f_0;
if (row[idx].f_29 != requestedId) return track->f_0;
tail-call table[kind](self, track);
```

So a caller asks for parameter `requestedId`, only rows whose `f_29` matches answer, and the row's
`f_28` picks the evaluator. That is why every slot's mismatch path returns `track->f_0`.

### 2. Best correction: eight `EvalDefaultE..L` slots are `EvalScale`, not `Default`

`0x3264A4..0x326560` is `bl 0x325BDC; vldr s1,[r4]; vmul.f32 s0,s0,s1` - a **multiply**. The real
`Default` family (`0x3260E8`, `0x3261CC`, `0x3263F8`, `0x326410`, `0x3267C0`) is `vadd.f32`. The
first pass had already noticed the bodies were "byte-identical to EvalScale" in the summary but left
the `Default` name, which describes the wrong arithmetic. Renamed `Ui_Tween_EvalScaleE..L` (0.50),
keeping the letter so the old name still maps.

### 3. Second correction: `0x0033598C` is `nn::err`, not sound

Every callee is the fatal-error applet: `Err_FatalErrInfo_Init` (0x51CBF8),
`Err_LaunchFatalErrorApplet` (0x51CC68), `Err_ThrowFatalError` (0x51CCFC), and FACTS.md pins
`0x51BA34..0x51CD40` as CTR SDK `nn::err`. The 0xF80-byte stack block is a `FatalErrInfo`, not a
sound channel-work block. Renamed `Err_ThrowFatalErrorWithCode` (0.50).

### 4. Vtable dumps settled six class names

Reading the `.word` tables in `asm/rodata/rodata_00745000.s` gave each destructor's class from its
own vtable rather than from its body:

| vtable | class | evidence |
|---|---|---|
| `0x764240` | battle damage popup | `0x32CCB4` slot 0, `0x32CBF8`, `0x32CC54` slot 3 |
| `0x76484C` | `Field_NpcAction_RunToLink` | `0x3317A8` slot 0, `RunToLinkSetup` slot 1, `RunToLinkUpdate` slot 3 |
| `0x764880` | `Field_NpcJumpAction` | `0x331D9C` slot 0, `Setup` slot 1, `Update` slot 3 |
| `0x7648B4` | `Field_NpcAction_RunTowardTarget` | `0x331F44` slot 0, `Start` slot 1, `Update` slot 3 |
| `0x7641B8` | `Ui_DiveManager` | `0x32C33C` is slot 2, right after `Ui_DiveManager_Dtor`/`DeletingDtor` |
| `0x764454` | `Field_Actor` | `0x32DD74` slot 0, `Field_Actor_BeginEffectState` before it |

Two destructors the first pass called `Gfx_Sprite_*` (`0x32DBD0`, `0x32E52C`) are field
actor/scene-node classes: their vtables `0x7642DC` / `0x764394` carry
`Field_Actor_ReleaseAttachedEffect`, `Field_Actor_RestartActionSequence`,
`Field_SceneNode_CreateChild` and `Field_Actor_UpdateVisibility`.

### 5. `0x00329D14`'s vtable literal is `0x00763E68`, not `0x00329D54`

The literal-pool word **at** `0x329D54` holds `0x00763E68`, and that vtable carries the named
`Ui_TwoListWindow_Init` (0x329AFC, slot 0x20) and `Ui_TwoListWindow_UpdateChildSelection`
(0x329A8C, slot 0x18). So the class is a two-list window variant - the old "Panel" wording was in
the right family. It is a subclass (slots 0/1 are its own dtor `0x329DB4` / `0x329D60`) and the two
embedded objects use the emotion-balloon (`0x767258`) and pane-group (`0x75ECE0`) vtables, so the
subclass name is still open and the entry stays `maybe_`.

## Not verified

- No emulator or runtime test - this is a name-only change.
- **The `Ui_Tween` prefix is an inference, not a proof.** The mechanism is proven (60-entry
  function-pointer table, dispatcher, keyframe pair + mode byte + random jitter), but the subsystem
  label is not: the callers are battle UI code (`Battle_EvaluateStatusConditions`,
  `Battle_RollAilmentInfliction`, `Battle_MessageRow_BuildLayout`, ...) and the table copier
  `0x326564` is named `Ui_CopyDefaultLayoutTable`. I confirmed at 0.50 rather than higher for that
  reason, and kept the prefix because the 14 slots already confirmed by R_061 use it - renaming half
  a table would be worse than a slightly wrong prefix.
- Which of `Field_Actor` / `Field_SceneNode` owns vtables `0x7642DC` and `0x764394`; I named
  `0x32DBD0` after the actor side and `0x32E52C` after the scene-node side only to keep them
  distinct.
- What `0x5E7848` does to the actor (detach vs. reset).
- The meaning of the `0x3C` length in `0x32DE04` and of the `0x221` byte it clears.
- Whether the `0x48` bound in the dispatcher is a bug or the table really was truncated at 60.
