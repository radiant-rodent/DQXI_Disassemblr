## The main finding: 44 of the 50 are interior labels, not functions

The batch scanner creates a candidate whenever it sees a `0xB5xx` byte pair (its Thumb `push`
heuristic). In this batch that fired 41 times inside two enormous field scene-object spawners, and
three more addresses are interior to ordinary functions.

The proof is one word of the image per address (`original/exefs/code.decompressed.bin`, file offset
`addr - 0x00100000`):

| address | first word | meaning | enclosing function |
|---|---|---|---|
| 0x00336190 | `0xEBF7B503` | `bl` | `Gfx_SpriteActor_AddChildC` 0x00336054..0x003361C0 |
| 0x0033DF68 | `0xEB0BB585` | `bl` | `maybe_Field_SceneObject_ApplyRecordModel` 0x0033DEC4..0x0033E288 |
| 0x0033ED60 | `0xEB0BB588` | `bl` | `maybe_Field_SceneObject_InitFromRecord` 0x0033EB5C..0x0033FECC |
| 0x00341394 | `0xE51FB540` | `ldr fp,[pc,#-0x540]` | `maybe_Field_SceneObject_InitFromRecordB` 0x003400B4..0x003418A0 |
| 0x00343650 … 0x003499C8 (27) | `0xE1CDB5B0` | `strh fp,[sp,#0xb0]` | spawner 0x0034354C..0x0034A038 (27,372 B) |
| 0x0034A140 … 0x0034CD20 (13) | `0xE1CDB5B0` | `strh fp,[sp,#0xb0]` | spawner 0x0034A03C..0x00353070 (36,916 B) |

`b0 b5 cd e1` is exactly the `0xB5xx` pair the heuristic reads as a Thumb prologue. A function entry
cannot be a store into an already-built stack frame, so these are interior addresses.

The two spawners are **single functions**, not function-pointer tables: each has exactly one
`push {...,lr}` prologue, exactly one return (`pop {r4-r11,pc}` at 0x0034A038 and
0x00353070), and **no data word anywhere in the image** points into either range. They are giant
`switch` bodies with inlined case bodies of roughly 1,000 bytes each.

The block *roles* the first pass guessed are nevertheless right: all 40 spawn-block names match
their `*_Init*` / `*_Setup*` callee one-for-one (`Sprite2D` → `Gfx_Sprite2D_InitFromDesc`,
`MarkerAnimated` → `Field_Marker_SetupAnimatedObject`, `EffectBillboardEmitter` →
`Effect_BillboardEmitter_Setup`, …). So the entries are `kept_maybe` at 0.30 with the name kept and
the summary rewritten to say plainly that the address is not a function entry.

## The six real functions

### 0x00319558 — corrected → `Ui_TwoPaneWindow_ApplyCursorMoveRequest` (0.50)

Vtable slot 0 of `0x0076317C` (siblings `Ui_Window_LayoutRows`, `Ui_Widget_UpdateAnimatedChildren`,
`Ui_TwoPaneWindow_ShowSecondPane`). Disassembly:

```
ldr r1,[r0,#0x98]! ; vldr s0,[pc] (=1.0f) ; ldr r1,[r1,#0x2c] ; blx r1     ; child->vt[+0x2C](child, 1.0f)
ldr r1,[r4,#0x184] ; ldrbne r0,[r1,#0x14] ; tstne r0,#1 ; ldrb r0,[r4,#0x14c]
ldrsb r3,[r1,#0x18] ; ldrsb r2,[r1,#0x17] ; ldrsb r1,[r1,#0x16]
add r0,r4,#0x138 ; b 0x1a60a0
```

`0x001A60A0` is `ldr r0,[r0,#0x38]; b Ui_Cursor_Move`, so the three bytes at +0x16/+0x17/+0x18 are
**signed cursor deltas** (dx, dy, wrap), not a position. The old name claimed a visibility update;
the body only reads the visibility bit and moves a cursor. The float argument on the child virtual
is the FACTS.md "VFP s0 argument silently dropped" trap.

### 0x003627B8 — confirmed → `Actor2D_Ctor` (0.50)

The class descriptor `0x00764D20` is a vtable whose slots are `Gfx_Sprite_CreateInstance`,
`Actor2D_ReRegisterObject`, `Container_IntrusiveList_NotifyAll`, `Field_SceneNode_UpdateMapRecord`,
`Actor_ApplyModelRecordFast`, `Field_SceneObject_ForceVisible`, and the only code reference to it in
the whole image is this function's literal pool. The sibling `0x00362B2C`
(`maybe_Actor2D_CtorWithSprite`) has the same shape.

### 0x00364A14 — corrected → `maybe_Field_SceneNode_AccumulateChildState` (0.40)

`0x0053CD1C` is not a transform merge: it builds the closure `{0x00537E70, acc, extra, context}` and
calls `0x006EF5AC`, a subtree walk that tests each node through `node->vt[+0x44]`. `0x00537E70`
itself is `return !(node->f_44 & 2) || node->f_45 == 0`. Nothing is broadcast and no transform is
computed, so the old name was wrong on both words. What `outState[1]` counts is still unknown, hence
`maybe_` at 0.40.

### 0x00364640 — kept_maybe, summary corrected (0.45)

The second argument is **not** a descriptor: the literal at `0x0036466C` is the ASCII string `"Nut"`
(`4e 75 74 00`), so the destructor detaches a part by name through `owner->vt[+0x84]`. The sibling
slot `+0x0C` (`0x00364670`) compares `self+0x2C` as a float against `owner+0x24->f_44`, which pins
the cached `owner+0x37C` as a float. What the `"Nut"` part is (a model bone or a bolt-like
attachment) is unverified, so the name stays.

### 0x00304900 — kept_maybe, summary corrected (0.40)

Step 0 of the small-window step table at `0x00729398` (entry 0; entry 2 is the named
`Ui_SmallWindow_InputToState1`). The disassembly (0x00304900..0x00304D44) shows: a global "pool
dirty" byte test, a rebuild of a shared pool of `0x1C`-byte records (zeroed, class descriptor
`0x007F52B8` installed, stored through `*0x007BE300`), then reads of the input state and of two save
bytes at `bag+0x985C` / `bag+0x2CFD`, then `std_InlinedVector16_PushByte` calls pushing sub-state ids
6, 0xB, 0xC..0x18 onto `self+0x3B8`. What the `0x1C`-byte records are is unverified.

### 0x0036B5D4 — kept_maybe, summary improved (0.45)

Creates eighteen child panes (ids 0..8 and 10..18, 9 skipped, high half = `self+0x28 << 16`) through
`0x001A6680`, then fills them from the UTF-16 string (`wcslen` 0x00100B74, `std_wcsncpy`,
`std_wcsncat`, `Str_WcsStr`, `std_memcpy`) and plays the layout animation. Ghidra truncates the body
at the `wcslen` tail call (mis-marked `noreturn`, FACTS.md). No vtable references the address, so
"NodeList" stays a guess.

## Open problems / not verified

- No emulator or runtime test (name-only change).
- What the `0x1C`-byte records rebuilt by `0x00304900` are.
- What the `"Nut"` part is, and the class behind vtable `0x00765244`.
- What `outState[1]` in `0x00364A14` counts.
- Whether the two giant spawners are one `switch` each or several functions with merged epilogues.
  The single-return evidence says one, but a compiler that tail-merges epilogues would look the same.
- `decomp/xref.json` caller lists are **wrong** for every address in this batch: a full-image `bl`
  scan finds zero callers for all five real functions, so the dossier's `CALLERS` lines
  (`Field_HitTestActors`, `Field_Actor_SetPlacement`, `maybe_Ui_State_Apply`) are false edges.

## Suggested follow-up tasks

1. **False-entry sweep.** Delete or flag every symbol whose first word is not a plausible prologue
   (`push {...,lr}`, `sub sp` + `str lr`, or a leaf-function start). This batch alone would lose 44
   entries; `0x00352DBC` (`Field_SceneObject_SpawnByType`) is a wrong *confident* name of the same
   kind and should be re-examined.
2. **Fix the disassembly desync at 0x00343630** (and the equivalent points in the second spawner):
   the linear sweep switches to Thumb there and produces garbage for the rest of the function, which
   is why Ghidra could not decompile 0x0034354C, 0x0034A03C or 0x003400B4. Recovering those three
   functions would give the field scene-object spawner its real case table.
3. **Name the `*_Init*` / `*_Setup*` callee pairs** listed in this batch's evidence (e.g.
   `0x00194878`, `0x0043FEC4`, `0x002F3098`, `0x006C2D4C`, `0x003A43D8`, `0x004C91E0`). They are the
   per-object-kind constructors of the field scene spawner and each one pins a spawn case.
4. **Repair `decomp/xref.json`**: it reports callers that do not exist for mid-function addresses.
   A `bl`-only rebuild would make the dossiers trustworthy for this kind of batch.
