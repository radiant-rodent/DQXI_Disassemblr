## Key decisions and findings

1. **Not every function-pointer table has a destructor at slot 0.** Several tables in this batch
   start with an ordinary virtual: `0x00763464` (Battle_Ui_MemberWidget), `0x0076A120` (the
   dungeon-window controller), `0x0076A46C` (the message window), `0x0072C508` / `0x0072C538`
   (the dive-form handler tables). "Slot 0 ⇒ deleting destructor" is only safe when slot 0 is the
   `vptr-reset + operator delete` pair. This is what let `0x003C36E8` be re-attributed.

2. **Corrected: `0x003C36E8` `maybe_Battle_Ui_ActionSequence_Step` → `maybe_Battle_Ui_MemberWidget_Update` (0.35).**
   It is slot 0 of four vtables (`0x00763464`, `0x00763938`, `0x007694A0`, `0x00769C60`) whose slot 1
   is the confident `Battle_Ui_MemberWidget_SelectActor` (0x003C332C), so the class is the battle
   member widget, not an action sequence. The body fetches the sequence object at `self+0x122C`,
   asks `0x00630DC8` for the pending count, marks byte `+0x108` on each widget returned by
   `vt[0x48]`, then handles the current widget's state `0x99`. Body is damaged (`halt_baddata`),
   hence 0.35.

3. **Confirmed: `0x00371F5C` → `Field_PlayerActor_DeletingDtor` (0.55).**
   Heads vtable `0x00765964`, whose slots 1/3/14 are the confident `Field_Actor_ResetStep`,
   `Field_Actor_UpdateInputDirection` and `Model_ApplyFacingTilt`, and whose slots 10–12 are the
   player-only attachment/motion virtuals.

4. **Corrected: `0x003D49CC` → `Ui_EquipWindow_DeletingDtor` (0.55).**
   Heads vtable `0x00769F58`, whose slot 1 is the confident `Ui_EquipWindow_Init` (0x003D4834) and
   whose remaining slots are the Gfx node methods. Spelled `DeletingDtor` rather than `DtorDelete`
   because `0x0046CFB4` already carries `Ui_EquipWindow_DtorDelete` (batch N_111) and
   `tools/merge_names.py` rejects duplicate names.

5. **Corrected: `0x003D1554` `maybe_Gfx_ResourceHandleList_Ctor` → `maybe_PendingList_Ctor` (0.40).**
   The ctor sets the done byte `+0x6A` to 0 and the resume node `+0xC` to 0 — exactly the two fields
   the drainer `0x003D1454` reads and writes — and that drainer is called only from UI screen-close /
   SE helpers. The "Gfx_ResourceHandle" subsystem was therefore wrong; the list is a pending-work
   list.

6. **Corrected: `0x003D9DF0` `maybe_Ui_SlotTable_NextRandomIndex` → `maybe_Ui_SlotTable_NextIndex` (0.25).**
   No RNG call appears in the body or in the disassembly prologue. The function copies `+0x23C`
   bytes out, or increments the counter at `+0x234` (capped by `+0x238`) and byte-swaps it.

7. **Three addresses in this batch are not entry points.**
   - `0x0036DCF6` is two bytes into the `blt` at `0x0036DCF4`; the coherent code is the epilogue at
     `0x0036DCFC` (`ldr r0,[r4,#0xC]; add sp,sp,#0x480; pop {r4,r5,r6,r7,r8,pc}`).
   - `0x0036E566` is two bytes into the `blt` at `0x0036E564`; coherent code starts at `0x0036E56C`.
   - `0x003C3704` is the fall-through continuation of `0x003C36E8` after the `beq` at `0x003C36FC`.
   All three dropped to 0.20–0.25 and their summaries now say so.

8. **Name collision left open on purpose: `0x0036CE84`.**
   Its vtable `0x007656F0` is the field actor-action table (slot 3 = confident
   `Field_ActorAction_Update`, slot 10 = confident `Field_ActorAction_OnStateNotify`), so the honest
   name is `Field_ActorAction_DeletingDtor`. That name is already used by `0x0036C304` (batch N_127,
   vtable `0x0076563C`), whose recorded evidence ("body `func_00193E44(); delete 0x0010F6CC`") does
   **not** match the disassembly — `0x0036C304` is `bl 0x001B7DB0; b 0x0010F6CC`. Rather than create a
   duplicate name I kept `maybe_` at 0.48 and recorded the conflict here.

9. **Two stale claims in the previous docs corrected.**
   - `0x00361FC4`'s doc cited "vtable `0x00764BB0` slot 29"; it is slot 29 of the table that starts at
     `0x00764C6C` (slot 1 = `Gfx_Sprite_CreateInstance`).
   - `0x003D70E0`'s doc called `0x0018CC14` a "has content" test; it is now named
     `Text_ResolveStyleBlock`.

10. **`0x0036D39C`'s class is now characterised but not named.** Vtable `0x00765730` slot 16
    (`0x0036D3AC`) resolves `Item_LookupRecord(*(u16*)(self+0x12))` and formats it with
    `Text_FormatMessageArg`, and slot 15 is the confident `Ui_ShowInfoMessage` — so it is a field
    action that reports an item. The "TurnAction" label is still unsupported, so it stays `maybe_`.

## Suggested follow-up tasks

1. **Reconcile `0x0036C304` (N_127) with `0x0036CE84`.** N_127's evidence does not match the
   disassembly (`bl 0x001B7DB0`, not `0x00193E44`). Decide which of vtables `0x0076563C` and
   `0x007656F0` is the base `Field_ActorAction`, then give `0x0036CE84` the freed name.
2. **Find the constructors of the field action family.** No `.text`/`.data` word references
   `0x0076563C`, `0x00765678`, `0x007656B8`, `0x007656F0` or `0x00765730`, so the vtable is installed
   by some indirect mechanism. Locating it would settle the base/derived order for five classes at
   once.
3. **A false-entry sweep.** `0x0036DCF6` and `0x0036E566` are two bytes into a `blt`; `0x003C3704`
   and `0x003C6BE4` are mid-function continuations. A pass that deletes every symbol whose first
   word is not a prologue (`push`/`stmdb sp!`) would remove a whole class of these.
4. **`0x003D1454` / `0x003D1554`.** Name the seven callers of the drainer; that would let the list
   class be named properly instead of `maybe_PendingList_Ctor`.
5. **`0x003D5888` / `0x003D59B4`.** Both touch the `+0x224` mode byte, so they are one class; the
   `maybe_Ui_TwoTextWindow_Ctor` (0x003D59F8) neighbour should be resolved to settle which.
