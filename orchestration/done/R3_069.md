## Method: the vtable dump was the missing evidence

The dossier's `NEIGHBOURS` field was empty for all 50 addresses and `scores.jsonl` gives every one of
them a context score of 0-2, so the pre-baked context alone could not settle anything. What did settle
22 of them was reading the **raw vtable** out of `build/code.bin` (base `0x00100000`) and resolving each
slot through `symbols.json` plus the `decomp/readable/functions/*_<addr>.c` filenames (the freshest names).

Two facts that make this reliable, both verified here:

- A class's vtable is usually **0x34 bytes (13 slots)**, but some are 0x3C or 0x40, so the grid has to be
  confirmed per table rather than assumed.
- **Slot 0 is a deleting destructor only when its body is `base_dtor + 0x0010F6CC`.** Several tables in
  this batch (0x0076DCC0, 0x0076E724) have a normal method at slot 0, so the body decides, not the index.
- In the field actor-action family the layout is stable: slot 1 = Start, slot 2 = End, slot 3 = Update.
  Six independent vtables confirm it (`Field_ActorAction_OnStartBase`, `Field_ClimbAction_Start`,
  `Field_ActorAction_StartAscentAnim`, `Field_BreakObjectAction_Start`, `Field_OpenItemBoxAction_Start`,
  `Field_ActorAction_FrogJumpStart` all sit in slot 1).

## The findings that matter

### 1. Four class labels were "one table off"
The first pass read the *next* vtable in rodata as if it belonged to the function. Fixed:

| address | old name | new name | why |
|---|---|---|---|
| `0x003E3ABC` | `maybe_Field_SceneEffect_DtorDelete` | `maybe_Field_ActorAction_DeletingDtor_vt76AE88` | the Field_SceneEffect slots are in 0x0076AEBC, not 0x0076AE88 |
| `0x003E50F8` | `maybe_Field_DragonJumpAction_DtorDeleteB` | `maybe_Field_Actor_DeletingDtor_vt76B090` | the dragon-jump table is 0x0076B05C |
| `0x003E57DC` | `maybe_Field_OpenItemBoxAction_DtorDelete` | `maybe_Field_GondolaAction_DtorDelete` | 0x0076B10C's slot 3 plays `"Gondola_Nut"` |
| `0x003E58B4` | `maybe_Field_HellTackleAction_DtorDelete` | `Field_OpenItemBoxAction_DtorDelete` | 0x0076B140's slots 1/3 are the item-box Start/UpdateEnd |

### 2. `0x003E4A3C` is the base field actor-action destructor
`maybe_Gfx_Effect2D_DtorDelete` -> `Field_ActorAction_DeletingDtor_vt76AFF4` (0.50). Slot 0 of vtable
0x0076AFF4, whose slot 1 is the confident `Field_ActorAction_OnStartBase` (0.65) and slot 2 its OnEnd
twin; `Field_ActorAction_Ctor` (0x003E4A10) sits immediately before. The old name came from the misnamed
0x003E49CC. Its five "callers" (`Ui_Object_DtorDelete`, `Actor_Action_Riremito_Dtor`, ...) are calls to
the base-destructor thunk `0x003E4A4C`, which `xref.json` maps to the nearest preceding symbol — a trap
worth remembering for every other deleting-destructor batch.

### 3. `0x00409710` is the frog-jump destructor, but the body is folded
`maybe_Ui_TextWindow_DeletingDtor` -> `maybe_Field_ActorAction_FrogJump_DeletingDtor` (0.45). Slot 0 of
vtable 0x0076D5AC, whose slots 1/3 are `Field_ActorAction_FrogJumpStart` (0.80) and
`Field_ActorAction_FrogJumpUpdate` (0.75). Kept `maybe_` because the same 24-byte body is also called
directly from Ui code (`Ui_EquipWindow_HandleInput`, `Ui_NumberedTextWindow_SetVisible`): the linker
folded several classes' deleting destructors onto one address, so the address serves more than one class.

### 4. `0x004137B8` is a Start hook, not a stop
`maybe_Field_ActorAction_StopTurn` -> `Field_ActorAction_TurnStart` (0.50). Vtable 0x0076DF34's slot 0 is
the deleting destructor `0x00413A78` (disassembly `ldr r1,[pc,#0x10]; str r1,[r0]; bl 0x294C88;
b 0x10F6CC`), so this address is slot 1 = Start; slot 3 is the confident
`Field_ActorAction_TurnTowardTarget`. The old name read the cleared `+0xE4` flag as a stop.

### 5. Two bodies did not match their names at all
- `0x003E737C` `maybe_Field_Actor_DeleteFromScene` -> `maybe_Field_Actor_UpdatePoseAndScale` (0.40).
  Disassembly is exactly `bl 0x003E7770; b 0x00386DE8` with self in r0, and 0x00386DE8 is the confident
  `Model_Actor_UpdateScaleB`. Nothing is deleted or unregistered.
- `0x003D10FC` `maybe_Battle_TargetMarkerList_Ctor` -> `maybe_Field_SceneObject_SubCtor` (0.30). The xref
  now shows one caller, `Field_SceneObjectCtor_vt21066C` (0x00210274). Ghidra status is
  `missing_function` (no readable C at all), so the body was read from `asm/text/text_003C0048.s`:
  zero `+0x1A0..+0x1AC`, then `0x00116AE0` (memset) on 0xD0/0xD0/0x59 bytes.

### 6. Name collisions were avoided, not created
`Field_ActorAction_DeletingDtor` (0x0036C304), `Ui_MessagePage_Dtor` (0x001DB5D0) and
`Ui_MessagePage_ReleaseParts` (0x003E2FF8) already exist, so 0x003E4A3C and 0x003E2B20 got vt-suffixed
names (`Field_ActorAction_DeletingDtor_vt76AFF4`, `Ui_MessagePage_Dtor_vt76ADA8`). All 17 new names were
checked against `symbols.json` plus every `orchestration/naming/out/*.json` and `refine/out/*.json`
before use.

### 7. Honest keeps (28)
- Damaged or undecodable bodies: `0x003E28B2`, `0x003F4BE0`, `0x003F6262`, `0x00417EE8`, `0x0041DBEC`,
  `0x0041AD34`.
- Interior-address artefacts, not function entries: `0x0043C6D4`, `0x0043C730`.
- Template copies whose callee is unnamed: `0x003E41D4`, `0x00413434` (identical bodies at 0x003ADB74).
- Deleting destructors whose vtable has no named class-specific slot: `0x003E0F3C`, `0x003E37D0`,
  `0x0040C3C8`, `0x0040CCC4`, `0x004145BC`, `0x00414610`, `0x00413BC0`.
- `0x003ECA7C` / `0x003ECAC0`: the readable C is truncated (one call only); the disassembly shows the
  full body, but the caller that would prove the smith-menu identity is unnamed.

## Not verified / open problems

- No emulator or runtime test (name-only change), so none of these names is behaviourally confirmed.
- **Which vtable is the root `Field_ActorAction`?** 0x0076AFF4 (slot 1 = `Field_ActorAction_OnStartBase`)
  and 0x0076563C (slot 0 = `Field_ActorAction_DeletingDtor`, N_127) both look like it. N_127's evidence
  says 0x0036C304 calls 0x00193E44, and its readable C does say `func_00193E44()`, but the disassembly
  calls 0x001B7DB0 (shown as `Ui_Layout_DeleteSubComponentD` by the nearest-symbol mapping) — so either
  the readable C or that name is wrong. That entry deserves a re-check.
- What the byte returned by `0x0029E488` means (it is a small wrapper that pushes `{r3,r4,r5,r6,r7,lr}`
  and calls 0x006F250C); this blocks `0x003E41D4` and `0x00413434`.
- What `0x00707C1C` does with the (table, context) pair registered by `0x00410168`.
- The "Gondola" class name rests on the `"Gondola_Nut"` animation string alone.
- Whether `0x005930EC` (`Ui_CriticalPopup_PlayAnim`) is really popup-specific: `0x0041B1F4` calls it on
  eight talk-window rows, which suggests a more generic "play the appear animation" meaning.
