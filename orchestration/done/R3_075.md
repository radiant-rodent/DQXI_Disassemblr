## What I did

Read the pre-baked dossier `orchestration/naming/refine/dossiers/R3_075.md` in chunks, then checked
every decision that hinged on a damaged body against the raw disassembly
(`python tools/fn.py 0xADDR --asm N`, plus direct reads of `asm/text/text_00240048.s` and
`asm/rodata/rodata_00725000.s` for the two `missing_function` addresses and the data blobs).

## Open problems / not verified

- No emulator or runtime test (name-only change).
- The class prefixes of the 25 kept entries are still guesses; several rest on a single field offset.
- `0x0025BBC8`'s two callees (0x006722D8, 0x00248870) are unnamed, so only the call shape is known.
- `0x00264FC8` is asserted to be data (its words are all pointers and decode to `rsbseq` garbage),
  but I did not prove that no code branches into it.
- `decomp/xref.json` callee lists are unreliable for several of these addresses: `0x003818C0` (a
  176-byte body that only calls one virtual) is credited with `Item_LookupRecord` and
  `Data_FindRecordIndexById`; `0x003ADB44` (48 bytes, two calls) with four unrelated callees;
  `0x003A08F8` with the whole `Fs_*` family. The xref maps a call to the nearest preceding symbol,
  so merged symbols swallow their neighbours' calls. I treated every callee list as a hint and
  checked the body before using it.
- `decomp/readable/functions/` was being rewritten by a concurrent merge worker while I worked
  (mtime 18:53, after the dossier was generated at 18:49). Two `fn.py` calls transiently reported
  "no readable file found" for files that existed; a retry fixed it. If a later worker sees the same
  symptom, retry before concluding the file is missing.
