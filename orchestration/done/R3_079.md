## Results Summary
- Total functions evaluated: **50**
- Confirmed (confidence >= 0.50): **3**
- Corrected (confidence >= 0.50): **29**
- Kept maybe (confidence < 0.50): **18**

The dominant finding of this batch is that **most of these symbols are not function entries at
all**: they are mid-function split symbols (Ghidra started a "function" at a branch or at a `bl`
inside a larger routine) or outright misaligned addresses that fall *inside* a 4-byte ARM
instruction. The readable C for those is `halt_baddata()` / coprocessor garbage, which is why the
first pass could only guess. Every decision below was made from the disassembly
(`asm/text/text_*.s`), not from the damaged C.

### Confirmed (3)
1. `0x006E59C4` -> `Ui_ScrollList_ScrollBy` (0.50)
   - `self->f_4C += delta`; page count = `(vtable[0x64](self) - 1) / 3 + 1` (0x66666667 magic);
     when the 4th argument is non-zero the index wraps into `[0, pages-1]`. The identical wrap
     block is duplicated at `0x006E6460`, confirming the template.
2. `0x006D6060` -> `Pack_CollectNumberedEntries` (0.50)
   - 32-slot buffer at `out+4..out+0x84`; each name is looked up through `0x0053D4C4` and the two
     ASCII digits at `baseName+6/+7` are bumped from `'00'` to `'31'`
     (`movlo r8,#0x31; movlo r7,#0x30`).
3. `0x006E7744` -> `Container_Value_Set` (0.50)
   - Tag switch on `node+4`: 1 = word copy, 2 = 16-bit copy, 3 = word copy + child-list re-parent
     (old children released through `0x0051435C`), 4 = other branch.

### Corrected (29) — highlights
- `0x0060E79C` / `0x0060E7B0` -> `Gfx_Screen_ForwardFadeOut` / `Gfx_Screen_ForwardSetAlphaVariant`.
  Both are 20-byte forwarders (`cmp r1,#0; ldreq r0,[r0,#4]; ldrne r0,[r0,#8]; mov r1,r2; b ...`)
  to the real entries `0x0017BD1C` / `0x0017BDC8` (`Ui_Bar_StartFadeOut` / `Ui_Bar_SetAlphaVariant`;
  the symbols at `0x0017BD2C` / `0x0017BDD0` are themselves split). `self+4`/`self+8` are the two
  per-screen fade windows created by `maybe_Gfx_Screen_BindTarget` (`0x0060E73C`) via
  `Ui_CreateFadeWindow`. The old `GetTarget` name described a getter that does not exist, and
  `0x0060E7B0` was mis-filed as a 4-byte VFP literal.
- `0x0060E810` -> `Gfx_Screen_GetClearColorByMode`. The real entry is `0x0060E7FC`; this symbol
  starts at its `bl #0x17bc6c` and then runs a 7-case jump table that returns byte-swapped global
  colours. It **returns** a colour, so the old `SetClearColor` verb was wrong.
- `0x0060EEDC` -> `Gfx_SpriteObject_Dtor_Part2`. Tail of the destructor at `0x0060EE9C`: tears down
  the child at `+0x24C`, unlinks self from the list at `+0x234`, calls `Field_Object_DtorBase`
  (`0x00335DAC`) and the allocator free (`0x0010F6CC`). Not a screen clear.
- `0x00613350` -> `Save_SetNameBuffer_Tail`. The `b #0x100a6c` (memcpy) tail of the 44-byte
  `Save_SetNameBuffer` at `0x00613324`.
- `0x006135F8` / `0x00613638` -> `Field_LevelMap_AddCell_Part2` / `_Part3`. The real entry is
  `0x006135E4`: reject names of 7+ wchars, scan the 0x32 records of 0x8C bytes at `self+0x5FE4` for
  a free slot, `memcpy` 0x84 bytes, copy `+0x84/+0x85/+0x88`, return 1. Not a "load cells" routine.
- `0x00619D28` / `0x00619FC4` -> `Object_DeletingDtor` / `Object_DeletingDtorB`. Identical
  `bl 0x00193E40` (installs base vtable `0x00758AE0`) + `b 0x0010F6CC` (allocator free) thunks.
  The `Ui_Bar_*` callers listed for `0x00619FC4` actually call `0x0061A0F8`, an internal entry of
  the same 496-byte region (the UI animation-slot colour setter).
- `0x00622020` -> `Ui_Widget_ReleaseGpuBufferEx_Tail`. Tail of `0x00621FB4`: releases the sub-object
  at `self+4` through `0x0036B514` and frees the allocation 4 bytes before the returned pointer.
- `0x00623134` / `0x00623178` / `0x00623258` -> `Sq_ObjectPtr_ReleaseTemp_Tail` /
  `Script_Object_Dtor` / `Script_Value_Dtor`. Squirrel `SQObject` refcount release
  (`tst #0x08000000`, decrement at `+4`, `blx [vtable+8]`) plus two destructors of script-bound
  classes (vtables `0x00780258` / `0x0075A728`, and a 0x14-byte value freed with
  `0x00147AEC(size 0x14)` — the old summary said 0x18).
- `0x0062DA24` / `0x0062DBC0` -> `Camera_BuildVisibleTargetLists_Tail` /
  `maybe_Camera_FindVisiblePathEntry_Tail`. Split epilogues of the two camera functions (they end
  exactly at these addresses), not misparsed data seeds.
- `0x00636E44` / `0x0063E064` -> `Container_GetPooledEntry` / `Container_GetPooledEntryThunk`.
  Relative-offset record-pool lookup (count at `+0x60`, offset array at `+0x58+0x24`,
  entry = `&offsets[i] + offsets[i]`). The same body at `0x00713C7C` has **241 call sites** across
  field, battle, script and UI code, so the helper is generic — the old `Anim_CheckMotionCondition`
  and `Data_InitRecordTables` names were both wrong.
- `0x0063A0A4` / `0x0063A6D4` -> `maybe_Ui_Record_GetField2CKind13` / `Kind12`. Getters that return
  the sign-extended byte at `record->f_4->f_2C`, gated on the kind byte at `+0x29` being 13 / 12
  (`0x0066C950` / `0x0066C978`). Not text updaters.
- `0x006E75FC` / `0x006E76B0` -> `Container_Value_Dtor` / `Container_Value_DtorB`. Install vtable
  `0x00781004`, release the owned member via `0x0050E5D8`, chain `Container_ObjectDtor`
  (`0x0011EE0C`). The `Script_*` subsystem of the old names was unsupported.
- `0x006E6854` -> `Gfx_EffectNode_InitFromName`. `0x005F541C(self, name)` (sets the ready byte at
  `+0x41`, parses the name) then `vtable[0x40](self, 4)`. The readable C body (a string-hash
  lookup) is a misparse; the disassembly is the ground truth.
- `0x006E2014` -> `Ui_Object_DtorThunk2_Tail`. The `b #0x10f6cc` tail of the 12-byte thunk at
  `0x006E2008`, not 4 bytes of alignment padding.
- `0x0062209E`, `0x0063349E`, `0x006E5A26`, `0x006E6466` -> `maybe_Code_MisalignedSymbol<addr>`.
  Each address falls **inside** a 4-byte ARM instruction (`ldrlt r0,[r4,#0x10]`,
  `ldrblt r0,[r0,#0x7c]`, `strlt r1,[r4,#0x4c]` twice), so Ghidra's Thumb decode produced the
  coprocessor garbage. There is no function at these addresses.

- **`0x00636E44` / `0x0063E064` pool semantics.** The relative-offset layout is certain; whether the

  chosen deliberately over a subsystem guess.

  refcount protocol are certain; which game class owns vtable `0x00780258` is not.

## Suggested Follow-up Tasks
1. **Split-symbol cleanup pass.** ~20 of these 50 symbols are mid-function splits or misaligned
   addresses. A dedicated pass could either delete them from `symbols.json` or mark them with a
   consistent `_Tail` / `_PartN` / `MisalignedSymbol` convention so modders stop reading
   `halt_baddata()` bodies as real functions. The `_Tail`/`_Part2`/`_Cont`/`_Body` convention
   already exists in `symbols.json` (33 names) — it just is not applied consistently.
2. **Name the real entries that Ghidra missed.** `0x0060E78C`, `0x0060E7A0`, `0x0060E7FC`,
   `0x00613354`, `0x006135E4`, `0x00619FD4`, `0x0061A0F8`, `0x006230EC`, `0x00623114`,
   `0x0062A480`, `0x006E96E4` and `0x00713C7C` are real code addresses with no symbol at all.
   Several of them are the *actual* functions whose split tails are in this batch.
3. **`0x00713C7C` / `0x00713AF4` container helper.** 241 call sites; worth a dedicated dossier to
   pin down whether the pool holds strings or records, which would also settle `0x00636E44`.
4. **`0x0060E7FC` `Gfx_Screen_GetClearColor` family.** `Ui_Bar_GetClampedValue` (0x0017BC6C) and
   `Ui_Bar_StartFadeOut` / `Ui_Bar_SetAlphaVariant` are called on the per-screen fade windows, so
   the `Ui_Bar_*` prefix on that whole 0x0017BBFC..0x0017BE38 block looks wrong; a pass over it
   would fix several names at once.
