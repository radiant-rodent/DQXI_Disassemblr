# R5_001 — second naming pass (refine), 117 low-confidence `maybe_` functions

## What I did
Re-examined all 117 functions of `orchestration/naming/refine/batches/R5_001.txt` using the
pre-baked dossier (`dossiers/R5_001.md`) plus `tools/fn.py --find` for family conventions, and wrote

confidence/`maybe_` and damaged-decompilation rules; both fixed as described below).

## Notable corrections (old name was wrong, not just weak)
- `0x001C8704` `maybe_Gfx_ResourceHandle_AcquireType1` → `Field_GadgetList_CreateEntry` (0.5): all four
  callers are `Field_GadgetList_FindOrAdd*` / `Event_GetOrAddActorSlot`, and the only constructor callee is
  `Gfx_SpriteAnimationBank_Create`; the 0x3C-byte wrapper is a cached gadget-list entry, "type 1" meant nothing.
- `0x001CBA7C` `maybe_Actor_FindComponentByEvent` → `Actor_FindComponentInState` (0.5): `0x00639954` is the
  proven active-state test, so the loop finds the component that *is in* a state, not one that "accepts an event".
- `0x0038104C` `maybe_Ui_Window_FindSubObject` → `Ui_Smith_FindStandObject` (0.5): both callers are
  `Ui_Smith_*` and the class comparison is literally `g_smithStandActor3DClass`.
- `0x0032DE54` `maybe_Field_Actor_SpawnStateEffect` → `Field_Actor_CreateItemModelEffect` (0.5):
  `Item_LookupRecord` on the held item id band 0xAA3..0xB3A and `Ui_ItemModel_Load(0x2DE)`.
- `0x002399D4` `maybe_Ui_Overlay_SetMarkerState` → `maybe_Ui_ActorAttachSlot_SetHandle` (0.45, kept maybe):
  14 callers are action/effect-end paths and the body ends in `Ui_RegisterActor(unit+0x4A88/0x4Bxx, handle, 0)`;
  "overlay marker" was wrong, but the Thumb body is damaged so it stays `maybe_`.
- `0x002175BC` `maybe_Menu_TalkParty_CreatePanel` → `Ui_WindowPart_CreateByIndex` (0.5): only caller is the
  generic `Ui_UpdateWindowParts`, and the switch builds ~30 unrelated widget classes; nothing here is talk-party
  specific (`talk_party.bxon` lives in `Ui_TalkParty_GetLayout`).
