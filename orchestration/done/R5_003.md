# R5_003 - second naming pass (refine) for 149 low-confidence `maybe_` functions

## What I did

Worked through all 149 addresses of `orchestration/naming/refine/batches/R5_003.txt` in batch order,
using the pre-baked dossiers (`orchestration/naming/refine/dossiers/R5_003.md`) plus the named
callers/callees/neighbours they list. For the ~15 cases where the dossier wording alone could not
separate two readings I opened the readable C file named in column 4; for one address the dossier was
missing entirely (see below) I read the recovered C directly. No asm/ or decomp/ tree walks, no
re-generated batches, no changes to shared files.

Result written to `orchestration/naming/refine/out/R5_003.json` (149 objects, one per batch address,
same order as the batch file).

## Numbers

| change | count |
|---|---|
| confirmed (dropped `maybe_`, confidence 0.50-0.55) | 30 |
| corrected (better/other name) | 15 |
| kept_maybe (< 0.5, name keeps `maybe_`) | 104 |

Confidence distribution: 0.25-0.35 for damaged/duplicate bodies, 0.40-0.45 for names whose action is
readable but whose owner class is inferred, 0.50-0.55 only where a **named** caller or a named global
pins both the action and the subsystem.

`python tools/check_refine.py R5_003` -> `R5_003: OK` (first run flagged one problem: a confident name

## Notable corrections (worth a second look by the M-task)

* `0x002C8C3C` - casino jackpot screen ctor parts (kept maybe_, no callers, all callees casino UI).
* `0x001D1FC4` `maybe_Camera_UpdateScreenTargets` - the body is a timer-driven **target-handle swap**
  (`Camera_ReleaseTargetHandle` -> `Camera_SetupFromRecord` -> `Camera_BuildVisibleTargetLists`), not a
  follow-position blend; caller is `Camera_UpdateScreenViews`.
* `0x001D2222` - decompiler mid-function split of 0x001D1FC4, not a callable "Ex" variant (kept maybe_).
* `0x004BFA20` `maybe_Battle_Ui_ActorFocusSequence_Update` - every callee and the only caller are battle
  UI, so the old `Field_` prefix was wrong.
* `0x003E4C14` / `0x00413C50` and the other `Field_*Action_*` names: kept at 0.40-0.45, no callers.
* `0x001D233C` `maybe_Field_ComputeActorPlacementPoint` - callers use a **world** point, never a screen
  position (`ActorScreenPosition` was misleading).
* `0x0060E110` `maybe_BattleScene_InitAnimSlots` - caller is `BattleScene_UpdateState`, it starts four
  `Anim_TimeTrack_Init` slots on the battle scene, not a FieldLevel sprite object.
* `0x004A781C` `maybe_Gfx_SpriteActor_CreateFromDescriptor` - callees are sprite-actor create/mesh/dtor;
  it does not bind an animation instance.
* `0x0020FA34` `maybe_Battle_UiFlow_CalcEffectWeight` - sole caller `Battle_UiFlow_BuildEffectList`;
  builds a weighted resistance-class value, not "column flags".
* `0x001E16D4` `maybe_Field_ComputeLocalMoveDirection` - normalises + rotates the move vector; it never
  clamps.
* `0x005929EC` `maybe_Battle_Unit_UpdateSkullRunPose` - poses an actor (twin of 0x004F129C); no anchor.
* `0x00106280` `maybe_Snd_ReleaseFinishedStreamTransfers` - only caller `Snd_StreamManager_Update`, so it
  reaps sound stream transfers, not Gfx uploads.
* `0x0031EFFC` `Ui_Widget_UpdateFadeTween` - 13 callers across UI/battle/event all drive widget tweens, so
  `Ui_TextFade_Update` was too narrow. Note: this one is a **confident** rename at 0.50.
* `0x0037446C` `Field_ActorAction_TurnActionCtor` - the ctor installs the named
  `g_fieldActorTurnActionVtable`, which identifies the action.
* `0x005AED74` `maybe_Gfx_EffectPart_ApplyRowFadeConfig` - writes fade to an effect part; the
  `Ui_ScrollList` prefix was wrong.
* `0x001FE804` `maybe_SequenceBase_StepSlotCursor` - 26 callers across battle UI, battle action sequences
  and the talk window; the old `FieldParty_AdvanceMemberCursor` was far too narrow.
* `0x0038859C` `maybe_SceneFlow_ApplyStateResource` - five scene-flow callers; it picks FS transfer
  priority **and** palette entry.
* `0x00541F10` `maybe_Data_SoundStreamResetPadding` - not a function: 12 bytes of literal data
  (`0x3F800000`, 0, 0) directly before `Sound_StreamBuffer_Reset` at 0x00541F1C.

## Open problems / not verified

* `0x003890C0` has **no dossier and no readable entry**: the batch points at
  `decomp/readable/recovered/maybe_Battle_Ui_UpdateStateMachine_003890c0.c`, which exists but is a
  "recovered, 0 bytes" stub with bad instruction data. I read that file directly, kept the name at 0.25.
  The dossier generator should include recovered/ stubs, otherwise such addresses are invisible to the
  next refine batch.
* The `Fx_EmitParticles*` family (Ring/Sphere/Cone/Arc/Radial*/Random*/Oriented) is 12 near-identical
  copies of `Fx_BuildParticleRenderQuad` + `Fx_InitSpawnedParticle` spawn loops. Only the shared builder
  is proven; none is corroborated by a caller, so all stayed `maybe_` 0.35-0.45. Resolving them needs the
  emitter-type dispatch table (which spawn function each emitter kind selects), not more reading of the
  copies.
* Same for the `Fx_UpdateParticle*` / `Fx_UpdateParticleList*` letters: A-H are confirmed as family
  members (their list updaters call one per particle) but the letter itself is only an ordinal.
* `0x00496B50` / `0x004973E8` / `0x0048FCA4` all compute the same `f_738 + f_EB8 + f_AF8` monster-UI stat
  and none identifies the stat as attack. Left as `maybe_Battle_Monster_GetAttackPower*` /
  `maybe_Monster_GetAttackStat` with that caveat in the summaries; a dedicated pass over
  `Battle_MonsterUI_Dispatch` row kinds would settle it.
* `0x001D1FC4` region: 0x001D2222 is a decompiler split and should ideally be dropped from future
  batches (it cannot be named independently).
* Names marked 0.50-0.55 are confirmed from named callers/globals, not from disassembly. Nothing here
  was checked against the ARM assembly (batch rules), so a mis-split body could still hide a wrong
  signature.
