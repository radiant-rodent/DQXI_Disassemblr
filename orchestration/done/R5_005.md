# R5_005 — refine pass 2, batch R5_005 (150 functions)

## What was done

Re-examined all 150 low-confidence `maybe_` functions of
`orchestration/naming/refine/batches/R5_005.txt` against the now-named neighbourhood
(named callers/callees, vtable siblings, string/constant hits, newer batch outputs) and wrote
one decision per address to `orchestration/naming/refine/out/R5_005.json`.

Worked from the pre-baked dossier `orchestration/naming/refine/dossiers/R5_005.md` in chunks of
~10 functions, appending to the output JSON after every chunk (15 chunks, scratch copies in
`out/scratch/R5_005/c1..c15.json`). `python3 tools/fn.py` was used only where the dossier was not
enough (missing readable file, vtable lookup, extra callers).

## Result

| change | count |
|---|---|
| confirmed (dropped `maybe_`) | 29 |
| corrected (better name) | 75 |
| kept_maybe (still ambiguous) | 46 |
| **total** | **150** |

33 entries reach confidence 0.5; 117 keep the `maybe_` prefix. Every address of the batch is
covered, in batch order, no duplicates.

Validation: `python3 tools/check_refine.py R5_005` → `R5_005: OK`.
The first run reported 5 problems (4 entries at confidence 0.5 that still carried `maybe_`, and
`maybe_UiCore_CheckSubObjectAndNotify` flagged as a predicate name on a void function); all five
were fixed by dropping the prefix where the evidence supported 0.5 and renaming the predicate to
`maybe_UiCore_EnsureSubObjectAndNotify`.

The full test run was **skipped** on purpose: rule 5 exempts naming/refine batches (this task only
writes one JSON file, which the dispatcher validates). Nothing else was executed, so no build or
bit-match claim is made here.

## Notable corrections (wrong first-pass guesses)

- **0x001E2DA4** `maybe_PartyPanel_RefreshRowAvailability` → `maybe_Ui_CasinoPanel_RefreshRowAvailability`.
  The whole `0x001E2xxx` block is the casino poker/prize panel base class (`Ui_PokerWindow_Ctor`
  installs `g_uiPokerWindowBaseVtable`); the body is the gold-cap / x1-x10-x100 price row refresh.
- **0x0032324C** `maybe_Ui_Window_DtorWithTweens` → `maybe_Battle_HpGaugeWindow_DtorDelete`: the body
  installs `g_battleHpGaugeWindowVtable`, which names the class outright.
- **0x004A1C08** `maybe_Ui_SelectListOwner_DtorDelete` → `maybe_Ui_CompositeWindow_DtorDelete`: it
  restores the seven-line-select, composite and three-line-two-select vtables in turn.
- **0x00651954** `maybe_Camera_TestPointOccluded` → `maybe_Field_TestPointVisible`: it returns 1 when
  both checks *succeed*, i.e. the old name inverted the result.
- **0x003AF004** `maybe_Monster_FieldBehaviour_UpdateChase` → `maybe_Field_Actor_UpdateSteering`:
  integrates turn rate / move-speed scale / forward speed; no chase target anywhere.
- **0x004645F4** `maybe_Font_GetAtlasCellForChar` → `maybe_Font_GetGlyphMetricForRow`: the return value
  is the glyph record's `+0x16` metric as a float; the atlas cell is only bound as a side effect.
- **0x00611998** `maybe_Ui_Equip_BuildItemGrid` → `maybe_Item_UseCreateMessageWindow`: it creates a
  `g_uiMessageWindowBaseVtable2` object and rolls a 0..99 chance; it builds no grid.
- **0x0018F974** `maybe_Field_CreateGimmickSystem` → `maybe_Scene_Ctor`: sole caller is
  `Ui_TitleScreen_Ctor`; two `Os_LightEvent`s plus 400 0x40-byte entries. (vtable `0x00782234` is a
  generic base descriptor reused by many classes, so it does not identify the class.)
- **0x002448BC** `maybe_Ui_Layout_SetCornerGradientColors` → `maybe_Ui_LayoutRequest_LoadResourceSections`:
  the body is pack-section resolution (section `0x69D`); the corner colours are the last few lines.
- **0x00105ACE** `maybe_Snd_StreamVoice_UpdateFragment` → `maybe_Snd_StreamSlot_UpdateAll_Tail`: it is a
  Ghidra mis-split tail of `0x00105584`, not an independent function.
- **0x00155664** `maybe_Script_ReturnTop` → `maybe_Script_ReturnNull`: 16 bytes of `Sq_VmPushNull(); return 1`.
- **0x003AD0F4** `maybe_Ui_SkillPanelWindow_DtorBase` → `maybe_Ui_Window_DtorBase`: vtable `0x00759388` is
  the shared UI base (also used by `Battle_Popup3D`, `Ui_SakusenWindow`).
- **0x004675CC** `maybe_Ui_SelectWidget_Create` → `Ui_PartySelectWindow_Create`: installs
  `g_uiPartySelectWindowVtableB`.
- **0x0027E368 / 0x0027E794 / 0x0027F1B0 / 0x0027FA20 / 0x00280050 / 0x00280498 / 0x002813FC** were
  spread over three prefixes (`Ui_BattleCmd_`, `Ui_BattleWindow_`, `Ui_PartyPanel_`); they are one
  class — the battle command window handler table — and are now `maybe_Ui_BattleCommandWindow_*`
  named by what each slot actually does.
- **0x0020DF9C** `maybe_Battle_PartySlots_NotifyChanged` → `maybe_Battle_PartySlots_AssignActor`: it
  calls `Menu_AssignActorToFreeSlot` and refreshes the slot; nothing is notified.
- **0x004A34A0** `maybe_Ui_MessageWindow_ShowEntry` → `maybe_Ui_ItemUse_ShowMemberResultPane`: it is the
  item-use result pane (same shape as 0x004D64F8), not a message window.
- **0x00381ED8** `maybe_Field_Menu_OpenPlaceMenu` → `maybe_Field_Menu_ApplyMemberRowAction`: the place id
  only selects which transition ids are used; no place menu is opened.
- **0x003CD9A4** `maybe_Battle_Ui_MemberWidget_SetInputState` → `..._ForwardSelection`: it pushes the
  selection out and clears `f_4DF`; it never sets an input state.
- **0x00395C00** `maybe_Ui_TextWindow_RefreshLine` → `maybe_Ui_MessageWindow_AdvanceControlStream`: no
  line refresh exists; the trailing `wcslen(NULL)` is the known `0x00100B74` noreturn artifact.

## Kept as maybe_ (46) — why

- Damaged decompilation (`halt_baddata`, `unaff_rN`, `in_ZR`, bad instruction data):
  0x003C3560, 0x005DB8A4, 0x002448BC, 0x0027E368, 0x0027E794, 0x00153280, 0x0060C5F8,
  0x003AF004, 0x002B558C.
- Body invisible because of the mis-marked-noreturn `std_ConstructArray` / `wcslen`:
  0x0020F13C, 0x00611998 (partly), 0x004645F4 (partly).
- No readable file at all (recovered stub only): 0x0027E794, 0x003AF004, 0x002B558C, 0x002B0C14.
- Class attribution unproven although the action is clear: 0x00438FE4, 0x005A04B8, 0x005A147C,
  0x0046CC5C, 0x0046CE28, 0x0018F974, 0x003AD0F4, 0x001E2DA4, 0x0020DF9C.
- Variant letter / sibling distinction unverifiable: 0x00414A94 (`DealHandC`), 0x00153280 (`SiftAlt`),
  0x00438FE4 (`MotionB`).

## Open problems / suggested follow-ups

1. **Handler tables.** Dumping `0x00728B8C`, `0x00728BD4`, `0x00728C94`, `0x00728D84`, `0x00728D8C`,
   `0x00728D9C` (slot index -> handler) would let a later pass name the whole
   `Ui_BattleCommandWindow_*` family by slot instead of by inferred action, and would confirm the
   class name.
2. **0x001CFF84** (ctor of the 400 x 0x40 entries in 0x0018F974) is unnamed; naming it would identify
   the scene object and turn `maybe_Scene_Ctor` into a real name.
3. **0x006115BC** (called by 0x00611998 with `(window, category, 1)`) is unnamed; it decides whether
   `maybe_Item_UseCreateMessageWindow` is a drop/lottery check or something else.
4. **0x0020F13C** needs a manual asm read: the readable C is one `std_ConstructArray` call because
   `0x00100050` is mis-marked noreturn.
5. **0x005DB8A4** and **0x003C3560** are worth a re-decompile (bad instruction data / mid-function
   split symbol `0x003C3594`); no naming pass can do better until then.
6. Several entries still carry a `maybe_` class prefix that a vtable dump would settle
   (`g_uiPartySelectWindowVtableB`, `0x00759388`, `0x00782234` are all shared or generic).

## Honesty note

Everything above is a naming decision backed by the readable C, the named neighbourhood and the
constants listed in the evidence fields. Nothing was verified by running the game or the emulator,
and no build/test was run (batch rules). Where the body was damaged or missing, the entry says so and
keeps `maybe_` with confidence < 0.5 rather than guessing.
