1. **`func_0062F070`, `func_0010EBD8`, `func_00123594` are still unnamed.** They are the
   count / pop / splice trio behind the entire `Ui_Window_ResetChildren*` family (about 20 functions
   in this batch alone). Naming them would let a later pass confirm that whole family at once.
   Suggested names from the observed use: `Ui_Object_CountChildren`, `Ui_Object_PopChild`,
   `Ui_Object_SpliceEmbeddedPane`.
2. **`Text_MarkLayoutDirty` (0x00487FC0) and `Battle_CalcRandomDamageVariance` (0x00491270) look
   misnamed.** 0x00491270 takes a *record id*, looks up `func_0063E05C(dm,id)` and rolls
   `func_001CA474(rng, 0, record->f_2E)` — it is a per-record random value, not a damage variance.
   0x00487FC0 sits inside the poisoned 0x00485D90..0x00497900 range. Both are outside this batch.
3. **`Ui_PokerWindow_*` callers of 0x001E4DD0** (`maybe_Ui_EquipMenu_SelectItem`) disagree with the
   body, which is clearly equipment selection for a party member. Either the three caller names are
   wrong or this is a shared casino-prize path. Worth a dedicated look.
4. **`maybe_Ui_SplitFunctionArtifact` (0x00263CD8)** is not a function — it is an instruction inside
   0x00263A70. It should be folded back by a symbol-boundary fix, not named.
5. **`maybe_Battle_Ui_UpdateState2A3D_Thumb` (0x00481C4C)** is a byte-level duplicate of 0x004824E0
   decoded separately because it lies inside 0x00481B5C's range. Same symbol-boundary issue.
6. The `Battle_UiFlow_*` prefix on 0x002DD1D8 / 0x002DD7E0 / 0x002DF270 rests only on a table entry
   at 0x00726F90; nothing in the bodies mentions battle. Left as `maybe_`.
