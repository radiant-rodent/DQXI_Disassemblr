* `0x002590A0` `Ui_CharaStatusWindow_Ctor` (0.60) - was `maybe_Ui_AnimRefPart_Ctor`. Installs
  `g_uiCharaStatusWindowVtable`, sits 0x3C bytes before `Ui_CharaStatusWindow_Dtor` (0x002590DC) inside
  the `Ui_CharaStatusWindow_*` block, and its only caller is `Ui_TsuyosaWindow_CreateInstance`.
* `0x0071371C` `Effect_FindPackInfoByName` (0.55) - was `maybe_Container_HandleResolveAsTypeByName`.
  The target class is the constant `g_effectPackInfoClassRecord`, not a parameter; callers
  `Effect_SetupPackInfo` / `Gfx_Effect2D_AttachPackInfo` pass pack-info names.
* `0x00501CFC` `Svc_AcClient_CloseIfSessionOpen` (0.55) - the 24-byte body is only
  `if (CheckSession()) AcClient_Close();`; the monitor/refcount tail belongs to the next entry 0x00501D14.
* `0x0018D380` `maybe_Ui_ListData_RemoveSlot` - a 19 x 0x98-byte list-data table, not the party roster
  (PartyMember is 0x12EC x 31). Its neighbour 0x0018D3D4 is called with `g_uiListData+0x6B8` and an id list.
* `0x003BDE6C` / `0x003BDF58` -> `ActorActionSeq_CollectPendingNodeIds` / `..._CollectStartedNodeIds`:
  both store *ids* of 0x10-byte action-sequence nodes (complementary +0xC filter), the old
  `Party_CollectMemberIds` name claimed the wrong kind of id.
* `0x001D6B90` `maybe_Ui_Window_Ctor_vt759F88` - callees `Ui_WindowState_Init` + `Ui_SlotTable_Ctor`, so the
  `Field_ObjectCtor` prefix was the wrong subsystem.
* `0x004C6DDC` `Field_CreateSpriteObject` - 24-byte pool alloc + `g_gfxSpriteObjectVtable`; "interactable"
  came from the caller, not the callee.
* `0x003FB8A0` `Battle_AnimElement_PlayDefaultMotion` - the state-2 gate is not proven to be a damage
  reaction, so the `PlayDamageAnim` claim was dropped.
* `0x0010AD08` `Gfx_CommandQueue_AcknowledgeSlot`, `0x0011233C` `Os_DspService_InvokeShutdownCallbacks`,
  `0x00107100` `maybe_Os_FlushDspServiceCommand`: three engine helpers whose old names named the wrong owner

* `0x0040D4F8`/`0x0040D620` `Effect_SpriteEmitter_SetupA/B` - child descriptor is `childType = 2` plus

## Open problems / not verified

1. **0x0039CBBC chain conflict (affects 3 entries).** `Text_LayoutSingleLine` (0x0039CBBC, conf 0.55 from
   batch N_055) is reached *only* through `maybe_Math_Vector3_Interpolate` (0x001D5098), whose five callers
   are all `*InterpolateOwnerVector*` / `Battle_Unit_ApplyModelParts`. One of the two readings must be
   wrong. I left 0x001D5098, 0x0039CA80 and 0x0039C954 as `maybe_` with the conflict written into their
   evidence; whoever resolves 0x0039CBBC should revisit those three in the same edit.
2. **Seven "deleting destructor" template copies** (0x0031F9C4, 0x0031F9F0, 0x003CDEB4, 0x002AB358,
   0x00424318, 0x0042B148, 0x004DDA60, 0x0059DED4) have byte-identical bodies and (mostly) no callers, so
   the class in the name cannot be verified from the body. They stay `maybe_` at 0.35-0.4; a batch that can
   read the vtable tables in the data sections would settle them cheaply.
3. **0x0062A4BC / 0x00629FEC** (`Monster_Count*`/`SumRecordedCounts`): the mechanics are clear but both
   callers (`Ui_ShopItemInfo_FillStats`, `Menu_StatusScreen_InitFaceAndCommands`) do not fit a monster walk
   and record accessor 0x0063DCA4 is unnamed. Kept `maybe_`.
4. **0x00646BB4** depends on 0x003AA574, which is still only `maybe_`/`SkillPanel_CanUnlockSkill` although
   here it is used as a category membership test - that callee is probably misnamed.
5. `0x0030BF0C`, `0x002CB154`, `0x002040D0`, `0x0055C84E`, `0x00108F32`, `0x006E5C68`, `0x006E5EE4`,
   `0x006555E0` are damaged/mid-function splits; they cannot be named better than they are now.
6. 0x005E54B8 keeps `maybe_` even though the tail call `Effect_FindOrCreateInstance` is unmistakable,
   because the body uses unaff_r6/r9/r10/r11 and in_cr7 (checker would reject >= 0.5).
