## Kept `maybe_` (96)

Mostly because the decisive evidence is still missing: no callers at all, damaged decompilation
(`unaff_*`, `in_ZR`, `halt_baddata`, `coprocessor_*`), unnamed vtables, or callers that contradict
the guess. Notable cases where I deliberately did **not** upgrade:

- `0x002798E8 maybe_Battle_Ui_AddUnitToRowGroupWithValue` — body is a byte copy of the now-confirmed
  0x00279760, but its two callers are equip code (`Party_EquipItemIntoCategorySlot`,
  `maybe_Model_RandomizeEquipSlots`), which contradicts the battle-row reading.
- `0x00634C3C maybe_Ui_Overlay_GetSlotScaleY` — the two listed callers do not actually reach this
  entry point (`Field_Actor_UpdateWalkInput` calls 0x00634CA4, a small getter *inside* this symbol's
  range), so the call-graph attribution is a mid-function split artefact.
- `0x0063ECF0`'s 155 "callers" are the same artefact: they target the tiny data-row getters Ghidra
  merged into the symbol (0x0063EE1C..0x0063F108), not the recipe check.

## Open problems / not verified

- The `0x0062Cxxx` cluster still carries UI names (`Ui_Overlay_HasReachedTarget`, `Ui_HitTestRows`,
  `Ui_HitTest_FindCell`) that cannot be right for map-cell work. That blocks
  `0x00634114 maybe_Field_Actor_CanPlaceAtCell` and the whole 2D map-chip family.
- `0x0062D6D8` is named `Camera_FindEntryCoveringPosition` but is called from NPC move code and from
  the move-override table path; one of the two readings is wrong. It is not in this batch, but it
  blocks `0x0062DDF0` / `0x0062DF2C`.
- `0x0063ECF0` is a split symbol: the recipe check ends well before 0x0063EEAC, and the rest of the
  1856-byte range is a run of tiny `dm->f_XXX` row getters. Those getters deserve their own batch.
- 15 addresses in this batch have no `decomp/readable/functions/` file; their bodies live in
  `decomp/readable/recovered/`. `tools/fn.py` returns "no readable file found" for them, which cost
  extra lookups. Worth teaching `fn.py` about the `recovered/` directory.
- `0x004E5B3C` / `0x0046E8B8`: the installed vtables (0x0077B190, 0x007731C8) are not in
  `symbols.json`, so the `Battle_CameraRange` class label rests on the caller name only.
