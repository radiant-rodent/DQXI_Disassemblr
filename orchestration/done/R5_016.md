Second naming pass over the 150 functions listed in
`orchestration/naming/refine/batches/R5_016.txt`, using the pre-baked dossiers in
`orchestration/naming/refine/dossiers/R5_016.md` (read in chunks of ~10-15 functions) plus

## Notable corrections (old name was actively misleading)

- `0x003E56A0` `maybe_Field_ClimbAction_SyncCameraToAnimSpeed` → `maybe_Field_ClimbAction_PauseAnimation`:
  the body writes no float and touches no camera; it is byte-identical to the pause tail at `0x00301D8C`.
- `0x00301D8C` `maybe_Field_Actor_StopAndHide` → `maybe_Field_Actor_PauseAnimation`: no hide/visibility call at all.
- `0x001EAC04` `…ResetListsAndShowPane` → `…ResetListsAndHidePane`: the broadcast flag is 0, and the twin
  `0x001EAD74` uses 1 for "show".
- `0x001F330C` `maybe_Game_GetFlag275A4` → `maybe_Game_IsUnlockFlagSet`: the named caller
  `Ui_RecipeBook_SyncModeFromRecord` stores the result in a local it calls `maybe_unlockFlag` and pushes
  the locked entry id `0x14` when it is 0.
- `0x002DB204` `…SetLinkRecord` → `maybe_Battle_Effect_SetLinkSkill`: the resolver `0x0018C1B8` is the
  documented `SkillRecord` wrapper (`dm->f_2BC`), so the linked record is a skill.
- `0x0036E870` `…SetValueFromByte` → `…SetValueFromMemberId`: the callee `0x0035EB98` is the documented
  party-member record accessor.
- `0x0020C08C` and `0x0037C8E0` are **not functions** (mid-function split symbols); renamed to
  `…_Tail` fragments so nobody mistakes them for entry points.
- `0x00316B4C`, `0x003A9CD0`, `0x004653A8`, `0x004797D4`, `0x00446E14`, `0x0044D780`, `0x004B0098`:
  the class was named by a vtable store or a named callee (`g_uiIconCache…`, `g_uiMovieTextWindowVtable`,
  `g_uiFourRowTextWindowVtable`, `g_uiTwoLineMessageWindowVtable`, `Ui_TenRowWindow_BuildRows`,
  `AnimObject_ForwardEvent`, `enableAutoAct02` + `"Act_02"`), replacing guessed or address-based prefixes.

## What is NOT verified

- 91 entries stay `maybe_` at confidence 0.2-0.45. Most have **no callers at all** and no vtable slot,
  so the class prefix is still an address-neighbourhood inference. I did not invent names for them.
- 12 addresses have no readable file under `decomp/readable/functions/`; I used the
  `decomp/readable/recovered/` stubs, several of which are `halt_baddata`-truncated
  (`0x003BC418`, `0x002C244C`, `0x002DD81C`, `0x0049AA74`, `0x003D75EC`, `0x003D82E0`).
- The five `…IsEventSceneValid` copies (`0x002B4918`, `0x002B6BAC`, `0x002F26B8`, `0x003A15A8`,
  `0x003A26AC`) share one 32-byte body that just returns `func_00636AFC(work+8->f_6C)`. The callee is
  still unnamed, so the "event scene valid" wording is unproven for all five.
- `0x001F4368` (`maybe_Ui_CompositeWindow_Dtor`) and `0x002B3D20` (`maybe_Field_SceneObject_Ctor`) lean on
  the globals `g_uiCompositeWindowVtable` / `g_fieldSceneObjectVtable`, which I could not independently
  verify (a whole-tree grep for them timed out and I did not retry — see below).
- `0x00262AD4` has conflicting evidence: the state ids 0x10..0x12 match the recipe-book state range, but
  the callees (`SaveSlot_IsUsed`, `maybe_Save_GetBlockByteEquals3`) read a save-slot record. Kept `maybe_`.
