# R5_020 — second naming pass (refine), 150 low-confidence `maybe_` functions

## What I did
- Read the pre-baked dossier `orchestration/naming/refine/dossiers/R5_020.md` (all 150 blocks).
- For the 24 addresses the dossier reported as "no readable file found" I read the actual
  `decomp/readable/recovered/*.c` files directly (the dossier generator only looks in
  `decomp/readable/functions/`, so recovered entry points were silently skipped; 19 of the 24 did
  have a body). 5 addresses (0x00304974, 0x0030535C, 0x00316414, 0x00323308, 0x0032B110) have no
  body anywhere and are kept as honest guesses.
- Decided all 150 entries and wrote `orchestration/naming/refine/out/R5_020.json`
  (UTF-8, one object per batch address, batch order preserved).

## Notable corrections (old name was wrong, not just vague)
- `0x00318920` KeyPromptWindow_SetIconVisible → **Ui_SubPart_SetVisibleFlag**: five named callers
  are generic UI helpers (`Ui_SetTwoSubPartsVisible`, `Ui_PaneCrossFade_*`, `Ui_ListWidget_SetModeB`,
  `Ui_MessageWindow_UpdateScrollText`); it is the shared two-sub-part visibility primitive.
- `0x00323BBC` Battle_Popup3D_ReleaseActorHook → **maybe_Battle_Popup3D_PlayTurnAnim**: the magic
  word 0x6E727554 is ASCII `'Turn'`, passed to the same actor slot +0x84 that receives `'Bt_Damage'`
  (0x0032CBF8) and `'dead'` (0x0032A6D0) — an animation tag, not a hook release.
- `0x004664C0`/`0x004664D8` ProfileScreen_* → **maybe_Ui_Root_CallHelper383A90** /
  **maybe_Ui_InputQueue_DrainAndBeginIconLoad**: bodies are a root-singleton helper call and an
  input-drain loop + icon-cache start; nothing mentions a profile screen or cursor.
- `0x00383B5C` Field_IsNotPaused → **maybe_Svc_Content_IsNotReady**: negates 0x0050D8FC, which the
  icon-cache state machine (0x00383B6C) uses next to the content-cache check 0x0050D864.
- `0x003076EC` ActionSeq_RunFlagStep → **maybe_Actor_SelectActionIdByRootFlag**: reads the UI root
  flag 0x00383A80 and dispatches action id 0xF/0x10 through vtable +0x54; no action-sequence state.
- `0x00327E00` SlotWindow_UpdateReelTimer → **maybe_Ui_SlotWindow_AdvanceReelSteps**: the switch maps
  reelStepCounter 5..10 to reel index 5..0; case 0xB restores the global payout pair.
- `0x00304F88` ActionSeq_GetStepKind → **maybe_Ui_DiveStart_GetPaletteByte**: indexes
  `g_uiDiveStartPaletteBytes` by the animator frame and returns a byte.
- `0x003A47F8` Actor2D_HandleObject_DeletingDtorB → **maybe_Ui_Overlay_AuxObject_DeletingDtor**
  (only caller is `Ui_Overlay_CreateAuxWidget`, which allocates it).
- `0x00332E88`-style over-claims fixed where the readable body has no such work:
  `0x00379560` → **maybe_Ui_Window_RefreshTextLabel** (copies present-window label ids, no counter),
  `0x003EC71C` → **maybe_Ui_SmithMenu_ApplyDetailRecordState** (no digit loop),
  `0x003EE7A8` → **maybe_Ui_SmithMenu_CloseDetailIfPending**,
  `0x003AC0E0` → **maybe_Ui_DetailTextBox_SelectEntries** (no skill-panel constant),
  `0x003A8CF4` downgraded to maybe_ because the plate pointer arrives in `unaff_r4`,
  `0x0032B61C` base dtor is 0x00193E44 (the recorded 0x002B09F4 link was wrong),
  `0x00412B6C` → **maybe_Str_WString_InitFromCString** (source is a runtime pointer, not a literal).

## Decisions / notes for the dispatcher
- The dossier's `CALLEES` lists are frequently wrong (e.g. 0x00322884 calls 0x00669DD4 but lists
  0x006698AC MoLive_Stream_BindPacket; 0x00336BB8 calls 0x001A1774 but lists 0x001A14EC). I treated
  them as address-adjacent noise and relied on the body plus the `CALLERS` list (which did match the
  readable bodies wherever I checked).
- `make_dossiers.py` should also look in `decomp/readable/recovered/`: 19 of the 24 "no readable
  file found" blocks do have a recovered body.
- Two entries keep the same wording as the first pass but with corrected confidence/summary; no
  shared files were touched.
