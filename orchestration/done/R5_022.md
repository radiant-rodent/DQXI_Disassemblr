## What changed, by neighbourhood

### CTR service IPC stubs (0x11E9xx-0x11F6xx, 0x11874C)
R_057 already fixed the family convention `Svc_IpcCmd<header hex>` (Svc_IpcCmd20040,
Svc_IpcCmd1100C2Read, Svc_IpcCmdD0082). I applied it to the members of this batch that the first
pass had named by command id only or had given a guessed subsystem prefix:

* `0x0011EBA0` Snd_IpcCmd20 -> **Svc_IpcCmd200040** (header 0x00200040; note its neighbour
  Svc_IpcCmd20040 uses 0x00020040, so the old name was ambiguous)
* `0x0011874C` -> **Svc_IpcCmd150082**, `0x0011973C` -> **Svc_IpcCmd190000**,
  `0x0011F65C` -> **Svc_IpcCmd80082**, `0x0011DED4` -> **Svc_IpcCmd8630000**,
  `0x0011F6C0` -> **Svc_IpcCmd130042**

Two real discoveries here:

* `0x0011709C` was `maybe_Os_AssertAndGetState`; the disassembly of `0x00117078` shows its result is
  passed as the *session handle* to `Svc_IpcCmd8630000` (which dereferences it and issues `svc 0x32`),
  so it is **Os_AssertAndGetSessionHandle** (and `0x00117098` is the same getter entered 4 bytes
  early). `0x00117078` became **Svc_IpcCmd863Request**.
* `0x0011E63C` -> **Os_WaitSemaphore** (negative-count waiters, ldrex/strex, arbitration call) and
  `0x0011EBD8` -> **Snd_SendIpcBuffer** confirmed: its only caller is now the named
  `Snd_QueryChannelInfo`.

### Sound / DSP
Confirmed `Snd_SetupChannelBuffers`, `Snd_SetChannelField1A` (sole caller now
`Snd_SetOutputMode`), `Snd_QueryChannelInfo`, `Snd_FlushChannels` (operates on
`g_dspServiceState`, closes with `Svc_IpcCmd200040`).
`0x00116D1C` was `maybe_Gfx_ReleaseCommandBuffers`; **both callers are named sound functions**
(`Snd_StreamVoice_Update`, `Snd_SetBgmVolume`), so it is now `maybe_Snd_ReleaseBufferPairs`
(0.45 - the object type is still unknown, hence `maybe_`).
`0x001123B0` stays `maybe_Snd_SetUnitFlagBit`: the bitmask/IPC mechanics are clear but its six
callers mix pad readers, buffer code and DSP setup.

### VRAM / Gfx
Confirmed `Gfx_DispatchVramRegionRequest`, `Gfx_GetVramRegionSize`, `Gfx_InvokeCallbacks`,
`Gfx_ResetStateBlock`, `Gfx_GetQueueStatus`, and - after checking the disassembly - the two
bank getters `0x001109A0` / `0x001109DC` (`cmp r0,#0x20000` / `#0x30000`, literal-pool words
0x1F2FFFFF, 0x1F5FFFFF at 0x001109D0/D4 and 0x1F180000/0x1F300000/0x1F380000 at
0x00110A1C..24 plus `moveq r0,#0x1F000000`). Both seeds start 4 bytes into the real functions
(0x0011099C / 0x001109D8) - recorded in the summaries.

### Video decoder (Mobiclip-style)
* Confirmed `Video_ConvertBlocks32_SamePlane` and `Video_ConvertBlocks16_A` because their
  dispatchers are now named (`Video_ConvertSelectB_A` / `Video_ConvertSelect_A`).
* Kept the eight pure-copy `ConvertPlanes*` kernels as maybes: they are byte-identical pitch
  variants with no caller, and the "3 vs 4 planes" wording is not verifiable.
* Renamed the 12 A-instance and 12 B-instance motion-compensation sub-block entries from
  `...ApplyMvCopyN` to **`Video_McPredict<V>ApplyMv<N>` / `..._B`**, i.e. the scheme the
  C instance already carries (`Video_McPredict1ApplyMv2_C`, confirmed in N_038). The old
  "CopyN" wording read like a copy of function N. Callers are the confirmed
  `Video_McPredict<X>ApplyMv[_B]` routines and each entry chains 2 -> 3 -> 4.
* Confirmed `Video_FilterPackedBytesRow` (both callers named decoder functions).
* Left the blend/interpolate/VLC-switch kernels as maybes: no callers, lost base registers,
  unrecovered jump tables.

### Other corrections
* `0x0012033C` `maybe_Gfx_CmdList_ResetSlot` -> **maybe_SlotTable_ReleaseSlot**: 16 callers span
  containers, UI, effects, FS and event handles, which rules out a command-list role; the body
  frees a slot by writing -1 0x98 bytes before the resolved pointer.
* `0x00117458` `maybe_Gfx_BlitWorker` -> **maybe_Os_WorkQueue_ProcessPending**: bitmap walk over
  0x14-byte work records that re-submits live entries.
* `0x0011AC6E` `maybe_Hid_ThumbReader` -> **maybe_MisSeededThumbStub**: the decoded body is
  `return 0x4C` and the 12 callers are destructors, so the HID label was wrong; the address
  itself is the problem.
* `0x00123FAE` -> **maybe_Os_TranslateMainRamAddressInterior** (interior of the now-named
  `Os_TranslateMainRamAddress`).
* `0x00101AA0` `maybe_Thunk_Call00100F04` -> **maybe_std_VprintfFloatHelper** (no more address in
  the name; called only from `std_vprintf_core`, reaches `std_strtod`).
* `0x00118108` `maybe_Os_CheckSemaphoreResult` -> **maybe_Os_HandleSyncResult** (predicate name on
  a void function, flagged by the checker).
* `0x00125098` -> **std_UnwindPersonalityRoutine** confirmed: EHABI compact personality routine
  (`bl` to the bytecode interpreter followed by inline `0x80xxxxxx` opcode words); its 80
  "callers" are exidx references, not calls.

## Not verified / open problems

1. `0x0011B7EC` has **no readable C at all** (only `decomp/ghidra/functions_index.json`) and
   `0x0010F31C` exists only as a recovered stub. Both are kept at 0.2-0.3 with that stated; they
   need a decompilation pass before they can be named.
2. Several seeds are mid-function and should be resynced rather than renamed:
   `0x001109A0` (real 0x0011099C), `0x001109DC` (0x001109D8), `0x0011C818` (0x0011C814),
   `0x001149AA`, `0x00114B12`, `0x00123FAE`, `0x0011AC6E`, and `0x00117098` (duplicate of
   `0x0011709C`).
3. The Ghidra call graph in the dossier is unreliable for some of these entries: for
   `0x001072C4` the recorded callees (0x0010C47C / 0x00112518 / 0x0010C642) are not the actual
   `bl` targets (0x0010C4B8 / 0x001125BC / 0x0010C660). Decisions above therefore lean on callers
   and bodies, and `0x001072C4` keeps its maybe_ with the contradiction stated.
4. `0x0011CB38` is called from `maybe_Hid_SetVibration` and `Os_WaitSemaphore` but carries the
   merged name `Game_GetDataManager` - that name looks wrong (it behaves like an OS scheduler /
   arbiter helper). Not in my scope; worth a dedicated check.
5. The merged readable C still shows pre-R5 names for a few neighbours (e.g. `0x0011E9C4` is
   `maybe_Svc_IpcCmd1100C2` in the file although R5_007 output renamed it
   `Snd_Dsp_SendCommand1100C2`), i.e. the readable tree lags the latest refine output. No action
   taken.
