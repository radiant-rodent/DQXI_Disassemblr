## Honest state of the kept entries

Most of the 94 `maybe_` entries share one of these blockers, documented per entry:

1. **Truncated static initialisers under guard 0x007BE2D0 / 0x007B2D40** — Ghidra marks
   `func_0010009C` noreturn, so the readable C stops at the guard acquire and the object being
   initialised is simply not in the C (e.g. 0x00680C14, 0x0069B5C0, 0x006B65A4, 0x006B68CC,
   0x006B6CFC, 0x006B7038, 0x006B7558, 0x0068ADE8). Their names remain placeholders.
2. **Damaged/split code** — `halt_baddata`, `in_ZR`/`in_OV`, `unaff_rN`, `coprocessor_*`
   (0x006661BEA, 0x006695BC, 0x006640FE, 0x00667F8E, 0x00668552..B2, 0x0066F580/F608,
   0x00673F48, 0x00674E66, 0x006770F2, 0x00142134..0x00142340, 0x0017F5B2, 0x00172698).
   These are fragments, not functions, and the summaries now say so.
3. **No caller and no distinguishable callee** — e.g. `maybe_Pack_*`, `maybe_Field_FindObjectInListA/B`,
   `maybe_Sound_SeqField_NotifyChange` (dropped return), `maybe_Util_ReleaseCountedNode`,
   `maybe_Event_CallHandler`, `maybe_Sys_InitTimingSlot`.
4. **Call-graph edges that do not match the body** — several dossiers list callees that never appear
   in the C (e.g. 0x0064E88C lists `Item_ConsumeForCraft`/`Party_GetSlotCountPlusPending`,
   0x00647F70 lists `MoLive_Stream_BindPacket`). I treated those names as noise and said so in the
   evidence fields rather than naming from them.
5. **Class-registration sites without a name string** (0x00682038, 0x00682208, 0x0068B23C,
   0x00691C0C, 0x006B3314): the registration shape (list head + 0x10-byte node + base/name/factory
   at +0xC/+0x10/+0x14) is certain; the class identity rests on the guessed globals
   (`maybe_g_listPanelClassRecord`, `maybe_g_modelClass`, `g_resourcePackTypeInfo`).

## Open problems / suggested follow-ups

1. **Fix the noreturn mis-marking in the decompiler helper set** (`func_0010009C`,
   `func_00100B74` = wcslen, `func_00100050`, `func_0010009C`'s guard veneer, `func_00172...` splits).
   Each is a cheap Ghidra annotation fix that would expose several dozen static initialisers
   (openings 1 above) — a tooling task, not a naming task.
2. **Dump the class-name strings in the literal pools** of the registration sites
   (0x00682038, 0x00682208, 0x0068B23C, 0x00691C0C, 0x006B3314, 0x006AF8A0 works, others do not)
   and resolve `PTR_LAB_*`/`iRam*` data labels. A tiny rodata-string lookup tool (`tools/str.py 0xADDR`)
   would let a follow-up batch name every `Field_RegisterActorClass_*` in one pass.
3. **Name the 0x007BE2D0 guard family** by grouping on the written global offsets: the truncated
   bodies still differ in the literal pools, so a batch that reads the disassembly (not the C) could
   split them into `*_StaticInit_<global>` groups.
4. **`Ui_SakusenWindow_*` / `Ui_RecordWindow_*` row flags** (0x006541E0) — the consumer semantics of
   the 10-byte row flag byte are still unknown; a UI-subsystem batch with the layout files
   (`editor_projects/`) could pin it.
5. **0x0064F8C0 status pair** — nobody consumes the two output bytes; a caller-based batch on the
   monster-state helper 0x00669250 (returns 6/7/0xC) would finish this one.
6. **0x00668552..0x006685B2 fragments** should be deleted from `decomp/ghidra` symbol tables rather
   than named; they only add noise to every future batch.
