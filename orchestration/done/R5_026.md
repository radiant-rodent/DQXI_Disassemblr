## The big finding: 77 of the 99 addresses are not functions at all

The batch is dominated by the `maybe_Field_SceneSpawnBlock_*` family (77 addresses). The previous pass
had already guessed they were "interior addresses", but assumed the bytes were *data* / damaged code.
They are neither: **they are interior addresses inside real ARM code that `symbols.json` marks as
`thumb`.** The batch scanner cut a fake "function" at every `0xB5xx` halfword (which reads as a Thumb
`push`) inside that ARM code.

Evidence (one `python tools/fn.py 0x00343A5C --asm 40`, i.e. ARM-mode disassembly at the "block start"):

```
0x00343A8C  str   sb, [sp, #4]
0x00343A90  ldr   r0, [r4, #0xc]
0x00343A98  mov   r2, #4
0x00343A9C  ldr   sl, [r0, #0x54]
0x00343AA8  mov   r0, #0x298
0x00343AB0  bl    #0x109dc8        ; Mem_AllocAligned_2
0x00343AB4  cmp   r0, #0
0x00343ABC  beq   #0x343ad8
0x00343AD0  bl    #0x43fec4
0x00343AE8  blx   r2               ; virtual call
```

That is coherent code with real callees - it just is not a function start (no prologue, `sp` already
adjusted, registers used before being set). Same check on 0x0035B3A0 (`bl 0x1C89B0` then
`ldr r1,[r5,#8]` with `r5` never set) and 0x0035C758 (`bl Mem_AllocAligned_2`, `cmp r0,#0` with `r0`
never set).

So the three "spans" are:

* `0x343650..0x34A03C` (27 KB) - after the 260-byte `maybe_Field_Scene_ApplyOverrides`
* `0x34A140..0x352DBC` (36 KB) - after the 260-byte `maybe_Field_SceneObject_InitSpriteNodes`,
  ending exactly at `Field_SceneObject_SpawnByType`
* `0x35A1D0..0x35E478` (17 KB) - ending exactly at `Ui_SceneFlow_UpdateChildTask`

Each span also contains the same stack-struct initialiser fragment (first words `0xE1CDB5B0`,
`0xE5CD2054`, `0xE5CD0058`) at many places, which is what the scanner kept cutting at.

Because the previous descriptive names (`Sprite2D`, `EffectMeshEmitterC`, `TalkPartyMessage`, ...) were
invented from the garbage Thumb "callee" lists, I replaced them with address-only honest placeholders
`maybe_InteriorCode_<addr>` (confidence 0.25) whose summary names the containing span and explains the
mode bug. Same treatment for six other interior/misaligned addresses:

* `0x00341394` - a 0x538-byte hole between `maybe_Container_Tree_InsertByKey` (ends exactly here) and
  `Ui_StatusWindow_BuildIndexTablesA`.
* `0x00363E3C`, `0x00363E68` - two fragments of one actor model-setup routine (0x363E68 starts with
  `bl Anim_Instance_ApplyTemplate` and then uses `r6`/`r5` loaded earlier).
* `0x0036AD6E`, `0x0036DCF6`, `0x0036E566` - addresses that land 2 bytes inside an instruction
  (`blt` at 0x36DCF4 / 0x36E564, real entry at 0x36AD70).

## Open problems / what is NOT verified

* The 77 `maybe_InteriorCode_*` entries are placeholders, not names. The real code in those spans is
  still unanalysed: whoever fixes the `mode` field will probably find several genuine functions there.
* All class attributions above (`Ui_SceneComposite`, `Gfx_Object`, `Ui_Panel`, `Ui_Window`) are
  inferences from neighbours/vtables, not proof; each entry says so.
* `0x0036151C` and `0x00361640` cannot be judged at all - there is no readable body and no asm for
  either address.
* The unnamed helpers that block many of these names are still unnamed: 0x001A6680 (pane API),
  0x0053CD1C (child-state fold), 0x001235A4 (intrusive list splice), 0x0028EE8C (actor alloc),
  0x00284D88 (idle test), 0x003DFEC4, 0x004A43CC, 0x001E3C70, 0x00193E44 (base dtor).
