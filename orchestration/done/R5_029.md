## What the batch actually was

The batch is dominated by **Ghidra artifacts**, not functions. 22 of the 33 addresses are
mid-instruction Thumb symbols inside ARM code. The previous pass had already spotted most of them
but kept subsystem-flavoured names (`Anim_CurveEvalCase_*`, `std_RbTree_EraseRebalance*`,
`std_SortHelper_71E66A`), which read like real functions. I renamed all of them to the project's
existing artifact convention `Code_MisalignedSymbol<ADDR>` (4 instances already existed at
0x0062209E, 0x0063349E, 0x006E5A26, 0x006E6466) and put the "which real function contains this"
information in the summary instead.

### Confirmed (6)

* `0x006E662C/66C4/675C/67F4/688C` → `Gfx_EffectNode_AttachAndApplyA..E`, 0.55.
  New evidence: the tail-call target `0x005F539C` is `Gfx_EffectPart_ApplyParamsFromVirtual`
  (symbols_recovered.json), and the sibling slot-4 functions of the same five class tables are
  named `Gfx_SceneNode_Destroy_1..5`, which confirms the five-class template family. Asm:
  `vtable[0x3C](self,4)` → `bl 0x003D9780` → `b 0x005F539C`.
* `0x006F4858` → `Math_EaseCurve_Vec2Sine`, 0.50.
  New evidence: the literal-pool word at `0x006F4894` is `0x3FC90FDB` (pi/2) and the sibling
  `Math_EaseCurve_Mode01` (0x006F4898) multiplies normalised time by it before calling the same
  helper `0x00673BC8` — that pins the helper as a sine. Summary corrected: the body is
  `out = from + to*f`, not a `from + (to-from)*f` lerp.

### Corrected (21)

* 16 × `Anim_CurveEvalCase_*` → `maybe_Code_MisalignedSymbol006E972E … 006EA68A`, 0.30.
  Verified in `asm/text/text_006C0048.s`: e.g. `0x006E972C` is a 4-byte `ldrblt r2,[r0,#8]`, so
  `0x006E972E` is not an instruction boundary; same for `0x006E9B1C`/`0x006E9B1E`. The coherent
  "keyframe binary search" that Ghidra recovers at `0x006E9B1E` is those ARM bytes decoded as
  Thumb.
* 3 × `std_RbTree_EraseRebalance*` → `maybe_Code_MisalignedSymbol0070D126/12A/12E`, 0.30.
  `asm/text/text_00700048.s` shows `0x0070D0F8..0x0070D15C` is one ARM function and
  `0x0070D124/128/12C` are 4-byte `strlt`/`strblt` instructions. The convincing "red-black delete
  fix-up" body is a bogus Thumb backward branch into the **already named**
  `std_RbTree_EraseNodeRebalance` (0x0070C528) — its labels `LAB_0070c900..LAB_0070c948` sit
  inside that function. The real RB-tree erase rebalance was never missing.
* `0x0071E66A` `std_SortHelper_71E66A` → `maybe_Code_MisalignedSymbol0071E66A`, 0.30.
  `0x0071E668` is a 4-byte `ldrlt fp,[pc,#0x684]` inside `std_insertion_sort_u16_item`
  (0x0071E598); the `Item_CompareEntryKey32`/`Item_LookupRecord` "callees" are decode noise.
* `0x006EF5AC` `Container_UnlinkNodeSubtree` → `maybe_Container_WalkSubtreeInvokeVisitor`, 0.40.
  The asm contains **no store instruction at all** (0x006EF5AC..0x006EF690 is ldr/ldrb/blx/cmp/b
  only), so nothing is unlinked. It is a depth-first walk of an intrusive tree (sibling link at
  node+4, parent at +0x0C, child-list sentinel at parent+0x14, flag byte +0x44) that calls the
  node's virtual slot +0x44 with a visitor context. The caller `maybe_Ui_TextLayout_InsertRun`
  builds `{&g_uiTextLayoutRunCallbacks, run, box, layout}` on the stack and passes `&contextPtr`,
  which is exactly that visitor table.

### Kept maybe (6)

* `0x006E5A26`, `0x006E6466` — already correctly named artifacts; summaries now cite the exact
  containing ARM instruction (`0x006E5A24` / `0x006E6464`, both `strlt r1,[r4,#0x4c]`).
* `0x006EF710`, `0x006EF774` — the intrusive-list teardown shape is clear (circular list at
  container+0x24, node base = link-0x44 / link-0x80, predicate + destructor + two unlinks), but
  the container class is unidentified. Important correction to the previous evidence: the
  dossier's callee names (`Sound_SeqPlayer_PrepareBank`, `Math_ClampVectorToRing`,
  `Sound_Track_PrepareResources`) are **bogus** — the real call targets `0x0054FD1C`,
  `0x0054FD38`, `0x005548B0`, `0x005548CC`, `0x0011FCBC`, `0x0011FCF8` are function entries that
  Ghidra merged into the preceding functions (mid-function split symbols, see FACTS).
* `0x00723E7C`, `0x00723EF0` — soft-float helpers next to `std_U64ToDouble`. `0x00723E7C`'s only
  literal is `0x7FC00000` (VFP default NaN) and it has no conversion arithmetic, so
  "FloatToUnsigned" is not supported by the body. `0x00723EF0` does show the unsigned-saturation
  idiom `mvn r0, r0, asr #31`, which supports "DoubleToUnsigned", but its body is truncated
  (`halt_baddata`). Both stay `maybe_` at 0.30.

## Not verified / open problems

* The five `Gfx_EffectNode_AttachAndApplyA..E` names still rest on the class-table slot and the
  two callees; I could not read the class tables at `0x0076E3EC..0x0076E6CC` (they are outside
  the `asm/data` dump, which only covers `0x0079B000+`), so the concrete effect-node classes are
  unknown. 0.55 is deliberately not higher.
* `0x00673BC8` (the "sine" helper) is a real ARM function (`push {lr}` at that address) but is
  mis-symbolised as a 2-byte Thumb stub, so it has no readable C. The sine identification rests
  on the pi/2 constant in its sibling, not on its body.
* `0x00723E7C` / `0x00723EF0`: the three "callers" in the dossier do not reference them in their
  readable C, so the xref may be wrong. Their true identity (and whether they are
  `__aeabi_f2uiz`/`__aeabi_d2uiz` or an FP-status helper) is unresolved.
