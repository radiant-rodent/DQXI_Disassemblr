# R_001 — second naming pass (refine), resumed

## What was done

Processed all **132** low-confidence `maybe_` functions in
`orchestration/naming/refine/batches/R_001.txt` (addresses `0x0011CB38`–`0x004DE588`) and wrote
`orchestration/naming/refine/out/R_001.json`.

No previous `R_001.json` existed, so this run started from the batch file. For each function I:

1. read the readable C and its doc header (previous name, confidence, batch, evidence);
2. re-read it against the now-named neighbours: named callers/callees were located with a
   full scan of `decomp/readable/**` for `func_00XXXXXX` / the current `maybe_` name, and
   ambiguous cases were opened and read (`Ui_MessageWindow_BindPanes`, `Script_Native_IsZone`,
   `maybe_Field_SceneObject_OnEvent`, `maybe_Ui_SceneFlow_*`, the new UI ctors, the equipment
   popup paths, …);
3. cross-checked `symbols.json`, `decomp/native_names.json` and the existing named siblings
   (e.g. `Ui_ListWindow_CtorBase`, `Ui_LoadWindow_InitPanes`, `Field_SceneObject_Show`);
4. decided confirm / correct / keep-maybe and recorded the **new** evidence, not the old.

**Result:** 79 `confirmed`, 11 `corrected`, 42 `kept_maybe`.
Confidence range 0.30–0.65. Confidences of 0.55 and above were reserved for functions with
body-level or named-caller proof; everything still ambiguous keeps the `maybe_` prefix.

### Honest keeps

42 functions stay `maybe_`. The main reasons:

* body still truncated / `halt_baddata` (`0x0029E41C`, `0x00352DBC`-family neighbours,
  `0x003400B4`, `0x0033EB5C`);
* only one weak caller or a vtable slot and no class anchor (`0x001E24B4`,
  `0x002F61EC`, `0x0031A8C0`, `0x0045571C`, `0x001FA9DC`, `0x0032CB3C`, `0x003A9CD0`);
* numbered/twin dtors whose mechanism is certain but whose owning class is not
  (`0x0017C570`…`0x00591918`);
* 2D/3D split is an inference (`0x003F463C`, `0x003F5528`);
* Ghidra split fragment with live registers only (`0x004DE588`).

## Open problems / not verified

* All names are still static-analysis hypotheses. No emulator or hardware playtest was done for
  this naming pass; nothing here proves runtime behaviour.
* Caller counts derived from text matching can be inflated by name-prefix collisions
  (e.g. `...SpawnCountBalloon` also matches `...SpawnCountBalloonEx`). Where the number mattered
  I opened the caller and checked the actual call site; the 998-caller count for
  `Game_GetDataManager` is plausible but not individually audited.
* Several low-score entries (`0x003433A0`, `0x004A10BC/0x004A1174`, `0x004DE588`) are only reached
  from tables or are dead/split code; they may never be exercised.
* `0x0029E41C` cannot be resolved further without fixing the disassembly (`halt_baddata` at
  `0x0029E448`).
* The runtime-type id behind `Container_HandleResolveAsType` is known only by address
  (`g_007134FC`), not by a symbolic class name.
* The "Container_" / "Ui_" prefixes for the pure libstdc++ teardown clones are a family label,
  not a proven class.
