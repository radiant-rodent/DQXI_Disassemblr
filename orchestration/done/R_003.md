# R_003 — second naming pass (refine), resumed

## What was done

Processed all **150** low-confidence `maybe_` functions in
`orchestration/naming/refine/batches/R_003.txt` (addresses `0x001818F4`–`0x003A11BC`) and wrote
`orchestration/naming/refine/out/R_003.json` (150 entries, in batch order).

Nothing from a previous worker existed (no `out/R_003.json`, no done report, no log entry), so the
batch was worked from scratch. For each function I:

1. read the readable C plus its doc header (previous name, confidence, previous batch, previous
   evidence) and did **not** re-derive what the previous pass already established;
2. rebuilt the call graph locally: every target address was searched across the 18,159 plain
   Ghidra export files (`decomp/ghidra/functions/**`) to find its **real** callers (the readable
   tree only names callees, never callers), and those caller files were resolved to their merged
   names and confidences;
3. annotated each body by resolving every inline `func_00XXXXXX` token to its merged name +
   confidence, so the decision rests on named neighbours;
4. cross-checked `decomp/native_names.json`, `symbols.json`, `symbols_recovered.json`,
   `decomp/ghidra/functions_merged.jsonl` and the other `orchestration/naming/refine/out/*.json`
   files that appeared while this lane was running (R_001, R_004);
5. recorded the **new** evidence, never the old text.

A useful by-product that shifted several verdicts: `func_0051B1FC` + `func_0011CD80` are the
RNG draw and the `__aeabi_idivmod` helper. Callers read the remainder out of `r1`
(`extraout_r1 + 0x78` in `0x001BA510`, `+2` in `0x001D5A10`), so any "returns something / N" body
built on that pair is `rand() % N`, not a count or a division. That alone disproved
`Ui_ItemList_GetSlotCount`. Likewise `0x00636AFC(world+0x6C)` turned out to be a single global
"active/enabled" predicate reused by six functions in this batch.

**Result:** 34 `confirmed`, 28 `corrected`, 88 `kept_maybe`. Confidence spread:
0.30 ×9, 0.35 ×9, 0.40 ×51, 0.45 ×43, 0.50 ×28, 0.55 ×8, 0.60 ×1.

One further external cross-check paid off: `game_assets/scripts/packs/script/**` contains
`ActorSetActionSeq(player, "Horse_Nut")`, `ActorSetActionSeq(soldier1, "Nut")` and
`Actor2DChangeAnim(door, "Nut")` (files `a_020`, `a_070`, `a_10_cs_140`, …). `"Nut"` is therefore a
real **action-sequence name**, which confirms the `Nut` family and disproves the `NutTree` wording
(no tree appears anywhere).

Every batch function got an entry; nothing was skipped.

## Honest keeps (88)

Reasons, in order of frequency:

* **Twin/thunk bodies.** Several addresses have byte-identical bodies, so at most one of the
  attached names can be right and the class cannot be told apart: `0x001E0990`/`0x001E0B90`
  (differ only by the 1/0 constant), `0x001E1534`/`0x001E1A7C`, `0x00385D38`/`0x00385D6C`,
  `0x002BDAC8`/`0x002BE754`, `0x002F3250`/`0x00385890`/`0x001A3788`/`0x002B4918`/`0x002B6BAC`
  (all the same `0x00636AFC` poll). These are documented as duplicates instead of being guessed
  twice; a *negative* result worth having.
* **Ghidra could not decode the entry.** `0x001CA7A0` (`halt_baddata` only), `0x0027E1B8`
  (44 bytes, decode fails though three callers exist), `0x0033DEC4` (tail is `halt_baddata`),
  `0x00184958`/`0x001849F0` (unaff_ registers, prologue is a mis-decoded `vmov`) — these are
  probably mid-function entries or inline data, not clean routines.
* **Opaque engine calls.** Many bodies are one or two calls into `0x005xxxxx`/`0x006xxxxx`
  addresses that are **not** decompiled entry points (`0x005F972C`, `0x00636AFC`, `0x005F7784`,
  `0x0020D23C/D268/F2CC`, `0x00622480`…). Nothing in the readable tree names them, so
  "stop"/"open"/"refresh" stay inferences. This is the single biggest blocker for this batch.
* **Unverifiable namespace only.** The operation is clear but the prefix is positional:
  `Ui_Overlay_*`, `Field_Gimmick_*`, `Battle_UiFlow_*`, `Battle_UiRow_*`.
* **Register-swapped twins.** `0x001D607C`/`0x001D61D0` return the adjacent bytes f_12/f_11; the
  place/room assignment cannot be proven, so both stay `maybe_`.

## Not verified

* Nothing was run in an emulator or on hardware — this lane only writes names.
* "Confirmed" means the **body and its named neighbours** support the name; it does not mean the
  class/namespace is proven. `Math_RandomPercent` (0.5) and the `Ui_ObjectList_Begin/End` pair
  (0.5, prefix is historical) are the two confirmed names I would revisit first.
* Signatures come from Ghidra; where the function reads `arg2..arg4` but Ghidra declared one
  parameter (`0x002281A0`), the signature was widened to document the registers, but the real
  calling convention is unverified.
* `0x0024C814`'s argument names are inherited placeholders (several registers were lost), so the
  signature is descriptive, not factual.

## Suggested follow-ups

1. **Name the ten engine helpers everyone uses.** `0x00636AFC` (the "active" predicate, used by
   6+ functions here), `0x0051B1FC` (RNG draw), `0x0011CD80` (`__aeabi_idivmod`, remainder in r1),
   `0x005F7784` (pick variant 0..N), `0x005E7848` (play animation id), `0x005F4F9C`,
   `0x002D0E84` (reset f_B8->f_FC), `0x00239A1C`, `0x0062AB3C` (game mode), `0x0063B11C`
   (party → group). They are not decompiled entry points today; a small pass that forces Ghidra to
   treat them as functions (or names them from the ARM side) would lift dozens of `maybe_` names.
2. **Struct pass on the `FieldAction` family** (f_28 owner, f_2C timer, f_30/f_31 flags,
   f_3C/f_40, f_50/f_58) — used by 12 functions in this batch and still unnamed.
3. **Struct pass on the `BattleUiRow`/`BattleUi` slots** (f_498..f_49E state map, +0xC39F row
   table, 0x470-byte target slots at +0x154) — would settle `UpdatePartyRows`/`UpdatePartyLabels`/
   `InitSlots` and the two `ResetBalloonSlots`.
4. **Deduplicate twin entries in the index** (`0x00184958`, `0x001849F0`, `0x001E1534`/`0x001E1A7C`,
   `0x00385D38`/`0x00385D6C`, `0x002BDAC8`/`0x002BE754`) — mark the secondary ones as shared tails
   so later passes stop trying to name them independently.
5. **Build on the `Nut` finding.** `ActorSetActionSeq(actor, "Nut")` / `Actor2DChangeAnim(door, "Nut")`
   appear across 36 scripts, so `vtable+0x84(string)` is "set action sequence" and the remaining
   `maybe_` on `maybe_Field_Action_Nut_*` is about the owning class, not the name. A sweep of
   `game_assets/scripts/` for the other sequence names (`Horse_Nut`, door/bridge gestures) would
   confirm dozens of `vtable+0x84` callers in one go.
