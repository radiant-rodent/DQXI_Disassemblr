# R_004 — second naming pass (refine batch R_004)

## Scope

- Batch: `orchestration/naming/refine/batches/R_004.txt` — 150 `maybe_` functions, addresses
  0x003A15A8 … 0x004FA84C.
- Output: `orchestration/naming/refine/out/R_004.json` — one object per batch address, in batch order.
- All 150 addresses covered; no other batch or naming file was touched.

## What I did

1. Read `README.md`, `orchestration/PLAN.md`, the batch file and `orchestration/naming/refine/scores.jsonl`.
2. For every candidate: read its readable C header + body, the files of its callers/callees/vtable
   neighbours, and the relevant confident names in `orchestration/naming/out/`, `symbols.json` and
   `decomp/ghidra/functions_merged.jsonl`.
3. Classified each function as `confirmed` / `corrected` / `kept_maybe` with a new summary that records
   *why* and what is still unproven, then wrote the JSON and validated it.

### Key finding about this batch

The batch was generated after `M1_merge_names`, but **all 150 candidates have context score 3**, i.e. the
only confident context is the callee `Os_GetGameWork`. There is no confident caller, confident vtable
sibling, distinctive shared string or shared constant for any of them. Verify with:

```
python -c "import json; rows=[json.loads(l) for l in open('orchestration/naming/refine/scores.jsonl',encoding='utf-8')]; print(sorted({r['score'] for r in rows if r['batch']=='R_004'}))"
```

So this is the cold tail of the R lane, not the "easiest wins at the top". There is nothing new to
confirm most guesses against; promotion therefore had to rest on the function body itself (a
self-identifying literal, a complete algorithm, or a confident ctor/dtor that documents the address in its
vtable). That is reflected in the moderate confidence values (0.50–0.60) and in the large `kept_maybe`
group.

### Corrections (all kept at <0.5 with a `maybe_` name)

- `0x003DD2D0` `maybe_Field_Actor_PlaySituationSe` → `maybe_Field_Actor_PlaySituationEffect`.
  The callee is the effect manager (`maybe_Effect_FindOrCreateInstance`, 0x35FF3C) at the same manager
  slot used by `PlayIdleEffect` and `CreateSpriteFromTemplate`; the old name claimed audio.
- `0x003E4B6C` `maybe_Field_Actor_StopEffectWhenNotPaused` → `maybe_Field_Actor_UpdateTrailWhenNotPaused`.
  The body only calls `maybe_Actor_UpdateTrailQuad` (0x2347D4) when the scene is not paused; it stops
  nothing.
- `0x004025BC` `maybe_Ui_PartyPanel_OtherMembersAlive` → `maybe_Ui_PartyPanel_CheckOtherMemberAvailability`.
  The comparison returns 0 when *all* existing other members carry the +0x10 flag and 1 when at least one
  lacks it — the opposite polarity of the old name. The caller (0x280990) shows a message when the
  result is 0, but the flag's meaning is still unproven, so the name is deliberately neutral.
- `0x0048F204` / `0x00491D48` `maybe_Battle_Monster_ApplyHitFlash` / `…ApplyBarValue` →
  `maybe_Battle_Row_UpdateIfKindMatches` / `…B`. The two recovered bodies are identical and contain only
  two 0x63DCA4 data-table lookups, two id compares and a `func_001CA474(battle+0x4218,0)` call — no
  colour, flash or bar write. Both old names could not be right at once.
- `0x004F8FF4` `maybe_Field_LampGimmick_UpdateBeamVectors` → `maybe_Field_LampGimmick_UpdateIdlePose`.
  The body is byte-for-byte the pose update of `maybe_Ui_ArcListWindow_UpdateIdlePose` (0x49CF00),
  including the +0x94 sub-object poll; there is no beam/direction math.

### Deliberately left as `maybe_`

- **The shared `core->f_8->f_6C` gate clones** (0x3A15A8, 0x3A26AC, 0x3A2A9C, 0x3A3434, 0x3A3878,
  0x3A3C90, 0x3A3FD8, 0x3A4464, 0x3D91B8, 0x3D9618, 0x40CCDC, 0x40D450, 0x40E300, 0x41E76C, 0x41EA78,
  0x4AF5E4, 0x4B0BC4, 0x4C9254, 0x4E6548, 0x4EFF2C, 0x47145C, plus 0x4CABFC which *was* confirmed
  because a confident dtor names it). The merged state now contains two confident names for this exact
  body — `Actor2D_IsEventSlotFree` (0x3A2E74, 0.50) and `Field_Gadget_IsFieldActiveB` (0x4CABFC, named by
  a confident dtor). The gate's real meaning is therefore unresolved; each summary says so instead of
  picking one.
- **Incomplete/identical helper pairs**: 0x49A6B0 vs 0x49A880 (clip band vs clip from rect; same body),
  0x48F204 vs 0x491D48 (corrected as above), 0x3D7814 vs 0x3D8D74 (damaged action-init twin). At most one
  of each pair can keep its old specific wording.
- **No caller/vtable at all**: 0x3F3E90 and 0x4A06E0 (same basis math as each other) — subsystem even
  (Camera vs Ui_Marker) is a guess.
- **Damaged decompilation**: 0x3D7814, 0x41EF50, 0x00475114, 0x484A1C, 0x47C954 — kept vague rather than
  promoting a name for code that Ghidra could not fully recover.

## Validation performed

- JSON re-read from bytes with strict UTF-8 (no cp1252), `json.loads` OK.
- 150/150 batch addresses present exactly once, in batch order.
- `previous_name` and `previous_confidence` match the batch line for every entry.
- Invariants checked programmatically:
  - `confirmed` ⇒ name = previous minus `maybe_`, confidence 0.50–0.70;
  - `kept_maybe`/`corrected` ⇒ name starts with `maybe_`, confidence < 0.50;
  - `change` is one of the three allowed values, every entry has a non-empty signature/summary/evidence;
  - no duplicate names within the output and no collision with a confirmed name in `symbols.json`.
- Final file size 99,595 bytes; 150 objects.
