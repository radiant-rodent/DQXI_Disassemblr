## The disassembly findings (the reason several old names were wrong)

| address | proof | consequence |
|---|---|---|
| `0x00100B74` | Thumb `ldrh` loop counting UTF-16 units until NUL | it is **`strlen16`**, not a debug-print channel and not non-returning. Every "reads the name then *logs* it" story built on it (0x0040D368, 0x0041200C, 0x00446C6C, 0x0045220C, 0x003D8FF0) was wrong: those functions *fill text/message argument slots*. Ghidra truncated each body right after this call, which hid the rest. |
| `0x001902A4` | `ldrh r2,[r0,#0xda]; bic r1,r2,r1; strh r1,[r0,#0xda]` | it **clears** bits of the member flag halfword at +0xDA (FACTS: the same halfword `maybe_Actor_EnsureVisible` tests bit 7 of). So 0x00406968/0x00406A54 are *Clear*StatusFlag*, not *Set*. |
| `0x0066B2CC(work,i)` | 3 instructions: `work[i*4+0x31F4]` | a per-index u32 counter array; entry 0 is clamped against `0x0098967F` (the gold cap) by the amount spinner → entry 0 is the wallet. 0x00151164 is therefore `return gold`, a **dropped-return getter** (Ghidra typed it `void`), not `Field_SetModeFlag`. |
| `0x00707C1C` / `0x006D3EA0` | `0x707C1C(obj,fmt,...)` = va-arg snprintf into `obj+4` with a 0x80-byte limit; `0x6D3EA0(slot,fmt,...)` = the same into 0x108-stride text slot `slot` (`ui->slot*0x108+8`, cursor at `+4`) | the `Ui_TextFormat_*` family: slots 2/8/9 are written with `"%ls"` (padded member name) and `"%d"`. |
| `0x00612848` | row address `bag+id*0x8C+0x5FE4`, `memcpy 0x84` + flags + owner key into the first free slot of `bag+0x7B3C`, returns 1/0 | it **copies a 50-entry source row into the 20-entry view table**; its merged name `maybe_Ui_DataPanel_GetRowNameLength` is wrong (the `strlen16` at the top is only a "label empty?" test). 0x003BD200 is an *add row to view* step. |
| `0x00612F5C` | `memcpy((0x31-index)*0x8C)` + clear entry 49 | delete row **by index** from the 50-entry table (its sibling 0x00612FC8 deletes by owner key). |
| `0x007292B0` | `{handler, arg}` pairs: +0x08 `0x0036949C`, +0x10 `0x00369AD4` (NextPage), +0x18 `0x0036A148` (LayoutPage) | 0x0036A4E4 does not *check* anything — it **schedules** the next guide-window action into self+8/self+0xC. |

## Not verified / open problems

- Everything here is **static**. Nothing was run in the emulator; no name was checked against live
  behaviour. Summaries say which part is inference.
- `decomp/readable/**` still shows the old names — that is expected until `M1b_merge_refined`.
- Names of three functions I rely on are themselves unverified: 0x0066B0E4 (per-slot character id?),
  0x0063F8F0 (record lookup), 0x0066B088 (map flag). If they turn out to be something else, the four
  `Party_Validate*` entries lose their basis (they are all ≤0.45 `maybe_`).
- `maybe_Party_AppendBlankMemberRecords` (0x003BDE2C) is the weakest new name: the 0x2A0 record stride
  is the only evidence that the array is the party, and the installed record's 7-character name sits at
  +0x4E, not at the member-record name offset +0xCA of FACTS.md.
- The `Ui_TextFormat_*` names claim "slots 2/8/9" from the manager offsets (+0x214/+0x844/+0x94C); the
  mapping `slot*0x108+4` is read from 0x006D3EA0, not from a documented table of slot meanings.
