## Method (why the batch looked "cold")
`scores.jsonl` gives every one of these functions the same neighbour list (just `Game_GetWork`,
score 3, `callers_conf = 0`), so the pre-computed context is useless here. The new evidence came from
three reads the first pass did not do:

1. **Containing rodata table.** Most of these are entries of vtables or of `{handler, 0}` action tables.
   Printing the slots around the address gave real, often named, siblings
   (e.g. `Ui_ProfileScreen_ResetCursor`, `Ui_ScrollBar_DrawRows`, `Ui_Window_CloseAndHide`,
   `Field_ModelSlotEmitter_DtorDelete`).
2. **Direct `bl #addr` callers** parsed out of `asm/text/*.s` and mapped back to the current function
   names (all 72 had zero *named* callers in the readable C, but several have `bl` callers whose
   owning function is now named — e.g. 0x0048B150 ← `maybe_Monster_GetDefenceStat`, 0x00636000 ←
   `maybe_Actor_InitStateModels`, 0x00646148 ← `Ui_Part_GetAnimState`).
3. **Raw bytes / literal pools** from `original/exefs/code.decompressed.bin` whenever the readable C
   looked like a Ghidra artefact (dropped return value, "does not return", folded body).

## Decisions worth knowing
- **0x004527D8 is a deleting destructor**, not a visibility-mask setter. Disassembly installs vtable
  0x7713D4 (whose `+4` slot *is* this function), publishes the 32-child mask on the way out, restores the
  base vtable and tail-calls base dtor 0x3A8200 + free 0x10F6CC → `Ui_ChildTransform_DtorDelete`.
- **0x00100B74 is wcslen** (pairs with the 0.8-confidence `std_wcsncpy` at 0x00100A74). Two names fell
  out of that: 0x004D6350 is `Party_GetMemberNameLength` (not a "throw"), and 0x004A3DA0 concatenates
  wide strings into a 0x27C buffer next to two functions that set message argument 5
  (`Ui_TextFormat_ReleaseSlot(5, "%ls", buf)`) → `maybe_Ui_InteractJob_BuildMessageText` (still maybe_,
  the Ghidra body is lost after the first wcslen).
- **Two Ghidra "setter/ensure" traps are getters**: 0x0062FFA0 (`0x66AF08` = `ldrb [r0+r1,#0x3165]`,
  callers assign the result) and 0x004AFB64/0x004B01CC (byte-identical 36-byte bodies returning
  0x0066AAD0's boolean).
- **0x0048B150 does return a record** (`bl 0x63FD68; pop {r4,r5,pc}`; caller reads `->f_C`), so it is
  `Battle_Enemy_GetRecordByIndex`, not a void index mapper.
- **The eight 0x0070BF2C..0x0070C00C thunks are skill counts**: 0x006298D0 reads
  `ldrh [record + i*2 + 0x122]`, and 0x003AA448/0x003AAB38 sum SP costs of exactly those ids through
  `SkillPanel_CanUnlockSkill` (skillId < 0x1B6, master record 0x0063CF74). `Party_GetListCountSlotN` →
  `Party_GetSkillCountSlotN` (0.60). Side note for future work: the earlier
  `maybe_MonsterBook_CountRecorded` (0x006291A8) is really "count non-0xFFFF u16 in a 60-entry list".
  Not renamed (out of this lane's address list) — see follow-ups.
- **0x00670668/0x00670900/0x006709C0 are field-object release callbacks**, not party removal: they are
  passed as the free callback to the field scene-object/gimmick builders (0x3DDE34, 0x4D7B4C …) and
  0x006136BC marks slot ids 0xFFFF in the 40-entry table at work+0x24A98+0x4DD8.
- **0x0066E67C and 0x00471820 are twins** (variant byte → story flag 0x1A8/0x1A7/0x1A9 → child vtable
  +0x14); 0x0066E67C was called `Actor_OnEventB`, which was the wrong family.

## Checker
`tools/check_refine.py` flagged `0x0064D488` (confidence 0.5 on a body containing `unaff_r6`). Instead of
lowering a correct name I checked the disassembly: `unaff_r6` is only the loop bound
`ldrne r6,[r0,#0xb4]` (the array end from `self->f_B4`), and the function returns the counter in r5.
The evidence now says so; the checker accepts it. No check was modified.
