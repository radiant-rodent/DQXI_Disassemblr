# R_013 — second naming pass (refine), resumed

**Task:** re-examine the 131 low-confidence `maybe_` functions in
`orchestration/naming/refine/batches/R_013.txt` with the now-named neighbours.
**Owned file:** `orchestration/naming/refine/out/R_013.json` (only file changed besides `AGENT_LOG.md` and
this report).

## What already existed when I started

- No `orchestration/naming/refine/out/R_013.json` and no done report.
- `out/scratch/R_013/progress_1.json` contained all 131 objects, but the summaries and evidence were
  machine boilerplate ("Refines previous guess with stronger named-context", "Ambiguous: previous evidence
  and moderate score N"), several `confirmed` verdicts were clearly unsafe (e.g. 0x003AD38C where the body
  is a row fill, 0x0018FC94 which calls no detach at all) and the file had never been through
  `check_refine`. I treated it as untrusted and rewrote everything from the readable C.

## What I did

For each of the 131 addresses I read the readable C (header + body), looked up its named callees in
`symbols_recovered.json` and its named callers by grepping `decomp/readable`, used the vtable/constant
neighbours from `orchestration/naming/refine/scores.jsonl`, and consulted `asm/text/*.s` where the decompile
was damaged. Verdicts:

| change | count |
|---|---|
| confirmed (dropped `maybe_`, confidence 0.5–0.55) | 49 |
| corrected (better/different name, old name wrong or misleading) | 13 |
| kept_maybe (still ambiguous, confidence 0.25–0.45) | 69 |

Progress was saved to the JSON in batches of 6–15 functions, so a resumed worker can continue at any point.

### Corrections (the old name claimed something the code does not do)

- `0x0028F5A0` `Actor2D_BuildSpritePanelsFromRecord` → **`maybe_Actor2D_PlayAnimOnParts`**: no allocation,
  no mesh/table build; it is a three-state action that plays one anim id on every child actor list.
- `0x003AD38C` `Ui_AspectObject_Init` → **`maybe_Ui_RowTable_InitFromRecord`**: it fills six 7-byte row
  descriptors from a record table and sets pane text; no aspect/quad setup.
- `0x00385EA8` `Ui_Window_InitEffect` → **`maybe_Field_Actor_SpawnEffectInstance`**: field scene-node code
  (`Effect_FindOrCreateInstance` with effect 0x4AD), not a UI window.
- `0x001810B0` `Field_Gadget_TriggerEffect` → **`Field_Gadget_TriggerCommand10`**: plays SE 9 and issues
  gadget command 10; no effect is created. (0x0038660C already owns `Field_Gadget_TriggerCommand`, which
  issues command 0x1A.)
- `0x0018FC94` `Ui_Window_DetachRenderNode` → **`maybe_Ui_Window_EnsureEntrySelected`**; `0x00214A78`
  `Ui_ReleasePaneById` → **`maybe_Ui_Window_SelectEntryA`**; `0x00304FC8` `Ui_Text_CommitLine` →
  **`maybe_Ui_Window_SelectEntryC`**: all three are the same "vtable +0x58 then select id from +0x28" body;
  nothing is detached, released or committed.
- `0x003CB4EC` / `0x003CB6FC` / `0x003CCD90` `..._PlayAnimB/C/D` → **`..._PlaySeB/C/D`**: they play the u16
  sound ids at member-record +0xB4/+0xBE/+0xB6, they do not start animations.
- `0x00181848` `Sound_PlaySeOnceId9` → **`Sound_PlaySeId9`**: the effect plays on *every* call, only the
  sound-manager creation is one-time.
- `0x0027FC60` `Ui_BattleCmd_HandleDebugCombo` → **`maybe_Ui_BattleCmd_HandleSecondaryInput`**: the body is
  the same input-guard pattern as its two siblings with command id 0x10; nothing indicates a debug combo.
- `0x004D0248` `Ui_ListWindow_ScrollToRow` → **`Ui_ListWindow_ScrollByRows`**: it adds the caller's delta to
  the current page rather than jumping to an absolute row.

### Deliberately left as `maybe_`

- Everything built on a body Ghidra could not decompile: `0x00304900` (single `halt_baddata`),
  `0x002107B4`, `0x003D7664`, `0x00308F1C`, `0x004A6EDC`, `0x0033376C`, `0x003BA310`, `0x00454004`,
  `0x006E540A/568E/5CCA/5F4E/6180/61DE` (the unreferenced 0x6E5xxx Thumb fragments).
- The `0x6E5xxx` files are fragments of one scroll routine, not real entry points (arguments arrive as
  `unaff_r*`, calls are emitted with no arguments); they keep `maybe_` at 0.25–0.35.
- Functions whose role is clear but whose owner is not: `maybe_Svc_SingletonCtor` (the 0x782928 base
  vtable is shared by many UI objects), `maybe_Gfx_Effect_Update`, `maybe_Field_Actor_UpdateModel`,
  `maybe_Battle_UpdateUnitDisplay`, the three `maybe_Ui_BattleCmd_*` handlers that share one input guard.
- `0x002FB644` and `0x003E60F0` have **identical two-instruction bodies** (`0x005E7594` +
  `Container_KeyedList_SelectEntry(self+0x60,0)`) but were given two different names in the first pass;
  both stay `maybe_` and their summaries now say so.

## Open problems / suggested follow-ups

1. `0x001D809C` is named `Ui_List_SelectEntryById` but is used all over the tree as a generic
   "push a value + high-half parameter into an object" helper (animation frames at 0x0018FCB0, draw
   priority at 0x001A6068, pager positions, pane ids). A dedicated pass should decide whether it is one
   generic setter (and the callers need re-reading) or several inlined siblings; several of the names in
   this batch inherit the misleading wording.
2. `0x003E6304` (`maybe_Field_Actor_SpawnAttachedEffect`) and `0x00385EA8` are two different field-actor
   effect spawners; M1b should keep them distinct (0x4AD vs the sprite descriptor path).
3. The `0x6E5xxx` block (six "functions") should be re-derived from the disassembly as one routine with
   offsets, or marked as data/fragments in `functions_index.json`; naming them individually is wasted work.
4. `0x00293FBC`, `0x00385EA8`-neighbour and the other 0x24A98-touching UI helpers should be re-checked
   after the bag/inventory naming pass, since work+0x24A98 keeps being mistaken for an item table.
