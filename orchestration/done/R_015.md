# R_015 — second-pass naming (refine), resumed

Batch: `orchestration/naming/refine/batches/R_015.txt` — 150 low-confidence `maybe_` functions.
Output: `orchestration/naming/refine/out/R_015.json` (150 entries, one per batch address).

## What the previous worker had done

All 150 objects existed, but the pass was mechanical:

* every `evidence` string was the same template (`Context score N; neighbours: none.` followed by the old
  doc comment), i.e. no neighbour was actually looked at;
* summaries were the old (sometimes truncated) doc headers, several ending mid-sentence;
* nothing had been re-checked against the newly merged names;
* `python tools/check_refine.py R_015` failed with 3 hard errors (conf >= 0.5 on damaged bodies:
  0x002CF9BE, 0x004A6840, 0x00217DAC).

I therefore treated the file as un-reviewed and decided every address again from the readable C plus the
new context. The old verdicts were kept only where I could re-verify them.

## Method

1. Indexed all 18.7k readable files once to find which ones *call* each function (name in the body, not
   in a comment) — that is what actually changed since the first pass.
2. Indexed every 0x00600000–0x00800000 constant (vtables / literal pools) appearing in each body and
   looked for the constructors that install the same vtable. This is how the three class-level
   corrections below were found.
3. Read the body of every non-destructor candidate (53) in full and the dasm-level facts where Ghidra
   damage was reported.
4. Applied a strict rule for the verdict:
   * **confirmed** — either the class is pinned by a *non-`maybe_`* constructor/vtable sibling, or the
     name only claims a mechanism (layout + destroying / non-deleting destructor) that the body proves;
   * **corrected** — the new context showed the old class/verb was wrong;
   * **kept_maybe** — mechanism clear, class label still a guess (or the body is damaged).

## Result

150 entries: **58 confirmed, 13 corrected, 79 kept_maybe**. `python tools/check_refine.py R_015` → `OK`.

### Deliberately kept `maybe_` (examples)

* ~50 destructor pairs with a clear layout but no constructor/vtable third party: the mechanism is
  certain, the class name is not (`maybe_Ui_BigScreen_Dtor`, `maybe_Ui_GuideWindow_Dtor`,
  `maybe_Ui_GoldWindow_Delete`, `maybe_Ui_Screen_DtorB..E`, ...).
* 0x002CF9BE / 0x00217DAC / 0x004683F0 / 0x004A6840 — Ghidra damage (`unaff_r*`, `in_ZR`/`in_CY`,
  `halt_baddata`, dropped argument registers). 0x002CF9BE is a byte copy of the tail of the confirmed
  0x002CF644 but is too damaged to raise above 0.35; 0x004A6840 ends in `halt_baddata()` (0.30).
* 0x002D3E1A — `coprocessor_load`/`in_cr0` damage (0.30).
* 0x00609480 — the symbol is 24 bytes but the readable body is 387 lines: it is an entry that falls
  through into 0x00609498 `BattleScene_UpdateScreenState0Main`, so the old name would mislead.
* 0x0041DD7C — called on an embedded object at +0x70 by `maybe_Ui_PopupWindow_InitPanes` and from the
  ambiguous 0x0066D398 thunk with four forwarded registers, so the class and the argument count stay open.

## Open problems / not verified

* Class identity for the ~60 GUI destructor pairs was **not** proven — only the teardown mechanism.
  A vtable dump (address → list of slots/owners) would settle them cheaply; there is no such table in
  the repo yet.
* `0x005931F0` / `0x0059321C` are named `..._77DD50` although the 0x77DD50 vtable never appears in their
  body (it arrives in `arg2`); the suffix documents the caller, not a verified fact.
* `0x00621E7C` shares vtable 0x007801B4 with `Ui_WorldMap_CreateMarkerArray`, but that ctor builds five
  0x10-byte markers at +0x60 while this body destroys four 0x13C objects at +0x204 — either the vtable
  is reused or one of the two names is wrong. Unresolved.
* `0x00257B30`'s table (`0x0072C5B8`) is copied to the stack; the eight handler addresses were confirmed
  from `Text_CommandHandler0`'s header, not re-read from the disassembly in this pass.
* `0x00609480` — whether the symbol really falls through (thunk) should be checked in
  `text/text_004f....s`/`text_005f....s` disassembly before merging.
