## State found / what I did

The previous worker had already written all 108 entries (no report and no AGENT_LOG entry existed).
The file was schema-clean and covered every address, but several entries had been generated from the
doc headers rather than re-read, and a few "confirmed" names contradicted the body or the
disassembly. I therefore re-read **every** function in the batch with its readable C and, where the
name depended on control flow, the ARM/Thumb in `asm/text/*.s`, then checked the named
callers/callees against `symbols.json` and the neighbouring readable files.

I kept the previous work where it held up, rewrote the wrong parts, and re-validated every entry
against the batch file (`previous_name`, `previous_confidence`, address order) and the schema.

Final split: **28 confirmed / 26 corrected / 54 kept_maybe**.

## Notable keep_maybe decisions

- `0x0031FDB8` / `0x00322130` stay `maybe_Battle_ActionSequence_Show*Results` at 0.35: both are
  near-identical playback phases (name changes, step sounds, number/actor popups, AdvanceTurn), but
  nothing names the owning class, so the old "SelectTargets"/"RunCommand" names were corrected
  without dropping the maybe_ prefix.
- `0x003C7F28`, `0x003C497C`, the `Ui_PartyPanel_*` handlers and the two `Ui_DataPanel_*` openers
  remain maybe_ because they are vtable/state-machine entries with no caller that identifies the
  class or the exact phase.
- The `Ui_AnimClip_*` constructors, the `Gfx_NodeCtor_*` wrappers and the composite destructors are
  structurally clear but their owning classes are unnamed; all stay < 0.5.
