## How the decisions were made

1. Read the readable C for all 109 (header carries previous name/confidence/evidence).
2. Built an index of which readable bodies *call* each target **by name** (after `M1_merge_names`
   bodies call functions by name, not by address). Result: for ~90 of the 109 there is **no caller at
   all** in `decomp/readable`, and most callees are still `func_XXXX` — which is why most stay
   `kept_maybe`.
3. Built an index of every vtable/table constant per body and listed the other readable functions that
   reference the same constant (this is how the shared base vtables 0x00759378 / 0x00782524 and the
   unique ones 0x007598B0 / 0x0075A07C / 0x007621BC were classified).
4. For every function whose readable body stops at a `std_ConstructArray` call (~25), dumped the full
   ARM listing from `asm/text/*.s` and named from what the code really does (e.g. 0x00173664,
   0x0063B6D0, 0x0063296C, 0x00650578, 0x0062D814, 0x00161270, the 0x006A**** static initialisers).
5. Cross-checked `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json` and the other
   `orchestration/naming/{out,refine/out}/*.json` for candidate names and for name collisions
   (names must be unique; twins get a `B` suffix).

Scratch (indexes, dumps, merge/validate scripts): `out/scratch/R_017/` (dump.py, callers.txt,
byname.txt, vtables.txt, merge.py, final.py).

## Not verified / open problems

- The 93 `kept_maybe` entries are honest guesses; most have no caller, several callees stay
  `func_XXXX`. Nothing about them is proven.
- **Biggest tooling gap:** ~60 of the 109 bodies end at the first `std_ConstructArray` call because the
  decompiler treats 0x00100050 as noreturn. Fixing that in `readable_c`/`enhance_decompiler` would
  recover the tail of that entire group and would let a future pass name them for real.
- The inlined game-work accessor (lazy 0x00764B84 block, globals 0x007BE31C/0x007BE320/0x00804160) is
  duplicated in dozens of bodies and has already produced at least four wrong names. Naming the
  accessor once (and telling the decompiler it is a function) would stop this recurring.
- `maybe_Ui_MessageWindow_InitRenderParams` (0x002AFA88) is used by 0x003B1330 as a per-row table
  copier; that name looks wrong and should be revisited.
- 0x004F91FC has a badly damaged body (`coprocessor_*`, overlapping instructions); only the constants
  and vtable cluster support the arc-layout reading.
- Suggested follow-ups: (1) `std_ConstructArray` noreturn fix + re-export of readable C for the
  affected addresses; (2) a task naming the inlined work accessor and the remaining
  `func_00xxxxxx` helpers that 20+ of these entries call (0x0066B710/B7C0/B7D4/B7E8/B908, 0x0063DCA4,
  0x0063E01C, 0x0035EB98 wrappers); (3) a duplicate-name check in `tools/check_refine.py` (currently
  only the merge step would catch it).
