## Method

1. Extracted each function's context score and neighbour list from
   `orchestration/naming/refine/scores.jsonl`, plus the previous name/confidence/evidence from the
   readable file header.
2. Built one inverted token index (all 18,661 readable `.c` files, ~9.5 s) for every previous name and
   `func_XXXXXX` in the batch, to find files that **mention** the address. Caveat found immediately: doc
   headers mention their neighbours, so this list is full of false callers. Every caller used as evidence
   was opened and checked against the body (this is why e.g. `Ui_Message_DrawPageByStyle` was rejected as a
   caller of `0x003CC348`).
3. Grouped the batch by neighbourhood (sprite/gadget builders 0x4C8xxx, party-panel UI 0x40xxxx, battle UI
   state handlers 0x48xxxx, battle row/sum builders 0x49xxxx, unit-model variants 0x4Axxxx) and re-read
   each member of a family against its siblings, which is where most corrections came from.
4. Read the full body where the header was empty (recovered fragments) or where the name looked wrong;
   otherwise relied on the header + named callees + named callers.

## Corrections (and why the old name was wrong)

- `0x004CA28C` `maybe_BattleActor_InitFromShortRecord` → `maybe_Field_SpriteObject_InitFromShortRecord`
  — every neighbour of this address (0x004C88C0 / 0x004CA008 / 0x004C9C64) is a field sprite-object
  builder and the body only touches record fields, f_2B8/f_2BA/f_240 and the span child at +0x24C; no
  battle-work field at all.
- `0x0028E334` `maybe_Actor_ApplyModelRecord` → `maybe_Model_ResolveHandleAndRefresh`
  — the body never reads its `record` arguments; it refreshes cached size/cell visibility, resets the
  default clip (`g_actorDefaultAnimName`) and resolves f_240 into f_244 via `Actor_GetModelHandleById`.
- `0x004021B8` `maybe_Ui_PartyPanel_UpdateMemberRows` → `maybe_Ui_PartyPanel_RefreshMemberRows`
  — same body as 0x00402180 minus the leading vtable+0x4C mode call; the "Rows vs Names" distinction did
  not exist.
- `0x004028A4` / `0x00402904` `..._UpdateMemberRows2/3` → `maybe_Ui_PartyPanel_BuildReserveRows` /
  `..._BuildReserveRowsB` — both start at party index 4 and fill at most four rows (limit 0x1F), i.e. the
  reserve members, not a second refresh of the active rows.
- `0x0028B71C` `maybe_Anim_CheckElapsedThreshold` → `maybe_Battle_CheckElapsedThreshold`
  — both callers are battle logic (`Battle_DecideFirstStrike`, `Battle_UpdateEnemySleepMask`).
- `0x003E8F84` `maybe_Field_Actor_UpdateWeaponAnim` → `maybe_Field_Actor_UpdatePoseAnim`
  — the function's own literal pool holds the animation names `Nut_1` and `Walk`; nothing points at a
  weapon track.
- `0x0040B7A8` `maybe_Ui_TextLabel_SubmitRotatedSlotText` → `maybe_Ui_LabelSlots_SubmitRotatedText`
  — the object is the *target* of four text slots (+0x10), not a label class the function owns. (This also
  removed the `check_refine` text-code flag; the evidence explains that 0x0061BD4C is used here as a
  generic id→string resolver, not as an item/inventory test.)

## Open problems / honesty notes

- 114 stayed `maybe_` on purpose. Many are plausible but unproven: the 0x004C8xxx gadget builders (no
  caller except a damaged spawner fragment), the 0x4A7E58/0x4A8084/0x4A85D8/0x4A8804 "Paired/Solo"
  unit-model variants (the flag pair f_142/f_143 is observed, the "partner present" meaning is inferred),
  and the 0x4D0A5C / 0x4D1F64 battle unit resets at 0.48.
- **Duplicate name conflict for the merge:** `0x003890C0` (this batch) and `0x004D0E54` are different
  functions both currently called `Battle_Ui_UpdateStateMachine`; 0x004D0E54 *calls* 0x003890C0. The
  former stays `maybe_`. `M1b_merge_refined` must not emit two identical names.
- `0x0047F9AA` is **not a function**: a thumb fragment inside 0x0047F794 (range 0x47F9AA..0x47F9FC is
  inside 0x47F794+0x216). Kept at 0.25 as an artefact; a later pass should delete it from the function list.
- Damaged/truncated bodies that cap confidence: 0x004C9C64, 0x0028E334, 0x00277E48, 0x00263B04, 0x00263BEC,
  0x003890C0, 0x004378DC, 0x002AB8C0 (`in_s0`), 0x00386DC0/0x00386DE8 (`in_s0`), 0x0049ED7C (`in_fpscr`).
- `0x00277E48 maybe_Model_SelectModelIdForActor` looks actively wrong (it stores per-id random values from
  the battle RNG and runs four category-slot hooks), but no better name is provable from the current
  names; it is flagged for the types pass rather than renamed on a hunch.
- `0x00279D0C maybe_Item_CheckBagAcquireSimple` — the readable C of the wrapper is truncated by the
  decompiler transform (only the local initialisation survives); the `Item_CheckBagAcquire` call is only
  visible in the Ghidra source. That is why it stays at 0.45.
- **Not verified:** everything is static analysis. No emulator run, no bit-match rebuild, no
  `tests/run_all.py` (rule 5's full run does not apply to refine batches). The readable C still shows the
  old names until `M1b_merge_refined` runs, so nothing here is visible in the viewer yet.
