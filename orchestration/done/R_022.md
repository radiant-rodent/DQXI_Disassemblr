## Method (and why it differs from a pure header re-read)

1. Read `README.md`, `orchestration/PLAN.md`, the batch file, `refine/scores.jsonl` (context score,
   `callers_conf`/`callees_conf`, `neighbour_names`) and the readable file's doc header
   (previous name, confidence, original batch, previous evidence).
2. Built a caller list per address two ways, because the batch scores only carry counts:
   - `grep` of `decomp/readable/**` for `0x<addr>` (data refs / constants), and
   - `grep` for `func_<addr>` — this is how a *named* caller appears in readable C. The second pass
     was decisive for many entries (e.g. every caller of `0x48748C` is a monster stat getter).
3. Where the pseudocode was damaged or a name looked wrong, opened the body in full and, for the
   damaged ones, the disassembly in `asm/` (`bl #<addr>` and the real prologue).
4. Promoted to `confirmed` only when a named caller/callee fixes the meaning **and** the class/role
   claim in the name was corroborated; otherwise `kept_maybe` with a sharper summary. 18 names were
   replaced because the body contradicted them.

## Corrections worth reviewing (all have the evidence in the JSON)

- `0x001D1FC4` / `0x001D2222` `maybe_Gfx_ComputeViewTransform(Ex)` → `maybe_Camera_UpdateFollowPosition(Ex)`:
  follow-camera position update (`Camera_BuildVisibleTargetLists`, `Camera_SetupFromRecord`, RNG shake,
  sin/cos), no matrix is built. The second address is a 2-byte-early entry split, not a separate API.
- `0x001E158C` / `0x001E1AD4` → `Field_ActorJumpTask_Ctor` / `Field_ActorWalkTask_Ctor`: the task name
  strings are the literals `0x706D754A` = "Jump", `0x006E7552` = "Run", `0x6B6C6157` = "Walk".
- `0x00473418` `ShowNameWindow` → `Monster_NotifyCommand20`: fills message arg 8 with the monster's
  two-part name and triggers field-gadget command 0x20; no window is created.
- `0x002F3A28` / `0x002F4708` → `maybe_Field_Marker_NotifyCommand00` / `NotifyCommand11`: both call the
  named `Field_Gadget_AddAndTriggerCommand` with 0 / 0x11; the old names (OnUpdate / IsEventPending)
  implied behaviour the bodies do not have.
- `0x003E73E0` `CreateController` → `maybe_Field_Actor_CreateSceneObjects`: vtable `0x726908` is the
  `Field_SceneObject` class (named deleting destructor `0x5B0274`), and the tail creates two collision
  objects.
- `0x003E870C` `BeginAttack` → `maybe_Field_Actor_ResetPoseState`: flag + counter + two cleared vectors,
  nothing attack-specific.
- `0x002826B0` `Ui_UpdateScrollOffset` → `maybe_Ui_ModelPreview_UpdateSpin`: the body is a reduced copy
  of the named `Ui_ListRow_UpdateWeaponPreview` (rotation state, `Gfx_Node_SetEulerRotation`, accessory
  attach/release).
- `0x0029DD44` / `0x0029DDAC` → `maybe_Ui_TwelveRowTextWindow_Ctor` / `..._DtorDeleting`: vtable
  `0x75EB0C` is shared with the named `Ui_TenRowTextWindow_Ctor`; the old names gave the ctor and dtor
  of one class two different class names.
- `0x00504324` `Svc_ReleaseAllSharedState` → `Svc_ReleaseSharedResources` (0x209 + 0x207 are shared
  resources, not state).
- `0x0048748C` `Monster_GetResistValue` → `maybe_Monster_GetRecordStatValue`: seven call sites, all
  inside the monster stat getters (attack/defence/agility/HP/MP bars); the two fields are stats, and
  "resist" was a guess.
- `0x00249448` / `0x0029954C` / `0x004A66D0` → `maybe_Ui_AdvanceChildWhenIdle(B/C)`: three copies of the
  same "if the input manager slot is empty, move the child to state 3" vtable slot with different slots.
- `0x004D1CDE` → `maybe_Battle_Ui_UpdateStateMachineFragment` at 0.30: the disassembly has **no**
  instruction at this address — it is 0xE8A bytes inside `Battle_Ui_UpdateStateMachine` (0x004D0E54, the
  entry installed in vtable 0x778E04). A Ghidra function-boundary casualty.

## Problems / honesty notes

- Static analysis only. **No** emulator run, no bit-match rebuild, no `tests/run_all.py`: rule 5's full
  run does not apply to a refine batch, and nothing here changes code or data. The JSON is a proposal
  file; readable C still carries the old names until `M1b_merge_refined`.
- `check_refine.py` initially flagged 4 entries (a predicate name on a `void` function and three
  "confidence >= 0.5 on a damaged body" cases). They were fixed by changing the decision, not the
  checker: `0x00371140` became `maybe_Field_Actor_UpdateCellTransition` (the body writes positions, so
  no predicate), `0x004D1CDE` was lowered to 0.30, and for `0x0026D9F0` / `0x00504324` the actual
  disassembly was cited (`bl #0x1ca474` at 0x0026DB34/0x0026DCBC; the 0x504324 → 0x504334
  fall-through into the 0x207 release block).
- Confidence was deliberately not inflated: 80 entries stay below 0.5. The main unresolved groups are
  (a) the 0x003A2xxx/0x0040Exxx "NotifyCommandNN" field-object handlers, where the command id and SE are
  certain but the *class* (Actor2D / TwoPartObj / ApproachObj / ModelObj / Object2D) is only inferred
  from the vtable data-ref; (b) the ctor families `0x002AC7EC`, `0x0041D760`, `0x004CE908`,
  `0x004FA5EC`, where the mechanism is known but the owning screen is not; (c) the three
  `AdvanceChildWhenIdle` copies, whose input-manager slots are unnamed.
- Two names in the neighbourhood look wrong to me but are outside this batch and were **not** touched:
  `Ui_SmithMenu_GetGlobal` (0x6F229C) is used everywhere as the generic UI manager, and
  `func_0021F8B8` is still an unnamed generic "delete object through the UI core" helper
  (`maybe_Container_ReleaseHandle` depends on it).
