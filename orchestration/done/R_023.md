# R_023 — second naming pass (refine), 150 low-confidence `maybe_` functions

## What I did

Worked through all 150 addresses in `orchestration/naming/refine/batches/R_023.txt`, in batch order
(highest context score first). For each one I re-read the readable C together with the header's previous
name/evidence, then checked the now-named callers/callees, the vtable siblings and the `neighbour_names`
context from `scores.jsonl`. For three low-level IPC/sound functions the readable body still contains
`unaff_` registers, so I read `asm/text/` and put the instruction-level evidence into the JSON.

Result: **75 confirmed / 31 corrected / 44 kept_maybe**, average confidence 0.467, 88 names at >= 0.5.
Every address is covered exactly once; every object carries `previous_name` (matching the batch),
`previous_confidence`, `change`, `params`, `summary` and an evidence line saying what NEW context decided it.

## Findings worth keeping

- **0x004ABC48 is not casino code.** The body is timestamp comparison over `Svc_Time_*` records plus a
  0x44-byte party-slot copy and `maybe_Ui_PartyStatusPanel_Build`; renamed `maybe_PartyStatus_LoadNewestRecord`.
- **IPC wrappers were named after their neighbours.** 0x001143C8 runs `Gfx_IpcCmd3E0080` *under* the lock
  (`Gfx_LockedIpcCmd3E0080`), 0x00107E9C only sends a byte (`Os_IpcSendByteLocked`), 0x0010D388 wraps
  `maybe_Svc_QuerySessionInfo` (`Svc_QuerySessionInfoLocked`), 0x00119C30 polls a status byte until a
  deadline (`Svc_WaitForStatusUntilDeadline`).
- **Equipped-item pairs, not "character pairs".** 0x00377420 / 0x003784D8 / 0x0038C9D8 all resolve the
  two ids from `func_006292F0(member, 0/1)` and classify them with `Text_GetCharPairStyle`; the code is
  about the equipped weapon/armour pair. (`Text_GetCharPairStyle` itself is therefore also misnamed — it
  classifies two *item* ids by category +0x29 — but it is outside this batch.)
- **0x0016A080 is battle units, not UI widgets.** It walks the four unit lists at +0x4298 and returns 1
  only when every unit's sound has finished -> `maybe_Battle_IsUnitSoundFinished`.
- **0x00667AE8 / 0x0066818C** are Field2D scene gates (all callers are Field2D render/update loops), not
  "UI element interactive" tests; they return 0 only for a fully idle object.
- **Tail-call truth from asm:** 0x0054F48C -> `b 0x519BF4` -> `0x517650(list, slot, track)`;
  0x0054F4F0 -> `b 0x519C08` -> `0x5176F4(list, slot, track)`. The readable bodies had the registrar
  inlined, which is why they looked like long functions with `unaff_r4/r5/r6`.
- **Name collisions avoided:** three names I first picked already existed at other addresses
  (`Battle_UnitModel_Update` 0x42A438, `Ui_Window_CtorBase` 0x2A4774, `Container_List_DestroyAll`
  0x2ABB8C, `Ui_MessageWindow_Dtor` 0x1C57E4); the JSON uses `Battle_UnitModelA_Update`,
  `Ui_Window_CtorBaseB`, `Container_List_EraseAllNodes`, `Ui_MessageWindow_DeletingDtor` instead.

## Open problems / honest limits

- 44 entries stay `maybe_` because the readable body is damaged (`halt_baddata`, `unaff_*`,
  `coprocessor_*`) or because the decisive callee is still unnamed. The most interesting ones:
  0x00369254 (guide-window page change), 0x003F6208 / 0x003F643C (decompiler-split continuation blocks,
  probably not real entry points), 0x004309A8 / 0x00430C86 (post-hit step machine),
  0x00435794 (impact effect branch, jump table lost), 0x00667EA4 (Field2D path step).
- 0x005E80A4 (`maybe_Actor_GetLookupState`) decompiles to bare `return;` statements, i.e. every return
  value was dropped; the name is intentionally vague.
- The `Text_*` row cluster (0x00486664…0x00498438) is now known to route through 0x00491270, whose name
  `Text_GetRowSpacing` is itself doubtful (it returns a battle-RNG-derived value in [0, record+0x2E]).
  Renaming that helper would unlock sharper names for six functions in this batch; worth a follow-up.
- The project's merge watcher applied this batch while it was being written (symbols.json and
  decomp/readable mtimes 22:55, headers say `Recovered: R_023`). I did not edit those files. I verified
  afterwards that all 150 readable files exist under exactly the final names, that no base name is
  duplicated, and that symbols.json carries the final names — but the merge was triggered by the tooling,
  not by me, so the orchestrator should treat `symbols.json`/`decomp/readable` as already merged for R_023.

## Suggested follow-ups

1. Name 0x00491270 (currently `Text_GetRowSpacing`) — it is the shared "random per-row value" helper used
   by 20+ battle-text functions; a correct name would fix six `maybe_` names from this batch.
2. Decide whether 0x003F6208 / 0x003F643C are functions at all; if they are shared tail blocks, mark them
   as such in the catalogue instead of naming them.
3. Recover the dropped returns of 0x005E80A4 from the disassembly (it is a small 136-byte function).
4. The 0x48xxxx–0x49xxxx battle-text-row cluster still lacks a model of its row record; a types pass (S_*)
   over the 0x3C0-byte layout built in 0x00467730 would let several names here become precise.
