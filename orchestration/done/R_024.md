# R_024 — second naming pass (refine), 137 low-confidence `maybe_` functions

**Status: complete.** `orchestration/naming/refine/out/R_024.json` has one entry for every address in
`orchestration/naming/refine/batches/R_024.txt` (137/137) and `python tools/check_refine.py R_024`
prints `R_024: OK`. The batch file was **not** regenerated.

Decisions: **60 confirmed / 22 corrected / 55 kept_maybe**. Highest confidence given is 0.55 (nine
functions); the confirmations sit at 0.50–0.55 because the evidence is call-site/callee/neighbour
evidence, not an emulator run. Nothing was pushed to 0.6+ on a hunch.

## Method

1. The doc header of each readable file (previous name, confidence, original `N_*` batch, previous
   evidence) was the starting point, as the task asked; I re-derived only what the new context changed.
2. **New evidence** came from:
   - `orchestration/naming/refine/scores.jsonl` `neighbour_names` + vtable/cluster fields for all 137;
   - the bodies of the now-named **callers and callees**, opened on demand (`grep` for the address or
     the current name) — this is what most corrections rest on;
   - `symbols_recovered.json` (current names), all other `refine/out/R_*.json` and `naming/out/N_*.json`
     for name conflicts (checked: no cross-address duplicates introduced; the only name I had to change
     for a clash was 0x002F6870, see below);
   - `asm/` when a body looked like data or a damaged prologue — that is how the 0x00591204 finding below
     was made.
3. Every entry's summary states *what and why*; evidence states what **new** fact decided the verdict,
   and for `kept_maybe` what exactly is still missing.

## Finding: 0x00591204 is data, not code

`asm/text/text_00580048.s` shows `pop {pc}` at 0x00591200, then the word 0x0046B5A4 and the ASCII map key
`"ReguralyShake"` at 0x00591204–0x00591215, then `push {r4, lr}` at **0x0059121C**. Nothing branches to
0x00591204, and the readable C it was given (`params->f_54 = params; unaff_r4->f_15 = ...`) is a decoding
of that data. So:

- 0x00591204 → `maybe_Camera_RegularShakeKeyData`, 0.30, "not a function".
- 0x0059121C is the real `maybe_Camera_CreateRegularShakeWork` (0.40); its five float parameters arrive
  in s0–s4, which is why Ghidra shows `in_s0..in_s4` unset in **both** entries.

Whoever merges should keep 0x00591204 out of the call graph (or drop it from the entry table); the
underlying data blob should become a `g_`-named object in a globals batch.

## Not verified / open problems

- Everything here is static analysis. No emulator run, no save state, no in-game confirmation of any
  renamed function; no readable `.c` file was regenerated (the merge step does that).
- Several names still rest on the project's own earlier guesses that I could not re-check: e.g.
  `maybe_Ui_SlotTable_*`, `maybe_Ui_LoadRecordTable`, `maybe_WorldMapMarker_*`, `maybe_Ui_WorldMapMarker_Dtor`
  (as the 2D-anim teardown) and `maybe_Ui_CmdQueue_PushEntry` (as the battle action push) look
  mis-attributed to me; I avoided depending on them where possible and said so in evidence.
- 0x003C35D0, 0x00204980, 0x00114AB4, 0x00591B8C, 0x00108F22, 0x0062DA68 have `halt_baddata` /
  `unaff_r*` / `coprocessor_*` bodies; their signatures are best-effort and stay below 0.5.
- The 0x00782A08 / 0x98-byte global context (0x7BE340) is used by 124 functions and still has no name.
  Naming it (one dedicated accessor + a plausible subsystem) would unlock a dozen `maybe_` entries in
  this and later batches — worth a task of its own.
