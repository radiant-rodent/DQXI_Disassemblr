## The batch-wide discovery (affects future refine batches)

**The readable C stops at the first call Ghidra marked "does not return".** 0x001A5F9C carries that
annotation, and it is the last call of roughly 40 of these 150 functions — so a large part of this batch
looks like a 3-line thunk while the real function continues for another 20–80 instructions.

Verified counter-example (asm `text_00180048.s` @0x001A5F9C):

```
push {r4,r5,r6,lr}; r4=r0+0x10; r5=[r0+0x14]; r6=r1
loop: r0=[r5]; r1=[r0]; r2=[r1,#0x1c]; r1=r6; blx r2; r5=[r5,#4] ...
pop {r4,r5,r6,pc}
```

i.e. **`Ui_Object_BroadcastToChildren(obj, flag)` is correct and it does return**. The companion
primitives, also verified in asm, are `0x00123594` = re-link a node into the intrusive list at
`obj+0x110`, `0x0062F070` = count that list, `0x0010EBD8` = pop its head. Nothing in that family frees
memory, which is why so many first-pass names say "Destroy/Release/Finalize" without support.

Examples of the hidden tails (all cited in the evidence fields): 0x002622C4 hides +0x804/+0x9D8/+0xF24
and calls 0x0029126C four more times; 0x0047A510 hides five more sub-widgets; 0x0030E948 broadcasts to a
second list at +0x1614; 0x00316140 binds a whole state record.

## Honest keeps (86)

* The whole "drain children → re-link embedded node → dispatch flag" family (12 × `Ui_Window_FinalizeA..L`,
  7 × `Ui_Window_ReleaseChildWidgetsA..G`, 4 × `DestroyChildren*`, 6 × `Ui_Screen_BroadcastFlag*`, the
  `ReleaseChildrenA..D`, `DetachChild*`, `DrainAndRelease*`): the *mechanics* are now certain (see above),
  but every one of them is a per-class vtable slot whose body is truncated, and nothing identifies the
  class. Keeping them `<0.5` and saying so is more useful than inventing a class name.
* Damaged bodies: 0x003C3560 (0.25, unaff/halt_baddata), 0x001BF838 (0.40), 0x002399D4 (0.32),
  0x002448BC (0.40).
* Everything whose only class evidence is itself a `maybe_` caller (0x0025AB04, 0x0041B280, 0x004655D0,
  0x0025A3C0, 0x0025B358, 0x0029AA14, 0x0025BEE4, 0x0064E4C4, 0x001D7AA0, …).

## Not verified / open problems

* **Static analysis only.** No emulator run, no `tools.build` bit-match, no `tests/run_all.py` — rule 5's
  full run does not apply to a refine batch, and nothing here changes codegen. The readable C keeps the
  old names until `M1b_merge_refined`.
* **Two shared callee names look wrong** (outside my batch, but they poisoned several summaries and should
  be fixed by a later task):
  * `0x00306A9C` is named `Ui_Message_SetNameArgs3`, but it is called exactly where an old value is
    *released* (`0x001E4C1C` before the memmove, `0x0036911C` when `f_14` is replaced).
  * `0x001FF200` is named `FieldParty_ResetMemberSlot`, but the field object ctors call it as the plain
    base-object reset.
* The A..L / A..G suffixes are still placeholders; identifying the UI classes needs a vtable-to-screen
  mapping (each of these is one slot of a known vtable address, e.g. 0x0072B56C for the Finalize group).
* `0x001A5F9C` being annotated noreturn in `decomp/ghidra` is the root cause of the truncation; the
  annotation (not the C) is what a regen task should fix, otherwise every future batch re-derives these
  same truncated bodies.
