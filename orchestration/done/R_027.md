# R_027 — second naming pass (refine), 150 low-confidence `maybe_` functions

## What was done

All **150** addresses in `orchestration/naming/refine/batches/R_027.txt` were re-examined and written to
`orchestration/naming/refine/out/R_027.json` — one object per address, batch order, 150/150 covered.
No other repository file was modified except `AGENT_LOG.md` and this report. Scratch (the dump helper
and the per-chunk JSON) is in `out/scratch/R_027/`.

**Result: 42 `confirmed` / 28 `corrected` / 80 `kept_maybe`; confidence range 0.25–0.55.**
`python tools/check_refine.py R_027` → `R_027: OK`.

Method per entry: start from the readable file's doc header (previous name/confidence/evidence), re-read
the body with its now-named neighbours (the batch's own `scores.jsonl` neighbour list, plus a scan of
`decomp/readable/functions/*.c` for callers and for the named callees that the readable C now shows
inline), then look for evidence that is harder than the first pass had. For a handful of addresses I
checked `asm/text/*.s` to see the real instruction (`bl` target, argument validity, `halt_baddata`
bodies). Where a callee's name turned out to be wrong, that is stated in the entry — the callee itself
was **not** renamed (outside this batch).

## Hard evidence found in this batch

1. **Vtable data symbols now decide battle-popup classes.** The merged state carries
   `g_battleCritPopupVtable`, `g_battleDamagePopupVtable`, `g_battleMpDamagePopupVtable`,
   `g_battleHealPopupVtable{,B}` and `g_battleMissPopupVtable`, each backed by a named ctor/dtor
   (`Battle_Popup_Heal_Dtor` 0x00403CC4, `Battle_Popup_InitMissPopup` 0x00403D18, …). Combined with the
   object size (0x530 vs 0xBB8 = 15×0xA8 + 5×0x50 + header) this turned:
   - 0x002E253C `EnsureLargeA` → `Battle_Popup_EnsureHeal`
   - 0x002E2864 `EnsureLargeB` → `Battle_Popup_EnsureCrit`
   - 0x002E2A18 `EnsureLargeC` → `Battle_Popup_EnsureDamage`
   - 0x002E2E20 `EnsureLargeD` → `Battle_Popup_EnsureMpDamage`
   - 0x002E2448 `EnsureSingleA` → `Battle_Popup_EnsureMissSingleB` (same object/vtable/layout string as
     the confident `Battle_Popup_EnsureMissSingle` 0x002E2650, plus an inline shake reset)
   - 0x002E2714 `EnsureSingleB` → `maybe_Battle_Popup_EnsureHealB` (the 15-number form; HP vs MP still
     unresolved, so it stays `maybe_`).

2. **0x0046978C is the tumble-end action-animation element.** Its vtable is
   `g_battleActionAnimTumbleEndVtable`, the sibling 0x00469808 is the *confident*
   `Battle_ActionAnim_BatTumbleEndElementCtor` (`…TumbleEndVtableB`, key `bat_tumble_end`), so the name
   changed from `…ElementCtorSlot9F` to `Battle_ActionAnim_TumbleEndElementCtor` (slot 0x9F and the
   data-blob key stay in the summary).

3. **`Gfx_SceneNode_LoadMeshByName` (0x005F541C) is a vtable-override base call.** The small functions
   0x00382048, 0x002F3110, 0x006E668C/0x006E6724/0x006E67BC/0x006E68EC and 0x003EA1AC begin with
   `bl 0x5F541C` and simply forward the caller's resource-name register (confirmed in
   `asm/text/text_00380048.s` and `text_002C0048.s`). They are overrides — "load the layout, then
   configure X" — not pure setters; their summaries now say so and the unnamed `resourceName` parameter
   is documented instead of being called a `ResourceEntry`.

4. **Same-body families.**
   - 0x00298AEC == 0x003B43FC (three calls: `Save_SlotUi_BuildThree`, `Ui_DualDisplayWindow_SelectDefaultPane`,
   `func_0029126C(ptr,1)`) → both corrected to `maybe_Save_SlotUi_ResetThree{,B}`.
   - 0x00382AD0 == 0x00387058 == 0x0039AA4C: all three clear `UiCore+0x94` after
     `Container_RingBuffer_Next`. The third (0x0039AA4C) inlines `Ui_GetCore`; the old
     `Container_RingBuffer_AllocSlots` mis-read that inline allocator as a slot array. The proof is the
     vtable 0x00782A08 = UiCore's vtable (from the confident `Ui_GetCore` header).
   - The four `maybe_Gfx_EffectNodeCreateChild_75B0xx` are the same allocate-0xAC-plus-64-entry-pool
     object family as the `maybe_Effect_ParticleEmitter_InitPool*` entries; noted in all eight.

5. **Name collisions avoided.** Two of my first-pass refinements would have collided with confident
   symbols and were renamed inside the batch: `Ui_MessageWindow_Update` already exists at 0x001C40F8
   (so 0x002CEF08 is `maybe_Ui_MessageWindow_UpdateFrame`), and `Ui_ReleaseTwoHandles` already exists at
   0x003A6E70 (so 0x00311C3C is `maybe_Ui_Object_ReleaseHandles`). A script check against every readable
   file stem found no remaining cross-address collision.

## Open problems / suggested follow-ups

1. **Mis-named callees that polluted several names in this batch** (each is outside R_027, so I only
   flagged it): `Ui_Talk_LoadDialogueLayout` (0x00644A9C) and `Ui_Message_SetItemNameArg` (0x006444D4)
   are record getters in the smith menu; `Gfx_SpritePool_Alloc` (0x005F24A4) is a no-argument lookup;
   `Snd_RequestBgmPlay` is used to stop sound 5 in `maybe_Ui_JockeyPanel_Destruct`;
   `Sound_CommandQueue_Push_2` resolves a message text id in 0x002CEF08;
   `maybe_Ui_Plate_SetLeftMargin/SetRightMargin` are record-cursor accessors used by the party-entry
   walk (0x004A4D80/0x004A54AC); `Ui_PagedIconSelect_RefreshPanes` name is good but the +0x2AC column
   meaning is not. Suggested task: one small batch to fix this cluster, then re-refine the 6–8 entries
   that currently say "blocked by a wrong callee name".
2. **`Gfx_SceneNode_LoadMeshByName` overload semantics**: it is used as a vtable slot whose resource
   name is passed in r1; callers that invoke it with one argument (the readable C shows `()` ) are
   overrides. A FACTS.md line would prevent future workers from naming such functions "Set…" when the
   leading call is the base override.
3. **UiCore inline copies**: 0x0039AA4C, 0x00282F04 and 0x002B5E30 each inline a full singleton
   create/return block for a known singleton (UiCore vtable 0x00782A08, record-manager vtable 0x00782990).
   Recognising them from the vtable constant is much faster than reading the allocator; worth a FACTS.md
   note.
4. **0x00382AD0/0x00387058/0x0039AA4C are the same operation** (clear UiCore+0x94 after the input ring
   buffer advances). `UiCore+0x94` is also cleared by the Sakusen pane handler when it consumes an event;
   the field is still "pending-input word" by inference only.
5. **Battle popup HP vs MP heal**: `g_battleHealPopupVtableB` is used by both
   `maybe_Battle_HealPopup_Dtor` (15×0xA8 + 5×0x50) and `Battle_Popup_InitMpHealPopup` nearby, so
   `maybe_Battle_Popup_EnsureHealB` deliberately stays neutral. A follow-up should read the layout
   strings for the two heal popups to split HP/MP.
6. Not verified: every name here is static inference. The strongest evidence (vtable symbols, string
   literals, confident callers) is marked as such in each entry's `evidence`; the rest should be
   re-checked when types/fields land in the `S_*`/`G_*` passes.
