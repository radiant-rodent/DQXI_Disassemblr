# R_028 — second naming pass (refine), 147 low-confidence `maybe_` functions

## What I did

Worked through all 147 addresses in `orchestration/naming/refine/batches/R_028.txt`, in batch order
(highest context score first). For each function I started from the readable file's doc header
(previous name, confidence, evidence), then re-read the body against the now-named callers/callees,
the `neighbour_names` / vtable / constant context in `orchestration/naming/refine/scores.jsonl`, the
current `symbols.json` / `symbols_recovered.json` names, and `grep` of `decomp/readable` for the
*current* name (the address in the batch file no longer appears in the readable C, so named callers
have to be found by name). Where a body was corrupted by Ghidra I read `asm/text/*.s` directly.

Result: **108 confirmed / 13 corrected / 26 kept_maybe**, average confidence 0.489, 109 names at >= 0.5.
Every object carries `address`, `name`, `signature`, `params`, `summary`, `confidence`, `evidence`,
`previous_name` (exactly the batch name), `previous_confidence` and `change`.

## Findings worth keeping

- **0x004908CC is item code, not text.** It resolves the member's equipped item (`0x35EB98` +
  `0x6292F0`), goes through `Item_LookupRecord` and picks a row metric from the item record's `+0x29`
  category. The first pass called it `Ui_Text_GetTypeHeight`; renamed
  `maybe_Item_GetRowMetricByCategory` (and said so in the evidence, since `check_refine.py` flags
  text-named item code).
- **The 0x66xxxx getters belong to Field2D, not Text.** 0x667068 / 0x667108 are called only from
  Field2D map code (`Field2D_Actor_CheckCollisionBox`, `Field2D_MapChip_ResetWalkTrigger`,
  `Field2D_MapChip_SetWalkTriggerState`, `Field2D_Scene_BuildFromMapData`, `Field2D_Scene_UpdateLayers`),
  and 0x667724's "two layout probes" are `Field2D_MapChip_PackLayerChipIds` calls that convert a
  sprite block's box into a chip range. Renamed `maybe_Field2D_Layer_GetField12`,
  `maybe_Field2D_Layer_GetKindGroup`, `maybe_Field2D_SpriteBlock_UpdateChipRange`. The sibling
  `maybe_Text_Style_GetField12B` (0x6688B4) is presumably misnamed for the same reason.
- **0x006D94F0 is a path builder, not a memory helper.** The body allocates a 0x30-byte-per-point
  block, evaluates the cubic between consecutive points (basis 0.125/0.25/0.5) and accumulates
  arc lengths; it is called by `Path_BuildFromPoints` immediately after `Path_ComputeDirections`.
  Renamed `maybe_Path_BuildArcLengthTable`.
- **Name clash avoided in the emitter family:** the batch's `maybe_Field_ModelSlotEmitter_Ctor`
  (0x4B2CA4) is *not* the constructor — 0x4B3374 already owns the confident
  `Field_ModelSlotEmitter_Ctor` (it installs both vtables 0x77696C/+0xD4 and the two intrusive lists).
  0x4B2CA4 only seeds the emitter's state from a definition block plus an optional template object,
  like the named sibling `Field_ModelSlotEmitter_ApplyDescriptor` (0x4B2A6C) -> renamed
  `maybe_Field_ModelSlotEmitter_InitFromDef`.
- **0x005E82C4 is a movement scale, not a render scale.** All four callers are NPC walk/run
  initialisers that store `out[0]` as their speed and use `out[1]` to choose the walk animation;
  `out[0]` is 1.0 x {0.5, 0.6, 1.5} selected by the actor data record's size class ->
  `maybe_Field_Actor_GetMoveSpeedScale`.
- **Destructors vs. the functions they call:** 0x004E1E4C was called `Ui_TargetMarker_ReleaseAll` but
  it is the container destructor that *calls* the now-confident `Ui_BattleTargetMarker_ReleaseAll` ->
  `Ui_TargetMarkerContainer_Dtor`. 0x004B65F4 was `Container_InitListPair`, but the helper it runs
  (`0x6F5384`) frees three owned pointers and most callers are destructors -> `maybe_Container_ResetListPair`.
- **0x006E524A** is the equipment-detail epilogue (byte-for-byte the tail of 0x3D6480/0x3D6750: store
  the sub-panel at owner+0x10CC, then `Ui_Panel_ResetAndPush`), not a generic "HandleCommand" ->
  `maybe_Ui_Panel_OpenDetailForCurrentId`.
- **0x003E9EF8** is the casino prize/coin counter label (called from `Ui_PokerWindow_Payout` and
  `Ui_CasinoPrizeWindow_Ctor`, fed by the bag money formatter 0x66B2CC), not a "debug label".
- **0x003E7770** is applied on every pose change; its callers (`Field_Actor_Suspend`,
  `maybe_Field_Actor_DeleteFromScene`, `maybe_Model_Actor_UpdateScale`) re-apply the current pose, and
  the body interpolates the 0x39-row motion table by frame progress -> `maybe_Field_Actor_UpdateMotionPose`
  rather than "LoadMotionSet".
- **0x0041E80C** initialises a draw object created by `Field_SceneObject_CreateDrawObject`, not a UI
  window: all four callers are scene-object/gimmick draw-object setup functions ->
  `maybe_Field_DrawObject_InitWorkData`.
- Item/text trap in the other direction: the `Text_CalcRow*` helpers (0x48F4AC/0x48BB34/0x490D28/
  0x491884) only consume the battle RNG (`func_001CA474` at work+0x5C+0x4218, established fact) and
  return layout offsets. The old header's "Item_LookupRecord/0x1CA3E4" hint for 0x490D28 was a
  misnomer, so the evidence of that entry says explicitly that it "returns a value and touches no item data"
  (needed because `check_refine.py` matches the word `Item_LookupRecord` in the header text).
- Confirmed-only entries where the new context really did decide it: the whole sound-sequence cluster
  (0x555308/0x555878/0x555794/0x55614C/0x55624C/0x55668C — all callees are now named), the movie-track
  quad (0x4FCC28..0x4FCF9C, pause/resume differ only in the decoder state), the regex builder/matcher
  cluster, `Gfx_ModelResource_Release` (sole caller is `Gfx_ModelResource_Parse`), and the two status
  value calculators 0x4F358C/0x4F3BC0 (attack/defence parameter-id chains compared side by side).

## Open problems / not verified

- Static analysis only. Nothing was run in the emulator and no bit-match rebuild was done (rule 5's
  full run does not apply to refine batches). No name here changes `asm/`, so `code.bin` is unaffected.
- `decomp/readable` was being regenerated by a background merge while this batch ran (file count fell
  to 6,693 and came back to 18,151 with the same paths). I re-validated after it settled, but if a
  later merge rewrites the tree again the batch paths stay valid because they are address-based.
- Still genuinely ambiguous and therefore left `maybe_`: the actor focus state machines
  (0x4BFA20/0x4F5138, damaged dispatch, unnamed state constants), the two vtable-only screen
  constructors (0x4D3590/0x4F4ACC), the object-list entry builder (0x5D19B8), the overlay batch
  entry (0x55D428), and 0x56D600 (second texture-unit block emitter).
