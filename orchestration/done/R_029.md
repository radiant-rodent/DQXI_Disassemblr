# R_029 — second naming pass (refine), 136 low-confidence `maybe_` functions

## What was done

Processed **all 136** addresses in `orchestration/naming/refine/batches/R_029.txt` and wrote
`orchestration/naming/refine/out/R_029.json` (one object per address, in batch order).
No other repository file was modified except `AGENT_LOG.md` and this report.

Method (per entry):

1. started from each readable file's doc header (previous name, confidence, original batch,
   previous evidence) instead of re-deriving the guess;
2. re-read the body against the now-named neighbourhood: built a caller index by scanning
   `decomp/readable/**` for every batch name (the C files do mention their callers by the
   merged names), and additionally resolved unnamed callees that mattered
   (`func_0010F6CC`, `func_0029126C`, `func_005F8528`, `func_001C7570`, `func_0063EFF0`,
   `func_002AB698`) by reading `asm/text/*.s` and the named users of the same address;
3. cross-checked `symbols.json` / `symbols_recovered.json` / `decomp/native_names.json` for
   siblings that already carried confident names (e.g. `Battle_AnimWindow_*`,
   `Field_*Action_Start/Update`, `Gfx_ModelInstance_Dtor`, `Ui_MessageCmd_Show*`,
   `Actor_Action_GrabNut_*`) and the packed four-character name constants passed to the
   actor task/action ctors (`0x6E7572` = "run", `0x74756E` = "nut", `0x6D756E` = "num");
4. decided, and wrote the *new* evidence (not the old) plus a fresh summary.

Scratch (caller index, per-function dumps, part files) is in `out/scratch/R_029/`.

**Result:** 20 `confirmed`, 39 `corrected`, 77 `kept_maybe`; confidence range 0.25–0.60.
`python tools/check_refine.py R_029` → `R_029: OK`.
All entries re-read as strict UTF-8; no name in the batch duplicates another batch name, a
`symbols_recovered.json` name, or an existing `decomp/readable/functions/*.c` file prefix.

## Corrected where the new context contradicted the first pass

The biggest single source of corrections was `func_0010F6CC`: it is the shared **operator
delete / refcounted release** (assembly: loads the 8-byte allocation header at `object-8` and
tail-calls its `vtable+4`). Several first-pass names had described a *construction* where the
body is a deleting destructor:

| address | old | new | why |
|---|---|---|---|
| `0x004ECD68` | `Ui_Object_ConstructComplete` | `maybe_Ui_Object_DtorBattleActorBase` | stores `g_battleActorBaseVtable`, runs the pack-handle and member dtors, then operator delete |
| `0x002C6A0C` | `Ui_Screen_ConstructSubObjects` | `maybe_Ui_Screen_SubObjectsDtor` | three base-table resets + `Gfx_MaterialBinding_Release`/`Gfx_TextureBinding_Release` + delete |
| `0x0055E274` | `Gfx_ModelInstance_ResetForReuse` | `maybe_Gfx_ModelInstance_DtorLinked` | stores its vtable, unlinks `self[2]/[3]`, frees |
| `0x00576E80` | `Script_ReleaseCallback` | `maybe_Script_CallbackHolder_Dtor` | two-call deleting destructor of the callback holder |

The second source was `func_0029126C`, which many first-pass notes called "release" or even
"noreturn assert". Its assembly is a plain **flag setter**: `ldr r2,[r0,#4]; strb r1,[r0,#0x14];
… and #0xFE / orr / strb [child,#0x44]; bx lr`. That flipped several names:
`0x0029AEC4` "ReleaseSubWidget" → `EnableSubWidget`; `0x0041CA58`'s trailing call is not a
release; `0x003DE694`/`0x00394CD0`'s "assert/finish" steps are flag writes.

Also corrected: three "Ctor" names that allocate nothing (`0x0025C624`/`0x0025DFC4`/`0x0025E0BC`
are widget rebuild/variant steps), three "InputToState4*" handlers that are actually
`StartAction4*` (animation id 4 + list confirm), `0x004CE35C`'s sibling `0x002C074C` is a 4-state
sequence ctor (not "4Anim"), `0x001BAB48` is an actor action/task ctor (not `Gfx_`),
`0x004F0C88` builds a 57-entry action table (not one entry), and `0x00619D28` is an anonymous
dtor thunk, not `Container_DestroyObjectRef`.

New evidence also forced two *downgrades* rather than renames:
`0x00235804` (init-vs-teardown direction unproven, 0.35 → 0.30) and `0x0066D680`
(its inline member is constructed by a function that was merged as a *destructor*, 0.30).

## Open problems / not verified

- Static analysis only. No emulator run, no bit-match rebuild (rule 5's full run does not apply to
  refine batches; `tools/check_refine.py R_029` is the applicable check and passes).
- The readable C in `decomp/readable/` still carries the **old** names; they change when
  `M1b_merge_refined` runs. Nothing I wrote changes behaviour.
- Judge calls worth a second opinion:
  - `0x003E3ACC` — still `maybe_Field_SceneEffect_Create`; the body spawns a 0x298-byte sprite
    actor (sprite 0x13E) into the field actor list but nothing identifies it as an "effect".
  - `0x00236B50` — `maybe_Ui_Overlay_ResetElementAnimation` vs. its now-named in-loop callee
    `maybe_Field_Actor_UpdateAttachTransform`: "reset" and "update" cannot both be right.
  - `0x0066D680` / `0x00235804` — construction vs. destruction still unresolved (kept below 0.5).
  - `0x0040459C` — "FindFirstUsableMember" tests `unit vtable +0x10 == 0`; whether that means
    usable, alive or visible is unknown.
  - `0x003B44B8` — renamed mechanically to `maybe_Ui_Widget_ApplyPendingEvent_3B44B8` because its
    body is byte-identical to `0x00298BC4`, so at most one of the two first-pass names could hold.
- 4 of the 15 vtable/neighbour constants I relied on are still unnamed (`0x0072C778`,
  `0x0072F49C`, `0x007AE6E8`, `0x00728F64` handler table), which caps confidence on the
  `Ui_*` and secondary-motion entries.
