# R_030 — second naming pass (refine), 79 low-confidence `maybe_` functions

## What was done

All **79** addresses in `orchestration/naming/refine/batches/R_030.txt` were re-examined and written to
`orchestration/naming/refine/out/R_030.json` (one object per address, batch order, 79/79 covered).
No other repository file was modified except `AGENT_LOG.md` and this report. Scratch (caller index,
helper scripts, the generator for the JSON) is in `out/scratch/R_030/`.

**Result: 22 `confirmed` / 21 `corrected` / 36 `kept_maybe`; confidence range 0.30–0.55.**
`python tools/check_refine.py R_030` → `R_030: OK`.

Method per entry: start from the readable file's doc header (previous name/confidence/evidence), re-read
the body against its now-named neighbourhood (a caller index was built by scanning every
`decomp/readable/functions/*.c` for the batch names), then look for evidence that is *harder* than the
first pass had:

1. names that already own an address (`symbols_recovered.json`, `decomp/native_names.json`,
   `orchestration/naming/out/*.json`, `refine/out/*.json`) — this also caught one name collision;
2. the rodata string behind a literal the code passes to the service opener;
3. `asm/text/*.s` where the readable C overruns the function (three cases).

## Key discovery (affects ~8 entries and probably many more batches)

`func_0011CCA0` is **`strlen`** (byte loop, then the word-at-a-time `uqsub8` trick) and
`func_001192C0(out, name, len, 0)` is the **srv GetServiceHandle IPC** (`svc 0x32`, it rejects
`len > 8`, i.e. the 8-char service-name limit). So every `func_001192C0(out, literal, strlen(literal), 0)`
prologue names its service outright. Decoded from `asm/rodata`:

| literal | string | used by |
|---|---|---|
| `0x0078C452` | `cfg:u` | 0x00112050 / 0x0011212C / 0x00112250 / 0x001121E4 |
| `0x0078C6F3` | `cfg:s` | 0x001182FC / 0x0011820C |
| `0x0078C6ED` | `cfg:i` | 0x001183A4 / 0x00118288 |
| `0x007418E4` | `ndm:u` | 0x0010C694 |
| `0x0078C495` | `gsp::Gpu` | 0x0051BCE0 (and `Gfx_InitDrawState`) |
| `0x007418AC` | `cecd:u` | already known (`Svc_Cecd_OpenService`) |
| `0x00754FC0` | `ir:USER` | 0x00122200 |

This turned the "anonymous shared session" family into ordinary service clients (see below) and is the
single most valuable outcome of the batch: these names are no longer guesses.

## Kept `maybe_` on purpose

36 entries stayed below 0.5, mostly because the subsystem is inherited rather than proven
(`Snd_Init/TeardownStreamContext`, `Snd_ChannelWorker`, `Snd_WaitBufferId`, `Snd_WaitTransferDone`,
`Snd_InitRuntimeBlock`, `Fs_AsyncLoadWorker`, `Fs_SeekStream`, `Container_MapLowerBound`,
`Gfx_MovieQueue_Peek`, `Mem_PoolDestroy/HeapFreeLocked`, `Os_WaitSyncObject/ReleaseSharedHandle/
InsertListNodeByKey/UnlockMonitor`, the four `Gfx_SetLayerState*`, the three `Ui_IconCache_*`,
`Svc_AcClient_Query`, `Svc_SetFieldLocked`, `Svc_SyncObject_DestroyB`, `Ui_MessageWindow_Command`) or
because the body is damaged (`0x0011223E` 0.30, `0x00115410` 0.30, `0x00111D0C`,
`0x00517942`, `0x001121E4`).

Two honest downgrades worth noting:
- `0x00547E7C` — the readable body overruns into 0x00547EB0; the disassembly shows the real function is
  0x34 bytes and tail-branches into the queue helper, so Ghidra's four-argument prototype is fiction.
- `0x00115410` (`maybe_Snd_SubmitBuffer`, 0.30) — the body reads its owner and flags from
  `unaff_r4/r5/r7` and the header's "2920 Thumb bytes" does not match the 20 statements, so *nothing*
  in it can be promoted without a fresh disassembly.

## Open problems / suggested follow-ups

1. **`ir:USER` cluster needs a second look.** `0x00122200` really does open the `ir:USER` service
   (literal 0x00754FC0 → "ir:USER", 7 chars, passes the `len <= 8` check of 0x001192C0) and
   `0x0011E54C` closes that very session, yet the surrounding cluster is called
   `Gfx_OpenGpuChannel` (0x0010BB34, 0.52) / `Gfx_ShutdownChannel` (0x0010BA40) / `Gfx_FinalizeSession`.
   The GPU session is the *other* block (`0x007AF178` = `gsp::Gpu`). Suggested task: re-check
   0x0010B9xx–0x0010C5xx as a unit (`ir:USER` client vs gsp client). I renamed only my own addresses
   (`maybe_Svc_Ir_SetupChannel` 0.35, `maybe_Svc_Ir_CloseService` 0.45) and flagged the conflict instead
   of touching confident names.
2. **`Os_AcquireSharedSession` (0x0010BDF8, 0.50)** should probably become a `Svc_Cfg_*` wrapper to match
   `Svc_Cfg_AcquireService`; same for the `maybe_Os_ReleaseShared*` family. Merge-time reconciliation.
3. **`maybe_Snd_OpenHandleIpc` (0x0011E940)** is the generic *service opener* (`strlen` + GetServiceHandle
   + session flag fiddling), not audio — it opens `cfg:s`/`cfg:i` in this batch. Worth renaming to
   `Svc_OpenServiceHandle` and would then fix the remaining `Snd_` prefixes in this area.
4. `maybe_Text_Font_ReleaseRef` (0x0050E5B8) is used as a **heap free** by `maybe_Mem_HeapFreeLocked`;
   the text/font name is very likely wrong (same trap type as the FACTS.md "Items, shop, inventory"
   entry). Suggested: check 0x0050E5B8 against the allocator family.
5. Three bodies should be re-disassembled rather than renamed further: 0x0011223E (18 bytes),
   0x00115410 (reported 2920 bytes, body is a fragment), 0x00547E7C (0x34 bytes, tail branch).
6. Not verified: everything here is static analysis; no emulator run, no bit-match rebuild (not
   applicable), and no runtime confirmation that a session named `cfg:u`/`cfg:s`/`cfg:i` is used the way
   the names imply — the *name strings* are hard facts, the "which subsystem needs them" reasoning is not.
