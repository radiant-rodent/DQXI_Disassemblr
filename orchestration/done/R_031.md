> Note: the batch file has CRLF line endings and its 5th column is the context score; the readable paths
> are clean. I read each path from a **snapshot** (`out/scratch/R_031/snap/`) because another worker was
> regenerating `decomp/readable/` while this task ran (the directory briefly dropped from 18,151 to 1,193
> files at 22:57). The snapshot is the state the batch was generated from; if `M1b_merge_refined` later
> regenerates the readable C, these entries are unaffected.

Method per entry: start from the readable file's doc header (previous name/confidence/evidence), re-read
the body together with its **now-named** callees and callers (a one-pass call-site index over
`decomp/readable/**` — the batch's `neighbours` field alone misses the call sites), then look for
evidence that is stronger than the first pass had. Where a callee name itself looks wrong, the entry says
so; the callee was not renamed (outside this batch).

## Hard evidence found in this batch

1. **The `'%d'` number-label family.** 0x0061B724 and 0x003B5850 both write a value into the global
   message buffer (global 0x7AC834 +0x848) with the format literal Ghidra prints as `0x00640025` /
   `0x00750025`, which is the UTF-16 `"%d"` at `0x0078C810` (`asm/rodata/rodata_00785000.s` line 7689,
   word `0x25006400`). Both then attach UI string 0x15 to pane 0 or pane 1 (`f_28<<16` vs `| 1`).
   The already-merged `maybe_Ui_SetNumberText` (0x003D2A8C) writes the same two panes with font ids
   0x21/0x15, which fixes the family. So `maybe_Ui_MessageWindow_SetStatusText` →
   `maybe_Ui_SetNumberTextPane0` and `maybe_Ui_SetIcon` → `maybe_Ui_SetNumberTextPane1` (the seven
   callers of the latter are item/shop screens passing counts and prices, not icon ids).
2. **One `vtable+0x18` query explains five "condition" functions.** `Ui_GetCore()->f_14->f_C` virtual
   +0x18 is the transition-busy flag: the confirmed `Ui_MessageWindow_IsTransitionBusy` (0x0064219C)
   proves the polarity through its caller `Ui_MessageWindow_UpdateInput`, which only runs its normal
   branch when the result is 0. The four `Script_MessageConditionCheck*` entries are the same query
   behind different guards (`f_C != -1`, `f_578 == 7`, `f_578 == 0x1A`, `f_120 == 0x3D`) and were renamed
   `maybe_Ui_QueryTransitionBusy*`; `maybe_Message_GetTextSpeed` (0x0063A764) returns the very flag byte
   `f_3D` that `Ui_Screen_IsTransitionIdle` inverts, so it became `maybe_Ui_GetTransitionFlag`.
3. **Arm/field object model is now readable enough to name the effect plumbing.** 0x005D8460 /
   0x005D84B4 / 0x005DD2F4 all go through `scene->f_E8` and the `0x003D55F4 / 0x003D5648`
   InitComponent pair (the same one `ApplyPartTint` uses), so "effect component at self+0xC0" versus
   "release the component at self+0xEC" is now a pair, not a guess.
4. **Timer pumps are one template.** `Svc_TimerSub_RunDue_24` (0x00316250), `Ui_UmaWindow_Update`
   (0x004D9134) and `maybe_Ui_FrameScript_UpdateB` (0x0029A920) are the same code with 24 / 11 / 11
   slots and 0x18-byte entries (base update, 1/30 s accumulator `0x3D088889`, callback at +0x34 with the
   +0x38 adjustor, then clear `UiCore+0x94`). That is why the first two could be confirmed at 0.5.
5. **The `UiCore+0x94` clear** (`*(u16*)(*Ui_GetCore() + 0x94) = 0`) appears in ~15 of these functions
   and is the reliable "this handler consumed the input" marker; it is quoted in the summaries instead of
   being called a "message pending flag" (the field is still only inferred).
6. **Class blocks are real**: `Ui_DiveCapture_Ctor_00444610` / `Ui_DiveCapture_InitPanes_00443AC8`
   (confident names) bracket 0x00444038, so `Ui_DiveCapture_HandleInput` keeps the class prefix; the
   same check made `Ui_WidgetStack_PushAt` safe (seven named callers in the record-detail window).
7. **Name collisions avoided**: the batch name `Ui_Widget_DeleteDtor` already belongs to the map-owning
   widget destructor at 0x00600CD0, so 0x00410C78 became `Ui_DescWidget_DeleteDtor` (its vtable
   0x0076DCF0 is the one `Ui_Widget_CreateFromDesc` installs); `maybe_Ui_SetNumberText` already exists at
   0x003D2A8C, hence the `Pane0`/`Pane1` suffixes. Both are `corrected`, not `confirmed`.

## Corrections where the first pass was wrong or misleading

- 0x005E2278 `maybe_Field_Gimmick_SpawnNamedEffect` → `maybe_Field_Gimmick_PlacePartsByIndex`: the body
  loops over the gimmick's parts comparing `part->f_1C` with the argument and calls the named
  `Field_ActorGroup_PlaceMember`; it places parts, it does not spawn an effect.
- 0x00211780 `maybe_Ui_LockInputInState` → `maybe_Ui_EnableViewInState2`: the single call is the
  `+0xC(1)` view-enable, not an input lock.
- 0x0037A968 `maybe_Ui_MemoriesWindow_Notify` → `maybe_Ui_EnableView`: byte-identical to the guarded
  `maybe_Ui_EnableViewIfSet` minus its guard; nothing touches a "memories" window.
- 0x004C7508 `maybe_Ui_Screen_IsTransitioning` → `maybe_Ui_Screen_AdvanceWhenTransitioning`: it always
  returns 1 and drives the animator, so an `Is*` name was wrong.
- 0x002F60DC / 0x002F6670 `CheckConfirm`/`CheckCancel` → `HandleConfirm`/`HandleCancel`: both always
  return 1 and act on the poll result.
- 0x005D5A24 `maybe_Script_SceneActiveObjectCheck` → `maybe_Script_GetSceneActiveObjectFlag`: a `void`
  stub that discards the `0x632F80` getter result (Ghidra trap rule).
- 0x005DD44C `maybe_Field_Gimmick_IsEventInputReady` → `maybe_Field_Gimmick_IsEventIgnored`: the returned
  polarity is "1 = not handled", the opposite of the old name.
- 0x005DFB14 `maybe_Field_Gimmick_UpdateTimerState` → `maybe_Field_Gimmick_Callback005DFB14`: the
  readable body is only `Ui_GetCore` + `halt_baddata`; the old name asserted a state machine that is not
  in the decompilation. Kept at 0.20.
- 0x002C6F74: the old header said the fallback rect is `[0]/[1]`; the body actually uses
  `puVar1[0x28]/[0x29]` (0xA0/0xA4) in the not-mode-1 branch. Summary corrected.
- 0x00153328 `maybe_Ui_FadeController_Update`: the readable file contains only the entry block for a
  0x85C-byte function, so the old "state machine" summary could not be verified; the summary now says so
  and the confidence stays 0.30.

## Kept `maybe_` on purpose (88)

Mostly three groups, and each entry says which applies:

- **No caller at all** (vtable slot) plus a generic body: the `Store*Pos*`/`Panel_Advance*` message
  helpers, the `ApplyDisplayModeRect_*` family, the `CloseScreenIfFlag*` family, the three
  `StopStateMachine{,B,C}` copies, the `Choice_*` trio. The body is documented exactly; the owner/subsystem
  is not provable from a single vtable slot.
- **Damaged decompilation**: 0x0023A4DC (`unaff_r6`), 0x003EE5C4 (five `unaff_*`), 0x005DC35C
  (`unaff_r5`, `in_r12`, unrecovered jump table), 0x004B3FF0 (garbled rect), 0x002D5B04, 0x00621FB4
  (`halt_baddata`), 0x005DFB14. These are capped at 0.20–0.35 per the project rule.
- **A name whose owner is still inferred**: `Battle_TextWindow_*` (the only caller is a *field* selection
  cursor, so `Battle_` is doubtful), `Gfx_Screen_CreateTarget*` (the only caller is UI sub-object setup),
  `GuideWindow_*`, `SakusenWindow_*`, `DualWindow_*`, `Field_Gimmick_ApplyPartTint` ("tint" vs
  "placement" is decided by a callee that is itself `maybe_`).

## Open problems / suggested follow-ups

1. **Wrong callee names that shaped several entries here** (outside the batch, only flagged):
   `Battle_TextWindow_UpdateVisibility{,Alt}` (0x00213E94/0x00214038) take `(manager, flag, pos, matrix)`
   and are used by a *field* label, so both the `Battle_` and the `Visibility` part are doubtful;
   0x004A3174 (`Field_ActorGroup_ApplyFormation`) is used as "apply a part descriptor" by
   `ApplyPartTint`; `maybe_Ui_ReleaseChildScreen` (0x002D23D0) and `0x002D2564` are two different
   "release the current screen" helpers that the `GuideWindow_*` wrappers use interchangeably.
   Suggested: one small batch to fix the 0x0021xxxx text-panel block, then re-refine the four entries
   that depend on it.
2. **`UiCore+0x94`** is cleared by every input-consuming handler in this batch. It is described as the
   "pending-input/mode word" but never proven; a `G_*`/`S_*` pass should name the UiCore fields
   (`+0x10` 2D manager, `+0x14` input/transition manager, `+0x94` mode word, `+0x98` current window).
3. **The `f_14->f_C` versus `f_14->f_1C` split** matters: slot `+0xC` of the `f_C` object is the
   transition-busy query, slot `+0xC` of the `f_1C` object is the view enable. Two different objects one
   field apart — worth a FACTS.md line before the next naming pass, because "virtual +0xC" alone is
   ambiguous.
4. **`maybe_Ui_SetNumberTextPane0/Pane1`** could be merged with the existing `maybe_Ui_SetNumberText`
   (0x003D2A8C) into one documented family (pane 0, pane 1, two-pane) when the UI text-field layout is
   known.
5. Not verified: everything here is static inference from the readable C, symbol table, literal pools and
   caller/callee graph. No emulator run, no bit-match build (not applicable to a naming-only batch).
