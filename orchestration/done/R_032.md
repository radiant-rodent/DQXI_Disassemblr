# R_032 — second naming pass (refine), 40 low-confidence `maybe_` functions

## What was done

All **40** addresses in `orchestration/naming/refine/batches/R_032.txt` were re-examined and written to
`orchestration/naming/refine/out/R_032.json` — one object per address, in batch order, **40/40 covered**.
Only that file, `AGENT_LOG.md` and this report were written; scratch is in `out/scratch/R_032/`.

**Result: 12 `confirmed` / 22 `corrected` / 6 `kept_maybe`; confidence range 0.30–0.55.**
`python tools/check_refine.py R_032` → `R_032: OK`.

Method per entry: start from the readable file's doc header (previous name/confidence/evidence), then
re-read the body with its **real** neighbours. Two local indexes made the context reliable:

1. A call-site scan over `asm/text/*.s` (`bl`/`blx`/`b` targets mapped back to their containing function
   from `decomp/ghidra/functions_merged.jsonl`). This found callers that the readable-text grep misses and
   — more importantly — **rejected false callers**: a function header that merely mentions a name (e.g.
   `maybe_Ui_Widget_UpdateCont1`'s header naming 0x00303480) otherwise looks like a call site.
2. A scan of `asm/rodata/*.s` for words pointing at each address, printed with their neighbouring slots.
   This identified the class vtables/family tables that give a slot its meaning (e.g. 0x726AB0 action
   handlers, 0x726B18 target-mode table, 0x762B78 horse/run action, 0x762924 field step action,
   0x758308/0x75832C battle manager, 0x72AA54 jackpot screen, 0x728508 jockey panel).

`functions_merged.jsonl` boundaries were checked whenever the function looked like a fragment.

## Hard evidence that changed verdicts

1. **The 0x726AB0 action-handler table names the battle queue family.** 0x0016EFB4 sits between
   `Battle_QueueAbilityAction` and `Battle_ExecuteItemAction`, so it is the normal-attack handler
   (`Battle_QueueAttackActions`, confirmed 0.55); 0x0016ED4C sits between
   `maybe_Battle_QueueAbilityActionVariant` and `Battle_QueueAbilityAction` and is the default-command
   handler — it maps the unit category (+0x31) to action ids 0xE/2/3/1 and *queues* them, so
   `ResolveActionType` understated it (`Battle_QueueCommandByCategory`, 0.55).
2. **0x762B78 is the horse/run action vtable** (`maybe_Field_Action_InitHorseParams`,
   `maybe_Field_Action_MoveStep`, `Field_Action_Horse_CheckCanContinue`). 0x00303480 and 0x003038CC are
   its turn-evaluation pair: `asm/text` shows `bl 0x3038CC` at 0x303714 with (out, self, dir, ctx). So the
   old `Anim_EvaluateAimPose` became `maybe_Field_Action_EvaluateTurnDirection`, and `HorseTurn` could be
   confirmed. The signature also gains the turn-scale float passed in s0 that Ghidra dropped.
3. **0x762924 is the field *step* action vtable**: `[ctor, 0x3017E0, 0x3019DC, Field_Action_PlayStepSound]`.
   0x3017E0 calls `maybe_Field_Actor_BeginStep`, 0x3019DC calls `maybe_Field_Actor_EndBehaviour`, and both
   release the step-SE handle f_74 → `Field_Action_StepBegin` / `StepEnd`, not `StopMove`/`StopStepSound`.
4. **0x7688B4 is slot 1 of the monster behaviour action** whose ctor 0x3AF5A4 installs 0x007688AC (the
   same class as the named `maybe_Monster_BehaviorAction_SyncEffectAndAnim` / `_UpdateBlend`). So
   0x3AEA9C is the generic action start, not a `FieldBehaviour_BeginAttack`.
5. **0x00617998 shares the text-style descriptor table** with the named `maybe_Ui_TextStyle_GetDescriptor`
   (0x1A5B60): same one-time flag 0x7BE30C, table 0x7BE310, allocation 0xA24 and ctor vtable 0x782990.
   It resolves a per-tag 8-byte record and appends it to a pointer vector; it does not format text.
6. **0x5988A8 is the battle member screen**, not field party: its only caller is
   `Battle_Ui_MemberScreen_UpdateB` and it also calls `maybe_Ui_BattleTargetMarker_CreateFromModelId`.
7. **0x62DE04 is camera code**: all three call sites are `Camera_UpdateWorkPath`/`UpdateWorkPathEx`,
   which refresh the path point only when the result is non-zero; the old "NPC step move" name was wrong.
8. **0x6347EC is a target-range predicate** (distance + facing angle between two battle units, distance
   returned through `*out`), used by `maybe_Battle_Action_SelectEffectTarget` — it never computes a
   transform.
9. **0x162A98 is an effect-part bind**, proven from the disassembly: r0 = partner, r1 = self,
   r2 = self->f_4 relative name, r3 = 12-float block, then `bl #0x5f56a0` = `Gfx_EffectPart_BindByName`.
   The readable C dropped three arguments, which is why the first pass thought it copied a pose.
10. **Two false entry points.** 0x00169076 and 0x0016907A are mid-routine fragments of the ARM function
    at 0x00168C64 (no prologue, r4/r6 live, the routine only returns at 0x1690EC). Their real work is
    battle command-slot dispatch (`Battle_InsertActionSlot` / `Battle_WriteActionSlot`); the old
    `Ui_Widget_UpdateCont*` names came from the false Thumb prologue. They are named
    `maybe_Battle_CommandSlots_UpdateContinuationA/B`.

## Kept `maybe_` on purpose (6)

- 0x0015EC8C — not a function: a tail block of `IsGimmickItemGetTimming`; the Ghidra C is unrelated float
  code, so the name is kept at 0.40 based on the disassembly only.
- 0x00163650 — damaged Thumb body (`unaff_r4/r5/r6`, misaligned asm); only the gain-lookup callee set is
  usable, so it is `maybe_Sound_LookupGainFromTable` at 0.30.
- 0x00166CA8, 0x00194220, 0x002BBA94, 0x006426D0, 0x001715C4 — family/vtable context improved but the
  owner or the meaning of one slot is still inferred; each entry says exactly which part is unproven.

## Open problems / suggested follow-ups

1. **`functions_merged.jsonl` has a wrong size for 0x00168C64** (`Field_Gimmick_CheckActiveNodes`): its
   1042-byte record ends mid-block at 0x169076, while the code continues to `pop {r4-r7}; bx lr` at
   0x1690EC. The two batch entries are the fragments. Suggested: correct the catalogue entry (or merge
   the three) in a decompiler/catalogue task — the R-batch pipeline cannot fix it.
2. **Two candidate names for the same code are both weak**: `Field_Gimmick_CheckActiveNodes` (0.75) is
   the function that physically contains 0x169076, but the contained code is battle command handling
   (battle work +0x5C, +0x4260 party list, `Battle_WriteActionSlot`). One of the two is misnamed; a
   dedicated pass on the 0x16xxxx battle command block should settle it. The fragments were named
   `Battle_...` because the callees are unambiguous.
3. **0x00163650's Thumb block is misaligned** in `asm/text/text_00140048.s` (0x163650 reads as
   `push {r1,r2,r4,r5,r7,lr}` followed by nonsense). A Thumb-realignment pass there would allow a real
   name.
4. **`Anim_BlendTransform`** renamed away from the non-existent `Motion_` prefix (no other `Motion_*`
   symbol in the binary). If `Motion_UpdateBlendTimer` / `AnimObject_UpdateAttachmentPoint` are later
   renamed, this one may want to follow.
5. Not verified: static only; no emulator or bit-match run. Readable C keeps the old names until
   `M1b_merge_refined` runs.
