Second naming pass for batch **R_033** (150 low-confidence `maybe_` functions, mostly UI destructors plus
ten behaviour functions at the end of the batch).

## What I produced

`orchestration/naming/refine/out/R_033.json` — one entry per batch address (150/150), 8 confirmed /
106 corrected / 36 kept_maybe. Signature/params are filled for each entry (`self` for destructors, the
readable header's argument list for the ten non-destructors).

Validation:

```
python tools/check_refine.py R_033
R_033: OK
```

(150 addresses present, `maybe_` prefix consistent with confidence, every `confirmed` name equals the
previous name minus `maybe_`, no predicate-on-void or damaged-body flags.)

## Method (recorded so the next refine worker can reuse it)

1. Scanned `asm/rodata/*.s` + `asm/data/*.s` for runs of consecutive code pointers and indexed
   `function -> (table start, slot)` over 2,998 tables (8,208 members). This is the missing piece: a
   destructor in this binary is `slot 0` or `slot 1` of its class table, and the other slots carry the
   class's *named* `InitPanes` / `Ctor` helpers.
2. Built `const -> functions` for every `0x006xxxxx/0x007xxxxx` literal in `decomp/readable/functions`
   (5,815 constants). Verified the ABI relation with the asm: a ctor writes `table_run_start - 4`
   (e.g. `Ui_FiveRowWindow_Ctor` writes `0x00772134` for run `0x00772138`, `Ui_DialogRoot_Ctor` writes
   `0x0075DC34` which is itself the run start). So "ctor writes T and dtor is slot k of T" is a reliable
   same-class link.
3. Used address adjacency as the second signal: this engine emits ctor, then D0 (deleting), then
   D1/D2 destructor bodies next to each other (e.g. `Ui_RowObject_Ctor` 0x0037C678 -> D0 0x0037C6B8 ->
   D1 0x0037C6DC).
4. Only then read the readable C / header and the neighbouring named functions.

Scratch: `out/scratch/R_033/` (`build_vt.py` vtable index, `index_consts.py`, `compact*.py`,
`mech.txt` mechanical dtor/ctor classification, `dec1..4.py` the decision tables, `build_json.py`).

## Notable outcomes

- **Destructors misread as constructors in pass 1** (body = table store + member teardown + `func_0010F6CC`):
  0x002A4838, 0x001EB180, 0x0028A3FC, 0x002A10B8, 0x0029A4D0, 0x002A504C, 0x002A5000, 0x00369060,
  0x0030E108, 0x002403B8, 0x00294820, 0x002BD834. Renamed to `_Dtor`/`_DeletingDtor`/`_DtorBody` with the
  reason in the evidence.
- **A shared base class resolved**: 0x0029485C / 0x00294820 / 0x00184E84 / 0x00184EC0 are the D2/D0 and two
  extra variants of the twelve-child `Ui_DialogRoot` (table 0x0075DC34, twelve 0x50-byte children at +0x4C,
  exactly what `Ui_DialogRoot_Ctor` 0x00184E38 builds). The old names ("Widget_DtorB", "Field_ObjectCleanup")
  were placeholders.
- **Swapped popup classes fixed**: 0x0046ADA4 is the damage popup (its table 0x00772B8C holds
  `Battle_Popup_InitDamagePopup`), 0x0046B1B0 the MP/HP-heal popup (table 0x00772BF0 holds
  `Battle_Popup_InitMpHealPopup`); pass 1 had "HealPopup" / "CritPopup".
- **Two real vtable classes recovered from the table**: 0x00211FD0 `Ui_CampSelectWindow_DeletingDtor`
  (0x0075B78C also holds `Ui_CampSelectWindow_Setup`), 0x0038BF2C `Ui_BattleEnemyListWindow_Dtor`
  (0x0076697C holds `Ui_BattleEnemyListWindow_InitPanes` - the "seven-slot sub-widget config" was its
  seven enemy rows).
- **36 kept_maybe**: mostly member-less 16-24 byte dtors whose table has no named member besides the shared
  widget slots (e.g. 0x004CEA98, 0x004CF860, 0x004DCF44), thunks, and the genuinely garbled 0x00417EE0.

## Honesty / limitations

- This is static analysis only. Nothing was run in the emulator; the readable C keeps the old names until
  `M1b_merge_refined` runs.
- Several names are class names inherited from a *named ctor* which is itself a `maybe_` name (e.g.
  `maybe_Ui_MovieWindow_InitBase`); those entries stay below 0.5 for that reason, as the template asks.
- The vtable-slot convention in this binary is not uniform: some tables put a `Script_Object_DestroyIfOwned`
  wrapper in slot 0 and the real destructor in slot 1, and a few entries are 4 bytes into the real function
  (`0x002403B8`, `0x0029D5BC`, `0x002B1A84` - noted in their evidence). Where the class could not be pinned I
  kept the old descriptive name rather than inventing one.
- 5 proposed names collided with existing symbols at other addresses; they were given `B` / `Body` /
  `Status` suffixes (`Ui_GoldWindow_DtorB`, `maybe_Ui_ShopWindow_DtorBody`,
  `maybe_Ui_EquipWindow_DtorB`, `maybe_Ui_MemberOrderWindow_DtorB`, `maybe_Ui_TalkWindow_DtorB`,
  `maybe_Ui_MessageStatusWindow_Dtor`). Checked: no duplicate name inside the file, no clash with
  `symbols.json` / other `refine/out/R_*.json` besides the same-address previous proposals.

## Suggested follow-up

2. A dedicated pass over the member-less destructors using the *callers'* ctor addresses (each

3. Type recovery for `Ui_DialogRoot` (twelve 0x50 children at +0x4C, three dtor variants) - it is the base
