# R_036 — second naming pass (refine), 150 low-confidence `maybe_` functions

## What was done

Processed all **150** addresses in `orchestration/naming/refine/batches/R_036.txt` and wrote
`orchestration/naming/refine/out/R_036.json`.

For every function:

1. read the readable C together with its doc header (previous name, confidence, proposing batch,
   previous evidence) — the header was the starting point, not the conclusion;
2. re-read the body against the now-named neighbourhood: grepped the candidate name / the callee
   addresses across `decomp/readable`, and opened the named callers and callees themselves
   (`Ui_SakusenWindow_*` handler family, `Container_NamedMap_Insert`, `Field_ObjectFactory_Type0003`,
   `Ui_ListWindow_UpdateScroll`, `Ui_Window_ResetState`, `Save_InitPartySnapshot`, `Gfx_Trail_AdvancePathNode`,
   `Ui_DiveStartWindow_Dtor`, …);
3. cross-checked `symbols.json` (names + descriptions), `decomp/native_names.json` and other
   `orchestration/naming/refine/out/R_*.json` entries for the same callees.

Decision mix: **45 confirmed / 50 corrected / 55 kept_maybe**. Confidence range 0.25–0.55; nothing was
pushed above 0.55, and every damaged body (`unaff_*`, `in_*`, lost call results) stayed at ≤ 0.45.

Rewriting was driven by three kinds of new evidence:

* **a named callee that fixes the object type** — e.g. `std_destroy_range` with element destructor
  `0x3E04BC` (the `Ui_AnimRefList` dtor) proved several "Init" functions were destructors;
  `Pack_ReleaseHandleEntry`/`Pack_ReleaseHandle` proved two "Init" functions were handle releases;
  `Fs_SplitResourceName`/`Fs_ClassifyResult`/`Fs_Object_ReadAll` proved two "message formatting"
  functions were file loaders;
* **named data symbols** — `g_battlePopup3DGaugeBarVtable`, `g_battleUiFlowInfoWindowVtable`,
  `g_battleCommandListRowStep`, `g_battleUiForceSlotRefresh`, `g_actorHandleRefVtable`, `s_null_btn`,
  `s_TurnR`/`s_TurnL`;
* **the caller's own confident name** — e.g. `Field_ObjectFactory_Type0003` calls `0x00438CE8` as its
  3D branch; `Ui_DiveStartWindow_Dtor` is the teardown body `0x002C2BA8` calls before freeing;
  `Ui_Window_ResetState` describes the 31-slot window `0x00623B48` builds.

## Honest keeps (55)

`kept_maybe` was used wherever only the *action* was provable and not the *object*:

* damaged bodies — `unaff_r*` / `in_*` / lost call results (`0x003BDAF8`, `0x00340C60`, `0x0038A4F8`,
  `0x003C4A20`, `0x003DAAB0`, `0x006E51E4`, `0x006E5C68`, `0x003AAB10`, `0x002DECC0`, `0x002A4D2C`);
* truncated control flow (`halt_baddata`) — `0x005F2F8C`, `0x006E51E4`, `0x006E5C68`;
* dtor/handle pairs whose mechanism is certain but whose owning class is a first-pass guess
  (`0x002BB758/77C`, `0x00419EC8/419F44`, `0x003D2DFC`, `0x002C2BA8`);
* functions whose only neighbour is a vtable slot (`0x002A2820/2A3060/2A2C94/2A309C/2A378C`,
  `0x004C7F6C` was the exception because the ctor prologue is explicit);
* identities inherited from another `maybe_` name (`0x00364BE8`, `0x0032A2C0`, `0x004A3B14`, `0x004AF5B0`,
  `0x00406D70`, `0x00364BE8`).

Two entries kept the same wording but a *better* summary rather than a new name
(`0x0031258C`, `0x00387CB8`), per the "correct vague beats precise wrong" rule.

  `0x002C2BA8` stays `maybe_Ui_DiveStartWindow_DeletingDtor` (the confident name lives at `0x00304F34`,

  `Ui_List_SetupRows` is `0x0023EDA0`).

  `maybe_` prefix"; the dtor role itself is solid (vtable + `std_destroy_range` + `Ui_Object_DtorBase`).
* Several entries are **sibling copies with identical bodies** and only differ by literal pools:
  `0x002DAC4C` ≡ `0x003CE0E4`, `0x003E9D38` ≡ `0x003E9DC0` (minus the returned base), `0x003BC520` ≡
  `0x003D2DFC`, `0x002A2820` ≡ `0x002A3060`, `0x002A309C` ≡ `0x002A378C`, `0x00419EC8` ≡ `0x00419F44`

  addresses should keep their A/B distinction.
