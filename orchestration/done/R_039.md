# R_039 — second naming pass (refine), 148 low-confidence `maybe_` functions

## What was done

All **148** addresses in `orchestration/naming/refine/batches/R_039.txt` were re-examined and written to
`orchestration/naming/refine/out/R_039.json` (one object per address, batch order, 148/148 covered).

**Result: 66 `confirmed` / 37 `corrected` / 45 `kept_maybe`; confidence 0.25–0.60 (average 0.46).**
`python tools/check_refine.py R_039` → `R_039: OK`.

Files changed: `orchestration/naming/refine/out/R_039.json`, `AGENT_LOG.md`, this report. Scratch (digest
builder, four JSON chunk writers, merge/validator, collision check) is in `out/scratch/R_039/`. No readable
C, symbols or tools were modified.

Method per entry: start from the doc header (previous name / confidence / evidence), then read the body
**for its call names**. The batch's context score counts confident callers/callees, but most new evidence
here came from (a) callees the merge had just named, (b) byte-identical twins at other addresses, (c) a
named callee contradicting the guessed subsystem. Where only the *meaning of a struct field* was guessed
(most of the sound/graphics register writers), the entry stayed `maybe_` with a more neutral name and
summary — a confident wrong name is worse than an honest `maybe_`.

The JSON was written in four chunks of ~50/22/50/46 entries (saved after each), then merged in batch
order and validated: every address present once, `previous_name`/`previous_confidence` identical to the
batch file, `change` semantics and `maybe_` prefix rules checked, no duplicate names inside the batch and
no collision with `symbols.json` / `symbols_recovered.json`.

## Open problems / suggested follow-up

- The four sound channel field writers (0x118BAC `SetChannelHalfword`, 0x118E58 `SetChannelMaskedFields`,
  0x118FD4 `SetChannelDescriptor`, 0x5164FC `ApplyMaskedWord`) are now named only by *what they copy*
  (halfword / masked fields / 13-halfword descriptor / one masked word), not by what the DSP field means.
  Naming the channel record fields (offsets 0x28 / 0x2E / 0x32 / 0x34-block / 0x14-block) would let a later
  pass replace these with the real DSP parameter names.
- 0x0066AD94 `maybe_Work_FindLastNamedRow` and 0x0066B19C `maybe_Work_CountNamedRows`: the readable body is
  only the tail call `func_00100B74(table+0x7B3C)`; the scanning loop exists only in the disassembly. They
  should be re-read from `asm/` before promotion.
- 0x00193098 `maybe_Party_ShiftSkillSlots`: the 0x44 stride and sentinels are clear but the shift count
  recovered as `0x78787879`; needs the disassembly. Also unproven that the records are skills/abilities.
- 0x00155E40 and 0x0018F48C both call 0x5F5B94, which is named `Field_Actor_PlayTalkMotionFromTable` yet is
  called here with id 3 as a teardown. Either that name or these roles are wrong — worth one focused task.
- 0x0019536C `maybe_Field_DispatchNpcEvent` is a vtable callback with several `f_35xx` flags decoded as raw
  bits; the event enum needs the NPC controller object named first.
