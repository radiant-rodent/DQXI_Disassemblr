# R_040 — second naming pass (refine), 145 low-confidence `maybe_` functions

## What was done

All **145** addresses in `orchestration/naming/refine/batches/R_040.txt` were re-examined and written to
`orchestration/naming/refine/out/R_040.json` (batch order, one object per address, **145/145 covered**,
no extras). No other repository file was modified except `AGENT_LOG.md` and this report. Scratch (a
direct-call graph, a vtable index, the per-entry viewer and the JSON builder) is in
`out/scratch/R_040/`.

**Result: 44 `confirmed` / 50 `corrected` / 51 `kept_maybe`; confidence range 0.30–0.55.**
`python tools/check_refine.py R_040` → `R_040: OK`.
Self-checks: every `previous_name`/`previous_confidence` equals its batch line, no duplicate names inside
the file, no name collision with `symbols_recovered.json` / `decomp/native_names.json` / any older batch
output, every name ≥ 0.50 free of the `maybe_` prefix and every `maybe_` name below 0.50, strict UTF-8
re-read after writing.

## Method (this is what made the second pass different)

The doc header only says what the *first* pass guessed. The new evidence came from three mechanical
sources, because the readable C of these low-confidence functions is mostly a dead end on its own:

1. **Direct-call graph over `asm/text/*.s`** (`out/scratch/R_040/graph.py`): parses every `bl`/`b` with
   its real instruction address and maps the call site to its owning function from
   `functions_merged.jsonl` (75,152 targets). This produced the "who calls it" column that the first pass
   mostly lacked, and it also *disproved* several claimed callers (see below).
2. **Vtable/`.word` neighbourhood index over `asm/rodata`** (`out/scratch/R_040/vtables.py`): for every
   data reference to a batch address it prints the surrounding table words resolved to function names,
   which is how most class identities were settled (`Ui_PokerCards_*`, `Field_SceneObject_*`,
   `Ui_SkillPanelWindow_*`, `Gfx_Sprite2D_CreateMeshA/B`, `Gfx_EffectParams_Create`, …).
3. **String literals straight from `build/code.bin`** (`out/scratch/R_040/str_at.py`): needed to read
   the pane-name templates in 0x002C2BC8 (`txt_l0`/`txt_r0`/`present`/`null_bottom`).

Each entry was decided as asked: `confirmed` only when named callers/callees **and** the vtable family
agree with the existing guess (all such entries sit at 0.50–0.55); otherwise `kept_maybe` with a sharper
summary, or `corrected` when the new context contradicted the old name.

## Open problems / suggested follow-ups

1. **The call-graph + vtable scripts are generally useful.** `out/scratch/R_040/{graph.py,vtables.py}`
   answer "who calls X" and "which class owns this vtable slot" for the whole binary in ~20 s. Promoting
   them to `tools/callgraph.py` (or `tools/reverse_index.py`) would make every later refine batch and the
   S_*/G_* type recovery much cheaper. I did not do it because `tools/` is outside this task's ownership.
2. **The 0x00759A00 vtable cluster is mixed.** `Item_Container_*` (0.6) and `Model_ApplyParam*` (0.4)
   sit in one table run (0x00759A20..0x00759A90). Either it is a per-record-kind dispatch table (then the
   `Model_*` names are fine) or the item names are wrong. Worth one dedicated task.
3. **`Ui_SubTable_*` (0x001E4B4C/0x001E4BC0) and the element ctor/dtor pair 0x00295640/0x00295660**
   need a type task: the same 3×0x10 array is used by a screen-view entry and by a script triplet table,
   and `0x00295640` is currently named `maybe_Ui_CompositeWindow_InitSingleton` (0.35), which cannot be
   right for an array element constructor.
4. **`0x0020E4FC` / `0x0020C08C`** are effect-parameter command builders whose type ids (8/0x6F/7/2 …)
   should be matched against the effect tables (`game_assets/` / `game_data/`) to name the effects.
5. **Flag 0x39 pair (0x001E7AE8 / 0x001E7B70)** — both unlock the same story flag from different paths;
   cross-checking Squirrel natives (`CheckSkillPanelOpenedQ590`, the text path) could pin the real
   condition and let both be named confidently.
6. Not verified: everything here is static analysis. No emulator run, no runtime confirmation that a
   renamed function is used the way the name says, and the readable C still carries the old names until
   `M1b_merge_refined` runs.
