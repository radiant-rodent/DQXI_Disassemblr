## Method (what actually produced the decisions)

1. Doc header first (previous name, confidence, evidence), then the **body re-read for its current callee
   names** — most first-pass evidence referred to raw addresses, which are now named.
2. For every address I checked where it is referenced in `asm/rodata/*.s`. In this engine the owning class
   is usually readable from the table run (named `Field_SceneObject_*`, `Ui_*_InitPanes`, `Gfx_Node_*`,
   `Battle_Ui_*` neighbours), and the slot **directly before** a `<Class>_InitPanes` entry is always that
   class's `SetVisible` virtual (it forwards to `Ui_Pane_SetVisibleWithAnim`). This decided the three
   "stub/thunk" names without guessing.
3. Identical bodies were treated as template copies ("same body as 0x…"), not as separate semantics; that
   is what unified the action-sequence, packet-post, dive/jumon and marker-wait families.

## Corrections worth merging carefully

- **Wrong subsystem, 4 functions**: 0x00628AF0 / 0x0064A0D0 / 0x00650DC0 / 0x006540E8 were
  `maybe_Ui_Element_IsIdle*`; they are slots of the *field scene-object* vtables (0x007588E8 next to
  `Field_SceneObject_Show/Hide/ClearPartFlag`, 0x0076B410 next to `Field_Actor_UpdateWeaponAttach`, 0x00775408
  next to `Field_ActorGroup_*`, 0x00778624 next to `Field_Object_*`) → `Field_SceneObject_IsPartsIdle(A..D)`.
  Cross-batch consequence: the shared callees `Ui_Span_IsIdle` (0x00641960) and `x6_` (0x006692A0) are also
  used by field actors, so their `Ui_` prefix and `x6_` name are probably wrong as well (not mine to change).
- **Wrong kind of function**:
  - 0x00630620 `maybe_Ui_ListWindow_CalcRowHeight` (declared `float`!) is a bool bitmask membership test:
    asm 0x00630658..84 is `cmp r0,#0xa5; lsr/and; ldr [r4,#0xe0]; ands; movne #1` → `maybe_Anim_Timeline_IsIdActive`.
  - 0x0024151C `maybe_Ui_List_GetLabel` is a constructor (base ctor + vtable 0x0075C87C).
  - 0x00240980 `maybe_Ui_List_CreateSubWidgets` is the constructor of the 0x1C8-byte block its only caller
    (`Ui_SpritePart_CreateFromDesc`) has just allocated → `maybe_Ui_Part_Ctor`.
  - 0x004E650C / 0x004E6A34 were named "Construct…" but are destructor bodies
    (`*self = vtable; self[0x96] = vtable+0xD4; Pack_Handle_Dtor(member); func_0028EFB4; func_0010F6CC`).
  - 0x0046855C / 0x004BF1FC / 0x00597E50 were "Assign/Release" helpers but are deleting destructors
    (`*self = vtable` is the dtor's own vtable store, the argument is a vtable, not an id).
  - 0x004ECDB0 `maybe_Ui_Object_ConstructBase` is a non-deleting base destructor (`g_battleActorBaseVtable`).
  - 0x00253688 `maybe_Event_UpdateCounter` is `Casino_Jackpot_UpdateCounter` (wrap path calls the named
    `Casino_RefreshJackpotCounters`, values wrap modulo 100 with a 300 limit).
- **Vtable-slot naming**: 0x002ABD30 → `Ui_TextListWindow_SetVisible`, 0x003F1A24 →
  `Ui_FourRowIconWindow_SetVisible`, 0x0041C034 → `Ui_EquipmentWindow_SetVisible`.
- **Unified template-copy families** (previously each copy had its own invented name):
  0x002A69A0 == 0x00308970; 0x00307624 = same without the list reset; 0x003174D0 == 0x00466680;
  0x002CFB04 == 0x003F0CEC; 0x004C7958 / 0x004C7C94.
- **Name collisions with existing symbols** (checked against `symbols.json`): `maybe_Ui_Object_DtorDelete`
  already exists at 0x004B4280 and `maybe_Ui_MessageWindow_DtorDelete` at 0x003B1220, so the new ones are

  nothing has been re-generated or re-checked against the rebuilt `code.bin`.
- Deliberately left below 0.5 because the decompilation is damaged or truncated: 0x005F48A8
  (`coprocessor_function`, `unaff_r5`), 0x002DD81C (halt_baddata after the first call), 0x0029E498 (body lost

  (`unaff_r6`).
- 0x00630620 (`maybe_Anim_Timeline_IsIdActive`): the id→record step is byte-identical to
  `Sound_RequestBgmById`, so I could not prove the table is the animation table; the bool/mask behaviour is
  proven, the table identity is not.
- The destructor family at 0x00467DB8 / 0x0047EB28 got `Container_HandleNode_Dtor(B)`; the owning class of
  those intrusive nodes is still unknown (only the two vtable constants 0x007721CC / 0x00774444 identify them).
- `func_0010F6CC` is described as operator delete throughout, but older headers in the repo call it a static
  destructor registration — one of the two is wrong project-wide.
