# R_043 — second naming pass (refine), 150 `maybe_` functions

Status: **complete**. Output `orchestration/naming/refine/out/R_043.json`, 150/150 addresses covered,
`python tools/check_refine.py R_043` → `R_043: OK`.

## What was done

This task was resumed with no prior `R_043.json` (nothing to inherit), so all 150 addresses were
examined from scratch in this session.

Result split: **97 confirmed / 15 corrected / 38 kept_maybe**.

Method (static only, no Ghidra, no emulator):

1. Read the doc header of each readable file (previous name, confidence, evidence) and the body.
2. Built a reverse-call index over all 18,151 `decomp/readable/functions/*.c` bodies: for each of the 150
   names, list every file whose *body* (after the header comment) contains the name. This gave real named
   callers for 115 of the 150; the rest are vtable/table-slot functions with no direct reference.
3. Re-read the disputed ones together with the now-named callers/callees (e.g. `Ui_MessageWindow_ShowRow`,
   `Ui_PopupEntry_SpawnFromTable`, `Battle_Monster_GetHpBarValue`, `Field_ObjectFactory_Kind15`,
   `Actor_Action_SkullRun_Update`, `FieldParty_Ctor`'s vtable symbol).
4. Cross-checked `symbols.json`/`symbols_recovered.json` for name collisions and for the vtable/class
   symbols (`g_battle2DUnitSubVtable`, `g_fieldPartyVtable`).
5. Wrote decisions with `out/scratch/R_043/build.py` (signatures taken from each file's `Signature:`
   header line, function name rewritten), then ran the checker.

## Why 38 stayed `maybe_`

- Damaged decompilation: 0x004ACD30 (`in_ZR`), 0x0071371C (`unaff_r4`), 0x00502CB4, 0x00530014
  (SBORROW), 0x0055C84E (Thumb/BADSPACEBASE), 0x0054392C (all arguments lost).
- Class label with no named caller and no vtable sibling to confirm it (status-panel dtors, overlay,
  screen-slide anim, battle action-model node state A/B, gimmick3107, effect-list dtors, movie surface ctor).
- Vtable-slot-only functions where the *mechanism* is certain but the *purpose* is an interpretation
  (0x00484EBC/0x004851D4, 0x004F0BD0, 0x0051B6B8, 0x00558EE8, 0x0054DF34, ...).

   - CECD command wrappers 0x50C328 (cmd 0x03, caller `..._WriteWithRetry`) and 0x50C55C (cmd 0x07, caller

2. `g_fieldPartyVtable` (0x769398) is installed into embedded sub-objects at +0xB464 by two large classes —
   likely a shared base vtable rather than "FieldParty"; the symbol deserves re-checking.
3. `func_001902CC(record, 0x8B, 0)` (used by 0x48C95C) and the four flag slots 0x5C..0x5F are still
   unidentified; naming them would settle whether 0x48C95C is really a status-immunity test.
4. The four `Ui_MessageWindow_OpenRow*` helpers are a table-driven family; a later batch could name the row
   table entries at `self->f_298` (stride 8) and 0x4441E8's mode values.
