## Method (because the batch had zero context)
1. Parsed the rodata region `0x0075FA00`–`0x0075FF90` (`asm/rodata/rodata_00745000.s`) into
   per-class method tables: runs of function words separated by three zero words, each run resolving
   through `symbols.json`. Every batch address except 0x002BF1C8/0x002BF5B4/0x002BFED4 turned out to
   be **inside** such a table; those three are table entry 0 (the destructor).
2. Followed the literal pools in `asm/text/text_00280048.s` to the constructors (e.g. 0x002BEDA8
   stores the descriptor `0x0075FB34`, whose table starts at 0x0075FB3C), which is what pins a class
   to a destructor.
3. Checked every named callee in `symbols.json` (0x18233C `maybe_Field_Actor_UpdateModel`,
   0x184CB4 Field_Object dtor body, 0x4D714C → 0x17C334 Ui_Object_DtorBody, 0x193E44 base dtor body,
   0x10F6CC operator delete, 0x29E488 → 0x29E498 shared graphics-context+0xF50 table lookup,
   0x1D8C2C Ui widget dtor body, 0x22CECC Actor_TrySelectIdleAnimation).

## Key findings (corrections that matter for readability)
- **Three of the twelve "functions" are not entries.**
  - `0x002BEF04` is the fall-through tail of `0x002BEEF8` (`ldrb r1,[r0,#0x48]; cmp; bxeq lr` then
    straight into the tail); `0x002BF1EC` is the tail of `0x002BF1D8` (`state != 0 && flag != 0`).
    The first pass had counted each routine twice (`ApplyFrameToModel` + `...B`).
  - `0x002BFA68` is literally the four-byte `b 0x22CECC Actor_TrySelectIdleAnimation` at the end of
    `maybe_Actor_Action_Move_Update` (0x002BF9F4), which branches *forward* to 0x002BFA6C - so the
    "620-byte CreateMoveSequence factory" (Anim_Sequence_CtorBase / Sound_PlaySeById / alloc) is the
    state==0/1 half of that same state machine, not a constructor.
  - `0x002BEDF4` is four bytes into the Field_ActorGimmick deleting destructor whose table slot is
    `0x002BEDF0` (`ldr r1,=0x0075FB34`).
- **"Frame index" at model `+0x128` is not supported.** The value comes from `0x0029E488`, which
  forces `index=-1, style=10, mode=2` into `0x0029E498` - the same shared
  graphics-context `+0xF50` table lookup that the *named* sprite factories
  (`Gfx_Sprite2D_InitFromDesc`, `Field_CreateActor`, `Gfx_CreateQuadSpriteEffect`) store into
  `node->f_b8->f_128`. The name therefore says "draw entry", not "frame", and keeps `maybe_`.
- **`0x002BF208`'s `+0x2C` is a state byte, not an animator pointer** (cleared to 0, then compared
  with 0..4 by `0x002BF298`/`0x002BF5C4`); the copied block is six dwords `actor+0x244..+0x258`
  plus the flag byte `actor+0x25C`.
- `0x002BFEE8` first calls the actor's virtual slot `+0x88` and then restores `+0x3AC..` into
  `+0x9C..`; its twin `0x002BFF64` does the copy without the call.
