# R_048 — refine pass on 150 low-confidence `maybe_` functions

## Scope
Batch `orchestration/naming/refine/batches/R_048.txt`: 150 addresses (context score 3 each — one
named caller or callee per function). They are mostly SDK/engine internals in `0x0010xxxx`-`0x003Axxxx`
(graphics, OS, sound, filesystem), the Squirrel binding shims in `0x0014Bxxx`-`0x00166xxx`, a text
layout block around `0x0018Cxxx`, a UI-window/layout block, the party/formation code around
`0x001Fxxxx`, and a large actor-action constructor/destructor family in `0x0022xxxx`-`0x004Cxxxx`.
Owned output: `orchestration/naming/refine/out/R_048.json` only.

## Result
`python tools/check_refine.py R_048` → **`R_048: OK`** (150/150 addresses, no missing/extra, no
flagged names).

59 confirmed / 46 corrected / 45 kept as `maybe_` (74 entries still below 0.5, all prefixed).

Both invariants were re-checked by hand: `previous_name`/`previous_confidence` match the batch file
exactly for all 150 entries, the JSON was re-read with a strict UTF-8 decode (no BOM), and no new
name collides with an existing `symbols.json` name or with another entry in this batch
(150 unique names).

## Method
1. Started from each file's doc header (previous name/confidence/evidence) and re-read the body.
2. Resolved every `func_XXXXXXXX` callee through `symbols.json`, and used the **now named callers**
   (from a single pass over `decomp/readable/**/*.c`) as the strongest new evidence — e.g.
   `Input_UpdatePadState` for 0x0010C47C, `Actor_CreateActionTable` for eleven action constructors,
   `MoLive_Reader_Process` for 0x00155380, `Ui_MemberTable_Init` for the party table.
3. For 20 tiny wrappers whose only fact is which string they test or which native they adapt, read
   the literal pool / raw bytes from `build/code.bin` (offset = address − 0x00100000) and the
   instructions from `asm/text/text_*.s`. That yielded the file-suffix literals (`.bch`, `.ptcl`,
   `.binst`, `.ani`, `.sndq`, `.epi`, `.arc`/`nw_testshader`, `.chp`), the `fs:USER` service name and
   the "HTP" type tag.
4. For two functions whose decompilation is known-bad, disassembled the real body by hand:
   0x0018D5A0 is a 0/1 **predicate** (not a noreturn throw) and 0x0018CEA4 is a 552-byte builder
   truncated by Ghidra to one call.

## Key findings (the corrections that change how the code reads)
- **File-type predicates, not string utilities.** `0x0019439C`, `0x001E6C20`, `0x004B3604`,
  `0x00576CC0`, `0x00315EC0`, `0x0046CF94` all had names like `Str_Contains`/`Ui_IsTextLayoutBusy`.
  Each is literally `strstr(path, "<suffix>") != 0`, with the suffix in the literal pool right
  behind the function. They are now `Fs_IsBchPath`, `Fs_IsPtclPath`, `Fs_IsBinstPath`, `Fs_IsAniPath`,
  `Fs_IsSndqPath`, `Fs_IsEpiPath`. This matters: the old names suggested six unrelated helpers where
  there is one resource-loader dispatch table.
- **The "Text_Throw*" trio was not throwing.** 0x0018D5A0 is `Text_SpanHasContent` (style < 7 and a
  non-empty span → 1). Its disassembly is `ldrh [r4]; ldrd [r5]; orrsne; movne r0,#1; pop`. The
  caller 0x0018C6B4 uses the result as a count, so that function is `Text_GetLayoutStats`, not a
  "measure cache". 0x0018CEA4/0x0018D24C are layout-span builders with 552-byte and 0x84-byte
  frames; the readable C shows one call because Ghidra lost the control flow.
- **One template, six touch-record copies.** 0x001A3E68, 0x001A40F8, 0x001D7098, 0x0021B6F0,
  0x00290760 and 0x003A1EB0 have byte-identical bodies apart from the "kind" passed to 0x0040DBB4
  (2/10/4/7/3/6) and the destination offset; they cache the 12-byte (type, kind, id, x, y) record at
  +0x4D8, and 0x00423794 turns that record into a 0x14-byte heap touch event. Old names
  ("QueryGroundInfo", "GetSpriteColorAndOffsets", "LoadSpriteFrame", …) described six different
  things; they are now `*_RefreshTouchInfo{,B}`.
- **Actor-action constructors.** Eleven batch functions are entries of `Actor_CreateActionTable`
  (0x0022AF9C) that start with the now confidently named `Actor_Action_InitDescriptor`; names like
  `Field_Actor_CtorSimple`, `Action_InstallVtable`, `Field_State_InitCarry` were describing a
  mechanism or an invented behaviour. They are now ctors of identified classes where the installed
  vtable is already symbolised (`Field_ActorMove_Ctor`, `maybe_FlwAction_Ctor`,
  `maybe_Field_ActionState_Ctor`) and stay `maybe_` where it is not.
- **`fs:USER`.** 0x00106AD0 passes the literal `"fs:USER"` (read from code.bin at 0x0072FC13) to
  0x0011CCA0, so it is the filesystem subsystem init → `Fs_Initialize`.
- **The five "ApiResultCheck/Ok" shims are named operations.** Each is a 16-24 byte adaptor around a
  confidently named Squirrel API function (`Script_Vm_NewSlot` 0.85, `Script_Vm_Clone` 0.85,
  `Script_Table_RemoveKey` 0.72, …). They are now `maybe_Script_NewSlot`, `…_GetInstance`,
  `…_TableRemoveKey`, `…_TableGetSlot`, `…_Clone`, `…_PushRootTable`, `…_ToStringNative`,
  `…_CheckOneParam` — still `maybe_` because the argument registers are lost.
- **`Pack_` → `MoLive_`.** 0x00155380 parses the 12-byte `L2` MoLive stream header; its only caller
  is the named `MoLive_Reader_Process`, not the PACK archive code.
- **Destructor family.** 0x0022AF8C is the Actor deleting destructor (its vtable 0x75C59C also lists
  `maybe_Actor_Dtor` and `Actor_CreateActionTable`); 0x004A4A90 is an actor-action deleting
  destructor, not a UI table one (its vtable slot 0 sits in the actor-action group).
- **`Actor_GetLinkedObject` → `Actor_ReleaseLinkedModelAttachments`.** The named callee
  `Model_AttachSlot_Release` shows the body releases the model's +0x40/+0x48 attach slots; it never
  returns the linked object.

## Not verified / open
- The readable C keeps the old names until `M1b_merge_refined`; this batch only wrote the proposal
  JSON. No build, emulator or progress run (rule 5's full run does not apply to refine batches).
- Several 0.50 "confirmed" names are class hypotheses whose *operation* is certain but whose owner is
  not (e.g. `Ui_MenuUpdate` vs. `Ui_JumonWindow_DispatchVirtual` share a frame-step body;
  `Ui_CreateTextWidget`/`Ui_CreatePaneWidget` are identified only by vtable neighbours).
- Names I relied on as evidence that may themselves be weak (for the reviewer, not mine to change):
  `Field_Object2D_BuildTouchEvent` (0x0040DBB4) — the body builds a tagged record that is later
  dispatched as a touch event, so the name is plausible but it is used here as "record builder";
  `Ui_CompositeWindow_DrawPanes` (0x295558) conflicts with the list-insert reading of 0x001E1D80;
  `Model_AttachSlot_Release` (0x0040ABEC) is 0.50.
- 0x00152EA8 still does not decode (`halt_baddata`); it keeps 0.10 and a neutral name.
- The party table at work+0x944C (8 × 0x60) is **not** the `func_0035EB98` member record (that one has
  the name at +0xCA and inventory at +0xEC), so `Party_GetMemberRecord`/`GetMemberCount` are about
  the slot table only; the count routine's decompiled loop tail is mangled.
- The formation/balloon block (0x001F9874, 0x001F9E20, 0x001FC7FC) has damaged decompilations
  (`in_s0`/`in_d8`/`in_d9`, `(fVar7 - fVar7)`), so those three stay `maybe_` at 0.40.

- Re-examine `Field_Object2D_BuildTouchEvent` (0x0040DBB4) as the shared touch/pointer record builder,
  and the six `RefreshTouchInfo` variants as one template family (same body, different kind).

  the *class* per vtable, not the constructor shape.
