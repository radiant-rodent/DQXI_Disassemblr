## Decisions worth flagging

- **Named-callee contradictions** (old name was wrong, not just vague):
  - `Script_NotifyVmGlobal` → `maybe_Save_BeginLoadRequest` (body has no VM accessor; it fetches the
    global-work singleton and calls `Save_BeginLoad`).
  - `Field_GetTimer` → `maybe_Field_CreateTimerObject` (the base-ctor result is *used*: vtable 0x007625D4 is
    stored into it — a constructor, not the dropped-return getter trap).
  - `ReleaseElementArray5` → `maybe_Ui_UpdateElementArray5` (caller `Ui_SlotWindow_ProcessPatterns`, callee
    an update routine).
  - `Ui_ForEachSlotDispose` → `maybe_Ui_ResetFourSlotPanes` (callee
    `maybe_Ui_SlotWindow_ResetPanes`; nothing freed).
  - `Ui_SpritePart_ReleaseResources` → `maybe_Ui_DeactivateAttachedWidget` (only hides / clears +0x94).
  - `Ui_Object_DrawHook` → `maybe_Ui_Object_ForwardToMoveSelection` (nothing is drawn).
  - `Ui_ListWindow_MoveSelection` (0x00454040) → `maybe_Ui_ListWindow_MoveSelectionThunk` (it *had the
    callee's name*).
  - `Ui_BattleWindow_HasPendingAnim` → `maybe_Ui_BattleWindow_IsAnimInactive` (not the inverse of
    `..._IsIdle`: both return 1 when f_14 == 0).
  - `Model_CheckTagAndStop` → `maybe_Model_HandleDeadTag` (the constant is ASCII `"dead"`, and the body is
    void, so `Check...` was a predicate name on a void function).
  - `Battle_Command_OpenTacticsWindow` → `maybe_Battle_Command_OpenItemPage` (only named callee is
    `Battle_ItemWindow_FillItemDetails`).
- **Field-action constructors** (`Anim_CreateVariantC..F`) renamed to the action they actually construct.
  The decisive evidence is the caller `Ui_FieldActionListWindow_InitPanes`, which builds the five-row list
  `nut`/`move`/`dash`/`jump`/`auto` and passes the row's name tag when it creates each object: row 1
  `0x65766F6D` = "move" -> `Field_CreateActionMoveStep`, row 2 `0x68736164` = "dash" ->
  `Field_CreateActionRun`, row 3 `0x706D756A` = "jump" -> `Field_CreateActionHorseStart`, row 4 "auto" ->
  `Field_CreateActionHorseInput` (auto mounted steering), row 0 "nut" -> `maybe_Field_CreateActionNut` (its
  vtable 0x0075FE38 has no symbol, so it stays `maybe_` at 0.48). Same treatment for the two
  `Field_SetupEnemyAi` children (`Anim_ClipSlot_SetEight/SetTwo` -> `Field_CreateEnemyAiArcAnim` /
  `...TwoSlotAnim`).
- **Curve-eval twins**: five byte-identical bodies (`Math_Curve_EvaluatePoint` + 0x005F3ADC) were named
  three different things; three were corrected to `..._ApplyCurvePosition`.
- **Deliberately left low**: the `Ui_MonsterRow_*` pair — both named callees are casino helpers
  (`Casino_Poker_DealAndEvaluate`/`_ReplaceCards`), so "monster row" is almost certainly wrong, but nothing
  identifies the real row class, so I only corrected the summary instead of inventing a name. All damaged
  bodies stayed below 0.5 (`unaff_r*`, `coprocessor_*`, `halt_baddata`, stack-only arguments).
- **First-pass "wins" I talked myself out of**: 0x00215320 looked like a textbook confirm — its caller is the
  confident `Map_AddInstance` — but that caller uses the returned record as the *container* for a new
  level-table instance (it writes the handle at +4), so the pool may be a generic instance allocator, not a
  UI window; it stays `maybe_Ui_FindFreeWindowSlot` (0.45). Three entries' only "confident" neighbour is the
  junk symbol `pI6`, which names nothing: 0x003646FC and 0x003A5380 went back to `maybe_`, while 0x00473980
  stayed at 0.50 because its body (stop the anim block, clear bit 0 of every child pane) is self-describing.
