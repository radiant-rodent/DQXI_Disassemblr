## Method (what actually produced the decisions)

1. Read the doc header of each readable file first (previous name, confidence, evidence), then the body
   **with its current callee names**, because most first-pass evidence quoted raw addresses.
2. Built an inverted call index over all 18,787 readable `.c` files in this working tree
   (`out/scratch/R_051/callers.json`, one pass, 5 s) so every batch entry could be read next to its
   *now-named callers*. That was the main new context: e.g. the nine `Gfx_Scene_*Intersect*` entries
   are called by `Gfx_Scene_TestSpriteHitA/B/C`, the fifteen `Fx_EmitParticles*` variants have no
   caller at all (dispatched indirectly), and the sound command handlers are all reached from
   `Sound_Command_ExecuteList`.
3. Used `symbols_recovered.json` to resolve every callee and to check for name collisions before
   confirming anything.
4. Where a body was a 4-byte stub or Ghidra had seeded mid-function, read the raw disassembly
   (`asm/text/text_00540048.s`) and the literal pools — this is how the six "text rect" wrappers were
   decoded.

## Corrections worth merging carefully

- **Six wrong-subsystem names, one family**: `maybe_Text_SubmitRect{10,18,20,28,30,40}` at
  0x00554C1C/38/90/AC/E58/FA4 are **not** rectangle adapters. Their true entries are 4 bytes earlier
  (0x554C18/34/8C/A8/E54/FA0), each starts with `ldr r2,[pc,#0xc]` = **0x0073D2E8**, and that is the
  16-entry channel method table already documented in the `maybe_Sound_SeqChannel_SetPauseMode`
  header (slot 0 = 0x54EBA4, slot 1 = 0x54E084, ...). Each wrapper loads the `{fn,adjust}` pair of one
  slot and calls the generic masked broadcast 0x6EF7D8 over the player's channel array at +0x90:
  - 0x554C1C slot 4 → `vstr s0,[r0,#0x10]` → `maybe_Sound_SeqPlayer_SetChannelFloat10`
  - 0x554D38 slot 3 → `+0xC`  → `maybe_Sound_SeqPlayer_SetChannelFloat0C`
  - 0x554D90 slot 2 → `+0x8`  → `maybe_Sound_SeqPlayer_SetChannelFloat08`
  - 0x554DAC slot 6 → `+0x104`→ `maybe_Sound_SeqPlayer_SetChannelFloat104`
  - 0x554E58 slot 8 → `+0x18` → `maybe_Sound_SeqPlayer_SetChannelFloat18`
  - 0x554FA4 slot 5 → `+0x14` → `maybe_Sound_SeqPlayer_SetChannelFloat14`
  The offsets are proven by the one-instruction setter bodies; the names follow the existing
  `SetChannelFloat108` / `SetChannelField83` / `FieldF4` / `FieldF0` convention (slots 7/9/10/11,
  also verified: `vstr s0,[r0,#0x108]; strb r1,[r0,#0xFE]` etc.).
  The six wrappers are **unreferenced anywhere in `asm/`** (no `bl`, no table word), so they are dead
  duplicates of the live command handlers — worth knowing before anyone "fixes" a call site.
- 0x005551B8 `maybe_Text_SetStyleIndex` → `maybe_Sound_SeqPlayer_SetAllChannelNotesFlag`: it stores a
  byte at player+0xE and applies it to every note of all 16 channels through 0x54E2B0, which walks the
  +0x130 list whose nodes carry +0x138/+0x139 — the same list the confident `Sound_SeqChannel_Stop`
  walks as its notes.
- 0x00579AA4 `maybe_Gfx_Light_Init` → `maybe_Script_EventVm_Init`: only caller is
  `Script_LoadEventScript` (`&self->f_70`), and the callee is the confident `Script_Vm_Create`
  (0x6BC454: 0xB8-byte Squirrel VM + tables + call frame). The old name came from reading the
  0x6BCxxx helpers as an "SDK light service"; they are Squirrel VM internals.
- 0x0058C2B8 `maybe_Gfx_SpriteParts_Add40` → `maybe_Gfx_SpriteParts_AppendRecord`: the append advances
  the cursor by 0x28 bytes (ten words), not 0x40. The "40" came from the `std_Vector40_Reserve`
  helper, not from the record size.

## Rejected confirmation (name collision with a real function)

0x0059F45C / 0x0059F494 look exactly like a deleting/non-deleting destructor pair and I had first
marked them `Battle2DUnit_DtorDeleting` / `Battle2DUnit_Dtor`. The collision check found that
`Battle2DUnit_Dtor` already exists at **0x005A1994** (vtable 0x77EAC0). These two restore vtable
0x774568, whose entries are `FieldParty_InitFromParams`, `FieldParty_ResetMemberSlot`,
`Battle_PartyMember_Update`, `Battle_Ui_Update` — i.e. they destroy an *embedded party-display
sub-object at +0x17E8 inside a container class that is not Battle2DUnit*. Both were put back to
`kept_maybe` at 0.45. This is the one place where the merge must not take my first reading.

## Open problems / honest uncertainties

- The 0x00552xxx-0x00556xxx band still carries text/font names (`Font_GlyphList_SetVisible`,
  `Ui_Text_DrawGlyphRun`, `maybe_Text_WindowQueue_Advance`) although the array at player+0x90 and the
  note list at +0x130 make it the sound sequencer. Those names are outside this batch; the merge of
  R_051 should not be read as endorsing them.
- 0x006EF7D8 `Event_BroadcastSlotMask` is really a generic "call this method on the objects selected
  by a 16-bit mask" dispatcher (its `self+0x90` array), not an event broadcast. Its name pushed the
  first pass towards "event/text" readings; a rename would help the next batch.
- Ghidra seeds in this band are systematically 4 bytes late when a function starts with a constant
  load (0x554C1C vs real 0x554C18, 0x554D38 vs 0x554D34, 0x554DC0 vs 0x554DBC, ...). I did not
  regenerate anything; the addresses in the batch are kept as given and the real entry is documented
  in each evidence string. A future re-seed would remove the duplicate "interior" entries.
- The 15 `Fx_EmitParticles*` variants are unreachable by direct call and have no address in any
  rodata/data table I could find; their distribution names (Ring/Box/Sphere/A...D) remain body-math
  inferences, hence 0.35-0.45 and `maybe_`.
- Not verified: static analysis only. No build, no emulator, no progress run. The readable C keeps the
  old names until `M1b_merge_refined`.
