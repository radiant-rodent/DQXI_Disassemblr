## What actually unlocked this batch

Every row had context score 0 (the batch generator found no *named* caller/callee), so the wins came
from two data structures, not from callers:

1. **A window step table at `0x0072C0E4..0x0072C21C`** — 8-byte `{fn, 0}` entries. It holds almost
   the whole 0x002FD–0x002FE band *and* the already-confident `Ui_Window_StartAction26`
   (0x002FE5BC), `Ui_ListData_BindEntries` (0x002FEBB0) and `Text_LayoutPage_BuildLines`
   (0x002FD45C). Roughly half the entries point at *function start − 4* (an inner entry of the same
   handler), which is what made the band look like unrelated fragments. A second table of the same
   shape at `0x0072C248..0x0072C38C` covers the sibling class at 0x00307xxx/0x00309xxx.
2. **`maybe_Ui_BaseWindow_UpdateStep` (0x002FCEAC)**: the core object at `self+0x3574` keeps a
   19-entry (index < 0x13), 0x18-byte-stride table of **ARM pointer-to-member functions**
   (`callee = obj + (adj>>1)`, and `if (adj & 1)` do a virtual dispatch through `[obj]`), invoked
   with the object at `core+0x20` as `this`. That proves the constants 0x12 / 0x10 / 0x0F / 0x0C /
   0x0B / 6 used by the handlers are the core's **step ids**, i.e. the first pass's "state" reading
   was structurally right even though the meaning of each id is still unknown.

0.40–0.45 only where the new evidence removed a specific doubt.

## Problems / caveats (honest)

- **0x002FB710 and 0x002FB790 are exported as `thumb` but the bytes are ARM code.** That is why their
  C is `halt_baddata`, and also why the addresses decode as `bl` instructions inside a longer routine
  rather than function starts: Ghidra split one ARM routine at wrong boundaries. Their names/evidence
  are inherited from N_106 and I did **not** re-derive the horse-action constructor identities; treat
  both as "part of the Field action-list fill routine" only.
- **Same corruption class elsewhere in this band**: `func_0062F680`/`func_0062F694` (widget button
  queries) and `0x00123564`/`0x00123594` (intrusive-list splice) are inner entries of Ghidra
  functions whose names are junk (`maybe_Field2D_ApplyActorVisualState`, `maybe_Snd_DetachChannel`).
  I did not rename them (not my batch) — see follow-ups.
- The `{fn,0}` step tables have no xref anywhere in the image (the address 0x0072C0E4 is never
  loaded): the sequence engine must reach them through a computed base or a class-descriptor table I
  did not find. So "step table" is inferred from shape (entry count vs the bound 0x13, the shared
  `vtbl+0x54`/`vtbl+0x14` idiom), not from a caller.
- Not verified: static analysis only. No `tools/build`, no `tests/run_all.py`, no emulator run —
  per the task rules the full test run does not apply to refine batches. The readable C still shows
  the old names until `M1b_merge_refined` consumes this JSON, so nothing in `decomp/` changed.
