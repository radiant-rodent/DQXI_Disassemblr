## How the work was done

The batch has almost no confident callers or callees, so three sources decided nearly every entry:

1. **The readable C next to the now-named callees.** Many bodies now call confident names
   (`Battle_Ui_BuildMemberRow`, `Sound_PlaySeById`, `Sound_GetPlayer`, `Ui_Object_DtorBody`,
   `Game_GetDataManager`, `Ui_Widget_Update`, `Gfx_ResourceList_Attach`, …), which is new compared
   with the first pass.
2. **Vtable / table membership read from `asm/rodata`.** A scratch helper (`out/scratch/R_056/vt.py`,
   `vtfind.py`, `vtsum.py`) found every rodata word that points at a batch address, printed the
   surrounding slot run, and named each neighbour through `decomp/ghidra/functions_merged.jsonl`.
   This is the cheapest reliable *class* evidence in this binary and it produced most corrections.
3. **The real disassembly** (`asm/text/...`) where the readable C was damaged or missing.

A second helper (`out/scratch/R_056/scan_refs.py`) scanned all 93,807 `.c` files under `decomp/` for
address references, which showed which functions are genuinely caller-less (most of the batch: they are
reached from vtables or are fallen into).

## Kept as `maybe_` on purpose

- **Damaged bodies** (`unaff_r*`, `coprocessor_*`, `halt_baddata`, bogus calls such as
  `func_0x00f51e9e`): 0x003C3704, 0x003C36E8, 0x003C48FC, 0x003C4ADC, 0x003C4BBC, 0x003D9DF0,
  0x003D8184, 0x003D8380, 0x003E24A6, 0x003E28B2, 0x003F6262, 0x004DB5AC — all kept ≤ 0.3.
- **Class label rests only on an unconfirmed family**: the `Field_Marker_*` constructors, the whole
  0x003CE0xx "ActionAnimObject" block, the 0x003E56xx..0x003E58xx action family, the
  `Battle_CommandWindow` / `Dungeon*Window` / `SmithMenu` UI labels.
- **Split fragments**: 0x003F4BE0 (2376 bytes) and 0x003F6262 (474 bytes) are Ghidra splits of one
  larger thumb function, fallen into rather than called; the batch listed them at 0.85/0.80 which was
  too high for a fragment, so they stay `maybe_` at 0.40.

## Notable single data points

- 0x003D7BC8 has **no readable C**: the batch path pointed at `decomp/ghidra/functions_index.json`.
  It was read from `asm/text/text_003C0048.s` and uses exactly the field set of 0x003D8184
  (+0x3770 bit 2, +0x134 list, +0x3778, +0x37D4→+0x10/+0x49, tail branch to 0x003D6C18), so it is
  `maybe_Ui_DiveForm_UpdateSelectionVisualB`, not a "command list update".
- 0x0029126C (used by four batch entries) is a two-argument element flag setter: it stores the byte at
  element+0x14 and mirrors bit 0 into the element user's +0x44. That explains the `on == 0` inversion in
  0x003D7DDC, but **which polarity means visible is still unknown** — hence `HidePane`/`ClearPaneFlag`
  stay `maybe_`.
- 0x0010F6CC (the tail of every deleting destructor) is operator delete: it loads vtable slot 1 from
  the object header at `r0-8`. It is still unnamed in the merged table.
- 0x00111394 and 0x00630D64 are **interior labels** of other functions (`0x00111378`, …), not entry
  points, so callees that call them can never be named from `functions_merged.jsonl`.
