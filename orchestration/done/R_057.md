# R_057 - refine pass (150 low-confidence `maybe_` functions)

Owner file: `orchestration/naming/refine/out/R_057.json` (150 entries, one per batch address).
Scope: the statically linked Nintendo SDK band at the bottom of `.text`, `0x00100080`-`0x0013B7C8`
(C++ runtime + newlib, the OS/session/IPC stubs, the driver channel/command block, the HID
helpers, the timer/perf helpers and the MPEG-style video converters). Game code starts around
`0x00146CA0` (`CameraZoom` in `decomp/native_names.json`), so **none of these 150 functions is game
logic** - the useful question for a modder is "which library call is this", not "which game feature".

## What decided this batch

Every row had context score 0 or 1 and `neighbour_names` was empty for all 150 - the generator found
no named neighbours because the whole band is library code with almost no game-side callers. So the
pass was driven by three kinds of *intrinsic* evidence plus the named callers I could still find:

1. **A caller index over the whole readable tree.** For each batch address I searched every readable
   file for the old name or `func_XXXXXXXX` and recorded who references it
   (`out/scratch/R_057/refs.json`). That turned up real context for 92 of the 150, e.g. 0x1144C0 is
   called by the now-confident `Svc_WaitReadyAndSendRequest`, 0x117E3C by the eight movie-track
   functions, 0x106A70's callee `Os_WaitRuntimeReady` is confident, and 0x116DAC's callee is the
   confident `Game_GetDataManager`.
2. **IPC command headers.** TLS+0x80 holds `cmd<<16 | normalCount<<6 | translateCount`, so every
   stub's command id is a *checkable fact* even when nothing calls it. That replaced the invented
   ordinals (`SendIpc1/2/3/4`, `SendRequest190000`) with the real command id (0x06, 0x08, 0x0B, 0x15,
   0x16, 0x17, 0x18, 0x19, 0x20, 0x3B, 0x3C) and exposed two wrong parameter counts in the old
   evidence (0x08630000 has *no* parameters; 0x001000C0 has *three normal* parameters, not a packed
   size).
3. **Literal constants in the body.** `0x8000` in 0x118C38 is the DSP's 32 kHz ceiling; the
   `0x1F00xxxx`/`0x1F2FFFFF`/`0x1F5FFFFF` literals in 0x1109A0/0x1109DC are VRAM region bounds, not
   screen sizes; the `0x180000` delta in 0x109F6C matches the base/limit shift in those two; the
   `0x20C49BA5E353F7CF` magic in 0x1237A0 is the inverse of 1000.

## The corrections that matter

- **0x00117E3C `maybe_Os_Abort` -> `Snd_LockSystemMonitor` (0.50).** `0x005177DC` is *not* a panic
  routine: the asm is `ldr r0,[pc,#0x90]` falling into the sound-system accessor `0x005177E0`, which
  asserts initialisation and returns the object at `0x007F09C8`. So 0x117E3C is "get that object,
  add 0x34, fall into the monitor lock at 0x117E50"; the exact mirror `0x0051864C` adds the same
  0x34 and branches to the unlock `0x00117ED0`. The eight movie-track callers use the pair as the
  *else* branch of the movie manager's own lock - a plausible, useful reading, and definitely not
  "abort".
  **This also invalidates three N_034 names**: `maybe_Sound_StartThread` (0x0051864C) and
  `maybe_Sound_StartMixerThread` (0x00517A38 / 0x00517A60) are accessor/unlock thunks, not thread
  starts. They are outside this batch - see follow-ups.
- **0x001109A0 / 0x001109DC `GetLcdWidth` / `GetLcdHeight` -> `maybe_Gfx_GetVramRegionEnd` /
  `maybe_Gfx_GetVramRegionBase` (0.45).** A width cannot be `0x1F2FFFFF`. The four literals are
  `0x1F000000`, `0x1F180000`, `0x1F300000`, `0x1F380000` (bases) and `0x1F2FFFFF`, `0x1F5FFFFF`
  (inclusive ends, = base + 0x2FFFFF), and the only caller (0x1094C0) compares a requested size
  against the pair, i.e. it is a range query. Both *seeds* are mid-function (0x1109A0's first branch
  tests flags set before it; the real entries are 0x11099C and 0x1109D8, which is exactly what
  0x1094C0 calls).
- **0x0011ECC0 `maybe_Gfx_ProcessInterruptRelay` -> `maybe_Snd_FlushChannelsOnStop` (0.45).** The body
  is the same flush sequence as `Snd_FlushChannels` (0x118788): same context `0x007AEA00`, same
  0x11E9C4 submit, same eight-hook table at `0x007E7998`, same closing command 0x20. Its only caller
  is 0x119AF4 in the *disable* branch, which is what makes it the stop-time variant. There is no
  interrupt relay in it.
- **0x00108C00 `maybe_Fs_CacheEntry_Init` -> `maybe_Gfx_InitE8Record` (0.45).** The layout is
  provable: ten words cleared, then two 0x60-byte memsets at +0x28 and +0x88, which ends exactly at
  0xE8 - the stride the pair constructor 0x1051F4 uses. 0x1051F4 itself
  (`maybe_Gfx_GetCmdBufOffsets`) is *not* a getter: 0x108C00 returns its argument, so the
  `+0xE8/-0xEC` arithmetic cancels and it is a two-record constructor (`maybe_Gfx_InitRecordPair`).
- **0x001051F4 / 0x0010C642 / 0x00112A60 / 0x0011709C / 0x0011CF9C / 0x0011DED4 / 0x00123FAE /
  0x00114B12** were corrected for the same class of mistake: the old name claimed an operation the
  body does not perform (getter for a constructor; queue for a field write; dispatch for a single
  discarded call; "object ready" for a non-null assert plus an unrelated global read; "textures" for
  one of four sub-initialisers with a literal 0; "service init" for a parameterless command; a
  "range B" entry for interior code; a "Thumb routine" for a byte-swap fragment).
- **Module prefixes the code contradicts**: 0x1123B0 (`Gfx_SetUnitFlagBit` -> `Snd_`, the stub it
  drives is the driver's unit-flag command), 0x112800 (`Gfx_ReleaseChannelObjects` -> `Snd_`, 24-entry
  driver channel array), 0x10C90C (`Gfx_BeginFrame` -> `Snd_`, same `0x007AEA98`/`0x007EF414` objects as
  the Snd stream code), 0x116DAC (`Pack_` -> `Game_`, callee is `Game_GetDataManager`).
- **0x00112A60 -> `maybe_Snd_FlushChannelBlock`** and **0x00119B4C / 0x0011938C / 0x0010CB30 /
  0x0010CB74** keep their Gfx_ prefix: the `0x007AE954` object they touch is shared with
  `Snd_UpdateState`, so there is no evidence to re-attribute them.
- **Two old evidence statements were simply wrong and are now fixed in the JSON**: `0x08630000`
  carries no parameters (the "three normal + three handle" decoding belonged to a different header),
  and `0x001000C0` carries three normal parameters with the buffer size in the *descriptor word at
  TLS+0x180*, not in the header. `maybe_Snd_ResetChannelUnits*` no longer calls +0x2A an "ADPCM"
  field: both pushes go to `SetChannelFilterInfo` / `SetChannelFilterCoefficients`.

## Kept `maybe_` (87) - and why

1. **Damaged decompilation** (kept at 0.25-0.45): 0x12677C (`unaff_r11`/`in_CY`), 0x119E8C
   (`unaff_r9`), 0x1094C0 (`in_r3`, lost jump table), 0x109F6C (`in_ZR`), 0x10C642 (`unaff_r6`/
   `in_s0`), 0x113924 (`in_ZR`/`unaff_r4`), 0x114B12 + 0x1149AA + 0x117458 + 0x11AC6E + 0x123FAE
   (mid-function seeds), 0x11B212 (`unaff_r9`/`unaff_r10`), 0x11B534 (VFP `in_s0`/`in_s1`), 0x125098
   (`halt_baddata`), 0x118D00 + 0x118F5C (dropped argument register).
2. **The body is clear but the *owner* is not.** The whole band is one static library; the first pass
   split it into `Os_/Gfx_/Snd_/Hid_/Video_/Fs_` by guesswork. I kept those prefixes where nothing
   contradicts them (0x10CB30, 0x10CB74, 0x119B4C, 0x11938C, 0x1165B4, 0x12033C, 0x118648, 0x11A7D0)
   rather than invent a better guess.
3. **Field meanings inside the driver channel block.** The nine setters 0x118B58, 0x118CA0, 0x118D00,
   0x118DCC, 0x118F5C, 0x119140, 0x1191A0, 0x122E78...0x1230E8 keep their field names as *hypotheses*:
   the offset and the dirty bit are certain, the label ("format", "pan", "volume", "loop") comes from
   the order in which 0x112CAC replays a saved state, and that is not proof. Two names were reduced to
   the offset instead of a guess (`maybe_Snd_SetChannelWord34`, `maybe_Snd_SetChannelWord3A`), and one
   was made vaguer on purpose (`maybe_Snd_SetChannelField1A`).
4. **The nine-member video conversion family** 0x126B0C...0x12A884: only the dispatcher pairing is
   proven (0x12A81C selects 0x12762C vs 0x1290A0 and always runs 0x1281E0; 0x12A84C selects
   0x126B0C vs 0x129EF4 and always runs 0x126EF4), not the block sizes the names claim. I kept the
   names but wrote the real lane offsets/strides into each summary (one old summary had copy A's
   0x1800..0x1c00 lanes on copy B, which is wrong).
5. **Placeholder names kept on purpose** where renaming would only be a different guess:
   `maybe_Os_ClearWaitFlag` (0.30 - calls a two-instruction helper and returns its argument),
   `maybe_Os_GetThreadClass` (0.32), `maybe_Os_EnsureInitialized` (0.35, no readable body at all:
   status `covered_by`), `maybe_std_Abort` (0.35), `maybe_Os_ThreadExit` (0.45).

## Open problems / follow-ups

- **Misnamed confident symbols in the 0x00517xxx-0x00519xxx sound block (found while verifying
  0x117E3C).** `0x005177DC` is the sound-system accessor, not a thread body, so
  `maybe_Sound_StartThread` (0x0051864C) is really the *unlock* of the system monitor,
  `maybe_Sound_StartMixerThread` (0x00517A38) and `0x00517A60` are further accessor thunks, and
  `maybe_Sound_GetSystemIfInitialized` (0x005177E0) is the *fall-through body* of the accessor, not a
  separate entry. A short "misnamed 0x517xxx/0x518xxx" task would fix ~6 symbols and would make the
  movie-track call sites read correctly.
- **The `nn_` question.** This whole batch is one static SDK library that the first pass split into
  `Os_/Gfx_/Snd_/Hid_/Video_/Fs_`/`std_` by neighbourhood. Some of those splits are certainly wrong
  (the 0x118xxx channel block is reached from both "Snd" and "Gfx" callers because it is one driver).
  A policy decision - re-prefix the band to `nn_`/`std_`, or keep the current taxonomy - should be
  taken *once* by a task that owns the whole 0x100000-0x146000 range; doing it batch by batch would
  churn the merged names.
- **The nine video converters (0x126B0C...0x12A884)** need one focused pass with the three dispatchers
  and the twin copies (0x12AC6C, 0x12B3A4, 0x12BF58, 0x12CE18, 0x12DC6C, 0x12E5C4/0x12E5FC,
  0x13230C/0x13233C) side by side; the block sizes in the names (`Blocks16`, `Blocks32`, `Planes3/4`)
  are still unverified labels.
- **Unnamed callees that would unlock more of this band**: `0x0010009C` (the "not initialised" assert
  used by 0x106F04, 0x1109DC, 0x1142A0 and 0x11B7EC), `0x0010B258`, `0x0010CC10`/`0x0010CC20` (the two
  driver state words), `0x00113A00`/`0x00113A40` (the frame state machine), `0x0011E9B4` (the "driver
  ready" gate every channel setter uses) and `0x0011F20C` (the runtime predicate).
- **`0x0011B7EC` has no readable C** (`status: covered_by` in `functions_index.json`): Ghidra merged it
  into its neighbour, so it can only be described from the index. If the readable-C generator ever
  splits covered_by entries, this one needs a re-run.

## Not verified

- No claim here was checked in the emulator; the batch is naming only and no re-merge (`M1b`) was run,
  so `decomp/readable` still shows the previous names until the merged state is regenerated.
- The `Snd_`/`Gfx_`/`Os_` ownership of most entries is a family label, not proof: the binary carries no
  RTTI and the services are reached through plain IPC handles.
- The field names inside the driver channel block (format/pan/volume/rate/output/loop/ADPCM) are
  inferred from the replay order in 0x112CAC, not from a header or from the DSP's own documentation.
