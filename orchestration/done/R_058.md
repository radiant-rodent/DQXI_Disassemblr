## What the batch actually is

| Range | Count | What it is |
|---|---:|---|
| 0x0012AC6C–0x0013233C | 15 | **B and C copies** of the movie codec's block-converter class (the A copy is R_057's) |
| 0x001336E4–0x00138C7C | 49 | **A copy** of the prediction / IDCT / filter block (48 routines + the 0x001336E4 data table) |
| 0x00139E90–0x0013F27C | 48 | **B copy** of the same block (the C copy is R_059's) |

Because 97 of the 112 are two copies of one code block (the prediction/IDCT block is emitted three
times in the ROM; its copies are +0x6600 apart), the batch is mostly "the same routine, twice". I
byte-compared **all 112** against their twin in
`original/exefs/code.decompressed.bin` and put the result in each summary, e.g.
`Byte-compared with the twin at 0x00133FB4 (Video_McPredict4ReadMv): 7 of 320 bytes differ, but the
decompiled body is identical…` — so the merge step can fold the copies mechanically without
re-deriving anything.

## The evidence that made the confirmations possible

N_037's own follow-up #1 ("open the .moflex files and confirm the Mobiclip reading") is now done,
by name rather than by decoding a frame:

1. The converter class has **exactly one caller outside the module**:
   `Gfx_Movie_ConvertSliceRowsTo16bpp` (0x006B8C38, called from `Gfx_Movie_AllocStreamObjectA`,
   both already named) calls the C-copy member **0x00132D80** with a `{src,dst}` slice record,
   advances the source by 0x28 bytes and the destination by one 0x200-byte row, and its summary
   already says "converts … the codec's planar format to 16bpp RGB565".
2. The RomFS holds exactly 10 `.moflex` movies, magic `4C 32 AA AB` (0xABAA324C) — the MOFLEX
   container — and the SoC has no video decoder, so this module is the software movie decoder.

That makes `Video_` a fact for this module instead of an inference, which is what allowed 31 names
to go from `maybe_` to confident (0.50–0.55) **and** what forced several families to be corrected
(see below). I deliberately did not push any of them above 0.55: what the variants *emit* is still
unproven.

## Corrections (the 6 groups, 51 entries)

1. **0x001336E4** `maybe_Video_McFilterOffsetTable` → `maybe_Video_TransformCoefficientTable`.
   Still data, but not offsets: the 428 bytes are 16 symmetric signed constants
   (−19199, −11520, −3840, +3840, +11520, +19199, then −28671/−20480/−12288/−4096/+4096/+12288/
   +20479/+28671) followed by 0xFFFFFFFF padding. A −19199-byte "jump offset" is impossible; the
   real relative jump tables are the ones at 0x00133810 behind the `VXS2` marker. No code in
   `code.bin` matches these bytes (best same-size match: 394/424 bytes differ).
2. **4 entries** `maybe_Video_ResidualBlockAdd{,2}` → `Video_IdctBlock8x8` / `Video_IdctBlock4x4`.
   The bodies clear a 64-word / 16-word coefficient array at `self+0x1b8`, fill it via 0x001377A0,
   then run an integer **inverse transform**: 8-point / 4-point butterfly
   (`x+(x>>1)`, `±(x>>1)`, `±(x>>2)`, `>>6` with 0x20/0x40 rounding) with DC-only and
   reduced-coefficient fast paths (`cmp ip,#0x7c` / `#0x17c`). The old name described only the
   final sample write. Verified in the disassembly, not just the (damaged) pseudocode.
3. **24 entries** `maybe_Video_McPredict{1..4}ApplyMv{2,3,4}` → `maybe_Video_McPredict{1..4}ApplyMvCopy{2,3,4}`.
   The *entry* is identical to the base routine (`push {r4,r5,r6,fp,ip,lr}`; `add r9,r0,#0x3bc`;
   `ldmia r9,{r5,r6}`; `b <same tail>`); what differs is the set of tiny per-block wrappers that
   follow it (`mov r5,#4/#8/#0xc/#0x10/#0x14` = block offset, `mov r6,#0x10/#8/#4/#2` = block size,
   `bl <entry>`, `bl 0x001352a0`). The old names implied three further apply modes; there are none.
4. **16 entries** `maybe_Video_FilterRgba*` → `maybe_Video_FilterPackedBytes*`. Nothing in this
   module holds a 32-bit RGBA frame (the only output conversion is planar → 16bpp RGB565 through
   0x00132D80), and the kernels average byte *i* with byte *i+1 across the word boundary*, which is
   only meaningful for consecutive samples. Same code, honest description.
5. **4 entries** `maybe_Video_VlcJumpStub{1,2}` → `maybe_Video_CoefficientSwitchTail{1,2}`: one
   relative jump through the coefficient switch table 0x00135418 with the code index left in r12;
   its callers are the coefficient case bodies 0x00135104/0x001351C8, so "VLC primitive" said
   nothing useful.
6. **2 entries** `maybe_Video_DecodeSignedMask` → `maybe_Video_IdctSubblocks`: it calls the (now
   identified) 4x4 IDCT once per set bit of the sub-block mask byte, so the bits select sub-blocks
   to reconstruct rather than carrying "signs".

Not a rename: the two plane-descriptor converters (`Video_ConvertPlanes4/3`) keep their names but
are now explicitly marked unproven — the "3 planes vs 4 planes" reading is not supported by the
code, which unrolls 4x in both.

## Other findings worth propagating

- **Ghidra span artifacts** (several `functions_index.json` sizes overstate the real routine):
  - 0x0013233C's 0xA44-byte span = the 0x38-byte dispatcher **plus** the 8-byte converter at
    0x00132374 that Ghidra merged into it.
  - 0x00133A08's span contains five 6-instruction per-block wrappers at 0x00133A20..0x00133A98.
  - 0x001352A0's span runs into the next entry (unconditional `bl 0x00135DCC` at 0x001353B4).
  - 0x001336E4 is not a function at all (see correction 1).
- The five MC filter banks are used as a chain: Predict1 uses (0x00133810, 0x00133850),
  Predict2 (0x00133850, 0x00133B04), Predict3 (0x00133B04, 0x00133D6C), Predict4
  (0x00133D6C, 0x00133FA4) — i.e. luma bank *k*, chroma bank *k+1*, each step coarser (index widths
  8×2, 8×2, 4×2, 4×2, 2×2). That is the real distinction between the four "Predict" variants, not
  four block sizes.
- The per-block wrappers prove the pipeline: predict a block (`bl <McPredictN…>`) then decode its
  coefficient sub-block mask (`bl 0x001352A0`), five blocks per macroblock at offsets 4/8/0xC/0x10/0x14.

## Kept as `maybe_` on purpose

`Video_ConvertPlanes4/3` (the 3-vs-4 reading is unsupported), `Video_VlcDispatchEntry{,2}` (what the
flag byte selects is unknown), `Video_InterpolateBlock4x4/2x2` (the DDA is confirmed, the phase/plane
is not), the whole `Video_BlendPlanes*` family (taps confirmed, but the "planes" may be rows of one
plane), and every corrected entry whose descriptor is still a guess.

## Not verified / open problems

- **No test suite was run** — excluded by the task. Nothing was executed against the ROM or the
  emulator; no readable C was regenerated and no symbols were merged.
- Which pixel format each `Video_Convert*` variant emits is still unknown (only the strip variant is
  tied to 16bpp by its caller). Decoding one `.moflex` frame and comparing against a dumped frame
  buffer would settle it.
- The sub-pel meaning of the five filter banks is inferred from index widths, not from a decoded
  frame; "luma/chroma phase" is the standard reading, not a proven one.
- Whether the A/B copies are reachable at all is unknown: only the C copy is wired to `Gfx_Movie_*`,
  so the A/B copies may be dead code the linker kept.
- 0x001356D4's mask bits are now known to select sub-blocks, but whether they are presence or
  sign flags is still open (0.42).
- 0x001354DC / 0x00135838 / 0x00135868 / 0x001377A0 are interior labels of other functions (Ghidra
  did not split them); they can never be named as callees until the split is done.
