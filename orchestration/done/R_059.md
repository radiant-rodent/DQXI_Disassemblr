## The 51-address video block (0x00140490–0x0014587C)
This is the `_C` copy of the video-decoder module. The pass-1 headers called these "byte-identical
duplicates" of the `_A` routines at `<addr> - 0xCC00`. I diffed every pair:

- 48 of 50 bodies are **textually identical** to their `_A` twin after normalising the function name and the
  module-relative table/dispatch references;
- every pixel kernel differs from its twin by **exactly halved frame offsets**: row pitch `0x400 → 0x200`,
  `0x200 → 0x100`, `0x3FF → 0x1FF`, `0x401 → 0x201`, `0xBFF → 0x5FF`, `0x100 → 0x80` (see
  `out/scratch/R_059/numdiff.py` output).

So the three copies at `+0x0000`, `+0x6600` and `+0xCC00` are the *same codec compiled for different frame
sizes* (the `_C` copy walks a half-height/half-pitch frame), not byte-identical clones. The name of each
`_C` entry is therefore inherited from the `_A` analysis and the summaries now say exactly what differs.
All 50 stay `maybe_` at the twin's confidence (≤0.48): the twin itself was never confirmed (N_037), and no
caller outside the module exists, so nothing new corroborates *which* codec syntax element each body
implements. A wrong confident name here would be worse than an honest `maybe_`.

## Main corrections (what the first pass got wrong)
- **`0x00150DFC` `maybe_Os_MutexLockOrAbort` → `maybe_Data_LookupValueWithTwoModifiers`.** The old name
  came from a Ghidra "subroutine does not return" call to `0x00100B74`. The disassembly of `0x00100B74` is
  `movs r1,#0; ldrh r2,[r0]; adds r0,#2; adds r1,#1; bne; bx lr` — **`std_u16_strlen`**. That also makes
  the body readable: two u16 names at `+0 / +0x3C` are rejected when empty or longer than 6 characters,
  then it resolves a row by `key` and combines two byte fields. Read from `asm/text/text_00140048.s`
  (0x00150DFC–0x00150F94).
- **`0x0015F838` `maybe_Battle_CalcValueWithModifier` → `maybe_Data_GetValueWithByteModifier`** and
  **`0x00156328` `maybe_Pack_FindTableEntry` → `maybe_Data_ResolveNameHashEntry`**: both use the engine's
  relocatable-container idiom (count at `+0x60`, relative-offset array at `+0x58 → +0x24`) that also shows
  up in `0x001B7F0C` and `0x00150DFC`; they are generic data-table helpers, not battle/PACK-specific.
- **`0x00158010` `maybe_Event_DispatchByType` → `maybe_Event_DispatchHandlerByte4B`**: body-for-body it is
  the already-named `Event_DispatchHandlerByte4` (0x0014BCA8, 0.50) with a different handler table
  (0x007A6880 vs 0x007C310C).
- **Battle command-queue trio**: `0x00169D1C` (`Ui_CmdQueue_PushEvent15`) → `maybe_Battle_QueueCommand0x15`,
  `0x00172338` → `maybe_Battle_QueueCommand0x00`, `0x00175B78` → `maybe_Battle_QueueCommand0x16`. All three
  go through the named `Battle_CommandQueue_PushEntry` (0.60); the `Ui_` prefix and the invented meanings
  ("null action", "reaction action") are gone.
- **`0x00163858` `maybe_Os_NotifyQueueEmpty` → `maybe_Util_ReleaseCountedNode`**: a plain
  decrement-to-zero + callback (intrusive refcount release); no OS queue is involved.
- **`0x0017BA38` `maybe_Ui_GetTableEntry` → `maybe_Data_GetEntry8`**: plain accessor for the 8-byte-entry
  BSS table at 0x007C33E8; its only caller is `maybe_Model_UpdateFaceAnimation`, so the `Ui_` prefix was
  wrong.
- **`0x001BB688` `maybe_Ui_SenrekiStoryWindow_Release` → `maybe_Ui_RowList_Close`**: vtable 0x00782A08 is the
  shared 0x98-byte UI row-list core; the scores neighbour is `Ui_RowList_DrawPage` and the sibling
  `0x001BB368` is `maybe_Ui_RowList_SetRowState`. There is no "senreki story window" in the code.
- **`0x001833E8` `maybe_Anim_PlayByName` → `maybe_Anim_PlayByNameB`**: its body is *literally identical* to
  `0x00182A28` (same `g_007A3C6C[self->f_313]`, same fallback, same `f_374` height fix) — a second
  emission of the field-actor method, not a generic animation-system entry.
- **`0x00181C14` `maybe_Field_SceneObject_UpdateVisibility` → `maybe_Field_SceneObject_ApplyParam`**: the
  `+0x51` byte is only a guard; the function forwards `value` to vtable `+0x84` and to `0x005F6000`, while
  its twin `0x0018193C` uses `+0x88` with no argument for teardown.
- **`0x00161D74` `maybe_Actor_SetOnceFlag` → `maybe_Object_TestAndSetChildFlag`** (it *returns* the previous
  value), **`0x00153D18` `maybe_Event_JumpToHandler` → `maybe_Script_GetArgAtBase`** (nothing jumps; it is
  one call to the VM argument accessor 0x005B5C6C), **`0x001B6E88` → `maybe_Movie_SampleOverlayPair`**
  (it tests the movie mode byte `f_104C` cached by `Gfx_Movie_IsPlayable`).
- **`0x00175B38` → `Ui_Window_ReleaseSubObject`** (0.50) and **`0x0023F514` → `Ui_PokerTable_UpdateCardSlots`**
  (0.50): both had a class noun the code did not support ("AnimationObject", "PokerCards"), now aligned with
  named neighbours (`Ui_RowList`-style teardown callers; `Ui_PokerTable_SetupCards` + poker-window tag
  0x003041A8).

## Useful findings for the follow-up work
1. **`0x00100B74` is `std_u16_strlen`** (see above). Several pass-1 headers claim it is a non-returning
   abort or a "record kind" reader; every body that appears to end at a call to it is actually truncated by
   Ghidra. This should go into `orchestration/naming/FACTS.md`.
2. **Event-command handlers**: `0x0015F0E4`, `0x0016213C`, `0x001623C8` are not free functions — their only
   caller is `Event_DispatchHandlerByte4` (the table at 0x007C310C), and all three poke the same
   level-view object returned by `0x005E64E0` (vtable slot `+0x38`/`0x0E`, `+0x3C`/`4`, `+0x40`/`4`). A pass
   that decodes the table's command byte would give them real command names.
3. **Two new duplicate pairs** worth merging in readable C: `0x00194F00` = `0x001950B0` (both request
   controller state 7) and `0x001E6C40` = `0x002BD5A4` (`str r1,[r0]; bl 0x005799D4; b 0x0010F6CC`).
   `0x00182A28` = `0x001833E8` is a third.
4. **`0x005799D4`** (destructor body used by both deleting-destructor thunks) and **`0x0010F6CC`**
   (operator delete) are still unnamed; naming them would let every dtor entry state its evidence
   mechanically.
5. The **relocatable-container idiom** (count `+0x60`, relative offsets `+0x58 → +0x24`, 8-byte rows) now has
   four users in this batch alone (0x00150DFC, 0x00156328, 0x0015F838, 0x001B7F0C). It is a type-recovery
   target: one struct + three field names would fix a lot of summaries.
