## What decided this batch

Every row had context score 0 or 1 and `neighbour_names` was empty for all 146, so "read the named
caller" was not available: only 34 of the 146 names are referenced anywhere in `decomp/readable`,
and 112 have no referencing file at all. Three things carried the pass instead:

1. **The load/save-screen state family became readable.** `Ui_Widget_Update` (0x001DAD58),
   `maybe_Ui_ObjectRef_IsFirstVariant` (0x0062F694), `Ui_SelectElement` (0x00259928),
   `maybe_Ui_Event_DispatchScriptCallback`, `maybe_Ui_RowData_AtIndex`,
   `maybe_Ui_Window_SetRowParamsAndRefresh`, `maybe_Ui_ListState_Reset` and the data-panel openers
   are all named now, so the 60+ state handlers in `0x0025A900`–`0x0025E890` are no longer opaque.
   Every one of them contains its transition id as a literal, so confirming them is a check of the
   body, not a guess: e.g. `0x0025AD80` contains exactly one `f_14(...,0x34)` call.
2. **The message-dialog family had a confident anchor.** `Menu_OpenMessageDialog1C` (0x0025A25C)
   and `Menu_OpenMessageDialog0C` (0x0025A7E0) are confident from R_014 with the exact five-call
   chain `func_00123594 -> Ui_SelectElement(owner+0x118) -> func_001F0BE4(id) ->
   func_001DAB30(owner+0x118)`. Six functions in this batch are byte-level members of that family,
   which is what turned the "TextArgWidget_Ctor_ArgNN" guess into a correction.
3. **Two confirmed save-task functions fixed their own sideliners.** `Save_LoadTask_StartSlot`
   (0x00248870) and `Save_SaveTask_StartSlot` (0x00248C08) pin the 0xA8-stride slot table and the
   task state numbers, which in turn identifies `0x0025BBC8` (a raw-ARM tail call to 0x00248870)
   and `0x0025D734` (same body, slot taken from the window table).

## Kept `maybe_` (57) — and why

The 57 kept entries fall into five honest groups:

1. **Nameless receiver or damaged body** (kept at 0.20–0.45): 0x0025BB0C, 0x00241FF0, 0x00244768,
   0x0025A248, 0x0025BB2C, 0x0025C1AC, 0x00263AE8/AF4/B24/B34/B6C (interior labels whose C is garbage),
   0x00263CE8, 0x00264CD8/64FC8 (data, not code), 0x00269354 (no body at all), 0x0026F3A0, 0x0027142C.
2. **The body is clear but the *class* is not**: the list/panel input handlers 0x0025B10C,
   0x0025B838, 0x0025B9A4, 0x0025C1DC, 0x0025DEF4 (all share the 0x142/4/8/1 mask but none is pinned
   to a named window), plus 0x0025B450, 0x0025B5B4, 0x0025B740, 0x0025C978, 0x002609CC, 0x00264CE0,
   0x003BC014, 0x003D5888, 0x002C321C (deleting destructors whose destructor body is unnamed).
3. **Item/bag semantics are not proven.** 0x00278604, 0x00279F1C, 0x00279C48, 0x0027909C keep
   `maybe_`: the loop is `id < 0x121`, not the 0xB3B ITEM rows, and the twin
   `Ui_RecipeBook_FilterByOwnedIngredients` runs the same scan for *recipe ingredients*; the
   established facts also record `func_0063E05C` as a message-ish row accessor, so "item record".
   is an interpretation. The flag bytes themselves (0x39, 0x60, type 2/3) are exact.
4. **The operation is right but the wording asserts more than the C shows**: `maybe_Save_LoadTask_Abort`
   (state 1 is also the failure state), `maybe_Save_LoadTask_Begin`, `maybe_Save_SaveTask_Continue`,
   `maybe_Save_LoadTask_ResolveObject` (0x002CE5A8 unnamed), `maybe_Item_*`, the row-group inserters
   0x00279760/0x002798E8 (their metric callers are misnamed as Battle_Monster{Hp,Mp}Bar_Update),
   `maybe_Ui_FrameScript_Update`, `maybe_Actor_Action_Move_UpdateAnimation` (a generic 4-step table
   runner), `maybe_Model_GetInstanceBase` (0x001CF7F8 unnamed), `maybe_Ui_BattleCommandWindow_GetState`
   (argument lost to `unaff_r4`).
5. **Data-block placeholders** that should not be promoted: 0x00264CD8 (alignment gap),
   0x00264FC8 (vtable pointer table).

## Open problems / follow-ups

- `func_001F0BE4(id)` is still unnamed. Its shape (id -> record, then `func_001DAB30(widget, record)`)
  is the fixed-message formatter; naming it would let the `Menu_OpenMessageDialogNN` and
  `Ui_LoadScreen_EnterStateNN` families be merged into one honest `..._SetFixedText` naming scheme.
  Several names in this batch (inherited, not introduced) say "anim" for what looks like a text id.
- **Suggested task:** name the load/save-screen support API: `0x0062F680` (readiness),
  `0x0062F070`/`0x0010EBD8` (queue count/drain), `0x0029126C` (play/flush state),
  `0x00123594` (unlink/list-append), `0x002CDB5C`/`0x002CE5A8`/`0x002CD6A8` (save I/O steps).
  Those six names would unlock another ~30 `maybe_` functions in the same band.
- `func_0063E05C` / `func_0063FD24` / `func_0063D018` and the `id < 0x121` scan need a data-side
  check (which table has 289 rows, and what is sub-entry type 2 vs 3). Until then the `Item_*`
  family in `0x00278xxx`–`0x00279xxx` stays hedged.
- `0x002785xx`–`0x00279xxx` neighbours still carry obviously wrong names from earlier batches
  (`maybe_Battle_MonsterHpBar_Update`/`MonsterMpBar_Update` are called from text-layout row code).
  Worth a dedicated "misnamed confident symbol" task — a wrong confident name is worse than a
  `maybe_` one.
