**Output:** `orchestration/naming/refine/out/R_061.json` - 150 entries, one per batch address,

## How the work was done

The batch is one of the weakest the generator produced (context score 0 or 1 for every entry,
`neighbour_names` empty in `scores.jsonl`), so nothing could be decided from callers alone. Three
sources were used, in this order:

1. **The readable C against now-named callees.** `decomp/readable/**` carries ~8,500 confident names;
   `Ui_Widget_Update`, `Ui_Window_ApplyState`, `Action_CtorBase`, `Ui_IconCache_FinishLoad`,
   `Ui_ApplyScaleToChildren`, `Ui_TwoTabCursor_OnInput`, `Ui_IsMode`, `Ui_RouletteWindow_BuildReels`,
   `Field_Action_MoveInput`, `Field_Action_OpenDoor`, `Field_Action_WalkStartToTarget`, ... appear in
   these bodies and often decide the verdict on their own.
2. **Vtable / state-table membership read straight out of `asm/rodata`.**
   `out/scratch/R_061/vt.py` finds every rodata word pointing at a batch address and prints the
   surrounding slot run, naming each neighbour through `symbols_recovered.json`,
   `decomp/ghidra/functions_index.json` and `symbols.json`. This was the decisive evidence for the
   field-action constructors, all destructor families, the popup ctor, the DiveForm state handlers
   and the two message-window advance handlers.
3. **The disassembly in `asm/text/*.s`** wherever the readable C was truncated to a tail call, decoded
   as Thumb instead of ARM, or missing entirely (the four batch entries whose only "path" is
   `decomp/ghidra/functions_index.json` have no readable C at all and were read from the listing).

Helper scripts (scratch only): `vt.py` (vtable dump), `h.py` (header + body dump), `n.py`/`bulk.py`/
`info.py` (address/name lookup), `callers.py` (who mentions an address), `validate.py` (self-check),
`final.py` (merge + strict UTF-8 round trip).

## Confirmed in bulk

- **The 24-entry tween evaluator table 0x007286A8** (0x00325A44..0x00325F48). Each body was read from
  `asm/text`: `sample`, `sample*track[0]`, `sample+track[0]`, a clamped mix, or a mode-byte test on
  +0x0C / +0x0D against 0,1,2,3,4,5,6,7 with a linear fallback at 0x00325C78. The names already
  described exactly that, so all 24 were confirmed at 0.50.
- **Field-action destructors**: Nut (0x00301E34), HorseInput (0x0030246C), Run (0x00302C90, whose real
  entry is the 4-byte thunk at 0x00302C8C), MoveStep (0x00304058, kept maybe_ at 0.48 because
  "MoveStep" is itself a maybe_ name) and the shared horse start `Field_Action_InitHorseParams`
  (0x00303768, slot 1 of both horse tables).
- **Message-window advance handlers** 0x0030F0B0 / 0x0030F208 (queue test + literal tween request 4).
- **Window-state processes** 0x00316BF4, 0x00316CA0, 0x00317194, 0x00317760, 0x00317864, 0x00317020,
  0x0031770C, 0x003177C8, 0x003168D0 - the requested state id is a literal in the body.
- **String-pinned UI classes**: 0x003188A0 (`p1_txt_chage`, `p1_icon_key_y`), 0x00318C34 (`num1_%d`,
  six rows), 0x00319520 (`Ui_TwoPaneWindow_ShowSecondPane`, same vtable as the named InitPanes),
  0x0030DB24 (`Ui_RouletteWindow_ResetPanels`, same 113-pane array as `Ui_RouletteWindow_BuildReels`).

## Traps found (recorded because they misled the first pass)

1. **0x0031F288 / 0x0031F2EC have misattributed readable C.** Both are 40-byte thunks
   (`add r4,r0,#0x14; ldr r0,[r0,#0x14]; ldr r1,[r0,#0x14]; blx r1; add r0,r4,#0xec; pop`); the
   `StartSubTween` body is actually at 0x0031F2B0 and the `StopSubTween` body at 0x0031F314. Both were
   kept as `maybe_` at 0.40 with the disassembly quoted, and a follow-up should check the readable-C
   generator where body and declared size disagree.
2. **0x001B7DDC is named `Ui_Layout_TriggerSound` (0.8, N_102) but is a wide-string pane setter**
   (`wcslen` + `wcsncpy` + 0x00116C10). That misnomer made 0x00307AC8 look like a string compare.
   It is outside this task's ownership, so it is only recorded here.
3. **0x003E49F0 (`Gfx_Effect2D_EndFrame`, 0.4) is the +0x0C slot of many field-action vtables.** Either
   the name is wrong or the slot is a shared stub; until the ctor/vtable base was matched this made the
   dtor/start/update/finish slot order look rotated.
4. **Interior / misdetected entries**: 0x00304974 and 0x00304C14 (inside 0x00304900), 0x00316398
   (inside 0x00316388), 0x00325882 (inside the tween dispatch). They are kept as `maybe_` with the
   interior status written into the summary, not renamed as if they were functions.

## What is NOT verified

- No emulator or console run, no runtime breakpoints: every verdict is static (readable C + disassembly
  + tables). Nothing here proves what the UI states *mean* to the player.
- The class labels inherited from first-pass neighbours (`EquipWindow`, `DiveForm`, `Battle_Popup3D`,
  `FieldParty`) are corroborated by vtables but not by caller-side feature code.
- The tween evaluator confirmations prove the arithmetic and the mode-byte test, not which visual
  property each slot drives.
- 0x0031F288 / 0x0031F2EC are explicitly flagged as unproven because their readable C is
  misattributed.
- Per the task, the bit-matching build and the test suite were **not** run; only the naming checker and
  a JSON/UTF-8 validator were used.
