# R_064 — second naming pass (refine)

**Status:** complete. Output: `orchestration/naming/refine/out/R_064.json` (96 entries, one per
address in `orchestration/naming/refine/batches/R_064.txt`).

## What I did

Re-examined every low-confidence `maybe_` function in the batch against the post-`M1_merge_names`
context. Concretely, for each address:

1. read the readable C (`decomp/readable/functions/<name>_<addr>.c`) including the doc header
   (previous name / confidence / batch / evidence);
2. resolved its **call sites in the real binary** — a script parsed every `bl`/`b`/`blx #target`
   in `asm/text/*.s` and mapped the call-site address to its owning function through
   `decomp/functions_index.json`, then looked the owner up in `symbols_recovered.json`;
3. resolved its **vtable slot** by scanning `asm/rodata/*.s` for the `.word` that holds the
   address, and dumped the surrounding slots so the sibling methods (the new confident names from
   M1) could be read;
4. for the interesting ones, disassembled the *callee* instead of trusting the stub (this is what
   broke two of the first-pass names — see below).

Result: **13 confirmed, 8 corrected, 75 kept as `maybe_`**.

| change | count | confidence band |
|---|---:|---|
| confirmed | 13 | 0.50 – 0.55 |
| corrected | 8 | 0.42 – 0.55 |
| kept_maybe | 75 | 0.30 – 0.48 |

90 of the 96 entries had context score 0 and 82 have no direct `bl`/`b` caller anywhere in
`.text`, so most of them can only be seen through a vtable. I did not inflate those: a vtable slot
plus an unnamed callee is not enough to drop `maybe_`.

## Corrections (what the first pass got wrong)

- **0x00402F94** `Ui_PartyPanel_PureVirtualStub` → `maybe_Ui_PartyPanel_SetFlag`.
  `0x0029126C` is not an abort handler and the call is not a trap. Disassembly:
  `ldr r2,[r0,#4]; strb r1,[r0,#0x14]; ldrne r0,[r2,#0x10]; ldrb r2,[r0,#0x44]; and #0xfe;
  orr r1; strb` — it stores a flag and propagates bit 0 into a child's `+0x44` (the visible bit).
  The same address is an ordinary vtable slot in other classes (`0x76DE7C`, `0x76E1DC`). Ghidra
  marked the tail branch "does not return", which is what produced the 0.90 pure-virtual name.
- **0x0041B23C** `Ui_Widget_SetChildFlag` → `maybe_Ui_Widget_SetChildVisible` (same setter, so the
  forwarded boolean is the visible bit).
- **0x0040D8C0** `Field_Object2D_SwapActorState` → `maybe_Field_Object2D_SyncTaskChain`. The body
  only *reads* `actor->f_312` (== 7) and attaches/detaches `&self->f_2C8` via `0x2337CC` /
  `Actor_CreateTaskChainB`; it never writes the actor state.
- **0x00423604** `Ui_PlaceWidgetInFreeCellB` → `Ui_PlaceWidgetInFreeCellThunk`. Its callee
  `0x4231B4` is now the confident `Ui_PlaceWidgetInFreeCell`; the body is a single tail call.
- **0x004A00B4** `Ui_ScreenCtor_vt775184` → `Ui_MotionPath_Ctor`. Vtable `0x775184` slots 0/1 are
  the confident `Ui_MotionPath_Dtor` / `Ui_MotionPath_DtorDelete`.
- **0x004EFC80** `Ui_ScreenObject_DtorDeleting_77C1C8` → `Field_BattleTrigger_DeletingDtor`.
  `0x77C1C8` is installed by the confident `Field_BattleTrigger_Gated_Ctor` (`0x4EFC44`), whose
  4-byte tail at `0x4EFC7C` loads the vtable and falls straight into this body.
- **0x004E1EC0** `Field_ObjectKind15_UpdateAttachment` → `maybe_Field_Object_ApplyPlacementAnim`.
  There is no kind-15 test in the body; it selects an animation name out of the table at
  `0x7A3230` (four entries) or plays `"sp13_start"`, applies the placement record, then the LOD.
- **0x0041B1F4** `Ui_TalkWindow_StopRowAnims` → `maybe_Ui_TalkWindow_ApplyRowAnims`, because its
  row callee `0x5930EC` is now `maybe_Ui_CriticalPopup_PlayAnim` — "Stop" contradicted it.

## Notable findings for later tasks

1. **The first pass's 0x47E984 evidence is wrong.** `0x00420F74` (`Monster_ModelInstance_Delete`)
   was justified with "0x47E984 is the monster model dtor". Read directly, `0x47E984` installs
   vtable `0x7743A0` (slot 1 = `Ui_AllocWidget_Dtor`), frees `+0xD0` and returns
   `Gfx_SceneNode_DtorBase(self+4)-4`; the rest of vtable `0x780820` is Ui_DrawList /
   Battle_Ui_UnitModel methods. The same 0x47E984 teardown is used by `0x421674` and `0x422B84`,
   so three "monster model" entries share one Ui-draw-list base destructor. I kept the name as
   `maybe_` with the corrected evidence rather than guessing a new class.
2. **Looks like a swapped pair:** `0x00438D38 StatusIcon_DeletingDtor` sits in vtable `0x76F40C`
   whose class-specific slot 6 is `Battle_ActorAction_ShowRevivePopup`, while
   `0x00438FD4 Motion_DeletingDtor` sits in `0x76F520` whose slot 6 is
   `Battle_ActorAction_ClearStatusIcons`. Both stay `maybe_` (the slot could be inherited);
   checking the two constructors would settle it.
3. **`0x29126C` deserves a name** — it is a plain flag setter (see above) referenced as a vtable
   slot from at least four classes. Naming it would unlock the ~8 tail-call wrappers like
   `0x402F94` / `0x41B23C`.
4. **Ghidra false entries**: `0x43C678`, `0x43C6D4`, `0x43C730` are interior addresses of
   `Battle_ActionAnim_PreMove2/3/4_Update` (0x0C bytes in), and `0x424030` is a fragment with an
   empty body. They should ideally be removed from the function catalogue rather than named.
5. 14 entries still have `halt_baddata()` as their entire readable body (0x417EE8, 0x429434,
   0x4359B8, 0x438C72, 0x43E040, 0x43E0B8, …). Re-running the decompiler on those addresses (or
   a manual ARM read) is a prerequisite for naming them.
