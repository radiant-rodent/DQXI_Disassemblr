# R_065 — second naming pass (refine) for 150 low-confidence functions

**Task:** re-examine the `maybe_` functions in `orchestration/naming/refine/batches/R_065.txt`
(150 addresses, 0x005018E8..0x0052F71C, every context score 0 or 1) and write
`orchestration/naming/refine/out/R_065.json`.

**Result:** 150/150 addresses covered — **23 confirmed**, **22 corrected**, **105 kept as `maybe_`**.
Confidence range 0.20–0.55. `python tools/check_refine.py R_065` → `R_065: OK`.

## What this batch is

Every function sits in the SDK/middleware half of `.text` (0x005xxxxx): the CTR-SDK service clients
(`ac:u`, `snd:u`, cecd file object, cfg, Y2R, the Fs archive layer) and the game's own effect module
(`Fx_`, 0x51Dxxx–0x52Fxxx). That is why the context scores were 0–1: these functions have almost no
*confident* callers, and the previous pass had to name them from constants and body shape.

Because the scores were flat, "start at the top" did not help; I worked the batch by neighbourhood
(ac:u senders → Fs archive layer → icon cache/Cecd → cfg/font → sound → Fx) and re-read each body
against its now-named neighbours rather than trusting the previous summary.

## Evidence used (what changed since the first pass)

1. **Named siblings pin the sessions.** The confident `Svc_Snd_Cmd0003` (0x005160E4) and
   `Svc_Snd_Cmd001D` (0x00516134) use the *same* session word 0x007AEAB0 as 0x005160C0/0x00516170/
   0x00516194. That fixed two wrong subsystem prefixes (below) and confirmed the three `snd:u`
   string/buffer senders.
2. **Named callers pin the command dispatchers.** `Svc_AcClient_Query` (0x005017B0) dispatches on the
   command id and calls 0x00501A40/0x00501A98/0x00501B34/0x00501B70/0x00501C8C, which turns the raw
   header literals into a real ac:u command table.
3. **Named callees pin the wrappers.** `Fs_ArchiveEntry_ReadInto/ReadBlock`, `Fs_SimulateReadLatency`,
   `Fs_Object_ReadChunk`, `Snd_StartVoicePlayback`, `Gfx_ModelResource_Reset`, `Fx_ApplyParticleState`
   and `Ui_IconCache_*` are all already confident, which is what made the Fs read/seek wrappers and the
   model-slot pair confirmable.
4. **Disassembly, where the decompiler misled.** The sound "thread start" family
   (0x00517A38/A60/B54/51864C and 0x00517DE8/51846C) all call 0x005177DC, and the listing shows
   0x005177DC is only `ldr r0,[pc,#0x90]` falling into 0x005177E0 (the `Sound_GetSystem` accessor).
   Ghidra's "subroutine does not return" note was wrong — the instructions after each call are
   `pop {r4,lr}` / `bx lr`, and 0x0051846C continues into `Snd_StartVoicePlayback`. Six names were
   therefore describing operations that do not happen.
5. **Byte-level checks.** 0x00505FD8's inner loop computes the destination index as
   `((y>>3)*(width>>3)+(x>>3))*0x40` plus the in-tile bit pattern — the GX 8x8 tile swizzle, not a
   format copy. 0x0052E918 copies `node[1]` for `node[2]<<4` bytes and returns the advanced pointer —
   an append, not a "get list head".

Besides the renames, two summaries were factually inverted and are fixed without renaming:
`maybe_Os_SvcCommandA0040` (0xA0040) is the **release** request (called by the teardown paths with
ids 0x207/0x209) and `maybe_Os_SvcCommand90040` (0x90040) is the **acquire** request (called by the
pool init paths). The previous pass had the pair the other way round.

## Kept as `maybe_` on purpose

105 entries stay `maybe_` (confidence 0.20–0.48). The Fx letter-suffix family
(`Fx_UpdateParticleListB/C/F/I/J/P/R/S/U`) is the largest group: I could describe what each body
does (per-particle integrate, sprite emit, trail history, spawn loop) but there is no way to say
*which emitter type* a variant serves without the emitter-template fields, and a confident wrong
variant name would be worse than the placeholder. The same applies to the 0x00502038 result-code
interior blocks, the two regex "entry" artefacts (not instruction boundaries), the damaged
`in_ZR`/`unaff_r*` bodies (0x0050669A, 0x0051821A, 0x00518768, 0x00526814, 0x005132E8,
0x0050DA1C, 0x0050DEA6) and the four `Os_SvcCommand*`/`Svc_Ipc_Send*` wrappers whose session words
(0x007AF090, 0x007B00E8, 0x007AF0F8) have no confident name anywhere yet.

## Not verified / open problems

1. **No disassembly review for most entries.** I only opened the listing where the decompiler was
   clearly wrong (the sound accessor family, the two regex artefacts, the interior blocks). The Fx
   field semantics (particle template +0xDC/0x300..0x698) are still inferred from offsets.
2. **`0x00502F24`/`0x00502FF8` were re-attributed to sound from the *callee* session only.** The
   surrounding 0x00502xxx block is labelled Fs everywhere; if that block is really the sound-archive
   manager, several more `Fs_` names there are wrong. This needs the 0x00502E20 family checked as a
   whole (not in this batch).
3. **`maybe_Svc_Cecd_ReadWithRetry` at 0.45** rests on the vtable-slot order (slot 0 = read); the
   slot semantics come from the previous pass, not from a named caller.
4. **The `snd:u` session claim (0x007AEAB0)** rests on two confident sibling names from the same
   region (`Svc_Snd_Cmd0003`, `Svc_Snd_Cmd001D`). I did not independently decode the session open
   call.
5. **`Ui_IconCache_*`**: I started from the hypothesis that this block is the CECD icon cache rather
   than the game UI, but dropped the rename when I found five *confident* `Ui_IconCache_*` names
   (`Close`, `SetPage`, `CommitEntry`, `ResetEntry`, `WriteRawBlock`) for the same object. Flagging it
   here instead of silently contradicting the merged state.
