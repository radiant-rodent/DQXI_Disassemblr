## Confirmed / better named (69)

The 68 fields at 0x308..0x464 are not DataManager fields. `Ui_Layout_LoadAndBind_Type1`
(0x006D9DC4) binds them as UiScreen layout parts: the even slot holds the resolved pack
entry for one `.bxon`, the following slot holds the `Pack_HandlePair` that keeps it alive.
`Field_SceneObject_ReleaseResourceHandles` (0x006DD840) zeroes the entry and returns the
handle via `Pack_ReleaseHandleEntry`. The first-pass `dm` prefix was dropped.

Reasons, in three groups:

- 0x30, 0x150, 0x210, 0x220 (and the second half of 0xf0's evidence) are vtable-slot
  artifacts: the cited code is `(**(code **)(*param_1 + N))(...)`, a virtual call, not a
  field access.
- 0x70, 0x90, 0xf0, 0xf8, 0x108, 0x128, 0x130 rest on the first pass's claim that
  `Field_SceneObject_CopyRecord` (0x00617674) scales offsets by 4. The body shows plain
  byte offsets (`dst->maybe_subRecordWord1C = src->f_1c`), so those copies land on 0x1c,
  0x24, 0x3c, 0x3e, 0x42, 0x4a, 0x4c — the evidence does not reach these offsets.
- The rest cite functions with no decompiled body (0x002B4DF4, 0x00339A30, 0x003568D0,
  0x0044B57C, 0x004489DC, 0x00449A88, 0x0044B800, 0x0046C5F8, 0x004AEFD8, 0x004CA9E8,
  0x0044F4EC, 0x002B4AE4), or the cited use is on a different object (0x6c is read off
  the game-work pointer in `Field_SceneObject_AdvanceBookFlag`, 0x20 is written on a
  0x38-byte child in `Field_SceneObject_InitModelFromLayout`). Not justifiable.
