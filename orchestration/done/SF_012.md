## What the block is

`0x468..0x6FC` is a run of 4/8-byte `.bxon` resource slots: each resource is
`{ u32 tablePtr; u32 packHandle; }`, table pointer at offset X and pack handle at X+4.
Confirmed from the raw decomp of `Field_SceneObject_ReleaseResourceHandles`
(0x006DD840), which emits monotonically ascending pairs:

```
*(undefined4 *)(param_1 + 0x464) = 0;   FUN_005634E0(param_1 + 0x468);
*(undefined4 *)(param_1 + 0x46c) = 0;   FUN_005634E0(param_1 + 0x470);
```

`Pack_ReleaseHandleEntry` (0x005634E0) validates `handle >> 0xC` against
`g_00563534`/`g_00563538`, frees the entry via `Pack_FreeHandleEntry` and poisons the
slot to `0xFFFFF000` — i.e. the released slot is a packed-resource handle, not a table.
The zeroed slot is the resolved record pointer of the same resource, so names are
`<resource>Table` / `<resource>Handle` (no `maybe_`; `dm` prefix dropped).

Resource identity per offset follows the fixed `.bxon` name list, whose order (with the
same gaps: no a040/a090/a120/a160, no b050, no c200) is used again by the independent
binder `Ui_Layout_LoadAndBind_Type1` (0x006D9DC4) for `g_resNameStoryA130`,
`g_resNameStoryA140`, … in the same sequence.
