# S_005 - class and field naming for the `Anim` subsystem

**Status:** completed
**Output:** `orchestration/types/out/S_005.json` (12 classes, 45 fields: the 42 batch offsets plus 3 deliberate extras)
**Also touched:** `AGENT_LOG.md` (one appended entry, Entry 361), this report.

## What the batch asked for

Name the 12 classes and every field of `orchestration/types/batches/S_005.json`
(subsystem `Anim`): `Anim_CurveSample`, `Anim_Tween`, `Anim_Timeline`, `Anim_Track`,
`Anim_AnimClip`, `Anim_CurveEval`, `Anim_CurveEvalCase`, `Anim_Owner`, `Anim_BoneTrack`,
`Anim_KeyframeTrack`, `Anim_PingPongFloat`, `Anim_Player`.

## Method

For every class I read the readable C of its constructor / only method first, then the
`update`/`evaluate` methods, and cross-checked every offset against the disassembly in
`asm/text/` whenever the pseudocode was damaged (`in_s0`, dropped float returns, `param_1 + N`
pointer arithmetic that does not mean byte offset N). `tools/fn.py` was used for the small
thunks that have no readable file. Vtables were resolved by reading the words out of
`original/exefs/code.decompressed.bin` at `addr - 0x00100000` and mapping them through
`symbols.json` - that is how the "vtable" claims in the batch were checked. No whole-tree walk
or grep was performed.

42/42 batch offsets covered exactly once, plus offset 0 of the three curve classes (see below).
0 errors and 3 warnings from `tools/typedb/apply.py`'s own `merge_structs`; `emit_struct`

## Findings worth carrying forward

### 1. The 0x007AE7C8 "vtable" is a static dispatch table, not a vtable

`Anim_CurveSample`, `Anim_CurveEval` and `Anim_CurveEvalCase` are **one 36-byte object**: the
animation keyframe curve. `struct_db` split it into three classes because three groups of
evaluator cells were clustered separately, and it reported `vtable 0x007AE7C8` / `0x007AE828`
because those addresses are the *table* the cells live in, not a per-object vtable.

`Anim_Curve_Dispatch` (0x0065B890) is 56 bytes:

```
push {r4,lr}; mov r4,r0; bl 0x65b760        ; Math_ComputeNormalizedRatio(curve, time)
ldrb r0,[r4,#0xc]                            ; key-format row
vldr s1,[r4]                                 ; curve->f_00  <-- a FLOAT, not a vtable
ldrb r1,[r4,#0xd]                            ; interpolation-mode column
vsub.f32 s0,s0,s1                            ; t = wrapped - start
add r0,r2,r0,lsl #5                          ; 0x007AE7C8 + row*0x20
ldr r1,[r0,r1,lsl #2]                        ; + col*4
bx r1
```

So `0x007AE828` is exactly `0x007AE7C8 + 3*0x20` = row 3, column 0. Offset 0 is `startTime`.

Full layout (all verified in the cell bodies):

| offset | name | type | evidence |
|---:|---|---|---|
| 0x00 | `startTime` | f32 | `vldr s1,[r4]` + `vsub.f32`; `Math_ComputeNormalizedRatio` reads `range[0]` |
| 0x04 | `endTime` | f32 | `range[1]`; F3M0 `(self[1] - *self)` is the duration |
| 0x08 | loop mode byte | u8 | `Math_ComputeNormalizedRatio` `ldrb r1,[r0,#8]`, 0 = no wrap, 1/2 = wrap |
| 0x09 | second loop mode byte | u8 | `*(char *)((int)range + 9)` in the same function |
| 0x0C | key-format row | u8 | `ldrb r0,[r4,#0xc]` in the dispatcher |
| 0x0D | interpolation-mode column | u8 | `ldrb r1,[r4,#0xd]` in the dispatcher |
| 0x0E | `keyCount` | u16 | `ldrh r2,[r4,#0xe]` then `add r2,r3,r2,lsl #3` = last key |
| 0x10 | `valueScale` | f32 | F2M1 `vldmia r4,{s1,s2}` + `vmla.f32 s0,rawValue,s1` |
| 0x14 | `valueBias` | f32 | same `vmla`, `s0` preloaded from `[r4,#0x14]` |
| 0x18 | `duration` | f32 | `vmul.f32 s2,keyTime,[r4,#0x18]; vcmp.f32 s2,in_s0` |
| 0x1C | `inverseDuration` | f32 | index estimate `[r0,#0x1c] * (keyCount-1) * t` at 0x006EB9C0 |
| 0x20 | `keyArray` | void* | `ldr r1,[r0,#0x20]`; keys are 16/12/8/6 bytes per format row |

I emitted offset 0 in all three classes (the three warnings in `report.json` are exactly these)
because leaving it as padding would hide a real float. Offsets 0x08/0x09/0x0C/0x0D are **not**
in the batch's field set, so they stay padding - they are documented here and in the class
`evidence` string.

**Suggested follow-up:** a merge task should collapse `Anim_CurveSample` + `Anim_CurveEval` +
`Anim_CurveEvalCase` into one struct (the readable C already calls it `AnimCurve`) and add the
four missing bytes. `apply.py` cannot do that on its own because it emits one typedef per class
and three typedefs with the same name would not compile.

### 2. Batch contamination - reported, not guessed

* `Anim_Track` merges **two different objects**. `Anim_Track_AccumulateTranslation` (0x007131A0)
  reads a 24-byte transform group: flags at +0x08 (`ldr r0,[r0,#8]`; 0x20/0x10/0x08 = skip
  translation/rotation/scale, 4/2/1 = "constant, do not evaluate the curve") and three curve
  pointers at +0x0C (translation, `Anim_Track_EvaluateVec3`), +0x10 (rotation quaternion,
  `Anim_Track_EvaluateVec4`) and +0x14 (scale, `Anim_Track_EvaluateVec3`).
  `Anim_Track_EvaluateVec3/Vec4` (0x00712200 / 0x00712100) instead take a **separate 16-byte**
  `{f32 start@0, f32 end@4, ?@8, keys*@0xC}` curve as their first argument. Offset 0x04 therefore
  has no meaning in the group and is `unknown_04` at confidence 0.0.
* `Anim_KeyframeTrack`'s recorded write (`*puVar6 = 0x00782AFC`) is to a **locally computed**
  pointer (`puVar6 = (u32 *)(iVar3 * 0x10)` in `Anim_KeyframeTrack_ResetState` 0x005ACB04), not
  to `self`. The real fields come from `Anim_KeyframeTrack_EvaluateAll` 0x005ABEB4:
  `iVar11 = Mem_AllocAligned(...); self[1] = iVar11; *self = iVar11; self[2] = iVar9;` and later
  `self[6]`/`self[7]` for the two track tables, so the object is at least 0x9C bytes and the
  batch's 8-byte size is a lower bound.
* `Anim_PingPongFloat` is the **owner** of the swing, not the swing state. The only field of the
  first argument that `Anim_PingPongFloat_Update` (0x0049D404) touches is +0xA4; the value and
  velocity live in the second argument at +0x13C / +0x140.
* `Anim_Owner`'s 268-byte size is a lower bound: the embedded `Anim_Instance` at +0xFC needs at
  least 0x28 bytes (its own +0x0C/+0x24/+0x26 are read by `Anim_Instance_Update` 0x002D0F4C).
* `Anim_Player`'s 72-byte size is a lower bound too: `Anim_Player_SetFrame` writes the current
  frame at +0x64, beyond the reported size.

### 3. `Anim_Timeline` is an orphan with a wrong symbol size

0x006631E8 is **124 bytes**, not 516: it ends at the `pop {r4,pc}` at 0x00663260, and the code
after it (0x00663270 onward) is a different function. Its three call-graph callers are bogus -
`Sound_Cwav_Open`'s only `bl` targets are 0x00663308 and 0x006632A0, not 0x006631E8.

The body is a small value generator:

```
if (limit(+0x08) > counter(+0x10)) return counter;          /* not ready yet */
cb = table[0x007E8120][type(+0x0D)];
if (!cb) v = 1.0f;
else if (type == 4) { if (flag(+0x1D)) { v = cb(phase(+0x14)); cached(+0x18) = v; } else v = cached(+0x18); }
else v = cb(phase(+0x14));
return (f32)count(+0x0C) * amplitude(+0x00) * v;
```

The callback table at 0x007E8120 is in BSS (filled at runtime), so the waveform set cannot be
read statically. All six fields are `maybe_*` at 0.40-0.45 and the owner is recorded as unknown.

### 4. `Anim_AnimClip` base constructor found

Ctor 0x005402F0 calls the **unnamed 0x24-byte base ctor 0x00537720** (its dtor is
`Ui_LayoutElement_Dtor` 0x00537768), then:

```
str  r1,[r0]          ; +0x00 = 0x007815D8 (vtable)
vstr s0,[r0,#0x24]    ; +0x24 = 0.0f  <-- VFP store, so the field is a FLOAT
strb r2,[r0,#0x28]    ; +0x28 = 0
str  r2,[r0,#0x2c]    ; +0x2C = 0
```

`Ui_AnimClip_Load` (0x0053D36C) allocates **0x34** bytes, overrides the vtable with 0x00781250
and clears +0x30; `Ui_AnimClip_PlayFrom` (0x005363E8) stores the start frame in `clip[0xC]` =
+0x30. The batch guessed +0x24 as `u32`; it is `f32`.

## Decisions I made without the orchestrator

* **Kept the generated class names and type names** (`Anim_CurveSample` etc.) even though the
  readable C uses `AnimCurve`. `apply.py` emits one typedef per class, so giving three classes
  the same `type` would produce three identical typedefs and break the header. The duplication
  is flagged above as a follow-up instead.
* **Added offset 0 to the three curve classes** although it is not in the batch's field set,
  because it is a verified float and would otherwise be emitted as padding. This is the only
  deviation from "every offset in the batch appears exactly once" (nothing is missing or
  duplicated) and it costs three warnings in `report.json`.
* **`unknown_04` in `Anim_Track`** rather than a plausible-looking name, per the rule that a
  correct vague name beats a precise wrong one.
* **`Anim_Instance*` / `Anim_Player*` for embedded objects** (`Anim_Owner` +0xFC, and the
  `Anim_Player` pointer at +0x108) follows the precedent set by `S_001`, which typed the
  embedded `std_StateSequence62` at +0x2C as a pointer. The evidence strings say explicitly that
  +0xFC is embedded (passed by address), so a later pass can correct the type without re-deriving
  the layout.
* **Did not run `apply.py --validate`** (it would rewrite the shared
  `orchestration/types/merged/report.json`). I imported `Evidence`, `merge_structs` and
  `emit_struct` and ran them on this file alone instead - same code path, no shared write.

## What is NOT verified

* No emulator run and no runtime check. Every name is static-analysis evidence only.
* The `maybe_*` names at 0.30-0.45 are hypotheses with the quoted evidence, not confirmed
  semantics: `Anim_Timeline` (all six fields), `Anim_AnimClip` +0x24/+0x2C, `Anim_Owner`
  +0xFC/+0x108, `Anim_KeyframeTrack` +0x04.
* `Anim_Timeline`'s owner is unknown; the object is only reachable through the runtime-filled
  table at 0x007E8120.
* `Anim_AnimClip` +0x2C has no reader in any recovered method - its purpose is genuinely unknown.
* `Anim_Owner`'s and `Anim_Player`'s real sizes are larger than the batch's numbers; I did not
  try to derive them.

## Suggested follow-up tasks

1. **Merge the three curve classes** into one `AnimCurve` struct (36 bytes, 12 fields) and add
   the four missing bytes 0x08/0x09/0x0C/0x0D. Needs a small change in `apply.py` (allow a
   class alias) or a hand-written entry in `orchestration/types/samples/`.
2. **Split `Anim_Track`**: the 24-byte transform group and the 16-byte `{start,end,keys}` curve
   are two classes. The curve is currently unnamed and is used by `Anim_Track_EvaluateVec3/Vec4`,
   `Anim_Channel_Evaluate*` and `Anim_Bone_ApplyTransforms` - it deserves its own batch entry.
3. **Find `Anim_Timeline`'s owner**: search for stores of the 0x007E8120 table index and for
   allocations of a 0x20-byte object with a float at +0x00.
4. **`Anim_AnimClip` +0x2C**: the concrete clip vtable 0x00781250 has slots at +0x0C
   (`Ui_AnimValue_UpdateScroll`), +0x10 (0x005360FC), +0x14
   (`Ui_LayoutElement_ApplyPaneVisibility`), +0x20 (0x0053681C), +0x24 (`Ui_AnimBinder_Init`),
   +0x2C (`Ui_Animator_BindByName`); 0x005360FC and 0x0053681C have no readable file yet and are
   the most likely readers of +0x2C.
