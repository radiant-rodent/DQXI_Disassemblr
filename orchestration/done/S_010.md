## Analysis & Evidence

### Class identification

- **It is a real ~60 KB object, not a namespace merge.** `Battle_Ui_Ctor` (0x0047DEA0) stores the
  vtable at `+0x00` and calls `Ui_Screen_CtorBaseEx` (0x004BF110) first; that callee's own
  documentation calls it the "0x129C-byte base". 233 methods are recovered for the class and they
  all take the same `self`.
- **Base corrected to `Ui_Screen`.** The generated `Ui_ActionPane` base came from base-constructor
  calls seen in a handful of methods; `Ui_ActionPane` appears in only 6 of the 233 functions, while
  `Ui_Screen_CtorBaseEx` is the first call of the constructor. `apply.py` skips `embed` when the
  first field offset (0) is below the base size, so this correction is layout-neutral.
- **Size raised 60776 -> 60780** because the last field (`+0xED68`) ends at 60780. `apply.py` takes
  the max of the declared size and the field extents, so this only makes the declared size honest.

### Decisions (recorded because the orchestrator could not be asked)

1. **29 batch offsets are vtable-slot artefacts, not fields.** `tools/typedb/struct_db.py`
   multiplies the slot offset by 4, so a call written `(**(code **)(*param_1 + 0x48))` is emitted as
   field offset `0x120`. These are named `unknown_vtableSlotNN` at confidence 0.0 with the reason in
   `evidence`: `0x120, 0x130, 0x150, 0x170, 0x180, 0x1A0, 0x1C0, 0x1D0, 0x1E0, 0x210, 0x220,
   0x230, 0x250, 0x290, 0x2C0, 0x360, 0x3B0, 0x3F0, 0x400, 0x410, 0x420, 0x430, 0x440, 0x450,
   0x470, 0x480, 0x490, 0x4D0, 0x4F0`.
2. **22 offsets come from damaged decompilation.** 0x00483308 stores the self pointer into its own
   fields and ends in `halt_baddata`; `0x2F10..0x2F6C` are `unknown_damagedNNNN` at 0.0.
3. **2 offsets are far outside the layout.** `0x5FB00` and `0x5FB0C` come from `param_1[0x17ec0]`,
   a mistyped `self`; named `unknown_outOfRange5fb00` / `unknown_outOfRange5fb0c` at 0.0.
4. **Field `size` is always derived from the declared type width** (u8 -> 1, u16/s16 -> 2,
   u32/s32/f32/void* -> 4) so the merge's padding walk stays consistent with the type it emits.
5. **Two unavoidable overlaps remain**: `0xE9` inside the f32 at `0xE8`, and `0x105` inside the f32
   at `0x104`. Both are byte accesses made through a *different* object; the `evidence` text says
   so and the merge will skip them.
6. **`unknown_*` names are not `maybe_`-prefixed.** The task's own example sanctions `unknown` at
   confidence 0.0; every other name below 0.5 was auto-prefixed `maybe_` by the build script.

## Suggested Follow-ups

1. **Fix `tools/typedb/struct_db.py`**: a call through `*param_1 + 0xNN` is a vtable slot, not a
   field. Emitting it as a field produced 29 false offsets in this batch alone and forces every
   S-batch worker to spend time on them.
2. **Split `Battle_Ui` in a later S batch.** It is a 60 KB aggregate: the target panel
   (`0x588`/`0x5A4`), the party row panel (2 x 0x5BCC at `0x18B4`), the member screen (0x58 at
   `0xB464`) and the balloon (`0xED34`) are separate objects embedded by value and deserve their
   own classes with their own constructors.
3. **Re-check 0x00483308** against `asm/` — if the decompilation is repaired, the 22
   `unknown_damaged*` fields can be named.
4. **Confirm the balloon style records** at `0xDE70`/`0xDEA4` (2 x 0x14) against the balloon draw
   code; they are the most likely place where a wrong guess is hiding.
