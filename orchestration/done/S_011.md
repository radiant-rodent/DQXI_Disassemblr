## Analysis & evidence

### 1. 82 of the 414 offsets are `struct_db.py` artefacts, not fields

`tools/typedb/struct_db.py` parses `ADDR = \b(\w+)\s*\+\s*(0x[0-9a-f]+)` and scales the offset by
the element width of the base pointer. A virtual call written
`(**(code **)(*self + 0x48))(self, ...)` therefore matches with `base = self`, `off = 0x48`, and
`element_width(self) = 4`, producing a phantom field at **0x120**. These entries always have
`reads == 0` and `writes == 0` and their only evidence lines are virtual-call expressions.

They are answered as `unknown_vtableSlotNN` (NN = the real slot offset) at confidence 0.0 with the
explanation in `evidence`, so the batch stays fully covered without inventing a member:

`Battle_ActionSequence@0x310` is the same artefact in a form the regex missed
(`pcVar10 = *(code **)(*param_1 + 0xc4);` - a slot load without the call), so it is named

**Suggested fix (follow-up task):** in `struct_db.py`, skip `ADDR` matches whose base is preceded by
`*` inside a `(code **)(...)` cast, or simply drop `ADDR` observations where the base pointer is
dereferenced first (`*self + 0xNN`). That would remove all 82 phantom offsets from every S batch.

### 2. 44 offsets are `weak` single accesses at implausible offsets

`Battle_Sequence` (24) and `Battle_ActionSequence` (20) contain offsets from 0xB464 to 0xE08C that
are touched once each. `Battle_Sequence` is 0xED38 bytes and `Battle_ActionSequence` is 0xE004
bytes, so these offsets are inside the declared size, but the accesses come from functions whose
`self` is really the battle work / a sequence sub-object (e.g. `param_1[0x3b4d] + 0x768` is a unit
model id, `param_1[0x3784]` is a state id). They are `unknown_0xNNNN` at 0.0 with that reason.

### 3. What each class actually is

- **`Battle_PartyMember`** - per-member battle display object. `Battle_PartyMember_Update`
  (0x00483870) is a state machine over `self[0x5e3]` (0x178C) with states
  0x245C/0x2495/0x249C/0x24A1/0x24A7/0x2475; every handler starts with
  `if (*(char*)(self+0xd2) != 0) return 1;` (0xD2 `isFinished`). 0x125C `stateId` doubles as the
  action-row id passed to `func_0063FD24(dm, id)`; 0x1260 is the SE record whose first `u16` goes to
  `Sound_PlaySeById`; 0x1264 is the voice handle waited on by `Sound_WaitForHandleOrTimeout`
  (0x001FFF9C). The class is polymorphic (vtable 0x77457C per the doc header) even though the batch
  reported no vtable, so offset 0 is `vtable`.
- **`Battle_Popup3D`** - 3D pop-up container. `Battle_Popup3D_InitPopups` (0x002E88B8) binds the
  `"null_pop"` pane through the layout vtable slot 0x2C, creates eight `"pop%d"` sprites from
  `"battle_up_3d_pop.bflyt"` and stores one `Battle_PopupObject` per slot at `self+0x11C`; 0x10 is
  the heap passed to `Mem_AllocAligned_2`; 0x5C is the battle work (`self->f_5c->f_4254` is the unit
  list); 0x158 is the fade accumulator; 0x1A0/0x1A4 are the objects bound to the `"target"` and
  `"result"` panes.
- **`Battle_Sequence`** - battle action-sequence driver. `Battle_Sequence_Update` (0x005A407C) is a
  state machine over `self[0x3784]` (0xDE10) with states 0xF46/0xF69/0xF80/0xF89/0xF8B/0xF91/0xFA4/
  0xFAB; 0x30 is a 3DS handle word resolved through the global handle table at 0x007B80C0; 0x4C/0x50/
  0x54 are the translation of the transform handed to `func_00234014`; 0x1260 is a `SpellRecord`
  (dereferenced at +0x2B8/+0x2BA/+0x293); 0xED34 is the current battle unit (+0x768 model id).
- **`Battle_Ui_TargetGroup`** - target-group marker manager. `Battle_Ui_TargetGroup_InitMarkerSlots`
  (0x004C1950) walks 26 unit pointers per 0x68-byte group block at `self+0x220` and unions each unit
  marker rect into **five 0x14-byte slots at 0x578/0x58C/0x5A0/0x5B4/0x5C8** (slot index is
  `unit->f_45`, stride 0x14, each slot `{u32 flags; f32 left; f32 top; f32 right; f32 bottom}` reset

- **`Battle_Popup`** - damage/heal pop-up window. `Battle_Popup_Ctor` (0x00469FF4) installs vtable

- **`Battle_ActionUi`** - battle action-UI director. `Battle_ActionUi_Ctor` (0x003F6E2C) chains

## Decisions taken (orchestrator not available)

1. **Artefact offsets are answered, not dropped.** The task says every batch offset must appear
   exactly once, so the 82 vtable-slot artefacts and 44 weak offsets are emitted as
   `unknown_vtableSlotNN` / `unknown_0xNNNN` at 0.0 with the reason in `evidence` rather than being
   silently omitted. `apply.py` accepts them (0 errors) and will emit them as ordinary members; the
   evidence text tells a modder they are not real.
2. **Field `size` is always the batch value.** `apply.py` advances the struct offset by the declared
   `size`, so embedded sub-objects (e.g. the 0x50-byte `Ui_AnimRefList` at `Battle_Popup+0x14C`) are
   declared as `u32` with the real extent described in `evidence`. Declaring the full struct type
   would have made the merge skip the following fields.
3. **`maybe_` prefix applied mechanically** to every name with confidence < 0.5, as the task
   requires, including names that read oddly with it (`maybe_positionX`).
4. **`--validate` was run** even though it writes `orchestration/types/merged/` (a generated
   directory, not a source file). It reported **0 errors, 3 warnings, none from S_011** (all three
   are `S_005` "offset has no access evidence").
