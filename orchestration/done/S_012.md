## Analysis & Evidence

### 1. Command controller family (`Battle_Command`, `Battle_ItemCommand`, `Battle_AttackTarget`, `Battle_SpellTarget`)

Four classes in this batch share the exact same 116-byte (`0x74`) memory layout and command window architecture:
- `+0x0` `vtable`: virtual method table calling slot 7 (`*self + 0x1c`) on state changes.
- `+0x4` `actorIndex`: actor party member index (`(char)self[1]`), passed to `func_002AB62C(ctx+0x4254, actorIndex)` to resolve the active party member.
- `+0x8` `actorWindow`: actor status/display window (`self[2]`), invoked via `vtable+0x14` with command state flags.
- `+0x10` `activeSubWindow`: active command sub-window (`self[4]`), updated via `vtable+0x70` / `+0x44`.
- `+0x14` `commandWindow`: root battle command window (`self[5]`), queries pad flags at `+0x130` and opens sub-pages via `vtable+0x4C`.
- `Battle_Command` also coordinates equipment context at `+0xC` (`self->f_C->f_C`), state at `+0x28` (`self[10]`), sub-window mode at `+0x2C`, popup context at `+0x34` (`Ui_PopupEntry_ClearAll`), and commit flag at `+0x44` (`Battle_Command_CommitActorAction`).
