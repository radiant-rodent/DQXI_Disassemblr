## What I did

Read `orchestration/types/batches/S_013.json`, then for every class opened the readable C of its
constructor / destructor / update methods (`decomp/readable/functions/`), cross-checked the raw
disassembly with `tools/fn.py --asm` where the pseudocode was ambiguous, and resolved the
referenced types against `orchestration/types/structs.json`.

The batch's `readable` paths were stale (the readable tree was regenerated after the batch was
generated), so I built an address -> file index once
(`out/scratch/S_013/readable_index.json`, 17,994 entries) and looked functions up by address.

### The three popups share one layout

`Battle_MpHealPopup_Dtor` (0x0046B1B0), `Battle_DamagePopup_Dtor` (0x0046ADA4) and
`Battle_Popup_Heal_Dtor` (0x00403CC4) all do the same two `std_destroy_range` calls:

```
std_destroy_range(self + 0x4C, 0x003E04BC /* Ui_LayoutRef_Release */, 0x50, N_digits);
std_destroy_range(self + 0x13C or 0x1DC, 0x003D2580, 0xA8, N_widgets);
Ui_Object_DtorBase(self);
```

* `+0x4C` — `N_digits` × 0x50-byte `Ui_AnimRefList` (ctor 0x003E0454, release 0x003E04BC), one
  animation-reference group per digit. `Battle_Popup_Prepare*NumberPanes` hides them with
  `func_003E043C(self + 0x4C + 0x50*i, 0)`.
* the next offset — `N_widgets` × 0xA8-byte number widgets, constructed in a loop by 0x001A6520
  (layout pointer at +0x30, pane at +0x4C, cached pane at +0x50, `Ui_AnimRef` at +0x54) and
  destroyed by the thunk 0x003D2580 into `maybe_Ui_IconButton_Dtor` (vtable 0x007699DC).

Because `0x4C + N_digits*0x50` lands exactly on the widget array, the two arrays are adjacent and
the object sizes follow from the destructor: 1324 (3 digits / 6 widgets) and 2996 (5 / 15). The
batch sizes (320 / 480) were only `highest strong field + 4`.

### struct_db artefacts

`struct_db` multiplies a vtable-slot offset by 4 and reports it as a field. Three batch offsets are
such artefacts and are emitted as `unknown_*` at confidence 0.0:

* `Battle_Ui_MemberAnim` +0x120 = slot 0x48 of `(**(code**)(*self + 0x48))(self,0)`
* `Battle_Ui_MemberAnim` +0x540 = slot 0x150 of `(**(code**)(*self + 0x150))(self)`
* `Battle2DUnit_StateBlock` +0xD0 = slot 0x34 of `(**(code**)(*self + 0x34))(self,0)`

`Battle_Ui_MemberAnim` +0x127C is **not** an artefact: the readable C shows `self + 0x49F` on an
`int*`, and the disassembly (`add r0, r0, #0x1000; add r0, r0, #0x27c`) confirms byte offset 0x127C.

## Decisions I made (orchestrator unavailable)

1. **Kept the batch `class` names.** `tools/typedb/apply.py` rejects a class that is not in
   `structs.json` (`merge_structs`, "class is not in structs.json evidence"), and
   `Battle_MpHealPopup` / `Battle_ActionModel` are not there. The true identity is stated in each
   `summary` and `evidence` instead, so the merge comment carries the correction.
2. **Raised three sizes** where the destructor proves a larger object (see table). `apply.py` takes
   the worker size and then raises it to `max(offset+size)`, so this is safe.
3. **Left the 0xA8-byte number widgets as `u8[N*0xA8]`.** No recovered class has that layout
   (`Ui_CursorWidget` is 100 B, `Ui_NumberPopup` 80 B, `Ui_Widget` is a 5548-byte namespace merge),
   so a typed array would give the wrong stride. The evidence names the ctor, the dtor and the
   inner offsets so a later batch can type it.
4. **Did not add fields outside the batch.** `Battle_Ui_MemberAnim` also reads +0x12D8 (actor
   pointer) and +0x137A (member byte), and `Battle_SceneInit` has three 0xC-strided slots at
   +0xA0/+0xAC/+0xB8; those are recorded in the class `evidence` but not emitted, to avoid
   colliding with another batch. Their existence is why those two sizes are documented as lower
   bounds.
5. **`Battle_Item` is not `Battle_UiFlow`** even though both are 440 bytes: `Battle_Item`'s +0x1B4
   is loaded as a plain index (`ldr r1,[r4,#0x1b4]` -> `func_002AB62C(battleWork+0x4254, index)`),
   while `Battle_UiFlow` dereferences its +0x1B4 as a pointer to a step record.

`verify_project.py` fails on exactly two checks, both WSL-environment artefacts, neither caused by
this batch:

* `model texture manifest` — `tools/verify_model_textures.py` imports `PIL`, which is not installed
  in the WSL Python (`ModuleNotFoundError: No module named 'PIL'`).
* `patched ROM exists` — the check builds the literal Windows path `build\DQXI_patched.3ds`; under
  Linux that is a filename containing a backslash. The 4 GB file does exist.

The full `tests/run_all.py` was skipped as instructed (naming batch, rule 5).
