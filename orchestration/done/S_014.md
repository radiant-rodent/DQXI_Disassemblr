### Camera_Work — per-frame camera snapshot cache
`Camera_Work_Snapshot` (0x003DF0D0) reads `Os_GetGameWork()->f_08->f_80` and copies the
camera transform (source node `+0x38..+0x5C` → `+0x28..+0x48`), four sub-camera bytes
(`+0x95`/`+0x99`/`+0x9D`) and four positions (`+0xF0`, 4 × vec3). The object holds **five
embedded publisher blocks** at `+0x0C/+0x58/+0x84/+0xB0/+0xDC`; each has a vtable word at
its start and a pending byte at `+0x10`. `Camera_Work_Update` (0x003DF2C0) calls their
vtable slot `+8` and clears the pending byte (verified in the disassembly:
`add r6,r4,#0xb0; ldr r0,[r6]; ldr r1,[r0,#8]; blx r1`).
Size raised 244 → 288: the 4 × 12-byte position array at `+0xF0` ends at `+0x120`.

### Camera_Field — field-camera pose record
`Camera_Field_Update` (0x0059A4B4) writes eye position (`+0x04..+0x0C`), target position
(`+0x10..+0x18`), a constant vector from `0x007E7024` (`+0x1C..+0x24`) and a smoothed fade
value (`+0x28`). It embeds a `Gfx_ScreenFade` at `+0xE0` (96 bytes, so `+0x104` is that
record's `+0x24` float) and four 0x24-byte Path occlusion objects at
`+0x160/+0x188/+0x1B0/+0x1D8`, destroyed by `Container_ReleaseListAndFree` / `Path_Dtor` in
`Camera_Field_Delete` (0x0059A814). The class shares the `Ui_MotionPath` layout — the
destructor calls `Ui_MotionPath_Release`/`Ui_MotionPath_Dtor` on the same `this`.

### Camera_TargetDescriptor — the class name is wrong
0x003EAA70 is a **save-code (Spell of Restoration) record init**, not a camera target. It
stores `0x303` at `+0`, three caller words at `+4/+8/+0xC`, zeroes a 40-byte payload at
`+0x10..+0x34`, then dispatches on `wcslen(name)`: length `0x14` → `SaveCode_EncodeFixed20`
(0x005EF4F0, requires `count == 0x14` and ids in `0x3000..0x30FC`), length `0x11` →
0x005EFE24, and on first use calls `Save_Crypto_SetKeyFromString` (0x005F0924, Blowfish key
schedule). Returns 3 for a null/empty name, 0 on success.
The class name **cannot** be changed here: `apply.py` resolves `class` against
`structs.json`, so a rename would be rejected. The correction lives in `summary`/`evidence`.

### Camera_MotionSet — the batch's ctor/dtor roles are swapped
0x003ED388 is the **destructor**, not the constructor: it stores vtable `0x0076B7F0`, runs
`std_destroy_range(self+0xAEC, 0x004CF57C, 0x50, 0x18)` (24 slot records) and
`std_destroy_range(self+0x528, 0x0045F07C, 0xB8, 8)` (8 track records), relinks two
intrusive list heads at `+0x514/+0x518` and `+0x520/+0x524`, then chains
`Ui_Object_DtorBase` on `+0x4BC/+0x34C/+0x300/+0x2B4`. 0x003ED378 is the deleting destructor.
The vtable's slot 6 is `Ui_Window_LayoutRows`, and the same object is described by the
existing `Ui_CameraAnimWindow` class entry (fields at `+0x300/+0x34C/+0x37C`), so this is a
camera motion-set **window**, not a plain data set.
Size raised 1324 → 4716: the 24 × 0x50 array at `+0xAEC` ends at `+0x126C`.

### Camera_RegularShake — periodic camera shake
`Camera_RegularShake_Ctor` (0x0059131C) calls `Container_NameHash_Ctor(self, "ReguralyShake")`,
stores five float arguments at `+0x7C/+0x80/+0x84/+0x88/+0x8C` and the slot byte at `+0x90`,
then installs vtable `0x0077D85C`. `Camera_CreateRegularShakeWork` (0x0059121C) allocates
exactly `0x94` = 148 bytes, which confirms the size. `Camera_RegularShake_Update` (0x005912C0)
counts `+0x80` down by the frame delta and calls the shake-node factory
`0x0046B40C(slot, x, y, z)` when it expires, reloading from `+0x7C`.

## Decisions I made (orchestrator unavailable)

1. **Kept the generated class names** even where they are provably wrong
   (`Camera_TargetDescriptor`, `Camera_MotionSet`), because `apply.py` rejects a class that is
   not in `structs.json`. The correction is in `summary` + `evidence`.
2. **Raised two sizes** (`Camera_Work` 244 → 288, `Camera_MotionSet` 1324 → 4716) because the
   destructor/snapshot code writes past the recorded "highest strong field". Both are backed
   by explicit array bounds in the disassembly, not by guesswork.
3. **Named the five `Camera_Work` vtable words `<role>Vtable`** instead of typing them as
   sub-objects: I could not find the constructor that installs them, so I do not know their
   class. Naming them `vtable` five times is impossible (duplicate-name check).
4. **`maybe_shakeParam0..2`** for `Camera_RegularShake +0x84/+0x88/+0x8C`: they are forwarded
   as the three float arguments of the shake-node factory, but the factory's own field
   meanings are not proven, so a precise name would be an invention.
5. **`maybe_upVectorX/Y/Z`** for `Camera_Field +0x1C..+0x24`: a constant 3-float vector copied
   from `0x007E7024` every frame. "Up axis" is the most plausible reading, not a proven one.

## Open problems / suggested follow-ups

1. **Type-name collision**: `CameraWork` is already used as a parameter type by the
   0x001Dxxxx camera work-list signatures (`Camera_UpdateWorkList`, `Camera_ApplyWorkEntries`,
   `maybe_Camera_UpdateTargetList`) for a *different* object. The generated
   `typedef struct CameraWork` will silently change the meaning of those signatures. A
   follow-up should either rename this class (e.g. `Camera_SnapshotWork`) or rename the
   0x001Dxxxx one.
2. **`Camera_TargetDescriptor` is a save-code record** — it belongs to the Save subsystem, not
   Camera. Suggest a follow-up task that renames it to `Save_CodeRecord` and moves it out of
   the Camera batch.
3. **`Camera_MotionSet` duplicates `Ui_CameraAnimWindow`** — the two class entries describe the
   same object. Suggest merging them.
4. **The object at `gameWork->ctx->f_80`** (the source of every `Camera_Work` snapshot) is not
   in `structs.json`. It has a target handle at `+0xB0` (resolved through the handle table at
   `0x007B80C0`), four candidate pointers at `+0xD0` (each with a node at `+0x26C`, `+0x2E0`,
   `+0x2F0`), a camera pointer at `+0x130` and a state machine at `+0x13C`. Finding its
   constructor would let the five `Camera_Work` publisher blocks be typed properly.
5. **`Camera_Field` shares the `Ui_MotionPath` layout** (`+0x91` active flag, `+0xA4..+0xB8`
   track handles). Either `Ui_MotionPath` should become the base class of `Camera_Field`, or
   the `Ui_MotionPath` name should be generalised (it is used by both UI and camera code).
6. **`Camera_RegularShake +0x50`** lies inside the 124-byte `Container_NameHash` base, so
   naming it here makes the struct flat instead of embedding the base. If the base's own
   batch names `+0x50`, the two answers should be reconciled.
