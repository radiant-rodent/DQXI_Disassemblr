# S_016 - Container classes and fields

**Task**: name the 15 classes and every field of `orchestration/types/batches/S_016.json`
(subsystem `Container`).
**Output**: `orchestration/types/out/S_016.json` - 15 classes, 176 fields, one entry per batch
offset, no duplicates.

## What I did

1. Read `README.md`, `orchestration/WORKER_RULES.md`, `orchestration/types/README.md` and the
   batch, then read `tools/typedb/apply.py` to learn exactly what the merge accepts (type
   whitelist, offset bounds, `maybe_` rule, how overlapping fields are emitted).
2. For every class I read the constructor first, then the update/draw/dtor methods, using the
   readable C in `decomp/readable/functions/` (resolved by address - the `readable` paths stored
   in the batch are stale `FUN_xxxx` names). Where the readable C was missing or ambiguous I read
   the disassembly from `asm/text/text_*.s` through `tools/fn.py`'s `asm_lines`.
3. I used `decomp/xref.json` (via a 20-line scratch helper) to find callers, which is how
   `Container_NodeList` was tied to `Field_SceneObjectCtor_vt23EC5C` and `Container_KeyedList` to
   `maybe_Ui_ListWindow_IsRowActivated`.
4. Wrote the answer in three chunks (`out/scratch/S_016/part{1,2,3}.json`), merged and checked
   offset coverage, then validated with `apply.py`'s own `merge_structs`/`emit_struct` **in
   memory** so nothing outside my owned file was written.

## Findings worth keeping

| Class | What it really is | Key evidence |
|---|---|---|
| `Container_KeyedList` | row-selection state of a UI list window | `rowArray` +0x3C, `currentIndex` +0x38, `pendingIndex` +0x39 (0xFF = none), `pendingSubIndex` +0x3A, `rowCount` +0x40; `CommitSelection` calls `maybe_Ui_ListWindow_IsRowActivated(self)` |
| `Container_NameHash` | FNV-1a name key | `hashSeed` +0x18 = `0x811C9DC5`, `hashValue` +0x54 recomputed by `uVar8 * 0x01000193 ^ c`, 32-byte name buffer at +0x5C..+0x78 |
| `Container_NamedMap` | two rb-tree + list maps keyed by `Container_NameHash` | `Insert` reads the record's +0x54/+0x5C..+0x78, i.e. the `Container_NameHash` layout |
| `Container_NodeList` | 0x4C-byte base sub-object of the field scene-object hierarchy | vtable `0x00782234`, allocator +4, two 0x8C-byte children, six 0x14-byte vtable-bearing sub-objects; caller `Field_SceneObjectCtor_vt23EC5C` calls it on `r2+0x4A3C` and continues at +0x4C |
| `Container_ByteBuffer` | `{void* base; u32 length;}` | `Append` = `memcpy(base + length, src, n)` |
| `Container_StringBuffer` | string builder with 7-byte SSO buffer at +0x11 | `data == self+0x11` while `len < 8` |

### Sizes corrected against the batch guess

* `Container_MultiList` 264 -> **540**. The ctor calls
  `std_ConstructArray(&self[0x104], 0x00106A10, 0x28, 7)`, so the object extends to
  `0x104 + 7*0x28 = 0x21C`.
* `Container_MaskedEntryList` 48 -> **56**. Four list heads 0xC bytes apart at
  `+8/+0x14/+0x20/+0x2C`.

Both are derived from constructor code, not from an allocation site, so they are strong but not
allocation-backed.

### Clusters that mix unrelated classes

`struct_db` clusters by offset overlap, so several of these "classes" are really two or three
different objects. I recorded the conflict in each class `evidence` and kept the fields
structural:

* `Container_MultiList` - ctor 0x00122124 / `ClearAll` 0x00451B74 vs. dtor 0x0055AD28 (which
  reads +0x1C as an rb-tree header and +0x2C as a byte flag).
* `Container_List` - ctor 0x00576A80 stores vtable `0x007826D8`; the batch's vtable is
  `0x00782704`, a sibling class.
* `Container_IntrusiveList` - three different heads (+4, +0xC..+0x14, +0x54..+0x58); the ctor
  0x004487F4 actually writes +0x11C..+0x134, not +0xB8/+0xC4.
* `Container_Node` - four different node destructors with different vtables.
* `Container_RingBuffer` - an index walker, a byte ring and a 0x1C-byte-entry heap at +0x344.

## Deliberately left unknown

28 offsets carry `unknown_XX` with confidence 0.0: they are only zeroed by a constructor or read
once with no derivable meaning. One deserves a note: `Container_IntrusiveList+0x300` - the only
recorded access is `Pack_ReleaseHandle(param_1+0xc0)`, which does not touch +0x300, so the offset
(and therefore the 772-byte size) is probably a mis-attributed access.

`Container_IntrusiveNode` has a single field at +0x3430 and its only method is really
`Ui_Object_SelectEmbeddedNode`, so the 13364-byte size is a mistyped-self artifact. I kept the
batch size (the merge recomputes it from the field anyway) and flagged it in the summary and
evidence.

## Verification

* `apply.py`'s `merge_structs` + `emit_struct` run in memory on `orchestration/types/out/S_016.json`:
  **15 classes, 176 fields, 0 errors, 0 warnings**; all 15 structs emit cleanly
  (preview kept at `out/scratch/S_016/structs_preview.h`).
* Offset coverage check: every offset in the batch appears exactly once, no duplicate field names,
  every field with confidence < 0.5 carries the `maybe_`/`unknown_` prefix.
* Strict UTF-8 decode of the output: OK, 0 non-ASCII bytes.
* Full `python tests/run_all.py` **not run** - naming/typing batches are exempt per
  `WORKER_RULES.md` rule 5, and the task says a JSON syntax check is what is required.
* `python tools/verify_project.py` (run anyway, read-only apart from its own
  `audit/PROJECT_VERIFICATION.json`): **OVERALL: FAIL**, with exactly two failing checks, both
  WSL path artifacts and both unrelated to this batch:
  - `patched ROM exists: build\DQXI_patched.3ds` - the file *does* exist (4 GB, 2026-10-25); the
    check does `ROOT / r["rom"]` with a Windows backslash path, which does not resolve under WSL.
  - `model texture manifest: no output` - the subprocess it shells out to produced nothing under
    WSL.
  Everything else passes: `code.bin` size and hash, all seven asset groups, 18787 native entry
  points, 18749 decompiled, 1196 decoded maps, editor binary, and the four C source replacements.

## Not verified

* No emulator run, no runtime check that any of these layouts is exercised as described.
* The two size corrections are constructor-derived, not allocation-derived.
* `Container_NamedMap+0x00`/`+0x04` may belong to the `ContainerTreePos` out-parameter of
  `FindNodeA`/`FindNodeB` rather than to the map; I named them `maybe_treePosNode` /
  `maybe_treePosParent` at 0.25 and said so in the evidence.

## Suggested follow-up

1. A `V_` batch over the Container functions to rename the helpers I had to cite by address:
   `func_001235A4` (list splice/insert), `func_00109600`, `func_0011CFAC` (ring-buffer copy),
   `func_0021F8B8` (handle release), `func_0010EC00`/`func_00115358`/`func_00115390`
   (rb-tree successor/erase helpers).
2. Split the mixed clusters: `Container_MultiList`, `Container_List`, `Container_IntrusiveList`,
   `Container_Node` and `Container_RingBuffer` each need 2-3 separate classes. `struct_db.py`
   could refuse to merge functions whose vtable stores disagree.
3. `Container_IntrusiveNode` should be dropped or re-clustered - it is a `Ui_Object` with an
   embedded node, not a 13 KB class.
4. `Container_NodeList` deserves a proper name (`Field_SceneObject_Base` or similar) once the
   field scene-object hierarchy is mapped; the generated name is a layout description.
