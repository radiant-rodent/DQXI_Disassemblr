# S_020 - Data subsystem classes and fields

**Task**: name the 1 class and every field of `orchestration/types/batches/S_020.json`
(subsystem `Data`).
**Output**: `orchestration/types/out/S_020.json` - 1 class, 2 fields, one entry per batch offset,
no duplicates.

## Result in one line

`Data_Record` is **not an object**. Its two "methods" are one `std::sort` template instantiation
over a `u16` id array, and its two "fields" are array element accesses. The JSON says so in the
class `summary` (which lands verbatim in the `structs.h` comment) and in both field `evidence`
strings.

## What I did

1. Read `README.md`, `orchestration/WORKER_RULES.md`, `orchestration/types/README.md`, the batch,
   and `tools/typedb/apply.py` (the merge rules: type whitelist, offset bounds, `maybe_` rule,
   `emit_struct` padding, 160-char class comment / 400-char evidence truncation).
2. Read the raw Ghidra C (`decomp/ghidra/functions/FUN_0071D06C_0071d06c.c`,
   `FUN_007231A0_007231a0.c`) and the readable C, then the disassembly in
   `asm/text/text_00700048.s` for both functions and for the comparator.
3. Traced the real callers from the disassembly (not from `decomp/xref.json`, which is wrong here,
   see below) and read `Ui_SmithMenu_BuildItemListBySlot` (0x004F27A8) to see what array is sorted.
4. Rendered the merged struct in memory with `apply.py`'s own `merge_structs` + `emit_struct` so
   nothing outside my owned file was written.

### The two batch offsets

* **+0x00** - `*param_1 = uVar1;` in the insertion-sort tail. `param_1` is `undefined2*` (`u16*`),
  so this is element 0 of the sorted array. Named `maybe_firstSortedId` (`u16`, conf 0.20).
* **+0x40** - `param_1 + 0x10` is **element 16**, i.e. byte `+0x20`, the libstdc++
  `_S_threshold` block boundary in `__final_insertion_sort` (`if (last-first < 0x21) ... else
  insertion_sort(first, first+16)`). `struct_db` multiplied the element index by 4, which is where
  the `0x40` offset and the 68-byte class size come from. Named `unknown_thresholdBound`
  (`u16`, conf 0.00).

## Decisions

* **Kept the generated class name** `Data_Record` / `DataRecord`. `apply.py` resolves classes
  against `structs.json`, so a rename would be rejected as "class is not in structs.json
  evidence"; the correction lives in `summary` + `evidence` (same approach as S_016's
  `Container_IntrusiveNode`).
* **Kept `size: 68`** from the batch instead of inventing a size, and said in the summary that the
  size is an artifact. Setting it to 2 would not change the emitted struct (the merge takes
  `max(evidence size, highest field end)`).
* **Emitted both offsets** as the task requires, with honest names and confidence 0.20 / 0.00, and
  with the width corrected to `u16` (the batch guessed `u32` from a 4-byte element assumption).
* **Did not** write `include/dqxi/*.h` - `apply.py --validate` only, never `--merge`.

## Not verified

* No emulator/runtime check (naming batch).
* The **identity of the `dm->f_3F4` table** is not proven. I proved only that `func_0063E998`
  reads it (40-byte rows, `id < 0x24E`, `u16` key at `+0x26`) and that the smith menu uses it to
  resolve item-variant ids. It is *not* the item table (`Item_LookupRecord` 0x0061BD4C is a
  different table, and the item sort-key getter 0x0063D96C reads `dm->f_0C`, not `dm->f_3F4`).
* Whether the `u16` key at `+0x26` is a display order, a category or something else is unknown.

## Open problems / suggested follow-ups

1. **`decomp/xref.json` has a false edge**: it lists `0x007231A0` as a callee of
   `Casino_Poker_EvaluateHand` (0x00416D10), but no `bl`/`blx` in that function targets
   `0x7231A0` or `0x723198` (it calls `#0x723430`, the guard of `std_Sort16BitRecords`, and
   `#0x72366c`). Conversely the xref **misses** the four real callers, because they call the
   guard address `0x723198`, which is not a known function start. Worth fixing in the xref
   builder: resolve a call target to the function that *contains* it, not to the next start.
2. **Rename the two functions** in a naming batch: `Data_Record_SortU16` ->
   `std_sort_u16_variantId` (or `std_sort_u16_itemVariant`) and `Data_Record_IntrosortU16` ->
   `std_introsort_u16_variantId`, matching the existing `std_introsort_u16_itemName` /
   `std_introsort_u16_monster` family. The `Data_Record_` prefix is what created this phantom
   class in `struct_db.py`.
3. **Name `func_0063E998`** (item-variant record lookup, `dm->f_3F4`) and the 40-byte record it
   returns (`+0x00` item id, `+0x0C` equip slot/type byte, `+0x26` `u16` sort key). That record is
   a real struct and is currently unnamed.
4. **Drop `DataRecord` from the generated headers** at merge time, or teach `struct_db.py` to skip
   classes whose only "fields" are `*param_1 = ...` / `param_1 + N` array accesses. `Data_Record`
   and `Data_PaddingArtifact` are the only two `Data` classes and neither is a real object.
