# S_022 — Event subsystem: 13 classes, every field named

## What I did

Named all 13 classes and all 86 field offsets of `orchestration/types/batches/S_022.json`
(subsystem `Event`) and wrote `orchestration/types/out/S_022.json` with **13 classes / 89 fields**:
the 86 batch offsets (each exactly once) plus 3 offsets I added because the batch dropped them
(`Event_TriggerObject` vtable at 0x00, `Event_CameraZoomTask` +0x04 and +0x08).

Method: read the readable C of every recovered method of every class (66 functions), starting with
the constructors (vtable store, base-ctor call, initialised fields), then the update/draw methods,
then cross-checked each field's width and pointed-to class against `orchestration/types/structs.json`
and the callers of the constructors.

## Findings worth carrying forward

1. **`Event_Camera` is not a camera.** `0x002B5994` (`Event_Actor_SetPositionAndFacing`) copies
   `self+0x9C/+0xA0/+0xA4` into the field actor's `f_9c/f_a0/f_a4` and derives the facing vector
   from `(x,y,z,w) = (+0x8C,+0x90,+0x94,+0x98)` with the textbook
   `2(xz+wy), 2(wz-xy), 1-2(x²+y²)` formula. The class is a transform record. All three old
   `Event_Camera_*` names were placeholders (R2_005 / R2_006 / R2_010 re-identified them).
2. **Five of the "Event" classes are actor actions, not events.** `Event_SkullRun`, `Event_Climb`,
   `Event_Gimmick`, `Event_Rura` and `Event_BeeRise` are constructed from
   `Actor_StartBehaviourState` (0x00230EC4), `Actor_StartStateOne` (0x002338DC),
   `Actor_CreateActionTable` (0x0022AF9C) and `Actor_CreateTaskChainB` (0x00234BBC), all through
   `Action_CtorBase` (0x00294C34) / `Actor_Action_InitDescriptor` (0x00294BD4). Their `+0x28` is the
   `Field_Actor*` they drive; their `+0x24` is the ctor's third argument, `actor[0x18]` — the actor's
   keyed action list (`Container_KeyedList*`), whose `+0x44` is read as the normalised progress.
   `Event_Climb` and `Actor_Action_Climb` are the same class under two names.
3. **`Event_ActorModels` size 4768 is wrong.** `Field_ObjectFactory_Actor` (0x006C0B64) allocates
   `0x6E40` bytes and calls `Event_ActorModels_Ctor` (0x004B8810), which runs
   `std_ConstructArray(self+0x129C, 0x0059F408, 0x2DC8, 2)` — two 0x2DC8-byte model slots, so
   `0x129C + 0x5B90 = 0x6E2C` fits. I set size 28224. The slot arrays are exact and self-checking:
   `modelSlots[16]@0x0C`, `attachSlots[8]@0x4C`, `partSlots[3]@0x6C`, `spriteSlots[3]@0x78` — each
   array ends exactly where the next field begins.
4. **`Event_Rura` size 68 is wrong.** The ctor (0x004F1CBC) copies a 16-byte inline SSO string
   (`"Rura_Start"`, strlen 9, limit 0xF) into `+0x40..+0x4F`, so the object is at least 0x50 bytes.
   I set size 80 and `char clipName[16]`.
5. **`Event_SubObject` is not event code.** Its only method 0x00256A58 is now
   `Ui_SceneFlow_ReleaseSubObject` (R_035): `Ui_ScreenEffect_ReleaseGrainAndVignette(self+0xC)`,
   `Ui_Window_ReleaseLists(self)`, `Pack_ReleaseHandleEntry(self+0x2C)`/`(self+0x30)`. I kept the
   generated class name (task rule) and said so in the summary and evidence.
6. **Phantom offsets.** `struct_db.py` sometimes attributes the *source* pointer's index
   (`puVar3[1]`) or a vtable slot (`(**(code**)(*self+0x84))`) to the class. Six batch offsets are
   such artefacts: `Event_Actor +0x210`, `Event_ActorModels +0x04` and `+0x120`,
   `Event_Climb +0x04`/`+0x08`, `Event_Gimmick +0x04`. They are emitted as `unknown_*` with
   confidence 0.0 and the reason in `evidence`, as the task requires.

## Open problems / not verified

- **Not verified in the emulator.** No runtime check that the named fields behave as described; this
  is a static naming batch.
- **`Event_Actor` is the weakest class (0.40).** Its two methods are script-method-table entries
  (0x0075F4B8) that take the object implicitly; the six words at `+0x304..+0x318` are a verbatim copy
  of the global default block at `0x007261B4+0x48..0x5C` and I could not determine what the six
  words mean, so they stay `maybe_defaultParam0..5` (0.45).
- **`Event_Handler` (0.40)** rests on two handler-table entries only. `+0xD8C` is a polymorphic
  sub-object with a state query (vtable +0x14) and a stop call (vtable +0x10); I could not identify
  its class, so it is `maybe_motionObject`.
- **`Event_ActorModels +0xA4`** is a byte passed to a slot vtable call (`+0x68`); its meaning is not
  visible, so it is `maybe_slotFlags` (0.40).
- **`Event_Gimmick +0x44/+0x45`** are bytes 8 and 9 of the 10-byte record returned by 0x003DD068
  (currently named `Ui_DragScroll_Begin`, which is a misnomer — `Actor_Action_ReadParams` uses the
  same call to load "state, timer, ids"). I named them `maybe_paramIdA` / `maybe_paramResult`.
- **`Event_Packet +0x44` / `+0x54`** are only the *first* component of two 16-byte quaternions; the
  batch has no offsets for the other three components, so the struct shows 12-byte padding after
  each. The merge will not name them until a batch covers them.
- **`Event_SubObject +0x2C/+0x30`** are typed `u32` because `Pack_ReleaseHandleEntry` takes the
  address of a one-word handle; if a `Pack_Handle` class is recovered later these should point at it.
