## What the batch really is (important for the merge)

`tools/typedb/struct_db.py` groups classes by **function-name prefix**, not by a verified layout.
For this batch that matters a lot:

1. **`Field_Object` is a name-prefix family, not one class.** There are 57 `Field_Object_*`
   functions in `decomp/readable/functions/`; the batch lists 24. Several of them receive an
   *interior* pointer, proven by the ARM listing:
   - `Field_Object_SetMode` (0x0066E370): `sub r4, r0, #0x258` — `self` is object+0x258.
   - `Field_Object_OnEvent` (0x0066E3AC): `sub r5, r0, #0x258`, then `ldr r0,[r0,#-0x20c]`.
   - `maybe_Field_Object_BindModelTransform` (0x0066D5A0): `self - 0x1330`.
   - `Field_Object_BindModelTransformB/C/D` (0x0066E0D8/0x0066E18C/0x0066E224): `self - 0xDDC0`.
   So a handful of the 84 offsets come from a different `self` base. I named the ones the
   base-class functions prove (dtor 0x00335DAC, ActivateChildren 0x003359C4, ReleaseChildList
   0x00335C24, GetWorldPosition 0x005E84C8, InitFromDescriptor 0x004D7154) and marked the rest
   `unknown_*` with the reason. The class summary says this explicitly.
2. **`Field_ObjectSprite_AddHandleToSlot` (0x002F22C8) and `Field_Object_DisableSceneEntry`
   (0x002F21D8) belong to `Field_ObjectSprite`** (S_025), not to `Field_Object`: they use the
   8-group × 8-handle slot array at +0x38 (0x100 bytes) with the per-group counts at +0x1D8
   (8 × u32, ending exactly at the child-list sentinel +0x1F8). Their offsets 0x24/0x28/0x34/0x38
   are still named here because the batch asks for them.
3. **Vtable-slot misreads.** `struct_db` parses `(**(code**)(*param_1 + 0xNN))(...)` as a field at
   `0xNN`. That produced 12 false fields, all marked `unknown_vtableSlotNN` at confidence 0.0:
   Field_Object 0xF0/0x710/0x720, Field_CollisionObject 0x2C0/0x2D0/0x2E0,
   Field_SpawnObject 0x210, FieldParty_TalkPanel 0xD0/0xF0/0x120.
4. **`Field_SubObject` is not a field class at all.** Its only function, 0x00626360, is
   `Ui_Core_GetOrCreateChild` in the current tree; the single offset is the UI core's cached
   child pointer at +0x10. Class confidence 0.2.
5. **`Field_TextObject` is not a text object.** Its only function, 0x00197FB8, is
   `maybe_Field_SceneObject_Ctor` — a 0x37C-byte field scene object built by
   `Field_InitSceneObjects`. Class confidence 0.3, summary says so.

## Open problems / not verified

- **`Field_Object` is not one class.** The 84 offsets are a union over several real classes
  (`Field_ObjectSprite`, `Field_SceneObject`, `Field_Actor`). 17 offsets are `unknown_*`; the
  placement block 0x68..0x94 is named `maybe_position*`/`maybe_rotation*`/`maybe_scale*` at 0.30
  from `Field_SpawnObject_ApplyRecord`'s doc ("position, rotation, scale, colour") and
  `Field_Object_InitFromDescriptor`'s 12-word copy — the block boundaries are not proven
  (SpawnObject writes 4-word blocks at 0x68/0x7C/0x90, InitFromDescriptor copies 12 contiguous
  words).
- **0x204..0x21C conflict.** `Field_Object_ActivateChildren` indexes 0x204 as an inline array of
  child pointers with count at 0x224, while `Field_Object_DeactivateChildren` reads a *byte*
  latch at 0x220 (`ldrb`/`strb`) and `Field_Object_ReleaseChildList` zeroes words 0x204..0x220.
  Both cannot be true of one layout; I named 0x204 `maybe_childArray`, 0x208..0x21C
  `unknown_childSlot1..6` and 0x220 `maybe_childrenDeactivated` (u8, 0.40) and said so in the
  evidence.
- **Field_CollisionObject 0x23C..0x250** is a 3-word block copied from another 3-word block, both
  seeded from the global 0x007E7000. `maybe_boundsMin*`/`maybe_boundsMax*` at 0.30 is a guess at
  the role; the copy direction is proven, the meaning is not.
- **Field_RenderObject** has no readable C (0x003E7CF8 is missing from
  `decomp/readable/functions/`); I read the ARM listing in `asm/text/text_003C0048.s` directly.
  All five offsets are relative to the +0x1F4 sub-object of a 0x208-byte object, not to a
  standalone 20-byte class.
- **Field_GameObject 0x1384/0x1390/0x1394** are only ever cleared by the ctor; no reader found.
- **Field_TextObject 0xC/0x14/0x20/0x24** are only ever cleared by the ctor; no reader found.
- No emulator or runtime check was done (naming batch).

## Suggested follow-ups

1. `S0_types_plan` / `struct_db.py`: stop grouping by name prefix alone — at minimum, drop
   functions whose `self` is an interior pointer (`sub rN, r0, #imm` in the prologue) from the
   class's field union, and stop parsing `(**(code**)(*param_1 + 0xNN))` as a field access.
   That alone would remove 12 false fields and ~10 bogus offsets from this batch.
2. Split `Field_Object` into the real classes: `Field_ObjectSprite` (slot array +0x38, counts
   +0x1D8, scene entry +0x28/+0x34), `Field_SceneObject` (placement block +0x68, position +0x9C,
   child list +0x1F8), `Field_Actor` (actor +0xF24, anim track +0x594).
3. `Field_Object_GetKind0Record` (0x00642A28) returns a `FieldPartRecord` from the array at
   `db+0xA9C` (count `db+0xAA0`); that record's 12-word head is what `Field_Object` copies to
   +0x68. A `FieldPartRecord` class would let the placement block be named properly.
4. `Field_TextObject` should be renamed (its only function is a scene-object ctor) and
   `Field_SubObject` should be dropped or moved to the Ui subsystem.
