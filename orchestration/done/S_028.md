## What each class really is

### `Field_Effect` — a 2D effect-handle list, not an effect instance
`0x0018F404` (`Field_Effect_SetAlphaAll`) and `0x0018F5E8` (`Field_Effect_StopAll`) both run
`for (i = 0; i < self->f_18; i++)` over 8-byte handle entries at `self + 8 + i*8`
(asm `0x0018F434 add r0,r4,r6,lsl #3` / `0x0018F438 ldr r0,[r0,#8]`). So:

| Offset | Name | Type | Conf | Why |
|---|---|---|---|---|
| +0x18 | `handleCount` | `u32` | 0.85 | loop bound of the handle array |
| +0x1C | `alpha` | `u32` | 0.80 | set to the alpha argument (`& 0xFF` applied per effect), to 0 by StopAll, to 1 by EnableAll; compared first so a repeat call is a no-op |
| +0x50 | `effectDesc` | `Field_EffectDesc*` | 0.70 | `0x0019EDDC` / `0x0019FF40` call `Field_EffectDesc_Build(self->f_50)`; `0x001D6958` builds a 0x70-byte descriptor |

The R2_002 pass named the same layout `Ui_EffectHandleList_EnableAll` (`0x0018F570`) /
`Ui_EffectHandleList_ReleaseAll` (`0x0018F374`), and their callers pass the **message window
itself** (asm `0x00615B70 mov r0,r4; bl #0x18f570`), so this object is the window's first base
sub-object. The three `return 1` stubs in the batch (`0x0019EE38`, `0x0019EF54`, `0x0019F8F4`)
are not this class's fields — they are effect-instance vtable slots grouped in by address.

### `Field_NpcManager` — actually the `Field_Object` base class
The generated name is not supported by anything. vtable `0x00764A38` has
`Field_Object_DtorBase` (`0x00335DAC`) in slot 1, the batch's `0x00335D28` in slot 2 and
`Field_Object_ReleaseChildList` (`0x00335C24`) in slot 4; the ctor at `0x00335CA8` installs
`0x00764A38` and is itself called by `Actor2D_AnimNodeCtor` (asm `0x0028E64C bl #0x335ca8`).
The three known fields are the embedded head of the intrusive child list:

because the batch generated it and the project already uses it in signatures.

### `Field_DragController` — touch-drag target that walks the player actor to itself
The batch's base `Actor_HandleRef` is wrong: `Actor_HandleRef_Ctor` is called on `self+0x298`,
i.e. a member sub-object. The real base is `Actor2D_AnimNode`: the ctor `0x002B4854` calls
`0x0028E630` (the 4-byte `ldr ip,[pc,#0x74]` prologue of `Actor2D_AnimNodeCtor`) and the dtor
`0x002B48C4` restores `0x0075D55C`, whose slot 2 is `Actor2D_AnimNode_DeletingDtor`.

| Offset | Name | Type | Conf | Why |
|---|---|---|---|---|
| +0x00 | `vtable` | `void*` | 0.95 | `0x0075F158`; slots 9/31/32 are `0x002B42AC` / OnEvent / Update |
| +0x78 | `posX` | `s32` | 0.70 | own X; `f_2E4 = f_78 - actor->f_78`, passed as action-0x0B target X; `ldrd r0,r1,[r4,#0x78]` |
| +0x7C | `posY` | `s32` | 0.70 | own Y, same evidence |
| +0x22C | `vtableSecondary` | `void*` | 0.70 | ctor stores `vtable+0x98`; the base ctor does the same for every `Actor2D_AnimNode` |
| +0x24C | `actorHandleRef` | `Actor_HandleRef` | 0.55 | base ctor calls `Actor_HandleRef_Ctor(obj+0x24C)`, then sets +0x294=0xFFFF, +0x296=0 |
| +0x297 | `dragState` | `u8` | 0.85 | 0 idle / 1 dragging / 2 finishing |
| +0x298 | `maybe_dragHandleRef` | `Actor_HandleRef` | 0.45 | ctor calls `Actor_HandleRef_Ctor(self+0x298)`; its event branch arms the drag |
| +0x2E0 | `targetCoordRecord` | `void*` | 0.50 | rect record `s16 x@0, y@2, w@0x10, h@0x12` + `u32@8`, `u32@0x14`, `u8@0x17`; name aligned with S_025 |
| +0x2E4 | `dragDeltaX` | `s32` | 0.80 | remaining X distance; `sign*(|d|-1)` per frame, compared with the zero pair at `0x007BE2D4` |
| +0x2E8 | `dragDeltaY` | `s32` | 0.80 | remaining Y distance, same |

Behaviour (from `0x002B432C` Update, `0x002B4750` OnEvent, `0x002B42AC` slot 9): on the +0x298
event it stores `f_2E4 = f_78 - actor->f_78`, `f_2E8 = f_7C - actor->f_7C` and sets state 1;
each frame it moves the player actor (`work+8 -> +0x54 -> +0x20`) one unit toward itself and
decrements the deltas; when both reach 0 it sets state 2 and fires
`Event_OnTriggerCommand(work+0x6C, 0x15)`; in state 2 slot 9 computes the direction to the
target rect corner `(x+w, y+h)` and plays the actor's facing animation through
`Field_SceneNode_PlayAnimation` (`0x005F36E0`). `Field_Gadget` (`0x003A25D0` ctor,
`0x003A2018` UpdateDrag) is a template copy with the same +0x297/+0x298 layout and
+0x2F0/+0x2F4 instead of +0x2E4/+0x2E8.
