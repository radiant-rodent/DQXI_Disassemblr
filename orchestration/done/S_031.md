## Decisions I made (and why)

* **`base` kept as `Ui_Object`.** The batch's `bases_seen` is
  `{Ui_Object: 24, Fs_ResourceSet: 3, Battle_Effect: 1}` — those are the
  *embedded sub-object* constructors the master ctor chains, not a real base
  class: the gimmick has its own vtable at +0 and its own fields from +4 on, and
  `Ui_Object` is 5016 bytes while this object has fields at 0. `apply.py` only
  embeds a base when no derived field lies inside it, so it will emit a flat
  struct with an inheritance comment. I recorded the reasoning in the class
  `evidence` rather than silently changing the generated value.
* **`type` = `FieldGimmick`** (class name without underscores), matching 308 of
  the 321 existing S_ entries.
* **Nine byte fields declared `size: 1`, not the batch's 4.** The batch reports
  width 4 for `*(bool*)` / `*(undefined1*)` accesses at 0x080, 0x09D, 0x0D9,
  0x0E5, 0x1D0, 0x1D1, 0x1D2, 0xAD0, 0x23B2. Declaring 4 would make the emitted
  struct lie about the field, so I used the real 1-byte width. This is the only
  deviation from the batch's `size` values.
* **73 `unknown_<hex>` fields at confidence 0.0.** These are the interior of the
  embedded sub-objects (0x41C..0x447, 0x5F4..0x61B, 0xAD1..0xAD6,
  0x10FC..0x1124, 0x1304..0x1320, 0x1438..0x1450, 0x1514..0x1548, 0x1FE0/0x1FE4).
  Each one is written from a register or a stack local in a single initialiser
  and has no reader anywhere in the recovered code, so there is no honest name
  for it. The `evidence` string quotes the raw access so a later worker can pick
  it up. I did **not** invent purposes to fill the slots.
* **Sub-object block starts named `embeddedObject<hex>`** where the first word
  is `*(int*)(self+off) = self` (a back-pointer to the gimmick). That pattern
  occurs at 0x2DC, 0x330, 0x40C, 0x5E4, 0x10EC, 0x10F8, 0x1114, 0x1244, 0x125C,
  0x12D4, 0x12E8, 0x12FC, 0x1434, 0x1510, 0x1528, 0x1540 — 16 embedded objects.
* **`maybe_gold` (+0x2E8) is only 0.4.** The only support is
  `docs/GIMMICK_DECOMP.md` ("the accessor at 0x64E158 returns a float / +0x2E8
  (gold-like field)"), which is a note about a *different* accessor's object, not
  about this class's own code. Flagged as `maybe_`.

## Open problems / not verified

* **The class is a merge of two objects.** `Field_Gimmick` (this batch, 280
  fields, 48 vtables) contains the whole `Field_UiGimmick` object (S_037, vtable
  0x00784174, size 0x1FE0) plus fields at 0x1FE0/0x1FE4/0x23B0..0x23B2 that lie
  *beyond* `Field_UiGimmick`'s size. Either the real object is 0x23B8 bytes and
  S_037 under-sized it, or `struct_db` merged a second class into this one. I
  could not settle it from the ctor alone: the ctor returns `base` and the dtor
  at 0x005E4D04 writes vtable 0x00784174 at +0, which points at the 0x1FE0
  reading. **A follow-up should check the allocation size** (the `new`/`Mem_Alloc`
  call site for the gimmick) to decide whether 9144 or 8160 is right.
* **The 73 `unknown_*` fields are genuinely unnamed**, not merely low
  confidence. Naming them needs the sub-object constructors' *readers*, which
  are not in this batch's function list.
* **`Field_Gimmick_BuildMessageText` (0x005E5C40), `Field_Gimmick_BuildPathTable`
  (0x005E092C) and `Field_Gimmick_BuildRowListFromConfig` (0x005D14A0) look
  misassigned** to this class: their bodies are a generic message formatter, a
  generic path builder and a generic row-list builder, and none of them touches
  a `Field_Gimmick` field. Their evidence was therefore not used for any name.
* **`Field_Gimmick_ClampObjectPosition`'s `gimmick->f_c0`** is a pointer to an
  object with f_54/f_58/f_5c/f_60 (I named it `sceneObjectRef`,
  `Field_SceneObject*`, 0.5), but the batch also carries byte writes at 0xC0
  from some other function. I trusted the direct call site; the conflict is
  noted here rather than resolved.
* **`maybe_gold` (+0x2E8)** rests only on `docs/GIMMICK_DECOMP.md` and should be
  confirmed against the accessor at 0x64E158 before a modder relies on it.
