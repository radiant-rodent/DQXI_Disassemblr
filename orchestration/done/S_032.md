## Field_LevelWork — what it is, and why most names are structural

`Field_Level_InitSpriteSets` (0x00610890) builds the level record and then calls, in order:

```
Gfx_SceneSpriteSubSet_Create(&self->f_26)   -> level+0x98
Gfx_SceneSpriteSet_Create(iVar2 + 0x7c)     -> level+0x114
func_00185688(iVar2 + 0x654)                -> level+0x768
Field_LevelWork_InitBlockB(iVar2 + 0x20)    -> level+0x788   <-- this class
Field_LevelWork_InitBlockA(iVar2 + 0x553c)  -> level+0x5CC4  <-- a different block
func_001CF8A8(iVar2 + 0x4d68)               -> level+0xAA2C
```

So **Field_LevelWork sits at `Field_Level+0x788`**, not at `+0x20` as the readable-C doc comment
for `Field_LevelWork_InitBlockB` claims (that comment reads the `+0x20` of the *previous* call).
`Field_Level`'s own field list agrees: it has a field at `0x788` (`FUN_001af6a0(param_1+0x788,0)`),
one at `0x5cc4` and one at `0xaa2c`.

The initialiser (0x001B3CEC) does nothing but clear the block. Its whole body is 25 repetitions of

```
block[0x12] = block + 2;   /* begin pointer -> inline storage */
block[0x13] = 0;           /* count = 0 */
block[2..0x11] = 0;        /* the storage itself */
FUN_00116AE0(block + 0x1a, 0x80);   /* memset of the bigger storages */
```

i.e. `{ u32 storage[N]; u32* begin; u32 count; }` groups. No reader of any of these fields exists
in the recovered code (the block is only ever reached through the level pointer, so struct_db
attributed every access to `Field_Level`, which has no fields in `0x788..0x5CC4`). I therefore
named the **structure** and not a purpose:

* `maybe_arrayNBegin` (`void*`, 0.45) — points at the inline storage,
* `maybe_arrayNCount` (`u32`, 0.45),
* `maybe_arrayNStorageK` (`u32`, 0.45) — word *k* of that storage,
* `unknown_word0` (`u32`, 0.0) — cleared, no reader,
* `maybe_nestedObject` (`void*`, 0.4) at `+0x734` — `FUN_006F0C90(block+0x1CD)` returns the
  sub-object that starts here and the initialiser keeps memsetting past the 1848-byte mark, so
  1848 is a lower bound on the real size.

The 25 groups (storage start / words / begin / count) are listed in `out/scratch/S_032/gen.py`.

**Batch defect worth fixing upstream:** the batch lists *both* `0x001B3CEC` (block at level+0x788)
and `0x001AB6F4` (block at level+0x5CC4, 0x3FC4 bytes) as constructors of this class. Only three
offsets (`0x328`, `0x32C`, `0x330`) come exclusively from InitBlockA; they happen to fall inside
group 9's memset region here, so I named them as group-9 storage. A future `struct_db` run should
not merge two initialisers whose blocks are at different level offsets.

## What is NOT verified / open problems

1. **The cluster mixes at least three object layouts.** `Field_Object2D`'s 118 offsets come from
   functions that disagree:
   * `+0x2C8` is a state byte in `RunStateSequence` but a float x in `PlaceEffectInFrontOfCamera`;
   * `+0x22C` is a secondary vtable (`piVar2[0x8b] = vtable+0x98`) in `CtorSprite` but a rectangle
     top in `UpdateSceneNodes`;
   * `+0x16C` is the base of an 8-byte-stride node array (`ReleaseSceneEntry`) but also the base of
     a 0x18-byte-stride array (`ResetAttachedNodes`, `+0x178+i*0x18`);
   * `+0x298..+0x33C` is a 0x84-byte parameter block copied by `Field_Object2D_InitSpriteActor`,
     which is called from `Field_SceneObject_InitSpriteActor` — i.e. those fields belong to
     **Field_SceneObject**, not to this class.
   I named each offset from its strongest single piece of evidence and recorded the conflict in the
   field's `evidence` string, but a modder reading the generated header should not trust
   `+0x298..+0x33C` as Field_Object2D members.
2. **The generated base `Anim_Instance` is doubtful.** `Anim_Instance` is 768 bytes and its
   `+0x44`/`+0x5C` are a pointer/count, while this class has a scene handle at `+0x5C` and nothing
   at `+0x44`. The object *embeds* a `Field_ObjectSprite` at `+0x70` and an `Anim_Instance*` at
   `+0xB8`, which is composition, not inheritance. `apply.py` keeps the evidence base when the
   worker passes `null`, so I left `Anim_Instance` in place and documented the doubt in the class
   `evidence` instead of silently changing it.
3. **`Field_LevelWork`'s 250 structural names carry no purpose.** They are honest about the layout
   and useless for gameplay work. Recovering the purposes needs a caller: nothing in the recovered
   code reads the block except its initialiser.
4. **`+0x1F4` is missing from the batch.** `UpdateSceneNodes` compares `*(u16*)(self+0x1F4)` with
   the parent's display mode (`f_38->f_ac`) — a real field that `struct_db` did not emit. It will
   become padding in the merged header.
5. **Not verified:** I did not run the full test suite (naming batch, rule 5) and I did not build
   the generated header (`apply.py --merge`), so I have not seen the C struct this produces.

## Suggested follow-up tasks

* **S_032b** — split `Field_Object2D` by vtable: the 0x0040Bxxx–0x0040Dxxx functions are one class,
  the 0x0041Exxx/0x004D7xxx ones (`InitSpriteActor`, `InitModel`, `InitModelVariant`, `DtorBase`,
  `UpdateSpriteBounds`, `SetSpriteHandle`, `NotifySceneCommand*`) are `Field_SceneObject`, and the
  0x00265878/0x0031F968/0x00483F74 ctors are two further variants. `struct_db` should cluster by
  vtable address, not by "first parameter looks like self".
* **T_0xx** — teach `struct_db` to ignore `(*(*self+0xNN))(...)` vtable calls when collecting field
  accesses; it produced four phantom fields in this batch alone.
* **T_0xy** — do not merge two initialisers into one class when their blocks sit at different
  offsets of the same parent (the `0x001AB6F4` / `0x001B3CEC` case).
* **N_xxx** — `Field_LevelWork_InitBlockB`'s doc comment says the block is at `level+0x20`; it is at
  `level+0x788`. Worth correcting in the readable tree.
