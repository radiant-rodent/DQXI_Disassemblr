# S_041 - Struct & Field Naming (subsystem: Fs)

## Summary
Task **S_041** named all 9 classes and all 29 field offsets assigned in
`orchestration/types/batches/S_041.json` (subsystem: **Fs**). Every batch offset appears exactly
once, every field carries an explicit C type, a confidence and an evidence string, and a local run
of `tools/typedb/apply.py`'s `merge_structs()` over the output reports **0 issues**.

## Analysis & Evidence Highlights

1. **`Fs_Cache` (size 32, 5 fields)** - the batch merged four different pool variants that share one
   header. All five constructors store a literal vtable at `+0x00`:
   `0x0078230C` (handle array, `0x00108574`), `0x0078233C` (pass-through, inlined in
   `Fs_CacheSet_Initialize`), `0x0078236C` (0x58-byte pool, `0x00108624`/`0x001086CC`) and
   `0x0078239C` (0x54-byte pool, `0x00108750`/`0x001087F4`). Every one is allocated with
   `Mem_AllocAligned_2(0x20, ...)` inside `Fs_CacheSet_Initialize` (`0x00103724`), which registers
   the pools by name (`sound`, `cmn_cache`, `weapon`, `PL_256`, `PL_400`, `F_PLmotion`, `F_Cache`,
   `Cache1`, `Cache2`, `B_PLsound`, `B_PLmotion`, `B_ENsound`, `B_ENmodel`, `B_ENmotion`).
   - `+0x10 slotDataSize` (0.60) and `+0x14 slotCount` (0.55) are proven by the two allocations
     (`bufferSize*slotCount` for the data buffer, `slotCount*0x54`/`*0x58` for the slot table) and by
     `0x0066522C`, which computes `bufferBase + slotDataSize*slotCount` as the pool end.
     `0x00108624` reads `+0x14` back with `ldrh` (u16) to store it in `slot[0]+0x54`.
   - `+0x08 maybe_refCount` (0.35) and `+0x0C maybe_byteLimit` (0.30) are set to `1` / `-1` by every
     constructor; no reader exists in this batch, so the roles stay `maybe_`.
   - **Important cross-subsystem finding**: the vtable slots of these pools are the
     `Font_GlyphCache_*` / `Font_GlyphPage_*` functions (`0x0056D028 AddGlyph`, `0x0056CF18 FreeSpan`,
     `0x0056D138 FindGlyph`, `0x0056D8C4 AllocSlot`, `0x0056D1E4 FillTexels`). The same pool class
     therefore backs both the streaming resource cache and the glyph atlas; the `Font_GlyphCache_*`
     names describe only the font use. This is recorded in the class evidence so the merge task can
     decide whether to rename them.

2. **`Fs_Worker` (size 11364, 5 fields)** - `Fs_Worker_Dtor` (`0x0056FF4C`) stores two vtable
   pointers (`0x007824A4` at `+0x00`, `0x007824BC` at `+0x04`) and destroys
   `std_destroy_range(self+0x2C40, 0x006F43E4, 0xC, 3)`, the ring buffer at `+0x2000`, the queue at
   `+0x1BCC`, the ring buffer at `+0x790` and the queue at `+0x35C`. The batch size `0x2004` was
   therefore raised to `0x2C64` (11364).
   - `+0x358 isStopRequested` (0.70): `ldrb r0,[r0,#0x58]` with `r0 = worker+0x300` at the top of
     `Fs_Worker_ProcessQueue` (`0x0056FDD0`); the thread body returns immediately when it is set.
   - `+0x35C openQueue` and `+0x1BCC requestQueue` (0.65): `Os_QueueTryPop` targets; the first feeds
     `Fs_NamedObject_Open` (`0x0056F7A4`), the second completes requests and recycles them.
   - `+0x2000 freeRequestRing` (0.60): `Container_RingBuffer_Push` target; the dtor closes the kernel
     handle at `+0x2014` with `Os_Handle_CloseField` (`0x006E75A0`), i.e. the semaphore the push
     blocks on when the ring is full.
   - `+0x300` is emitted as `unknown_stateBlock` with **confidence 0.0**: it is not a field, only an
     address computation (`add r0,r0,#0x300`) used to reach `+0x358`. The region `+0x1C..+0x33C` is a
     20-entry 0x28-byte array destroyed by `std_destroy_range(self+0x1C, 0x00570050, 0x28, 0x14)`.

3. **`Fs_Channel` (size 57628, 4 fields)** - the generated name is wrong. The object is the engine's
   big heap/transfer object (at least `0xE11C` bytes) and `maybe_Fs_Channel_InitFields`
   (`0x00103544`, called from `Engine_Initialize` `0x00101B74` and `InitHeaps` `0x00102EF8`) only
   touches the `+0xE0F8..+0xE118` block:
   - `+0xE0F8 commandBuffer`: `Gfx_CommandBuffer_Submit(&self->f_e0f8, self->f_e114, 0x2000, 0x11, -1)`.
   - `+0xE104 commandBufferCallback`: the command buffer's own `+0x0C` word, set to `self+4`; the
     transfer thread entry `0x001150DC` loads it and calls its vtable slot `+0x08` on completion.
   - `+0xE114 transferSource`: stored from `arg2` and passed to `Gfx_CommandBuffer_Submit`.
   - `+0xE118 completionEvent`: `Os_LightEvent_Init(&self->f_e118, 0, arg3, arg4, arg4)`.
   All four are typed `u32` on purpose: `+0xE0F8` and `+0xE104` are two words of the same embedded
   command buffer, so declaring `+0xE0F8` as a 20-byte `Gfx_CommandBuffer` would overlap `+0xE104`.

4. **`Fs_ArcHeader` (size 12, 3 fields)** - `maybe_Fs_ArcHeader_Parse` (`0x00114DD0`) checks magic
   `0x50524743` ('CGRP') and a size field in `0x01000000..0x01000100`, then stores `section+8` for
   each of three resolvers: `0x0011BB70` (u16 id `0x7800`), `0x0011BB08` (id `0x7801`),
   `0x0011BBDC` (id `0x7802`).
   - `+0x00 pairTable`: `Container_ForEachPair` (`0x0010E08C`) reads its first word as the entry count
     and `0x00115D78` walks 8-byte `{key, offset}` entries from it.
   - `+0x04 dataBlob`: the base those offsets are added to (`out[1] = out3[1] + entryOffset`).
   - `+0x08 subTable`: second 8-byte-entry table read by `0x0065F138`/`0x0065F148`
     (`Sound_WaveArchive_LoadAndCache` enumerates banks through it); optional.

5. **`Fs_FileJob` / `Fs_FileRequest` (size 24, 3 fields each)** - the two asynchronous file-request
   state machines (`0x002EB658` / `0x00408D38` and `0x0032F5BC`).
   - `+0x0C resultCode` (u8, 0.70): 1 aborted, 2 read request failed, 3 result error, 4 invoke
     failed, 5/6/7 specific result codes, 8 success, 9 open failed. The state itself lives at `+0x08`.
   - `+0x10 requestResult` / `+0x14 requestResultHigh` (0.60): the two words of the 8-byte
     nn::Result-style cookie written by `Fs_Request_Build` (`0x001D0218`) and polled by
     `0x00655398` / `0x006552AC` / `0x006552BC` / `0x00655304`.
   - `Fs_FileRequest`'s batch base `Os_SyncObject` was **cleared** (written as `""`): `struct_db`
     built that class from `Fs_FileRequest_Init` (`0x001D0134`), which is called as
     `Fs_FileRequest_Init(*(u32*)(self+4), self)` and initialises the *owner* object (fields
     `+0x0C`/`+0x48`/`+0x4C`), not a base of this 24-byte record. An 80-byte base cannot fit in a
     24-byte object.

6. **`Fs_AsyncIo` (size 68, 2 fields)** - `maybe_Fs_AsyncIo_Register` (`0x001D0378`) marks the
   per-object byte in the global array at `0x009C55`, stores `io+0x40` at `+0x0C`, then calls
   `Gfx_CommandBuffer_Submit(io, 0x001D0170(), 0x1000, 0x10, -1)`.
   - `+0x0C completionCallback` (0.60): loaded by the transfer thread entry `0x001150DC`, which calls
     `(*(*word+8))()` when the transfer completes. The sibling `Fs_FileRequest_Init` sets the same
     word to `self+0x44`.
   - `+0x40 maybe_callbackVtable` (0.45): first word of the embedded callback object the `+0x0C`
     pointer targets, so the real object extends past the batch size `0x44`.

7. **`Fs_Request` (size 8, 2 fields)** - the 8-byte async request result block itself
   (`resultLow`/`resultHigh`, 0.50 each), filled by `Fs_Request_Build` (`*out = local_30;
   out[1] = puStack_2c`) and cleared by `maybe_Fs_Request_WaitForService` (`0x00502128`, `*req = 0`).
   The batch's third function `0x001D033C` is `Fs_ReportFatalError` and does not touch the block.

8. **`Fs_ResourceHandle` (size 64, 2 fields)** - `Fs_Resource_Dtor` (`0x005F951C`) is
   `str r1,[r0],#0x3c; bl 0x12416C (Pack_ReleaseHandle); sub r0,r0,#0x3c`: it installs the incoming
   vtable at `+0x00` and releases the generation-tagged pack handle at `+0x3C`. The same `+0x3C` slot
   is released by `Fs_Resource_Release` (`0x005F9138`) and `Fs_Resource_Reset` (`0x005F9428`), and
   `Fs_Resource` (164 bytes) carries the remaining fields - so this class is the header part of a
   resource, not a separate handle wrapper.

## What is NOT Verified
- `Fs_Cache` `+0x08` and `+0x0C` have no reader anywhere in the batch; `maybe_refCount` and
  `maybe_byteLimit` are the best honest guesses (0.35 / 0.30) and may be wrong.
- `Fs_Worker` `+0x300` is emitted as `unknown_stateBlock` (0.0) because it is an address-computation
  artifact, not a field. The real object size `0x2C64` is derived from the destructor's
  `std_destroy_range(self+0x2C40, ..., 0xC, 3)`; the dtor's later pointer arithmetic is damaged
  decompilation, so the intermediate offsets (`+0x790`, `+0x324`) are inferred, not proven.
- `Fs_Channel` is a misattributed class: the four fields belong to the engine's big heap object, and
  the class name is kept only because `structs.json` keys on it. The `u32` types for `+0xE0F8` and
  `+0xE104` are a deliberate compromise to avoid overlapping fields.
- `Fs_AsyncIo`'s real size is larger than 68 (the embedded callback object at `+0x40` has a vtable);
  the batch size was kept.
- `Fs_Request`'s two words are named `resultLow`/`resultHigh`; whether the pair is a result code, a
  handle or an IPC request id is not proven (0.50).
- The `Font_GlyphCache_*` vtable-slot names on the `Fs_Cache` pools are inherited from an earlier
  naming pass and were not re-verified function by function.

## Suggested Follow-up Tasks
- **Rename the pool vtable slots**: `0x0056D028`, `0x0056CF18`, `0x0056D138`, `0x0056D8C4`,
  `0x0056D1E4` are shared by the resource cache and the glyph atlas; a neutral
  `CachePool_*` family (AllocSlot/FreeSpan/FindSlot/...) would fit both callers better than
  `Font_GlyphCache_*`.
- **Split `Fs_Cache`**: the batch merged four classes (0x54 pool, 0x58 pool, handle array,
  pass-through). A dedicated batch should split them, since `+0x10`/`+0x14` mean different things in
  each variant.
- **Split `Fs_Channel`**: the four `+0xE1xx` fields belong to the engine heap object; a class for that
  object (with `Engine_Initialize`/`InitHeaps` as evidence) would remove the misattribution.
- **Find the readers of `Fs_Cache +0x08`/`+0x0C`**: they are not in this batch; the resource loader
  that looks a pool up by name in the table at `Fs_CacheSet+0x54` is the likely caller.
- **`Fs_Worker`**: recover the 20-entry 0x28-byte per-type record array at `+0x1C` (fields at
  `+0x18`/`+0x1C`/`+0x20` relative to each record) as its own class.
