# S_050 — class + field naming, batch S_050 (subsystem Gfx)

## What I did

Named all **15 classes** and all **148 field offsets** of `orchestration/types/batches/S_050.json`
and wrote the result to `orchestration/types/out/S_050.json`.

Method per class: read the readable C of the constructor / setup function first (vtable store,
base-init call, every initialised field), then the update/draw/release methods that read the
fields, then cross-checked each offset against the base class in `structs.json`
(`Gfx_Node` for the effect emitters, `Gfx_Scene_SpriteCtx` for the scene sprites) and against the
callers (`tools/fn.py`). Where a field's purpose could not be proven I used `maybe_*` with
confidence < 0.5, or `unknown_<hex>` with confidence 0.0 and a description of what is known.

## Decisions worth knowing

1. **Two struct_db offsets are misattributions and are reported as `unknown_*` with confidence 0.0.**
   * `Gfx_SpriteParts +0x8e4` — the evidence line is `*(u8*)(*param_1 + 0x239) = value` from
     `Gfx_SpriteParts_SetFlag239` (0x0047AF5C), where `param_1` is a `GfxSpritePart**` array; the
     `+0x239` byte belongs to the pointed-to part. `0x239 * 4 = 0x8e4` explains the bogus offset.
     The real builder is **0x94 bytes** (the stack block `auStack_bc..local_28` in
     `Gfx_Scene_CreateSpritePart40` 0x002E77CC), so I reported `size: 148`.
   * `Effect_ActorTrail +0xe0` — the evidence line is `(**(code**)(*param_1 + 0x38))(param_1)`, a
     vtable slot 0x38 call; `0x38 * 4 = 0xe0`. The real object is **0x54 bytes** (its sibling
     `Effect_ActorTrailVariant` is exactly 84 and has the same tail), so I reported `size: 84`.
   * **Consequence for M2:** `merge_structs` bumps those two sizes back to 2277 and 228 because the
     offsets must be present. Dropping those two `unknown_` fields restores 148 and 84 and removes a
     2132-byte padding array from `include/dqxi/structs.h`. Please drop them in the merge.
2. **`Gfx_Scene_SpriteCtx` is a shared base, not a leaf class.** `Gfx_Scene_SpriteCtx_Init`
   (0x002E7F5C) has 60 callers (`Field_NpcMoveTowardTarget`, `Ui_LayoutParams_Init`,
   `Camera_UpdateWorkPath`, ...). Its `+0x18/+0x50/+0x58/+0x5c` are four different sprite pools
   (entry strides 0x34, 0x40, 0x24 and 0x70), which is why they are named separately rather than
   "pool1..pool4".
3. **`Gfx_SceneSpriteSubSet` size is 124, not 100.** `Field_Level_InitSpriteSets` (0x00610890)
   creates it at `levelWork+0x98` and the next container at `+0x7c` later, and the six 4-byte
   sub-sprite slots at `+0x60` end at `+0x78`.
4. **The emitter `+0x9c/+0xa0/+0xa4` triple is the inherited `Gfx_Node` position** (f32 x3), not a
   colour: `Gfx_Node_Ctor` (0x005F8178) copies the 8-float block `0x007E719C` into `+0x88..+0xa4`,
   and S_045 already named `+0x8c..+0x98` quaternion / `+0x9c..+0xa4` position. The same offsets
   mean something else in each emitter subclass (`+0x2c8..+0x2d0` is a position snapshot in
   Billboard, a variant group/id in SelectEmitterVariant, the definition pointer in Sphere), so
   those are named per class.
5. **64-bit values are split into `*Low`/`*High` u32 pairs** (`Gfx_MovieThread +0x150/+0x154`,
   `+0x158/+0x15c`, `+0x168/+0x16c`). The batch lists both halves as separate 4-byte offsets; a
   single `u64` member would overlap the next one and produce invalid C.
6. **`Gfx_Material +0x0c`** is the source of `memcpy(self+4, self+0xc, 0x38)` (confirmed in the
   disassembly at 0x00198F4C..0x00198F58), which overlaps its own destination. I named it
   `maybe_savedParams` and recorded the overlap rather than inventing a cleaner story.

## What is NOT verified

* No field name was confirmed against a running game or an emulator; everything is static evidence
  from the readable C, the disassembly and `structs.json`.
* `maybe_isVisible` (`+0x118` in all four emitters) is a guess: `Gfx_Node_Ctor` initialises
  `+0x118/+0x119/+0x11a` as three flag bytes and every emitter setup re-sets `+0x118 = 1`, but **no
  reader of `+0x118` exists in the recovered code**, so the flag's meaning is unproven.
* `maybe_definitionLayer` (`+0x26c`) is a byte copied from a definition record in every emitter
  setup; the same offset is a `0xFF`-terminated id in `Field_SceneObject`/`Field_Prop`. Purpose
  unproven.
* `Gfx_SceneSpriteSubSet +0x44..+0x5f` (10 fields) and `Gfx_Scene_SpriteCtx +0x08/+0x0c/+0x10` are
  only ever zeroed by their constructors; no reader was recovered, so they are `unknown_*` or
  `maybe_*` at confidence <= 0.4.
* `Gfx_MovieThread +0x158` receives the same delta as `+0x150` in `Join`; the difference between the
  two 64-bit counters is not recovered.
* `Gfx_MovieQueue +0x18/+0x20/+0x24` are only copied into the peek output descriptor; their exact
  meaning (timestamp / duration) is a reading, not a proof.
* The effect *definition* records (`EffectBillboardDef`, `EffectSphereDef`, ...) are not in this
  batch and were not recovered: the two spawn blocks that build them
  (`maybe_Field_SceneSpawnBlock_EffectBillboardEmitter` 0x0034CD20 and
  `..._EffectSelectEmitter` 0x0035C650) are interior addresses with damaged decompilation
  (`halt_baddata`), so several `+0x2xx` emitter fields are named only by the definition word index
  they receive.

## Suggested follow-up tasks

1. **M2 merge**: drop `Gfx_SpriteParts@0x8e4` and `Effect_ActorTrail@0xe0` before emitting
   `include/dqxi/structs.h` (see decision 1).
2. **New batch `S_0xx` for the effect definition records**: `EffectBillboardDef`, `EffectSphereDef`,
   `EffectVariantDef`, `EffectQuadDef`, `EffectHelixDef`, `EffectSpriteDef`. They are the missing
   half of the emitter fields (`+0x2c8..+0x2d6`, `+0x26c`, `+0x88`). The spawn blocks are damaged,
   but the setups read them at fixed offsets, so a struct_db pass restricted to the
   `Effect_*Emitter_Setup` functions would recover them.
3. **`Gfx_Node` size is wrong (57596)** and blocks setting `base: Gfx_Node` on the emitters. A
   dedicated pass on `Gfx_Node_Ctor` (0x005F8178) plus the allocation site would fix the base chain
   for the whole effect/sprite family.
4. **`Gfx_Scene_SpriteCtx`** deserves its own batch: it is the header of every scene sprite and its
   `+0x08/+0x0c/+0x10` are still unknown. `Gfx_Sprite`'s constructor (which stores ctor arguments
   there) is the place to look.
5. **`Gfx_MovieThread`**: find the second 64-bit counter's reader (probably a stats/debug screen) to
   separate `+0x150` from `+0x158`.
