# S_055 - Struct & Field Naming (subsystem: Map)

## Summary
Batch `S_055` contains **one** class with **5** field offsets. All 5 were named, plus the
class's real vtable pointer at `+0x00`. The headline finding is that the batch class is
**misnamed**: `Map_Object` is not a map object at all, it is the monster ecology **"chase"
action** (`ecoCh`) - the very same object batch **S_037** already named `Field_NpcAction_Chase`.

## The class

### `Map_Object` (`MapObject`) - really the monster ecology chase action
- **Role**: polymorphic action object owned by a monster actor's ecology list. It waits for its
  target, spins the owner actor toward it, then winds the spin down.
- **Size**: 68 bytes (`0x44`) - **allocation-backed**, not just "highest field + width".
- **Base**: none declared (see Decisions).
- **Class confidence**: 0.60.
- **Evidence**:
  - `Monster_SetupEcology` (0x00178B08) does `Mem_AllocAligned_2(0x44, ...)` and passes the block
    to `Monster_Action_EcoChase_Ctor` (0x004D6F24) together with the string `ecoCh`.
  - `Monster_Action_EcoChase_Ctor` installs vtable `0x00779E30` and sets `+0x34 = 0`,
    `+0x38 = 1.0f`, `+0x3C = 2.0f`, `+0x40 = 4.05f` (`0x4081999A`).
  - The ctor chains `Monster_AiBehavior_Ctor` (0x00619CF4) -> `Gfx_ObjectDesc_Ctor4` (0x0019C8F4)
    -> `Gfx_ObjectDesc_Init` (0x00193D84), so `+0x00..+0x2B` is a `Gfx_ObjectDesc` header
    (vtable `+0x00`, name buffer `+0x08`, mode `+0x18`, flags `+0x1C`, kind `+0x20`, id `+0x24`,
    owner `+0x28`).
  - The batch's only function `0x004D6BB8` is vtable slot 2 (the action's *start*); its siblings
    are `Field_NpcAction_Chase_Update` (0x004D6C54, slot 4) and `Field_NpcAction_Chase_Dtor`
    (0x004D6F6C, slot 1).
  - The generated name comes from the R2_005 guess `maybe_Map_Object_UpdatePlacementScale`
    (confidence 0.45), which read `Map_PlaceObject(ownerActor, 0)` as a placement path. It is a
    turn-request write into `ownerActor+0x31C`, exactly as the sibling
    `Field_NpcAction_RunToLinkSetup` (0x003314B0) does.

## Decisions (the orchestrator was not available)
1. **Kept `class` = `Map_Object`.** `tools/typedb/apply.py` (`merge_structs`) rejects any class
   that is not in `structs.json`, so the key cannot be renamed. The misnomer is stated in the
   `summary` and `evidence` instead.
2. **Kept `type` = `MapObject`.** Renaming it to `FieldNpcActionChase` would make the merge emit a
   second `typedef struct FieldNpcActionChase` next to S_037's entry and break
   `include/dqxi/structs.h` (duplicate typedef). `MapObject` is already used by
   `Map_PlaceObject(MapObject*, u32)` in the readable C, so it is at least not a new name.
3. **Added `vtable` at `+0x00`** although the batch did not list it. The class is demonstrably
   polymorphic (ctor stores a vtable, dtor/start/update are slots). The merge reports it as a
   *warning* ("offset has no access evidence; kept as worker hypothesis"), not an error.
4. **`base` left `null`.** The ctor chain proves a `Gfx_ObjectDesc` header, but the recorded
   `Monster_AiBehavior` size (100 bytes) is larger than this 68-byte allocation, so declaring that
   base would be wrong. The chain is documented in the class evidence instead.
5. **`startDistance` / `endDistanceDelta` reuse S_037's names** so the two structs that describe the
   same object agree. My own evidence records the caveat: the sibling `Field_NpcAction_RunToLinkSetup`
   reads the same record field (`ownerActor+0x2C4->+0x1C`) as a *delay*, so the value may be a time
   rather than a distance. Confidence is therefore 0.55, not S_037's 0.85.

## Open problems
1. **Duplicate class.** `structs.json` holds both `Map_Object` (this batch) and
   `Field_NpcAction_Chase` (S_037) for the same 0x44-byte object. After the merge,
   `include/dqxi/structs.h` will contain two structs with identical layouts under different type
   names. The `Map_Object` entry should be dropped from `structs.json` (or aliased to
   `FieldNpcActionChase`) by whoever owns `tools/typedb/struct_db.py`.
2. **`MapObject` is already the wrong type for `Map_PlaceObject`.** `Map_PlaceObject` (0x001798D0)
   writes a pointer at `object+0x31C`, which a 0x44-byte `MapObject` cannot hold. That signature
   needs its own class (the real field object), not this one.
3. **`startDistance` / `endDistanceDelta` are not proven to be distances.** They are two floats from
   the actor's ecology record compared against a limit at `self->f_24->+0x44`. Resolving what
   `self->f_24` points at (a `Gfx_ObjectDesc` field at `+0x24`, set from the descriptor ctor's third
   argument) would settle it.
4. **Vtable address ambiguity.** `Monster_Action_EcoChase_Ctor` stores `0x00779E30`, but the rodata
   word at `0x00779E30` is `0x00000000` and the dtor sits at `0x00779E34`. Either slot 0 is a null
   entry or the recorded base is off by one word; the field name `vtable` is unaffected, but the
   slot numbering in the readable C (`Field_NpcAction_Chase_Dtor` "slot 0 of 0x00779E34") should be
   re-checked.
