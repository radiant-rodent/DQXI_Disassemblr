# S_058 - Menu subsystem: 13 classes / 177 fields

## What I did

Named every class and every field offset of `orchestration/types/batches/S_058.json`
(13 classes, 177 field offsets, subsystem Menu) and wrote the result to
`orchestration/types/out/S_058.json`.

Method: for each class I read the readable C of its constructor / loader / destructor first
(vtable store, base-constructor call, initialised fields), then the update/draw methods that
read the fields, then cross-checked widths against the batch `size` and against
`orchestration/types/structs.json`. Where the batch evidence looked like a mis-parsed access I
checked the disassembly with `python tools/fn.py 0xADDR --asm N` before naming anything.

## Findings the orchestrator should know

1. **`Menu_Actor` and `Menu_Item` are not classes.** `Menu_Actor_PlayUiAnimation` (0x0020A9B8)
   receives the **battle work** (`work+0x5C`) as `self` and reads its current actor at +0x4320;
   `Menu_Item_InitEffectParams` (0x0020D294) receives the same battle work (+0x4200, +0x423E,
   +0x4244 = the 3D/2D mode flag, +0x4320, +0x4D78 = the effect-parameter block, +0x4E64).
   `maybe_Menu_ShowRowDescriptionPopup` (0x00305534) instead takes a menu-row object. Both
   classes are marked confidence 0.15 and every offset is `maybe_*`/`unknown_*`.
   **Suggested fix:** drop both from `structs.json`, or make `apply.py` ignore `weak` fields when
   it computes the struct size - otherwise the merge emits a 17,188-byte `MenuActor` and a
   20,070-byte `MenuItem` struct with one field each.
2. **`Menu_Slot` merges two unrelated objects.** `Menu_Slot_StoreActorId` (0x0020A560) scans five
   0x40-byte party-slot records at +0x4C and is called only from battle party UI
   (`Battle_Ui_UpdatePartyStatus`, `Battle_ActionUi_RefreshMemberFlags`, ...). The
   0x004A0FC0..0x004A168C block is a minigame screen (pane groups, three selector sub-objects, a
   3D model widget, `Casino_Slot_SetDigitSprite`), which the earlier `Casino_Slot_*` renames tie
   to the casino slot machine. `Menu_Slot_GetOccupancyState` (0x0064C32C) is called with
   `self+0x24C` (asm 0x004A1448: `add r0,r4,#0x24c; bl 0x64c32c`), so its +0x38/+0x68 are fields
   of that embedded selector, not of `Menu_Slot` - the batch attributes them to the outer object.
3. **`Menu_ItemBox` merges two classes.** 0x002FCC44 installs vtable 0x00762760 and clears only
   +0x4C (its only named caller is `Ui_SkillPanel_Ctor`); 0x003047C0 installs vtable 0x00762BB8
   (`Ui_PokerWindow_CtorB`) and clears +0x4C..+0x5C. The five trailing words are `unknown_*` at
   confidence 0.0.
4. **`Menu_Cursor` is a handle holder, not the cursor.** `Menu_Cursor_Resolve` (0x006337CC)
   decodes `self->f_b0` as a 21-bit-tag / 11-bit-index handle into table 0x007B80C0; the
   accessors then read the *resolved* object (+0x8C quaternion, +0x9C position, +0x270 slot
   index, +0x2A4 scale, +0x2C9 state). The batch's +0x00/+0x04/+0x08 are
   `Menu_Cursor_GetPosition`'s `out_vec3` parameter, not fields of self - emitted as `unknown_*`
   at confidence 0.0.
5. **The batch missed two real `Menu_TalkParty` fields.** `maybe_Menu_TalkParty_CreatePanel`
   case 0x12 writes `*(u32 *)(self + 100)` (+0x64, `Ui_RecipeBook`) and `Menu_TalkParty_ReleaseAll`
   releases `*(int **)(self + 200)` (+0xC8) through vtable slot +4. `struct_db` did not record
   them because the readable C prints the offsets as decimal literals. I did not emit them
   (the task requires exactly the batch offsets); they should be added to the batch.
6. **The 16-byte inline name buffer of the icon records** (+0x24..+0x33) is emitted as four
   `nameWordN` u32 fields, because the batch lists four separate 4-byte offsets and a single
   `char[16]` would overlap them. `Menu_IconModel_LoadBch` formats it with `%s.bch`, so the
   buffer is a real inline char array.
7. **`Menu_HorseRace` is bigger than the batch size.** The four `plate_dN` widgets are spaced
   0x1C4 bytes from +0x24C, so the object reaches at least +0x95C, not 592. I kept the batch
   size (an unbacked larger size would be reported as suspicious by `apply.py`) and recorded the
   real extent in the class evidence.
8. **`Menu_ItemSelect`'s +0x49/+0x4A/+0x4C/+0x11C/+0x124..+0x134 are probably `Ui_Object` base
   fields** - `structs.json` records `Ui_Object` accesses at exactly those offsets. They are
   named by their observed role here (`maybe_isOpen`, `maybe_isClosing`, `animRefList0`,
   `childContainer`, `listNNext`/`listNPrev`) with the base-class caveat in the evidence.
