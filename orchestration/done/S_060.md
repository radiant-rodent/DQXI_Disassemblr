## What the classes are

- **`Model_Actor`** — the field/battle actor model (Gfx_Model layout, vtable `0x0077AE0C`). The deleting
  dtor `0x004E2DD8` stores that vtable at +0 and the embedded animation-controller vtable `0x00782060`
  at +0x9C. Named the node transform (+0xC..+0x28), the animation offset block f_D0..f_FC and flags
  f_100/f_104/f_108, the two attach slots (+0x220 weapon, +0x224 equipment mesh), the scale fields
  (+0x1CC/+0x1D4), attachment-part count (+0x250), the unit index (+0x273), the three effect-part
  handles (+0x708/0x70C/0x710), the attachment-effect handle (+0x6FC) and the arm/mask status bits
  (+0xF22, used by 0x0040136C / 0x00401424).
- **`Model_Attach` / `Model_AttachSlot` / `Model_Preview`** — three overlapping views of the same
  ~0x6E0-byte attach-slot object (vtable `0x0075C334` for `Model_AttachSlot`): inline node name
  f_65C..f_678, node id f_67C, local matrix f_680, child list f_6B0/f_6B4, resource set f_4F0,
  render model f_11C, owner f_654, visibility flags f_588..f_58B, cull distance f_594, fade range
  f_5B4..f_5C4 and spin range f_5C8..f_5D8. Consistent names were reused across the three classes.
- **`Model_Equip`** — character-equipment controller: four attachment-node pointers at +0x40+8*slot and
  their item ids at +0x44+8*slot, grip slot/state (+0x60/+0x61), visibility mask (+0x62), character id
  (+0x65), accessory slot modes (+0x68/+0x69), plus the 0x6EC-byte mesh subtype's owner/slot backrefs
  (+0x6E4/+0x6E8).
- **`Model_Face`** — blink/mouth controller: intervals (+0xEC/+0xF0), elapsed (+0xF4), flags (+0xF8),
  eye/mouth frame bytes (+0xE8/+0xE9), open amounts (+0xC4/+0xCC), countdown (+0x1D0), next intervals
  (+0x1C4/+0x1C8), blend values (+0x1D8/1DC/20C/210) and frame id (+0x254, 0xFFFF = none).
- **`Model_Instance`** — placed model instance: instance handle/id/token (+0xC..+0x14), 4x4 transform
  (+0x18), mesh (+0x28), node array/matrices/count (+0x168..+0x174), AABB min/max (+0x17C..+0x18C) and
  the per-node bounds array (+0x194).
- **`Model_Node`** — transform node that composes a look-at/Euler world matrix plus a projection matrix
  (`0x00664130`): position (+0x34..+0x3C), target/Euler (+0x40..+0x48), up vector (+0x4C..+0x54),
  near/far (+0x58/+0x5C), anim array (+0x1C) and child list (+0x98/+0x9C).
- **`Model_ResourceSet`** — three embedded binding lists (+0x10/+0x3C/+0x68) with count/owner words, and
  two heap blocks (+0x94/+0x98); released by 0x003BF3EC / 0x003BF2A8.
- **`Model_Object`** — actually the shared scene-object base with vtable `0x00764ABC`; its only recovered
  method tears down the child list. Kept the generated class name per the task.
- **`Model_ObjectType0x74`** — battle-action-model factory variant (type 0x74, vtable `0x76C5F0`),
  arm/mask flags at +0xF22/+0xF23 and the invalid handle `0xFFFFFC00` at +0xF24.
- **`Model_SecondaryMotion`** — three owned chain buffers (only +0xC is in the batch) and three flags.
- **`Model_SwitchAttachmentsByState`** — helper view that shows/hides the per-player-state attach slot
  at +0x244; the batch only evidences the shared hidden byte at +0x51.

## Decisions (and honest limits)

1. **Two batch offsets are vtable-slot artifacts, not data.** `Model_Actor` +0x210 is the vtable call
   `(**(*self + 0x84))` in `Model_Actor_PlayGripAnimation`; `Model_Equip` +0x330 is
   `(**(*self + 0xCC))` in `Model_Equip_UpdateActorEquipment`. They are emitted as `unknown_210` /
   `unknown_330` with confidence 0.0 and explained in `evidence`.
2. **`Model_Attach` merges two object types.** Offsets 0x00..0x38 belong partly to the 0x228-byte
   attachment record allocated by `0x0064EA10`, while the rest belong to the 0x6E0-byte attach slot.
   +0x00 comes from the out-array of `Model_Attach_InitPointNames`, so it is marked `unknown_00` (0.0)
   rather than pretending it is a vtable of the slot; +0x04/+0x08 keep the handle/list readings from
   the 0x228-byte record with low confidence.
3. **`Model_Equip` also merges two objects.** Offsets 0x00..0x69 are fields of the 0x6C-byte equipment
   mesh owner; +0x6E4/+0x6E8 are the backrefs of the 0x6EC-byte mesh object that
   `Model_Equip_CreateWeaponMeshes` allocates (confirmed by `puVar6[0x1B9]`/`puVar6->f_1BA`).
   The size (1772 = 0x6EC) comes from the child mesh, not the owner.
4. **`Model_Actor` +0x30..+0x3C has conflicting readings.** `maybe_Model_Actor_UpdateStateAnimation`
   uses +0x30..+0x33 as four state bytes; `maybe_Model_Actor_CacheAttachOffset` writes +0x30/+0x34/
   +0x38/+0x3C as floats of a source-node transform. The state-byte reading has more corroborating
   methods (0x004E237C, 0x004E21E4) so +0x30..+0x33 are bytes; +0x34/+0x38/+0x3C are `maybe_sourcePos*`
   with 0.3 confidence and the conflict is written into their evidence.
5. **`Model_SwitchAttachmentsByState` size 84 is inconsistent with its body** (the two methods index
   `model+0x244`); I kept the generated class/size and named only the batch offset at +0x51.
6. **Class names were kept** (`Model_*` / `Model*`) because `apply.py` rejects a class that is not in the
   batch and the project already uses these types; where the real role differs (Model_Object is the
   scene-object base, Model_Attach/Equip are mixed views) it is stated in the summary/evidence.
7. Fields below 0.5 confidence are prefixed `maybe_`; unnameable ones are `unknown_*` at 0.0.
