### Monster_Model — the big correction

* **Size.** The batch says 4884 (`max_strong_field+width`). That is wrong: it comes from
  `Monster_Model_BuildFromRecord` / `Monster_Model_BuildDualPattern`, whose first parameter is a
  **`MonsterActor`**, not a model — so their `0x125C` / `0x1310` accesses are not this class.
  The real allocations are `Mem_AllocAligned_2(0x164, …)` in `Monster_Model_Create` and
  `Mem_AllocAligned_2(0x2dc, …)` in `Monster_Model_CreateDualPattern`. I kept **732 (0x2DC)**,
  the dual form, which covers every field the batch lists up to 0x2D8.
* **Base.** The batch's base `Text_Layout` is wrong — no base constructor is called. Set to `null`.
* `0x14` is the **vtable of an embedded model node A**: `Monster_Model_Create` does
  `puVar2 = func_0047E894(result + 8); *puVar2 = 0x0078081C` with `result = self + 0xC`.
  `0x144` is the vtable of node B (`func_0047E1FC(param_1 + 0x144, 0)`), and
  `maybe_Monster_Model_DestroySubNodeLists` destroys the child lists at `+0x18` and `+0x148`
  (stride 0x130), which confirms the two-node layout.
* `0x278` / `0x27C` are the two **render nodes**: `Monster_Model_SetBoundingBox` stores
  `(*(*objA + 0x80))()` and `(*(*objB + 0x80))(objB)` there. `0x280` is a **s16 state id** with a
  `-1` sentinel (`Monster_Model_SetStateById`), not a u16.
* `0x288` / `0x28C` / `0x290`: **conflicting evidence, recorded honestly.** `Monster_Model_SetStateById`
  really does `ldr r3,[r4,#0x288]; ldm r0,{r0,r1}; blx r3` (0x00422AFC..0x00422B08), i.e. a callback
  plus two arguments; but `Monster_Model_SetBoundingBox` writes a 3-float **min** vector there with
  `vstmia r4!,{s0,s1,s2}` (0x00421734). The two functions use different vtables (0x00780A90 vs
  0x00780A20), so SetBoundingBox probably belongs to a different class. I kept the callback reading
  at confidence 0.4 and put the conflict in the evidence. `0x294`/`0x298`/`0x29C` are the matching
  **max** vector (unambiguous, `stm r4,{r1,r2,r3}`).
* `0x2C4`/`0x2C8`/`0x2CC`/`0x2D4` are four embedded **state vtables** selected by writing their
  address into the field at `0x2BC` (`*(int *)(self + 700) = self + 0x2c4` etc. in
  `Monster_Model_HandleStateEvent`, and `… = self + 0x2d4` in `maybe_Monster_Model_InitSubObject`).
  Renamed from `modeVtable*` for consistency.
* `0x2D8` is `defaultScale` = `0x3F800000` (1.0f), confirmed in `maybe_Monster_Model_InitSubObject`.
* `0x4` is **not** `fadeAlpha` — it is the secondary vtable `0x00780974` written by
  `Monster_Model_Create`. (The fade counter is a different object's `self[1]` in
  `Monster_Model_UpdateFadeAlpha`, which is damaged Ghidra.)
* `0x30`, `0xF0`, `0x110`, `0x200` are **not fields**: they are vtable slots 3, 15, 17 and 32.
  `struct_db.py` matches `param_1 + 0xc` inside `(**(code **)(*param_1 + 0xc))` and scales it by 4
  because `param_1` is an `int*`. Emitted as `unknown_vtableSlotN` at confidence 0.0.
* `0x20C`, `0x125C`, `0x1310` are **not Monster_Model fields** (all beyond the 0x2DC allocation);
  they belong to the `MonsterActor` parameter of the two builder functions. Emitted as
  `unknown_*` at 0.0 with the reason.
* `0x118`..`0x158` are recorded **relative to the embedded node at +0x14**, so their real object
  offsets are +0x14 (0x12C..0x16C). Each evidence string states the real offset. `0x15C` and
  `0x2A0` are the same field seen with two different bases.

### Other classes

* **Monster_BehaviorAction** — `0x28` is the owning **actor** (`self->f_28->f_268` is its model,
  `&self->f_28->f_5f4` its transform), not an "effect object". `0x2C` is the base of a 2-entry
  array of 0x18-byte **action slots** (`self + 0x2c + self->f_30 * 0x18`), not a vtable. `0x38` is
  an **integer** frame counter (`+ 1`), so its type changed from `f32` to `u32`. `0x4C` is a switch
  **jump table**. `0xB8..0xE4` are a 12-float copy of the actor's transform matrix (0xC8 is never
  accessed, which is what makes it a 3x4 matrix).
* **Monster_FieldBehaviour** — same `0x28` actor correction and the same 12-word transform copy.
  `0x2C` is an embedded object with its own vtable (`this = param_1 + 0x2c`), so `stateObject`
  rather than `stateVtable`.
* **Monster_Action** — `0x2C` is an embedded **member pair** (`Ui_Object_InitMemberPair(puVar2 + 0xb)`),
  not a vtable. The float parameters at 0x30..0x40 were named `maybe_turnRate`/`maybe_chaseSpeed`/
  `maybe_chaseRange` with no support; renamed to `maybe_paramNN` at 0.35.
* **Monster_ActionSet** — the ctor stores literal floats (6.0f, 6.0f, 0.26f, 0.6f, 1.2216f, 0.1745f,
  0.349f, 0.2f, 0.15f, 1.2216f). `maybe_gravity`/`maybe_maxPitch` were unsupported; renamed to
  `maybe_moveParam6c`/`maybe_moveParam70`. The remaining semantic names are kept at ≤0.4 with the
  literal value quoted in the evidence.
* **Monster_AiBehavior** — `0x4`/`0x8` are **mis-parsed offsets**: the stores are
  `puVar4[0x12] = puVar5[1]` and `puVar4[0x13] = puVar5[2]`, i.e. object offsets 0x48/0x4C.
  `0x2C` is a mis-render of byte **0xB** (`*(undefined1 *)(puVar3 + 0xb)` on a `u32*`; the readable
  C field is `f_b`). `0x20` is relative to the member pair at 0x60, so the real offset is 0x80.
* **Monster_PatternNode** — `0x138`/`0x13C` are **flag words** (`x = x & u | u`), not sentinels;
  `0x130`/`0x134` were `maybe_rangeX/Z` with no support, now `maybe_param130/134`; `isEnabled` at
  0.4 violated the `maybe_` rule and became `maybe_flag142`.
* **Monster_Handle** — confirmed as `Battle_UnitModel_AssignHandleA/B` (0x0042A3B4 / 0x0042A780),
  reference-counted pack handles at `+0x13C` / `+0x138`. The class is really `Battle_UnitModel`;
  the generated name is kept because the batch fixes it.
* **Monster_Record** — the single field `0x208` is the character parameter block:
  `maybe_Battle_SetMemberStatMessageArgs` reads `actor->f_208->f_768` and passes it to
  `func_0035EB98` as a **character id**. Note that function also takes a `MonsterActor`, so this
  offset may belong to the actor rather than to a record; confidence 0.5.

## Open problems / not verified

1. **The merged size will still be 4884, not 732.** `apply.py` computes
   `size = max(declared, highest field end)`, and the batch forces fields at 0x125C and 0x1310.
   A worker cannot fix this from the answer file. **The batch generator should drop offsets beyond
   the class allocation** (`size_alloc` is available in `structs.json` but is `null` here because
   `ALLOC_CALL` did not pick up `Mem_AllocAligned_2`).
2. **`Monster_Model` merges at least three classes.** `Monster_Model_Create` (0x164 bytes, vtable
   0x007808B4), `Monster_Model_CreateDualPattern` (0x2DC, vtable 0x00780A20) and
   `Monster_Model_SetBoundingBox` (vtable 0x00780A90) are different objects sharing a name prefix.
   The 0x288 conflict above is a symptom. Splitting them needs a batch-level decision.
3. **`Monster_Model` 0x288/0x28C/0x290** — the callback-vs-float-vector conflict is documented but
   not resolved. Resolving it needs a caller of `Monster_Model_SetStateById` with a non-`-1` state
   entry, or a check of whether `Monster_Model_SetBoundingBox` is ever called on this object.
4. **`Monster_ActionSet` float semantics** are guesses from literal values only; the ctor doc calls
   the block "movement/steering parameters" but nothing pins individual fields.
5. **`Monster_Model` 0x118..0x158** are named `maybe_nodeFieldNNN` — the node tail is only ever
   zeroed or set to constants, so no purpose could be established.
6. **`Monster_EcologyActor`** has no constructor that writes most of its fields; the two 3-vectors
   at 0x178..0x18C and 0x194/0x198 are named `maybe_vec*` from the copy pattern only.
7. `Monster_Record` has exactly one batch field, so the class is effectively unnamed beyond `params`.
