Key evidence (all verified in code, not guessed from the generated names):

* **Os_SyncObject / Os_CriticalSectionObject are one object.** 0x001D0134 writes +0xC = self+0x44,
  +0x48 = self, +0x4C = arg and starts a thread via 0x0010EAB0; the thread entry 0x001150DC (asm
  0x1150DC) does `p = [self+0xC]; (*p)->vt[2](p)` — hence the embedded callback at +0x44 with
  vtable/owner/arg. 0x005761D8 installs vtable 0x00782668 (rodata first slot = 0x005761D8), joins
  the thread, closes the handle at +4 with `svc #0x23`, and 0x0010EA00 frees +0x10/+0x14. So the
  generated `Os_CriticalSectionObject` label is wrong; both classes describe the same 0x50 bytes.
* **Os_OwnerTable.** The readable C is truncated by the mis-marked `std_ConstructArray`
  (0x00100050, thumb `blx` marked noreturn). The real function entry is **0x001064D4** (Ghidra
  started at +4 and lost `ldr r1,[pc] ; str r1,[r0],#4`): +0 gets 0x0075C310, then seven 0x30-byte
  nodes built by 0x00109558 (which zeroes a 0x30 node, puts vtable 0x007824D0 at +0 and 0x007821B8
  at +8, returns its argument), 0x007821C8 at +0x154, 5x0x10 ctor calls at +0x158 and +0x1D4, list
  headers to +0x374, function ends at 0x106720. Getter **0x001D0170** allocates 0x37C bytes, calls
  this ctor, and returns `obj+0x33C` — that returned pointer is the heap handed to
  `Mem_AllocAligned` by Fs_FileRequest_Init/0x001D0134 and Fs_AsyncIo_Register. Two independent
  sources agree on 0x37C = 892 bytes.
* **Os_SequenceTask.** Ctor 0x0010673C (asm read in full) builds two 3-word intrusive-list anchors
  (+0x04/+0x10: owner/next/prev), an embedded rb-tree node base at +0x1C (parent/left/right/colour
  at +0x20/+0x24/+0x28/+0x2C, confirmed by `std_RbTree_EraseNode`'s documented node layout), the
  FNV-1a offset basis 0x811C9DC5 at +0x30, the `Container_String` vtable 0x00782534 at +0x34 and
  +0x60, the literal `"SequenceTask"` at +0x64, and state bytes 3/0/0/1 at +0x84..+0x87. Fs_Task_Create
  (0x00107F84) and Container_HashTableInsert (0x00107FC0) hash the +0x64 name, insert the +0x1C node
  into the map at param_2+0x18, store the map at +0x5C, the heap at +0x88 and the value byte at +0x86.
* **Os_WorkQueue.** 0x00114E60/0x00114FAC push/pop 4-word nodes `{next, state, sequence,
  previous-sequence}` into a ring at +0x00 and pop completions from an embedded OsQueue at +0xB4;
  f_174 is a monotone sequence, f_178 the completed sequence, f_184/f_188 the in-flight rollback pair.
  Callers are sound-stream/DMA code (Snd_QueueWaveCommand, Sound_Stream_SubmitDmaCommand, ...).
* **Os_Handle.** 0x006E75A0 closes `*(u32*)(self+0x14)` with `svc #0x23`; Fs_Worker_Dtor calls it on
  `self+0x800`, i.e. one handle holder per Fs worker queue.

## Deviations / decisions (honest list)

1. **Class names kept as generated** (`Os_SyncObject`, `Os_CriticalSectionObject`, ...) because
   `tools/typedb/apply.py` rejects a `class` that is not in `structs.json`. The correct identity is
   stated in every `summary` instead. `Os_CriticalSectionObject` is NOT a critical section and
   `Os_SyncObject` is NOT a sync primitive — both are the thread wrapper.
2. **`Os_CriticalSectionObject` has one extra field beyond the batch**: offset 4 `threadHandle`.
   The dtor closes it in the same function (`piVar1 = self+1; svc #0x23; *piVar1 = 0`), so it is
   real; the merge dry-run reports one warning ("offset has no access evidence") for it. Without it
   the struct would be a vtable with no body.
3. **Sizes deviated where the batch was built from a truncated decompilation**:
   `Os_CriticalSectionObject` 4 -> 80 (same object as Os_SyncObject) and `Os_OwnerTable` 4 -> 892
   (ctor + getter allocation). All other sizes are the batch values and were re-verified against the
   ctor's highest write (`Os_SequenceTask` 0xB0 exactly: last write +0xAC, next function at 0x1068AC).
4. **`mapKeyName0..mapKeyName7`** are the eight 4-byte words of the 32-byte inline name buffer at
   +0x38. The batch lists each word separately (the ctor zeroes each word), so I named each word
   instead of declaring one `char[32]` that would make the merge skip seven required offsets. The
   evidence on each word says which bytes of the name it covers.
5. Fields whose purpose could not be honestly established are `unknown_58`, `unknown_85`,
   `unknown_8C`, `unknown_94`, `unknown_9C`, `unknown_A0`, `unknown_AC` (confidence 0.0) and the
   `maybe_`-prefixed state bytes of `Os_SequenceTask` / `Os_WorkQueue` (0.30–0.45). The class-level
   confidence is the weakest important field, not an average.

## Open problems / not verified

* `Os_SequenceTask` +0x84..+0xAC (state block) is only known from the ctor's initial values; no
  reader of most of these bytes was found among the functions struct_db attributes to the class.
  `+0x98` is a probable observer/subscriber (read by vtable slot 0x002595AC), `+0x86` is a definite
  boolean value, `+0x88` the allocator — the rest are hypotheses or `unknown_`.
* `Os_OwnerTable` is a global singleton with no direct caller; only the getter 0x001D0170 proves its
  allocation size and the +0x33C heap. The meaning of the seven 0x30-byte pools is inferred from
  vtable 0x007824D0 slot 0 = `Mem_SmallBlockAllocChunk` (0x006F1D1C); the object's own method table
  0x0075C310 was not resolved into named methods.
* `Os_SyncObject` +0x44's vtable is not written by 0x001D0134 — it must be installed by the derived
  constructor (Fs file-request / Fs_AsyncIo). I did not chase that ctor.
* `Os_WorkQueue` +0x184/+0x188/+0x18C semantics (in-flight rollback pair) are inferred from the
  Push/Drain code only; the sound-thread consumer of the +0x00 ring was not analysed.
