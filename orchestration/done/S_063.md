Classes:

1. **Pack_HandleTable** (size 600, 31 fields, no vtable) — the per-scene pack-resource handle table
   reachable as `Ui_SceneFlow + 0x60` (`structs.json` types that field `Pack_HandleTable*`, and
   `Ui_SceneFlow_TeardownAll` passes `self->f_60` to `Pack_HandleTable_ReleaseAll`/`ReleaseObjects`).
   Evidence-backed layout:
   * `+0x38..+0x9f` `PackHandle[26]` (Acquire writes `table + index*4 + 0x38`, ReleaseAll loops
     `i < 0x1a` over `table + j*4 + 0x38` and calls `Pack_FreeHandleEntry`);
   * `+0xa8 + index*0x10` = 16-byte slot record `{refCount(+0), packId(+4), slot word(+8),
     pack tag(+0xc)}` (Acquire tests `+0xa8 + index*0x10`, Add does `iVar6->f_a8++`,
     `iVar6->f_ac = id`, `iVar6->f_b4 = packObject+0x64`);
   * `+0xa0` cached `PackEntry*` of the mounted common 2D pack (format id 0x6a1), `+0xa4` its
     extra retained `PackHandle`;
   * three intrusive containers at `+0x14/+0x18`, `+0x24/+0x2c`, `+0x24c/+0x254`.
   Names: `slot1PackHandle` (+0x3c = element 1 of the handle array, the common-pack slot),
   `commonPackObject`, `commonPackHandle`, `slot1RefCount`, `slot1PackId`, `maybe_slot1UiHandle`,
   `maybe_slot1PackTag`, `slot7RefCount`..`slot24RefCount` (the 18 slots Add's free-slot fallback
   probes one by one), and `maybe_list*EndMarker` / `maybe_list*FirstNode` for the three containers.
2. **Pack_HandleEntry** (size 24, 6 fields) — head of the multiple-inheritance object built by
   `Pack_HandleEntry_Init` (0x001242AC): vtable at 0, secondary vtable (`0x007824A4+0x18`) at +4,
   base vtable `0x00782234` at +0xc and +0x14, zeroed state words at +8/+0x10, then
   `std_ConstructArray(entry+0x1c, 0x28, 0x14)` = twenty 0x28-byte sub-handles. Names: `vtable`,
   `secondaryVtable`, `maybe_baseStateA`, `subVtableB`, `maybe_baseStateB`, `subVtableC`.
3. **Pack_Entry** (size 4716 = 0x126c, 2 fields) — the object accepted by `Pack_AcquireResourceHandle`
   as `PackEntry*` (RTTI 0x007E7250, part pointer +0x58, data size +0x5c, format id +0x60); its
   deleting destructor releases the `PackHandle` at +0x1268. Names: `vtable`, `packHandle`.
4. **Pack_ResourceChain** (size 92, 2 fields) — the non-deleting destructor of an Fs_Resource-derived
   pack object that owns four `PackHandle`s (+0x3c, +0x48, +0x54, +0x58) and restores the Fs_Resource
   base vtable 0x0077F6C4. Names: `vtable`, `packHandle`.

## Decisions (orchestrator not available)

* Kept the generated `class`/`type` keys for all four classes (the merge rejects unknown classes and
  the type names are already used in recovered signatures such as `PackEntry*`/`PackHandle`).
  Where the generated name is doubtful (`Pack_ResourceChain`, `Pack_Entry`) the doubt is stated in
  the class summary/evidence instead of renaming.
* `Pack_HandleTable.size` kept at the batch's 600. It is consistent with the layout found
  (`26*4 handles at +0x38` + `26*0x10 slot records at +0xa8` + list words up to +0x258) and with
  `Ui_SceneFlow`'s `Pack_HandleTable*` member; it is **not** the 0x2C64-byte named-object cache
  discussed below.
* Slot-record fields are named per-index (`slot7RefCount`..) instead of inventing an array name that
  the batch does not contain; the evidence text repeats the record layout so a modder can rebuild
  the `struct { u32 refCount; u32 packId; u32 word8; u32 tag; } slots[26];` view by hand.
* Everything I could not honest-name got `maybe_` and confidence < 0.5 (the three list pairs,
  `maybe_slot1UiHandle`, `maybe_slot1PackTag`, `maybe_baseStateA/B`). Nothing was invented.
* Deliberate honesty: `Pack_HandleTable_Get` (0x0010AF94), which the batch lists under
  `Pack_HandleTable`, actually allocates a 0x2C64-byte object whose 0x28-byte buckets are consumed by
  `Fs_NamedObject_GetOrCreate` (`iVar12 = parent + key*0x28`, `iVar12->f_1c/f_20`). That is the
  file-system named-object cache, not the 600-byte handle table. The caveat is recorded in the class
  `evidence`; the function itself is outside this task's ownership (function naming).

## What is NOT verified / open problems

* The three intrusive containers (+0x14/+0x18, +0x24/+0x2c, +0x24c/+0x254) are named only as
  end-marker/first-node pairs from the loop conditions in `Pack_HandleTable_ReleaseObjects`,
  `ReleaseAll` and `UpdateRelease`. I did not recover which container is a list and which is an
  rb-tree (ReleaseAll erases with `std_RbTree_EraseNode`, ReleaseObjects advances with `node[1]`),
  nor the container element types. Confidence 0.40–0.45, all `maybe_`.
* `maybe_slot1UiHandle` (+0xc0) and `maybe_slot1PackTag` (+0xc4): the writes are proven (0x0055DBB0
  with slot index; copy of pack object +0x64) but the semantic is not. 0x0055DBB0 has no readable C.
* `Pack_HandleEntry`'s real size is much larger than 24 (the ctor appends 20 x 0x28 bytes at +0x1c and
  the allocation is 0x2C64); the batch's 24-byte size covers only the multiple-inheritance head. A
  follow-up should give that sub-handle array its own class (the element ctor is 0x001150A0).
* `Pack_Entry`'s identity: only a deleting destructor was recovered, so `+0x58/+0x5c/+0x60/+0x64`
  (part pointer/size/format id/tag) come from the *other* class's functions (`Pack_AcquireResourceHandle`,
  `Pack_HandleTable_Add/LoadCommon`) that accept the same RTTI; they are not in this batch.
* `Pack_ResourceChain` is almost certainly a wrong class name for an Fs_Resource-derived D1; only the
  vtable and the last handle are attributed here.
