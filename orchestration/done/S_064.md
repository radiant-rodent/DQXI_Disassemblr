# S_064 - Party struct field naming (batch S_064)

## What I did

Named the single class and all 17 field offsets of `orchestration/types/batches/S_064.json`
(subsystem Party):

**Party_Status / `PartyStatus`, size 0x4B34 (19252), base None, class confidence 0.65**

The object is the party-status / field-marker overlay controller stored at `(work+8)->f_48`.
It owns up to 12 character marker rows (0xC stride: model handle at +0x210, charId at +0x214),
the live row count (+0x274), the enable/mode bytes (+0x27C..+0x27E), the display variant
(+0x27F), the selected page word (+0x281/+0x282), two state-effect handles (+0x14/+0x18),
the initialization byte (+0x10), the marker-creation gate (+0x11), the three vertex-strip
buffers of its embedded ribbon trail (+0x4A2C/+0x4A30/+0x4A34), and a three-byte
pending-actor-registration block (+0x4AE0/+0x4AE1/+0x4B30).

Key evidence chain:

- `Ui_OverlayManager_Reset` 0x00235848 is called with `self->f_48` (= `(work+8)+0x48`) by the
  scene-work teardown 0x0019ECE4; `Party_Status_AddMember` 0x00239510 gets the same
  `(work+8)+0x48` from `PartyAdd` 0x001653BC; `Party_Status_SelectPage` 0x00239A94 gets it
  from `Ui_Overlay_ApplySlotSetup` 0x00235E0C.
- `Ui_Overlay_Update` 0x0023D988 gates on +0x10; `Ui_Overlay_AddEntry` 0x0023E4A8 gates on
  +0x11 and uses +0x274 as the row count; rows are at +0x210/+0x214, stride 0xC.
- `Ui_Overlay_ApplySlotSetup` calls `Gfx_Trail_ResetSamples(self,...)`, which writes the
  0x39 x 0x30-byte sample history at self+0x3F80 and submits the 25-pair strip through
  `func_006F511C(&self->f_4A2C, template, buffer)`; hence +0x4A2C/+0x4A30/+0x4A34 are the
  vertex-strip buffers, not a mistyped `self`.

## Decisions (orchestrator was not available)

1. Kept the generated `class` key `Party_Status` and `type` `PartyStatus`. `apply.py` rejects a
   class that is not in `structs.json`, and four other batches (G_002, G_015, G_050, G_055)
   already reference `PartyStatus`. The current decomp names for the same methods are a mix of
   `Party_Status_*` and `Ui_Overlay_*`; the summary/evidence state that the object is the
   field-marker / party-status overlay so a later rename pass can decide.
2. Raised `size` from the batch's 644 to 0x4B34. 644 is only "highest strong field + width";
   the same `self` reaches +0x4B30 (read in `Ui_Overlay_Update`) and `structs.json` already
   records `size_min = 19249`. A 644-byte struct would truncate every trail and registration
   field.
3. Treated the six `weak` high offsets as real fields. `Ui_OverlayManager_Reset` allocates all
   three buffers on `self` with `Mem_AllocAligned(800/100/100, heap, 4)`, checks them for null
   and frees them via `func_0010F69C`; `Ui_Overlay_Update` reads `self+0x4B30`. This is
   allocation/read evidence on the same object, not a typo'd `self`.
4. For +0x4A2C I reused S_047/Gfx_Trail's `vertexStripBuffer` name for cross-batch consistency,
   but deliberately did **not** reuse S_047's `isVertexStripReady` (+0x4A30) and
   `vertexStripCount` (+0x4A34): Reset proves both are separately allocated 100-byte buffers.
   The real 25-entry count is at +0x4A38, which is outside this batch.
5. +0x281 is written as a 16-bit word (`self->f_281 = *(u16*)sel`) yet compared byte-wise in
   six other functions. Emitted as u16 `pageAndMode` plus its sub-byte +0x282 `modelPartsMode`,
   the same overlap pattern already used by other S_ batches (e.g. S_002/S_007).

## Open problems / not verified

- `Party_Status` and `Gfx_Trail` (S_047, size 19000) are almost certainly the **same physical
  object**: both describe the +0x3F7C..+0x4B30 trail layout, and Gfx_Trail has holes exactly at
  the low offsets used here (+0x10/+0x14/+0x18, +0x274...). The type DB emits them as two
  classes. A follow-up should decide whether `PartyStatus` embeds/derives from `GfxTrail` or
  whether the two classes should be merged; until then both structs are emitted with the same
  tail layout.
- S_047's +0x4A30 `isVertexStripReady` and +0x4A34 `vertexStripCount` are contradicted by the
  `Mem_AllocAligned` calls in 0x00235848; worth a small correction batch.
- +0x4AE0/+0x4AE1/+0x4B30 are named `maybe_` (conf 0.3-0.4): Ui_Overlay_Update proves they
  select which embedded actor record (+0x4A88 vs +0x4AE4) is re-registered, but the records
  themselves are not decoded.
- +0x14/+0x18 (`maybe_closedStateEffect`/`maybe_openStateEffect`) are proven effect/actor
  handle values (created by effect factories, resolved through the 0x007B80C0 handle table,
  receive animation calls), but their exact visual role is inferred from enable/disable state.
- Emulated verification was neither needed nor performed for this naming batch.
