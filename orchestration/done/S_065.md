# S_065 - Regex struct field naming (batch S_065)

## What I did

Named both classes and all 6 field offsets of `orchestration/types/batches/S_065.json`
(subsystem Regex). The subsystem is the game's own small regex engine, used by the NG-word /
masked-pattern text filter (`Text_NgWord_MatchWord` 0x005145E8, `Text_MaskPatternMatches`
0x005150B4).

**Regex_State / `RegexState`, size 0x18 (24), base None, class confidence 0.60**

This is **not** a state node. It is the compiled automaton container that every
`Regex_State_*` method takes as its first argument, and the readable C already calls the same
object `RegexMatcher`. `Regex_Match_Build` (0x005133C8) proves the layout:

```
*m    = allocator            /* 0x00 */
m[1]  = state list head      /* 0x04 next, 0x08 prev; sentinel is m+1 */
m[3]  = *m                   /* 0x0C copy of the allocator, used for state nodes */
m[4]  = key count            /* 0x10 */
m[5]  = key array            /* 0x14 */
```

Fields named:

- `+0x10 keyCount` (u32, 0.90) - counted from the parsed key list, sizes the visited bitset as
  `(keyCount+15)>>4` 16-byte blocks (`Regex_Buffer_Init(...,m[4],...)`) and bounds every key
  loop in `Regex_State_CollectEdges` / `SplitOverlappingClasses` / `DeduplicateKeys`.
- `+0x14 keyArray` (void*, 0.80) - `keyCount*4` bytes filled with the key-node pointers;
  `Regex_State_CollectEdges` dereferences each entry as a node whose child list head is at
  +0x08/+0x0C, and the final pass of `Regex_Match_Build` compares each entry with the accept
  key node.
- `+0x90 unknown_misscaledStateBitset` (u32, **0.00**) - phantom, see decision 2.

**Regex_Set / `RegexSet`, size 0x0C (12), base None, class confidence 0.85**

A character-class range set: an intrusive circular list of sorted, disjoint
`(u16 start, u16 end)` code-unit ranges. The set object itself is the list sentinel, so the
first two words are the head links.

- `+0x00 rangeListNext` (void*, 0.80) - `Regex_Set_AddRange` inserts with
  `node->next = *set; node->prev = set; *set = node; node->next->prev = node`;
  `Regex_Set_Normalize` resets it to the set address when the list is emptied.
- `+0x04 rangeListPrev` (void*, 0.80) - every walk starts at `set[1]` and follows `node[1]`
  (node->prev) until the node address equals the set (`Regex_Set_RemoveChar`,
  `Regex_Set_Subtract`, `Regex_Set_AddList`, `Regex_Set_Normalize`).
- `+0x08 allocator` (void*, 0.85) - first argument of the 16-byte block allocator 0x00514390
  and of the matching free 0x0051435C for every range node. `Regex_Set_Normalize` saves it to
  a local, zeroes it while emptying the list and restores it, so it is 0 only while the set
  has no nodes.

## Decisions (orchestrator was not available)

1. **Kept the generated `class`/`type` keys.** `apply.py` rejects a class that is not in
   `structs.json`, and `RegexState` / `RegexMatcher` are already used in recovered signatures
   (`Regex_State_CollectEdges(RegexMatcher* m, RegexState** state)`). The fact that
   `Regex_State` is really the matcher container is stated in the summary and evidence rather
   than renamed here; see follow-up 1.
2. **Lowered `size` from the batch's 148 to 24.** Offset 0x90 is a `struct_db.py` scaling
   artifact: its `ADDR` regex matched `*param_2 + 0x24` and multiplied by 4 because `param_2`
   is a pointer-to-pointer, so the real access is `(*state)->f_24` - the state node's key
   bitset pointer, not a member of this object. The evidence entry has `sizes_seen: []`,
   `reads: 0`, `writes: 0`, and no `0x90` appears anywhere in the five raw Ghidra bodies. The
   offset is still emitted (as `unknown_misscaledStateBitset`, confidence 0.0) because the
   batch requires every offset exactly once; the merge therefore still emits
   `sizeof(RegexState) == 0x94` with a 0x78-byte hole, which is unavoidable from this batch.
3. **`0x00514390` is a 16-byte block allocator, not a counter.** Read from
   `asm/text/text_00500048.s`: it scans a bitmap for `n` free bits, sets them and returns
   `base + offset*16`. That is why every `func_00514390(pool, n)` call allocates `n` 16-byte
   blocks (`(keyCount+15)>>4` for a bitset, `1` for a 16-byte list node, `3` for a 48-byte
   state node). This is what makes `set[2]` and `*m` allocators rather than counts.
4. **`Regex_Set` is a set, not a list of pairs.** The seven methods are exactly the character
   class algebra (AddRange / AddList / AddPredefinedClass / RemoveChar / Subtract / Intersect /
   Normalize), and `Regex_State_DeduplicateKeys` / `SplitOverlappingClasses` call
   `Regex_Set_RemoveChar` / `Intersect` / `Subtract` on `node+0x10` of a class node, so the
   set is the value of a regex class node.
5. **`void*` for the two pointer fields.** No class in `structs.json` describes the key node or
   the range node, so a named pointer type would have been invented. The evidence text says
   what the pointer points at.

## Open problems / not verified

- **`Regex_State` is misnamed.** The object is the matcher/automaton; the per-state node is a
  separate 48-byte structure (`+0x00` next, `+0x04` prev, `+0x08` own key node, `+0x0B` accept
  flag, `+0x14`/`+0x18` child list head, `+0x1C` child-node allocator, `+0x24` key bitset).
  That node is not a class in `structs.json`, so its fields could not be named in this batch.
- **`sizeof(RegexState) == 0x94` is wrong** and comes only from the phantom 0x90 field. The
  real object is at least 0x18 bytes; nothing in the five methods touches 0x18..0x8F.
- `keyArray` element type is `void*` because the key-node class does not exist in the type DB.
  The evidence (child list head at +0x08/+0x0C, `Container_Value_SetFromRef` copy) is solid,
  but a follow-up should introduce the node class and retype the field.
- `Regex_Set`'s `allocator` is 0 while the set is empty (`Regex_Set_Normalize`). Whether the
  original code really stores the pool in the set or in a shared context is not proven; the
  alloc/free call sites are unambiguous, the lifetime is inferred.
- The `maybe_`-prefixed methods `maybe_Regex_State_BuildRecursive` (0x005131E4) and
  `maybe_Regex_Set_Intersect` (0x00513DA4) are damaged decompilations (`halt_baddata`,
  `unaff_r4`); nothing in this batch depends on their bodies beyond the shared field layout,
  which `Regex_Match_Build` and `Regex_Set_AddRange` prove independently.
- Emulated verification was neither needed nor performed for this naming batch.

## Suggested follow-up tasks

1. Rename the class `Regex_State` -> `Regex_Matcher` (and `RegexState` -> `RegexMatcher`) in
   `structs.json` / the M1 names, and rename the per-state node class to `Regex_State`. The
   readable C already uses `RegexMatcher` for this object in three signatures, so the type DB
   is the only place that disagrees.
2. Add the 48-byte state node and the 16-byte range node as classes so `keyArray` and the
   `Regex_Set` list links can be typed instead of `void*`.
3. Fix `tools/typedb/struct_db.py`'s `ADDR` path: when the base is a pointer-to-pointer
   (`*param_2 + 0x24`), the offset is byte arithmetic on the dereferenced value and must not be
   scaled by the element width. This produced the phantom 0x90 here and probably similar
   phantom fields in other S_ batches.
4. Name `0x00514390` / `0x0051435C` (`Pool_AllocBlocks` / `Pool_FreeBlocks`) and
   `0x005128A4`, `0x0051093C`, `0x005108A4` - they are the shared 16-byte block pool and the
   bitset helpers used by the whole regex subsystem and are still `func_*`.
