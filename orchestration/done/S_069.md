# S_069 — name the 13 Sound classes and their fields

**Status:** completed (naming batch; no code changes, no rebuild run by design)

## What I did

Named every class and every field of the 13 classes in `orchestration/types/batches/S_069.json`
(subsystem **Sound**): **13 classes / 351 fields**, each batch offset named exactly once.

Output: `orchestration/types/out/S_069.json` (only file changed besides `AGENT_LOG.md` and this report).

Method: read the readable C of each class's ctor/reset, then its update/draw-ish methods, then
cross-checked with the disassembly (`tools/fn.py --asm`) where the C was ambiguous; used
`structs.json` for the type names of the objects the fields point at. `tools/fn.py` dossiers
callers/callees were enough — no tree walks, no new caller-search scripts.

## What the subsystem turned out to be

A CTR-Sound-style engine, not Nintendo NW4C:

| Class | Identification (evidence) |
|---|---|
| `Sound_WaveBuffer` (264) | per-sub-channel DSP wave buffer. `Sound_WaveBuffer_Reset` writes sample rate `0x7FD8` = 32728 Hz at `+0x20` and the 1.0f gains; `ComputeLayout` lays out the 0x280-byte chunks at `+0x3C..+0x80`; `BuildChannelParams` converts them into the `0xA0`-scale fixed-point steps/volumes/pans at `+0x9C..+0xEC`. `Sound_Channel` holds the pointer at `+0x68`. |
| `Sound_StreamBuffer` (96) | stream DMA buffer object: vtable `0x7816D8`/`0x7816F8`, four 0x10-byte descriptors at `+0x08`, 1.0f pair `+0x48/+0x4C`, one-shot flag `+0x59`, adjusted secondary vtable `+0x5C`. |
| `Sound_RingBuffer` (16) | plain word ring buffer: data `+0`, capacity `+4`, write cursor `+0xC` (wrap in `Sound_RingBuffer_Write`). |
| `Sound_WaveArchive` (524) | BCSAR loader/cache front end: archive handle `+0x4`, load refcount `+0x208`, pending flag `+0x20A`; entry resolution via vtable `+8`/`+0x10`. |
| `Sound_Stream` (13720) | **BCSTM streaming decoder** (`SetBufferStride` validates `0x4D545343` = "CSTM"): file reader `+0x14` (vtable `+0x24` read / `+0x40` seek), stream-info block `+0x18`, loop start/end `+0x28/+0x2C`, loop-start callback `+0x30`, read cursors `+0x58/+0x5C/+0x60`, embedded `Sound_Mixer` at `+0x2314`, thread-started byte `+0x328E`. |

| `Sound_Track` (548) | sequence track: vtable `0x781C90`/`0x781BD0`, four 0x10-byte sub-objects at `+0xF4`, per-voice pitch/volume/pan block `+0x138..+0x19C` (1/127 normalisation proves MIDI 0..127 volume/pan), channel index/owner `+0x1A0/+0x1A4`. |

## Decisions / judgement calls

1. **Kept the generated class names and types**, including the inconsistent `Sound_Stream` /
   `Sound_Voice` types (the project's readable C and `structs.json` already use them).
2. **Merged clusters.** The batch clusters sometimes mix two objects: `Sound_Voice` mixes the
   612-byte voice ctor with the stereo PCM channel struct used by `StartPcmStream`/`Stop`/
   `UpdateVolumes`, and `Sound_Stream`'s tail `+0x3574..+0x3594` belongs to a vtable-bearing
   sub-object polled by `Sound_Stream_UpdateBuffer`. I named what is consistent across functions and
   left the rest `unknown_*` at confidence 0.0 instead of inventing a purpose.
3. **`Sound_WaveArchive` `+0x40`** is deliberately `unknown_40`: its "evidence" lines are virtual
   calls through `(*self + 0x10)` (vtable slot 4), not a member — a real Ghidra/DB trap.
4. **Width conflicts.** Where a 4-byte guess would overlap the next batch offset (`Sound_WaveBuffer`
   `+0xC`, `Sound_Stream` `+0x24`, `Sound_Voice` `+0x14`, `Sound_Track` `+0xC`, …) I shrank it to the
   actual gap (`u8`/`u16`/`u8[3]`) and said so in the evidence, so the struct emitter keeps every
   member at the right offset.
5. `Sound_WaveBuffer` `+0x14`/`+0x18`/`+0x28`: `Init` treats them as an aligned buffer base + size
   (zero-filled with `__aeabi_memclr`), while `Reset`/`ComputeLayout` use the same slots in a
   parameter-block idiom. The ambiguity is recorded, confidence 0.3, `maybe_` prefix.
6. The ambiguous 1.0f/0 pairs in `Sound_Voice`/`Sound_Track` are named by structural role
   (`maybe_volumeA/B`, `maybe_*TargetA/B`), never by a guessed DSP meaning.

## Open problems / not verified

* The exact meaning of the `Sound_Voice` gain/target pairs and of `Sound_Track`'s `+0x150..+0x170`
  block is not verified (all `unknown_*`/low confidence).
* `Sound_ArchiveStream` `+0xCC..+0x108` and `+0x3C/+0x50` are unverified (unknown).
* `Sound_Stream` `+0x68/+0x70/+0x88/+0xF8/+0x100/+0x118` are only touched through unnamed CRT/GUI
  helpers and stay `unknown_*`.
* `Sound_StreamBuffer` `+0x48/+0x4C` are inferred as default gains from the 1.0f seed only.
* No emulator/real-hardware check was needed or done (pure data naming).
