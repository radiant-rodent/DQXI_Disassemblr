# S_070 - Sound subsystem classes and fields

**Task**: name the 8 classes and every field of `orchestration/types/batches/S_070.json`
(subsystem `Sound`).
**Output**: `orchestration/types/out/S_070.json` - 8 classes, 417 fields, every batch offset
covered exactly once.

## Status: resumed and completed

A previous worker named all 8 classes and all 417 fields and appended `AGENT_LOG.md` Entry 415,
but stopped before writing this report. I audited the existing JSON against the batch, re-ran the
project validator, corrected two evidence strings, and wrote this report. The per-field naming is
the previous worker's work; the section "What I verified myself" is mine, and I say explicitly
below what I did **not** re-derive.

## Result in one line

The batch is the Nintendo 3DS SDK sound library (`nn::snd`, a Wii snd port) plus one game-level
object. Two of the eight "classes" are merges of several different objects (`Sound_System`,
`Sound_Channel`) and one merges three stream classes (`Sound_StreamPlayer`); three batch offsets
are phantoms from `struct_db` mis-parsing and are emitted as `unknown_*` at confidence 0.0.

## What I verified myself

1. **Coverage.** All 8 classes present; the class set equals the batch; every one of the 417 batch
   offsets appears exactly once; no duplicate offsets and no duplicate field names inside a class.
2. **Class metadata.** `type`, `size` and `base` match the batch for all 8 classes.
3. **Project validator.** `python3 tools/typedb/apply.py --validate` reports **0 errors and
   0 warnings for S_070** (the single remaining error is `S_066 Save_SlotUi@0x324 unknown type
   'UiWindow'`, another worker's batch).
4. **Type naming.** `Sound_SeqNote` is written as type `SoundSeqNote`, which is the underscore-free
   form required by the task and already declared in `include/recovered_types.h:1072`
   (`typedef struct SoundSeqNote SoundSeqNote;`). The same convention is used by S_071 for
   `Sound_Stream_Request -> SoundStreamRequest`.
5. **`Sound_System +0x04` / `+0x08` (the one contested field).** `Os_LightEvent_Init` (0x00111CD8)
   initialises an 8-byte `nn::os::LightEvent`: state word at `+0`, `LightLock` gate at `+4`, state
   set to `-2` (`0xFFFFFFFE`, CLEARED_STICKY manual reset) and the gate to `1` via `func_00117C40`.
   The constructor calls `Os_LightEvent_Init(self+4, 1)`, so the event really is at `self+4` with
   its gate at `self+8`. `Sound_System_Teardown` gates on bit 0 of the state word, which is 0 while
   the state is `-2` and 1 once the event has been signalled - so the two readings are consistent,
   not contradictory.
6. **`0x00550808` is a constructor, not a mutex lock.** The readable C stores a vtable
   (`*mutexObj = 0x00781BD0`), initialises ~20 fields and ends with `return mutexObj;`. The
   `Sound_System_LockMutex` name (N_092) comes from the trailing `Os_MutexLock` call and is wrong.
7. **Vtable `0x00781BD0`.** Read directly from `asm/rodata/rodata_00765000.s`: 26 slots
   (`0x00781BD0..0x00781C34`), slot 16 = `0x005517D0` `Sound_Stream_DispatchDma`, slot 21 =
   `0x005518F4` `Sound_Stream_SubmitDmaCommand`. No class in `structs.json` claims this vtable.

## What I changed

Two `evidence` strings in `Sound_System`, both factual corrections; no name, type, size, offset or
confidence was touched:

* `+0x04` - now states the exact LightEvent state value (`-2` / `0xFFFFFFFE`) and explains why the
  teardown's `& 1` gate works.
* `+0x08` - previously said the gate is "cleared by the constructor"; `Os_LightEvent_Init` actually
  sets it to **1** through `func_00117C40` (`LightLock::Initialize`). Corrected.

## The three phantom offsets

| Class | Offset | Why it is not a field |
|---|---|---|
| `Sound_Channel` | `+0xD0` | only evidence is `FUN_00117E50(param_1 + 0x34)` with `param_1` an `int`, i.e. byte `0x34`, not `0xD0` |
| `Sound_Emitter` | `+0x330` | only evidence is the vtable dispatch `(**(code **)(*param_1 + 0xCC))(...)`, which `struct_db` read as the array element `param_1[0xCC]` |
| `Sound_Emitter` | `+0x340` | same cause, slot `+0xD0` |

All three are emitted as `unknown_*` with `confidence: 0.0` and the reason in `evidence`, per the
"never invent a purpose" rule.

## Decisions

* **Kept every generated class name and type.** `apply.py` resolves classes against `structs.json`
  and rejects renames, so the real identity and the merges live in `summary` + `evidence`.
* **Batch evidence lines are unreliable.** `struct_db.py` maps `param_1[N]` to `N*4` and
  `param_1 + N` to `N`, but the raw Ghidra sources use `int param_1` (byte offsets) in most
  functions and `undefined4* param_1` in others, so the same expression can mean two different
  offsets. The previous worker re-derived every offset from the raw
  `decomp/ghidra/functions/FUN_*.c` with `out/scratch/S_070/raw2.py` instead of trusting the batch.
* **Widths corrected** where the batch default of 4 would overlap the next offset: `u8`/`u16` at
  `Sound_SeqNote +0x84`, `Sound_Channel +0x34/+0x36/+0x6C`, `Sound_System +0x2C/+0x34/+0x35`.
* **Nothing invented.** A real member whose purpose is not established is `unknown_*` at 0.0 with
  the constructor/teardown access quoted, never a guessed purpose.

## Not verified

* **The 35 `unknown_*` fields** (18 in `Sound_System`, 13 in `Sound_Channel`, 2 each in
  `Sound_SeqPlayer` and `Sound_Emitter`). Most are only cleared by a constructor or teardown and
  have no reader in this batch, so their purpose is genuinely unknown.
* **The `Sound_Channel` four-object split** is inferred from four disjoint field families, not from
  an allocation. The class-level confidence is 0.3 for that reason.
* **The `Sound_StreamPlayer` three-vtable merge** - three constructors store three different
  vtables, so the entry covers more than one concrete class.
* **The `Sound_System` low offsets `0x1C..0x3C`** are only cleared by the constructor at
  `0x00550808`, which probably belongs to a different object than the `0x1AB0`-byte manager the
  teardown describes. The class-level confidence is 0.35 for that reason.
* **`Sound_SeqNote +0x0C`** owner pointer - probably inherited from the `Sound_Voice` base.
* I did **not** re-derive the per-field naming of the other 415 fields; I audited structure,
  metadata, types and the one contested field, and spot-checked `Sound_Emitter` and `Sound_System`
  field by field.

## Suggested follow-up tasks

1. **Split `Sound_Channel`** into the four real objects: the 24-slot channel pool (mask `+0`,
   head `+4`, tail `+8`, count `+0xC`, monitor `+0x10`), the per-slot channel node, the DSP unit
   manager (per-unit hooks `+0x14+sub*4`, active flags `+0x30+sub`, mixer states `+0x34+sub*8`)
   and the wave definition. The batch merged them because they share the `Sound_Channel_*` prefix.
2. **Split `Sound_System`**: the constructor at `0x00550808` builds a small object (vtable
   `0x00781BD0`, fields up to `+0x3C`) that is almost certainly a `Sound_Stream`-family class, while
   `0x001EE09C` tears down the `0x1AB0`-byte game-level sound manager. Identify the owner of vtable
   `0x00781BD0` (26 slots, slots 16/21 are `Sound_Stream_DispatchDma` / `Sound_Stream_SubmitDmaCommand`)
   and register it in `structs.json`.
3. **Fix `tools/typedb/struct_db.py`**: it turns `(**(code **)(*p + 0xNN))(...)` into `p[0xNN]`
   (offset `4*NN`) and it mixes `int param_1` byte offsets with `undefined4* param_1` word offsets.
   Both produced phantom fields in this batch and probably in others.
4. **Find readers for the 35 `unknown_*` fields** by following the objects from their owners
   (`Sound_SeqPlayer` for the sequencer fields, the channel pool for `Sound_Channel`) rather than
   from this batch's function list.
5. **Rename `0x00550808`** from `Sound_System_LockMutex` to a constructor name once its class is
   known; the current name is actively misleading.
