## Open problems / honest uncertainty

1. **`tools/typedb/struct_db.py` offset-scaling bug (important, affects other batches too).**
   `element_width()` returns `param["width"]` for a pointer parameter, and `parse_signature`
   sets `width = 4` for *every* pointer. For functions whose self is declared `char *` the
   offsets are therefore emitted as `4 x` the real byte offset. In this batch: 
   `Sound_Decoder` 480/496/512/528/544 (real +0x78/+0x7C/+0x80/+0x84/+0x88),
   `Sound_AdpcmChannel` 64/80/112/128 (real +0x10/+0x14/+0x1C/+0x20) and
   `Sound_Mixer` 0 (byte, unaffected but scaled by width 1 because it is `char *`).
   I kept the batch offsets (so nothing is dropped) and marked each affected field
   `PHANTOM` / `REAL OFFSET +0xNN` in its evidence. **Suggested follow-up:** fix
   `element_width()` (`char`/`u8` → 1) and regenerate S_071 (and any other batch that had a
   `char *self` function), then re-run the merge.
2. **Sound_PlayerSlot** is only observed through `Sound_PlayerSlot_Clear` (a half-page of
   zero stores); `ResetAll`, `ClearBusyBit` and `ClearFlags` are damaged Thumb splits
   (`halt_baddata`), so 13 of its 16 offsets stay `unknown_*` at 0.0. Its reported size 64
   is also too small for the ring buffer initialised at +0x3C (`FUN_00116AE0(self+0x3C,
   0x100)`).
3. **Snd_StreamSlot** has exactly one function (0x00105584) and it is a damaged ARM/Thumb
   split (`unaff_r4`, raw coprocessor accesses); the slot-record layout (0x24 stride) and
   the three counters are inferred from the surrounding reads, not from a clean ctor.
4. **Sound_ChannelWork** is the `nn::err` FatalErrInfo record, not a sound structure (its
   only function, 0x0051CBF8, is the constructor listed in the established facts). I kept
   the generated class name (apply.py resolves names against structs.json) and said so in
   the summary, but the class is really mis-attributed — a rename pass should move it.
5. **Sound_SequencePlayer / Sound_Frame / Sound_Stream_Request** report sizes (84 / 4908 /
   296) that only cover the first member of larger embedded data (16-entry note table from
   +0x3C, 0x260-byte command block at +0x1328, embedded stream at +0x124). The sizes come
   from `size_source = max_strong_field+width`; the real objects are bigger.
6. Unresolved meanings: Sound_Mixer +0x27/+0x38/+0x40/+0x50/+0x51/+0xB94/+0xCF8,
   Sound_Driver +0x1CC and the second release list at +0x1E0 (first node only in the
   batch), Snd_StreamSlot +0xD8/+0xDC, Sound_SequencePlayer +0x08/+0x0C,
   Sound_ChannelWork +0xEE5/+0xEE6/+0xF76.
