# S_073 - Str subsystem class and fields

**Task**: name the 1 class and every field of `orchestration/types/batches/S_073.json`
(subsystem `Str`).
**Output**: `orchestration/types/out/S_073.json` - 1 class, 1 field, offset 0 covered exactly
once.

## Result in one line

`Str_BitBuffer` is **not an object**: it is a raw `u8` bit-packed byte buffer shifted in place by
the title-screen save-code ("Spell of Restoration") encoder/decoder. The single "field" at +0x00
is `buf[0]`, the first byte of that buffer. The JSON says this in the class `summary`/`evidence`
and in the field `evidence`.

## Findings worth keeping

| Item | What it really is | Evidence |
|---|---|---|
| 0x005F01AC `Str_BitBuffer_ShiftRight` | long-branch veneer: pushes `{r4,r5,lr}`, stashes `r0/r1/r2`, `bl #0x005F02E0`, restores the args, pops; the real `bx lr` is missing because 0x005F01D4 (a second prologue) follows in the same symbol | asm at 0x005F01AC..0x005F01D4 |
| 0x005F01D4 (decompiled as 0x005F01AC) | shift-right body: `bits>>3` byte offset, `bits&7` bit shift, copies `next >> (8-shift) \| cur << shift`, then zero-fills the tail | `strb` at 0x005F0218 / 0x005F0264; callers use it for 6-bit save-code symbols |
| 0x005F02E0 | the *other* shift direction (walks from the buffer end: `sub r1,r1,#1`, reads `[buf+size-1]`, `lsl`/`orr`, stores downward). Likely the shift-left counterpart; not named by me (naming is not this batch) | asm 0x005F02E0..0x005F0300 |
| 0x005F02D4 | tiny helper `ands r0,r0,#7; movne r0,#8; bx lr` -> returns 8 when the bit count is not byte aligned, else 0 | asm 0x005F02D4 |
| `SaveCode_Decode` 0x005EF3CC | zero-fills `arg3` (length `arg4`), then loops: shift by 6 `func_005F02E0(arg3,arg4,6)` and OR the 6-bit alphabet index into `*arg3` | readable C |
| `Save_Crypto_SealBlock` 0x005F09A4 | calls `0x005F01AC(&local_20, 3, 1)` on a 3-byte stack scratch | documented evidence line of the function |

## The single batch offset

* **+0x00** - `buf[0]`. All observed accesses are byte-wise: `strb r5,[ip,#1]` at 0x005F0218 and
  `strb r3,[r0,r2]` at 0x005F0264 in the shift body, plus
  `*arg3 = *arg3 | (u8)(iVar4 << 2)` in `SaveCode_Decode`. Named
  `maybe_firstBufferByte` (`u8`, size 1, confidence 0.35). The batch's 4-byte `u32` width comes
  from Ghidra having widened the `u8*` argument; the hardware stores are `strb`.

## Decisions

* **Kept the generated class name/type** `Str_BitBuffer` / `StrBitBuffer`. `apply.py` resolves
  classes against `structs.json`, so a rename would be rejected; the correction lives in
  `summary` + `evidence` (same approach as S_020 `Data_Record` and S_016
  `Container_IntrusiveNode`).
* **Kept `size: 4`** from the batch (max_strong_field+width) instead of inventing a size, and
  said in the evidence that it is a placeholder: callers pass 3-byte locals, not allocated
  objects.
* **Corrected the field width to `u8`** (actual `strb` accesses). The emitter then pads bytes
  1..3, which is honest: no access to them was ever observed.
* **Confidence 0.35** (<0.5) because the *offset* is certain but the object framing is not, so
  the name carries the `maybe_` prefix. Class-level confidence 0.15.
* **Did not** write `include/dqxi/*.h` and did not run `apply.py --validate`, because that writes
  `orchestration/types/merged/report.json`, which this task does not own.

## Not verified

* No emulator/runtime check (naming batch).
* Whether 0x005F02E0 is really "shift left" (it walks from the buffer end and shifts the other
  way) - inferred from the assembly, not from a caller that documents the direction.
* What the 6-bit alphabet (`0x0072EF3C`, 64 `u16` ids) in `SaveCode_Decode` represents; the
  readable C of `SaveCode_Decode` is also visibly damaged (it stores `iVar1`/`iVar2` into the
  literal address `0x0072EF3C`, a Ghidra mis-typing of the table pointer).
* The 3-byte stack scratch in `Save_Crypto_SealBlock` shows a 3-byte buffer, so a 4-byte class
  size is definitely not an allocation size.

## Open problems / suggested follow-ups

1. **Naming batch**: 0x005F02E0 -> a `Str_BitBuffer_*` shift-left name; 0x005F01AC -> a veneer /
   thunk (`Str_BitBuffer_ShiftRightThunk`), because the decompiled body at 0x005F01D4 currently
   lives under the veneer address; 0x005F02D4 -> a small "byte-align bit count (0 or 8)" helper.
   Also fix the mid-symbol split 0x005F01AC/0x005F01D4 in the symbol map.
2. **`struct_db.py`**: skip classes whose only "fields" are `*param_1 = ...` array accesses when
   the class has no ctor, no vtable and no allocation (same lesson as `Data_Record`,
   `Data_PaddingArtifact`). `Str_BitBuffer` is a phantom created purely by the function-name
   prefix.
3. **Re-export `SaveCode_Decode`** readable C: its body writes the literal address
   `0x0072EF3C` as if it were a variable, which hides the 64-entry alphabet table.
