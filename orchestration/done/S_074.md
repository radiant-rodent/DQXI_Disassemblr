# S_074 — type naming batch (subsystem Svc)

## What I did

Named all 7 classes and all 42 field offsets in
`orchestration/types/batches/S_074.json`, writing only
`orchestration/types/out/S_074.json` (19,505 bytes, UTF-8, strict decode + `json.loads` OK).

Batch makeup: 7 classes / 42 offsets (`Svc_Object` 13, `Svc_SyncObject` 8, `Svc_Blob` 7,
`Svc_TimerSub` 7, `Svc_Content` 4, `Svc_CacheIndex` 2, `Svc_Handle` 1).

## What the classes actually are

The "Svc" subsystem here is mostly a **name-based cluster**, not one object family. Three of the
seven records are not standalone classes at all. The real identities:

1. **Svc_Object (1144 B, vtable 0x0075A4DC)** — a service/IO owner object. Its destructor
   `maybe_Svc_Object_Shutdown` (0x001DC080) is slot 0 of vtable 0x0075A4DC and shows the layout
   directly: kernel handle at +4 (svcCloseHandle), a buffered two-word id at +8/+0xC flushed through
   `Svc_Ipc_Send080E0080` by the base dtor 0x00505688 (and forwarded as request words by Cmd1/Cmd3),
   an owner pointer +0x18 with the handle it releases at +0x1C, and two embedded sub-objects: a
   0x007804BC object at +0x20 (the same vtable head as `maybe_Gfx_MoviePlayer_Dtor` 0x001DBFFC) and a
   52-byte `Text_NgWord` state at +0x30 (closed by `Text_NgWord_CloseService` 0x00515058, work buffer
   at +0x34). The batch also lists the separate **8-byte** `SvcObject` wrapper (vtable 0x00780EAC,
   handle at +4) because its `Create*`/`Get*Checked` helpers share the name; the two layouts do not
   overlap (8-byte object has no +0x18..+0x474).
2. **Svc_SyncObject (68 B)** — a seven-kernel-handle bundle. `maybe_Svc_SyncObject_DestroyC`
   (0x0050F0F8) unlinks the embedded `OsHandleBlock` at +0x2C through `Os_CloseHandleAndUnlink`
   (0x00111E44) and closes +0x00/+0x08/+0x10/+0x1C/+0x24/+0x40 with svc 0x23; DestroyA/B
   (0x00509A20/0x00509B40) are the smaller variant that owns only +0x14. The sibling is waited on by
   the icon-cache code near 0x0050A714.
3. **Svc_Blob (320 B)** — the loaded **icon-cache block archive**. `maybe_Svc_Blob_Serialize`
   (0x00658B28, called by `Ui_IconCache_WorkerThread` 0x004121B4) copies a 0x70-byte header, 16 inline
   0xC-byte block entries at +0x70..+0x130 (size at +4, pointer at +8), then payload (+0x138, size
   +0x134) and a 0x20-byte trailer (+0x13C). `FindRecordByName` (0x0065945C) uses the parsed index:
   header pointer +0xC (count at +8), name pool +0x10, 0x3C-byte record array +0x18.
4. **Svc_TimerSub (1348 B)** — the per-frame timer template shared by UI windows, recovered from the
   24-slot variant 0x00316250 (vtable 0x00763034 slot 1); the same template appears with 5 slots in
   `maybe_Ui_DungeonWindow_Update` (0x002E9614). It calls the shared core virtual at +0x98 slot +0x2C,
   advances a 1/30 s clock (+0x124 f32, +0x128 integer ticks), fires the due timer from the 0x18-stride
   entry array at +0x11C via the member-function adjustor table at +0x13C, and clears a UI mode word
   in `Ui_GetCore()` when +0x540 is set.
5. **Svc_Content (188 B)** — an **archive mount record** (plain fs code, not a service):
   `maybe_Fs_Archive_OpenRecordByPath` (0x00504AE0) passes `&self->f_20` to `Fs_Archive_ResolvePath`,
   `&self->f_48` to `Fs_Archive_FindFile` and `&self->f_b8` to `Mem_PoolAllocNode`. `Fs_Archive_FindFile`'s
   own doc confirms the file table is exactly 0x28 bytes after the directory table at +0x20, so
   +0x20..+0x48 is the 0x28-byte directory table and +0x48..+0x70 the file table. +0xB0 is a base data
   offset added to every resolved entry, +0xB8 the block pool for the 0x30-byte accessor nodes.
6. **Svc_CacheIndex (964 B)** — the **icon-cache index**: `Ui_IconCache_WriteIndexTable` (0x00658618)
   uses the count at +0x210 for `table == 0` and at +0x3C0 for `table == 1`, then writes one 8-byte
   timestamp record per entry (via `func_00658548` and `func_001009DC`).
7. **Svc_Handle (120 B)** — **not a class**: the only batch access is `Sound_Handle_IsStale`
   (0x006307A4) reading `SoundPlayer + 0x74`. `Sound_Player` (type `SoundPlayer`, 648 B) already exists
   in `structs.json`; the other two clustered functions (0x002BD89C plain interface get/set,
   0x001C3858 handle-object dtor) are unrelated.

## Decisions

- Kept every generated class name/type because `tools/typedb/apply.py` resolves classes against
  `structs.json` and my file may only supply names. The real identity is stated in each `summary`
  and `evidence`.
- **+0xC0 and +0xD0 of Svc_Object are phantoms** (struct_db turned the vtable-slot expressions
  `*piVar2 + 0x30` and `*param_1 + 0x34` into array elements `param_1[0x30]`/`param_1[0x34]`). Emitted
  as `unknown_0xc0` / `unknown_0xd0` at confidence 0.0 with the reason, as the rules require.
- `directoryTable`/`fileTable`/`accessorPool` in Svc_Content are typed `u32` because
  `ArchiveDirTable`/`ArchiveFileTable`/block-pool are not registered `structs.json` types; the
  evidence says they are embedded 0x28-byte structs, not scalars. `baseOffset` is a genuine u32.
- `timerSlots` (Svc_TimerSub +0x11C) is `void*`: the raw code both virtual-calls
  `(*(int*)(self+0x11C))[+0x10]` with `this = self+0x11C` and indexes `self + 0x11C + i*0x18`; the
  exact type of the embedded timer header/array is unresolved, so it is a pointer-sized handle rather
  than an invented struct.
- `Svc_TimerSub +0x98` is `maybe_coreObject` (0.40): nearly every `Ui_*` class has a +0x98 object and
  calls its vtable slot +0x2C, but this template passes no `this`, so I did not claim "owner window".
- `Svc_Handle` is deliberately low confidence (0.30) and its summary says it should be folded into
  `Sound_Player` rather than being a real class.

## Not verified / open problems

- The exact owner class of the 1144-byte `Svc_Object` (movie/notice/media IO owner?) is not proven; the
  embedded sub-object at +0x20 has vtable 0x007804BC, which no `structs.json` class claims.
- `Svc_SyncObject`'s primitive kinds per handle (thread vs event vs semaphore) are unknown; only
  "kernel handle closed with svc 0x23" is certain.
- The true types of `Svc_Content` +0x20/+0x48/+0xB8 (directory/file table, block pool) are described
  in evidence but emitted as `u32` for type-system reasons.
- `Svc_Blob` +0xC/+0x10/+0x18 are read by exactly one function; they are named by role
  (indexHeader/namePool/recordArray) at 0.5-0.55 confidence.
- `Svc_TimerSub` +0x11C's dual use (virtual object + timer array base) is odd; the 0x18 stride and the
  +0x34/+0x38 callback fields inside an entry imply a larger real entry than the stride, which may be
  a decompilation artifact.
