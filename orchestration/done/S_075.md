# S_075 - Text struct/field naming (15 classes, 347 field offsets)

## What I did

Named every class and every field offset of `orchestration/types/batches/S_075.json`
(subsystem Text, 15 classes, 347 offsets) into `orchestration/types/out/S_075.json`.

Method: for each class I read the recovered constructor/update methods (raw Ghidra C in
`decomp/ghidra/functions/` plus the documented readable versions in `decomp/readable/functions/`
and `tools/fn.py` dossiers), then classified each batch offset as one of

1. a real member (named from the code that touches it),
2. a vtable-slot artefact, or
3. a mistyped-self access far beyond the object (emitted as `unknown_<hex>`, confidence 0.0),
4. a real member whose purpose could not be established (also `unknown_<hex>` / low-confidence
   `maybe_*` with the constructor/store evidence quoted).

`font.*`, `text codec` etc. were not touched: this batch only writes the JSON.

## What the Text subsystem turned out to be

* **Text_TalkWindow** - the talk/dialogue window. Its real state machine is not the state word at
  +0x1750 as the batch implied: **+0x1750 is the current line index** (loop counter compared with
  the line count from `FUN_00630D64`), **+0x17FC is the state word**, and **+0x17A0 is an embedded
  popup-entry block** that `Battle_QueueActionMessage` (`0x001FE274`) fills (the whole block
  +0x17A0..+0x19DE, including the effect handles at +0x181C/+0x1820, lives inside it).
  +0x175C is the per-line record (`+0xCE` command kind, `+0xDE` skill id, `+0xD0`, `+0xAA/+0xAC`
  voice ids), +0xF4..+0xFC is a 3-word effect direction vector fed to
  `Gfx_EffectPart_SetDirection`.
* **Text_Window** - the base reveal/advance window. +0xD2 is the "finished" byte; +0x125C is the
  message id read as a signed short; the class is polymorphic although the batch recorded no
  vtable.
* **Text_MessageWindow / Text_MsgWindow** - the message/battle-log window and its per-line state.
  +0x175C is a `CharacterRecord` pointer (fields +0xA6/+0xC9/+0xE5/+0x48 match), +0x1758 is an
  `ItemRecord` pointer (`+0x45` stack limit), +0x1750 is the line index, +0x181C/+0x1820 are the
  two line effect handles stored by `Text_MessageWindow_UpdateLineEffects`.
* **Text_Layout** - the per-member layout engine, and by far the most informative class.
  `Text_Layout_Init` (`0x00459FE0`) is really `Party_StatCalc_ApplyBaseStats`: it loads the member
  record (`func_0035EB98`) into +0x04 (charaId), +0x05 (level), +0x06 (six equipped item ids from
  `func_006292F0`), +0x12 (60 skill ids via `Party_CountLearnedSkills`, `FUN_006291A8`), +0x8A
  (extra skill slots), +0x92..+0xA2 (five words from member+0x1C8..), +0x468/+0x46C..+0x486 (the
  growth-table row, 14 signed accumulators) and +0x6D0..+0x754 (34 character scale floats).
  `AddGlyph` adds the ten u16 spacing values +0x92..+0xA4 into the accumulators, copies
  +0x6D0..+0x754 to the live block +0x310..+0x394, and collects learned skill ids into +0x770.
  `CollectGlyphs` splits the command ids into a spell table (+0xF2D, 40 bytes), skill table
  (+0xEF0, 60 bytes) and an unidentified u16 table (+0xF56, ids < 0xE8).
* **Text_Message** - one formatted message: record pointer at +0x12D8 (+0xE2 action id, +0xE8
  message id) and the popup parameter block at +0x127C.
* **Text_StyleList is not a class**: `Text_StyleList_Insert` shifts 0x44-byte style records at
  owner+0x92F4 (inside the large `Ui_TextLayout`), and the "ctor" `0x00192F84` is already documented
  as `maybe_Ui_InitFourTripleByteSlots` writing at +0x9750.
* **Text_CharList is not text**: its only method `0x002C4004` is `Item_SortIdList` (item-id
  comparator). The 556-byte object is a u16 id array (270 entries) with a count at +0x228.
* **Text_Row** - a 0x58-byte battle message-row descriptor (Text_Row_Init zeroes it); the batch's
  1900-byte size and the 0x768 word come from the larger owner object the same functions are
  called with.
* **Text_SpanCursor** - a real 20-byte polymorphic cursor (vtable 0x00783B88, Next/Prev/
  StepMultiline) over 6-byte span records; +0xC is the direction flag, +0x10 the repeat counter.
* **Text_GlyphCursor / Text_FontManager / Text_Buffer / Text_LayoutState** - small real objects:
  glyph visibility cursor, font-manager singleton (vtable 0x007621BC, intrusive style list, eight
  0x20-byte style slots at +0x10 - so the recorded 16-byte size is too small), the growable
  text-command byte buffer, and the layout init state (vtable 0x0045BFF4, 0xF00-byte work area).
* **Text_WordData** - a serialized word/ruby text record deep-copied and pointer-relocated by
  `maybe_Text_WordData_Copy` (`0x0058FF38`); its recorded 392-byte size is too small (the copy
  writes past +0x2A8), and the eight header words could not be identified.

## Important correction about the batch evidence

The batch frequently reports a field at `4 * k` because the extractor turns a **vtable slot byte
offset** `(**(code **)(*param_1 + 0xNN))` into an array element `param_1[0xNN]`. Those are not
fields. Every such offset in this batch is emitted as `unknown_<hex>` with confidence 0.0 and an
evidence string that names the vtable slot - that is why `Text_TalkWindow`/`Text_Window`/
`Text_MessageWindow`/`Text_Message` have many `unknown_*` entries, and why `Text_Layout`'s
+0x30/+0x120/+0x180/+0x2B0/+0x3A0/+0x430/+0x490/+0x4A0/+0x4C0/+0x4D0 are unknown.

Also, the batch silently drops offsets that the C prints in decimal (`param_1 + 800` = 0x320,
`param_1 + 900` = 0x384); those two words are part of the +0x310..+0x394 block but are not in the
batch, so they are not emitted.

## Verification

* `python out/scratch/S_075/check.py` (imports the real `tools.typedb.apply`,
  `Evidence`, `merge_structs`, `check_identifier`, `normalise_type`):
  `classes 15 fields 347` / `merge issues 0` / `problems 0`.
  The independent checks are: class set identical to the batch, every batch offset exactly once,
  no duplicate names, valid C identifiers, every type accepted by `normalise_type`, and
  `maybe_` iff confidence < 0.5 (`unknown_` exempt).
* The file was re-read with `bytes.decode("utf-8", "strict")` and `json.loads`; max field evidence
  length 238 chars (the dispatcher truncates at 300); class evidence all < 400 chars.
* Full `python tests/run_all.py` and `python tools/verify_project.py` were **skipped on purpose**:
  rule 5 exempts naming batches, and the dispatcher validates the JSON.
* `python tools/typedb/apply.py --validate` was **not** run because it rewrites
  `orchestration/types/merged/report.json`, which this task does not own; the in-process
  `merge_structs` call above reproduces its field/type/name rules without writing anything.

## Open problems / not verified

* Text_TalkWindow: the meaning of +0x1708 (actor popup list), +0x1268/+0x1270 (value list for
  `Ui_PopupEntry_SpawnNumberList`), +0x19D4/+0x19D8/+0x19DC/+0x19DD and +0x18A4/+0x1980 is only
  inferred from the one helper each is passed to.
* Text_Layout: the 14 signed accumulators +0x46C..+0x486 are a per-stat total in growth-record
  field order, but the individual stat names are not confirmed (the growth record is not decoded
  here). The u16 table at +0xF56 holds ids < 0xE8 which does not match the item range 0xB3B, so
  its id kind is unknown. +0xBE8 is only a base address inside the collect block.
* Text_MessageWindow: +0x24/+0x28/+0x2C/+0x30/+0x34 meanings come only from
  `Text_MessageWindow_ResetState`; +0xD8 and +0xB4 are inferred from one helper call each.
* Text_Row: only the 0x58-byte descriptor is understood; the 0x768 word and the row-type probes
  through vtable +0xE8 belong to the larger owner object.
* Text_WordData: the eight header words and the element arrays are unidentified; the recorded size
  392 is wrong.
* The batch's vtable table for Text_TalkWindow (FieldParty_*/Battle_Ui_* slot names) does not match
  the class and was not used.
