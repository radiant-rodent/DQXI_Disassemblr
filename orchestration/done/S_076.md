# S_076 — Text subsystem, 15 classes / 233 fields

## What I did

Named all 15 classes and every field of `orchestration/types/batches/S_076.json`
(`Text_Style`, `Text_Page`, `Text_Block`, `Text_NgWord`, `Text_Renderer`, `Text_LayoutPage`,
`Text_StringView`, `Text_WindowQueue`, `Text_Range`, `Text_CharSet`, `Text_Command`,
`Text_GlyphRenderer`, `Text_Scroller`, `Text_GlyphCache`, `Text_Element`).

Method: read each class's constructor(s) and the methods that touch the disputed fields
(`decomp/functions/<name>.c`, plus the disassembly in `asm/text/*.s` when the readable C was
damaged), then cross-checked widths and defaults against `orchestration/types/structs.json` and
the already-named sibling classes in `orchestration/types/out/S_069.json` (Sound_Track /
Sound_Voice) and `S_070.json` (Sound_SeqChannel). Evidence for every field is in the JSON.

Key findings:

* **Text_Page** is a real, cohesive text page (vtable `0x007803AC`, ctor `0x00192450`):
  intrusive-list node at +4/+8/+0xC, six equipment-slot bytes at +0x11C..+0x121
  (`maybe_Text_ClearCell` resolves each slot with `func_006292F0`), typing clock `+0xDC` and
  reveal deadline `+0x12D8` (read together by `Text_AdvanceTyping 0x00190A7C`), 20- and
  30-entry `0xFFFF`-initialised glyph tables at +0x1274/+0x129C, five packed s16 x/y
  coordinates at +0x1C8..+0x1D8, and two blocks (0x78 / 0x1C bytes) copied verbatim by
  `Text_Page_BuildAtOffset` / `Text_Page_ExportLayout`.
* **Text_NgWord** is the NG-word/profanity validator: `SvcContentObject` service at +0x28,
  0x4000-byte pattern buffer +0x24 (base+0xB000), normalisation buffer +0x2C (base+0xF800),
  mount flag +0x19, character being masked +0x1B.
* **Text_CharSet** is the glyph-set builder: u16 ids appended at self+0xA for item ids
  0..0xB3A via `Item_LookupRecord`, `charCount` at +0x228, vtable `0x007600F4`.
* **Text_Block** and **Text_LayoutPage** are two views of the same 0x3D0C-byte UI
  message/list block; Text_Block is the `Actor_SubObject`-based row container, Text_LayoutPage
  its line builder.
* **Text_Style is not one class.** The batch merged (a) the 0x60-byte TextStyle record from
  `Text_Style_Create 0x001927E0`, (b) a Sound_SeqChannel/Sound_Track-like mixer/envelope block
  at +0x5C..+0x166 written by three constructors that sit inside the Sound module
  (`0x0054EC70`, `0x0054FD50`, `0x00554910`), and (c) a `Text_MsgWindow*` at +0x175C only read
  by the `0x00666xxx` record predicates. Fields 0x8C..0xA8 match Sound_SeqChannel's named
  envelope block (S_070) exactly in offset and width, and the ctor default 0x7F matches a
  full-volume envelope; those are `maybe_*` at 0.30–0.35. Everything else in that class is
  `unknown_*` at 0.0. The summary and class evidence state the conflation and that size 5984
  is max-field+4, not an allocation.
* Three offsets are struct_db artefacts of virtual calls, not fields:
  `Text_Command` +0x490/+0x4A0 (`(**(code**)(*self+0x124/0x128))`) and `Text_CharSet` +0x70
  (`(**(code**)(*self+0x1C))`). They are `unknown_*` at 0.0 with the real vtable slot named.
* **Text_GlyphRenderer** is the type of the global function table at `0x007E8120`
  (`maybe_Text_GlyphRenderer_Setup 0x00556A24` writes five code pointers); the batch only lists
  +0x4..+0x10, so only those four are emitted.
* Text_Command's `+0x175C` is the same message-window pointer as in Text_Page/Text_MsgWindow:
  the popup helper reads pointee +0xDE as a SkillRecord id (0xFF = none).

## Open problems / not verified

* `Text_Style` remains a contaminated class (see above). Its 0x0..0x40, 0x5C..0x70,
  0x74..0x76, 0x100..0x108 and 0x165..0x166 are only initialised by damaged decompilation of
  three audio ctors; I did not invent purposes for them.
* `Text_Page` +0xEC..+0x118 (12 u32): copied as a block to/from the layout run, probably
  colour/attribute words; no colour constant is stored, so they stay `maybe_colorWord*` 0.25.
  +0x12/+0x16 are layout metrics with unknown formula; +0xDA/+0xE6/+0xE8/+0xEA/+0x12DE..+0x12E8
  are only zeroed or set to 0xFF.
* `Text_Block` vs `Text_LayoutPage`: the methods prove a UI list-row/message block, but the
  batch's 0x150/0x170 offsets have no direct access and the five "dtor" variants may be
  different sub-object destructors of the same composite. Low confidence (0.35–0.4) overall.
* `Text_Range`, `Text_StringView`, `Text_Scroller`, `Text_Element`, `Text_GlyphRenderer` live at
  0x0055xxxx–0x00556xxx, i.e. inside the Sound module address range; their generated names come
  from M1, and only their own constructor evidence was used. Text_Element's vtable 0x0078182C
  is not in structs.json, so its true class is unknown.
* `Text_CharSet` offset 0 is the class vtable 0x007600F4 but was not in the batch; I did not add
  offsets outside the batch (apply.py emits the vtable/padding).
* `Text_GlyphCache` +0x17E8 is the end of the 255 × 0x18-byte cache array, not a key field
  (the class is really the 0x18-byte entry type); it is kept because the batch demands the
  offset, named `maybe_cacheArrayEnd` 0.25.
