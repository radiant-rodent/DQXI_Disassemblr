## Decisions recorded

* **Class names kept exactly as generated** (`Text_Font`, `Text_LayoutLine`, …) because `tools/typedb/apply.py`
  resolves classes against `structs.json` and rejects unknown ones. Where the generated name is misleading the
  `summary` + `evidence` state the real object (same approach as earlier S_ batches).
* **The `+0x43E0` "field" of `Text_LayoutLine` is a struct_db artefact.** It comes only from `0x002FCFD4`,
  whose presumed `self` is a page builder of at least `0x4400` bytes (`Text_GlyphCache_FindOrInsert(self+0x43e0)`,
  capacity test at `self+0x580`). I emitted it as `unknown_glyphCache` with confidence 0.0 instead of inventing
  a meaning or letting it enlarge the class (per the "do not trust weak fields" rule).
* **`Text_Font +0x54` is named `maybe_blockCounter`, not "refCount".** It is 0 after heap creation and is
  decremented on every block release; the matching increment is not in this module, so the exact meaning
  (live-block count vs. release count) stays unproven.
* **`Text_LayoutLine +0x24` is `void*`, not `Font_GlyphCache*`.** `Font_GlyphCache`'s vtable has only 8 slots,
  so the called slot `+0x28` cannot belong to it; the pointer's real class is not recovered.
* Batch sizes were kept. `Text_LayoutLine`'s 40 is `max_strong_field+width`, not the true record size
  (the same records use `+0x38`); this is stated in the field evidence so the merge pads rather than truncates
  semantics.

## Open problems / not verified

1. The class of the font/metrics object behind `Text_LayoutLine +0x24` (a vtable object with an int-returning
   slot at `+0x28`) is unknown; a later pass should find the writer of `+0x24` and name it.
2. `Text_Font`'s true identity: both recovered methods are `nn::fnd::ExpHeap` create/free code. It may be a
   font-owned glyph heap, but that is not proven; the class should be re-examined (or renamed in a later merge)
   if more methods appear.
3. `Text_MessageStack +0x594` points at an object whose `[0]` leads to an 8-byte-stride record table
   (count `+0x60`, rows `+0x58`). The record semantics (id `0x2B`) are not recovered.
4. `Text_MessageStack`'s own begin/end (`+4/+8`) and entry layout are not part of this batch's offsets; they are
   documented in the summary/evidence so a later batch can emit them.
5. `0x002FCFD4` is misnamed `Text_LayoutLine_AutoSize` (it is a page/builder "append wrapped line" routine);
   a future refine batch should fix the name and re-home its `self` fields.
