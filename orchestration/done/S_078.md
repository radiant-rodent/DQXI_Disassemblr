## What the subsystem turned out to be

The batch is the **generic UI object layer**, and three of the fifteen "classes" are name
clusters rather than single types.

* **Ui_Object** is the shared base of every window. `Ui_Object_CtorBase` (0x001A66A0) builds the
  intrusive ring at +0x18/+0x1C/+0x20, clears +0x24..+0x44 and sets the byte at +0x48 to 1;
  `Ui_Object_DtorBase` (0x001A6768) releases +0x38 through vtable+4 and unlinks the ring;
  `maybe_Ui_Object_SetDrawPriority` (0x001A6068) stores +0x2C and pushes it into +0x38;
  `Ui_Widget_SetNamedPaneText` (0x001A619C) guards on +0x30/+0x34;
  `Ui_Object_SetNamedDrawParam` (0x001A60B8) reads +0x04 → +0x10 for the pane-name lookup.
  `structs.json` lists **350 vtables** for this class, so every offset above 0x4C is the first
  field of some derived class (Ui_RowObject, Ui_DiveSubObject, Ui_SubObject, Ui_Widget, Ui_Screen…).
* **Ui_ListSubObject** is a `Gfx_ObjectDesc` (0x00193D84: vtable +0x00, second vtable +0x04,
  inline name +0x08, mode +0x18, flags +0x1C, kind +0x20, id +0x24) extended with four default
  blocks copied from the BSS globals 0x007E7000 (3 words) and 0x007E709C (4 words).
* **Ui_AspectObject** is really a six-row list window: `maybe_Ui_RowTable_InitFromRecord`
  (0x003AD38C) writes six 7-byte rows at +0x49 and six 0x14-byte row animation refs at +0x1D.
* **Ui_RenderObject** indexes an array of 0x414-byte render nodes at +0x2C with the byte at +0x28
  and gates the submit on +0xC7C / +0xC80 / +0xC84.
* **Ui_SceneObject** is proven by `Ui_SceneObject_Release` (0x00626BC8): +0x0C/+0x10/+0x14/+0x90
  are four releasable handles and +0x94 is a sound-effect id with 0xFFFF = none.
* **Ui_LayoutObject** is the layout binding record proven by `Ui_LayoutObject_Bind` (0x003E0360):
  owner screen at +0, layout name at +4, bound-layout handle at +0x14.

## Decisions

1. Kept every generated class name and `type`, including the underscore in `Ui_Object` and
   `Ui_OverlaySlotObject` — 28 other `S_*.json` outputs do the same, and `apply.py` resolves the
   type through `structs.json`.
2. `Ui_Object.base` set to `""` so `apply.py` drops the evidence base `ItemList_Iterator`. That
   base came from one contaminated base-ctor call; a UI object does not derive from an item-list
   iterator. `apply.py` turns `""` into `None` explicitly.
3. 76 of the 93 `Ui_Object` offsets are emitted as `unknown_word_XX` / `unknown_u8_XX` /
   `unknown_u16_XX` at confidence 0.0 with the raw access line and the reason, because they are
   provably other classes' fields. The same rule was applied to the 11 unnameable `Ui_TextObject`
   offsets and the 3 unnameable `Ui_ListSubObject` tail words. Nothing was invented to fill a slot.
4. `Ui_AspectObject` +0x49 is typed `u8[4]`, not `u32`: a `u32` member at an odd offset is
   silently realigned to +0x4C by the compiler. The `_Static_assert` / `offsetof` check caught it.
5. `Ui_DiveSubObject` +0x60 and `Ui_SubObject` +0x4C are typed `void*` and named
   `maybe_animRefList`: the ctor passes their address to `Ui_AnimRefList_Ctor`, so they are the
   first word of an embedded 80-byte object that the batch only recorded as one word. Declaring
   the full struct type there would have made the generated `sizeof` a lie.
6. The struct_db's offset attribution is inconsistent — sometimes a byte offset, sometimes a `u32`
   word index (`FUN_00100BE0(param_1 + 0x1c, …)` was filed under +0x70, `param_1[1] = …` under
   +0x354). Those offsets are marked unknown with the mismatch spelled out rather than guessed.

## Open problems / not verified

* The meaning of the four default blocks in `Ui_ListSubObject` (colour vs vector) is unknown; the
  names only record that they are default blocks copied from a global.
* The contents of the 0x414-byte render-node array in `Ui_RenderObject` are not modelled.
* `Ui_TextObject` may not be a glyph object at all: its second function (0x00566560) is a
  `Gfx_ModelInstance` deleting destructor, so the class is only weakly anchored.
* The "dive mini-game" attribution of `Ui_DiveSubObject` rests only on address clustering.
* Six `Ui_Object` offsets (+0x4E, +0x53, +0x55, +0x71, +0x72, +0x8E) fall inside a wider
  neighbouring field and are therefore skipped by the struct emitter (it prints a comment naming
  each one). They are present in the JSON as required.

## Suggested follow-up

* **S0_split_ui_object**: split the `Ui_Object` cluster. `structs.json` has 350 vtables under that
  one name; a per-vtable field clustering (group accesses by the vtable stored at +0x00 of the
  same allocation) would turn the 76 unknown offsets into real per-class layouts.
* **S0_fix_offset_attribution**: `tools/typedb/struct_db.py` mixes byte offsets and `u32` word
  indices when it records a field access. Normalising that would remove a whole class of
  unnameable offsets across every S_ batch.
* **S0_emit_align**: `tools/typedb/apply.py` should refuse (or warn) when a field's type alignment
  does not divide its offset — that is how the `Ui_AspectObject` +0x49 `u32` would have been
  caught without a separate compile step.
