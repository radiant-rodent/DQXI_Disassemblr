## What the subsystem turned out to be (Ui_Window)

allocation. Verified layout anchors:

- **+0x00** vtable — every ctor stores its own table (`Ui_Window_InitBase` → `0x007582B8`,
  `Ui_Window_CtorBase` → `0x0075E540`, `Ui_Window_CtorA` → `0x007594D4`).

## Decisions (and why)

1. **Kept every generated class name and type.** `apply.py` resolves classes against `structs.json`
   and rejects renames; the real (newer) identities are written into `summary`/`evidence`
   (`Ui_ThreeLayoutObject` = item-select window, etc.).
2. **The 157 `unknown_*` fields are honest, not filler:**
   - 0x24A98 / 0x2D540 / 0x2DEE0 / 0x2E1E4 / 0x2FB18 / 0x2FB20 are **GameWork** offsets
     (`Ui_Window_ResetState` and `Ui_Window_UpdateFadeTimers` receive GameWork as `self`;
     +0x24A98 is the known save/party block).
   - 0xDE10 is a single weak write `param_1[0x3784] = -1` — beyond any window allocation.
   - The bulk of 0x128..0x350 is only touched by `maybe_Ui_Window_ScriptCmdJ_ContB` (0x00263AF4),
     whose decompilation is (per its own doc) a misplaced structure-copy routine, and by
     `maybe_Ui_Window_ClosePartB`, so no interpretation can be tied to a field.
   - Several offsets are **extractor artefacts**: `(**(code **)(*param_1 + 0xNN))()` is a vtable
     dispatch, and `struct_db` records it as `param_1[0xNN]` → field 4*NN (0x30, 0xF0, 0x100, 0x130,
     0x150, 0x170, 0x500, 0x510 …). Those are named `unknown_*` and the evidence says so.
3. **Widths**: I kept the batch width for every offset (so the merged struct stays internally
   consistent), and stated the true width in the evidence where it differs (u8 for the layout/mode
   bytes at 0x49/0x4C/0x50/0x5E/0x68/0x69/0x134/0x135, u16 for the message id at 0x14 and the 0xB-byte
   argument records at 0x388/0x394).
4. **`base` overrides**: `Ui_AnimObject`'s `Ui_AnimRefList` base is composition (the ctor initialises a
   member at +0x14), so base is null; `Ui_EmbeddedObject`/`Ui_SingleLayoutObject`/`Ui_SmallObject` keep
   no base because the evidence only shows `Ui_Object_DtorBase` chaining through an offset.
5. **Confidence** is per field; class confidence is the weakest important field (0.35–0.55). Names with
   confidence < 0.5 all carry the `maybe_` prefix.

## Open problems / not verified

- The `Ui_Window` batch is a **merge of at least three `self` types** (a text-layer window, a
  `WidgetHost` pane stack whose 12-byte entries start at offset 0 of *its* object, and `GameWork`).
  The +0x04..+0x14 "text label ids" therefore conflict with the scroll-anchor floats written by
  `Ui_Window_UpdateScrollOffset` at the same offsets in a different class; I kept the label reading
  (majority of the window methods) but the evidence says the two readings disagree.
- Everything in 0x190..0x3DE4 beyond the named anchors (widget/menu/message sub-object slots) is only
  observed through constructors copying a static template — the field *meaning* is a slot index, not a
  type, so most stay `unknown_*`.
- Not verified: whether `Ui_Window` is really 195,356 bytes (the number is `highest field + width`,
  forced by the GameWork mistypes). No allocation size is evidenced for this class; the individual
  window classes allocate their own sizes.
- `Ui_SmallObject`'s size (4) is certainly too small — its vtable is a full widget vtable — but no
  field is evidenced above +0x00, so no larger size could be justified.
- `Ui_EmbeddedObject` +0x120 has no field access at all; `Ui_AnimObject` +0x00 has two readings
  (vtable vs freed curve buffer), so both are low confidence.

## Suggested follow-ups

1. **S_066** uses the field type `UiWindow`, which does not exist in `structs.json` evidence (only the
   `Ui_Window` class does). Either S_066 should use `Ui_Window*` or the type merge should map
   `UiWindow` → `Ui_Window`.
2. `tools/typedb/struct_db.py` should drop offsets derived from `(**(code **)(*param_1 + N))`
   vtable dispatches (they produce phantom fields at 4*N) and should refuse to attribute a field when
   the same class has two conflicting `self` types (the Ui_Window pool). Regenerating this batch after
   that fix would remove a large part of the 157 `unknown_*` entries automatically.
3. A dedicated pass over the real window subclasses (item/shop/equip/battle windows) would be more
   useful than more work on this aggregate; the individual classes already have their own names in
   `structs.json`.
