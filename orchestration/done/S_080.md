## Why most offsets are `unknown` (important for the merge)

The batch class is a **name-prefix cluster**, not one object. Offsets 0x7C..0x5D4 come from a
0x3940-byte menu/message composite (`FUN_001D85EC(…, param_1+0xFA4, "win_load_message", 0xC)`,
`win_talk`, `win_yesno`, `win_load_keyboard`, `menu_dive_region2/3` — it embeds child window
definitions at 0x984/0xC5C/0xDB8/0xFA4/0x1A60/…); `+0x48` there is an overlay-manager pointer and
`+0x6C` a script-resource handle. `+0x3240` is battle work
(`FUN_00490994(param_1 + param_1[0xC90]*0x18 + 0x5D0, …)`, the attack-damage routine) and
`+0x4FB8/0xDF64/0xE078/0xE088` are the four weak (mistyped-self) accesses.

Consequence: `apply.py` computes `sizeof = max(offset+size)` over the fields it receives, so the
generated struct is **0xE08C even though the class is 0x7C**. The JSON's `size` is 0x7C and the
class summary/evidence say so explicitly. Suggested fix (follow-up task, not mine to do):
`make_batches.py`/`struct_db.py` should assign fields per function only when the function's
`self` type matches the class vtable, or emit a per-function `self` source so a worker can drop
foreign offsets.
