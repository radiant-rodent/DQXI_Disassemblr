# S_081 - struct field naming batch (Ui, 3 classes / 391 fields)

## What I did

Named all 3 classes and every one of their 391 batch offsets in
`orchestration/types/out/S_081.json` (UTF-8, 101,132 bytes).

Method, per class: read the constructor / initialiser readable C with
`python tools/fn.py`, then the update/draw methods that read the fields, then the
`InitPanes` binder that maps pane-name strings to offsets. Every offset was cross-checked
against the vtable slot names and, where the C was ambiguous, against the raw Ghidra C.

## Data problem found (important for the dispatcher's struct_db)

`struct_db.py` attributes every access made through a parameter whose type is the class, so a
class's `fields[]` list collects offsets that are **not members of that class**. Three
mechanisms produced most of the 162 `unknown_*` entries here:

1. **Global constant table reads.** `0x0072A600->f_XX` accesses are attributed to the enclosing
   class. In Ui_SakusenWindow this alone accounts for 0x68-0x110, 0x90-0xA0, 0xC0, 0xD0 and
   0x160.
2. **Placement-new chains in constructors.** `iVar5->f_XX` where `iVar5` is a running pointer
   into a freshly allocated block, not `self` (Ui_SakusenWindow ctor 0x002A3E78,
   Ui_ShopWindow ctor 0x001C1274).
3. **Other classes' `param_1`.** e.g. `Ui_ShopItemList_*`'s `shop` parameter,
   `Ui_ListWindow_Ctor1F8`'s 0x1F8-byte class, `Ui_ListWindow_InitDataObjects`' second list
   class.

These offsets are emitted as `unknown_*` at confidence 0.0 with the real owner named in the
`evidence` string, rather than guessed. A fix in `struct_db.py` (skip accesses through a
pointer that is not the function's own `self`, and skip the `0x0072A600` table) would remove
most of them automatically.

## Open problems / not verified

* **162 `unknown_*` and 100 `maybe_*` fields are not verified.** They are listed in the JSON
  with the reason in `evidence`. The `maybe_*` ones are positional or inferred from a single
  access; the `unknown_*` ones are either contaminated offsets (see above) or real fields whose
  purpose the recovered code does not reveal.
* **Ui_ShopWindow size changed from the batch's 15,852 to 9,500 (0x251C).** Evidence: the
  allocation in `Ui_ShopWindow_Ctor` (0x001C1274) is `Mem_AllocAligned_2(0x0000251C, ...)`.
  The batch's 15,852 came from a single write at +0x3DE8, which is 0x18CC bytes past the end of
  the allocation; that offset is kept as `unknown_u8_3de8` with the explanation. This is
  static evidence only - not checked at runtime.
* **Ui_ShopWindow's real base is `Ui_Window`, not `Ui_Object`.** `Ui_ShopWindow_CreateSubObjects`
  calls `Ui_Window_CtorBaseB(self+0x11C)`. I kept `Ui_Object` in the JSON on purpose so the
  merge does not embed the 195,356-byte `Ui_Window` into this class; the discrepancy is stated
  in the class `evidence`, and offsets below 0x11C are named after S_079's `Ui_Window` fields.
  The dispatcher should decide whether to switch the base once `Ui_Window` is named.
* **Ui_ListWindow 0x170-0x410 (28 fields) are positional names only**
  (`maybe_pageWidgetField<hex>`, confidence 0.25). They fall inside the first of the three
  0x330-byte `Ui_TenRowModePanes` widgets constructed at +0x16C. `Ui_TenRowModePanes` is not
  named by any S_ batch yet, so no cross-reference was possible.
* **Ui_SakusenWindow 0x4C-0xA0 (22 offsets) stay `unknown_*`.** `Ui_SakusenWindow_Data_Ctor`
  (0x0041E6D8) zeroes exactly those 22 words, but of *its own* 0x114-byte object (allocated by
  `Ui_SetupSakusenWindow`), and the same offsets are also read from global 0x0072A600, so they
  are not proven to be window fields.
* **Nothing was checked against a running game or emulator.** This is a static naming batch:
  no code was generated, no header was emitted, no build was run.

## Suggested follow-up tasks

1. **Name `Ui_TenRowModePanes`** (0x330 bytes, ctor 0x0045E69C) in its own S_ batch. That would
   resolve the 28 positional `maybe_pageWidgetField*` offsets in Ui_ListWindow.
2. **Name the `Ui_SakusenWindow_Data` block** (0x114 bytes, ctor 0x0041E6D8, allocated by
   `Ui_SetupSakusenWindow`) so the 22 `unknown_*` offsets at 0x4C-0xA0 can be attributed to it
   instead of to the window.
3. **Fix `struct_db.py`** to stop attributing (a) `0x0072A600->f_XX` global-table reads,
   (b) placement-new chain accesses in constructors, and (c) accesses through parameters that
   are not the function's own `self`. This would remove most `unknown_*` fields across all Ui
   batches, not just this one.
4. **Revisit the Ui_ShopWindow base class** once `Ui_Window` is fully named, and confirm the
   9,500-byte size against a second allocation site if one exists.
