## What the four windows are

* **Ui_ArcListWindow** - curved ("arc") list window for the battle/summary menus. Two 3-float
  anchors at +0x04/+0x10, arc centre at +0x1C, transition duration +0x28, 12-entry 0x18-byte
  animation-slot table at +0x94 (count +0x98, elapsed +0x9C, frame counter +0xA0, delta +0xA4,
  handler table +0xB4), six focus bounds +0x3C0, control points +0x3D8/+0x3E4, motion deltas
  +0x42C..+0x44C, scroll aim +0x508..+0x520, swing state +0x530..+0x538, and the 4x26
  container-handle grid starting +0x220.
* **Ui_EquipWindow** - equipment-change window loaded from `ui_equip_msg.bxon`. Literal panes:
  `win_equip_equip1` +0x198, `win_equip_type` +0x1E4, `win_equip_equip2` +0x24C,
  `win_equip_name` +0x360, `win_equip_dougu` +0x3C8, `win_talk` +0x438, `win_yesno` +0x20E4.
  Inline 0xC-byte pane stack +0x128 (count +0x164), input flags +0x17C, cursor +0x17E/+0x17F,
  member record +0x11C, six equipment slot records from +0x2188.
* **Ui_PanelMessageWindow** - 3D battle panel message window. 14 two-word text slots
  (+0x0C..+0x6C, sentinel 0xFFFFF000), icon panel +0x70, command array +0x74/count +0x78,
  0xC-byte descriptor table +0x170/index +0x1AC, layout panel +0x188, skill-panel pair
  +0x390/+0x394, own message object +0x2548.
* **Ui_EquipmentWindow** - item/"dougu" window loaded from `win_dougu_*` BFLYT panes
  (party1 +0x1C4, sort2 +0x6D4, sort +0x720, sort3 +0x76C, how +0x7D8, num +0x930,
  hand +0x9A0, party2 +0xA08, hp1 +0xE20, dougu2 +0xEE0, fukuro2 +0xF40), plus category
  mode +0x7D4, number max/value +0x4C/+0x50, detail widget +0x1084 and item model +0x10D0.

## Method

* Read the batch field dumps plus `python tools/fn.py <addr> -b 0` doc summaries for every
  recovered method (no tree walks, no repo-wide greps).
* Read the constructors (`Ui_ArcListWindow_Ctor/CtorWithMode/CtorEmbedded`,
  `Ui_PanelMessageWindow_Ctor`) and the biggest update/dispatch functions
  (`UpdateFocusBounds`, `UpdateAnimSlots`, `UpdateScrollAim`, `DispatchEvent`,
  `SetClampedNumber`, `InitPanes`, `Setup`) to resolve field layout.
* Cross-checked widths against neighbouring offsets and the batch `size`.
* Generated the JSON deterministically from explicit per-offset maps
  (`out/scratch/S_082/build.py`); every batch offset is emitted exactly once with its `size`.

## Not verified / open problems

* `Ui_EquipWindow` +0x2C..+0x88: a large ctor-initialised block with no semantic use found;
  left as `unknownState*` (0.15). The batch ctor `Ui_EquipWindow_Ctor` (0x0033563C) builds a
  0x414-byte base, not this 8716-byte object, so its stores could not be used to type them.
* `Ui_ArcListWindow` +0x94: the doc (N_065) calls it the 12-entry animation table, but the
  assembly also treats +0x94 as a pointer to a polymorphic sub-widget and +0x98 as the slot
  count. The batch offsets were followed; the overlap is real in the decompiler output.
* `Ui_PanelMessageWindow` +0x70: `FUN_003AB758`/`FUN_005A6300` return a base 0x364 bytes before
  this object, so the icon panel at +0x70 is inferred (0.6), not proven.
* Most `Ui_PanelMessageWindow` intrusive-list words (+0x130..+0x360) are link words with no
  distinctive payload, named `listNode*`/`childLink*` at 0.3-0.45.
* `Ui_EquipmentWindow` +0x1120..+0x115C: 16 words only ever zeroed by `PlayAnim`; named
  `animState0..15` (0.5) without a per-word meaning.
* Vtable-dispatch-only offsets were emitted as `unknownCallTargetNNN` at 0.0
  (ArcListWindow +0x50/+0x2B0/+0x2C0/+0x2D0/+0x2E0/+0x310, EquipWindow +0xBC/+0x100,
  EquipmentWindow +0xD0/+0xE0/+0x160).
