# S_084 — name the classes and fields of 6 Ui classes (RESUMED)

## What I found on resume

A previous worker had already written a **structurally complete** `orchestration/types/out/S_084.json`:
6 classes, 405 fields, every batch offset present exactly once, no duplicate names, 0 errors under a
local replica of `tools/typedb/apply.py`'s checks. What was missing was naming quality: **105 fields
were still `unknown_*` at confidence 0.0**, and several names were guesses that the evidence did not
support (`maybe_callbackAdjust`, `maybe_callbackCallCount`, `maybe_handle304`, …).

I kept that work and improved it rather than rewriting it. Result: **105 → 62 unknown**, 156 fields
carry a real name, 187 are `maybe_*`.

## What I did

Method per class, in this order:

1. Read the class's own readable C (`decomp/readable/functions/<Class>_Ctor_*.c`, `_Dtor_*.c`,
   `_Init_*.c`, `_Layout*.c`).
2. Ran `tools/fn.py` on **every callee that receives `self + offset`**. That is how the embedded
   sub-objects were identified: `Ui_NodeList_Register` (0x0036B45C), `Ui_Object_DtorBase`
   (0x001A6768), `Ui_MessagePage_Dtor` (0x001DB5D0), `Ui_LayoutRef_Release` (0x003E04BC),
   `Ui_TwoColumnListWindow_CtorB` (0x00380164), `Ui_SelectableGrid_Ctor` (0x003701B4),
   `Sound_SetVoiceGainByHandle` (0x001EDF88), `std_destroy_range` (0x00100BE0).
3. Read the **retail image directly** (`original/exefs/code.decompressed.bin`, file offset =
   vaddr − 0x00100000) to turn the `PTR_DAT_*` vtable stores in the evidence into real vtable
   addresses, then into class names via `structs.json`. This is what proved that
   `PTR_DAT_0029a5c8 → 0x0076E848` is a widget-family table (its slots are `Ui_Widget_ReleaseSub`,
   `Ui_SetThreeObjectVisibility`, `Ui_Pane_SetVisibleWithAnim`).
4. Read the **disassembly** of the two destructors whose batch offsets looked impossible. This was
   the single most valuable step — see "Ground truth" below.

Helper scripts (scratch only): `out/scratch/S_084/peek.py` (image reader + vtable→class resolver),
`dump.py` (per-class evidence dump), `where.py` (which of the class's own functions contains a code
fragment), `check.py` (local replica of the `apply.py` validation rules), `patch1-3.py` (the edits).

### Ground truth recovered from the disassembly

`Ui_CompositeWindow_Dtor` (0x00282578) really tears down:

```
Pack_ReleaseHandle(self+0x438); vtable stores at self+0x3E0 and self+0x3C4;
list unlinks at self+0x44C/+0x440, self+0x3D8, self+0x3B8;
std_destroy_range(self+0x294, 0x48, 4);
Ui_LayoutRef_Release(self+0x244);
node destructor 0x0036B514 on self+0x11C
```

`Ui_CreditWindow_Dtor_2` (0x002880F4) really releases:

```
0x0032A288(self+0x11C); 0x002B0654(self+0x22C); vtable store at self+0x11C;
Ui_LayoutRef_Release(self+0x1B8) and (self+0x168); Ui_Object_DtorBase(self+0x11C)
```

Several batch offsets for those two classes (CompositeWindow 0x194/0x1B4/0x2FC/0x1E18/0x2968,
CreditWindow 0x13C/0x18C/0x1DC/0x280/0x2D0) come from **chained sub-object constructor returns** in
the Ghidra pseudocode, so they are measured from the wrong base and are not members of the class.
They are kept (the batch requires every offset) as `unknown_chained*` / `unknown_weak_*` with that
explanation in the evidence, and the real offsets are recorded in the class-level evidence.

## Decisions made (orchestrator not available)

1. **Kept the previous worker's output instead of rewriting it.** It was already valid and mostly
   reasonable; a rewrite would have destroyed evidence I could not reproduce. I only changed fields
   where I had a new, checkable argument.
2. **Weak fields are kept.** All 494 weak fields across every finished `S_*` batch are kept by the
   other workers, so dropping them here would have made S_084 inconsistent. They are named
   `unknown_weak_*` at 0.0 with the reason in the evidence. Note for the merge: they inflate
   `Ui_CompositeWindow`'s emitted size to 0x2EBF0, which is a merge-side artefact, not a real size.
3. **`unknown_<descriptor>` instead of `unknown_word_<offset>`** where the access pattern proves
   *something*: `unknown_boundA`/`unknown_cursor`/`unknown_pageSize` for the SlotWindow range block,
   `unknown_vtableSlot58` for offsets that are only a vtable slot constant times 4, `unknown_chained4c`
   for offsets measured from a chained constructor return. This follows the task's own example
   (`unknown_counter`).
4. **Renamed two misleading names** in `Ui_CompositeWindow`: `maybe_callbackAdjust` → `maybe_flags`
   (the only evidence is a bit-0 test) and `maybe_callbackCallCount` → `maybe_counter` (incremented,
   reset, passed as an argument — nothing proves "callback").
5. **`Ui_CameraAnimWindow` +0x370 is an inline 32-byte buffer, not a `char*`.** `Ui_CameraAnimWindow_Init`
   passes `&self->f_370` to `sprintf` as the `%s` argument and `Ui_CameraAnimWindow_Init_2` copies
   eight words into it and `std_strncat`s onto it. The batch has no entry for +0x384, so the buffer is
   emitted as `cameraAnimName` plus `cameraAnimNameWord1..7`, following the existing
   `maybe_actionBufferWord0..13` convention in `Battle_Ui`.
6. **`Ui_CompositeWindow` +0x194/+0x1B4 are flagged, not trusted.** Both are `Ui_LayoutRef_Release`
   targets, but they are only 0x20 apart while `Ui_LayoutRef` arrays use a 0x50 stride
   (`std_destroy_range(..., 0x003E04BC, 0x50, 7)` in `Ui_CreditWindow_Ctor`). Named `maybe_layoutRef`
   (0.4) and `maybe_layoutRefB` (0.35) with the conflict written into the evidence.

## Open problems / not verified

* All 62 `unknown_*` fields. Most are zero-initialised state with a single write and no reader
  (`Ui_CameraAnimWindow` +0x220..+0x26C, `Ui_SlotWindow` +0x20..+0x44, `Ui_CasinoWindow` +0x14C..+0x154),
  or chained-pointer artefacts. I could not name them honestly.
* The exact type behind the interface tables at `Ui_CompositeWindow` +0x168/+0x208/+0x224
  (0x0076E848, 0x00782EFC, 0x00782E20 are not in `structs.json`; the last two have entries only at
  +0x08 and +0x1C, so they are not UI class vtables).
* Whether `Ui_CompositeWindow` +0x194/+0x1B4 are really two `Ui_LayoutRef`s (see decision 6).
* The meaning of the `Ui_SlotWindow` range block at +0x46C..+0x480 — only its arithmetic is proven
  (a bound pair, a cursor compared with a page size, and a two-term sum compared with the cursor).
* `Ui_CameraAnimWindow` has no recorded base class; the batch found no base-constructor call and the
  only candidate (`func_005F8528`) has no readable body. Left as `null`.
* Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-up tasks

1. **`struct_db.py`: keep the function name with each evidence line.** The single biggest cost in
   this batch was that `evidence` lines lose their function attribution, so a `param_1 + 0xNN` access
   cannot be traced back to the function that made it. One extra field per evidence line
   (`{"fn": "Ui_X_Dtor", "line": "..."}`) would remove most of the guesswork.
2. **`struct_db.py`: do not attribute offsets through reassigned local pointers.** Chained
   sub-object constructors (`puVar1 = Ui_Object_CtorBase(&puVar1->f_57)`) make the following
   `puVar1[0xNN]` accesses relative to a different base. Either reset the base at every assignment
   or mark such fields `weak`.
3. **A `tools/typedb/` helper that resolves `PTR_DAT_*` / `DAT_*` vtable stores to class names.**
   I wrote one in scratch (`out/scratch/S_084/peek.py`); it is ~40 lines and turned three opaque
   fields into identified embedded objects. It belongs next to `struct_db.py`.
4. **Re-check `Ui_CompositeWindow` and `Ui_CreditWindow` offsets against the disassembly** (the real
   teardown offsets are listed above). Their batch field sets are partly wrong, so a re-generated
   batch for those two classes would be worth more than further naming effort on the current one.
5. **`Ui_LayoutRef` size is unresolved**: `structs.json` says 64, `Ui_CreditWindow_Ctor` destroys
   arrays with a 0x50 stride, and `Ui_CompositeWindow` has two release targets 0x20 apart. A dedicated
   layout pass on `Ui_LayoutRef` would settle three classes at once.
