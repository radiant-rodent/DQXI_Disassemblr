## Open problems / not verified

* The batch is not one class per function-name cluster: several of these names cover two
  overlapping views of one object family. In Ui_GuideWindow the closer object (vtables
  0x007654C8/0x00765554) and the 2824-byte member-row window share offsets; the same is true
  for Ui_ItemInfoWindow (0x00761E68 vs 0x0077B564) and Ui_StatusWindow (the constructor at
  0x0061BBDC is the `Ui_TimeWindow` constructor). I kept the generated class names as required
  and encoded the dominant owner per offset in `evidence`; fields below 0.5 are `maybe_`/
  `unknown_`.
* Every `maybe_*` below 0.5 remains a hypothesis: the closer/UI-object base fields at
  +0x11C..+0x138 (emitted once as member-gauge/list/ring words), the `Ui_StatusWindow` base
  block +0x00..+0x58, most of `Ui_RecordDetailWindow` +0x10..+0xA0 and +0x800/+0xAAC, and the
  `Ui_BattleCommandWindow` 0x70..0x88 / per-member row component names (the 8-byte row layout
  and reset values are proven, the individual member meaning is not).
* `Ui_ItemInfoWindow.base` is left null: the vtable has `Ui_Window_LayoutRows` and
  `ApplyScreenTransform` slots but there is no base-constructor call in the recovered bodies.
* I did not verify that any of these structs compile; this batch only writes the JSON naming
  file (the dispatcher/apply step emits headers).
