## Decisions recorded (orchestrator was not available)

1. **Bases.** The batch's `base` is inferred from base-constructor calls, and
   for two classes that call is demonstrably a *child* allocation, so I wrote
   `base: ""` and explained it in `evidence`:
   * `Ui_EquipTextWindow` - `Ui_EquipWindow_Ctor_2(iVar5, self+1)` where
     `iVar5 = Mem_AllocAligned_2(0x22A8)`, stored at +0x58.
   * `Ui_MonsterBookWindow` - `Ui_SenrekiWindow_Ctor(iVar8, self+1)` where
     `iVar8 = Mem_AllocAligned_2(0x2D4)`, stored at +0x8C.
   Where the batch base is plausible (Ui_Object / Ui_Window / Ui_3DBackground
   / Ui_AnimRef) I kept it.
2. **Unknown vs maybe.** Offsets whose only "evidence" is a virtual-dispatch
   expression (`(**(code **)(*self + 0x34))(...)`) are not fields of the
   object; they are `unknown_0xNNNN` at 0.0 (37 offsets). Every other
   low-confidence name is `maybe_`.
3. **Mixed clusters are documented, not averaged.** Three classes merge two
   object variants in the batch; the class summary/evidence states which
   offsets are which:
   * `Ui_MessageSelectWindow` - 0x1D4-byte choice window (vtable 0x00763C94,
     rows/cursor/anim refs) plus the 0x00382CFC message-pane variant; the
     `0x15C..0x1D0` groups are modelled as four 0x20-byte
     {vtable, list head, size, two frame values} blocks from ctor/dtor
     symmetry.
   * `Ui_GoldWindow` - 0x4C0-byte shop/casino counter plus the small
     0x003B59DC variant ("txt_num_l"/"txt_gold"/icon_up/icon_down).
   * `Ui_PokerWindow` - +0x28 is read as a resource pointer by one caller and
     as a u16 flag word by another.
4. **Weak field.** `Ui_PartySelectWindow` +0xD070 (53360) is far outside the
   4704-byte object -> `unknown_0x0d070` at 0.0; it must not define the type.
5. **Type glitch.** The batch gave `Ui_MapWindow` the type `Ui_MapWindow`
   (underscore). Per the rules `type` is the class without underscores, so the
   output uses `UiMapWindow`; the class name is unchanged.
6. Arrays: offsets that start a `u16[6]` (+0x6E/+0x7A in EquipTextWindow) are
   typed `u16` with the extent in the evidence, so apply.py's gap padding
   stays byte-accurate.
7. One batch type guess was corrected on evidence: `Ui_KyoukaiWindow` +0xD98
   is an integer frame counter (`+= 1`), not `f32`.

## Warning for the merge step (not fixed here - not my file)

`Ui_PartySelectWindow` has one `weak` batch offset, +0xD070 (53360), far
outside the 4704-byte object. It is emitted as `unknown_0x0d070` at 0.0 as the
task requires (every batch offset exactly once). `tools/typedb/apply.py`
currently grows a class's `size` to `max(offset + size)` over all fields, so
merging this file will declare `UiPartySelectWindow` 53364 bytes and insert a
~48 KB `_pad_` array. Suggested merge-side fix: ignore `weak`/confidence-0
fields that lie beyond `size + 0x800` when computing the struct size (the
evidence check already rejects such offsets when there is no access evidence;
here the batch *does* carry one access, so the check passes).
