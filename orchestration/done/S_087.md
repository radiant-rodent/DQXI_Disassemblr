# S_087 — struct/field naming batch (subsystem Ui, 15 classes / 380 fields)

## What I did

Named all 15 classes in `orchestration/types/batches/S_087.json` and every one of their 380
batch offsets. Output: `orchestration/types/out/S_087.json` (UTF-8, strict-decode + `json.loads`
re-read clean, 15 objects / 380 fields).

Classes (batch field counts):
`Ui_BattleTargetWindow` 33, `Ui_DiveStartWindow` 33, `Ui_BattleWindow` 31, `Ui_RacingWindow` 28,
`Ui_BattlePartyWindow` 27, `Ui_3DAttachmentWindow` 26, `Ui_PartyStatusWindow` 26, `Ui_BigWindow` 25,

Method: for each class I read the readable C constructor + update/input methods and the doc header

role from earlier batches N_003/N_015/N_046/N_055/N_063/N_067/N_088/N_127/R2_004/R2_007/R2_009/
R2_012/R3_010/R3_023/R3_028/R3_036/R3_038/R_015/R_021/R_024/R_027/R_028/R_036/R_049/R_078), then

`Ui_AnimRefList`, `Ui_NodeList`, `Ui_ListWindow`, `Ui_GridCursor`, `BattleHpGaugeWindow`, `PackHandle`).

## Important findings / decisions

* The batch generator's offset attribution is inconsistent: sometimes a byte offset
  (`*(int *)(self + 0x98)`), sometimes a `u32` word index (`param_1[0x4a]`), and for
  multiple-inheritance constructors the decompiler has already re-based the pointer onto an
  embedded sub-object. Where that makes an offset unprovable I emitted `unknown_0xNN` at
  confidence 0.0 with the reason, rather than inventing a purpose. This is spelled out in the
  class summary/evidence for `Ui_BigWindow` (+0x48..+0x84), `Ui_PartyStatusWindow` (low offsets),
  `Ui_DiveStartWindow` (0x48..0x6C, 0xE4), `Ui_MemoriesWindow`/`Ui_PastPlaceWindow` (+0x20),
  `Ui_BattlePartyWindow` (0xA0/0xD0/0xE0/0x120) and `Ui_ComplexWindow`'s pager state block.
* `Ui_PartyStatusWindow` is a mixed cluster: the low offsets come from `SaveData_PartyContainer_Ctor`
  (0x001939C0) / `SaveData_PartyContainer_Reset` (0x0019371C) which the generator assigned to this
  class; the real window fields are the state word `+0x125C` and the sixteen 0x58-byte member rows
  built at `+0xB464` by the dtor's evidence. Because the mx-field size (0x8BC4) is therefore too
  small I set `size = 0xBCE4` and said so; the merge will still grow to max(offset+size).
* `Ui_BattleTargetWindow` is a genuine ~0x3554-byte composite (four target panes at +0x154 stride
  0x470, result window +0x1314, 21-row target list +0x1360, own-character pane block at +0x3000).
  Verified `battleState` +0x34D0 (2 = enemy turn) and `pageIndex` +0x34D4 from Hide/ScrollPage.
* `Ui_DiveStartWindow` and `Ui_BigWindow`/`Ui_JewelShopWindow` share the same composite-constructor
  idiom as the previously named Ui_MessageWindow cluster; I named only the anchored fields
  (message page/pair, style byte, node lists, pad handles, 'win_gold'/'win_houjyu_select'/'win_talk'/
  'win_yesno' panes, fade panels) and left the embedded-object word indices unknown.
* `Ui_3DAttachmentWindow` is not a text window: its vtable slots are Model/Gfx node helpers; fields
  are the secondary base vtables (+0x220/+0x228), the self back-pointer, the eight copied view
  dwords (+0x234..+0x250), a 5.0 scale triple and a -0x400 depth bias. Base left empty (no base
  constructor in the ctor).
* `Ui_BigWindow.base` kept `Ui_Object`; `Ui_JewelShopWindow`, `Ui_PartyStatusWindow` and
  `Ui_3DAttachmentWindow` have base `""` because the batch base was null/unproven.
* Naming/style rules followed: every confidence < 0.5 field is `maybe_*` (or `unknown_*` at 0.0);
  no field names duplicate inside a class; no `maybe_` at confidence >= 0.5.

## Verification

* `python out/scratch/S_087/merge.py` — asserts per class: batch offset set == emitted offset set,
  unique names, `maybe_`/`unknown_` prefix iff confidence < 0.5 (after the fix-up run), class set
  identical. Result: `WROTE orchestration/types/out/S_087.json ok=True`, all 15 classes ok,
  380/380 offsets.
* Strict UTF-8 re-read + `json.loads` of the output: OK.
* `python tools/typedb/apply.py --validate` → **0 errors / 0 warnings for S_087** (the 5 errors and
  11 warnings in the report belong to S_066/S_089). Disclosure: `--validate` rewrote the derived
  `orchestration/types/merged/*` and `report.json` (generated cache, not hand-edited); no other file
  outside my ownership was touched.
* `tests/run_all.py` and `tools/verify_project.py` were skipped per naming-batch rule 5.

## Open problems / suggested follow-ups

* The struct_db offset attribution (byte vs `u32` word index) should be fixed; it produced definite
  wrong offsets in this batch (e.g. `Ui_BigWindow` +0x48..+0x84, `Ui_BattlePartyWindow` 0xA0/0xD0/
  0xE0/0x120, `Ui_MemoriesWindow` +0x20, `Ui_3DAttachmentWindow` unaffected). A re-run of the
  extractor with the pointer type of each function's `self` would remove ~25 unknowns here.
* The `Ui_BattleTargetWindow` / `Ui_PartyStatusWindow` / `Ui_PartyStatusWindow`(save container)
  clusters should be split into their real classes (`SaveData_PartyContainer`, `Ui_PagerWindow`,
  `Ui_TextPairRow`, `Ui_SkipPromptWindow`, `Ui_UmaWindow` sub-object) instead of being merged by
  the M1 name prefix.
* Unverified: every `maybe_*` (about 60 fields), the exact meaning of the eight transform words at
  `Ui_3DAttachmentWindow +0x234`, the three zero bytes at `Ui_RacingWindow +0x26A..26C`, whether
  `Ui_BattleWindow +0x70` is 3 or 4 anim groups (ctor template says 3/4 in two variants), the
  `Ui_BigWindow +0x48..+0x84` block (real offsets likely base+0x1B8+word*4), and the true identity
  of the low `Ui_PartyStatusWindow` fields.
