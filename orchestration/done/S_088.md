* `Ui_RecordWindow` — `senreki_title`; FUN_00387FC0 walks ids 0..299 and tests the unlock bitmask at

* `Ui_SlotPlateWindow` — `plate1_base`, `plate2_base`, `select_r/c/l`, `slot_rot_loop`
  (slot-machine plates; three visibility bits packed in the byte at +0x195).
* `Ui_StampWindow` — `stamp1`, `pager_num_l/r`, `stamp_complete`; 35 entries of 0x9c bytes at +0x12c.
* `Ui_BattleEnemyListWindow` — 7 x 0x50-byte rows + `Ui_Cursor` + text element.
* `Ui_TalkLightWindow` — embeds a 0xccc-byte `Ui_MessageWindow` at +0x184 (size confirmed by the

## Decisions (recorded as required)

1. **Types**: kept the batch's `type` for every class. For `Ui_SlideWindow` the generator left the
   type as `Ui_SlideWindow` (underscores not stripped); I did **not** normalise it because the rule
   says not to rename a class the project may already use in signatures. All field types are from the
   safe set (`u8/u16/u32/s8/s16/s32/f32/void*/char*`); no class type is used as a *value* type, so no
   wrong-embedding risk.
2. **Struct_db virtual-call artefacts**: many offsets in this batch (e.g. Ui_ChoiceSelectWindow
   +0xd0/+0xe0/+0xf0/+0x120, Ui_SlideWindow +0x150/+0x160/+0x210, Ui_BattleEnemyListWindow
   +0xc0/+0xd0/+0xe0/+0x120) have evidence that is only a virtual-slot call such as
   `(**(code **)(*self + 0x34))(...)`. Those are emitted as `unknown_0xNN`, confidence 0.0, with the
   real slot number stated in `evidence` — rather than inventing a field.
3. **Weak fields**: Ui_CharaStatusWindow +0x4754 and +0x4890 lie beyond the 8656-byte object, so they
   are misattributed accesses from another function; emitted as `unknown_*, 0.0`. They still appear
   because the batch requires every offset exactly once.
4. **Intrusive list header at +0x11c..+0x134** (Ui_TwoTextWindow, Ui_TalkLightWindow,
   Ui_DungeonHpWindow) is a self-referencing list init (`next = self`, `prev = self`). Named as
   `maybe_list*` words at 0.3–0.35, not as gameplay state.
5. **Offset re-basing caveat**: `Ui_RecordWindow_InitTitlePane` calls `FUN_00478380(param_1 + 0x30)`
   and that callee uses +8/+0x264 relative to its own base. The batch offsets are emitted as given;
   the doubt is spelled out in the +0x30 field evidence instead of silently changing offsets.
6. **"Unknown but real" vs "invented"**: fields that are only zeroed or only single-access got
   `maybe_*` names at ≤0.45 (e.g. `maybe_offsetX/Y/Z`, `maybe_flag50..60`), or `unknown_*` at 0.0 when
   even the kind of value is unclear (e.g. `unknown_0x90`, `unknown_0x4c`). No purpose was filled in
   just to have a name.

## Open problems / not verified

* Every `maybe_*` field below 0.5 — in particular the per-class flag bytes and the "offset" triples
  of `Ui_SceneWindow` / `Ui_SlideWindow` (position vs index is not distinguishable from one copy).
* `Ui_ChoiceWindow` +0x51..+0x54: four bytes set to 4/2/3/0xFF, used as indices into the option
  table `DAT_0047bdf8` and then into `data+0x11c`. Whether they are option *text ids* or *option
  kinds* is not settled (named `maybe_optionTextId0..3`, 0.4).
* `Ui_PresentWindow` +0x380c pool of 400 x 0x40: present/achievement entries — the element layout was
  not decoded.
* `Ui_RecordWindow` +0x90 and +0xa0 remain unexplained (only virtual-slot calls).
* `Ui_SlotPlateWindow` `activePlateValues` is a 3-pointer record `{left,center,right}`; its struct is
  elsewhere in `structs.json` and was not matched by name.
* No emulator run, no rebuild, no `verify_project.py`: this batch only produces JSON.
