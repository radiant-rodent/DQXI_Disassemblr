## Decisions worth knowing

1. **`struct_db` offset artefacts.** Several batch offsets are not object fields. I kept the offset
   (the merge requires it) but named it `unknown_*` at confidence 0.0 and wrote the real offset in
   the evidence:
   - `puVar3[8] = puVar2` in a ctor where `puVar3` is the local returned by
     `Ui_Object_InitMemberPair(self+0x11C)` → the store is the owner back-pointer at **+0x13C**
     (`Ui_BoushiShopWindow` +0x20, `Ui_DungeonBattleWindow` +0x20).
   - `piVar4[10] = self` on a freshly allocated 0x2C-byte `Ui_ActionPane` child → the child's owner
     field, not `Ui_ActionWindow` (`Ui_ActionWindow` +0x28).
   - `(**(code **)(*param_1 + 0xNN))(...)` → a vtable call, and the tool emitted `0xNN*4` as an
     offset (`Ui_BaseWindow` +0x130/+0x180, `Ui_SevenSlotWindow` +0xD0/+0xE0/+0x120,
     `Ui_FourRowTextWindow` +0xD0/+0xE0/+0x120, `Ui_KyoukaiSelectWindow` +0xF0,
     `Ui_NineRowPagedTextWindow` +0xD0/+0xE0/+0x1B0).
   - `param_1` typed `int*` in the readable C → the tool multiplied the real byte offset by 4
     (`Ui_BaseWindow` +0x204 = real 0x81, +0x214 = real 0x85; `Ui_FourRowTextWindow` +0xC0 = real
     0x30, +0x110 = real 0x44, +0x160 = real 0x58; `Ui_KyoukaiSelectWindow` +0x4C/0x9C/0xEC/0x13C/
     0x1DC/0x22C = real 0x13/0x27/0x3B/0x4F/0x77/0x8B; `Ui_MenuWindow` +0x9C = real 0x27,
     +0x1DE4 = real 0x779, +0x1E34 = real 0x78D; `Ui_NineRowPagedTextWindow` +0x54 = real 0x15).
     In those cases the *real* offset is also in the batch, so both entries are named and the
     evidence says which is which.
2. **`base` corrections.** The batch infers a base from any base-constructor call, including calls
   on members. I set `base` to `""` (→ `None`) for `Ui_CasinoWinWindow` (`Ui_PokerWinWindow_Init`
   targets the member at +0x11C), `Ui_RouletteWindow` (`Container_ArrayCtor`/`Ui_RouletteSelectGrid_Ctor`
   on members), `Ui_KyoukaiSelectWindow` (seven `Ui_AnimRef` members at 0x4C+n*0x50),
   `Ui_MenuWindow` (`Ui_Window_CtorBaseEx` on +0x138) and `Ui_StoryListWindow`/`Ui_BaseWindow`/
   `Ui_EquipListWindow`/`Ui_FourRowTextWindow`/`Ui_NineRowPagedTextWindow` (batch base was already
   null). `Ui_Object` is kept where the destructor really calls `Ui_Object_DtorBase`.
3. **Shared conventions confirmed across the batch.** The pane/element id is `(row << 16) | column`
   (`Ui_BattleSpellWindow` +0x28, `Ui_EquipListWindow` +0x28, `Ui_NineRowPagedTextWindow` +0x28,
   `Ui_StoryListWindow` +0x188); the per-row stride byte is a copy of a global column count
   (`0x007A7C04`, `0x007A7A38`) at +0x66; `Mem_AllocAligned_2(size, heap, align)` makes +0x24/+0x48
   a heap handle; `Ui_Object_InitMemberPair` + a vtable overwrite marks an embedded `Ui_AnimRef`.
4. **`Ui_BaseWindow`** is the shared step driver: `maybe_Ui_BaseWindow_UpdateStep` (0x002FCEAC)
   advances a 1/30 s clock and dispatches through a 19-entry, 0x18-byte-stride table of ARM
   pointer-to-member-function pairs, with `self+0x3594` as the `this`-adjust base. Its
   `maybe_Ui_BaseWindow_Close`/`_Release` occupy the close/release slots of four window vtables.
5. **Sizes were echoed, not inflated.** Several batch sizes are only `max_field + 4`; I did not
   raise them, so `apply.py` padding stays inside the observed object.
