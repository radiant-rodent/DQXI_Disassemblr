## Decisions worth knowing

1. **Virtual-call artefacts.** Many batch offsets whose only evidence is `(**(code **)(*self + 0x34/0x38/0x3C/0x40/0x48/0x58/0x84/0x98))(...)` are not object fields. They are emitted as `unknown_offset_0xNN` at confidence 0.0 with the real vtable slot in the evidence. This was verified once in the assembly: Ui_PagedTextWindow +0xE0 comes from `ldr r0,[pc,#0xe0]` at 0x0041E0AC (constant-pool load), not an object access.
2. **Offset aliasing.** Several offsets are projected onto the wrong base because the constructor advanced a pointer:
   - Ui_PastScenarioWindow +0x4C: the ctor writes `linked` into the embedded Ui_Object, so the real address is +0x184. Kept as `maybe_linkedObjectId` (0.3) with the mismatch stated.
   - Ui_TitleMessageWindow +0x20: `puVar3[8]=base` is memberPair(+0x11C)+0x20 = class +0x13C. Emitted `unknown_offset_0x20` at 0.0.
   - Ui_ScrollListWindow +0x11C..+0x138: these stores come from `maybe_Ui_ScrollListWindow_CreateSubObject` (0x003B7F54), whose sub-object has the same 0x138-byte header as Ui_PastScenarioWindow. Named by analogy with 0.3-0.35.
3. **Class merging.** `Ui_CursorWindow` merges two different classes: the Ui_Object-based ctor 0x002F70D4 (vtable 0x00761ED8, secondary vtable stored at +0x4C) and the Ui_SlotSub-based ctor 0x004DC528 (vtable 0x00780B54). +0x4C/+0x50/+0x54 are therefore `maybe_` at 0.35-0.45 with the conflict written into the evidence, and the class confidence is 0.4.
4. **Bases.** Kept only where a base ctor is actually called: Ui_SwapWindow = Ui_WindowBase, Ui_RecordQuestWindow / Ui_ScrollListWindow / Ui_ThreeLineTwoSelectWindow / Ui_TitleMessageWindow / Ui_FourRowIconWindow = Ui_Object, Ui_CursorWindow = Ui_SlotSub. The batch "bases" of Ui_CasinoJackpotWindow / Ui_TitleWindow (Ui_AnimRef) and Ui_ScrollListWindow's Ui_ListWidget are embedded members, so they were not used as bases; several null-base classes stay `""`. Each class evidence says why.
5. **Sizes.** Echoed from the batch but flagged where they are only max-field+4: Ui_PastScenarioWindow (embedded Ui_Object at +0x138), Ui_ScrollListWindow (real 0x12F0 per ctor/dtor list heads at +0x1298/+0x12B4/+0x12D0), Ui_CasinoJackpotWindow (last anim ref ends at 0x2CC), Ui_TitleMessageWindow (Ui_Cursor at +0x2048). Sizes were deliberately not inflated so apply.py's padding stays inside the observed object and does not invent memory.
6. **Honest empties.** Fields that are only zeroed or written once are `maybe_*` at 0.3-0.45 (e.g. Ui_DualMessageWindow +0x4B/+0x4C), never given a game meaning.

## Not verified / open problems

- Every `maybe_*` below 0.5 (the evidence string says what the store/load literally does, not what the game uses it for).
- The role of the two intrusive rings in the PastScenario/ScrollList sub-object header: only the self-referential ring pointers are proven, not what the lists contain.
- The 8-byte entries of the Ui_ItemWindow table beyond the `u16 itemId` prefix (stride 4 u16 is proven, the remaining 6 bytes are not).
- Whether Ui_TimeWindow +0x25A..+0x25C are hour:minute:second in that order (they are three clock-time bytes passed together to 0x001A60A0).
- Ui_TitleWindow +0x16C: read/cleared around a `Ui_ChildSprite_Detach`, but the object it holds is not proven.
- The class boundary inside Ui_CursorWindow (two ctors, two vtables).
- True allocation sizes of the four windows listed in decision 5; `size_source` is `max_strong_field+width` for all of them.
- Ui_FiveListWindow's first child pointer lives at +0x384, which is **not** one of the batch offsets; the five child bodies (+0x80..+0x31C) are named, the pointer slot for child 0 is only described in evidence.
