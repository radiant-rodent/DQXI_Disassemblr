## Decisions (and why)
1. **Vtable-call artefacts.** The batch emits offsets `0xD0/0xE0/0x120/0x160/0x210/...` whose only
   "evidence" is `(**(code **)(*param_1 + 0x34))(...)` etc. `struct_db.py` multiplies the vtable
   byte slot by the element width of `*param_1` (0x34→0xD0, 0x38→0xE0, 0x48→0x120, 0x58→0x160,
   0x84→0x210). They are **not** data members. They are emitted as `unknown_vtableSlotNN`,
   confidence 0.0, with the real slot named in `evidence`; the header emitter skips them when a
   wider member already covers the offset (e.g. inside `gaugeRows`).
2. **Cross-object attribution.** `puVar2[6] = 10` (TenRow) / `= 5` (FiveLine) is the row count of
   the text scroller at +0x54, not of the window; `puVar3[8] = puVar2`, `piVar3[10] = self` and
   `Ui_Object_InitMemberPair(puVar2+0xB)` (ActionListWindow) belong to a freshly allocated row part.
   Those offsets are `unknown_*` at 0.0 (or `maybe_paneSetId` 0.35 for +0x28) with the reason.
3. **Sizes corrected only with proof.** Ui_PartyHpGaugeWindow 2748 = 0x138 + 4*0x260 + 4
   (`std_destroy_range(self+0x4E,0x260,4)`, matching the Ui_PartyHpGauge class' 0xAB8 counter);
   Ui_SimpleWindow 408 (0x198 allocation stated by the ctor's recovered doc and its caller).
   All other sizes were echoed unchanged.
4. **Pane types.** Panes created through `layout->vt[+0x2C]` are typed `Ui_LayoutPane*`, because
   `0x005387EC Ui_LayoutPane_InitFromRes` is the recovered `nw::lyt::Pane` initialiser
   (+0x2C children, +0x80 name, visibility bit +0x44).
5. **Float fields.** `f32` is used where the value arrives in `s0` (`in_s0`) or is a literal float
   (0x3F800000, 0xBF800000, 0x3EB33333) — the known VFP-argument/branch-inversion trap.
6. Base classes kept from the evidence; `Ui_ActionListWindow` keeps `Ui_ActionPane`,
   `Ui_SimpleWindow` keeps `Ui_SmallObject`.

## Known gaps / not verified
* All 23 `maybe_*` and 29 `unknown_*` fields (what each literally does is in its `evidence`).
* The element type of the two 0x44-byte text buffers in Ui_StatusParamWindow: only the split
  "4-byte header + 0x40 text" is proven (Tomb: `self+idx*0x44+0xF4` is passed as the text pointer).
* The class of the text-scroll container at +0x54 (TenRow/FiveLine): its layout (row count +0x18,
  rows at +0x1C stride 0xC) is proven, `func_00622248` has no readable file, so it is `void*`.
* Ui_TenRowTextWindow +0x38: an object whose byte +0xC is compared with the rows-on-page count.
* Ui_ActionListWindow +0x138 (f32 0.35) and +0x160 (owner with state bytes +0x599/+0x59A).
* Ui_NineLineTextWindow +0x9C..+0xA4: only "three consecutive words copied into the effect
  parameter block" — named `maybe_posX/Y/Z`.
* The class boundary inside Ui_TwoListWindow: +0x74/+0x78 come from ctor 0x0039322C
  (vtable 0x00766B74), while the class' own vtable is 0x00763E68.
* Nothing was compiled; only the naming JSON was produced.
