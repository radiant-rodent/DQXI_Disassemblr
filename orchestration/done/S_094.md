# S_094 - struct field naming batch (Ui, 15 classes / 87 fields)

## What I did

Named all 15 classes and every one of their 87 batch offsets in
`orchestration/types/out/S_094.json` (UTF-8, 35,239 bytes).

Method, per class: read the constructor / initialiser readable C with
`python tools/fn.py`, then the update method that reads the fields, then checked the
**raw Ghidra C and the disassembly** for every offset I was unsure about
(`decomp/ghidra/functions/FUN_xxxx.c` + the matching `asm/text/text_xxxx0048.s`
window). The disassembly was decisive three times (see "Data problem" below).

Classes: Ui_DamagePopupWindow, Ui_EightLineTextWindow, Ui_ItemMenuWindow,
Ui_MemberListWindow, Ui_PagedTextListWindow, Ui_RankingWindow, Ui_RowListWindow,
Ui_SevenLineSelectWindow, Ui_SevenLineTextWindow, Ui_SkillPointWindow,
Ui_StrengthCompareWindow, Ui_SubWindow, Ui_BattleMainWindow, Ui_ClockWindow,
Ui_DungeonPlaceWindow.

Name mix: 51 clear names, 13 `maybe_*` (confidence < 0.5), 23 `unknown_*` at 0.0.

Highlights (full per-field evidence is in the JSON):

* `drN` (**0x001A6520**, 273 callers) is the shared **window/layout binder**: it stores the
  layout at +0x30, two ids at +0x24/+0x28 and an optional 'icon_cursor' object at +0x38.
  That pins +0x30 / +0x28 for every class in the batch (`+0x28` low u16 is the
  `(groupId << 16 | paneIndex)` pane key, hence `paneGroupId`).
* `Ui_EightLineTextWindow` +0x4A/+0x4C/+0x4E are three u16 **item ids** (0x3D/0x54/0x69)
  resolved with `Item_LookupRecord` and formatted with `Text_FormatMessageArg`.
* 0x50-byte animation units are typed **`Ui_AnimRefList`** (structs.json size 0x50,
  ctor 0x003E0454 `Ui_AnimRefList_Ctor`, release 0x003E04BC `Ui_LayoutRef_Release`),
  not `Ui_AnimRef` (whose 800-byte size is one weak access at +0x31C).
* `Ui_RowListWindow` is the ten-row list: `Ui_List*` +0x38, `entryCount` +0x4C,
  `visibleRowCount` +0x50, `isDimmed` +0x48, u16 `entryIdTable` +0x160.
* `Ui_ClockWindow` +0x4C/+0x50/+0x54 are the `txt_r3_period`/`txt_r3_colon1`/`txt_r3_colon2`
  glyph panes.
* `Ui_MemberListWindow` and `Ui_SubWindow` are **mixed class groups** (their functions belong
  to neighbouring classes: `Ui_UmaWindow_DeletingDtor` and `Ui_AnimRefList`/`Ui_Window_EnsureChildObject`);
  I kept the generated names, set class confidence 0.40 / 0.35 and said so in the class evidence.

## Data problem found (important for the dispatcher's struct_db)

`tools/typedb/struct_db.py` scales every `param_1 + N` by **4 whenever the first parameter is any
pointer** (`parse_signature` sets `width = 4` for every pointer, common.py line ~196), but Ghidra
types the same self parameter differently per function. Consequences visible in this batch:

1. `Ui_RankingWindow`: the raw C is `undefined1 *param_1`, so `param_1 + 0xc` is **byte 0xC**;
   the batch lists it as 48 (0x0C*4) *and* also lists the correct 12 from the other function.
   Assembly `add r0,r4,#0xc` / `#0x5c` / `#0xac` proves the real offsets are 0x0C/0x5C/0xAC.
   I emitted the x4 entries as `unknown_scaledAnimRef0C/5C/AC` at 0.0 with the real offset in the
   evidence, so the merge does not lose the information.
2. `Ui_PagedTextListWindow` +0x18: `puVar2[6] = 7` is written through the scroller returned by
   0x00622248, i.e. `self+0x54+0x18` = +0x6C, not +0x18.
3. All the 0xD0/0xE0/0x120 entries are `(**(code **)(*param_1 + 0x34/0x38/0x48))(...)` vtable
   dispatches, i.e. **not object fields at all**. I followed the S_083/S_093 convention
   (`unknown_vtableSlotD0/...`) so the struct emitter can skip them.

Suggested fixes for `tools/typedb/struct_db.py` (not my file, not edited):
use `type_width(base_type)` for pointer parameters instead of a hard-coded 4, and never treat
`(**(code **)(*p + N))` as an object field access.

## Open problems / not verified

* Every `maybe_*` (13) and `unknown_*` (23) field. The notable ones: `Ui_DamagePopupWindow`
  +0x1DC/+0x20C/+0x228 (an embedded second window record; the pane name at +0x228 is only read),
  `Ui_SkillPointWindow` +0x60/+0x64 (pane +0x1C assumed to be X position - same 3-vector evidence
  as `Ui_SevenLineTextWindow`), `Ui_SubWindow` +0x48 (only known to be copied into the created
  child scene object) and +0x50 (cleared then used as a fetch index), `Ui_DungeonPlaceWindow`
  +0x130/+0x154 (transform blocks, only the first word reported).
* Class boundaries: `Ui_SubWindow` (confidence 0.35) and `Ui_MemberListWindow` (0.40) really are
  groups of neighbouring classes; `Ui_MemberListWindow`'s dtor 0x004CC998 was renamed
  `Ui_UmaWindow_DeletingDtor` by R_033 (vtable 0x007786EC). Kept the generated names per the rules.
* `Ui_RowListWindow` +0x38 is used as a `Ui_List*` (passed to `Ui_List_SelectEntryById`, +0xC read)
  but the +0xC field itself was not decoded.
* All `size` values are echoed from the batch (the 0.0 artefact entries force them back up in
  apply.py anyway); the class evidence states the real extents, which are larger for most classes
  (e.g. `Ui_MemberListWindow` >= 0x45C, `Ui_DamagePopupWindow` >= 0x280, `Ui_DungeonPlaceWindow`
  >= 0x4A4). A merge that trusts these sizes will emit padding beyond the real object for
  `Ui_RankingWindow`, `Ui_EightLineTextWindow`, `Ui_SkillPointWindow` and `Ui_SubWindow`.
