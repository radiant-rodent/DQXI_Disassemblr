# S_096 — Ui struct/field naming batch (15 classes)

## What existed before

No `orchestration/types/out/S_096.json`, no `orchestration/done/S_096.md` and no scratch
directory existed when this worker started, so the "resumed" batch was done from scratch.
`orchestration/types/batches/S_096.json` lists 15 Ui classes with 4 sampled offsets each
(60 fields total).

## What I did

Read the constructor/update/method bodies of every class from
`decomp/readable/functions/` (and `decomp/readable/recovered/` for
`Ui_DigitTextWindow_Ctor` / `Ui_ThreeRowWindow_Ctor`), checked the raw Ghidra
pseudocode and the ARM disassembly with `python tools/fn.py 0xADDR --asm N` whenever a
field's role was not obvious, and cross-checked referenced helper names with
`tools/fn.py`.

Wrote one JSON object per class to `orchestration/types/out/S_096.json`:
15 classes / 60 fields = 35 clear names, 9 `maybe_*` (8 of them below 0.5) and 16
`unknown_*` at confidence 0.0.

### Decisions worth recording

1. **Vtable artefacts.** The batch offsets `0xD0`, `0xE0`, `0x120` are not object fields.
   They come from `(**(code **)(*param_1 + 0x34/0x38/0x48))(...)`: Ghidra typed the vtable
   as `int*`, so struct_db multiplied the byte slot by 4. Confirmed in asm
   (e.g. `ldr ip,[r2,#0x38]` in `Ui_ThreeRowWindow_InitPanes`). They are kept as
   `unknown_vtableSlotD0/E0/120` at 0.0 (matching S_092–S_095) so the batch's offset set is
   covered exactly once; the emitter can skip them.
2. **False bases cleared.** The batch base `Ui_AnimRef` for `Ui_ColorGaugeWindow` and
   `Ui_TenRowModePanes` for `Ui_ThreeModePaneWindow` come from `bases_seen`, which counts any
   call to a function whose class has role `ctor`. Both calls are layout/animation binders
   (`Ui_AnimRef_Bind`, `maybe_Ui_TenRowModePanes_Setup`), not base constructors. I set
   `"base": ""` for those two and explained it in the class evidence; all other bases are
   kept as generated (`Ui_Object` four times).
3. **Sizes echoed.** Class `size` is copied from the batch (so apply.py padding stays inside
   the observed object) even where the real object is larger: Tactics needs ≥ 0x2D8 for its
   eight 0x50-byte anim refs, ThreeMode needs ≥ 0x9E0 for its three 0x330-byte groups,
   MiniPlate ≥ 0x1F5. The real extent is stated in the class evidence.
4. **Embedded objects.** `Ui_AnimRef` fields are typed `Ui_AnimRef` with size 4 (the batch
   width), following S_087/S_094. `Ui_LayoutRef` is the 0x3C-byte embedded layout/animation
   binding block (fields `0` and `4` used, next field at +0xD4 in `Ui_MiniPlateWindow`).
5. **Unknowns instead of guesses.** `Ui_NumberWindow` +0x4C/+0x50 (ctor writes 1/0, no reader)
   and the MovieText node slots stay `unknown_*`/`maybe_*`; no purpose was invented.

## Not verified / open problems

* All 9 `maybe_*` fields (8 below 0.5) and all 16 `unknown_*` offsets — they are listed with their real
  evidence in the JSON; nothing was compiled or run.
* `Ui_DungeonSkillWindow` +0x98 (pointer to an object whose vtable slot +0x2C is called) and
  +0x128 (embedded section widget) are the weakest named fields (0.45/0.40).
* `Ui_MovieTextWindow` +0x11C/+0x138/+0x150 are embedded list/pane nodes; the helpers
  `func_00123594`/`func_001235A4` have no readable file, so only the registration role is
  proven, not the object class.
* `Ui_DualWindow` +0x10 is only released by the template-copy destructor 0x00310C90; the
  ctor in the batch fills +0x8/+0xC. The class may really be two template instantiations.
* `Ui_TextureNameWindow` +0xF0 is a copied material frame/UV word; `func_0065DBC8` has no
  readable file, so the exact record type is unknown.
* The true base of `Ui_ColorGaugeWindow`/`Ui_ThreeModePaneWindow` is not proven (see
  decision 2); `Ui_Object` is the most likely but was not asserted.
* `Ui_KeyPromptWindow` +0x10 `textId` is a 16-bit value shifted into the high half of the
  pane/text-id argument of an unnamed helper (0x003828B8); the name is an inference at 0.5.
