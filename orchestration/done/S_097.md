# S_097 — struct/field naming batch (subsystem Ui)

## What I did

Named all 15 Ui classes and all 46 field offsets in
`orchestration/types/batches/S_097.json`, using the readable C of each class's
constructor / InitPanes / dtor plus the shared UI helpers
(`Ui_Object_CtorBase` 0x001A66A0, `Ui_Object_InitMemberPair` 0x0021C2DC,
`Ui_NodeList_Register` 0x0036B45C, `Ui_PrizeWindow_Init` 0x001E61B8,
`Ui_ListWindow_CtorBase` 0x002CF200).

## Key decisions

1. **Batch offsets 208 / 224 / 288 are not fields.** In Ui_TxtLowerWindow,
   Ui_CampSelectWindow, Ui_ColorSelectWindow, Ui_CommandTargetWindow,
   Ui_EightRowIndexedWindow, Ui_EightRowTextWindow, Ui_FourLineMenuWindow,
   Ui_GoldCounterWindow, Ui_GridTextWindow and Ui_DualDisplayWindow the only
   "evidence" is `(**(code **)(*self + 0x34/0x38/0x48))(...)`; `struct_db.py`
   multiplied the vtable byte slot by 4 (0x34→0xD0, 0x38→0xE0, 0x48→0x120).
   Verified in asm, e.g. `Ui_CommandTargetWindow_InitPanes`:
   `ldr r1,[r4]` / `ldr ip,[r1,#0x34]` / `blx ip`. They are emitted as
   `unknown_vtableCall34/38/48` at 0.0 with the real slot named, so a later
   emitter can drop them instead of creating fake members. Same convention as
   S_093 / S_095 / S_096 / S_098.
2. **Three more batch offsets are base-relative artefacts** and are also
   `unknown_*` at 0.0:
   - `Ui_CreditEffectWindow +0x4C` — the store is
     `std_ConstructArray(base + 0x13, 0x003E0454, 0x50, 7)` where
     `base = self + 0x11C` (the embedded Ui_Object returned by
     `Ui_Object_CtorBase`), so the seven 0x50-byte AnimRefList entries really
     start at **self+0x168**.
   - `Ui_MessageCommandWindow +0x20` — the store is `puVar3[8] = puVar2` where
     `puVar3 = self + 0xD8C` (the embedded command list), so the real offset is
     **+0xDAC** and the value is a back-pointer to the owning window.
   - `Ui_IconRowWindow +0x54` — the only access is in 0x003D2560 / 0x003D2584,
     which install vtable 0x007699DC (`maybe_Ui_IconButton`, a *different*
     class); in that class it is a 0x50-byte `Ui_LayoutRef` released by
     `Ui_LayoutRef_Release(self+0x54)`.
3. **Sizes corrected where the batch value is provably too small.** The batch
   `size` is only `max_strong_field + width`, so it is a lower bound:
   - `Ui_CasinoPrizeWindow` / `Ui_MedalPrizeWindow`: 20 → **356 (0x164)**.
     `maybe_Menu_TalkParty_CreatePanel` (0x002175BC) allocates
     `Mem_AllocAligned_2(0x164, ...)` in case 7 and case 0x11 respectively, and
     the ctors write up to +0x164.
   - `Ui_ColorSelectWindow`: 212 → **440 (0x1B8)** = 0x78 + 4·0x50 cursor rows.
   - `Ui_EightRowIndexedWindow` / `Ui_EightRowTextWindow`: 212 → **556 (0x22C)**
     = 0x4C + 8·0x3C rows.
   - `Ui_CreditEffectWindow`: 288 → **920 (0x398)** = 0x168 + 7·0x50.
   - `Ui_IconRowWindow`: 88 → **136 (0x88)** — InitPanes writes the third strip
     pane at +0x84.
   - `Ui_MessageCommandWindow`: 3472 → **3696 (0xE70)** = 0xD8C + 0x24 + 8·0x18.
     The 9-slot sibling ctor needs 0xE88; the batch merges both ctors into one
     class, so the smaller variant is used and the difference is stated in the
     class evidence.
   The remaining classes keep the batch size (a harmless upper bound).
4. **Bases filled in where the batch had `None`.** Ui_CampSelectWindow,
   Ui_CommandTargetWindow, Ui_DualDisplayWindow, Ui_FourLineMenuWindow,
   Ui_GoldCounterWindow and Ui_GridTextWindow are set to `Ui_Object`: each
   starts with `drN(self)` and drives only the standard Ui_Object
   pane/text/refresh virtuals (+0x34/+0x38/+0x48), and the dtors are exactly
   `Ui_Object_DtorBase + func_0010F6CC`. Ui_CasinoPrizeWindow and
   Ui_MedalPrizeWindow get `Ui_PrizeWindow` (they call `Ui_PrizeWindow_Init`);
   Ui_MessageCommandWindow gets `Ui_ListWindow` (it calls
   `Ui_ListWindow_CtorBase`).
5. **Nothing was invented to fill an offset.** The 4 `maybe_*` and 21
   `unknown_*` fields say exactly what the code shows and no more; no
   `param_1`/`FUN_xxxx` is left in a name.

## Verification

- Strict UTF-8 decode + `json.loads` pass.
- Own validator: 15/15 classes, class/type equal the batch, every batch offset
  present exactly once, no duplicate offsets or names, every name a valid C
  identifier, `maybe_`/`unknown_` prefix exactly when confidence < 0.5, every
  field inside the declared class size — **0 structural problems**.
- Real merge dry run (`tools.typedb.apply.Evidence` + `merge_structs` on this
  file only): **15 classes / 46 fields / 0 issues**.
- `python tools/typedb/apply.py --validate`: **no S_097 issue**. The single
  error is another worker's (`S_066: Save_SlotUi@0x324 unknown type 'UiWindow'`);
  the 45 warnings belong to other batches.
- `tests/run_all.py` and `tools/verify_project.py` deliberately skipped:
  WORKER_RULES rule 5 excludes naming batches (N_/R_/R2_/G_/S_/V_) because this
  task only writes one JSON file. No source, header or binary changed.

## Not verified / open problems

- Every `maybe_*` (4) and `unknown_*` (21) field:
  - Ui_TxtLowerWindow +0x50 `maybe_stateIndex` (0.4)
  - Ui_CommandTargetWindow +0x4 `maybe_layoutHolder` (0.3), +0x4C
    `maybe_modePane` (0.45)
  - Ui_IconRowWindow +0x30 `maybe_layout` (0.4)
  - `unknown_*` at 0.0: the 0xD0/0xE0/0x120 vtable-call artefacts (14:
    TxtLower 1, CampSelect 3, ColorSelect 1, CommandTarget 1, EightRowIndexed 1,
    EightRowText 1, FourLineMenu 3, GoldCounter 1, GridText 1, DualDisplay 1),
    plus Ui_CreditEffectWindow 0x4C, Ui_MessageCommandWindow 0x20,
    Ui_IconRowWindow 0x54, and the four header words
    Ui_CasinoPrizeWindow/Ui_MedalPrizeWindow 0xC and 0x10.
- `Ui_CommandTargetWindow +0x4` is only proven to be a pointer whose +0x10 is
  the window's `UiLayout` (asm: `ldr r0,[r4,#4]` / `ldr r0,[r0,#0x10]` /
  `ldr r2,[r0]` / `ldr r3,[r2,#0x2c]`). The holder type is unknown.
- `Ui_IconRowWindow +0x30` is the same shape but one level deeper
  (`self+0x30 -> +0xAC -> +0x10`); the intermediate type is unknown.
- `Ui_CasinoPrizeWindow` / `Ui_MedalPrizeWindow` +0xC and +0x10 have **no
  reader anywhere in the class family** (`Ui_PrizeWindow_Init`,
  `Ui_PrizeWindow_Dtor`, `maybe_Ui_MedalPrizeWindow_SetCounterText/SetProductText/
  SetItemText` never touch them). They are the same words the shared header
  initialiser `Ui_Object_InitMemberPair` writes for 84 other classes, so they
  are header sentinels, not prize data — but their purpose is unknown.
- `Ui_MessageCommandWindow` merges two constructors with different entry counts
  (8 vs 9 × 0x18). The declared size 0xE70 covers the 8-slot variant only; the
  9-slot variant needs 0xE88. Whether they are really one class or two sibling
  classes is not proven.
- `Ui_CreditEffectWindow +0x11C` is typed as a vtable word (`objectBaseVtable`,
  `void*`) rather than a full embedded `Ui_Object`, because embedding a
  5016-byte Ui_Object would blow up the struct. The real base sub-object is
  larger than 4 bytes.
- `Ui_GridTextWindow +0x4C` / `+0x9C` are typed `Ui_AnimRef` (4 bytes) although
  they are 0x50 bytes apart, i.e. each is a `Ui_AnimRefList` whose head is the
  `Ui_AnimRef`. Same choice as S_093's `Ui_ScoreCheckWindow`.
- `Ui_IconRowWindow`'s batch includes two functions (0x003D2560, 0x003D2584)
  that belong to `maybe_Ui_IconButton` (vtable 0x007699DC), not to this class.
  The class attribution of the batch is therefore slightly over-broad.
- Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-up

1. Fix `struct_db.py`'s offset extraction for `(**(code **)(*X + 0xNN))(...)`
   and for `base + 0xNN` stores where `base` is not the object base. That would
   remove ~17 of the 21 `unknown_*` fields in this batch (and the same class of
   artefact in S_092/S_093/S_095/S_096/S_098) at the source instead of
   per-batch.
2. Recover the type of the holder at `Ui_CommandTargetWindow +0x4` and
   `Ui_IconRowWindow +0x30` (both reach the `UiLayout` through a `+0x10` /
   `+0xAC -> +0x10` chain). A single named `UiLayoutHolder` would fix several
   windows at once.
3. Split `Ui_MessageCommandWindow` into the 8-slot and 9-slot classes (vtables
   0x00768B40 and 0x00768BA0) so each gets its own size.
4. Fix S_066's `unknown type 'UiWindow'` (not my batch).
