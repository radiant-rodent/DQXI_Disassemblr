## What I did

(subsystem Ui), using `tools/fn.py` dossiers, the Ghidra/readable C in
`decomp/ghidra/functions/`, `decomp/readable/functions/`, the batch vtable slots and
`orchestration/types/structs.json`.

(37 batch offsets + 13 additional strongly-evidenced fields: `vtable` at +0 for 10 classes and
`paneSetId` u16 at +0x28 for 7 text windows).

## Decisions (also in the JSON evidence)

1. **Vtable-call artefacts.** Offsets 208 / 224 / 256 / 288 in seven classes are not members:
   `(**(code **)(*self + 0x34/0x38/0x40/0x48))(...)` are virtual calls through the vptr, and
   `struct_db` treated `*self + slot` as `self + slot` and multiplied by 4
   (0x34->0xD0, 0x38->0xE0, 0x40->0x100, 0x48->0x120). Verified in asm (e.g.
   `ldr r1,[r4]; ldr ip,[r1,#0x38]; blx ip` in 0x003B56A8). They are emitted as
   `unknown_vcall34/38/40/48` at confidence 0.0, matching the S_093/S_096/S_098 convention,
   because the instructions require every batch offset to appear once.
2. **Text tag base.** The real, repeatedly used member at +0x28 is a `u16` shifted into the high
   half of every text-layer id: `tag = (u16)*(self+0x28) << 16 | row`. It is named `paneSetId`,
   the name already used by 11 other Ui batches (Ui_StatusParamWindow, Ui_ProfileWindow, ...).
   It is an extra field (not in struct_db's evidence), hence the expected merger warnings.
3. **+0xD4 is a pane receiver, not a scalar.** In Ui_TwoLineGuideWindow the call
   `Ui_Window_CollectNamedPane(self+0xD4, name, tag, self+0x98)` matches
   Ui_DungeonMessageWindow exactly, where +0xD4 is `Ui_TextElement`; +0x98 is the layout
   reference (`Ui_LayoutRef`) as in Ui_CreditWindow. Both are typed as embedded objects with
   only their first word covered.
4. **+0x138 in the Balloon/Fade windows is an embedded Ui_Object.** For Ui_FadeWindow the three
   dtors call `Ui_Widget_ReleaseSub(self+0x138)` and `Ui_Object_DtorBase(self+0x138)`, which is
   exact proof; Ui_BalloonWindow has the same FindPaneAndNotify + Gfx_Node_SetVisible pattern
   and is typed by analogy (0.55).
5. **0x50-byte anim groups are `Ui_AnimRefList`.** The arrays in EffectIcons/EightSlot/FiveRow
   are constructed/released as 0x50-byte elements (ctor literal 0x003E0454 = Ui_AnimRefList_Ctor
   for FiveRow, dtor 0x003E04BC = Ui_LayoutRef_Release for all three; read from the instruction
   pool), matching S_013/S_094. Class sizes are extended by the proven array extents
   (636 / 728 / 480).
6. **Ui_CreditTextWindow base cleared.** The batch base `Ui_SlotPanel` is a false positive from
   `bases_seen`: `maybe_Ui_SlotPanel_Ctor` is called on `self+0x11C` (a member), not on `self`
   (placement-new convention proven by Ui_GuideWindow_Ctor `Ui_Object_CtorBase(self+0x4E)`).
   Base is set to "" and the embedded panel is a `maybe_slotPanel` field (0.45). The size is
   raised to 556 = 0x11C + the panel's proven 0x110 extents (two anim lists + 3-word array at
   panel+0x104).
7. **Ui_ChildWindow size corrected 172 -> 248.** The dtors release the 0x50-byte groups at
   +0x58 and +0xA8 and then destroy self, so the object is at least 0xF8; the batch size was
   only highest-strong-field+4.
8. **Ui_TitleTextWindow +0x918 / +0xBC8.** +0x918 is `messageWidget` (Ui_SelectElement +
   FUN_001dab30, same calls as Ui_TalkWindow's messageWidget); +0xBC8 is the first word of an
   embedded layout object (vtable slot +0x18 invoked with 0), named `maybe_layoutRoot` at 0.45
   after Ui_ActionWindow's naming of the same offset.
9. **`Ui_TitleTextWindow` 3020 is a lower bound.** The embedded +0xBC8 object is only partly
   covered; the class evidence says so.

## Open problems / NOT verified

- Every `unknown_*` (13) field and the `unknown_vcall*` naming: they document extractor
  artefacts, not real members. If the dispatcher prefers omission, they can be dropped.
- The `paneSetId` and `vtable` additions are strong by analogy but absent from struct_db's
  evidence (merger warnings, not errors).
- Ui_CreditTextWindow's embedded panel class is still `maybe_` (R3_024, 0.45); only its shape
  (two 0x50 anim lists + 3 x 4-byte entries at panel+0x104) is proven.
- Ui_BalloonWindow +0x138 is typed Ui_Object by analogy with Ui_FadeWindow, not by its own
  destructor (no dtor in this batch).
- Ui_TitleTextWindow +0xBC8 class and true extent are unknown; +0x918 widget class is
  `Ui_Widget` from the sibling Ui_Window/Ui_TalkWindow uses, not from a vtable dump.
- Ui_TwoLineGuideWindow +0x98/+0xD4 sizes are not proven (only first word recorded).
- All sizes for classes whose allocation size is unknown are lower bounds; nothing was
  compiled, exported or emulator-tested.
