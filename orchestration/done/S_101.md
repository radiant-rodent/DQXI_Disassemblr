## Decisions (important; some contradict the machine-generated batch)

1. **Kept every generated class name and `type`**, even where the current refine pass has renamed
   the only recovered method. This is explicit in the batch instructions and required by
   `apply.py` (the class must exist in `structs.json`). The discrepancy is recorded in the class
   `summary`/`evidence` for `Ui_ModelWindow` (now `maybe_Battle_ActionModel_CommitAttachNodes`) and
   `Ui_PopupWindow` (now `Ui_PagedTextChildWindow_InitPanes`).
2. **Four batch base classes are false positives and were cleared with `base: ""`.**
   `struct_db.py` treats any callee whose last name token starts with `Init*/Reset*/Create*` as a
   constructor. Here the "base ctor" was really a method call:
   * `Ui_FieldActionListWindow` — `Battle_ActionAnimEntry_Create(...)` creates a row, it does not
     construct the window.
   * `Ui_FieldMessageWindow` — `Ui_Panel_ResetAndPush(...)` resets the panel hanging off self+4.
   * `Ui_LoopPaneWindow` — `Ui_AnimRef_ResetPanes(...)` resets the anim ref at +0x4C.
   * `Ui_PopupWindow` — `Ui_PagedTextWindow_InitRows(...)` initialises the embedded child at +0x70.
   `Ui_CursorSelectWindow` → `Ui_Object` is a real base ctor (`Ui_Object_CtorBase`) and was kept.
3. **struct_db offset artifacts** (vtable-slot byte × 4 from `(**(code **)(*param_1 + SLOT))`):
   `Ui_TwoColumnTextWindow` +0x60/+0xD0, `Ui_EmotionWindow` +0x30, `Ui_ListTextWindow` +0x120,
   `Ui_PlaceNameWindow` +0xD0. Verified against the assembly that no load/store exists at those
   offsets. Emitted as `unknown_vtableCall18/34/0C/48` with confidence 0.0 and the real vtable slot
   named in the evidence, matching the S_092/S_093/S_096/S_098 convention.
4. **Sizes are echoed from the batch on purpose** (padding stays inside the observed object);
   the true lower bounds are stated in the class evidence where an embedded sub-object is proven
   (`Ui_LoopPaneWindow` >= 0x9C, `Ui_PopupWindow` >= 0x194, `Ui_DiveWarningWindow` /
   `Ui_DungeonStartWindow` >= 0x240).
5. **The +0x138 pane receiver is typed `Ui_AnimInOutWindow`, not `void*`/`Ui_AnimRef`.**
   `Ui_Widget_FindPaneAndNotify` (0x001D85EC) dispatches to `sender->vtable+0x20`; slot 8 of the
   widget vtable 0x0076AB6C is `Ui_AnimInOutWindow_InitPanes` (0x003E0628), and 0x0029126C
   (called right after on the same pointer) is that widget family's set-visible slot. Note this
   differs from the S_100 answer which called the 0x50-byte units `Ui_AnimRefList`; `Ui_AnimRefList`
   is a different (0x50-byte) clip unit, while the 0x108-byte +0x138 receiver is the in/out window.
6. **`Ui_LoopPaneWindow` +0x4C is typed `Ui_AnimRef`** (0x50-byte unit; `Ui_AnimInOutWindow` spaces
   three of them at +0x4C/+0x9C/+0xEC), matching S_096's convention.
7. **`Ui_FieldActionListWindow` +0x48 is the heap field** (`allocator` void* 0.8): it is the second
   argument of `Mem_AllocAligned_2(size, heap, align)` for every row allocation.
8. **`Ui_EightRowListWindow` +0x22C is `entryTable` void* 0.8**, the same name/type as the sibling
   `Ui_EightRowPagedWindow@0x250` (S_092); the table's +0x14/+0x18 are begin/end pointers.
9. **`Ui_FiveRowStatusWindow` +0x49 is the first byte of a 5-entry u8 row→member table**
   (InitRows fills it with 0xFF then numbers real members). The batch lists size 1, so it is typed
   `u8` and the array extent is documented in the evidence.
10. **Genuinely unknown offsets were not invented**: `Ui_FieldMessageWindow` +0x14 is
    `maybe_textObject` void* 0.4 (an embedded object registered at panel+0x10CC whose concrete
    class is unproven) and `Ui_ModelWindow` +0x28 is `maybe_modelOwner` void* 0.3 (points at an
    object whose +0x224 is a `Model_Equip*`; three candidate classes share that offset).

## Open problems / weakest answers

* `Ui_ModelWindow` is probably not a UI class at all: the only method is a battle model attach
  commit, and the class name is a stale M1 label. Class confidence 0.3; the field is 0.3.
* `Ui_FieldMessageWindow` class attribution is weak (R2_009, no caller); +0x14's concrete type is
  unknown (`void*`), and `base: ""` is my correction of a false `Ui_Panel` base.
* `Ui_PopupWindow` is really a paged-text child container; class name kept only because the batch
  and `structs.json` use it.
* The type of the +0x138 receiver (`Ui_AnimInOutWindow`) is inferred from vtable slot
  `+0x20 = 0x003E0628`, not from a dumped vtable of that particular instance.
* All echoed sizes are lower bounds from the batch; see decision 4.
* Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-up tasks

1. Fix `tools/typedb/struct_db.py` base detection: only treat a callee as a base constructor when
   the call is an assignment/return of the constructed pointer (or when the callee name ends in
   `Ctor`/`Construct`), not for `Init*`/`Reset*`/`Create*` method calls. This batch alone had four
   false bases; many other S batches likely carry the same error.
2. Teach `struct_db.py` to skip `*self + SLOT` vtable dispatches when computing field offsets
   (the `SLOT*4` artifacts) so workers stop re-deriving `unknown_vtableCall*` entries.
3. Re-run the `N_`/`R_` naming pass for `Ui_ModelWindow` (0x004ED870) and
   `Ui_PopupWindow` (0x00403D88) so the class names match the current function names.
4. Identify the concrete class of the object stored at panel+0x10CC (used by
   `Ui_FieldMessageWindow`), then replace `maybe_textObject` with a real type.
