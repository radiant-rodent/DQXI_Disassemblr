## What the classes are

* **Ui_RaceWindow** — the racing HUD window. `Ui_Layout_BuildTwoChildren` (0x00411588)
  calls `Ui_RaceWindow_BindPanels(self+0x210, self+0x98)` and
  `Ui_Racing_InitLapNumberPanes(self+0x210, ...)`, so the class is the sub-window
  embedded at layout+0x210. Field +0x196C = `racingPane`: the pane group looked up by
  the literal `"racing"` (0x00451204) through `func_0053649C(layout->f_14, name)` — the
  same idiom as `Ui_GaugeBar_BindPanes` storing `"gauge_bar"` at gaugeBar+4.
* **Ui_SmithMaterialWindow** — the blacksmith material list. Ctor 0x004DCC24 binds five
  rows x four columns (`txt_l0-4`, `txt_num_c0-4`, a `%s_sl` shadow of each centre name,
  `txt_num_r0-4`) at ids i, i|5, i|10, i|15, matching `menu_kaji_material_3d.bflyt`.
* **Ui_TitleThreeLineWindow** — binds `txt_title`, `txt_l1`, `txt_l2`, `txt_l3` plus an
  unlabelled fifth pane at 0x005A2624.
* **Ui_SinglePaneWindow** — one-pane window, vtable 0x0076A230 (slot 0 dtor 0x003D627C,
  slot 7 init 0x003D6238 binding the literal `txt`).
* **Ui_TxtRightWindow** — binds the single right-aligned pane `txt_r`.
* **Ui_TextLayerWindow** — small widget wrapping the dual-layer text renderer embedded at
  +0x70 (`Text_SetupDualLayersDefault(self+0x70, ...)`); 0x0066D294 is a method of that
  sub-object, its `this` being window+0x70.
* **Ui_SaveWindow** — owns the label record at +0x764 whose text
  `Ui_SaveWindow_LoadSlotName` measures with `wcslen`.
* **Ui_ResultWindow** — a phantom class, see below.

## Decisions and problems found

1. **Four of the eight batch fields are struct_db parser artefacts.**
   `Ui_SinglePaneWindow`, `Ui_SmithMaterialWindow`, `Ui_TitleThreeLineWindow` and
   `Ui_TxtRightWindow` all report offset `0xD0` with the evidence line
   `(**(code **)(*param_1 + 0x34))(...)`. That is the vtable slot 13 pane-bind call:
   struct_db's "address of a subobject passed to a call" pass matched `*param_1 + 0x34`
   and multiplied `0x34` by 4 because `param_1` is declared `int *`. The complete
   constructor bodies (68–584 bytes, read in full) touch only the vtable at +0 and the
   `u16` layout id at +0x28, so nothing exists at +0xD0. Emitted as `unknown_0d0` at
   confidence 0.0 with the real expression quoted. Consequence: the batch size 212
   (= 0xD0 + 4) is only an artefact-derived lower bound; the real class sizes are
   unknown. I kept 212 so the merger does not drop the offset.
2. **`Ui_ResultWindow` is not a real class.** Its only method `maybe_Ui_BuildFlags`
   (0x0064055C) has 24 callers from unrelated windows (Ui_DiveWindow, Ui_NumberRoll,
   Ui_SmithMenu, Ui_SubWindow, Ui_TxtLowerWindow, Ui_ThreeLineTwoSelectWindow) and only
   fills a two-byte flag pair from one byte of its first argument; refine pass R2_013 had
   already rejected the `ResultWindow_BuildEntryFlags` name. The generated class name is
   kept (the merger keys on it) but class confidence is 0.2 and the summary says so.
   Its +0x11C byte is `maybe_windowKind` at 0.4.
3. **`Ui_SaveWindow`'s +0x764 is not a `Casino_Slot`.** The batch's `Casino_Slot*` type
   guess came from the stale name `maybe_Casino_Slot_EvaluateWinLines` for 0x0064A2C8,
   which the readable tree has since renamed `maybe_Ui_Window_GetLabelText`. The record
   holds a data-manager record id at +4, an inline buffer at +0xC, flags at
   +0x1C..+0x1E, a kind at +0x20 and inline UTF-16 text at +0x22, so it is an embedded
   label record. Named `slotNameLabel` (`void*`, 0.5).
4. **`base` left null for all eight.** The shared base constructor is the seed symbol
   `drN` (0x001A6520, 273 callers) which belongs to no recovered class. The only
   candidate, `Ui_Window`, has a bogus 195,356-byte size, so setting it would emit a
   195 KB embedded base. The base-constructor evidence is recorded in each class's
   `evidence` string instead.
5. **Offset 0 added only where the batch recovered a vtable** (`Ui_SinglePaneWindow`,
   0x0076A230). The other seven are polymorphic too (they call virtual +0x34) but their
   vtable addresses were not recovered, so no offset-0 field was invented for them.
6. **The same offsets are also clustered into `Ui_Window` by struct_db.** S_079 named
   +0x11C `childManager`, +0x764 `maybe_casinoSlot`, +0x196C `maybe_childLayout` and
   +0x70 `headerText`. Those are base-class guesses; the +0x764 one is now known to be
   wrong (see 3). Whoever owns `Ui_Window` should revisit them.

## Not verified

* Every `maybe_*` field (2 of 9) and every `unknown_*` field (4 of 9).
* The `Ui_ResultWindow` and `Ui_SaveWindow` class identities — both rest on a single
  function name, and `Ui_SaveWindow_LoadSlotName` is a 0-byte tail call.
* The real sizes of the four 0xD0-artefact windows.
* Whether +0x196C / +0x764 / +0x11C / +0x70 are `Ui_Window` base fields rather than
  members of these derived classes (struct_db clusters them into both).
* The exact type of the pane group returned by `func_0053649C` (no readable file, not in
  `symbols_recovered.json`) and of the embedded text object at `Ui_TextLayerWindow+0x70`
  (no recovered class owns vtable 0x00766CB0).
* Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-up tasks

1. **Fix `tools/typedb/struct_db.py`**: in the "addresses of subobjects passed to a call"
   pass, skip matches whose base expression is dereferenced (`*param_1 + 0x34`) — that is
   a vtable slot, not a field. This alone removes the four bogus 0xD0 fields here and
   probably many more across the 151 S batches (S_104 and S_105 reported the same class
   of artefact).
2. **Re-batch `Ui_ResultWindow`**: the class has no real object. Either drop it or
   re-derive it from a genuine result-screen function.
3. **Re-batch `Ui_SaveWindow`** once a non-thunk save-window method is found; the current
   class rests on one 0-byte tail call.
4. **Revisit `Ui_Window`'s +0x764** (S_079's `maybe_casinoSlot` is wrong — it is a label
   record) and its +0x11C / +0x196C / +0x70 names.
5. **Recover the class of the dual-layer text widget** at `Ui_TextLayerWindow+0x70`
   (vtable 0x00766CB0, method 0x0066D294) — it is currently typed `void*`.
