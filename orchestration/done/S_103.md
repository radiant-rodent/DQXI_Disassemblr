# S_103 — Ui_Layout struct field naming

**Status:** completed (static naming batch; no code, headers or binaries changed)
**Owned output:** `orchestration/types/out/S_103.json` (single class, 463 fields, 164,444 bytes UTF-8)

## What the batch is

One class, `Ui_Layout` / `UiLayout` (generated name; kept as required), size 7848 (0x1EA8),
base `Ui_AnimClip` (echoed from the batch). 24 recovered methods + 72 functions that the struct
database attributes to the `Ui_Layout_*` name cluster.

## What I found (and the caveat that drives the whole answer)

The cluster is **heterogeneous**. It contains genuinely one layout object, but the M1/R_* name
prefix also absorbed functions that operate on sibling objects:

* `maybe_Ui_Layout_LoadAndBind_Type1` (0x006D9DC4) is the strongest evidence for the real layout
  root: it resolves ~100 named BFLYT parts. The asm shows `add rX,r4,#0x2B4` followed by
  `str <resource entry>,[rX]` and `Pack_HandlePair_MoveAssign(rX+4)`, and every later base is
  exactly +8 (`0x2BC, 0x2C4, 0x2CC, …`). So **+0x2B4..+0xA24 is one array of 8-byte slots
  `{resource pointer, pack handle}`** (239 slots). Every accessed offset in that range is named
  `layoutPartNNN` / `layoutPartNNNHandle` (plus byte aliases where struct_db split a pointer).
* `Ui_Layout_LoadBflyt` (0x0053D77C) parses `FLYT`/`grp1`, fills rootPane +0x10, pane registry
  +0x14 and layoutId +0x24; `Ui_GaugeBar_BindPanes` (0x003A5418) independently proves
  `layout->f_10` is the root pane (vtable+0x2C = find-by-name) and `layout->f_14` is the pane
  registry used by `func_0053649C(registry,name)`.
* `Ui_Layout_ReleaseChildren` / `ResetChildren` (0x0053D57C / 0x0053D718) operate on a
  **UiLayoutPlayer** (vtable 0x0078144C), not this object.
* `Ui_Layout_AllocSlotNodeB` (0x0018121C) constructs a **different class** (vtable 0x00758818),
  `maybe_Ui_Layout_ForwardSlot08/0C` are **Sound_3D** helpers (current names
  `maybe_Sound_3D_ForwardSlot08/0C`), and vtable 0x007585CC itself is shared with the
  field/NPC-node family (slot 4 is `maybe_Field_NpcFinishAction`). `Ui_Layout_InitShader`,
  `Ui_Layout_TriggerSound*`, `Ui_Layout_PlayNutAnim` etc. all run on scene-node objects.
* Several offsets are pure **struct_db artefacts** and are emitted as `unknown_*` at 0.0 with the
  real explanation, matching S_092/S_093/S_096/S_097/S_101:
  * vtable-slot scaling: 0xE0 = slot 0x38, 0xF0 = slot 0x3C, 0x100 = slot 0x40, 0x150 = slot 0x54;
  * callee/base-relative stores: 0x74 (shader record +0x1D), 0xA4/0xAC (new pane record 0x29/0x2B),
    0x90/0x54/0x58/0x5C/0x60 (UiLayoutSlot-relative because UpdateSlotProgress receives
    `&layout->f_138`, i.e. real layout offsets 0x1C8/0x18C/0x190/0x194/0x198);
  * 0x48..0x4F, 0x5E, 0x61 are the embedded text-style object at +0x254 seen through a wrong base
    (style+0x48 = layout+0x29C, and 0x29C..0x2B0 are in the batch too).

## Field naming decisions

* Slots: `layoutPart000` … `layoutPart238` (`void*`, 0.5) and `layoutPartNNNHandle` (`u32`, 0.45);
  byte-split entries got `layoutPartNNNPtrByteK` / `layoutPartNNNHandleByteK` (0.3–0.45).
  0x734 additionally noted as the sound target of `Ui_Layout_TriggerSoundByAttr`; 0x9F4 noted as
  the slot whose low byte `Ui_Layout_UpdateScreenBuffers` tests as an enable flag.
* Real header: `vtable` 0.95, `rootPane` 0.7, `widget` 0.6, `paneRegistry` 0.5, `layoutId` 0.6,
  `childListHead`/`childListSentinel` 0.4, `layoutRef` 0.4 (self+0x98 is the layout passed to the
  gauge/race binders; slot +0x2C is called on it every frame).
* Layout-level slot machinery: `slotState` 0.45, `slotActionTable` 0.5 (0x120) and
  `slotActionTable2` 0.45 (0x13C) are 12-byte `{object, code ptr, jump offset}` tables indexed by
  `activeSlotIndex` 0x15C / `activeSlotIndex2` 0x160; `animSlot`/`animSlot2`/`animSlot3` 0x138/0x140/0x19C
  (0.3–0.4, typed `UiSlot`); `slotFlags`/`slotFlags2` bits 0x20; `raceWindow` 0.5 (proved by
  `Ui_RaceWindow_BindPanels(self+0x210, self+0x98)`).
* Sibling slot-node class (`AllocSlotNodeB`, vtable 0x00758818) offsets 0x22C..0x250 and the
  embedded style/initialisation block 0x254..0x2B0 are honestly named `maybe_*` (0.15–0.3) or
  `unknown*` (0.0) from their constructor constants only; the three self-referential anchors
  0x25C/0x260/0x264 are `maybe_listAnchor*`.
* 0x1EA4: `maybe_soundQueue` (`UiSoundQueue`, 0.35) — `TriggerSoundByAttr` passes its address to
  0x0062F038 and plays the result through 0x734.
* Nothing was invented to fill a slot: 35 fields are `unknown_*` at 0.0, 208 are `maybe_*` below 0.5,
  211 are `layoutPart*` (the accessed members of the 239-slot table) and 9 are plain header names.
  Class confidence 0.35 because of the mixed cluster.

## Not verified / open problems

* The class identity itself: `Ui_Layout` is a name-prefix cluster, not a clean object. The vtable
  0x007585CC is shared with the field/NPC-node family and `AllocSlotNodeB` builds an object with a
  different vtable (0x00758818). A follow-up should split the cluster:
  * `UiLayout` (BFLYT root + part table, 0x2B4..0xA24) — rename the 0x0053D7xx/0x006D9Dxx group;
  * `UiLayoutPlayer` (0x0053D57C/0x0053D718, vtable 0x0078144C);
  * `UiLayoutSlot`/`UiPartSlot` (0x0061A1B4/0x0017B* family, the embedded blocks at +0x138);
  * the 0x0017Axxx/0x001B7xxx/0x005Fxxxx Gfx/NPC-node family (vtable 0x007585CC);
  * the `maybe_Sound_3D_*` helpers at 0x00542xxx.
* The size 7848 is `max_strong_field + width` from the single 0x1EA4 access
  (`TriggerSoundByAttr`); it is a plausible upper bound but no allocation of 0x1EA8 was found.
* Part-slot numbering is positional, not semantic: the name-hash table at 0x006DD760 has not been
  inverted, so `layoutPart000..238` are honest placeholders. A later worker could map each slot to
  its pane name by decoding the hashes / the `grp1` table.
* Header 0x18/0x1C/0x20 (layout-file section words) are only provisionally named; the section tag
  was not decoded.
* 0x1EA4 typed `UiSoundQueue` by role only (no vtable of that embedded object was dumped).
* All 0.0/`unknown_*` fields remain unknown by design.
