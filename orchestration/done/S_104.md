## What the classes really are

* **Ui_TextLayout** (vtable 0x007815A0, 12 slots) is the BFLYT `nw::lyt::TextBox`-style
  text layout: the real methods are `Ui_TextLayout_BuildDrawParams` (0x0053F078),
  `DrawString` (0x0053F7FC), `FreeBuffers` (0x0053F184), `MeasureAndPlaceRun`
  (0x0053EED4), `DrawScaled` (0x0053F208), `Ui_TextBuffer_AppendChars` /
  `WriteCharsAt` (0x0053F940 / 0x0053F9EC). Named from their bodies:
  `font` (+0xB4), `glyphBuffer` (+0xA4), `glyphQuads` (+0xF8), `fontAux` (+0xFC),
  `bufferCapacity` (+0xCC), `bufferLength` (+0xCE), `textFlags` (+0xD0),
  `alignFlags` (+0xD1), `clipWidth` (+0x3C). The ctor 0x00277BBC proves the object is
  0xA7F4 bytes and explains the tail: 16 buckets of 0x9BC bytes at +0x10 (end 0x9BD0),
  16 per-bucket state words at 0x9BD0, 0x7C eight-byte sorted rows at 0x9C10 and an
  embedded 0x228-byte `Ui_LayoutState` at 0xA5C8.
* **Ui_DataPanel** is the save-data display panel (the object `OpenWithStrings` /
  `Reset` / `OpenSimple` operate on): message-text block at +8 (0x181A bytes copied from
  work+0x2E2F8), 31 x 0x200 party/member preview records at +0x1830, an embedded
  SaveWork image at +0x5630 (`Ui_DataPanel_CopyFromWork(self+0x5630, work+0x24A98)`),
  two bound panes with kind 0x5E, mode at +0xE0F4, state at +0xE110, mutex at +0xE118.
  `maybe_Ui_DataPanel_OpenFromByte` allocates 0xE3C8 bytes for the singleton, so the true
  panel size is ~0xE3C8, not the echoed 0x24A9C.
* **Ui_SixRowChildLayout** is a small helper used by `Ui_SixLineTextWindow_InitPanes`;
  +0x28 is the u16 high half of the animation node id (`row | f_28 << 16`).
* **Ui_CampLayout** is not a class at all: 0x00210A38 is 8 literal-pool bytes misfiled as
  a Thumb function (doc N_103 says the same; its "body" contains `halt_baddata()`).

## Decisions (some contradict the machine-generated batch)

1. **Kept every generated class name and `type`** (required by the batch and by
   `apply.py`).
2. **Cleared two false bases with `base: \"\"`:**
   * `Ui_TextLayout` batch base `Ui_RecipeBookState` — no base-ctor call exists; the real
     methods are pane/text-box methods.
   * `Ui_DataPanel` batch base `Ui_Part` — `maybe_Ui_DataPanel_OpenFromByte` calls
     `maybe_Ui_Part_SetupFromActorSprite(&self->f_5A4, self)`, a method on an embedded
     sub-object, not a base constructor (same failure mode as the four false bases in
     S_101 decision 2).
3. **Struct_db parser artefacts** are named `unknown_*` at 0.0 with the real expression
   quoted, not invented fields:
   * `Ui_TextLayout` 0x160/0x180/0x1B0/0x1E0/0x3A0/0x4E0 = vtable-slot byte × 4
     (slots 0x58/0x60/0x6C/0x78/0xE8/0x138).
   * `Ui_DataPanel` 0x80 (a `u32* + 0x20` sort step), 0x2F8 (insertion-sort midpoint
     0x2B8+0x40 in `maybe_ItemBag_SortEntriesByKey`), 0x570 (+0x15C-element list bound).
   * `Ui_TextLayout` 0xA7F4 is the word just past the ctor-proven size (0xA7F4).
   * `Ui_CampLayout` 0x11C/0x120 are the two stores of a bogus
     `halt_baddata()`-derived body.
4. **Ui_DataPanel is a fusion of four different bases**, and the field evidence must be
   read per base: ItemBag-relative (+0x2B8..+0x274C), SaveWork-relative (+0x4B30,
   +0x5418, +0x88E4, +0x88FA, the sequential CopyFromWork blocks), GameWork-relative
   (`CaptureSceneState` writes 0x27224+), and the panel itself (0x5630, 0xE0D8..).
   Names use the verified FACTS where available: `itemOwnershipMask` (0x168 B = 2880
   bits), `fieldTriggerMask` (0x64 B), `saveNameBuffer` (64 wchar_t), `pastwordVisitedBits`.
5. **Sizes are echoed from the batch on purpose** (S_101 convention), and the true lower
   bounds are stated in the class evidence: `Ui_TextLayout` = 0xA7F4 (ctor),
   `Ui_DataPanel` ≈ 0xE3C8 (allocation). `apply.merge_structs` grows them to 43,000 and
   173,608 respectively because a few batch offsets are relative to another base; the
   class evidence calls this out explicitly.
6. **Nothing was invented to fill an offset.** 230 of 374 fields are `unknown_*` at 0.0
   (mostly the sequential SaveWork-image copies in `Ui_DataPanel_CopyFromWork`, whose
   meaning is not identifiable from the copy alone, plus the parser artefacts above);
   72 are named at >= 0.5 and 72 are `maybe_*` at 0.25–0.45.

## Open problems / weakest answers

* **`Ui_DataPanel`'s true identity is mixed.** The batch merged the save-data panel with
  ItemBag (`0x00611xxx`), SaveWork (`0x00612xxx`/`0x00614xxx`) and GameWork
  (`CaptureSceneState`) helpers. Several class offsets therefore do not denote panel
  members: +0x2B8..+0x274C are ItemBag entries, +0x4B30/+0x5418 are SaveWork bitmasks,
  0x27224+ are GameWork offsets. Do not emit a single 0x24A9C/0x2A628-byte struct from
  this class without splitting it.
* **`Ui_TextLayout`'s 0x9BD0..0xA7F4 tail** is described from the ctor + FACTS
  (16 × 0x9BC buckets, 0x7C rows, embedded 0x228-byte layout state), but the 0x0026xxxx
  methods that touch it now carry `BattleAi_*` names (FACTS: poisoned range
  0x00269F64..0x00277700). Whether the tail is really the text layout's row/candidate
  store or a separate battle-AI context sharing the `self` pointer is **not resolved**;
  those fields are `maybe_*`/`unknown_*`.
* All `maybe_*` (72) and `unknown_*` (230) fields are unverified beyond the quoted
  evidence line; in particular `maybe_renderObjectHandle`, `maybe_drawKeyLow/High`,
  `maybe_actionOwner`/`actionContext`, `maybe_workBuffer` and `maybe_saveWork`.
* `Ui_DataPanel` +0x20/+0x24 copy two words from the unnamed global 0x007285FC; +0x8980/
  +0x8984 and the eight 0x64-bit "accumulators" are only known from the copy/restore
  sequence.
* The `Ui_CampLayout` class has no real function and no fields; it should be removed from
  `structs.json` by a tooling fix, not renamed.
* The full test run and `tools/verify_project.py` were **not** run (naming batch, rule 5).
  Nothing was compiled, exported or emulator-tested — static naming only.
