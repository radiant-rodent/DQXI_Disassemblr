## What the classes really are (evidence)

* **Ui_Widget** (vtable 0x007584E8, size 5548, base Ui_Object) is the shared on-screen
  widget. `Ui_Widget_InitLayoutLinks` (0x0021F7C4) proves the two embedded layout-text
  lists at +0x14 and +0x768 with cursors at +0x74C/+0x760 and the default limits
  (+0x1248=0xF, +0x1228=+0x1230=1, +0x124C/+0x124D/+0x1254=0). `Ui_Widget_CountChildren`
  (0x005797D8) walks the child ring +0x10..+0xC, `Ui_Widget_FindChildByName` (0x005B0A54)
  walks the pane list at +0x14, `Ui_Widget_ProjectAnchorObjectAlt` (0x0044703C) resolves
  the actor handle at +0x4C, and `Ui_Widget_DetachAndDestroy` (0x001C7524) uses the
  per-kind slot list (`owner + kind*0xC + 0x24`). +0x4D8 is an embedded `Field_Object2D`
  (`Field_Object2D_RunTouchTransition 0x00423648(self+0x4D8, self)`). The 162-field batch
  is a **union** of many derived widget classes, so most high offsets are `maybe_*`.
* **Ui_ListWidget** (vtable 0x0076CF80, 760 B) is the scrolling list widget:
  `Ui_ListWidget_ConfigureRowFromType` (0x002578D4) reads row-type bytes from the
  +0xC..+0x10 buffer, sends the +0x24 / +0xA8 column blocks to
  `Ui_ProfileWindow_SetEntry(f_130, ...)` and uses the mode byte +0x12D. A second ctor
  (0x002E8C68) builds the intrusive node/list at +0x13C..+0x15C.
* **Ui_PlateWidget** is a six-row plate: `Ui_PlateWidget_InitRows` (0x00229594) links six
  embedded row descriptors (link / self / id / flags) against fixed owner pane offsets and
  the "plate_base" layout is at +0xA8.
* **Ui_TextListWidget** ctor (0x00478A84) builds four embedded intrusive list heads with
  their own sub-object vtables 0x0078312C and 0x00783438.
* **Ui_ThreeListPanel** is the save-slot panel: `Save_SlotUi_ResetThree` (0x003B43FC) and
  0x003B4FC8 rebuild/select the three-slot `Save_SlotUi` sub-panel at +0x158.
* **Ui_SingleLayoutPanel** is really the character-status window layout
  (`Ui_CharaStatusWindow_DeletingDtor` 0x0025958C releases the layout ref at +0x11C).
* **Ui3D_Panel** is the battle animation-window destructor helper
  (`maybe_Battle_AnimWindow_DtorWithVtable` 0x004E45D0 stores the secondary table at +0x220).
* **Ui_StatComparePanel** writes nine stat rows through `Ui_TextElement_SetString` /
  `Ui_Element_SetColor` using the pane row base +0x28 and text table +0x34.
* **Ui_NumPanel** binds the single pane named `num` into `Ui_AnimRef_Bind(self+0x4C, ...)`.

## Decisions (some contradict the machine-generated batch)

1. **Kept every generated class name and `type`** (required for merge compatibility).
2. **Cleared no bases**, but noted in `Ui_Widget`/`Ui_Object`-like classes that the batch
   list is a union: with `base: Ui_Object` the first 0x1398 bytes overlap the base class,
   so offsets there repeat Ui_Object member meanings and are named consistently with
   S_078's Ui_Object output where they coincide.
3. **Struct_db artefacts** are `unknown_*` at 0.0, with the real expression quoted:
   `Ui_ValuePanel` 0xD0 / 0xE0 / 0x120 are exactly 4 × the vtable slots +0x34/+0x38/+0x48,
   i.e. `(*self+0x34)(self,...)` was mis-scaled into a field offset — the constructor
   touches no member at those offsets.
4. **Offset-scaled sub-object stores**: Ui_TwoListPanel +0x58/+0x5C are `puVar3[0x16/0x17]`
   where `puVar3` is the embedded sub-object (not `self`), so they are named
   `maybe_subObjectState58/5C` at 0.3 rather than given a false self-relative purpose.
5. **Sizes are echoed from the batch on purpose** (S_101/S_104 convention); the class
   evidence states what is certain (vtable, ctor, sub-object spans).
6. **Nothing was invented to fill an offset**: 3 fields are `unknown_*` at 0.0 (all
   Ui_ValuePanel parser artefacts) and 235 are `maybe_*` between 0.3 and 0.45. The
   remaining 80 fields are named at 0.5–0.95 (vtable, layout links, list heads, six plate
   rows, child draw lists, profile window, single-pane anim ref, etc.). `maybe_` is used
   strictly below 0.5 (no `maybe_` name carries 0.5 or more).

## Open problems / weakest answers

* **Ui_Widget's 162 fields are not one class.** Vtable 0x007584E8 is real, but the batch
  aggregates accesses from many derived widgets (world-anchor widget at +0x4C, touch
  object at +0x4D8, save-slot panel at +0x158, window-layout fields at +0x54/+0x10C).
  Several names (`maybe_actorHandle`, `maybe_fieldObject2D`, `maybe_saveSlotUi158`,
  `maybe_stateHandlerTable`, all the `maybe_*` sound state/timer bytes) are only true for
  the functions quoted in their evidence, not necessarily for Ui_Widget itself.
* **Ui_Object overlap**: offsets below 0x1398 duplicate the Ui_Object base; the merge keeps
  both definitions and chooses the most specific class at emit time. If Ui_Object is ever
  re-named, these names should be reconciled.
* **Ui_ListWidget** is likewise a fusion: the 0x00258000 ctor builds a 0x31C-byte view
  object (`self[0x4C]`), while 0x002E8C68 builds the intrusive list; the column blocks at
  +0x24/+0xA8 are typed `u8` (block start) because their internal layout is not decoded.
* **Ui_PlateWidget** 0x1C4..0x1C8 / 0x1CC..0x1120 (`Ui_Part`, entry list, row-list object)
  are only known from call sites; the six row descriptors (0x120..0x1C0) are solid.
* Full `tests/run_all.py` and `tools/verify_project.py` were **not** run (naming batch,
  rule 5). Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-up tasks

1. **Teach `tools/typedb/struct_db.py` to skip vtable dispatches** (`(*self + slot)(...)`)
   when computing field offsets; that alone removes the Ui_ValuePanel artefacts and
   probably many `unknown_vtableSlot*` entries in other batches.
2. **Split `Ui_Widget`** by vtable/derived-class identity instead of by function name
   prefix: the batch mixes UiWorldAnchorWidget, the touch-object widget, the save panel and
   the generic widget. A per-vtable grouping would give cleaner field names.
3. **Decode the +0x24/+0xA8 row field blocks of `Ui_ListWidget`** (`Ui_ProfileWindow_SetEntry`)
   and the 0x0x31C view object built by 0x00258000 — then the nine +0x28..+0x48 pointer
   words can get real names.
4. **Confirm `Ui_TwoListPanel`'s subclass identity** (slots 0/1 are its own dtor pair
   0x329DB4/0x329D60; vtable 0x00763E68 also carries Ui_TwoListWindow_Init) and whether the
   pane-group/emotion-balloon sub-objects are at +0x80/+0xD8 as the ctor argument chain
   suggests.
