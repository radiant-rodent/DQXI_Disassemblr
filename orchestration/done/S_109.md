# S_109 - Ui struct field naming (15 classes / 300 fields)

## What I did

Named all 15 classes and every one of the 300 field offsets in
`orchestration/types/batches/S_109.json` (subsystem Ui) and wrote
`orchestration/types/out/S_109.json` (UTF-8, 70.6 KB).

Classes: Ui_Message (109), Ui_PanelMessage (34), Ui_RecipeMessage (11),
Ui_SpiritCaptureMessage (10), Ui_TwoLineMessage (8), Ui_TrainingMessage (6),
Ui_TitleMessage (3), Ui_PresentMessage (1), Ui_LayoutText (41), Ui_Text (36),
Ui_MainMenuText (21), Ui_StreetPassText (12), Ui_ListText (4), Ui_IconText (2),
Ui_MessageText (2).

Work method: read the batch dumps plus the readable C of the constructors and the
main update/draw methods (`tools/fn.py`, `decomp/ghidra/functions`,
`decomp/ghidra/recovered`), and used the established facts (item/party/message
tables, `Ui_FourStateWidget` vtable slot 6 = 0x0029126C, `Ui_AnimRef` pane helpers
0x003E00CC/0x003DFF34/0x003E043C/0x003E04BC, `FUN_0035EB98` party record,
`0x0063FD24` action rows, `0x0018C184`/`0x0018C1B8` spell/skill wrappers,
`Gfx_SpriteActor_AddChildC`, `Event_OnCutSceneCommand`).

## Important findings / decisions

1. **Many offsets in `Ui_Message` and `Ui_Text` are vtable-slot numbers, not
   members.** struct_db scraped `(**(code **)(*param_1 + N))(...)` expressions and
   multiplied `N` for `int *param_1`. Those offsets are emitted as
   `unknown_vtableSlot0xNN` with confidence 0.0 and the real expression quoted in
   `evidence`. I did not invent a purpose for them. In `Ui_Text` this affects
   0xE0/0x120/0x160/0x180/0x1A0/0x540; in `Ui_Message` 0x80/0xD0/0xF0/0x100/
   0x120/0x180/0x1E0/0x1F0/0x230/0x250/0x290/0x2B0/0x2C0/0x310/0x420/0x430/0x440/
   0x450/0x460/0x470/0x480/0x490/0x4A0/0x4E0/0x4F0/0x500/0x510/0x520/0x540;
   in `Ui_LayoutText` 0x50/0x60; `Ui_StreetPassText` 0x150; `Ui_ListText` 0x1A0.
   `Ui_Text` 0x148 is NOT such an artefact: it is the address `self+0x148` passed
   to the Ui_AnimRef helpers, so it is named `maybe_animRef`.

2. **`Ui_Message`'s six weak fields at 0x92F4..0x9448 do not belong to this
   class.** They all come from `Ui_Message_ResolveSpeakerName` (0x0062A07C), whose
   only callers are `maybe_Actor_LinkSubObjectNodes` and
   `maybe_Field_SceneSpawnBlock_NpcColorBalloon`; the function compares two
   pointers into the caller (0x92F4 vs 0x9448) and runs `wcslen` on +0x92FC. That is
   a speaker-name block of an actor/NPC object, not a UiMessage member. The offsets
   are still emitted (rule: every batch offset exactly once) as
   `unknown_actorSpeaker*` at confidence 0.0. The class size stays the
   evidence-based 5104 (0x13F0); the merger will inflate the emitted struct to
   0x9449 because of those six offsets - this is a pipeline artefact, not the real
   layout.

3. **`Ui_RecipeMessage` and `Ui_TwoLineMessage` bases are embedded objects, not
   bases at offset 0.** In `Ui_RecipeMessage` the ctor builds `Ui_Object` at +0xA0
   (its own vtable is at 0). In `Ui_TwoLineMessage` the Ui_AnimRefs are at +0x4C and
   +0x9C. I therefore cleared `base` (the merger accepts "" -> null) and said so in
   the class evidence. `Ui_MainMenuText`'s `Ui_TsuyosaWindow` is likewise embedded
   at +0x30, so its base was cleared too.

4. **`Ui_PanelMessage` is a skill-panel message, not a generic panel.** Its rows
   are 0x1C-stride records with a u16 skill id at +8; `ResolveTargetPos` calls
   `SkillPanel_CanUnlockSkill(characterId=self+0x199, skillId=row+8,
   panelType=rowPanelTypes[row])` and `UpdatePrices` writes ten cost labels using a
   1/10/100 multiplier. That is why the fields are named `characterId`,
   `rowTable`, `rowPanelTypes`, `costMultiplier`, etc. The generated class name was
   kept.

5. Other named structures: `Ui_Message` +0x6C is an EventState (passed to
   `Event_OnCutSceneCommand`), +0x90 is the message-argument text objects
   (`Ui_MessageArgs_LoadCharacterModels`), +0x12D8 is the message record, +0x1380
   the state id, +0x138C the current actor. `Ui_SpiritCaptureMessage`/`Ui_TitleMessage`/
   `Ui_PresentMessage` embed a `UiFourStateWidget`; `Ui_StreetPassText` and
   `Ui_TrainingMessage` are resource+handle holders for named `.bxon` packs;
   `Ui_LayoutText` is the glyph-quad writer with its string descriptor at 0,
   vertex buffer at +0x400 and 0x60-byte colour matrix at +0x62C; `Ui_Text` is the
   higher-level text object with a layout object at +4 and an embedded
   ContainerInlineVector8B at +0x10A8.

## Verification

* Strict UTF-8 read + `json.loads`: OK.
* Class list/order equals the batch; per-class emitted offset set equals the batch
  offset set exactly (300 total), no duplicate offsets or names.
* Every name is a valid C identifier; every field with confidence < 0.5 is
  prefixed `maybe_` or `unknown_`; every `unknown_*` is 0.0.
* `tools/typedb/apply.py --validate`: 0 errors / 0 warnings attributable to S_109
  (the single reported error is pre-existing `S_066:Save_SlotUi@0x324 unknown type
  'UiWindow'`). Note: `--validate` also rewrites `orchestration/types/merged` as a
  side effect of the tool.
* In-process `Evidence` + `merge_structs` restricted to S_109: **0 issues**, 15
  classes / 300 fields merged.
* Per WORKER_RULES rule 5 the full `tests/run_all.py` and
  `tools/verify_project.py` were skipped (naming batch, no code changed).

## Open problems / not verified

* Every `maybe_*` field (roughly half of the total) is a hypothesis; the JSON
  evidence says exactly what the code shows.
* The `Ui_Message` merged size 37961 vs the true 5104 is caused by the misattributed
  speaker-name offsets; upstream struct_db should exclude
  `Ui_Message_ResolveSpeakerName` from the UiMessage field evidence.
* `Ui_Message` itself looks like a union of at least two real classes: its vtable
  (0x0077B8F0) has 15 slots but `Ui_Message_Update` calls slot +0x150, so some of the
  24 batch methods belong to a larger message-window class. I kept the generated
  name and flagged the vtable-slot artefacts.
* `Ui_Text` likely also mixes classes (its +4 layout object, +0xD4 Ui_TextElement
  array and +0x10A8 inline vector are separate sub-objects); only the offsets the
  batch asked for were named.
* `Ui_RecipeMessage`'s +0x4C..+0x54 offsets are written through the embedded
  Ui_Object pointer (`puVar3 = self+0xA0`), i.e. they are base-relative; the emitted
  names say so but the header will place them at +0x4C of the derived class. This
  needs an upstream re-base.
* Nothing was compiled, exported or emulator-tested - static naming only.

## Suggested follow-ups

* Split `Ui_Message` into the real `Ui_Message` (vtable 0x0077B8F0) and the larger
  message-window class whose vtable has >= 0x154 bytes, then re-run struct_db.
* Exclude `0x0062A07C` from the UiMessage evidence set (it is actor speaker-name
  code) so the class size stops inflating to 0x9449.
* Give `Ui_PanelMessage` its real name once the skill-panel screen class is
  identified (it is a skill panel list message).
* Decode the row-record fields +0x12..+0x17 used by `Ui_PanelMessage` colour
  gradient code (six icon/part slot ids) to turn `maybe_gradientMode*` into real
  names.
