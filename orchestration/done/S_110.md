# S_110 — Ui struct/field naming (14 classes, 420 offsets)

## What was done

Named every class and every batch field in `orchestration/types/batches/S_110.json` and wrote
`orchestration/types/out/S_110.json` (14 classes / 420 fields, 102,953 bytes UTF-8: 157 solid
names, 212 `maybe_`, 51 `unknown_`).

Method: read `README.md`, `orchestration/PLAN.md`, `orchestration/WORKER_RULES.md` and the batch;
then read the readable C of the constructors and update/draw functions of each class (located by
address suffix under `decomp/readable/functions/`), cross-checked offsets/widths against
`orchestration/types/structs.json`, and used `python tools/fn.py` for callee identities and
vtables. No whole-tree walk/grep was used.

Checks performed on the output:

* strict UTF-8 decode + `json.loads` — OK;
* emitted offset list == batch offset list, in order, for all 14 classes; no duplicate offsets;
* every name is a valid C identifier, unique inside its class; `maybe_` exactly when
  confidence < 0.5, `unknown_` at 0.0;
* every field `type` resolves through `tools.typedb.apply.normalise_type` (builtins, `void*`,
  `void (*)(void)`); class `type` is `class` without underscores;
* in-process run of the real merger (`tools.typedb.apply.Evidence` + `merge_structs`, nothing
  written to disk): **0 issues, 14 classes, 420 fields**.

The full `tests/run_all.py` / `tools/verify_project.py` run was deliberately skipped per
WORKER_RULES rule 5 (naming batch: only one JSON file, dispatcher validates it).

## Decisions and problems found

1. **Kept every generated class name and the batch `type` rule** (`type` = class without
   underscores). Stale/unproven identities are explained in `summary`/`evidence`, not renamed,
   because the merger keys on `class`.
2. **struct_db mis-attribution is common in this batch.** Several "classes" are unions of a big
   object and smaller ones that appear at offset 0 in other functions:
   * `Ui_ItemMenu` 0x48..0xE8 is the separate `Ui_ItemMenu_Row` object (vtable 0x00765274) zeroed
     by its ctor; its three `0xFFFFF000` pack-handle pairs (0x80/0x84, 0x88/0x8C, 0x90/0x94) and the
     vtable/type word at 0x98 are named, the remaining zero-initialised words are `unknown_*` 0.0.
   * `Ui_List` above +0x3000 (cursor/change counter at 0x3280/0x3284) and 0x48B4..0x48B8 are a
     message-list and an input event, not fields of the big list.
   * `Ui_ItemList` 0x4/0x8/0xC are a four-entry u32 weight table read by
     `maybe_Ui_PickWeightedKeyValue` (0x0018DE24), unrelated to the item screen.
   * `Ui_DebugMenu`: 0x10/0x11/0x14 *are* real (same object), but the class name is unproven —
     the function docs say the page/attract reading cannot be confirmed and vtable slot 1 is the
     shared `Ui_SmithMenu_Init`.
   * `Ui_RowList` +0/+8/+0x14..+0x30 come from `maybe_Ui_RowList_Ctor` (0x003DFB14), which the
     recoverer flags as a generic drawable-row base, not the 5-row story list.
   * `Ui_MainMenu` is a text-resource holder *and* the item-screen list block (see table).
3. **Input-event contamination**: `Ui_SmithMenu` 0x16/0x17/0x18 are accessed as `ev->f_16/f_17/f_18`
   on the `UiInputEvent` argument; emitted `unknown_*` 0.0 rather than inventing self fields.
4. **Weak field**: `Ui_Menu` 0x4A3C has one access and is almost certainly a mistyped `self`; kept
   at 0.0. Note the merger inflates `Ui_Menu` size from 2088 to 19008 because of it (same known
   upstream behaviour as reported by S_109) — the batch size is the true one.
5. **Size caveats**: `Ui_ItemMenu` 4380 is a lower bound (`Mem_AllocAligned_2(0x1170)` = 4464 in
   `Ui_ItemMenu_Create`). `Ui_SmithMenu` 4732 = 0x127C matches its highest field and its ctor.
   `Ui_PointText`/`Ui_TitleText` 212 is the base-window size, not a member layout.
6. Names were only given above 0.5 when a string literal, a named callee, an allocation constant
   or a direct store/compare supports them (e.g. `s_menu_kaji_list_buki` -> `weaponList` 0.9,
   `criticalIcon` 0.85, `itemIdBegin/End` 0.7, `entryListSentinel/Begin` 0.65); everything inferred
   from shape alone is `maybe_` < 0.5.

## Not verified

* Every `maybe_*` field and every class-level base (`Ui_SmithMenu`/`Ui_ItemMenu` inherited
  `Ui_Object` from the batch; `Ui_List` `Ui_AnimRef`; the rest left null on purpose because the
  shared seed constructor `drN` belongs to no recovered class and `Ui_Window`'s 195,356-byte size
  is bogus).
* Which sub-object the 0x48..0xE8 block really belongs to for Ui_ItemMenu, and the real split of
  Ui_MainMenu / Ui_List / Ui_ItemList (all are unions of several classes in struct_db).
* The equipment-list update functions 0x00199A10 / 0x0019A514 / 0x00199B60 have no readable C, so
  six of its ring/index fields stay inferred.
* `Ui_DebugMenu`'s real identity, `Ui_PointText`/`Ui_TitleText` real sizes, and the exact 0xD0
  artefact origin (documented as the virtual +0x34 pane-bind call).
* Nothing was compiled, exported or emulator-tested — static naming only.
