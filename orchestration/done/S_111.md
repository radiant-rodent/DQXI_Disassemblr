## Decisions / problems found

1. **struct_db ×4 artefacts.** Several "fields" are vtable-slot numbers scraped from
   `(**(code **)(*self + N))` and multiplied by 4: `Ui_ShopItemList +0x1B0` (slot 0x6C),
   `Ui_SixRowCountList +0x160` (slot 0x58), `Ui_DrawList +0x230` (byte +0x8C of the append list).
   `Ui_SkillList +0x32` is a *value* (`self+0x32`) stored at +8, not an offset. All emitted as
   `unknown_*` confidence 0.0 with the real expression quoted; class sizes that only come from these
   offsets are lower bounds.
2. **`Ui_IconList` size is badly under-reported.** The batch size 468 (0x1D4) is just the highest
   strong field, but `Ui_IconList_AreAllIdle` walks 113 slots of 0x58 at +0x828 and
   `RefreshIcons` writes 28 bytes at +0x18A; the real object is at least ~0x2900 bytes. Recorded in
   the class evidence.
3. **`Ui_ShopItemList` merges two uses.** `PopulateRows` treats `self` as the row-list window
   (vtable, +0x4C page, +0x50..+0x53 column enables, +0x54 row provider); the 0x1E9xxx step handlers
   treat the same parameter as a small step record (`*shop` = next handler pair from 0x007295C0,
   `*(u16*)(shop+4)` = item id, `shop[5]` = quantity). Fields are named from the row-list use where
   possible and the conflict is stated in `maybe_selectedItemId`.
4. **`Ui_ObjectList` is not a generic Ui object list** — its callers are field-gimmick code
   (`Field_Gimmick_SetupListFromConfig`, field UI-gimmick ctor/dtor). The generated class name was
   kept (merger key) and the summary says what it really is.
5. **`Ui_AnimRefList`'s vtable is at +8, not +0.** The batch marks offset 0 as a vtable because of
   `*puVar3 = DAT_003e0498`, but `puVar3` is the embedded `Anim_AnimClip` returned by
   `Anim_AnimClip_Ctor(self+2 words)`. Offset 0 is the owner (`Ui_AnimRefList_Init` stores it there);
   the clip timing words reported at 0x30..0x44 are actually clip-relative and shifted by 8.
6. **`Ui_FourRowList`'s +0x30/+0x40** come from `Ui_FourRowList_InitRowDefaults`, which initialises a
   separate 0x44-byte defaults record, not necessarily the widget; kept at confidence 0.2.
7. `Ui_ChildWindowList` has only one recovered function, so all but the vtable/owner/embedded +0x10
   block are name-only hypotheses at 0.2–0.3.
8. Confirmed `Ui_PaneList+0xBC8` = `Ui_RowList` via `Ui_RowData_AtIndex` (vtable at +0, 0xCC-byte rows
   from +0x14). The anim controller at +0x11C is an embedded object with vt[+0x10]/vt[+0x14]; its class
   is not in `structs.json`, so it stays `maybe_animController` / `void*`.

## Not verified

* Every `maybe_*` field, and the class-level base assignments (all left `null` except
  `Ui_AnimRefList` = `Anim_AnimClip`, which its own ctor chains).
* The true split/identity of `Ui_ShopItemList` (window vs step record) and `Ui_ObjectList`
  (field-gimmick list vs UI list).
* The extent of `Ui_IconList` (113-slot array at +0x828) and the child-window/list semantics of
  `Ui_ChildWindowList`.
* Exact type of the `Ui_PaneList+0x11C` animation controller and of `Ui_IconList+0x160` (both are
  objects owning a vtable/resource table but no recovered class).
* Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-ups

* Fix `tools/typedb/struct_db.py` so `(**(code **)(*p + N))` is never emitted as offset `N*4`
  (affects many S batches) and so values of the form `p + N` are not emitted as field offsets.
* Re-cluster `Ui_ShopItemList` and `Ui_ObjectList` (two different objects each) before the S merge.
* Add `Ui_RowList`/anim-controller types to the field-type choices so `Ui_PaneList+0x11C/+0xBC8` and
  `Ui_IconList+0x160` can be typed precisely.
* Have a later pass extend `Ui_IconList` past 0x1D4 using the 0x828 icon-slot array evidence.
