## Decisions (some contradict the machine-generated batch)

1. **Kept every generated `class` and `type`** (the merger keys on `class`). Wrong identities are
   stated in `summary`/`evidence` instead of renaming; the worst case is `Ui_MonsterRow`, which is
   the casino poker card row.
2. **`base` cleared for `Ui_Row`, `Ui_ListRow`, `Ui_QuestList`**:
   * `Ui_Row_Ctor` allocates through `Ui_Object_CtorBase`; the batch's `Ui_AnimRef` base only came
     from the two embedded anim-ref lists at +0x4C/+0x9C, and `Ui_AnimRef`'s evidence size (800)
     is larger than the row (492).
   * `Ui_ListRow` passes itself to `Model_Attach_CreateWeaponAttachment`, but `Model_Attach`'s
     evidence size (1760) is larger than 1752, so it cannot be a base; the named fields are row
     fields, not attach fields.
   * `Ui_QuestList`'s `Ui_MessageWindow` base came from a stale name for 0x002AFA88; the geometry
     (0x35 × 0x8C = 0x1CFC = the whole object minus its count) proves it is a plain row array.
   All other bases were already null in the batch.
3. **struct_db artefacts emitted as `unknown_*` at 0.0**: `Ui_ItemHaveList +0xD0` (actually vtable
   slot 0x34 × 4), `Ui_Row +0x160` (slot 0x58), `Ui_MemberRow +0x120` (offset inside the portrait
   record) and `+0x250` (offset inside the pane). Sizes that follow only from them are lower bounds.
4. **`Ui_TextRow` size raised 0x34 → 0x120**: the ctor's
   `std_ConstructArray(self+0xC words, 0x003E0454, 0x50, 3)` builds three 0x50-byte animation-ref
   lists at byte +0x30, so the batch size truncated the object.
5. **`Ui_TextRow +4` is the vtable** (0x00759378, written by the ctor), not the `0xFF` byte the
   batch evidence quotes (`param_1[1] = 0xff` is the *byte* at +1 in the same ctor).
6. **`Ui_Row +0x04/+0x08` stay unknown**: `Ui_Row_SetDefaultIconSet` writes seven u16 icon ids at
   +0..+0xD on a *separate* 0x46-byte icon-set object (a vtable sits at row+0), so those writes
   cannot be row fields.
7. **`Ui_PartyMemberRow` contains two overlapping row subclasses** (BindPanesL vtable 0x771DA0 vs
   BindPanesR vtable 0x771DBC). I named the left-layout pane/enable pairs and documented the
   overlap instead of forcing both tables into one meaning.
8. Names above 0.5 rest on a string literal (`p1_txt_tr_hp`, `null_p1_tr_str`, `txt_have_l0`), a
   named callee (`Item_LookupRecord`, `Ui_Element_SetColor`,
   `Model_Attach_CreateWeaponAttachment`, `Casino_Poker_*`) or a direct store/compare. 6 fields are
   `unknown_` at 0.0, 40 are `maybe_*` < 0.5; nothing was invented to fill a slot.

## Open problems / suggested follow-ups

* `Ui_MonsterRow` should be renamed to a poker-card row class (`Ui_PokerCardsRow`) upstream in
  `tools/typedb/struct_db.py`/`make_batches.py`; the five functions are already named
  `Casino_Poker_*`/`Ui_PokerCards_*`, so only the cluster key is stale.
* `Ui_Row` is a union of at least three objects (row widget vtable 0x00768CC8, grid-text window
  vtable 0x00768E48, 7-icon set). A follow-up should split the cluster by vtable.
* `Ui_ItemHaveList`, `Ui_MemberRow`, `Ui_DungeonList`, `Ui_PanelRow` have too few real accesses to
  prove their identity; their class names still rest on one family of function names.
* `Ui_QuestList`'s 0x8C-byte row record is still unnamed (only the count is); it is built by
  0x002AFA88, which still carries a stale `Ui_MessageWindow_*` name.
* `Ui_PartyMemberRow`'s right-layout 8-entry `{u32, pane}` table at +0x34 likely belongs to a
  different subclass; splitting would make both layouts nameable.
