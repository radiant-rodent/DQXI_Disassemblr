## Corrections made (10 fields + 1 summary)

1. **`Ui_PluralIconCursor` +0x30 `layout` → `owner`** (real error). The batch evidence is
   `func_0053D4C4(*(u32*)(*(u32*)(self+0x30) + 0xac), "icon_single")` — +0x30 is *dereferenced at
   +0xAC* to reach the layout, so it holds the owner panel, not the layout. Same role as
   `Ui_PartyPanel_Cursor` +0x30 `owner`.
2. **`Ui_PluralIconCursor` +0x70/+0x74/+0x80 and +0x10C/+0x110/+0x11C** renamed from
   `maybe_singlePaneId`/`maybe_singleAnimId`/`maybe_singleIconId` (and plural) to
   `maybe_singleInitParam4/5/3` (and plural). The only evidence is `*(param_1 + off) = param_N`;
   the real panes are at +0x7C/+0x118 and the anim refs at +0x98/+0x134, so "paneId"/"animId" was a
   precise-but-wrong guess. These six words are +0x24/+0x28/+0x34 of the two embedded
   `Ui_CursorWidget`s, and `Ui_CursorWidget_InitPanes` (0x00291050) writes only +0x04/+0x08/+0x0C/+0x10,
   so their meaning is genuinely unproven. Confidence 0.30, consistent with `Ui_PartyPanel_Cursor`'s
   `maybe_initParam4/5/3` for the same physical fields.
3. **`Ui_GridCursor` +0x38 and +0x458**: confidence 0.55/0.50 → 0.45 so the `maybe_` prefix matches
   the task's <0.5 rule (names unchanged).
4. **`Ui_ListCursor` +0x410 `partyList` → `partyView`**: the *address* of the word is passed to the
   `Party_*` functions, so it is the base of an embedded party view, not a pointer to a list.
5. `Ui_PluralIconCursor` summary updated to mention the owner pointer.

## Open problems (for the merge task / follow-up batches)

1. **`Ui_AnimRef` size is inflated in `structs.json`**: 800 (0x320) from a single weak access at
   +0x31C. The real object is ~0x4C bytes — `Ui_CursorWidget` (base `Ui_AnimRef`) has its own fields
   from +0x4C, and `Ui_PluralIconCursor` embeds two `Ui_CursorWidget`s 0x9C apart. If the merge emits
   `Ui_AnimRef` fields inline at their declared size, every layout that embeds one will be wrong.
   **Recommend the `Ui_AnimRef` batch fix its size.**
2. **`Ui_CursorWidget` size conflict**: S_107 says 156 (0x9C), this batch's `Ui_PartyPanel_Cursor`
   (base `Ui_CursorWidget`) says 100 (0x64). All six of `Ui_PartyPanel_Cursor`'s fields
   (+0x24/+0x28/+0x30/+0x34/+0x4C/+0x60) are *inherited* `Ui_CursorWidget` fields, so the derived
   class has no fields of its own. `apply.py` will not embed the base (base size > class size) and
   will emit them flat, which compiles but duplicates the base's fields under different names.
3. **Same physical field, two names**: `Ui_PartyPanel_Cursor` +0x30 `owner` vs S_107's
   `Ui_CursorWidget` +0x30 `layout`. The code (`self->f_30->f_ac` is the layout) says `owner` is
   right and S_107's `layout` is wrong. Worth a consistency pass over the `Ui_CursorWidget` family.
4. **False-positive offsets kept as `unknown_*` at 0.0** (required to appear exactly once):
   `Ui_EquipRow` +0x281, `Ui_ItemIconRow` +0x100, `Ui_PartyIconRow` +0x160, `Ui_TwoColumnRow` +0xD0,
   `Ui_TextPairRow` +0xD0, `Ui_GridCursor` +0x100/+0x160, `Ui_TwoTabCursor` +0xF0,
   `Ui_PartyPanel_Cursor` +0x60. All are `(**(code**)(*self + 0xNN))()` vtable-slot parser artefacts.
   Because `apply.py` forces `size >= max(offset+width)`, these also inflate the class sizes
   (`Ui_EquipRow` 644, `Ui_ItemIconRow` 260, `Ui_PartyIconRow` 356, `Ui_TwoColumnRow`/`Ui_TextPairRow`
   212, `Ui_GridCursor` 14296, `Ui_TwoTabCursor` 13624). The sizes were left as the batch reported them
   and the inflation is stated in each class's `evidence`.
5. **`Ui_Cursor` size 8180** is the *owner window's* size, not the cursor's: the cluster carries the
   owner's per-frame fields and an embedded cursor at +0x1FF0. Stated in the summary.
