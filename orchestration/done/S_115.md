## Decisions / problems found

1. **`Ui_MapCursor` size raised 12 → 192.** `Ui_MapCursor_Ctor` calls
   `std_ConstructArray(cursor+3, 0x00619A8C, 0x24, 5)`, so the object is 0xC + 5*0x24 = 0xC0 bytes.
   The batch size came only from the highest directly indexed field.
2. **Vtable-slot artefacts.** Offsets that only appear as `(**(code **)(*param_1 + N))` in the
   sampled evidence are emitted as `unknown_*` 0.0 with the real expression quoted:
   `Ui_FaceIcon +0x90/+0xA0`, `Ui_CursorIcon +0x60`, `Ui_RankIcon +0x40/+0x50`,
   `Ui_NpcIcon +0x120`, `Ui_ItemIcon +0x60`. They should be dropped upstream if the merger
   allows it; they are not members.
3. **`Ui_QuestIcon` is not an object with fields.** The three `Create*` functions fill an 8-byte
   `{pane, handle, ..., updateCb}` factory record. Batch +4 is the `0x007B80C0` handle-table tag and
   +0x92A60 is `gameWork+0x24A98` (bag offset) mistaken for a self offset; both are unknown_ 0.0.
   The merger should not inflate the class with +0x92A60.
4. **`Ui_FaceIcon` is a composite.** `maybe_Ui_FaceIcon_Init` (0x002445F4) builds an object whose base
   is `return - 0x1190`; the +0x1194/+0x11B4 anim-ref vtables and +0x11D4 sprite handle live in the
   tail. The zeroed +0x10..+0x2C words are `unknown_*` 0.0 rather than invented counters.
5. **`Ui_CursorIcon` embeds a Ui_Cursor at +0.** `Hide`/`Show` use +0x140 (visible flag) and +0x144
   (owner), the dtors re-link the intrusive ring at +0xB4..+0xBC and release the layout ref at +0x64;
   +0x21CC is a second cursor and +0x2310 the manager. The batch's `size=8980` (0x2314) matches.
6. **`Ui_Sprite` merges three related records** (`Ui_Sprite` root, an embedded node/param block at
   +0xFC, and the `UiSpriteParams` block used by `Ui_Sprite_ApplyParams`). The parameter block is
   named from the callee it feeds (`func_0029E740` size setter → width/height, `Text_SetCharCode` →
   char code); ambiguous node copies stay `maybe_*` < 0.5.
7. **`Ui_HitIcon` slot array** is exactly 0x28 × 0xC from +0x58 to +0x238; +0x238 is the loop
   terminator, not a stored member (`maybe_slotsEnd`).
8. **Types** use the `type` spelling from `structs.json`, not the class spelling:
   `UiNodeList`, `UiListWidget`, `UiAnimRefList`, `UiSixRowCountList`, `UiActor*`, `Ui_Object`,
   `Ui_Sprite`.
9. **Bases** were kept exactly as generated. No class was renamed; `type` = class without underscores
   for all 15.

## Not verified

* Every `maybe_*` field (83 of 140 are below 0.5) and all `unknown_*` offsets; no emulator, export or
  rebuild was run — this is static naming only.
* The real identity of `Ui_ResourceIcon` (its functions are damaged: `unaff_r5/unaff_r9`) and of the
  `Ui_Sprite` param block owner.
* `Ui_MapIcon` +0x120/+0x144 dispatch table semantics and +0x29C condition object.
* `Ui_FaceIcon` +0x9C record type and +0x118 widget-stack entry layout.
* `Ui_NpcIcon` four-slot callback table element type (only object pointer + two callbacks inferred).
* The vtable-slot artefacts above still appear in the batch; upstream should filter them.

## Suggested follow-up

* `struct_db`: drop offsets that are only `*self + N` vtable dispatches, and clamp unioned
  multi-object classes (Ui_FaceIcon, Ui_Sprite, Ui_MapIcon) before generating batches.
* A focused batch on the `Ui_Cursor` base (0x001D7xxx) would let `Ui_CursorIcon`'s inherited half be
  typed properly; same for `Ui_Sprite`'s node/param records (0x0029Fxxx).
