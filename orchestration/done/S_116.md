Method: read the annotated readable C of every ctor / init / update / dtor for the class (from
`decomp/readable/functions|recovered/`, found by address with a `glob` on one directory - no tree
walk), cross-checked offsets against `structs.json` (`Ui_DiveWindow` at 0x2988, `Ui_TextElement`,
`Ui_WorldMapMarkerList`), and separated real members from decompiler artifacts.

Key decisions and traps recorded:

* **vtable-slot artifacts**: several "fields" are just `slot*4`. Renamed to `unknown_*` 0.0 with the
  arithmetic in `evidence`: `Ui_ItemModel +0x100` (slot 0x40), `Ui_Effect +0x60` (slot 0x18),
  `Ui_SpriteActor +0x30` (slot 0x0C) and `+0x330` (slot 0xCC),
  `Ui_BattleTargetMarker_Manager +0xF0` (slot 0x3C) and `+0x430` (slot 0x10C).
* **`Ui_DiveManager` merges two objects**: `Ui_DiveManager_Recreate` allocates 0x5C4 for the manager,
  but `Ui_DiveManager_BindContext` is called with the 0x2988-byte `Ui_DiveWindow` (it writes +0x2984).
  The +0x9BC/+0xBEC/+0x2984 fields are therefore named as window fields, and the class summary says so.
  Likewise +0x4B8/+0x728 are the window's `s_menu_dive_stock1/stock2` lists (from `Ui_DiveWindow`'s
  own evidence) - the manager only stores a byte flag at the same numeric offset.
* **`Ui_Scene` merges a Sound_Voice ctor**: 0x005434E8/0x00543528 are a voice subobject ctor/delete
  (they only touch +0/+4/+8 and the +0xC subobject); +4/+8 are `unknown_*` 0.0 and the class name
  stays a placeholder.
* **`Ui_MenuActor` size 568 is too small**: it writes per-slot effect handles at `self + slot*4 + 0x278`
  for 0x121 slots. The batch size was kept so the dispatcher's offsets stay valid; the summary states
  the real extent.
* **widths/types**: byte flags emitted as `u8` where the code does `*(char*)`, but the batch `size`
  was kept unchanged (the merger uses it for padding). `type` spelling follows `structs.json`
  (`Ui_List`, `Ui_TextElement*`, `Ui_Object`, ...) and builtins.
* 92 fields are `maybe_*` (<0.5) and 25 are `unknown_*` (0.0); nothing invented to fill a slot.

  offsets, every name lowerCamelCase, `maybe_` exactly when confidence < 0.5 or `unknown_` at 0.0,

## Open problems / not verified

* Real identity/purpose of `Ui_DiveScene` (likely a `Field_SceneNode`, not a dive object) and whether
  the merger should split it from the dive classes.
* All `maybe_*`/`unknown_*` fields, in particular the 0x4A8..0x5C0 intrusive-list bookkeeping of
  `Ui_DiveManager` (list element types unknown; only the self-referential rings and the release-slot
  calls are evidenced), the `Ui_Scene` +0x8E0/+0x930 sub-object types, and `Ui_Actor +0x9F8`
  (shared static 0x00782534, semantics unknown).
* The 0x0B8/0x0BC "double buffer" of `Ui_Scene` is structural only (read->clear->store), the value
  being passed is not identifiable.
* `Ui_ScreenEffect` +0xC is a u32 resource handle per the loader but is read as a byte flag by
  `maybe_Ui_ScreenEffect_ApplyFrameColor` - two variants or a damaged decompilation; not resolved.

## Suggested follow-up

1. Split `Ui_DiveManager` (0x5C4) from `Ui_DiveWindow` (0x2988) in the struct DB, or at least exclude
   the window-only offsets from the manager cluster (and vice versa).
2. Re-run the `Ui_SpriteActor` cluster against a full 0x298-byte layout: the batch size 820 exceeds the
   0x298 allocation of `maybe_Ui_SpriteActor_CreateEntry`, so the trailing offsets probably belong to
   a derived node class.
3. A small dedicated pass on the nine `Ui_DiveManager` intrusive lists (cross-reference the embedder
   list types at 0x007830F0 / 0x00783230 / 0x0078326C / 0x00783334 / 0x00782E34) would turn the
   remaining `maybe_list*` bookkeeping into real container types.
