# S_117 — UI struct/field naming (15 classes, 147 fields)

## What I did

Named all 15 classes and every field offset in `orchestration/types/batches/S_117.json`.
Output: `orchestration/types/out/S_117.json` (38,292 bytes, UTF-8).

Method: read the readable C of each constructor/update/dtor named in the batch,
then resolved the literal pane-name strings that the battle window manager passes to
`Ui_Widget_FindPaneAndNotify`. The pane names are embedded in `.text`
immediately after the code (`build/code.bin`, file offset = vaddr - 0x00100000), so
`0x0027C5D0/0x0027CE04/0x0027CE74/0x0027CF3C/0x0027CF48/0x0027D0E8/0x0027D0F8/0x0027D258/0x0027EB34`
decode to `win_dougu`, `win_party`, `win_skill`, `win_tokugi`, `win_text`,
`win_command`, `win_mode`, `win_training`, `win_skip` and give exact window names.

## Class identities found (some batch names are wrong; `class`/`type` kept as generated)

- `Ui_WindowManager` — real global window manager singleton, vtable `0x0075CE50` (confirmed:
  dtor `0x0027A7F0` loads that literal and stores it at `[self]`). Four 12-byte intrusive
  `Ui_WidgetList`-style list triples at `+0x704/+0x710/+0x720/+0x72C`; two global list links at
  `+0x8/+0xC` and `+0x28/+0x2C`.
- `Ui_BattleWindowManager` — the battle-window view of the same object
  (`Ui_InitWindowManager` calls `CreateWindows` on the manager). Every child slot was mapped by
  the pane-name literals; see the file's field evidence.
- `Ui_ScreenManager` — duplicate of the project's existing `FieldParty_Ui` (`FieldParty_Ui_Ctor`
  `0x003C2120`); `+0x2218` is an embedded `Ui_LayoutParams`.
- `Ui_ScreenController` — owns fifteen child UI objects at `+0xC..+0x44`, each named from its
  constructor; `+0x6C` is the selected child index.
- `Ui_AnimController` — 3-step animation advance loop (0x18-byte entries, dispatch table `+0x4C`).
- `Ui_ListRowData` — really `Ui_ScreenAnchor` (ctor `0x004ACCD0`): anchor x/y `+0x4/+0x8`,
  host `+0xC`, default scale `-1.0f` `+0x1C`.
- `Ui_ListData` — a mix of an entry-vector block (offset 0 = vector begin) and the outer list
  window (list-data pointer `+0x3570`, row block `+0x184`, entry limit `+0x3768`).
- `Ui_RowData` — the 0xCC-stride row accessor of a `UiRowList`.
- `Ui_SlotTable` — talk speaker-slot table: selected id `+0`, 10-byte id arrays `+0xD/+0x17`,
  ten u16 speaker slots `+0x23`, 2D/3D flags `+0x37/+0x38`, timer `+0x3C`, active value `+0x40`,
  embedded SmithMenu pane `+0x11C`.
- `Ui_MessagePartTable` — two intrusive lists `+0x120/+0x13C`, part array pointer `+0x158`,
  kind `+0x11C`.
- `Ui_PokerTable` — poker widget: card0..card4 / null_txt / select panes, icon cursor/change,
  poker_txt, embedded `Ui_PokerWinWindow` at `+0x128`.
- `Ui_CardTable` — really `Ui_SubTable` (vtable `0x0075A694`), 3 × 0x10-byte entries behind `+8`.
- `Ui_Table` — misidentified inner sub-object; its dtor does `r0 += 0xD6C` to reach the
  seven-line select window owner.
- `Ui_TextTable` — batch aggregate over the global text block `0x0063D300`; its only batch
  field is spurious.

## struct_db traps handled

1. **x4 word-index scaling** in `Ui_SlotTable`: batch offsets `0x84..0x100` are 4× the real
   bytes `+0x21..+0x40` (e.g. `0xDC` is really byte `+0x37`). Both the real-offset entry and the
   scaled duplicate were emitted (batch contract) and each evidence line names the true byte.
   Same pattern: `Ui_RowData +0x110` = vtable slot `+0x44`; `Ui_TextTable +0xD4` = record byte
   `+0x35`.
2. **Static-table reads** (`Ui_MessagePartTable +4/+8/+0xC`) and **vtable-slot expressions**
   (`Ui_ListData +0x150`) were emitted as `unknown_*` at 0.0 with the offending expression quoted.
3. `Ui_BattleWindowManager +0x70` comes from `puVar4[0x1c] = 0` on the newly allocated
   `win_command` child, not from `self`.
