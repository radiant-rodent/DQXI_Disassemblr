## Important findings / decisions

1. **`struct_db` ×4 scaling bug in `Ui_MessageBuffer`.** `Ui_MessageBuffer_Init` takes `u8* self`,
   so the real fields are the two 0x200-byte buffers at +0x2/+0x202 and the state block at
   +0x404..+0x420. The batch offsets (0x808, 0x1010, …) are exactly 4× those byte offsets. I kept
   every batch offset (the output contract) and each `evidence` line states the true byte offset, so
   the merge is internally coherent and the bug is documented. **Follow-up:** fix the parameter
   typing in `struct_db.py` / regenerate the batch; the class's real size is ~0x424, not 4228.
2. **Ui_NameEntry: size 416 → 492 (0x1EC), base Ui_AnimRef → Ui_Object.** The dtor
   (`std_destroy_range` stride 0x50 count 2 at +0x14C, count 3 at +0x4C) proves the object extends to
   0x1EC; it then calls `Ui_Object_DtorBase`. Upstream vtable-slot artefacts +0xE0/+0x120 are not
   members.
3. **Ui_SceneEntry: size 2836 → 5568 (0x15C0).** Disassembly: entry = pool + i*0x2C; transform at
   entry+0x480, flags at entry+0x484/+0x485. Each pool = 0x480 + 36*0x2C = 0xAB0; pool B at +0xB10
   ends exactly at 0x15C0. The 0x480-prefix detail is stated in the two field evidence lines.
4. **Ui_NameEntry +0xD0 left `unknown_D0` (0.0).** The ctor at 0x0021DD64 references a
   `Container_MultiList` at a +0x34-relative address, but a 0x108-byte `Container_MultiList` cannot
   start at +0xD0 without overlapping the 0x50-byte label pages. I refused to guess.
5. **vtable-slot / indirection artefacts** emitted as `unknown_*` 0.0 with the expression quoted:
   Ui_NameEntry +0xE0 (slot 0x38), +0x120 (slot 0x48); Ui_EquipmentWindowNode +0x210 (slot 0x84);
   Ui_Entry +0x620 (`*(float*)((*style)+0x188)`, a double indirection); Ui_GlyphNode +4/+8
   (`pfVar6[1]/[2]` index `maybe_g_defaultBasisVector2`, a global).
6. **Ui_NamedEntry +0x14..+0x53 is one `char name[0x40]`.** The 15 per-word batch offsets are the
   ctor's memcpy stores; they are emitted as `unknown_18..unknown_50` at 0.0 with that fact in the
   evidence so the generated header shows a single readable name buffer. The ctor's +4/+8 list words
   are folded into the +0 description to keep the emitted offset set exactly equal to the batch's.
7. Sizes were corrected only where construction/destruction evidence is stronger than
   "highest field + width" (Ui_NameEntry, Ui_SceneEntry). Everything else keeps the batch size.

## Open problems

* `Ui_Entry` is a mixed group: `Ui_Entry_GetDisplayText` is a real entry-table function, but
  `maybe_Ui_Entry_FillStyleParam` (style descriptor) and the two `Field_Npc*_GetTalkAttrByte`
  functions do not operate on this object at all. The class should probably be split/renamed by a
  later pass.
* `Ui_GlyphNode` and `Ui_AnimNode` only have a create/release pair recovered; their real layouts are
  unknown (all fields at 0.0).
* `Ui_ProgressEntry`: the function walks eight 0x30-byte source records at +0x130 but writes
  0x24-byte output records from +0x2AC; the record stride and the 692-byte size are not fully
  reconciled.
* `Ui_PanelNode` +0x20/+0x24 and +0x584/+0x590 semantics (list vs plain words) are only inferred
  from the unlink pattern.
* The `Ui_MessageBuffer` ×4 batch scaling and the `Ui_NamedEntry` list offsets need a
  `struct_db.py`/`make_batches.py` fix, not a worker fix.
