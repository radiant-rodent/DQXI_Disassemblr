# S_119 — naming batch: 14 Ui classes / 362 fields

## What I did

Named every class and every batch offset of `orchestration/types/batches/S_119.json`
(subsystem Ui, 14 classes, 362 fields) and wrote `orchestration/types/out/S_119.json`
(UTF-8, 102,006 bytes, strict decode + `json.loads` OK).

Method: read the batch, then for each class read its constructor/update in
`decomp/readable/...` and `tools/fn.py` (0.5 s per dossier), cross-checked widths and
offset arithmetic against the `asm/text/*.s` listing where the decompiler was damaged,
and reused existing project evidence (`orchestration/types/out/S_104.json` for the
DataPanel offsets, `S_078.json` for the inherited `Ui_Object` fields).

## Statistics

* 362 fields = exactly the batch's 362 offsets, one field per offset, none duplicated.
* 78 fields at confidence >= 0.5; 177 `maybe_*` (< 0.5); 107 `unknown_*` (0.0, real gaps with
  no recoverable meaning). Nothing was invented to fill a slot.
* Every field name is lowerCamelCase and a valid C identifier; every type resolves through
  `structs.json`/builtins (`tools/typedb/apply.normalise_type`).

## Decisions / problems found

1. **struct_db dword-scaling in `Ui_LayoutParams` (all 121 offsets).** In this class the raw
   Ghidra C typed `param_1` as a dword pointer, so every recorded offset is exactly **4x the real
   byte offset** (e.g. batch 48 = real +0xC, batch 1424 = real +0x164, batch 4532 size = real
   ~0x470). Verified against asm: `Ui_LayoutParams_Init` 0x002E8538 does
   `strb #0xFF,[r0]`, `ConstructArray(r0+0x188, ..., 8, 4)`, `ConstructArray(r0+0x1C4, ..., 0x68, 2)`,
   and `LoadFromId` 0x002E7FBC does `memcpy(self+0x24, ..., 0x13D)`; the batch evidence itself says
   `param_1 + 0x164` for offset 1424. Because the task contract says every batch offset must appear
   exactly once, I emitted the batch offsets and wrote the **true byte offset into every evidence
   line** (same convention as S_117/S_118). The emitted `UiLayoutParams` therefore has 4x padding
   and its `sizeof` is 0x11B4 instead of the real ~0x470 — **a follow-up must fix struct_db's
   `element_width` for this batch and regenerate**. No data was guessed because of this.
2. **Dword-scaled byte fields** also occur in `Ui_WindowState` (+0x4/+0x8/+0xC are really bytes
   +1/+2/+3), `Ui_State` (+0x150 is really byte +0x54) and `Ui_RecipeBookState` (+0x224/0x225/0x226
   come from `self+0x89` on a dword pointer => byte 0x224). Evidence states the real byte each time.
3. **Vtable-slot parser artefacts** were emitted as `unknown_*` 0.0 with the offending expression
   quoted: `Ui_DiveForm` +0x120 (slot 0x48) and +0x150 (slot 0x54).
4. **Merge consistency:** reused the exact field names S_104 chose for the shared DataPanel offsets
   and S_078 chose for the inherited `Ui_Object` fields. Kept every generated `class`/`type`;
   the wrong/stale names (`Ui_RecipeBookState`, `Ui_ListState`, `Ui_TextLinePool`) are explained in
   `summary`/`evidence` instead of renamed, because the merger keys on `class`.
5. **`Ui_TextBuffer`'s batch "ctor" 0x005487EC is unrelated** — it initialises a 0x10-byte object
   (stores +0/+4/+8/+0xC/+0xD/+0xE only), so it was not used as layout evidence; the layout comes
   from Append/Write/Release.

## Open problems / not verified

* `Ui_LayoutParams` is emitted 4x-scaled (see decision 1). A follow-up should fix struct_db and
  regenerate; the true byte offsets are already in the evidence strings.
* Almost all `Ui_LayoutParams` tail scalars and the two mid-size blocks are copied blindly from the
  data row — their meaning is not recovered (only the class-level purpose is proven by the
  Text_CalcRowGeometry / Text_MeasureRowByType / Battle_Message_BuildRowForMonsterEx callers).
* `Ui_PanelState` merges a row/step sequencer with an unrelated layout-properties clearer; fields
  +0xC..+0x60 may belong to the latter object. `Ui_ListState` merges DataPanel offsets with a
  standalone intrusive-list remover. Both are documented in the summaries.
* `Ui_DiveForm` list rings are typed `u32` (embedded sentinels/nodes); the list helper
  `func_001235A4` is proven to be an intrusive link, but the ring element type is not named.
* `Ui_MessageDualBuffer`/`Ui_MessageExtendedBuffer` are blocks inside a message window, not
  standalone 48-byte objects (the ctor keeps constructing past +0x858).
* `Ui_TextLinePool` and the damaged 0x00304C14 body are not verifiable at all.
* Nothing was compiled, exported or emulator-tested — static naming only.
