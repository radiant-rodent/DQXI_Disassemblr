# S_121 — name the classes and fields of 6 Ui classes

## What I did

Named all 6 classes and **all 395 batch offsets** from `orchestration/types/batches/S_121.json`
(subsystem Ui). Nothing was guessed from a single line of evidence where a function body was
available; vague names are `maybe_*` below 0.5 confidence per the rules, and fields whose only
"evidence" was a vtable-slot constant became `unknown_*` at 0.0.

Method per class: read the constructor / initialiser first (`Ui_Part_Ctor`, `Ui_PartyStatus_Reset`,
`Ui_Balloon_Ctor`/`ResetState`, `Ui_SceneFlow` slot bodies), then the update/layout methods
(`Ui_Part_SetupFromAnimRecord`, `Ui_Part_UpdateAnimState`, `Ui_ModelView_UpdateModelRotation`,
`Ui_ModelView_BuildPathTable`, `Ui_Balloon_SpawnForMember`/`UpdateForMember`,
`Ui_PartyStatus_ApplyValue`), then cross-checked offsets and widths against
`orchestration/types/structs.json` and the already-finished sibling batches (S_014 Camera_Field,
S_043 Gfx_Sprite, S_064/S_087 party classes). `tools/fn.py` was used for dossiers instead of
walking `asm/`/`decomp/`.

## Validation

Naming batch, so the full `tests/run_all.py` / `tools/verify_project.py` runs were **skipped** per
WORKER_RULES rule 5 (no code or binary changed). A JSON structural check was run instead:

```
OK classes=6 fields=[88, 67, 65, 61, 59, 55] bytes=86868
ALL CHECKS PASS
bytes 86868 BOM False
```

The check verifies:
* strict UTF-8 decode of the written bytes (no BOM, no cp1252 byte),
* `json.loads` parses,
* class list/order == batch class list/order,
* per class: emitted offset set == batch offset set (every offset exactly once, no extras),
* no duplicate field names inside a class,
* every name matches `[a-z][A-Za-z0-9_]*`,
* `maybe_` prefix present for every confidence < 0.5 name (except the prescribed `unknown_*` at 0.0),
* every field has non-empty evidence,
* every type is a builtin (`u8 u16 u32 s8 s16 s32 f32 void*`), a type/class name from
  `structs.json`, or `void (*)(void)`.

Known intentional width deviations from the batch's `size` (left as the true access width so the
merge does not create overlapping fields): `Ui_SceneFlow` +0x10, +0x1C, +0x44 are stored with
`undefined1` in the decompiled code (batch recorded size 4 because other accesses use word
indexing); they are typed `u8`.

## Decisions made (orchestrator not available)

1. **`Ui_ModelView` is a camera rig, not a text widget.** `Ui_ModelView_ComposeCharacterText` and
   `Ui_ModelView_SetCharacterText` are prior-batch names; the bodies build **3D point paths** via
   `Path_BuildFromPoints` from 0x14-byte records, and `UpdateModelRotation` calls
   `Camera_SetTransitionTarget` with an orbiting eye offset. I kept the existing function/class
   names (rule: do not rename what signatures already use) but named the fields honestly as
   paths/camera pose, and the class summary states the camera-rig reading.
2. **`Ui_PartyStatus` offsets >= +0x4B30** (`0x4B30`, `0x5418`, `0x5762`, `0x59AC`, `0x89A8`,
   `0xB0FC`, …) exactly match `GameWork+0x24A98` save-work fields from `SaveData_ResetSaveWork`
   (item-ownership mask 0x168 bytes, field-trigger mask 0x64 bytes, quest/pastword tables). They
   are almost certainly a mistyped-self artefact of the struct DB. I emitted them with `maybe_`
   names at confidence 0.2 and wrote that suspicion into each evidence string rather than inventing
   per-object purposes.
3. Fields whose only evidence was `*param_1 + 0xNN` vtable dispatch (e.g. `Ui_PartyStatus`
   0x40/0x70/0xF0/…, `Ui_Screen` 0xF0/0x120, `Ui_Part` 0x310) are `unknown_*` at 0.0 with the
   vtable-slot number quoted in evidence. This is a struct_db extraction artefact.
4. `Ui_Part` merges several part subclasses: +0x4C is an anim index (`*0x1C` stride) in one
   variant and a `null_shadow_l` pane handle in `Ui_Part_SetupFromAnimRecord`; +0x1C/+0x24 are
   floats in one variant and record pointers in another. Named `maybe_animIndexOrPane` at 0.35 and
   flagged the ambiguity instead of picking one.
5. `Ui_Balloon` +0 conflicts: batch vtable 0x0075B4B4 says vtable, but `Ui_Balloon_Ctor`
   (0x005F8DCC) stores the style byte at +0. Emitted `vtable` (0.8) and documented the conflict in
   the class evidence; the ids at +0x122C are a popup-entry/balloon queue manager whose +0xBC is
   pushed through `Battle_MessageQueue_PushEntry`.

## Open problems / not verified

* Every `maybe_*` and `unknown_*` field — read the confidence column as the real guarantee.
  336 of 395 fields are below 0.5; only vtable/known-layout fields are high confidence.
* `Ui_ModelView`: the owner object at +0x2C and what `owner+0x74` really is (record pointer vs
  position word) are unresolved — the readable C and the Thumb call at 0x002AE8F4 disagree.
* `Ui_Part`: the exact split between the part subclasses (which offsets belong to which variant)
  is not recovered; the four pane-handle slots +0x50/+0x54/+0x58 are solid, the +0x4C index is not.
* `Ui_PartyStatus`: the boundary where the mistyped-self save-work fields begin is inferred, not
  proven; the ten-dword array at +0x2964 and the 12-byte block at +0x31CE are named only from
  their cleared/0xFF initialisation pattern.
* `Ui_Screen`: what the four embedded vtable words (+0x224, +0x9A8, +0xD80, +0x1684) construct is
  unknown (only `Ui_Object_DtorBase` at +0x224 is proven); the vtable-word pseudo-fields are 0.0.
* `Ui_Balloon`: whether +0x122C is a `Ui_PopupEntry` or a manager that *owns* the queue at +0xBC;
  the two animator blocks' internal layout was not expanded (batch only exposes their bases).
* `Ui_SceneFlow`: pointer field types are inferred from the callee family (`FUN_...` that take
  `self+offset`), not from a recovered declaration; some callee names in that family may themselves
  be provisional.
* Nothing was compiled, exported or emulator-tested. This batch is static naming only.
