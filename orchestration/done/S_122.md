# S_122 — Ui struct/field naming (11 classes, 413 fields)

## What I did

Wrote `orchestration/types/out/S_122.json` with one object per class and one entry for
**every** offset in `orchestration/types/batches/S_122.json` (413 offsets across 11 classes,
exactly once each, no duplicates). Class names/types were kept exactly as generated.

Method: for each class I read the readable C of the constructor and of the update/state methods
via `tools/fn.py` (dossier + body) rather than walking the trees, then cross-checked offsets
against the already-merged views of the same objects in earlier batches
(`S_079` Ui_Window, `S_106` Ui_Widget, `S_078` Ui_Object, `S_110` Ui_List) because several of
these classes reuse the Ui_Window offset layout (especially Ui_RecipeBook, Ui_LoadScreen).

## Main ground truth recovered

* **Ui_WorldMap** (all 49 fields, class confidence 0.70) is the best case: `+0x20` is the
  `Ui_WorldMapMarkerList` allocated by `Ui_WorldMap_CreateMarkerArray` (0x6F4 bytes), `+0x48..+0x58`
  are the five `Ui_MapShipIcon*` updated in a `i<5` loop, `+0x60` is the single ship icon, and
  `+0x44/+0x5c/+0x68/+0x70/+0x7c` are the packed pack handles for `ui/map/<name>.pack`,
  `ui_map_pack.bxon`, `ui_map_param.bxon` and `ui_map_ship_location.bxon` (string literals in
  `Ui_WorldMap_Setup`/`Load`, handle swap + `Pack_ReleaseHandleEntry`). `+0x8c/+0x8d/+0x8e/+0x91`
  are the flag bytes read from `params[4]`/`ids[1]` (extended record, mode 2, has labels, ship map).
* **Ui_LoadScreen** is a Ui_Window subclass: `+0x11c` is the embedded `Ui_Sequence` state object
  (requests states 0x2B/0x2C/0x3C), `+0x718` the embedded load window, `+0x820` the `Ui_Menu`
  state machine, `+0x82c/+0x834` the background and `bg_jumon` pane ids.
* **Ui_RecipeBook**'s vtable 0x0075B3CC is the `Ui_Sequence` table and its high offsets are shared
  with Ui_Window (`+0x118` detail window pointer, `+0x11c` state sequence, `+0x11e4` save-slot
  record whose `+0xa8` goes to `SaveSlot_IsUsed`, `+0x10a8` inline byte vector, `+0x224` state),
  while `+0x4/+0x8/+0xc` are the variant vector documented by `Ui_RecipeBook_PushVariantEntry`.
  The class summary states that the batch mixes the sequence object and the window it drives.
* **Ui_AnimClip** matches its doc exactly: `+0xc` = start frame (`clip[0xc] = frame` in
  `Ui_AnimClip_PlayFrom`), `+0x48` the 0x48-byte reference block, `+0x80` the keyframe name buffer;
  `+0x1c..+0x40` are copied verbatim from the clip descriptor and are therefore only
  `maybe_descriptorNN` (role not recovered).
* **Ui_ScreenLayer** is fully mapped from `Ui_ScreenLayer_SetCameraMatrix`: 10-float draw matrix
  at `+0xb0..+0xd4` (eye/at/up), orthonormal basis at `+0x100..+0x128` (right/up/forward + w),
  and the 16-float projection matrix at `+0x160..+0x19c` (uploaded to device+screen*0x7C+0x754/+0x784).
* **Ui_Pane**: `+0x28` texture (size written to texture+0x138/+0x13c), `+0xa4` `Ui_LayoutText*`,
  `+0xb8` `Ui_GlyphQuadArray`, `+0xcd` quad count, `+0xd0` child-pane table, `+0x1680` child object.
* **Ui_MonsterBook**: `+0x4c/+0x50` enemy_book_2d_adjust entry+handle, `+0x54/+0x58`
  enemy_book_drop_item entry+handle, `+0x60` `mask_empty` pane id, `+0xb0` entry array,
  `+0x134` embedded entry list, `+0x118c/+0x11dc` model-shown flag and model angle.

## Traps / decisions

1. **The batch classes are function-name aggregates, not always one real object.**
   `Ui_SlotMachine` (292 bytes, vtable 0x00777DA8) is *one reel sub-part* built by
   `Ui_SlotMachine_CtorSubParts`; the actual slot machine is the larger object built by
   `Ui_SlotMachine_Ctor` (vtable 0x00766D74) which embeds six of these with variant 0..5.
   `Ui_RecipeBook` and `Ui_Anim` likewise mix methods typed against different objects.
   The summaries say so; where an offset could not be attributed to this object I used
   `unknown_*` at confidence 0.0 (e.g. the tangle of zero-initialised reel-A/reel-B internals).
2. **Vtable-slot parser artefacts**: `(**(code **)(*self + 0xNN))(...)` was recorded as a field
   at 0xNN. Those offsets are emitted as `vtableSlotNN` with type `void (*)(void)` and
   confidence 0.0 and the expression quoted in evidence, instead of inventing a data member.
3. **Confidence naming**: `maybe_` exactly when confidence < 0.5, `unknown_` at 0.0, otherwise
   plain lowerCamelCase nouns. No precise purpose was invented to fill a slot — e.g. the
   `maybe_descriptor1c..40` block in Ui_AnimClip and the reel-part zero words are deliberately vague.
4. **Reused names from earlier batches** where the same offsets belong to the same object family
   (Ui_Window/Ui_Widget/Ui_Object/Ui_List views), so the merged structs stay consistent.
5. `tools/typedb/apply.py --validate` was deliberately **not** run: it rewrites the shared
   `orchestration/types/merged/report.json`, which this task does not own.
6. `python tests/run_all.py` / `python tools/verify_project.py` were skipped on purpose:
   WORKER_RULES rule 5 exempts naming/typing batches (S_*).

## Test / validation results

* JSON syntax: `json.load` OK.
* Strict UTF-8: decoded the file with `bytes.decode("utf-8")` — OK (95,684 bytes, 11 classes,
  413 fields).
* Offset contract: for every class, the emitted offset set equals the batch offset set
  (asserted by the generator; 49/49, 49/49, 40/40, 40/40, 39/39, 39/39, 38/38, 33/33, 29/29,
  29/29, 28/28).
* Names: all match `^[a-z][A-Za-z0-9_]*$`, no duplicate names inside a class,
  `maybe_` prefix exactly when confidence < 0.5 (plus the `unknown_*`/`vtableSlot*` exceptions).
* Types: every type is a builtin (`u8 u16 u32 s8 s16 s32 f32 void* char*`), `void (*)(void)`,
  or a class that exists in `orchestration/types/structs.json` (checked programmatically).
* Generator + checker: `out/scratch/S_122/build.py` (it asserts the offset contract before writing).
* Full rebuild/verify suite: not run (see decision 6).

## Open problems / not verified

* Every `maybe_*` and `unknown_*` field. In particular:
  * Ui_SlotMachine `+0x50..+0xb4`: zero-initialised internals of two embedded `0x0077C164`
    sub-objects; their purpose is not recoverable from the ctor alone (unknown, 0.0).
  * Ui_RecipeBook `+0x28..+0x60` (15-word descriptor copy) and `+0xb4c` — only single reads,
    no semantics.
  * Ui_Anim `+0x1c..+0x28` (frame range) and `+0x160`, `+0x224/+0x226` (animation-id halves):
    the union of float/byte usage in this aggregate prevents a firm type.
  * Ui_AnimClip `+0x1c..+0x40`: copied descriptor words; per-field roles unknown.
  * Ui_LoadScreen `+0x48b4..+0x48b8`: weak single reads, probably a mistyped self.
  * Ui_WorldMap `+0x11c..+0x148`: zeroed by the destructor inside/around the layout-reference
    block; only +0x124 has evidence (`Ui_LayoutRef_Release`).
* Field widths follow the batch (`size` from the batch) except where a byte/word pair was
  clearly mis-merged; overlapping regions (e.g. the label array in Ui_WorldMap +0x24 and the
  5-pointer label array at +0x30) are described as arrays in the evidence.
* Nothing was compiled, exported or emulator-tested — this is static naming only.

## Suggested follow-up

* Merge S_122 and re-check `Ui_SlotMachine`: the batch should be regenerated so the class is
  either the reel part (0x124, vtable 0x00777DA8) or the full slot machine (0x16F8, vtable
  0x00766D74) — currently its ctor and its fields come from different objects.
* Same for `Ui_RecipeBook`: split the `Ui_Sequence` base (vtable 0x0075B3CC) from the
  `Ui_Window` screen that owns it; most high offsets are Ui_Window members.
* A `Ui_Anim` follow-up should separate the Ui_AnimSpriteNode fields (0x8..0x34), the movie
  controller fields (0xc..0x28), and the animation-instance fields (0x4c..0x5dc) for the same reason.
