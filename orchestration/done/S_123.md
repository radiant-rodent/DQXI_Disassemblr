# S_123 - name the classes and fields of 15 Ui classes

## What I did

Named all 15 classes and **all 360 batch offsets** from
`orchestration/types/batches/S_123.json` (subsystem Ui). Every class keeps the generated
`class` name and its `size`; `type` is the class name without underscores. Nothing was renamed
at class level.

Method per class: read the recovered initialiser/constructor first, then the update/layout
methods, then cross-checked each batch offset against the readable-C lines quoted in the batch
and against `orchestration/types/structs.json`. Function doc headers in `decomp/readable/...`
(already written by earlier naming/refine batches) were used heavily instead of re-reading
assembly; `tools/fn.py` was not needed because every class's functions were already in the
batch. No whole-tree walk/grep was performed.

The generator/validator is `out/scratch/S_123/gen.py` (scratch only). It asserts the emitted
offset set equals the batch offset set per class, no duplicate offsets/names, and then applies
the rule "confidence < 0.5 -> `maybe_` prefix".

## Validation

Naming batch: `tests/run_all.py` and `tools/verify_project.py` were **skipped per WORKER_RULES
rule 5** (no code or binary changed; a full run costs 3-6 minutes and would not exercise this
JSON). The required JSON syntax/semantic check of my own output was run instead:

```
wrote orchestration/types/out/S_123.json classes 15 fields 360
VALID UTF-8 JSON; classes 15 fields 360 offsets all covered
```

The check verifies:
* strict UTF-8 decode of the written bytes (no BOM, no cp1252 byte) and `json.loads` parses;
* class list/order equals the batch class list/order, `type == class without '_'`, `size` equals
  the batch size;
* per class the emitted offset set equals the batch offset set (every offset exactly once, no
  extras, no duplicates);
* no duplicate field names inside a class;
* every `maybe_`-less name has confidence >= 0.5; every name below 0.5 starts with `maybe_`,
  except the 18 prescribed `unknown_*` entries at 0.0;
* every field has non-empty evidence;
* every type is a builtin (`u8 u16 u32 s8 s16 s32 f32 void*`), a class/type name that exists in
  `structs.json` (`Ui_AnimRef`, `Ui_AnimRefList`, `Ui_AnimWindow`, `Ui_List`, `Ui_ListCursor`,
  `Ui_MessageWindow`, `Ui_Panel`, `Ui_SpriteList*`, `Anim_Tween`) or `void (*)(void)`.

I did **not** run `tools/typedb/apply.py --validate`, because that rewrites the shared
`orchestration/types/merged/report.json` and this task owns only `S_123.json`.

## Decisions / traps handled

* **Mistyped `self` fields are `unknown_*` at 0.0**, not invented names: `Ui_SlotGrid +0x100`
  (only a `(*(*self+0x40))(self,0)` call site), `Ui_IconAtlas +0x90` (only vtable+0x24),
  `Ui_TextBuilder +0x240` (evidence reads a different base +0x90), `Ui_TitleScreen
  +0x58/+0x5C/+0x60` (these are resource-row fields `puVar4[0x16..0x18]`, not members of the
  title screen), `Ui_System +0x34C/+0x354` (allocator/self-reference only), `Ui_LoadingScreen
  +0x30/+0x50/+0x70/+0xA0` (all dereference the UI core, not the loader) and `+0x1811` (read
  from `(*0x007BE308)+0x1811`, the save work), `Ui_ItemScreen +0x134/+0x135` (write-only flags).
* **`Ui_ItemScreen` has no vtable at +0**: +0/+4 are the two step-handler words written by every
  handler in the 0x00729554 table (the docs of `maybe_Ui_ItemScreen_*` describe the handler
  pair). The class is therefore not polymorphic in the recovered code.
* **`Ui_SpriteTree` 0x74..0x77 correction**: 0x74 is the layout-dirty flag cleared after the
  sprite list update, 0x76 is the requested layer passed to `Ui_SpriteTree_UpdateLayerAssignments`,
  0x75/0x77 are copied into the frame/uv block. (First pass had these shifted by one; fixed.)
* **`Ui_SlotGrid` animation panes are 0x50 bytes each**, not `sizeof(Ui_AnimRef)`; the batch
  only records the first word of each pane, so they are typed `Ui_AnimRef` with the batch size 4
  and the 0x50 stride stated in the evidence.
* **Embedded objects** (`Ui_Panel` in ItemScreen/ModelSelect, `Ui_ListCursor`,
  `Ui_MessageWindow`, `Ui_AnimRefList`, inline `Anim_Tween` pairs) are typed with the struct type
  without `*` because the recovered code passes their address to the runtime; the batch's
  4-byte field width is kept and the true stride is stated in evidence.
* **Class-level confidence is 0.40-0.55** and reflects the weakest important field. 199 of 360
  fields are below 0.5 and therefore carry `maybe_`; 18 are `unknown_*` at 0.0. Nothing was
  invented to fill a slot.

## Open problems / not verified

* Every `maybe_*` and `unknown_*` field is unverified by definition. In particular the border
  sprite ordering of `Ui_WindowFrame +0x60..+0xA8` (the phase condition per part is known, the
  exact corner/side identity is not), the exact list-widget boundaries in `Ui_ListWindow1F8`,
  and the three glyph-code page records of `Ui_IconAtlas`.
* `Ui_SlotGrid` is a generator aggregate: its `MoveHighlight`/`UpdateCrossFade` functions read
  offsets up to +0x1E4 which are larger than the class size (1008), so those methods most likely
  belong to a larger owner (item window) and were not used to type fields.
  `Ui_SlotGrid` also inherits `Ui_AnimRef` by base constructor calls, but a 0x320-byte base
  cannot fit inside 1008 bytes with the derived fields starting at +0x28; the base relation is
  kept as generated and not used for layout.
* `Ui_LoadingScreen` mixes at least three different objects (a 0x20-byte storage record, the
  0x174-byte window and the 0x2008-byte list object), so several offsets are only valid for one
  of them; the evidence text names the function where each offset is real.
* `Ui_TitleScreen`'s `Gfx_Drawable2D` base and `Ui_LoadingScreen`'s `Fs_ChannelTable` base are
  inherited from the generator's base-constructor calls and may be artefacts.
* `Ui_MotionPath`'s `+0xAC/+0xB0` are certainly released handles (Release/Dtor) but their role
  (second/third key track) could not be proven, so they stay `unknownKeyDataB/C`.
* Nothing was compiled, exported or emulator-tested - this is static naming only.
