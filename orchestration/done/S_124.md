# S_124 — Ui class/field naming (15 classes, 272 batch fields)

## What I did

Named all 15 classes and every offset of `orchestration/types/batches/S_124.json` exactly once, and
wrote `orchestration/types/out/S_124.json` (UTF-8, one object per class: class, type, summary, size,
base, confidence, evidence, fields).

Method: read the readable C of each class ctor (via `python tools/fn.py 0xADDR`, which resolves the
renamed files; the batch's `functions/FUN_*.c` paths are stale names), then the update/bind/dtor
methods, cross-checked constants, string literals, vtable/slot calls and struct widths. No whole-tree
searches. Scratch generator: `out/scratch/S_124/gen.py`.

## Traps / decisions (for the next worker)

1. **vtable-slot artefacts** (15 fields): `(**(code**)(*self+0xNN))()` was recorded as a field at
   `0xNN*4`. Emitted as `unknown_vtableSlotNN` at 0.0, with the offending call quoted:
   Ui_OverlaySlot +0xF0/+0x100/+0x150/+0x160; Ui_BattleTargetMarker +0x180/+0x1A0/+0x540;
   Ui_Pager +0x1D0/+0x210/+0x220/+0x240/+0x250/+0x260; Ui_LayoutTextBox +0x1C0.
2. **u32-pointer scaling bug** (same family as S_127's Ui_TextColorRange): when the decompiler typed
   `self` as `u32*`, struct_db multiplied the byte offset by 4. It is visible in Ui_SpriteSpan: the
   real reads are bytes 0xC..0x16 (`span->f_c`, `span[0xD]`, `span->f_e`, ...), while the batch lists
   0x30..0x58. I emitted the fields at the batch offsets (the merge requires them) and quoted the real
   byte offset in each evidence line; the span layout may therefore be shifted by a factor of 4 and
   needs an asm check.
3. **Ui_Composite is Ui_ItemListWindow**: the readable tree already names 0x002D9658/0x002D9570
   `Ui_ItemListWindow_Dtor` (vtable 0x00760724 / 0x0075EB0C). The generated class name was kept; the
   summary says so. Sizes: 3 child objects (0x50) at +0x70, 14 rows (0x78) at +0x160.
4. **Ui_BattleTargetMarker merges two objects**: the 13,008-byte widget (delete-dtor + update at
   0x003D3F54) and the marker set embedded at +0x3274 (fields +0x14..+0x22C, relative to the set).
   The class evidence says this explicitly; low offsets are named for the set, not for the widget base.
   The widget is also larger than 13,008: the set's Anim_ModelInstance at +0x327C would run past the end.
5. **Ui_SceneComposite size 144 is a lower bound**: the ctor doc says ~0x53F4 bytes and constructs an
   11 x 0x18 array at +0x8C plus a 0x14-element array beyond +0x194. Size kept at 144 (batch value,
   as every other S_* output does); the evidence records the real extent.
6. **Ui_ListWidget_Screen: base size > derived size** in structs.json (Ui_ListWidget 760 vs screen 620).
   The +0x140/+0x22C/+0x250 words are sub-object vtables (0x0078330C/0x007833FC/0x00783000) and the
   surrounding pairs are intrusive-list links, not scalars.
7. **Ui_Pager / embedded Ui_AnimRef**: `FUN_003DFF34`=Ui_AnimRef_ResetPanes takes the anim pointer, so
   +0x4C/+0x9C/+0xEC look like three ~0x50-byte anim-refs, but the ctor's page array starts at +0x50.
   I kept the page array at +0x50 (ctor evidence) and marked the anim-ref words `maybe_` at 0.35.
8. **Ui_Toggle +0x2C/+0x34** writes go to a locally allocated anim object (`piVar7[...]`), not provably
   to self -> `unknown_*` at 0.0.
9. **Ui_DamagePopup vs Ui_DamagePopupGroup** are the same +0x50 layout seen twice; names kept parallel
   (popupN / popupNSprite / popupNNumberClip). Whether a "popup" is a whole number or one digit position
   is not settled: SetValue writes the units/tens/hundreds digits to +0x98/+0xE8/+0x138, which looks
   like one object holding all digit positions.
10. **Ui_MessageWindow2 +0x49..+0x4D** are five bytes zeroed together with no reader -> `unknown_flag*`
    at 0.0 rather than invented visibility/line-state names.

## Not verified

Every `maybe_*` and `unknown_*` field; the exact float-vs-fixed-point nature of Ui_OverlaySlot +0x98/+0x9C;
the per-position meaning of the Ui_LayoutTextBox metric block (+0xD8..+0xF0); the semantic difference
between the four child lists of Ui_SceneComposite; the ownership of the Ui_SpriteSpan record bytes 0x30..0x58
(see scaling trap 2). Nothing was compiled, exported or emulator-tested — static naming only.
