# S_125 - Ui classes and fields (15 classes, 218 field offsets)

## What I did
Named every class and every field offset of `orchestration/types/batches/S_125.json`
(15 Ui classes, 218 offsets) into `orchestration/types/out/S_125.json`.

Method: for each class I read the readable C of the batch functions (ctor first, then update/draw
siblings), resolved stale `readable` paths with a small address->file helper, and checked the ARM
assembly (`tools/fn.py --asm`) whenever the pseudocode was damaged or an offset looked suspicious
(`Ui_ListView_UpdateItemCountAndVisibility`, `Ui_PaneCrossFade_SetState`). Shared offsets were
cross-checked against earlier batches so the same object is named the same way
(`Ui_BattleCommandWindow` fields from S_085, `Ui_Object` from S_078, `Ui_AnimRefList` from S_111,
`Gfx_ScreenView` from S_052). No `asm/`, `decomp/` or `include/` tree was walked or grepped.

## Files changed
- `orchestration/types/out/S_125.json` (new; 51,834 bytes, UTF-8, 15 objects, 218 fields)
- `AGENT_LOG.md` (appended Entry 455)
- `orchestration/done/S_125.md` (this report)
- Scratch (not part of the deliverable): `out/scratch/S_125/build.py` (generator + offset

**Side effect to know about:** `python tools/typedb/apply.py --validate` rewrites
`orchestration/types/merged/report.json` (it prints "wrote orchestration\types\merged"). It touched
only that generated artefact; no header, decomp or another task's `out/` file was modified.

## Checks
- Offset contract: for all 15 classes the emitted offset set equals the batch offset set exactly
  (asserted by the generator, printed `PROBLEMS: none`); no duplicate offsets and no duplicate
  field names inside a class.
- `maybe_` prefix is present exactly on names with confidence < 0.5; `unknown_*` names are 0.0 and
  carry the offending expression in their evidence.
- Strict UTF-8 decode + `json.loads` of the written file: OK (51,834 bytes, 15 classes).
- `python tools/typedb/apply.py --validate`:
  - **0 errors / 0 warnings attributable to S_125** (`report.json` has no issue with `batch ==
    "S_125"`), every field type resolves through structs.json/builtins.
  - Overall run: 1270 classes / 23,873 fields; the single error is pre-existing
    `S_066: Save_SlotUi@0x324 field type: unknown type 'UiWindow'`.
- `tests/run_all.py` and `tools/verify_project.py` intentionally skipped: WORKER_RULES rule 5
  exempts naming batches (N_/R_/R2_/G_/S_/V_) and requires only a JSON check of the output.

Confidence spread: 63 fields >= 0.5, 105 `maybe_*`, 50 `unknown_*` at 0.0.

## What the classes actually are (short)
- `Ui_ListView` - container-backed list: itemCount +0x4C, embedded count container +0x54, bound
  source range +0x7F4, empty indicator +0x7F0, two intrusive registrations +0x7FC..+0x82C.
  Note: its asm also drives row widgets at +0xE8/+0xEC, i.e. two shapes were clustered.
- `Ui_PaneCrossFade` - two-pane fade: pane A duration/state +0x4C/+0x50, pane B group +0x5C
  (duration/state +0xA8/+0xAC), running flags +0x68/+0xB8, pane-change event bookkeeping
  +0xF0..+0x100.
- `Ui_RecipeInfo` - recipe info part: text `std_String` +0x358 -> `Ui_Slot` +0x2F0, SE handle
  +0x224, step controller +0x11C, style/flags +0x350..+0x354.
- `Ui_SenrekiWindowPart` - battle-records sub-part, vtables +0x0/+0x30/+0x38, four children +0x44.
- `Ui_TimerDisplay` - six 0x9C-byte digit widgets at 0x50, 0xEC, 0x188, 0x224, 0x2C0, 0x35C.
- `Ui_TwoPositionSelector` - AnimRefList `position1` +0x58 / `position2` +0xA8, icon ids +0x51..+0x54.
- `Ui_ActionSeq` - one 0x64-byte action-sequence entry (not a widget).
- `Ui_BattleCmd` - `UiBattleCommandWindow` subclass; all fields inherited, names reused from S_085.
- `Ui_DateDisplay` - really the shared text-window `Ui_TextWindow_BindRowPanes` base.
- `Ui_HorseraceReceptMsg` - horse-race reception panel loading `horserace_recept_msg.bxon`.
- `Ui_LayoutSystem` - global layout descriptor (two tables, global scale 1.0f).
- `Ui_MenuView` - the per-frame `ViewWork` object (two GfxScreenView collections + three lists).
- `Ui_MonsterRecord` - 300-entry monster-id table object.
- `Ui_PaneGroup` - pane group / equip part with `Ui_AnimRefList` and an 8-step fade counter.
- `Ui_TextRenderer` - actually `Sound_StreamBuffer_InitDefaults` (stale class name kept).

## Open problems / not verified
- 50 `unknown_*` offsets are vtable-slot parser artefacts (e.g. `*self + 0x34` recorded as
  `0xD0`) or reads of a separately allocated object, not self. They need a `struct_db.py` fix,
  not more naming. List: Ui_ListView +0x100/+0x1B0, Ui_TwoPositionSelector +0xD0/+0xE0/+0xF0/+0x120,
  Ui_BattleCmd +0x140, Ui_PaneGroup +0x30/+0x100, Ui_HorseraceReceptMsg +0x58/+0x5C/+0x60, plus the
  zero-init-only state words.
- `struct_db` class clustering is wrong for several entries: Ui_ListView (container + row-widget
  view), Ui_MonsterRecord (outer object + allocated id table 0x30 bytes later), Ui_DateDisplay
  (shared text-window base), Ui_TextRenderer (Sound_StreamBuffer). I kept the generated class names
  because the merger keys on them and said so in each summary.
- Ui_BattleCmd's size (1068) is smaller than its base `Ui_BattleCommandWindow` (1076) from S_085:
  all its fields are inherited base fields, so the two records must stay consistent (they now are
  for the shared offsets).
- Not proved: the two-base layout of Ui_SenrekiWindowPart; the exact Ui_PaneCrossFade fade-group
  sub-structure; the meaning of the Ui_ActionSeq status bytes/trailing words; the Ui_PaneGroup
  default triples (typed f32 from copy shape only); Ui_MenuView +0x38..+0x48; the
  `Sound_StreamBuffer` attribution (came from the existing function doc, not re-proved).
