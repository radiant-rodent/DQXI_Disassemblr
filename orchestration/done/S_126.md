## Open problems

1. `Ui_Element`, `Ui_AnimPlayer`, `Ui_Label`, `Ui_DebugLabel`, `Ui_HandleSet`,
   `Ui_BoushiPart`, `Ui_Font` and `Ui_MessagePart` should be re-batched by vtable/constructor
   instead of by function self-type; their merged structs will otherwise contain fields of
   unrelated engine classes. This is stated in each class summary.
2. Sizes derived as `max_strong_field+width` are lower bounds / artefacts:
   `Ui_Element` 932, `Ui_AnimRef` 800 (the single use of +0x31C is on a different object; the
   real object is roughly 0x4C bytes — see S_114), `Ui_HandleSet` 60.
3. `Ui_AnimRef`'s size being 800 means any struct embedding one (e.g. `Ui_Tween` +0x60) will
   be laid out too large by the merger. The fix belongs to the `Ui_AnimRef` batch, not here.
4. `Ui_WindowPart`'s 62-entry table at +0x140 is not modelled (the batch has no entries for
   the table's callback/encoded-slot fields at +0x10/+0x14).
5. `Ui_Label` +0x208 is read as a pointer (→ +0x768 character id) in one routine and as a
   u16 value in another; emitted as `maybe_memberSource` at 0.3.
6. `Ui_Tween` +0xC..+0x18 (four words copied to/from a target record) are only seen in the
   damaged opcode dispatchers 0x003A7128 / 0x003A71D0 — emitted at 0.2 as
   `maybe_vectorValue0..3`.
