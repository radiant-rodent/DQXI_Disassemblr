# S_127 - Ui classes and fields (15 classes, 138 fields)

## What I did

Named every class and every field of `orchestration/types/batches/S_127.json` and wrote
`orchestration/types/out/S_127.json`.

Batch contents: `Ui_ItemRows`, `Ui_TextColorRange`, `Ui_TitleDemo`, `Ui_Animator`,
`Ui_BattleCommandPopup`, `Ui_CasinoJackpot`, `Ui_CasinoWin`, `Ui_MessagePartTableSmall`,
`Ui_PagedIconSelect`, `Ui_PokerCards`, `Ui_ProfileScreen`, `Ui_ScreenSlideAnim`,
`Ui_SevenRowSelector`, `Ui_SlotMachineDisplay`, `Ui_TextLineCache`.

Method: for each class I read the ctor/dtor/update in `decomp/readable/functions/` (located by
address with a small scratch helper, no tree walks), then `python tools/fn.py <addr>` /
`--asm` for the callees that define the field meaning (`Gfx_BindIndexedResourceSet`, `Ui_Part_*`,
`Ui_TextListWindow_UpdateItemRects`, `Casino_Slot_UpdateSpinState`, ...), cross-checked widths
against `orchestration/types/structs.json` (e.g. `Gfx_ResourceSlot` 52 = the 0x280 -> 0x2B4
stride, `Casino_Slot` 5880 = this batch's slot-display size, `Ui_TextListWindow` = the
`Ui_SevenRowSelector` layout), and only then wrote names. Nothing was invented to fill a slot:
30 fields that are extraction artefacts or have no reader are `unknown_*` with confidence 0.0
and the offending expression quoted.

## Findings the orchestrator should act on

1. **`Ui_TextColorRange` has a struct_db scaling bug.** The init body (0x00542910, 84 bytes) is
   `strb` stores at byte offsets 0,1,2,3 (0), 4 (0x7F), 5 (u16 0), 7 (0x40), 8,9,10 and a memset
   at 11, but the batch offsets are 0,4,8,12,16,28,32,36,40,44 (i.e. 4x) because the body was
   indexed as `u32*`. I kept the batch offsets (the dispatcher validates them) and encoded the
   real byte in every field name/evidence, but the merged struct is wrong. The class is also
   **not** a text colour range: it sits between `Snd_InitStreamSlot` and `Str_CopyDirectoryPath`,
   and `Str_CopyDirectoryPath` writes its 0xFE-byte path at `this+0xC` - the real struct is a
   ~0x10A-byte path/stream descriptor. Suggest renaming the model and letting an `Fs_*` batch own it.
2. **`Ui_SevenRowSelector` duplicates `Ui_TextListWindow`.** 436 bytes, and its fields sit at
   exactly the offsets listed for `Ui_TextListWindow` in `structs.json` (+0x54 embedded text-list
   window, +0x64, +0x1B0 artefact). It is the same object; only the seven-row use is new.
3. **`Ui_SlotMachineDisplay` duplicates `Casino_Slot`** (both 5880, same dtor function family,
   six reels at 0x1A4 stride); `Casino_Slot` is the better name and both are lower bounds
   (the sixth reel starts at 0x16F4, so the real size is >= 0x1898).
4. **`Ui_PokerCards` is a mixed cluster**: +0/+4/+8/+0xC/+0xD/+0xE..+0x12 are a small card-flag
   record (5 hold bytes, selected card, payout pair) while +0x98 is the poker *table's* owner hook
   (`Ui_PokerTable_UpdateCardSlots` operates on a 0x60-stride card-slot array at +0x5B8, far
   outside 156 bytes). It should be split.
5. **Repeated vtable-slot artefacts** (`(**(code**)(*self+0xNN))()` recorded as a field at
   `0xNN*4`): `Ui_ItemRows` +0xF0/+0x160/+0x180/+0x1A0, `Ui_PagedIconSelect` +0x100/+0x160,
   `Ui_SevenRowSelector` +0x1B0. They even define sizes (SevenRowSelector 436 = artefact+4).
6. **Underestimated sizes** (max_strong_field+4): `Ui_CasinoJackpot` (embedded `GfxEffectPart`
   at +0x2EC is 548 bytes), `Ui_SlotMachineDisplay`, `Ui_ProfileScreen` (node list at +0x2000 and
   the destructor chain run past 8196).

## Open problems / what is NOT verified

* Every `maybe_*` (26) and `unknown_*` (30) field. In particular: the `+0x38`/`+0x0E`
  "countSource" object in `Ui_ItemRows`/`Ui_PagedIconSelect` (a list whose +0xC is an entry
  count, or a row-label provider - the code only reads `->f_C`); the two floats at
  `Ui_CasinoJackpot +0x288/+0x28C` (both set to 0.0f, they live *inside* the first
  `GfxResourceSlot`); `Ui_ProfileScreen +0x124` (compared with 0x3E800000 = 0.25f) and its mode
  words +0x29E/+0x2A0; the `Ui_SlotMachineDisplay +0x98` owner hook; the
  `Ui_SevenRowSelector +0xAC` record table (0x8C-byte records, bounds check via a mangled
  `0x00001CFC + table` base); the five counters of `Ui_TextLineCache` (no reader recovered).
* `Ui_ProfileScreen +0x20` and `Ui_BattleCommandPopup +0x58/+0x5C/+0x60` are pointer
  misattributions (member pair at +0x11C; the loaded text table) - emitted as `unknown_*`.
* Class-level confidence is the weakest important field; `Ui_TextColorRange` is 0.15 for the
  reason above.
* Nothing was compiled, exported or emulator-tested: static struct naming only.
