# S_129 - struct field naming batch (Ui)

## What I did

Named all 15 classes and every batch offset exactly once in
`orchestration/types/out/S_129.json` (105 fields = the 105 offsets in
`orchestration/types/batches/S_129.json`; 15/15 classes present).

Method: read the constructor/update/destructor readable C for each class with
`python tools/fn.py` (0.5 s per call), cross-checked the raw assembly
(`--asm 40`) whenever the readable C had a suspicious `param_1 + N` (typed
pointer vs word indexing), and used `orchestration/types/structs.json` for the
type names (`UiText`, `UiTextElement`, `UiAnimRef`, `UiAnimRefList`,
`GfxSpritePane`). No whole-tree walks or greps were run.

## What the classes are

- **Ui_BattleScreen** (60864 bytes, secondary base at +0xDE10): large battle-screen composite.
  The batch's size 4 is a `max_strong_field+width` artefact (all real accesses are `weak`
  single-access hits); the deleting dtor `0x0046C8C4` proves the object by destroying the
  target-marker container (+0xED40), model instances (+0xED48), an `Effect_LinkInstance`
  (+0xDE80) and two inline arrays (+0xDED8 0xE4x0x10, +0xED98 0x14x2). Size set to the
  highest proven end (0xEDC0).
- **Ui_Cue** (68): short-lived UI sound cue (id, descriptor callback pair, mode byte, sound
  handle, elapsed/duration floats). Real layout confirmed from assembly
  (`vldmia`/`vstr` +0x14 timer, duration +0x18); the batch's +0x30/+0x38/+0x40 are stale
  word-indexed aliases of +0x14/+0x18/+0x20 and are marked `unknown_*` at 0.0 rather than
  inventing three extra floats.
- **Ui_GuideWindowChild** (2820): guide-window object with an intrusive child list
  (+0xAF0/+0xAF4/+0xAF8), a second vtable at +0xAE8 and four 0x260-byte member rows at +0x11C.
- **Ui_HopeSelect** (884): hope-select menu; 'win_hope_select' child at +0x138, optional
  second child +0x324, input object +0x370 whose three cursor axes are forwarded.
- **Ui_MessagePair** (756): two-line message widget (left/right Ui_Text + panes + owner list);
  SetupPanels uses the embedded objects at +0x248/+0x29C/+0x2F0, so the emitted size is a
  minimum.
- **Ui_MpDamagePopup** (400): 'pop_mpdamage%d' popup, three 0x50-byte digit parts at +0x4C
  and the number pane at +0x18C.
- **Ui_PagedListWindow2** (436): 16-row two-column paged list; entry count +0x4C, pager
  container +0x54, u16 entry-id range +0x174/+0x178.
- **Ui_PartSlot** (128, base Ui_AnimRefList): two animation refs bound from adjacent anim ids
  (0x364960/0x364968); handles at +4/+0x5C, refs at +8/+0x60.
- **Ui_PartyMemberSlot** (6124): party member battle/field slot with its own state machine
  (`stateId` +0x17DC -1 -> 0x2BD3 -> 0x2BE5/0x2BEC), chara id +0x1230, action id +0x125C,
  completion byte +0xD2, embedded action UI +0x17E8.
- **Ui_Resource** (40): pack-handle holder (20-bit index + 12-bit generation at +4) plus five
  state words cleared on release.
- **Ui_SlotNumberPlate3D** (112): 3D casino slot number plate; two 10-entry coin texture
  arrays +0/+0x28 (not in the batch's top-7) and eight 4-byte values fetched per digit strip
  through vtable slot 0xC.
- **Ui_SlotPlateNumber** (140): slot-machine plate; icon_l/c/r (+0x4C..+0x54), digit strips
  5/4/3 panes (+0x58/+0x6C/+0x7C) and icon_jackpot (+0x88).
- **Ui_TextFade** (28): fade/scroll tween state (current/start alpha, duration, elapsed,
  0..4 state machine at +0x1B).
- **Ui_TextLabel** (104): **mixed cluster**. 0x00401A74 is a battle member-number label
  (Ui_TextElement +0x34, text-group id +0x28, battle unit index +0x4C); 0x0040AC1C and
  0x0040B7A8/0x0040BA94 are Model_Equip_* (established facts) on a model-equipment object
  (+0x38 model ptr, +0x65 charaId, +0x66 dirty). Documented instead of renamed because the
  merger keys on the class name.
- **Ui_TextPage** (28): the 7-word (0x1C) page-entry descriptor emitted by
  `maybe_Ui_TextPage_RefreshThreeEntryCache` (handle + 3 x {id, value}); the batch's ctor
  function is the large *container* constructor, so the class name here means the record.

## Traps found in the batch (handled, worth knowing)

1. **Vtable-slot artefacts**: `(**(code **)(*self+0xNN))()` was parsed as a field at
   `0xNN*4` for `Ui_PagedListWindow2` +0xD0/+0xE0/+0x1B0 and `Ui_PartyMemberSlot` +0x120.
   These are not fields; emitted as `unknown_vtableSlotAlias*` at 0.0 with the call quoted.
2. **Stale word-indexed selves**: `Ui_Cue` +0x30/+0x38/+0x40 come from an `int*` self in older
   readable C; assembly shows the fields are at +0x14/+0x18/+0x20. Marked `unknown_*` 0.0.
3. **Mixed class clusters**: `Ui_TextLabel` merges a UI label with `Model_Equip_*`;
   `Ui_MessagePair` merges the pair helper with the widget constructor that embeds three
   objects it treats as pairs; `Ui_TextPage` names a 7-word record while its ctor builds a
   much larger container. Summaries state this.
4. **Underestimated sizes**: `Ui_BattleScreen` 4 and `Ui_MessagePair` 756 are lower bounds;
   BattleScreen's size was corrected from its dtor (0xEDC0).

## Open problems / suggested follow-ups

- **Ui_TextLabel split**: 0x0040AC1C / 0x0040B7A8 / 0x0040BA94 should belong to a
  `Model_Equip_*` class, not `Ui_TextLabel`. A cleanup batch should move those functions
  (and the +0x38/+0x3C/+0x65/+0x66 fields) and re-run struct_db.
- **Ui_TextPage**: decide whether the 0x1C descriptor deserves its own class (e.g.
  `Ui_TextPageEntry`) instead of reusing the container name; the container ctor currently
  contributes no fields to this class.
- **Ui_BattleScreen** needs an allocation site or a vtable scan to pin the exact size
  (0xEDC0 proven end; 0xEE00 is the likely aligned size).
- **Ui_SlotNumberPlate3D** +0x50..+0x6C: identify what vtable slot 0xC returns (4 values per
  digit strip) - likely pane/material or animation-frame indices.
