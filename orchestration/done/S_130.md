# S_130 - Ui class and field naming (15 classes / 90 fields)

## What I did

Named all 15 classes and every field offset of `orchestration/types/batches/S_130.json`
(Ui subsystem). Output: `orchestration/types/out/S_130.json` (38,241 bytes, UTF-8, 15 classes,
90 fields, 35 fields at confidence >= 0.5, 45 `maybe_*`, 10 `unknown*`).

For every class I read the readable C of its ctor/update/dtor, then checked the raw ARM
disassembly (targeted `Select-String` on the single `asm/text/text_00XX0048.s` chunk plus
`tools/fn.py`) whenever the readable C used word-indexed `self` arithmetic or a vtable-slot
call, because `struct_db` sometimes records a slot constant as `slot*4`. I also cross-checked
`structs.json` for a class with the same vtable/size (this is how `Ui_Dialog` turned out to be
`Ui_TitleMessageWindow` and `Ui_BigView` turned out not to be UI at all).

### Key findings (details in the JSON summaries/evidence)

* **Ui_Dialog (508 -> 8320)** is misnamed: its deleting destructor 0x00395328->0x00395338
  stamps vtable **0x00766E14** (literal at 0x39549C) and frees a handle table at **+0x2074**;
  `structs.json` maps 0x00766E14 to **Ui_TitleMessageWindow** (8268+ bytes). UpdateLayout also
  resolves `frame_green`/`frame_blue`/`frame_red` panes from `self+0xA8`.
* **Ui_BigView (3456)** is **not UI**: dtor 0x001C9AE8 runs `Field_ShutdownSlots`, destroys
  three 10-entry 0xC-byte tables (+0x24/+0x9C/+0x128), a 2-entry table (+0xD58), an intrusive
  node (+0xD78/+0xD7C) and a pack handle (+0x18). Callers: Actor_ApplyModelSetByName,
  Model_Preview_ApplyParts, Gfx_ScreenView_ReleaseNamedObjects.
* **Ui_AnimQueue (3504 -> 3712)** is an embedded animation-step player at +0xD8C: vtable +0,
  index < 8 at +4, 1/30 s elapsed at +8, tick at +0xC, delta at +0x10, relocation table at
  +0x20, eight 0x18-byte step entries from +0x34 (asm 0x003B3EB8). Eight entries end at 0xE80.
* **Ui_DialogRoot (292 -> 1428)**: Create 0x006D6F84 allocates 0x594; Init 0x0019CBF4 stores
  the vtable at +0, owner at +0x11C and registers a Ui_NodeList at +0x120, then builds the
  embedded window at +0x164 (twelve 0x50-byte Ui_AnimRefLists; their +0x4C entry in the batch
  is flagged because in the outer object they really start at +0x1B0).
* **Ui_InLoopOutAnim / Ui_NumberRoll / Ui_Root / Ui_GlyphQuadArray / Ui_SpriteMoveTo /
  Ui_CurveAnimator / Ui_Effect2DOverlay / Ui_EffectSlot / Ui_TextSpan / Ui_ListItemValue /
  Ui_PooledRecord** are named from ctor/update evidence ('in'/'loop'/'out' bind names,
  'select2'/'select3', 1/30 s clock, 0.5f/0.1f thresholds, capacity/used/buffer, etc.).
* **Vtable-slot artefacts**: `Ui_NumberRoll` +0xD0/+0xE0/+0xF0 and `Ui_TextSpan` +0x1B0 are
  `(**(code**)(*self+0x34/+0x38/+0x3C/+0x6C))()` slot constants multiplied by 4, not fields;
  emitted as `unknown*` at confidence 0.0 with the call quoted.
* **Bogus `self` reads**: `Ui_DialogRoot` +4 came from the literal-pool global 0x00729C78 and
  +0x30 from the WidgetHost argument (`owner+0x30`); both `unknown*` at 0.0.

## Open problems / honest caveats

* Every `maybe_*` and `unknown*` field is unverified. Specific weak points:
  * Ui_EffectSlot: the three container header/begin pairs are read correctly from asm, but the
    container types (list vs rb-tree, and exactly which word is the header) are inferred from
    the helper calls, not from a named ctor.
  * Ui_TextSpan: the +0x198 sub-object (another span owner) belongs to the embedding widget, not
    to the 500-byte span array; the class may actually be a parent text widget.
  * Ui_ListItemValue: class identity and the meaning of +0x18/+0x2C/+0x30/+0x34 are unproven;
    the recovered ctor's original decompilation was corrupt, so I verified offsets from asm but
    not their purpose.
  * Ui_Root: the two child-window objects at +0xCC0/+0xD14 and the child-list node semantics at
    +0xD1C/+0x1614 are inferred from a single shutdown path.
  * Ui_CurveAnimator: the three mask words are named from the 1.0f/0.5f/0.1f comparisons in the
    step loop; the exact "reached" semantics are a reasoned reading, not a named caller.
* Size corrections were made only where the object end is proven by asm: Ui_AnimQueue 3712,
  Ui_Dialog 8320, Ui_DialogRoot 1428. Other sizes are the batch's `max_strong_field+width`
  values and may be lower bounds.
* The batch's class grouping is wrong for at least two classes (Ui_Dialog, Ui_BigView). I kept
  the batch class names (the merge keys) and documented the real object/class in the summary
  and evidence rather than silently renaming them.
