# S_132 — Ui struct/field naming (15 classes)

## What I did

Named all 15 classes and every one of the 63 batch field offsets in
`orchestration/types/batches/S_132.json` (subsystem Ui), and wrote
`orchestration/types/out/S_132.json`.

Method: for each class I read the constructor/sibling methods in `decomp/readable/`
(dossier via `tools/fn.py`, plus `--asm` where the readable C disagreed with the raw
Ghidra body), cross-checked field widths against `structs.json`, and disassembled a few
unnamed helpers directly from `original/exefs/code.decompressed.bin` with capstone
(`out/scratch/S_132/armdump.py`) to settle contradictory decompilations. No whole-tree
walks were done.

Fields: 63 total — 46 with confidence >= 0.5, 11 `maybe_*` (<0.5) and 6 `unknown_*` at 0.0.
File is 28,957 bytes, UTF-8, one class object per batch class (same class/type keys, no
renames), offsets emitted exactly once and equal to the batch offset sets.

## Classes (short)

* **Ui_Timer** (324): timed UI part; child part +0x98 advanced via vtable slot +0x2C,
  countdown s32 +0x140 (plays SE 0xDD at 0), state byte +0x138 bit 0x10 = reset/hide
  (+0x13D=0, +0x94 visible=0, +0x140=-1, confirmed in assembly).
* **Ui_Transition** (24, base Ui_Overlay): fade helper. +4/+8 are an 8-byte handler record
  copied from overlay handler table `0x0072A79C` (`ldrd r0,r1,[table,#0x28]; strd
  r0,r1,[r4,#4]`); +0xC fade-quad handle, +0x10 faded window, +0x14 frame counter.
* **Ui_WidgetGroup** (488): child-list dispatch (owner/end +0x10, first node +0x14) plus a
  second listener list at +0x1E0/+0x1E4; +0x1D0 is an unproven 16-byte out-buffer.
* **Ui_AnimBinder** (36): layout-animation binder (resource +0xC, animatable object array
  +0x18, 8-byte {target,tag} bindings +0x1C, count +0x20 not in batch, capacity +0x22).
* **Ui_AnimValue** (48): smoothed scalar (value +0x10, velocity +0x24, wrap mode +0x28
  0 stop / 1 loop / 2 ping-pong, status bits +0x2C).
* **Ui_ChildSlot**: chimera — real 2-digit index cursor at parent+0x2F14 (Ui_AnimValue
  pointers +0x4C/+0x9C for index%10 and (index/10)%10); +0x2F00 is the parent window's
  5-entry icon-material table (`0x003EAF08` = `if (i<5) return base[i]`).
* **Ui_ChildTransform** (real >= 0xBE8): row/ring of up to 32 digit-named child panes built
  through layout factory +0xA8, visibility mask persisted under save key +0xB64 (u16 id) /
  +0xB66 (u8 sub) via `0x0066B64C`/`0x00613A10` (asm: key=id|sub<<24, entries at
  savework+0x3220).
* **Ui_CommandStack** (372): 0xC-byte entries +0x11C, handler +0x120, (tag<<1)|1 dispatch
  word +0x124, depth +0x170.
* **Ui_DigitDemo** (368): binds position2/position1 anim refs +0x11C/+0x16C against layout
  +0x98 and fills the text-element list at +0xD4 with three columns of digit panes.
* **Ui_FiveRowSelector** (real >= 0xAC): rebinds five 0xC-byte rows at +0x70 to ids
  delta*5+i and re-selects Ui_List +0x38 with `(selectedRow-1)|(entryGroupId<<16)`.
* **Ui_FloorMapJumpTrigger** (72): **not UI** — field map-jump trigger, section id +0x45
  (0xFF none) applied through `Field_HandleMapJumpEvent`; readable C already renamed it
  `maybe_Field_MapJumpTrigger_ApplySection`.
* **Ui_HandlePair** (16): {Gfx_Sprite* +0, active pack handle +4, pending handle +8, ready
  callback +0xC}. Batch base Gfx_Sprite is impossible for 16 bytes; cleared.
* **Ui_IconButton** (88): duplicate view of `Ui_IconRowWindow` (same size, +0x30/+0x54):
  pane name +0x4C, resolved icon +0x50, anim ref +0x54.
* **Ui_ListOwner** (real >= 0x58, base Ui_Object): secondary vtable at +0x4C and inline
  0x24-byte Ui_AnimRefList sub-objects destroyed by `std_destroy_range(obj+0x4C,0x24,2)`;
  the ctor returns an enclosing object 0xA4 bytes earlier.
* **Ui_ListWidgetScreen** (624): inline UTF-16 label +0x154, embedded polymorphic object
  +0x22C fired once via latch +0x23C, child generation handle +0x26C resolved through
  `0x007B80C0`.

## Decisions / traps

1. Batch function `0x001BFBD4` attributed to Ui_Transition is `maybe_Ui_ItemScreen_NextStep`
   and was not used for the layout.
2. The previous doc headers called +4/+8 a "timer pair"; assembly shows an 8-byte record of
   code pointers from overlay handler table `0x0072A79C`, so they are named as a handler
   record. Offset +8 is left unlisted (it is not in the batch) and will be padding.
3. Three classes are mis-grouped by the generator: `Ui_ChildSlot` mixes two objects 12 KB
   apart, `Ui_IconButton` duplicates `Ui_IconRowWindow`, `Ui_FloorMapJumpTrigger` is a Field
   object. Class keys were kept because apply.py rejects class names absent from
   structs.json; each summary/evidence states the mis-grouping.
4. Batch sizes are lower bounds where the field cluster stops early
   (Ui_ChildTransform, Ui_FiveRowSelector, Ui_ListOwner). Sizes were left at the batch
   values so the merge keeps its evidence-based size; the real minimum is in the evidence.
5. `Ui_HandlePair` base was cleared (`""` → null) because Gfx_Sprite (~784 B) cannot be the
   base of a 16-byte object; the +0 word is a Gfx_Sprite pointer, not a base sub-object.

* Exact semantics of the `Ui_CommandStack` +0x124 handler tag beyond the dispatch encoding.

* Real class of the +0xD4 object in `Ui_DigitDemo`: named `textElementList` by analogy with
  S_090/S_091, but its +8/+0xC/+0x10 layout is window-like.
* +0x1D0 blob in `Ui_WidgetGroup`; purpose of `Ui_ListOwner` +0x50/+0x54 inside the inline
  base sub-object.
* Nothing was compiled, exported, or emulator-tested — static naming only.
