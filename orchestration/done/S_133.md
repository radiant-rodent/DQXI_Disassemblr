# S_133 — UI struct/field naming batch

**Status:** completed (static naming only — nothing compiled, exported or emulator-tested)

## What I did

Named all 15 classes and every one of the 55 offsets in
`orchestration/types/batches/S_133.json` and wrote the result to
`orchestration/types/out/S_133.json`.

Method: for every class I read the named readable C of its ctor/update/methods in
`decomp/readable/functions/`, then cross-checked the suspicious offsets in the ARM
disassembly (`asm/text/*.s`) so that the batch's `type_guess` was not trusted blindly.
`orchestration/types/structs.json` was used for base layouts (`Ui_Window`, `Ui_ListWindow`,
`Ui_AnimRef`) and for valid type names.

## Decisions recorded (also in AGENT_LOG Entry 462)

1. **Kept the generated class names** even where the identity is doubtful:
   `Ui_WorldMapMarker` is really `Ui_LayoutRefList`/pane-group code (vtable 0x0076828C,
   dtor 0x003A8200), `Ui_ScreenFade`'s third function (0x003686B8) is
   `Scene_TransitionSequence_Setup` of a *different* class (vtable 0x007654E8), and
   `Ui_TargetMarker` mixes a marker-object dtor with a container dtor. The summaries say so
   rather than silently renaming.
2. **Size correction only where asm proves the object end**: `Ui_WorldMapMarker` 292 → 2288
   (dtor `add r0,r0,#0x120; std_destroy_range(0x50, 0x19)` → end 0x8F0). All other sizes
   were left at the batch value even when the base class is larger (consistent with
   previous S_* batches).
3. **Vtable-slot artefacts**: `(**(code **)(*self + 0xNN))()` had been recorded as a field at
   `0xNN*4` for `Ui_PagedListWindow3 +0xD0/+0xE0/+0x120` and `Ui_WorldMapMarker +0x50`.
   These are emitted as `unknown_*` with confidence 0.0 and the quoted call; asm of
   0x004CE6E8 / 0x003A8200 confirms there is no data access there.
4. **Sub-object offset caveat**: `Ui_BigScreen +0x20` comes from `puVar3[8]` where
   `puVar3 = self + 0xD8C` (real byte +0xDAC). It is named as the inherited
   `Ui_Window` child-ring word with that caveat, not as a BigScreen-owned field.
5. **Width corrections backed by byte stores**: `Ui_ScreenFade +0xC` is `u8` (not f32),
   `Ui_ActorSlot +0x10` is `u8`, `Ui_TextRun +0x12` is `u16`.
6. Honest unknowns: 7 `unknown_*` at 0.0, 11 `maybe_*` with confidence < 0.5 (plus 2
   `maybe_` kept at 0.5 as a hedge); 37 fields at confidence >= 0.5.

## Test / validation results

* JSON syntax + schema self-check: `python out/scratch/S_133/validate.py` → **errors: 0**
  (strict UTF-8 decode, `json.loads`, per-class offset set equals the batch set, no duplicate
  offsets or names, every type is a builtin or a `structs.json` type, `maybe_`/`unknown_`
  confidence rules enforced).
* Real merger smoke test, in-process, writes nothing:
  `python out/scratch/S_133/validate_merge.py` (uses `tools.typedb.apply.Evidence` +
  `merge_structs`) → **issues for S_133: 0**; all 15 structs merge with 4/4/4/4/4/4/4/4/4/4/3/3/3/3/3
  fields and the sizes listed above.
* `python tests/run_all.py` and `python tools/verify_project.py` were **not** run —
  WORKER_RULES rule 5 explicitly exempts naming batches (N_/R_/S_/…) because they only write
  one JSON file. No bit-matching code, headers or exported data were changed.

## Open problems / not verified

* Every `maybe_*`/`unknown_*` field, as listed in each field's evidence.
* Real engine identity of `Ui_WorldMapMarker`, `Ui_ScreenTransition`, `Ui_TargetMarker`; the
  batch's self-type grouping clearly mixes two classes in each of these.
* `Ui_Map +0x8C/+0x91` flags; `Ui_ScreenFade +0xC` unit (display brightness index vs mode);
  `Ui_ScreenTransition +0x30` owner class; `Ui_TextArg +0x1C` record layout beyond
  `{u16 id, u32 count}`; `Ui_TextRun` field semantics (copy/zero evidence only);
  `Ui_Callback +0x2A0/+0x2A4` payload meaning; `Ui_BigScreen +0x20` inherited-field name.
* `Ui_WorldMapMarker`'s `base: Ui_AnimRef` (from the batch) is inconsistent with its own field
  at `+0x120` (< 800-byte Ui_AnimRef) — the base inference is probably wrong for this cluster.
