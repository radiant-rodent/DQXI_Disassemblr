# S_135 — UI struct/field naming batch

**Status:** completed (static naming only — nothing compiled, exported or emulator-tested)

## What I did

Named all 15 classes and all 45 offsets in `orchestration/types/batches/S_135.json`
and wrote `orchestration/types/out/S_135.json`. For each class I read the named
readable C of its ctor/update/method, then checked the suspicious offsets in the
ARM disassembly via `python tools/fn.py 0xADDR --asm N` (no tree walks).
`orchestration/types/structs.json` supplied base layouts and valid type names
(`Ui_AnimNode`, `Ui_AnimRefList`, `Ui_TextElement`, `Ui_Object`,
`std_StateSequence42`, `Ui_Layout`).

## Decisions / traps

1. **Batch offsets were trusted only after asm checks.** `Ui_ModePane +0x2C8`
   is real (`ldrb r0,[r7,#0x2c8]`), and the readable doc's “+0xB2” is wrong;
   `Ui_NumberPane +0xD4` is real (`add r5,r5,#0xD4`); `Ui_MultiBase +0x258`
   is real (`str r1,[r0],#0x258`).
2. **Vtable-slot artefacts** were emitted as `unknown_vtableSlotNN` at 0.0 with
   the call quoted: `Ui_NumberPane +0xD0`, `Ui_RouletteWheel
   +0xD0/+0xE0/+0x120`.
3. **Embedded sub-object at a batch field.** `Ui_MessageWindowRoot +0x3574` is
   `Ui_Object_InitMemberPair` + 8 × 0x18 state records, i.e. an embedded
   `std_StateSequence42`; `Ui_StampAnimPlayer` fields are 0x50-byte
   `Ui_AnimRefList`s; `Ui_NumberPane +0xD4` is the base of an embedded text
   element. The merger then extends the sizes to 13920 / 548 / 364, which is
   consistent with those widths.
4. **Mis-grouped clusters kept under the generated class name** (the dispatcher
   requires the batch class keys): `Ui_ScreenChild` merges six unrelated child
   ctors (bases `Ui_CompositeObject`, `Ui_ArcListWindow`, `Ui_MotionPath`, ...),
   so I cleared its base; `Ui_ModePane` looks like a fragment of
   `Ui_SlideWindow`; `Ui_PaneAnim` like a fragment of `Ui_Layout`;
   `Ui_NumberPane` merges three methods that may belong to different widgets.
5. Confidence/`maybe_` rule applied strictly: every field with 0 < confidence <
   0.5 starts with `maybe_`; every 0.0 field starts with `unknown`.

## Verification

- `python out/scratch/S_135/write_out.py` → `OK ... 23780 bytes, 45 fields, 15 classes`
  (strict UTF-8 re-decode + `json.loads`, per-class emitted offset set == batch
  offset set, no duplicate offsets/names, all types valid, naming/confidence rules).
- In-process run of the real merger (`tools.typedb.apply.Evidence` +
  `merge_structs`, nothing written): **0 issues for S_135**, 15/15 structs
  merged, 3 fields each.
- `python tests/run_all.py` and `python tools/verify_project.py` were skipped
  per WORKER_RULES rule 5 (naming batch); the required JSON syntax check above
  is the substitute.
