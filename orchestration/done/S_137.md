# S_137 — Ui class/field naming batch

## What I did

Named all 15 classes and all 30 batch fields in `orchestration/types/out/S_137.json`
(subsystem Ui). Every class keeps the generated `class`/`type`/`size`; every batch offset is
present exactly once with the batch width.

Method: read the constructor/destructor/update bodies from `decomp/readable/` for every recovered
method, checked vtable stores and base-constructor calls, then cross-checked each field against
`orchestration/types/structs.json` (neighbouring classes, field widths, vtable slots) and, where
needed, against the ARM disassembly (`tools/fn.py --asm`) and the rodata table bytes in
`asm/rodata/rodata_00725000.s`.

that every field type is a builtin, a type from `structs.json`, or a pointer to one.

## Decisions and traps

- **Sizes are lower bounds** where struct_db stopped at a strong field. I kept the batch sizes and
  documented the real minimum in the evidence: Ui_Drawable (>=0xD88), Ui_ItemSlot (panes at +0xAC),
  Ui_Event (children at +0x90/+0x94), Ui_LoopPane/3 (embedded Ui_AnimRef at +0x4C),
  Ui_LayoutPicture (4×0x20 quads at +0xA8).
- **Unknown/aliased offsets**: Ui_Event +0 (all recorded accesses are `*event`, not `self`),
  Ui_GlyphSlot +0x30 (all quoted lines access +0xC), Ui_Drawable +4 (`unaff_r7` in damaged Thumb
  code), Ui_GlyphRenderer +4 (only a zero store). These are `unknown_*` at confidence 0.0.
- **Ui_EquipPart +0x30/+0x34**: verified in rodata that 0x0072B810 is nine 8-byte `{code pointer, 0}`
  rows; the copied pair is a control-code handler pointer plus its always-zero argument/padding.
- **Ui_DirectionIndicator**: the +0x28 text-layer key and +0x98 countdown are confirmed by the
  identical 156-byte `Ui_TextBlink` layout (its +0x98 is decremented and reset to 0x1E).
- **Ui_IconRequest +0xC/+0x10**: typed `void*` rather than guessing a class; the object has a byte
  +0x94 (hidden flag), a kind byte +0x12C (1..7), and +0x12D/+0x12E frame RG values.
- **Ui_ItemGrid** is partly mis-grouped: 0x004AE4A4 is `Ui_PartyListWindow_SetVisible`. The class key
  was kept (apply.py rejects classes absent from structs.json) and the mismatch is in the summary.
- **Ui_FadeAnimator** base is `Ui_CurveAnimator` (both ctors call `Ui_CurveAnimator_Ctor`, bases_seen=4).
- Type spellings follow `structs.json` exactly (`UiGlyphQuadArray`, `UiAnimRef`, but `Ui_Widget`,
  `UiMessageWindow`); inconsistent but required by the merger.

## Open problems / not verified

- Every `maybe_*`/`unknown_*` field (13 fields below 0.5, 6 at 0.0).
- The real type of `Ui_IconRequest` +0xC/+0x10 (best candidate Ui_ListWindow, but its recorded field
  set lacks +0x94).
- Identity of the `Ui_GlyphRenderer` object (no readable export; only ctor disassembly) and its
  first argument.
- 0x00284DF8 (Ui_EquipPart handler) is not in the readable export, so the exact handler role is
  unverified.
- Whether `Ui_Event` +0xC is an embedded state sequence or a pointer to one (slot call pattern
  matches `Ui_WindowState` +0x11C).
- Purpose of `Ui_ItemSlot` +0x60 (cleared before base teardown, never read in the recovered methods).
