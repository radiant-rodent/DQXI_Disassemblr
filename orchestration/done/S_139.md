# S_139 — Ui class/field naming batch

## What I did

Named all 15 classes and all 29 batch fields in `orchestration/types/out/S_139.json`
(subsystem Ui). Every class keeps the generated `class`/`type`/`size`; every batch offset is
present exactly once with the batch width; no extra offsets were added.

Method: read the constructor/destructor/update bodies from `decomp/readable/` with
`python tools/fn.py <addr> -b <n>` for every recovered method of the batch (plus the
cross-referenced functions `Ui_TextList_UpdateMeasureState`, `Ui_TextList_CtorSmall`,
`Ui_SlotMachine_ApplySymbolAnim`, `Ui_RouletteWindow_Ctor`, `Ui_TextLayer_SetText`,
`maybe_Ui_PublishValueToManager`, `maybe_Field_Object_Ctor_vt77635C`,
`Ui_WidgetStack_PushAt/PushPositionedChild`), then cross-checked the struct_db evidence against
`orchestration/types/structs.json` and, where the readable C was ambiguous, against the ARM
disassembly in `asm/text/*.s` (only the specific address ranges of the batch functions were read,
never the whole tree).

## Decisions and traps

- **Sizes are lower bounds** where struct_db stopped at a strong field. Batch sizes were kept and
  the real minimum is stated in the class evidence: Ui_StampBookPage (3 × 0x50 anim-ref lists at
  +0x134 → 0x224), Ui_TimerDisplayPart (Ui_AnimRefList_Ctor in place at +0x4C → 0x9C),
  Ui_SubWindow2 (R3_013 allocation 0x16C), Ui_TextPager and Ui_WindowWith16Records (embedded
  sub-objects past the recorded tail), Ui_TutorialPane (handle pair at +0x4C).
- **Vtable-slot artefacts** (struct_db stores `slot*4` as a field): Ui_ThreeLineTextWindow2
  +0xE0 (`*self+0x38`) and +0x120 (`*self+0x48`), Ui_WidgetStack +0x50 (`*self+0x14`). These are
  named `maybe_vtableSlotNN` at 0.3 with the call quoted, following the S_002 precedent; the
  disassembly confirms no direct access at those offsets.
- **Ui_WindowResource +0 and +0x344 are not self fields**: the reset body writes the vtable of the
  newly allocated 0x37C-byte child (`*local_2c = ...`) and does pointer arithmetic on that same
  child (`local_2c + 0xd1`). Both are `unknown_*` at 0.0; the class evidence records the real
  holder layout seen in Reset (dirty byte +4, animators +8/+0xC/+0x10, allocator +0x18).
- **Ui_BagCategory** merges two different objects: `CountItems` reads {owner +0, entry array +4,
  count +8} while `FilterAvailable` writes a 7-byte packed category buffer (`*out = local_38`).
  The one batch offset is therefore `maybe_categoryBytes` at 0.3, with both readings quoted.
- **Ui_ValueHolder** keeps its generated name, but R3 already renamed its ctor to
  `maybe_Field_Object_Ctor_vt77635C`; the class evidence says so. The float at +0x48 is solid
  (the -1000.0f sentinel is written by the ctor and published to (work+8)->f_50->f_F8).
- **Ui_SubWindow2** is one of the two 0x16C-byte `maybe_Ui_TwoChildObject_*` children; its +0x11C
  is a `Ui_LayoutRef` because the dtor calls `Ui_LayoutRef_Release(self+0x11C)` and then recovers
  the object base by subtracting 0x11C.
- **Ui_TextPager +0x353C** is a compact `Ui_TextList`: the update calls
  `Ui_TextList_UpdateMeasureState` on it and that routine builds the page-number text in a wchar
  buffer at +0x1C and sets the flag at +0x2C. The only other batch offset (+0x3574) is a
  polymorphic embedded child driven with state 6/7; it is left as an opaque
  `maybe_pageIndicator` (u32, 0.3) because its class is not proven.
- **Ui_WindowWith16Records +0x70** was verified in the disassembly (`str r1,[r0],#0x70` then
  `bl 0x002DB7B4`): the decompiler's `self+0x1c` was a u32*-scaling artefact. The container type
  has no recovered class name, so `void*` is used as a stand-in and the 16 × 0xE4 record array is
  described in the evidence.
- **Types** follow `structs.json` spellings exactly (`UiAnimRefList`, `UiLayoutRef`, `UiTextList`,
  `UiHandlePair`, `UiTextElement`, `Ui_Widget`). Embedded objects recorded with a 4-byte access
  keep the batch width (precedent S_015/S_137) and the evidence states the real extent.
- 21 fields at confidence ≥ 0.5, 5 `maybe_*` below 0.5 and 3 `unknown_*` at 0.0.

## Open problems / not verified

- Every `maybe_*`/`unknown_*` field (9 + 3).
- The class/identity of `Ui_TextPager` +0x3574 (a polymorphic child; page indicator is only a
  guess) and the true extent of the embedded `Ui_TextList` at +0x353C (small 0x38-byte variant vs
  the 0xE4-byte `UiTextList` in structs.json).
- The identity of `Ui_ValueHolder` (R3_024 says Field scene object) and what
  (work+8)->f_50->f_F8 actually controls.
- `Ui_WindowResource`: the real holder layout is known from body accesses (+4/+8/+0xC/+0x10/+0x18)
  but two of the three batch offsets are child-object artefacts, and the class identity
  ("Ui_WindowResource" vs the UI core/window-system root reached via GameWork->f_0) is not proven.
- `Ui_WindowWith16Records`: the container class at +0x70 and the full object size (16 × 0xE4
  records imply well over 0xF10 bytes, not 0x74).
- `Ui_ThreeLineTextWindow2` has real fields (vtable +0, u16 text-id base +0x28) that the batch did
  not list; they are described in the evidence but not emitted because the batch offsets were
  kept exactly.
- `Ui_BagCategory`: which of the two merged objects the class name is meant to describe.
- `Ui_SlotSymbol` +0x4C (written 0 only, never read in the recovered methods) and
  `Ui_TimerDisplayPart` / `Ui_StampBookPage` true sizes.
- Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-up tasks

1. struct_db fix: record vtable-slot accesses as slots, not as byte offsets (`slot*4` artefacts),
   and stop scaling typed pointer arithmetic with u32* (Ui_WindowWith16Records +0x1C vs +0x70).
2. Give the `Ui_TextList` compact variant its own class (0x38 bytes, page-number buffer at +0x1C,
   flag +0x2C) instead of merging it with the 0xE4-byte text list.
3. split `Ui_BagCategory` into the category list (`CountItems`: owner/entries/count) and the
   7-byte filter result; re-batch Ui_WindowResource around the real holder fields.
4. Name the container ctor 0x002DB7B4 used by Ui_WindowWith16Records and the polymorphic child at
   Ui_TextPager +0x3574.
