## What the classes turned out to be

1. **`Ui_BattlePopup`** — battle pop-up window. `+0x204` is the object handed as the first
   argument to `Battle_PopupEntry_Create` (0x002DFDE8), which reads its `+0x1C4/+0x1C8/+0x1CC`
   entry lists and `+0x24` allocator and allocates the 0x24-byte entry; the same pointer's
   `vt[+0x18]`/`vt[+0x74]` activate and reset it. No structs.json class has those offsets, so the
   type stays `void*`.
2. **`Ui_CasinoSlotFreeSpin` / `MetalChange` / `Queen`** — three casino slot windows. Each ctor
   runs the shared `UiWindow` init 0x001A6520 and then stores
   `Ui_PlayAnimByName(self->f_4, '<name>', 0, 1, arg)` at `+0x4C`. The name accessors
   `func_0065425C/00654270/0065424C` hold the literals `freespin` / `metalchange` / `queen`, and
   0x0053D604 returns `UiAnimClip*`, so `+0x4C` is the clip.
3. **`Ui_Choice`** — choice prompt state block. `+0x10` is incremented by
   `maybe_Ui_Choice_Tick`, fires at `0x27` and is zeroed by `maybe_Ui_Choice_Confirm`.
4. **`Ui_DigitRoll`** — five-digit rolling counter (ctor 0x002D00EC installs vtable 0x00760480).
   `+0x10` drives the five digit offsets (`i*-5 + f_10`), plays SE 0xE61/0xE62 at 0 and 10 and
   completes at `0x2E`.
5. **`Ui_EquipmentDetail`** — equipment detail panel (base `Ui_Panel`). `+0x14` is stored into
   `panel+0x10CC` immediately before `Ui_Panel_ResetAndPush`, so the panel re-reads it on every
   push. The payload is never written in this batch, hence `maybe_textSource` at 0.35.
6. **`Ui_LayoutGroup`** — small layout/position entry. `+0x28` is a `Field_Actor*`: position
   `f_9C/f_A0/f_A4`, range `f_D8`, flags `f_35C/f_35D/f_300`, `vt[+0xC8]`.
7. **`Ui_LayoutParts`** — BFLYT `prt1` (Parts) pane. Ctor 0x00540340 calls
   `Ui_LayoutPane_InitFromRes` (0x005387EC) and stores vtable 0x00781650 at `+0`.
8. **`Ui_LayoutPlayer`** — layout-player factory context. `+0x24` is the object whose `vt[+0xC]`
   resolves the `blyt` resource by name and which is then passed to the player's init `vt[+0x38]`.
9. **`Ui_LayoutRequest`** — scene layout-request block. `+0x3E4` points at four 8-byte pack handle
   pairs filled by 0x002448BC (`res/model3d.bxon`, two more, `res/motion/equip.bxon`); the sibling
   `+0x3E8` is the `res/model2d.bxon` handle passed to `Ui_Model2D_LoadResource`.
10. **`Ui_ListItemRef`** — list row reference. `+0xC` selects the row table in
    `Ui_ListItemRef_ResolveRow`: 0 = bag rows `+0x5FE4` stride 0x8C, 1 = `*0x007AB814+0x6B8`
    stride 0x98, 2 = `+0x7B3C` stride 0x8C.

## Traps and decisions

1. **Three batch classes are stale struct_db groupings, not real classes.** `Ui_Handle` (its only
   method 0x001C69BC is now `maybe_Ui_Window_ScriptCommandHandlerM`, so the object is a
   `Ui_Window`: asm proves embedded child widgets at `+0x804/+0x9D8/+0xF84`, six panes hidden via
   0x0029126C and a script-state byte vector at `+0x10A8`), `Ui_InteractJob` (0x004A3B3C is the
   72-byte `Field_InteractJob` deleting destructor while 0x004A3C74/0x004A3D14 are message
   formatters reading `+0x208`) and `Ui_EnsureSharedStatic` (13 of its 14 methods are identical
   `__cxa_guard_acquire(0x007BE2D0)` stubs). The class names are kept verbatim because
   `apply.py` rejects any class that is not in `structs.json`; the summaries say plainly what the
   object really is, and the class confidences are 0.3 / 0.2 / 0.1.
2. **`Ui_EnsureSharedStatic`+0x00 is `unknown_id` at confidence 0.0.** asm 0x0069A028 is
   `strh r2,[r0]` + `str r2,[r0,#4]` + `stm r4={r2,0xff}` at `+8/+0xC`, i.e. a 16-byte record
   `{u16 id; u32 a; u32 b; u32 0xFF}` filled from the caller's arguments. Nothing identifies the
   id, so it is not invented.
3. **`Ui_LayoutParts` size raised 4 → 0xB0** because the ctor calls the 176-byte `Ui_LayoutPane`
   base ctor; base changed `Ui_AnimClip` → `Ui_LayoutPane` (the batch's `Ui_AnimClip` is the
   grandparent). All other sizes are the batch values.
4. **Width corrections:** `Ui_ListItemRef`+0xC and `Ui_InteractJob`+0x208 are declared `u8` (the
   code reads `(char)ref[3]` and `*(u8*)(self+0x208)`), not the batch's `u32`.
5. **`Ui_Handle`+0xF84 is an *embedded* `Ui_Object`** (its address is passed to
   `Ui_Object_BroadcastToChildren`) but is typed `Ui_Object*` because every struct-typed field in
   `include/dqxi/structs.h` is a pointer and an embedded 5016-byte member would break the emitted
   `sizeof`. The evidence text says so.
6. **`maybe_Ui_Layout_SetCornerGradientColors` (0x002448BC) is misnamed.** Its body is a pack
   handle loader (`*out = puVar5; Pack_HandlePair_MoveAssign(out+1, ...)`) for `res/model3d.bxon`
   (entry id 0x69D) plus three more resources; the string was verified in
   `original/exefs/code.decompressed.bin` at `VA-0x100000`. This is why `Ui_LayoutRequest`+0x3E4
   is *not* typed `Ui_Layout*` as the batch guessed.
7. **`Ui_EquipmentDetail`'s doc is wrong about `self+0x14`.** The `f_14/f_16/f_12` reads in
   `maybe_Ui_EquipmentDetail_ScrollNameB` are `PartyMember` fields (HP at `+0x14`), not self
   fields; only the `panel+0x10CC = self+0x14` store touches the class field.

## Not verified / open problems

* The payload behind `Ui_EquipmentDetail`+0x14 — only the pointer store is observed; the reader is
  the panel draw code, which is not in this batch.
* The concrete class of `Ui_BattlePopup`+0x204 — no `structs.json` class has
  `+0x1C4/+0x1C8/+0x1CC`, so it stays `void*`.
* Whether `Ui_LayoutGroup`+0x28 is `Field_Npc` rather than `Field_Actor` (the `+0x35C/+0x35D/+0x300`
  reads are clustered on `Field_Npc`, but `Field_Actor` is large enough to hold them).
* The two extra resources loaded by 0x002448BC (name literals at 0x00244BD0 / 0x00244BE8 were not
  decoded).
* `Ui_Choice`+0x04/+0x08 and `Ui_EquipmentDetail`+0x08 are real fields that are not batch offsets,
  so they are documented in the class evidence only (emitted set == batch set, matching the
  S_139/S_141/S_142/S_143/S_145/S_146 precedent).
