## Open problems / not verified

* Every `maybe_*` / `unknown_*` field, as usual.
* Ui_PanelStack, Ui_ShopItemInfo, Ui_SpriteCache and Ui_TextPane have **no real field in
  this batch**: their only batch offset is a vtable-slot artefact
  (`4 × slot offset`, because `struct_db` scaled `(**(code**)(*self+0xNN))()` by the
  pointer width). They are emitted as `unknown_*` at 0.0 so the merger pads them.
  Ui_PanelPart +0x3C is a real instruction but the dtor's r2 is undefined.
* Ui_MessageScreen +0x13C: only the state setter call is visible; the concrete class is
  unknown.
* Ui_PartyMember: the Ui_Panel base comes from two base-ctor matches; what the pane
  manager stores at its +0x10CC (address of +0x14) is not explained.
* Ui_ScreenBase +0x30 is only known as "the word the screen constructor stores at
  screen+0x11C"; no reader in this class.
* Ui_ScrollGrid's body is truncated by three `halt_baddata` sites (the row-index access
  itself is intact).
* Class roles are best-effort: Ui_PartyMember is an item-use window, Ui_PanelPart a Ui
  window dtor group, Ui_PanelStack a stage-class family; names were kept per the batch
  rule, so the mismatch lives in the evidence text.

## Suggested follow-up

1. Fix `tools/typedb/struct_db.py`: do not scale `*self + 0xNN` vtable-slot offsets by the
   pointer width (slot N must not become field 4N). This alone would remove 4 of the 5
   unknown fields in this batch.
2. Identify the Ui window class that owns secondary vtables `0x0076D6A8` / `0x0076D6E8`
   (Ui_PanelPart) by finding the matching primary vtable and the ctor that stores it.
3. Re-batch `Ui_PartyMember` around the `Ui_ItemUse_*` functions so the item-use result
   window is not named after a party-member record, and confirm its base (Ui_Panel vs
   Ui_Window) from the base-constructor address.
4. Name `func_0065D3D0`, `func_00669D88`, `func_00669DD4` (Ui_SpriteCache / Ui_SpriteMarker
   helpers) in a normal N_/R_ batch so their roles are explicit.
