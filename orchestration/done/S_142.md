# S_142 — Ui class/field naming batch

## What I did

Named all 7 classes and all 7 batch offsets in `orchestration/types/out/S_142.json`
(subsystem Ui). Every class keeps the generated `class`/`type`/`size`; every batch offset is
present exactly once with the batch width. No extra offsets were emitted (the real +0x28 text-layer
field of the pane classes is described in the class evidence instead), matching the S_141/S_139
precedent of "emitted offset set == batch offset set".

Method: read the readable C of every recovered method (constructors/initialisers/setters) from
`decomp/readable/`, checked vtable stores and base-constructor calls in the adjacent functions,
then cross-checked `orchestration/types/structs.json` (neighbouring classes, field widths, vtable
slots) and the ARM disassembly where the C was ambiguous. Used the established facts and the
S_137/S_139/S_141 outputs for naming consistency (`textLayerId` for the u16 at +0x28).

The two 0xD0 fields are **vtable-slot artefacts**: struct_db scaled the virtual pane-bind slot
`*self+0x34` by the 4-byte pointer width (0x34 * 4 = 0xD0). The ARM of 0x004AACC0 touches only
[r4] and [r4,#0x28]; 0x004C61AC does `ldr ip,[r2,#0x34]` / `blx ip`. Both are emitted as
`unknown_0xd0` at confidence 0.0 with the call quoted, exactly like S_141's Ui_TextPane.

## Open problems / not verified

- Owning screens of Ui_TextPane2, Ui_TextRows, Ui_ValueLabel are unknown.
- Whether Ui_TextRowL1 and Ui_TxtL1Window (0x004EE838) are one class or two; vtable 0x007780A8
  belongs to the two-pane initialiser 0x004C61AC only, and 0x004EE838 is a merged sibling.
- Ui_TouchFocus's +4 link is inferred as a forward node pointer from the `begin = begin[1]` walk
  (not observed being written); the focused widget is the object at node +0.
- Ui_TwoPane +0x50 is treated as an embedded Ui_AnimRef (the address is passed to Ui_AnimRef_Bind/
  SetFrame); the batch type/width follows the S_015/S_137/S_139 convention for embedded anim refs.
- Ui_WindowWith6Blocks has no caller; the six-part timer-display geometry is a match to
  0x002BBA60/0x002BB90C but the owning screen is not proven.
- All class-level confidences for the two 0xD0-only classes reflect class identification, not the
  (0.0) phantom fields. Sizes are batch lower bounds; real extents are stated in the evidence.
