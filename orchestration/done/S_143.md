### Key finding: these are not 15 heap objects
No batch function has a constructor, a vtable store or an allocation. `struct_db` keyed every
"class" off its first parameter, so the batch describes three kinds of *views*:

1. **`Video_ResidualBlockAdd` (696 / 0x2B8)** — the 8x8 luma transform-block workspace of the
   Mobiclip-style video decoder, seen by `Video_IdctBlock8x8` (0x0013BC3C `_B`, twin 0x0013563C;
   the R_058 refine kept the class name but renamed the function). The function clears the 64 signed
   coefficient words at **+0x1B8** (`add ip,r0,#0x1b8` + eight `stmia ip!,{r4-r11}`), lets the fill
   routine 0x001377A0 populate them and runs the DC-only / reduced / full 8-point integer IDCT into
   eight 0x400-spaced sample lanes of `*(void**)(ctx+0x44)`. So +0x1B8..+0x2B4 is exactly
   `s32 coeffBlock[64]` → `transformCoeff0..63` (+0x1B8 is the DC term, scaled `+0x20 >> 6`).
   +0x78 is only `add ip,r0,#0x78` (an argument address for 0x001377A0) → `unknown_78` at 0.0.

2. **`Video_ResidualBlockAdd2` (500 / 0x1F4)** — the 4x4 chroma counterpart
   (`Video_IdctBlock4x4`, 0x0013BDE8 / 0x001357E8): 16 coefficient words at +0x1B8, 4-point
   butterflies, four sample lanes. → `transformCoeff0..14`; +0x178 → `unknown_178` at 0.0.

3. **`Video_FilterRgbaWord4` (1044 / 0x414)** — not a struct at all: the packed-word sample plane
   read by `Video_FilterPackedBytesWord4` (0x0013E924 / 0x00144F24). The 1:2:1 filter masks
   `0x7F7F7F7F`, halves and recombines the carry and walks `arg1 += 0x80` per two rows while
   `param_1[0x40]` is the next row → **0x100-byte row pitch**. The 19 offsets are only the accessed
   words of rows 0/1/2/4 → `row0Word1..4`, `row1Word0..4`, `row2Word0..4`, `row4Word0..4`.

4. **`Video_McPredict{1,2,3}ApplyMv{,2,3,4}`** (12 classes, all 964 / 0x3C4) — twelve identical
   field views of one shared motion-compensation context (the readable C already calls it
   `McCtx*`): +0x0C = first of the luma frame-plane pointers (`*(int*)(self + blockOffset + 0xc) +
   x + (mvY>>1)*0x100 + (mvX>>1)` is the subpel filter's arg1, `self->f_c + x` its arg2), +0x24 =
   chroma counterpart (two calls 0x80 apart for the two components), +0x3BC/+0x3C0 = accumulated
   X/Y **motion-vector predictor** (ReadMv adds the decoded delta, ApplyMv reuses it; `>>1`/`>>2`
   give luma/chroma offsets, `&7`/`&1` the subpel phase). The leading digit is the filter variant
   (luma subpel banks 0x4A10 → 0x5568 → 0x5A5C → 0x5CEC, chroma one bank further); the 2/3/4 suffix
   is the chained block emission (wrappers pass r5 = 0x04/0x08/0x0C/0x10 block offset and
   r6 = 0x10/0x08/0x04/0x02 size).

## Open problems / not verified

* Which frame slot each `+0x0C`/`+0x24` entry is (reference vs current picture, ring size) is not
  proven — hence `lumaFramePlane`/`chromaFramePlane` (`void*`, 0.6), not `referenceFrame`.
* Meaning of `+0x78` / `+0x178` and of the callee 0x001377A0: 0x001377A0 has no readable export;
  both offsets are therefore `unknown_*` at 0.0 (argument addresses, not members).
* Two coefficient words of the 8x8 block (0x1F4, 0x258) and the 16th 4x4 word (0x1F4) are **not**
  in the batch: Ghidra emitted those zeroing stores as decimal `*(u32*)(param_1 + 500)` /
  `+ 600`, which `struct_db` does not read as field offsets. I documented the gap in the class
  evidence and left them out so the emitted offset set stays equal to the batch (the merger would
  pad them anyway).
* Whether the 8x8 coefficient block at +0x1B8 and the McPredict plane pointers at +0x0C really
  belong to one object is unproven: `Video_DecodeCoefficientBlock` also shows a +0x3C4-based alias
  of the same array, so the two views may not share a base.
* The filter-bank/step mapping of the 2/3/4 copies comes from the existing R_058/E3 oracle docs,
  not re-derived from disassembly here.
* Nothing was compiled, exported or emulator-tested — static naming only.

## Suggested follow-up

1. Give `struct_db` a fix for **decimal-form offsets** (`param_1 + 500`): it silently drops real
   array elements from batches (hit here three times).
2. Give the video decoder one real `VideoDecoderContext` struct (merge the 12 `McCtx` slices plus
   the `+0x0C`/`+0x24`/`+0x44` plane pointers) instead of 12 duplicated pseudo-classes; same for a
   `VideoCoefficientBlock8x8` / `4x4` type so the 64 words become one array member.
3. Re-batch the `Video_FilterRgba*` family as *buffers*, not classes (the whole family, see
   `Video_FilterRgbaBlock*` / `Frame` already in `structs.json`, has the same artefact).
4. Identify 0x001377A0 (coefficient/residual fill) and the two `+0x78` / `+0x178` sub-structures.
