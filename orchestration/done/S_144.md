# S_144 — Video struct/field naming batch

## What I did

Named all 10 classes and every offset of `orchestration/types/batches/S_144.json`
(Video subsystem, 31 fields) in `orchestration/types/out/S_144.json`, keeping the generated
class names/types/sizes/bases exactly as the batch supplied them.

The batch contains two very different groups:

1. **`Video_McPredict4ApplyMv`, `…2`, `…3`, `…4`** (964 bytes each) — four views of the *same*
   shared motion-compensation context (`McCtx`) that the readable C already names:
   - `+0x0C` `lumaFramePlane` (`void*`, 0.6): first of the luma frame-plane pointers. Filter arg1 is
     `*(int *)(self + blockOffset + 0xc) + x + (mvY>>1)*pitch + (mvX>>1)`; the wrappers pass
     blockOffset 0x04/0x08/0x0C/0x10/0x14.
   - `+0x24` `chromaFramePlane` (`void*`, 0.6): the chroma counterpart (both chroma calls, 0x80 apart).
   - `+0x3BC` `motionVectorX` (`s32`, 0.8) and `+0x3C0` `motionVectorY` (`s32`, 0.8): the stored
     X/Y predictor. ApplyMv reuses it, ReadMv (0x00133FB4) adds the freshly decoded delta; `>>1`/`>>2`
     give luma/chroma sample offsets and `&3`/`&1` the variant-4 subpel phase.
   Addresses: class 1 = 0x0013A6F4 / 0x00140CF4; class 2 = 0x0013B22C (now
   `maybe_Video_McPredict4ApplyMvCopy2_B`) / 0x0014182C; class 3 = 0x0013B338 / 0x00141938;
   class 4 = 0x0013B43C / 0x00141A3C. B copies use a 0x100 row pitch, C copies 0x200, base A-track
   0x001340F4 0x400.
   Field names and confidences are deliberately identical to the S_143 McCtx slices.

2. **The six `Video_FilterRgba*` entries are not classes.** Each groups the B and C copies of a
   packed-byte 1:2:1 video post-filter kernel; the R3 sweep has since renamed them
   `Video_FilterPackedBytesBlock2 / Frame / Word4d / Block / Word4b / Word4c`. The raw Ghidra
   signature is `void FUN(byte*/ushort* param_1, int *param_2, int param_3)`: `param_1` is the source
   frame buffer, `param_2` the destination and `param_3` the row-pair count. They mask with
   0x7F7F7F7F so the average cannot carry between the four packed byte lanes (Mobiclip-style decoder
   region 0x0013xxxx). The recorded offsets are source-frame sample positions, not members:
   - Block2 / Frame: 0x34 → byte 0x0D (`row0Word3`), 0x404 → byte 0x101 (`row1Byte1`),
     0x804 → byte 0x201 (`row1Byte1Wide`, C copy).
   - Word4d: 0x1C → byte 0x0E (`row0Word3`), 0x204 → byte 0x102 (`row1Byte2`),
     0x404 → byte 0x202 (`row1Byte2Wide`).
   - Block: 0x204 → byte 0x102, 0x404 → byte 0x202.
   - Word4b: 0x0B → `row0Word2` (word bytes 0x08..0x0B), 0x0F → `row0Word3HighByte`.
   - Word4c: 0x0B → `row0Word2` (unaligned window bytes 0x0B..0x0E), 0x0F → `row0Word3HighU16`.

## Decisions / traps

- **struct_db offset-scaling bug**: for the `byte*`/`ushort*` filters the generator multiplied the
  pointer index by 4, so batch offsets are 4 × the true byte offset (e.g. 0x404 → byte 0x101).
  For Word4b/Word4c the first parameter is a bare `int` base, so 0x0B/0x0F are true byte offsets.
  Every evidence string states both numbers so the merge keys stay intact. This is the same class
  of artefact as the S_141/S_143 vtable-slot offsets.
- The filter fields are named by their provable source-frame position and say explicitly "not a
  struct member"; no `unknown_*` was needed.
- Generated class names are kept even where the functions were renamed, and the current symbol
  names are quoted in the class evidence for cross-reference.
- Sizes stay at the batch values (max_strong_field+width) even though they are artefacts of the
  phantom offsets; the true address extent is in the evidence.
