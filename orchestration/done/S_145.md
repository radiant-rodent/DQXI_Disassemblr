## What the classes turned out to be

All 15 are instances of the same **`std::StateSequence` fixed-state machine template** that
N_122, N_123, N_124 and R_081 already recovered and that the sibling worker S_146 named for
`std_StateSequence15..30`. Each object embeds one dispatch table (six slots:
`Delete, Tick, event dispatch, ChangeState, QueueState, SetState`) and an inline array of state
records plus the owner's transition callback:

```
+0x00  vtable                                  (batch value; six std_StateSequenceNN_* slots)
+0x04  u32 current state id                    (real, not a batch offset)
+0x08  f32 elapsedTime                         (vadd.f32 / vstr s0,[r4,#8])
+0x0C  u32 frameCount                          (incremented per tick, zeroed on transition)
+0x10  f32 deltaTime                           (vstr s0,[r4,#0x10])
+0x14  u32 pendingState[2]                     (real, not a batch offset)
+0x1C  u32 pendingStateCount
+0x20  void* callbackTarget                    (this-base for the state PMFs)
+0x24  state records, n x 0x18 or 0x40
+n*stride+0x24  transitionCallback + transitionCallbackThisAdjust
```

I verified the arithmetic `0x24 + n*stride == callback offset` for every class; that also fixes
the state count per class:

## Decisions (things the orchestrator could not answer)

1. **Batch offsets 0x40 and 0x50 are not real fields.** Their only evidence is
   `(**(code**)(*param_1 + 0x10))` / `+ 0x14`, i.e. a vtable-slot byte offset multiplied by 4 by
   the u32-pointer scaling in `tools/typedb/struct_db.py` (the comment at
   `struct_db.py:281` documents exactly this scale). In every class these addresses also fall
   inside the embedded state-record array. They are emitted as `unknown_0x40` / `unknown_0x50` at
   confidence 0.0 with that reason, matching S_146 — no invented purpose.
2. **No extra offsets were added.** +0x04 (current state id), +0x14 (pending-state stack) and the
   transition-callback *code* word (absent from the batch for 06/26/41 because Ghidra reads it as
   raw pointer arithmetic) are real but are documented in the class `evidence` only, following the
   S_139/S_141/S_142/S_143/S_146 precedent that the emitted offset set equals the batch set.
3. **Width corrections:** +0x08 and +0x10 are `f32`, not the batch's `u32`; the asm shows
   `vldr/vadd.f32/vstr s0` and the `0.0f` store in `ChangeState`.
4. **`stateZeroExitCallback` / `stateZeroExitCallbackThisAdjust`** exist only in the single-state
   0x40 variants (06, 26, 41). Their asm reads the pair directly (`ldr r2,[r4,#0x2c];
   ldr r0,[r4,#0x30]; ldr r3,[r4,#0x20]; add r0,r3,r0,asr#1; blx r2`, guarded by the old state
   id being 0); the multi-state classes reach the same words through the indexed record pointer,
   so the batch generator did not see them and they stay out of those classes.
5. **Class names and `type` kept exactly as generated** (`std_StateSequenceNN`, and
   `stdStateSequence41` for 41) because that is what `structs.json` and the readable signatures
   already use; stripping underscores would split the existing C type.

## Honest gaps / not verified

* **What each state means is unknown.** The machine is recovered, not the vocabulary; no state
  handler was named. `summary` says only "n-state machine", the owner and the transition rule.
* `callbackTarget` (+0x20) is proven to be the `this` base of the state PMFs, but it is not proven
  whether it points at the sequence itself or at the embedding owner (0.7, same as S_146).
* The payload words of the 0x40-byte state records were not decoded; that is why +0x40/+0x50 stay
  `unknown_*` (they could be payload that no recovered function reads directly).
* Owner addresses are quoted from the readable-C docs; for 04 two sibling sources disagree
  slightly (`Monster_EcologyCoSubCtor` 0x00330F40 in N_123 vs 0x00331000 in G_034) and I kept
  N_123's value. The vtable address and slot names are facts either way.
* Everything is static. Nothing was compiled, exported or emulator-tested.
