# S_146 - struct field naming: std_StateSequence15..30

## What I did

Named all 15 classes and every one of the 135 batch offsets in
`orchestration/types/batches/S_146.json`, writing `orchestration/types/out/S_146.json`.
All 15 classes are instances of the same **`std::StateSequence`** fixed-state-machine
template family; the field layout was recovered from the readable C *and* the ARM
assembly of the two functions every class shares (the `_ChangeState` and `_Tick`
family) and cross-checked on both template variants:

* `std_StateSequence15_ChangeState` 0x006CC17C, `_Tick` 0x006CC3A4 (0x18-byte records)
* `std_StateSequence21_ChangeState` 0x006CD488 (0x40-byte records, verified in asm)

Recovered layout (offsets are bytes from the object base):

| offset | meaning | type | conf |
|---|---|---|---|
| 0x00 | vtable (not in the batch) | - | - |

## Decisions (recorded, no orchestrator to ask)

1. **`type` kept as `std_StateSequenceNN`** (with underscores), not `stdStateSequenceNN`.
   That is the type name the readable tree already prints in signatures and the value in
   `structs.json` for these classes (`source: "type"`); stripping the underscores would
   break existing usage. The instruction "type is the same without underscores" was
   written for `Ui_GaugeWindow`-style names; the `std_` family already exists without a
   unique typedef, so the C type was not renamed.
2. **Only the batch offsets are emitted** (no extra +0x00/+0x04/+0x14 entries).
   `+0x04` (current state id) and the pending stack at `+0x14` are real and described in
   the class-level `evidence`; adding them would only generate "no access evidence"
   warnings and would deviate from the batch contract. Precedent: S_139/S_141/S_142/S_143.
3. **`unknown_0x40` / `unknown_0x50` at confidence 0.0 in all 15 classes.** These batch
   offsets have `reads=0, writes=0` and their only evidence is
   `(**(code**)(*param_1 + 0x10))` / `+ 0x14` - i.e. vtable slot bytes 0x10/0x14 scaled
   by the u32 pointer width. They also fall inside the embedded state-record array, which
   is only reached through the computed record index. No purpose was invented.
4. `+0x08` and `+0x10` were corrected from the batch's `u32` to `f32` (VFP
   `vldr`/`vstr` in `_Tick`).
5. `+0x20` is `callbackTarget` (void*), confidence 0.70: the asm proves it is the base
   the pointer-to-member this-adjustment is added to before every state call.

## Open problems / not verified

* The meaning of the two `unknown_0x40`/`unknown_0x50` words is unknown; they may be
  payload words of state record 0/1 that no recovered function reads directly.
* Whether `callbackTarget` (+0x20) points at the sequence itself or at the embedding
  owner object is not proven (it is only used as a PMF `this` base).
* The payload layout of the state records beyond the three member-function-pointer
  pairs (enter / exit / can-enter) is not decoded.
* The semantic meaning of the individual states of each machine is not named here
  (only the count/stride is established).
* Nothing was compiled, exported, or emulator-tested - static naming only.

## Suggested follow-up

* Fix `struct_db` so a vtable slot dispatch `(**(code**)(*self + N))()` is not recorded
  as field offset `4*N` (this produced the phantom 0x40/0x50 fields, and the same bug is
  noted in S_141/S_142/S_143).
* Batch the +0x24 state-record array explicitly (offset, PMF pair, payload) if a batch
  generator can express arrays; current batches only carry the object head and tail.
* Identify the callers of the unnamed slot 2 (`can-enter`, e.g. 0x006CC3F0) and slot 4
  (`pending push`, e.g. 0x006CC2F0) in each class so the template's exact API can be
  documented once for the whole family.
