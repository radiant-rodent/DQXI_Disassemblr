# S_147 - struct field naming: std_StateSequence31..38, 40, 42, 43, 46, 47, 48, 50

## What I did

Named all 15 classes and all 135 batch offsets in
`orchestration/types/batches/S_147.json`, writing `orchestration/types/out/S_147.json`.
All 15 classes are further instances of the same **`std::StateSequence`** fixed-state-machine
template family already handled by S_146 (05..30). The field layout was recovered from the
readable C and the ARM body comments of the two functions every class shares
(`_ChangeState` and `_Tick`) and cross-checked against the class sizes:

* Every class has the same head layout; only the record stride, the state count and
  therefore the size differ.
* For every class the generator asserts `0x24 + stateCount*recordStride == callbackOffset`
  and `callbackOffset + 8 == objectSize` - all 15 hold exactly (`check.py` re-checks the
  batch offsets/sizes, `merge_check.py` re-checks the merged structs).

Recovered layout (bytes from the object base; batch offsets only are emitted):

| offset | meaning | type | conf |
|---|---|---|---|
| 0x00 | vtable (not in the batch) | - | - |

| 0x10 | delta time of the last `_Tick` (write-only here) | f32 | 0.80 |
| 0x14.. | pending-state stack; id read as `*(u32*)(self + count*4 + 0x10)`, first slot +0x14 | - | - |
| 0x1C | pending-state stack depth | u32 | 0.85 |
| 0x20 | object used as `this` for the state member functions (PMF this-adjustment base) | void* | 0.70 |
| 0x24.. | state record array: enter PMF, exit PMF, can-enter PMF + payload | - | - |
| N-8 | owner's state-changed callback, pointer half of a member-function pointer, `(*cb)(target, oldId, newId)` | `void (*)(void)` | 0.75 |

## Decisions (recorded; no orchestrator to ask)

1. **`type` kept as `std_StateSequenceNN`** (with underscores), matching the value in
   `structs.json` and the sibling batch S_146. Stripping the underscores would introduce a
   typedef name that no other class's field references, and the readable tree already uses
   the underscored type in signatures.
2. **Only the batch offsets are emitted** (no extra +0x00/+0x04/+0x14 entries). The current
   state id (+0x04) and the pending stack (+0x14) are real and are described in the
   class-level `evidence`; adding them would produce "no access evidence" warnings and
   deviate from the batch contract (same decision as S_139/S_141/S_142/S_143/S_146).
3. **`unknown_0x40` / `unknown_0x50` at confidence 0.0 in all 15 classes.** Their batch
   entries have `reads=0, writes=0`; the only evidence is the vtable slot dispatch
   `(**(code**)(*param_1 + 0x10))` / `+0x14`, i.e. slot bytes 0x10/0x14 scaled by the u32
   pointer width. They also fall inside the embedded state-record array, which is only
   reached through the computed record index. No purpose was invented.
4. `+0x08` and `+0x10` corrected from the batch's `u32` to `f32` (VFP `vldr`/`vstr`;
   `+0x10` is the dt argument stored as `in_s0`).
5. `+0x20` typed `void*` at confidence 0.70: the asm proves it is the base the
   pointer-to-member this-adjustment is added to before every state call, not whether it
   points at the sequence itself or at the embedding owner.
6. Class confidence 0.65 (weakest important field is `transitionCallbackThisAdjust` 0.65).

## Open problems / not verified

* The purpose of the two `unknown_0x40`/`unknown_0x50` words is unknown; they may be
  payload words of state records 0/1 that no recovered function reads directly.
* Whether `callbackTarget` (+0x20) points at the sequence itself or at the embedding owner
  object is not proven (only used as a PMF `this` base).
* The payload layout of the state records beyond the PMF pairs (enter/exit/can-enter) and
  the semantic name of each individual state are not decoded.
* The owner names for 33/34/38 come from the class dossiers (child-object factories);
  those factories allocate 0xAC-byte children whose vtable *symbol* is 4 bytes before the
  batch's first-slot address (Itanium offset-to-top/typeinfo word) - this is consistent
  with 40..50, but was not re-checked in the executable image.
* Nothing was compiled, exported or emulator-tested - static naming only.

## Suggested follow-up

* Fix `struct_db` so a vtable slot dispatch `(**(code**)(*self + N))()` is not recorded as
  field offset `4*N` (source of the phantom 0x40/0x50 fields; same bug as S_141/S_142/S_143).
* Batch the +0x24 state-record array explicitly (offset, PMF pair, payload) so the state
  tables become readable instead of being padding.
* Name the two unnamed vtable slots (slot 2 = can-enter, slot 4 = pending push) once for
  the whole family, and decode each machine's individual state ids for the classes whose
  owner names are now known (e.g. Ui_ProfileScreen_Ctor, Ui_ArcListWindow_CtorParts).
