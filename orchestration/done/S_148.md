## What the classes are

All 15 are further instances of the same **`std::StateSequence`** fixed-state-machine
template family already handled by S_145/S_146/S_147/S_149/S_150. Each object embeds a
table of `N` state records (enter/exit/can-enter member-function pairs plus payload) and
the embedding owner's state-changed callback. The vtable is installed by the *owner's*
constructor, not by a constructor of the sequence itself - which is why `struct_db` never
saw a write at offset 0 and the batch has no offset-0 field.

Recovered layout (bytes from the object base; **only batch offsets are emitted**):

| offset | meaning | type | conf |
|---|---|---|---|
| 0x00 | vtable (not in the batch) | - | - |
| 0x04 | current state id (not in the batch) | u32 | - |
| 0x08 | seconds spent in the current state, accumulated by `_Tick` (`vadd.f32`) | f32 | 0.90 |
| 0x0C | frame counter, +1 per `_Tick`, zeroed on a transition | u32 | 0.90 |
| 0x10 | delta time of the last `_Tick` (write-only here) | f32 | 0.80 |
| 0x14..0x18 | pending-state stack (2 slots); id read as `*(u32*)(self + count*4 + 0x10)` | - | - |
| 0x1C | pending-state stack depth | u32 | 0.85 |
| 0x20 | object used as `this` for the state member functions (PMF this-adjust base) | void* | 0.70 |
| 0x24.. | state record array: enter PMF, exit PMF, can-enter PMF + payload | - | - |
| N-8 | owner's state-changed callback, `(*cb)(target, oldId, newId)` | `void (*)(void)` | 0.85 |
| N-4 | this-adjustment half (bit 0 = virtual flag, `adj>>1` added to 0x20) | u32 | 0.80 |

## What I verified (and how)

1. **Batch contract** - emitted offset set equals the batch offset set exactly for all 15
   classes (no missing, no extra, no duplicates); class sizes equal the batch sizes.
2. **State counts / strides** - parsed each class's own `_ChangeState` body: the reject
   bound (`0x1a < uVar4` => 27 valid ids), the index bound (`uVar6 < 0x1b`) and the record
   stride (`self + state * 0x18`) agree with the summary for all 15. Classes 64 (0x30) and
   66 (0x40) genuinely use a wider record than the rest - confirmed in their bodies.
3. **Vtable addresses** - all 15 class-level vtable addresses in the output match
   `structs.json` / the batch (0x0075A964, 0x0075A988, ... 0x0075AC10).
4. **Owners** - the `Owner:` line of each recovered `_ChangeState` doc header matches the
   owner named in each summary, all 15.
5. **No copy-paste errors** - every `transitionCallback` / `transitionCallbackThisAdjust`
   evidence string quotes that class's *own* offset (checked all 30).
6. **Field semantics** - read `std_StateSequence51_Tick` (0x006C577C): `vstr s0,[this+0x10]`,
   `vadd [this+8]`, `++[this+0xC]` confirm `deltaTime` / `elapsedTime` / `frameCount`, and
   `ChangeState` zeroes +0x08/+0x0C on a transition.
7. **Phantom offsets** - batch offsets 0x40/0x50 have `reads=0, writes=0`; their only
   evidence is `(**(code**)(*param_1 + 0x10))` / `+0x14`, i.e. vtable slot bytes 0x10/0x14
   scaled by the u32 pointer width. They lie inside the state-record array. Emitted as
   `unknown_0x40` / `unknown_0x50` at confidence 0.0 with the reason - no purpose invented.
8. **Real merger** - in-process `tools.typedb.apply.Evidence` + `merge_structs` +
   `emit_struct` (writes nothing): 15 structs, 135 fields, **0 issues**, and
   `lastFieldEnd == size` for every class.

## Decisions (recorded; no orchestrator to ask)

1. **Did not rewrite the previous worker's JSON.** It passed every check I could construct,
   including the real merger. Rewriting would have risked regressing verified evidence.
2. **Only the batch offsets are emitted** (no extra +0x00 vtable / +0x04 current state id /
   +0x14 stack entries). This is the established family convention (S_145/S_146/S_147/S_149/
   S_150) and the batch contract. Consequence: the generated struct starts with
   `u8 _pad_000[0x8]`, so the vtable pointer and current state id are padding rather than
   named members. The vtable address is still recorded at class level in `structs.json`, so
   the information is not lost. Flagged as a follow-up below.
3. **`unknown_0x40` / `unknown_0x50` at confidence 0.0** rather than inventing a purpose,
   matching S_146/S_147/S_149/S_150.
4. **`type` kept as `stdStateSequenceNN`** exactly as generated and as `structs.json` uses it.
5. **`base` left `null`**: all 85 `std_StateSequence*` classes in `structs.json` are flat
   (`base: None`); there is no shared base class to inherit from, and inventing one would
   make `apply.py` reject the entry.
6. **`void (*)(void)` kept for the callback** even though the emitter renders it as invalid C
   (`void (*)(void) transitionCallback;`) - see open problems. Changing it to `void*` here
   would diverge from the family vocabulary over a bug in a file I do not own.

## Open problems / not verified

* **`apply.py` emits invalid C for function-pointer fields.** `emit_struct` does
  `decl = f"{ftype} {name}"`, so a field typed `void (*)(void)` becomes
  `void (*)(void) transitionCallback;` instead of `void (*transitionCallback)(void);`.
  This affects S_147/S_149/S_150 and every other batch that used the task-sanctioned
  `void (*)(void)` type. `include/dqxi/structs.h` is currently a 509-byte stub, so the bug
  is latent - it will surface on the next full `--merge`. **Not fixed**: `tools/typedb/
  apply.py` is outside my ownership.
* The purpose of the two `unknown_0x40`/`unknown_0x50` words is unknown; they are almost
  certainly payload words of state records that no recovered function reads directly.
* Whether `callbackTarget` (+0x20) points at the sequence itself or at the embedding owner
  is not proven - it is only ever used as a PMF `this` base.
* The payload layout of the state records beyond the PMF pairs, and the semantic name of
  each individual state, are not decoded.
* The owner names for 59/62/65/66/68/69/70 are `maybe_` in the readable tree; I confirmed
  they match the recovered doc headers but did not re-derive them from the constructors.
* Nothing was compiled, exported or emulator-tested - static naming only.

## Suggested follow-up

* Fix `emit_struct` in `tools/typedb/apply.py` to place the field name inside the
  function-pointer declarator (`void (*name)(void)`), then re-run `--merge`.
* Fix `struct_db.py` so a vtable slot dispatch `(**(code**)(*self + N))()` is not recorded
  as field offset `4*N` - this is the source of the phantom 0x40/0x50 fields in every
  `std_StateSequence` batch (same bug as S_141/S_142/S_143/S_147).
* Batch the +0x24 state-record array explicitly (offset, PMF pair, payload) so the state
  tables become readable instead of padding, and batch offset 0x00/0x04 for this family so
  the vtable pointer and current state id stop being `_pad_000`.
* Decode the individual state ids for the classes whose owners are now known
  (Ui_InitWindowManager, Ui_BoushiShopWindow_Ctor, Ui_ShopWindow_PartCtor,
  Ui_ListWindow_CtorMain, Ui_DiveForm_DerivedCtor, Ui_DiveStartWindowPart_Ctor).
