# S_149 - struct field naming: std_StateSequence09, 45, 71-74, 76-81, 83-85

## What I did

Named all 15 classes and all 133 batch offsets in
`orchestration/types/batches/S_149.json`, writing `orchestration/types/out/S_149.json`.
All 15 are further instances of the same **`std::StateSequence`** fixed-state-machine
template family already covered by S_145 (01..14, 26, 41), S_146 (15..30) and
S_147 (31..38, 40, 42, 43, 46, 47, 48, 50). The layout was taken from the readable C
headers/body of the two functions every class shares (`_ChangeState`, `_Tick`, written by
N_122/N_123/N_124), the batch field evidence, and the arithmetic between the recorded size,
the state count and the record stride:

* Every class has the same head layout; only the record stride, the state count and
  therefore the size differ.
* For every class with the adjust word: `0x24 + stateCount*recordStride == callbackOffset`
  and `callbackOffset + 8 == objectSize` - all 13 hold exactly.
* For 09/45: `0x24 + 15*0x18 = 0x18C` and `0x18C + 4 == 0x190` (see decision 5).

## Decisions (recorded; no orchestrator to ask)

1. **`type` kept as `std_StateSequenceNN`** (with underscores), matching `structs.json` and
   S_145/S_146/S_147. That is also the type the readable tree already uses in signatures;
   stripping underscores would split the typedef. Class names kept exactly as generated.
2. **Only the batch offsets are emitted** (no extra +0x00/+0x04/+0x14 entries). The current
   state id (+0x04) and the pending stack (+0x14) are real and are described in the
   class-level `evidence`; adding them would deviate from the batch contract (same decision
   as S_139/S_141/S_142/S_143/S_145/S_146/S_147).
3. **`unknown_0x40` / `unknown_0x50` at confidence 0.0 in all 15 classes.** Their batch
   entries have `reads=0, writes=0`; the only evidence is the vtable-slot dispatch
   `(**(code**)(*param_1 + 0x10))` / `+0x14`, i.e. slot bytes 0x10/0x14 scaled by the u32
   pointer width. They also fall inside the embedded state-record array, which is only
   reached through the computed record index. No purpose was invented.
4. `+0x08` and `+0x10` corrected from the batch's `u32` to `f32` (VFP `vldr`/`vstr`;
   `+0x10` is the dt argument stored from `s0`). Verified in the asm of
   `std_StateSequence71_Tick` (0x006D10EC) and the header of every `_ChangeState`/`_Tick`
   notes the same body is emitted for all 53 sequences.
5. **09/45 have no `transitionCallbackThisAdjust` in the batch.** Their `_ChangeState`
   reads the encoding word at `*(u32*)(self + 400)` (= +0x190) in addition to the pointer
   at +0x18C, so the real object is at least 0x194 bytes; the batch records only +0x18C and
   sizes the class 0x190. I kept the batch size and the batch offset set and stated the
   missing word in both class `evidence` entries instead of adding an offset the batch does
   not contain. A later batch/struct_db fix should emit +0x190 and size 0x194.
6. `+0x20` typed `void*` at confidence 0.70: the code proves it is the base to which the
   pointer-to-member this-adjustment (`encoding>>1`) is added before every state call, not
   whether it points at the sequence itself or at the embedding owner.
7. Class confidence 0.65 = the weakest important field (`transitionCallbackThisAdjust`
   0.65), like the sibling batches.

## Open problems / not verified

* The purpose of the two `unknown_0x40`/`unknown_0x50` words is unknown; they may be
  payload words of state records 0/1 that no recovered function reads directly.
* Whether `callbackTarget` (+0x20) points at the sequence itself or at the embedding owner
  object is not proven (only used as a PMF `this` base).
* The payload layout of the state records beyond the PMF pairs (enter/exit/can-enter) and
  the semantic name of each individual state are not decoded.
* The 09/45 size is almost certainly 0x194, not the batch's 0x190; not "fixed" because the
  offset is outside the batch.
* Owner names come from the N_122/N_123/N_124 readable headers (vtable store sites); the
  factory-to-vtable-symbol relationship (symbol 4 bytes before the batch's slot-0 address,
  Itanium offset-to-top/typeinfo) was not re-checked in the executable image.
* Nothing was compiled, exported or emulator-tested - static naming only.
