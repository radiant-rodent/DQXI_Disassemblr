# S_151 - struct field naming: std_FixedString31, std_WString

## What I did

Named both classes and all batch offsets in `orchestration/types/batches/S_151.json` (subsystem: std), writing `orchestration/types/out/S_151.json`.
Both classes are standard string template implementations from the game's CRT / utility library:

1. **`std_FixedString31`** (size 36 = 0x24 bytes, type `stdFixedString31`):
   - Fixed-capacity 31-character NUL-terminated string used across model attachment points (`Model_Attach_InitPointNames` 0x0068C710), weapon equip attachment (`Model_Equip_AttachWeaponNode` 0x003F3B08, `Model_Equip_AttachItemSlot` 0x0040B7A8), and effect parts (`Gfx_EffectPart_BindByName` 0x005F56A0).
   - Constructor `std_FixedString31_Ctor` (0x006F4528) installs rodata pointer `0x00782750` at +0, clamps `strlen(src) + 1` to 0x1F (31 chars), copies via `memcpy(out + 4, src, n)`, appends NUL terminator at `out[4 + n] = 0`, and overwrites the vtable pointer with `0x00782534` (slot 0 is no-op `0x00572C48`). Default constructor at 0x006F45A0 writes byte 0 at `out + 4` and installs `0x00782534` at `out + 0`.
   - Size is 36 bytes (0x24): 4 bytes header + 32 bytes inline character buffer. In `Model_Attach_InitPointNames` (0x0068C710), three consecutive instances are constructed at `0x007C50B4` ('L_Weapon'), `0x007C50D8` ('R_Weapon'), and `0x007C50FC` ('Shield'), establishing an exact array stride of `0x24` (36 bytes).
   - Offset +0x00 is named `vtable` (`void*`, conf 0.85).

2. **`std_WString`** (size 4 bytes shared header, type `std_WString`):
   - Common header/base of the fixed-capacity wide string template family (`FixedWString<N>`).
   - Format constructors and initializers (`std_WString_FormatCtorA..I` at 0x006F0CE4..0x006F0F24, `std_WString_FormatInitA..E` at 0x00707C24..0x00707CB4) each install a distinct rodata class/vtable word at +0x00 (`0x007820A0` for capacity 10 in `FormatCtorA`, `0x007820F0` for capacity 3 in `FormatCtor3`, `0x00782130` for 8, etc.), clear the wide character at +4 (`*(u16*)(out + 4) = 0`), and format arguments into `out + 4` using `std_vswprintf` (0x001001FC).
   - Callers pass `result + 4` to text display methods (e.g. `Ui_TextLayer_SetText` in `Ui_ItemRows_RefreshRows`).
   - Offset +0x00 is named `vtable` (`void*`, conf 0.80).

## Decisions (recorded; no orchestrator to ask)

1. **Strict adherence to batch offset parity**:
   The previous worker draft included an extra field at offset 4 (`text: char[32]`) for `std_FixedString31`. However, offset 4 was not part of `orchestration/types/batches/S_151.json` or `structs.json`. Emitting extra offsets produces `offset has no access evidence; kept as worker hypothesis` warnings in `apply.py` and causes offset parity assertion failures in automated batch validators. Following precedent in S_139, S_141, S_142, S_143, S_145, S_146, S_147, and S_149, only the batch offsets (offset 0 in both classes) were emitted in `fields`. The merge emitter cleanly generates `u8 _pad_004[0x20]` padding from offset 4 to 36, and the 32-byte inline buffer is thoroughly documented in the class summary and evidence.
2. **`std_FixedString31` size raised 4 -> 36 (0x24)**:
   The batch size was 4 based only on `max_strong_field+width`. The 36-byte size is conclusively proven by the array of 3 consecutive instances at `0x007C50B4`, `0x007C50D8`, `0x007C50FC` in `Model_Attach_InitPointNames` (stride 0x24 = 36 bytes) and the constructor's 31-character clamp + null byte buffer layout at `out + 4`.
3. **`std_WString` size kept at 4**:
   `std_WString` represents the polymorphic base/header of the `FixedWString<N>` family. Its format methods format into `out + 4` with various capacities (3, 4, 10, 16, 32, 128, 256). Its common struct size is 4 bytes.
4. **Types and class names**:
   Maintained exact match with `structs.json` (`std_FixedString31` / `stdFixedString31` and `std_WString` / `std_WString`).
