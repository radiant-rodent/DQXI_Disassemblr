# VG_014 — second naming pass (170 functions)

## Result

- Functions answered: 170 of 170 (`python tools/gapfill.py VG_014 --check` -> `170 answers, 0 problem(s)`).
- Variables named: 671 (parameters and locals).
- Variables deliberately left out: 0 — every row the tool listed received a name.

Naming followed the requested lowerCamelCase scheme. Names already listed as used by the tool were
never reused, and no function received two variables with the same name.

## Where names are weak

A handful of bodies are damaged or register-driven; those entries were given a confidence below 0.5
and every name in the entry carries the `maybe_` prefix, as required:

- `0x0024039C` maybe_Ui_CasinoWindow_CtorLiteralPool — literal-pool fragment reusing a neighbour's body.
- `0x00242564` maybe_Ui_MonsterBook_FillEntry — unstable-register body, roles inferred from calls.
- `0x00244768` maybe_Ui_MonsterBookEntry_Ctor — bad-instruction constructor fragment.
- `0x0024B998`-adjacent case `0x0025B9A4` maybe_Ui_Panel_HandleInput — bad-instruction handler.
- `0x0025C1DC` maybe_Ui_PaneList_OnInput — key source and list base come from r5/r6.
- `0x0025B450` maybe_Ui_CloseDetailView — r4/lr passed through a virtual call.
- `0x00288AE0` maybe_Ui_CreditWindow_SelectModelFrameEx — soft-float compare flags and literals.
- `0x00258000` Ui_ListWidget_Ctor — the two temporaries swap roles between style branches.

Elsewhere vague but still truthful names were used where the body only supported a generic role
(e.g. `workValue`, `scratch`, `coreArg` for the stack word fed to `Ui_GetCore`). Parameters that are
never read were named `unusedParamN` / `unusedArgN`, or with a `maybe_` prefix inside low-confidence
entries.

## Coverage notes

- The `Ui_GetCore`/`Gfx_GetContext`/`Game_GetWork` stack argument pattern recurs throughout; those
  temporaries are named `coreArg`/`coreArgCopy` (or `maybe_coreArg` when the entry is uncertain).
- Destructor chains that walk a single running base pointer were named `objectPtr`, with unlinked
  list neighbours as `listPrev`/`listNext`.
- Resource-loading routines that compare a chain node against the pack type info use
  `typeNodePtr` and `validateResult`.
- Smart-handle bookkeeping uses `handleValue`/`handleMask`/`handleEntry` (not reusing the names the
  first pass had already claimed).
- Pane-registration routines use `panePtr`/`textElement`/`messageRecord`/`childCount` consistent
  with their neighbours in the same batch.
