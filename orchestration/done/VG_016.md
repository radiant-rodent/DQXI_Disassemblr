# VG_016 — second pass over 130 local-variable tables

## Scope

- Batch: `orchestration/types/gap/VG_016.json`
- Functions answered: 130 of 130 (`python tools/gapfill.py VG_016 --check` → `130 answers, 0 problem(s)`)
- Variables named in this pass: about 690 (locals, stack temporaries and unnamed parameters across all 130 functions)
- Nothing was left out: every variable the tool listed received a name. Nothing was renamed outside the
  "variables still to name" tables.

## Conventions used

- Names are lowerCamelCase and describe the role seen in the body (`entryIndex`, `scratchBuf`, `corePtr`,
  `handleValue`, `nameBuf`).
- Reused single-register temporaries got one honest role name (`workPtr`, `workInt`, `tmpValue`,
  `valueResult`), since the same register carries several unrelated values in these decompilations.
- Parameters that are never read got `unusedArgN`; parameters only forwarded to `Ui_GetCore`/`alloc` got
  `coreArgSrc` / `allocArg`.
- Nine entries stayed below 0.5 confidence and every one of their names is prefixed `maybe_`:
  - `0x0036855C` maybe_Ui_GuideWindow_ReleaseScene — `maybe_scratchValue` (incoming register, only spilled for `Ui_GetCore`)
  - `0x00368654` maybe_Ui_GuideWindow_UpdateClose — `maybe_unusedArg2/3`, `maybe_forwardedArg`, `maybe_remainingFrames`, `maybe_coreArgBuf`
  - `0x0036869C` maybe_Ui_GuideWindow_ReleaseSceneB — `maybe_scratchValue`
  - `0x0037A968` maybe_Ui_MemoriesWindow_Notify — `maybe_viewObj`, `maybe_scratchValue`
  - `0x0037C8E0` maybe_Ui_RecordWindow_RefreshPage — `maybe_selfPtr` (false entry, damaged body, uninitialised this pointer)
  - `0x0038295C` maybe_Ui_PaneAnim_ApplyToChildren — `maybe_preservedArg4..8` (argument registers lost at `func_0053CD1C`)
  - `0x00382AD0` maybe_Ui_MessageWindow_NotifyAdvance — `maybe_scratchValue`
  - `0x00387058` maybe_Ui_TitleTextWindow_NotifyAdvance — `maybe_scratchValue`
  - `0x003B27BC` maybe_Ui_QuestWindow_AddEntry — `maybe_preservedR8`, `maybe_flagResult` (bad-instruction decode)

## Difficult spots (named, but noted here)

- Functions with `halt_baddata`/bad-instruction bodies were still fully named from the decodable part:
  `0x0036E3F8`, `0x003A9398`, `0x003A9640`, `0x003A8D80`, `0x003B8AD0`, `0x003B8B88`, `0x003B9BF0`.
- Copy-paste destructor/release families (guide window, message-select, scroll list, skill panel, equip text,
  list window 0x1F8, record detail) all follow the same node-unlink/frame-pair pattern, so `prevNode`/
  `nextNode`/`frameWord`/`objPtr` were used consistently there.
- The big grid/row renderers (`0x003B5A44`, `0x003B8010`, `0x003B887C`) reuse `iVar5`/`iVar6` for pane
  results, member records and config entries; `workInt`, `memberData`, `configEntry` and `textId` record
  the dominant role.
