# VG_019 — second pass, local variables (done)

## Result

- Functions covered: **155 / 155** (`python tools/gapfill.py VG_019 --check` -> `155 answers, 0 problem(s)`).
- Variables named in this pass: **~680** entries (PARAM rows and locals), spread over 23 `--add` calls of
  1–8 functions each.
- Nothing listed by the tool was left unnamed: every row in every "variables still to name" table received a
  name. The only names not written are those the tool never asked for (already-named rows and the
  "already used names" list), which were treated as reserved.

## How the names were chosen

- Names came from the body, plus the `hint`, `calls`, `fields` and `consts` columns. Typical mappings:
  loop indices -> `index`/`cursor`-style names, stack buffers passed to a call -> `buf`/`scratch`/`...Out`,
  return values kept in a temp -> `...Result`, a pointer to a read field -> `...Ptr`, a copy of a parameter
  -> a `...Copy` / role name.
- Recurring patterns that were recognised and named consistently across the batch:
  - `arg4` copied into a stack slot whose address goes to `Game_GetWork` / `Ui_GetCore` / `Game_GetDataManager`
    -> `maybe_workOut` / `maybe_coreOut` (the slot), `maybe_workArg` / `maybe_coreArg` (the parameter).
  - `entryPtr`, `slotPtr`, `rowPtr`, `memberRecord`-style locals in the actor/party accessors.
  - The `iRam...`-guarded entity type-walkers (`iVar1`/`iVar2` -> `typeNode` / `component`).
  - The 16-word key copies in the hash-map lookups (`keyWord1..15`).
  - The `in_fpscr` values used as float rounding-mode source -> `fpStatusReg` where the entry was confident.
- Confidence: each saved entry carries a single `confidence` value. Where it is below 0.5, **every** name of
  that entry is prefixed with `maybe_`, as the rules require; above 0.5 the name is written bare. No name was
  reused inside a function, and no name from a function's "already used names" note was reused.

## Low-confidence / weak-but-true names

Most of these are leftovers the first pass skipped for a reason, so a large share of the entries are
`maybe_`-prefixed:

- **Unused parameters** (`maybe_unusedArg1`, `maybe_unusedArg2`, `maybe_unusedParam`, ...): the parameter is
  never read in the body (typical of create/init wrappers, condition callbacks and the `halt_baddata`-damaged
  scroll/cursor routines). The name records the only true statement available about them.
- **Shared scratch registers** (`maybe_scratchInt`, `maybe_scratchWord`, `maybe_workOrHandlerPtr`,
  `maybe_typeInfoOrEntry`, `maybe_packEntryOrSize`, `maybe_countOrResult`): one register is heavily reused for
  different roles inside the same body, so a single honest role name does not exist; the name states the set
  of roles seen.
- **Dead/uninitialised registers forwarded to a call** (`unaff_r4/r5/r6`, `in_lr`, `extraout_r1`,
  `unaff_r9/r10`, `unaff_r11`): named by position/role in the forwarding call (`maybe_arbiterArg1`,
  `maybe_linkRegister`, `maybe_restoreWord`, ...).
- **Zero-initialised stack blocks** (`maybe_zeroWord1..16`, `maybe_tmplByte1..6`, `maybe_entryHdr1..3`):
  buffer/record fields that are only ever cleared before a call; named by their position in the block.
- **Copied member-record fields** in `maybe_Ui_ItemDetail_Setup`: the 80-odd locals mirror member-record
  offsets, so they are named `maybe_memberF10`, `maybe_memberF1274`, ... to keep the offset visible.
- **Truncated bodies** (`halt_baddata`, "Removing unreachable block", "Heritage AFTER dead removal"): for
  those functions only the printed prefix was used; names cover the visible part and the hint columns only.

## Nothing was omitted

No variable was skipped for lack of information. The only intentionally uninformative names are the
`maybe_unused*` ones, and those are prefixed and below 0.5 confidence as the rules prescribe.
