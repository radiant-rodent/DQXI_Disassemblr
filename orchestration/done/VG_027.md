## What was left out and why

Nothing. Every listed variable received a name, including the ones where only a coarse
statement was possible. The reasoning behind the vague ones:

- **Damage-only locals (`in_r3`, `unaff_r*`, `in_cr*`, `in_fpscr`, `in_lr`, `in_s0`, `in_d0`)**
  — named after the single thing the body does with them ("unusedArg" when the value only feeds
  an `Os_GetGameWork` out-slot, "fpStatus" when only the `>>0x16 & 3` rounding bits are read,
  "cr*" for coprocessor leftovers). Confidence < 0.5, so all of these carry `maybe_`.
- **Stack buffers that are only a call's out-slot** — `osWorkArg` / `maybe_osWorkArg`
  (`Os_GetGameWork` results) and `maybe_compilerCtx` / `maybe_hitTestArg` variants.
- **Zero-filled record blocks (0xB0-byte action/command records, 0x8C sub-records, 0x2C8 slots)**
  — named positionally (`recordWord*`, `cmdWordNN`, `recWordA..`, `recShortA..`, `recByteA..`)
  because only their offset inside the record and their initial value (0 or 0xFFFFFFFF) is known.
- **Split fragments / false entry points** (0x00169076, 0x0016907A, 0x0016A78C, 0x001637F4,
  0x001638BC, 0x00148CA4, 0x00148BA8) — the documented name does not match the visible body, so
  names describe what the code demonstrably does and the whole entry is marked `maybe_`.
- **Fully unused parameters** — `unusedArg1/2/3` / `maybe_unusedArg*`, kept named rather than
  dropped so the parameter table stays complete.
