## Naming choices worth recording

- Vector / matrix blocks: identity and inverse matrices in `maybe_Battle_ActorAction_UpdateMotionB` were named
  per element (`matM00`…`matM0B`, `invM08`); the dozen-float stack blocks in the camera and multi-part code
  became `vecAX/Y/Z`, `transformRow0..3`, `texU0/texV0/…`, `entryWord0..13`.
- Constant-filled descriptor blocks (fade quad, sprite-actor params, multi-part sprite slots) were named
  `quadParam0..11`, `headerA0..A5`/`headerB0..B5`, `zeroA…`, `oneA…`, `flagFF…` — vague but faithful to the
  fact that they are literal-filled struct fields whose semantic names are unknown.
- `Os_GetGameWork(&x)` / `Game_GetWork(&x)` stack arguments were always named `workBuf`, `gameWorkBuf`,
  `gameWorkOut`, `gameBuf`… depending on which sibling in the same function already used `gameWork`.
- Message param blocks (functions 7, 86) used the same names in both: `messageId`, `messageAlpha`,
  `senderId`, `receiverId`, `messageFlags`, `messageColor`.
- `fpscr`-derived variables (only feeding the float rounding-mode bits) were named `fpscrValue`.
- 360.0 / 1/360 fmod pairs in the camera path setup were named `degreesScale` / `turnScale` with
  `turnsValue` / `turnsCopy` around the `func_006731EC` call.
- Unevaluated incoming/leftover registers (`in_r3`, `unaff_r4`, `unaff_r5`…) were named `incomingWord`,
  `extraReg*`, `extraChar`, `extraCount`, `extraPtr`, etc.
- Truly unread parameters were named `unusedArg` / `unusedArg2` / `unusedArg3` (no rename of anything outside
  the listed tables).
