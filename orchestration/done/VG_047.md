# VG_047 - second pass over local variables (54 functions)

All 54 functions listed by `tools/gapfill.py VG_047 next` were answered in 13 `--add` calls.
`python tools/gapfill.py VG_047 --check` reports: **54 answers, 0 problem(s)**.
Every variable that the tool listed was named (roughly 670 names in total, parameters included);
no variable was skipped, so nothing is listed as "left out" on the variable side.

## Rules applied

- lowerCamelCase everywhere; names unique inside their function and disjoint from the
  "already used names" note of that function.
- Only variables from the "variables still to name" table were touched; nothing outside
  `orchestration/types/gap/VG_047.json`'s second-pass scope was renamed.
- Where the body did not prove the role, the name is still given but the entry uses
  confidence < 0.5 and every name of that entry carries the `maybe_` prefix
  (e.g. `maybe_scratchBuf`, `maybe_stateOrRecord`). 45 of 54 entries are in that low-confidence
  group; the 9 entries at 0.5 are the verbatim popup-record / state-slot handlers
  (`0x4824E0`, `0x482A60`, and the 0x487-0x490 state twins) whose locals are literally the
  arguments of one documented call.

## What was named, by kind

- **Structural / role names (confidence 0.45-0.5):** state-step temporaries (`maybe_stateDelta`,
  `maybe_nextState`, `maybe_isFirstState`), scratch argument buffers for `Os_GetGameWork` /
  `Game_GetDataManager` / `Sound_GetPlayer` (`maybe_gameWorkArgBuf`), vtable read results
  (`maybe_actorRef`, `maybe_modelRef`, `maybe_popupEntry`) and the repeated message / model-actor
  popup records (`maybe_msgActorRef`, `maybe_msgModelRef`, `maybe_msgIdXX`, `maybe_msgAttrXX`,
  `maybe_msgFlagXX`) shared by the whole 0x47E000-0x485000 battle-UI family.
- **Unused parameters:** every parameter the body never reads was named `maybe_unusedArgN`
  (23 cases: 0x468590, 0x46EAE0, 0x471CE0, 0x472044, 0x4726C0, 0x47948C, 0x4794C0, 0x47A960,
  0x47C7A8, 0x47C954, 0x47F794, 0x481B5C, 0x481C4C, 0x485F14 and their arg3 variants).
- **Descriptor fills (confidence 0.4):** the 0x98-byte display descriptor of 0x46E50C and the
  0x68-byte spawn descriptor of 0x471DF4 are named by offset (`maybe_descA4` ... `maybe_desc2E`,
  `maybe_desc98` ... `maybe_desc60`) with the recognisable members named for what they hold
  (zero/one vectors, colour, basis axes, `maybe_invalidIdTemplate` = 0xFFFF, name words of the
  built asset string).
- **Damaged bodies (confidence 0.3):** 0x47285C, 0x475114, 0x47C7A8, 0x47D47C, 0x47F794,
  0x47F9FC, 0x4800A4, 0x481B5C, 0x483308, 0x48356C, 0x485F14 contain `halt_baddata` /
  overlapping instructions. Their locals still got names from visible use (camera-minus-node
  deltas and squared distances for the look-at maths, `g_vector3Zero`/`g_vector4One` slots,
  row-table bytes, register leftovers), plus explicit phantom names for decompiler artefacts:
  `maybe_coprocessorOut0/1/4/8`, `maybe_coprocessorArg0/3`, `maybe_registerOut`,
  `maybe_unaffArg*`.

## Left out and why

- Nothing from the "variables still to name" tables was left out.
- Function-level renames were **not** performed: several entries keep an `InitB`/`UpdateState`/
  `Rename` style name from the first pass even where the body suggests another role
  (0x46CE28, 0x46EAE0, 0x468714, 0x47285C, 0x47D47C, 0x47EBC8, 0x483E30, 0x484030, 0x485D90).
  Those names are outside this pass's scope (variables only) and the reasoning is recorded in
  the evidence fields instead.
- No hex/call resolution was done via `tools/fn.py`, because every listed variable could be
  classified from the printed body, hint, calls, fields and consts columns alone.
