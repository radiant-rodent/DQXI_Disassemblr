## How the names were derived

Only the columns supplied by the tool were used: the decompiled body, the `hint`, `calls`, `fields`
and `consts` columns, plus the "already used names" note for collision avoidance. No function was
viewed twice and no caller/callee lookup was needed.

Recurring shapes and the names given to them:

- `Game_GetDataManager(...)` result -> `dataManager`; the stack slot handed to it -> `contextValue` /
  `contextArgCopy`; the word at `*dataManager` -> `dataManagerArg`.
- A word reused for a vtable address, then a constructor constant -> `rowVtable`, `stateVtable`,
  `elementVtable`, `elementCtor`, or `tmpWord` when the same slot carries three or more unrelated
  constants.
- The seven/eight stack slots initialised immediately before `Ui_Widget_ShowWithRecord` ->
  `msgArgWord` + `msgArgField0..5` (message-argument record: zero word, 0xFF default style byte,
  zero fields).
- The six slots initialised immediately before `Battle_MessageQueue_PushEntry` -> `descWord`,
  `descField0..2`, `descSentinel`, `descSentinelCopy` (popup descriptor: zero word, 0xFF byte,
  0xFFFF id sentinel and its copy).
- A pointer threaded through a chain of virtual calls and written back to the same slot each time ->
  `nodeValue` / `cursorValue`.
- Uninitialised incoming registers -> `incomingR3`, `incomingR12`.
- Parameters never referenced in the body -> `unusedArgN`; parameters forwarded unchanged ->
  `forwardedArgN`.
- Heavily reused scratch with no single meaning -> `tmpValue`, `tmpPtr`, `tmpWord`, `tmpInt`,
  `tmpOffset`, `lowByte`, `flagA`/`flagB`, `borrowFlag`.

  single meaning exists; `tmpWord` / `tmpOffset` / `tmpInt` is the honest description.
