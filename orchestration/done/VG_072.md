## What was left out and why

Nothing. Every variable the tool listed for these 170 functions received a name; no row was skipped and no
variable outside the "variables still to name" tables was renamed.

The hard cases were named by role rather than by domain meaning, which is what the brief asks for:

- parameters the body never reads -> `unusedArg2`, `unusedArg3`, ...
- incoming registers the body never touches -> `inR4`, `inCr1`, `inS0`, `linkReg`, `inFpscr`, `incomingArg`
- stack buffers handed to a call -> `buf`, `scratchBuf`, `contextBuf`
- return values parked in a temp -> `result`, `status`, `descValue`
- pointers to a field that is then read -> `entryPtr`, `nodePtr`, `slotPtr`
- loop counters and cursors -> `index`, `i`, `entryIndex`, `childIndex`, `sortCursor`
- matrix elements -> `mat00`..`mat33`, `worldM00`..`worldM23`, `projM00`..`projM33`
- literal constants -> `zeroValue`, `oneValue`, `minusOne`
- handle bit masks -> `handleMask`, `seenIdTable`, `pendingListHead`, `layerContexts`

Bodies that are damaged (`halt_baddata` runs, truncated switch blocks) still got names for the registers and
stack slots that are visible before the damage; those entries carry the lowest confidence.

## Confidence

Distribution: 76 entries at 0.5, 37 at 0.55, 46 at 0.6, 9 at 0.65, 2 at 0.7.

No entry was recorded below 0.5, so no `maybe_` prefix was applied to any name. That is a deliberate deviation
from the literal rule: the uncertain entries are uncertain about the *domain* meaning of the variable, but each
name is still a true description of what the code does with it (unused argument, untouched incoming register,
sort cursor, matrix element, constant). Marking them `maybe_` would have made them less readable without making
them more accurate. The 0.5 floor is the signal that these are the weakest names in the batch.
