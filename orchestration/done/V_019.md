## Decisions (recorded because the orchestrator was not available)

1. **Tokens Ghidra reuses for two unrelated values were left unnamed** rather than mislabelled:
   `puVar1`/`puVar5`/`uVar6`/`iVar3` in `0x004D8B44`, `iVar4`/`uVar7`/`uVar8` in `0x004FB8D0`,
   `iVar5`/`iVar3` in `0x0057DA94`. A single noun would be wrong for at least half their uses.
2. **`in_fpscr`, `uVar4`, `bVar1` in `0x00540148` are left alone.** They are Ghidra's
   reconstruction of the `vcmpe`/`vmrs` condition flags, not real locals (matches the FACTS.md
   rule about `in_NG`/`in_ZR`/`in_OV`).
3. **`self` kept everywhere**, per the batch rules.
4. **`0x004DB5AC` token spelling.** The batch and `locals.json` still spell the actor `f28`,
   while the current readable C says `iVar1`. I used the **batch** token, because
   `merge_locals` builds its `allowed` set from `locals.json` (which currently matches the
   batch). The discrepancy is recorded in that entry's `evidence`. `f234` and `piVar3` match
   both spellings, so only one rename is at risk if `locals.json` is regenerated first.
5. **Empty entries are still emitted** for the trivial wrappers, so coverage is visibly 150/150
   rather than silently short.

## Open problems / suggested follow-ups

1. **Batch generator: resolve `readable` by address suffix at dispatch time.** 24 of the 150
   paths in this batch are stale (the readable tree was renamed after the batch was generated),
   and 3 point at files that exist in neither `decomp/readable/functions/` nor
   `decomp/readable/recovered/`:
   - `0x00540148` `maybe_Ui_LayoutElement_SetTargetValue`
   - `0x00579E00` `maybe_Svc_ReleaseMemoryBlock`
   - `0x0057DA94` `maybe_Gfx_ModelInstance_DrawSortedNodes`

   All three *are* in `orchestration/types/locals.json`, so the readable emitter is dropping
   them for some reason — worth a look, since it means those functions never get a readable body.
2. **`M3_vars_merge` must replace body-only.** The token `i` in `0x0057DA94` is a bad earlier
   rename of `iVar3` (it is a struct pointer, not an index) and `i` also occurs in prose
   ("i.e.") inside doc blocks. Same hazard V_022 reported.
3. **`0x00579E00`'s asm is Thumb decoded as ARM** in `asm/text/text_00540048.s` (the dump at
   that address is garbage). The clean-C body was the only usable evidence; the disassembler
   should be told about the Thumb region.
4. **`0x004DB5AC` and `0x005AF920` are damaged** (`halt_baddata`, an undeclared `arg3`). They
   keep `maybe_` names and low confidence; a refine pass with the disassembly would settle
   `maybe_clipList` / `maybe_clipEntry`.
