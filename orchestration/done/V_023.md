# V_023 — local variable / parameter naming (Ui subsystem)

**Status:** completed. **Output:** `orchestration/types/out/V_023.json` (143 entries, 970 renames, 79,172 bytes).

## What the batch is

150 functions in `0x0019A890`–`0x00211538`, mostly Ui code: equipment window, item screen, shop item
list, jumon (spell) window, poker/casino window, party-status panel, panel-message, `Ui_Part`
layout-animation helpers, plus a tail of save-slot byte getters, field actor tables and party helpers.
The batch was generated before `M2_types_merge`, so its `readable` paths and its variable hints are
stale; I resolved every function by the `_<address>.c` suffix of the **current** `decomp/readable/`
tree and read the merged field/global names from there.

## Method

The work was split across five parallel sub-workers (30 functions each) against the post-M2 readable C,
then merged, de-duplicated and re-validated centrally. Each sub-worker used
`out/scratch/V_023/dump.py LO HI` (signature + variable table + condensed body) and
`out/scratch/V_023/validate.py` (token exists in the batch record, legal C identifier, no duplicate
name inside a function, no collision with an untouched token, `maybe_` iff confidence < 0.5).

## Decisions

1. **Stale tokens dropped, not guessed.** 8 batch tokens no longer exist in the current readable C and
   were removed instead of emitted: `f4a` (×3, a field name mis-parsed as a local — the body declares
   `uVar1`), `f28` (same, `uVar2`), `iVar3`/`uVar5`/`iVar3` (already renamed by the readability pass to
   `uiPartGetAnimState`/`uiPartMatchAnimRecord`), `textLineGetMaxInsertCount` (the callee is now
   `Shop_GetMaxAffordableCount`, so the body says `shopGetMaxAffordableCount`). A rename of an absent
   token is a no-op at merge time and would have shadowed an existing map.
2. **Register artifacts dropped.** 12 renames of `unaff_rN`, `in_fpscr`, `in_stack_*` were removed
   centrally: per `FACTS.md` those mean damaged decompilation, so a name would be a guess. `in_s0..s2`
   (dropped VFP float arguments) and `in_r3` (the incoming context word) were kept where the body
   proves what they hold.
3. **`function` always carries the batch name**, even where the readable file has since been renamed
   (96 of 143 entries). That is what `locals.json`/`apply.py` look up by; the address fallback also
   works.
4. **`self` kept everywhere.** Parameters whose batch name no longer matches the body position
   (e.g. batch `item`/`screen` vs body `screen`/`context`) were left unnamed rather than mis-renamed.
5. **Multi-purpose Ghidra temporaries left unnamed** where one name would be wrong in half the body
   (`iVar1` in `Ui_EquipmentWindow_NavigateLists`, `iVar2` in `Ui_EquipmentWindow_RefreshDetail`,
   `iVar5` in `Ui_ItemScreen_HandleInput`, …). `LAB_xxxx` goto labels were not renamed.
6. **Omitted functions (7):** `0x0019C93C` (only `layout`, already named; `arg2`/`arg3` unread),
   `0x001A4704` (batch token `effect` is now `actor`), `0x001CE344` (body is two calls, no locals),
   `0x001E5A08` and `0x001EAAA0` (only `self`/`ui`, already named; `f1c` already renamed away),
   `0x001EAC4C` (token `ui` is now `window`), `0x001F0750` (token `uVar1` is now
   `actorResolveReferenceObject`).

## Not verified

The maps are not applied to `decomp/readable/` (that is `M3_vars_merge`), so nothing was recompiled and
the names are not yet visible in the C. Semantic accuracy is bounded by the readable C: I read no
assembly for this batch, so a name is only as good as the decompiled body plus the merged field names.

## Found but NOT fixed (outside my ownership)

1. **96 of 143 entries will be silently dropped by the current merge path.** `apply.py` keys
   `merged/locals.json` by `locals.json`'s function name (the pre-M1 name, e.g.
   `maybe_Ui_EquipmentWindow_NavigateLists`), while `tools/readable_c.py:473` looks the map up with
   `func["name"]` from `function_by_address` (the current name, `Ui_EquipmentWindow_NavigateLists`).
   `M3_vars_merge` must look the entry up by address (`maps["function_by_address"]` already exists) or
   re-key `merged/locals.json` by address, otherwise only the 47 entries whose name did not change will
   apply. This is the same defect V_021 reported for 32 of its 95 entries; V_023 is hit much harder
   because M1 renamed most of this Ui batch.
2. **The batch generator should resolve `readable` by address suffix.** 100 of the 150 `readable` paths
   in `V_023.json` point at files that no longer exist under that name.
3. **`apply.py --validate` is not read-only.** It rewrote `orchestration/types/merged/report.json`
   (generated report only; `merged/locals.json` and `include/dqxi/*.h` kept their Nov 9 mtimes, so no
   source changed). The task file calls it a validation step, so this should be stated there.
4. **Batch variable extraction picks up field names as locals** (`f4a`, `f28` in this batch). Those
   entries can never be renamed and should be filtered in `tools/typedb/inventory.py`.
