## Decisions worth recording

* **Poisoned ranges respected.** `0x00269F64..0x00277700` is `BattleAi_*`, not `Ui_TextLayout_*`.
  The batch still carries the old `Ui_TextLayout_*` function names, but I named the variables from
  the real callees (`BattleAi_IsTargetValidForAction`, `BattleAi_HasCandidateCapacity`,
  `BattleAi_RollCandidateWeight`, `func_0063D018` SkillRecord, `func_0063CFC8` SpellRecord,
  `func_00629214`/`func_0062921C` skill/spell lists). So `self` became `aiCtx`, the candidate
  arrays became `candidateTable`/`candidateIds`/`candidateCosts`, and the record pointers became
  `actionRecord`/`spellRecord`. `0x002736BC` (old name `Ui_TextLayout_MeasureElementWidth`) is the
  BattleAi damage estimator per FACTS.md, so its locals are `memberRecord`/`equipRecord`/`targetUnit`.
* **Damaged decompilations were left mostly unnamed on purpose.** Functions with
  `unaff_rN`/`in_rN`/`CONCAT22` chains/`halt_baddata()` (`0x00263BEC`, `0x0027168C`, `0x002904D8`,
  `0x0029E41C`, `0x00296598`, `0x0026E56C`) got only the handful of names the callees justify, and
  the rest of their 100+ stack slots were left alone. `0x0027168C` got no local at all.
* **Reused scratch slots got `maybe_` compound names** rather than a wrong single noun, e.g.
  `maybe_workOrChildManager`, `maybe_rowTypeCountOrWindow`, `maybe_workOrStateId`. Ghidra reuses one
  register for several meanings in these bodies; a single noun would be a lie.
* **Fake trailing parameters were not renamed.** The 8-byte-alignment prologues produce `arg2`/`arg3`/
  `arg4` that are never read (only copied into a `Game_GetWork` out slot). Those stay `argN` and the
  `evidence` says so, rather than inventing a meaning.
* **`self` was kept** wherever it is genuinely the object (`Ui_RecipeBook_*`, `Ui_PaneGroup_*`,
  `Ui_SakusenWindow_*`) and only renamed where the readable C already used a better noun
  (`window`, `actor`, `aiCtx`, `parent`).
* **Shared UI control-code pattern.** The shop-window family (`0x00284FD0`, `0x002851C4`,
  `0x002853D4`, `0x0028561C`, `0x00285704`, `0x00285AE4`, `0x00285B44`, `0x00285FCC`) all build the
  same four-byte block `{code, 0xFF, 0, 0}` for `Ui_MessageWindow_ExecControlCode`; those slots are
  named `controlCode`/`controlCodeB`/`controlArg1`/`controlArg2` consistently across all of them.
