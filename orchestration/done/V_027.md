# V_027 — local variable / `argN` renaming batch

## What was done

Renamed the local variables and remaining `argN` parameters of all **149** functions in
`orchestration/types/batches/V_027.json` (UI equip/skill/message/world-map panels around
`0x0039D7C8..0x003F7290`, the field actor/action cluster `0x003BD148..0x003F44AC`, and the
`Model_Equip_*` 3D attachment cluster `0x0040A680..0x0040B748`).

* 149 of 149 functions answered, 0 to do.
* 886 names written (params + locals), of which 26 carry the `maybe_` prefix (3%).
* 9 functions have nothing to rename (their variable table lists only the already-named `self`);
  each says so in its `evidence`.
* Every entry has an `evidence` string naming the concrete signal used (callee name, vtable slot,
  string constant, field offset/width, sentinel constant, merged field name).

## Files changed

* `orchestration/types/out/V_027.json` — the only owned output file (149 records, UTF-8, 112,059 bytes).
* `orchestration/done/V_027.md` — this report.
* `AGENT_LOG.md` — one appended line.
* Scratch: `out/scratch/V_027/INSTRUCTIONS.md` and `chunk_w1..w7.json` (the per-slice answer files).

No other file was touched. The readable C tree was not modified (M3_vars_merge applies the maps).

## Decisions taken (no orchestrator available)

* **The batch was split across 7 child agents.** 149 functions at roughly 7 KB of body + variable
  table each is far more than one context can hold, and the work is mechanical: read a chunk,
  name the tokens, save. I wrote one shared brief (`out/scratch/V_027/INSTRUCTIONS.md`, the task's
  own rules restated: exact tokens, lowerCamelCase, `maybe_` below 0.5, evidence, no exploration,
  no `--add`), gave each child a disjoint index range (0:21, 21:42, 42:63, 63:84, 84:105, 105:126,
  126:149) and its own chunk file, then merged the seven chunks myself with `--add` and ran
  `--check`. Children were forbidden to touch `orchestration/types/out/V_027.json`, to run
  `--add`/`--check`, or to edit anything outside their chunk file, so the merge stayed serial and
  the owned file was only ever written by `batchview.py`.
* **One chunk was rejected and repaired.** `chunk_w7.json` renamed `cVar1` in `0x004067CC`, a token
  the batch does not list for that function; `--add` refused the whole chunk (nothing saved). I
  dropped that one token and re-added.
* **Table is authoritative, body is the evidence.** Where the variable table and the current
  readable C disagree on a token name (M2 renamed some of them), the table token was renamed, as
  the task requires. Those renames are no-ops for the merge (see open problems).
* **Damaged decompilations stay vague.** `0x003D75EC` (`halt_baddata`), `0x003E24A6`
  (`register0x00000054` / `unaff_*` spill noise), `0x00409FF4` (dead-code obfuscation) got
  confidence 0.3–0.5 and `maybe_` on every name.
* **Reused registers were left unnamed rather than given two meanings.** Where one token holds two
  unrelated values (e.g. `iVar3` in `0x003C4D20`, `iVar6`/`iVar8` in `0x003E3DCC`, `iVar5` in
  `0x003EFC48`), the child either named it by its dominant use (and said so in `evidence`) or
  omitted it. Omission was preferred.
* **Stack-descriptor padding was not named.** The 12-float identity matrix in
  `0x0040A758` *was* named (`matrix00..matrix23`) because the body shows the `g_identityMatrix4x3`
  copy; the opaque 0x12-byte effect parameter blocks in `0x0040A980` / `0x0040B364` were not.
