## Naming approach

Names were taken from the merged readable C, not the raw Ghidra file: field
names (`self->maybe_iconAnim`, `memberData->f_edc`), global names
(`g_uiRootSingleton`, `g_battleConditionParamTable`), and the named callees
(`Party_CountAliveMembers`, `Item_LookupRecord`, `Ui_Window_PushPane`,
`Svc_Time_MakeTimestampFromRecord`, `Battle_Enemy_GetDisplaySlot`, ...).
Recurring patterns:

* `Game_GetWork` out-slot locals became `gameWork` / `gameWorkPtr` / `workOut`.
  Where the rule pass had already claimed `gameWork` for a field, I used
  `gameWorkPtr` (0x004920A0, 0x004A4ADC, 0x004A4D80).
* `func_0035EB98(gameWork, id)` results became `memberData` / `monsterData`;
  `func_006292F0` item ids became `itemId`; `Item_LookupRecord` buffers became
  `itemRecordOut` / `itemRecord`.
* The `func_0035EB98` + `f_73C/f_73E/f_740/f_742/f_744/f_746` family
  (0x00495A24 … 0x004973E8) got `memberDataA/B/C` plus `displaySlot`,
  `slotScale`, `statScale`, because the bodies are the same formula with a
  different field triple.
* `argN` parameters that are never read were left unnamed rather than guessed
  (e.g. `arg4` in 0x00461B28, `arg2`/`arg3` in the `Ui_ProfileScreen_*`
  handlers, `arg5` in 0x0048CA0C, `arg8` in 0x0049100C).

## What I skipped and why

* **11 functions with no names at all** — nothing in the body justified a name:
  0x0041E80C, 0x00452988, 0x0045407C, 0x00455AAC, 0x004573CC, 0x00459A70,
  0x00463324, 0x0046C014, 0x004775D4 (all from the earlier worker, confidence
  0.0–0.2), plus 0x00463580 and 0x00468688 which I answered with a parameter
  rename only.
* **Parameters that are never read.** The decompiler keeps `argN` slots that no
  instruction touches; naming them would be invention.
* **Stack slots reused for several unrelated values.** In the long bodies
  (0x0046EE3C, 0x004ABC48, 0x004AC46C, 0x004A2CE0) the same `local_xx` holds
  different things in different branches; I named only the slots with a single
  consistent role and left the rest.
* **Split string literals.** Byte groups like `local_40/local_3c/local_3a/local_39`
  in 0x00465160 are one `'txt_l0'` literal the decompiler broke into scalars;
  naming each fragment would be noise.
* **0x004666B8** has no readable C at all; I named only the three variables
  whose role is unambiguous from the variable table and left `bVar1`/`piVar4`
  alone.
* **0x004A4D80** hit bad instruction data; several names there are deliberately
  vague (`highWord`, `maskLow`, `partyIndex`) and the entry is at confidence 0.5.
