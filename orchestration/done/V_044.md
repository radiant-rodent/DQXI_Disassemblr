# V_044 - local variable naming batch (done)

## What I did
- Worked through all 150 functions of `orchestration/types/batches/V_044.json` via
  `python tools/batchview.py V_044 next` / `--add`, in 26 chunks (nothing viewed twice).
- Read names only from the printed current readable C, the variable tables, the merged field
  names (`actor->f_2EC`, `maybe_tableCount`, ...), callee names and constants/strings.
- Result: `orchestration/types/out/V_044.json`, 150 answers, 603 renamed tokens
  (locals + remaining `argN` params). `--check` reports `150 answers, 0 problem(s)`;
  the file also parses as JSON (150 objects).

## Coverage
- 141 functions got at least one name; 603 tokens total, average ~4 per function.
- ARM batch is dominated by Actor2D / Ui_* / Model_Attach families, so the same roles
  repeat: `gameWork` (Os_GetGameWork/Game_GetWork result), `gameWorkOut` (its scratch
  buffer), `dataManager` (Game_GetDataManager), `slot`/`stateSlot` (+0xC0 slots and
  +0x244/+0x420 per-state arrays), `patternIndex` (work+0x48+0x281), `effectParams` and
  `nameBuf` (Effect_FindOrCreateInstance record + inline FixedString15), `meshParams`
  (&g_actor2DSpriteMeshDefaultParams + allocator word), `taskEntry`/`taskTable`
  (Container_SlotReplace installs, actor->f_60/actor[0x18]).
- The seven `Actor_TryPlayActionSeqXX` functions are pure save/overwrite/restore pairs of
  one field block: their saved copies are named `savedParam<N>` after the field index
  they come from, and the `func_005E74A0` result is `playResult`.

## Skipped (deliberately)
- 9 functions have no locals at all (only `Os_GetGameWork`/`Game_GetWork` scratch buffers
  or a two-line body): Actor_ReleaseBoundsCheck, Model_Attach_UpdateChildrenRoot,
  Actor_CheckInteractionDone, Ui_Part_DeletingDtor, Ui_SpritePart_ReleaseResources,
  Actor_OnPlayEvent, Actor_TryPlayActionSeq11, Ui_Overlay_BindEntrySlots,
  Actor_ResetStateModelIfCurrent. A further four (Actor_ApplyStateAnimEvent,
  Actor_SelectIdleAnimation, Actor_InitStateController, Actor_UpdateStateTimer-like stubs)
  only had stack buffers, no renamable locals.
- `scratch` / `arg2` / `arg3` parameters: left alone almost everywhere. They are either
  unused or already descriptive, and the body often re-assigns them, so a noun would be wrong.
- Variables deliberately NOT renamed because the same token carries two unrelated values in
  one function (naming would be precisely wrong): e.g. `iVar2` in
  Actor_CreateBehaviourTasks / Model_SyncAttachmentVisibilityByState, `iVar1` in
  Actor_CreateActionTable, `fVar13` cluster in Actor_UpdateFollowTarget,
  `piVar1` in Actor_PlayAnimationByState, `uVar2`/`iVar5` in Ui_SpritePart_Create.
- Mangled/damaged bodies (Model_CreateCharacterModelWithEquipment, ActorPart_CreateNamed,
  Actor_ApplyModelPartsA, Actor_EndStateChain[Ex]) got only the tokens that survive the
  unaff_/halt_baddata noise.

## Decisions recorded (orchestrator could not be asked)
1. Twin/wrapper families (Actor2D_CreateWithAnimInstanceA/B, Model_UpdatePatternTransform[A],
   Actor_SelectAttractAnimation vs Try-variant, the Seq0A..Seq16 group, Ui_Part slot loops)
   receive identical names for identical roles, so the merge stays consistent.
2. Opcode-ish field tokens already in the batch (`f38`, `f11c`, `f420`, `f2c4`, ...) were
   renamed by meaning (e.g. `variantKind`, `renderModel`, `effectHandle`, `savedParam0`)
   rather than by offset.
3. Where the readable C and the batch table disagreed on the token (rule-pass rename lag),
   the batch table token was used, since that is what the checker and merge consume.
4. Names I could not support past ~0.5 were omitted instead of guessed; function-level
   confidence below 0.5 was only reported for the "nothing clear" entries.
