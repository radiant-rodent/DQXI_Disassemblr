# V_070 - local variable naming batch

Batch: `orchestration/types/batches/V_070.json` (150 functions, Gfx_Scene / Gfx_DrawPacket /
Model / FieldParty / Battle_Ui / Camera / Ui_Text / Text_Command families).

## What I did

Worked through the whole batch with `python3 tools/batchview.py V_070 next` -> `--add -` cycles
(7-8 functions per call) until it reported "nothing left to name", then ran
`python3 tools/batchview.py V_070 --check`, which reported:

```
V_070: 150 answers, 0 problem(s)
```

Result written to `orchestration/types/out/V_070.json`; additionally syntax-checked with
`json.load` (list of 150 objects, UTF-8).

## Counts

- 150 functions in the output file (all batch functions covered).
- 132 functions received at least one name.
- 863 names total: 860 locals + 3 parameters (`arg2`/`arg2`/`arg4` in
  `Gfx_DrawPacket_Release`, `maybe_Container_ObjectRef_Release`,
  `maybe_Scene_ReleaseSubBuffer`-style helpers where the argument is overwritten with the buffer
  pointer).
- 18 functions were reviewed and deliberately left unnamed (see below).

## Naming approach

- Used the merged field/global names in the current readable C (`entryPoolAArray`,
  `hitResultAttr0OrPoolBitmapB`, `g_defaultBasisVector3`, `Game_GetDataManager`, ...) to infer
  local roles.
- Recurring patterns got consistent names across siblings: `gameWork`/`gameWorkBuf` for
  `Os_GetGameWork` results, `dataManager`/`dataManagerBuf` for `Game_GetDataManager`,
  `soundPlayer`/`soundPlayerBuf` for `Sound_GetPlayer`, `popupOwner` for `func_001FD96C`,
  `statePtr`/`isFirstState` for the `[... + stateOffset] == -1` member-action state machines,
  `hitRecord` for `scene->hitResultBufferOrScenePtr`, `newCapacity` for vector-growth counts,
  `entry`/`sprite`/`node` for the Gfx_Scene alloc/attach helpers.
- Names were kept vague where the decompiler conflates several roles into one token
  (`iVar2` reused as count / pointer / result). Those tokens were usually left alone rather than
  given a misleading name.
- Decompiler artefacts (`extraout_r1*`, `unaff_*`, `in_s0..s4`, `in_fpscr`,
  `CONCAT22/44` temporaries, FP status flags) were not named unless they carried a single clear
  role.
- Per-function confidence is 0.5-0.75. No name was written with confidence below 0.5, so no
  `maybe_` prefixes were emitted.

## Skipped (reviewed, nothing clear) - 18 functions

All of these are either one-line deleting destructors (`Ui_Object_DtorBody`/`Ui_3DBackground_DtorBody`
+ `operator delete`), trivial Show/Hide flag flips with no locals, or stand-alone
constructions where every variable is already a named parameter:

- `maybe_Container_ObjectRef_Init` - all three params already named, no locals.
- `Gfx_Scene_Delete`, `maybe_Field_Actor_Delete`, `maybe_Battle_Unit_Delete`,
  `Event_TriggerObject_Delete`, `Ui_NumberPopup_Delete`, `Ui_3DBackground_Delete`,
  `Ui_CriticalPopup_Delete`, `Field_Char_Delete`, `Field_BattleTrigger_Delete`,
  `maybe_Ui_ModelView_Delete`, `maybe_Field_ObjectSprite_Delete`, `Battle_AnimWindow_Delete`,
  `maybe_Ui_LabelPane_Delete`, `maybe_Ui_TextWindow_Delete` - deleting destructors, only the
  named `self`/`Xxx*` parameter.
- `Field_Actor_Show`, `Field_Actor_Hide` - single named actor parameter, only flag field writes.
- `Field_Char_PlayNarrowPassAnim` - single named `chr` parameter.

`maybe_Ui_TextWindow_Delete` (0x0059F9FC) had no readable C at all; only the named parameter.

  `gameWorkBuf`) was named and the function confidence is 0.5.
