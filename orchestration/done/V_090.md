# V_090 - local-variable naming batch

Batch: `orchestration/types/batches/V_090.json` (150 functions)
Output: `orchestration/types/out/V_090.json`

## What I did

- Worked through `python3 tools/batchview.py V_090 next` chunk by chunk until "nothing left to name",
  then ran `--check`: **275 answers, 0 problems**.
- Answered **146 of 150 functions** with renames: **874 local names** and **12 parameter names**
  (`argN`/`value` -> noun, e.g. `arg1` -> `initFlag`, `value` -> `vtable`, `recordId` -> `actionId`).
- The remaining **4 functions were reviewed with no justifiable name** (only a `self` parameter or a
  fully lost body): `0x0044AD1C`, `0x00455644`, `0x00474084`, `0x004925DC`.
- Scratch chunks (my own JSON per `--add` call) are in `out/scratch/V_090/`.
- JSON syntax of the output file re-validated with `json.load`; no other files were touched.

## How names were chosen

- Field/global names from the merged headers drove most names: `unit->targetActor`, `model->f_8c..f_98`
  (quaternion -> `quatX..quatW`), `self->jumpOffsetX/Y/Z`, `self->lerpCoordX/Y/Z`, `g_gameWork`,
  `g_actorAttachGadgetHandleMap`.
- Recurring idioms got consistent names: the lazy `0x2FB28` game-work block (`gameWorkRef`,
  `allocSize`, `elementCtor`, `blockIndex`, `blockOffset`), the `Pack_Handle_Dtor` + ring-unlink
  destructor template (`nodeBase`, `unlinkedNode`, `nextLink`), the `std_ConstructArray(x, ctor, stride, n)`
  constructors (`elementCtor`, `widgetCursor`, `<thing>Window`).
- Most of this batch is constructors and wrappers where the object is the only meaningful value, so
  many functions got exactly one name.

## What was skipped and why

- 98 printed functions were deliberately left blank (recorded by the tool as "reviewed, nothing
  clear"): bodies truncated by bad-instruction data (`halt_baddata`), bodies reduced to a single
  `std_ConstructArray`/`func_00116AE0` call with no field evidence, or variables that are pure
  decompiler temporaries (`in_fpscr`, `unaff_rN`, coprocessor `in_crN`, concatenation splinters).
- Experienced multi-purpose temps (`iVar2`, `uVar4` reused as size / offset / object) were left
  unnamed rather than given one wrong role.
- Per-function confidence is 0.5-0.7 for nearly everything; 106 of the 146 answers are at
  confidence 0.45-0.55, and every name in those records does start with `maybe_` where the rule pass
  required it (the checker enforced this).
- No function was viewed twice; no callers beyond the batch view; no build or test run.
