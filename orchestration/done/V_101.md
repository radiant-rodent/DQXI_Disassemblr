# V_101 - local variable naming batch

Batch file: `orchestration/types/batches/V_101.json` (136 functions listed, 135 reached by the
batch tool). Output: `orchestration/types/out/V_101.json`.

## What was done

- Walked the batch with `python tools/batchview.py V_101 next` until it reported
  "nothing left to name", answering every printed chunk in one `--add` call.
- 135 functions recorded, 468 variable/parameter renames total.
- Final `python tools/batchview.py V_101 --check`: `135 answers, 0 problem(s)`.
- JSON syntax check of `out/V_101.json`: parses cleanly (135 entries).

Naming decisions worth recording:

- `self` was kept wherever it was already called `self`; only `argN` parameters that the body
  actually uses were renamed (e.g. `color` -> `eyePos` in `Gfx_SetCameraLookAt`, where the third
  argument is provably the eye position because the body builds `target - color`).
- The repeated `Gfx_GetContext` idiom was named consistently: the raw return followed by
  `*ptr` was called `gfxContext` / `deviceContext` and the pointed-to object `gfxDevice`, and the
  stack buffer handed to `Gfx_GetContext` was called `contextOut` (with `contextOut0/1/2` where
  three branches each have their own buffer). Where the rule pass already used `gfxContext` for
  the same variable, an alternative was picked instead of duplicating.
- Intrusive-list helpers `func_0010EBE4` / `func_001235A4` made the list heads and node links
  nameable (`layerListHead`, `deviceListHead`, `nodeLink`, `animCursor`, `nextCursor`,
  `prevLink`/`nextLink`).
- Matrix code: I only named components the body proves (forward/right/up basis rows of
  `Gfx_SetCameraMatrix` and `Ui_ScreenLayer_SetCameraMatrix`, the inverse-translation triple of
  `Gfx_Model_DrawOverlayPasses`). Generic float scratch was left alone rather than guessed.

## Skipped (recorded as "reviewed, nothing clear")

where the decompilation is truncated/damaged:

  `Gfx_TextureBinding_Dtor(Delete)`, `Gfx_MaterialSet_Release/Dtor`, `Model_ResourceSet_ReleaseCachedLists`,
  `Model_ResourceSet_DtorLists`, `Field_LevelData_Reset`-style one-liners, `Gfx_SceneSprite_DtorThunk`,
  `Anim_UpdateAndCheckFinished`, `Gfx_Movie_StartPlayback`,
  `maybe_Script_Table_DtorDelete` / `maybe_Script_Value_DtorDelete`, `maybe_Object_DtorMultipleBases`.
- `Ui_List_DestroyTwoPools`, `Ui_LayoutAnim_SetTwoValues`, `Ui_Widget_UpdateAnchorAndTransform`,
  `maybe_Ui_Screen_ConstructSubObjects`-adjacent helpers whose only locals were already named.
- Damaged or truncated bodies where any name would be a guess: `maybe_Ui_BattleTargetMarker_Update`,
  `maybe_Gfx_GetEntryByteProperty`, `maybe_Model_ApplyResourceAppearance` (199 lines cut off),
  `Ui_SceneFlow_UpdateFadeAndJobs` (52 lines cut off), `maybe_Ui_DrawList_InsertNodeAt1C`.
- In partially named functions I omitted the tokens whose meaning changes mid-function (reused
  registers such as `iVar1` in `Gfx_ShutdownPainters`, `iVar3` in `maybe_Event_ResetScreenFade`,
  `fVar7`/`fVar9` in `Model_Face_UpdateBlink`, the 24-float scratch block in
  `Model_SetFaceLookAtTarget`) rather than give them a name that is only right for half the body.
