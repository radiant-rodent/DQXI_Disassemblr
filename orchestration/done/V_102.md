Renamed locals and remaining `argN` parameters for the Ui-subsystem batch `V_102` (149 functions in
`orchestration/types/batches/V_102.json`), using the current readable C plus the merged field/global names.

- Output: `orchestration/types/out/V_102.json` (123 entries: 80 functions with names, 43 recorded as

  function again).

## What was renamed

Straightforward cases where the body/call/field names made the role clear, e.g.:

- hash-map lookups: `iVar1`/`iVar2` -> `targetKey`/`entryKey` (global key vs. entry vtable getter).
- refcount/destructor helpers: `iVar1`/`iVar2`/`iVar3` -> `refCount`, child pointers -> `childNode`,
  destructor stat counters -> `nextNode`/`prevNode`.
- UI layout slots: allocated node pointers -> `slotNode`, sizes -> `allocSize`, action tables ->
  `slotActionTable`, callbacks -> `slotAction`.
- Gfx node attach/detach: child counts -> `childCount`, handle maps -> `handleMap`, instances ->
  `effectInstance`.
- Sound stream: `f3578` -> `subStateIndex`, embedded object -> `embeddedObject`, callback ->
  `streamCallback`.
- Event command dispatcher: `commandCount`, `commandIndex`, `blockIndex`, `commandBlock`, `writeIndex`,
  `entryOffset`.

## Skipped and why

- 43 functions were omitted (nothing justifiable): pure wrappers with only already-named params
  (e.g. `Actor_Node_ShowVariantB..I`, `Gfx_Node_DeleteSize78`, `Sound_Emitter_Dtor`,
  `Ui_Window_CloseDefault`, `Field_Effect_BuildDescA/B`), functions with no locals, or damaged
  decompilation with `halt_baddata()`/`unaff_` registers where any name would be a guess
  (`maybe_Actor_Node_CheckBounds`, `maybe_Actor_Node_ResetVariant`, `maybe_Gfx_Vertex_DecodeNormals`,
  `maybe_Gfx_Texture_SwizzleBlock`, `Gfx_Render_SetViewportReg`).
- Vague `p1`/`p2`/`p3` parameters were left untouched where the body only forwards them (e.g.
  `Actor_Node_SetVisibleAll`, `Field_Gimmick_SetEmoteState`, `Ui_Layout_DisableSubNodes`).
- No name used confidence < 0.5, so no `maybe_` prefixes were needed; the lowest confidences (0.5-0.55)
  are on callbacks/context pointers inferred only from a single call site.

## Note on token names

Some batch variable tokens (e.g. `f48c`, `f30`, `f2c`, `f24`, `fe4`, `fc`, `f18`) differ from the
local identifier in the readable C (`cVar1`, `uVar7`, ...) because the readable tree was regenerated
after M2. Answers use the batch tokens, which the batch tool validates; the tool rejected readable-C
tokens (`cVar1`) as not in the batch, so batch tokens were used throughout.
