  or whose parameters are already nouns (`vtable`, `desc`, `entry`, `count`, `out`, `text`).
- Individual variables deliberately left unnamed:

    `in_ZR`, `in_cr0/1/9`, `extraout_r1*`) — no evidence of role;

    `arg2` in `Monster_Model_StartChildTweens` / `Monster_Model_SetBoundingBox`);

    `Ui_Message_BindTextPageParams`, `iVar7`/`uVar2`/`puVar8` in `Monster_Model_HandleStateEvent`,
    `iVar2`/`iVar5`/`puVar8` in `Monster_Model_SetStateById`, `fVar4`/`fVar5` in

    least one of the uses;

  - matrix words `f8c`/`f90`/`f94`/`f98` in `Field_ActorAction_UpdateTurnDirection` — the four

## Decisions recorded for the orchestrator

- `f28` in `Field_ActorAction_UpdateTurnDirection` is `self->targetActor`, but the rule pass had
  already claimed the token `targetActor` in that function, so it is `targetActorPtr`.
- Where the batch record's token differed from the current readable C (e.g. `f374` vs `uVar4`,
  `f58` vs `uVar7`, `f9c` vs `iVar4`), the batch-record token was used, since that is what the
  tool validates and what `M3_vars_merge` consumes.
- `maybe_` names were used only where the role is genuinely unproven: `maybe_ctorParam`,
  `maybe_sourceWord`, `maybe_secondaryFlag`.
