## What I skipped and why

27 functions got no names:

- 15 `std_StateSequence*_Delete` stubs: body is a single `func_0010F6CC(self)` tail call,
  only the already-named `self` parameter exists.
- 8 `maybe_Anim_CurveEvalCase_*` (0x006E972E, 0x006E9862, 0x006E9942, 0x006E9A4A,
  0x006E9D3E, 0x006E9E7A, 0x006EA076, 0x006EA582): the decompiled bodies are coprocessor

  register artifacts. Nothing in them identifies a value.
- 3 `Math_EaseCurve_Mode00/01/02`: the body is a bare `func_00672E44()` / `func_00673BC8()`
  call with the result dropped; only the already-named `from`/`to`/`dt`/`duration`
  parameters exist.
- `Str_WStringInsert`: the decompiler dropped everything after `func_00100B74(self + 4)`
  (noted in the readable C); only the already-named `self`/`pos`/`sub` parameters exist.

## Decisions worth recording

- In the `Anim_CurveSample_F3M*` / `F2M*` families the `fVarN` temporaries are reused for
  several unrelated values inside one function (e.g. `fVar13` is a scale, then -2.0f, then a
  bias). Naming them would have been wrong, so they were left unnamed; only the pointers,
  indices and flags with a single consistent role were named.
- `bVar*` booleans that are reused for two different comparisons (e.g. the capacity test
  then the `'9'` digit test in `maybe_Pack_CollectNumberedEntries`) were left unnamed rather
  than given a name that is only right for half the function.
- `LAB_006ef5f4` in `maybe_Container_UnlinkNodeSubtree` is a goto label, not a variable, and
  was left alone.
- `self` parameters were kept as `self` throughout; the only `argN` left in the batch was
  `arg3` in `Event_BroadcastSlotMask`, renamed `receiver` because it is the object whose
  vtable supplies the member-pointer thunk.
