## How names were chosen

The batch is the `Actor*` / `Gimmick*` / `Player*` / `IE*` / `PictureCard*` / `Effect2D*` block
around 0x001544C4–0x0015D958. The recurring shapes drove most of the naming:

* `arg1` bounds-checked against `f_430`/`f_434` with stride 0x10 → `actorIndex`; the same check
  on a second argument → `targetActorIndex`.
* `*(int *)(*(int *)(*gameWork + 8) + 0x6c)` → `fieldSystem`; `+0x58` → `eventContext`/`eventState`;
  `+0x70` → `eventManager`; `+0x74`/`+0x78` → `cameraController`/`camera2DController`;
  `+0x48` → the player object; `+0x50` → `weatherController`; `+0x94` → the audio object;
  `+0xb4` → `levelWork`; `+0x88` → `levelGroupTable`.
* handle values read from `actor+8` / `actor+0xc` and looked up in `g_actorAimLocatorHandleMap`,
  `g_actor2DHandleTable`, `g_actorAttachGadgetHandleMap` or
  `g_fieldEffect2DAttachActorHandleMap` → `locatorHandle` / `actorHandle` / `attachHandle` /
  `effectHandle`, with the map entry as `handleEntry` and the resolved object as
  `aimLocator` / `spriteActor` / `gadgetObject` / `effectObject`.
* the `uStack_NN`/`auStack_NN` slot whose address is passed to `Os_GetGameWork` / `Game_GetWork`
  → `workSlot` (numbered `workSlot2`, `workSlot3` when a function has several).
* `f_760`/`f_764` with stride 4 → the 2D effect array (`effectIndex`, `effectArrayBase`,
  `effectSlotPtr`).
* `f_39c`/`f_3a0` → the message table pointer and index (`textTable`, `entryIndex`).
* `argN` that is only forwarded to one callee was named after that callee's role
  (`Field_GadgetDef_FindByName` → `gadgetName`, `Field_Locator_FindByName` →
  `locatorName`, `Item_LookupRecord` → `itemId`, `Item_CountEquipped` → `memberIndex`/`itemId`).

## What I skipped, and why

* **Unused `argN`.** Most of these functions are declared with four `u32` parameters but only
  one or two are read. The unused ones (`arg2`/`arg3`/`arg4` in ~60 functions) were left as
  `argN` — there is nothing in the body to justify a name.
* **`arg4` in the `Os_GetGameWork(&uStack_NN)` pattern.** `arg4` is written into the stack slot
  whose address is then passed to `Os_GetGameWork`; that is a decompiler artifact, not a real
  parameter, so it was left alone (the slot itself became `workSlot`).
* **Register artifacts.** `in_r3`, `in_s0`, `in_fpscr` were left alone except where the value is
  genuinely used (`in_fpscr` → `fpscr` in the functions that read the rounding-mode bits,
  `in_s0` → `footStepVolume` in `ActorSetFootStepVolume`).
* **Already-correct tokens.** `result`, `i`, `j` were left as they are.
* **`BattleEndToTraining` (0x0015767C).** The body is a field-by-field copy of a 0x48-byte
  record into a local buffer. Only the buffer (`fieldData`), the source (`sourceData`), the
  game-work base and the one constant-written byte (`maybe_messageKind`) were named; the 20
  copied fields (`local_56`..`local_14`) have no visible meaning.
* **`MessageRegistActor` (0x00159B7C).** The decompilation is truncated (`halt_baddata`,
  "bad instruction data"), so only the allocation/UI-core locals were named.
* **`QuestCompletedMessage` (0x0015C314).** The message-parameter block's constant-initialised
  bytes (`local_30`..`local_22`) were left unnamed; only the block itself and the text pointer
  field were named.
* **`SetEmbarkartionInfo` (0x00158C28).** `local_28` and `local_24` are overwritten with
  unrelated values (a vtable pointer, then 0xff) inside a `g_vector3Zero` copy, so they were
  left alone; `local_2c` got `maybe_workSlot` because it doubles as the `Os_GetGameWork` slot.
* **`GetTalkPartyPageSize` / `GetTalkPartyYesIndex` / `IsYesNoOpenTalkParty`.** All three only
  call `Battle_ActionAnimTable_InitSlots()` and read a byte out of the result; the function
  names say "talk party" but the body shows a battle action anim table, so the local is
  `maybe_talkPartyTable` at confidence 0.4.
