# V_131 - local variable naming batch

## What I did

Named the local variables and remaining `argN` parameters of the 150 functions in
`orchestration/types/batches/V_131.json`, working only from `python3 tools/batchview.py V_131 next`
chunks and the merged field/global names already present in the readable C.

- 142 functions answered in `orchestration/types/out/V_131.json` (8 functions were already covered
  before this run started, hence 142 records for 150 functions).
- 902 names total: 161 parameters and 741 locals.
- 9 names carry the `maybe_` prefix (confidence below 0.5).
- 2 records are deliberately empty (`L69` 0x003934E8, `hnU` 0x00556C60): their bodies only touch
  `self` and never read `arg1`, so there was nothing to justify a name for.
- `python3 tools/batchview.py V_131 --check` reports `142 answers, 0 problem(s)`.
- The output file parses as JSON (verified with `json.load`).

## How names were chosen

- Field and global names from the M2 merge drove most decisions: `unit->targetUnit`-style fields,
  `g_actorAimLocatorHandleMap`, `g_actorAttachGadgetHandleMap`, `g_actor2DHandleTable`,
  `g_fieldBattleActionSequenceMap`, `g_partyMemberJoinTable`, `g_dataManager`,
  `g_fsCacheSetSingleton`, `g_uiCore`, `g_osGameWork`, `g_fxGlobalEmitterFrameState`.
- Recurring idioms were named consistently across the batch: the actor-entry lookup
  (`fieldWork->f_430` + index*0x10, bounds `f_434`) became `actorIndex` / `actorEntry` /
  `handleKey` / `handleMapEntry` / `actorHandle`; the packed-handle check (`>>6` tag, `&0x3f` slot)
  became `handleKey`; `Game_GetWork`/`Os_GetGameWork`/`Ui_GetCore` out-param buffers became
  `workBuf`/`workBuf2`; the party loops over `gameWork+0x27218` became `partyCount` /
  `memberIndex` / `memberCounter`.
- Where a token was reused for several unrelated objects in one function (very common in this
  batch), it got a deliberately vague name (`workPtr`, `entryPtr`, `slotPtr`) rather than a
  precise wrong one.

## What I skipped and why

- Parameters that are never read (`arg2`/`arg3`/`arg4` in most of the `Get*`/`Is*` wrappers) were
  left unnamed.
- Register artifacts (`in_r3`, `in_fpscr`, `in_s0`, `unaff_r4`..`unaff_r8`, `in_lr`,
  `extraout_r1`) were left unnamed except where the value is genuinely used (`in_s0` as
  `deltaTime`, `extraout_r1` as a modulo result).
- Stack scratch that is only a copy of a struct field with no readable consumer
  (`local_54`..`local_1c` in `BattleEndToDefaultField`, most `local_*` floats in `txf`) was left
  unnamed.
- Functions whose body ends in `halt_baddata` (`IsGimmickItemGetTimming`,
  `GetMiniGameIDFromGimmick`, `PartyTalk`) were named only up to the point where the recovered
  code is still meaningful.
- `XTC` (0x004318B4) and `txf` (0x005C73D8) are large and only partially recovered; only the
  variables whose role is visible in the printed part were named.
