Second naming pass (**refine**): re-examine the low-confidence `maybe_` functions listed in
`orchestration/naming/refine/batches/R_072.txt`.

Owns ONLY: `orchestration/naming/refine/out/R_072.json`. Do not edit any other file except
AGENT_LOG.md and your done report (skip rule 5's full test run; it does not apply to you).
The batches were generated by `tools/make_refine_batches.py` from the merged state after
`M1_merge_names`; do not regenerate them.

What changed since the first pass: the readable C now carries ~8,500 confident names, so most of
these functions have named callers, named callees, or named vtable siblings. Each batch is sorted
by a context score (highest first) and grouped by neighbourhood, so start at the top of the file:
those are the easiest wins.

For each function:

1. Read its readable C (path in column 4; context score in column 5). The file's doc header carries the **previous name**,
   the previous confidence, the original proposal batch and the previous evidence — start from
   that, do not re-derive everything from scratch.
2. Re-read the function **with its now-named neighbours**: open the readable files of its named
   callers/callees (grep the address or the current name across `decomp/readable`), check the
   vtable siblings and string literals listed in
   `orchestration/naming/refine/scores.jsonl` (field `neighbour_names`), and cross-check
   `symbols.json`, `symbols_recovered.json`, `decomp/native_names.json`, and any newer batches'
   outputs in `orchestration/naming/out/` / `orchestration/naming/refine/out/`. Squirrel scripts
   in `game_assets/scripts/` show what bound natives do from the game-logic side.
3. Decide, and be honest:
   - **confirm** — the new context supports the existing guess: drop the `maybe_` prefix, set
     confidence 0.5-0.7 (do not inflate because you feel safer; 0.7+ needs strong evidence).
   - **correct** — the new context shows the first guess was wrong or misleading: write a better
     honest name and say what the old name got wrong.
   - **keep_maybe** — still ambiguous: keep the `maybe_` name (you may still refine the name or
     summary if that makes them more accurate), and keep confidence < 0.5.

Write `orchestration/naming/refine/out/R_072.json`: a JSON array, one object per function:

```json
{"address":"0x0029E41C", "name":"Gfx_GetSharedCoreNode",
 "signature":"u32* Gfx_GetSharedCoreNode(u32 nodeKind, u32 resourceIndex)",
 "params":{"param_1":"nodeKind"},
 "summary":"one or two sentences: what and why",
 "confidence":0.6,
 "evidence":"what NEW evidence changed the verdict (named caller X calls it as ..., constant ...)",
 "previous_name":"maybe_Gfx_GetSharedCoreNode",
 "previous_confidence":0.40,
 "change":"confirmed"}
```

`change` is exactly one of `confirmed` | `corrected` | `kept_maybe`; `previous_name` must be the
name in the batch file; `change:"confirmed"` implies the new `name` equals `previous_name` minus
its `maybe_` prefix (unless you also fixed the wording, then it is `corrected`). Confidence
< 0.5 ⇒ the name must keep the `maybe_` prefix. Naming is unchanged:
`Subsystem_VerbNoun` PascalCase; generic library code `std_`/`nn_` style. Never invent; a correct
vague name (`Battle_UpdateUnitState`) beats a precise wrong one. Save progress to the JSON every
~25 functions so a resumed worker can continue. Cover **every** address in the batch.

If the first pass already got the guess right but the context is still weak, prefer
`kept_maybe` with an improved summary — a wrong confident name is worse than an honest `maybe_`.
