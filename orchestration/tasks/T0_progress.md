Build the human-facing progress tracker, modelled on AnyPS5's progress page
(github.com/boykopovar/AnyPS5 → boykopovar.github.io/AnyPS5/progress.html: plain tables of
Implemented / Total / % per library, a coverage-map SVG, SVG badges, raw progress.json, and a
history.html with one point per day, all generated by tools/progress.py).

Owns: `tools/progress.py`, `progress/` (output), `orchestration/dispatch.py` (only add a call to
progress.py after each task finishes — keep everything else as is).

Write `tools/progress.py` (stdlib only, no network, no external JS) that generates into `progress/`:
1. `progress.json` — all raw numbers below, plus timestamp.
2. `progress.html` — static, readable, dark/light friendly; sections:
   - Native code: per subsystem (use the subsystem grouping from `decomp/ghidra` /
     `decomp/by_subsystem` / `tools/organize_ghidra.py`): Total functions, Named (not FUN_/sub_/maybe_),
     Documented (has a summary comment), Matching C (replaced in `src/` and bit-matching), %.
     Also count naming proposals in `orchestration/naming/out/*.json`.
   - Scripts: CNUT total vs decompiled to readable `.nut`, vs recompile-verified.
   - Assets: per family (models, textures, layouts, tables, audio, maps, text) source count vs
     converted vs round-trip-editable (use `audit/*.json` manifests where present).
   - Editor features: checklist read from `progress/features.json` (create it with the features
     listed in orchestration/PLAN.md, status todo/partial/done).
   - Build health: last bit-match result + last test run (parse whatever logs/audit files exist).
   - Counting rules explained in a short "Notes" section, like AnyPS5.
3. `progress.svg` — coverage map: one small cell per native function, grouped in labelled blocks by
   subsystem, ordered by address; colours: grey unnamed, amber proposed, blue named, green
   documented, purple matching C. Legend included.
4. `badge-functions.svg`, `badge-assets.svg`, `badge-editor.svg` (shields style, percentage).
5. `history.jsonl` append one line per run (keep only the last line per calendar day) and
   `history.html` — inline SVG line chart over days for named-% / assets-% / editor-%.
6. `tasks.html` — live worker board: every task in `orchestration/tasks/` with lane, deps, state
   (from `orchestration/state.json`: pending/RUNNING/DONE/FAILED), start/end time and current
   model from `orchestration/logs/<id>.log` headers, last ~15 log lines for RUNNING tasks, and the
   done report (rendered as preformatted text) for finished ones. Auto-refresh with
   `<meta http-equiv="refresh" content="30">`. Link all pages to each other.
Everything must work when generated data is missing (show 0 / "not generated yet", never crash).
Then in `orchestration/dispatch.py`, after a task's state is saved (DONE or FAILED) and also once
when the dispatcher starts, run `python tools/progress.py` (ignore its failures).
Add `run_progress.bat` at repo root that regenerates and opens `progress\progress.html`.
Test: run it now, open the HTML files' text to sanity-check, and include the summary numbers in
your report. Also add a "Progress" link section to README.md (top).
